## Findings considered and rejected

- **Shared Supabase test stub fixture** (original finding #3): REJECTED after
  adversarial verification. The ~6 inline stubs are three structurally
  incompatible paradigms (stateful write-back object-literals, error-injecting
  per-table classes with embedded domain logic, and a read-only result stub),
  with divergent method surfaces (`.in()`/`.delete()`/`.upsert()` each appear in
  only one). The load-bearing value of each stub is its per-test embedded
  behavior, which cannot live in a shared fixture; extracting only the chainable
  no-op skeleton would be a forced, leaky abstraction. Not worth doing.
- **Refund via request_corrections privilege escalation**: REJECTED (upheld). The
  refund case re-checks `canRunRefund` (run_refunds / finance:manage) at
  `actions.ts:508` even when approval is suppressed; a request_corrections-only
  user is 403'd before any money moves.
- **donor_activities / donor_pledges cross-tenant IDOR**: REJECTED (upheld). The
  donor row is tenant-verified (404s on mismatch) and donor ids are UUID FKs, so
  a verified donor's activities/pledges cannot belong to another tenant. Adding
  `.eq("tenant_id")` would be defense-in-depth only; folded as an optional
  consistency add into plan 003.

# 0004. The proxy sets page scope; API scope headers must match a live membership

**Status:** Recorded on 2026-11-22 from code comments in `packages/auth`
([#2751](https://github.com/Asymmetric-al/core/issues/2751)). It describes the
code as it is and ratifies no product intent. Accepted platform intent is in
[`docs/adr/`](../../../../docs/adr/README.md).

## Context

A page and its calls to the app's own API must agree on the tenant and the assignment, the membership row used for the request. The browser can supply HTTP headers, so a header name does not establish who chose its value. A tenant page also has an address that remains visible after the proxy rewrites the request. Rendering the right data under the wrong address would still mislead the person using the page.

## Decisions

1. **Take the membership class from the app, not the client.** `forwardedRequestHeaders` in `packages/auth/middleware.ts` sets `ROLE_CLASS_HEADER` (`x-asym-role-class`, in `packages/auth/request-headers.ts`) from `AuthMiddlewareOptions.roleClass`, or removes it when unconfigured. Mission Control and Web Studio use staff, the missionary workspace uses missionary, and the donor portal uses donor. Pages and APIs that rely on this class must run through the proxy. The matchers exclude Next.js assets, certain root-level static filenames and, in admin and donor, `/maplibre/`. Routes that answer those paths, including the public donor site's catch-all, cannot trust the client's headers as scope. Cited: [plan 5.1][authority-plan], [plan 5.2][tenant-plan], [council round 2, AR7][reviews].
2. **Discard client-supplied page scope before stamping an admitted address.** `forwardedRequestHeaders` in `packages/auth/middleware.ts` removes the seven names in `PAGE_SCOPE_HEADERS` in `packages/auth/request-headers.ts`: tenant, assignment, address prefix, rewrite marker, the verified name's organization and generation, and the document's generation claim. Only after admitting a row for the tenant address does `authMiddleware` stamp those values on the rewritten request: a live database row for a real user, or the test assignment of an admitted end-to-end session. This makes `ADDRESS_PREFIX_HEADER` the admitted document prefix, including a staff suffix when present, rather than a client's choice. Cited: [plan 5.2][tenant-plan], [AL-2675](https://github.com/Asymmetric-al/core/issues/2675).
3. **Keep API tenant and assignment headers as proposals.** On the app's own API requests, `forwardedRequestHeaders` in `packages/auth/middleware.ts` preserves `TENANT_HEADER` and `ASSIGNMENT_HEADER` (and the generation claim, decision 8), the names in `API_SCOPE_CLAIM_HEADERS`. `packages/auth/request-headers.ts` re-exports both names from `@asym/database` so the fetch wrapper and data clients use the same names as the resolver. Unless server code passes its own values, `getAuthContext` in `packages/auth/context.ts` uses the tenant header to narrow the search and proposes the assignment for checking against the surface class and the caller's live rows, or an admitted end-to-end session's test assignments. The database reads that same assignment header through `tenant_guard.request_assignment_id()` and, for row-level security policies, `authz.request_assignment_id()`. Sending a row ID is not proof that the caller holds it. Cited: [plan 5.1][authority-plan], [plan 5.2][tenant-plan].
4. **Pass the original pathname to the layout.** `authMiddleware` in `packages/auth/middleware.ts` sets `x-asym-pathname` to the full tenant-addressed pathname, not the shorter rewrite target. A layout redirecting to sign-in can therefore send the visitor back to the same tenant address.
5. **Read only an exact address prefix.** `readAddressPrefix` in `packages/auth/tenant-server.ts` returns `ADDRESS_PREFIX_HEADER` only when parsing it produces precisely the same prefix: `/<tenant>` or `/<tenant>~<staff-sub-role>`, with no trailing path. Otherwise it returns `null`. Link builders and document-scope readers need the admitted prefix, not an arbitrary destination. Cited: [council round 1, A3][reviews].
6. **Refuse to render a document whose assignment disagrees with its address.** `readDocumentScope` in `packages/auth/tenant-server.ts` returns `null` without a valid prefix. With one, it requires an authenticated user ID and a resolved assignment. Both the context and the assignment must name the address's tenant; a staff suffix must equal the assignment's staff sub-role. A mismatch throws rather than displaying one tenant's page or one staff role's data under another's address. The resulting document scope carries the resolved user, tenant, assignment ID and prefix. Cited: [council round 1, A3][reviews].
7. **With the switch on, the verified name bounds every claim.** The proxy sets `NAME_TENANT_HEADER` (`x-asym-name-tenant`) from the lookup of the stamped host, never from the client; `getAuthContext` refuses a tenant claim, from the header or the caller, that differs from it, and `readDocumentScope` throws when the address names another organization. See [0015](0015-organization-from-the-verified-name.md).
8. **With the switch on, the name's generation is trusted and the document's is a claim.** The dashboards' middleware sets `NAME_GENERATION_HEADER` (`x-asym-name-generation`) beside the name from the lookup, never from the client; the document's own generation travels as `SCOPE_GENERATION_HEADER` (`x-asym-scope-generation`), which `PAGE_SCOPE_HEADERS` removes from pages and the tenant rewrite and `API_SCOPE_CLAIM_HEADERS` keeps on `/api/*` with the tenant and the assignment. Like them it is a proposal: `getAuthContext` refuses it, absent or different, as `generation_mismatch` before any row is read. See [0015](0015-organization-from-the-verified-name.md), decisions 12 to 14.

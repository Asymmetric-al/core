## Why

Donors need a coherent way to understand and manage their giving, documents, ministry connection and account choices. The current portal contains partial wiring, legacy financial/document assumptions and inconsistent state/route boundaries; the ratified Phase25 session now defines the complete donor outcomes and their permanent source-owned execution.

## What Changes

- Deliver the thirteen accepted donor jobs across Home, Ministry Updates, exact access/representation, history/filter/export, recurring giving, Wallet, receipts/statements, independent communication preferences, notifications, personal contact, newsletter requests, conditional pledges/matches and distinct DAF/IRA records.
- Adopt all Q01–Q29 corrected execution and Q30 scope acceptance, including final F01–F14 owner reconciliations and the confirmed primary donor-journey testing approach.
- **BREAKING:** replace reached raw financial/receipt/profile/default/route assumptions with qualified source contracts; preserve valid links and historical rights through the explicitly allowed migration paths, not generic fallback aliases.
- Preserve exact shared base-maia/Base UI and product-owned composition; distinguish invisible inapplicable rare features from safe explicit-route failures.
- Record supported-native Auth G01 and each finite provider/source/artifact/capacity qualification as mandatory owned activation conditions. Accepted product scope does not claim these conditions have passed.
- Publish one extensive, independently verifiable user-story specification with normative contracts, source traceability, design/testing and implementation tasks. No runtime implementation, provider actions or implementation-ticket graph is part of this change.

## Capabilities

### New Capabilities

- `donor-dashboard-depth`: the complete donor experience, exact per-surface rules, source read/command adoption, rare-record treatment, recovery and approved testing/activation requirements.

### Modified Capabilities

- `donation-lifecycle`: add precise Phase25 consumer behavior for source-owned history, annual measure, Wallet preference/removal, recurring entry and canonical document coverage, preserving existing server authority and money separation.
- `identity-and-access`: add exact donor task/representation/personal-contact/native social qualification and the bounded P28/P12 guest-origin newsletter-recipient access amendment, without changing the sole current authorization boundary.
- `crm-core`: add narrow admitted personal contact, own-employee matching and DAF-advisor projection adoption, plus P32's request-only external-enrollment exclusion, with source provenance and no new financial authority.

## Impact

The donor application consumes shared API, Auth, database/query, UI, communication, contribution, recurring, credit, document and public-content owners. The reached Phase3/4/6/7/9/10/12/13/14/16/17/18/19 contracts and Q25-only P28/P12 and P32 owner boundaries require explicitly listed narrow amendments. Phase22–24 specification branches remain proposed/unmerged dependencies until live evidence changes; their status is not rewritten as shipped. This PR directly amends the earlier active `add-donor-self-service` Wallet requirement, proposal and tasks to remove the incompatible provider-default and combined replacement/removal wording. Its annual official-document and separate optional Support overview boundaries remain valid; the Phase25 read-only DAF/match/IRA views neither replace that document purpose nor authorize recognition in official totals. The remaining sound predecessor boundaries are preserved.

Rollback/containment disables the affected new consumer or preparation/egress/issuance admission while maintaining canonical money, audit, already accepted reconciliation and currently permitted historical access. It never restores a raw bypass, changes a financial fact or deletes irreplaceable history. No new feature family, tax calculator, CRM, provider broker, generic notification/request engine or global dashboard builder is introduced.

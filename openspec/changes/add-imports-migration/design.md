# Design: Imports And Migration

## Context

Phase 30 moves an organization's records into Asym from a previous system, starting with SiteStacker, and supports careful everyday imports after go-live. The founder ratified Q1–Q21 (with every recorded amendment) in the [decision log](../../../docs/features/imports-migration/grill/decision-log.md); the glossary is [CONTEXT.md](../../../docs/features/imports-migration/CONTEXT.md) and the rationale lives in the Phase 30 ADRs 0001–0021. The canonical specification is [Phase 30 — Imports & Migration](../../../docs/prds/sitestacker-parity/phase-30-imports-migration.md). This design does not reopen any decision.

Current reality on `develop` (`629cb71dc`): nothing for imports is implemented, qualified or activated. There is no parser dependency, no import session, plan, run or staging table, no Data Tools route, navigation entry or capability, no Party, Household or custom-field tables, no money owner import commands, no private import storage and no malware scanning. Reusable pieces are `csvSafeCell` (ADR-0212), the workflow-orchestration dispatch ledger with Inngest, the `withTenant` tenant guard, Postgres 17 database tests in CI, Playwright with axe, and TanStack Table. Background jobs cannot yet carry a staff actor's authority. Contribution bulk batches, the private CSV encoder in contribution-batch results and the Payload import-export plugin are not precedents.

Binding predecessor constraints C1–C23 apply. The most load-bearing are: Phase 30 owns transport, staging, mappings, plans and import-run evidence while target owners own validation and acceptance (C1); no automatic donor merge (C2, ADR-0216); Phase 29 holds exact source bytes and custody (C11); holding a Phase 30 role never widens a target owner's authority and deferred jobs re-prove it (C16); restricted identities carry an alias and restricted export is blocked (C17); Legal Entity and currency are never inferred from Site and history never falls back to the Default Site (C19); imports never issue, release or stop an Issued Giving Address (C20); and the acceptance gate requires zero unintended send, enrollment, payment or public effect with published reversal and reconciliation procedures (C23).

## Goals

- Let a ministry complete a whole Switch itself, with Asym coaching by default and hands-on help only through approved Asym help access.
- Carry every committable family into its owner's protected home with exact provenance, or record a Visible exclusion; never commit a guess.
- Make imports and import reversals effect-dark: no sends, automations, welcomes, receipts or public effects (a Gift file's gifts are receipted and thanked only when a person posts them in Phase 15).
- Keep restricted people, sealed families and Asym-side values invisible to anyone who cannot already see them.
- Give staff one Data Tools home with one status vocabulary, resumable long jobs and an honest way back to every import.

## Non-Goals

The proposal's non-goals are controlling. In particular this design adds no AI mapping, no hosted importer, no new grid, no ad hoc task rows or email sender, no generic workflow engine, no Phase 28-named custody or run tables, and no route, DNS or publication authority.

## Decisions

### Architecture: one domain module, thin handlers

Phase 30 is one domain module in the shared API package (`packages/api`, working name `imports-migration`). It exposes server commands (create draft, upload, confirm header row, map columns and values, decide rows, plan, confirm, stop, resume, prepare and confirm import reversal, record Switch census answers, dispositions, attestations, reconciliation controls and sign-offs, place and release Legal hold) and server queries (Imports list, Import page, Switch task list, Remembered mappings, row outcomes, streamed downloads). Admin route handlers and server actions stay thin: they authenticate, call one command or query and render the result. Business database logic never lives in `apps/admin`.

The module calls target owners only through their typed import commands (owner ports): Phase 9 People and timeline commands, Phase 4 duplicate filing, Phase 11 field batch command, Phase 13 adoption command, Phase 15 draft-batch intake, Phase 16 recurring evidence, Phase 3 restriction import (O41), Phase 29 custody and Phase 23 content plans. Each Minimum Switch Kit owner port is a validate step and an apply step, so practice runs can check every kit row without writing (O28). Phase 30 never writes an owner's tables directly and never writes the legacy `donations` table.

### Durable jobs

Heavy work (parsing, checking, planning, committing, reversing, backfills, Practice copy builds and purges, the Retention sweep) runs as durable jobs on the existing workflow-orchestration dispatch ledger and Inngest.

- **Payloads carry identifiers only** (Tenant, import, chunk, plan revision), never file names, cell values or content.
- **Chunked claims.** Work is split into ordered chunks claimed with a lease and fencing token. A lost lease resumes from the last committed chunk. A chunk's writes and its row outcomes commit in one transaction.
- **Idempotency.** Every chunk apply carries a semantic key (import, plan revision, chunk) and each row's owner write is keyed by its Source Record Binding or row key, so retries and replays write nothing twice. An Exact repeat import recognizes prior work and writes nothing.
- **Per-batch authority re-check.** Before each chunk, the job re-derives the current Phase 12 permissions, clearance and grant expiry of the person it acts for (its recorded confirmer, reviewer or resumer) for the exact Tenant (C16). On loss it stops after the current chunk as Needs attention ("Stopped: {name} no longer has permission"); anyone holding the needed permissions may resume the rest under their own name.
- **One heavy job per ministry.** A lock on the Tenant (and on the Switch) admits one heavy job at a time; later confirmations wait as "Waiting to start, after {name}'s {import} (started {time})", start on their own when the lock frees, and re-check permissions, plan freshness and the Switch pause at start.
- **Halting.** Every Switch, run and import can be stopped after the current chunk; rows already saved stay saved.

### State machines

Import (People import, Gift file, Switch run):

| From                                                 | To                | Trigger                                                                                  |
| ---------------------------------------------------- | ----------------- | ---------------------------------------------------------------------------------------- |
| Draft                                                | Checking file     | upload completes                                                                         |
| Checking file                                        | Ready to review   | file parsed and planned                                                                  |
| Ready to review                                      | Waiting to start  | Confirm while another heavy job runs                                                     |
| Ready to review, Waiting to start                    | Importing         | Confirm, or the lock frees and the plan re-checks                                        |
| Importing                                            | Stopping          | Stop after this batch, or authority lost                                                 |
| Importing, Stopping                                  | Done              | every row imported or deliberately unchanged                                             |
| Importing, Stopping                                  | Needs attention   | anything left out, waiting, held or partly written                                       |
| Needs attention                                      | Importing         | resume of an import that stopped after a batch with unprocessed rows remaining           |
| Checking file, Waiting to start, Importing, Stopping | Stopped or Failed | nothing was written                                                                      |
| Draft, Ready to review                               | Discarded         | discarded by a person, or, for a People import or Gift file draft, unchanged for 14 days |

A plan older than 24 hours, or whose file changed, is rebuilt before Confirm. "Stopped" and "Failed" always mean nothing changed; anything partly written is Needs attention. Done and Discarded never change. The only path back to Importing is resuming an import that stopped after a batch with unprocessed rows remaining, by anyone holding every permission it needs, on the same import record, plan revision and idempotency records, never as a competing import. An import reversal never rewrites the import's status; it adds a separate second label: Reversal prepared → Reversing → Reversed or Partly reversed.

Held row: Held for review → Committed by reviewer, or Left out by reviewer, or "Left out: not reviewed in time" at the file's deletion date.

Import reversal record: Preparing → Prepared; Prepared → Expired (after 24 hours or at the window's end, whichever is first); Prepared → Running (on confirm); Running → Stopping → Stopped (resumable), Finished, Finished with items left as they are, or Failed (resumable). Each import is reversed at most once: at most one import reversal per import is ever confirmed, and a stopped or failed one resumes for its remaining items on the same record and is never replaced by a new one. At most one prepared page exists for an import at a time. No record returns to Prepared: an Expired page is never revived, but while the Import reversal window is open and no import reversal of that import has been confirmed, preparing again builds a new page. No confirm is accepted after the window. Reversal prepared · Reversing · Reversed · Partly reversed is the import's separate second label (see above), not the record's states.

Switch (logical states derived from recorded facts; the six recorded stages of the main document's decision 14): Preparing (readiness census, Practice runs, Practice copies, dispositions) → Scheduled (go/no-go passed; Switch Boundary, End date, pause limits and tail closure date recorded) → Committing (Switch Boundary passed; Editing pause attested; final Source Snapshot Manifest taken after the Boundary and sealed; readiness census retaken at the final export; everyday imports paused until go-live; families committed through owner commands in owner order: every Imported restriction before any Adopted email permission; Parties, contacts and suppression evidence commit and reconcile before Asym giving and exact continuity open, and Asym checkout opens only after a verified Phase 13 Settlement Account Binding exists; the remaining families then commit with no outward effect) → Switch live (go-live declared; the Switch stays Switch live while the Legacy Recurring Tail and its Legacy Tail Backfills run until the recorded tail closure date) → Switch closed (every legacy executor proved stopped, formally cut over or ended, and the Legacy Recurring Tail closed) → Decommission signed off. Before go-live a Switch may become Aborted: plans are discarded, committed rows stay invisible and any Practice copy is destroyed. An Aborted or inactive Switch is purged as Abandoned after 180 days without owner activity; when a Switch aborted before go-live is purged, its owners dispose of its never-visible committed rows (Q15 clause 5, amending Q1 clause 10). After go-live authority never returns to the source system.

### Data entities and invariants

Phase 30 owns these logical records, each scoped by Tenant and environment with same-scope keys:

- **Switch** with its source declaration (system, instance, Source profile), Switch lead, Switch Boundary, census answers, End date, pause limits, tail closure date, each history family's Coverage start, attestations and sign-offs. Together with import provenance, the Coverage starts form the history-coverage record that Phase 30 supplies to Phases 28, 33 and 35, whose first-gift and lapse logic reads it (Q13 clause 1, O3).
- **Source Snapshot Manifest** and its files: Phase 29 custody reference, per-file SHA-256 digest (including each file inside a ZIP), filter, exporter role, source version, export times and on-screen control counts.
- **Import** (People import, Gift file or Switch run), its plan revisions, mapping version, write-mode choices, decisions and row outcomes; Practice runs are recorded with their Switch and listed on the Switch tab.
- **Remembered mapping** per Tenant and source, versioned; **Field draft** keyed by draft ID.
- **Staged rows** per run, with source file, row and source ID.
- **Source Record Binding**: append-only link from (Tenant, environment, source system, installation or provider account, mode, record family, source ID, role) to an Asym target; follows Phase 4 survivors; tombstoned on erasure. Its carrier is the governed `crm_record_links` socket once O7's revoke and owner generalization land (D9).
- **Reconciliation report versions** and sign-offs; **Legacy Surface Dispositions**; **Email list dispositions** and **Consent adoption dispositions** (the Adopted email permissions themselves are owner records); **Old link list** rows handed to owners; **Legacy Tail Backfills**; **Import reversal records** and **Reversal prior values**; **Legal holds**, copy confirmations and the deletion log; Practice copy records and purge receipts.

Invariants:

- Every source row has exactly one outcome, and Review counts add up to the file's rows.
- Identity and convergence rest on Source Record Bindings, never on a file digest or manifest.
- Run evidence (counts, totals, digests, mapping versions, sign-offs, actors) holds no donor or supporter row content.
- An artifact without a Retention class cannot be stored.
- No Asym identity holds a Data Tools permission or makes a Switch decision, except that Asym's named legal role may place and release a Legal hold through its own Phase 12 legal-hold capability (O74), never a Data Tools permission, and without reading any content (Q15 clause 9).
- Imports and import reversals never send and never fire automations or field-change triggers. A Legacy Tail Backfill triggers no donor-facing message and no gift-triggered effect. An end it records produces exactly the signals an Asym recurring arrangement's end produces, while a move or a planned end at tail closure produces none (Q7 clauses 1 and 5, O32). A Gift file's gifts are receipted and thanked by Phase 15 only once a person posts the batch. Everyday imports and import reversals never grant consent, and a dated opt-in in an everyday import file is kept as evidence only. A Switch run creates consent only as Adopted email permissions for people on a moved list, under that list's published Consent adoption disposition, and only when Q9's evidence rules hold (the person had not withdrawn, the list was sent to within the 12 months before the Switch Boundary, and the evidence meets the rule for where the person lives). Each one starts on Adoption hold, and lists move only once O42 and O43 are live (Q9 clauses 3, 5 and 7; C10 as amended by Q9). Every Imported restriction commits restrict-only and before any Adopted email permission, and no import, Legacy Tail Backfill or import reversal lifts or loosens a restriction, opt-out or block (Q9 clause 1, Q18 clause 3).
- Logs and traces carry import identifiers only, never file names or values.

**Source basis** (resolves D16): the one declared source for a gift population and period (for example SiteStacker's transaction export, a Historic Giving copy, or a processor report). Exactly one source basis applies per population and period, with an overlap proof; Historic Giving ledger lines are never gifts.

### File custody

Phase 29 holds exact source bytes, custody, access and disposal under a new staff-migration custody profile defined with the Phase 29 owner (O19, O64, O70). Every file takes one File safety check before it is stored: quarantine, a malware scan Asym runs itself, a type allowlist and a size cap (import files follow their qualified profile's limits, such as the Size profile for staff-migration uploads; an imported attachment or photo is capped at 25 MB by default, with Phase 29 setting the profile), image re-encoding that removes location data, an opaque storage name, and download-only access. Uploads are resumable and direct to storage with determinate progress (O99); only the upload needs the page open. Raw files and staging stay in the Tenant's hosting region. Care and personnel files are never uploaded before their sealed home exists; only the digest of the Ministry-held sealed export is recorded.

### Downloads

Downloads are generated on demand and streamed within the request, never stored. They are text-typed and formula-safe through the one encoder (ADR-0212), limited to 1,000,000 rows (larger sets are filtered first) and audited by identifiers only. Your file's rows need Data Tools Manage, or the Prepare permission granted on its own, and contain only file cells and reasons. Downloads with Asym data need the ministry's existing export permission plus on-screen visibility and never include protected people. Asym never sends a raw export back; Verify your copy hashes the ministry's own files in the browser.

### Permissions

Phase 12 adds a Data Tools permission module with View, Manage and Admin levels (O102). Phase 30 mints dotted permission keys under Phase 12's rules; Replace and Clear, Reverse imports and Run the Switch are Phase 12 `sensitive` and appear only at Admin. Replace and Clear is two permissions, one offering Replace as a column's Write mode and the other the separate Clear action; a person holding only one of them is offered only that action. Individual permissions stay grantable for advanced cases (for example Prepare without Run). The Owner group holds Data Tools Admin; no other seed holds Data Tools; existing users get nothing on launch. Clearance is never part of a level. Money commits also need the money owner's permission (`finance:record_contribution` for a Gift file's Confirm), history correction keeps its own permission, and creating fields needs Phase 11's. Every page, action, projection and job chunk checks through the single Phase 12 decision point; there is no role-name gate and #2281's platform approval is not used.

### Visibility rule

A row's Asym-side facts (match, record, current values, outcome detail) show only to people who can see that record. The file's own cells show to Data Tools Manage holders and to a person granted Prepare on its own. Counts are whole-file and identical for everyone. A Switch real export stays restricted until a cleared member holding Run the Switch narrows it; until then uncleared viewers, helpers and Asym help access see headers, counts and validation summaries only, and restricted people only by alias. In a Switch real export, source fund names show only to cleared members, before and after narrowing; everyone else sees the same counts without the names. Another ministry's import, or an unknown import identifier, is not found for Data Tools holders, while people without Data Tools access see the same no-access page at every Data Tools address, whether or not the import exists. Rows matching someone the preparer cannot see, a staff member or someone marked deceased are Held for review with one wording and never change the counts. Hide values hides every value for the session and never reveals more.

### Mission Control composition

Data Tools is one System-group sidebar entry next to Admin in `apps/admin`, with tabs that each have their own address (Imports, Switch, Remembered mappings) and no sidebar children. Its visibility, and Cmd-K's, come from one server-side capability decision (O98). Shortcuts ("Import people" on the People list, O93; "Upload a Gift file" in Contributions, O94) open the same Data Tools flow with the kind chosen. A shortcut appears only where the flow works for that person and is never a dead button or disabled without a written reason; between the Switch Boundary and go-live, everyday import start actions read "Paused during the Switch, from {Boundary} until go-live." Pages use `PageShell`, a segment error boundary that keeps the import's identity, per-tenant status streamed and never cached (an intentional Stream decision under Cache Components), and polling while active that pauses when the tab is hidden. Shared components (stepper, file input with drop zone and resumable transfer, live-region announcer, task-list composition) are added to `packages/ui` in exact `base-maia`; Phase 15's accessible editable grid fixes cells and `DataTableResponsive` renders lists. Finished and Needs attention notices go through Phase 17 staff notifications (O96); imports that need a person appear in the Tasks Hub through a registered Source work projection (ADR-0183, O97). The Eve panel is not shown on Data Tools pages in v1.

### Effects suppression

Owner writes made by a People import, a Switch run, a Legacy Tail Backfill or an import reversal are marked import-origin. Import-origin creates apply no field defaults, and these writes fire no welcome, goodbye, automation, field-change trigger or send, with one exception: an end a Legacy Tail Backfill records (source stop evidence, or a stop staff confirm in the backfill review) produces exactly the signals an Asym recurring arrangement's end produces, while a move or a planned end at tail closure produces none. Nothing a Legacy Tail Backfill brings in, including schedule changes, stops and contact facts, triggers a donor-facing message (Q7 clauses 1 and 5, Q12 clause 6, Q18 clause 8, O32, O76, O78, O89). Switch history and Legacy Tail Backfill money, with its refunds, chargebacks and corrections, is written by owner commands with Recorded outside Asym. Each owner derives its existing gate from that fact at write time, and the writing command sets `historical=true` on resulting events, so no receipt, acknowledgment, donor message, staff or missionary task or notice, welcome, tribute letter, milestone or other gift-triggered effect follows, while the gifts still count in every total (Q4 clause 1, Q7 clause 1, O1, O33, O34). A Gift file is the exception: its rows are never import-origin and never carry Recorded outside Asym or `historical=true`. Phase 30 only hands them to Phase 15 as file-origin draft gift batches of ordinary current gifts first recorded in Asym, under the batch's own human gate, and creating those draft batches sends nothing. Once a person posts a batch in Contributions, Phase 15 issues receipts and thank-yous under Phase 7/14 rules (Q12 clauses 6–7, the Q12 amendment to Q4, O50, ADR-IM-012). Legacy charges on a connected payment account that Asym did not create are never Asym-recorded gifts (O35). The Practice environment captures all mail in a Practice outbox and refuses provider keys, domains, webhooks, settlement bindings, integrations, AI and tax-document issuers.

### Activation sequencing and kill switches

- Data Tools is off and default-deny until O102 ships, and no import kind is switched on for any ministry until the other release gates also pass: O103 and O104, the navigation decision (O98), resumable upload through the File safety check (O99), the Retention classes and sweep (O70, O71), authenticated admin accessibility checks (O101) and the carrier that lets background jobs act with a staff actor's authority under Phase 12's rules. The entry appears only when at least one import kind is switched on for that ministry; each kind (People import, Gift file, Switch) has its own kill switch. Turning a kind off does not turn off import reversal: Prepare reversal stays available within its Import reversal window. Import reversal prepare and confirm have their own off switch, per ministry or globally; while it is off, no import reversal page can be prepared or confirmed, and a running import reversal stops after its current chunk and stays resumable for its remaining items.
- People imports need O47, O51, O78, O87 and O88 (with prior-value capture in the same release), O89 and O93 ahead of activation; Gift files need O50, O90 and O94. Phase 17 staff notices (O96) are required only before the first Switch; until they exist, the Imports list and the Switch task list are the way back to anything waiting.
- A Switch's Start action appears only to holders of Run the Switch, only when the Switch kind is switched on for the ministry, and only when Asym's preconditions hold (Q2, Q6, Q20): an Approved Practice environment (O29, O30); O31's pre-real-data fixes (the Stripe platform-key fallback and any-tenant USD lane removed, the hard-coded tenant removed, and the CMS tenant resolver honouring `isActive`), which must be live before any real export enters any environment; the Phase 29 staff-migration custody profile and scanner; the Approved-environment read-back including the `super_admin` check; the complete retained-state census (D13); and Phase 17 staff notices (O96).
- No real export enters any environment until the rest of Q2's gates also hold: a signed agreement with data-processing terms, the ministry's own Tenant with the single-installation checks done, restricted-by-default classification and a fresh readiness census answered on the started Switch.
- O41 and O47 do not gate Start. Scheduling a started Switch additionally needs every Minimum Switch Kit family committable through its owner's typed import command with its no-write check (O28), every other family committable or an accepted Visible exclusion, a Phase 16 external read-only target for every legacy recurring cohort, a complete readiness census, any residual system declared and accepted in writing, a Source profile status that permits it (no Switch while the profile is Unavailable, and only its design partner's Switch while it is Pilot-qualified; Q2 clause 2, Q3 clause 5), O41 and O47. Go/no-go also needs the latest Practice copy to be built on the current mapping version and production release with no unresolved mismatches; each copy's dress rehearsal times every family, including one forced interruption and resume, and lists each row the plan accepted but the commit rejected as a mismatch (Q6 clause 2).
- O26 is needed only before any Asym help access, and O27 and O105 only before an outside helper is added, since a ministry can complete a whole Switch itself (Q5 clauses 2, 3 and 5; Q20 clause 12).
- No Switch giving history commits until the Phase 13 and Phase 7 owner commands that write Recorded outside Asym exist (O22, O53), the prototype receipt link and text statement (#1031) are retired and O60's Reader readiness check passes. Gift files never carry Recorded outside Asym and do not wait for this gate (Q12 clause 7).
- No Legacy Tail Backfill commits until the post-boundary money command that also writes Recorded outside Asym (O13) exists and O33, O34 and the zero-donor-messages test pass. No Legacy Tail Backfill money commits until the prototype portal receipt link and text statement (#1031) are retired, as for Switch giving history (Q4 clause 7, O24). No Switch for a ministry with recurring giving is offered until O12, O31 and O36–O40 are live. Lists move to Asym only once O42 and O43 are live; until then they are kept or retired, so adoption never blocks a Switch.
- Notes, interactions, files, applications and care commit only after D40–D49 are fixed, O68's Reader readiness passes and counsel has answered the family's questions; these are not Minimum Switch Kit families, so a Switch never waits for them.
- A family becomes importable only when its import reversal row is published and its owner correction link works (C23).
- The Retention sweep runs in report-only mode before deletion is enabled; pausing it is audited.

## Test Seams

Three seams are confirmed. Existing seams are preferred and no new browser harness is added.

1. **Primary seam: the Phase 30 server commands and queries.** The Phase 30 domain module's public commands and queries in `packages/api`, exercised as Vitest acceptance suites following the repository's per-issue acceptance-suite pattern, with a fixed clock and each owner module behind its published interface: the owner ports (validate and apply) and Phase 29's custody and scanner port. A controlled double that honours the published contract stands in only for an owner command that does not exist yet, and the dependent kind stays off until the real owner command passes the same suite. This is the primary seam for plans, row outcomes, write modes, Held for review, import reversal checks, status and Switch task-list derivation, retention dates and effect suppression.
2. **Real database seam.** The same commands against migrated local Supabase with real roles, following the existing realstack acceptance pattern (`bun run test:acceptance`, Postgres 17 in CI): RLS and grants (no client grants on any Phase 30 table; anonymous and authenticated roles denied; Reversal prior values unreachable through any view or remote procedure), structural Tenant scope, constraints (at most one confirmed import reversal per import and at most one prepared page per import at a time, one outcome per row, tenant-aware composite keys, constrained states), forward-only states that a direct update cannot bypass, append-only bindings, idempotent chunk claims, per-batch authority re-check, one heavy job per ministry, Legal hold, Retention sweep, hostile cross-Tenant cases and the two-session races (two editors on one draft, two Confirms, two held-row reviewers, a plan rebuilt during Confirm, the Switch Boundary reached while an import is Waiting to start, and an import reversal racing a later edit).
3. **Journey seam: Mission Control Data Tools in Playwright.** Authenticated Playwright journeys through the admin app under the admin configuration (the end-to-end tracer, which is a People import from the People list shortcut through results and Prepare reversal; a Gift file from Contributions to draft gift batches; the Imports list as the way back; the Switch task list; held-row review; the no-access and follow-only pages; Hide values; the segment error boundary keeping the import's identity; polite announcements and the lasting banner) with axe at 1280, 768 and 320 CSS px and a keyboard-only pass (O101), using injected provider adapters and the outbox to prove zero outward effects.

## Risks And Trade-offs

- **Owner dependencies stall release.** Many families depend on unbuilt owner commands. Mitigation: per-kind kill switches and family-level gates; People imports can ship before money families; nothing waits on optional families.
- **Restricted data exposure through previews.** Mitigation: one visibility rule enforced server-side, Held for review with uniform wording, Narrowing for Switch exports, Hide values, alias rendering and identifier-only logs.
- **Long jobs outliving authority.** Mitigation: per-chunk authority re-check and resumable stop.
- **Template path too hard for ministries.** Mitigation: Remembered mappings, clear validation messages and the Q3 template monitor; a named profile only with its own design partner.
- **Tail attrition and double charges.** Mitigation: stop evidence before first Asym charge, To-cancel list, End date offer rule and measured attrition at the first Switch.
- **Retention drift.** Mitigation: classes on every artifact, report-only sweep first, verified deletions and a published schedule.
- **Scale.** Mitigation: Size profile limits, chunked durable jobs, streaming downloads, and limits confirmed by the production-shaped practice run.

## Migration And Rollout Plan

1. Land read models, Retention classes, structural constraints and the deletion log before any writer; keep every kind switched off.
2. Ship the Data Tools permission module (O102) and the shell entry with no kind enabled; verify no-access behavior.
3. Enable People imports for qualified Tenants once their owner gates pass, including the scoped restriction-import command; then Gift files; then the Switch, whose Start action appears only behind its Start preconditions (including the Approved Practice environment) and which is scheduled only once its scheduling gates pass.
4. Run the first Switch with a named design partner on pilot terms; record attrition, mapping measures and pause timings; recalibrate defaults only through recorded profile changes.
5. Turning a kind off stops new starts and hides its entry points; running jobs stop after their current chunk as Needs attention and can be resumed by an eligible person, under their own name, once the kind is switched back on. Every import record stays readable, Prepare reversal stays available within its Import reversal window, and every committed fact, binding, restriction, receipt and audit record is kept. Turning import reversal prepare and confirm off, per ministry or globally, stops new prepares and confirms; a running import reversal stops after its current chunk and stays resumable, and nothing committed is deleted. Rollout is roll-forward only: recovery is forward through owner corrections.

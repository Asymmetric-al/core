# Change: Phase 27 donor-development specification

## Why

Staff need one source-backed way to cultivate ministry partnerships, make relevant financial/nonfinancial Requests, coordinate appeals and follow through. Existing CRM surfaces do not establish these complete behaviors. The founder selected and ratified D1–D30 in the Phase 27 grill session, explicitly invoked `/to-spec`, and confirmed the real integrated testing seam.

## What Changes

- Formalize the complete partnership, stage-list, Request/review, appeal/intake, context, giving-pattern and assignment-policy contracts without reopening settled decisions.
- Reconcile P3/P9/P12/P15, roadmap/P28 and optional DON-15 owner language within the ratified scope.
- Add the generated donor-development behavioral projection and explicit scoped owner deltas.
- Record independently verifiable stories, exact acceptance, preserved operating controls, source trace and an unchecked delivery/proof plan.
- Publish one implementation-ready specification issue using the configured ready-for-agent label mapping. No implementation-ticket graph is created.

## Impact

Mission Control is primary. P28 consumes the same source through its qualified projection; P9 owns CRM, interactions, assignments and shared tasks; P12 owns permissions; finance/commitment/recognition/content/dispatch/document owners retain their facts. Future implementation affects the shared API/database/auth/UI boundaries and native source jobs. This change itself edits documentation and its deterministic generation/validation only.

The canonical package is [Phase 27](../../../docs/prds/sitestacker-parity/phase-27-donor-development.md). Stories are authored in its story registry, requirements/acceptance in normative volumes, and OpenSpec/trace indices are generated. Publication does not prove implementation or activation.

## Gates and Non-goals

E7 campaign temporal attribution and C-01 posted-correction approval remain explicit upstream owner-policy gates. Affected lanes cannot be guessed or declared complete; unrelated qualified work remains usable. Provider/runtime, migration, accessibility, capacity and pilot gates remain required. No feature code, production change, donor contact, automation activation, new CRM/task/finance store, compulsory missionary reporting or wealth scoring is authorized by this task.

## Rollback

Documentation corrections use a new explicit spec version and coordinated regeneration/publication. Retain dated evidence and original decisions. Future runtime disable/rollback must fence new effects while preserving committed history, physical handling, manual protections and source recovery; destructive schema downgrade is prohibited. Keep this change active until implementation has actually shipped and qualified.

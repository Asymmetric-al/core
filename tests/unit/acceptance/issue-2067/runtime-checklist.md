Run the real-stack test (skipped without the env var). CI Integration (ruling 7) uses the `postgres:15` service with `scripts/sql/supabase-compat-bootstrap.sql` and `scripts/verify/supabase-migrations.mjs`, not `supabase start`; locally use any disposable Postgres 15+ prepared the same way:

```sh
DOCUMENT_CUTOVER_IT_ADMIN_DATABASE_URL=postgresql://postgres:<local-db-password>@127.0.0.1:5432/<disposable-db> \
  bun x vitest run tests/unit/acceptance/issue-2067/reader-role.integration.acceptance.test.ts
```

It needs `psql` on PATH (or `PSQL_BIN`; CI installs it with `scripts/github/install-postgresql-client.sh`) and an admin role that can `ALTER ROLE document_cutover_reader`, `SET ROLE anon / authenticated / service_role`, and owns `public.pdf_templates`. It sets a random test-only password, logs in as the reader over TCP, and restores `NOLOGIN PASSWORD NULL` afterwards. Its row-level-security, probe-object and DO-block checks run inside rolled-back transactions.

How the static and integration halves of ruling 10 agree: the static checks require exactly the statements that produce the ACLs the integration test reads. A per-function `REVOKE … FROM PUBLIC, anon, authenticated, service_role` after `CREATE FUNCTION` removes the built-in PUBLIC `EXECUTE`, grants only to the reader add only the reader, and with no other schema grant only the owner and reader remain in `nspacl`. On box Postgres 17, three deliberate breakages each turned both halves red: PUBLIC `EXECUTE` left on one function, schema `USAGE` granted to anon, and an extra function with no revokes. The one deliberate gap: a migration that uses `REVOKE … ON ALL FUNCTIONS IN SCHEMA` produces correct ACLs (integration green) but fails the static check, because the ruling asks for an explicit revoke per function. (A per-schema `ALTER DEFAULT PRIVILEGES … REVOKE … FROM PUBLIC` is a Postgres no-op, which is why ruling 10 went to option (b).)

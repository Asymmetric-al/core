# Protected Paths

Map of repository paths that must not be hand-edited or that a gate protects.
Each row names the evidence that controls it. Live GitHub branch-protection
state lives in [`docs/ci.md`](../ci.md#branch-protection); reverify it before a
platform-sensitive decision.

Protection kinds:

- **Documented** — a repo file states the rule.
- **Repository-enforced** — a repo-owned script, hook, test or lint rule blocks
  violations. The row says where it runs (CI, `ci:preflight`, local hook, or
  manual command only).
- **Platform-enforced** — GitHub or Vercel enforces it (claimed only with
  direct platform evidence).
- **Unknown** — protection plausibly exists but is not observable here.

## Hash-pinned review ledgers

These ledgers record sha256 hashes of the source or proof files they cite.
Editing a cited file, even a comment, makes the ledger entry stale and fails
its gate. Update the ledger entry in the same change after re-reviewing the
claim; never edit the hash alone to make the gate pass.

| Ledger                                         | Pinned field                                                | Enforced by                                                        | Kind                                                                   |
| ---------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `tooling/shadcn/upstream-review-baseline.json` | `proofSources[].sha256`                                     | `scripts/verify/shadcn-diff.mjs` via `verify:shadcn-diff`          | Repository-enforced (`ci:preflight`)                                   |
| `docs/qa/react-doctor/exceptions.json`         | `sourceFileHash`, `sourceContextHash`, `evidenceFileHashes` | `scripts/react-doctor-ledger.mjs` via `bun run react-doctor:check` | Repository-enforced (manual command only; not in CI or `ci:preflight`) |

| Path pattern                                        | Protection                                                                                                                                                              | Controlling evidence                                                                                                                                                                                                                                                                                | Kind                                         |

| `apps/*/app/api/**/route.ts`                        | Must be thin re-exports; must not import `@asym/database/supabase/*`, `@supabase/ssr`, `@supabase/supabase-js` directly                                                 | [`data-access-boundary.md`](../guides/architecture/data-access-boundary.md#rule) "Rule"; `scripts/verify/data-boundary-check.mjs` (`verify:data-boundary`, CI and `ci:preflight`); root `eslint.config.mjs` `no-restricted-imports` applies only to editor and root-config runs, not `bun run lint` | Documented + Repository-enforced (CI script) |
| `apps/`, `packages/`, `scripts/` and `.env.example` | Must not restore Twenty clients (`packages/api/src/crm/client/*`, `@asym/api/crm/client`) or reference retired `TWENTY_*`, `NEXT_PUBLIC_TWENTY_*` or `CRM_SYNC_*` names | `scripts/verify/data-boundary-check.mjs` (`RETIRED_TWENTY_RUNTIME_MARKERS`)                                                                                                                                                                                                                         | Documented + Repository-enforced (CI script) |

The Twenty check is a marker scan, not proof of absence. Approved exceptions to
the Supabase-import rule are listed under "Approved Exceptions" in
[`data-access-boundary.md`](../guides/architecture/data-access-boundary.md#approved-exceptions).
A new exception goes in that table and, if under `apps/*/app/api/`, is also
excluded in `data-boundary-check.mjs`.

## Branch / push guards

| Path / target               | Protection                                                                                                                           | Controlling evidence                                                       | Kind                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Local pushes                | `bun run ci:preflight` (`--full` when a push targets `production`); no commit identity check                                         | `.husky/pre-push` → `scripts/git/pre-push.mjs`; `docs/ci.md`               | Repository-enforced (local hook; bypassed by `--no-verify`) |
| Direct push to `production` | Allowed only through `bun run release:production` or a true emergency with a concrete reason in `ASYM_PRODUCTION_PUSH_BYPASS_REASON` | `scripts/git/pre-push-guard.mjs`                                           | Repository-enforced (local hook)                            |
| `develop` / `production`    | Required checks, force-push and deletion settings                                                                                    | [`docs/ci.md`](../ci.md#branch-protection); live GitHub settings           | Platform-enforced                                           |
| Agent commands on GitHub    | Only an active organization member with Core Write or higher, or an approved App identity, can direct agent commands                 | [`docs/ops/github-access.md`](../ops/github-access.md); Eve GitHub channel | Webhook boundary                                            |

## Platform evidence limits

- [`docs/ci.md`](../ci.md#branch-protection) owns the dated GitHub
  branch-protection inventory. Reverify it before a platform-sensitive decision.
- Vercel project protection (deployment approvals, protected env scopes) is not
  observable here; only repo-side `vercel.json` gating and
  `verify:vercel-build-controls` are.

# Env Var Audit

## 1. Summary

- CI jobs, gates and required checks are described in [`docs/ci.md`](./ci.md); this audit covers only how they consume environment variables.
- `@asym/env` (`packages/env/`) validates startup environment variables at runtime via `@t3-oss/env-nextjs` + `zod`.
- `SKIP_ENV_VALIDATION=1` bypasses env validation in CI `build`, `smoke`, and `test-e2e` jobs.
- `turbo.json` declares build env inputs, and `.env.local` was not inspected to avoid reading local secrets.

## 3. CI-Specific Findings

### `ci.yml`

- Jobs that run Turbo inject `TURBO_TOKEN` (GitHub secret) and `TURBO_TEAM` (GitHub variable) for Turborepo remote cache, and restore a local `.turbo/` cache with `actions/cache`.
- The `build` job injects `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from GitHub secrets plus `SKIP_ENV_VALIDATION=1`, so `@asym/env` does not throw when the secrets are empty on fork PRs. `test-unit` uses stub Supabase values.

### `ci-integration.yml`

- `migrate` runs against a Postgres service container; `DATABASE_URL` and `PAYLOAD_DATABASE_URI` are job-level stub connection strings, not secrets.
- `smoke`, `test-e2e-smoke` and `instant-nav` use stub Supabase values (`https://example.supabase.co`, `example-anon-key`) and `SKIP_ENV_VALIDATION=1`. The full `test-e2e` job takes `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from repository secrets and switches to the stub values (plus `ASYM_E2E_REQUIRE_HERMETIC_SUPABASE=1`) only for non-production pull requests, pushes to `develop` and non-production manual runs. E2E jobs set `PLAYWRIGHT_BASE_URL=http://127.0.0.1:3005`.

### Turbo build env inputs

- `turbo.json` `build.env` keys hash into the Turborepo cache key ([task `env`](https://turborepo.dev/docs/reference/configuration#env)). They are limited to variables that can affect compiled Next.js or workspace output or Payload build-time behavior: `NODE_ENV`, `CORE_EVE_BUILD_MODE`, `NEXT_PUBLIC_*`, `GOOGLE_SITE_VERIFICATION`, `BING_SITE_VERIFICATION`, `SUPABASE_*`, `PAYLOAD_SECRET`, `DATABASE_URL`, `PAYLOAD_DATABASE_URI`, `PAYLOAD_DATABASE_POOL_MAX`, `DONOR_APP_URL`, `SKIP_ENV_VALIDATION`, `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, `RESEND_ENCRYPTION_KEY`, `SENTRY_AUTH_TOKEN`, `SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_RELEASE`, `CLOUDINARY_API_SECRET`, `ALLOW_DEMO_ACCOUNTS` and `DEMO_ONLY_LOGIN`. `turbo.json` is the source of truth; `globalEnv` adds `VERCEL*` variables to every task hash.
- Runtime-only secrets (for example `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `CRON_SECRET`, `DOCRAPTOR_API_KEY`) stay out of `build.env` so changing them does not bust the build cache for unchanged source.
- Playwright, E2E, demo-credential and generic CI flags (`PLAYWRIGHT_*`, `E2E_*`, demo account credentials under `DEMO_*`, `CI`, `ASYM_USE_CI_ENV_DEFAULTS`) are excluded (the demo-mode switches `DEMO_ONLY_LOGIN` and `ALLOW_DEMO_ACCOUNTS` are the listed exceptions): they are test or dev-server concerns and caused unrelated cache invalidation when listed.

### Playwright config

- `playwright.config.ts` reads `CI`, `PLAYWRIGHT_BASE_URL`, and `PLAYWRIGHT_PORT` at config evaluation time.
- **`E2E_AUTH_BYPASS` + per-app E2E cookies:** When bypass is enabled (Playwright sets this alongside `ASYM_USE_CI_ENV_DEFAULTS`), `POST /api/auth/demo-account` issues an httpOnly cookie named by app surface (`asym_e2e_auth_donor` / `asym_e2e_auth_admin` / `asym_e2e_auth_missionary`, derived from the request `Host` port) instead of a Supabase session. `packages/auth/context.ts` (`getAuthContext`) and `packages/auth/middleware.ts` read the cookie that matches the current host so donor Playwright sessions do not authenticate the admin app on another localhost port. Optional **`ASYM_E2E_AUTH_SURFACE`** (`donor` \| `admin` \| `missionary`) is a fallback when the URL has no port (e.g. some unit tests). Production: bypass is off when `NODE_ENV === "production"`.
- **`E2E_AUTH_SECRET` (optional — auto-fallback for safe datasources; min 16 chars when set) + `E2E_AUTH_ALLOWED_SUPABASE_REFS` (optional) — D22 non-prod isolation floor.** The bypass cookie is HMAC-SHA256 signed (`base64url(payload).base64url(sig)`, with a signed 1-hour `exp`); `packages/auth/e2e-auth.ts` refuses to mint an unsigned cookie and rejects any unsigned/forged/expired cookie. Verification uses Web Crypto (`crypto.subtle.verify`, constant-time, edge-safe). **Zero-config by default:** when `E2E_AUTH_SECRET` is unset, a built-in **public** fallback key is used automatically for datasources that cannot hold real data — loopback, the non-resolving `example.supabase.co` placeholder, or no datasource — so local dev and the placeholder CI job need no secret setup. For any **real** remote Supabase project the fallback does not apply: `E2E_AUTH_SECRET` must be set (an explicit, confidential ≥16-char key) or mint/verify fail closed. Independently, the bypass is bound to **datasource identity** (not `NODE_ENV`, which is non-`production` on staging/preview too): every bypass-grant site (`context.ts`, `middleware.ts`, `apps/admin/.../supabase-strategy.ts`) calls `assertSupabaseDatasourceAllowedForE2EBypass`, which logs and throws unless `NEXT_PUBLIC_SUPABASE_URL` is loopback, the `example.supabase.co` placeholder, unconfigured, or a project ref/hostname listed in **`E2E_AUTH_ALLOWED_SUPABASE_REFS`** (comma-separated). Production project refs and their read replicas are never allowlisted; the ref regex requires a letters-only Supabase TLD so a lookalike host (`myref.supabase.evil.com`) cannot spoof a ref. `packages/env/src/schema.ts` additionally throws if `E2E_AUTH_BYPASS` is truthy on a protected deployment, and enforces the 16-char secret minimum.
  - **Fail-fast demo endpoint.** `POST /api/auth/demo-account` refuses to mint (`503 DEMO_E2E_BYPASS_MISCONFIGURED`) and `GET` reports the roles unavailable (with a `reason`) whenever no signing key is available (a real datasource with no `E2E_AUTH_SECRET`) or the datasource is not allowlisted — so a misconfigured bypass surfaces at the availability probe / login click instead of as a later middleware `500`.
  - **CI/dev wiring (zero-config for the common paths).** `scripts/run-with-ci-env.mjs`, `scripts/dev/setup-mission-control-cloud.mjs`, and the placeholder E2E CI job (`test-e2e-smoke`) set only `E2E_AUTH_BYPASS=true` + `NEXT_PUBLIC_SUPABASE_URL=https://example.supabase.co` — no secret/allowlist, because the placeholder is a non-confidential datasource (fallback key + implicit allowlist). The internal hosted-demo E2E job (`test-e2e`, `continue-on-error`) points at a **real** Supabase via secrets, so it still supplies `E2E_AUTH_SECRET` + `E2E_AUTH_ALLOWED_SUPABASE_REFS` (demo project ref, never prod) or it fails closed.
  - **When you DO need to configure the two vars.** Only for a **real remote** Supabase project you point the bypass at (e.g. a hosted demo/staging with actual data): add the project ref to `E2E_AUTH_ALLOWED_SUPABASE_REFS` **and** set a confidential `E2E_AUTH_SECRET`. Both are deliberate, per-datasource opt-ins — never inferred from `NODE_ENV`. Loopback (`127.0.0.1:54321`) and the `example.supabase.co` placeholder need neither.
  - **Testers never handle the secret — but know which mechanism runs where.** `E2E_AUTH_SECRET` / `E2E_AUTH_ALLOWED_SUPABASE_REFS` live **server-side only**; the signing/verification happen in the same server process and the cookie is `httpOnly`, so a tester (or Playwright) only ever `POST`s `{ role }` to `/api/auth/demo-account` and the browser auto-replays the cookie. There are **two mechanisms behind that one endpoint**, selected by `NODE_ENV` (which is `development` under `next dev`, `production` under `next build`/`next start`):
    - **Signed-cookie bypass** — runs only when `isE2EAuthBypassEnabled()` is true, i.e. `NODE_ENV !== "production"` **and** `E2E_AUTH_BYPASS` truthy. This is local `next dev` and the **CI E2E jobs** (which launch apps via `bun run … dev`). Here the two vars above apply and the bypass mints a signed cookie with no real Supabase. Configuring the two vars is necessary **and** sufficient _only in these dev-mode environments_.
    - **Real Supabase demo login** — in a production build, the signed-cookie bypass is off. If demo access is enabled (`ALLOW_DEMO_ACCOUNTS=true`), the endpoint signs in with an existing Auth login matching the server's `DEMO_*_EMAIL` and `DEMO_PASSWORD`. `bun run seed:demo:users` is local-only and refuses every hosted project. Do not provision hosted accounts with it or enable the bypass there.

### Fork PR safety

- GitHub secrets are unavailable on fork PRs. The `build` job receives empty Supabase values; this is safe because `SKIP_ENV_VALIDATION=1` prevents `@asym/env` from throwing.
- Turbo remote cache is unavailable without `TURBO_TOKEN`, so CI falls back to the local `.turbo/` cache restored with `actions/cache`.

## 4. Risk Notes

- `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are required by `packages/env/src/schema.ts` (non-optional `z.string().url()` / `z.string().min(1)`); they throw at app startup unless `SKIP_ENV_VALIDATION=1` is set.
- Env vars referenced in build/test steps that could affect CI if unset:
  - Build (Turborepo hash / `turbo.json` `build.env`): see **Turbo build env inputs** above.
  - Tests: `DATABASE_URL` (integration jobs), `CI`, `PLAYWRIGHT_BASE_URL`, `PLAYWRIGHT_PORT` (`.github/workflows/ci-integration.yml`, `playwright.config.ts`) — not part of `build.env` in `turbo.json`.
- Sensitive-looking env vars (names indicate secrets/keys): `STRIPE_SECRET_KEY`, `RESEND_API_KEY`, `RESEND_WEBHOOK_SECRET`, `RESEND_ENCRYPTION_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_DB_URL`, `SENTRY_AUTH_TOKEN`, `CLOUDINARY_API_SECRET`, `DOCRAPTOR_API_KEY`, `CRON_SECRET`, `TURBO_TOKEN` (secret), and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (client-safe key but still a key).
- No untracked or ignored env files were inspected; only tracked references were used for this audit.

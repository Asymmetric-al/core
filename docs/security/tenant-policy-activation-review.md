# Tenant policy activation review (WP2b, second release)

Plan 5.4 asks for this review before `authz.current_tenant_id()` is repointed ("Policies that switch on are reviewed first"). The helper reads the token claim `app_metadata.tenant_id` today. When it starts to return the tenant that the request names, every policy keyed on it switches on. This document lists those policies, the tables that admit on membership or ownership alone, the write grants that go, the tables a donor or missionary may not read, the policies that keep no tenant condition, and how each open question was ruled.

Issue AL-2675. Branch `feature/AL-2675-wp2b-r2-policy-migration`, cut from `develop` at `cc3a82a6d`. The first version of this document was written before any policy changed. Three reviewers read it and the coordinator ruled on its thirteen questions on 19 November 2026. This version follows those rulings, and the migration follows this version.

## How the list was taken

The whole migration chain was replayed on a fresh Postgres 17.11 database (`node scripts/verify/supabase-migrations.mjs`, 115 forward migrations, both gates passing), and the demo seed applied. The list below comes from that catalog, not from reading migrations. This is the query, run as `postgres`:

```sql
with rel as (
  select c.oid, n.nspname as schema, c.relname as tbl,
         exists (select 1 from pg_attribute a
                  where a.attrelid = c.oid and a.attname = 'tenant_id'
                    and a.attnum > 0 and not a.attisdropped) as tenant_table
    from pg_class c
    join pg_namespace n on n.oid = c.relnamespace
   where n.nspname in ('public', 'authz', 'storage')
     and c.relkind in ('r', 'p')
),
grants as (
  select rel.oid, string_agg(distinct case a.grantee when 0 then 'PUBLIC:' else '' end
                             || a.privilege_type, ',') as privs
    from rel
    join pg_class c on c.oid = rel.oid
    cross join lateral aclexplode(c.relacl) a
   where a.grantee in (0, 'authenticated'::regrole)
   group by rel.oid
),
colgrants as (
  select rel.oid, string_agg(distinct att.attname || ':' || a.privilege_type, ',') as cols
    from rel
    join pg_attribute att on att.attrelid = rel.oid and att.attnum > 0 and not att.attisdropped
    cross join lateral aclexplode(att.attacl) a
   where a.grantee in (0, 'authenticated'::regrole)
   group by rel.oid
)
select rel.schema, rel.tbl, rel.tenant_table, coalesce(g.privs, '') as grants,
       coalesce(cg.cols, '') as column_grants, p.polname,
       case p.polcmd when 'r' then 'SELECT' when 'a' then 'INSERT' when 'w' then 'UPDATE'
                     when 'd' then 'DELETE' else 'ALL' end as cmd,
       (select array_agg(case r when 0 then 'public' else r::regrole::text end)
          from unnest(p.polroles) r) as roles,
       pg_get_expr(p.polqual, p.polrelid) as using_expr,
       pg_get_expr(p.polwithcheck, p.polrelid) as check_expr
  from rel
  join pg_policy p on p.polrelid = rel.oid
  left join grants g on g.oid = rel.oid
  left join colgrants cg on cg.oid = rel.oid
 where p.polroles && array[0::oid, 'authenticated'::regrole::oid]
 order by rel.schema, rel.tbl, p.polname;
```

It returns 180 policies on 68 tables. A policy is **claim-keyed** when its text calls `authz.current_tenant_id()`: 84 policies, all on tenant tables (76 Support Hub, 1 `field_policies`, 3 content tables, 4 others). A table is a **tenant table** when it has a live `tenant_id` column, as the catalog gate defines it. The appendix lists all 180 policies.

The functions that write a governed table were found the same way, from the catalog: every function whose text inserts into, updates or deletes from one of them, with its security mode, whether `authenticated` may execute it, and the triggers that call it (section 4).

## Who the claim-keyed policies admit today

The tenant arm of a claim-keyed policy admits no one on a hosted database, because no hosted token carries the claim (A19). Two corrections to the first version of this document:

- **The super-admin branch admits people today.** 77 of the 84 policies carry `OR authz.is_super_admin()`: the 76 Support Hub policies and `field_policies_read`. A profile whose `role` is `super_admin` reads, inserts, updates and deletes every row of the 19 Support Hub tables in every tenant (`20260515025814_support_hub_core_modules.sql:551-573`), reads every `field_policies` row, and writes `field_policies` through its three super-admin policies (`20261005050728_field_policy_foundation.sql:37-42`). So "migrations only" in section 4 describes the code, not what the database allows. The branch stays, with the same meaning, until WP2c removes it (Q6).
- **The seed's tenant claim admits no one either.** The seed writes `tenant_id` into the account metadata of its three logins (`supabase/seed.sql:130, 318`), so their tokens carry the claim. The old helper accepts a claim only when it matches a UUID with a version digit of 1 to 5 (`20260226113000_authz_memberships_foundation.sql:136-137`; NX-03), and the seed's tenants, `00000000-0000-0000-0000-000000000001` and `…002`, have version digit 0. On the replayed and seeded chain, with the seeded donor's token claim set, `authz.current_tenant_id()` returns NULL and the donor reads no row of `funds`, `campaigns`, `assets` or `support_inboxes`. A claim that names a version-4 tenant is accepted, which the release's test uses for its red step (Q2). Nothing reads the claim after this release, so the seed stops writing it.

## What the repointed helper returns

After this release `authz.current_tenant_id()` no longer reads the token. It returns the tenant named in the `x-asym-tenant` request header when all of these hold, and NULL otherwise:

- the value is a hyphenated UUID, in any letter case, compared as a `uuid`; an absent or blank header means no value, and anything else raises `22P02` wherever a policy's lookup runs, so a client defect on a read with rows to judge is an error and not an empty list. Where the lookup never runs, because the table is empty or the filter finds no candidate row, the answer is an empty list and not an error; nothing is admitted either way (council R13, tested on an empty result). The assignment header is read the same way, and so is the command lane's (Q11);
- the caller is signed in;
- the request's assignment resolves: the membership row that `x-asym-assignment` names, when it is the caller's, live, and in that tenant; or, with no assignment header, the caller's one live row there, of any class;
- the tenant row exists. There is no status column yet; this is the interim, and WP3 adds the status test inside the same function, so every policy gets it at once (Q5).

The role-class, sub-role, tenant-administrator and capability checks judge that one row and nothing else. A person's other rows, in this tenant or another, add nothing. A request that names no tenant gets no tenant, so no policy keyed on it admits a row through its tenant-bound branch. Two things still answer without one: the reviewed exceptions of section 3, and the `(SELECT authz.is_super_admin())` branch that some policies keep beside the tenant condition until WP2c removes it (a `super_admin` profile with no headers still reads `support_inboxes`, for one).

`authz.caller_assignment(tenant, class)`, which the member directory and the CRM table-preference functions use, follows the same rule (defect 9). With no header it now counts every live row of the caller in the tenant, of any class, so a person who is staff and donor in one tenant passes its staff check only when the request names the staff row. The first release sends the header on every request, so its callers are unaffected; a caller that sends none and holds two rows there is refused. A tenant header that names another tenant than the one the function is asked about selects nothing, so the member directory answers only for the tenant the request selected; with no header, a caller's one live row there still serves (council R8).

On the Data API, "refused" means an empty answer, not an error: a request whose tenant and assignment resolve to no row of the caller's gets no row through a policy's tenant-bound branch and no `42501`; the reviewed exceptions and the retained super-admin branch still answer, as above. `authz.request_assignment()` returns exactly one record, with every field null when nothing resolves, not an empty set; `current_tenant_id()` reads that record's tenant (council R15; both tested).

## 1. The claim-keyed policies, and who gains what

84 policies on 25 tables. Three groups:

- **Support Hub, 76 policies on 19 tables.** Each table has a SELECT, INSERT, UPDATE and DELETE policy of one shape: the row's tenant is the active tenant and the caller holds a staff row there of any sub-role (`has_staff_membership(tenant_id)`, evaluated per row), or `is_super_admin()`. Signed-in users hold SELECT, INSERT, UPDATE and DELETE on all 19. On repointing, every staff member of the tenant would gain read and write on every row, `support_audit_log` included. The write grants are revoked and the write policies dropped in the same migration (section 4, Q7), so what switches on is read only. That column is right only because the repoint, the rewrite and the revocation ship in one migration: the staff check today matches any staff row the person holds (`20260226113000:181-203`), so a repoint shipped alone would open writes. Two tables are narrowed further (Q1).
- **Five tables of donor-facing content, one policy each.** `assets`, `campaigns` and `funds` have the tenant condition alone, so on repointing every member of the tenant, of any class, would read every row and column: fund amounts, inactive funds and their missionary, unsent campaigns with their audience filters and creating donor, the uploader and purpose of every asset. They become staff-only in this migration, with the class condition as an explicit term (Q2). `field_policies` admits any member of the active tenant to the global rows and the tenant's rows, which donor and missionary rows need. `follows` admits a donor's own follows and any staff member to all of the tenant's.
- **`donor_feed_preferences`, 3 policies.** Own rows only, but not bound to a class: a staff member who also gives would read and write their own preferences under the staff assignment. The migration binds them to a donor assignment.

## 3. Policies that keep no tenant condition

The exit line of WP2 asks for the tenant condition on every signed-in policy of a tenant table. After this release it is met with nine named exceptions in `public`, the nine rows of the table below that are in `public` (`posts`, `locations`, the four post tables, `account_claim_requests`, `profiles`, `field_policies`), and one outside it. The catalog gate scans `public` only (`scripts/verify/tenant-rls-catalog.mjs`); it pins each exception in `public` to its exact deparsed text, its command, its sorted roles and whether it is permissive (`docs/security/tenant-policy-exceptions.json`), so any change fails the gate until it is reviewed again (council R3). The file holds a tenth pin that is not an exception: `donor_activities`, which has no tenant column and carries the request's tenant on its donor row. With the four post tables it is one of the five tables that reach their tenant through a parent row, where every signed-in policy must be a pin, so that a second permissive policy, which Postgres would OR with the reviewed one, fails the gate.

The write policies of every table in this list go with the grants (Q7): with them gone, an accidental re-grant fails the catalog gate's grant rule, where a kept policy would have admitted every staff sub-role. The deny-all `FOR ALL` policies of the six finance tables stay, because they also cover the SELECT grant.

The same holds where no write grant was ever given. Signed-in users hold no privilege on `pdf_templates` and only SELECT on `crm_record_links`, so the write policies of both admitted nothing; they would have admitted every staff sub-role the day a grant came back, and the gate's grant rule would have passed it, because a policy stood. They are dropped too (the coordinator's follow-up on Q7). The rule is: no signed-in INSERT, UPDATE or DELETE policy, on any table in `public`, where no signed-in role the policy names holds the privilege its command needs. The catalog gate states it exactly and cheaply as `WRITE_POLICY_WITHOUT_GRANT`: for each such policy the catalog query asks Postgres whether `authenticated` or `anon`, each when the policy names `PUBLIC` or a role it holds by membership (fixcheck F4), holds that privilege on the table or on any of its columns (`has_any_column_privilege`, `has_table_privilege` for DELETE), which counts grants made through `PUBLIC` and role membership. A `FOR ALL` policy also writes, so it is held to the rule too: where no such role holds `INSERT`, `UPDATE` or `DELETE`, only a plain deny may stand, `false` for every command it governs (council R3; `docs/security/tenant-guard.md`). The deny-all policies of the six finance tables are such denies. On the chain before this change the rule names exactly five policies, the INSERT and UPDATE of `crm_record_links` and the INSERT, UPDATE and DELETE of `pdf_templates`, and on the chain after it none; the migration asserts the same rule before it commits. The SELECT policy of `pdf_templates` stays with the tenant condition; it admits nothing while no read grant exists.

Write grants that stay: `crm_notes` (INSERT; a restricted note is inserted through RLS, plan 5.4) and `donor_feed_preferences` (INSERT, UPDATE; a donor's own preferences).

In all, the migration alters 55 policies in `public` and 8 on `storage.objects`, and drops 101: the 100 write policies above, which no signed-in write grant stands behind, and "profiles staff tenant select". Its rollback, `supabase/migrations/rollback_20261119135300_request_tenant_policies.sql`, stops, changing nothing, unless 20261119135300 is the newest version in the migration ledger, because over a later migration it would undo what that one changed. It then restores the 63 and recreates the 101, puts back 6 functions as they were (`current_tenant_id` with its comment, `has_membership`, `has_staff_membership`, `caller_assignment`, and the parallel marks of `is_super_admin` and `current_user_id`), drops the 9 functions and 1 trigger the migration adds, gives the 42 tables back only the privileges each held, and ends with PostgREST's schema reload. It leaves the Realtime publication alone: no hosted database published the 7 tables, so they go back only through a marked block for a database built by replaying the chain. On such a database, with a ledger whose newest version is this one, the chain and then the rollback with that block run has the release schema fingerprint of the chain without the migration, and the same function comments; without the block the two differ in those 7 members alone (council R10, R17; fixcheck F1).

## 6. Storage and Realtime

- **Profile and editor-image buckets.** Every policy of `profiles` (`avatars|covers/<tenant>/<user>/<file>`) and of the editor images in `document-uploads` (`editor/<tenant>/<user>/<file>`) that a signed-in user reaches moves to live membership in the tenant the object path names: the upload and replace checks, which compared the path's tenant with `profiles.tenant_id` and admitted one tenant per person, and the owner-only reads and deletes, which named no tenant (plan 5.2, "check live membership in the tenant named in the object path"; Q10). The test takes no assignment, because Storage cannot carry the header: any live row of the caller in that tenant. A replace (update) tests it on the object as it stands as well as on the object as it will be, so a person revoked in one tenant and live in another cannot update or move an object under the first, however the Storage server phrases its statement; no code path moves an object out of a legacy folder (council R5). So a person whose membership has ended can no longer delete or read through the API their images in that tenant's folder. That does not withdraw an image: both buckets are public, the upload routes return a public URL (`packages/api/src/upload/editor-image.ts`, `packages/api/src/upload/image.ts`), and anyone who already has it, a former member included, can still fetch the image. Do not rely on ending a membership to withdraw a published image; only deleting the object, by its owner while still a member or by the server, does. The no-legacy ruling covers files outside the owner-folder layout.
- **`email-assets`.** Its public read policy was dropped by WP1.1b (`limit_email_assets_bucket`; record D-14), which was that acceptance line's red step. The bucket has no policy for signed-in or anonymous users. The release keeps the test as a regression guard.
- **Realtime.** Seven tables are in the `supabase_realtime` publication of a replayed database: `funds`, `locations`, `posts`, `post_comments`, `post_fires`, `post_likes`, `post_prayers`. The migration removes each one that is present, and asserts none remains. One screen subscribes: the public map reads `locationsCollection` (`packages/database/hooks/public-locations.ts`), whose Realtime is on by default (`packages/database/collections/tables/app.ts`, `supabase-collection.ts`). The installed adapter (`@supabase-labs/tanstack-db` 0.1.0) keeps a catch-all channel that ends in `CHANNEL_ERROR` and lets Realtime rejoin it, so with `locations` out of the publication the map's channel would error and rejoin. The release turns that collection's Realtime off in `packages/database/collections/tables/app.ts`, which the first release does not change. Nothing instantiates the other six tables' collections, but whoever first did would get the same reconnect loop, so their Realtime is switched off too (council R14).

## 8. The questions, as ruled

The coordinator ruled on 19 November 2026 (`wp2b-r2-rulings.md`), after three reviews and a cross-examination of them.

- **Q1. Support Hub reads.** The application shows a non-administrator only their own notification preferences and their own personal saved views, and lists every signature to everyone (`packages/api/src/admin/support-hub/ownership.ts:131-175`; `route-helpers.ts:66`, where `canManageAll` is the tenant-administrator flag). Ruled: `support_notification_preferences` and personal rows of `support_saved_views` are narrowed to the caller's own agent row (`support_agents.user_id`) or the tenant-administrator flag on the selected row; workspace and ownerless views stay readable to every staff member, and the other Support Hub tables stay staff-wide. The database is the stricter of the two: it finds the caller's agent row by its linked login only (`support_agents.user_id`), where the screens also match an agent row that has no linked login by email (`matchSupportAgentId`, `ownership.ts:60-79`). So an agent whose row is not yet linked would see their own preferences and personal views on the screens and not through the Data API. No signed-in reader of these tables exists today: the Support Hub reads and writes them on the service key (section 4), so this limit changes nothing a person sees in this release.
- **Q2. `assets`, `campaigns`, `funds`.** Ruled staff-only in this migration, with the class condition as an explicit term (section 5).
- **Q3. Public reads.** Ruled: named exceptions that end in WP7, pinned in the gate by exact text (section 3). Anonymous SELECT on these tables is not revoked in this release; closing the public reads is WP7's, with its replacement reads.
- **Q4. A claimant's own claims.** Ruled: a named exception that ends in WP5, pinned in the gate (section 3).
- **Q5. "The tenant is active."** Ruled: the tenant row must exist, as the interim; WP3 adds the status test.
- **Q6. The `is_super_admin()` branch.** Ruled within "leave it exactly as it is" when a bare call is written as `(SELECT authz.is_super_admin())`. The gate accepts exactly that one disjunct beside the tenant condition, until WP2c removes it, and fails any other. No fixture of the acceptance tests on unfiltered reads is a `super_admin` profile. The migration also marks `authz.is_super_admin()` `PARALLEL SAFE`, as the new helpers are, because a policy that names a parallel-unsafe function denies every caller-token read a parallel plan (TP1, section 6.2); the coordinator confirmed this is within Q6. The mark is true of the function as it stands (`20260226113000_authz_memberships_foundation.sql:143-156`): one `STABLE` SQL statement, `SECURITY DEFINER` owned by `postgres`, that reads one permanent table, `public.profiles`, for the caller's row with `role = 'super_admin'`. It finds the caller through `auth.uid()`, which reads two settings, `request.jwt.claim.sub` and `request.jwt.claims`; a parallel worker starts with the leader's settings, so it reads the same caller. (`auth.uid()` is marked parallel-unsafe only because that is the default, and the request-tenant helpers call it too.) The function writes nothing: no row, no sequence, no temporary table, no cursor or prepared statement, and no setting other than its own `search_path` for the length of the call, which Postgres allows in a worker. Its meaning does not change.
- **Q7. Write policies on tables whose grants go.** Ruled: dropped (section 4). The coordinator's follow-up widened it to every table where signed-in users hold no write grant: the write policies of `pdf_templates` and `crm_record_links` go too, and the catalog gate holds the rule as `WRITE_POLICY_WITHOUT_GRANT` (section 4).
- **Q8. `crm_merge_candidates`.** Ruled: INSERT and UPDATE revoked now, and the write policies dropped.
- **Q9. Commenter names.** Ruled first: fixed in this release, through a narrow definer read (section 7). Changed by the council's R1: the release job migrates before it promotes the apps, so the running first release would lose every author in between, and after any application rollback. The read and the move of `comments.ts` onto it ship in the first release; this migration keeps the drop of "profiles staff tenant select" and no longer defines the function. As ruled, the read joins a commenter's profile by login, as `authz.caller_profile_ids()` does; returns `display_name` alone, and NULL when it is blank, with no fallback to another name field; and returns a name and an avatar only to a caller with a live membership of any class in the post's organization, other signed-in callers getting the rows with no name. This release's real-stack Q9 case asserts that whenever the chain defines the read.
- **Q10. Storage reads and deletes.** Ruled: the live-membership test on the path's tenant on both buckets (section 6).
- **Q11. Header parsing.** Ruled: one behaviour on both lanes, the command lane's (section "What the repointed helper returns").
- **Q12. `email-assets`.** Closed by record D-14 (section 6).
- **Q13. Restricted notes.** Ruled: only the tenant-administrator flag on the selected row opens them, and the insert binds the author to the caller (section 2). A `super_admin` profile with an unflagged staff row in a tenant reads no restricted note there.

Account links were backfilled from every donor and missionary profile before the policies moved, so a donor or missionary linked before the change reads exactly what they read before: `tests/unit/acceptance/issue-2678/own-row-policies.realstack.acceptance.test.ts` reads every policy with the base's text and with the new text for every fixture caller and compares the rows; the only difference is a donor whose record names no profile and who is linked by an account link, who now reads their own rows and nothing else.

New tables carry the tenant condition: `parties` (staff of the tenant, or the caller's own linked Party), `account_links` (the caller's own link, or staff), and `external_identifiers` (staff). `follower_requests` and `missionary_tasks` became tenant tables with forced row security and one plain-deny `SELECT` policy each; no signed-in role holds a privilege on either. `authz.caller_profile_ids()` stays, for the `crm_notes` insert, and matches by `user_id` only.

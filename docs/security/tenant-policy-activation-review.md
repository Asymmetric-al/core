# Tenant policy activation review (WP2b, second release)

Plan 5.4 asks for this review before `authz.current_tenant_id()` is repointed ("Policies that switch on are reviewed first"). The helper reads the token claim `app_metadata.tenant_id` today. No hosted token carries that claim, so every policy keyed on the helper has never admitted anyone on a hosted database (A19). When the helper starts to return the tenant that the request names, each of those policies switches on. This document lists every one of them, the tables that admit on membership or ownership alone, the write grants that go, the tables a donor or missionary may not read, and the questions that need a ruling.

Issue AL-2675. Branch `feature/AL-2675-wp2b-r2-policy-migration`, cut from `develop` at `cc3a82a6d`. Written before any policy changed. The migration that acts on it is in the same branch.

## How the list was taken

The whole migration chain was replayed on a fresh Postgres 17.11 database (`node scripts/verify/supabase-migrations.mjs`, 115 forward migrations, both gates passing), and the demo seed applied. The list below comes from that catalog, not from reading migrations. This is the query, run as `postgres`:

```sql
with rel as (
  select c.oid, n.nspname as schema, c.relname as tbl,
         exists (select 1 from pg_attribute a
                  where a.attrelid = c.oid and a.attname = 'tenant_id'
                    and a.attnum > 0 and not a.attisdropped) as tenant_table
    from pg_class c
    join pg_namespace n on n.oid = c.relnamespace
   where n.nspname in ('public', 'authz', 'storage')
     and c.relkind in ('r', 'p')
),
grants as (
  select rel.oid, string_agg(distinct case a.grantee when 0 then 'PUBLIC:' else '' end
                             || a.privilege_type, ',') as privs
    from rel
    join pg_class c on c.oid = rel.oid
    cross join lateral aclexplode(c.relacl) a
   where a.grantee in (0, 'authenticated'::regrole)
   group by rel.oid
),
colgrants as (
  select rel.oid, string_agg(distinct att.attname || ':' || a.privilege_type, ',') as cols
    from rel
    join pg_attribute att on att.attrelid = rel.oid and att.attnum > 0 and not att.attisdropped
    cross join lateral aclexplode(att.attacl) a
   where a.grantee in (0, 'authenticated'::regrole)
   group by rel.oid
)
select rel.schema, rel.tbl, rel.tenant_table, coalesce(g.privs, '') as grants,
       coalesce(cg.cols, '') as column_grants, p.polname,
       case p.polcmd when 'r' then 'SELECT' when 'a' then 'INSERT' when 'w' then 'UPDATE'
                     when 'd' then 'DELETE' else 'ALL' end as cmd,
       (select array_agg(case r when 0 then 'public' else r::regrole::text end)
          from unnest(p.polroles) r) as roles,
       pg_get_expr(p.polqual, p.polrelid) as using_expr,
       pg_get_expr(p.polwithcheck, p.polrelid) as check_expr
  from rel
  join pg_policy p on p.polrelid = rel.oid
  left join grants g on g.oid = rel.oid
  left join colgrants cg on cg.oid = rel.oid
 where p.polroles && array[0::oid, 'authenticated'::regrole::oid]
 order by rel.schema, rel.tbl, p.polname;
```

It returns 180 policies on 68 tables. A policy is **claim-keyed** when its text calls `authz.current_tenant_id()`: 84 policies, all on tenant tables. A table is a **tenant table** when it has a live `tenant_id` column, as the catalog gate defines it. The appendix lists all 180 policies.

The functions that write a governed table were found the same way, from the catalog: every function whose text inserts into, updates or deletes from one of them, with its security mode, whether `authenticated` may execute it, and the triggers that call it (section 4).

## What the repointed helper returns

After this release `authz.current_tenant_id()` no longer reads the token. It returns the tenant named in the `x-asym-tenant` request header when all of these hold, and NULL otherwise:

- the value is a canonical lower-case UUID (any other value raises `22P02`, so a client defect is an error and not an empty list);
- the caller is signed in;
- the request's assignment resolves: the membership row that `x-asym-assignment` names, when it is the caller's, live, and in that tenant; or, with no assignment header, the caller's one live row there, of any class;
- the tenant row exists. There is no status column yet (question Q5).

The role-class, sub-role, tenant-administrator and capability checks judge that one row and nothing else. A person's other rows, in this tenant or another, add nothing. A request that names no tenant gets no tenant, so every policy keyed on it admits nothing.

## 1. The claim-keyed policies, and who gains what

84 policies on 25 tables. Three groups:

- **Support Hub, 76 policies on 19 tables.** Each table has a SELECT, INSERT, UPDATE and DELETE policy of one shape: the row's tenant is the active tenant and the caller holds a staff row there of any sub-role, or `is_super_admin()`. Signed-in users hold SELECT, INSERT, UPDATE and DELETE on all 19. On repointing, every staff member of the tenant, whatever the sub-role, would gain read and write on every row, `support_audit_log` included. The write grants are revoked in the same migration (section 4), so what switches on is read only.
- **Five tables of donor-facing content, one policy each.** `assets`, `campaigns` and `funds` have the tenant condition alone, so every member of the tenant of any class gains read of every row. `field_policies` admits any member of the active tenant to the global rows and the tenant's rows. `follows` admits a donor's own follows and any staff member to all of the tenant's.
- **`donor_feed_preferences`, 3 policies.** Own rows only, but not bound to a class: a staff member who also gives would read and write their own preferences under the staff assignment. The migration binds them to a donor assignment.

## 8. Questions that need a ruling

Each is open. The migration takes the default named here so that the rest of the work can go on, and changes when the ruling differs.

- **Q1. Support Hub reads.** Every staff sub-role reads all 19 tables directly through the Data API: other agents' saved views, signatures and notification preferences, and `support_audit_log`. The plan admits "a live staff membership of any sub-role, as the Support Hub policies admit today". Default: as the policies say. Should the three per-agent tables be narrowed to the agent's own rows?
- **Q2. Content tables for every member.** `assets`, `campaigns` and `funds` open to every member of the tenant, donors and missionaries included. The `tenant-read-floor` rulings accepted this for `funds` and `campaigns` and flagged `assets`. Now it switches on. Default: as ruled.
- **Q3. Public reads with no tenant condition.** `posts` and `locations`, and the four post-reaction and comment tables, keep `TO anon, authenticated` reads of published, public rows with no tenant condition, and `anon` holds SELECT on them. A signed-in person reads every tenant's public posts. The exit line asks for the tenant condition on every signed-in policy of a tenant table; the no-header list asks for these reads to keep working. Default: kept as listed exceptions. A ruling should say whether a signed-in visitor's public reads move to the verified-host read functions of WP7.
- **Q4. A claimant's own claims.** `account_claim_requests_requester_select` keeps no tenant condition, because a claimant may hold no membership yet. Nothing reads it on a signed-in token. Default: kept as a listed exception. The alternative, a tenant condition, would hide every claim from the person who made it.
- **Q5. "The tenant is active."** `public.tenants` has no status column; WP3 adds one. Default: the helper requires the tenant row to exist (a membership cannot name a missing tenant anyway). WP3 puts the status test inside `authz.request_assignment()`, so every policy gets it at once.
- **Q6. The `is_super_admin()` branch.** Kept on every policy that has it, with the same meaning. Where a policy is rewritten, the bare call, which runs once for every row, is written as `(SELECT authz.is_super_admin())`, which runs once for a statement. The branch sits beside the tenant condition, not inside it, so it still admits across tenants until WP2c removes it. Default: as described.
- **Q7. Write policies on tables whose grants go.** They are rewritten in the new form and kept. Without a grant they admit nothing; WP2c's plan counts them (the staff check in "46 insert, update and delete policy statements"). Default: kept. Dropping them is the alternative.
- **Q8. `crm_merge_candidates`.** Signed-in users hold INSERT and UPDATE; nothing writes it on a signed-in token; the plan does not name it. Default: unchanged here, for WP4a.
- **Q9. Commenter names.** See section 7. The first release's delegates or WP4a must move `packages/api/src/posts/comments.ts` off the embed.
- **Q10. Owner reads and deletes in Storage.** They stay owner-only, with no membership test, because they name no tenant: a person who leaves a tenant can still read and delete the objects they uploaded there. Default: unchanged. The alternative adds the path's tenant to them, which would also stop an owner from deleting a file stored before the owner-folder layout.
- **Q11. Header case.** The tenant and assignment headers must be canonical lower-case UUIDs on the read side; any other form raises `22P02`. The command lane's `tenant_guard.request_assignment_id()` accepts upper case. The first release sends lower case. Default: the read side is strict, the command lane unchanged.
- **Q12. `email-assets`.** Already closed by WP1.1b (section 6). Its acceptance test cannot fail before this migration.
- **Q13. Restricted notes.** Today `profiles.role` admin or super_admin opens restricted notes in every tenant where the person holds a staff row (record section 9, the row owed before WP2c). After this migration only the tenant-administrator flag on the selected staff row opens them. A super_admin profile keeps access only where WP2a's backfill set the flag (its profile tenant).

## What to build

Consume authoritative ministry/source change provenance to identify only affected prospective request, invitation, promise or eligible owner. Routine name/login/participant metadata alone does not create donor-wide work. Apply current restrictions immediately, even before review. Review neither grants access nor sends/transfers work; genuinely different future ministry/purpose uses explicit source disposition.

## Context and contracts

Staff see a scoped review of genuinely affected future obligations, while routine name or participant changes preserve continuity.

Current authority, tenant/field/history-safe read and write behavior, atomic source history/receipt/required intent, truthful lost-response recovery and applicable two-session concurrency proof accompany this slice. Base UI/base-maia/Zinc, keyboard/screen-reader/mobile/zoom behavior and slow/failing network recovery accompany every reached screen. These are in-slice delivery obligations under REQ27-Q01–Q14, not deferred to final qualification. Terminal Q tickets prove composition and release evidence.

## Scope and non-goals

- No new CRM identity, authorization engine, task/notification platform or shadow finance ledger.
- No duplicate implementation of already owned request, encounter, Party merge or finance command.

## Acceptance criteria

- [ ] Renaming ministry or ordinary participant change creates no blanket donor review, new enrollment or implied allegiance.
- [ ] An open invitation expressly naming a departed person is reviewed only where that source fact affects future work.
- [ ] Current restriction blocks consequential action immediately while review remains unresolved.
- [ ] Review leaves independent gifts, past encounters, presented requests, permissions and ministry identity intact.
- [ ] Unavailable owner coverage is explicit and never silently interpreted as unaffected or empty.

Primary source cases are reproduced below so the implementer can distinguish one slice's first-demonstration ownership from later composed regression proof. An AC whose multi-step scenario crosses a later producer must have that producer as a genuine blocker or its primary acceptance transferred explicitly; a mocked internal owner does not satisfy it.

### AC27-P06-01

**Given** ministry name or participant metadata changes without changing source eligibility or represented future work, **when** source updates propagate, **then** history remains and no blanket supporter review, new journey, task or consent inference occurs.

### AC27-P06-02

**Given** an open invitation names a person who leaves the ministry, **when** the authoritative source change is accepted, **then** only the affected future invitation/follow-through is presented for permitted review; replacement-person supporter allegiance is not inferred.

### AC27-P06-06

**Given** current restrictions conflict with future work while a review remains pending, **when** a consequential source action is attempted, **then** the restriction applies immediately rather than waiting for staff to complete the review.

## What to build

Implement the first native cultivation source command and smallest real staff start/detail journey. Select actual canonical supporter Party and exact Ministry Assignment Tenant/Legal Entity/purpose; support ministries without participants, gifts, email or Page. Preserve one ordinary active/paused meaning via relational uniqueness and semantic receipt. Existing visible work is reused without resetting stage/owner/obligations. With minimum result authority absent, hidden-existing and absent produce equivalent bounded denial. Admit only expressly requested local referral/ask/work effects via their owners. Start has visible eligible established lead or deliberate authorized choice, current approved list with optional assessment, and due source task or accountable actionable exception. Include real fixture and minimal ADR0183 adapter qualification needed by this behavior; no database-only scaffold ticket. Deliver the bounded reusable native Source work adapter as part of this real behavior: occurrence identity, current recipient/source-action predicates, minimal My Tasks projection, identifier-only durable local intent, source receipt reconciliation and typed source end. It grants no independent task completion. Later request/context sources may reuse that component without any cultivation enrollment prerequisite; no separate framework/S02 ticket.

## Context and contracts

A staff member deliberately starts ordinary identified-ministry work once, with a visible eligible owner, approved list and truthful next action, or safely reuses existing work.

Current authority, tenant/field/history-safe read and write behavior, atomic source history/receipt/required intent, truthful lost-response recovery and applicable two-session concurrency proof accompany this slice. Base UI/base-maia/Zinc, keyboard/screen-reader/mobile/zoom behavior and slow/failing network recovery accompany every reached screen. These are in-slice delivery obligations under REQ27-Q01–Q14, not deferred to final qualification. Terminal Q tickets prove composition and release evidence.

## Scope and non-goals

- No new CRM identity, authorization engine, task/notification platform or shadow finance ledger.
- No duplicate implementation of already owned request, encounter, Party merge or finance command.

## Acceptance criteria

- [ ] Implement and prove deliberate create/reuse, identity, current authority, optional initial assessment, responsibility preservation and durable source effects now. Only the complete scenario invoking later lead/list or Request commands moves to its named owner.
- [ ] One visible start accepts the actual known context without re-entering facts; no gift/referral/import/score timer automatically enrolls.
- [ ] Two ordinary create/reuse commands and a pause race leave one ordinary identity and one effect receipt; lost response recovers original actor/time.
- [ ] No-participant/no-finance/no-Page ministry is usable; unidentified-ministry introduction stays with Party/task owner without dummy enrollment.
- [ ] Same action with hidden-existing versus absent context exposes no difference without minimum result authority; metadata-only reuse grants no history/edit access.
- [ ] Approved list and optional assessment are explicit submitted intent; start preserves existing responsibility/stage and uses appropriate task or owned exception.
- [ ] Real effective-role hostile Tenant/entity/actor/owner edits and before/after-commit faults prove source/history/receipt/work atomicity. Accessible contextual UI clearly distinguishes internal intent from supporter assent.

### AC27-P01-01

**Given** a Party and eligible ministry with no participant, Support Binding, gift, email address or public Page, **when** authorized staff deliberately start ordinary work, **then** the identified relationship can be recorded without inventing any missing financial, public or participation fact.

### AC27-P01-03

**Given** a worker participates in two ministries and a church has a named committee contact, **when** staff select a support relationship, **then** the actual Party and exact ministry are distinguishable; neither the worker login nor church contact silently substitutes for the selected subject.

### AC27-P01-04

**Given** a relationship is not yet attributable to an identified ministry, **when** staff record an introduction or authorized task, **then** the useful Party/referral/task record is accepted through its owner without creating a cultivation enrollment or dummy ministry.

### AC27-P01-05

**Given** two Tenants or two Legal Entities have similarly named ministries, **when** a command supplies a mismatched or hidden reference, **then** the command produces no cross-scope relationship or restricted identifying result; legitimate explicitly authorized multi-entity work uses each exact admitted scope.

### AC27-P03-02

**Given** a gift, score change, imported contact or introduction-only note arrives, **when** the source fact is processed, **then** no new enrollment is admitted; separately qualified financial/service facts and existing Party/task work remain usable.

### AC27-P03-03

**Given** an ordinary enrollment already contains stages, owner and several open asks, **when** a new start operation resolves to permitted reuse, **then** those existing facts remain unchanged and only separately requested authorized work is added.

### AC27-P03-04

**Given** paired fixtures differ only in whether a forbidden ordinary enrollment exists, **when** a caller lacking minimum admission-result authority attempts entry, **then** observable availability, bounded response, counts and errors do not expose the hidden difference or admit a workaround duplicate.

### AC27-P03-05

**Given** a caller has limited reuse metadata authority but not history/edit authority, **when** the command resolves existing work, **then** only that admitted metadata is returned and no edit, history, missionary or finance access is created.

### AC27-P05-01

**Given** a partnership has one established currently eligible lead, **when** staff start or review responsibility, **then** that lead is visibly prefilled and changeable without a separate confirmation; the unrelated creator/Party representative is not substituted.

### AC27-P05-02

**Given** the partnership lead is unknown or several candidates are equally plausible, **when** staff start work, **then** the UI requests an authorized choice and does not use first result, administrator status or ministry membership as proof.

### AC27-P05-05

**Given** a user becomes responsible for partnership or task work, **when** the source assignment is accepted, **then** no independent read, financial, consent, publication or missionary grant is created.

### AC27-P07-01

**Given** appropriate authorized existing work already addresses the enrollment need, **when** staff start or continue cultivation, **then** the existing source task can satisfy next action and no duplicate task is created merely for enrollment.

### AC27-P13-01

**Given** valid old rows are paired with hostile proposed Tenant, entity, Party, ministry, owner, actor or purpose fields, **when** each admitted insert/update/upsert/delete/returning/RPC/service/import/repair path is exercised under real effective roles, **then** all independently forbidden resulting states and spoofed attribution fail without leaking hidden constraint/source details.

### AC27-P13-02

**Given** source links are null, partially-null composite references, cross-Tenant or mismatched entity references, **when** the command and applicable database constraints are exercised, **then** required identity cannot be fabricated and optional references are wholly absent or valid against their owners.

### AC27-P13-03

**Given** member-without-grant, revoked-member, former-member-with-independent-grant and admitted service contexts exist, **when** read/action/result commands are evaluated, **then** current exact authority determines outcomes; role labels, enrollment and membership neither add nor remove independent valid grants by inference.

### AC27-P13-04

**Given** faults occur at every local acceptance/history/receipt/work/intent boundary, **when** the command executes, **then** pre-commit failure leaves no partially accepted business change; post-commit secondary failure retains one source receipt and visible repairable pending/failed state.

### AC27-P13-05

**Given** same intent is submitted through multiple transports or after a lost response, **when** duplicates, changed payload and stale out-of-order events arrive, **then** one intended effect remains; changed meaning conflicts and old events/receipts do not overwrite newer state or acquire new disclosure authority.

### AC27-P13-06

**Given** permission revocation and acceptance contend in independent transactions, **when** each valid ordering is forced, **then** stale authority cannot create a new effect after the revocation boundary; accepted earlier history stays true without preserving future forbidden access.

### AC27-P13-07

**Given** hidden source facts differ in paired fixtures while permitted inputs are identical, **when** counts, ranking, filters, selection, cached responses, errors and exports are observed, **then** unauthorized facts do not alter observable permitted output; stale responses after Tenant/role change are rejected.

### AC27-P13-08

**Given** sensitive source material is redacted, expires or is lawfully erased, **when** history, task previews, notifications, reports, logs, exports, generated files and retained derivatives are reconciled, **then** admitted structural evidence remains only where permitted and protected bodies/identities are not restored or copied to evade source restrictions.

### AC27-P13-09

**Given** an external owner returns an ambiguous timeout after possible success, **when** recovery runs, **then** the source/provider receipt is reconciled before retry and no blind duplicate effect or false success is reported.

### AC27-P30-02

### AC27-P30-07

### AC27-P32-02

**Given** retained rows include ambiguous one-profile-to-many-ministry mappings and unknown historical purpose/time, **when** migration runs repeatedly and is interrupted/resumed, **then** only evidenced mappings are retained, unresolved associations stay explicit and no newly approved enrollment/stage/task/contact/message effect is fabricated.

### AC27-P32-03

### AC27-Q01-01

- **GIVEN** a staff actor uses either a list, detail, board or later qualified projection.
- **WHEN** the same business change is submitted.
- **THEN** the same owner validation and durable outcome apply and there is one authoritative history.

### AC27-Q01-02

- **GIVEN** a dependent source is unavailable or not qualified.
- **WHEN** a consumer attempts a source-owned effect.
- **THEN** the dependent action reports unavailable with safe recovery, makes no substitute fact and leaves unrelated valid work usable.

### AC27-Q02-01

- **GIVEN** two tenants contain similar identities and a staff actor supplies a foreign ID or forged attribution.
- **WHEN** any list, command, job or receipt is requested.
- **THEN** no foreign value or effect is returned, counts do not disclose it and accepted audit attribution comes only from the authenticated source.

### AC27-Q02-02

- **GIVEN** a user loses access after submit but before job execution or receipt recovery.
- **WHEN** the delayed path runs.
- **THEN** current policy denies the forbidden effect or disclosure while preserving lawful already accepted work.

### AC27-Q03-01

- **GIVEN** an authenticated user can edit a permitted record.
- **WHEN** they attempt to change tenant, author, scope or a reference to an ineligible row through table, RPC, upsert or view.
- **THEN** each bypass is rejected atomically by the actual deployed policies/constraints or qualified source boundary.

### AC27-Q03-02

- **GIVEN** a privileged job or definer runs.
- **WHEN** it attempts an out-of-scope write or disclosure.
- **THEN** the actual capability ceiling denies it and the test verifies grants, policies and function configuration rather than SQL strings alone.

### AC27-Q04-01

- **GIVEN** the source commits but the response is lost.
- **WHEN** the actor retries the same operation.
- **THEN** one business effect/history entry/required work intent exists and the permitted original result is recovered.

### AC27-Q04-02

- **GIVEN** source success precedes failed task or notification projection.
- **WHEN** recovery executes twice.
- **THEN** source success remains true, one required effect is visible after recovery and no extra task/message is created.

### AC27-Q05-01

- **GIVEN** two real database sessions edit the same source revision.
- **WHEN** their commits are deliberately interleaved.
- **THEN** at most the permitted serialized intent wins and the other gets a recoverable conflict without losing authorized draft input.

### AC27-Q05-02

- **GIVEN** a backdated or corrected encounter, gift or decision arrives.
- **WHEN** current projections recompute.
- **THEN** history preserves its original and corrected meaning and recorded time does not masquerade as occurrence time.

### AC27-Q14-01

- **GIVEN** an acceptance run accidentally uses demo auth, fake source storage or a missing required owner.
- **WHEN** suite preflight runs.
- **THEN** it fails and cannot be reported as real integration evidence.

## Recorded decision

For a deliberate genuine return after a valid closure, resume the **same
cultivation enrollment** when the supporter, identified ministry, ordinary
purpose and authoritative scope are the same. Preserve the earlier valid closure
and record the later return; do not create a linked successor enrollment merely
because work stopped and later resumed.

This is renewed current work on a continuing journey, not erasure of the closed
period or a replay of the former work. Current authorization, responsibility and
applicable source rules govern the return. Ended tasks, obsolete reminders,
accepted ask outcomes, revoked permissions and erased content do not revive.
Any currently required shared work follows its existing source contract; an
already valid appropriate obligation may satisfy the next-action rule without
creating an extra task solely because the journey reopened.

A genuine change of ministry, purpose or authoritative scope still follows D2/D3.
Reopening does not change money, Party lifecycle, consent or assignment authority.
D8 selects the normal parent identity on return; it does not select a current
stage default, restore the former lead, erase an erroneous close, or freeze a
database uniqueness predicate before remaining collision/correction rules.

## Adversarial check

### What could go wrong with this answer?

An implementation could erase the closure, reset the original start timestamp,
revive cancelled child work or count two simultaneous returns as two starts.
It could also reuse the wrong ministry or leak a hidden matching journey.
Preserve D3/D7's exact scope, current action/result authority, durable accepted
history, concurrency and idempotency requirements. Reopening the parent does not
reopen ended child work. These are inherited safeguards, not new product scope.

### What hidden assumptions are we making?

The earlier close was valid and the same supporter/ministry/purpose remains
appropriate. It does not establish that old participants, supporter intentions,
stage, lead, access or planned asks are still current. D2 still requires review
of materially affected future work. Mistaken closure and duplicate/colliding
historical records are distinct cases; the normal-return answer cannot silently
choose their resolution or prove current data coverage.

### How does this affect the whole product?

P27 keeps one continuing cultivation identity and its truthful lifecycle history.
P9 keeps Party/ministry/assignment truth, shared Tasks Hub keeps projections, and
P12 keeps current authority. Finance and communication owners remain independent.
Required current work still needs a due shared task or the already required
owned actionable exception. No separate period model, workflow engine, permission
store, financial effect or donor-facing reopening flow is introduced.

### How does this affect the end-user experience?

Staff return to the same development record and see what happened before and
what is current. The benefit is continuity rather than proof of fewer typing
steps: the rejected linked-effort alternative could also reuse existing context.
Reopening should not reset a known relationship to a new prospect or pretend an
old stage has been reassessed. Whether staff must review that stage as part of
reopening, or may update it later, is the next practical product question.

### Does this follow modern best practices?

The official CRM and ministry documentation already checked for D7 supports
separating relationships from individual solicitations, preserving status history
and recognizing ongoing nonfinancial partnership. It does not prove that one
parent-record lifetime is universally superior. Reusing the continuing journey
is a product judgment grounded in D1/D3; retaining history and currently qualified
effects follows Core's existing contracts. No new vendor test or staff pilot is
claimed for this answer.

### Does this fit Asym’s existing repo and product direction?

Yes. D1 selects continuing partnership, D3 defines one ordinary journey while
reserving lifetime, and D7 explicitly allows this fork to be settled later.
ADR-0183's never-reopened predecessor is an ended **source-work occurrence**, not
the parent cultivation enrollment. This distinction allows renewed work on the
same journey without replaying old tasks or notifications. Current generic task
reopen/status helpers remain unqualified substitutes for this source operation.

### Should we adjust the recommendation?

No material amendment is needed. Accept A within the question's explicit scope,
record its meaning in the glossary, and continue the interview. Preserve the
inherited safeguards above without demanding another approval of the same answer.
Do not imply that D8 alone settles every return/correction collision, stage rule,
database constraint or end-to-end implementation requirement.

Two independent reviewers checked this selection against the existing ownership,
lifetime and UX boundaries. This is a document/decision update, so verification
checks links, decision status, glossary and the required seven-part structure;
it does not repeat earlier mechanical tests as supposed proof of reopening.

The later specification must demonstrate these user/domain outcomes:

1. A valid close followed by a genuine return preserves the same journey identity,
   original start, closure fact and newly accepted return, including across retries.
2. Multiple close/return cycles preserve each prior accepted fact; old closed-period
   reporting is not rewritten as continuously active and closed time does not
   become invented activity or contact. Exact duration/stage metrics remain to
   be defined before those metrics ship.
3. Old tasks/reviews/attention and their actual outcomes remain ended. Current
   appropriate work is admitted or reused only through its qualified source rule.
4. Current authority and eligible responsibility apply after lead/role/participant
   changes. Reopening cannot restore former access or override restrictions.
5. Concurrent requests, stale commands and lost responses produce one accepted
   intended return; a replay after a subsequent close cannot reopen it again.
6. Wrong-scope, different-purpose, hidden-existing and already-current cases do
   not silently create duplicates or reveal forbidden history. Exact correction,
   merge and collision policy must be settled before its database implementation.
7. Prior stage/ask facts remain historical truth. The next question determines
   the stage-selection experience; no reset, advancement or verified-current
   assessment is inferred from D8 alone.

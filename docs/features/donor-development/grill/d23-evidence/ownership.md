## Smallest coherent operating policy — proposed product judgment

Use one finite native review choice in the existing qualified P27 configuration
scope: the organization default is **Review not required** initially or **Review
required**. On a particular request, the authorized requirement/exception owner
can choose **Use organization default**, **Require review**, or **Review not
required**. Show the effective result and its basis. Ordinary request editing
does not carry that administrative power; an exception is explicit, attributed
policy evidence, never an approval. No new entity/team hierarchy, currency
threshold engine, custom purpose taxonomy or executable condition language is
needed. This does not claim to detect every high-value request automatically.

When review is required, staff deliberately submit the exact prepared proposal
for one review decision. A draft whose policy says review is required is not yet
an actionable reviewer assignment. The reviewer sees relevant proposed terms and
changes, then approves or returns an intelligible non-approval outcome; an actual
rejection must not become supporter decline. Revision/resubmission retains the
prior decision and uses a new review occurrence. The request responsibility,
review responsibility, reviewing authority and presenter remain distinct.

The current requirement governs each future supported presentation/send action,
including an old unpresented draft. Default changes preserve explicit case
choices. Removing the last requirement ends outstanding mandatory review as
**No longer required**, never **Approved**; tightening requires sufficient valid
approval before prospective action. Neither operation presents or sends anything.
Approval of unchanged terms is not invalidated solely by an unrelated routing or
default metadata change: evaluate whether it satisfies the current requirement.
Past presentation and valid past decisions remain history. An ended review task
never revives; genuinely required further review has a successor occurrence.

This deliberately differs from P22's pinned-profile backlog semantics. It is a
P27 recommendation, not an asserted cross-domain rule. The strongest smaller
alternative is explicit case requirements only, without an organization default;
it is adequate for rare exceptions but forces repeated marking when an agency
normally reviews proposals. Arbitrary amount rules or a general approval chain
add complexity without being necessary to deliver the selected capability.

## Remaining qualification, not another founder questionnaire

Before release, prove the exact P12 action/capability mapping, qualified source
policy scope, review-relevant proposal fields, current reviewer responsibility
and recovery, source task/attention binding, and final P6/17 action admission.
Include permissions/policy/terms races, replay after timeout, lost responses,
withdrawn requests and truthful non-approval endings. No generic permission,
bulk-review or approval migration facility is authorized by this note. Imports
may preserve attributable historical evidence; they cannot manufacture current
human approval or activate outward work. Existing paused/closed journey meaning,
financial history, legal retention and lawful deletion continue with their owners.

This resolves the selected native capability without claiming Phase 27 is ready
to ship. Any new unconditional human-separation rule or automation language would
be a material additional policy, not a hidden implementation safeguard.

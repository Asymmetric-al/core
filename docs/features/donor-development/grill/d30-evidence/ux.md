# D30 UX evidence — understandable assignment changes

2026-10-11 UTC. The selected direction keeps reviewed transfers as the default and permits an organization to enable automatic changes to existing rule-managed role assignments. This appendix proposes the experience and acceptance evidence; it does not establish a shipped P27 interface, observed ministry preference or measured usability. Current source inspected at `225c02e9499bd6c0d493223cd4b1a4120ff787e3`.

## One clear responsibility, one understandable change

Lead with the actual role and person, followed by how that assignment is controlled. Put a proposed change beneath it rather than replacing the current name optimistically. An illustrative church record could show:

```text
Church-relations representative
Current: Maria Santos                         Managed by rules
Proposed: Daniel Kim
Reason: This church now matches the North region rule.
                                      Review change · Keep Maria
```

These are illustrative names and wording, not a new role catalog or territory engine. A proposal is not a completed transfer. After an accepted transfer, the current person changes and the permitted history explains who or which rule made the change. A related task can still belong to Maria; its independent responsibility remains visible in its own context. Avoid a large transfer wizard, staff compliance dashboard or constant assignment badges on unrelated screens.

[Q30](../phase27-q30-assignment-rule-changes.md):17–23,56–89 supplies the boundaries: P9 role-qualified assignments and derived portfolios; separate partnership, Request and task responsibility; protected overrides; applicable handoff requirements; repeatable finite operations. User selection supersedes that question file's earlier A-only recommendation. The strongest simpler alternative is reviewed transfers everywhere: fewer unattended changes, but recurring review work for organizations deliberately operating rule-managed portfolios. Optional automatic operation is reasonable if its scope, exceptions and effects remain understandable. No vendor material proves that either policy improves ministry outcomes.

## Required interaction outcomes

**UX01 — Name the setting's actual effect.** In the authorized assignment settings, use a compact, labeled choice such as **Existing assignments: Review transfers / Transfer automatically**. Reviewed is the initial policy; failed fetching is not evidence that it is currently saved. Explain that automatic operation covers approved rules for the displayed role/scope and preserves manual choices. Initial assignment remains a separate existing behavior. Do not label the whole feature Off, imply all responsibilities transfer together or add a generic automation designer. The shared control can be chosen during implementation; these outcomes do not mandate radio cards or a particular overlay.

**UX02 — Make activation and existing-record application different actions.** Draft edits are inert. The deliberate policy activation explains which future events can change assignments and when the policy takes effect. A preview states its scope and freshness, shows understandable rule order and the applicable result, and separates transferable matches, protected manual choices and blocked cases. No arbitrary first page masquerades as the full impact. **Apply to current matches** is a separate, finite reviewed operation, not a hidden consequence of saving or enabling automatic mode. If impact is unavailable, say so; never display zero changes as a fallback. Refreshing a preview cannot expand an already accepted group.

**UX03 — Explain rules without technical noise.** Show the applicable rule's readable name and a concise permitted reason. Where multiple rules match, explain the qualified first applicable ordered rule; an ineligible result is not permission to silently use a lower rule. Do not expose private condition values. Distinguish **No matching rule** from **The matching rule cannot assign this person**. When a match disappears, retain a valid current assignment and expose the need for review; do not silently unassign it. Rule ordering needs keyboard/button access if ordering is editable, not drag alone.

**UX04 — Make manual control deliberate and reversible through a new action.** **Keep Maria** means keep Maria as a manual assignment, including when the assignee ID stays unchanged; the interface states that rules will not replace this choice. A manual change to another eligible person has the same visible protection. **Use rules again** explicitly releases that protection and shows the current rule result. Under reviewed mode this does not pretend a proposed replacement is already current; under automatic mode it explains any immediate qualified result of the action. A blocked result is shown before acceptance. Returning to rules does not restore a historic person, bypass handoff conditions or grant access. No mandatory narrative reason or second acknowledgment is added for an ordinary change.

**UX05 — Review in context, singly or as a finite group.** The review displays supporter, exact role, current/proposed person, reason and permitted affected-work context. Staff can accept the shown transfer, choose another eligible person or keep the current person manually. Closing the review is Cancel, not a silent manual exception. The group version identifies selected rows versus all matching results before capturing the finite set; staff can remove rows and inspect exceptions. One clear **Transfer selected** action accepts that review, without a dialog per row. Proposals do not automatically become tasks. Only a real source-required repair or handoff creates/reuses qualified actionable work.

**UX06 — Treat empty and unknown as different facts.** A verified empty role can say **Unassigned** with an appropriate assignment action. An intentional protected vacancy says **Left unassigned manually**, with the qualified path to change it or use rules again. It is not eligible for silent initial filling. Unknown legacy control mode remains protected pending reconciliation; do not present it as rule-managed. Loading, fetch failure, restricted details, no search matches and no eligible staff are distinct states. A filtered-out or departed current person does not become an empty role because the picker lacks their ID. Duplicate names need permitted distinguishing context, not UUIDs or unnecessary private email disclosure.

**UX07 — Preserve truth through delays and conflicts.** While saving, keep current and proposed facts readable and prevent duplicate intent; do not close context or announce the new assignee early. An accepted result updates the role and gives persistent recoverable feedback. If another person changed the assignment or the rule/recipient became ineligible, show the permitted current state and require a fresh deliberate choice, rather than silently rebasing the transfer. A lost response says **Checking whether this change was saved** while recovering the same submitted operation. Do not encourage another unrestricted transfer. Older replies cannot overwrite newer current state; a historical successful receipt is labeled as that operation's result.

**UX08 — Report partial groups honestly.** Show source-confirmed outcomes with exact permitted records and next actions: transferred, retained/protected, needs refreshed review, blocked or unresolved. The concise summary remains available after the toast disappears and after navigation/reconnect. Retry recovers the original operation; resolving a conflict uses a newly reviewed intent. Neither reruns a live filter nor reapplies successful items over later manual choices. Do not call every failure unchanged when acceptance is still unknown. Revocation can limit even outcome disclosure; unavailable details must not leak hidden names, work counts or protected reasons.

**UX09 — Explain stopping, re-enabling and departures.** Moving back to reviewed mode stops future automatic acceptance under the prior policy; it does not reverse completed transfers or erase history. In-flight outcomes are reported truthfully. Re-enabling uses the new policy context and does not silently replay stale proposals or sweep current matches. A staff departure is an eligibility/continuity problem with an owned repair route, not an excuse to restore access, erase attribution or claim every task moved. Display the permitted actual assignment and specific unresolved responsibility. Preserve any independently required receiving-person acknowledgment; do not impose it universally. Show **handoff complete** only when the owning source supports that claim.

**UX10 — Keep the daily surface calm and accessible.** Use a readable role heading, person name, one secondary control-mode description and contextual Change/review action. Defer full rule history and detailed impact until useful. On narrow screens stack **Current** and **Proposed** with text labels; do not depend on arrows, avatar color or hover. Keep complete names/reasons reachable with keyboard and touch, wrap long localized labels, use locale-aware dates with explicit timezone where timing matters, and preserve RTL reading order. Slow searches must not clear the chosen ID or mutate the draft. Keep focus stable, inline errors associated with their fields, and announce material completion/failure without repeating every background refresh.

## Fresh primary references and their limits

All opened 2026-10-11; these document supported patterns, not an evaluation of Core or missionary practice.

- [HubSpot assignment workflows](https://knowledge.hubspot.com/workflows/assign-and-rotate-record-owners-using-workflows), updated September 1, 2026, explicitly separates overwriting an existing owner and documents eligible/ineligible recipients. This supports making replacement intentional and eligibility visible; its workflow product, licensing, fallback-to-unassigned behavior and distribution algorithms are not Core requirements.
- [Microsoft assigned records and details](https://learn.microsoft.com/en-us/dynamics365/sales/wa-manage-unassigned-records) exposes previous/current assignment, rule context and distinct failure reasons. It also warns that legacy records can show Needs attention without an actual problem. Prefer concrete actionable reasons; do not copy its hover-only explanation, raw permission errors or processing-time claims.
- [Salesforce nonprofit portfolios](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-philanthropy-and-partnerships/manage-portfolios-and-view-donor-profiles), undated, documents both organization-rule assignment and manual reassignment. This establishes a comparable pattern, not evidence for wealth screening, automatic cultivation admission or ministry effectiveness.
- [Base UI Radio Group](https://base-ui.com/react/components/radio-group) documents accessible group/option naming and controlled versus initial values. Use the installed shared primitive API, not a hand-built ARIA imitation; choosing a control does not establish a correct settings command.
- W3C [On Input](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html) supports predictable effects; [Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) supports perceivable non-disruptive feedback; [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) covers narrow/zoomed content. [Error Prevention](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html) permits checking/correction/reversal and expressly does not demand confirmation for every ordinary save. These are informative explanations of criteria, not a conformance certificate or mandate for extra dialogs.

## Prioritized concerns and required proof

These grades assess prospective misuse/reuse risk, not deployed D30 vulnerabilities. Likelihood is qualitative, not measured incidence.

| Concern                                                                                   | Severity / likelihood                 | Required prevention                                                                                                     |
| ----------------------------------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Proposed/legacy Owner display mistaken for all current responsibility or access           | High / plausible                      | UX05–07 exact role and authoritative current value; independent work/access unchanged unless separately qualified.      |
| Enabling automatic mode sweeps old records or overwrites manual/vacant exceptions         | High / plausible                      | UX01–04 explicit scope, prospective activation, finite deliberate current-match application and protected control mode. |
| Partial/lost responses encourage duplicate or stale transfers                             | High / plausible                      | UX07–08 durable recoverable per-item results and newly reviewed conflicts.                                              |
| Empty selector, missing settings or departure falsely appears unassigned/safely routed    | High / plausible                      | UX01,06,09 separate known facts, unavailable data and owned repair.                                                     |
| Technical explanations, repeated dialogs and inaccessible comparison hide the next action | Medium / likely without design review | UX03,05,10 concise role-specific wording, one deliberate acceptance and accessible comparison.                          |

Future acceptance must use the actual product and qualified source, not a synthetic form:

1. **Mode comprehension:** In a fresh tenant and an existing automatic tenant, authorized staff identify saved policy, draft changes, exact role/scope and future-versus-current application. Simulated fetch failure never shows a false saved default; refetch does not discard their draft.
2. **Protection:** Keep the same person manually, choose another person, leave an eligible role deliberately unassigned, then exercise relevant rule changes. All three protections survive. Use rules again explains and performs the mode-appropriate result without transferring unrelated roles/work.
3. **Rule exceptions:** Exercise overlapping ordered rules, ineligible first result, no match and departed person. UI and source agree; there is no unsafe fallthrough, false empty state or restored access.
4. **Finite group:** Select across pages, review/remove rows, change a matching record before acceptance and introduce one conflict. Only the accepted finite identities are attempted, with distinguishable recoverable outcomes and no per-row confirmation cascade.
5. **Recovery:** Delay/reorder replies, lose a successful response, navigate away/reconnect and retry. Exactly one accepted intent is represented; later manual changes remain current. Partial outcomes remain discoverable without a toast or full-directory reload.
6. **Policy transition:** Disable during outstanding work, then re-enable. Verify future-policy boundaries, honest in-flight results, preserved history and no stale-proposal sweep. Qualified handoff blockers remain actionable without disclosing protected work.
7. **Permission:** Revoke reviewer/recipient eligibility during selection and test restricted affected work. No unauthorized change or inference through names, reasons or counts; the user receives an appropriate permitted recovery path.
8. **Accessible usability:** Keyboard and screen-reader users complete individual/group review and settings changes; test 320 CSS-pixel reflow, zoom, long names, translated/RTL copy, touch and slow network. Participants can explain who is responsible now, what will change and the next action without coaching. Include authorized staff and relevant administrators, not a new missionary supervision surface.

No code, prototype, browser session, test suite, production mutation or pilot was performed for this appendix. Prior shared-control tests cannot prove these D30 flows. Documentation verification checks local references and whitespace only; the outcomes above remain product acceptance gates.

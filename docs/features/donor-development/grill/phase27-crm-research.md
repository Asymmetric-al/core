## Material conflict register

1. **Operational last touch versus meaningful contact.** #618 specifically defines `lastTouchAt` as greatest of latest CRM activity event and latest linked-task `updated_at`, while the founder request excludes generic record updates, notes and task maintenance from meaningful-contact recency. Recommendation: preserve the P9 operational field's honest meaning and use an independently named, source-backed meaningful-interaction measure for P27. If changing existing P9 semantics/labels is wanted, identify P9 owner and seek explicit amendment. Do not silently repurpose the field.
2. **General shared tasks versus read integration.** Preserve #1704 correction: #618 is Party read/link consumer, not missing general task engine prerequisite. Current service is a useful starting seam but lacks proof for atomic request/result/native reminders. Qualify the exact behaviors required, not a blanket phase dependency.
3. **Many role-qualified assignments versus edge uniqueness.** #607 active uniqueness `(tenant, from, to, relationship_type)` excludes role; one catalog family + singular role may constrain one staff person holding two roles on the same Party. This is an engineering/contract reconciliation to investigate before asking founder for schema choices. Never quietly change the accepted primary-owner meaning or invent parallel owner columns.
4. **Old “fresh build/no users” wording versus current census.** P9 plans delete legacy shape, but August local notes and later consumers are real source. Current user explicitly requires retained-data census. No production census performed; no conclusion that retained data is empty or safe to discard.
5. **Legacy support totals versus source-qualified measures.** Capped/raw/current scalar readers cannot prove full history, refunds, currency, entity or purpose. Maintain coverage/unknown signals and consume money-owner services; do not turn UI values into new materialized truth.

## Highest-leverage question recommendation

Begin with the **purpose and lifetime of one enrollment**: should it track an ongoing relationship for a particular organizational purpose, surviving individual asks, or a bounded fundraising effort with its own end? Preserve explicit source separation: Party assignment answers “who is responsible for this relationship,” enrollment answers “what development effort are we intentionally working on,” ask answers “what request did we present,” and task answers “what happens next.” Several purposes for one Party must not be collapsed into a single stage.

Subsequent activation choice: recommend deliberate enrollment, separate from staff assignment. Assignments form portfolios even for relationships not under active cultivation; starting an enrollment activates next-action obligations. This avoids bulk transfers/imports becoming silent outreach and leaves room for nonfinancial church partnership. This is a recommendation, not a ratified answer.

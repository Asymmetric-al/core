## Founder question — answered A

**When starting new partnership work, should Asym fill in a starting stage list
that staff can change, or ask staff to choose whenever several lists are available?**

A stage list is the organization's menu of stages for describing partnership
progress. This question applies only when a valid list has not already been chosen.
Neither option changes the list on existing partnership work.

**A — Prefill a clear starting choice (recommended).** If only one eligible list
is available, show it selected. If several are available, the organization may
choose a usual list to appear selected; staff can change it before starting the
work. If no eligible usual list is set, ask staff to choose.

**B — Ask whenever there is a choice.** If only one eligible list is available,
show it selected. If several are available, leave the selection empty and ask
staff to choose. There is no organization-set default.

In both proposed options, prefilling is visible and does not start work, select an
initial stage or contact anyone. Staff still deliberately start the partnership
work. A genuine zero-choice state follows D15 and provides a permitted recovery
path rather than a guessed list. The common sole-option behavior is explicitly
part of the offered initial-choice policies, not a behavior already ratified by D16.

**Recommendation:** A. It can reduce repeated selection for an organization's
usual work while keeping other approved processes available. It also permits
leaving the default unset when no single list is usually appropriate. B's strongest
benefit is preventing a preselected list from being overlooked when work regularly
uses different processes. The tradeoff is another choice on each start with several
eligible options. This is a product judgment; actual error rates or agency
preferences have not been measured.

## Pre-answer review frontier — preserved provenance

- If A is selected, qualify one optional organization-governed usual choice in
  the actual catalog/source scope. Do not introduce defaults by personal memory,
  Party type, screen, team, list rank, arbitrary first result or AI guess. No
  forced default is implied. Physical representation and configuration capability
  remain source-owner implementation decisions, not new entities or grants here.
- A default is usable only when currently eligible and permitted. Its existence
  or name must not be disclosed to an unauthorized person. Missing/unavailable
  defaults do not cause an arbitrary fallback; a proven sole eligible option is
  the explicitly offered common case, subject to source validation.
- A configured default change must not silently replace an established draft,
  submitted intent or accepted binding. User edits retain D16's visible dependent
  stage handling; source changes must be reconciled before acceptance. A restored
  list does not silently restore an old default under D15.
- Either option keeps list selection distinct from stage assessment, permission,
  journey identity, D4 admission, task effects and consent. No click on a picker
  or default change creates or alters partnership work.
- A reviewed group must expose and bind its actual member intent. A later default
  change cannot retarget members during execution/retry. Current eligibility and
  truthful per-member acceptance/reuse remain required.
- A saved-choice correction is still a separate operation and question. Neither
  option authorizes clearing a recorded stage, switching saved work, mapping by
  label, creating another ordinary journey or deleting/recreating a mistake.

## Recorded answer and completed review

The founder selected **A — Prefill a clear starting choice**, emphasizing clear,
beautiful, understandable UI/UX, visible options and next actions, and deep edge-case
review. The [full D17 adversarial review](phase27-d17-adversarial-review.md) evaluates
all 22 categories and records the exact decision, R01–R15, AC01–AC22, five evidence
appendices, four actual-source checks and nine isolated PostgreSQL checks.

**Disposition: Accept.** Preserve established valid intent. Otherwise show a proved
sole eligible list or, among several choices, a permitted usable organization usual
list; if neither applies, ask. The usual setting is optional, editable and clearable.
Staff can inspect alternatives and change the visible list before the ordinary
Start action. No additional acknowledgment, stage selection, automatic admission,
contact, hidden fallback hierarchy or change to saved work follows from prefill.

Default refreshes cannot replace established intent. Concrete submitted choices
survive retries and group execution; current eligibility and authority still apply.
Withdrawal, restoration, disclosure and configuration use the qualified source
boundaries in D15–D17. Actual list configuration validity is separate from whether
one particular starter can discover/use it. Shared form mechanics require deliberate
initialization handling; existing components do not by themselves prove the flow.

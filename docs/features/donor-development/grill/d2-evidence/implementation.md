# Phase 27 D2 — implementation, data integrity and operational review

> Evidence appendix, researched 2026-10-09. Findings are inputs to the
> [consolidated D2 review](../phase27-d2-adversarial-review.md), which
> reconciles recommendations and controls their decision status. This is
> grooming research, not a ratified specification or runtime qualification.

Research date: 2026-10-09. Decision under review: ordinary missionary-support cultivation targets the organization's **Ministry Assignment**, rather than a separate journey for each participating missionary person. D1's continuing purpose-specific journey remains accepted. This note evaluates D2; it does not decide enrollment uniqueness, purpose categories, stage rules, sharing, automatic entry or target-retirement disposition.

**Recommendation: keep the Ministry Assignment target.** It matches an existing accepted source identity and avoids person-keyed migration debt when couples, teams or participants change. No inspected implementation fact requires reversing D2. Several existing implementation patterns cannot safely be promoted into the new product unchanged. Their correction is an implementation/qualification obligation, not permission to invent a second Ministry Assignment, task engine, permission system or financial source.

## What changes technically, without prematurely choosing a schema

The ministry reference must resolve to one exact owner record rather than a profile, household, Page or financial account. That requires a typed owner read/validation seam, appropriate same-scope constraints, commands with current authority and revisions, and UI that distinguishes the source ministry from participants and responsible workers. **Scope precision:** a supporter Party can be Tenant-scoped; the Ministry Assignment is Tenant-and-Legal-Entity scoped. Do not invent a Party Legal Entity column or Party/Legal Entity composite FK. Enforce each source's actual constraints and the admitted enrollment context, including the ministry's exact Legal Entity where relevant.

One prospective dedupe meaning is “same supporter Party + same ministry + same independently established purpose + same relevant scope.” This is a candidate semantic rule, not a frozen key or unique index: staff/user, currency, reporting year and participant count must not accidentally split the same intended journey, but exact meaning depends on the as-yet unresolved purpose owner/identity and permitted concurrent journeys. Concurrent **same-intent** creation must nevertheless commit once and return the original authorized result. This does **not** yet require a particular enrollment table count, a generic polymorphic target catalog, “one per Party+ministry forever” uniqueness, an automatic agency parent enrollment, or a prescribed stage configuration language. Those would silently decide unresolved product semantics.

**Retained-data precision:** one legacy missionary profile may map to multiple real Ministry Assignments. That is an ambiguous mapping, not permission to copy every donor into every ministry, pick the primary/latest ministry, or create a shared target. Retain original source row and evidence; route only the unresolved association for authorized clarification while preserving unrelated valid records. Preserve legacy task/history identity where real, but import/retarget/backfill itself emits **zero newly approved cultivation task/message/stage events**. Any later activation must be a separately authorized source command. Cutover must reject old donor-profile/local-seed writers to the newly authoritative enrollment path; rollback may not re-enable those bypasses.

For new source work, implement the narrow P9-owned Ministry Assignment contract required by the consuming journey, with its owner review/qualification. Do not gate all of Phase27 on a full future website or missionary product, and do not invent a P27-local Ministry Assignment fallback. Missing exact source capability is visible/unavailable until delivered. The earlier [#1704](https://github.com/Asymmetric-al/core/issues/1704) correction still stands: #618/#1046 are read/source consumers, not missing general task prerequisites; extend the shared task owner end to end instead of treating whole phases as blanket blockers.

## Tests and evidence that would actually close these concerns

1. **Real PostgreSQL:** migrations applied to disposable local DB; actual grants, roles, RLS, same-scope FK/constraint failure, null/orphan/direct-writer denial, selected exposed-view/RPC boundaries. Use the privileged command role too, because service-role bypass is precisely why application filtering alone is insufficient.
2. **Two independent DB connections:** concurrent source retirement/reassignment, stale/ABA revision, stage change/task completion, duplicate command, same-purpose native/workflow attempt and deterministic lock ordering. Assert final rows/history/effect receipts, not only HTTP status.
3. **End-to-end actor/surface proof:** real authenticated admin and scoped missionary journeys against same backend, without mocked success or auth bypass. Cover people with several ministries and coupled participants with different permissions; prohibit hidden enrollment enumeration and aggregate leakage.
4. **Failure/recovery:** each commit boundary, lost response/readback, executor retries, unknown external success, owner revocation and suppression between preparation and dispatch, incompatible writer fencing, import/restore/rollback with no replay.
5. **Performance:** characterize pilot workload first; measure approved set-based queries and visible UI behavior at that scale. Existing code constants—100 gift detail rows, 50 activity/pledge rows, 50 CRM page rows and `maxPages: 8`—describe current truncation/cache, **not** acceptable P27 history or performance limits. Keyset pagination requires matching indexes and real measurement; no claim of constant total cost is made. No arbitrary capacity SLA is proposed.
6. **Concrete risk signals:** `unauthorized_development_disclosure`, `duplicate_accepted_source_purpose_effect`, and `accepted_invalid_source_scope` are proposed names for zero-tolerance qualification failures and investigated operational incidents, not product score dimensions or fabricated measured rates. Assert zero in the negative/race/migration fixtures; detection must retain only minimized authorized diagnostic evidence. Ordinary task backlog or timing telemetry may aid operators but no new alert threshold/SLA is ratified here.

Current tests inspected are useful unit/structural evidence only: `tests/unit/packages/api/admin/mission-control-tasks.test.ts:1–130,240` uses fake stores/`vi.fn`; `tests/unit/supabase/mission-control-tasks-migration.test.ts:14–77` searches SQL strings; CRM detail fixture test proves the >100 truncation flag. None proves D2 PostgreSQL atomicity, deployed isolation or complete source history. These tests were read, not run.

## Decision conclusion

Keep D2's Ministry Assignment reference. Its strongest technical benefit is avoiding false identity equivalence between a ministry and whoever currently serves there. The immediate safeguards preserve accepted owner contracts and do not materially expand D2. Material future choices still require founder decisions: what counts as a distinct purpose, permitted concurrent journeys, explicit activation, what retirement/split means for obligations, and which interactions each participant may see. This review must not be treated as ratification of those unanswered choices or as a complete specification.

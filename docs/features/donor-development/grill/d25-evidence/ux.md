# D25 UX evidence — gifts awaiting finance

2026-10-10 UTC / 2026-10-11 Asia/Bangkok. D25 A is selected. This appendix proposes the smallest coherent reporting and follow-through experience; it is not an implemented handoff, a new finance specification or a practitioner-validated prototype. Current source inspected at `225c02e9499bd6c0d493223cd4b1a4120ff787e3`.

## Recommendation and smallest useful flow

Keep A: the appeal can show **Awaiting finance** items and help staff reach the same qualified P15 intake. An item represents a particular reported gift/handoff, not an exclusive supporter category. A church can have one gift recorded by finance and another awaiting finance. Neither fact replaces the other.

Use three understandable moments: **report what is actually in hand**, **continue the same intake/handoff**, and **show finance's source-confirmed result**. These are explanatory moments, not three required forms, a frozen status enum or permission for P27 to write a contribution. The normal small flow needs an identified source item, a truthful physical-receipt report, a responsible follow-through person and only the relevant known details. Opening from an existing intake resumes it; staff must not re-enter the gift in a second appeal ledger.

Illustrative example, not an observed ministry workflow: Maria receives a church's check; Joel is responsible for getting it into finance. The permitted appeal view can show “Check awaiting finance,” “Received by Maria,” and “Follow-through: Joel,” with the appropriate next action. If the source later establishes that finance received the check, the current holder and action can change without claiming that the contribution is recorded. Once the source confirms the relevant financial record(s), show **Recorded by finance** and a permitted link. A source-owned action such as sending the original check can still remain. Financial recording does not prove physical handoff, deposit, bank clearance, irrevocable funds or pledge fulfillment.

The strongest B alternative keeps all pre-recording work in finance and ordinary tasks. It is smaller and avoids an additional appeal projection, but requires appeal staff to find unresolved handoffs elsewhere. A is worthwhile if it is one source-linked view with direct continuation, not a duplicate entry system or a custody-management product. This preference is product judgment. [Q25](../phase27-q25-gift-handoff-visibility.md):51–76 supplies the governing separation of financial truth, possession, responsibility and permissions.

## Exact proposed UX clauses

**UX01 — Start one source item, in context.** Within the appeal, provide **Report gift awaiting finance** only through the qualified source action. Carry visible appeal/context into the light intake; do not request raw IDs or repeat known supporter details. If an authorized existing source intake describes the same gift, offer to open/continue that item instead of starting another. The action records an operational report, so success says **Added to Awaiting finance**, not “Gift recorded,” “Funds received” or “Receipt sent.” P15 owns any staging and eventual financial write.

**UX02 — Capture what is known without making it up.** Record the permitted evidence that a specific gift was physically received, by whom, and with honest time precision; distinguish event time from recording time. A promise, an email saying a check is coming or an unposted draft is not this evidence. The reporter, current asserted holder and responsible follow-through person may differ. Label **Received by / Currently with / Responsible for follow-through** only as the source can actually establish them; do not invent a complete custody trail. An unknown current holder is a visible unresolved fact, not the last assignee by default.

Unresolved donor, value, currency or receiving Legal Entity can remain explicitly unresolved only through the qualified source reporting/repair path. This does not permit an incomplete financial commit. Avoid requiring a fake Party, arbitrary amount, USD default or guessed entity to report a real handoff. Distinguish **Donor not yet identified**, a known donor's anonymity preference and identity withheld from this viewer. An appeal's church contact is not automatically the legal donor/check payer. Unknown data and protected data must not share a misleading “Anonymous” label. No mandatory check photograph, bank-detail upload or duplicate donor search is added just to make the report credible.

**UX03 — Make the next work obvious.** A compact row/card shows the permitted gift descriptor, qualified current state, responsible person and next useful action, such as **Continue intake**, **Provide missing details** or **Open finance record**. Show a reported amount/currency only with clear pending meaning and current viewing permission; do not place it inside recorded funding totals. The smallest useful summary is an item count, accurately labeled and scoped. A pending item with unknown amount is still countable when authorized, but not money.

Keep at most one shared task identity for each source-backed work occurrence under [ADR-0183](../../../../adr/0183-source-owned-work-projects-into-one-shared-tasks-hub.md):24–100. Reuse an existing P15 handling/deposit task when it represents the same work; do not add a duplicate appeal queue. Each task ends only when its exact source-owned purpose is satisfied. Recording a contribution cannot close a still-required physical-handling task. Reading a notification or completing an ordinary task cannot record a gift, transfer possession or resolve the handoff. Show the real source due date/aging meaning when applicable; do not invent a universal reminder interval. Loss of an assignee requires qualified responsibility recovery, not a broadcast to all finance staff. The source remains discoverable to authorized staff even if no current eligible recipient exists.

**UX04 — Handoff changes responsibility or possession only when evidenced.** Reassignment changes who must follow through; it does not assert that the physical item moved. Recording a physical handoff requires the applicable source action/evidence and does not itself post a contribution. “Sent to finance” must not silently become “Finance has it” if receipt is unconfirmed. Avoid a mandatory transfer wizard or parallel custody ledger: expose only the next source-supported action and its truthful result. The previous report remains traceable when corrected.

**UX05 — Finance continues the same work, not a duplicate form.** The relevant finance actor opens the exact qualified intake with available context retained. Donor resolution, validation, designation, currency, entity, review and financial commit follow P15/P13 authority; P27 neither bypasses them nor adds its own duplicate entry. Staff without full finance access may receive a qualified limited handoff outcome, not a copied financial record or an unusable unrestricted deep link. A source read error or an unavailable intake is a repairable error; it is not permission to save locally and pretend the handoff exists. The feature must not ship a create action that only produces a 501 or an unowned note.

**UX06 — Financial recording and handling completion are independent source facts.** Use the owner-confirmed exact financial reference set to show **Recorded by finance**; separately show any actual remaining handling action. P15 allows entry and deposit independently: posting cannot imply that the original check reached finance or was deposited, and handing it to finance cannot imply posting. End only the source work whose particular obligation is satisfied. Do not infer either fact from matching donor/name/date/amount, draft existence, a staff checkbox or the first apparently related gift. Do not freeze one handoff to one financial row: the source must qualify split/designated or multiple-instrument cases. If some of the reported gifts are recorded and another remains outstanding, make both facts visible. Do not manufacture a “remaining amount” by subtracting unverified reports from unrelated financial totals. A smaller installment does not mean the whole pledge is fulfilled, and D25 does not decide financial attribution formulas.

Where source-reported terms differ from the original report, show a permitted correction/reconciliation explanation rather than silently rewriting the report or alleging a shortage. Posting, deposit, bank clearance, receipt generation/delivery and commitment fulfillment retain their own meanings. A later refund/return/correction updates the qualified financial projection; it does not blindly reopen an old handoff or resurrect ended tasks. New corrective work must have its own source predicate.

**UX07 — Correct the report without canceling reality.** Before submission, Cancel leaves no submitted item. After source acceptance, offer **Correct report** or the applicable source-owned withdrawal/duplicate-resolution action; explain its effect. Withdrawing an erroneous report does not destroy the physical gift, reverse money, cancel a donor promise or establish that no one must handle it. A lost item or unknown holder remains owned unresolved work with preserved evidence. Once finance has recorded money, corrections go through the financial owner rather than editing a P27 amount or deleting the pending record. Removing a supporter from the appeal or closing cultivation must not hide an outstanding financial handoff obligation.

**UX08 — Duplicate and uncertain outcomes get direct recovery.** Exact retry returns the accepted source item/result; it cannot create a second handoff, gift, receipt or task. A possible duplicate is a source-qualified comparison with a clear **Open existing intake** path and permitted distinguishing facts; equal amounts/names or a repeated check number alone are not proof of duplication. Show already-recorded evidence when established and avoid asking staff to enter the gift again. If save times out or the dialog closes mid-request, retain the submitted operation identity for status recovery and make clear that its outcome is unconfirmed. “Try again” must mean safe continuation/replay, not a new financial request. Preserve permitted edits on correctable validation failure and separate successful source acceptance from downstream notification failure.

**UX09 — Keep the interface calm and legible.** Place **Awaiting finance** beside relevant appeal facts with a plain item count and one primary contextual action; do not move the whole supporter into a Received/Given lane. Use readable sentence-case labels, short persistent help, semantic emphasis and full relevant terms. Error, no pending items, filtered no matches, loading and inaccessible source data require different messages/actions. Success should remain understandable if the item leaves the current pending filter, with a permitted link to the confirmed source result and history. No standalone money chart, receipt preview or control-total form is needed for the reporting step.

## Observable states and their next action

These are presentation conditions, not a new lifecycle enum.

| Known condition                                                         | What staff should see                                                                                                                                                                     |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Promise or check reportedly in transit; no qualified physical receipt   | Existing Request/follow-up facts. Do not label a gift in hand or Awaiting finance solely from that statement.                                                                             |
| Qualified physical-receipt report, follow-through pending               | **Awaiting finance**, current responsible person, permitted holder/evidence context and exact source continuation.                                                                        |
| Missing donor/amount/entity or uncertain holder                         | The specific permitted unresolved fact and its owner/action. No zero, fake donor, assumed currency or claimed financial completion.                                                       |
| Physical handoff recorded but finance has not recorded the contribution | Source-qualified handoff context; still awaiting the relevant finance action.                                                                                                             |
| Source confirms some, but not all, covered gifts                        | Distinct recorded and unresolved facts/items. No supporter-wide completion or invented arithmetic.                                                                                        |
| Source confirms the relevant financial record(s)                        | **Recorded by finance** with permitted reference/history and any still-required handling action. No implied physical handoff, deposit, clearance, receipt delivery or pledge fulfillment. |
| Invalid/duplicate report corrected                                      | Traceable source disposition and remaining real obligation, if any; no silent deletion or cancellation of money.                                                                          |
| Source load fails, operation outcome unknown or viewer loses access     | Unavailable/uncertain state with safe recovery. Never show zero awaiting, empty donor, completed work or unrestricted details as a fallback.                                              |

Acceptance on the actual implementation must demonstrate:

1. Report a physically received check with reporter, holder and responsible person differing; then hand it to finance and continue the same intake. Distinguish the two events from financial recording without duplicated entry.
2. Report with honestly unresolved donor/value/currency/entity through the admitted source path. Identify required next repair without creating a fictitious Party, zero gift or guessed currency; block financial commit until its owner requirements are met.
3. Start from an existing qualified intake and from the appeal; converge on the same source identity. Test duplicate suggestions and exact retries, including two legitimate similar gifts.
4. Record one gift while a second remains pending for the same supporter; test partial/multiple-source resolution and protected actuals. Recorded totals never incorporate pending reports or duplicate source references.
5. Change responsibility without asserting physical movement; record receipt by finance separately; lose an assignee or holder. Test posting while the original check still needs handoff/deposit and physical handoff while posting is pending. Keep each exact source action discoverable and routed only to eligible actors; reuse existing handling/deposit work without duplicate tasks or closing the wrong purpose.
6. Correct a mistaken report, resolve a duplicate, close/remove appeal work, and process a later source refund/correction. Preserve history and real unresolved obligations; no P27 money rewrite, forged cancellation or stale task resurrection.
7. Inject validation failure, unavailable source, dropped success reply, close during save, stale updates and permission loss. Recover the same operation with correct permitted current facts and no duplicate gift/task/notification effect.
8. Exercise keyboard, screen reader, touch, 320 CSS-pixel reflow/equivalent zoom, long translations, RTL, explicit currency/date presentation and light/dark themes. Persistent labels, errors and outcome announcements work; overlays/mobile keyboards do not cover focused fields or next actions. Physical-event calendar dates do not shift with the viewer's timezone. Test the actual composed flow, not only shared controls.
9. In a moderated staff/finance pilot, participants explain what is physically reported, who acts next, whether finance has recorded the gift and what remains unknown. Complete one report/handoff/recovery without coaching or retyping already supplied data. Record confusion and iterate; no usability, speed or aesthetic result is yet measured.

## Primary comparison and accessibility evidence

Fresh primary retrievals on 2026-10-10 UTC:

- [MPDX Track an Appeal](https://help.mpdx.org/article/191-track-an-appeal), updated November 2, 2021, distinguishes in-hand Received from donation-system Given. It is a real published ministry-product comparison, not recent runtime validation. Its editable amounts/contact buckets and color-coded totals must not override Core's owners or nonexclusive item facts. A fresh attempt to open the separate Flows guide failed; that page is not additional proof for this appendix.
- [Blackbaud Approve a Batch](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-gift-batch-approve.html) separates entering gifts from the action creating gift records and describes asynchronous completion. It supports visible source progress/result, not a new mandatory P27 approval step or proof of physical custody.
- [Salesforce Track Gift Transactions](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-fundraising-operations/track-gift-transactions) distinguishes Gift Entry from processed transactions and links to resulting records. It also explicitly includes unpaid expected transactions, so “transaction exists” is not universal evidence of received money. Its product workflow/capacity is not Core policy.
- [W3C form instructions](https://www.w3.org/WAI/tutorials/forms/instructions/) and [redundant entry](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html) support persistent guidance and reuse of information within the process; they do not mandate cross-session persistence or bypass source validation.
- [WCAG error prevention](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html) supports correction/reversal or suitable review, without requiring another confirmation for every ordinary save. [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) supports accessible waiting/error/result feedback.
- [Base UI Dialog](https://base-ui.com/react/components/dialog), [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) guide focus and responsive composition; actual consumer testing is still required.

No new UI/prototype test, browser run, live finance operation, database mutation or source activation was performed. Existing offline form/route test names and current code were inspected, not rerun; their mocked/disabled legacy path does not qualify D25. This appendix verifies document links and source citations only. The source-qualified handoff/read/continuation seam and the actual product proof above remain release prerequisites, rather than reasons to build a P27 shadow writer.

## Founder question — A selected

**When starting new partnership work, should staff choose from the organization's
approved stage lists, or should the organization also be able to restrict which
lists can be used for particular kinds of work?**

A stage list is the menu of stages used to describe a partnership's progress.
For example, an agency might have lists called “Missionary support” and “Church
partnerships.” The question is whether authorized people use judgment to choose
the fitting list, or whether organizational rules further limit their choices.
These names illustrate the distinction; they do not establish a mandatory process
taxonomy or verified universal ministry practice.

**A — Let staff choose the appropriate approved list (recommended).** Use the
shared organization-approved choices available for new work, within existing
source and permission boundaries. Names and short guidance explain their purposes.
This keeps setup simple and gives staff flexibility without another rule system.

**B — Let the organization restrict choices by kind of work.** An organization
can define a narrower allowed set for particular kinds of partnership work.
This can prevent mismatched choices, with additional configuration to maintain.

**Recommendation:** A as the smallest coherent policy. B is appropriate if the
organization needs to enforce process-specific choices rather than guide them.
This is a product judgment, not evidence that agencies universally prefer A or
that extra applicability rules are inherently wrong.

## Boundaries and consequences to review after the answer

- “Approved choices” means current new-use choices in the actual governed catalog
  and source scope. Neither answer reveals hidden configuration, grants record
  access, crosses tenants/entities, or turns list selection into authorization.
- A would decline an additional process-specific restriction layer. It would not
  remove existing source validity, disclosure, admission or permission checks.
  An available name alone does not make a journey legitimate under D2/D3/D4.
- B would authorize bounded applicability configuration. The actual grouping,
  exceptions, editing authority, zero-choice behavior and effect of later changes
  would then need explicit qualification. Do not silently invent a “partnership
  type” entity, per-ministry rules, team hierarchy, new ACL or general rule builder.
- Either answer still leaves one source list and one stage/valid absence per
  journey. Neither changes an existing journey's binding, requires a repeated
  picker, duplicates an ordinary partnership, switches lists by surface or infers
  an initial stage.
- Initial list suggestions/defaults, exact starting-form behavior and any later
  list-switching facility remain dependent decisions. A known valid source choice
  must not become a new unnecessary question, and array order is not a default.
- Ratified D15 continues to govern unavailable lists and retained work. No fresh
  admission is allowed merely because staff can still use that list elsewhere.
- Both options preserve deliberate human admission, clear context and the normal
  stage/lead/next-action experience. Choice alone creates no task or donor
  interaction; actual admission retains D4's required source-owned work.

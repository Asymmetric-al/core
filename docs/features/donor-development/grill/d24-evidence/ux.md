# D24 UX evidence — an appeal's recorded working audience

2026-10-10 UTC / 2026-10-11 Asia/Bangkok. The founder selected D24 A. This is research and proposed ordinary product design, not an implemented appeal UI or a formal specification. Source inspected at `225c02e9499bd6c0d493223cd4b1a4120ff787e3`. No product changes or tests were performed.

## Recommendation: one usable working list

Keep A. The appeal has one **Working list** of supporters, with **Add supporters**, useful search/filtering and contextual actions. A saved filter helps find candidates; accepting a finite selection deliberately adds those supporters. Later filter matches, edits or deletion do not change the recorded audience. Keep this distinction in concise help near candidate selection, not a mandatory acknowledgment or technical explanation of snapshots.

For example, an authorized user selects 40 churches for an appeal. A church later stops matching the search criteria; its recorded inclusion does not silently disappear. Another newly matches; it is not automatically added. Existing request/response history remains attached to its real subject. Names and eligibility can change independently: a recorded list does not freeze personal details, consent or access rights.

Three planning meanings are sufficient: **included**, **excluded**, and **removed**. Do not turn them into a custom workflow, a kanban progression or three parallel administration tools. The main list shows included entries; excluded entries and membership history are deliberately discoverable through concise filters/navigation. **Remove from working list** ends planned inclusion; **Exclude from this appeal** records the explicit instruction not to approach through this appeal. Both stop new appeal-planned work and preserve history. Both require a fresh, authorized **Return to list** to come back; plain Add, refresh and retry do not undo either decision. Their distinct intent belongs in readable history, not duplicated configuration panels.

The strongest B alternative is an audience that follows a saved filter automatically, with independent historical asks/response retention. It reduces manual maintenance for changing populations but makes planned membership change independently of an appeal-specific staff choice. A provides clearer coordination for this selected product direction. Neither choice changes communication permission, finances, Request review or task ownership. These boundaries come from [Q24](../phase27-q24-appeal-working-audience.md):57–83, subsequently answered A; preference for A is product judgment, not measured ministry feedback.

## Exact proposed UX clauses

**UX01 — Add one or a group in the same context.** **Add supporters** opens permitted candidate search from the named appeal. Show enough permitted identity context to distinguish similarly named people/churches. Do not require a new partnership, Request, task, recipient list or amount for membership. A single-row add can use the same ordinary action without a group wizard. Multiple selection culminates in a readable finite set and an explicit **Add N supporters** action. No new approval or typed confirmation is required merely to plan inclusion.

**UX02 — Make selection scope explicit.** Label the header for what it actually selects, such as **Select 25 on this page**; with nonpaginated loading, name the loaded scope accurately. Never use “all” to imply server-wide matching rows merely because every loaded row is checked. A separately supported **Select all N matching supporters** must resolve an authorized, complete, bounded candidate set before acceptance; unknown/partial counts cannot masquerade as complete results. Staff can inspect and deselect that set without opening every record or acknowledging every row. If complete capture cannot be supported, offer truthful page/individual selection rather than silently truncating results.

Keep explicit selected identities while staff navigate pages or candidate filters, show total selected and any outside the current view, and provide a working **Review selected** / **Clear selection** path. A global clear really clears the complete selection. Keyboard selection must have the same documented scope as its visible counterpart; it must not unexpectedly broaden an action. Changing filters may change candidate results, never silently substitute the selected supporters. Sorting or names changing must not rebind checkmarks to different people.

**UX03 — Capture a finite intent, then record truthful results.** At acceptance, use the reviewed set, not a query rerun later. Show preparation/loading separately from saved membership. A supporter who begins matching after capture is not added by the current operation. Current access, scope, exclusion/removal and contact rules are rechecked at the source; stale eligibility is not a promise of success. An authoritative same-member result is **Already on the list**, not a duplicate row. Previously excluded or removed entries remain unchanged by ordinary Add and have a permitted **Return to list** path. A changed candidate set needs a fresh deliberate selection, not an automatic broadening of the accepted one.

**UX04 — A working row explains reality and the next action.** Prioritize supporter, permitted responsible staff/context and the relevant actual Request/response or next-work summary. Membership alone means **On working list**, not asked, accepted, committed or funded. Actual Request facts remain source-backed; a drag, checkbox or list-status change cannot create them. “No Request recorded” requires an authoritative permitted read; unreadable or unavailable facts are not “Not asked.” Do not introduce response buckets as editable financial statuses, a completion percentage based on membership, or a new task for every list entry. Existing admitted action requirements and shared tasks remain authoritative.

**UX05 — Remove and exclude without losing what happened.** Contextual **Remove from working list** explains that the entry leaves planned work and its actual history remains. **Exclude from this appeal** explains the appeal-specific do-not-approach decision. A concise optional note can help future staff; no universal reason taxonomy or additional required review form is needed. These actions do not delete the Party, revoke general consent, remove unrelated appeal membership or cancel source-owned financial commitments. If the supporter was already asked, preserve the Request, reviewed/presented terms, response and confirmed outcomes and make them reachable from permitted history. Removal/exclusion must never make it appear the earlier request did not happen.

Both actions end only the appeal-specific future work that the owning source proves no longer applicable. Do not silently close unrelated shared tasks or erase an open response/financial obligation. When appeal-linked outward work is pending, present its actual owner-qualified stopping/cancellation outcome; “excluded” must not imply recall of a message already sent or a conversation already held. No new delivery integration is claimed by this clause.

**UX06 — Return is deliberate and currently checked.** Use one **Return to list** action for excluded/removed entries, with the relevant prior meaning visible. Validate the present Party, appeal scope, actor and eligibility; retain the old removal/exclusion event and actual outcomes. Return does not reset an already-asked person to unasked, duplicate a Request, clear suppression, resend a message, reopen a closed partnership or revive ended tasks. An old Add receipt/retry cannot return someone whom staff later removed. Returning membership is a new current intent, not erasing history or blindly undoing later work.

**UX07 — Current restrictions and organizational contacts remain independent.** Lawfully retained inclusion can stay visible after a contact restriction changes, with permission-safe indication that further action is unavailable. Do not automatically remove or return membership when consent changes. Do not expose protected restriction reasons, hidden names or counts simply to explain selection. New candidate suggestions and actionable inclusion must satisfy the current owner rules. Listing a church records that Party; it does not select all its pastors, members or email addresses as recipients. Any later communication resolves its actual recipient and purpose independently.

**UX08 — Merge and continuity need visible reconciliation, not silent duplication.** A canonical identity update may affect two rows or a pending selected set. Use the qualified Party-owner result, preserving both membership and Request provenance without double counting support or multiplying contacts. When previously distinct entries conflict—especially included versus excluded/removed—do not choose the more permissive result or let a name change conceal the conflict. Show an authorized, understandable reconciliation state and current permitted source link; uncertain future outreach remains unavailable. No new merge/split taxonomy or autonomous identity correction is introduced here.

**UX09 — Results remain useful after the toast.** For a group operation, show durable permitted outcomes such as **17 added · 2 already listed · 1 could not be added**, with an inspectable recovery list where allowed. Distinguish skipped prior exclusions/removals from transient failures without revealing restricted records. Retain the accepted selection identity across a lost reply and recover the same operation's results. Retry cannot re-run a live filter or overwrite a later membership decision; retry only unresolved work under the source contract. A successful row leaving the current filter gets an understandable success message and permitted destination, not an apparent failed save. A pending operation has an honest progress/uncertain state; closing its UI does not promise server cancellation.

## State and count clarity

| Situation                                                      | Visible meaning and action                                                                                                              |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| No recorded entries, authoritative successful read             | Purposeful empty state and **Add supporters**, if permitted.                                                                            |
| Working-list filter has no matches                             | **No supporters match these filters** and **Clear filters**; do not imply the appeal is empty.                                          |
| Candidate loading / saved filter failed / partial pages loaded | Loading or retry; disclose incomplete scope. Do not enable an inaccurately labeled all-results action.                                  |
| Selected candidates beyond current filter/page                 | Retained total selected with inspectable set and complete clear; final action count matches submitted identities.                       |
| Already included / previously excluded / previously removed    | No duplicate; preserve prior decision and offer only the appropriate current authorized action.                                         |
| Access lost or row no longer safely describable                | Remove protected presentation and give permitted recovery; no fabricated removal, completed task or global count hint.                  |
| Old history after removal, return or merge                     | Preserve actual facts, with their timing/provenance and lawful access; do not conflate historical inclusion with current actionability. |

Counts must name their scope: current working list, selected candidates, filtered visible results or historical facts. Only show a complete total when the source can authorize and establish it. Loading/errors/restricted reads never become zero. History and current inclusion overlap; do not add their counts into a misleading total. Source-confirmed monetary rollups retain financial-owner rules and are not manufactured from audience membership.

## Material risks and measurable acceptance

These are prospective D24 risks with qualitative severity/likelihood, not measured incidents or verified vulnerabilities in a shipped appeal feature.

| Risk                                                                 | Severity / likelihood                           | Permanent prevention and proof                                                                                                                                                                                       |
| -------------------------------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| “All” affects a different population from staff's selection          | High / plausible given shared scope differences | UX02–03: test header, keyboard, multiple pages, filtered hidden selections and complete capture. Submitted stable identities exactly match the readable accepted set.                                                |
| Refresh/retry re-adds removed or excluded supporters                 | High / plausible                                | UX03,05–06: remove/exclude during an in-flight Add, then replay it. The newer decision survives; only fresh authorized Return changes it.                                                                            |
| Membership becomes contact permission or a financial/response fact   | High / plausible                                | UX04,07: included restricted church produces no recipients, sends, approval, commitment, gift or fabricated response; current eligibility remains independent.                                                       |
| History disappears after cleanup or merge                            | High / plausible                                | UX05,08: remove an already-asked entry, return it and reconcile a duplicate identity; retained Requests/outcomes remain truthful with no duplicated money or action.                                                 |
| Partial failures require redoing successful work or leak hidden rows | High / plausible                                | UX09: inject item failure, dropped reply and access loss; recover permitted per-item outcomes without duplicating accepted effects or exposing protected identities/counts.                                          |
| Three planning states become unnecessary administration              | Medium / plausible                              | Keep one main working list, contextual actions and one return path; no per-entry approval/task, mandatory reasons, status builder or repeated setup screens. Pilot must distinguish remove/exclude without coaching. |

Required actual-product acceptance:

1. Add a single supporter and a reviewed group using search and an available saved filter. Change the filter, qualifying data and saved-view availability afterward; recorded membership remains deliberate and history remains accessible as permitted.
2. Select across pages/filters; change sort/name; clear globally; test keyboard equivalence and mobile selection. Final selection count and every accepted identity agree. A partial or failed all-results preparation cannot claim completeness.
3. Change current eligibility and membership after capture. Produce honest accepted/skipped/failed outcomes. Adding the same supporter twice yields no duplicate, and an old replay cannot undo later removal/exclusion.
4. Remove and exclude both an unasked and an already-asked supporter; deliberately return them. Preserve factual Requests, review and responses; stop only qualified future appeal work and do not fabricate recall, consent or fresh unasked status.
5. Apply contact restriction changes, organizational contact changes and a qualified Party merge with conflicting membership. Verify protected displays/counts, current recipients, history and source-owned reconciliation rather than a permissive automatic winner.
6. Inject slow pages, candidate failure, lost success reply and partial batch failure. The selection/result remains understandable; retry recovers its same finite intent and does not repeat successful effects or substitute current matches.
7. At 320 CSS pixels/equivalent zoom, use keyboard, screen reader and touch with long translated names/RTL. Supporter checkbox names, mixed header state, selection scope, errors and results are understandable; no essential action requires hover. Floating controls/mobile keyboards cannot cover focused rows, change controls or result recovery. Preserve light/dark contrast and Core touch targets; check actual shared composition, not only primitive demos.
8. In a moderated pilot, staff explain who is on the working list, who is selected for a pending change, who has actually been asked, and who cannot currently be approached. They complete remove/exclude/return and partial-failure recovery without facilitator explanation. Record confusion and iterate; no time-saving or aesthetic result is yet measured.

## Primary research and evidence limits

Freshly retrieved 2026-10-10 UTC:

- [HubSpot: Create segments](https://knowledge.hubspot.com/segments/create-active-or-static-lists), updated September 14, 2026, explicitly distinguishes automatically changing active segments from point-in-time static membership with manual additions/removals. It distinguishes processing preview from final count. This supports clear capture semantics, not Core's authorization or source-history guarantees.
- [HubSpot: Add/remove segment records](https://knowledge.hubspot.com/segments/add-or-remove-contacts-from-a-list), updated June 5, 2026, uses saved views to find candidates, individual/page selection, and explicitly says static-list removal does not delete the CRM record. Its product-specific size limits and workflows are not Core requirements.
- [Mailchimp: Archive/unarchive contacts](https://mailchimp.com/help/archive-unarchive-contacts/) distinguishes visible selection from selecting beyond the screen and restores current subscription status separately from audience presence. Useful contrasts only: Core must not copy its typed confirmation ceremony or import-triggered automatic unarchive behavior.
- [W3C checkbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/) and [Base UI Checkbox](https://base-ui.com/react/components/checkbox) describe named, keyboard-operated checked/mixed states. A mixed checkbox does not by itself communicate page/server selection scope; the consumer supplies that meaning.
- [WCAG status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) inform async feedback and falsifiable accessibility checks, with their stated scope/exceptions.

Current source establishes reusable controls and important consumer obligations; it does not establish a qualified appeal service. Vendor documentation demonstrates its own product behavior, not missions-staff preference or a Core implementation. No browser, user pilot, full UI accessibility evaluation, database probe or test suite was run for this appendix, as requested. Link and document integrity are the checks performed; all actual UI proof above remains a future acceptance gate.

# D4 — database, reviewed groups and durable admission

Research-only review, 2026-10-09, checkout `225c02e9499bd6c0d493223cd4b1a4120ff787e3`. Parent supplies the founder's selection: an authorized human deliberately starts ordinary cultivation, individually or in a reviewed group. The checked-in Q4 question still says unanswered; this review uses the later answer supplied by the parent. D1, amended D2 and tightened D3 remain binding. This is evidence for the D4 decision review, not implementation, an approved physical schema, a production finding, a migration or permission to contact donors.

**Recommendation: retain deliberate individual/reviewed-group admission. Use one source command for both, a fixed reviewable selection for group work, and atomic acceptance of each journey with truthful recoverable partial results.** A background worker may finish an already reviewed bounded operation without becoming an automatic source of new selections. Ordinary PostgreSQL transactions, constraints and source-owned durable receipts are sufficient; D4 needs no new batch framework, rule builder or approval queue.

The group is a convenience for expressing several deliberate intentions. It must not silently mean “whoever matches this saved search whenever a worker runs.” Atomicity of one journey's source/history/required obligation is mandatory; an all-or-nothing transaction across unrelated supporters is not implied by reviewing them together. Exact user-visible partial-result behavior is a proposed implementation requirement for ratification, not a silently accepted new lifecycle or result enum.

## What the actual CRM and batch code establishes

### Selection is currently a loaded view, not a durable group authorization

`packages/database/hooks/admin-crm-infinite.ts:77` requests pages of 50; `:192–207` keys its infinite query by filters/sort and retains at most eight pages, with previous data as placeholder; `:210–220,228–255` constructs and replaces the local loaded collection. `apps/admin/app/(app)/crm/page-client.tsx:521–540,569–578` passes those rows to the shared table with infinite loading, manual sorting/filtering and row selection.

The shared checkbox calls `toggleAllPageRowsSelected` at `packages/ui/components/shadcn/data-table/data-table-responsive-inner.tsx:294–307`; the action bar derives selected original rows from `getFilteredSelectedRowModel` at `data-table-action-bar.tsx:67–72`. These are useful selection controls, not proof of all matching CRM records, persisted identity across page eviction, or reviewed source-purpose meaning. None is an admitted group manifest. The current CRM bulk archive explicitly says unavailable (`page-client.tsx:68–69`), while export uses the donor report slice rather than supplied selected IDs (`:72–80`). D4 must not infer selection semantics from that export behavior or label the existing grid an enrollment facility.

### Contribution batches have useful components and important reuse limits

- `packages/api/src/admin/contribution-batches/route.ts:32–80` accepts explicit record IDs, caps that domain's request at 1,000 and rejects duplicate IDs. This is better evidence of bounded explicit membership than a live query. Its numeric limit is contribution-specific, not a proposed D4 capacity.
- `route.ts:100–147` hashes action/IDs/payload and checks a caller-supplied count/hash for high-risk actions. The `previewId` need only be nonempty (`:39–45`); the inspected validator does not look up a server-owned review record, actor, scope, source revision or expiry. Self-consistent caller inputs are not proof that a human reviewed an authoritative preview. This is a source-validation limit, not a statement that a cryptographic review-signature service is necessary.
- `route.ts:193–246` persists the batch then its items in separate Supabase calls; on item failure it attempts a compensating failed marker. Those calls are not one database transaction. The first POST has no durable start-operation lookup in the inspected route. The migration `20260526202500_contribution_operation_batches.sql:3–53` gives batches/items generated IDs but no start-command uniqueness key; the table is service-owned (`:64–71`). Do not copy this admission shape as a proof of atomic manifest creation or idempotent lost-response recovery.
- `apps/admin/app/(app)/contributions/main-body.tsx:369–391` creates a fresh confirmation token while no received batch response is remembered, then remembers continuation only after response parsing. `:405–440` usefully resumes a known batch and reports failed/partial outcomes. If the first persisted-create response is lost, that in-memory continuation does not establish recovery of the same group; it can submit a new batch. This does not establish that every contribution effect duplicates: underlying action owners have their own idempotency behavior.
- `process-batch.ts:414–464` first selects pending IDs, then updates only rows still `pending` and processes the IDs actually returned. The conditional update is an important competing-claim guard; do not incorrectly call this an unconditional read-then-write claim race. It still does not provide a permanent source receipt or worker-fencing guarantee.
- `process-batch.ts:78–134` executes items and catches per-item failure, then `:664–723` stores returned outcomes afterward in separate calls. A source effect can commit before its batch status is recorded. Stale recovery (`:37–38,364–378,593–607`) marks old running/open items failed; final writes (`:706–719`) do not match a worker claim token or expected running revision. Timeout alone is not proof that the source did not commit, and no lease fence is visible in that final update. This is a concrete unsafe shape to copy for D4; actual impact depends on the action owner and runtime ordering.
- `process-batch.ts:236–248,528–546` restricts processing to the batch creator when set and reruns the action-permission assertion at request entry. `route.ts:340–369` supplies current actor capabilities. These are useful controls, not the full accepted P12 exact source/field/context/epoch contract, especially across a long-running group.
- `preview.ts:12,139–151` chooses immediate versus background execution; `process-batch.ts:16` uses chunks of 25. These are existing contribution implementation settings, not measured optimal D4 limits. The batch is still processed through source actions, a useful ownership pattern.
- `tests/unit/packages/api/admin/contribution-batches.test.ts:410–485,1275–1317` uses fluent-query mocks to model these paths. It does not exercise real PostgreSQL conflicts, policies or crash boundaries.

### Task creation, notes and shared jobs are seams to qualify, not new engines

`packages/api/src/admin/mission-control-tasks/service.ts:62–77` and `store.ts:75–123` insert task, links and event through separate calls. A journey requiring valid next work cannot rely on this call sequence alone to commit the journey/task/association/history together. Reuse the shared task owner with a qualified atomic boundary; do not create another task engine or mechanically generate one administrative task per selected row when suitable existing work satisfies the invariant.

`packages/api/src/admin/crm/notes/service.ts:190–244` has tenant-scoped idempotency lookup and a reload after `23505`, which is useful precedent for unique-backed retry handling. It returns the existing note without matching the new input fingerprint in that branch; command logging occurs afterward (`:256–275`). Therefore it is not a ready-made D4 command receipt/atomic history contract. D3's hidden-row reuse protections still apply.

`packages/api/src/shared/with-operation.ts:128,145–163` obtains authenticated context and generates a new correlation request ID per HTTP request. That ID is not a stable logical admission key. The service client and broad role gate do not themselves prove source eligibility or human review.

`packages/api/src/admin/support-hub/move-service.ts:297,324–382` uses explicit IDs and product work claims; `:389–411` stores the operation after item effects. Retry reads previous items before its batch claim (`:446–470`), retries failed IDs and preserves successful items (`:457–499`), a useful partial-retry design. However its retry-result `.update` is awaited without checking the returned error (`:502–509`) and success is then returned (`:511–516`); the shape does not prove durable truthful status on persistence failure. “Already at destination” is treated as previous success in this move-specific code (`:359–365`), which must not be generalized into “journey exists, therefore this reviewed command committed.” Existing other-domain code merits qualification, not unquestioning reuse.

`packages/api/src/workflows/claims.ts:22–38` calls the existing scoped work-claim RPC. `supabase/migrations/20260611181000_workflow_work_claims.sql:71–88` expires old active claims and inserts a new active claim under a partial unique arbiter. Expiry permits another attempt; it does not cancel the old worker, prove an effect failed, or permanently suppress a replay. D4 may reuse qualified durable execution/claims without making Workflow Studio configuration a prerequisite or treating service credentials as human admission.

## Required decision wording and ranked concerns

Severity describes the consequence of the named mistake; likelihood is conditional engineering judgment, not measured incident frequency. These preserve D4 unless a wording clarification is expressly proposed.

### DB4-01 — reviewed scope expands before execution

**High severity; high likelihood if a saved query is rerun. Clarify D4.** New matches, sort/page changes or changed ownership may silently add unreviewed people. A loaded page can also be mistaken for every match.

**Exact prevention:** “A reviewed group binds an explicit bounded selection and the intended ministry/purpose/action, with attributable human review. Execution and retry use that same selection; newly matching people require new deliberate selection. A saved query may help assemble candidates but is not continuing authority to admit future matches. Distinguish selected loaded rows from a reviewed complete result set.”

The stored reviewed selection can be a small source-owned command payload plus durable receipt; do not mandate a new generic manifest service. For cross-page groups, materialize server-validated IDs and approved meanings before processing. A hash identifies unchanged content but proves neither current authority nor human review by itself. Holding an MVCC database transaction open while a person reviews is not an acceptable substitute.

**Acceptance proof:** review A/B, then add C to matching data before execution; only A/B are considered. Add/remove filters, page eviction, same-name rows, renamed/merged sources, repeated IDs and modified ministry/purpose after review; no silent expansion or reassociation. The user can understand the actual selected membership/count without exposing hidden work. No current D4 implementation proves this.

### DB4-02 — first lost response creates a second operation

**High severity; plausible on ordinary network interruption. Clarify D4 retry semantics.** The current contribution continuation only remembers an operation after receiving it. A new server correlation ID or confirmation token on each retry cannot recover the original operation.

**Exact prevention:** “Preserve one stable logical command identity and the reviewed input meaning across submission, reload and retry. The source atomically accepts that intent once and retains an attributable result/receipt. Same key with different membership or meaning rejects; a repeated exact intent resolves the original permitted result rather than creating another group, journey, initial task or stage event.”

Bind the key to appropriate source scope and admitted command meaning, with a uniqueness constraint. Do not infer original command success merely because another actor created the relationship. Preserve current permission when retrieving old receipts. Resource identity, group-command identity and accepted task/message effects remain distinct; no new receipt namespace from changing a label or worker.

**Acceptance proof:** connection lost immediately after group receipt commit and after a journey commit; retry after tab/browser restart; duplicate concurrent POSTs; changed payload under the same key; two distinct reviewed groups containing the same ordinary supporter/ministry. Exactly one admitted journey/initial obligation for the same intended ordinary work and no mutation of hidden existing facts. Output may say unresolved until authoritative reconciliation; it may not assert failure from a network exception alone.

### DB4-03 — compound acceptance is only partly committed

**High severity; concrete risk if current task/batch call sequencing is copied. Preserve D4; require source atomicity.** A journey can exist without its next work, source association, history or receipt; a batch can start without its stored reviewed items.

**Exact prevention:** “Commit acceptance of the reviewed group identity/membership consistently before work proceeds. For each journey, commit the source result, attributable history/receipt and the required valid local next work or owned actionable exception atomically. Queue only necessary durable effect intent inside the proper owner transaction; no browser multi-call sequence represents that transaction.”

Use a narrow server-owned PostgreSQL function/RPC or approved transaction-capable owner path. Scope/deduplication/expected revision checks belong inside that boundary. Linking already appropriate work is valid if its owner contract permits it; every row does not require a duplicate task. External effects remain with existing owners and cannot share a cross-provider SQL transaction.

**Acceptance proof:** failure after every constituent write, including task association/history/receipt; none leaves half an accepted journey. Manifest/item persistence failure does not start an unreviewable group. Actual SQL transaction tests and actual service invocation are required; mocks only establish control flow.

### DB4-04 — whole-batch atomicity is promised without need or partial success is concealed

**High severity for false results; medium-high likelihood if generic bulk UI is copied. Proposed clarification, not a forced physical strategy.** One invalid independent person may unnecessarily roll back all good work, or a success toast may conceal only some completed items.

**Exact prevention:** “A reviewed group preserves the atomic contract of each individual journey. Where independent items may complete separately, report and retain each authoritative outcome and permit recovery of unresolved work without rerunning confirmed successes. Do not promise the whole group is all-or-nothing unless the accepted interaction explicitly requires and implements that behavior.”

Recommend independent per-journey commits for unrelated supporters, with group progress derived from durable item receipts; this bounds lock duration and failure blast radius without an arbitrary batch size. Reject an invalid shared command shape/context before starting; handle later item-specific change/denial honestly under current authority. A small single-transaction group can be valid when its product contract genuinely needs it. Savepoints can isolate an item's failure within an outer transaction, but released savepoints are not independently committed or visible before outer COMMIT; they do not prove durable progress to a worker/client mid-batch. A DB function called through one RPC cannot be assumed to commit each loop iteration independently.

**Acceptance proof:** mixed new/reused/ineligible/changed/denied items; failure at item two; client disconnect during processing; results after restart agree with actual source receipts. Confirmed success survives later independent-item failure only when per-item commits are the chosen contract. Counts never imply disclosure of hidden existence or successful admission when an item remains unresolved. Cancellation stops unstarted work through the source contract and never deletes already admitted history as a fake rollback.

### DB4-05 — stale worker or timeout manufactures failure/success

**High severity; plausible under delayed requests/crash recovery. Preserve D4.** Current batch action and status updates are separate; running-item timeouts and expired work claims do not establish source outcome. An old worker can finish after another path marks an item failed or cancellation is requested.

**Exact prevention:** “Resolve ambiguous outcomes from authoritative source receipts before retry or terminal status. Processing ownership and completion writes must honor current attempt/expected revision where needed; expiry alone does not authorize a repeat accepted effect. Late workers cannot overwrite a newer disposition. Reconcile progress rather than marking a committed source result failed.”

An existing guarded pending-to-running claim may be sufficient to assign a fresh attempt; it is not permanent idempotency. Use qualified source command receipts and any required fencing in the existing execution owner. `SKIP LOCKED` can help queue workers distribute fixed items but provides an intentionally incomplete view, not a reviewed selection or proof that no work remains. No Tenant-wide lock is needed for unrelated journeys.

**Acceptance proof:** force worker A to stop after source commit but before item result; let recovery run, then allow A to finish. Duplicate execution does not duplicate accepted work, old completion cannot erase a newer state, and result repair does not invent a new stage event or contact. Empty claim selection while another worker holds items cannot imply whole-group completion. Test independent connection barriers rather than timing guesses.

### DB4-06 — human attribution is mistaken for current authorization

**Critical severity; medium likelihood if caller-supplied actor/approval fields or old review is trusted. Preserve D4 and D3 privacy floors.** A job can add actors' names to new matches, continue after permission revocation, reuse a hidden journey or infer hidden existence from mixed per-item errors.

**Exact prevention:** “The server records deliberate human intent from an authenticated authorized source operation and the exact reviewed selection. A worker acts only on that accepted operation and current qualified authority; it may not manufacture review, choose additional candidates or use its service credential as permission. Revalidate source/action/context/field eligibility at consequential admission and expose only the permitted create/reuse result.”

Party is compatible Tenant scope; Ministry Assignment is exact Tenant/Legal Entity. Do not invent Party entity columns. Authorize both existing and proposed rows and any returned projection, with D3's uniform bounded behavior where admission observability is not allowed. Preserve original initiator separately from the actual executor/retry actor without freezing column names. No new human click per item, manager queue or automation policy is required merely because execution is asynchronous. A group review is not communication consent or approval for arbitrary follow-on sends.

**Acceptance proof:** forge actor, group membership or source scope; permission/source revision changes after review and during execution; same logged-in user switches context; hidden existing journey versus absent row; allowed metadata but denied history. No automatic replacement ministry, skipped-then-requeued hidden duplicate or unauthorized result count. Existing coarse `withOperation` role gates are not this proof.

### DB4-07 — retries and reuse reset existing work or create outward effects

**High severity; plausible if “start” is implemented as blind upsert. Preserve D1–D3.** Existing ordinary work can be reset to prospect, owner/stage overwritten, multiple next tasks created or imported historical tags converted into new approvals. An outbox fired simply because a group row exists can contact donors without qualified intent.

**Exact prevention:** “Create or reuse the intended ordinary journey through the owner-qualified command. Reuse preserves existing progress, responsibility, unfinished obligations and history; it is not a stage reset or reapproval of old work. New changes require their own admitted meaning and current revision. Historical import/migration is separate and outward-effect-dark; a new human admission does not itself authorize contact.”

**Acceptance proof:** existing journey with multiple asks/tasks; concurrent ordinary starts; retry after correction/merge; legacy task attachment emits zero newly approved cultivation task/message/stage effects. Gifts/referrals/newsletter arrival and generic rules cannot call new-work admission absent the admitted human intent. Appropriate source-linked existing tasks can satisfy next work; one clear contextual action may record a referral/ask and admit its journey without duplicate entry.

### DB4-08 — result, preview and recovery copies become new private-data stores

**Critical severity for disclosure; medium likelihood. Preserve existing P12/custody requirements.** Group snapshots can copy donor notes, ministry aliases, history or permission facts into durable JSON, logs, task descriptions and export files. “Failed item” messages can contain raw constraint or hidden-source details.

**Exact prevention:** “Keep the minimum reviewed identity/action/provenance needed for recovery. Do not snapshot whole CRM DTOs or private history into the group payload. Preview, membership, item outcomes, counts and exports remain source-governed data; authorize them at read/recovery time and follow owner retention/erasure/restore rules.”

**Acceptance proof:** restricted source added to a fixture causes no unauthorized observable difference; error/export/log paths redact source internals; restore of an old group cannot widen current access or rerun completed effects. A group receipt is not a permanent permission snapshot. No new retention duration is selected here.

### DB4-09 — per-row network loops or arbitrary numeric limits become product architecture

**Medium severity; plausible under large review groups. Preserve D4; measure implementation.** Current contribution caps/chunk sizes and CRM page windows are unrelated to measured cultivation capacity. One network call per permission/lookup/task plus a giant all-Tenant lock scales poorly, while unbounded manifest JSON and result serialization harm both reliability and privacy.

**Exact prevention:** “Use bounded source-validated selections, set-based scoped reads where possible, indexed semantic identity and short owner transactions. Measure realistic group sizes and query plans before choosing limits and deadlines. Keep current result authority and individual transaction guarantees under batching.”

**Acceptance proof:** realistic skewed Tenant data, mixed eligible/changed records, actual RLS/owner checks, concurrent singles/groups and interrupted pagination; bounded memory/queries/retries and usable progress. No SLA, maximum D4 batch count, throughput or timing promise is inferred from source constants or a synthetic mechanics fixture. Monitor confirmed duplicate identity/effects, invalid scope and unauthorized result disclosure as zero-tolerance violations; workload alerts need measured approved budgets.

## Proof now versus proof before activation

The evidence above is current source inspection plus current primary documentation. Existing D3 synthetic checks establish SQL mechanics only: transaction rollback, uniqueness/scope/null behavior, hidden conflict observability and the coordinated CTE snapshot counterexample. They establish no D4 review, manifest, authorization, per-journey command, recovery or UI behavior.

A narrow additional synthetic experiment would be useful for the new D4 boundary: after fixed review of A/B, add C before execution and compare live-predicate versus fixed-ID execution; then fail item two under one whole-batch transaction versus independent per-item transactions. If savepoints are included, show that release does not survive rollback of the outer transaction. Use explicit barriers and disposable synthetic tables, no application schema or fictional P12 model. This reviewer proposed that test to the parent and did not run it or start competing Docker work. Even a passing fixture would prove mechanisms and counterexamples, not qualify the actual source command.

Before activation, the real source needs authenticated human-reviewed entry through every door, compatible Party/Ministry scope, current source authorization and observability, deduplication/receipt semantics, atomic required work/history, fixed group identity, truthful partial results, cancellation/recovery, old-writer fencing, and browser flows with lost first response and page/filter drift. Existing unit mocks and a PostgreSQL lab cannot waive those tests. D4 has no reason to activate optional rule-based admission or require the donor to opt into an internal cultivation record.

## Suggested concise addition to D4

> A reviewed group records a bounded selection and its intended source context; later execution and retry cannot silently add newly matching people. One clear authorized action can start or reuse the selected work, including through an existing qualified background executor, without a separate click per person. Each journey's acceptance and required accountability commit together. Group progress and retries preserve authoritative outcomes, current permissions and the original reviewed intent; a lost response is reconciled, not assumed to mean failure. Existing work is reused without resetting it or repeating accepted effects. Exact partial-result interaction and lifecycle rules remain separately qualified.

## Opening decision recommendation (inference, not ratification)

Highest leverage unresolved choice: **What should a cultivation enrollment remain responsible for over time?** The user has already settled multiple purpose-specific enrollments, separation of stages from ask/task/commitment/workflow state, and portfolio derivation from assignments. Do not ask those settled questions again.

Recommend an ongoing relationship-development responsibility for a defined purpose, capable of containing successive annual or special asks and stewardship work, rather than opening/closing an enrollment for every ask. A church's annual budget renewal and a special building-project request can be separate asks while the church partnership persists. Allow deliberate completion of a genuinely finished purpose and pause/end history; these are future decisions, not already designed here. A completed gift must not silently end the relationship or imply its next action.

Evidence supports separation of responsibility, specific solicitations, tasks, interactions and financial records; it does **not** establish that any vendor has Core's exact enrollment concept, concurrency rules or lifecycle. Whether Asym also needs distinct bounded cultivation initiatives beyond separate asks remains a founder product choice. Avoid making indefinite enrollments become stale obligations: next-action exceptions, review dates, pause/end semantics and stage aging need later grooming.

## Salesforce current product: Philanthropy and Partnerships in Fundraising

Edition: current integrated Fundraising platform in **Agentforce Nonprofit / Agentforce Education**, formerly called Nonprofit Cloud / Education Cloud. The official module explicitly says this is not the managed-package fundraising solution and directs NPSP users elsewhere. No customer license tier asserted. Content sitemap lists these units' last modification as **2026-09-08**; this is sitemap metadata, not evidence of every feature's release date.

1. **Portfolio and profile** — [Manage Portfolios and View Donor Profiles](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-philanthropy-and-partnerships/manage-portfolios-and-view-donor-profiles). Source-supported: portfolios use Actionable Lists; definitions compile criteria across records; automated assignment and manual reassignment are described; donor profile is a special Person Account layout; components support giving/relationships; donor briefs are PDF documents using templates. Limitation: the standard trial described does not have a portfolio configured. These instructions are not a verified running customer instance. Some examples use wealth criteria and aggregated RFM likelihood framing, which conflict with Asym's explicit no-wealth-screening/donor-dignity scope. Do not copy vendor score interpretation or their membership authority into Core.
2. **Action plans, interactions and solicitations** — [Work with Prospects and Donors](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-philanthropy-and-partnerships/work-with-prospects-and-donors). Source-supported: Action Plan Templates are predefined tasks/document checklist items; a qualification action plan appears on the profile and its tasks in Open Activities. Interaction Summary is a permanent record for rich reportable meeting information, linked to an Interaction. The example distinguishes confidentiality and draft/published status; confidential summaries limit selected sharing. Opportunity tracks a **particular solicitation**, while the Person Account persists. Interaction summaries and other records may relate to both account and opportunity. Gift acceptance leads to Operations creating a Gift Commitment tied to the Opportunity, with Gift Transactions tracking payments. Limitation: privacy depends on org configuration; article's public/published example does not establish Asym's access rules, and shared reference must not be interpreted as copied private content.
3. **Financial record meanings** — [Understand Fundraising Records](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-fundraising-operations/understand-fundraising-records). Source-supported: Gift Designation is intended fund/purpose; Gift Commitment represents a promise, recurring or pledged, related to schedules, designations, campaign and opportunity; Gift Transaction tracks one-time payments and installments fulfilling commitments. Distinct operational donor-support profile is described. This is useful precedent for P27 consuming P13/P16 instead of owning money.
4. **Commitments** — [Create and Manage Gift Commitments](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-fundraising-operations/create-and-manage-gift-commitments). Source-supported worked example includes amount/frequency, schedule start and optional end, designation, and automatically created transaction schedule records. Read together with transaction status: scheduled transaction creation must not be mistaken for received money. No implication of authorization to charge in Core.
5. **Gift processing** — [Track Gift Transactions](https://trailhead.salesforce.com/content/learn/modules/nonprofit-cloud-fundraising-operations/track-gift-transactions). Source-supported: Gift Entry and Gift Batch precede processing; a saved batch entry is not yet its generated transaction; dry-run and processing are separate. An entry can match a Gift Commitment; due date and transaction completion date remain separate. Limitations: this documented workflow is not a recommendation to recreate gift entry in P27 or use a Source Code to prove an ask's fulfillment.

Terminology translation: donor profile → authorized Party record shell; portfolio → authorized assignment/saved-view projection; action plan tasks → P9 shared tasks with P27 purpose; Opportunity → P27 ask/proposal (not global Party stage); Interaction + Summary → source-owned encounter and permitted development-purpose context; Gift Commitment → P16; Gift Transaction/Designation → P13. Translation is our inference, not an exact schema mapping.

## Blackbaud Raiser’s Edge NXT

Edition: official **Raiser’s Edge NXT web view**, with explicit database-view/proposal caveats where stated. Official online help retrieved 2026-10-09. No visible article publication/edit date was supplied; treat source date as undated, retrieval current. No production or licensed instance inspected.

6. [Opportunities](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-opportunities.html): one opportunity belongs to one constituent; a constituent can have multiple opportunities; same fundraising campaign needs separate opportunities per contacted constituent. Work Center limits work lists to assigned opportunities or constituents the fundraiser works with. This is useful precedent for purpose-specific work rather than one global donor pipeline, not proof of Core access authorization.
7. [Opportunity Records](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-opportunity-record.html): actions show date/status including past due and notes; opportunity-level fundraiser assignments and credit; status timeline shows how long in current stage and history; likelihood and last-rated date are distinct. This documents responsibility for an ask apart from record-level relationship responsibility.
8. [Add or Edit Opportunities](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-opportunity-add-edit.html): purpose, stage, deadline, funding, assigned fundraiser, campaign/fund, anticipated gift type/instrument, likelihood/date rated; organizational constituent has an opportunity contact. The page documents UI limitations around adding custom fields on creation versus editing, and separate section editors. Do not infer unrestricted financial authority from an editable form.
9. [Opportunity Funding](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-funding-amounts.html): requested ask and realistically expected amount differ; expected supports forecasting. **Funded** can include one-time gifts, recurring gifts, pledges, matching gift pledges, noncash and other types. **Committed** and **Received** are separate figures derived using Giving Analysis settings, reference only and do not change Funded. Original Ask/date survive normal ask revision, but an explicit original-ask correction action exists. Older opportunities display zero original ask until entered: useful warning against copying an unknown-as-zero legacy convention. Linking pledge/recurring payments does not automatically update Funded, stated as preventing double counting. **Do not translate Funded as Asym received/cash fulfillment.**
10. [Manage Opportunities](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-opportunity-manage.html): inactive retains history and can be reactivated; default lists show active work. Gift-link operation includes amount allocation; amounts applied across opportunities may not exceed gift amount; other-constituent opportunity links are possible. New recurring gifts cannot be newly linked; individual payments should be linked; legacy links remain editable/removable. Deleting an opportunity deletes actions/notes/attachments and requires removing gift links first. That deletion behavior is a vendor fact, not recommended for Core source/history ownership.
11. [Linked Gifts](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-linked-gifts.html): explicit gift/opportunity links, amounts applied, and distinction between linked amount and funded totals. Supports explicit source links; does not support fuzzy date/amount matching as fulfillment.
12. [Manage Opportunity Statuses](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-opportunity-statuses.html): status, entry date, comment; previous status dates editable and status history deletable; overdue thresholds configured by admins. Useful stage-aging precedent with a caution: Core should retain audit/history meaning instead of blindly copying mutability.
13. [Fundraisers](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-solicitors.html): staff, volunteers, committees, board members can act as fundraisers. Stop Assignments prevents new work but existing assignments remain; help says reassign work first because person then disappears from Work Center portfolio. Concrete failure mode for leave/departure: stopping new assignment is not a completed handoff.
14. [Analyze Opportunities](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/bb-analyze-opportunities.html): requested/expected/raised summaries; counts by status/purpose/fundraiser/campaign/fund; projection accuracy and average differences/times; default all active opportunities; dashboard filters and saved views. **Documented freshness caveat:** metrics update within three hours of edits; after reports unused over one month, first refresh may take up to 24 hours. Do not use reports as immediate command confirmation. Values and active-scope defaults limit comparability.

Core implications (inference): separate requested, forecast, commitment and received meanings; retain forecast time/version and exact source coverage; keep responsibility/credit separate from financial totals; lifecycle changes must preserve open obligations. No verified portfolio-performance statistics found or reused.

## Virtuous CRM+

Edition: articles explicitly describe **Virtuous CRM+**, with some labels covering Virtuous CRM. Public official Zendesk Help Center API exposes both `edited_at` (content edit) and `updated_at` (may include other metadata); dates below use **edited_at**. Retrieved 2026-10-09. No running customer instance or pricing/entitlement proof.

15. [What is My Portfolio?](https://support.virtuous.org/hc/en-us/articles/29210941980045-What-is-My-Portfolio), edited **2025-07-02**: portfolio means selection of Contact relationships a user maintains; informed by Organization Groups; user can belong to only one Organization Group and portfolio is inactive without assignment. Group users lack Data Health Tool. Portfolio summarizes recent giving, upcoming asks, relationships, tags, open asks, with quick Add Task and record navigation. A contact can be removed from the group from the view. Useful presentation precedent; not Core authority model. Core already forbids a separately writable membership store and assignment-based access grants.
16. [Moves Management and Responsive Fundraising in Virtuous CRM+](https://support.virtuous.org/hc/en-us/articles/29269791559949-Moves-Management-and-Responsive-Fundraising-in-Virtuous-CRM), edited **2025-07-03**: Organization Groups define relationship responsibility (and can restrict visibility); Gift Ask Pipeline tracks **specific Gift Asks**; notes describe past interactions, tasks future actions; notes need accurate logging for inactivity queries. Workflow steps can define moves-management stages and add/remove groups, notes or tasks. Do not copy assignment/access coupling or make native cultivation rely on optional Workflow Studio. Opening promotional performance phrasing is excluded from evidence.
17. [What is the Gift Ask Pipeline?](https://support.virtuous.org/hc/en-us/articles/360051317631-What-is-the-Gift-Ask-Pipeline), edited **2025-07-02**, metadata updated **2026-08-04**: Kanban by customizable ask statuses; default current user's asks/current fiscal year and filters reset after navigation. Status probability produces weighted total (100 at 50% yields 50); individual probability override supported. Actual closed-column giving requires **both explicit Gift-to-Gift-Ask linking and ask Closed status**. Declined column is zero probability. Useful disclosure of reporting prerequisites; not proof of historical forecast snapshots or fulfillment reliability in all correction cases.
18. [How Do I Create a Gift Ask?](https://support.virtuous.org/hc/en-us/articles/10647492200589-How-Do-I-Create-a-Gift-Ask), edited **2022-12-14**: follows a specific solicitation; required ask amount, currency, ask type, probability; recurring asks add frequency; team members, marketing segment/project and tasks can be associated. Article is older current help; does not fully specify cadence/term/horizon or currency aggregation.
19. [How Do I Link a Gift with a Gift Ask?](https://support.virtuous.org/hc/en-us/articles/10623580364301-How-Do-I-Link-a-Gift-with-a-Gift-Ask), edited **2022-12-14**: actual Gift must first be imported/created; then user edits Gift reporting/tracking to choose Gift Ask by ID, amount or date and saves. Search fields identify candidate asks; they do not automatically prove fulfillment.
20. [How Do I Set Fundraising Goals for my Team?](https://support.virtuous.org/hc/en-us/articles/360059446551-How-Do-I-Set-Fundraising-Goals-for-my-Team), edited **2023-06-02**: goals tied specifically to asks and ask fulfillment (article says best suited to major gifts), calendar/fiscal year, monthly/quarterly/annual team goals, optional individual goals. Not a general valuation of nonfinancial relationship value.
21. [How Do I Create a Task?](https://support.virtuous.org/hc/en-us/articles/360059923452-How-Do-I-Create-a-Task), edited **2025-07-16**: contact/gift ask/grant/campaign tasks share Tasks page; due date required; recurring task duplicates on completion at selected frequency; person/owner can be identified; direct and bulk creation exist; reminders and digest reduce repeated messages. Specific default two-day deadlines and notification timing are vendor choices, not evidence of ideal Core policy. Bulk query guidance warns not to alter query before completion: useful indication that Asym needs stable purpose/audience identity, not a reason to copy that UX.

## Classification and limits

- **Durable pattern candidate:** lasting relationship responsibility, distinct specific asks, reusable tasks/interactions, separate promises/payments, explainable explicit gift associations. Supported across procedural official documentation; Core ownership must still govern implementation.
- **Useful precedent:** focused portfolio cards and fast task creation, status aging, original-vs-revised asks, team goal periods, reference-based meeting context.
- **Conflict with Asym first principles/scope:** assignment that itself grants access; wealth-derived suggested asks; person-level one-score importance; using workflow enrollment as native cultivation; unknown legacy amount represented as zero; ambiguous funded = received; deleting source-owned obligations with an ask.
- **Unresolved/unavailable evidence:** vendor transaction-level correction/refund behavior, concurrent update guarantees, accessibility of drag-only paths, cross-currency rollups and privacy-safe scoring are not established by these pages. No API/database/runtime verification performed. Do not claim absent features from documentation silence.
- Search engines were unhelpful/challenged; discovery used official Trailhead sitemap, official Blackbaud linked help, and public Virtuous Help Center search API. Salesforce Help app itself returned a loading shell, so factual claims use accessible official Trailhead procedural content. No remote data writes.

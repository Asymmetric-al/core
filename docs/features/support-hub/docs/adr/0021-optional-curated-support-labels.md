### Accepted product and permission scope

One flat tenant Support catalog supplies optional labels. Zero, one or several labels are valid; intake, reading, replying, assignment, delegation, ordinary status changes and Resolve never require a label. No automatic/default catch-all, primary-topic field, private/nested/per-inbox taxonomy, new approval queue or mandatory classification mode. D20 remains the shared personal/team retrieval capability.

Current eligible Support staff may read general reusable catalog wording; actual source editing authority governs application/removal on exact original endpoints. Distinct delegated Support configuration-management authority governs vocabulary. Existing IAM supplies capabilities rather than a new global role or per-label ACL platform. D18 publishers, D19 reviewers and D20 Shared-view maintainers gain no implicit label management or source/CRM access. Tenant custody survives curator departure, without account cascades or same-email inheritance. Empty vocabulary or missing curatorial coverage does not block Support work. General catalog visibility grants no usage counts or restricted conversation facts; actual privacy ownership can restrict/correct sensitive metadata.

### Accepted identities and full user journey

Support owns stable catalog IDs and original-conversation memberships in Asym Postgres through the shared API boundary, reusing qualified Core IAM, configuration/history, query and base-maia UI capabilities. P9 Party tags, P11 field/taxonomy and CRM/giving/care domains remain distinct. No universal tag service, new custom-field engine or duplicate CRM state is introduced.

Readable Unicode names replace ASCII slug identity. The accepted authoring bounds are a nonblank name of at most 80 Unicode scalar values and optional description of at most 140 after NFC/trim, with 320/560 UTF-8 byte bounds. These are explicit product choices, not legal/vendor optima. Shared server/DB-consistent versioned normalization, casefold collision checks, exact validation and independently generated compatibility tokens prevent empty-slug and silent-identity failures. Active/ordinary archived names stay reserved while retained under owner policy; privacy disposal may remove forbidden comparison/name material without ID reuse. No silent clipping, synonym merge, arbitrary survivor or normalizer-upgrade reinterpretation.

Labels/Add label remains visible in conversation details. Search readable eligible names with meaning where useful, preserve selected state/focus and keep the picker open for deliberate additional choices. Loading, empty, no-match, failed, uncertain, archived, read-only and unavailable states are distinct. No labels is neutral. Add/Remove requires no confirmation modal; uncertain outcomes reconcile the original command. Keyboard/touch/IME, non-Latin/RTL text, focus/selected-state distinction, semantic tokens, zoom/reflow and assistive-technology proof are mandatory. Manager controls stay outside listbox options. The 24×24 CSS-pixel minimum or applicable WCAG exceptions are correctly qualified, not a universal chip-size claim.

One shared management experience provides Active/Archived, New/Edit/Archive/Restore in Support settings and qualified contextual access, with preserved form/draft/return context. Optional meaning and restrained appearance do not become a content-publication workflow. Rename corrects wording while preserving meaning; materially new meaning gets a new identity. Rename-to-existing-name never transfers or deletes memberships. Archive stops new use while retaining authorized applied values and D20 filters/report meaning; Restore returns future eligibility but cannot restore removed labels or replay pre-archive intent. Ordinary Delete and a generic catalog-merge engine are excluded; actual records/privacy disposal remains separate.

### Accepted durable source behavior

Explicit Add/Remove replaces read-invert toggles and stale whole-array replacement. Bind immutable label/source identity, current capability, control/lifecycle/topology/revision and durable command context. Atomically commit the exact effect, minimal trusted history, revision and receipt. A retry returns original outcome and current state separately; old Add after later Remove cannot resurrect it, and receipt expiry cannot turn old intent into a new effect. Current source/lifecycle races must have a qualified single ordering. Update is not Create. No-op retries create no false activity; secondary index/cache failures are repairable without repeating authoritative writes.

D10-R24 remains exact: original endpoints retain memberships, the combined display is a permitted deduplicated union, already-effective Add is unchanged, fresh Add anchors to the continuing origin, combined Remove ends the exact current contributors atomically, and Undo merge partitions current memberships while preserving later edits. Topology or permission changes require current review, not partial hidden-source mutation. Related conversations do not inherit labels. Existing bulk paths use explicit bounded IDs and durable per-conversation sub-intents with truthful partial results; no new all-matches action or stronger macro/automation scope.

All APIs, grants, RLS USING/WITH CHECK, views/RPCs, definer/service/worker paths, fixtures, macros, caches, exports and restores must enforce the same curation/source boundary. Trusted server identity supplies tenant, actual actor/profile and admission facts. Tenant-aware endpoint constraints, immutable IDs, valid state/revision/bounds and unique membership defend integrity. Retire old permissive/cascade/toggle/upsert writers instead of relying on a safe-looking UI. Catalog/cache access cannot expose another tenant or retain late revoked-scope results. No label edit changes messages, recipients, D3 work, D14 targets, D15 following, D17 retention or CRM last-contact/business outcomes.

### Accepted reporting and privacy corrections

Archived applied labels still count; unavailable/purged/forbidden reference meaning is never dropped or converted into No labels. Deliberate membership changes may alter live matches, while catalog maintenance cannot silently broaden saved predicates.

The current-label report forms complete current authorized components first, then qualifies earliest original-conversation start and current responsible inbox before applying the half-open period in the visible reporting timezone. It evaluates the current eligible label union at one server instant. Missing original-start evidence stays in separately qualified Start date unconfirmed; incomplete label evidence is not zero or improved coverage. Total N, labelled L and unlabelled U obey L+U=N only for complete metadata. Per-label distinct counts use N as denominator, can overlap and exceed 100% in sum; N=0 is no population. This is current categorization/current grouping, not historical inflow, at-resolution classification or a tag-change warehouse.

Charts, table, drilldown and authorized export preserve basis/scope/unknowns. Source-derived metadata, catalog wording/comparison material, memberships, histories, receipts, query state, caches and restored copies keep their qualified finite purposes and current D16/D17/records-owner restrictions.

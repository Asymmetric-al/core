## Technical timing and authorization evidence

[PostgreSQL date/time functions](https://www.postgresql.org/docs/current/functions-datetime.html),current page resolves to PostgreSQL 18, distinguishes transaction-start `now()`/transaction_timestamp from a fresh clock reading that changes during execution. That distinction matters when an assignment worker waits on a control lock across the coverage end. D7 requires a fresh authoritative effect-admission time after current controls, not a stale transaction timestamp. It is not a recommendation to upgrade the database version or an assertion that a SQL function alone proves all concurrency.

[PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) and [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) distinguish old/new row policy checks, grants and privileged paths. Coverage needs the same tenant/resource/actor guarantees across client, function, view and service-role entry points; simply finding ENABLE ROW LEVEL SECURITY in a migration is insufficient. No credential or live database was accessed during this public-doc review.

Core's workflow specification requires product-owned claims and a shared dispatch ledger, with identifier-only envelopes, recovery and tenant-adjustable failure escalation. D7 uses those contracts. A fixed personal Support command is proposed as a narrow owner operation analogous to D3 reminders; this distinction needs explicit later OpenSpec/permission qualification. It is not an already-implemented self-service permission or an exception allowing arbitrary configurable automations without automation:manage/preview/test/activity requirements.

## Independent challenges resolved in the final package

1. **Scoped coverage versus global Receive:** an early compound Start-and-Off proposal was rejected because Receive is tenant-wide. Preserve the stored preference and derive the covered-inbox restriction. End uses the current value without restoration writes; scope removal has the same declared effect.
2. **Keep without ping-pong:** manual assignment/reaffirmation to a covered person explicitly records episode+assignment-control intent. Ordinary work status/Send/notes do not imply it. Same-owner Keep is not a fake reassignment, metric increment or assignment notification.
3. **Move compatibility:** the old scope is fenced. A move-retain into active coverage resolves the same deliberate Keep/handling choice rather than appearing to retain and then silently stripping the owner. Leaving/removing scope invalidates Keep; changing only the end does not.
4. **Time is not a late callback:** effective end is checked at fresh guarded admission; a merely queued evaluation from earlier is not permission. A valid effect may complete after the boundary, but a later worker cannot obtain retrospective authority. Expired cleanup cannot block a new explicit episode.
5. **Active versus actually transferred:** allow the declared coverage arrangement to be recorded with disclosed paused/missing-cover gaps, preserving safe current custody. Show held/failed/unknown outcomes persistently on the same compact summary after details close. Never report fully covered from an active row alone.
6. **Not just the status string:** current-Open catch-up, already-Open fresh work, both waits and previously Resolved reopenings need D3 causal evaluation and durable recovery, including Pause/start gaps. Authorized explicit Set Open is included without an extra email or implicit Keep. No provider timestamp or generic activity counter owns that decision; past/current-instant scheduled ends are rejected in favor of explicit End coverage.
7. **Canonical identity versus display hydration:** the new three-case exact-source probe demonstrates a real lossy null shape. Coverage queries must use canonical assignment IDs; a missing card/agent lookup is not proof Unassigned.
8. **No borrowed author/draft:** current composer integration still needs the earlier ratified owner repair. Coverage must not transfer private drafts, author as assignee or rewrite already admitted prepared mail.
9. **Numeric limits stated correctly:** the checked-in local Data API max_rows 1,000 and application request cap 2,000 are distinct; neither proves deployed cardinality. No arbitrary cap may define complete coverage.

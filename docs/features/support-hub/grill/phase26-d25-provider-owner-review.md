**Disposition: Accept with required amendments.** Equal paths are a sound product choice. They expose three consequential gaps that must be resolved expressly: Resend receiving requires more provider privilege than the outbound-only credential allows; an Asym-managed reply destination cannot complete an external-mailbox challenge by consuming its own inbound message; and authenticated webhooks do not make every address/header in their payload authoritative. The permanent path is to extend the existing shared owners narrowly, keep proof dimensions separate, and qualify the real provider before opening a route.

## Owner contract and exact required amendments

The clauses below are recommended exact grooming language. Their descriptive names are not preselected database table or public API names.

### P25-P01 — Separate provider credential purpose

**Concern: material; severity high; likelihood high if existing outbound setup is reused unchanged.** A send-only key cannot retrieve mail; substituting Full access would quietly broaden every outgoing worker. A receiving outage could also trigger an unsafe global fallback. This changes the owner contract required for C, not C's choice of journey.

> The tenant's existing shared Resend connection gains a distinct receiving credential purpose. It uses a separate encrypted Full-access key because Resend currently offers no receiving-only permission. The interface must state that the provider key can manage the whole tenant Resend account: Asym's narrow operation allowlist is an application boundary, not provider-enforced read-only scope. The outgoing Sending-access key, its domain restriction/proof, and all dispatch-selection rules remain unchanged. Only a bounded shared receiving/proof worker may decrypt the receiving revision; no outgoing adapter, browser, Support command, AI tool or export can obtain or substitute it. Provider operation selection accepts closed owner commands, never caller-provided URLs, verbs or resource IDs. There is no global or cross-tenant fallback.

Explicitly amend ADR0029/P6's connection description and P17's line1481 universal credential-kind statement: one instantiable **outgoing** kind remains; P26 authorizes the additional **receiving** purpose in the same owner aggregate. Its local allowlist covers exact authorized received-email/raw/attachment retrieval, bounded recovery listing and required account/domain/webhook proof reads. Setup and repair use existing guided provider administration; this decision does not introduce arbitrary provider management. A later managed mutation needs its own exact authorized operation and ambiguous-success recovery. OAuth remains deferred because it currently adds grant/refresh lifecycle without narrower provider access.

Proof: outgoing Full-access rejection still fails; receiving key cannot reach send/contact/template/domain-delete operations through any app path; denial remains after key rotation; compromise drill fences the receiving facet and evaluates whole-account impact rather than pretending the key was read-only. Residual risk is provider-level broad privilege if this key or its worker is compromised; isolation/custody/operation restrictions reduce, but cannot erase, it.

### P25-P02 — Prove the same provider account

**Concern: material; severity critical; likelihood medium without an exact proof contract.** A valid key from another tenant can be mislabeled and read or route wrong-account mail. Key hint, staff account label, DNS ownership and payload tenant metadata are not sufficient.

> Receiving credentials, domains, registered webhook objects and receipts bind to the exact tenant-owned provider account represented by the existing connection. Establish proof using exact already-bound provider object identifiers retrieved under the candidate credential and canonical evidence comparison; an existing server-created qualification-send provider ID may also corroborate the account. Where new setup requires it, run the constrained qualification canary. Activation requires qualified positive and wrong-account evidence. Provider labels or payload metadata never select the owner. Credential rotation within an already-proved account may reuse current immutable object proof without demanding new outgoing production mail; receiving repair remains possible while ordinary sending is unavailable. An account/region move creates a new connection generation and cannot migrate old receipts by relabeling them.

Expected implementation evidence: exact domain/webhook retrieval isolation and any canary lookup must be confirmed against the pinned real API; these are not yet live-qualified here. Account-managed receiving domains may not share custom-domain API representation; qualify that case explicitly. If account provenance cannot be proved, show incomplete proof and do not activate.

### P25-P03 — Shared authenticated ingress, independent business owners

**Concern: material; severity high; likelihood high if each inbox creates its own webhook.** Endpoint quota, duplicate fanout, lost subscriptions and secret sprawl otherwise grow with inbox count.

> Reuse one opaque per-connection Resend ingress where the qualified provider supports the required subscriptions. Authenticate the exact raw request against the connection's bounded current/overlap secret revisions before interpreting its event. Dispatch only registered event kinds: receiving events enter P26 intake; outgoing events enter the existing P6/P17 delivery-evidence path. The outbound reducer still makes no lifecycle transition for `email.received`. Update the ingress contract expressly; preserve the union of both owners' required subscriptions. Inbox creation does not create an endpoint or copy a secret. Svix-event dedupe and provider-receipt business idempotency retain separate scoped identities. Unknown events never trigger a fallback owner or generic action.

This extends P17's described ingress scope, not its outbound reducer's authority or a generic event bus. One ingress carries shared failure impact; readiness must name the affected facets. Test receiving-enabled/outgoing-enabled subscription edits, duplicate replay, wrong key/route, old rotation signatures, and quota exhaustion.

### P25-P04 — Receiving address provenance

**Concern: material; severity critical; likelihood medium, elevated for forwarded/multiple recipients.** A signed payload can contain attacker-written addresses and authentication claims. Current tenant inference from recipient domains violates the owner boundary.

> Tenant selection comes solely from the already-authenticated registered connection. Within that tenant, normal intake requires source-qualified exact receiving-address evidence and one admitted inbox binding. To/Cc/Bcc, `received_for`, subject, Message-ID, Reply-To, display name and arbitrary Received/Authentication-Results fields are content or diagnostic evidence until their provider/trusted-hop semantics are qualified. They cannot establish tenant, CRM identity, mailbox control or inbox authority. Ambiguous, conflicting, unsupported or unproved routing enters the existing held-intake process; it never picks the first recipient or a default inferred from the outgoing sender domain. Domain-wide catch-all receipt is not domain-wide Support admission.

The mandatory spike must establish documented/supported recipient semantics plus live crafted To-versus-envelope, Bcc, multiple routes, forwarding, duplicate/forged Received and Authentication-Results cases. Raw ordered duplicate-preserving headers may be necessary; a string dictionary cannot substitute. Do not promise the current public API already satisfies this mandatory contract. If it fails, block activation under D1; contingency research is not permission to quietly deploy a second provider.

### P25-P05 — Two genuine human reply proof methods

**Concern: material; severity high; likelihood certain for a managed address without an external mailbox.** P17's current external challenge becomes circular or impossible if its code is consumed through the very Support route being verified.

> A P17 Human reply destination has one exact current proof method: external mailbox access, or a P26-managed Support return route. Existing external access proof retains its same-initiating-human, fresh capability/step-up, exact-address, expiry and anti-replay protections; its challenge never appears in Support and inbound automation cannot complete it. For a managed route, P26 supplies a typed proof binding the tenant, provider account/connection, receiving domain/address, inbox binding and configuration generation to current source-qualified inbound and approved-sink round-trip evidence. The authorized stepped-up P17 reply manager accepts that proof and separately acknowledges the accountable monitoring team/person. P17 consumes and pins the resulting destination revision; it does not acquire receiving, threading or mailbox-health ownership. Changing an inbox destination does not silently assign Default human replies or another product's purpose.

Amend P17's human-replies section, exclusive proof shape and acceptance criteria. There is no new configurable reply-purpose taxonomy, arbitrary template, customer identity or alias engine. In the existing-address path, complete mailbox access proof before activating forwarding where needed. Forwarding configuration and the actual receiving path still need separate proof. Test that a code retrieved from setup/intake, another actor, a different address or older configuration cannot make the external destination Ready; test managed proof invalidation after route/permission/account change.

### P25-P06 — Qualification without a readiness cycle

**Concern: material; severity high; likelihood high if production gates are copied literally.** Requiring a Ready receiving destination before the only permitted canary can test it makes setup impossible; weakening all sends to escape the cycle is worse.

> Existing P17/P6 qualification operations may use the exact candidate sending credential, sender and reply destination before production Ready solely for bounded, inert, same-generation proof with an approved real sink. Qualification never enables ordinary reply, acknowledgement, catalog mail or arbitrary recipient/content sends. The approved sink's controlled reply or new inbound message proves the candidate return path; operator-mediated proof is sufficient where no automated sink capability has been authorized. No new Asym platform mailer, relay, bootstrap credential or fallback is implied. P26 may recognize and verify exact qualification traffic while the route is inactive, but it produces only minimized setup evidence: no conversation, requester/CRM record, D13 acknowledgement, reply target, follower event, saved-content use count or operational report entry.

This is an explicit narrow extension of P17's existing canary class. It must freeze the candidate identity, proof mode, approved sink and expected evidence before I/O. The last activation step rechecks the same generation atomically and makes only the selected inbox operational. Qualification-submission uncertainty keeps the proof unresolved; it does not generate a fresh uncontrolled canary.

### P25-P07 — Sending, receiving and ownership are different facts

**Concern: material; severity high; likelihood high for DNS onboarding.** A single Connected badge can hide broken replies or disruptive root MX edits.

> Sending proof, external mailbox access, receiving-domain/MX control, exact inbox routing, human monitoring responsibility and operational activation remain separate facts. Sender/Reply-To resolution consumes the existing P17 owner; setup cannot claim the public support address is an allowed From identity merely because it receives mail. Prefer a dedicated receiving subdomain when creating a new domain path. Show exact provider-supplied DNS values only after the intended domain and existing mail routing are understood. No automatic root-MX replacement, blind SPF record replacement or website-verification reuse is allowed. Keep the prior working route active until an explicitly reviewed, fully proved replacement cuts over; explain any unavoidable external provider interruption before the tenant changes DNS.

Test external care address plus a different approved transactional From, domain already used by Google/Microsoft, multiple MX priorities, receiving-enabled/sending-disabled and reverse combinations. Do not assert MX change is reversible merely because a config row can roll back.

### P25-P08 — Exact, bounded content acquisition

**Concern: material; severity high; likelihood high during retries or larger mail.** Missing bodies, partial attachment lists, default image expansion and expired URLs can create false completeness, memory pressure or lost evidence.

> Verify the pinned received-email and attachment responses structurally and by expected provider identity. Request a bounded suitable representation, handle the actual served format, preserve CID relationships, and enforce byte/count/time limits before materialization. Honor pagination and explicit failed/missing items; do not report a partial page as all attachments. Refresh an expired provider URL through the bound account/object API when permitted; never store it as permanent asset authority. A metadata event, `{}` response or successful HTTP status alone is not content retrieval. A valid attachment-only message follows D1's intake contract rather than being permanently rejected as an empty-body error. Retain pending/failed acquisition visibly and retry the same durable source effect; do not create a blank conversation or duplicate source on retry.

Controlled download URLs must come from the validated provider response; fetch without forwarding API credentials, obey allowed provider origins/redirect restrictions, prevent internal-network fetches and avoid URL logs. Raw/header copies remain restricted, bounded source material subject to D16/D17; they do not enter body-free P6 history. Current helpers fail three isolated cases below. Real provider size, type, region, URL origin and retrieval window limits remain qualification evidence, not guessed permanent constants.

### P25-P09 — Forwarding authentication and loops

**Concern: material; severity high; likelihood medium/high for real forwarding.** Blind SPF rejection loses legitimate requests; blind trusted-header acceptance or allowlisting bypasses abuse controls. Auto-acks can create loops or disclose information to forged senders.

> Qualified provider/trusted-hop evidence feeds D19's existing admission and review policy. Do not treat SPF alone as requester authentication, assume DKIM survives all forwards, accept an unvalidated ARC chain, or turn an arbitrary X-Forwarded/Authentication-Results header into an allowlist. Preserve unknown, failure and conflict separately. Prove direct and forwarded delivery, spam filters, upstream forwarding restrictions, self-address/return loops, Auto-Submitted messages and repeated deliveries before making the selected route operational. No diagnostic verification message triggers D13. No app-layer DSN or acknowledgement is sent to unadmitted suspected forged originators.

A successful path test proves the tested path at that time, not capture of every upstream filtered message, mailbox history or sent-folder synchronization. Normal mailbox filtering/security controls are not broadly disabled to make a test pass.

### P25-P10 — Recovery and temporal account boundaries

**Concern: material; severity high; likelihood high over the integration lifetime.** Reconnect can duplicate intake, route old mail by today's mapping, or attribute another account's receipt to an old row.

> Receipt identity binds tenant, provider account/connection lineage and provider email ID independently of webhook delivery attempt. Preserve original receipt/route-generation evidence. Replays, repaired reads and bounded recovery listing reconcile that same source before any business mutation. Same-account receiving credential replacement may perform current authorized read/recovery with auditable revision selection; it cannot change source ownership. Account/region replacement does not retry old work through a new identity. Permission, DNS, endpoint and credential drift invalidate affected proof without deleting configuration or history. Disablement/re-enable and signing-secret rotation have explicit pending proof, cutover, backlog and old-secret retirement states. Suspected compromise does not retain old authority merely for overlap convenience.

Provider event IDs, email IDs and RFC Message-IDs remain distinct. A replayed event with a fresh Svix timestamp is not new mail. Use bounded paginated replay/listing to recover gaps; respect retention and suppression/redaction tombstones so repair cannot resurrect expired or redacted content. A quiet inbox is not itself proof of failure.

### P25-P11 — Shared quota and failure fairness

**Concern: material; severity medium/high; likelihood high at load or attack.** An influx of receipt/attachment reads or incoming mail can consume capacity needed by other Asym messages in that tenant.

> The existing shared connection capacity owner accounts for inbound and outbound API use and provider quota together. A separate key, inbox or domain does not get a new rate bucket. Bound retrieval/recovery concurrency and queue work fairly under current provider response evidence; distinguish API throttling, email quota, content unavailability, source rejection and endpoint failure. Surface the affected tenant connection and accountable next action. No permanent provider rate number or business policy is copied from a guide, and one tenant cannot consume another tenant's credentials or capacity.

Readiness never claims accepted SMTP receipt of mail that the upstream provider rejected before Asym could observe it. Recovery reports the bounded known gap, not fabricated recovered counts. Test simultaneous controlled outgoing work and incoming backlog under synthetic429/quota responses and later the qualified real provider limits.

### P25-P12 — Provider mutation, secrecy and ambiguous success

**Concern: material; severity high; likelihood medium.** Creating or rotating an endpoint can succeed before a network error, leading to duplicate endpoints, lost secrets or harmful repeated rotation.

> Any authorized provider setup mutation records an operation intent, exact object/configuration generation and expected identity before I/O. On ambiguous success, reconcile the intended object by exact bound provider identity; do not blindly create another object, reset DNS, delete old objects or rotate again. Capture creation/rotation secrets directly in managed custody. A lost response may use the qualified exact-object read recovery path; it must not assume a read succeeded or read another object. Every provider read response is scrubbed for secrets, including documented signing-secret fields and unexpected secret fields. Document an explicit interrupted-operation recovery path that preserves the prior working revision where safe and leaves unproved state incomplete. Provider mutation never uses arbitrary caller resources or changes unrelated tenant endpoints/subscriptions.

Test success-with-lost-response, repeated UI submission, timeout after rotation, secret-bearing provider reads, partial credential save, and two concurrent setup managers. Direct source verification supersedes stale search excerpts: current CLI README 0155104e5960c251f696e2518b76664f5d0ea1b9 line502 agrees with the API that GET includes the signing secret. Build fixtures must prove the exact recovery shape and prevent leakage.

### P25-P13 — Retention and independent provider responsibility

**Concern: material; severity high; likelihood medium.** Treating Resend as permanent backup or claiming Asym redaction erased all copies creates misleading promises and unsafe recovery.

> Setup explains that Asym's Support retention, raw/download processing lifetimes and tenant Resend retention are separate. Current provider plan and retention evidence is shown where operationally useful; no indefinite recovery promise or automatic provider erasure is made. Provider-dashboard sharing/export is not an Asym Support sharing capability. Minimized setup and operational evidence excludes message bodies, challenge values, signed URLs, keys and raw headers. Recovery must stop at recorded deletion/redaction barriers. If provider removal requires a support request, the owning privacy/operations process records that distinct outcome without claiming it completed locally.

D16/D17 remain authoritative on Asym copies and audit retention. No new universal retention policy or legal-compliance claim is introduced by D25.

### P25-P14 — Evidence and release gates

**Concern: material; severity high; likelihood high if polished setup screens are accepted as proof.** Source, SDK declarations and current documentation cannot establish actual supported receiving behavior.

> Release qualification pins the adapter/API/SDK fixture family and proves both setup paths, wrong-account/key cases, exact recipient/header provenance, full and attachment-only acquisition, authenticated duplicate/out-of-order events, inactive qualification isolation, managed/external destination proof, interrupted cutover/reconnect/rotation, shared capacity and bounded recovery. Any SDK/API change regenerates affected fixtures. No dependency upgrade follows from this grooming decision. Critical provenance or owner-proof failures block real routing; an administrator cannot override them. A release evidence pack separates local synthetic tests, source review, real provider qualification, browser/accessibility verification and staff usability findings.

## Isolated source counterexamples actually executed

[Machine-readable results](phase26-d25-provider-source-experiments.json) and [experiment source](phase26-d25-provider-experiment.ts.txt) record three actual exported-helper calls under Resend6.11.0, with all fetches intercepted by fixed synthetic responses and a clearly fake key. The source SHA256 is in the result. `bun --no-env-file` was used. No provider, environment, message or DNS access occurred.

1. **HTTP200 `{}`**: `getReceivedEmail` reports `success:true,data:{}`. This proves its success return does not establish the mandatory received-email schema.
2. **Attachment page `has_more:true`**: the helper returns the first attachment as successful data and loses remaining-page information. This proves a consumer cannot infer full acquisition from this helper alone.
3. **New response fields/default request**: runtime raw/received_for/html_format survive the unchecked cast, while the request has no html_format query. This disproves a claim that TypeScript's older declaration removes those response fields, and establishes the actual default representation path. It does not demonstrate a live provider's body size or semantics.

The experiment is explanatory evidence of current source behavior, not implementation tests or a proof that a proposed solution works. All three checks produced their expected counterexample; exactly three intercepted calls occurred and no fixture remained. No source edit or installed dependency change occurred.

## Implementation proof checklist and order

Resolve P01–P06 in the recorded decision and owner amendments first. Then design the exact proof/credential/route-generation and ingress contracts together before implementing screens. Preserve D1–D24 while tracing these amendments into the eventual formal specification and tickets only when the founder authorizes that stage. Build the mandatory provider spike before real domains open. Following provider qualification, prove the two accessible journeys with interrupted progress and actual permission differences; finally prove production-shaped recovery, migration and cutover. Tests must cover:

- Wrong tenant/account/key/route/event selectors; malformed and malicious provider data; no tenant discovery from content.
- Full-access receiving credential denied to outgoing paths and vice versa; no secret through errors, traces, exports or repair UI.
- Existing-address challenge independent of forwarding, same actor/step-up, no Support-visible code, replay/expiry/address changes.
- Managed destination uses exact P26 proof; own intake cannot substitute external access; no automatic Default destination mutation.
- Candidate qualification succeeds while operational route remains off; ordinary sends/intake stay fenced until atomic activation; no setup noise in Support/CRM/reporting.
- Direct, forwarded, Bcc, multiple recipients, spoofed/duplicated headers, attachment-only, missing raw, unknown schema, partial pages, CID/data-URI response, expired URL, rejected file and bounded download.

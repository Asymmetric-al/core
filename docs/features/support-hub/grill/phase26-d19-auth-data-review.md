# D19 independent authorization, data and CRM review

Date: 12 September 2026. Scope: designated reviewers per inbox with tenant oversight, for retained email held before ordinary Support admission. Read-only source review at Core `7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd`; no runtime, database, provider, permission, migration or concurrency test was run. The founder selected A; the amendments below are proposed for the parent synthesis, not independently ratified. D1–D18 remain unchanged.

## Disposition

**Accept with required amendments.** A is a sound responsibility model if designation is separated from current authority and the action is separated from future routing/sender policy. Current technical recovery/routing code provides useful infrastructure, but it is not a proved implementation of the new review contract. No replacement CRM, role hierarchy, inbox provider, generalized workflow system or bespoke policy language is needed.

The strongest alternative is one central tenant team. The same eligible team can cover several inboxes under A, so central staffing should be an ordinary configuration. A's benefit is explicit accountability at each responsible inbox, not an assertion that decentralized staff are always better reviewers.

## Independent findings and required amendments

### DA01 — Responsibility must not create access

**Material concern: yes. Severity high, likelihood medium if broad staff roles are reused.** A reviewer designation might silently grant whole inbox or restricted-message access. Membership changes could leave stale authority in claims, queues or cached rows. The evidence is the current coarse role wrapper and service-role operation path, plus D1's explicit contrary invariant. This narrows A, not rejects it.

**Exact proposed language:** “Intake-review designation records responsibility only. At every list, preview, action, download, retry, result and deferred continuation, the owning server boundary evaluates current tenant membership, active designation, applicable review capability, held-content classification and permitted destination. A role label, team membership, inbox assignment or previous successful read alone is insufficient. Revocation denies subsequent work immediately at the authoritative boundary and invalidates user-scoped projections without copying restricted content into oversight.”

Use one routine review capability for eligible one-item decisions, qualified by reason/source/inbox. Do not invent separate roles for each button. Keep configuration/future-policy, permanent disposal, security/classification and platform unknown-tenant powers separate because their effects differ. A backup/team is effective only through its currently eligible members; no automatic grant to restore coverage.

### DA02 — Enforce equal tenant endpoints and immutable provenance

**Material concern: yes. Severity high, likelihood medium under service-path mistakes/import/backfill.** ID-only FKs permit inconsistent endpoint tenants even when each row carries a tenant. Editable source/actor/reason fields can turn a permitted row into a different forbidden row. This changes the database qualification, not A.

**Exact proposed language:** “Tenant-owned review, receipt, destination, actor-membership and admission references must be equal-tenant by database constraint or one authoritative owner-enforced relationship where a cross-owner FK is inappropriate. Accepted source identity, original receipt evidence, deciding actor and prior disposition evidence are not caller-editable. Current state is changed only by the qualified command; corrections append a new decision rather than replacing history.”

A `(tenant_id,id)` candidate key on tenant-bound intake rows permits composite FKs without forcing null-tenant platform rows into a tenant. Null-tenant→bound assignment remains a separate platform owner operation. Avoid generic untyped `{type,id}` links when a known relation can be constrained. Do not make arbitrary arrays of candidate IDs into a grant. Reject/delete/cascade behavior must not erase source audit or conversation truth by accidental inbox/user deletion. Exact physical table names need not be frozen now.

### DA03 — Preserve server-only raw stores; test all access paths

**Material concern: yes for proposed exposure. Severity high, likelihood medium.** Building the review UI by granting direct table access could expose raw HTML, recipient arrays, provider payloads or unrelated held mail. The inspected migrations deliberately revoke such grants. This narrows implementation reuse.

**Exact proposed language:** “Raw receipt, routing and review evidence remain server-owned. The browser receives a minimized qualified read model and invokes scoped commands. Browser direct writes to disposition, decision attribution, receipt identity or audit are denied. Any later exposed read relation uses a currently authorized predicate and safe columns; owner-definer views, RPC execute grants, storage access, reporting, exports and service-role jobs must preserve the same boundary. If any ordinary row update is allowed, both the existing-row eligibility and resulting-row validity are explicitly specified and tested.”

Do not claim PostgreSQL always permits reassignment if WITH CHECK is omitted: in applicable policies PostgreSQL uses USING for the check by default. The real requirement is to specify/test both semantic predicates; broad same-tenant predicates still fail to protect inbox/source/actor changes. `FORCE RLS` also does not constrain a BYPASSRLS service role. Keep privileged authority validation explicit.

### DA04 — Narrow release is a different effect from future routing

**Material concern: yes. Severity high, likelihood high if SaveAndContinue is reused.** A routine action could alter future routing, redirect an existing rule or release other messages. It could also appear to approve identity or overwrite CRM. The inspected route function demonstrates these broad effects. A needs a narrow command.

**Exact proposed language:** “Release this message authorizes only the current retained logical input to re-enter canonical intake subject to all current non-overridable gates. It never creates or changes a persistent recipient/alias/domain rule, sender allow/block policy, CRM record, relationship, email-verification state, consent or external message. Choosing an eligible one-item destination is recorded on that disposition; it does not create future routing. Broader changes are a separately named owner action with explicit scope and impact.”

A release may correctly continue an existing conversation. Its confirmation/result must distinguish released for processing from admitted to actual conversation and technical failure. Reusing shared command infrastructure is correct; repurposing route-save semantics is not.

### DA05 — Transactional disposition and durable admission responsibility

**Material concern: yes. Severity high, likelihood medium.** Save-success/audit-failure, resolve-success/dispatch-failure, simultaneous release/dismiss, and response loss can drop accepted work or duplicate admissions. Current sequential route writes and non-unique read-before-insert demonstrate the weak seam. A's implementation contract changes.

**Exact proposed language:** “The current-state transition, immutable decision record and durable admission/continuation obligation commit atomically under the current disposition revision. Unique receipt-level business-effect identity and a serialized or equivalent conditional transition prevent duplicate admission and conflicting release/dismiss results. A repeated command returns its durable outcome; replays may resume incomplete secondary work but cannot create another source message. A lost response is reconciled by logical command identity before retry. Claims and transport idempotency are supporting mechanisms, not the durable business guarantee.”

Admission rechecks current restrictions and active destination even after prior review. If changed, retain a truthful owned hold; do not quietly admit elsewhere. Correction never reuses a pre-revocation authorization snapshot. If new safety reason requires a new review round, append it under the same receipt identity with one current disposition. Do not conflate retry attempts with multiple business decisions.

### DA06 — Actual acting profile, original author and original time

**Material concern: yes. Severity high for audit correctness, likelihood medium when IDs differ.** The current user/profile mismatch can produce FK failure after route mutation or incorrect attribution; using release time as received time also distorts source evidence. This changes the permanent seam.

**Exact proposed language:** “The authenticated acting profile/membership is resolved from trusted server context, independently of the auth-user identifier. Original message author and original received evidence remain source facts. The review record identifies the actual reviewer, decision time, reason and disposition revision. Support-ready admission time is recorded when admission truly succeeds; absent original timestamps remain explicitly absent/unqualified and cannot be replaced with current time for eligibility.”

Preserve D13's original fifteen-minute utility and terminal exclusions; no replay acknowledgement. Preserve D14 reply-target readiness and no fabricated earlier work time. Do not copy message text, addresses, raw headers or freeform secrets into audit just to explain a decision; use bounded reason codes and source references.

### DA07 — A CRM context link must not launder held content

**Material concern: yes. Severity high, likelihood medium.** A familiar name/known contact could be treated as trust, held content could appear on a CRM timeline before admission, or tenant oversight could use CRM access to bypass intake restrictions. D1/D9/current owner boundaries prohibit this. This narrows the journey.

**Exact proposed language:** “Held intake is not an ordinary CRM interaction and does not create, merge, delete, verify or update CRM identities/relationships, last-contact values or giving records. Current authorized CRM context may be opened separately when legitimately needed, preserving place and draft/review context, but it cannot prove requester identity or grant access to the held input. After valid admission, CRM displays the same permission-aware conversation projection under ratified related-record semantics; it does not store a second copy of the held body or a synthetic reviewer-authored communication.”

The requester/email sender, represented organization, authenticated reviewer, assigned coordinator and CRM owner remain separate. Shared ministry email addresses and forwarded mail are permitted evidence shapes, never identity proof. Restricted care classifications remain with their actual owner; neither recipient inbox nor CRM name overrides classification.

### DA08 — Coverage/oversight metadata is still protected data

**Material concern: yes. Severity medium to high by class, likelihood medium.** Cross-inbox counts, sender names, subjects, candidate destinations and “three hidden items” can leak sensitive ministry activity; stale counts can conceal abandoned work. A needs a deliberate summary contract.

**Exact proposed language:** “Oversight receives only the coverage and workload aggregate categories its current capability authorizes, evaluated before counting and pagination. It does not receive body, subject, sender, attachment name, candidate restricted inbox, CRM identity or raw provider evidence merely to display health. An authorized aggregate is labelled as such and never represented as the total content-visible queue. Query failure is unavailable, not zero. Drill-through independently rechecks content authority.”

Per-inbox review list/search/order/count/empty state must use one authorized predicate; cursor scope includes tenant and authorization context and resets on permission change. Use indexed tenant+responsible-inbox+current-disposition/age predicates with bounded pagination. No all-tenant body fetch followed by client filtering and no per-row provider/CRM fan-out. Certified workloads must set actual page, endpoint and fan-out budgets later; do not copy old `.limit(50)` or runtime throttle settings as product limits.

### DA09 — Retention and correction cannot rely on cascade deletion

**Material concern: yes. Severity high, likelihood medium over account/inbox lifecycle.** Current FK cascade/set-null patterns can erase explanation or sever identity. Raw snapshots/HTML/attachments/logs can outlive the purported held-content deadline. Current migration architecture plus D16/D17 makes this a required owner seam, not an invented compliance program.

**Exact proposed language:** “Pre-admission held content has its own qualified bounded lifecycle, including unresolved, dismissed, released, expired and preservation-restricted cases. Inbox/reviewer/route removal cannot erase or orphan accepted-input responsibility or required decision evidence. Retention acts on the complete owned content graph, with source restrictions, legal preservation, provider custody limits and backup restoration controls inherited from D16/D17. Expired content is not recoverable by ordinary Undo; the durable disposition remains truthful without retained raw content.”

A routine dismiss decision is not immediate permanent deletion or sender blocking; any reversible correction must re-enter current qualification under the same receipt identity. Release Undo must not pretend to unsend mail or erase later CRM/support work. Do not retain unrestricted before/after raw bodies in a supposed append-only audit. Retention periods and control-state details are for the parent's full lifecycle synthesis; this independent report does not invent a universal legal period.

### S1 — Stable admission identity versus cancel/re-release attempts (material)

R13 says accepted-input identity, source generation and decision sequence, but does not explicitly state which belongs in the permanent effect key. An implementer could include the decision generation in the admission key (duplicate message after Return/re-release) or use one canceled transport key forever (legitimate re-release remains suppressed). R18 cancellation also must invalidate already queued work, not merely change the UI.

**Append to R13/R18:** “The durable admission-effect identity is stable for the canonical input and each D1-qualified recipient occurrence. Source/gate revisions, review decisions and continuation attempt IDs are fences and lineage, not reasons to mint another admission effect. Return to review invalidates the pending decision/continuation generation. A later eligible release records a new authorized decision and continuation attempt against the same stable admission-effect identity. Old canceled workers cannot act under the new decision, and a canceled attempt cannot permanently suppress a valid later release.”

**Expand P13/P19/P20:** prove Release→Return→Release before admission, with both old and new workers arriving in either order; obtain exactly one admission by the current decision, or no admission if current gates deny. Repeat with a lost response and gate/source revision change. Verify a provider retry or new review sequence does not change the business-effect identity.

### S2 — Pending review authority cannot become worker authority (material)

R04 names current actor checks and R17 includes revocation, but R17's outbox clause mentions only current gates/frontier/scope. Make the deciding actor/decision qualification explicit so a service worker cannot complete a revoked person's stale release solely because the worker has elevated permission. Do not retroactively falsify already valid completed history.

**Append to R17:** “At the admission fence, the decision must remain currently qualified for its deciding actor/designation, source and destination; the service worker's own privileges do not substitute. A revocation that wins before admission blocks that pending positive effect and records an owned current outcome. If admission committed first, retain its valid historical evidence and apply current restrictions to subsequent access/effects. Use the owner-qualified authorization/restriction fence and decision revision; this does not require one global version counter across all platform domains.”

**Expand P19:** actor loses designation or source/destination permission after durable release request but before worker admission; ensure no admission through cached permission. Also prove the opposite valid ordering and no audit rewrite.

### S3 — Tenant-owned references versus global identity (material precision)

R14's broad structural-equality sentence and P14 must not require global auth identities themselves to become tenant-owned. The exact relevant binding is active tenant membership plus the real acting profile, while dynamic authorization cannot be guaranteed by a FK.

**Narrow R14/P14:** “Stored tenant-owned review/source/inbox/conversation/team/route endpoints enforce equal tenant identity with composite constraints or the existing equivalent tenant guard. Global auth/profile identities, where applicable, are bound through the authoritative tenant membership and actual acting-profile relationship rather than copied into a new tenant identity. Foreign keys establish relational integrity; current permission and classification checks remain required at each command/admission fence.”

This retains the requirement to fix existing ID-only review→receipt/route relations and protects against weakening it into an application convention. P14 should name the actual persisted tenant endpoints separately from permission-revocation tests.

### S4 — CRM “match” wording accidentally forbids permissible lookup (material ambiguity)

R22's “create/match/merge a Party automatically” overstates D9, whose R02 permits owner-qualified correspondence attribution but denies that a match candidate is automatically a Related Party. Do not authorize a new auto-link by correcting the wording.

**Replace that phrase:** “create or merge a Party, establish a related-record association, assert verified identity, or perform a CRM mutation automatically.”

Add: “An authorized read-only identity lookup follows the existing owner's qualified semantics; a candidate match never proves human identity, representation authority or a related-record association. Correspondence eligibility still requires genuinely admitted source-message evidence under D9-R02 and is not created by a held-item lookup.” Keep the restriction on ordinary CRM interaction/last-contact before admission.

### S5 — O07 needs a reproducible capacity trigger (required control qualification)

“Backlog predicts missing a deadline” is a reasonable intended signal but lacks the estimator/measurement provenance that makes the threshold falsifiable. Avoid introducing a new predictive analytics subsystem.

**Narrow O07:** “Backlog or oldest processing age exceeds the deployment's recorded owner-qualified capacity threshold for completing within the earliest applicable active deadline; or any retained input lacks its durable disposition/continuation obligation.” Tie the deployment threshold to P34/P41's measured load and bounded drain proof, record its units/value/owner before activation, and report unqualified capacity rather than inventing an estimate when evidence is missing. The threshold need not be a universal product number. The existing owner and no-blind-replay response remain appropriate.

The 14-day/25-page/50-max/24-hour/48-hour values are explicitly proposed product judgments rather than claimed legal or measured vendor requirements. This review does not independently certify their operational optimum. No new contradiction was found in the Email Studio/P6/Resend split or the retention ban on reviving expired bytes.

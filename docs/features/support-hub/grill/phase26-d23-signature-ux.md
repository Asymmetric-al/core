# Professional signatures without slowing down a reply

Fully founder-ratified D23 UX, 12 September 2026, accompanying [D23-R01–R28](phase26-d23-adversarial-review.md). A and Tiptap are selected; the complete amendment package is fully ratified. These are required interaction outcomes, not tested screens.

## What a responder sees

The ordinary reply composer contains the editable answer and one compact managed signature immediately below it, before any deliberately included quoted history. Staff see its actual resolved wording before sending. Signature text is readable/selectable but not an independent editable region that a pasted reply, Select all or a formatting command can accidentally change. The complete outgoing document still includes this managed slot as canonical structured content; visual separation does not mean a hidden append at Send.

Illustrative content only; these examples establish no new inbox, role or ministry workflow:

```text
Maya Chen
Donor Care · Example Ministry
example.org/contact
```

```text
Alex Rivera
Staff Support · Example Ministry
support@example.org
```

The displayed name is the actual responder's qualified public wording. The second line describes the tenant's real inbox/team. It is not inferred from access rights, giving access, a CRM record or the conversation coordinator. An optional logo can sit above the same text using the qualified presentation; no essential meaning depends on loading it.

The quiet **Signature** menu offers Details, **Refresh signature**, **Hide for this reply** or **Restore signature** when appropriate. It is labelled and keyboard/touch accessible. No routine picker, permanent extra toggle row or mandatory preview dialog is added. Hide affects only this draft's optional closing; a small “Signature hidden · Restore” state explains it. The next reply starts with its configured signature. Required organization/legal content in the shared frame remains visible and cannot be removed through this control.

Refresh copies the current selected signature revision into only the managed slot. It preserves the answer, audience, attachments and this draft's Hide choice and participates in draft undo/revision handling before admission. Restore reveals the retained pinned copy after current eligibility checks; if unusable, it offers explicit Refresh/repair rather than silently substituting newer content. An actual sending-inbox or resolved-language change requalifies the copy for that new context and shows the change before approval, preserving the answer/audience/attachments and the omission choice where allowed. Routing or assignee changes alone do not trigger it. Manually typed closings and quoted older signatures are not deleted by guesswork. Inserting D18 wording never appends a second signature.

## A focused inbox settings page

At **Support settings → Inboxes → [Inbox] → Reply signature**, show:

- The selected publication's internal name, authored language and a readable synthetic example.
- A clear state: **In use**, **Newer version available**, **Needs attention**, or an explicit permitted team-only/no-optional-signature posture.
- **Change signature**, which selects an eligible published revision, previews its effect and saves the inbox binding through Support.
- **Edit in Email Studio** and **New signature** when the person has the separate authoring capability.
- A concise explanation: “Used for new email replies from this inbox. Existing drafts keep their selected version until refreshed.”

Do not expose tenant IDs, compiler hashes or provider jargon in the normal screen. Details/history can show source/revision and actual actor when helpful. A person who can configure this inbox but cannot publish may select an existing eligible source. A person who can publish but cannot configure the inbox can edit the source without implicitly changing that inbox. A person with neither receives a useful read-only preview instead of a dead-end editor.

An explicit selection persists an exact published revision, not a mutable “latest” alias. A newly published revision appears as available to authorized managers; it does not silently update inboxes. **Use for inboxes** supports a deliberate bounded selection with before/after and permitted affected names, current revisions and any blocker. The selected set changes atomically or not at all. Users outside the scope cannot infer hidden inbox names/counts.

## Create or edit in Email Studio

The contextual action opens a focused **Reply signature** source view inside the existing authoring surface and preserves **Back to [Inbox]**. Email Studio's Signatures-purpose list addresses the same source records. It has search, Active/Archived, internal names, language, published/draft status and current permitted use. It is not a second library copied from Support.

**New signature** starts with a text-first compatible starter. A logo-with-text starter is an example of the same allowed content, not another layout engine. **Customize** or **Duplicate** deliberately creates a new source draft with provenance; a shared-source edit creates a candidate under its existing identity. Neither operation changes current use.

The form contains internal **Name**, optional **Description**, authored **Language**, a short Tiptap editor and synthetic preview. These metadata controls remain ordinary inputs. The signature body toolbar offers only the qualified purpose's emphasis, links, typed public fields and governed logo control; undo/redo remain available. Typography, color/contrast, spacing and logo presentation use the compatible Email Studio Brand Kit controls. More professional appearance comes from readable composition and dependable output, not arbitrary HTML or CSS.

The public-field picker explains the actual value meaning: **Responder public name**, optional owner-qualified public title, and qualified team/organization values. It contains no donor/customer/CRM property browser, role inference, signature-source author, assignee, personal email, private phone, location, avatar or protected-action token. Current contact wording and links use approved team/organization details; D23 adds no per-person public email/phone descriptors or private-profile fallback.

A Logo control chooses or uploads through the existing governed asset picker. It shows scan/readiness, accepted types and the actual published size/dimension bounds. The author can replace/remove it and supply appropriate alternate-text intent without editing markup. Essential identity remains text; an optional repeated logo in the shared frame is handled by the approved complete-message presentation before review. Loading and failed uploads do not become broken image URLs in a publication.

## Save, publish and apply are distinct

| Action                               | Visible result                                                                                       | What stays unchanged                                                                  |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Autosave / Save draft                | Saved checkpoint with current revision, or Not saved/Conflict with repair                            | Published source and inbox bindings.                                                  |
| Preview                              | Synthetic complete-message HTML/plain-text and supported scenario previews                           | No source publication, inbox update or message.                                       |
| Publish                              | Exact candidate becomes an eligible immutable source publication                                     | Existing bindings, copied drafts and history.                                         |
| Submit for review                    | Existing P17 review state when policy requires it                                                    | No implied publication or application.                                                |
| Use for this inbox / Use for inboxes | Exact selected eligible publication becomes the source for future draft copies in the reviewed scope | Already copied draft text and admitted preparation/history.                           |
| Publish and use for this inbox       | One deliberate UI action sequences publication and application                                       | If application fails, the source is Published but not Applied; prior binding remains. |
| Restore a prior version              | New draft from permitted historical source, with comparison and normal publication                   | Existing immutable history.                                                           |

The contextual publish-and-use button names the actual target inbox. A success state must report both stages accurately. The UI can reconcile an uncertain result without asking the person to republish or recreate the same signature. When another manager changes the inbox meanwhile, show the current binding and compare rather than overwriting it. No signature operation sends mail or generates a new CRM interaction.

A new publication may remain unassigned. Publishing signature content must not require authority over every inbox that once used it. By contrast, a change to an existing shared Brand Kit/Role Layout still follows its own P17 impact and protected-review rules. The focused signature editor cannot quietly broaden those permissions.

## Public name and privacy

“Public responder name” means the current tenant-membership presentation value approved under the identity owner's policy. Approved does not invent another review queue for every nickname. Staff who can maintain their own public presentation use the shared owner command from a contextual link with a clear explanation of external use. The change does not edit legal/auth/CRM names. Tenant-specific context remains clear if the same person belongs to more than one tenant.

Use the full supplied public string without first-name extraction or ASCII-only restrictions. A public title is optional and must have a qualified source; use the team line if there is none. Missing optional fields omit their complete line/separator. Missing name chooses only an expressly approved team fallback, with its actual result visible, or blocks with a focused repair message.

**Team only** is appropriate when the inbox intentionally speaks as a team. Do not label it Anonymous: headers, body, quoted content and attachments can still identify people. The complete preview must make that distinction visible when configuring the policy, and full-message privacy needs go through the existing identity/sender owners.

## Archive and safety correction

An unused source can be archived from new selection/copying. If a source is currently selected by inboxes, show **Replace and archive** to a person with the necessary source and affected-inbox rights. They review an eligible replacement or explicit permitted team/no-optional-signature posture for each affected consumer. The replacement and archive conditions must win one ordered atomic result; otherwise archive does not complete. This is a real dependency, not a broken editor asking for direct database repair.

A source editor without those inbox rights can see a scoped explanation that the source is in use and the necessary configuration handoff; hidden names/counts stay hidden. If the complete affected set exceeds the atomic action's registered bound, authorized managers can deliberately apply replacements to bounded subsets while the source stays active, then archive against the complete remainder; the UI never truncates the affected set or claims premature completion. No requirement to compile a broken body precedes an archive/configuration correction. A safety restriction is different: it can fence unsafe source use immediately even if replacement is unavailable or no manager is present. The owning repair path distinguishes safe existing pins, definitely-unsubmitted work and possibly-sent effects.

Restore makes a permitted source eligible again after current checks, but does not rebind old inboxes or restore removed content by accident. Creating staff departure, role loss or same-email reuse does not delete the team's signature or hand its custody to another person. Ordinary signature retirement never recalls sent mail or reconstructs redacted history.

## Tiptap across Support Hub

| Surface                                                    | Editing choice                                                                           | Required restraint                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Human email reply                                          | Shared Tiptap Reply profile with managed signature projected alongside the editable body | Canonical complete draft and actual audience approval; no arbitrary HTML export as authority.          |
| Internal note                                              | Shared Tiptap Internal note profile                                                      | Separate draft; no external signature or delivery, inert saved scaffold mentions.                      |
| D18 My/Shared reply wording                                | Same P17 structured Tiptap authoring with purpose-specific fields                        | Preserve existing personal/shared permissions; no signature duplication or automatic business actions. |
| Reply signature                                            | Narrow P17 Tiptap profile                                                                | Managed public-field vocabulary, one optional governed logo, no tables/layout scripting.               |
| Existing rich staff brief or long-form Support content     | Shared Tiptap with its actual owner profile                                              | D12 source/retention/visibility remains; do not invent a new rich-text fact to justify an editor.      |
| Subject/name/label/search/email/filters/date/status/reason | Appropriate ordinary shared/native input                                                 | No rich content or editor dependency for simple values.                                                |
| Admitted history, result snippets and static previews      | Safe source-aware static renderer                                                        | Avoid one editable engine per message; renderer is not a new write authority.                          |

The accessible equivalent outline edits the same canonical source; it is not a raw HTML or second authoritative plain-text mode. Content-error handling preserves the unsupported original and disables writable autosave until repair. The signature-purpose link contract may permit qualified mailto/tel without broadening an unrelated Post editor's HTTP/HTTPS-only policy.

## Required visual and usability proof

Preview typical, longest permitted public name, absent optional fields, team-only, long authored translations, RTL/mixed script, images blocked, narrow/zoomed viewport, dark/light/high contrast and real plain text. Browser preview is useful but does not promise pixel equivalence across email clients. A professional published signature is gated by the P17 complete-message rendering checks.

Keyboard, screen reader, touch and IME users must complete creating, saving, resolving a conflict, choosing a logo/field/link, reviewing, publishing, applying, refreshing, hiding/restoring and returning to the inbox. The normal reply path adds no obligatory steps. Local loss of connection preserves qualified draft recovery and shows Not saved; reconnection does not automatically send or publish.

# Q29 — Requester-facing help discovery

**13 September 2026. D28 is founder-ratified and the root is recording it. Q29 is unanswered.** This is independent option research for one next product question, not an accepted answer, new formal specification, implementation or public content publication.

**Best recommendation: A — Relevant public guidance beside Contact support.** At the existing Help entry, provide a small curated set of relevant, currently public and discoverable guidance. Keep **Contact support** immediately available. This option does not add a whole-library search or catalog. Use the same Web Studio/public-content owners, not a second knowledge base or public version of the staff finder.

The strongest reason for A is that it adds an opportunity to find an answer at the moment someone seeks help while retaining the direct contact journey. Its value depends on useful maintained material; the research does not establish how much content an Asym tenant has, how often a donor needs it, or a quantified reduction in Support requests. If no eligible guidance exists, direct contact remains the complete useful path.

## The actual three alternatives

These are competing scope choices, not three modes all tenants must configure.

| Option                                                                | What a requester actually gets                                                                                                                                                                                           | Principal advantage                                                                                                                                     | Honest tradeoff                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Relevant public guidance beside Contact support — recommended** | Open the existing Help entry; see a small curated set of qualified public guidance relevant to that entry, or choose Contact support immediately. Reading guidance does not lose the current task or an entered message. | Relevant assistance where the person already is, with a direct route to staff.                                                                          | Needs maintained public selections, source/locale checks and careful contact-form return behavior. It is a contextual entry, not a new searchable article catalog or standalone help-center destination.                                                                                 |
| **B — Direct contact and ordinary website guidance**                  | Help opens the existing qualified contact experience. Ordinary public Web Studio pages, links and site discovery continue to exist; no requester-facing guidance finder is added by Support.                             | Smallest additional scope and the shortest path to a person; especially credible where questions need individual handling or public material is sparse. | People may miss a useful existing answer at the point of contact, and staff may need to send a link already available elsewhere. This does not remove staff Guidance or ordinary website content.                                                                                        |
| **C — A dedicated public Help center**                                | A tenant-branded destination for browsing topics, searching and opening maintained public help pages, with direct contact available throughout. It uses the same qualified CMS sources.                                  | A useful home for a substantial library that people want to explore, bookmark and revisit independently.                                                | Adds a distinct navigation/discovery experience and content-organization commitment. It need not be an enterprise portal, but its public browse/search and maintenance journey is broader than A. No current Asym evidence proves that larger destination is necessary for most tenants. |

**A versus B:** A preserves B's direct contact and can prevent an unnecessary round trip when a useful public answer exists. B remains a legitimate deliberate choice; an empty or stale answer list would be worse than its clean contact experience.

**A versus C:** A answers “what can help me here?” C answers “where can I explore all this organization's help?” Both can be elegant and retain immediate contact. C is stronger for a substantial maintained body of content and an independent browsing need, but those facts have not been established. The distinction is the breadth/destination commitment, not that C must be cluttered or technically difficult.

Illustrative example, not an observed ministry workflow: a person opens Help while trying to locate a giving statement. A can offer a current public explanation of where statements are found and Contact support beside it. The actual statement remains in its authorized owner surface. B goes straight to the team; C also supplies a separate help destination with related topics. None should require reading an article, signing in or rating an answer before contacting Support.

## Core constraints: what is already decided

The independent [Q29 gap review](phase26-q29-gap-review.md) records the source trace. I directly re-read D1/D27-C and the relevant P23 planning objects. P23 ADR0168/0172 are in immutable **PR1340 planning tree `9069dcad67f9630323474ca5ee8bcc85ca7bf0f6`**, not the current runtime HEAD `7abd2c11`; no shipped capability is inferred. The root owns fresh PR-state verification.

1. **Immediate contact is an invariant.** [D1](phase26-d1-adversarial-review.md) already requires qualified Help entry/contact and normal email continuation without a requester archive, login barrier or mandatory self-service. Q29 chooses accompanying discovery, not whether a person may contact the tenant.
2. **Staff Guidance is a different audience.** [D27-C](phase26-d27c-adversarial-review.md) allows staff to find selected public Pages and consult private Staff guides. That does not publish the staff selection to visitors. Internal title/body/history/search never enters a public corpus. Shared-by-link public Pages can be useful to staff without being eligible for public discovery.
3. **Public content is auth-invariant.** [P23 ADR0168](https://github.com/Asymmetric-al/core/blob/9069dcad67f9630323474ca5ee8bcc85ca7bf0f6/docs/adr/0168-one-exact-public-audience-and-app-owned-authenticated-surfaces.md#L22) fixes one public representation for the exact trusted Tenant/Site/locale/generation/resource. Donor attributes, role, cookies or browsing history cannot alter CMS public body/list membership. Authenticated app surfaces retain their own owner. “Contextual” must mean qualified public page/task/surface context, not a private donor segment.
4. **Public access is not public listing.** [P23 ADR0172](https://github.com/Asymmetric-al/core/blob/9069dcad67f9630323474ca5ee8bcc85ca7bf0f6/docs/adr/0172-versioned-site-search-sharing-profile-and-d1-compiler-ownership.md#L122) expressly excludes Shared-by-link Pages from on-site discovery. A/C must use appropriately qualified publicly listed sources; D27 staff selection cannot override that reach setting. A listing change belongs to the actual owner and cannot be an accidental side effect of selecting a help link.
5. **Public search and form owners remain shared.** [P23 ADR0161](https://github.com/Asymmetric-al/core/blob/9069dcad67f9630323474ca5ee8bcc85ca7bf0f6/docs/adr/0161-derived-public-site-search-projection-and-adverse-first-convergence.md#L16) owns exact-scope derived public search. [P23 ADR0170](https://github.com/Asymmetric-al/core/blob/9069dcad67f9630323474ca5ee8bcc85ca7bf0f6/docs/adr/0170-purpose-bounded-public-form-definitions-and-domain-owned-routing.md#L37) owns qualified public form purpose/occurrence and domain routing. Support should not add a public full-text index, second contact submission ledger or direct email sender.
6. **CRM and giving remain authoritative.** An article can explain how to find a statement, update information or contact a team. Reading it cannot prove identity, expose a gift, execute a refund, update contact details, create a Party/Support request or mark a problem solved. Actual owner actions retain their authorization. Public queries and article visits do not become contact history or CRM intent scores.
7. **D28 is unrelated to article use.** A public article view, search, negative article reaction or contact-button click is not a completed human Support opportunity and cannot produce a D28 invitation. No survey or article-rating feature is bundled into Q29.

## What a strong A journey would need after selection

These are consequences to qualify in the selected-answer review, not additional decisions silently settled before the founder chooses.

- **Entry and orientation.** Help opens within the established surface with a clear Contact support action immediately available. Relevant public titles are concise and task-oriented; a small selection earns its space. Do not insert a required category chooser or ask “Have you checked the articles?” A literal column layout, floating widget or number of suggestions is not frozen now.
- **Deliberate contextual selection.** Offer only the small qualified selection appropriate to the current Help entry. Safe context uses an approved surface/page identifier and independently qualified locale; it does not inspect a private contact form, CRM record, page query string or error payload to generate suggestions. A promises no new library search, catalog or automatic recommendation engine.
- **Read and return.** Opening guidance preserves where the person was. If contact text already exists, switching to/read/back from a public answer preserves that local draft under the contact owner's existing custody. A source page should be rendered by its real published reader; do not promise a full-fidelity miniature for arbitrary embeds/forms. A contextual summary/link is sufficient when inline rendering is unsuitable.
- **Human contact stays direct.** The same contact action remains reachable on entry, beside the curated guidance, while reading and in empty/failure states. Guidance unavailability cannot take down a working contact path. A user does not need a negative article rating to reveal a form. The contact occurrence and acknowledgment use the already qualified owners and exactly one intended outcome.
- **No useful guidance.** Show direct contact without an empty “knowledge base” detour, fake popular answers or broader fallback into another Site/locale. If relevant content is unavailable, say so quietly where needed; never suggest the user caused the failure.
- **Maintenance.** A qualified maintainer chooses public discovery content/context in its actual owner, previews the requester presentation and can remove a selection without deleting the source. Source withdrawal/listing/locale changes remove ineligible discoveries promptly. An inbox manager or staff-guide publisher does not automatically acquire Web Studio publication authority. No parallel article copy or second public visibility switch.
- **Mobile/accessibility.** Use existing shared UI/typography, descriptive links, keyboard/focus return, long translated titles, RTL and readable single-column flow. Keep Contact support visible without hover or unnecessary animation. Respect authenticated app and anonymous CMS boundaries; a logged-out visitor can still reach the normal qualified public contact path.
- **Truthful outcomes.** Do not call an article click “resolved,” no-contact “deflected,” or page abandonment “satisfied.” Any later analytics proposal needs explicit units and owner qualification; no new tracking program is necessary to choose this journey.

If C is chosen, the same rules apply plus a complete help-home/topic/browse/search/breadcrumb/canonical-link and maintenance journey. Its labelled search must describe its qualified public corpus, preserve exact Site/locale/source eligibility and retain direct contact in results and no-match states. It must not import private contact text or CRM facts into public queries. C may use an existing public Site/page route; it need not create a subdomain, duplicate brand, another editor or an account-only portal. If B is chosen, D27 staff guidance and current public pages remain useful and immediate contact must still have its already required full proof.

## Recommended founder-facing framing

**Question:** When someone opens Help, how much public guidance should Asym provide alongside contacting the tenant's Support team?

Show the three actual options with their complete distinction: **A — Relevant public guidance beside Contact support; B — Direct contact, with ordinary public pages kept separate; C — A dedicated browsable and searchable Help center.** Recommend **A** because it brings a small curated set of useful public explanations into the existing help journey while preserving immediate contact and shared ownership. B is strongest when material is sparse or issues need individual handling. C is strongest when a real maintained library merits independent browsing and search.

Do not claim that A is already chosen, that Q29 re-ratifies D27-C, or that all three must be implemented. After the founder chooses, complete the selected journey's adversarial review and precise source/maintenance/accessibility proof. No Q29 ADR, schema, UI implementation, tenant setting, external message or public content change was made by this research.

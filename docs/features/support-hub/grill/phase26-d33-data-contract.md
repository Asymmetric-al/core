## Conditional desired-state command

Input contains only the closed desired mode and expected preference revision (plus the existing trusted request envelope). The server resolves the scope/key itself. Execute one atomic conditional operation:

1. Resolve current authenticated profile, tenant membership and permission for the reader/personal preference. Reject unsupported mode/unknown mutable fields; do not silently drop them.
2. Read/lock or conditionally address the unique preference row. Confirmed missing is virtual revision0. A concurrent first insert is protected by the unique constraint and reconciled as a race, not a duplicate row.
3. If expected revision equals current revision, persist the deliberately chosen mode and advance revision once, including an explicit same-value confirmation. This prevents an old request at revision0 or an old pre-reset revision from becoming valid again.
4. If revision differs and desired mode equals current mode, return **Already current** with the current revision. This confirms current desired state, not that the earlier transport request definitely committed. It produces no new write.
5. If revision differs and desired mode differs, return conflict with currently authorized value/revision. The stale request never overwrites it. A new deliberate reapply uses the freshly presented revision; do not automatically rebase queued writes.

This is desired-state idempotency, not exactly-once transport or business history. It needs no durable outbox, retry workflow or receipt journal. A browser AbortController/timeout cannot establish that a server write was cancelled. Reconcile a lost response against current state; distinguish confirmed rejection, unconfirmed commit and superseded value.

| Race / retry                                                       | Required result                                                                                                                    |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Two first Full saves at revision0                                  | One insert at revision1; other returns Already current1. No duplicate or extra revision.                                           |
| First Full versus first Compact at revision0                       | One admitted revision1; other conflicts if different. UI keeps its own desired local view without calling it saved.                |
| Save Full at0, response lost, retry Full at0                       | Current Full1 returns Already current1; no extra write.                                                                            |
| Full1 then deliberate Compact at1→2, old Full-at0 retry            | Conflict/current Compact2. Never reset to Full.                                                                                    |
| Confirm Compact from absent0→1, delayed Full-at0 arrives           | Conflict/current Compact1. An explicit reset/confirmation fences older absent-state writes.                                        |
| Same-value deliberate save Full at current1                        | Advance to2, confirming that fresh intent; a retry at1 returns Already current2.                                                   |
| Another device changes while a local write is queued               | Preserve newest local view, reconcile current revision, stop automatic queued rebasing; explicit retry decides whether to reapply. |
| Old mutation error/response arrives after a newer confirmed result | Ignore it for current view/cache rollback. Do not restore a whole stale response.                                                  |
| Tenant/profile switch during read/save                             | Result remains bound to original scope; it cannot populate the new scope's reader or preference.                                   |

Serialize client writes and maintain a current local-intent generation. Newer desired local view is never reverted by older responses. A queued request may proceed using the exact acknowledged successor of this client's preceding accepted command only while no intervening external revision/conflict is known; otherwise stop and reconcile for explicit reapply. Choosing a temporary mode while a preference request is unresolved remains available and has no save effect. No offline autosave queue later surprises the person after switching tenants or signing out.

## Grants, RLS and service-role path

The current preference implementation revokes direct browser grants and uses a service command. Retain least privilege and qualify the additive command instead of broadening clients to write a generic settings JSON object. RLS is defence in depth for granted row access; it does not protect a service role that bypasses it. Actual tenant/profile/key checks and immutable-scope transition constraints remain necessary in the server/RPC path.

Require unique/non-null scope, closed enum/checks, tenant-aware membership integrity, valid revision range and owner-qualified delete behaviour. A profile FK and tenant FK separately do not prove their pair belongs to a current membership. Index the actual point lookup/unique scope; do not create a full-text or content index for the preference. Domain money precision, public storage buckets and append-only business events are not part of this schema.

Verify table grants, policies, SELECT eligibility and UPDATE old-row/new-row checks, views/functions and execution grants. PostgreSQL may reuse USING as WITH CHECK when no separate expression is supplied; do not claim every omitted WITH CHECK automatically opens reassignment. Nevertheless make the intended old/new invariants explicit and prove allowed writes cannot retarget tenant/profile/key or accept arbitrary revision/attribution. Functions that run with elevated rights need fixed trusted resolution, least execution grants and current caller checks; SECURITY DEFINER is not an authorization repair by itself. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html).

## Cache and lifecycle

Keep confirmed preference, local mode and transient disclosure state separate. Preference keys include tenant/profile/key, segment keys include current source lineage, and asynchronous cache results carry scope/version. No content in durable browser storage is required to remember a two-value default. Existing approved server read-model hooks/TanStack Query can cache preference state with correct scoping; they cannot reuse the current table-only key or indiscriminate rollback unchanged.

Passive refresh updates the known default for the next untouched reader entry. It never reshapes active reading without deliberate application. Access revocation is different: it immediately fences affected content and clears stale client state on the existing source-change/reconnect/visibility contract. Fresh reload uses the confirmed default; same navigation-session back from CRM/preview can restore authorized IDs/anchors/disclosures. Missing or changed targets have truthful recovery.

Activate only after the full safe reader, typed preference command and bounded segment profile pass actual proof. Schema compatibility must preserve existing D20/CRM settings. Unknown future versions remain explicit and read-only rather than being coerced into Compact and overwritten. Rollback retains preference rows/revisions and source restrictions. A segmentation kill switch serves qualified Full for the affected profile without writing the person's saved mode.

See [P01–P36 and O01–O06](phase26-d33-proof-and-operations.md). The actual-source helper probe establishes two current limitations; proposed CAS, RLS, cache, browser and source-map behaviours remain unexecuted release obligations.

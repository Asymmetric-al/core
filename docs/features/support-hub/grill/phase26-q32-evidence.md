This demonstrates why “Preview” needs truthful, consistent behavior; it does not prove a universal web format matrix or require Asym's same layout. ## Scope, ownership and proof constraints

“Preview” delivers some representation of file data to the device. It is not a prevention mechanism for screenshots/downloads or a guarantee of recall. Viewing and Download remain separately deliberate actions. Rendering failure, unsupported type, denied access, expired/removed content and pending/failed hygiene must not collapse into one misleading unavailable state or an automatic download fallback.

Every option retains current source/tenant authority before metadata and bytes; D16/D17 derivative restrictions; private qualified delivery; D22 filename-only search; no AI/OCR/content-index expansion; and the same authorized Support detail via CRM. Any later conversion would be a governed derivative, not a new authoritative document. A sender-supplied filename/content-type is not sufficient file qualification. Supported format/version/size/page/pixel limits, renderer isolation/accessibility and resource/recovery proof must follow the chosen scope, without pretending selection proves qualification.

Email Studio owns governed later content preparation and P6 actual dispatch. Reading a file does not attach it to a reply, publish it as a reusable asset, change recipients or send mail. TipTap remains authoring for the existing rich-text surfaces, not an arbitrary binary viewer. Broader C still excludes document editing, annotation, file management and external sharing unless separately justified and authorized.

This question does not allocate a library, provider, new table, file-format allow-list or quantitative renderer limits. No runtime browser, database, attachment upload/download, malware, provider or participant test was executed. Source refresh, independent question review and deterministic recording checks establish a well-grounded question; the chosen answer will receive the complete adversarial design review afterward.

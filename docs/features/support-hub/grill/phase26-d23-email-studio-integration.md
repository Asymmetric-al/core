# D23: Email Studio, signatures, Tiptap and delivery

**Fully founder-ratified, 12 September 2026.** This addendum explicitly records the accepted D23, D4, D13 and D18 boundaries. It introduces no new product choice, template key, permission, runtime path or implementation authority. The [independent seam review](phase26-d23-email-studio-seam-review.md) confirms the complete accepted package; the [full decision](phase26-d23-adversarial-review.md) and [data contract](phase26-d23-data-contract.md) remain authoritative grooming records.

## One authoring source, several purposeful surfaces

Email Studio/Phase17 owns the canonical structured signature source, authored variants, immutable revisions/publications, governed assets and preparation. D23 qualifies a narrow published Saved Section purpose, **Reply signature**, distinct from D18's Reply/Internal note saved wording. It is not a personal signature library, a new Service message layout variant per inbox, a system-message catalog key or a provider-hosted template.

Support owns the exact published signature selection for an inbox, current draft, managed signature copy, actual actor/visible audience checks and local reply admission. Existing shared identity owns the tenant-membership public responder name and optional qualified public title; approved team/organization content belongs to its actual owner. Responder name is not assignee, template author, legal/full name, login email or CRM owner. The generic profile update that also changes full_name is not a public-name shortcut.

The same signature source is reachable through Email Studio and the contextual inbox action. There is no HTML synchronization, copied configuration library, second staff directory or alternate CRM record. Capability to configure an inbox, edit/publish an asset, maintain public identity and send a reply remains separate. Real permissions—not navigation—decide which actions appear and execute.

## Save, publish, select and copy

| Operation                    | Owner and authoritative result                                                                   | What it does not do                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| Add/Edit/Duplicate signature | P17 authoring candidate with canonical Tiptap JSON and provenance                                | Does not publish, change inbox selection or send.                                         |
| Autosave/Save draft          | P17 revision-checked draft checkpoint                                                            | Does not make unsaved content usable for others.                                          |
| Publish                      | P17 exact immutable eligible signature publication                                               | Does not silently advance inbox bindings or already copied drafts.                        |
| Use for inboxes              | Support atomic, bounded, current-authorized replacement of exact selected publication references | Does not modify the signature source, sender headers or CRM facts.                        |
| Publish and use              | One UI action with truthful distinct publication/application results and durable reconciliation  | Does not claim Applied when only Published succeeded.                                     |
| New reply/explicit Refresh   | Copy the exact selected eligible variant into one managed canonical draft slot                   | Does not create a live Saved Section expression or expand a mutable template at dispatch. |
| Hide/Restore                 | Deliberate omission/restoration of this draft's optional closing                                 | Cannot hide required organization/legal framing or change later drafts' defaults.         |

Ordinary publication and binding changes leave existing valid copies pinned. Refresh preserves the draft's omission choice. Restore uses its retained eligible copy, not an unselected newer publication. Actual sending-inbox/language changes requalify the copy visibly before approval; routing and assignee changes alone cannot impersonate a responder. Source restriction, permission loss and retired unsafe dependencies remain stronger current-use fences.

The existing compatible Service message Role Layout and Brand Kit are complete immutable P17 dependencies. Saved Sections are copy-in authoring accelerators, not a live fragment graph. Repeated insertion/refresh adds at most one managed signature and never guesses away manual or quoted historical text.

## Tiptap edits; P17 validates and compiles

Use shared Tiptap for suitable rich authoring: replies, internal notes, D18 wording, signatures and qualified existing long-form Support fields. Purpose-specific profiles constrain nodes, marks, attributes, variables and assets in both editor and server; a hidden toolbar button is not a schema restriction. Validate original canonical JSON before any parser can discard unknown meaning, preserve invalid retained source for read-only repair, and prevent a stripped autosave.

Signature authoring uses a compact public-value vocabulary and professional text with one optional governed logo. Simple subjects, names, labels, search and other ordinary values stay appropriate inputs. Conversation history uses safe static rendering, with errors distinguishable from empty content. No new Tiptap Cloud, AI, collaborative editing or paid editor service is accepted.

P17's server compiler owns deterministic complete-message HTML and real plain text. Synthetic shared-source previews and actual authorized-context preparation remain distinct. Browser HTML, independently editable bodyHtml/bodyText, arbitrary extra extensions or React Email export do not become authority. The observed mixed Tiptap dependency closure must be aligned and qualified before activation; no upgrade was performed by this ratification.

## Actual email continues through tenant Resend

Human Support replies remain outside the finite system-message catalog. **No new system-message template key is required for signatures.** The published signature is an Email Studio authoring asset. D13's **Support request received** retains its own actual template, intake eligibility and deduplication; signatures cannot make an automatic acknowledgement appear human or satisfy a human-reply target.

An actual reply obtains exact P17 ready preparation, passes Support's current-source/actor/audience admission, and is delivered by Phase6 through the tenant's qualified Resend connection. P6 freezes the envelope, sender/reply identity and prepared HTML/text; there is no mutable Resend template ID/alias, rendering at retry, direct Support mailer or shared Asym sender fallback. Resend CLI remains operational tooling for separately authorized test/admin work, not an app-level compiler or alternative delivery spine.

Internal notes remain non-deliverable. Adding, saving, publishing, applying, refreshing, hiding or searching signatures creates no mail, acknowledgement, CRM interaction, business completion or follower notification. Real source repair attention uses existing qualified owner presentation; it is not a new signature-email campaign.

## Lifecycle and proof

Routine archive requires explicit safe replacement/posture for active consumer bindings. A popular source can first be deliberately rebound in bounded subsets, then archived against the complete remainder; no hidden truncation. Safety restriction can fence use without waiting for replacement or a manager quorum. Shared sources survive ordinary creator departure. Restore cannot reinstate old permissions or disposed content.

Signature source, public-name data, draft copies, preparation, admitted messages, delivery evidence and minimal audit each retain their actual finite owner purpose. D16/D17/D22 source restrictions and restore barriers continue to apply. Today’s template/profile must not replace historical admitted wording or provide a Recent-copy search fallback. Editing a signature cannot recall sent mail.

[Ratification validation](d23-ratification-q24-validation.json) verifies preservation and consistency. The seven historical current-source experiments and prior validation remain unchanged. All 44 proposed-design runtime/database/RLS/renderer/browser/AT/capacity/provider proof groups remain required and unexecuted. Ratification records the decision; it does not declare the feature implemented.

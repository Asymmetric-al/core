## Proposed actual A/B/C fork

**Question:** When a tenant sets up a Support inbox, which email-address path should Asym lead with?

Illustrative example, not a claim about every ministry: a tenant already tells donors and churches to email `help@example.org`, currently handled in its ordinary email service. Its administrator is now preparing Support Hub. Keeping that public address avoids asking people to learn a different one; a new dedicated address can instead provide a cleaner separation when the old address should stay in another workflow.

| Option                                           | What the administrator experiences                                                                                                                                                                         | Strongest benefit                                                                                                  | Main tradeoff                                                                                                                                                               |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Keep an existing Support address first**   | Start with the public address the team already uses and a guided verified forwarding path into its qualified Resend receiving route. A dedicated new receiving address remains available when appropriate. | Preserves requester familiarity and minimizes address-migration work where an existing appropriate address exists. | Retains an external forwarding dependency and requires a clear transition away from replying in two places. Not every tenant has a suitable existing address.               |
| **B — Create a dedicated Support address first** | Lead with a new purpose-specific address on a qualified receiving domain/subdomain; keeping an existing address through forwarding remains available.                                                      | A deliberately separate intake destination with fewer forwarding dependencies for new programs.                    | Tenants with an established public address must either communicate the change or keep forwarding anyway; domain setup and sender compatibility still require qualification. |
| **C — Present both paths equally**               | The first setup screen explains existing-address forwarding and dedicated receiving and asks the administrator to choose, without a default recommendation.                                                | Neutral and flexible across varied starting points.                                                                | Adds an early technical choice for teams that could have followed a sensible contextual default; does not itself improve verification or recovery.                          |

**Single recommendation: A — Keep an existing Support address first**, with an obvious dedicated-address route for tenants starting fresh or needing separation. This preserves the accepted two-path capability and chooses the normal experience, rather than imposing forwarding on every tenant. The recommendation is conditional product judgment: it is strongest when an appropriate public Support address already exists. No evidence supports automatically forwarding a personal employee inbox, a general ministry mailbox containing unrelated/sensitive work, or replacing its root-domain mail routing.

The scope stops at the chosen experience and its consequences. Do not freeze provider-address generation, specific DNS records, physical schemas, verification token formats, timer values or a new onboarding workflow service before the answer and owner qualification. Sender/Reply Identity, public address, receiving route and support-inbox name remain separate existing concepts.

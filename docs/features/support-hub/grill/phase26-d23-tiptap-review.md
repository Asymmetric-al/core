# D23 independent Tiptap integration review

Reviewed 12 September 2026. This is an independent source and primary-documentation review for the selected **A — Inbox-managed signatures with responder personalization**, including the founder's explicit direction to use Tiptap for suitable Support Hub rich-text authoring. It is exploratory grooming. No dependency, runtime, schema, provider, inbox or production content was changed.

**Disposition: Accept with required amendments.** Tiptap is a good fit and is already present. The permanent path is purpose-specific shared editor profiles feeding Core's governed canonical document and compiler. Neither current toolbar choices nor Tiptap's schema parsing alone enforce that contract. Signatures must join the prepared canonical message, not exist solely as a browser HTML/text appendix.

## What the primary Tiptap material establishes

- [Schema documentation](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/editor/core-concepts/schema.mdx#L11) explains extension-defined nodes, attributes and nesting, and that unrecognized formatting can be discarded. Adopt explicit schemas; do not interpret parser normalization as strict business validation.
- [Invalid-content handling](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/guides/invalid-schema.mdx#L19) provides checking/events and acknowledges HTML limitations. Its generic suggestion that noncollaborative editors may strip unknown content conflicts with Core's protected-meaning preservation. Core's rule wins. Its broad JSON accuracy wording does not mean arbitrary business attributes are strictly rejected: the installed-source experiment below demonstrates otherwise.
- [Current parser source](https://github.com/ueberdosis/tiptap/blob/7ab690e5056fe999988552822c4fc1b1064bf094/packages/core/src/helpers/createNodeFromContent.ts#L37) and [editor source](https://github.com/ueberdosis/tiptap/blob/7ab690e5056fe999988552822c4fc1b1064bf094/packages/core/src/Editor.ts#L535) show permissive fallback paths. The installed 3.22.3 source similarly retries after `contentError`; merely enabling a flag does not prevent a lossy save. Avoid feeding unchecked sensitive source into fallbacks that print content in warnings.
- [React composable API](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/guides/react-composable-api.mdx#L13) supports shared context/composition, while allowing hook-based integration where appropriate. Prefer it for new shared integration after version qualification; do not force an unrelated editor rewrite. [Next.js installation](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/editor/getting-started/install/nextjs.mdx#L52) confirms `immediatelyRender: false`; a generic composable example omitting this does not override the Next.js-specific setting.
- [Accessibility](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/guides/accessibility.mdx#L13) explicitly leaves the headless interface's accessibility to its integrator. Accessible Base UI controls, focus, keyboard, names and state announcements are Asym responsibilities, not supplied guarantees.
- [Performance](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/guides/performance.mdx#L21) supports editor isolation/selective subscriptions. [Static rendering](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/editor/api/utilities/static-renderer.mdx#L21) avoids editor instances for display. Neither source proves email-client compatibility, production latency or a safe outgoing-email compiler.
- [Persistence examples](https://github.com/ueberdosis/tiptap-docs/blob/de0873c397b84b221b1924193301819200333f74/src/content/editor/core-concepts/persistence.mdx#L8) illustrate JSON and browser storage. Adopt structured persistence through the authorized owner; do not copy the localStorage demo into sensitive Support drafts or create a second persistence authority.

## Exact amendments to carry into the main decision

**T01 — One authority.** “Tiptap is the shared rich-text authoring engine for appropriate Support surfaces. Its purpose-specific profiles edit or adapt to the versioned canonical Asym document. The P17 owner validates and compiles the complete outgoing document, including the signature, into deterministic HTML and true plain text. Browser exports and editor JSON are inputs or previews, never independent delivery authority.”

**T02 — Signature copy and identity.** “An inbox selects an eligible published Reply signature section. A new external draft copies its exact qualified structured revision into a managed signature slot with provenance; no nested live fragment lookup is introduced. Template/default edits affect future copies. A deliberate refresh replaces only that slot, with expected draft revision, preserving reply body. Typed public-responder fields resolve from the actual authorized sending staff member at preparation; the assignee, CRM owner, template author and last editor cannot impersonate that responder. Changed identity/inbox context invalidates preparation and presents the resulting signature for review.”

This copy model honors [P17 Saved Sections](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/phase-17-system-messages-template-management.md#L930) and ADR0030. The source revision copied and the responder values resolved are different dependencies. The prepared complete message freezes both. Do not introduce per-inbox Role Layouts, mutable nested fragment expansion, or duplicate Brand Kits.

**T03 — Strict validation.** “Before load, save, publish, prepare and admission, validate the canonical schema/version/profile, exact allowed keys/attributes, bounded nodes/nesting/text/assets, protected meanings, typed variables and same-tenant references. Tiptap content checking is supplementary. Invalid or unsupported stored source cannot be auto-stripped, replaced with an empty document or autosaved back; preserve authorized last-known-good/read-only evidence and provide a repair or reviewed migration path.”

**T04 — Paste and import.** “Convert external pasted rich content into the supported purpose profile with visible repair guidance when meaning or assets cannot be preserved. Strip unsafe execution and harmless foreign styling in the controlled import path; never silently strip a protected fact, typed variable, reference or material content. Preserve the current draft on failure. Links and pasted/dropped images do not trigger arbitrary server URL fetches or bypass governed upload/asset admission. Raw HTML editing is unavailable.”

**T05 — Professional semantics.** “Signature contact text remains selectable and readable with images blocked and in plain text. Logos have governed asset identity, dimensions and appropriate alternative text; the signature never consists of an image alone. The signature profile permits qualified HTTPS, mailbox and telephone contact links with scheme-specific validation, rejecting header/control-character injection and unsupported URI schemes; it does not broaden other domains' link policies. Preview uses the same shared email compiler and exact signature content, with synthetic library data and authorized draft context.”

**T06 — Save and conflict.** “Draft autosave reports saving, saved or failed truthfully and never publishes. Save, publication, selection and draft refresh remain separately authorized actions. Revision-aware writes preserve unsaved text on conflicts, failed validation and network failures; a stale tab cannot overwrite a newer signature or publish a different revision than reviewed. No browser-local durable body store, cross-tenant clipboard service or Tiptap cloud persistence is added.”

**T07 — Accessible operation.** “Each purpose has a visible label, accessible name, appropriate toolbar controls and a keyboard path to every action; mode distinction does not rely on color. Preserve selection when opening link/variable dialogs, return focus predictably, expose missing-field and save status without announcing each keystroke, support IME and bidirectional/international names, and keep one-finger mobile editing usable. Signature tokens are understandable as public fields, not raw template syntax.”

**T08 — Versions and display.** “Qualify and lock one compatible maintained stable Tiptap 3 package family across the participating editor/renderer/React Email closure. Version schema/profile/compiler separately from package version. Reader-first rollout and explicit compatibility checks prevent old tabs from stripping new nodes. Upgrades create reviewed drafts/publications as ADR0030 requires; do not recompile admitted history in place. Use static display and bounded editor instances; establish quantitative performance/resource limits with production-shaped proof rather than vendor claims.”

**T09 — No incidental expansion.** “This decision does not add real-time coediting, Hocuspocus/Yjs infrastructure, Tiptap Cloud, paid document services, AI generation, AI search, tracked changes, general document conversion or a new workflow platform. Existing source-owned draft/review history meets this need. Any future editor capability must independently satisfy purpose, permission and canonical-output contracts.”

## Executed source experiments and required proof

[Machine-readable experiment](phase26-d23-source-experiments.json) ran seven synthetic installed-source cases in the required WSL worktree, with hashes of the exact imported shared files. It directly imported `createDefaultExtensions`, installed Tiptap 3.22.3 `getSchema/createNodeFromContent`, and the current pure Support serializer. It did not run a browser, touch production data, fetch the fixture image, save anything to Core or send email.

Observed: three non-toolbar node types accepted; one unknown paragraph attribute discarded despite strict content flag; one unknown node explicitly rejected; supplied fixture agent email included; signature absent from returned JSON but present in HTML/text. This is bounded proof of source behavior, not an XSS finding or proof of the proposed D23 design.

Required independent implementation acceptance tests:

1. Every profile's complete node/mark/attribute/command/paste allow-list: positive examples plus forbidden hidden tools, malicious attributes, deep/oversized input, duplicate slots and unsupported schema versions.
2. Full canonical message → HTML and plain text → stored prepared receipt includes identical body/signature meaning, correct actual responder and exact source/compiler/presentation dependencies; note/brief has no external signature.
3. Missing public name uses only the approved team presentation; assignee/template author/CRM owner/login email never becomes fallback; responder/inbox change invalidates an old prepare.
4. Strict prevalidation catches unknown attributes before a parser can drop them. `contentError` and renderer failures cannot autosave empty/stripped content or log sensitive source. Old tabs cannot overwrite new-profile documents.
5. Word/Gmail/Outlook rich paste, malformed HTML, copied images, tracking links, invalid schemes, text containing literal braces, RTL/IME and long international names preserve supported meaning and keep drafts on failure.
6. Explicit refresh replaces only one managed signature slot; retry is idempotent for the expected revision; template edits do not mutate existing drafts/admitted messages; two-tab saves have a clear conflict/recovery path.
7. Keyboard/screen reader/mobile tests for variable and link insertion, toolbar focus, mode clarity, error association, undo/redo, saving status, zoom, image-blocked rendering and meaningful plaintext. Test current representative Gmail, Outlook desktop/web and Apple Mail clients as part of the shared P17 email qualification.
8. Participating package-resolution/peer audit, SSR hydration, code-split load, bounded worst-case documents, input responsiveness during inbox updates and no per-history-item editor mount. Record actual device, size, concurrency and thresholds before claiming performance.
9. Multi-tenant API, worker and asset admission tests reject forged tenant/actor/revision/section/public-profile references; public-name source updates and permission loss are rechecked before preparation.
10. Migration/rollout/rollback and redaction/retention tests preserve last-known-good evidence and prevent reconstruction of withdrawn content via old library copies, stale previews, browser caches or server logs. D16/D17/P17 remain owning retention rules.

The result completes this Tiptap subreview; proposed production profiles, compiler, RLS, browser behavior and email-client output remain unimplemented and unexecuted.

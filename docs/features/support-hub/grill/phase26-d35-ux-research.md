# D35 — Own-note editing and visible history: UX research

**14 September 2026. Founder selected A; this report proposes the detailed UX safeguards for the full adversarial answer.** It is not a ratification of those amendments, a formal specification or a claim of implemented behavior. No product, private vendor account, database, provider, GitHub state or publication was changed. The parent owns the final reconciled decision; these candidate clauses are research input.

**Recommended experience:** edit one's own ordinary internal Support note in place, save deliberately, preserve its original chronology and show a quiet **Edited** history action. A single read-only history view exposes currently permitted full versions without a Restore button or permanent diff interface. Keep correction distinct from new information, and source privacy distinct from ordinary editing. No autosave, grace timer, forced reason, extra recipient picker or new collaboration platform is needed.

## Core constraints that shape the design

The actual ratified D23-R13–R15 requires shared Tiptap 3 with a code-owned Internal-note profile and safe static history rendering. It does not enable every extension, accept lossy unknown canonical data, notify from a saved scaffold or treat rich-text input as authorization. D17-R05 expressly preserves the existing deadline on note edits. D15 E3/R08 distinguishes new note publication from routine edits and does not send a new alert on every save. D9/D26 preserve one canonical currently authorized Support source through CRM; D16 privacy removal remains stronger than ordinary version access.

The approved app controls remain **Base UI / base-maia**, Maia/Zinc and shared semantic tokens. No Radix replacement, separate editor/diff package or new settings surface is needed for this task. Exact dependency qualification belongs to the shared owner and the parent technical review, not a vendor example.

## The ordinary edit journey

1. **Find the note in context.** The posted card retains its Internal note label, original author and posting time. Its action menu is keyboard-focusable and available on touch, not mouse-hover-only. **Edit note** appears only for the real original human author with current source/edit authority; the server rechecks on opening and Save. Other staff retain ordinary new-note clarification and the separately authorized privacy route.
2. **Open one correction editor.** Edit the note in place with a modest **Editing internal note** heading/label, the qualified Tiptap content and visible **Save changes** / **Cancel** actions. Do not replace or contaminate an existing reply/new-note draft. Preserve the canonical source, reader position, current Find target and Compact/Full preference. One active posted-note editor per current detail is sufficient; switching to another edit must not silently abandon a dirty correction.
3. **Make the correction.** Keep text formatting and safe links under the existing note profile. No required reason, markup syntax, preview stage or second confirmation appears for an ordinary Save. Do not treat every small change as a new event. An invalid or unsupported canonical document stays read-only with the existing Needs migration/repair explanation rather than being flattened into a successful-looking editor.
4. **Save deliberately.** The visible action says what will happen. Keep the editor stable during the request; show a concise saving state. Ordinary text entry, blur, closing a toolbar and navigation do not autosave. A true unchanged candidate can return unchanged without manufacturing another edit timestamp/history entry. Apply the canonical note's validity rules, not a new arbitrary text-only rule that invalidates a previously qualified attachment-containing note.
5. **Return to the corrected note.** After durable success, render the current permitted note at its original chronological position and show **Edited** with reachable edit metadata/history. Restore focus to the note action or corresponding stable card location. Use a polite, brief saved status; do not add a permanent success banner, duplicate timeline event or new publication alert for each typo.
6. **Cancel or leave.** Cancel discards only this unsaved correction, retaining the posted note and unrelated reply/new-note draft. A clean editor closes without a dialog. For actual dirty navigation or replacing the active edit, use one existing shared confirmation with **Keep editing** and **Discard changes**. Do not ask whether to save on every focus change, tab change or view preference adjustment. Save is a separate deliberate action.

Those labels are proposed consistent UI language. The final root design may use the platform's exact existing action label if it retains the same clear meaning.

## History without a second document application

The initial note may have no Edited marker; its ordinary menu can expose **Note history** where current source history exists. After an edit, **Edited** is a reachable history action, not a hover-only tooltip. The normal conversation shows the current corrected content, original author/time and discreet changed state. It does not show an expanded list of revisions under every card.

Open one existing shared history panel/sheet titled **Note history**. Identify the original note, preserve the surrounding conversation and return focus on close. Show an ordered version list with clear **Current**, **Original** and earlier edited-version labels, each with truthful timestamp/actor. Load and display one full permitted version at a time through the safe static renderer; do not mount Tiptap editors for the history. A current version label is not an editable historical snapshot.

Use bounded paginated history queries and explicit loading/failure states. Make the allowed Original version reachable without loading every intervening body. If old content is unavailable under current source/privacy/retention, show only whatever minimal unavailable-state metadata the owner permits. Do not reveal forbidden revision counts, snippets or author facts, and do not invent an original version for legacy data with unproved provenance.

There is no **Restore this version**, bulk rewrite, automatic diff, branching document history, export-new-copy action, public link or history search subsystem. An author who needs to correct current wording starts an ordinary current edit. Viewing a past version does not renew custody, reindex it as current, issue a file link without current authority or expand Support/CRM access. History is useful only while its source remains eligible; it is not an immutable-forever archive.

For conflict resolution, a simple two-section review is sufficient; the root's data command must bind the author's deliberate final action to the actual current version. The exact action that adopts a new base must be visible and truthful. Merely inspecting current text is not consent to overwrite it. Choosing to discard a dirty candidate requires the ordinary confirmation; choosing to keep it does not make stale Save valid. No generic collaborative merge engine is justified.

On an actual account/tenant switch or source privacy revocation, privacy takes precedence over ordinary dirty-state protection. On an ordinary same-author navigation attempt, user control takes precedence over accidental data loss. Browser/OS tab discard cannot be promised recoverable without an already-qualified draft owner; this proposal adds no localStorage, offline edit queue or server autosave capability.

## Attachments, mentions and meaningful corrections

**Recommended bounded default, reconciled with the root's usability/data review:** ordinary correction changes the qualified note body, preserves existing attachment membership/bindings and does not acquire new files or introduce a new notifying-mention picker. Normal paragraph or select-all deletion may remove an existing typed mention node or inline asset appearance; it must not encounter a hidden Save-time requirement to restore those tokens. New supporting material and deliberate new attention use a fresh ordinary note under the existing owner. This is a simplification proposal, not a claim that vendors uniformly prohibit such edits.

Existing typed mention/reference nodes must be faithfully loaded from strictly validated original canonical JSON; they are not silently converted into text, remapped to a similarly named current person or re-fired as new mention events on Save. Deliberate removal during an ordinary edit is distinct from lossy initialization. Unknown canonical structure remains read-only rather than disappearing on parse. New or retargeted mention IDs are forbidden, including through raw or pasted content.

Show actual existing source files in a read-only **Existing files** section while editing. Removing an inline image appearance leaves its file membership/bytes unchanged; explain concisely: **Removing an image from the text does not remove the file from this note or its history.** The current note's original file list remains visible under current authorization, so an image is not silently converted into hidden retained data. No add/remove/replace file management is introduced. Existing metadata and file access remain governed by original bindings and current source/P29 authority; do not reacquire an asset or renew its life. D16 remains the route for removing unsafe material from current/history representations. The editor must not call an appearance change privacy deletion.

Deleting an existing mention node preserves already-delivered attention facts and does not revoke independently granted rights. The no-new-attention contract needs UI and server enforcement, not merely a hidden toolbar button. Normal safe text containing an @ character is not proof of a semantic mention. Where body deletion leaves only existing files, apply the actual canonical note validity rule rather than inventing an incompatible text-only ban.

**Correction versus new event is guidance, not an AI classification problem.** A typo or transcription mistake can be edited. A later changed plan, new decision or action performed deserves a new dated note. If the correction changes what another worker needs to do, the author can add a fresh concise clarification or use the existing deliberate attention path. Edited does not mean seen; changing a historical sentence about a refund does not change the refund or authorize its disclosure. Other staff do not edit the original author's words.

## Accessibility and mobile qualification

[W3C's menu-button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/) establishes explicit keyboard interaction and menu state; reuse the qualified shared component. Enter/Space open the action menu, its items have ordinary keyboard behavior, and closing returns focus predictably. These are distinct from text-editor keys: Enter inserts a paragraph, arrows move the caret and IME composition is not a Save command. A discoverable optional shortcut cannot replace the visible action.

[W3C keyboard guidance](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) emphasizes predictable focus and avoiding shortcut conflicts. If an existing shared modal/sheet is used for history or dirty-state confirmation, follow its [dialog focus/inert-background pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/); do not stack a second editing modal over the history pane. History reading and version selection should not steal focus after an asynchronous response.

[W3C status guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) supports programmatically exposed saving/saved/error outcomes without unnecessary focus changes. Announce meaningful changes once; avoid per-keystroke live chatter. A save conflict needs visible understandable text, not only a toast or color. Use the same concise labels in screen-reader announcements and visible controls.

Preserve the product's separate 200% text-resize and effective 320 CSS-pixel/400% reflow checks. Cover the note editor, current/history bodies, version list, error/conflict review and dirty confirmation with long names, translated labels, RTL/bidi and mobile keyboard open. Primary touch actions use the shared 44 CSS-pixel target where adopted; WCAG 2.5.8 remains 24 CSS pixels or valid exceptions, not a false universal 44-pixel rule. D29-X01 is ratified precedent for precise proof, not a reason to redesign the product shell. Quiet static indicators suffice; no animated edit badge or attention pulse is needed.

## Proof, operations and what remains unknown

The useful release evidence is outcome-shaped: the author corrects a note from each entry surface; a different staff member cannot; original chronology remains; allowed history explains the change; Cancel leaves the note alone; unknown save reconciles once; concurrent devices cannot silently overwrite; privacy/expiry invalidation removes unsafe editor/history/file representations; new mentions/assets cannot be smuggled through paste/raw input; mobile/AT users can complete every state; old permitted sources remain intelligible through migration without inventing originals.

Tenant maintenance should require no new settings screen: permissions use the existing source authority, ordinary edit/history is local to the note, privacy and retention use their actual owners, and legacy qualification is migration work. Monitoring should reuse the parent's explicit safety/source/save-error controls, not collect draft text or a staff editing leaderboard. This report does not invent a separate edit audit lake, arbitrary revision cap, performance guarantee or forever-retention rule.

No rendered Asym prototype, browser/AT test, user study, database race, provider effect or migration test has been run by this report. The strongest supported recommendation is a clear, deliberately saved author correction with truthful finite history and protected source semantics. The root's full decision must reconcile these candidate clauses with exact owner and data contracts before treating the detailed amendment package as ready for founder ratification.

## The three accepted amendments

**1. Receiving credential purpose — verified consistent.** D25-R05 adds a receiving-purpose key under the same tenant connection and managed revision/custody system. The existing outgoing Sending-access key and its proof/dispatch fences remain unchanged. Resend requires Full access for non-send API reads; **Asym**, not Resend, requires the separate receiving key as the accepted safeguard. Current OAuth does not offer a narrower receiving scope. The receiving adapter exposes only closed, exact-resource read/proof operations. A pending unproved key may perform bounded account-proof reads but cannot retrieve ordinary bodies/files before the owner mapping is proved. Full access remains provider-level whole-account privilege; local restrictions must not be described as provider-enforced read-only permission. See [API permissions](https://resend.com/docs/api-reference/api-keys/create-api-key) and [OAuth scope documentation](https://resend.com/docs/guides/building-a-resend-oauth-client).

The accepted amendment changes ADR0029/P6/P17's universal outgoing-only credential description expressly. It preserves one owner, no global fallback and no receiving-key path to outgoing sending, arbitrary provider mutation or ordinary Support/AI secret access. Same-account repair can rely on qualified exact current provider-object evidence without requiring another production send. Wrong-account behavior remains a mandatory real-provider proof.

**2. Shared opaque signed ingress — verified consistent.** D25-R06 extends the connection ingress to dispatch qualified `email.received` events to P26 after raw-body signature and exact scope verification. Outgoing events retain the existing P6 reducer; an incoming event makes no outgoing lifecycle transition. One per-connection endpoint can carry the required subscription union without a webhook per inbox, while source-receipt idempotency remains separate from webhook delivery dedupe. Rotation, proof invalidation and shared endpoint failure preserve independent incoming/outgoing readiness.

This is an explicit change to the earlier ingress scope, not a second delivery ledger or configurable event router. No content field, recipient domain or provider metadata can select the tenant. Authentication of a webhook does not authenticate a requester or every message header. The [receiving API](https://resend.com/docs/api-reference/emails/retrieve-received-email) describes `received_for` as derived from Received-header clauses; D25 correctly leaves precise envelope/trusted-hop behavior behind mandatory qualification rather than claiming that field proves it.

**3. P17 managed Support reply destination proof — verified consistent.** D25-R12 extends the existing Human reply destination's exclusive proof shape. P26 supplies exact current tenant/account/environment/domain/public-address/inbox-binding/generation and controlled new-mail/return-path evidence. The qualified stepped-up P17 reply manager accepts the exact destination revision and accountable monitoring responsibility. P17 owns proof acceptance and the frozen Reply-To identity; P26 owns capture, threading and intake health.

Existing external-mailbox access proof keeps its same-initiating-human, current capability, step-up, single-use and expiry protections. Its code cannot be exposed through Support or completed automatically when Asym receives it. A provider's forwarding-destination confirmation is a distinct, narrowly authorized setup task; it is neither that P17 access challenge nor ordinary correspondence. Managed-route proof cannot silently repoint Default human replies or another product's purpose. No new purpose taxonomy, generic alias engine or per-inbox template is introduced.

## Qualification without circular readiness

D25-R08/R11–R15 separates capture-capable candidate setup from an inbox active for ordinary work. The accepted narrow P17/P6 qualification operation may use the exact candidate sender, Reply-To and credential before production Ready solely for fixed inert proof with an approved real control mailbox/sink. A controlled external new message and reply test the actual route; an authorized human can perform the external steps. This does not create a new platform sender, automatic relay, arbitrary-recipient test tool or bootstrap fallback.

Proof mode, candidate generation, target, content and expected evidence are frozen before I/O. Refreshing status sends nothing. Ambiguous submission reconciles the same occurrence. Normal replies, D13 acknowledgements and catalog mail stay gated. Verification creates no Support conversation, CRM record, ordinary target, follower event or reporting credit. Real early mail retains separate finite custody and original receipt/expiry history; activation later reconciles only currently eligible input under D19. Final activation rechecks current proof, access and generation and commits only the selected binding and its durable continuation.

This explicitly resolves the earlier external-mailbox-only proof model. It does not treat a successful synthetic fixture, provider2xx, code match, DNS lookup or wizard checkbox as current operational readiness.

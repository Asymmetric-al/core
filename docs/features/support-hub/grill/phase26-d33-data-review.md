## Permanent owner and state model

**Reuse the accepted shared preference owner, not the current CRM-only interface unchanged.** D20-R01 requires generalizing Core's existing named-view/preference/list machinery, and D20-R12 explicitly separates personal display preferences from shared view definitions. Register one closed Support conversation-reading setting. Do not store it as a fake gift-history table option, a saved query, a notification preference, a profile biography field or a generic unvalidated JSON key. No generic preference engine, settings inheritance tree or new named-view object is required.

| State                            | Authority and meaning                                                                                                                   | Persistence                                                                                                                                                               |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Personal Support reading default | Shared preference owner; exact current tenant + authenticated profile/member + closed Support-reading key; value `compact` or `full`.   | One server-backed value and monotonic revision. Default Compact when a successful read establishes no explicit value. No tenant default/admin override or per-inbox copy. |
| Current reading mode             | The mode intentionally applied in this current reader visit, initially resolved from the saved default.                                 | Transient reader state. Choosing a temporary mode does not write the default. A deliberate default change may also apply locally immediately, with separate save status.  |
| Expanded regions/navigation      | Current original-source regions deliberately opened, search-target expansion, viewport/focus and qualified return context.              | Transient, source/revision-bound and cleared on unauthorized context changes. No per-message expansion rows or viewed/read activity.                                      |
| Fold projection                  | A dispensable mapping over the current authorized safe source presentation, qualified by source revision and renderer/detector version. | Prefer computation/reuse under existing bounded source caches. Never a second authoritative body, retention purpose, search corpus or permanently retained transcript.    |

The preference is the same when the person opens the same permitted Support detail through CRM. It must not depend on CRM read permission when used in Support, or require full Support administration merely to personalize a reader the person may use. A profile ID comes from the authenticated owner projection, never a supplied agent ID, email match, conversation assignee, CRM owner or a client assumption that auth-user ID equals profile ID.

Logical uniqueness is `(tenant, profile/member, closed preference key)`. Physical table/key names remain a qualified extension of the shared owner; do not introduce parallel stores or synchronize with a legacy Support preference row. The existing API/approved database hooks and authenticated-context mechanics are reusable where they satisfy these requirements. The current gift-history allow-list and patch schema do not yet do so.

## Required amendments and independently testable outcomes

### DC01 — Scope and ownership must be explicit

**Concern: material; severity Medium; likelihood plausible.** A global user setting leaks workstyle across tenants, an inbox setting changes teammates' experience, and a support-agent row introduces fragile email matching/offboarding. A CRM-only route also denies legitimate Support-only readers. S01–S04/S09–S12 establish the existing owner distinctions.

**Effect:** narrows C to one personal setting; does not reject it.

**Exact clause:** “Store the Compact/Full Support reading default for the current tenant and authenticated profile/member through the shared personal-preference owner. It applies to authorized Support reading from Support Hub and CRM. No inbox/team/global-account default, administrator override, conversation row or notification setting is introduced. Resolve custodian and tenant from trusted current context; use Support reader/personal-preference authority, not unrelated CRM administration or an email-derived agent.”

**Proof:** same person in two tenants can have distinct defaults; another person in the same tenant is unaffected; a Support-only authorized reader can manage their setting; wrong tenant/profile/agent input and same-email replacement cannot read/write it.

### DC02 — Qualify one typed setting without another engine

**Concern: material; severity Medium; likelihood high if current helpers are copied.** Current route/helper fields reject or discard the new concept, and a generic JSON merge can corrupt existing column/pin state. S03/S07 and the two real-source observations show why “reuse” must be precise.

**Exact clause:** “Add one closed Support-reading key with only `compact` and `full` to the qualified shared preference schema/command. Preserve unrelated settings and existing registered subjects. Reject unknown mode/schema/input fields rather than ignoring them. Reading mode is neither a named view nor query criteria; it cannot change a saved view's revision, filters, pins, sort, startup route or audience.”

**Proof:** unsupported modes/unknown payload fields fail; saving/resetting reading preserves all existing preference scopes byte-for-byte where unchanged; old gift-history and Support-view consumers retain their existing meaning.

### DC03 — Known absence, unavailable and invalid are different

**Concern: material; severity Medium; likelihood common on slow or failed reads.** Treating read failure as no preference can falsely show a saved Compact default and overwrite an existing Full choice. Silent late hydration can move the document under the user. S05/S08 and accepted D20/D23 recovery distinguish these states.

**Exact clause:** “A successful absent preference resolves to Compact without a write. Loading, unavailable, invalid and unsupported-version preference states remain explicit. Keep authorized conversation reading available with a clearly temporary mode when preference resolution fails; do not write that fallback or label it saved. Passive hydration, reconnect or another device's update must not collapse an active reader, move focus or replace a deliberate local disclosure. Apply the confirmed default to a new untouched reader entry, or through an explicit local action.”

**Proof:** offline/unavailable read with existing Full never persists Compact; a delayed preference read cannot collapse an already expanded region; loading/error is not a false successful preference save; failure of content authorization still blocks content rather than using the presentation fallback to bypass it.

### DC04 — Saved default and local reading effects must remain separate

**Concern: material; severity Medium; likelihood likely with ordinary controls.** Expanding a search match or selecting Full for one exchange could unintentionally change all future reading. A failed save could also rewind a useful temporary view. Current S08 rollback is not a suitable complete UI contract.

**Exact clause:** “Per-region expansion, search-target reveal and temporary conversation mode never save the personal default. A deliberate default change may apply locally immediately, but persistence is separately Saving, Saved, Not saved or Needs confirmation. On failure retain the user's allowed local mode for this visit, explain that future defaults were not confirmed, and offer a scoped retry. Reset affects this one setting only and means an explicit Compact value, not clearing unrelated preferences.”

**Proof:** many disclosure/Find/file-preview actions cause zero preference writes; failed save preserves current reading/focus while another device continues using the last saved default; only explicit Save changes persistence.

### DC05 — Conditional desired-state saves prevent stale overwrites

**Concern: material; severity Medium; likelihood plausible with multiple tabs/devices or retries.** An old delayed Full save can overwrite a newer Compact choice, and deleting the row for Reset can make an old absent-row request valid again. Current S05/S06 contain no expected preference revision; `schema_version` is not such a revision.

**Exact clause:** “The preference command accepts the desired mode and expected monotonic revision for this exact key. Derive identity/time server-side and compare/update atomically. A new explicit save with the matching revision advances the revision, including explicit Compact from an absent default; do not delete/reset the revision fence. A stale request must not overwrite a newer different value. If its desired value is already current, return that confirmed current value/revision without another write, labelled as current state rather than a historical command receipt; otherwise return a conflict with current state. A new deliberate reapply uses the current revision.”

**Proof:** concurrent first saves have one admitted successor; lost response/retry does not repeatedly advance the row; Full→Compact followed by old Full retry conflicts; Compact-from-absence prevents delayed absent-generation Full from overwriting it; unrelated source work is never part of this transaction.

**Proportionate implementation:** this is a small atomic desired-state command, not a business workflow/outbox or permanent receipt journal. Serialize/sequence local saves; use an opaque safely serialized revision rather than client wall-clock ordering. Distinguish “already current” from proof that the exact earlier request committed.

### DC06 — Cache keys and mutations require tenant/principal partitioning

**Concern: material; severity High for attached reader state, Medium for the mode alone; likelihood plausible with retained clients.** Current S08 keys omit tenant/profile, and whole-response rollback can restore older data over a newer optimistic change. It is not enough to assume the query client always remounts on an account change.

**Exact clause:** “Key all preference requests/cache entries by current tenant, real profile/principal and closed preference key/schema. Tie responses and optimistic state to the originating session/context and local mutation sequence. Cancel/invalidate and clear inappropriate preference/reader state on logout, account or tenant change. Ignore late old-context responses and older save rollbacks; a new person's cache cannot be populated from the previous person's response. Content caches additionally retain source and permission/restriction scope.”

**Proof:** tenant/account switch during read and save; reverse-order success/error responses; newer optimistic intent survives older rollback; current source removal plus delayed body/projection response does not repopulate restricted text. Inspect the actual app query-provider lifecycle rather than assuming it.

### DC07 — Database constraints and grants must enforce the same scope

**Concern: material; severity High; likelihood possible through privileged or direct paths.** Separate tenant/profile FKs and application checks alone do not make a valid same-tenant custodian relationship. A service-role call can bypass RLS, and unguarded direct updates can change owner/key/revision. S02/S06 acknowledge existing RLS and revoked client grants rather than alleging their absence.

**Exact clause:** “Enforce non-null tenant/custodian/key identity, one row per exact preference key, allowed mode, valid schema and monotonic revision, and the current qualified tenant-membership relationship. Identity and revision fields are not caller-editable. Use composite same-tenant references where the actual owner model permits, plus the single authenticated command's current membership check. Audit actual grants, effective SELECT/USING/WITH CHECK, permissive policies, function execution/search path, invoker/definer paths and service-role validation. Keep client DML revoked unless a fully equivalent RLS-safe collection mutation is explicitly qualified.”

**Proof:** actual authenticated/anonymous/service tests cover read/create/update/reset and forged owner/tenant/key/revision; allowed updates cannot transform the row into another user's row; direct RPC callers cannot manufacture a trusted profile or capability. Revoke default PUBLIC execute where required. No new financial precision or conversation FK is needed for this value.

### DC08 — Folding cannot become source mutation or access authority

**Concern: material; severity High; likelihood plausible with parser-derived caches.** Writing a stripped body, restoring raw HTML to reveal “Full,” or using an older projection can lose inline answers or expose restricted content. S13 and D22/D23/D32 require a stricter permanent path than current body selection/catch-null behavior.

**Exact clause:** “Compact and Full consume the same currently authorized safe source representation. A fold map identifies original-source/revision-bounded regions and remains derived and dispensable. It never rewrites retained body bytes, joins sources into a new message, changes custody, authorizes hidden spans or substitutes raw transport HTML. Source restriction/expiry and relevant renderer/source changes invalidate stale projections; unsupported render/segmentation keeps qualified content visible or shows truthful unavailability, never a successful empty message.”

**Proof:** exact original body/digest unchanged by mode/save; unique inline/forwarded context remains visible; source revision and redaction invalidate spans; a Full preference cannot bypass content eligibility; no raw source/public storage URL is introduced.

### DC09 — Do not build a cross-source disclosure graph for a cosmetic mode

**Concern: material; severity High for disclosure, Medium for complexity; likelihood possible.** Comparing against inaccessible messages to decide “duplicate” can leak their existence or conceal the only visible copy. Broad reuse across conversations/tenants creates hidden dependencies and retention copies.

**Exact clause:** “Recognizing a repeated region cannot consult or reveal an unauthorized source or require a cross-tenant/cross-conversation corpus. Any contributing comparison source must be currently eligible, and the derived result must remain bound to its actual source/revision and restriction inputs. Prefer a bounded per-message presentation qualification; a quote marker or signature-shaped suffix alone does not prove that content is disposable repetition. Uncertain or meaningful changed content stays visible.”

**Proof:** inaccessible predecessor, merged originals with different source bases, forwarded-only history, changed contact details and mixed inline responses cannot become a hidden first/only answer. No new searchable shadow transcript or retained comparison corpus is created.

### DC10 — Search and attachment actions remain independent

**Concern: material; severity High; likelihood common if DOM visibility drives search.** A Compact default can accidentally remove hits, make Find stop at mounted messages or hide the only attachment entry. S14 governs both pathways already.

**Exact clause:** “Reading-folded text remains in D22's exact eligible source population; authorization-hidden spans remain excluded. Search/Find navigation reveals the exact current matching region without changing the saved default, joins no phrase across a forbidden gap and preserves original-source identity. D32 attachment metadata and independently authorized Preview/Download actions remain discoverable and deliberate; no automatic byte fetch follows from Compact/Full.”

**Proof:** hit inside a folded/unmounted quote; expired hit; malformed body; empty Find; duplicate roots; identical filenames; no preference write, attachment fetch or other source disclosure merely from revealing a text match.

### DC11 — Configuration lifecycle must not revive identity or source content

**Concern: material; severity Medium; likelihood plausible at offboarding/restore.** Copying preference state to a same-email replacement, restoring stale revision zero or retaining projected bodies with a harmless preference would create incorrect continuity. D20 already owns finite configuration lifecycle.

**Exact clause:** “A mode preference contains no message text, filenames, recipient lists, search terms, source-derived region bodies or CRM snapshots. Access ends with the relevant membership; no automatic transfer to a replacement account or global-user alias. Keep its lifecycle, deletion, backup and restore within the shared configuration/identity owner, without a new conversation retention clock or per-preference retention setting. Source restrictions apply independently to every reader/projection after restore. Removing a profile/tenant may retire its personal preference but cannot delete Support messages or shared definitions.”

**Proof:** offboard/reinvite with changed stable identity; source redaction then backup restore; preference deletion with continuing source work; mode configuration cannot recover purged text. Any restored revision/custodian state is requalified before writes/read reuse.

### DC12 — Rollout and evidence must stay narrow and truthful

**Concern: material; severity Medium; likelihood high if new UI arrives before the owner path.** Old code can ignore a new setting, falsely report saved success or silently clear it in a whole-JSON write. A weak fold detector could then be mistaken for the user's Compact preference failing. S03/S07/S08 show real mixed-version risks.

**Exact clause:** “Deploy the typed preference read/write contract and same-context cache guards before advertising a persistent choice. Old readers may ignore the new presentation key but must preserve it in unrelated writes; unsupported schema cannot be silently coerced or overwritten. Do not infer user defaults from old local UI flags or global storage. Compact starts for confirmed missing preferences; preserve existing explicit values on migration. A detector kill switch may fall back to qualified full presentation while retaining the saved Compact preference and explaining temporary unavailability; it never bypasses safe rendering or source authorization.”

**Proof:** old-code/new-schema and new-code/old-schema cases, dropped responses, unknown enum/version, restore/reset races, no mass write-on-read backfill, actual browser/AT/source tests. Document which gates were really executed. No new per-save notification, P6 interaction, metric of staff diligence or CRM business audit is created.

## Exact command/read outline

1. Resolve current authenticated tenant/profile/member and the narrow personal-reader capability. Read only the closed preference key through the shared owner.
2. Return known stored mode/revision, or successful absence with virtual initial Compact/revision zero. Keep unavailable/forbidden/invalid distinct. A preference error can use temporary presentation only after independent source authorization succeeds.
3. For an explicit save, validate exactly the mode and expected revision; neither user nor tenant/owner attribution comes from the body. In one atomic boundary, compare current revision and create/update just this key. A first explicit Compact save also establishes a revision fence; read-only absence does not.
4. Matching expected revision applies desired mode and advances revision. A stale retry with the same currently stored value returns current state without a new write; a stale request with different desired value returns conflict. Do not turn current-state convergence into a fabricated original operation receipt.
5. UI separates local mode from durable state, orders its own intents and suppresses old-context responses. A conflict/failure keeps the allowed local choice temporary until deliberately reconciled. Passive cross-device/hydration updates do not move an active reader.
6. Derive/render/fold only current eligible safe source content; disclosures, Full view, Find and attachment navigation continue to use source-owner checks. Preference load/save creates no conversation, CRM, template, transport or document effect.

This outline is intentionally smaller than a workflow: no provider/outbox, general rules engine, approval, tenant default, audit snapshot stream or per-region persistence is needed. Real source safety is still mandatory and cannot be reduced to this harmless enum's authorization.

## Current primary documentation and instruction reconciliation

The current [Supabase RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security), also retrieved through Supabase `search_docs`, distinguishes grants from row policies, warns that service roles can bypass RLS, and explicitly states that an omitted WITH CHECK reuses USING when applicable. [PostgreSQL17 CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html) is the primary authority for that fallback. The skill's blanket statement that missing explicit WITH CHECK necessarily permits ownership reassignment is too broad; this review evaluates effective old/new-row checks and actual grants rather than making that incorrect claim.

Supabase also warns that user-editable metadata is not authorization authority and JWT authorization data can be stale. A harmless display preference is not itself a permission grant; that fact must never let its Compact/Full value, copied agent metadata or cached JWT determine who may read a source or modify another person's setting. Current identity/member qualification remains independent. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Final synthesis

**C is sound with the twelve amendments above.** First qualify the one typed shared personal setting and trusted tenant/profile scope. Then implement the small conditional save/cache contract and complete local-versus-saved UX. Separately qualify conservative folding over the existing safe source renderer, preserving D22 search and D32 file/CRM continuity. Finally prove actual SQL/grants/negative authorization, overlapping requests/session switches, preserved original bytes and complete accessible reading journeys.

The decision does not require a new generic preferences system, another CRM field or a durable workflow for each setting change. It does require current-source safety, explicit state and truthful persistence. Current source checks and two pure-helper observations are completed; all proposed D33 database/API/browser/AT/concurrency/migration/fold-fidelity outcomes remain unexecuted implementation proof.

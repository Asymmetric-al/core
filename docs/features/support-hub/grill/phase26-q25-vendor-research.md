## The actual remaining decision

**When a tenant sets up a Support inbox, which email-address path should Asym lead with?**

The [independent gap review](phase26-q25-gap-review.md) checked current source and accepted decisions before selecting this question. Generic inbox movement would repeat substantial D6/D8/D10/D23 decisions: current work and original source lineage survive qualified movement, eligible assignees are retained, private drafts and restricted sources remain protected, and actual sending context is distinct from team assignment. Destination authorization still needs release proof, but discoverable implementation proof is not a new founder preference.

The [Phase 26 roadmap at the current source baseline](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L2937) already includes forwarding and BYO-domain/MX receiving, with Resend qualified first. [D1-R2](phase26-d1-adversarial-review.md) already requires ordinary Reply and new mail to the visible Support address to reach recoverable intake, and separates website domain, sending authentication, receiving routing and monitoring. It prohibits replacing existing root MX as a setup shortcut. Those rules govern every option.

The current UI points a missing-inbox user toward integration settings, while route repair exposes lower-level recipient/alias/domain controls; neither establishes a finished first-inbox journey. That source finding makes the front-door default a genuine remaining product choice. It does not establish a measured usability failure or authorize replacing integration ownership.

## Three credible options

Illustrative example only: a tenant has published `donorcare@example.org`, currently handled in its ordinary email service, and wants authorized staff to handle that work in Support Hub. Another tenant is starting a new Support inbox and has no suitable published address. Neither example asserts a common frequency or a private ministry workflow.

| Option                                           | What the administrator sees first                                                                                                                                           | Best reason to choose it                                                                                                                                      | Main cost                                                                                                                                                                                    |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Keep an existing Support address first**   | Enter the public address the team already uses, then follow the qualified forwarding setup. A clear “Use a new support address instead” path remains immediately available. | Preserves requester familiarity and minimizes address migration when an appropriate address exists. It starts with the outcome people recognize.              | Existing provider routing and forwarding policy remain dependencies. Teams need a deliberate transition to answering Support work in Asym.                                                   |
| **B — Create a dedicated Support address first** | Start with a new purpose-specific address on a qualified receiving domain/subdomain; the existing-address path remains available.                                           | Clean separation for a new team or an address that should not continue to mix Support with unrelated work. Direct receiving removes the extra forwarding hop. | Requires qualified domain setup and adoption of a new public address. An established address may still need forwarding for continuity. Fewer hops does not itself prove greater reliability. |
| **C — Present both paths equally**               | Two equally prominent plain-language choices: “Use existing address” and “Create dedicated address,” with one sentence explaining each.                                     | Avoids presuming the tenant's starting point while keeping both choices clear.                                                                                | Adds an upfront decision for someone who could have followed a contextual default. It does not reduce either path's proof or maintenance needs.                                              |

**Single recommendation: A — Keep an existing Support address first, with an obvious dedicated-address path.** The strength is continuity where it helps, not a mandate to forward all mail. Do not funnel a tenant without a suitable address through invented placeholder data or a failed connection before exposing B. C is a defensible neutral choice; A earns the recommendation because it gives a concrete normal path while leaving the alternative easy to find.

## Recommended shape of the journey, subject to the Q25 answer and review

These are proposed UX consequences to evaluate after the founder chooses. They do not silently ratify new limits, routes, schema or activation rules.

1. **Start in Support's inbox setup with recognizable language.** Show the tenant and inbox context and ask for the address people should use. Keep the public address distinct from the inbox's internal name and any internal forwarding target. Explain the selected path in one sentence before provider instructions.
2. **Guide the authorized administrator to the owner settings.** Reuse the tenant's integration and domain readiness rather than creating a second Resend credential store. Show the specific route and copyable instructions, preserve progress when the administrator leaves to use provider settings, and provide a contextual return path. A copy/share-instructions action must not expose credentials or imply that Asym changed the provider.
3. **Show separate, truthful checks.** Receiving, sending and the ordinary reply journey are different. A green sender-authentication result is not evidence that inbound messages reach the right tenant/inbox, or that someone owns recoverable held intake. Show the failing check, the next action and a recheck path without erasing completed work. Do not claim that a test proves future uninterrupted delivery.
4. **Finish in the existing Support operating model.** Present the already-owned coverage/reviewer setup, public sender/signature preview and acknowledgment setting in context. Use the D6/D13/D19/D23 mechanisms, not a new permission or workflow engine. Do not silently enable receiving, acknowledgments or dispatch merely because a DNS or provider check passed.
5. **Make the transition clear.** Staff should know when to begin handling the newly connected Support work in Asym and which old mailbox remains an upstream copy. Forwarding is not historical import, two-way sync or a record of replies staff send elsewhere. New setup must not erase a working route merely to test its replacement.
6. **Keep repair close to the inbox.** A later broken connection should point authorized staff to the existing owner settings and retain truthful incomplete/unknown status. Unrelated conversation reading or permitted draft work must not be represented as provider failure. Preserve the established D1/P6 failure and recovery distinctions rather than inventing a single “Connected” flag that overclaims readiness.

The polished interface should use Asym's existing shared controls and responsive layout: clear labels, copy feedback, readable status text, keyboard access, preserved focus and resumable steps. It needs neither an architectural diagram in the normal user flow nor a large checklist of unrelated inbox features. Settings requiring another owner's authority should preserve context while opening that owner's surface; they must not grant that authority through setup.

## Material upstream limits that affect every option

**Forwarding must be qualified for the tenant's actual mail service.** Microsoft's current documentation says its default Automatic forwarding behavior differs by organization; some existing organizations retain enabled behavior while new or previously inactive organizations use disabled behavior. Other blocking controls typically override an allow. The documentation applies to all cloud mailboxes' built-in security and Defender for Office 365 Plan 1/2. Asym should explain the specific failed route and direct the authorized mail administrator to a scoped repair, not instruct all tenants to weaken organization-wide safeguards. [Microsoft, updated 18 August 2026](https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding).

**Upstream filtering is not uniform.** Google's user-configured Gmail forwarding excludes spam, while Microsoft's administrator-forwarding documentation says spam/phishing can still be forwarded. The precise routing method matters. A message blocked or retained upstream is not already in Asym's custody, and the product must not claim it can recover such mail through Support's held-intake queue. Do not disable spam defenses to manufacture completeness. [Google Workspace user forwarding, updated 10 September 2026](https://knowledge.workspace.google.com/admin/gmail/let-users-automatically-forward-their-own-gmail-emails), [Microsoft forwarding, updated 3 February 2026](https://learn.microsoft.com/en-us/microsoft-365/admin/email/configure-email-forwarding?view=o365-worldwide).

**Forwarding and direct receiving preserve the same domain boundaries.** No route may automatically establish requester identity, create CRM contacts, grant restricted CRM/care access or convert an unrelated employee mailbox into shared Support intake. Website DNS, outbound sender authentication, SMTP return path, public Support address, receiving domain and internal destination are separate concepts. This is existing D1/P6/P17/CRM discipline, not an argument for adding another setup product.

**Email Studio remains the content owner.** P17 owns governed wording, exact published revisions, typed variables/assets and preparation. Support owns its qualified inbox bindings and human workflow; P6 owns tenant Resend dispatch and delivery/recovery evidence. Setup can select or preview the existing D13 acknowledgment and D23 signature through those seams, but cannot create an alternative editor, template runtime, credential owner or sender. Tiptap remains the selected rich-text authoring technology at the existing suitable surfaces; a DNS/address form is not a rich-text editor.

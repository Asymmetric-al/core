# D27-C — Guidance experience for readers and maintainers

**Fully founder-ratified, 13 September 2026. D27-C is the current Guidance decision; D1–D27 and all adopted amendments are accepted.** The substantive answer below is preserved; its earlier pending/paused statements describe the answer stage. The full ratification appended below governs current status. Q28 requester-feedback resumes unanswered. This remains exploratory grooming, not formal specification, implementation or release proof.

The product has **one Guidance surface**. Two plain tabs, **Public** and **Internal**, answer the most important question before staff select anything: is this material intended for recipients, or is it an instruction for staff? They have equal visual weight; their actions deliberately differ. There is no mixed All list, another main workspace, nested knowledge tree or personal wiki.

## Layout and access

Use the existing Support auxiliary context area. Opening Guidance replaces the contents of that recoverable area rather than adding a fourth permanent pane. A narrow screen uses a single sheet/full-page stack. The same surface opens from the canonical Support detail in CRM. A Guidance entry in the Support surface also allows consultation without a conversation; no request is created just to read instructions.

The compact hierarchy is:

1. Guidance title, Close/Back and permission-appropriate Manage guidance action.
2. Public / Internal tabs with normal keyboard focus and selected-state semantics.
3. Search guidance; relevant visible filters on one compact row.
4. A readable result list: title, concise summary, useful language/source metadata.
5. Selected source reader with a clear purpose label and source-appropriate actions.

Avoid decorative article cards/hero images, new dashboard metrics, popularity rankings and icon-only audience badges. Let titles wrap, keep body text readable and preserve Core's shared base-maia/Base UI tokens, spacing, type scale and focus behavior. A known source restriction uses plain text and an appropriate icon, not a red warning on every ordinary staff instruction.

## Public journey

1. Staff read the request and keep the actual reply or internal-note draft in place. Open Guidance manually; no private message is mined into a search query. Public is the first-use tab for a fresh conversation. An explicit tab choice may persist within that conversation's current session; a note/reply purpose change does not silently select a tab.
2. Search the tenant's deliberately selected public sources. Title, summary and eligible body text are covered, including selected Shared-by-link Pages. Site/language filters are shown only where useful. A blank query provides a predictable paginated list; partial indexing is disclosed instead of false No matches.
3. Preview the current owner-qualified public Page. Show title, Site/public destination, language and any meaningful Shared-by-link indication. The public projection is passive: no forms, donation widgets, scripts or embeds execute in the staff session. Consequential interactive sections are labelled with Open public page rather than silently omitted.
4. Choose **Insert link** at a valid caret or **Link selected text** to preserve ordinary selected wording. If the source/selection/draft is stale or the selection is protected, preserve the draft and request a valid source/position. Opening or previewing never inserts.
5. Return to the linked text in the same draft. Recipients, Reply/Internal note, signature and work status stay unchanged. Review/send normally under P17/Support/P6; Internal note never becomes email. Public link edits, withdrawal, same-source continuity and retention retain all D27 safeguards.

Illustration only: staff can share the tenant's published “Find your receipt” instructions when such a Page exists. That link does not generate a receipt, verify the requester or prove that a giving action completed.

## Internal journey

1. Choose **Internal**. Preserve the query and independently run the private Staff guide search. The public Site filter no longer applies; its previous value is restored when returning to Public. Show a language filter only where it is useful, without implicit translation or fallback. Do not auto-switch the composer to Internal note.
2. Results include only current published guides available to this actor through the tenant's Support-read capability. The guide's title/summary/body are private. Drafts, history, archived guides and hidden-match counts do not appear. No results means no matches in a complete qualified query; permission or service problems have distinct safe states.
3. Open the guide in the same reader. Keep **Internal — for Support staff** visible. Show its actual publication date, language and maintainer context. Use meaningful headings and ordered steps; a derived in-page table of contents may appear when a guide has enough headings to need it, without a maintained taxonomy.
4. Read the instruction and use normal authorized product navigation if needed. For example, a general guide might explain where staff find the existing receipt workflow. The destination checks the staff member's current giving/CRM permissions and owns every action. The guide cannot grant approval, preselect a donor, auto-run a task or mark a procedure complete.
5. Close or return to the original conversation with its query, scroll, draft and context intact. The internal reader offers **Open guide** for a full-page authenticated view when a longer guide is easier to read that way. It offers no Insert into reply/note, Copy article, Quote section or automatic citation.

Internal consultation-only is intentional. D18 Saved notes already supplies reusable note wording; a Staff guide supplies maintained instructions. Adding typed internal references to messages would require additional audience, disclosure, retention and serialization work not needed to read and act on guidance. Normal text selection, operating-system copying and retyping are not claimed to be impossible. Known internal-purpose structured content must still fail an unauthorized import/publication path.

## CRM and independent consultation

From a CRM record, the existing permitted Support overview/Communications list opens the same canonical conversation detail. Guidance inside it has the same current permissions and state as in Support. A CRM-only reader does not gain internal-guide access; a Support reader does not gain restricted CRM data. Returning preserves the existing context. Lookup does not create a relationship, Activity, last-contact event, rating, note or financial effect.

Opening Guidance without a conversation shows the same read-only Public/Internal sources and appropriate management actions. Public link insertion is absent because there is no current editable conversation. Reading an internal instruction is not a reason to invent a ticket. This keeps Support a coherent feature within Asym rather than an organizing model for every staff action.

Shared addresses, unknown requesters, cases made for someone else, CRM merges, changed contact details and moved/reopened requests do not change guide access or grant authority. Guide maintainership is also distinct from conversation handling and CRM record ownership.

## Maintainer journey: create and publish an internal guide

1. Open **Manage guidance → Internal**. Readers without authoring/publication authority can still consult published guides but do not receive broken editing controls. Management is a list of source records, not a second inbox: Draft, Published, Unpublished changes, Archived, and deletion progress where applicable. Search and simple state filtering are sufficient.
2. Choose **New staff guide**. Enter a clear title, short purpose summary, fixed content language and a current eligible maintainer. The audience is stated as **Support staff in this tenant** and is not an editable per-inbox or public/private toggle. A language change after source creation uses a separate deliberately authored guide; no automatic translation/synchronization is implied.
3. Author with the shared Tiptap Staff guide profile. Provide readable headings, paragraphs, emphasis, bullet/numbered lists and descriptive links. Do not show upload, embed, live recipient/CRM variable, executable checklist or AI controls. A short scope note explains that guides contain reusable instructions, not case data or secrets. It is not a guarantee of automated sensitive-data detection.
4. **Save draft** records only the candidate. Draft-only autosave can reduce loss if it reports Saving/Saved/Unsaved/conflict accurately; it never publishes. A second editor or stale autosave produces a recoverable conflict rather than last-write-wins. The candidate is available only to currently authorized tenant guide authors/publishers, not ordinary readers.
5. Preview the candidate as a staff reader and inspect the changed text against the current published version, if any. Show the real language and common audience. **Publish to staff** is a separate deliberate action that requires current tenant-scope publication authority. An authorized maintainer may both write and publish; there is no invented two-person floor or inherited D19 inbox-review permission.
6. The exact reviewed revision becomes current. Publication makes it available in Internal; no second Add-to-guidance step. If the search projection is catching up, management and affected searches show truthful updating/partial states. Failure after an ambiguous response checks the receipt rather than creating another publication.

Authors may read/edit the common tenant guide candidates through explicit authoring capability; readers see only published content. A tenant-wide publisher cannot be inferred from an inbox-specific saved-reply curator. The feature uses current P12 actions, not a new role enum or guide ACL editor.

Public management remains different: **Add/Remove from guidance** changes the curated public selection; **Edit in Web Studio** changes source content under CMS authority. Removing a public selection does not unpublish its source. There is no Convert to Public action on an internal guide. If staff genuinely need new public wording, the CMS source must be independently authored/reviewed/published for that audience; no internal guide body is automatically transferred.

## Honest states, privacy and accessibility

“No published staff guides yet,” “No guides match these filters,” “Results are still updating,” “Internal guidance is temporarily unavailable,” “Your access changed,” and “Your changes were not saved” describe different facts. Do not expose an inaccessible title/count in an error. Do not say an email was not sent merely because a Guidance action failed; another action/tab may have submitted it. A guide read has no authority over P6 send state.

Tab/search/preview navigation must be keyboard and screen-reader usable, with visible focus, named actions and restrained result announcements. Escape closes only the current layer; Back restores query and scroll; closing returns to the trigger or insertion point. Search typing/IME does not trigger navigation. Slow previous responses cannot replace newer results. Public/internal purpose is visible text, never a color or tooltip alone.

On mobile, one stack serves list → reader → return. Controls remain reachable under zoom/reflow; long titles and RTL text wrap normally. Use existing reduced-motion and focus conventions, no hover/drag-only actions. Text-first guides avoid large downloads; there is no private offline library or new local-storage body persistence. External links do not receive the private guide/conversation URL as referrer and do not trigger automatic server fetches.

The [40 proof groups](phase26-d27c-adversarial-review.md#required-proof-matrix) include representative staff/CRM/authoring/maintenance, keyboard/AT/mobile and failure journeys. None has been run against a new feature. This blueprint establishes what must work; it does not certify visual polish or user satisfaction before implementation and observation.

Public retains owner-qualified selected CMS Pages, exact Site/locale/public-generation/destination, complete title/summary/body search including selected Shared-by-link Pages without public-discovery widening, safe passive preview and deliberate Insert link/Link selected text. ### Accepted authoring, maintenance and safeguards

Each guide has a fixed authored language, clear title/summary, accountable maintainer, one current candidate and one published head. Translations are separate deliberate guides, not synchronized locale families. The narrow shared Tiptap profile covers structured instructional text and descriptive links, without a new media/upload service, embeds, live CRM/recipient values or script. Validate complete original canonical JSON and trusted source/command purpose before generic parser normalization; unknown protected data must not be silently stripped and accepted.

Save draft/autosave changes only the candidate. Publish to staff admits the exact reviewed revision/head/audit/receipt and required continuation, and makes it available in Internal without a second selection switch. Current readers retain the prior publication while unpublished changes are edited. Restore creates a candidate and does not silently replace saved/unsaved work. Archive/delete during editing makes save/discard and actual effects explicit. Maintainer departure does not cascade-delete tenant-owned content/history.

Ordinary Archive and source safety restriction remain independent: a restriction persists across candidates, revisions, Restore and Publish until the actual authorized protection owner admits a current reviewed release. A new revision or ordinary publication capability cannot clear it. Delete archived content re-proves current generation, authority and applicable records retention/hold, can stop serving while required content remains restricted, and reports actual allowed disposal. Required purge/restore/tombstone behavior cannot silently resurrect content. Each source/candidate/revision/derived/evidence class has a declared custody and final-disposition rule before activation.

Current capability checks plus effective grants/RLS/column/view/RPC/service controls enforce non-null tenant/source/purpose, tenant-qualified relationships, valid language/head/state, protected actor/approval/time and one expected-generation/idempotent command boundary. Search authorization/current heads precede snippets/counts/paging; Internal never joins public search/API/sitemap/AI. No first-page-cap filtering, N+1 shortcut, private query egress or raw-body diagnostics is accepted. Failed/partial source results, save conflicts and purge progress remain truthful and isolated from unrelated work.

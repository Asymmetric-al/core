# Inbox-managed signatures and governed Tiptap authoring

**D23 and every adopted amendment are fully founder-ratified, 12 September 2026. Historical disposition: Accept with required amendments.** A and the explicit Tiptap direction, the complete review/UX/data/identity/Email Studio/Resend contract and required proof are accepted. D1–D22 remain fully ratified. This is grooming authority, not an implemented feature or formal specification.

The strongest path is a managed signature that staff see before sending, backed by Email Studio's existing structured authoring and preparation. Tiptap supplies editing; it does not supply identity authority, safe email delivery or a canonical validation policy by itself. Keep the interaction small while making source ownership, privacy and lifecycle exact.

The [UX journey](phase26-d23-signature-ux.md), [data/Email Studio contract](phase26-d23-data-contract.md), [evidence register](phase26-d23-evidence.md), three independent reviews, [limited installed-source experiment](phase26-d23-source-experiments.json) and [validation](phase26-d23-validation.json) form the complete record. S/T/X references below resolve in the evidence register. Likelihood is qualitative reasoning about exposed conditions, not measured incident prevalence.

## Corrected decision clauses

### D23-R01 — One managed model for all legitimate Support inboxes

Adopt inbox-managed signatures with responder personalization as the ordinary human-email reply model. B, universal team-only signatures, is the strongest simpler alternative: less identity disclosure and configuration, less personal continuity. C, personal signature libraries, offers individual variants but adds stewardship and inconsistent details without a demonstrated Asym requirement. A permits a deliberately configured team-only signature within the same managed model; it does not implement all three alternatives.

Use the same capability for Donor Care and any other authorized Support inbox. Inbox wording and approved public responder details express the actual team; do not create departments, staff roles, ministry workflows or donor-specific template variants merely as examples. This signature has no business-action, permission or identity-verification authority.

### D23-R02 — Email Studio owns the reusable source; copy it into the draft

Qualify a narrow **Reply signature** purpose in Phase17's existing tenant-owned structured Saved Section authoring/publication capability. It is distinct from D18's Reply/Internal note saved wording; it is not a third mode in that picker. Support owns a compatible same-tenant inbox-consumer binding. There is no Support-owned raw-HTML signature store, personal signature library, new email Layout Role or system-message catalog key.

When a new external reply draft first needs its signature, resolve one eligible complete published signature variant and copy that exact structured revision into a managed draft slot, with source/revision/copy provenance. Do not store a runtime nested Saved Section expression or re-expand mutable source on Send. Ordinary signature edits never fan out into existing draft copies or history. P17 prepares the complete approved body using the existing compatible Service message Role Layout and Brand Kit; no per-inbox Role Layout is introduced. Reuse is one owner and copy semantics, not synchronization between two libraries. This explicitly qualifies the previously open D4/D18 signature seam while preserving ADR0030.

### D23-R03 — Public responder identity has its own qualified meaning

Resolve personalization from the actual authenticated human admitting the reply and that person's current tenant membership, through the existing identity/profile owner's authorized public-presentation projection. Never use conversation assignee, template author, CRM record owner, supplied agent ID, email match or a user-editable claim as authority. Public responder name is an explicitly suitable display value; do not split first/last names, derive it from a login address, disclose legal name by default or infer a title from IAM privileges.

If the existing owner lacks a suitable public-name field/command, qualify that minimal tenant-membership presentation extension in the identity owner. Do not create a second staff directory or repurpose the current displayName endpoint that also changes full_name. Own-public-name edits require current identity-owner permission, clear external-use explanation, trusted attribution and a new revision; changing them does not change legal/auth/CRM identity. Optional public title is available only from an equally qualified owner field; inbox/team wording is sufficient otherwise. Private email, phone, photo, location and care/missionary records are not fallback inputs.

### D23-R04 — Separate authoring, publication, inbox configuration and sending

Use existing Core capability and scope conventions for signature-source read/use, source author/edit, publish/review, inbox binding management and actual Support reply. A delegated inbox manager can select an eligible published source within their scope without becoming its publisher; a Studio publisher gains no inbox administration, conversation or CRM access merely by publishing. General reusable metadata and source previews obey their authorized audience; impact counts and linked inbox names reveal only permitted configuration context.

Keep ordinary qualified self-publication under P17 simple. Its existing protected-publication and tenant-stricter independent-review rules remain effective when actually applicable, including shared Brand Kit/layout changes used by protected messages. Do not invent an always-two-person signature review rule or bypass a protected floor by naming content a signature. Human reply composition is not a new publication event.

### D23-R05 — Add, find and edit through one coherent management journey

Provide Support settings → Inboxes → the selected inbox → **Reply signature**, showing effective source, language, current published revision, a compact preview and clear **Change signature** and authorized **Edit in Email Studio** actions. New signature and Customize open the same focused P17 authoring capability with a preserved return destination; no disconnected second editor or copy/paste transfer. Email Studio exposes the same assets through its Signatures-purpose view with search, Active/Archived and meaningful name/usage metadata. Contextual access shows only eligible assets.

New starts from a restrained tenant-compatible starter or a deliberate copy of an eligible source. Duplicate creates a new source identity and unpublished draft with provenance, never a live alias. Give it a clear internal name, optional description and declared language. UI labels explain internal metadata versus recipient-visible text. Unsaved work, permissions, loading, no signatures, no matches, validation failure, save uncertainty and unavailable assets have distinct repairable states. No setup wizard or personal-signature onboarding is required for every responder.

### D23-R06 — Saving a draft does not publish or apply it

P17 draft autosave uses optimistic concurrency and explicit Saving/Saved/Not saved/Conflict feedback. A save checkpoint, preview, commit, publication and inbox application are different effects with different receipts. A published source opens as a new editable candidate; its current publication stays in use until a valid new publication succeeds. Review the exact candidate, language/fields/assets, before/after and permitted consumer impact. Ordinary **Publish** or required **Submit for review** follows existing P17 rules; failure preserves the prior good publication.

An unpublished new source cannot be selected as an inbox's effective signature. A contextual **Publish and use for this inbox** convenience may sequence the existing commands, but must truthfully distinguish Published from Applied. If the second step fails, the source remains published and the prior inbox binding remains effective; reconcile the same apply intent. No cross-owner best-effort transaction may show both steps complete when only one succeeded.

### D23-R07 — Deterministic inbox defaults and safe shared updates

Each inbox resolves exactly one effective complete signature variant for a supported locale, or one explicit permitted team-only/no-optional-signature posture. The logical binding identifies an exact eligible immutable signature publication and its approved locale-resolution generation; every draft copy records the exact selected variant revision. There is no personal-first/first-row/null-owner fallback ladder, row-order default or runtime deep merge. Reusing one source across several inboxes is deliberate. Publishing a new signature revision does not advance inbox bindings automatically or require a global inbox transaction. It may remain published and unassigned.

Change binding compares its expected revision and commits the new binding/resolution evidence and history atomically. The maintainer's reviewed Use for inboxes action may apply a published revision to an explicit bounded authorized set, validating all selected consumers and expected heads before an atomic set replacement; failure changes none of that selected set. Keep source publication separate from application and show current versus available newer version. A contextual Publish and use can complete the ordinary single-inbox journey in one deliberate action with R06's truthful two-stage result. Existing draft copies remain pinned when the binding changes; an explicit refresh copies from the now-selected revision. Qualified public-name changes are resolved under current actor/public-data checks before new preparation. Actual source/privacy/retirement fences can stop unsafe use. Do not manufacture a per-inbox shared-content fork merely to store selection. Changing a shared source does not change From/Reply-To, routing, assignment or CRM ownership.

### D23-R08 — Professional visual freedom within the email presentation system

Default to clear, compact text: approved public responder name, team/organization identity and only useful approved contact information. Permit restrained emphasis, line breaks, links and an optional approved logo through the signature profile. Tenant Brand Kit supplies compatible email-safe typography, colors, spacing and contrast; app editing controls retain base-maia/Base UI and shared semantic tokens. Do not force Asym's web UI colors into tenant email branding.

Offer a clean text starter and a logo-with-text starter as authored examples within the same profile, not new Layout Roles. Essential identity stays real text. Do not include promotional banners, donation appeals, tracking pixels, animated imagery, social-icon strips, personal portraits, long disclaimers or decorative complexity by default. No mandatory role-by-inbox-by-language style matrix. Plain text must preserve useful identity and link meaning. No universal optimal pixel size, byte cap or deliverability claim is inferred from a vendor example; enforce qualified shared presentation/asset bounds and publish their concrete values before activation.

### D23-R09 — Governed logo, links and asset disclosure

The initial signature purpose permits at most one logo occurrence. Select a qualified tenant-owned immutable asset with scan/readiness, content type, dimensions, size, alternative-text purpose and publication/use scope; uploading or replacing it uses the shared asset owner and creates a new version. A draft upload is not a published or publicly retrievable file. Remove staged unused assets through the owner's cleanup path. Never fetch arbitrary pasted image URLs, store base64/blob URLs as publication authority, hotlink private case files or render an employee avatar implicitly.

The complete message must deduplicate/omit optional repeated branding through its qualified presentation contract before review, never hide required identity. Hosted/CID representation is the existing P17/P6 asset contract's decision: provider CID support alone does not qualify it for Asym. Do not introduce a second image pipeline. Images blocked, omitted or unavailable must leave the signature understandable. Informational HTTPS, mailto and tel destinations require context-specific validation and escaping; visible labels cannot conceal a changed destination. Header injection, protected-action links, message-recipient variables and arbitrary record-path tokens are forbidden here. Links disclose no private context and never change the actual Reply-To.

### D23-R10 — Language and team-only behavior are explicit

Store exact authored language variants under the same source and the existing P17 locale/fallback rules. A translation is independently authored/reviewed content with truthful freshness, not an automatic translation promise or a combinatorial signature library. Copy the variant matching the reviewed reply's resolved locale; do not infer language from a person's name or rewrite their public display name. Long, non-Latin, single-part and RTL/mixed-script names must remain intact.

An inbox may deliberately use team-only signature wording. Missing optional public-name data uses only an explicitly configured compatible team fallback, visibly reflected before approval. A missing required value blocks preparation with a targeted repair path; no fabricated sample/name/email substitution. Team-only signature means exactly that: From display, body, attachments and quoted history may still identify staff. Do not promise anonymity; any fuller privacy need must be checked through the existing complete-message and Sender/Reply Identity owners.

### D23-R11 — One visible managed block in the normal reply composer

Show the resolved managed signature inline below the editable human body before Send, with a quiet labelled **Signature** details menu. Its display is not another focusable editor instance. Normal responders do not pick from a library on each reply or directly rewrite the managed source. **Refresh signature** deliberately replaces only the managed slot against the expected draft revision, preserves body/attachments/recipients and the draft's omission choice, and returns focus predictably. Restore reveals the retained pinned copy after current eligibility checks; it does not silently fetch a newer version. If that copy cannot be used, offer explicit Refresh/repair rather than substitution. An actual sending-inbox or resolved-locale change reselects/requalifies the signature copy for that new context and shows the difference before approval, preserving the body/audience/attachments and omission choice where permitted; routing or assignee changes alone are not that trigger. Any actor/audience/public-data change invalidating reviewed preparation is shown before new approval.

Because this is an optional human closing, allow **Hide for this reply** and **Restore signature** as deliberate local draft actions where the signature purpose permits omission. They never remove required organization/legal/footer content owned by P17, change the inbox default or persist as a hidden preference for later replies. No extra confirmation modal is needed for reversible hide/restore. Exactly one managed signature slot exists per draft; D18 insertions, refresh and retries cannot duplicate it. Do not regex-delete a manually typed closing, a quoted previous signature or historic content to guess intent. Internal Notes carry internal authorship and no external signature.

### D23-R12 — One canonical document and exact preparation/delivery

P17's versioned Asym structured document with canonical Tiptap JSON is the authoritative content representation; HTML and real plain text are derived compiled artifacts. The signature copy and its origin, typed field descriptors and omission state participate in the reviewed complete draft/preparation. Signature-source authoring previews use stored synthetic fixtures. Real responder/recipient context is resolved only in the authorized live Support draft/preparation, never exported into the shared library preview.

Support owns current actual actor, visible audience, source access and atomic reply admission. P17 resolves only authorized public presentation facts and compiles the complete body with compatible immutable dependencies. Phase6 sends the sealed HTML/text/envelope through tenant-owned Resend under D4/ADR0029/0032. No mutable provider template, direct Support mailer, global fallback or rerender on retry. A routine publication/name change does not rewrite prepared or sent history; actual restrictive fences follow definitely-unsubmitted versus may-have-submitted recovery. Signature content is not delivery proof, a cryptographic signature or proof of representation.

### D23-R13 — Tiptap everywhere it serves rich authoring, with bounded profiles

Use shared Tiptap 3 editing for human email replies, internal notes, D18 personal/shared reusable wording, signature authoring and any existing Support staff-brief/long-form field whose accepted owner contract supports rich text. For fields intentionally plain, a Tiptap plain-text profile is appropriate only if it improves an existing long-form editing workflow without changing its authoritative semantics. Do not add rich data merely because the editor can.

Use purpose-specific code-owned profiles for Reply, Internal note, saved wording and Reply signature over the same canonical schema. Only authorized nodes/marks/attributes/assets/variables are enabled for that purpose in both editor and server. Signature admits paragraphs/text/hard breaks, restrained emphasis, safe links, public responder tokens and the governed optional logo; not headings, lists, tables, code, blockquotes, mentions, receipt/action nodes or arbitrary layouts. Reply/note retain their separately qualified vocabulary rather than inherit every StarterKit feature. Search, subjects, labels, names, emails, dates, filters, statuses and reason selectors stay appropriate native/shared inputs. Read-only conversation history uses the safe static renderer rather than mounting an editor for every message. Unsupported content/rendering failure is an explicit current-authority-aware unavailable/repair state, never a successful empty message; static text derivation preserves block boundaries and D22's source/redaction semantics.

### D23-R14 — Validate before parsing; never silently lose canonical meaning

Validate the complete original JSON against the versioned canonical purpose/schema, including unknown attributes, marks, node positions, allowed value types, depth/size/count budgets and protected/source metadata, before a Tiptap/ProseMirror parser can normalize it. Then perform editor-schema and server semantic/disclosure validation. Toolbar visibility is not a content or permission boundary. The installed-source experiment proves that hidden toolbar features remain schema-admissible and unknown attributes can disappear despite a strict parser option.

Handle contentError by stopping writable initialization/autosave/admission and preserving the original owner-retained bytes, with a useful read-only Needs migration or repair state. Merely enabling content checks does not authorize retrying stripped content. Known safe clipboard text/formatting conversion may normalize into the profile with a clear concise report of removed unsupported formatting; unsafe active content and external assets never execute/fetch. Unknown canonical saved structure must not be treated like harmless pasted styling. Migration is a reviewed new candidate with loss report, never silent in-place replacement.

### D23-R15 — Variables, mentions and editor actions stay inert until authorized

Use indivisible typed picker nodes rather than executable brace strings or arbitrary property paths. For signatures, allow only the current purpose's public responder and approved team/organization descriptors; forbid donor/giving/care/missionary fields, protected actions, dynamic recipient lists, arbitrary expressions, free-form CSS/HTML and user-defined nodes. Do not recursively interpret resolved text. Literal braces in correspondence are ordinary text unless they are actual typed nodes.

Shared editor reuse does not enable @mentions, broadcasts, AI rewrites, collaboration or automation in a signature. Internal-note mentions follow the existing current-user and admission checks; a saved scaffold does not notify anyone. Switching Reply/Note preserves separate drafts and provenance. Pasted hidden/internal-only data cannot become externally disclosable by changing the toolbar or stripping its origin. Signature/public-name edits never update a CRM record or complete an underlying action.

### D23-R16 — Accessible, responsive and durable authoring

Use Core's shared Base UI/maia controls, visible labels, semantic toolbar/button states, keyboard navigation, screen-reader naming, focus restoration and equivalent accessible outline/field editing of the same document. Placeholder text alone is not a label. Pasting, undo/redo, links, variables, logo selection/removal and publication have keyboard/touch paths; no hover-only repair or drag-only rearrangement. Announcements distinguish formatting toggles, save status and failures without reading every keystroke or countdown.

On mobile, the signature remains a compact inline part of the message and long-form editing uses available width. Test narrow/zoomed viewports, text expansion, RTL/IME, focus with the virtual keyboard and images blocked. Reuse D4/P17 tenant/principal-scoped draft recovery; preserve unsaved work across qualified navigation/retry, never publish or send from offline/queued editor intent automatically. Mark Not saved until server confirmation. Revoked access clears unauthorized material and stale responses cannot repopulate another tenant's editor.

### D23-R17 — Database and RLS make ownership enforceable

Asym Postgres remains authoritative through packages/api. Use tenant-aware keys/FKs for inbox, signature source/family/revision, publication, asset and membership endpoints; stable source identity is distinct from mutable name and real actor attribution. Require valid purpose/state/revision combinations and one effective binding per inbox, with exact locale resolution. No nullable owner-agent convention may toggle a shared object into personal ownership. Reject unknown ids, stale expected revisions and update-as-create behavior; do not silently upsert a lost published source.

Revoke unqualified direct table writes. Evaluate grants, RLS SELECT and effective USING/WITH CHECK for every mutation, views/security-invoker behavior, function execute grants, fixed definer search paths and service/worker checks. Omitted WITH CHECK can inherit USING in PostgreSQL; the required proof is actual old/new-row and column invariants, not syntax alone. Tenant, actual actor, authorship, publication, audit and membership facts come from trusted current server context. Updates cannot move rows across tenant/owner/source/purpose or invent publication. Narrow column mutation and owner commands enforce facts beyond row visibility. Asset/storage paths use the same source and tenant checks.

### D23-R18 — Concurrency and idempotency attach to the business effect

Autosave, create/copy, publish, inbox apply, refresh/hide, archive/restore and public-name changes each use their owning revision/command boundary. Same durable intent and identical inputs reconcile its original result; changed input conflicts; a new deliberate action has a new identity. Old replay cannot restore an earlier default or overwrite a later draft. Server responses distinguish original outcome from current state. Out-of-order autosave replies cannot mark a newer draft Saved.

Publication and its head/control evidence are atomic; inbox rebinding and its revision/history are atomic. Serialize default switch against source publication/restriction/archive and current capability generation so a retired/cross-scope source cannot win a race. A preview is not a write lock; compare current heads at commit. Durable secondary work is idempotent and source-revision-aware; logs/events carry minimal identifiers, not full draft bodies. Correct actor history records service execution separately from initiating human authority.

### D23-R19 — CRM continuity without a staff or customer shadow

Requester, message participant, authenticated responder, tenant membership, CRM Party, represented organization, coordinator and CRM owner remain distinct. Signatures personalize the responder, not the requester. Support opened from an authorized CRM context uses the same draft, signature source and sending path, preserving return context; the CRM association never expands source or signature permissions. Public-name maintenance stays in its identity owner and cannot update Party.full_name/contact values or create CRM people to satisfy a renderer.

Only normal admitted correspondence contributes to its existing permitted Support/CRM history projection. Saving, publishing, selecting, refreshing or hiding a signature is configuration/draft history, not a contact interaction or new sent message. CRM merges, contact changes or unlinking cannot reassign responder identity or rewrite old correspondence. Giving, receipts, refunds, recurring gifts and care workflows retain independent domain permissions and authoritative outcomes.

### D23-R20 — Archive, restriction, departure and retention differ

Routine archive stops new selection/copying, preserves required history and does not revoke valid draft copies/preparations. An archive of a source still effectively bound to inboxes requires explicit reviewed replacement/return to a compatible team default or permitted no-optional-signature posture for those consumers; no dangling defaults or invisible fallback. A source maintainer lacking inbox-management scope cannot silently rebind those inboxes. If all affected consumers exceed the registered atomic-operation bound, authorized managers may deliberately rebind bounded subsets while the source remains active, then atomically archive against the complete remaining set/revision; never silently truncate the affected set. A safety restriction must remain available even when ordinary replacement or compilation fails: current-use fences stop unsafe use and route repair to the right owner.

Shared source custody is tenant-owned and survives creator departure. Member removal revokes the person's current use, not shared publications or sent messages by cascade. No email-based reassignment of custody. Source revisions, public-name revisions, copied draft/prepared/admitted text, assets, audit and command receipts keep their actual finite owner purposes. D16/D17 restrictions and restore barriers govern copied content and known derivatives; no forever signature history, stale public-name exposure, leaked draft export or silent resurrection. Already sent email cannot be recalled by editing a signature.

### D23-R21 — Source-derived search and history remain truthful

D22 searches eligible admitted original message content, including whatever signature was actually admitted, under its current source/revision/retention rules. It does not search the reusable signature library, private drafts, provider Recent or today's resolved profile in place of past wording. Ordinary signature-source changes do not bump conversation activity, reply-target metrics, labels, follows or search timestamps. A template/public-name correction requiring source restriction uses the owning privacy workflow rather than silently rewriting a historical reply. Reports do not count signature insertion as a reply or support completion.

### D23-R22 — Failure recovery belongs to the failing owner

Editor load/save failures preserve authorized draft work and show local repair. Signature publication failure keeps the previous valid publication; binding failure keeps the previous binding. Missing/restricted required facts or dependencies block the affected preparation with exact safe guidance, not every unrelated inbox. A configured compatible team/no-optional-signature posture may proceed only if the complete current approved message remains allowed; no secret fallback strips unsafe content after approval.

Email Studio maintenance or signature library search is not a Resend operation. Sending failure remains D4/P6 exact-effect recovery, with prepared/may-have-submitted states and no blind rekey/resend. Technical logs contain safe identities, revisions, cause classes and timing; durable author/publisher/configuration history is distinct from source communication history and security audit. Real owner repair attention uses existing P17/P6 presentation contracts, not a new signature-email template or notification campaign.

### D23-R23 — Qualify the actual Tiptap dependency closure

Use stable Tiptap 3 as explicitly selected, through the shared UI boundary. Prefer its current composable React API where it improves shared toolbar/context composition; retain a sound useEditor wrapper when replacing it adds no benefit. Next.js editor initialization must keep immediatelyRender:false where required; mounted editor state and production server compilation remain separate.

At this evidence date the installed core/react family is 3.22.3; the lock also includes 3.23.1 Tiptap html/suggestion/superscript entries and React Email editor 1.5.3. npm reports core stable 3.31.3. These facts are not an upgrade performed or a forever version pin. Before activation, audit the exact consumer dependency closure, align the interdependent Tiptap release/peer cohort and qualify the current stable release with React Email, parser, extensions and Node runtime. No blind whole-repo upgrade, copied third-party UI kit, Radix primitive, second editor framework or mismatched duplicate editor runtime is authorized by grooming.

### D23-R24 — Browser editing does not prove email rendering

Use the P17 server compiler and approved node mappings for deterministic HTML and real plain text. Tiptap static rendering and React Email export are useful implementation capabilities, not automatic substitutes for the canonical validator or proof of email-client compatibility. Never accept caller-provided bodyHtml/bodyText as independently authoritative signature sources. Do not pass untrusted JSON directly through a renderer and rely on its unknown-node fallback.

Qualify the pinned mappings in the actual production runtime without general DOM emulation or a new markup language. Prove complete-message output, synthetic and actual authorized-context parity, no duplicate wrapper/footer, email-safe layout/read order, stable links, HTML/text equivalence, images-blocked/dark/light/high-contrast/narrow/long-name/RTL cases and representative supported mail clients. Use real test deliveries only in the later authorized test flow, through the tenant's qualified Resend path with safe synthetic fixtures and test attribution. This grooming sends none.

### D23-R25 — Bound the work and keep ordinary composition fast

Before activation, register concrete numeric document bytes, nodes/depth, field lengths, variable/link counts, logo dimensions/bytes, complete-message totals, autosave/compile/query budgets and tested concurrency in the shared purpose/asset contracts. Enforce the strictest applicable bound before expensive parsing/rendering and prove zero, exact maximum and over-limit outcomes. The one-logo signature bound is a product choice, not a vendor limit. Do not claim unlimited signatures, payloads or editor instances, nor import folklore byte/font thresholds as universal safety.

Use complete authorized queries and pagination for library/consumer management, indexed tenant/source/revision/binding lookups, scoped caches and bounded impact evaluation. Signature-source publication is independent of a global inbox graph. Selected binding sets are bounded and atomic; existing P17 Brand Kit/Role Layout shared-dependency changes still keep their governing complete-graph validation. Load editor code for editing surfaces; read-only message lists use static rendering. Isolate editor subscriptions to necessary state, preserve focus/selection, and avoid recompiling the whole message or rereading every CRM record on each keystroke.

### D23-R26 — Migrate deliberately and preserve a safe rollout path

Inventory every old signature row, bodyHtml/bodyText/agent-generated path, inbox setting, macro/import/fixture, editor profile and API writer. Do not auto-publish raw legacy HTML or silently import private staff data into a public signature. Convert eligible content into a new structured candidate with source provenance/loss report; incompatible sources stay access-controlled read-only Needs migration. Reconcile inbox defaults explicitly, including missing/departed owners and existing agent-owned selections. Preserve original history and required privacy fences, not destructive cascades.

Add owner schema/contracts before compatible readers; qualify conversion, P17 preparation and binding commands; fence old writers/direct sends; then activate per qualified scope. Stop controls can disable new signature/editor writes while preserving safe existing reads, drafts and already admitted effect reconciliation. Rollback cannot revive raw HTML authority, mixed unsupported schema, withdrawn assets or old broad policies. Restore requires current source restrictions before serving; use roll-forward when new schema/content cannot safely run on old code.

### D23-R27 — Trace every requirement to proof without overstating readiness

Maintain D23-R01–R28 → UX/data/evidence → ADR/glossary → future OpenSpec/design/tasks/tickets → implementation and release evidence. Do not create those later-stage artifacts or claim linked tickets now. P01–P44 below are required independent outcome proof, not tests mirroring the implementation. Preserve current-source experiments with exact versions and their limits; they do not prove proposed server validation, RLS, browser usability or delivery. Documentation validation checks consistency, preservation, source pins and links only.

### D23-R28 — Finish the bounded capability without importing adjacent products

No Tiptap Cloud, paid collaboration/comments/version-history service, AI generation/search/translation, CMS/editor migration outside the genuine shared seam, campaign signature system, generic workflow engine, digital-signature product or new CRM is required. Existing P17 revision/preview/publication, Core IAM/assets, shared UI and P6 delivery remain the owners. D13 automated acknowledgements retain their real Email Studio template; human signatures add no system-message catalog entry. No routine signature save/publish/apply sends mail or changes Support work. Further AI search remains the founder's separately recorded future direction.

# Q30 — The Support reporting home

**13 September 2026. D1–D29 and every adopted amendment are fully founder-ratified. Q30 is unanswered.** This is one product decision about the breadth and composition of the reporting home. It does not reopen accepted metric definitions, add implementation authority or select A automatically.

## The question

**What should Support's reporting home provide for a person overseeing the team's work?**

For example, Maya oversees donor care for a tenant supporting missionaries and mission projects. At the start of her day, she wants to find requests that need attention. At a weekly review, she wants to understand reply performance, the subjects people asked about and the feedback actually received. This is an illustrative scenario, not evidence that all ministries have a dedicated team lead or weekly review meeting.

D14 already defines live reply attention and historical reply/target reports. D21 defines label reporting with its own cohort and coverage; D28 defines optional feedback and its limits. D20 provides useful work views. The remaining choice is how these are brought together. The current code already has an Overview scaffold; its presence and current calculations do not settle the permanent design.

## Three actual options

| Option                                           | What staff get                                                                                                                                                                                                                                                                  | Strongest benefit                                                                                                                                                  | Cost and limitation                                                                                                                                                                                                                          |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — A focused Support overview (recommended)** | One curated overview with two clear areas: **Work now** and **Results for a selected period**. It summarizes selected already-qualified work/report information and links to the exact conversations or detailed report. Existing full reports and work views remain available. | A useful starting point without requiring the tenant to build a dashboard. Helps people move from a concern to the work behind it and reduces repeated navigation. | Requires a disciplined default selection, clear differences between live and historical scope, and maintained drilldowns. It will not satisfy every specialist layout preference.                                                            |
| **B — Work views and separate reports**          | Staff use the accepted work views for current handling, with a simple Reports index leading to reply/target, label and feedback reports. There is no combined overview. Existing reporting correctness and access requirements still apply.                                     | Smallest presentation and configuration burden. Strong choice for small teams that already work comfortably from their queues and need reports only occasionally.  | Leads must open several places to assemble an overall picture. Cross-report review needs more navigation, even with clear links and preserved context.                                                                                       |
| **C — A configurable Support overview**          | Start with a useful curated layout, then let qualified users choose, arrange and save views made from approved report blocks, with explicitly governed sharing where needed. Ordinary work views and detailed reports remain available.                                         | Serves tenants or roles with materially different review needs; a larger tenant can create relevant inbox-focused layouts without waiting for a product change.    | Adds layout ownership, defaults/reset, saved visibility, block/filter compatibility and maintenance. It must use or explicitly qualify shared reporting composition, not build a Support-only report engine or arbitrary formula/SQL editor. |

These are alternative product scopes, not three modes that all need to ship. C includes a useful default; it is not a blank canvas requiring every tenant to configure something. B retains every already-ratified report and mandatory correctness repair; it does not preserve the current flawed implementation or remove needed reporting. A provides a fixed useful composition, not an unchangeable product forever.

## Single best recommendation: A

A gives a tenant one dependable place to understand current Support work and recent results, with little setup. Its purpose is to make the accepted information usable together, not to add more metrics. It should feel like part of Support Hub and use Asym's shared reporting definitions. A person's ordinary conversation view remains directly accessible; an oversight page need not replace every staff member's default landing page.

The strongest case for B is infrequent reporting by a small team: queues plus occasional detailed reports may be enough. The strongest case for C is repeated demand for different approved combinations across several operational roles/inboxes. No current Asym usage study establishes that customization is necessary at launch. Vendor availability alone does not establish it either. A is the proportionate default on the evidence available; selecting C would require completing its shared-owner and maintenance contracts rather than postponing them behind a nonfunctional builder.

## A's practical journey, without prematurely freezing the design

1. **Open Overview from Support.** Use the current authorized tenant/inbox scope and a small, clear scope control. Do not open on a broad tenant aggregate the viewer cannot access.
2. **See Work now.** Current reply attention and actionable work remain all-age, with a visible As of/refresh state. Changing a historical period must not hide an old unanswered request. Current work groups can overlap; do not present them as an additive pie or a single invented score.
3. **Open the work behind a concern.** A count or action takes the user to the corresponding exact authorized list or report. Preserve scope and return location. A report cohort is not silently translated to an ordinary Created date filter.
4. **Review Results for a selected period.** Reuse the accepted reply/target, topic-label and optional feedback reports, explaining the actual cohort, time basis and sample/coverage where needed. Topic labels describe their ratified current-cohort view, not a fabricated history of labels at the time. Feedback is voluntary sampled evidence, not a score for all donors.
5. **Investigate a specific request.** Open the same canonical Support detail; CRM context and business actions still require their own current permissions. Returning preserves the report context.
6. **Understand unavailable information.** Disabled feedback, unknown timing, empty samples, incomplete data and loading/error states are distinguishable from zero or perfect performance. A chart failure must not prevent ordinary conversation work.

The final answer to Q30 will determine the complete layout, accessibility, filtering, metric selection, source/authorization, performance and maintenance requirements. The question does not prematurely choose chart counts, refresh intervals, retention windows or a dashboard schema.

## Boundaries preserved in every option

- **One set of definitions:** D14 target/duration semantics, D21 label cohorts, D28 feedback safeguards and D20 work-query meaning remain unchanged. No donor-value weighting, agent leaderboard, invented capacity score, resolution SLA or automatic AI judgment is introduced.
- **Now is not a period:** current all-age work and historical samples are visibly separate. Counts and drilldowns carry their exact source predicates; mixed units are not added or mislabeled.
- **Shared reporting ownership:** Phase 33 plans a governed metric/dimension/access layer and report composition. It is not already a shipped dashboard service. Support supplies qualified source facts and consumes shared reporting capabilities where appropriate; it cannot create a competing semantic layer, warehouse or generic BI engine. Simple source-owned reports remain useful without waiting for all future Phase 33 features.
- **Authorization before numbers:** tenant, Support/source, field/classification and relevant CRM permissions apply before aggregates, counts, labels, drilldowns, export, cache and navigation. Sharing a layout grants no underlying data access. Current denial or incomplete evidence is never displayed as zero work.
- **Email Studio seam:** viewing or configuring an overview sends nothing. It does not create a management digest, change D29 acknowledgements, D28 feedback or D14 alerts. If separately authorized later, scheduled report runs belong to Phase 33; Email Studio/P17 prepares the governed message and P6 handles delivery with recipient-specific authorization. None of that is part of A/B/C here.
- **No extra product scope:** no chat/telephony/workforce monitoring, arbitrary CRM joins, donation analysis or cross-tenant comparisons. Existing domain actions remain with their owners.

## Research behind the recommendation

[HubSpot's Summary and Analyze documentation](https://knowledge.hubspot.com/help-desk/analyze-help-desk), updated 1 December 2025 for Service Hub Professional/Enterprise with a Service seat, distinguishes a current overview with ticket drilldowns from historical analysis. [Intercom's workload guidance](https://www.intercom.com/help/en/articles/6560699-monitoring-your-team-s-workload-and-capacity) likewise distinguishes the Inbox dashboard from historical reports. Their navigation pattern is relevant; their status, staffing, SLA, AI and productivity models are not automatically Asym requirements.

## F01 — Process control acknowledgement separately from snapshot display

**Medium severity; plausible under ordinary allowed concurrency.** The runtime explicitly allows one control mutation and at most one snapshot-only read in flight, while combined control responses can carry a peer snapshot. Therefore the same response contains two independently ordered facts: acknowledgement of the serialized control and a candidate peer projection. A generic latest-request-wins gate over the whole response could discard a valid new control sequence/window merely because a later snapshot-only request started. Conversely, accepting that acknowledgement must not replace a newer displayed peer projection with its older embedded snapshot. This can cause avoidable re-registration, rejected controls, disappearing cues or stale peer presentation. It does not invalidate A or require another protocol.

**Exact correction:** “A valid acknowledgement of the current instance's serialized control SHALL be processed under the expected control sequence/generation independently of its optional peer-snapshot payload. Peer projection application uses its own request/context generation. A later snapshot-only request cannot discard an otherwise valid control acknowledgement; an accepted control acknowledgement cannot overwrite a newer peer projection. A changed tenant/source/real session/instance still invalidates the old response under both paths.”

**Proof:** start a combined control; begin a later snapshot-only read; deliver both responses in each order. The next control uses the accepted current window without inventing a generation or re-registering, while the displayed names come only from the current projection generation. Also repeat with an intervening source/tenant/session change, which accepts neither old path.

### F02 — Distinguish prohibited operational payloads from retained technical backup rows

**Medium severity; likely proof contradiction if read literally.** P29 initially grouped backup restore with logs/exports and required absence of topic content. The data model intentionally uses regular logged rows containing an opaque observer topic and profile/session/source references. Those minimal technical rows can exist in platform backups/WAL until the owning retention policy expires them. R20 and P34 already correctly avoid promising backup erasure at row expiry. A proof requirement implying that backup media cannot contain the declared technical topic would contradict the selected storage approach or encourage an unnecessary unlogged/excluded-backup design.

**Exact correction:** constrain no raw topic/draft/name payloads to operational logs, traces, error bodies, rate-limit diagnostics and exports. Separately verify that backups retain only the declared minimal technical state under the actual platform retention/access policy; they create no staff-facing history, cannot resurrect an old lease and are never claimed erased by the15minute row-cleanup target. P34 already covers the restore/retention outcome. No new storage capability, consent flow or backup platform is required.

The only remaining initial-ledger correction is F02. It does not alter A, timing values, source/privacy authority or Email Studio/P6/CRM ownership.

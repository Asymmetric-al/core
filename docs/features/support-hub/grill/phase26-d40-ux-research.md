## The strongest version of B

Keep two independent actions: **Mark unwanted / Restore** changes the current qualified conversation disposition; **Hold future email / Stop holding** changes a narrowly reviewed receiving-inbox policy. The second never happens by default. Future matches join D19's existing **Needs review** custody and decision path. Stopping a policy does not release already-held input, and restoring an admitted conversation does not stop a policy.

This makes recurring unwanted correspondence manageable without turning a CRM person into a blocked account, treating every future message as malicious, or duplicating the intake queue. The ordinary user sees the message and scope, chooses an action and receives a truthful result. The existing owners perform the checks; no rule language, domain wildcard, IP rule, operator tree or compulsory combined wizard is needed.

## Strongest alternative, reconsidered fairly

**A — Current set-aside only** remains simpler: it needs no future hold policy, false-positive matching or policy maintenance. Its cost is repeated unwanted correspondence reaching ordinary handling. The founder has now selected the broader B, so the permanent solution is to implement that extra need narrowly, not keep arguing for A or quietly omit the management/recovery half.

B retains A's easy normal path. Staff may mark current correspondence unwanted and stop there. A worker who has receiving-policy authority can additionally review one exact sender/inbox pair. If a colleague lacks that authority, the current action remains usable; no fake broad administrator role or mandatory permission detour is introduced. If the fixed future-hold owner is unqualified or unavailable, the UI honestly reports that limitation rather than silently enabling the legacy automation scaffold.

**C — Existing Resolve plus labels** still has lower implementation cost but would rely more heavily on staff conventions and could obscure the distinction between non-support correspondence and genuine successful care. It does not satisfy the selected future-mail holding need. None of the alternatives may erase current obligations, infer identity from an address, or manipulate feedback/reporting by labeling a difficult request unwanted.

## Repository facts relevant to the actual interface

Fresh inspection after the checkpoint confirms an existing Support settings shell and contextual conversation header, not the complete new capability. `SupportSettingsLayout.tsx` provides a responsive settings layout. `InboxSettingsForm.tsx:31–67` loads an active/default settings object, resets local form state when it changes, and can fall back to the literal name Donor Care. That is not sufficient evidence of the inbox whose receiving policy should change. A hold must display a real current-authorized **receiving inbox**, never guess from the active default or current conversation handler.

`ConversationHeader.tsx:46–93` currently places status/action controls in the reader, including a direct Resolve mutation. D40 should extend the qualified contextual-menu pattern established by the ratified grill decisions, not copy that old direct-status shortcut. The existing settings navigation includes an Automations route; D1/D19 keep Phase34 as the sole configurable rule-engine owner, so that route is not the future-hold implementation boundary.

This distinction matters after a move: mail may have originally reached inbox A while the conversation is now handled in B. A future hold uses the exact qualified receiving-inbox and sender identity, as agreed with the root review. Its preview must name A when A is the scope; choosing the visible handler B without qualification would change the wrong future population. The same problem exists with a merged conversation containing multiple original sender/inbox pairs. The same canonical incoming-email evidence may be reached through an admitted message or a currently authorized qualified D19-held input; no Release is required merely to start a separately authorized future policy, and no existing input gate is cleared by doing so.

## Permanent solution, kept small

Support owns the unwanted episode and current-source work consequences. The fixed receiving-policy owner owns one exact mailbox/inbox hold and its start/stop control. D19 owns held-input custody, explanation, Release/Dismiss/Return and other gate checks. CRM remains authoritative for people/relationships; P17/Email Studio and P6 retain actual content/preparation and delivery. Neither action creates a new mail purpose, survey, provider spam report, contact deletion, unsubscribe or third-party rule.

The selected answer's recommended disposition is **Accept with required amendments**: complete both capabilities, with one small current action and one optional reviewed policy action, a persistent recovery path for each, and a reused held-input journey. Research does not justify an enterprise anti-spam console, all-tenant lists, new wizard, private sender taxonomy, AI classifier, new reader/editor or general workflow builder. B is selected; all detailed UX clauses remain proposed for ratification, and no Q41 is opened.

**Single best recommendation: A — Formalize the accepted design with `/to-prd`.** The remaining immediate need is a coherent, inspectable contract and clear evidence obligations. The accepted user and technical tests still gate activation. A does not declare perfect UX, freeze every implementation detail or preclude focused prototypes and staff research during design. Material contrary evidence must produce a targeted explicit correction; acceptance is not a reason to preserve a weak design.

These options choose the **next activity**, not three permanent methods or product configurations. B and C are credible alternatives when integrated interaction or actual work habits are the principal uncertainty. The documentary coverage check is already performed in this turn, not work the founder must request again. No choice silently discards another method's necessary evidence.

## Concrete example

Consider this illustrative task, assembled from accepted journeys rather than presented as observed ministry behavior: a staff member opens a request, checks permitted CRM context, begins a Reply, leaves to handle another item, resumes the correct private draft, sees a new message and completes the reply without losing context or confusing Internal note with external Reply.

- A records the full outcome and proof across D2/D4/D9/D26/D33–D39, including exact domain authority, private drafts and current send review.
- B lets the founder or researcher operate representative transitions, including an interruption or failed action, in the actual proposed visual arrangement. It should not reproduce all forty decisions just to look complete.
- C checks a recent comparable real task to learn whether these transitions, interruptions and context needs accurately reflect intended staff work.

D40's Mark/Restore versus Hold/Stop distinction is another justified prototype task if B is chosen. A prototype has value only if it tests a named uncertainty. No extra mailbox, CRM, communications engine or workflow scope follows from illustrating the journey.

## Research supporting the alternatives

[Current research and full comparison](phase26-q41-vendor-research.md) distinguishes verified method/product facts from the recommendation above.

GOV.UK's current alpha guidance recommends focusing prototypes on risky assumptions rather than reproducing the whole wider journey, and treats prototype code as experimental. This supports a bounded B, not a production implementation or a mandatory government process for Asym. Published 2016, updated 2019; checked 15 September 2026. [Risk-focused prototyping](https://www.gov.uk/service-manual/agile-delivery/how-the-alpha-phase-works).

Research with intended users supplies evidence that founder preference and documents cannot. Interviews should use concrete experiences, while moderated usability testing observes actual or likely users attempting relevant tasks. This supports C for work discovery and actual-user evaluation of B or the later product; neither can be manufactured through agent roleplay. [In-depth interviews](https://www.gov.uk/service-manual/user-research/using-in-depth-interviews), [moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing).

W3C distinguishes evaluation involving users from standards-based accessibility evaluation; both contribute evidence. A prototype walkthrough cannot close production accessibility or actual source-authorization obligations. [Involving users in accessibility evaluation](https://www.w3.org/WAI/test-evaluate/involving-users/).

For a directly relevant product example, HubSpot documents associated-record context beside its help-desk conversation and a History tab, with ticket access restrictions. This supports testing Support-to-CRM continuity as part of a complete task. It does not establish Asym permissions, vendor architecture or a requirement to copy HubSpot's settings/AI/layout features. Service Hub Professional/Enterprise with feature-specific seat/permission limits; page updated 7 September 2026. [HubSpot help-desk workflow](https://knowledge.hubspot.com/help-desk/manage-tickets-in-help-desk).

None of these sources establishes that PRD-first is universally best. A is the reasoned next-step judgment for this accepted session, subject to its stated empirical limits.

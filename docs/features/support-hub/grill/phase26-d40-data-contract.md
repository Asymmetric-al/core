## Current primary technical evidence

Supabase's current API guidance separates object grants from row policies and explains changing default exposure. Inspect the actual project roles/default privileges; a new table cannot be assumed private merely because another project now opts into exposure. Functions need EXECUTE controls, and a PostgREST pre-request hook does not protect every Storage/Realtime path. [Securing your API](https://supabase.com/docs/guides/api/securing-your-api), [default-exposure change](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

PostgreSQL policies check permitted old rows and proposed new rows; an omitted UPDATE WITH CHECK can reuse USING. SECURITY DEFINER uses its owner's actual privileges, not an automatic universal bypass. Protect effective policy unions, function owners/search paths/EXECUTE and view semantics. A partial unique active-rule index is useful but does not serialize a policy check against a concurrent new rule by itself. [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html), [CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html), [partial indexes](https://www.postgresql.org/docs/17/indexes-partial.html), [explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html), [Supabase views](https://supabase.com/docs/guides/database/views).

These qualifications correct overbroad skill examples; the skills themselves are unchanged. Do not import their illustrative performance multipliers or arbitrary timeouts as measured Asym capacity. The current Supabase changelog was retrieved and relevant default-grant and reserved-Realtime-schema changes inspected; no platform or dependency upgrade was performed.

SMTP preserves local-part case even though many providers discourage exploiting that distinction; DNS mailbox domains are case-insensitive. RFC From describes author mailbox claims, while Reply-To describes the requested reply destination. They are not interchangeable blocking identities, and standards do not prove a claim was authenticated. [RFC5321 §2.3.11](https://www.rfc-editor.org/rfc/rfc5321#section-2.3.11), [RFC5322 §3.6.2](https://www.rfc-editor.org/rfc/rfc5322#section-3.6.2). Private Storage operations have their own policies and service keys bypass them; signing a URL does not give D40 an independent right to reveal or restore bytes. ## Exact proposed contracts

### C01 — Two owners, two independent actions

“Support owns Mark unwanted and Restore for exact admitted original conversations. The canonical incoming-email policy owner owns a fixed exact observed-mailbox hold within one qualified receiving inbox. D40 adds the narrow policy predicate and management use case to that boundary, not an independent Support rule registry, arbitrary filter builder, domain policy or CRM-person status. Marking unwanted does not enable the future hold; enabling/stopping a hold does not mark, restore, dismiss or release existing correspondence.”

Use existing `packages/api` command ownership and shared projected reads. A new physical table, if needed by the qualified owner, remains an implementation choice; naming an unimplemented owner contract is not evidence that it currently exists. Do not append sender types to the recipient-route enum and inherit its destination-changing/auto-resume behavior.

### C02 — Exact original disposition and valid topology

“Mark unwanted qualifies the complete current reviewed email-origin component and every included original under current tenant/source/action authority. It is allowed only for non-support correspondence with no legitimate Support work or retained genuine commitments that the action would conceal. One nuisance message, shared email, an optional label or AI classification cannot authorize hiding a mixed component. Bind accepted contributors to immutable original IDs, exact topology and source/work versions; preserve D10 provenance and Undo. D26 manual creation and D29 public-form decisions are not replaced or broadened by this email-origin action.”

Use one current source disposition plus append-only decisions; do not copy or delete message bodies and do not add a fifth D3 work status. A component is absent from ordinary work only when the source projection proves every included original is unwanted and no independently owed work is hidden. New legitimate admitted input for B makes B ordinary and the A/B component visible for current review; it does not silently restore A's unrelated original or erase A's history. A new Merge involving unwanted material requires the accepted Restore path first. D10 Undo reprojects the surviving original designations; no new per-message classifier or generic split editor follows.

### C03 — Operation-specific authority and trusted attribution

“Viewing set-aside material, marking it, restoring it, inspecting active hold policy, enabling/stopping that policy and deciding a held input each require their own existing qualified source/inbox capability. Staff assignment, review designation, policy authorship, shared email, CRM relationship or tenant-admin label alone is not blanket body access or policy authority. Derive tenant, auth user, actual profile/membership, current capability and decision time from trusted server context.”

A policy manager may Stop an independently retained active rule without revealing an expired original body. A reviewer can Release one permitted input without authority to alter future policy. Do not require the original creator to remain employed to manage an active rule, and do not block actual security revocation to preserve reviewer coverage. Follow D19's coverage/oversight exception handling rather than grant emergency access.

### C04 — Exact observed address is not sender identity

“Enable future holding only from one currently permitted, canonical accepted input with an unambiguous source mailbox qualified by the intake owner's versioned parser and equality contract. Show that exact address as observed, plus the receiving inbox. A display name, Reply-To, Return-Path, CRM contact field, forwarded body, embedded original header, shared-address relationship or synthetic missing-address fallback is not a substitute.”

Preserve the exact parsed local part under qualified syntax; normalize domain comparison under the owner's DNS/IDNA rules. Do not generically lowercase local parts, strip dots or plus tags, equate aliases, expand to a domain, or infer all mailboxes of a person. Multiple From mailboxes, malformed/unsupported syntax and uncertain forwarded origin make this shortcut unavailable with a plain explanation; they do not pick the first address or invite arbitrary unreviewed text entry. Existing broader mail parsing/routing behavior must not be silently changed for unrelated features; qualify the canonical predicate required here and its normalization version.

A verified provider webhook establishes an integration event, not the human sender's identity. Authentication evidence, if used, comes only from its trusted receiving boundary; user-supplied Authentication-Results or quoted headers cannot elevate trust. This is a review hold on observed mail, not identity verification. Shared/forwarding addresses can carry legitimate mail: preserve one-input Release and simple Stop, and never label a CRM person blocked.

The qualifying canonical source may be an already admitted inbound message or a currently authorized D19 held input with the same proved exact mailbox/receiving pair and independent hold-management permission. Enabling future holding never requires releasing unwanted current mail first, and it does not change that held input's own review gates or historical acceptance decision. Review-body access is not granted merely by policy-management permission.

### C05 — Receiving inbox remains distinct from current handling

“The hold key is the actual tenant-qualified receiving inbox and exact observed source mailbox. Bind that inbox through D1's canonical receiving/recipient occurrence and qualified connection/routing evidence, not the conversation's current handling inbox, a mutable merged root, a visible To string alone, or a guessed domain. Transfers, aliases, rename, Merge/Undo and forwarding do not silently expand or move the rule.”

A receiving-inbox alias already owned by that same qualified inbox follows its actual owner mapping; this does not grant domain-wide matching or a new alias management feature. Multiple recipient occurrences retain their D1 independent scope. A rule for inbox A cannot hold delivery to B solely because A's conversation was moved to B. When the one receiving scope is not provable, keep existing safe intake review and withhold policy activation. A retired/replaced inbox must not transfer a rule to a newly created inbox with a reused name/address.

### C06 — Future means first canonical intake acceptance

“Hold Enable/Stop and the first durable accepted canonical input/receiving occurrence use one qualified intake-owner ordering boundary. The input retains the applicable policy revision/decision once. If first acceptance wins before Enable, that Enable does not retroactively hold the input. If Enable wins first, a later matching first acceptance records the hold gate. Stop affects later first acceptances; it does not release or reinterpret previously held input.”

Use durable acceptance and immutable policy revisions, not sender Date, received-at guesses, webhook redelivery, worker execution time or a global message counter. Capture a coherent policy checkpoint with first accepted input; where receiving scope is initially unresolved, the intake owner must later resolve the applicable retained version for that original acceptance rather than read worker-time policy. Missing evidence remains pending/restricted recovery, not an invented pass. This versioned boundary is an explicit preactivation gap in current source, not an existing deployed mechanism.

Serialize empty-rule insertion, Enable/Stop and first decision too: locking only a row that does not yet exist leaves a race. A short owner-scoped policy-head/shared-admission versus exclusive-change lock protocol is one viable design; choose and prove the actual protocol with deterministic lock order and bounded retries. Do not hold DB transactions across provider fetch, scan, network dispatch or user interaction. Current independent security, tenant/source restrictions and expiry are rechecked at final admission even though the ordinary hold decision is historically fixed.

### C07 — Minimal relational facts and constraints

“Store only facts needed for current disposition, exact policy and once-only review/admission. Tenant-owned references must agree structurally or through an equivalently constrained authoritative boundary. Caller data cannot transform a permitted row into a different tenant, receiving inbox, original, match address, actor, decision or authorized effect.”

D40 adds no money fields, floating amounts or copied CRM data.

### C08 — Enable, Stop and duplicate requests

“Enabling a hold reviews and commits one exact scope under current policy authority and expected version. Concurrent identical requests resolve to the same effective rule or a truthful Already holding result; they do not redirect an existing rule, create stacked holds, broaden scope or replay a second notification. Stop ends that rule's future applicability and records its own authorized correction history.”

Policy commands and disposition commands keep separate results. If one succeeds and the other fails, preserve and show the actual success rather than a false all-or-nothing toast or compensating action. Changing address/inbox scope is not an unrestricted UPDATE: stop the old scope and explicitly enable a new independently qualified one. Hold again is a fresh activation of the retained exact pair, requalifying current policy authority, receiving scope, review coverage and custody; it never resurrects old approval or requires recovering an expired triggering body. Lost command responses reconcile the durable same operation/effect; retries cannot re-enable a newer stopped generation or undo a later Restore. A Stop can be idempotently repeated but cannot erase matched historical gates.

### C09 — Held input and the exact Release exception

“A D40 match enters D19's existing retained Needs review path before ordinary Support admission. It carries an explicit future-mail-hold reason alongside other independently current gates. Reviewers may Release that one qualified input, Dismiss it, or return a dismissed input to review under D19. Release neither disables the rule nor grants sender trust; Stop neither releases this input nor dismisses it.”

The durable release exception targets the exact canonical input/recipient occurrence and the hold-gate occurrence matched from first-acceptance evidence, not the mutable current active-rule head. Same-effect valid retries recognize that exception and cannot loop the released input back into the same hold. Later Stop/re-enable does not attach a new ordinary hold to old input. Release still cannot bypass malware, missing body, classification, unknown binding, expiry, changed reviewer authority or other source gates. An exemption is not reusable for another email from the same address.

Before admission, an authorized D19 cancellation can invalidate that attempt; a new release uses a new decision generation but the same single admission effect. After admission, cancellation reports actual Already released and correction uses the current source owner. Held messages retain original receipt/custody deadlines; policy activation, viewing, Stop, Return and retries do not renew them. No body/file preview or external confirmation is implied by matching a rule.

### C10 — Atomic admission and unknown success

“Canonical input/D1 recipient occurrence has at most one actual Support admission effect. The input-to-Support linkage, source message/conversation contribution, current disposition reactivation where applicable, custody receipt and required owner obligations commit under one qualified authoritative admission boundary. A read-before-write, temporary worker claim, workflow event ID or repair-to-first-duplicate lookup alone does not provide this invariant.”

D19 decision/audit/continuation commits atomically; downstream admission checks the still-valid decision and all current gates. If source admission committed but the response or secondary delivery is lost, reconcile the same effect and required outbox obligation. Do not manufacture a new input, message, release, CRM occurrence or preparation to retry. Current source's separate routing and bridge writes are a verified gap to close, not a model to endorse. Preserve already admitted evidence on replay; a new hold policy cannot pull admitted content backward into intake.

### C11 — Database grants, RLS and privileged paths

“Keep raw input, sensitive policy mutation, review, disposition mutation and durable history server-command owned. Existing RLS-enabled/no-browser-grants raw intake tables are an appropriate posture. Approved browser read projections expose only current permitted source/policy metadata; they do not grant raw rule or history mutation. Inspect actual table/schema/column grants, effective SELECT/USING/WITH CHECK policies, views, RPC EXECUTE and every service-role path.”

USING qualifies the old row; WITH CHECK and immutable-field/command constraints qualify the resulting row. Broad same-tenant predicates are insufficient for current inbox/source capability, trusted actor or valid state transitions. An omitted WITH CHECK can inherit USING, and SECURITY DEFINER uses its actual owner's rights; neither shorthand substitutes for testing effective authority. Fix search_path and qualify objects for justified definer functions, revoke ambient execution, and test owner/BYPASSRLS roles, policy unions and invoker/definer views. A direct update must not transfer scope, clear a hold, forge admission or change audit attribution.

Services derive their input from authenticated canonical source/operation context and recheck tenant, actor delegation, receiving/source scope and current restrictions. A valid signed webhook is not permission to accept caller-selected tenants or spoofed sender identity. No service credential enters a browser, message body, log, output artifact or client token. An API pre-request check does not replace Storage/Realtime policies. Expected hidden-row denial must not reveal policy existence through raw uniqueness/FK errors or counts.

### C12 — Files, caches, privacy and recovery views

“Set aside and held-review views reuse current authorized source representations; do not create a second transcript store, public bucket or revealable privacy archive. D16 restrictions and D17/D19 custody still apply to bodies, previews, derivatives, signed URLs, search, exports, notifications and restored data. Restore cannot bypass a restriction or bring expired bytes back.”

Plain filenames, snippets, counts, matched addresses and rule history can be sensitive; authorize before pagination, aggregation or presentation. Signed URL issuance uses the current source permission and approved short-lived delivery boundary; old URLs/cache/provider copies require the already accepted owner inventory and restriction handling. A nuisance hold is not a legal preservation hold and grants no malware override. No automatic link fetching, remote images, file execution, public lookup or private-message extraction follows from marking or reviewing.

### C13 — Existing work, drafts, reading and CRM

“Mark/Restore and admission serialize with the exact source/work/topology boundary and relevant accepted send/result guards. A stale tab cannot hide new genuine work, erase a pending obligation, manufacture resolution or submit from a no-longer-valid source. Never reset recipients/drafts, post a note, clear D39 reading state, acknowledge P17 notifications, stop required direct attention, or mutate CRM/consent to make the action succeed.”

Manual Restore re-establishes current ordinary review under current authority; it does not replay a saved old assignment/status/reminder snapshot. A newly admitted relevant B contribution restores B's participation in ordinary work without clearing unrelated A provenance. D28 sampling, invitations and truthful reporting cannot interpret non-support disposition as a successful resolution or improve denominators secretly. Definitely unsubmitted obsolete optional material uses its existing cancellation owner; a may-have-begun P6 effect keeps immutable reconciliation rather than a fake recall or fresh dispatch. Existing dirty drafts remain private and subject to their own live source guards; no default external response is created.

A genuinely new actionable P6/owner recovery after an otherwise valid Mark makes the affected original and its current work home visible for review, ending only the now-inapplicable unwanted exclusion. Its actual owner records the obligation and any real purpose change; do not manufacture a new human message, source-content timestamp, D39 unread event, reply fulfillment or duplicate notification. Duplicate or already-reviewed outcomes do not repeatedly reopen work. Other originals and historical designation evidence remain intact.

CRM Parties, represented organizations, requesters, participants, real actors and mailbox claims remain distinct. Marking/holding changes no Party/relationship, registration, consent, contactability, suppression, login, giving or care fact. Existing admitted correspondence history remains honest and permission-aware; held input stays outside ordinary CRM correspondence history under D19. Source navigation through CRM reuses the authorized Support record rather than duplicating it.

# Q38 — Research for unfinished new internal notes

**Research date: 14 September 2026. Question-stage evidence only.** D37's complete private Reply-draft decision is the accepted baseline; its full ratification is recorded separately. Q38 is a new unresolved choice, not permission to implement or a selected note-draft policy. This document does not reopen D35's local correction of already posted notes.

## Verified product gap

[D37-R01](phase26-d37-adversarial-review.md#d37-r01--scope-need-and-strongest-alternative) expressly limits the initial durable My drafts finder to external Reply drafts and preserves separate new-Note working state without inventing its durable storage. [D2-R04](phase26-d2-adversarial-review.md#d2-r04--stable-drafts-and-intentional-edits) requires Reply and Note working state to remain structurally separate. The [independent gap review](phase26-q38-gap-review.md) checks the exact D23 preservation language and current Save draft rejection for Note mode. Existing local text is not evidence of durable note storage or a cross-conversation finder.

The legitimate question is whether and how unfinished **new internal notes** should be saved for later. A posted note is shared under the conversation's current internal authority. A private unposted note draft must not be mistaken for a posted note, staff activity, CRM interaction, notification or customer reply.

## Strongest three alternatives

| Alternative                                         | What staff do                                                                                                                                                                                       | Benefit                                                                                                                                      | Cost and limitation                                                                                                                                                                                                         |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Automatically save note drafts in My drafts** | Write a new Note; eligible changes are saved quietly. Resume it from its conversation or the existing My drafts destination, clearly identified as an internal-note draft.                          | Interrupted internal writing has the same dependable return path as external replies; no separate remember-to-save habit or new destination. | Creates additional governed private stored content automatically and requires reliable kind separation, posting/consumption and note-specific permissions.                                                                  |
| **B — Save note drafts deliberately**               | Choose **Save note draft** when the note or its changes should be kept for later. Successfully saved versions appear in the same My drafts destination; unsaved later edits remain visibly unsaved. | Gives staff deliberate control over what unfinished note content becomes a durable draft while still offering a useful return path.          | Saving is a recurring step; forgetting it requires honest navigation protection and risks losing unsaved changes on browser failure. It is not a blanket guarantee that typed text never exists transiently in the browser. |
| **C — Keep notes as current-session work**          | Write and post in the conversation. Keep existing separate local Note/Reply working state; show an honest guard when navigation would discard unfinished Note work.                                 | Smallest durable-data scope and no saved-note lifecycle to maintain.                                                                         | No durable resume or My drafts entry for new notes; staff may need to finish before leaving. Browser crash/close recovery is not guaranteed.                                                                                |

These are alternative policies for this one kind of writing. They are not three settings, an automatic/manual preference hierarchy, or three features to build together. The earlier weaker B—durably save notes but hide them from My drafts—was evaluated and rejected as the primary comparison: it retains most persistence cost while deliberately impairing the already chosen return path. The deliberate-save option exposes a more meaningful control-versus-friction tradeoff.

**Single recommendation: A.** New internal-note authoring already exists, and D37 defines the intended qualified private persistence/finder capability for replies; its runtime proof remains unexecuted. Extending that experience to a separate, correctly identified Note kind is the most coherent way to preserve interrupted work. This is a product judgment, not a measured claim that all ministries write long notes or that every vendor implements the same private-draft model. **B is the strongest alternative** when deliberate durable retention of unfinished note text matters more than reducing save steps. C remains valid when the smaller scope is the priority.

## Complete illustrative journey

This is a usability fixture, not an asserted tenant workflow frequency. Maya begins an internal handoff note about a Support request, briefly consults permitted CRM context, then handles another conversation before finishing.

Under A, meaningful note work receives the same truthful saved/unsaved distinction as other private writing. The visible mode remains **Internal note**. Returning through My drafts opens that exact note, in its exact qualified conversation, in the existing composer. If a Reply draft also exists, the two remain distinguishable and neither is converted, overwritten or consumed by the other's action. Maya reviews and deliberately selects the existing **Add note** action to post. Only then can the posted-note and eligible attention rules apply.

Under B, Maya must deliberately save the new note or later edits before relying on cross-navigation persistence. The saved note uses the same My drafts destination and the same clear Note identity. If she leaves with later changes, the interface distinguishes the saved version from unsaved work; it must not silently autosave in a way that nullifies the chosen policy.

Under C, a same-session switch that genuinely preserves the qualified local Note working state can preserve her writing. A transition that destroys it must explain the actual loss and offer Stay or deliberate discard. A persistent saved note must not be claimed from a mounted component, browser history or best-effort unload warning.

The design implication for A/B is modest: a clear textual **Internal note** versus **Reply** distinction in the existing list and resumed composer; the metadata-only row, accessible source context and direct activation remain. The question does not preselect another tab, global filter, note-body snippet, count badge, shortcut, modal, pixel geometry or fixed timing. Use existing Base UI/base-maia semantics rather than a yellow-only distinction. On narrow screens, show the note's conversation and internal nature before forcing the keyboard open.

### Feedback and evidence limits

The [Intercom community discussion](https://community.intercom.com/helpdesk-9/abandon-message-creation-7161) began May 15, 2024. Participants describe interruption and resorting to another writing app. A support-engineering reply on March 11, 2025 describes a then-current reply draft being cleared after switching to and posting a note. This is dated, self-selected feedback and an old support response—not a fresh verification of all Intercom behavior or a measure of prevalence. It is useful for testing that Asym's separate Reply/Note working slots never erase one another.

No production donor/staff study or authenticated vendor note-draft session was performed for this question. Primary documents establish selected behavior, not universal usability superiority. No nonprofit-specific need for a new diary, member-care record or organization-wide notes workspace has been established; those are excluded rather than invented. All timings, storage details, quotas and permission mappings require the selected answer's owner review, not competitor inference.

## Architecture, privacy and Email Studio boundaries shared by every option

1. **Same Support source through CRM.** CRM may host the same authorized Support detail. It does not own another copy of a new note draft, infer author from assignee, populate a Party from typed names or make saving an interaction/last-contact fact. Current source and independent CRM authority remain separate.
2. **Unposted is private; posted is internal.** An unfinished note is not visible to teammates merely because they can read the conversation. Source/tenant/author scope applies to list metadata, body, attachments and recovery. A private-draft label never authorizes retention after source restrictions or expiry.
3. **Save and post are different effects.** Saving neither publishes a note nor sends a mention notification, executes staged work, changes status, creates external content or satisfies follow-up. Deliberate Add note uses existing authorized internal-note admission. Posting may cause already-admitted internal attention; do not claim that all internal note actions can never cause a notification.
4. **Purpose-specific, shared implementation.** If A/B wins, reuse D37's correct owner/controller/atomic-bundle/recovery capabilities where appropriate, with distinct note purpose and note eligibility. Do not blindly copy email fields, signature requirements, email-readiness gates, Send/P17 preparation, message transport states or external-reply cardinality into internal notes. Exact note cardinality/schema/lifecycle remain for the selected-answer review.
5. **No cross-purpose conversions.** Switching between Reply and Note selects separate working content. A late save, posting completion, restore or discard cannot overwrite or consume the other kind. No known internal-purpose material becomes an external reply through this finder or generic editor toggle.
6. **Email Studio/P17.** Shared schema/editor reuse is allowed, but private note storage and posting remain Support-owned. P17's governed message preparation is used for actual admitted communication purposes; saving or resuming a note is not a new email-preparation, template-publication or send operation. If posting results in an already-qualified internal notification, that notification follows its existing content/purpose/attention contract.
7. **P6.** Actual delivery/reconciliation remains with the existing delivery owner. New-note saving has no provider draft, inbox synchronization, secondary mailer or outbound transport dependency. A later external reply still follows D23/D36/D37 and P17/P6 unchanged.
8. **D35 stays settled.** Editing a previously posted note remains the accepted local Edit/Save changes/Cancel workflow with visible history. Q38 introduces no posted-note autosave, revision draft finder, restore history service or revision-sharing policy.

## What the selected answer must settle, without preselecting it here

For A/B, require an exact distinct note-draft identity/cardinality, who may save/resume/post, how meaningful changes and incomplete notes are handled, atomic current-version saves, operation recovery, privacy/retention, attachment and mention references, posting consumption and duplicate-post prevention, merge/source affinity, migration away from current unqualified paths, and cross-surface tests. For B, distinguish deliberate saves from later unsaved edits; no quiet auto-persistence should override the policy. For C, prove actual same-session preservation and precise leave/crash limitations without pretending a hidden browser store is durable support data.

Under every policy, test a saved or locally retained Reply beside a new Note; rapid conversation switching; permission loss; source merge/unmerge; Post/Discard versus late save; multiple tabs; failed attachment transfer; a CRM side visit; keyboard/IME/mobile navigation; and a mistaken external-mode action. D37's genuine editor source findings must be reused, not replaced by a new widget-only test suite. No quantitative reliability, zero-loss, offline-recovery or perfect-UX claim is established now.

**Q38 remains unanswered. A is the single recommendation, not an adopted policy.**

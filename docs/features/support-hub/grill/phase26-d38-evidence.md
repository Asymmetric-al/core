## Current source findings that change the permanent path

1. The composer has separate local Reply/Note strings/files, but changing conversation resets them. Its Save draft function rejects Note. Durable new-note persistence cannot be obtained by adding a finder over that state.
2. Inserting a mention invokes `logSupportActivity`; with an agent actor, that helper POSTs a synthetic note to the actual `/notes` route and ignores the activity verb. The source therefore contains an unintended publication producer before Add note. Removing it from only the new draft endpoint would leave the original callback path open.
3. Actual Note submission serializes without selected attachments and submits caller author plus HTML/text. The adapter stores `json:null`, inserts a note and then separately bumps conversation state. A committed insert followed by failure makes an ordinary retry capable of another note; these calls are not one atomic private-draft/post protocol.
4. Existing tenant filters, same-tenant composite foreign keys, RLS enablement, anon revocation and both mutation predicates are present. The missing controls are private real-owner/source/purpose enforcement, narrow effective access and atomic lifecycle, not imaginary absence of all tenant protection.
5. D10 general-note posting follows the current continuing original, while private working origin remains stable. D24 excludes Note-plus-work mode. D15 optional following does not own every direct mention. Those accepted boundaries narrow generic reuse from Reply.

## Supabase implementation basis

Use the browser's qualified editor/controller and approved scoped read model; send meaningful complete candidates to the canonical `packages/api` command boundary. The authenticated server resolves current tenant, real actor and operation-specific source rights. One qualified Postgres transaction/RPC owns each save/post/discard operation. Postgres supplies persistent records and concurrency/constraint enforcement; Realtime events, a browser component and a Vercel function's memory do not supply that durability. Supabase documents object grants separately from row policies, while its database-function interface permits the bounded transaction boundary. [API security](https://supabase.com/docs/guides/api/securing-your-api), [database functions](https://supabase.com/docs/guides/database/functions).

The save command only stores private Note state. Add note rechecks and commits one admitted note, initial history, asset relationships, consumed draft, immutable result and required source/attention obligations. Storage finalization/cleanup and notification delivery are separate recoverable effects; calling them inside the SQL transaction cannot make provider/blob I/O atomic. Supabase's Storage permissions and signed capability behavior require their own current-authority controls. [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [bucket fundamentals](https://supabase.com/docs/guides/storage/buckets/fundamentals).

The invoked skill was checked against primary technical evidence rather than treated as infallible. An omitted `WITH CHECK` can inherit `USING`; SECURITY DEFINER runs with its owner's actual privileges; views/grants and effective policy combinations require their own analysis. The full [C01–C15 contract](phase26-d38-supabase-contract.md) captures these corrections, no raw client DML shortcut, current actor mapping, typed constraints, indexes, retention, rollout and actual proof obligations. [PostgreSQL 17 policy reference](https://www.postgresql.org/docs/17/sql-createpolicy.html), [function reference](https://www.postgresql.org/docs/17/sql-createfunction.html).

# Q29 — Requester help discovery evidence

Researched 13 September 2026. D28 is fully ratified; this evidence supports one unanswered choice about requester discovery, not a public Help-center implementation.

## Why this question comes next

The [Phase 26 roadmap](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L2895) frames Support as one staff inbound/work surface with owner boundaries. It is not an instruction to turn the whole ministry product into a help desk. D1–D28 now cover conversation work, collaboration, routing, privacy, wording, guidance and feedback. Requester help discovery remains genuinely unselected: [D1-R1](phase26-d1-adversarial-review.md) guarantees ordinary contact without mandatory self-service; [D27-C](phase26-d27c-adversarial-review.md) covers the staff finder, explicitly retaining separate public/Internal ownership. Neither chooses whether a requester Help entry presents helpful public content or whether a dedicated Help center is required.

Other possible next topics were examined: more channels/AI would expand scope without a newly demonstrated need; implementation proof/legacy migration must be captured, but discoverable source facts are not a founder feature vote; general reporting remains a possible later product branch while D14/D21/D28 already fix their specific metric invariants. Completing the requester-entry journey is the clearest next coherent surface decision. The [independent gap review](phase26-q29-gap-review.md) checks that prioritization and the strongest alternatives.

## Proposed recommendation and rejected shortcuts

Recommend **A** as the strongest present product judgment: public guidance at an existing point of need, with immediately available direct contact and graceful no-guidance fallback. **B** is a serious simpler alternative for sparse/individualized support. **C** is strongest for a substantial maintained public library and independent search arrivals. None is a requirement to reproduce a competitor's enterprise feature set.

Do not expose D27-C Internal Staff guides or Shared by link content in public discovery; copy articles into a new Support source; infer article applicability from private CRM/giving content; paste conversation details into public search/URLs/analytics; count reading as a solved request; create a ticket or D28 feedback opportunity from a guide click; or make advice execute an owner's protected action. Email Studio remains responsible only when an actual independently qualified message is prepared; browsing is not a message trigger.

The user's answer will settle this scope. Detailed authoring/curation scope, UI composition, public-search semantics, source withdrawal, privacy, contextual intake, mobile/keyboard/recovery and release proof will then receive the required adversarial review. No new D29 decision, formal spec, runtime, provider changes or real messages are recorded before that answer.

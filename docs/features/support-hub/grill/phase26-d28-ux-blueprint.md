# D28 — Complete feedback experience

**Fully founder-ratified D28 A, including the complete UX and all amendments; 13 September 2026.** The [R01–R32 decision](phase26-d28-adversarial-review.md) governs. This is a behavioral blueprint, not a rendered/validated production interface. [Current product research](phase26-d28-ux-research.md) supports the choices; its research alternatives are not extra runtime modes.

## Tenant setup, save and maintenance

The tenant manager reaches **Support settings → Feedback** from the existing Support settings area. There is one compact policy card, not a marketing campaign wizard. Header: **Automatic feedback invitations**. Supporting sentence: “Invite feedback after a random sample of eligible completed Support conversations.” Initial state: **Off**. Adjacent status distinguishes Off, On and Needs attention; a failed readiness check never appears On solely because settings were saved.

When configuring On, the card exposes only:

- **Inboxes:** select currently qualified work inboxes the manager can administer. Show each actual public team identity and delivery readiness. Restricted or unavailable inboxes have a clear reason and owner repair route, not a misleading enabled checkbox.
- **Invite a random sample:** labelled number input, suffix%, min 1/max 100/step 1, initial 25. Include keyboard increment/decrement and direct entry; no precision slider. Text: “Each eligible conversation has this chance of being selected. Actual invitations may be fewer because contact limits and safety checks still apply.” An illustrative “About 1 in 4 eligible opportunities” updates at 25%, explicitly approximate. Do not show an invented monthly prediction without real source coverage.
- **Reviewed by:** existing eligible coverage destination plus accountable named tenant feedback owner. This records work ownership, not permission grants. No D19 reviewer, CRM owner or guide publisher is auto-promoted.

Below these fields, a quiet “How it works” summary is always accessible: “Wait 24 hours after completed work. Never ask the same mailbox more than once in 30 days. No reminders. No catch-up invitations for old completed work.” It explains that email-only and ambiguous-recipient exclusions mean this is not a survey of every donor. The 24/30 values are fixed launch behavior; the user need does not justify separate knobs for every timer.

**Preview invitation** shows the current governed P17 team template, selected locale and synthetic non-redeemable action, with preview warnings specific to actual missing requirements. **Edit invitation in Email Studio** preserves the policy draft and return location; publishing wording never turns the policy On. An actual external test send uses a separately authorized P17 test contract after implementation; nothing is sent during grooming or by merely opening preview.

Save validates fields in place, announces errors and focuses the first invalid field only on submit. Saving the first On policy opens one concise effect review showing scope, percentage and fixed guarantees. **Enable invitations** admits one versioned command. While saving, retain values and disable duplicate submission. Timeout says “Checking whether the settings were saved”; reconcile the command rather than issuing another activation. After success, show persistent On status and saved-by/time. No toast-only acknowledgement.

Subsequent percentage changes use ordinary Save and explicitly say “Applies to newly completed work; already waiting invitations keep their previous selection setting.” Scope removal cancels definitely-unsubmitted work in that scope. Added inboxes never backfill old completions. Navigation preserves the draft; browser/tenant changes do not accidentally save. Concurrent edits show a revision conflict with current values and preserve the local unsaved proposal for deliberate reconciliation.

## Turning it Off

Off has immediate meaning: stop all new automatic invitations and fence pending effects before external submission may begin. The save review states: “Pending invitations will be cancelled. Messages whose submission may already have begun cannot be recalled. Previously issued links remain usable until their original expiry.” The resulting card reads **Off — no new invitations**. Historical ratings remain visible under their source retention policy.

Turning On later is a new sending epoch, never a Resume backlog button. There is no hidden list waiting to be delivered. Safety/privacy revocation of a specific issued link is a separate actual owner action, not a side effect of ordinary Off. Owners can still read feedback and use ordinary Support correspondence while invitations are Off.

## Normal worker journey

An authorized worker handles a request through the existing conversation. They can consult Public/Internal Guidance, insert an approved public link, use a curated reply or shortcut and send through Tiptap/D4. None adds a survey to that human reply or changes its recipients/signature. When genuinely finished, the worker uses the existing ordinary completion action; there is no new mandatory survey checkbox, “ask this donor” picker or invitation confirmation for every closure.

The conversation's Feedback section is collapsed by default until relevant. It may say **Waiting until [local time]**, **Not selected**, **Not invited — contact limit**, **Invitation submission uncertain**, **Invited**, **Feedback received**, or **Unavailable**. “Invited” is tied to actual qualified submission evidence and includes uncertainty where applicable; Selected alone never renders Sent. A restricted source is omitted without exposing hidden inbox names or recipient details. Optional informational states do not compete with the main work status.

If work reopens during the quiet interval, its pending timer is cancelled and the ordinary work journey proceeds. A later genuine completion can start a new interval if no draw has occurred. After an opportunity has been sampled, reopening/merging never causes another draw. A merged group has one current selection chance; another linked original cannot retry a Not-selected result. Independently sampled pre-merge history remains visible honestly. Staff do not get a Try again or Include anyway action. They can continue appropriate care regardless of sampling or feedback.

Examples are illustrative, not evidence of current ministry practice: a donor asks how to obtain a giving statement; a staff member asks about account access; a missionary asks a general administrative question. In each case the invitation evaluates the support experience, not the correctness of a receipt, permission entitlement or success of a mission project. Actual restricted member-care/location context is excluded by its owner rules rather than copied into a generic survey.

## Requester email and response journey

1. **Receive one optional email.** It uses a professional public team identity, a neutral subject such as “How was your support experience?”, brief explanation and one **Give feedback** CTA. It contains no gift amount, private case subject, missionary location, transcript, promotional appeal or personal agent performance request. Sender/reply route is qualified; a person can reply normally for continued help. The invitation explains that responding is optional and provides the protected feedback-preference action. There are no smiley-rating URLs, open tracking or reminders.
2. **Open the existing protected doorway.** The generic page explains that continuing opens an Asym action. Its selector-only GET reveals no tenant, action type or case. One deliberate **Continue** validates the fragment verifier at the exact same origin. This extra step preserves the existing P17 contract; a new direct survey URL is rejected. No login or CRM record is created. Missing fragment/unsupported browser uses the existing generic safe recovery and never moves the secret into a query string.
3. **Answer a small form.** Once authorized, show public team identity, the fixed localized question and actual link expiry. No requester name, contact details, previous comment or conversation appears. Use a fieldset with three equal-weight labelled radios: Dissatisfied; Neither satisfied nor dissatisfied; Satisfied. Nothing is preselected. The optional comment is a native textarea, not Tiptap: short plain feedback needs no rich text complexity. Show a 2000-character Unicode-aware limit and preserve text during recoverable validation failures. “Authorized staff may read this feedback. Please do not include sensitive personal or financial details. For further help, reply to the team's email.” Do not call it anonymous or promise monitoring 24/7.
4. **Review and Submit feedback.** Radio choice and comment remain editable before Submit. There is no immediate write on radio selection. An empty rating is a labelled error; negative ratings never require explanation. A valid submission atomically records one response and shows **Thank you. Your feedback has been recorded.** No extra thank-you email follows. The receipt does not imply an underlying request was solved, a complaint was reopened or a financial action completed.
5. **Retry/revisit/correction.** A lost network response checks the same receipt; identical retries cannot duplicate feedback. A used link says feedback has already been recorded without echoing the prior score/comment. Changed replays cannot overwrite another shared-mailbox person's submission. Staff also cannot change the score. A later correction or deletion follows the existing qualified Support/privacy route and is attributed honestly. Expired/revoked/unavailable states show neutral recovery without hidden case information or automatically emailing a replacement link.
6. **Stop invitations.** The invitation's distinct protected preference action leads through the same shared handoff to a clearly scoped confirmation: “Stop feedback invitations from this organization.” It requires no rating, donor login or explanation. P3 records the purpose preference idempotently. Confirmation explains that ordinary Support contact remains governed separately. Feedback participation itself changes no preferences. This action has separate purpose/state and a proposed 90-day validity from its own issuance, independent of the 14-day rating window. A used/expired rating or deleted Support content does not strand the preference action in the original email. Using one action does not consume the other. The 90 days expires only the preference credential, never the resulting recorded opt-out. The P3 preference persists under its independently authorized lifecycle; policy Off→On, CRM merges, key rotation and new invitations cannot clear it or opt anyone back in. After the preference action’s own expiry, the existing qualified contact/privacy route can handle the request; the system does not auto-send a fresh invitation.

The public form intentionally has no Attach file, user profile, knowledge search, multistep survey, chat bot, fundraising link or rich editor. It remains a narrow action inside Asym's existing protected presentation. Review official client/fragment behavior during release proof; the blueprint does not claim universal client support.

## Staff review and CRM-first journey

**Support Reports → Feedback** opens a clean overview with a date-cohort selector and permitted inbox filter. A compact funnel shows Eligible → Selected → Issued → Responded, with suppression and provider-unknown detail available on demand. The response list defaults to **Needs review**; **All feedback** is a simple alternative, not a custom saved-view builder. Rows show rating text, received time, permitted inbox and permitted conversation reference. Comments appear only to a current source-authorized reader, not in tenant-wide notification bodies.

Open a row into the same conversation detail, retaining filter, position and review context. The Feedback section shows the exact submitted question version, score/comment, invitation time and “Submitted through this invitation; respondent identity is not verified.” For a neutral/positive rating with no work needed, **Mark reviewed** records reviewer/time. If further care is needed, the worker takes the existing explicit Support follow-up/reply path. Mark reviewed, reading a low rating and replying are different actions. A negative score never silently reopens work, sends an apology or creates a CRM task.

From CRM, a permitted worker opens the existing Communications → Support relation and gets the same canonical detail/Feedback section. Back returns to the same CRM record and list position; it does not duplicate comment text into a separate Activity. The Overview's up-to-three unfinished preview remains only a preview; historical resolved Support and its permitted feedback remain discoverable through the complete Support list. Revoked Support permission removes the feedback section/source, including counts and snippets, even if the CRM record remains readable. Restricting a CRM record does not delete Support source facts; links/navigation are re-evaluated separately.

## Empty, incomplete and operational states

- **Off/first use:** brief explanation and Configure for qualified managers; ordinary staff see no setup burden.
- **No ratings yet:** “No feedback received for this cohort” with actual issued/unknown/eligible counts; never a 0% satisfaction score or presumed satisfaction.
- **Small sample:** counts remain usable;20 responses is only a caution threshold before a trend, not an assurance of statistical validity. No global donor/agent benchmark.
- **Paused readiness:** show the responsible owner action and expiry consequence. Do not create fresh invitations when the dependency returns after send-by.
- **Unavailable/permission loss:** safe no-content state; no stale comments, hidden totals or public recovery link into CRM.
- **Low bandwidth:** keep text readable and form minimal; recover the same command receipt, never tell the person to request another survey.
- **Duplicate/merged work:** current canonical navigation with original invitation provenance; no duplicate visible “new response” solely because a link or merge changed.

## Visual and interaction requirements

Use existing Core semantic typography, spacing, Base UI components and restrained tokens. Keep the primary invitation policy card short, with details progressively exposed; no decorative KPI wall. Public form is one column with generous labelled targets and no motion required to understand state. Neutral choices are visually equal. Tables collapse into readable labelled rows on mobile. Focus returns to the triggering control when panels close; assistive technology receives error, save and receipt status once. Long international names are never forced into Western first/last assumptions because the response form does not ask for them; RTL and long translated question labels wrap without clipping.

P33/P34/P39 require actual browser, assistive-technology and staff/requester usability proof. Research identifies a strong design direction; no screenshots or user tests have been fabricated.

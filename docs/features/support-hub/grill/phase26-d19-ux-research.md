# D19 independent UX and primary-source research

**Disposition recommendation: Accept A with required amendments.** Designated eligible reviewers per responsible inbox is a sound default over one intake-review capability. The same qualified team can cover several inboxes. The important amendments are current source eligibility, coverage continuity, safe inspection, one-input disposition, honest consequences, and bounded recovery. A generic Recover button or a spam folder with administrative powers would not satisfy the decision.

Research verified 12 September 2026. Scope is routine tenant-bound held intake before ordinary Support admission. Documentation demonstrates vendor behavior; it does not establish vendor architecture, measured usability, ministry prevalence, or production safety in Core. No browser prototype, assistive-technology, provider, database or runtime test was performed.

## Complete proposed user journey

### 1. Set responsibility close to each inbox

Use existing tenant settings and an inbox's Intake review section. The compact form contains:

- **Reviewers:** eligible people or an existing team.
- **Backup coverage:** eligible people/team or the tenant's qualified central review team.
- **Oversight contact:** the operational owner of coverage and aging exceptions.
- Read-only **Coverage** feedback, and the inherited review/retention policy in plain language with an authorized settings link.

“Reviewers inspect held email for this inbox. Adding a reviewer does not grant access to restricted content.” This helper is visible once near the control, not repeated on every row. The picker explains missing eligibility without exposing other inboxes, private groups or personnel facts outside configuration authority.

Save validates active tenant membership, designation capability and appropriate source/inbox rights. A new inbox cannot activate real incoming mail without a usable ordinary review path and separately owned technical/security recovery paths. A tiny tenant may deliberately have one qualified reviewer and a named oversight responsibility; do not pretend that the same person is independent backup, or require an enterprise shift engine/two employees. Show **Single-person coverage** truthfully. This is an operating risk to acknowledge in setup, not authorization to weaken safety.

Teams use current memberships and permissions. Going offline is not loss of authority or proof that the team is unstaffed. Offboarding, team deletion or permission revocation must re-evaluate coverage without deleting retained input. A coverage gap raises one owned exception and uses an already eligible backup; never auto-grant the administrator body access or widen a team. Activation can be blocked prospectively, but established intake must not discard messages due to staffing drift.

### 2. Find work without running a second help desk

Keep **Intake review** under the responsible inbox, with a permission-aware combined view for people who cover several inboxes. The explanatory sentence is **Held email needs review before it enters Support.** This is not Open/Waiting/Resolved work and not a second CRM.

Default list columns: safe sender identity display, subject if permitted, **Why held**, **Received**, **Review by**, and inbox in a combined view. Offer reason, inbox and received-date filters, simple safe search and a separate **Reviewed** history. Avoid body snippets by default; held subjects can themselves be sensitive and need source access.

Sort actionable review by review due time, with original receipt and a stable ID as ties. Preserve filter, scroll, selection and keyboard position when opening a detail or returning from an admitted conversation. A coverage badge belongs at inbox level, not repeated on every message. Empty states distinguish “Nothing needs review” from “No results with these filters” and “Review is unavailable”; failure must never render a misleading zero.

### 3. Inspect safe evidence, then show only meaningful actions

A split view on desktop and full detail on narrow screens keeps one familiar reading order:

1. Sender address and display name, safely established destination, original received date.
2. A short **Why held** explanation with deeper provider/technical facts behind **Details**.
3. Safe body preview and separate attachment states.
4. An action area naming what will happen.
5. Collapsed **Review history**.

Use reason labels tied to genuine evidence and current permissible next step:

| Presentation                    | Meaning                                                          | Main next step                                                                                              |
| ------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **Possible spam**               | A reviewable signal held this input; it is not established abuse | Inspect, then Release this message or Dismiss from Support intake                                           |
| **Destination needs review**    | Tenant is trustworthy but eligible destination is not settled    | Select only a currently permitted destination for this input; submit for qualified routing review if unable |
| **Sender check needs review**   | A relevant authentication/evidence discrepancy exists            | Inspect evidence; release only if the owning policy explicitly permits this class                           |
| **Waiting for message content** | Provider content is missing or retrieval incomplete              | Technical recovery; no pretend security approval                                                            |
| **File check pending**          | A required file assessment is incomplete                         | Owner-governed wait/recovery; do not offer a release that overrides required checks                         |
| **Restricted review required**  | Qualified security/classification/care handling applies          | Owned referral if permitted; no body or reason detail outside authority                                     |

Unknown/conflicting tenant binding never belongs in this tenant list. Generic “Spam” is not the name for every hold. Reason does not itself grant release; available actions are derived by the source owner from current evidence, policy and authority.

Safe preview is data. Do not render sender HTML in the main application's trust context. Prefer a sanitized, noninteractive presentation with links inactive and external resources blocked; retain plain-text view. Link labels reveal actual destination as inert text when authorized, without forcing a URL visit. No automatic attachment download, unsafe inline preview, remote images, forms, scripts or active embeds. Attachment cards show **Checking**, **Unavailable**, **Restricted** or **Available** accurately. “Not detected as malware” must not be promoted to “Safe sender.” Original bytes remain source-owned and restricted.

Microsoft's safe-preview pattern supports the approach; [OWASP XSS prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html) supports context-appropriate output encoding and sanitization. This does not mandate a new sanitizer dependency if Core's existing qualified capability suffices. Staff should not export raw suspicious mail merely to perform routine review.

### 4. Release one input with a clear consequence summary

Use **Release this message to Donor care** or an equivalent action whose target is unambiguous. A compact review confirmation states the destination, message scope and any material consequence. Avoid routine typed confirmation or a new two-person approval workflow. The normal path needs inspection plus one deliberate confirmation, not multiple identical “Are you sure?” dialogs.

The UI must not claim “No email will be sent” if D13 can still produce a qualified receipt confirmation. When currently applicable, explain that existing automatic receipt rules still apply; an old released input does not renew their window. The release screen is not an email composer and cannot customize/send an ad hoc notice.

The completed result says what actually occurred: **Added to conversation #…** for a valid continuation or **Created conversation #…** for a qualified new request. If admission is durable but still processing, show **Release accepted — processing** and reconcile the original operation. A lost response is not a new release attempt. Preserve original input, author, receipt, files and review attribution; never silently recover as a copied message with the reviewer as author.

If the responsible inbox or destination changes between preview and commit, return a refreshed consequence review instead of admitting unseen context. If a current security or source restriction changes, explain that release is now unavailable and identify the owned next step without leaking protected details.

### 5. Dismiss without disguising deletion or future blocking

Use **Dismiss from Support intake** for a review decision that this input is not a Support request. Require a short structured reason such as unwanted solicitation or automatic message; an optional note must not encourage copying sensitive content into permanent audit text.

The confirmation explains that this message will not enter Support, future sender treatment is unchanged, and the applicable removal date. Do not call this Delete if content remains retained, and do not call it Resolved because no Support work was admitted.

Provide **Return to review** from the reviewed detail while the retained source and policy permit it. A toast may offer the shortcut, but cannot be the only recovery route or depend on a few-second deadline. After content expiry, show an honest tombstone and explain that it cannot be reconstructed. Returning to review preserves the original receipt and expiry semantics; it does not automatically release, reset retention, verify a sender or change CRM data.

A release cannot promise blanket Undo after ordinary Support admission has exposed the content or produced an external effect. Corrections use the authoritative conversation/restriction/redaction mechanisms with honest history. A cancelled pending release, if supported, must be decided atomically before admission, not simulated by hiding a row.

### 6. Refer work while keeping responsibility visible

A reviewer unable to decide chooses **Send for qualified review** only when the owning domain exposes that operation. It routes a scoped durable reference to an already authorized owner. It does not forward the body in email, add arbitrary followers, or grant the recipient access.

The result names the qualified team where permitted and displays **Waiting on …** as a review disposition, not a new conversation status. The existing reviewer/oversight can track safe progress. Handoff acceptance or failure is visible; a broken referral cannot remove the original item from accountable work.

Do not build a ticket-approval engine for this. One ordinary review capability, its owned referrals, and existing Core work/notification primitives suffice.

### 7. Keep the queue quiet but accountable

Use neutral text for held age, a muted due indicator and a text/icon **Review overdue** state only when the review target is crossed. Use source-owner timestamps. No ticking seconds, blinking red rows, color-only meaning or automatic focus movement.

The review target is an internal review commitment, independent of D14 customer-reply targets and D13 acknowledgment utility. Show **Received …**, **Review by …**, **Content removes …** as separate concepts. Localized exact date/time and timezone are available by keyboard/touch in Details, not only by hover. Changing browsers, local time or tab visibility does not pause server deadlines.

Oversight receives scoped coverage/age/disposition counts without body access. Meaningful signals include no eligible reviewer, review target exceeded and policy expiry approaching. Notifications coalesce at the inbox/exception level and use existing preferences. A coverage notification must be assigned to a real operational owner even if that owner cannot read the bodies. No per-message public promises or D14 performance credit result from review actions.

Avoid a new business-hours engine. Reuse an established schedule capability if policy calls for staffed review hours; otherwise define elapsed-time semantics explicitly. Nothing in vendor documentation proves a ministry-specific ideal review interval.

### 8. Preserve CRM and cross-surface continuity

Before admission, a held input must not create or merge a person, modify a shared email identity, add an interaction to a CRM timeline, mark “last contacted,” subscribe a person or resolve a gift action. A permitted CRM context link is read-only supporting context and must clearly distinguish a possible association from a verified requester.

After admission, ordinary D1/D8/D9 identity and association rules apply once. The intake review result can open the canonical conversation while retaining the review return path. CRM consumes the canonical permission-aware interaction projection, never a second copy owned by the intake queue. Dismissed input does not become CRM activity simply because staff recognized a name.

## Bulk actions and the smallest complete scope

Do not launch a one-click **Release all**, **Empty queue**, sender block, contact delete or implicit select-all-results operation. Large volumes justify efficient review, not unidentified consequences.

A defensible Phase26 baseline is single-item release plus bounded, deliberate multi-item dismissal after selection. For each selected item, show scope/count/reason and the retention consequence; every item revalidates independently and returns its own outcome. Stale, restricted or no-longer-held items remain untouched. A partial result retains failed items in view and offers only eligible retry. Selection is frozen to explicit IDs and never grows when new mail arrives.

Whether any bulk release is added should require a demonstrated need and proof that the entire selection has compatible reason/destination/authority. The current founder choice does not require it. Previous/Next with persistent filters supplies throughput without a new rule engine. This is a deliberate product scope judgment, not a claim that competitors lack bulk recovery.

## Accessibility and interaction evidence

[WCAG 2.2 status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) supports programmatically exposed async outcomes without unnecessary focus changes. [WAI alert guidance](https://www.w3.org/WAI/ARIA/apg/patterns/alert/) warns against frequent interruption and disappearing essential alerts. Apply polite status announcements to ordinary result feedback, reserve alerts for actionable failures and keep recovery in persistent history.

[WCAG 2.2 target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) defines a 24-by-24 CSS-pixel AA minimum with exceptions. Core's touch convention requires at least 44px button hit targets; follow the stronger local convention with shared tokens. [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and [use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) support a usable narrow layout and text/icon meaning rather than colored badges alone.

[WAI modal-dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) supports correct initial focus, contained keyboard interaction and restoration to a logical trigger. The brief release confirmation must state scope and consequences; routine reversible dismissal needs clear persistent correction, while genuinely irreversible deletion belongs to the existing qualified disposal owner. [Error prevention for data](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html) offers review, checking or reversibility patterns, not a requirement for endless confirmation dialogs.

Local sources inspected: canonical grill-with-docs, grilling, domain-modeling; docs/ai/rules/frontend.md and testing.md; accessibility-review skill and emil-design-engineering/touch-accessibility.md. The touch skill's advice to pause time-limited UI actions when tabs are hidden must not be applied to authoritative D13, review or retention deadlines. Persistent recovery eliminates a toast deadline without changing those source clocks. No runtime UI or WCAG-conformance claim is made.

## Final synthesis for the parent review

A's strongest plausible alternative remains a qualified central review team. A can support that same staffing by deliberate inbox designations without inventing a second operation. The permanent design is one calm inbox-adjacent review surface, explicit safe reasons, exact input/destination actions, qualified fallback responsibility, source-authorized recovery and truthful time/history.

Resolve the command semantics, coverage gap response, held-content retention class and post-release correction boundaries before recording the amended decision. Capture precise permission/timestamp/notification contracts and proof in the later authorized formal spec. Require source authorization, concurrency, unsafe-preview, expiry/reopen, navigation and accessibility proof before release. Do not claim hypothetical safeguards have been implemented.

No unverified numerical retention or staff-review benchmark is recommended here. The lifecycle owner review must choose a bounded platform-qualified held-content policy and explain its review/expiry windows. A missing policy must prevent activation, not silently adopt Zendesk, Help Scout, HubSpot or Zoho defaults.

### Additional exact UX proof

- Confirm the same item never appears as an independently actionable duplicate in ordinary Processing and technical Processing issues; navigation can refer to one authoritative recovery receipt.
- Test D13-eligible, ineligible and eligibility-changing release previews. Acknowledgment hint changes do not start a new window or authorize a send.
- Race Cancel release with admission; show either proven cancellation or actual admitted destination. A lost cancellation response reconciles the existing effect.
- Expire an unreviewed item, then record operational review of that missed intake. Attention can finish without restoring bytes, inventing a dismissal or deleting the missed-expiry count.
- Expire an already dismissed item. It remains historically Dismissed, no longer recoverable, and is not misreported as an unreviewed expiration.
- Complete the last pending business decision while admission remains processing. The empty state must not claim the entire intake is finished.
- In a one-person tenant on a weekend, policy text explains elapsed hours without implying backup staff or business-hour coverage that does not exist.

The proposed max-50 loaded-page dismissal limit is a defensible product safety bound, accurately identified as such in R11; it is not a measured capacity claim. Keep the default page of 25 and explicit selection membership. Do not add bulk release simply because the vendors offer it. The source and date controls should constrain the policy, not add a wizard or a checklist to every routine review.

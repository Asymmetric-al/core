## High-consequence checks

**Purpose/nullability and the private-to-posted transition are sound.** Note candidates cannot acquire external audience, signature, prepared email or D24 work-plan fields merely because Reply shares an aggregate/editor. Immutable private origin/purpose are distinct from the explicitly reviewed publication destination. A new Note is not shared internal content until Add note; at admission it gets current staff-source visibility and its first D35-compatible canonical revision. The separate Reply draft/plan remains intact. Current source's `json:null`, caller author and delivery-state flag are identified as inadequate implementation, not accepted architecture.

**File-only notes are handled without weakening admission.** R04/P06 explicitly allow meaningful canonical body or a ready, clean, currently permitted selected attachment, with no dummy text requirement. Pending-only work can save; any still-selected unfinished/invalid/unsafe file blocks Add note until ready or deliberately removed. R09/P18 do not pretend a PostgreSQL transaction includes object-storage writes. Existing immutable file occurrences and durable owner finalization/cleanup bridge that boundary; no new upload product or external URL acquisition is implied.

**Concurrency covers current authority, not just draft revisions.** R05/R15/R16 explicitly require a common lock/version protocol for topology/source/privacy and note admission. P07/P19/P20 exercise both orderings of source/permission/merge changes. A stale check followed by an independent insert is not compliant. Fast Add note may admit the newest settled candidate without a forced preliminary autosave round trip, but it must resolve earlier dependent saves and qualify the absent/current slot and generation under the same admission protocol. No new key, empty lookup or canceled request proves nonacceptance.

**RLS is neither overstated nor replaced by UI filtering.** R11/P17 require effective SELECT/USING/new-row WITH CHECK, constrained identity columns, inherited/permissive policies, schema/EXECUTE grants, invoker/definer privileges and service paths. The linked contract correctly states that omitted UPDATE/ALL WITH CHECK may inherit USING and that SECURITY DEFINER uses owner privileges rather than universally bypassing RLS. Base-table, RPC and Storage access have their own enforcement; a PostgREST pre-request or private bucket label alone is insufficient. This is a required closure, not a claim current deployed privileges were exercised.

**Existing premature note producers are correctly closed.** R08/R23/P09/P25 identify the actual mention callback/helper as an implementation path to replace before activation. The five-assertion source-backed probe is explicitly mocked/no-network evidence; it is not real server, RLS or notification proof. Actual publication creates the source occurrence and identifier-only required obligations once. Autosave/picker/hydration creates none; downstream attention failure never makes the note disappear, resurrects its draft or authorizes reposting.

**Email Studio and retention semantics stay precise.** A note save/post does not prepare an outgoing human reply or publish a template. A separately authorized published-note/direct-attention channel can use P17/P6 under its own occurrence and current eligibility; the in-product case has no provider preparation. Actual D17 native-note admission occurs once, while drafts/edits do not renew the source. The existing data contract's expired-frontier and source-derived custody requirements remain incorporated. Retaining control evidence is not permission to keep arbitrary sensitive bodies forever.

**The formal authority conflict is explicitly resolved.** R25/P30 and the data contract preserve accepted ADR0001/current Core's Asym-owned CRM model while flagging stale Twenty-backed OpenSpec prose for later authorized formal reconciliation. No retired provider or synchronization is restored. This review does not silently amend formal OpenSpec or claim the contradiction is absent.

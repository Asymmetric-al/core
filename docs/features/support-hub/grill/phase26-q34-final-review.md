## Supabase caution is accurate and consequential

The current [Supabase Presence documentation](https://supabase.com/docs/guides/realtime/presence) says clients publish small state payloads, warns against high-frequency updates, and explains that reconciliation can produce join/leave events without actual user movement. It also permits a custom presence key. Therefore a client-supplied name/key is not trusted staff identity, a join event is not a durable staff visit, and every keystroke should not be assumed an appropriate Presence update. The evidence states these limitations correctly without selecting the mechanism.

The current [Realtime Authorization documentation](https://supabase.com/docs/guides/realtime/authorization) distinguishes permission to publish from permission to receive and calculates channel access when the client joins. Private channel configuration and database policy qualification are explicit. The question correctly warns that channel membership is not permanent source authorization. Actual revocation, actor binding and source-safe fanout would still need proof in the selected answer; generic table subscriptions or a private flag alone do not establish them.

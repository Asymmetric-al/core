## Existing facts versus required new behavior

P23 ADR0170 already governs purpose-bounded forms, one Primary Outcome, atomic occurrence/primary/child/outbox acceptance, independent delivery recovery, no-JS public forms and no uploads/payments. Its Contact concept does not supply an already implemented minimal field schema or certified Support adapter. Current Support source models have email-shaped constraints/defaults and provider linkage; those are not authority to fabricate an email for a form request. D26's staff-recorded source is also distinct from a visitor's own text.

P23's released public body/list audience is invariant; portal/app ownership is separate under P24/P25. D27's public staff finder may select Shared by link Pages, while requester discovery cannot. P23 Article-list support does not automatically certify a Page-reference Help leaf. The permanent path is the explicitly bounded qualification below, not another CMS or generic form engine.

## Two producer adapters, one accepted outcome

**Public adapter:** use trusted public host/base/route → exact P23 Site/locale/current generation → released form/purpose/route. Reject forged form/tenant/route overrides and stale incompatible schema. Current generation and adverse owner gates remain authoritative even when a browser has old HTML.

**App adapter:** use the verified current portal/app tenant/principal → exact approved Help entry binding → same qualified Contact purpose/admission semantics. Optional current-owner context is resolved server-side and rechecked at Submit. It is never private JSON appended to the public form endpoint, a raw record ID accepted because the user is logged in, or a personalized public CMS audience. Qualify this consumer explicitly; the public endpoint cannot borrow app cookies as Site proof.

Both produce the same typed ordinary inquiry and one primary Support acceptance contract through `packages/api`. P23's canonical occurrence, outbox and recovery remain common; there is no app-specific or public-widget submission database. A management interface can coordinate setup, but public and app publication/activation do not become one distributed transaction. Compatible current source revisions must be proven; a stale schema/route cannot silently reinterpret answers.

The standard Support entry's Primary Outcome is certified Support handoff. If the tenant's broader platform currently offers only an independently qualified public email/phone contact, that contact may remain available under its owner while Support form setup is incomplete; D29 must not force-enable Support or fabricate a conversation to make the larger Asym product usable. It also must not silently switch a submitted Support form into P23 Email-only delivery. Other existing P23 forms can still deliberately choose their one Verified Email Destination before release.

## Input, prefill and context rules

Normalize message line endings to LF, require nonblank input, count Unicode scalars rather than bytes/grapheme clusters, and enforce≤10000 scalars. Optional unsplit name≤200 scalars. Preserve original meaningful text; do not rewrite names, transliterate scripts, strip punctuation or treat a subject line as a required routing field. Enforce the current qualified mailbox parser's real length/encoding support; the field remains one declared reply endpoint. Mailbox syntax and authenticated self-prefill do not prove that a new edited address is owned by the actor.

A 256 KiB raw-body guard precedes expensive decoding/parsing; the released envelope has its own field/count/byte bounds. URL-encoded four-byte Unicode can use 12 wire bytes per scalar, so a 64 KiB limit would incorrectly reject some otherwise valid 10000-scalar messages. The synthetic encoding fixture is 126677 bytes including 200 four-byte name scalars and bounded synthetic control fields; the actual released schema must prove its total envelope. HTML `maxlength` uses UTF-16 units, so do not set it blindly to the scalar limit and reject supported emoji early; client hints/counters must match server semantics or defer to the server. Invalid/oversized input returns actionable errors without logging the body or silently truncating it.

The authenticated app may prefill only the actual current requester's authorized self-contact, visibly and editably. Represented organization/linked Party data does not select the reply mailbox. Optional **About** context is a typed source-owned reference with an allowed safe display, not a data snapshot. Its admission requires current actor/source authority and same tenant. If it expires or becomes unauthorized, do not silently retarget; offer explicit ordinary contact without private details. Auth/principal/tenant switches invalidate private prefill/context and local draft state. No long-lived visitor body store/localStorage/device history is introduced to preserve optional guide navigation.

## Work, email and CRM effects

Form admission contributes a genuine external requester source/time to the certified Support adapter. Native form text is a distinct source kind; no email-only default timestamps/direction/provider fields are invented. The first actual staff reply reviews the form's response endpoint and current contactability. It freezes either the real existing acknowledgement lineage or the first actual outgoing lineage through D4/P17/P6. Subsequent actual email carries its actual provider/RFC evidence. A P6 communication event exists for actual communication at the relevant qualified owner seam, not an invented received-email record for a form.

D14's first owed response uses trusted form admission and current source/calendar semantics. It does not start late when a workflow wakes or treat browser Received as a reply. Existing acceptance uncertainty and explicit human coverage remain unchanged. D28 only considers genuinely completed work after actual accepted human public correspondence plus its established one-opportunity/sampling/courtesy/recipient rules. A guide click, form submit or automated acknowledgement creates no feedback eligibility.

The same source appears through CRM's authorized Support relation and canonical detail. Optional source references may link existing CRM context only under D9 and current owner permissions; they do not create duplicated Activity bodies, verified identities or a financial completion. A form asks for help; it cannot itself cancel a gift, issue a receipt/refund, edit a contact or access confidential care. Authorized actions stay behind their actual owners.

## RLS, storage and finite custody

Public anonymous clients post only to the qualified server boundary. Revoke direct unnecessary Data API grants to route/control/occurrence/private Support/audit tables and prove appropriate RLS on exposed data. Authenticated staff roles are not global read authority; check actual capabilities/current scopes and all derived views/counts. Mutations must constrain old and new state via effective USING/WITH CHECK, field privileges and command invariants. PostgreSQL may reuse USING when WITH CHECK is omitted; missing syntax alone is not proof of a hole. Security-definer RPCs need demonstrated need, fixed search_path/schema-qualified dependencies and restricted EXECUTE; service-role work re-proves the same actor/source authority. No secret/service key enters the public form.

Define custody for: public/app config revisions; selected refs/current availability; opaque app context; replay/receipt material; occurrence/recovery envelopes; actual Support text/name/response endpoint; P17 sealed bytes (web confirmation Recent sent copy is Off-only, with no permanent generated support_messages body and only a synthetic Template used preview); P6 transport facts; child work/claims; error responses; exports/search/CRM projections; technical logs and backups. The source owner specifies finite retention, purpose end, holds/restriction and physical cleanup. P23 occurrence cannot become a parallel inbox. D16/D17 cover governed Support content and all representations, with actual new source time and no old-clock renewal from a link/merge/read. Form rejection/validation errors have short purpose-bound custody, not an analytics archive of unsent questions.

Response endpoints, names and comments stay out of metrics/logs/tags/URLs. Private submitted/error/receipt/app-context responses are no-store/no-referrer; immutable public guide/title/contact publications use only their qualified public cache. Replaying a backup reestablishes source revocations and disposal fences before ordinary serve/send/retry. Unknown current authority is not permission to serve a stale positive cache.

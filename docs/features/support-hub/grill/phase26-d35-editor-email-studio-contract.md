## Canonical profile and installed-source truth

D23 already requires purpose-specific code-owned profiles, exact original JSON validation, deterministic safe derivation and qualified editor/render dependency cohorts. D35 reuses that requirement for **correction of an existing Internal note**, with an edit-time allowed-reference inventory from its loaded current base. This is a bounded command/profile context, not a second canonical schema or reusable workflow engine.

Current inspection finds core/react/static-renderer3.22.3 alongside mention/suggestion/html and some extensions3.23.1. Public npm reports core/react3.31.3 as stable on14September2026. These are evidence-date facts, not versions installed by this work or a permanent upgrade instruction. D23's compatible cohort/parser/render qualification remains a prerequisite; do not claim the mixed current consumer is proven safe because packages are present.

The current generic editor's JSON/string normalization and static viewer's blank-on-error behavior do not meet the accepted strict-source contract. Validate complete saved/candidate keys, attributes, marks, allowed node positions, value types, purpose and depth/size/count budgets before ProseMirror can discard unknown data. A content error stops writable initialization/admission; retain the original owner-governed material and show a truthful read-only repair state. Known safe clipboard formatting conversion differs from losing unknown canonical saved content. Exact released profile limits are shared by native note creation and correction; a large old note may not be silently truncated to enter Edit.

Tiptap's documented Pro snapshot history belongs to its collaboration/Document Server system and brings private-registry/Yjs/server dependencies. It is unnecessary for a source-owned note revision and static history reader. Reuse the ordinary editor and store revisions under Support; do not add Pro history, tracked changes, document restore, co-editing or an external snapshot service. [Tiptap snapshots](https://tiptap.dev/docs/collaboration/documents/snapshot), [content checking](https://tiptap.dev/docs/guides/invalid-schema), [React performance](https://tiptap.dev/docs/guides/performance), [Next.js integration](https://tiptap.dev/docs/editor/getting-started/install/nextjs).

## Editing without reference or notification surprises

Allow prose, supported formatting and ordinary safe links. Existing mention or inline-image appearances may be deliberately moved/deleted, including normal paragraph deletion and local undo. The server validates a subset of permitted base references and unchanged retained target/source/purpose attributes. This prevents new notifying targets, foreign assets and retargeting without freezing paragraphs or rejecting normal editing through a hidden immutable-node rule.

The actual file list/occurrences/bytes remain unchanged and visible under **Existing files**, with D16/D32 checks on every access. Removing an image from text is not removal from the note/history. No new upload, file replacement/removal or notifying mention picker is presented in this edit. New supporting material or deliberate attention uses an ordinary new note; actual sensitive removal uses D16. Editing does not copy attachments into a new occurrence or renew their deadline.

Do not reuse the current creation composer's mention-insertion callback: it calls `logSupportActivity`, whose generated sentence is posted through the ordinary note endpoint. That path must be absent from mount, candidate parsing, input, paste, undo, reference deletion, history, Save and Cancel. Programmatic initialization and literal @name text create no publication/attention. Unknown saved semantic nodes cannot disappear merely because a permissive parser accepts the result.

## Quiet edits and source-dependent notification safety

Routine edit success creates no new D15 follower notice, notifying mention, donor email, P17 preparation or P6 send/retry. Editing is not republishing; it neither calls addPrivateNote nor increments native-human publication/message/unread/response/retention clocks.

Source-dependent previews, attention entries and pending communication must still follow current D15/D16/D17 fences. Separate these cases:

| Case                                                                               | Required outcome                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary currently valid source preview                                            | Show only its current permitted representation through the owner. A stale excerpt is not a second source of truth.                                                                                   |
| Prepared but not safely submit-authorized source-dependent content becomes invalid | Stop or correct it through the existing owner safety-continuation/material contract before further render/decrypt/send. No ad hoc rewrite of immutable prepared content or silent replacement email. |
| Provider submission may already have occurred                                      | Reconcile actual in-flight results and preserve factual evidence. Do not claim recall or repeat a provider call because the note was edited.                                                         |
| Delivered notification                                                             | Its bytes/facts remain historical under their custody contract; editing cannot unsend it. Current links still reauthorize and must not reveal old forbidden payload.                                 |
| Valid body-free historical event                                                   | May remain while its facts and purpose are permitted. Do not erase or falsify every previous notice merely because the body changed.                                                                 |
| New ordinary note or separate deliberate staff attention                           | Has its own actual current-source/admission/audience rules and normal P17/P6 consequences. It is not falsely claimed to have no possible notification effect.                                        |

New or removed mention appearances do not change Follow membership or grant conversation access. The contrast in vendor behavior is material: Front documents access consequences for a mention into some individual-inbox conversations, while Freshdesk's current restricted-ticket behavior preserves access restrictions. Core's existing current audience/source intersection governs, regardless of a token or link in text. [Front comments](https://help.front.com/en/articles/2256), [Freshdesk ticket actions](https://support.freshdesk.com/support/solutions/articles/231527-perform-ticket-actions).

D29's web acknowledgement source/profile, P23 Confirmation toggle,15-minute utility/24-hour courtesy and first-form-reply contract are unchanged. Note editing neither triggers nor configures it. Likewise a saved note correction does not mutate governed outgoing signature/wording, recipients, receipts, giving actions or public guidance.

## History, redaction and source truth

Store ordinary editorial revisions as Support-owned content, with minimal ordered edit metadata distinct from purgeable JSON/HTML/text. **View history** is read-only and reauthorizes the exact source and representation. It has no Restore, historical mention replay, file acquisition, external export, automatic summary or AI authority. Ordinary current search uses the current head; older permitted versions remain reachable only through explicit history.

Redacting a span in today's note cannot establish where its meaning exists in earlier versions. When the source owner cannot qualify a safe earlier representation, restrict that affected older body and known derivatives as a whole, retaining only permitted body-free evidence. No fuzzy matching or new semantic redaction service is needed. D16's qualified safe representation/removal is distinct from an ordinary author revision. D17 deadlines remain anchored to the original content generation; neither edit/history nor new preparation renews them.

Metadata can also be sensitive. Do not expose hidden authors, files, timestamps, counts or gaps from inaccessible revisions or merged constituents. Source removal/unlink/merge/Undo and restored backups preserve current restrictions. A source-dependent receipt or history link is not authority to retrieve a disposed body.

## D34 reuse and UI isolation

A posted-note edit is deliberate note composition, but the existing D34 producer must explicitly qualify this context. Bind the real principal/session, original note/source and edit authority. An A-source note inside a merged reader cannot reuse a Reply instance targeting B. The neutral cue does not reveal note mode, note ID, candidate text, recipients, assets or selected historical version. Reading history, focus and hydration do not start it.

Retain D34's existing timers, snapshot/currentness rules and stop-on-save/cancel/source/session loss behavior. One qualified controller context follows the active editing activity; switching to Reply/Note preserves separate private drafts and stops/rebinds correctly. There is no second schema, service or presence history. A missing cue is never an edit lock, permission grant or guarantee that another device will not save; the conditional source-head save is always required. D34 outage does not block editing.

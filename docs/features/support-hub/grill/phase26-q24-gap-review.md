**Recommended next question:** What reusable shortcuts, if any, should staff have for deliberately changing Support work beyond the existing individual actions and saved reply wording?

**Single recommendation: A — Curated Support-only manual action shortcuts.** Keep the saved wording and Send journeys already accepted. Add a small maintained collection only for useful combinations of existing Support operational commands, with clear current effects and deliberate application. This is a product judgment about proportional capability, not measured Asym demand or a claim that mature vendors prove it necessary.

## What earlier decisions do and do not settle

- [D3-R03 and R11](phase26-d3-adversarial-review.md) require identical canonical work semantics, authorization, revisions and evidence across menus, keyboard, bulk and macro entry points. They do not decide whether a new reusable shortcut library should exist. Bulk has exact selected IDs and honest correlated per-item outcomes; a macro decision does not silently add all-matches execution.
- [D4-R02–R04](phase26-d4-adversarial-review.md) already supplies staged **Send and open / wait for requester / wait on our side / resolve** choices. Saved wording is content-only. A work-changing macro is separately disclosed and cannot resolve merely while placing unsent text. The strongest broader option must respect this distinction.
- [D18-R01–R04](phase26-d18-adversarial-review.md) explicitly excludes a business-action macro builder from the wording decision. My replies is not permission to create My operational workflows. Reply/Internal note content cannot switch purposes during insertion.
- [D21-R10/R19](phase26-d21-adversarial-review.md) preserves explicit idempotent Add/Remove and the original source/contributor discipline. The current label runner's convenience API is not the permanent contract.
- [D23](phase26-d23-adversarial-review.md) keeps signatures in P17 authoring/copy/preparation and outside action execution. Neither a shortcut nor its descriptive text can edit the managed signature, change identity, send mail or reinterpret a prepared message.

## Actual options for the founder

These are alternative launch scopes, not three tenant modes to implement.

| Option                                               | Practical experience                                                                                                                                                                                                                                                       | Strongest benefit                                                                                                                                        | Real cost/tradeoff                                                                                                                                                                                                              |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Curated Support-only manual action shortcuts** | Qualified maintainers save useful presets for bounded combinations of existing Support operational actions. Staff choose an eligible shortcut, see its exact current changes and deliberately apply it. Reply wording and sending stay in their current separate controls. | Saves repetitive operational work while keeping message approval and source ownership legible; a maintained shared set avoids personal operation sprawl. | Adds shortcut stewardship, stale-reference handling and a correctly authorized composite operation. A shortcut that merely repeats one obvious native action may offer no value and should not be created by default.           |
| **B — Native actions plus saved wording**            | Staff use existing label/assignment/work controls and D18 wording; D4 already combines sending with an explicitly chosen work transition. No reusable action library is added.                                                                                             | Smallest product and easiest action-by-action explanation; removes the legacy unsafe runner rather than rebuilding it.                                   | Teams repeating a genuine combination perform the same controls repeatedly and depend on habits or guidance to remember each step.                                                                                              |
| **C — Curated staged reply-and-work shortcuts**      | A maintained shortcut can prepare eligible D18 wording together with intended Support changes, with all effects visible. Nothing is sent or prematurely completed while drafting; the normal guarded final action admits the reviewed combination.                         | Greatest reduction in repeated compose-and-organize work and closest to a mixed macro experience.                                                        | Requires a larger staged composite contract across private draft, current content, work changes and final Send; more stale-review and partial-effect hazards, and more potential confusion with content-only My/Shared replies. |

**Recommendation: A.** It creates one useful distinction: saved wording helps write; manual action shortcuts deliberately change Support work. B remains a fully credible complete launch choice, especially if observation shows little repeated multi-action work. C is a real broader alternative, but D4 already solves the common Send-and-status combination. There is not yet evidence warranting a broader mixed draft/action product as the default.

Illustrative example, not a newly invented ministry workflow: staff review a conversation, add two existing Support labels and assign it to a currently eligible colleague. A named shared shortcut can show those three intended changes together before Apply. If the assignee is no longer eligible or a label has been archived, it explains the blocked selection rather than silently skipping a step. The conversation body, prepared email, CRM Party and giving records remain unchanged. No claim is made that a specific tenant currently performs this combination frequently.

For C, the analogous illustration is choosing a reusable information-request reply together with an intended wait/label action. That wait cannot become true simply because the unsent wording appeared. The full intended operation must remain staged for the same final reviewed boundary. This makes C genuinely broader than A rather than a renamed identical recommendation.

## Phase 34 ownership must be reconciled explicitly

The [Phase 26 roadmap boundary](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L2954) reserves the sole configurable trigger/condition/action vocabulary for Phase 34, keeps `support_automation_rules` inert, forbids a parallel builder and says Phase 26 does not forward-gate on Phase 34. The [Phase 34 definition](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L3639) is a general workflow product, not permission to implement it locally under a different label.

**Required interpretation for A:** bounded manually invoked presets over already-qualified, code-owned Support commands, through the shared action contract seam. No tenant-created trigger, condition, branch, loop, delay, script, arbitrary HTTP action or independently extensible action vocabulary. Qualify the narrow registry/descriptor seam if absent; do not pull the Phase 34 rules engine forward or create a Support-specific interpreter that later requires synchronization. A curator choosing allowed target arguments is not entitled to invent new command semantics or bypass source permissions.

If the chosen implementation actually requires an ordered arbitrary action language, conditional branching or a separate configurable action registry, it would conflict with the existing boundary. That implementation must be narrowed or explicitly reconciled with the owning platform decision before acceptance; calling it “manual” would not resolve the conflict. Option C has the same boundary and the additional D4/P17 staged-message obligations.

## Current source makes scope selection consequential

The [server macro runner](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/packages/api/src/admin/support-hub/mutations/run-macro.ts#L33) iterates actions independently, records failed/skipped outcomes and continues; it skips canned-response sending and team assignment. `ok` treats skipped actions as non-failed. This is source behavior, not proof that an exact production macro was invoked.

The [client runner](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/apps/admin/features/support-hub/lib/macro-runner.ts#L66) has a separate mutation bag, defaults `stopOnError` to false, receives caller actor context and offers a canned-insertion callback. It does not itself send the donor reply. These parallel runners and old work mutations need convergence/fencing under any option. Do not describe the existing server runner as auto-sending or assume hardening its UI alone completes the permanent path.

The [roadmap's macro/canned coverage](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L2954) and open ledger matter together: existing source is a design input, not accepted authority to keep every current action kind. In particular, legacy priority, generic snooze, notes and canned actions must not be swept into A merely because a union type already names them.

## Prerequisites and boundaries for the selected-answer review

1. Prove the useful allowed operational combinations against D3/D6/D7/D8/D10/D21, including source topology, current assignee eligibility and archived labels. Exact action coverage follows the founder's answer; Q24 itself does not accept every legacy action.
2. Keep Apply separate from choosing/previewing a shortcut. Show concrete current effects in plain language, with keyboard/touch access and no hidden action from slash-based wording insertion. Native individual actions remain available.
3. Shared curation/use rights are distinct from authority to perform each underlying action. A shortcut is not a permission grant; target metadata, eligibility and effects are checked at current authorized source scope.
4. One deliberate invocation binds exact shortcut revision, conversation/source topology and expected current control revisions. Retry reconciles the same business effect. Decide atomic local composite behavior through the owning command; do not bless the current sequential best-effort loop or promise undo across irreversible effects.
5. No CRM/giving/care mutation, message send/forward, internal note creation, redaction/retention override, intake release, provider call, identity change, follow/notification fan-out or automatic background execution is implied by A. Necessary existing command-produced history/attention remains truthful; “no messages” does not erase legitimate operational evidence.
6. Shortcut configuration lives with operational command ownership, not Email Studio. Email Studio keeps D18 wording, D23 signatures and P17 preparation. B changes none of these; C may reference eligible content but cannot store an alternate HTML body/compiler or acquire send authority.
7. Missing/retired targets, author departure, simultaneous edits, permissions loss, result ambiguity, stopped runs, archived definitions and old-client/migration behavior require explicit lifecycle and outcome proof. Do not invent a forever execution-body archive.
8. A does not create a new bulk feature or mass-action audience from D20/D22 results. Existing qualified batch entry points need their own exact ID/per-item semantics if later included. No implicit all-current-matches scope.

No new runtime tests were appropriate for choosing this product fork. This review used current source, full coverage/register context, ratified owner contracts and current primary documentation.

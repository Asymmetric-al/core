# D37 — Private My drafts: current UX research and complete journey

14 September 2026. The user selected **A — A private My drafts view**. This research develops that answer and supplies proposed amendments for the independent D37 review; it does not declare the detailed package ratified, create implementation authority or advance to Q38. Read alongside [the Q37 comparison](phase26-q37-private-draft-discovery.md) and [its evidence](phase26-q37-ux-research.md).

## Conclusion

Provide **one stable My drafts destination inside Support**, across the signed-in person's currently accessible inboxes in the current tenant. Selecting a row resumes the same saved external Reply in the existing conversation/composer. No separate editor, draft-to-ticket conversion, autosend, team queue, approval inbox or global Asym personal-work product is needed.

The complete value is **write → leave safely → find → resume in context → send deliberately or discard deliberately**. Discovery alone cannot compensate for unqualified private persistence, inaccurate Saved feedback, or a source/recipient change during restoration.

This is a product judgment grounded in the accepted interruption/recovery journey. Neither the frequency of ministry staff interruptions nor Asym task-completion improvement has been measured. Those are usability-validation subjects, not assumed facts.

## Proposed interface: restrained, recognizable, useful

### Stable entry and scope

- Place **My drafts** in Support's existing personal/work navigation, adjacent to the conversation-work destinations, before customizable saved views where the current shell groups these. Keep the entry available when empty to provide a predictable return path. Do not replace an existing landing choice or make D30 Reports → Overview a required entry.
- Start with **no sidebar count**. The label is enough to find writing. It avoids confusing drafts with conversations, active workload or unsaved keystrokes and does not require a count query on every shell.
- On the page, use the title **My drafts** and brief explanation **Your saved replies, across your accessible inboxes. Only you can view them.** Actual privileged privacy controls remain separate; this does not promise that infrastructure operators can never process a restricted object.
- Default to all currently accessible Support inboxes and all ordinary D3 work states. Inherited Open, assignee, priority or previous conversation-view filters must not hide drafts. Explicit current source permission, deletion, spam/deletion lifecycle rules, restriction and expiry still govern eligibility.
- Do not add New draft here. Staff begin an external reply in its actual source conversation. The destination resumes existing work.

### Rows and sorting

Use the existing qualified Support list/table pattern with one primary row action: open the draft in context. Readable rows, a clear selected state, shared Maia typography, subtle separators, and normal pointer/focus treatment are sufficient. No card wall, dashboard chart, urgency colouring, avatar crowd or animated row reordering.

A row contains currently authorized **conversation title/identifier**, short permitted requester context when useful, **inbox**, and **last saved edit**. Show a concise exception only when useful, such as **Review needed**, with the actual reason in the conversation. Actual unresolved Send recovery is separately labelled and cannot be an ordinary fresh-send draft row. Neither draft body snippets, quote text, attachments, recipient lists nor restricted CRM fields are fetched merely to render this finder. A visible participant label is conversation context, not a promise that they are the current recipient.

Sort by the last **accepted meaningful author edit**, newest first, with a stable id tie-break. Opening, reading, polling, cursor movement, an unchanged save, maintenance or source revalidation does not bump the order. A changed quote/source restriction is not a new human edit. Do not move the focused/selected row while someone is navigating; reconcile order on deliberate refresh/re-entry or another explicit list update while retaining identity and focus. No recent-only cutoff: use bounded pagination to reach every eligible row.

Do not invent a second density preference: D33's Compact/Full reading choice is about the conversation reader. Reuse the shared list's responsive baseline. Date text is localized with an accessible full timestamp/time zone; relative time never selects ordering or authorization.

### Search and filter

One field: **Find a draft**, with persistent helper **Search conversation titles**. Search the permitted conversation titles over the complete eligible personal set, not just the loaded page. It is not D22 body search and never indexes private draft content or a joined CRM profile.

One optional **Inbox** filter is enough initially when more than one eligible inbox exists. Selecting it visibly narrows scope; clearing returns to all accessible inboxes. Avoid assignee/status filters initially because they recreate the ambiguity the chosen view solves. Show active filter chips and a clear reset action. Current restrictions apply to results, suggestions, empty states, counts and pagination. Query text is sensitive user input: avoid unnecessary logs, analytics and externally shared URLs. The navigation-state mechanism can retain safe client-local query text while private content never enters a shareable link.

### Responsive and accessible behavior

- Use Core **Base UI/base-maia** via shared packages, Zinc semantic variables, existing spacing/radius/type tokens, and existing focus/motion behavior. Do not copy a vendor's palette or create an app-local component fork.
- Desktop opens the existing conversation detail/composer while retaining the list return path. Narrow screens use a single-column list then the existing reader, with a clear **Back to My drafts** control. No nested drawers around the whole reply task.
- Keyboard activation is equivalent to pointer activation. Use proper link/button/table semantics, named overflow controls, focus-visible treatment, and logical DOM order. Ordinary Enter in the editor inserts text according to the existing composer contract; list shortcuts never leak into the editor or Send.
- Resume should not force the mobile keyboard open over the recipient/context header. When returning within a still-valid mounted editor, preserve the selection and caret. Across reload/devices, guarantee correct content and source identity; do not promise exact cursor restoration unless safely supported.
- Following normal list navigation, return focus to the selected draft row and restore filter/search/scroll. If that row is gone, focus the next stable row or heading with a concise status. Never send focus to an unrelated action.
- Expose Saving/Saved/error outcomes accessibly without grabbing focus or announcing every keystroke. WCAG's [status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) explicitly supports updates without focus and warns against excessive chatter. [Focus-not-obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) and [target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) inform the sticky-header/mobile tests; shared controls must meet the actual criteria, not merely use a framework.

### Save cadence is an engineering proposal, not vendor evidence

A **750 ms quiet-period save and a 5-second maximum dirty interval** can be a reasonable prospective initial scheduler target for an online active editor, with immediate Save now and a supported-navigation flush. These numbers were proposed by the root design review, not established by the cited products, user research or measured infrastructure. The interval limits when the client attempts/coalesces a save; it is **not** a guarantee that the server acknowledges data within that time, nor a cross-device synchronization SLA.

Do not save on every selection transaction, run several concurrent saves for one draft, or write the entire list on every keystroke. A new change during an in-flight save remains dirty and follows in order against the acknowledged revision. Keep the list off the editor's per-transaction render path. The exact production workload, regional RTT and failure budget must qualify the chosen scheduler. Connectivity errors expose accurate status; reconnection retries saving under current checks but never sends.

### Empty, loading, partial and restricted states

- Initial load: render the stable shell/title and restrained row placeholders; do not flash **No drafts** before an authoritative empty result. Keep all row actions inert until their identity and authority resolve.
- Empty: **No saved replies yet. Replies you start and save will appear here.** Offer **Open conversations**. Avoid implying a compulsory draft-creation task.
- Filtered empty: **No drafts match this search.** Offer Clear search/filter. Do not say there are no drafts in other inboxes.
- List read failure: **We couldn't load your drafts. Try again.** Preserve safe navigation state. Do not label cached results current or zero. An independent known conversation remains available under its own checks.
- Partial pagination failure: keep already qualified rows with a clear retry for the remaining page; do not show a total/finished inventory claim.
- Unsupported schema: **This draft needs an app update before it can be edited.** Preserve canonical content through owner-controlled recovery; never strip nodes and resave a partial version.
- Changed source: keep independently safe text accessible when actual authorization permits; explain the specific permitted correction inside the composer. Suppress forbidden names/bodies/reasons.
- Access lost: clear unauthorized row/editor/cache representations; use the existing body-free operation recovery handle where applicable. A finder does not preserve leaked metadata as a convenience.
- Inbox disabled: inbound/outbound operational readiness is separate from source read permission. A permitted draft stays discoverable; Send states the actual transport restriction. Do not silently retarget it to another inbox.
- No internet: known current-session local work stays accurately labelled **Not saved**; no promise of general offline recovery or browser localStorage copying. Private cloud-saved drafts are only confirmed through current server reads.
- Attachment upload incomplete: draft persistence does not claim upload complete. Resume shows the real staged/uploaded state and blocks unqualified sending rather than replacing or losing the entire reply.

## Tiptap and platform implications

The finder is ordinary permission-filtered metadata; it does not need an editor instance per row, HTML preview rendering, collaborative document service, full draft-body text index, history plugin, AI writer, provider draft synchronization or another state-management library.

The one existing qualified Tiptap composer restores canonical versioned JSON after authorization. [Tiptap's core concepts](https://tiptap.dev/docs/editor/core-concepts/introduction) describe a structured schema, document state and transactions; the document can be retrieved as JSON. JSON alone does not preserve the entire application draft: recipients, source pins, managed-block dependencies, staged work and operation identity belong to the application envelope.

[Tiptap's React performance documentation](https://tiptap.dev/docs/examples/advanced/react-performance) supports isolating editor state updates and selective rendering. It does not supply autosave durability, permission isolation, revision concurrency, or authoritative Saved semantics. The dedicated D37 technical review must pin actual installed/source versions and hydration/content-check behavior before implementation. No automatic dependency upgrade follows from this design.

Core's frontend rulebook requires shared Base UI/base-maia, owner-owned privileged commands, qualified collection hooks for browser table data and TanStack Query for server read models. A personal draft projection must not simply reuse current raw outbound draft-message rows. Root/data review owns exact APIs, DB/RLS/grants/indexes and qualification evidence.

## Email Studio, CRM, privacy and source continuity

**Support owns the private human draft and finder, its source selection, explicit audience and current send admission. Email Studio/P17 owns governed canonical content and full-message preparation; P6 owns actual dispatch, retry and reconciliation.** A finder read/save/resume/discard does not publish a template, prepare a new delivery, notify a donor, create a CRM interaction or execute pending Support work.

A draft started in CRM's authorized Support detail is the same draft visible in My drafts. There is no CRM copy or synchronization system. The underlying conversation and separately authorized CRM context remain distinct. Following a link or composing for a shared address neither identifies a CRM party conclusively nor grants giving/care/location access. Reassignment never transfers a private draft to its new assignee.

D36 quotes remain inert and source-bound across restoration; D16 restrictions and D17 expiry still apply to controlled derivatives. Keeping a draft does not extend source lifetime. D35 posted-note correction state remains outside this finder; new-note working state retains its separate accepted preservation behavior. D34 presence conveys composing activity, not draft bodies, finder membership, history or ownership transfer.

## Prospective usability proof

These are required acceptance tasks, not tests already executed:

1. Begin a meaningful reply from Support, leave for an authorized CRM record, then resume from My drafts without re-entering target/recipients/text/quote/files/staged actions.
2. Start through CRM, navigate into Support, return to CRM; one draft remains with correct authority and no new interaction.
3. Find an older draft after conversation resolution, reassignment or inbox scope change; no inherited Open/assignee filter or recent-only cutoff hides permitted work.
4. Search a metadata match beyond the first page and clear a filter; no private body query/index or user/tenant count leak.
5. Observe Saved only for the current acknowledged revision; interrupt network, navigate, reconcile a lost response, and verify text remains correct.
6. Two-tab conflict/discard: stale writes and confirmation cannot overwrite/delete newer revision; a late response cannot affect another selected draft.
7. Unknown Send: resume recovery and demonstrate one admission/dispatch effect rather than a fresh send.
8. Keyboard-only and screen-reader resume, discard cancellation, loading/error feedback, and back focus work. Touch/mobile/zoom/reflow preserves visible context and usable targets without surprise keyboard or obscured focused controls.
9. Restrict a quoted source, lose CRM/source permission, merge records, change recipients, disable outbound readiness and introduce an incompatible schema. Only the affected action/data is constrained; independent safe work survives.
10. Open My drafts empty, with one row, across pages and with long/international titles, identical visible names, RTL text and multiple time zones. No mistaken recipient implication, truncation-only identity, list jumping or ambiguous time ordering.

The resulting UI should be simple because the domain obligations are handled underneath, not because they are omitted.

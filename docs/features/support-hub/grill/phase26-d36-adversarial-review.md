# D36 — New replies with deliberate, editable quotations

**Current status — full founder ratification, 14 September 2026:** D36 A and every amendment, addition, adjustment, change and final correction are fully ratified. This includes R01–R26, all23category outcomes, the complete C01–C15/ES01–ES10 prose as reconciled by F01–F03, two glossary terms,30required release groups and five operating controls. D1–D36 including D29-X01 are fully ratified. Earlier proposed/pending/no-Q37 wording is historical. The [full ratification](phase26-d36-full-ratification.md) is incorporated in full; actual runtime proof remains required and unexecuted.

**14 September 2026. Disposition: Accept with required amendments.** The founder selected **A — New reply only; add a quote when useful** and requires a seamless, simple, beautiful experience. This intent is recorded. The detailed amendment package below is proposed for ratification; D1–D35 and their amendments remain fully ratified. Q36 is answered at intent level. No Q37, formal specification, tickets or implementation is opened.

The permanent interaction is **write a reply → optionally Add quote → review in place → Send**. The existing editor is the workspace. There is no history-inclusion setting, mandatory preview dialog, second editor, forwarding product, AI extractor or transcript builder.

## Exact corrected decision

New human Support email replies begin with the new authored answer and the governed signature/footer, without automatically appended earlier email text. Staff can add a currently permitted message or selected excerpt through a visible Add quote action or the source email's Quote message action. Each deliberate insertion creates one visible, source-attributed, editable quotation in the current draft without changing the reply target, recipients, subject, signature or thread headers. Staff can trim, format, remove and undo naturally; meaning-bearing changes are honestly labelled as an edited excerpt. Source identity and disclosure dependencies remain qualified through editing, draft persistence, preparation and dispatch. Support owns source and audience authorization; Email Studio/P17 prepares the complete reviewed canonical message; P6 dispatches and reconciles its immutable material. CRM exposes this same authorized capability. The following clauses, UX, proof and evidence records constitute the complete corrected decision.

## Required decision clauses

### D36-R01 — Default, scope and alternative

Use A for new human external replies, including entry through CRM. Do not append history on editor mount, draft restore, retarget, Reply-all, signature change, preparation, retry or provider submission. Already saved deliberate content stays visible under its own current authority; the new default does not silently strip legacy drafts. B, automatically quoting the exact message being answered, is the strongest competing policy: it saves a step when question and answer must travel together, but repeats content including possible nested history. C adds further reading and disclosure burden. Neither becomes another tenant/personal setting. Staff remain responsible for an understandable answer; recipient-client grouping is not guaranteed.

### D36-R02 — Discoverable entry with no extra ceremony

Place a text-labelled **Add quote** action beside the existing reply-target/context row, with a concise accessible description identifying the selected email. It directly quotes that exact eligible email without an intermediate picker or confirmation. Each eligible email in the current original email thread also offers **Quote message** through its keyboard/touch-accessible actions. This uses the same insertion command and never means Reply, Reply-all, Forward or Change target. Avoid the ambiguous label original: it could mean first email or reply target. A missing source in a form/phone-origin first reply produces no fake email and no dead history control. A source already displayed but temporarily unavailable may expose a permitted neutral explanation and retry.

### D36-R03 — Selection is an accelerator, not a requirement

When a contiguous text selection belongs to one currently authorized source message, offer **Quote selected text** in that message's existing action path. Capture the selection before focus moves. The server verifies the exact source, representation/revision and selection against canonical content; DOM offsets, first substring match or clipboard HTML alone are insufficient. Preserve Unicode graphemes, repeated passages and paragraph boundaries. A cross-message, stale, hidden/unloaded or unmappable selection is not silently widened to the whole email. Explain the selection could not be used. Quote message plus ordinary trimming is an accessible fallback only when the whole insertion fits and is representable. Do not fetch hidden source text merely because the reader is Compact.

Provide a non-destructive **Choose excerpt** action in the existing source reader for users who need a smaller excerpt without browser text selection. In this exceptional mode, **Start here** on a permitted semantic block selects that one block; optional **Extend through here** on a later block selects a contiguous range. Show the selected range/count and **Add excerpt / Cancel**. Controls work with keyboard, touch and assistive technology. Bind exact source/revision and canonical block endpoints; reuse qualified source-selection mechanics without granting privacy/edit authority. Safe list/table structures remain indivisible where splitting would lose meaning. Load only the bounded current source page under the reader contract; no thread-wide picker, second editor or default wizard. A single indivisible block may still be unsupported/over-budget: explain that limit and preserve the answer rather than claiming every source can be quoted.

### D36-R04 — One insertion in the current editor

Reuse D18's stable insertion grammar: remember the current draft and caret, insert at a valid block boundary without replacing a selection, or fall back to the end of authored body before the managed signature when no valid caret exists. Never insert into the signature/protected footer or overwrite an answer. An outstanding insertion is bound to its original draft, operation and source, not whichever ticket opens next. If the draft's insertion anchor changed incompatibly, retain the permitted result for an explicit reapply or ask the user to invoke again; never jump into another draft. One action creates one undoable insertion, even after double-click or repeated network result. A separate deliberate action may insert another quotation: no arbitrary one-quote cap or multi-message bulk inclusion feature.

### D36-R05 — Natural editing with honest attribution

Insert the quote expanded with a restrained block border and readable ordinary type. Reuse the normal Reply editor for trimming, supported formatting and safe links. Source identity/date metadata is server-derived and cannot be edited into another speaker or source. Initially show a qualified **Excerpt from [sender], [date/time]** attribution; if meaning-bearing canonical content changes, including text/ordered content, meaningful list/table structure or link destinations, use **Edited excerpt from …** in both the composer and outgoing HTML/plain text. Only qualified presentation-only changes are exempt; qualified Undo to the exact inserted semantic excerpt may restore the original label. Compare the source-qualified canonical semantic projection, not a semantic-AI guess or plain-text-only equality. A changed hyperlink destination with identical anchor text must be marked Edited. The label is truthful provenance, not a claim that the source author approved a rewrite. Staff can write their interpretation outside the quote. Do not add a trim-only editor, change-reason form, diff viewer or approval dialog.

### D36-R06 — Visible inclusion, simple removal

Show the actual inserted content on first addition. Offer **Remove quote** on its labelled block and ordinary editor Undo; neither requires confirmation. Preserve the surrounding answer, recipients, signature and other quotations. Later collapse is optional reading convenience with the explicit label **Quoted text — included in email** and an accessible Expand control, not a tiny unexplained ellipsis. Collapsing never excludes bytes. Do not auto-collapse immediately after insertion, silently expand all older history, or move focus because a background result arrived. Expanding/collapsing is local display state, separate from D33 Compact/Full. Undo cannot restore content made unavailable by source privacy or permission changes.

### D36-R07 — Exact reviewed representation, no hidden extraction promise

Quote the eligible source's qualified safe email-body representation or verified selection, preserving meaning, block order, locale and direction. It can already contain nested quotes or signature/address text; show that actual content and let staff trim it. D33 visual folding and heuristic reply/signature detection are not extraction authority. Do not silently invent a fresh-message-only parser, remove negation/table relationships, append concealed headers, or reconstruct extra signature/recipient blocks. Nonessential unsupported styling may be normalized with a concise loss indication. If safe meaning-preserving conversion cannot be established, do not return a successful empty or truncated quote: offer the permitted readable source and the ordinary answer path. Sanitized quote projection is derived, never a new authoritative incoming message.

### D36-R08 — Text quotation does not acquire files

Initial deliberate quotation carries safe text/structure/links, not historical attachments, inline images, tracking pixels, remote resources, embedded documents, provider objects or signed storage URLs. If the selected visible content had omitted media, say **Images and attachments aren't included**; use neutral placeholders only when their metadata is permitted. Do not silently collapse an image-only source into a meaningful text quote. Staff can use the existing independently authorized attachment path. Ordinary permitted web links remain inert clickable links, validated without fetching; tokenized action/private-storage links follow their owner and are not rebroadcast as ordinary URLs. D32 preview grants no attachment/send authority. The shared required signature/logo remains separate.

### D36-R09 — Current source and disclosure eligibility

At extraction and material admission, require current authenticated staff identity, tenant membership, exact original source read authority and the existing Support authority to disclose the included content to the actual outgoing audience. Only eligible external email messages from the current selected original email thread are offered. A merged staff handling timeline is not one email transcript. Internal notes/D35 history, internal guidance, D26 private briefs and unrelated CRM/financial/care material are outside this quote action. A nonstaff email recipient does not need staff RLS access; disclosure eligibility is the existing communication boundary, not a requirement that every recipient be a Core user. Matching email, assignment, participation, Party link or possession of a source ID never grants permission.

### D36-R10 — Recipient changes get proportional review

Adding a quote never adds recipients. Later audience expansion or a material recipient identity change revalidates each quote's disclosure and invalidates prior audience review. Put **Recipients changed — review quoted text** beside the quote/recipient context, expand affected quotations and provide a single clear inline acknowledgment for the now-eligible complete audience. Reuse any D2 review covering those exact quotes/audience instead of adding a second confirmation. Pure recipient removal revalidates without a gratuitous acknowledgment unless another material source rule changed. Server denial cannot be overridden by acknowledgment. New recipients must not see source-recipient/Bcc metadata merely because it was in an email header; do not reconstruct header lists. The final audience is sealed by the existing send contract.

### D36-R11 — Reply target and topology stay stable

Quote message from an earlier eligible email adds context only. It does not retarget Reply. If staff explicitly change the D2 reply target, retain the answer and show existing quote source attribution; revalidate the quotes and invoke the existing single target/context review. Never swap their bodies for the new target. New incoming mail, assignment changes, CRM merges, Support merges/Undo, reopening or sorting cannot silently switch source, target or audience. Source identity remains the original message. If a topology change removes eligibility, withhold affected content and explain only permitted facts; do not turn a formerly valid source into a new send authority.

### D36-R12 — Fast local interaction and honest loading

Adding/removing/collapsing a quote does not publish work, create an activity or send anything. Show action feedback promptly while source qualification runs; cancelable extraction failure leaves the answer untouched. A late result after Remove, Cancel, navigation, tenant switch or newer source selection is ignored. Keep typing responsive while fetching. An in-progress quote cannot silently miss the click on Send: show **Finish adding the quote or cancel it to send**, with Cancel add available. If a quote is unavailable, Send remains blocked only for a draft that still intends to include it; explicitly remove it to send the independently valid answer. Do not make optional extraction service failure disable unrelated plain replies.

### D36-R13 — Private drafts, restore and multiple tabs

Use the accepted D4 private draft/version/save/recovery contract; create no second quote-draft table, long-lived browser body cache or offline queue. Preserve user input and quote dependencies together. Ordinary failures keep permitted unsaved text with the current save status; known saved and unknown outcomes remain distinct. Concurrent draft writes or quote results cannot silently replace a newer document. Real account/tenant changes and permission/privacy loss clear forbidden data, including editor undo buffers and pending results. Draft restoration never automatically acquires a fresher source body, missing images or new recipients. Material changes require the ordinary review; a quote source snapshot is not a live content subscription.

This action belongs to external Reply. Switching to Internal note preserves the existing separate purpose-specific draft; it does not convert a note/history into an external quote or let a pending Reply insertion land in the Note editor. Existing explicit purpose-qualified content movement retains D23/D16 source rules.

### D36-R14 — One canonical message, inert source text

Use ADR0030/D23's versioned document and code-owned Reply profile with a typed source-bound quotation or equivalent qualified schema representation. Validate untrusted original/candidate nodes, marks, attributes, positions and bounds before lossy parser normalization. Derive HTML/plain text in the shared server compiler. Source text, `{{braces}}`, @names, copied signatures and links never become executable variables, mentions, commands, protected actions or resource fetches. Source attribution identifiers are internal metadata and must not leak into public HTML attributes/URLs. Keep ordinary user-created blockquote formatting distinct; it cannot claim source provenance from a caller-written label. The current global brace-substitution serializer is not an acceptable permanent quote compiler.

### D36-R15 — Provenance survives known transformations

Bind each insertion to immutable original source identity, qualified content/representation revision, selected range or whole-body projection, sanitized snapshot identity and deriving operation. Keep source-owned restriction/expiry dependencies across the draft, canonical document, prepared material and known editor copy/cut/move/unwrap/Undo transformations. Exact internal selection/edit operations may carry lineage; arbitrary clipboard claims do not establish it. Drop a dependency only when all retained derived material from that source is proven absent. If mapping is unqualified, conservatively withhold affected dependent material under D16 rather than infer clean state from text similarity. Do not build global clipboard surveillance, substring matching or AI provenance. Independently retyped/external text cannot be guaranteed traceable; retain the honest D16 limitation rather than promising universal recall.

### D36-R16 — Database and mutation boundaries

Support/API owns the qualified extraction and draft-admission command; browser data follows approved packages/database collections or qualified server read models. Reuse source/draft/preparation records and their dependency manifest, not a second CRM or reusable quote library. Persist tenant-aware source/draft references with composite tenant keys or equivalent enforced same-tenant relationships, non-null original source identity for a managed quote, immutable source/actor fields, valid schema/revision checks and indexed reverse dependencies for restriction lookup. Server context derives tenant, real actor and validated owner/source references; caller JSON cannot assert authorship, approval or provenance. Current IDs/body evidence are not silently backfilled from email strings.

Where rows are exposed, qualify grants plus RLS for SELECT/INSERT/UPDATE/DELETE, and both pre-state USING and post-state WITH CHECK on allowed updates. Post-state validity alone does not make tenant/owner/source columns immutable; restrict those columns/commands explicitly. SELECT-policy prerequisites, policy combination, views, RPC EXECUTE grants, definer search_path and service-role bypass must be tested. Use invoker views where appropriate; privileged paths must repeat equivalent tenant/current-authority checks. No source body/history grants are added to recipients. Delete/cascade behavior must preserve required restriction/effect evidence without orphaning derived content; body/key disposal follows D16/D17. No new money column/type or giving mutation is introduced.

### D36-R17 — Privacy and retention outrank stale convenience

Apply D16/D17 to source and every controlled quotation representation before serving, materializing, decrypting, exporting or sending it. A current redaction/expiry/restriction makes old source material ineligible even when a draft, preview, cache, undo or saved quote predates the change. Preserve independently safe authored answer text when reliably separable; otherwise withhold the affected larger representation and give a truthful recovery path. Removal and Undo are not privacy restoration. Retention deadlines do not restart at quote insertion; the earliest applicable source/intent/prepared deadline continues to govern execution material. Already delivered mail and independent downloads cannot be recalled or rewritten. Body-free send/audit facts remain truthful; no claim of erasure from every external copy.

Classify each governed materialization in the finite D16 representation inventory. Tracked source-derived draft/prepared/display copies retain their restrictions; independently authored or received quoted emails are separate evidence requiring their qualified owner correction. Do not run a global matching-text erase cascade, automatically renew a linked original on native reply admission, or drop all lineage at send. Actual native admission retains D17's own clock; merely copying old text is not a new lifetime for the old source.

### D36-R18 — Atomic preparation and immutable delivery

At Send, bind the reviewed draft revision, exact target/audience and qualified source/privacy/topology generations to the existing semantic intent. Recheck them at the authoritative preparation boundary and current P6 dispatch eligibility; a stale cached capability or a Realtime hint is insufficient. The source-fence/preparation transition and source restriction/expiry ordering must serialize so two individually valid operations cannot permit unsafe material. P17 prepares the complete reviewed message, including edited-quote labels and signature/footer, and freezes its hashes/schema/presentation dependencies. P6 seals and dispatches those bytes. If material has definitely not been submitted and must change, return to qualified preparation/review under the owner contract; do not mutate frozen material. Once submission may have begun, reconcile the same intent/envelope and apply ADR0032's bounded recovery; no new key, re-render or blind second send.

### D36-R19 — CRM continuity without duplicate truth

Support reached from a CRM person/organization/relationship view uses the same original-source reader, current draft and quote command. Preserve return context and scroll without duplicating note/message bodies into CRM. A quote action creates no Party/contact, association, CRM Activity, follow-up task, ownership change or giving operation. Requester, email participant, authenticated principal, CRM person, represented organization, assignee and CRM owner stay distinct. Source quotation or a sentence about a receipt/refund is not evidence that its owning business action succeeded. Linking/unlinking/merging CRM entities changes navigation/projection only under its owner; all source and business permissions still apply. CRM remains usable without Support enabled.

### D36-R20 — Email Studio's exact role

Support chooses and authorizes the source content, target, audience and deliberate quotation action. Email Studio/P17 owns compatible structured authoring/schema, governed signature/presentation, full-message compilation and immutable preparation. P6 owns sender/connection qualification, delivery identity, provider submission/retry/reconciliation and communication evidence. They must not independently fetch a Support transcript, auto-add history, re-evaluate source text as a template, attach historical files or inject unseen source headers after review. Quoting is not Email Studio template publication, Saved Section publication, a new signature default or a campaign feature. D29 optional Contact confirmation, D15 staff attention, D34 composing awareness and D35 note editing remain unchanged.

### D36-R21 — Accessible, coherent Maia interface

Use exact base-maia, Base UI shared primitives and semantic tokens. Keep quote text as readable as the answer; use a subtle border rather than tiny pale type or a visually dominant nested card. All add/remove/expand actions have visible or accessible text and work without hover, selection gestures or keyboard shortcuts. Maintain source-to-composer focus and stable reading position; concise status announcements do not read entire quotes automatically. Preserve IME composition, screen-reader editing, bidi names/Thai/RTL text, local date formatting with accessible absolute time/timezone, keyboard/virtual-keyboard access and reduced motion. Prove WCAG2.2AA relevant criteria, including 320CSS-pixel reflow, 200% text resize and unobscured focus. Apply existing touch tokens; 44CSS-pixel touch hit areas are a product target, distinct from WCAG2.5.8's 24CSS-pixel minimum and exceptions.

### D36-R22 — Bounded work without a new platform

Extract only the selected source on demand; do not load/compile an entire thread or tenant to add one quote. Reuse the existing editor, static renderer, async read model and current source cache discipline. Publish the D23 shared Reply limits before activation: raw/normalized input bytes, nodes/depth, selection and source-reference counts, complete HTML/text/MIME bytes, compile/extraction timeout and tested concurrency. The stricter owning/provider limits win. Test zero, maximum and maximum-plus-one, using explicit units and representative Unicode/nested/table-heavy sources. No silent truncation; offer a smaller selected excerpt or remove quote while preserving the answer. No new quote-specific arbitrary cap, worker platform, vector index, live collaboration, automatic summarization or promise of unlimited/instant performance.

### D36-R23 — Compatible rollout and repair

Qualify the shared schema/compiler, source provenance/disclosure, draft persistence, restrictions and P6 fences before exposing Add quote. Additive schema deployment and server readers precede new writes. Mixed-version readers cannot drop unknown quote nodes or re-save a blank/stripped draft; provide a safe read-only incompatible state. Classify existing authored blockquotes and raw drafts truthfully; do not invent source IDs, sender attribution or proof from matching text. Unqualified drafts need a reviewed migration path, not destructive automatic cleanup. A feature kill switch can stop new insertion/preparation while keeping authorized reading and accepted-intent reconciliation. Rollback cannot re-enable restricted old material or replay sent messages; after new format writes, compatible roll-forward is the safe path.

### D36-R24 — Useful evidence without body surveillance

Record body-free technical extraction/admission/failure timings and typed reason codes, with protected correlation to source/draft version/intent only as authorized. Durable communication history records the actual prepared/sent result through existing owners, not every click or keystroke. Source dependency evidence and authorization/adverse decisions must be diagnosable without copying quoted content, recipient addresses, filenames, raw errors, signed links or editor documents into logs/analytics. Ordinary quote addition/removal creates no attention event or notification. No staff productivity score, contact-deflection metric or new dashboard. Named residual controls and thresholds are in the proof record; security and content correctness are release gates, not monitor-only risks.

### D36-R25 — Prove full user and owner outcomes

The required release groups in the proof record must pass on qualified nonproduction browser, API, actual RLS/grants, editor, compiler, privacy, migration and dispatch paths before activation. Include Support-to-CRM journeys, recipient changes, duplicate requests, concurrent drafts, source-restriction races, stale/late responses, unexpected HTML, literal tokens, nested/forwarded mail, rich/Unicode selections, mobile/keyboard/screen reader and representative recipient clients. Documentary checks and finite synthetic models cannot substitute for that proof. Record actual limits, installed versions, dataset shape, test results and remaining empirical limitations. Trace these clauses to later OpenSpec/design/tasks/tickets/implementation/release only when those stages are authorized.

### D36-R26 — Scope and evidence discipline

This is a Support reply feature within Asym. Keep all prior accepted owner contracts. Do not add a second CRM, support-wide workflow engine, public/internal guidance feature, SLA/automation/reporting suite, AI quoting, external helpdesk integration or a product-wide clipboard policy. Commercial vendor behavior is comparative evidence, not architecture authority. The new default is founder-selected; exact UX/safety amendments are product/engineering judgments proposed here. No controlled Asym ministry usability study, deployed SQL/RLS verification or provider/client deliverability proof has run for D36. Those unknowns have named release evidence, not fabricated claims that the experience is perfect or production-ready.

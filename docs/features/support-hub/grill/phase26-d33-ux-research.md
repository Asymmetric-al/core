# D33 C — Personal Compact/Full reading: independent UX research

**13 September 2026. Founder selected C, with Compact initially unless changed.** This report proposes the complete personal-setting and reading journey for the parent's adversarial synthesis. It does not independently ratify amendments, change runtime UI, install a component or certify a tested experience.

## Recommendation

Accept C with a narrow, visible **Reading: Compact / Full** control in the conversation header, beside the existing reading/search controls. Use one exclusive choice in the shared Base UI radio-menu pattern. The menu explains that changing it saves **only this person's Support reading default in this tenant**. Do not require a trip into tenant administration, invent a preferences dashboard or use a nullable toggle group for a two-value preference.

Keep three facts distinct: the saved personal default, the mode currently applied to the open conversation, and temporary expansion of individual repeated regions. Ordinary **Show quoted history**, **Show signature** where accurately identified, or a conversation-scoped expansion action changes disclosure in the current view. It must not silently save Full, alter anyone else's presentation or change what is quoted in an outgoing email.

The strongest A alternative remains one consistent Compact default with reversible expansion; it has less settings/state maintenance. C is now founder-selected and adds a defensible benefit for people who repeatedly prefer full reading. B, full content for everyone, avoids detection surprises but forces repeated content into every reader's ordinary view. The disciplined implementation of C adds one personal preference and reuses the same safe reader; it does not create two conversation systems or a layout builder.

## Proposed placement and exact control semantics

Use a small labelled **Reading: Compact** button in the conversation's reading toolbar, adjacent to Find and separate from Reply/Note, recipient and send controls. On mobile keep it reachable in the same reading area; it may move into the existing reading/overflow menu if the current mode remains plainly discoverable. Do not make a custom floating toolbar or add a global settings destination solely for one enum.

The popup uses one exclusive radio selection:

| Choice      | Description                                                                         |
| ----------- | ----------------------------------------------------------------------------------- |
| **Compact** | Fold clearly repeated email history and signatures. Expand any section when needed. |
| **Full**    | Show message text, including quoted history and signatures.                         |

A short line establishes scope before the choice: **Changing this saves your Support reading default. Only you, in [tenant name].** Selecting a different value applies the requested mode deliberately and saves it through the actual personal preference boundary. No extra confirmation modal or two-person approval belongs here. A selected radio cannot become no selection. The initial value is Compact only when absent/defaulted or in the explicitly labelled temporary-loading fallback described below; that is not an assertion that an unknown stored preference is Compact.

The trigger describes the mode currently applied to this view. Keep the saved value and pending/unknown state separately known. Ordinary expansion of sections does not relabel the default or write it. A temporary conversation-wide expansion can be labelled **Expand repeated content in this conversation**, with an inverse collapse action; it changes disclosure under the current mode rather than persisting Full. Do not overload one unlabeled switch to mean both temporary expansion and saved preference.

If the person's saved preference changes remotely while the current view is active, do not reshape the message under their pointer. Retain the active presentation; apply the latest qualified preference when the next conversation opens or after an explicit current-view choice. If the menu must show a difference, state it compactly—for example **This view uses Compact; your saved default is Full**—instead of presenting the current view as already updated. No notification or modal is needed for an ordinary remote preference change.

### Save and load states

The parent's settled proposed direction is **temporary Compact on a failed/unknown preference read**, honoring the founder's initial Compact choice without treating failure as a confirmed absent value. This is separate from source-rendering failure.

| Condition                         | Required user-visible behavior                                                                                                                                                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Confirmed no saved preference     | Apply initial Compact. No mandatory setup prompt and no automatic write merely to materialize the default.                                                                                                                                              |
| Valid saved Compact/Full          | Apply that mode when the conversation opens under the correct tenant/profile context.                                                                                                                                                                   |
| Preference load unknown or failed | Keep the actual temporary mode Compact and show **Could not load your default. This view only.** Offer explicit Retry. Do not show a false saved value, write fallback Compact or block ordinary Support work.                                          |
| Deliberate save pending           | Keep the chosen view stable; show quiet **Saving…** associated with the control. Disable conflicting duplicate actions only as necessary; reading and Close remain usable.                                                                              |
| Save confirmed                    | Briefly indicate **Saved for you**; do not emit repeated success noise for each section expanded. The preference changes no one else's view.                                                                                                            |
| Save definitely failed            | Retain the chosen presentation for this view with **Could not save your default. This view only.** Offer Retry; do not unexpectedly jump back or imply persistence.                                                                                     |
| Save response ambiguous           | Say **Could not confirm your default was saved**, not definitely Not saved. Reconcile/retry the same intended preference command under current scope; no stale automatic replay over a newer choice.                                                    |
| Late preference response          | Never overwrite a newer deliberate choice or collapse active reading. An account/tenant change invalidates the response and its scoped client state.                                                                                                    |
| Source segmentation failure       | Show full **currently permitted safe content**, not missing/blank content and not raw original HTML. This does not save Full or prove the stored preference is Full. A minimal source-safe notice can explain that compact presentation is unavailable. |

Preference failure cannot authorize unsafe content. Source access/rendering failure cannot be “fixed” by changing the personal preference. Distinguishing these cases avoids both a false saved default and a dangerous original-source escape.

## Complete staff journey

1. **First entry.** Staff open a permitted conversation from Support, search, a report or CRM. Existing tenant/source restrictions, message chronology and return context are preserved. Initial Compact requires no onboarding wizard. Recipient/audience identity, delivery state and attachment availability remain outside any repeated-body fold.
2. **Read current work.** Clearly repeated eligible content may be folded. Unknown quote structure, changed inline answers, first/only forwarded context and unique contact details remain readable. Compact is a presentation strategy, not a claim that a language model identified everything important.
3. **Inspect one region.** Use a visible, keyboard-accessible disclosure such as **Show quoted history** only when that label is accurate; use neutral **Show more message text** when the source classification cannot justify a stronger label. Expansion stays in source order and preserves focus. No change to the personal preference occurs.
4. **Read the whole current conversation.** Use the scoped expansion action when many regions need inspection. Expansion applies as permitted messages load under existing bounded pagination; it does not force every retained message or file into the network/DOM at once. Preserve any currently open region and the actual Tiptap draft.
5. **Make Full the personal default.** Open Reading, see personal/tenant scope, choose Full and receive truthful save feedback. Current presentation changes deliberately; subsequent eligible conversation openings use the saved preference. Returning to Compact uses the same two-choice control, not a different reset page or admin request.
6. **Follow a search match.** D22 Find or a result automatically reveals the exact currently permitted matching span, including within a folded region or unmounted message. This is a temporary navigation disclosure. It neither saves Full nor changes ranking/query meaning. A stale/redacted result produces source-safe unavailability, never expansion of an old snapshot.
7. **Inspect an attachment.** A D32 file card stays findable independently of a folded quote. Preview opens the same qualified viewer; closing restores the preceding conversation position, open regions, reading mode and draft. Quoted HTML image parts still obey their own current safe rendering/access rules.
8. **Return through CRM.** The same Support detail and current source basis remain authoritative. Full means full allowed message presentation in that context, not all mixed-source material from every linked person/organization. Returning to the record preserves the existing navigation contract and creates no duplicate CRM file/activity/task.
9. **Leave or switch identity.** Temporary disclosure state can survive the immediate qualified reader/CRM return journey while the same view remains active, but is not another persistent per-conversation preference library. Logout, tenant/profile switch and loss of scope clear inappropriate state and invalidate late responses. The saved enum is scoped to the authenticated person and tenant.

Do not apply this folding setting to the active reply/note editor, prepared-message approval, recipient review, D23 signature preview or D24 pending plan. Staff must inspect the actual content being prepared/sent through those existing controls. D33 also does not silently add automatic note/call-brief collapse merely because an internal note uses blockquote formatting.

## Visual, keyboard, mobile and international behavior

Use shared Maia controls and tokens, with a short readable button label rather than a mystery gear or three-dot-only disclosure. Full and Compact share typography, contrast, spacing and source headers. They differ in repeated-content disclosure, not basic accessibility or global density.

W3C's [Disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/) describes a button with expanded state and Enter/Space operation. The implementation must also preserve logical focus, screen-reader order and a predictable target after collapse; if focus is inside the region being collapsed, return it to the trigger. Do not announce entire private message bodies into a global live region. Selecting the radio menu and expanding message content are distinct accessible actions.

Preserve legitimate text direction at each message/quoted block and isolate filenames/addresses appropriately. Test long international names, mixed RTL/LTR, CJK/Thai, signatures with non-Latin separators and text zoom. Recognition must not treat an English **From:** line, `>` marker, horizontal rule or a closing phrase as sufficient proof that all following content is repeated. Email markup, visible text and Tiptap-authored semantic blocks are different source forms.

On mobile, mode/disclosure controls stay reachable with touch and screen reader; no hover-only tooltip, swipe-only reveal or tiny ellipsis. Preserve the scroll anchor when an earlier block expands or collapses. Keep the send bar and draft stable, avoid animation that moves text during keyboard navigation, and use existing reduced-motion behavior. Full mode still uses bounded rendering/loading and honest coverage—never a silent length cut presented as the complete message.

## Maintenance without a settings project

The user maintains one Compact/Full preference through the reading control. There is no inbox policy, administrator override, per-conversation stored default, personal fold-rule editor, device-specific hierarchy or configurable detector threshold. An existing personal-settings surface may link to the same preference if product navigation already calls for it; it must not become a second independently stored value or a required route merely to change reading mode.

The shared reader owner maintains conservative segmentation, safe source mapping and regression fixtures. When recognition cannot safely establish a useful compact projection, retain full currently allowed text. Failure repair belongs to the responsible source/reader path, with content-safe diagnostics; users should not need browser extensions or manual database repair. A new detector version cannot rewrite original bodies, extend retention, change outgoing quote inclusion or silently turn previously restricted material into an expandable section.

Preference storage and caches must use the actual authenticated tenant/profile partition. Local expansion does not need a durable audit per click, user analytics containing private excerpts or a new communication event. Save retries must not replace newer preferences, and remote updates must not jolt an active reader. These are small correct-state obligations of C, not justification for a generic preference engine.

## Independent disposition and evidence limits

**Accept with required amendments.** C can be complete and clean with one contextual personal preference, conservative repeated-content disclosure and honest load/save states. The principal product rule is simple: **choosing a default saves a preference; opening content only helps the person read it.**

The parent-proposed temporary Compact fallback on preference failure is recorded above; source/segmentation failure is separately full permitted display. This reconciles the founder's initial choice with truthful persistence and safe content handling.

No vendor source proves the exact preferred placement is universally optimal, and no measured Asym thread distribution or user study was available. No runtime, authenticated design-demo inspection, browser test, detector-accuracy result, load test or accessibility certification is claimed by this report. Those require implementation/release evidence. No code, formal specification, ticket, production setting or real email was changed.

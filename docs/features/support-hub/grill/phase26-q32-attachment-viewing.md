# Q32 — Viewing attachments inside Support

**13 September 2026. D1–D31 and every adopted amendment are fully founder-ratified. Q32 is unanswered.** This question selects the breadth of staff attachment viewing inside Support. Tenant/source permission, malware hygiene, retention, revocation and trustworthy file delivery are already required in every option.

## The next question

**How much attachment viewing should Support provide inside a conversation?**

For example, Maya receives a screenshot or PDF with a donor-care inquiry. She wants to inspect it, compare it with the request and continue her reply without losing her place. A spreadsheet may instead be easier to inspect in its normal application. These are illustrative cases, not measured evidence of the file mix across Asym tenants.

The next choice is whether the conversation itself offers a useful viewer, and how broad its supported document types should be. The existing metadata chips do not establish that the upload, preview or download journey is complete.

## Three actual alternatives

| Option                                                          | What staff experience                                                                                                                                                                                                                                                                            | Best reason to choose it                                                                                                                          | Cost and limitation                                                                                                                                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Preview common images and PDFs in Support (recommended)** | Deliberately open a qualified image/PDF from its message, inspect it in a focused viewer, then close it and return to the same conversation/draft. A separately qualified Download action remains available. Unsupported preview formats receive a clear explanation and Download where allowed. | Covers a useful bounded inspection route without a routine external-app detour. Preserves context and gives consistent Preview/Download meanings. | Requires a real accessible, constrained image/PDF viewing capability, type/resource qualification and complete failure/revocation handling. It will not preview every document.                         |
| **B — Show file details and offer Download**                    | See permitted filename/type/size/availability, then deliberately download an eligible file and inspect it in an application on the device. No new in-Support viewer is added.                                                                                                                    | Smallest viewing scope; people use familiar specialist applications and their full tools.                                                         | More context switching and deliberate local copies; suitable applications may not be present, especially on mobile. This still requires the complete qualified byte-access/download path.               |
| **C — Preview images, PDFs and more document formats**          | Include A, then add a broader approved set such as word-processing documents, spreadsheets or presentations through a qualified shared viewing/conversion capability. Keep Download where allowed.                                                                                               | Fewer external-app detours when non-PDF documents are a significant part of real support work.                                                    | More format/rendering/conversion fidelity, accessibility, security, dependency and operational work. No evidence yet establishes which additional formats Asym tenants need often enough to justify it. |

These are alternative current scopes, not three modes or tenant settings to implement. C is a real broader viewer option; it does not imply editing, OCR, annotations, document generation, a new file repository or a full File Manager. B is a complete qualified download journey, not permission to leave the current static chips unfinished. A does not promise every image encoding or every PDF variant renders successfully.

This choice concerns the additional attachment-inspection surface. It does not remove already-qualified inline message-image rendering or authoring, and it does not authorize automatic new attachment previews when a conversation opens.

## Single best recommendation: A

A provides the strongest balance for the demonstrated conversation-inspection task: open a relevant file, inspect it, return to the reply. Keeping the initial viewer bounded to qualified common images and PDFs avoids turning a narrow Support workflow into an office-document conversion product. B is strongest if actual work mostly requires specialist applications; C becomes stronger if research demonstrates frequent additional formats and a suitably qualified shared capability.

The intended interaction is metadata first, **Preview** and **Download** with distinct meanings, and no automatic file opening. The viewer remains tied to the original message and immutable byte version; closing it restores focus, scroll, selected conversation and unsent TipTap draft. Entering Support through CRM uses the same authorized source and return context. Essential controls must work with keyboard, touch and supported assistive technology. Exact viewer placement, supported encodings/PDF variants, resource limits and rendering technology will be decided and adversarially reviewed after this scope answer, not silently selected by this recommendation.

Preview does deliver/render bytes to the device; it is not a claim that nothing was downloaded technically or that already-delivered information can be recalled. A missing preview cannot become an automatic download. A blocked file cannot become downloadable just because the renderer failed or the filename is visible. Processing/pending hygiene, denied access, withdrawn/expired content, unsupported format and transient failure are distinct states under every option.

## Settled boundaries that remain intact

- **Original Support source and Phase29-compatible byte ownership:** Support owns the conversation attachment occurrence and its source restrictions. The shared file/access owner supplies immutable byte identity, private delivery, malware hygiene and access audit. No duplicate file database, CRM attachment copy, P29 full-product prerequisite or open-ended new storage provider is introduced.
- **Current permission before access:** D16-R15, D19-R06 and D22-R21 apply to metadata, preview, download, derived representations and return navigation. Membership/CRM association is not an access grant; no raw provider link or reusable bearer URL bypass may be introduced. The scope answer is not a vote on whether to enforce security.
- **Retention and source correction:** D16/D17 apply to originals and governed thumbnails/previews/conversions. Shared physical bytes do not transfer other domains' semantic ownership. Opening a requester-supplied receipt-like PDF does not make it an authoritative Asym receipt or complete a financial action.
- **Search remains D22:** conversation text and permitted filenames are searchable. This choice adds no attachment-content indexing, OCR or AI retrieval. A rendered document does not quietly join the search corpus.
- **Email Studio and TipTap:** reading or downloading performs no send, draft insertion, forwarding or attachment-to-template reuse. P17 governs later qualified email preparation and P6 actual delivery. TipTap remains rich-text authoring, not a binary/PDF/office-document viewer. Existing signature/saved-reply/shortcut asset rules remain independent.
- **Public/requester surfaces remain D1/D29:** this staff-viewing choice does not create a requester portal archive, external sharing links, a public file library, or attachment upload on D29's contact form. Existing actual email/owner-authorized delivery remains separately governed.

## Research and decision status

Current official documentation demonstrates materially different implementations: [Front](https://help.front.com/en/articles/2412) distinguishes preview/download and changes behavior by environment; [HubSpot](https://knowledge.hubspot.com/records/add-and-remove-attachments-from-records) provides record-context preview and separate download; [Zoho Desk](https://help.zoho.com/portal/en/kb/desk/data-administration/security-settings/articles/working-with-attachments-control) documents image inspection and separate restrictions. These inform clear actions and preserved context, not a copied vendor permission model or an assertion of universal PDF-preview support.

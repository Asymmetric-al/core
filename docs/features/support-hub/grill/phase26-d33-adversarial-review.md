# D33 — Personal Compact or Full reading

**Fully founder-ratified, 13 September 2026.** D33 C and every amendment, addition, adjustment, change and update are accepted in full, including initial Compact and exact Base UI/Maia. D1–D33 remain fully ratified. Earlier selected/proposed/pending/no-Q34 passages are preserved historical evidence and create no repeat ratification gate. The full ratification appendix below supersedes their status only; all substantive requirements and proof limits remain intact.

**Historical opening (superseded status, preserved substance):** **Disposition: Accept with required amendments.** C — a personal Compact or Full default — is selected, with **Compact as the initial default unless the person changes it**, and exact Base UI/Maia required by the founder. The complete amended contract below is proposed after review; separate full ratification is not presumed. D1–D32 remain fully ratified. No Q34 is opened.

## Corrected decision

Support offers one personal **Compact / Full reading default**, initially Compact, scoped to the authenticated staff member in the current tenant and reused by the same authorized Support reader when entered through CRM. A labelled **Reading: Compact** control beside conversation Find opens a small, single-choice menu that clearly saves a personal default. Temporary section expansion and **Expand repeated content for this conversation** never save Full. Compact folds only safely established repetition; changed, uncertain and first/only context remains visible. Full displays complete currently permitted safe email content through bounded loading. Neither changes originals, search meaning, authorization, current drafts, signatures, outgoing quotation, Email Studio preparation, delivery or CRM facts.

Use the existing shared personal-preference ownership established by D20, with one closed typed setting and trusted server mutation; do not disguise it as a CRM table/view or build a generic preference engine. Use existing `@asym/ui` Base UI primitives with exact `base-maia`, Zinc-oriented semantic tokens and Core geometry/motion. ReUI and the old shadcn mail example inform hierarchy only. No new layout/theme selector, alternate primitive base or shell replacement is added.

## Evidence and alternatives

The [evidence record](phase26-d33-evidence.md), [browser inspection](phase26-d33-browser-reference-review.md), [independent UX research](phase26-d33-ux-research.md), [data review](phase26-d33-data-review.md) and [owner review](phase26-d33-owner-review.md) separate actual source, verified external behavior, reported friction, inference and product judgment. Fresh Core/related-PR pins are in the [registry](phase26-d33-source-evidence.json). Existing source is inspected critically; it does not certify deployed conformance.

The strongest simpler alternative remains one common Compact default with temporary expansion: it avoids persisted state but makes people who routinely prefer Full change it repeatedly. The founder explicitly selects that personal convenience. Full for everyone avoids quote interpretation but creates repeated scrolling. The permanent solution adds exactly one personal enum, not preference hierarchies, tenant overrides, saved layouts or a mailbox replacement. Placing it only in distant profile settings reduces contextual discoverability; a bare toggle in the message body confuses a persistent preference with temporary inspection. The labelled reader-header menu wins this tradeoff.

Zendesk documents newly inserted inline answers behind quoted-reply expansion. Front and Help Scout document easy expansion across a conversation. These support reversible reading controls while exposing the danger of over-aggressive classification; no vendor behavior proves an optimal Asym detector. [Zendesk](https://support.zendesk.com/hc/en-us/articles/4408821456922-Adding-and-removing-the-delimiter-from-email-notifications), [Front](https://help.front.com/en/articles/2416), [Help Scout](https://docs.helpscout.com/article/11-understand-conversation-icons-and-colors).

## Exact clauses

### D33-R01 — Selected scope and initial default

Provide exactly Compact and Full as personal Support email-reading defaults. Confirmed absence of a setting means Compact without an automatic database write. Compact is about repeated content, not smaller typography, compressed spacing, hiding whole messages, changed sort order or fewer records. Full is the same safe currently permitted source without automatic repeated-region folding. Internal notes, work history, active drafts, prepared/send reviews and signature previews retain their existing complete presentation.

### D33-R02 — Personal scope and authoritative owner

Use one value per current tenant, actual authenticated staff profile and closed Support-reading key in D20's shared personal-preference capability. It follows that person across devices and the qualified Support/CRM reader within that tenant. It is not per inbox/conversation/view, a tenant setting, CRM contact field, authenticated requester preference or impersonated person's profile. Membership/Support-surface eligibility is rechecked; changing a default grants no conversation access. No administrator overrides another person's value through this control.

### D33-R03 — Location and choice semantics

Place the visible labelled control in the conversation reader's utility header beside Find, separate from Reply, Send and work/status actions. Keep it reachable without scrolling the whole conversation, including the empty reader pane for an otherwise authorized staff member. Menu title: **Your Support reading default**. Choices: **Compact — Fold repeated quoted history and signatures**; **Full — Show complete message content**. Supporting copy: **Only for you in [tenant name]. Changes save automatically.** Exactly one known/default choice is selected; unknown/error state is not displayed as a confirmed saved selection. Use shared Base UI radio-menu semantics, not an empty-capable toggle or new settings page.

### D33-R04 — Temporary disclosure versus saved default

Label folds **Show quoted history** or **Show repeated signature**, with an accessible expanded state and a corresponding Collapse control. The menu has a separate **This conversation** group with **Expand repeated content** and, when applicable, **Use my default for this conversation**. Temporary expansion never writes the preference. When the conversation-wide temporary command is used, show **Reading: Full · this conversation** and keep the menu's saved-default group accurate. Individual expansions preserve the default label; do not invent a third persisted Mixed mode. Reset clears temporary overrides for this conversation and applies the latest confirmed default, preserving the active search match and focus.

### D33-R05 — Save feedback and failure

A deliberate default choice changes this reader immediately and saves the absolute value. Show quiet accessible **Saving…**, then **Default saved** only after authoritative confirmation. A definite rejection or unknown/lost response leaves the chosen local view intact with **This view only** and accurate **Could not save** or **Could not confirm your default was saved** copy plus Retry. No modal confirmation, automatic collapse, toast-only recovery, false Saved state or permanent offline queue. Retry first reconciles current state; it never blindly overwrites a newer choice. Selecting the already-displayed value can explicitly confirm that default; simple reading never saves it.

### D33-R06 — Concurrency and idempotency

Use an absolute Compact/Full command and expected monotonic preference revision, scoped from trusted server context. A fresh deliberate save at the matching revision atomically persists/advances the revision even if the displayed value already matches; absent has virtual revision zero and first save creates a row. This fences stale writes after explicit Compact/reset. A stale repeat whose desired value is already current returns **Already current** and the current revision without a new effect; a different current value yields conflict. No toggle command, blind last-write-wins, delete-to-reset, automatic conflict rebase, durable workflow/outbox or business-event ledger is needed. Serialize local writes; preserve the newest local intent, reject stale responses/rollback and stop queued autosaves on external conflict for explicit retry. See the exact contract and race cases in the [data contract](phase26-d33-data-contract.md).

### D33-R07 — Loading, absent and unavailable are distinct

The preference does not block authorized conversation reading. Use a correctly scoped confirmed value if available; otherwise start a temporary Compact presentation. A failed/unknown read is not evidence of an absent row: show **Could not load your default. This view only.** No fallback value is automatically saved. Choices can alter local reading while persistence is unavailable; Retry must obtain current revision before any new save. A late fetch or another device's change updates the known default for future entry, not the current reader's active position/disclosures. A brief **Default updated elsewhere** notice may offer deliberate application.

### D33-R08 — Conservative source-preserving folding

Build an expendable versioned display-segment map over the same current qualified safe source; never rewrite, remove or replace original text. A received quotation marker, closing-shaped tail, sender identity or D22 search-normalized match alone is insufficient. Auto-fold only a whole structurally bounded quote region whose complete rendered meaning is established as repeated against a currently permitted earlier source in the same qualified conversation context. Any inline edit, changed/uncertain portion or first/only forwarded context stays open as a whole. Do not build word-level speculative diff folding or call an uncertain extraction the new answer.

### D33-R09 — Equality and signature boundaries

Repetition comparison preserves meaningful text, whitespace, case, links and targets, images/qualified asset identity, alternative text, tables and semantic formatting such as deletion/strikethrough. Different hrefs or changed values cannot fold as equal because displayed words match. A received/manual standalone signature without a qualified boundary remains visible. A structurally identified D23-generated historical signature may fold only when its actual historical rendered content repeats currently permitted earlier content; a current profile/template is not proof of historical equality. First/unique contact details remain visible. Quote-only/signature-only messages keep their sole substantive body visible rather than becoming an apparently empty response. No external resource fetch, cross-tenant comparison, hidden earlier source or live P17 lookup is allowed to establish repetition.

### D33-R10 — Full presentation and safe fallback

Full exposes all eligible body content within the existing bounded source-loading contract, without automatically fetching every historical body, attachment or remote image. It is not raw MIME/HTML, a second renderer with weaker rules or a redaction bypass. Segmentation uncertainty/failure shows the affected qualified full content. If full rendering itself fails, show a truthful failure and qualified text fallback when available, never blank-success or raw unsafe markup. Attachment-only messages remain valid and show their qualified attachment controls. Unsupported content is identified, not silently discarded.

### D33-R11 — Preserve context and important chrome

Sender/recipient/audience, message kind, timestamp, delivery state and qualified attachment states/actions stay outside repeat folds. Use the same chronological source order. Expanding/collapsing or choosing a default preserves the current message anchor, keyboard focus, conversation draft, recipients, staged work and return context. A collapse containing focus moves focus predictably to its disclosure trigger before content unmounts. Do not move Send under the pointer or reset another open fold through background hydration.

### D33-R12 — Complete Find and exact navigation

D22 source matching, no repeated-text ranking boost, authorization gaps and complete conversation Find remain unchanged. A search/Find result reveals and focuses/highlights its exact currently eligible source region even if folded or not mounted. Search expansion is temporary; clearing Find does not abruptly re-collapse the inspected region. A later deliberate reset may restore Compact except for the active match/focus. Browser-native find/hidden-until-found can supplement but never substitute for D22's authorized full search scope. Folding cannot create false no-matches or join text across hidden sources.

### D33-R13 — Access, source changes and lifetime

Authorize each original source/projection under current tenant and source restrictions before display, expansion, Find or cached reuse. D16/D17 restriction/expiry and current loss of access override all reading modes, render maps and delayed responses. A source generation/restriction change invalidates affected maps/overrides; a newly full fallback is still authorized first. Comparison evidence from an earlier source is not permission to read it. Merge/Undo/reopen/CRM linking preserve original identity and invalidate stale context-dependent maps; they neither reset the personal default nor resurrect removed content.

### D33-R14 — Closed preference data invariants

Require non-null tenant/profile/closed key, Compact/Full check, monotonic nonnegative virtual/positive persisted revision and trusted update time. Enforce one logical row per scope and tenant-aware membership relationship; do not create money, party linkage, content body or owner-config fields. Reset is an explicit Compact write, not row deletion/ABA. Account/tenant deletion follows the shared personal-data owner, independently of Support message retention; removing a preference cannot delete business history. Membership loss immediately blocks ordinary reads/writes, with qualified lifecycle cleanup instead of per-inbox duplicates.

### D33-R15 — Supabase and API qualification

Derive actual tenant/profile/actor/key from authenticated server context and a closed command, not caller-supplied identity or editable JWT metadata. Reuse the approved API/data-read boundary. Preserve least-privilege grants and RLS with explicit current-owner/source checks for SELECT and both UPDATE old-row/new-row semantics; immutable scope fields cannot be retargeted. Examine permissive policy combinations, invoker/definer behavior, execution grants and service-role bypass explicitly. No browser service key, generic settings-object write, CRM table-ID spoofing or assumption that RLS protects a privileged path. Actual current preference routes/helpers require additive qualification before reuse.

### D33-R16 — Cache and navigation state

Preference cache keys include tenant, real profile and closed key; body/segment keys include tenant, current original source/restriction generation and renderer/segment version. No SSR/CDN/shared-user cache or browser storage of content just to remember reading mode. Default and current-session overrides are distinct. Back from file preview/CRM in the same authorized navigation session restores safe message anchors and disclosure state; a fresh conversation entry or reload uses the confirmed default. Switching tenant/profile clears prior scope before rendering; stale responses cannot repopulate it. Reconnect/visibility return revalidates access and known defaults without surprising active-reader reshaping.

### D33-R17 — CRM and business-domain continuity

Use the same authorized Support reader and personal preference through CRM. Requester, participant, authenticated profile, Party/CRM record, represented organization, Support assignee and CRM owner remain distinct. Matching email is not identity or access proof. Preference/folding actions create no person, link, task, Activity, file copy, giving change or business completion. Link/unlink/merge/deletion permission changes are handled by existing owners; inaccessible context is not revealed in folded labels, counts or cache metadata.

### D33-R18 — Email Studio and rich-text seam

P17/Email Studio retains governed wording, signature publication and source-qualified outbound preparation; P6 retains send/outcome/reconciliation. D33 reads/saves/disclosures create none of those effects. Folding does not change outgoing quoted-body inclusion, recipients, headers, signature/legal footer, reply mode, D24 plan, attachment reuse or prepared snapshot. Drafts and send reviews remain outside D33. Use D23's qualified static history renderer; TipTap remains qualified rich-text authoring, not an editor per historical message, importer or signature-stripping mechanism. See the [full seam](phase26-d33-email-studio-integration.md).

### D33-R19 — Exact Base UI and Maia

Preserve `base-maia`, Base UI, Zinc-oriented semantic CSS variables, existing shared geometry/type/radius/spacing and Lucide conventions. Build by composing qualified `@asym/ui` Button/DropdownMenu radio items/Collapsible and existing responsive reader shell. No ReUI registry install, new dependency, copy of Radix v3 mail primitives, app-local component fork or alternate style is implied. Read current installed APIs: Core pins Base UI1.5.0 while current online documentation advertises newer versions. A public sample's `type="single"` is not authority over Core's actual array-valued ToggleGroup; choose exclusive radio semantics instead.

### D33-R20 — Accessibility, mobile and visual quality

At 320 CSS px, use the existing sequential list→conversation pattern with a labelled Reading control in the reader header; no forced desktop three-pane squeeze. Preserve 44 CSS px primary touch targets, visible focus, meaningful labels, keyboard radio/disclosure navigation, expanded state and polite status announcements. Body text retains normal Core size/line height in both modes. Reflow/text zoom/RTL/CJK/Thai/long names, display timezone and low-bandwidth reading must work. No hover-only information, colour-only status, icon-only mystery control, focusable collapsed descendants, height animation or long-motion scroll. Shared Maia tokens and existing reduced-motion rules apply.

### D33-R21 — Bounded work and performance

Do not classify the entire corpus on each toggle, query all earlier bodies without bounds or render thousands of editors. Reuse exact safe source projections, bounded progressive loading and cancellable/memoized segmentation keyed by current lineage; cache failure never creates unsafe reuse. Record finite byte/node/depth/comparison-window/time budgets in the qualified segment profile and test below/at/above them; exceeding any budget yields full permitted content, never truncation or a background retry storm. This implementation safety manifest is required before activation and does not change intake/retention limits. Proposed release fixtures and measurable interaction budgets are in P31–P33; no production capacity claim is made.

### D33-R22 — Operations and proportionate evidence

Log bounded technical outcomes, preference conflict/failure and segment fallback reasons with opaque correlations; no message text, filenames, email addresses or quoted content. A preference change is not durable Support/CRM business history and needs no per-click audit event or notification. Security/source access history remains with its existing owner. Use O01–O06's named signals, thresholds, owners and responses. A fallback that preserves full content is not automatically a privacy incident; false repetition classification or scope leakage is a material defect.

### D33-R23 — Migration and rollback

Add the closed preference subject/typed command compatibly; existing members with no row inherit Compact without mass backfill. Fence incompatible old preference writers and shared cache shapes before activation. Preserve originals before enabling segmentation; inventory any historically stripped/missing source and disclose unavailability rather than invent restoration. Deploy qualified full renderer, preference boundary, segment rules and UI together behind a narrow rollout gate. A segment kill switch shows qualified Full while retaining the saved choice; rollback never re-enables unsafe source rendering or drops new preference rows/revisions. No migration to ReUI or whole-shell redesign is required.

### D33-R24 — Required proof and traceability

Trace D33-R01–R26 and every category fix into the scoped glossary/ADR, future formal requirements/design/tasks/tickets and actual P01–P36 release evidence. Those future artifacts are not created or claimed complete in this grooming stage. Prove actual DB/grants/RLS/service commands, input classification, cache/source fencing, race/replay, renderer, browser/accessibility and end-to-end Support↔CRM journeys. Structural docs checks, a real helper probe and reference-page inspection are evidence with explicit limits, not product release tests.

### D33-R25 — No new domain or future AI authority

This adds one personal reading preference, not a whole-product display system, requester mailbox, filter builder, configurable dashboard, approval engine or AI feature. Future AI remains separately researched and permission-bound; message/attachment content remains untrusted and gives no instructions to the application. Folding is not summarization, relevance judgment, anonymization, identity proof or business verification. No customer/giving/care workflow is inferred solely from commercial helpdesk terminology.

### D33-R26 — Resolve source and document conflicts permanently

Interpret the old roadmap's quoted-reply stripping language as non-destructive derived presentation under D16/D17/D22/D23; formal compilation must remove contradictory destructive wording. Repair current blank-on-render-error, broad generic rich-text fallback and unqualified asset/network behavior under D23 before D33 activation. Extend D20's actual shared preference seam rather than inserting a dropped field into the current CRM-only helper, reusing an unscoped cache key or allowing sibling-setting replacement. Existing scaffold behaviour remains a gap, not an accepted exception.

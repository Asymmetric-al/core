# D25 independent receiving setup, data and lifecycle review

Reviewed 12 September 2026 against Core `/home/conrad/code/core-worktrees/grill-with-docs-2026-09-10`, independently verified at `7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd`. The founder selected **C — two equally presented setup paths**, keeping an existing public Support address through forwarding or creating a dedicated receiving address. This review concerns the common data/authorization/activation contract and both paths' lifecycle consequences. It preserves D1–D24 and does not implement, change DNS/provider state, inspect credentials, access a live database or send mail.

**Disposition: Accept with required amendments.** Equal plain-language entry choices are sound. Both paths must converge on the same qualified tenant-owned receiving/inbox contract while preserving their distinct external steps. The current global webhook/worker credential path, recipient-domain tenant inference and mutable route save behavior cannot be used as the permanent implementation.

## Material findings and exact proposed corrections

### DR01 — Equal setup paths must converge on one owner contract

**Concern: yes. High severity; medium likelihood.** Two UI choices can accidentally grow separate connection, routing, verification or source-ownership systems. That makes address changes and recovery inconsistent. C remains accepted with one shared final contract.

**Exact clause:** “Present Use an existing Support address and Create a dedicated Support address equally in plain language. Each creates or updates a versioned setup candidate owned by the same Support receiving/inbox boundary. The chosen external path records its actual prerequisites and evidence; it does not create a second provider adapter, inbox truth, credential store or workflow engine. Public address, receiving transport endpoint, accountable inbox/team, Sender Profile, Reply-To/continuation destination and authenticated actor are distinct. P17/P6 retains sender/preparation/delivery ownership. Website-domain or sending proof does not substitute for receiving proof.”

**Proof:** Both choices reach the same authorized inbox capability; switching paths preserves safe candidate work but invalidates incompatible proof; no duplicate inbox/provider/CRM identity or copied connection state.

### DR02 — Tenant custody comes from registered connection and receiving authority

**Concern: yes. Critical severity; medium likelihood if current heuristic survives.** A forged or merely unrelated header/domain/tag can select another tenant or wrong inbox. Global webhook credentials and default_from_email inference undermine tenant-owned receiving. C requires replacement before activation.

**Exact clause:** “Resolve incoming webhook custody from an opaque registered endpoint/connection/environment binding and the provider's qualified account/receiving identity, then validate event scope against that registration and the exact authorized receiving endpoint/domain generation. A tenant_id in message/provider metadata, recipient domain, sender domain, default From address, forwarded header or guessed alias is not tenant authority. Verify raw signature against that registration's current qualified secret/revision under bounded transition rules. Provider authentication does not make every message-derived field authoritative. Unknown/contradictory custody enters existing bounded non-public security/technical handling or qualified refusal; it never enters a guessed tenant inbox.”

**Proof:** Two tenants sharing similar domains, malicious tenant tags, spoofed From/To/Cc, provider-account mismatch, old registration callback after replacement, new receiving subdomain differing from From domain, one event addressing multiple tenants; no cross-tenant candidate/body disclosure.

### DR03 — Qualify actual receiving recipients and thread affinity

**Concern: yes. Critical severity; medium likelihood.** Visible To/Cc/Bcc and In-Reply-To are not necessarily the transport recipient or permission to append to a protected original thread. Current first-match precedence masks some contradictory routes. This narrows authoritative routing.

**Exact clause:** “Document which provider event/retrieval fields carry attested receiving/envelope context versus sender-controlled message headers. Route only from the qualified receiving identity and explicitly established endpoint mapping. Preserve visible recipient/header data as observations, not permission or tenant lookup keys. A thread/reference/token may resolve original affinity only after current D1/D2 source/participant/tenant controls; it cannot override contradictory custody or authorize historical disclosure. Compare relevant configured/saved mapping authority and treat ambiguity/conflicting applicable identities explicitly; never choose the first parent or winning array row merely to make a route.”

**Proof:** Envelope-versus-visible-recipient difference, forwarded original headers, Bcc only, two configured support addresses, repeated/copied Message-ID, spoofed known In-Reply-To, plus-token reuse and old-route reply after move. If the provider cannot supply enough evidence for one route form, that form stays unavailable with precise qualification gap rather than guessed data.

### DR04 — Exact address registration and catch-all scope are different

**Concern: yes. High severity; high likelihood with catch-all receivers.** A receiving domain may accept every local part. Registering help@ must not admit payroll@, arbitrary aliases or unrelated ministry mail into Support. A staff boolean is not broad domain-routing authorization. This narrows scope and avoids unnecessary enterprise routing.

**Exact clause:** “Default actual routing registrations to the reviewed exact public/receiving address mapping. Provider catch-all delivery is transport behavior, not consent to expose every address to the Support inbox. Any existing explicitly supported domain-default rule retains its distinct current capability, reviewed domain scope and impact; a checkbox alone never proves domain ownership. Do not infer aliases from dots/plus syntax, address similarity, organization relationship or CRM records. Domain/parent/subdomain claims remain exact. Already-routed messages retain original affinity; changing future mapping does not bulk move history.”

**Proof:** Unregistered local part, duplicate recipient/alias rule with different destination, parent versus child domain, casing/IDNA/local-part handling, shared address across inboxes, broader domain rule authored through ordinary exact-address setup; no unknown-address auto-creation.

### DR05 — Setup proof is purpose-, actor-, candidate- and generation-bound

**Concern: yes. High severity; medium likelihood.** A stale forwarded verification email or one-time address confirmation can activate a changed address, another tenant or a new actor. Receiving a code does not prove DNS, routing, staffing or end-to-end delivery. This changes activation evidence.

**Exact clause:** “Use the existing qualified owner verification/test primitives with purpose-specific proof, bound to tenant, actual authorized initiating actor, exact candidate/address/receiving-registration/connection revisions, issued/expiry state and replay protection. An old challenge cannot verify a new address/path or another principal's candidate. Verification actions require current capability and relevant step-up under the owning contract; GET/open/scanner activity is not activation. Separate address access, provider receiving/domain state, route test, outbound/continuation proof and operational coverage. A test request or clicked I changed DNS control is not successful proof. Current incompatible change invalidates only dependent evidence and preserves unrelated qualified work.”

**Proof:** Forwarded code/link, replay, expired challenge, actor/tenant switch, address edit after issuance, DNS pending/failed, callback after cancel, permission revocation before completion, accepted-but-response-lost provider test. Do not reuse a different P17 challenge merely because it sends an email; qualify identical semantics or the minimal purpose extension.

### DR06 — Pre-activation mail and forwarding confirmation need safe custody

**Concern: yes. High severity; high likelihood during real forwarding/DNS setup.** Mail can reach Resend before staff activate the inbox. Configuration confirmation mail could become a donor request, trigger D13 or expose privileged links broadly. Canceling the UI does not undo external delivery. This is required for both journeys.

**Exact clause:** “Establish the candidate's exact receiving registration and finite source custody before external configuration can deliver to it. Pre-activation arrivals enter the qualified retained setup/intake state and do not create ordinary conversations, CRM identities, requester confirmations, reply-target clocks or follower notifications. Provider forwarding verification material has a restricted purpose-owned setup view/action rather than being treated as a normal request; recognizing it requires qualified evidence, not sender-name matching. After activation, eligible real input is admitted once under D19 with original evidence/times. Cancel or Change path stops incompatible candidate authority and clearly preserves any external steps still in place; it never pretends to remove DNS/forwarding or deletes accepted source evidence.”

**Proof:** Verification mail before forwarding enabled, real requester mail before final activation, canceled candidate still receiving, changed path with old endpoint callback, expired held source, duplicate provider confirmation. Original received time, D19 expiry and D13 courtesy utility never restart merely because setup completes.

### DR07 — Activation and route replacement must be conditional and atomic locally

**Concern: yes. High severity; high likelihood if save-on-unique-conflict remains.** A create retry can redirect a live route and overwrite creator attribution. Audit failure can leave routing changed without evidence. C requires a single clear local cutover boundary.

**Exact clause:** “Create, amend candidate, verify, activate, replace, pause and retire are distinct authorized owner commands with expected candidate/active-binding/control revisions and durable semantic command identity. Duplicate create returns its original result; an existing active address conflicts unless the user deliberately reviews a Replace operation with current rights. Never reinterpret an arbitrary uniqueness error as redirect permission or rewrite created-by attribution. Final local activation atomically commits the selected qualified endpoint/inbox binding, current proof pins, required routing controls, attributable history and durable resumption obligations. A stale or failed required local component leaves the prior complete active state intact. External DNS/provider changes are not part of a fictitious database transaction.”

**Proof:** Two administrators claim same exact mapping; duplicate create after later replacement; uniqueness from unrelated constraint; lost response; source proof invalidates before commit; audit/outbox failure; missing row update; stale disable/restore. Provider mutation succeeds but local activation fails: show true external/applied and local/not-active states, reconcile original candidate rather than create another endpoint.

### DR08 — Resume eligible intake completely without marking it done early

**Concern: yes. High severity; high likelihood under current capped resume helper.** Selecting50 rows before matching can strand later eligible messages; query errors become zero; resolved-before-dispatch loses discoverability on interruption. This changes recovery primitives.

**Exact clause:** “Activation/route repair creates durable source-owned eligibility/resumption work covering the complete current qualifying source set with bounded pages/claims and stable progress. Match authorization and route predicates before pagination; distinguish Unknown/failed from zero. Do not mark source review or routing complete before its required durable admission/dispatch relationship exists. Shared executor retries the same semantic source effect against current source, address, setup and D19 gates; no ad hoc untracked callback loop. Newly arriving qualifying work is discoverable through the same path, and already admitted material is never re-admitted or retrospectively rerouted by the scan.”

**Proof:** First matching source after row50, partial batch failure, process death between review transition and enqueue, new arrivals during scan, source expiry at boundary, route replacement while queued, duplicate resume after inbox move. Expected batch size is a work bound, not a hidden total limit.

### DR09 — Replacement/reconnect preserves old effects and necessary continuation

**Concern: yes. Critical severity; medium likelihood.** Connecting a new key/account or changing public address can cause old prepared mail to use a new identity, old replies to strand, or duplicate received IDs after rotation. Blind replacement is not a safe reconnect.

**Exact clause:** “Distinguish credential revalidation/rotation for the same provider account from replacing the receiving account/domain/address or public routing identity. Qualify replacements before atomically switching new-work bindings. Preserve original provider account/received identity, source lineage and immutable already prepared outbound connection/sender/Reply-To snapshots. Same received message delivered through old/new credential generations remains one durable effect; credential revision alone never creates a new intake identity. Old callbacks and old reply destinations retain only their explicitly qualified bounded continuation/reconciliation authority; never attach delayed old mail to a new tenant or unrelated inbox. If retiring an old destination prevents continuation, show the exact consequence and require the appropriate deliberate owner transition rather than claiming all old links still work.”

**Proof:** Key rotation same account, provider account replacement, old/new webhook overlap, delayed source fetch with old provenance, public address changed while replies are outstanding, inbound duplicate across reconnect, former address reissued, old prepared provider ambiguity. No sender/profile switch or rekey to repair already admitted mail.

### DR10 — Pause/retire is scoped; external flow cannot be silently wished away

**Concern: yes. High severity; medium likelihood.** A Support inbox pause could call the tenant-wide Resend disconnect and break receipts/security mail. Pausing local routing while forwarding continues can silently lose input or accumulate indefinite content. This defines minimal lifecycle safety.

**Exact clause:** “Describe the exact scope of each stop action: setup candidate, new normal intake, a receiving address/route, or tenant provider connection. A per-inbox stop never disconnects shared tenant communication infrastructure or changes other inboxes. Source already accepted remains under finite custody/recovery and current restrictions; continued external delivery has an explicit held/refused/transition disposition with truthful operator visibility. Retire/disable does not erase history or imply external DNS/forwarding was removed. Secure revocation proceeds even if a replacement is unavailable, with the existing safe failure/repair state. Ordinary retirement preserves qualified continuation and provides clear external cleanup steps; no infinite retention or automatic take-back is inferred.”

**Proof:** Pause one inbox while receipts/other inboxes operate; forwarding still on after pause/cancel; outstanding source/prepared mail at retirement; security revocation without manager; resume cannot resurrect expired content/replay confirmation; failed external cleanup remains visible.

### DR11 — Narrow permissions and actual relational invariants close service bypasses

**Concern: yes. Critical severity; medium likelihood.** Server-only tables are protected from raw authenticated clients, but their service commands can still choose another tenant source, route or inbox. ID-only review FKs/candidate arrays do not prove tenant alignment; ctx.userId may not be profile identity. This is enforcement qualification.

**Exact clause:** “Separate integration/credential authority, receiving-address/domain administration, inbox configuration, routine route repair, D19 source review and source-content access through current Core capabilities. Setup role does not grant all restricted mail visibility or CRM permissions. Derive tenant, actual user/profile/member, initiating actor and trusted audit/approval fields server-side. Use true endpoint data types, non-null required revision/state identities and tenant-aware relationships for setup, receiving registration, route/inbox, source/review, challenge/proof, durable effect and asset references. Enforce one unambiguous current authoritative binding at its exact logical scope and immutable original attribution. Evaluate effective USING/WITH CHECK, column grants, service/BYPASSRLS, views, RPC execution/search paths, storage and restore paths together; retain the existing service-only route-table posture where appropriate.”

**Proof:** Same-ID cross-tenant source/route/review binding, invalid candidate inbox list, wrong user/profile attribution, generalstaff domain-wide route alteration, forged active/proof fields, direct service/import/REST route bypass, old permissive policies, soft-deleted source and restored permissions. No new money model or generic domain-ownership platform is required.

### DR12 — Readiness, audit and configuration metadata need truthful finite meaning

**Concern: yes. High severity; medium likelihood.** Connected, saved, domain verified, test requested and active can be confused. Success counters or notification history can leak addresses/confirmation tokens or create false CRM activity. This changes projections and observability.

**Exact clause:** “Present exact current setup/configuration state separately from underlying connection, sending, receiving, route and coverage evidence, each with its relevant generation and checked-at facts. Green cached health is not activation authority. Show the actionable failure owner without raw provider secrets or hidden cross-tenant candidate details. Configuration/challenge/test events are technical/governance evidence, not donor communication, contact interaction or human reply metrics. Retain minimized IDs, revisions, proof type/result, actual actors, timestamps and original command outcomes under the owner's finite purposes; secrets/codes/protected links/raw mail bodies do not enter general logs, URLs, exports or long-lived audit. Source/backup restore reapplies current restrictions before serving.”

**Proof:** Stale health response after address change, provider proof expired/revoked, token in logs/URL, test mail counted as new donor contact, inaccessible destination error disclosure, read-error count zero, backup restored before current route/revocation fence. Existing P17/P6 attention may expose real repair without routine setup-email campaigns.

### DR13 — Normalize setup identities deliberately and preserve existing mail services

**Concern: yes. High severity; medium likelihood.** Lowercasing every local part, parsing with a one@ helper, accepting arbitrary DNS/admin URLs, or replacing root MX can misbind identity or disrupt ministry-wide email. C does not authorize hazardous shortcuts.

**Exact clause:** “Use the shared qualified exact mailbox/domain normalization and security contract, with supported IDNA/international address behavior and separate display versus canonical values. Preserve provider-supported local-part semantics; no Gmail-style dot/plus inference or blanket lowercasing assumption creates aliases. Setup instructions target only the exact approved receiving domain/subdomain. Existing root-domain MX is never replaced as a convenience; the existing-address route retains its actual email-provider forwarding custody. Render bounded copyable DNS/mailbox values as inert data and use known-safe provider/admin destinations; never execute or fetch user-supplied setup content. Both paths preserve D1's ordinary-new-mail and reply continuity proof.”

**Proof:** Non-ASCII domains, case-sensitive/local-part distinction where supported, quoted/multiaddress/CRLF/control input, parent/subdomain confusion, unrelatedwebsite domain, competingexistingMX, falseconfirmcheckbox, externalprovider forwardingrewrite. Actual provider support constraints must be verified by the provider reviewer, not inferred from regex acceptance.

### DR14 — Safe rollout replaces heuristic custody, not only the setup screen

**Concern: yes. High severity; high likelihood because incompatible source paths exist.** A new wizard over old global handlers, default-domain inference or route save behavior does not deliver safe onboarding. Unproved legacy connections cannot be marked verified by migration. This is a mandatory activation gate.

**Exact clause:** “Inventory actual legacy inbox/route/source/provider relationships and their evidence without assuming fixtures reflect production. Add compatible owner records/constraints and explicit legacy-unqualified states; do not invent receiving proof, tenant custody, prior challenge approval or new timestamps. Qualify registration/verification/activation and worker source routing before exposing live setup; fence global/default-domain/metadata-inference and stale route writers for the enabled traffic. Migrate source identities and unique constraints without duplicate admission, preserve historical provenance and current privacy fences, and use a bounded reviewed repair path for ambiguity. Mixed versions/restore cannot route new qualified identities through old heuristics. Kill switches stop new unsafe activation while preserving existing valid intake/reconciliation; roll forward when rollback would revive a bypass.”

**Proof:** Legacyglobalprovider sources, missingaccountidentity, ambiguous shared domain, oldroute writer during newsetup, orphan registration/provider-success-localfailure, connectionrotation migration duplicate, source expired during backfill, concurrent inbox deletion, old backup restored. No source hash or schema migration is claimed executed by this review.

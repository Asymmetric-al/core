# D24 independent research: curated reply-and-work shortcuts

**Researched 12 September 2026. Disposition: Accept C with required amendments.** The founder selected curated reply-and-work shortcuts and requested complete, modern use and maintenance journeys. D1–D23 remain ratified. This document is independent research and proposed UX requirements for D24; it does not ratify the full amendment package or claim implementation. Future AI assistance is acknowledged as a separately evaluated direction, not a present feature or execution authority.

## What the choice should achieve

A well-chosen shortcut prepares both a useful answer and the routine Support changes that belong with that answer. It must still feel like writing and sending a human reply: find the shortcut, inspect the current wording and concrete changes, make any necessary adjustment, then explicitly send. Opening or selecting the shortcut changes no live work and sends nothing.

C has a real advantage over the prior A recommendation when the same answer and follow-through go together. A's action-only collection would leave staff assembling the wording separately; B's ordinary controls require repeating each choice. The founder has now chosen to handle the broader combined journey, so C should not be reduced to A or an embellished saved-reply picker. The extra staging, source revision, audience and recovery work must be completed as part of the capability.

Keep the scope proportionate. The current selection is one external human reply in one accessible conversation plus a bounded set of existing Support actions. It does not automatically add personal action libraries, note-and-work variants, action-only modes, bulk sending, branching, generic automation or arbitrary cross-domain commands. D18 already covers personal/shared wording and internal-note structures. Phase34 remains the configurable action vocabulary owner; D24 uses the qualified manual preset seam rather than creating a parallel rules language.

The known user groups are tenant staff helping donors and supporting missionaries/projects. No tenant diary study, ticket-frequency dataset or measured click/time saving was supplied. Examples below are deliberately illustrative. A shortcut cannot infer that a missionary's location is public, that a project relationship gives access, or that a donor-care request authorizes giving changes. The same narrow capability serves legitimate inboxes through their current scopes; it does not define the rest of Asym.

## A clear everyday journey

### Discover without a noisy composer

Expose one labelled **Reply shortcuts** entry in the external Reply composer and an equivalent command-palette route. Retain D18's **Saved replies** entry and explain the distinction in a compact tooltip/help sentence: saved replies insert wording; reply shortcuts also prepare work changes. Do not mix them in an undifferentiated list, make a slash command the only route, or introduce a bar of commonly used macro buttons.

The picker shows eligible current-inbox/current-purpose results with a meaningful name, a short description, language and a compact action summary. Search matches useful human metadata and the permitted shared wording through the same owner-qualified search, not hidden CRM properties or restricted source text. Favorites and recent selections are convenience projections that recheck access. An empty library is a neutral state with ordinary composing still available; authors see a contextual New shortcut action when authorized.

A preview is available without inserting anything. It shows the actual proposed wording for the current authorized context, required fill-ins, files and the intended changes. Generic maintenance previews remain synthetic. Avoid making a modal preview mandatory for every use: the prepared draft plus its pending-change summary is the normal final review surface.

### Stage one complete shortcut

Selecting **Use shortcut** copies the exact eligible Shared saved-reply revision into the current Tiptap Reply draft using D18's safe insertion semantics and creates one pending action set. Insertion defaults to the current caret; replacing an existing answer is a separate explicit operation with the same source-aware recovery/Undo as D18. An existing signature stays managed under D23 and is never inserted by the wording source.

No live status, assignment, label, reminder or communication changes at this point. The pending work appears under a quiet **With this reply** heading close to the final button. Show concrete changes rather than a vague “3 actions” badge:

```text
With this reply
Status: Open → Waiting for requester
Labels: Add Receipt question
```

This is an illustrative presentation, not a new status/label or factual tenant workflow. An equivalent missionary/project-support example may request clarification using approved general wording and an existing topic label. It must not insert locations, travel details, giving data or private project relationships merely because the current conversation is linked to such a record.

One reviewed status target is authoritative. The existing D4 After sending control and the shortcut summary must edit/show the same pending value, not contradictory competing controls. The standalone live header status remains explicitly immediate. Preserve D4's exact primary labels, including Send reply, Send and wait for requester and the other qualified state choices. The adjacent **With this reply** summary is present whenever additional shortcut changes are pending, is programmatically associated with the commit control and explains its full result. A normal-looking Send reply button must never be presented without the additional pending assignment/label effects it will admit.

### Adjust the answer and its work deliberately

Staff can edit the inserted wording and allowed pending fields without editing the shared source. Required D18 one-use fill-ins remain recognizable; missing required values block admission with a focused repair path. Values resolve from the current authorized conversation/audience, never the previously viewed profile, first related Party, coordinator or source author. A group reply cannot pick an arbitrary participant to satisfy personalization. No required fill-in is replaced with a sample value.

Pending actions can be removed or changed within the supported command vocabulary, and the visible summary updates. A label already present is explicitly **Already set**, not a hidden failure; an archived label or newly ineligible assignee is **Needs review**, not silently omitted. The exact admission contract must distinguish a safe no-op from an unavailable requested effect.

Keep one staged shortcut at a time. **Change shortcut** defaults to **Keep current reply**, explicitly stating that it preserves the existing answer and replaces the pending shortcut changes. Current wording/asset provenance remains real; the usage result records this as a modified use with retained wording, not as insertion of the new recipe's wording. The new recipe's wording must still be eligible and previewable. An optional explicit **Replace reply** follows D18 overwrite/recovery semantics while preserving the managed signature and independently existing attachments. No hidden append, body diff/merge or action stacking occurs. The action plan is one flat desired patch, not an ordered list of instructions or macro sequence.

Provide **Keep reply only** as a deliberate way to retain the current answer while removing all pending shortcut work and returning to ordinary Send reply. This is a clear exit from the combined operation, not an automatic fallback after an action failed. Staging, changing or undoing a shortcut must treat body changes and pending-plan state as one guarded draft-history operation. Undo that reverses the shortcut insertion/staging also reverses its plan; Undo of later ordinary typing does not secretly remove unrelated state. Keep-current-reply changes are also undoable coherently even when no text changed. Tiptap's native text history alone does not establish this boundary; do not infer plan state from text equality. Later edits remain preserved under truthful conflict/recovery semantics, and already admitted effects cannot be reversed through editor Undo.

### Send once, then show the actual result

The explicit combined button admits the exact reviewed human reply and permitted local changes through D4's qualified atomic boundary. Preflight rechecks current actor, audience, source/recipe versions, exact work state, targets and permission. A stale source or changed conversation calls for current review; it does not silently rebase the recipe or skip the affected action.

The successful local result is **Queued**, with the admitted local work visible in history. P6/Resend later supplies actual external evidence. No toast promises Delivered simply because the local transaction committed. An uncertain response reconciles the original command; repeated clicking cannot mint a second message or reset a later assignee/status change.

If preparation or admission fails before that boundary, no requested local work is applied and the draft stays repairable. If mail later fails or delivery is uncertain, preserve the admitted effect and D4 recovery; do not rerun the whole shortcut, silently undo valid local history or mark the underlying business action complete. UI history can summarize the shortcut once and disclose component results without duplicating communication records or flooding the timeline.

### Navigate and recover without losing meaning

Draft restoration restores the pending action set, exact source revisions, fill-in state and reviewed context alongside the answer. It must never restore text alone while dropping work or attribution. Current permissions/safety fences still apply after restoration. A brief **Review changes** state explains an affected target or audience; no global reset should be necessary.

Moving between a permitted CRM record and Support retains the same conversation, draft and return path. It does not grant additional CRM access, create a Party, update contact-history timestamps or convert a Support label into a domain claim. Sender/recipients and D23 responder identity remain under their already accepted owners. Header/composer edits affecting those facts invalidate relevant review normally.

Mobile, touch, keyboard and assistive-technology users get the same full intent, not text-only degradation. The pending summary wraps cleanly above the action bar on a narrow screen. Controls must remain accessible with a virtual keyboard open; tooltips/hover are supplementary. Keep selection/focus stable through background updates and avoid making every keystroke trigger full evaluation/compilation.

## Creation, editing and publication

### One management location, two actual owners

Use **Support settings → Reply shortcuts** for the action-preset collection, with a contextual link from its picker that preserves the conversation/draft return path. Action metadata/configuration belongs to the qualified Support/Phase34 manual-preset seam. Reusable wording remains the same Email Studio Shared asset used by D18; no new Support-owned rich-text body is stored.

The New shortcut form needs a concise internal **Name**, brief **When to use**, eligible inbox scope, an exact **Shared saved reply** selection, authored language resolution and the bounded **With this reply** action controls. Human-friendly names may contain spaces and Unicode; do not require delimiter categories, coded prefix taxonomies or no-space identifiers. Availability narrows the collection but never grants the person the underlying action or source permissions.

The content section shows its selected published revision, language, fill-in requirements and preview, with **Edit in Email Studio** or **Create shared wording** for authorized authors. Those contextual actions preserve return context and act on the existing source owner. A person with action curation but no content-publishing right can choose eligible published wording; they cannot publish it indirectly by saving a shortcut. Personal My replies cannot become Shared source simply by being referenced by a shared recipe.

Creating generic wording does not copy a real donor or missionary conversation into a reusable asset. Saving a shortcut from live use, if offered as convenience, must create an unshared candidate with safe static action references and intentionally selected generic Shared wording only; it must not harvest recipient-specific content, files or resolved fill-ins. Prefer New rather than a broad Save this conversation as shortcut command.

### Save draft, review and publish without bureaucracy

Saving a candidate and publishing a usable recipe are separate effects. A published revision stays active while a maintainer edits a candidate. Show Saving/Saved/Not saved/Conflict truthfully and preserve the candidate under current source policy. Autosave cannot silently activate revised actions.

Before publication, show a compact before/after for wording source/revision, permitted inboxes, language and effects. Synthetic evaluation covers supported start states and missing dependencies without contacting real recipients or applying real work. Verify every referenced action/target/source remains compatible; show blockers at the relevant control. Avoid an always-two-person review for ordinary recipes; apply the existing actual owner policy and separately required protected-content rules.

If a flow needs both Email Studio publication and recipe publication, it can offer one clearly labelled contextual sequence, but it must report each effect separately. “Wording published; shortcut still a draft” is a valid recoverable result. Do not clone or republish wording to retry the second stage. No publication sends mail, changes a live conversation, enrolls a workflow or invents a system-message catalog entry.

### Source drift is visible and deliberate

A usable recipe pins the exact approved Shared wording and action-definition revision. A new ordinary wording publication shows **Newer wording available** for authorized maintainers; it does not change a staged draft or silently change the recipe's next behavior. Reviewing an update compares old/new wording, fields, assets, locale and work effects, then publishes a new recipe revision. Already staged content remains pinned until an explicit valid refresh/replacement under current fences.

Distinguish ordinary staleness from unavailability. A safe older wording revision is not broken just because a newer one exists. Archived/inaccessible/unsafe content, retired actions, deleted targets and changed scope can make new use unavailable. The manager sees the specific permitted dependency requiring repair; ordinary responders see enough to recover without learning hidden inboxes, people or source contents. Safety restriction fences old staged copies/preparations according to D4/D16–D18; a library pin does not create a permanent right to use unsafe data.

Rename changes internal metadata, not content or recipient-facing identity. Duplicate makes a new candidate identity and preserves source provenance; it is not a live alias. Restore from history produces a newly reviewed candidate after current checks, never an in-place reversal of published/admitted history. Shared custody survives curator departure; role loss does not transfer custody by matching email or delete the team's valid recipe by cascade.

## Maintenance and reporting that help a team

The management list should default to usable published entries with a compact status filter covering **Draft**, **Published**, **Needs attention** and **Archived**. These labels must map to actual lifecycle versus derived dependency health rather than independent flags that can contradict each other. Search, inbox scope and a small set of useful sort choices are enough. Reuse an existing simple category pattern only when actual collection size warrants it; do not start with nested folders, mandatory tags, per-role variants or an AI recommender.

Show the curator/stewardship scope, last published change and last successful use where permitted. A details panel explains the current source dependency and revision. **Needs attention** prioritizes real blocked dependencies; **Newer wording available** remains an informational maintenance state. A zero-use entry is not automatically bad: seasonal or infrequent mission support can be legitimate. Do not auto-delete or force quarterly republication merely from low usage.

Archive should remove a recipe from new selection without requiring its broken action targets or wording to compile successfully. It preserves finite required provenance/history and does not recall messages. Safety restriction is a distinct immediate current-use fence; neither a missing manager nor a validation error may prevent stopping an unsafe recipe. Restoration rechecks eligibility and does not automatically resurrect restricted content. No empty-team workaround or destructive Delete is needed for temporary non-use.

Usage answers whether the shared collection is useful and healthy. It must distinguish **selected/staged** from **successfully admitted**, abandoned work, preflight/admission failure and later delivery outcomes. Default operational counts should be based on actual successful admissions; repeated retries do not add uses. A modified use can retain source/recipe provenance without claiming the original full recipe ran unchanged. Do not score staff by clicks, treat high usage as better care or call message admission delivery.

The reporting date axis is the actual relevant event time, not conversation creation time. A drilldown must return exactly the accessible conversation occurrences contributing to the chosen numerator/time interval, including an older conversation used today. Aggregate counts and detail rows honor the same tenant/access policy; a wider report role does not silently grant source content. Retention can remove body while preserving minimized legitimate counts/provenance under its owner; that does not authorize a second transcript archive.

[Zendesk's longer-period reporting recipe uses tags](https://support.zendesk.com/hc/en-us/articles/4408835645466-Explore-recipe-Reporting-on-macros-using-tags). That is a vendor workaround, not an Asym requirement: do not pollute D21's curated Support labels with hidden analytics tags or depend on staff retaining a label forever to preserve usage evidence. [Its usage help](https://support.zendesk.com/hc/en-us/articles/4408823377690-How-often-are-macros-used) also distinguishes a short management usage window. Core should use direct minimal recipe-use facts at the authoritative admission boundary.

## Future AI: useful preparation now, no speculative infrastructure

Current vendor AI products demonstrate different authority levels, not one universal model. [Zendesk suggested macros](https://support.zendesk.com/hc/en-us/articles/4408826078362-Applying-suggested-macros-to-tickets) can be reviewed before submission. [Zendesk auto assist](https://support.zendesk.com/hc/en-us/articles/7051314237466-Using-auto-assist-to-solve-tickets), edited 8 September 2026, also describes pre-approved automatic actions and an attachment-preview limitation. Those broader behaviors require their own risk assessment. Front's AI-assisted recipe creation is likewise a different workflow from recommending an existing approved recipe.

The most promising later first step to evaluate is permission-aware recommendation of an existing eligible curated revision, with a clear explanation and normal human review. That is a research direction, not a selected AI design. Authoring suggestions, response rewrites, choosing action targets, automated publication and unattended execution are separate capabilities with materially different authority and source risks. Do not conflate them under one AI switch.

Today, stable recipe/source revisions, typed allowed effects, current-context evaluation, explicit provenance, ordinary eligibility and exact admission already make the feature understandable and testable. Those are enough useful seams. No embeddings, transcript export, model prompts, agent account, AI score columns, unused provider adapters, background training job or auto-generated tenant recipes are needed now. A later AI decision must obey the actual shared AI owner and source-retention/retrieval policies and preserve the same action authorization; an untrusted message cannot instruct it to expand recipients or invoke a different command.

## Proof needed before activation

1. A responder finds an eligible shortcut by human wording, stages it, fixes a required fill-in, inspects both pending work and actual signature/audience, and admits it without a mandatory extra modal or unwanted work on selection.
2. A maintainer creates/edits/duplicates/publishes a recipe through its actual configuration owner while content remains in Email Studio; denied content-publication/inbox/action permissions do not become inherited from another capability.
3. Current-context switching, late response, unread/new input, changed audience, linked/merged/unlinked CRM and multiple participants cannot resolve the wrong person or return stale recipe effects.
4. Existing draft caret/selection, insertion/replacement, Undo after later edits, one-shortcut replacement, Keep reply only and Note/Reply switching preserve the correct content, signature, pending work and authority.
5. Missing fields, changed label/worker/scope/source state and concurrent state edits produce exact no-op/conflict/block outcomes; no required action is silently dropped. Native controls and shortcut pending values cannot disagree.
6. Lost save/publication/admission response and provider uncertainty preserve one durable effect; restoration retains complete intent and attribution; later retry never replays an obsolete work update or duplicates a message.
7. Safe ordinary source updates, unsafe-source restriction, archive of a broken recipe, curator departure and restore have the distinct documented results without direct database repair or content resurrection.
8. Keyboard/screen-reader/IME/touch/mobile/low-bandwidth journeys cover discovery, editing, link/variable controls, preview, save conflict, publication, use and recovery. Reflow/zoom and no hover-only action are demonstrated in the actual Core design system.
9. Reporting uses the right event/time/permission cohort, shows older conversations used in the chosen period, deduplicates retries and distinguishes selection, admitted use, modified outcome and provider delivery. It adds no hidden topic labels or transcript exports.
10. A malicious or malformed message, clipboard payload, variable value or future-looking AI hint cannot modify recipients, author identity, scope, typed effect vocabulary, personal data access or protected business authority.

These are required independent outcome tests, not claimed passes. No runtime implementation, database/RLS verification, live provider trial, browser accessibility run or measured tenant study occurred in this research. The root review must settle the exact small action catalog and its authoritative composite admission rather than leave a generic execute-anything interface.

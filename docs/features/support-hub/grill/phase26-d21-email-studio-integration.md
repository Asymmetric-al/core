# D21: Support labels and the Email Studio boundary

**Fully founder-ratified, 12 September 2026.** This addendum explicitly records the accepted D21-R03/R18/R19, D18 and D20 boundaries. It introduces no new template, role, publication flow, notification channel or implementation authority. The [independent seam review](phase26-d21-email-studio-seam-review.md) supplies the ownership matrix and source qualifications.

## Separate owners, coherent journey

Support owns the tenant label catalog and original-conversation label applications in Asym Postgres. Core's qualified IAM, API, history, configuration and shared query/UI capabilities support this owner. A curated list of labels is not an Email Studio library: their data, permissions, revisions, visibility, retention and lifecycle remain distinct.

Email Studio is the Phase17 owner of D18 reusable wording, eligible immutable content revisions, governed presentation and message preparation. Support owns the current conversation/draft, intended Reply or Note, recipient authority and source admission. Phase6 owns actual communication delivery/evidence through the tenant's qualified Resend connection.

A label maintainer, label applicator, conversation reply author, Email Studio publisher, intake reviewer and Shared-view maintainer are distinct capabilities, even when one person holds several. Catalog maintenance grants no conversation-body or CRM usage access by itself. Conversely, publication permission cannot authorize a label mutation. Applying a label never grants access to restricted source, CRM, giving or member-care information.

## Ordinary label operations

| Operation                      | Owner and outcome                                                       | Email Studio / communication boundary                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Read/search the catalog        | Current Support/IAM-authorized configuration read                       | No template rendering, recipient lookup, publication or send. Catalog text is not a new message variable.                          |
| Create/Edit/Rename             | Qualified Support configuration command; stable ID and current revision | No Saved Section, content approval queue or Email Studio visit. Rename cannot edit reusable wording or reinterpret business facts. |
| Archive/Restore                | Support lifecycle command; stops/restores future application            | Does not archive/restore a template, cancel a draft, recall mail or reapply removed conversation labels.                           |
| Add/Remove on a conversation   | Exact source-aware command with durable receipt and history             | Does not insert reply text, create a message, change recipients, follow the conversation, acknowledge intake or call Resend.       |
| Merge/Undo label union         | D10-derived projection of current original memberships                  | No synthetic label-added event, automated reply, follower notice or new P6 communication.                                          |
| D20 filtering or D21 reporting | Current authorized source query/aggregate                               | Results are not a recipient audience, scheduled digest or send instruction.                                                        |
| CRM-context label edit         | Same Support command, with independent CRM/source access                | Does not write Party tags, contact history, giving evidence or completed business actions.                                         |

**No new email template is required for labels.** Ordinary label changes remain quiet under D15. Email Studio unavailability cannot block a catalog read, label edit or otherwise valid unlabelled Support work. A label-catalog outage likewise cannot prevent an otherwise valid reply merely because the catalog is unavailable; actual reply/source/preparation eligibility still applies independently.

## Actual replies remain on the established path

From an authorized conversation, a person may insert eligible D18 wording into the current draft. It is a copy with original revision provenance; modifying it does not edit the reusable source. A human external reply uses the exact P17 ready-preparation contract, Support's guarded atomic admission and Phase6 delivery/evidence through tenant Resend. Membership in a label or search/view result never supplies recipients or sender authority. No direct mailer, provider-template mirror or global connection fallback is introduced.

An internal Note uses its existing Support validation/admission and D18 applicable validation; it remains non-deliverable and does not invoke external preparation or Resend. Label edits leave draft text, private ownership, mode, recipients and admitted intent intact. Current source/permission changes still govern whether that draft or intent can proceed.

D13's **Support request received** Email Studio template and original confirmation eligibility window remain separate. Labels cannot release D19-held intake, establish requester identity, renew that window or stand in for a human reply. Resolving Support or applying a label cannot claim that a CRM/giving task or provider delivery succeeded.

## Automation and real maintenance failures

The existing macro, bulk, import and provider writer paths must use the qualified label command or remain fenced. D18 reusable wording insertion is content-only. D21 does not activate keyword/AI classification, automatic label creation or label-triggered actions. Phase34 remains the separately governed configurable automation owner.

D21's five operational controls identify actual authorization, data, reporting, recovery or migration failures. Where such a real source obligation already qualifies for staff attention, use the existing source-owned P17/P6 local presentation contract with its safe facts and current recipient authority. Do not turn every successful label edit into a notification, borrow an unrelated event/template key or assume a default email. A local no-artifact occurrence uses `prepared.none@1`/local `available` where its owner contract qualifies it; it has no Resend call or provider delivery state. The source's repair determines completion, not merely reading attention.

## Independent retention and proof

Catalog wording, normalized comparison material, original memberships, change history, command receipts and derived queries/caches retain their own qualified finite owner purposes. Actual source bodies, current drafts, prepared messages and P6 delivery evidence have separate lifetimes. Labels neither renew D17 content retention nor preserve restricted information in an archived vocabulary. D16/actual owner restrictions apply to current and historical names, previews, indexes, exports and restored backups. Privacy disposal may remove forbidden name/comparison material while retaining only the necessary safe identity/fences.

The [ratified D21 record](phase26-d21-adversarial-review.md), [UX](phase26-d21-labels-ux.md) and [data contract](phase26-d21-data-contract.md) carry these boundaries into required proof. [Ratification validation](d21-ratification-q22-validation.json) establishes documentary preservation and consistency only; all 36 implementation proof groups remain required and unexecuted. The earlier isolated slug helper/algebra experiment is preserved as limited evidence, not live service or delivery proof.

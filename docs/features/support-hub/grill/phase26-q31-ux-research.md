# Q31 — Follow-up time choices: independent UX research

**13 September 2026. Q31 is unanswered. D1–D30 are founder-ratified.** This research concerns how staff select the time of an existing Support follow-up reminder. It does not reopen the reminder's owner, shared visibility, work-state transitions, due processing, reply-target rules or notification policy. It creates no accepted D31, formal specification, implementation or ticket.

## This is a genuine remaining choice

[D3-R07](phase26-d3-adversarial-review.md) requires the actual date, time and relevant zone to be visible before commitment, distinguishes duration from calendar expressions, handles DST ambiguity and preserves the accepted instant when a viewer changes zone. It expressly does **not** select a morning hour, default delay or personal preset hierarchy. The [D3 UX](phase26-d3-ux-blueprint.md) similarly reserves reminder preset defaults while retaining explicit date/time selection.

That leaves a real bounded choice: a common set of quick options, explicit Custom only, or reusable personal options. It is not a reason to ask again whether Support reminders should exist or whether snoozing privately hides work. It also does not reopen the separate reporting-timezone preferences resolved by D30.

The independent source-gap reviewer found inconsistent current UI literals: the detail menu contains duration choices and a Tomorrow morning expression implemented as a fixed-hour delay, while other entry paths hardcode another duration. Those are implementation observations to reconcile, not founder authority for a permanent preset list. D3's earlier source probe already demonstrated that adding 16 hours can turn Tomorrow morning into noon. Fixing such incorrect semantics is required under every option.

## Three actual options and one recommendation

| Option                                                                  | What staff would get                                                                                                                                                                                       | Strongest benefit                                                                                                                                                     | Real tradeoff                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A — A small consistent quick-choice menu, plus Custom — recommended** | Product-maintained quick choices are available through the same shared time-selection experience. Each choice shows its resolved date/time/zone; Custom always permits an exact date and time.             | Reduces repeated date entry without requiring people to configure a menu. Staff can learn one predictable interaction across qualified Support surfaces.              | The standard list cannot fit every recurring schedule. Its labels, exact time rules and zone behavior must be chosen carefully; a convenient default is not a promise of staff availability.                                   |
| **B — Choose an exact date and time each time**                         | Open the shared date/time control, enter or choose the actual follow-up time, inspect its zone and save. There are no quick presets.                                                                       | Smallest preference/configuration surface and most explicit intent. Strong where follow-up times mostly reflect specific commitments rather than recurring intervals. | Repeated routine choices take more interaction. Precision does not automatically make a calendar/time picker quicker or more accessible.                                                                                       |
| **C — Reusable personal quick choices, plus Custom**                    | Start from a useful baseline; each staff member can create and maintain their own recurring timing choices through shared preferences. Selecting one still sets the same existing shared Support reminder. | Strong for people with differing recurring work patterns; repeated unusual times no longer require rebuilding a Custom choice.                                        | Adds preference ownership, create/edit/remove/reset, zone semantics, cross-device behavior and compatibility maintenance. Personal menu preferences must never become private reminders or change other staff's pending times. |

**Recommend A.** It captures the frequent-interaction benefit demonstrated by help-desk tools while keeping the initial product simple. A's common menu means consistent product-defined choice semantics, not a new tenant-managed schedule, a universal wall-clock instant or an extra administrative preset library. Exact Custom remains the permanent escape path for a particular commitment. C is a legitimate later or alternative scope if recurring differences warrant its complete preference lifecycle; it is not inherently overengineered. B remains strongest when most times are genuinely specific and quick choices would mainly add noise.

No current Asym study proves how often a ministry schedules follow-ups, whether morning is suitable, which duration should be first, or that personal presets are necessary. Therefore this question should not silently choose the exact menu, morning hour, default delay, weekday calendar, zone precedence or a preset-count limit before the founder answers. Illustrative labels such as In one hour or Tomorrow are examples of different time semantics, not ratified values.

## Reported friction, kept separate from verified current behavior

An [Intercom community discussion begun 27 June 2022](https://community.intercom.com/helpdesk-9/can-you-change-or-add-custom-snooze-times-for-your-agents-1666) includes users reporting that a fixed 9 AM return competed with their busiest period and that repeatedly selecting Custom took too much effort. Later comments describe different working hours. These are concrete reported experiences, not a representative survey or evidence about Asym tenant frequency. Older product-limit statements in that thread are not used as current capability facts; the current official article above governs present product comparison.

The useful lesson is modest: avoid presenting a fixed morning default as universally appropriate, and retain an efficient exact alternative. The thread supports taking C seriously for recurring schedules; it does not justify adding personal presets, shift rosters, automation or calendar integration before selection.

## A's illustrative journey if selected

1. From a qualified conversation, staff open **Follow-up reminder** using the existing shared control. The same actual Support detail is used from Support or an authorized CRM record. No recipient or business-domain action changes.
2. The menu shows a short set of common choices and **Choose date and time…**. Each quick choice exposes the actual result and zone before commitment. A keyboard or command-palette entry opens that same choice, not a hidden hardcoded duration.
3. A duration and a calendar choice remain visibly different. An elapsed interval does not pretend to mean tomorrow morning; a calendar-day expression does not add a fixed number of hours. Exact values and default policy are decided after the founder selects the scope.
4. Staff select a quick choice or use Custom. D3 rejects invalid/past/ambiguous input under its current boundary, preserves input on recoverable errors and confirms the real saved instant. A changed underlying conversation/reminder is handled by the existing command/version rules.
5. The actual reminder appears in the existing detail/list and stays explainable to another authorized viewer. A different display zone may show a different wall clock but cannot change the saved instant. Editing/removing uses the same owner; no second personal reminder is created.
6. Due processing continues through D3's already-ratified Open-review lifecycle and safe recovery. Selecting a convenient menu time does not pause D14 targets, promise an external reply, send an email, create a CRM task or certify availability.

For A, ordinary staff maintain no preset library. For B, step 2 goes directly to exact date/time entry. For C, a separate personal preference journey must let people create/edit/remove/reset reusable **choice definitions**; it must never edit previously scheduled reminders. The exact ownership and preference API must be qualified rather than assumed to exist.

## Final recommendation and stage

**A is the best recommendation:** a small consistent menu that saves routine effort, always showing the actual time and retaining Custom. B is a credible precision-first minimal alternative; C is a credible recurring-schedule alternative with a real additional preference lifecycle. The question should display all three choices and their tradeoffs plainly, rather than show only the recommendation or depend on a linked document.

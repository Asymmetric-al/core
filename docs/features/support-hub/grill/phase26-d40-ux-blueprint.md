# D40 — A clear current action and a manageable future hold

**Current ratification — 15 September 2026:** The founder fully ratifies D40 B and every amendment, addition, adjustment, change, update and incorporated correction. D1–D40 and all amendments are fully ratified. The [full ratification](phase26-d40-full-ratification.md) incorporates this entire record and all supporting prose. Earlier proposed/pending/intent-only and no-Q41 wording below is historical, not a repeat approval gate. Original evidence and unexecuted-runtime limits remain unchanged.

**15 September 2026. B selected; detailed amendments proposed. D1–D39 fully ratified; no Q41.** This is the complete proposed UX contract for current unwanted correspondence and optional future-mail holding. It incorporates the selected B, existing Core decisions, [fresh primary research](phase26-d40-ux-research.md) and coordination with the data/lifecycle review. It is not a prototype, implemented UI or formal specification.

## UX01 — Four verbs with distinct consequences

“Use **Mark unwanted**, **Restore**, **Hold future email…** and **Stop holding** as distinct labelled actions. Mark unwanted and Restore apply to the current qualified admitted conversation disposition. Hold future email and Stop holding apply to a reviewed exact receiving-inbox/mailbox policy. Neither pair silently performs the other. D19's separate Release to inbox, Dismiss and Return to review continue to govern individual held inputs.”

Do not use Block person, Ban contact, Unsubscribe, Clear spam, Trust sender or Delete as synonyms. A policy hold means review before admission; it does not establish malicious identity. A legitimate complaint or difficult request cannot be marked unwanted to remove real obligations. The same meaning and controls apply in the authorized Support reader reached through CRM.

| User intention                                                         | Correct action       | What must remain independent                                                                 |
| ---------------------------------------------------------------------- | -------------------- | -------------------------------------------------------------------------------------------- |
| Stop treating this qualified non-support conversation as ordinary work | Mark unwanted        | Future-mail policy, CRM identity, subscriptions, delivery evidence and lawful source history |
| Correct that current disposition                                       | Restore              | Existing sender holds and already-held inputs                                                |
| Hold new email from a reviewed exact address in one receiving inbox    | Hold future email…   | Current conversation disposition and each existing input's recorded intake decision          |
| Stop that policy for newly received email                              | Stop holding         | Already-held inputs, other gates, current unwanted conversation and prior decisions          |
| Admit one held input after qualified review                            | D19 Release to inbox | Future sender policy and other input decisions; remaining safety gates still apply           |

## UX02 — Current action in the existing conversation menu

“Place **Mark unwanted…** in the existing conversation More actions menu, distinct from the ordinary work-state picker and visually separate from permanent disposal/security actions. It opens one compact reviewed effect summary for the exact current qualified source/work scope. Never add Unwanted as a fifth everyday work status, a freeform label convention or an action on a CRM person.”

This current Mark capability applies to qualified ordinary email-origin conversations, including their later notes and replies. It does not replace D26 staff-recorded/created-in-error correction, D12 related-work correction or D29 web/form safety and their own current source rules. Existing source kind/provenance remains intact; merely having an address or quoted email does not qualify another source as email-origin.

The summary identifies the current permitted conversation and receiving/handling context only where it affects the action. It explains:

> This correspondence will move out of ordinary Support work. Later email still follows normal intake. This action sends no email.

The primary action is **Mark unwanted**; secondary is **Cancel**. No mandatory essay, typed phrase or second generic confirmation is added. Show the actual retention consequence: **Recoverable until [current deadline]** only when that is true. If source content is already due to expire or the resulting action makes expiry immediately applicable under D17, say so before admission; there is no invented new recovery grace period. Restriction, holds and independent lawful metadata custody retain their actual meanings.

The server-qualified action must establish that real remaining work, owed correspondence, owner assistance and actionable recovery are not being buried. If that is not true, show a specific permitted explanation such as **This conversation still has work to review**, with the existing relevant review path. A checkbox saying the user accepts the risk is not a bypass. Mixed legitimate/unwanted content or originals cannot be hidden wholesale; use the data/lifecycle contract's exact eligibility and already accepted source-correction paths.

## UX03 — A calm result and persistent recovery

“After confirmed current disposition, show a quiet persistent **Unwanted** banner in the same reader with a visible **Restore** action wherever the actor has current restore authority. Keep the authorized source, notes and history readable under their existing rules. Preserve the selected record, position and drafts rather than immediately closing the pane or selecting a different conversation.”

When the entire qualified component is set aside, show the Unwanted designation in place of a misleading active Open/Waiting presentation. Preserve actual work/source history; a dormant stored work value is not a current obligation. A component containing ordinary legitimate work remains visible under the main decision's exact original-source projection.

Show **Marked unwanted. This action sends no email.** as the brief confirmed result. A toast may supplement it but cannot be the only evidence or recovery route. This wording describes the Mark action; it does not deny or recall any earlier or possibly submitted communication. Marking does not imply deletion, successful support, requester awareness or a future sender hold.

The banner's current-policy line is independently qualified. Where the applicable policy is known and visible, it says either **Future email follows normal intake** or **Future email from [address] in [receiving inbox] is held for review** with the qualified management action. Do not assert that no hold exists when that lookup failed or the actor cannot inspect that policy. A neutral **Future-mail settings unavailable** is preferable to a false assurance or hidden-scope disclosure.

## UX04 — Unwanted discovery without another work queue

“Add one built-in **Unwanted** inbox view over the same canonical admitted conversations, containing only currently all-Unwanted components with no genuine ordinary work to hide. The normal D20 work views exclude only those qualified components through an explicit projection amendment. If a component contains an ordinary original or actual owed work, it stays in ordinary work and is not presented as wholly Unwanted. Its other originals' unwanted designation/history remains accessible in the authorized combined reader and D22 search. Do not create another content store or search index.”

Ordinary authorized D22 search includes admitted unwanted source matches and labels that matching original **Unwanted**, opening the same source/current reader and applicable Restore path. It must not label the entire mixed component unwanted when another original is ordinary. This preserves accurate source and current-work meaning without requiring a separate original-management dashboard.

The view uses the existing bounded list controls and current tenant/inbox scope. Default ordering follows the latest current unwanted designation, with a stable tie-breaker; do not rewrite source message times. Show permitted subject, actual source sender, marked time and current availability where useful. Reuse existing complete server pagination and its approved 25/50 list facilities; no numerical badge, all-matches selection, new bulk effect, advanced filter builder or folder hierarchy is needed.

An authorized complete empty result says **No unwanted conversations in this inbox**. Loading, inaccessible scope, partial result and failed lookup are not that empty state. A search with no match says **No matching conversations** while retaining the query. Unknown/expired content is never represented as a fully restorable record merely because metadata remains; current source/custody determines what can be listed.

Held inputs remain in D19 **Needs review**, not Unwanted. One is admitted correspondence disposition; the other is input awaiting admission. The UI need not teach internal architecture, but its labels and navigation must preserve that distinction.

## UX05 — Restore is a current correction

“Restore uses the exact current unwanted episode and current source/work authority. It removes the applicable current designation and returns the conversation to **Open for review** under qualified current handling/coverage. It does not rewind old status, old assignments, expired reminders, source dates, original message IDs or independently admitted effects.”

Keep the visible Restore control in the banner, Unwanted view's contextual actions and the same qualified search/CRM reader. Where current preflight permits a simple restore, one explicit action is enough; the banner/action summary already explains its effect. A changed or ambiguous work plan requires the current existing review, not a blind historical replay. Confirm **Restored to Support work** only after the actual owner result; preserve the reader context.

If an applicable hold remains active, explain before/at Restore: **This restores the conversation. It does not stop holding future email.** Offer the separately authorized management path. If source bytes are expired or restricted, never promise restoration of them; show the actual permissible correction, metadata availability and reason. A missing old source cannot be replaced by a copied transcript or recreated CRM record.

## UX06 — Notes and drafts remain useful

“Current authorized Internal note creation and original-author posted-note correction remain available on an unwanted conversation for explanation and accountability, without requiring Restore. D35/D38 and current source lifetime still apply. External Reply or new Support work requires the current Restore/review path first; it cannot silently restore by sending.”

Keep the accepted private Reply and Note working states, save truth, files and revision guards intact. The Reply area says **Restore this conversation to reply**, with the qualified Restore action. Do not erase an existing Reply draft or switch its mode/recipient to make the disabled action look simple. Notes retain their clear Internal label; publishing one is not an email and does not invent completed work or renew an expired source clock.

Current Mark unwanted, Restore and policy operations preserve both dirty drafts, selection and IME. If a real navigation would destroy work, apply the existing D37/D38 leave protections to all affected working states. A draft alone is not proof of an actual Support obligation; a possibly admitted send/post requires its existing recovery and cannot be dismissed through this UI. Do not mutate Tiptap document content to store the designation or policy.

If a genuinely new actionable owner result or delivery-recovery obligation arises after a valid Mark, its qualified original/current work home returns to visible **Open for review**, ending only the now-inapplicable current exclusion. Show the actual recovery need; do not fabricate an incoming human message or erase prior classification history. Duplicate or already-reviewed results do not repeatedly reopen work. The sender-hold policy remains unchanged, and a provider-status event alone does not become a D39 human-content unread contribution.

## UX07 — Start a hold from exact existing evidence

“Offer **Hold future email…** contextually from an actual admitted inbound message's More actions or from the trusted action area of a currently authorized qualified D19-held input. Both use the same canonical input owner and independently proved single From mailbox, actual receiving inbox and current hold-management authority. A conversation-level convenience may prefill only when there is one unambiguous eligible pair; otherwise select the actual source message explicitly. Do not infer the pair from a CRM card, display name, Reply-To, quoted forward, CC/BCC list, current assignee or current handling inbox.”

A held input need not be released into ordinary Support merely to create a future hold. Starting the policy changes neither that input's existing gate/decision nor its safety, classification, availability or Release requirements. Review access alone does not grant policy authority. Keep the trusted action outside untrusted message content; it grants no new right to preview an unsafe body or attachment. A manual/web-only record, arbitrary entered address or quoted message is not a qualified canonical incoming-email occurrence.

The future action does not require misclassifying all current work as unwanted. A mixed conversation may retain genuine work while a separately authorized exact future policy is reviewed from an eligible source; ordinary policy eligibility still applies. Mark unwanted never launches or checks the hold automatically.

A move matters. If input reached receiving inbox A and the conversation is now handled in B, the hold review names A and checks A's current authority. It cannot silently act on B or all inboxes. Merged originals with different sender/inbox pairs need one exact source selection. Missing, ambiguous or unsupported sender/receiver evidence leaves this action unavailable with a useful explanation, rather than a guessed address or arbitrary input form.

## UX08 — One small, explicit future-policy review

“The hold review presents an immutable exact address/inbox pair and current receiver/review readiness. It uses one primary **Start holding** action and Cancel. No preselected block checkbox, domain/IP matching, alias expansion, multi-inbox scope, freeform rule builder or combined Mark-and-hold command is introduced.”

Suggested compact content:

```text
Hold future email

From                 offers@example.org
Receiving inbox      Donor care

New email from this address to this inbox will wait in Needs review.
This does not block a person or change this conversation.
This does not change email already in Asym.

Cancel                                      Start holding
```

The address/inbox above are synthetic copy examples. Use the real currently authorized pair; never use a fallback inbox name. Match policy is the source owner's exact canonical mailbox semantics. Do not collapse plus aliases or broaden to a domain merely to increase hit rate. Clearly state that a mailbox can carry legitimate email and that held messages use the inbox's existing review team. This is a fixed hold policy, not a trust-verification claim.

Hold readiness requires the qualified receiving owner and viable D19 review coverage. If it is unavailable, retain current work and explain **Future-mail holding is not ready for this inbox** with the existing permitted setup/repair path. Do not expose hidden team names or use a saved-rule row as proof the receiver enforces it. The action becomes **Starting…** while pending and **Holding future email** only after the owner confirms effective admission. Original received timestamps never decide a retroactive batch sweep.

## UX09 — Explain what happens to future input

“A matching input is held under the policy snapshot established by the receiving owner at its first accepted intake boundary. It joins the existing D19 Needs review journey with the additional plain reason **Sender hold** and the currently permitted exact address/inbox explanation. No second review queue, new Support conversation, automatic deletion or hidden auto-release is created.”

An input first accepted before a hold became effective keeps its recorded decision even if downstream processing is delayed. Stopping later likewise does not rewrite already accepted input. User-facing copy refers to newly received email in Asym after activation; the technical contract binds the actual trusted first intake boundary, never the provider's earlier receipt time, sender's Date header or an arbitrary worker execution time.

D19 reviewers still see all relevant gates and source availability. **Release to [inbox]** decides that one input under current authority; it does not stop the hold. **Dismiss** does not strengthen it. Technical Retry is not Release. Any ordinary automatic confirmation after release still requires D13's existing eligibility and deadline; neither this policy nor this UI invents an email notice.

If held material reveals a false positive, the reviewer can make the appropriate one-item decision and, if separately authorized, navigate to the hold's management. A qualified held input may also launch the independent exact future-hold review without first being released, as UX07 specifies. Stopping or starting future holding is not bundled with Release. Staff without future-policy authority retain the existing qualified escalation path; they do not need a new omnipotent reviewer role.

## UX10 — A durable, small management location

“Manage existing holds in **Support settings → [receiving inbox] → Sender holds**, within the qualified inbox receiving settings. The inbox context is always explicit. Default to **Active**, with a second **Stopped** view for retained policy history/correction. Exact sender/inbox pairs are read-only; change of target is a new reviewed policy operation from qualified input, not editing an existing identity.”

Each row shows the full mailbox, current policy state, relevant created/stopped time and permitted attribution. Do not show message bodies, sensitive source titles, live private content, noisy hit counters or a staff productivity score. Provide exact-mailbox search and the existing bounded server pagination, without advanced filters, aggregate badges, imports, arbitrary Add-rule forms or a global contact blocklist. An original conversation need not remain readable or retained to stop a currently authorized policy: policy control has its own declared minimal custody and capability.

Active rows offer **Stop holding**. Stopped rows may offer **Hold again…**, which reviews the same pair under current source/policy capability, route readiness and review coverage. It creates/admits the current qualified generation; it does not resurrect an old token or repeat a previously stopped command. If current required proof is no longer available, explain the necessary current qualification rather than blindly activating an old row. Stopping remains independently usable where authorized.

Empty copy: **No active sender holds in this inbox** after complete successful Active loading; **No stopped sender holds** for Stopped. Keep inbox context and help visible. A failure says **Could not load sender holds** with Retry, not a reassuring empty list. Existing stop/history data is limited by its actual finite control-purpose retention, not an indefinite promise to display every previous policy.

## UX11 — Stop holding is easy and does one thing

“Stop holding is a contextual conditional action for the exact active policy generation shown. Its visible helper says **New email received by Asym will follow normal intake. Messages already held still need review.** No second generic confirmation is necessary when the exact current pair and effect are already presented. Never combine Stop with Release all, Restore conversation, trust/allowlist, or a provider change.”

Show **Stopping…** while pending. Only confirmed success shows **Stopped holding [address] in [inbox]**. In Active view, remove/move the row after the actual result while preserving selection and keyboard focus predictably; it remains discoverable in Stopped while retained. A supplemental result may link to Needs review, under current permission, but does not imply a visible pending count if that population is unknown.

There is no blind Undo that reactivates a stopped policy. **Hold again…** remains the clear requalification path. If another authorized operator changed the policy, show **This hold changed. Review its current state**, preserving the intended action without overwriting it under a new revision. Ordinary safety/review gates may still hold future email after this particular rule stops; the UI says normal intake, not guaranteed delivery to work.

## UX12 — Role and capability clarity

“Current disposition, restore, source read, D19 review, hold management and control-history read are separately authorized operations under existing Core owners. One person's assignment, generic staff status, reviewer membership, CRM relation or permission to read the old message does not automatically grant future-policy control.”

A qualified ordinary worker may mark/restore current unwanted correspondence while lacking hold controls. The page stays useful; do not make future-policy setup a condition of current cleanup. Where revealing the action's existence is permitted, a disabled control can explain **You don’t have permission to change this inbox’s sender holds** and retain the established authorized help/request path. Do not imply that a generic administrator label grants the capability or expose hidden inbox/team/actor names through denial messages.

The sender itself receives no notice, account ban or subscription change. Managers see only authorized policy/source data, not private drafts or another person's read history. Holding an address does not grant visibility into all CRM people who use it or all other inboxes receiving from it.

## UX13 — Truthful pending, failure and changing context

| Situation                                                        | Visible behavior                                                                                                                      | Required boundary                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Known current action success                                     | Confirm its exact current/policy effect and retain the persistent inverse control where valid.                                        | Never infer success from a clicked button or an optimistic moved row.                                |
| Definite rejection                                               | Retain the applicable confirmed state and useful error/retry path.                                                                    | No partial fake current disposition or effective-policy promise.                                     |
| Lost response/unknown outcome                                    | **Could not confirm the change. Checking current state…** then truthful resolved/unconfirmed state.                                   | Reconcile the original operation under current authority; no fresh key or blind new-revision replay. |
| New message/work/topology during current review                  | **Conversation changed. Review the latest activity.**                                                                                 | No burying newly legitimate work or extending a prior review to new originals.                       |
| Sender/receiving route/current policy changes during hold review | Recheck and show the actual current pair/effect before a new deliberate admission.                                                    | No default-inbox fallback, scope expansion or expired generation replay.                             |
| Coverage disappears                                              | Existing D19 coverage exception/repair is visible to its owner; stop control remains independently qualified.                         | Offboarding/security revocation is never blocked, and intake is not silently dropped.                |
| Source content expires                                           | Source displays the true current availability and permitted correction; policy management remains accessible under its own authority. | No new recovery grace, body recreation or resetting D17 clocks.                                      |
| Hold cannot be loaded/enforced                                   | Show unavailable/unknown readiness and qualified repair.                                                                              | A stored policy is not proof the intake receiver is enforcing it; no silent passthrough assurance.   |

Keep ordinary authorized reading, note work, CRM navigation and independently valid owner operations useful during a policy lookup outage. Actual current-disposition/send/hold commands still require their own guards. Error repair cannot stop all source privacy/retention enforcement or bypass a held-input safety gate. No setting refresh replaces a draft or discards changes to unrelated inbox settings.

## UX14 — Coherent, accessible and restrained visual design

“Use the existing shared Base UI menus, dialogs, tabs, buttons and form relationships with exact **base-maia** tokens. Keep the message content and exact address/inbox identity visually primary. Use a quiet Unwanted banner and clearly labelled policy status; no red person badge, alarm animation, unread count, dense admin dashboard or custom control toolkit.”

Current action and future hold previews are short: readable title, exact scope, concrete consequence, primary action, Cancel. Long addresses and international inbox names wrap or expose their full accessible value; do not truncate away the part that distinguishes the target. Use direction-isolated mailbox text where needed and preserve Unicode/IDN source semantics without pretending visual similarity proves equality.

Menus/actions are reachable by keyboard and touch, have descriptive accessible names, visible focus, proper Escape and predictable focus return. Use Core's touch targets of at least 44 CSS px, readable type at 320 CSS px/400% zoom and no hover-only action. Pending/confirmed/error messages are visible and politely announced without repeating on every background event. Keep the same route and essential actions usable on mobile; avoid horizontal page scrolling or controls hidden behind the keyboard.

Do not animate list reordering or auto-scroll to a different record after an action. When a row legitimately leaves the current view, keep its reader/result accessible until the user navigates, with predictable focus to the retained result or nearest stable control. Existing reduced-motion behavior remains. No browser prototype or automated check alone establishes this quality; actual intended-staff and AT journeys are required.

## UX15 — CRM, Email Studio and reporting stay coherent

“The same authorized Support source and disposition appear when reached through CRM, with return navigation preserved. No CRM Party, organization, relationship, contactability, donation, receipt, consent, login or care record is deleted, blocked, copied or updated through these controls. The mailbox/inbox policy belongs to receiving, not to CRM identity.”

Current action, Restore, Start/Stop holding and management create no Email Studio draft/template/prepared message, P6 dispatch/provider spam report, tracking pixel, automatic response, unsubscribe or survey purpose. They do not read/archive P17 notifications or claim D39 viewing. Actual note posting, legitimate newly admitted input and allowed typed attention retain their already accepted effects. D28 spam/auto-only exclusions and genuine handling facts remain: a mark/restore cycle cannot fabricate a successful resolution, reroll feedback, erase past delivery or improve historical metrics.

An active sender hold is an inbound per-occurrence gate, not a global outbound or contactability suppression. A valid D19 release returns that specific admitted input to its normal purpose rules without stopping the policy or creating a fresh deadline/opportunity. D13 still requires its original confirmation qualification; D28 still requires actual eligible completed work, and Release itself is no feedback trigger. Other legitimate conversations keep their independently authorized communication behavior. Current Unwanted designation still disqualifies its own definitely-unsubmitted optional effects through their actual source/P17/P6 fences; already or possibly submitted evidence remains immutable.

## Required complete journeys and acceptance evidence

These are future runtime/participant proofs for root's consolidated matrix, not tests claimed run now.

1. An eligible single unwanted conversation can be marked in one compact review, remains identifiable/readable under current source rules, leaves default work views, appears in Unwanted and authorized ordinary search, and can be restored from the persistent same-source path. Only all-Unwanted components enter the Unwanted view; a mixed component remains ordinary while its matching unwanted original is accurately labelled in authorized search/history. No hold or email occurs.
2. Restore changes only the qualified current episode; an active applicable policy stays active and the UI explains this. Old expiry, assignments, reminders, P6 evidence and CRM facts are not replayed.
3. Both draft modes survive all current/policy commands. Internal note and original-author correction remain usable when allowed; external Reply/new work follows explicit Restore/current review. Pending admitted operations cannot be discarded as drafts.
4. Hold creation starts from one actual admitted inbound message or currently authorized qualified D19-held input, with independent exact From/receiving-inbox and policy rights. A held input is not first released merely to expose the action and all its current gates remain unchanged. A moved A→B conversation reviews receiving A; merged/multiple sender pairs cannot silently pick a latest/default/CRM-derived target. Ambiguous/missing input evidence and manual/web/quoted substitutes fail honestly.
5. Mark unwanted never enables a hold. Start holding has one exact address/inbox review, current policy authority, viable existing review coverage and no domain/alias/all-inbox broadening.
6. Inputs first accepted before versus after start/stop retain the correct intake policy snapshot despite delayed processing, retries or stale email Date headers. No retroactive batch changes occur.
7. Future matches use D19 Needs review with Sender hold plus other actual gates. One Release does not stop the policy; Stop does not release or undismiss the backlog. Other safety gates still govern.
8. Sender holds management works independently of reading/retaining the original conversation. Active/Stopped, full mailbox, existing search/pagination, Stop and requalified Hold again have truthful empty/error/unknown states and no private-content or hidden-count leak.
9. Stale concurrent Start/Stop/Restore/disposition responses cannot reverse newer decisions, expand source scope or create duplicates. Pending/unknown outcomes reconcile the original effect; requalification never silently reapplies an old intent.
10. Incoming legitimate work, mixed originals, existing assistance, owed replies and delivery recovery cannot be buried by current disposition. Qualified later admitted input returns appropriate current handling without requiring requester resubmission or inventing another original message. In A+B, newly ordinary B makes the component ordinary and removes it from the all-Unwanted view; A's remaining classification/history is preserved and labelled at original scope. Newly actionable owner/delivery recovery after Mark similarly exposes the affected current work, without a fake incoming message, changed future hold or provider-status-generated D39 unread.
11. Permission changes, receiving-route changes, reviewer offboarding, source expiry, holds and old-generation replay preserve current authority and useful recovery. No fallback Donor Care name or saved default is treated as target authority.
12. Current/held/policy/reporting views remain source-authorized and coherent through CRM; no Party/account block, unsubscribe, P17 engagement sweep, provider spam feedback or D28 eligibility invention occurs. With an active sender hold, a legitimately released input and a separate existing legitimate conversation retain their normal independently qualified communication eligibility; no mailbox-wide outbound suppression is inferred.
13. Real keyboard, touch, screen-reader, IME, mobile, zoom/reflow, long-address and mixed-script tasks complete with clear scope, focus and result states. Low-bandwidth failures preserve drafts and never falsely show an effective hold or restored content.
14. Intended staff distinguish the four verbs and D19 Release without coaching: set aside one item, optionally hold future mail, correct each independently, and recover a legitimate held input. Test ordinary workers and appropriately authorized policy/review staff rather than assuming everyone has the same permissions.

The resulting journey is complete but small: one current classification with a persistent Restore path, one optional exact future hold with independent Stop management, and the existing review queue. All added UX clauses remain proposed for founder ratification; no Q41, product implementation, new package or external mutation is introduced.

# D38 — Research for automatic private new-note drafts

**14 September 2026. A selected; detailed amendments proposed.** The founder selected **A — Automatically save note drafts in My drafts**. D1–D37 and their amendments remain ratified. This research deepens the selected new-note journey; no Q39 is advanced. It is exploratory grooming, not implementation or a formal specification. [The UX blueprint](phase26-d38-ux-blueprint.md) contains the proposed interaction contract.

## Decision and strongest alternative

**Accept with required amendments.** Save unfinished new Internal notes privately and make them discoverable alongside private Reply drafts. One existing destination and editor can serve both purposes, but a private note draft must never become a posted note, a colleague-visible draft or an external reply merely through autosave, mode switching or restoration.

B, deliberate Save note draft, is the strongest alternative: it gives explicit control over durable retention, but creates a different save habit from D37 replies and an extra recurring step. C, current-session work only, is a legitimate smaller-scope option but cannot complete dependable cross-session resumption. A is the founder's selected product direction. Vendor evidence supports useful patterns and failure tests; it does not establish universal demand, guaranteed time savings or the superiority of every autosave implementation.

## Repository authority and real remaining work

[D37](phase26-d37-full-ratification.md) already accepts private source/author-scoped durable Reply drafts, truthful bounded autosave, atomic bundles, same-person concurrency control, exact-operation recovery, a small metadata finder and safe discard/Send consumption. Its R01 explicitly excluded durable new Note work from that first scope. D38 changes that exclusion for new unposted notes only; the rest is reused where purpose-appropriate. It does not reopen D37's accepted Reply timing, list limits or privacy.

[D2-R04](phase26-d2-adversarial-review.md#d2-r04--stable-drafts-and-intentional-edits) and [D23-R15–R16](phase26-d23-adversarial-review.md#d23-r15--variables-mentions-and-editor-actions-stay-inert-until-authorized) require separate Reply/Note working content, inert draft scaffolds, careful restoration and current authorization. [D35](phase26-d35-full-ratification.md) still keeps corrections to already posted notes local and deliberately saved with visible history. [D15](phase26-d15-adversarial-review.md#d15-r06--finite-useful-activity-set) distinguishes actual human note publication from optional-follow information and independently governed direct attention; saving a private draft is none of those source events.

[D10-R14](phase26-d10-adversarial-review.md#d10-r14--where-later-messages-notes-and-changes-remain) owns where general notes attach in merged work. A draft slot is not permission to disregard the current reviewed posting destination. A source/topology change must not quietly publish to another original conversation or broaden the note's visible audience. Preserve private work, explain a changed destination using permitted context, and review that actual change before Add note. Do not introduce a source-selector workflow for every ordinary note.

The current Note-rejecting Save draft path and conversation-change resets described in the [Q38 source review](phase26-q38-gap-review.md) are implementation gaps. The existing Tiptap editor is not a qualified Note persistence store. [D37's actual installed-library observations](phase26-d37-tiptap-contract.md) already demonstrate silent whole-document replacement and permissive normalization hazards. Reuse those findings and independently qualify the new purpose; do not rerun an editor showcase and call it a data-integrity proof.

## Feedback and failure evidence

In an [Intercom community discussion](https://community.intercom.com/helpdesk-9/abandon-message-creation-7161), users in May 2024 and March 2025 reported difficulty interrupting work and resorting to a separate writing app. A March 11, 2025 support reply described a then-current Reply draft disappearing after switching to and posting a Note. This is dated self-selected feedback and historical support guidance, not a fresh test or proof of the current product. It motivates a real Asym test: post a Note with a separate Reply draft and prove the latter remains unchanged.

No interviewed ministry cohort or measured rate of long internal notes is established. The legitimate fixture is an interruption in already authorized Support note authoring; do not infer donor-care diaries, member-care notebooks, staff monitoring, a records approval system or organization-wide knowledge capture.

## Technical and accessibility patterns

[Tiptap 3.x persistence](https://tiptap.dev/docs/editor/core-concepts/persistence) supports structured JSON through an application backend. That is compatible with the existing canonical Core editor and source-owned private persistence. Its localStorage and simple setContent examples are illustrative, not secure draft recovery recipes. No Tiptap Comments, Collaboration, Version History, document server or new vendor is necessary for an ordinary Support Internal note. The node/mark profile and immutable source metadata must be qualified before rendering writable content; ordinary editor normalization cannot silently erase protected meaning.

[W3C's Status Messages guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) explains exposing important status changes to assistive technology without moving focus. Apply that to meaningful Saved/Not saved/error results while avoiding repeated announcements for each keystroke. It is explanatory WCAG 2.2 guidance, not proof the future implementation conforms. Core's existing Base UI/base-maia and D37 reflow/zoom/IME/touch tests remain the concrete implementation baseline.

No new timing is proposed. D38 should reuse D37's accepted qualified 750ms quiet/5-second checkpoint-attempt contract, including one in-flight operation per draft controller, IME/network exceptions, current-version acknowledgment and honest file state. These values are accepted Asym engineering targets; neither a vendor standard nor a promise of durable storage within five seconds.

## Synthesis

First qualify the distinct note purpose, private save and deliberate post transaction using D37's sound shared mechanisms. Then update the existing composer and finder with clear kind/private-state copy, preserving the complete candidate and exact source through navigation. Finally verify actual two-purpose, multiple-tab, source-change, attachment, denied-access, mobile/IME and publication/attention journeys. Security, current-source integrity, correct publication and no loss of the other draft are release gates, not monitor-only concerns.

No item is deferred to an undefined monitor in this research. Operational signals belong in the consolidated D38 proof/operations contract with explicit owners, thresholds and responses. The chosen A is recorded; the detailed amendments are proposed for ratification after the full independent review. No Q39 is advanced.

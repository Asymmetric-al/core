# D34 — Show when a teammate is composing

**Fully founder-ratified, 13 September 2026.** D34 A and every amendment, addition, adjustment, change and update are accepted in full. D1–D34 remain fully ratified. Earlier selected/proposed/pending/no-Q35 passages are historical and create no repeat ratification gate. This status supersedes those passages while preserving all substantive requirements, source evidence and unexecuted release obligations.

**Historical opening (superseded status, preserved substance):** **13 September 2026 · Disposition: Accept with required amendments.** The founder selected **A — Show when a teammate is composing**. D1–D33 and their full amendments remain ratified. This complete D34 amendment package is proposed for ratification; selecting A is not represented as prior approval of every new numeric or technical detail. This is exploratory grooming evidence, not a formal OpenSpec, implementation or release approval. No Q35 is opened.

Keep the feature small: a quiet, current, authorized **“Maya Chen is composing”** cue. A staff member can notice another person's recent drafting activity before duplicating effort. Their draft remains private. The cue does not reserve the conversation, guarantee someone will respond, disable Send or replace the existing authoritative check for newer committed work.

The permanent implementation uses Core's authenticated API and Supabase database for a short-lived technical session, Supabase private Broadcast for expendable refresh hints, and a fresh authorized HTTP snapshot for names. It adds no generic presence platform, shared editor, activity history, notification workflow or second CRM. **Accuracy means bounded and honestly described freshness, not a promise of zero network delay.**

## Exact corrected decision

The following clauses are the complete proposed answer to record. Supporting data, UX and proof documents explain them without creating competing requirements.

### R01 — Meaning and scope

Support SHALL show recent deliberate composition by currently eligible authenticated staff in the current authorized Support reader. It SHALL NOT show passive viewers, last-seen times, draft previews, cursor positions, work duration or typing statistics. The cue is advisory; absence is never an all-clear or evidence that nobody else is working. It grants no assignment, ownership, coverage, Follow, read receipt, permission, lock or completion meaning.

### R02 — Small, discoverable presentation

Use one stable utility line immediately above the active Reply/Note composer, also visible at that location before composition starts. Preserve D33 Reading/Find and the current reader shell. Show “Maya Chen is composing”; both Reply and Note use the same neutral wording. Show at most two qualified names inline, then an additional qualified count; narrow layouts may show “3 teammates composing” with an accessible current-name disclosure. Two is a layout limit, not a query limit. No passive roster, takeover, modal, sound, toast per event, red alarm styling or pulsing typing dots is added.

### R03 — Identity and complete projection

Names come from Core's authorized internal staff identity owner, not a browser payload, email address, requester, CRM contact, assignee or public email signature. Omit the current authenticated profile and deduplicate eligible sessions by real profile only after source and identity qualification. One tab stopping does not clear another eligible active tab. Use existing authorized same-name disambiguation, international names and bidi isolation. A hidden person's existence SHALL NOT leak through a generic label, count or overflow. If a bounded query cannot establish the complete permitted set, show unavailable rather than a partial exact count.

### R04 — Genuine input, private content

Qualifying activity includes actual input/deletion, paste, dictation, IME composition and deliberate composer operations such as formatting, link edits, recipient changes, saved-wording/signature insertion, attachment selection/removal and undo/redo. Focus, selection, reading, opening, draft restoration, prefetch, autosave, remote/programmatic updates and background AI generation alone do not qualify. Detect intent through the existing editor/controls without serializing or transmitting text, keys, preedit candidates, recipients, attachment identities, body length or Reply/Note mode for awareness.

### R05 — Eligibility and endings

Publishing requires the current visible, active document, a qualified mounted composer and current compose authority for its exact source. Moving focus within composer controls does not stop it. Stop promptly on idle, explicit discard/cancel, successful reply/note admission, source/tenant/session exit, access loss, hidden document or inactive application window. Opening a modal file preview suspends composition while preserving the draft. Stop is best effort; server expiry is mandatory. Return, reconnect, focus restoration or a restored draft alone SHALL NOT resume composing; a fresh deliberate composition action is required.

### R06 — One explicit initial timing profile

Send a leading start or explicit stop promptly, without a trailing typing debounce. Ordinary combined control/snapshot refresh runs every **5 seconds** while locally composing or displaying a current peer cue, otherwise every **10 seconds** while the reader is eligible. Use a **15-second** composing liveness bound, a **30-second** observer lease and a **30-second** local inactivity cutoff. A renewal cannot refresh the fresh-input frontier unless new qualifying input occurred. Server expiry is the minimum of liveness, last accepted fresh input plus 30 seconds, session/observer expiry and source fences. Controls carry a fixed **15-second** server-issued freshness window; snapshots have at most **12 seconds** of display trust from request start. These are initial Asym engineering choices, not vendor standards. The detailed clock and ambiguity semantics in the data contract govern boundary cases.

### R07 — Trusted session and source

Core SHALL derive tenant, authenticated profile, actual auth-session binding and current source authority on the server. A profile or client-provided session ID is not an auth-session proof. The current auth owner must expose a qualified real-session binding; legacy Support email-to-agent matching is insufficient. Each server-issued reader instance binds its exact tab/context, original-source affinity and current topology/restriction generation. Reader permission and composition permission are distinct checks. Source changes cannot silently retarget an existing instance.

### R08 — Narrow database boundary

Use one regular application-schema technical session record per issued reader instance with separate observer and composition deadlines. Keep trusted scope immutable; use actual Core key types, same-tenant relationships, finite time/sequence constraints, unique opaque instance/topic identity, indexed current-source/expiry lookup and bounded cleanup. No custom object is added to Supabase's managed `realtime` schema. Revoke direct client lease DML/read and raw-row change publication; only closed authorized commands and projections may access it. Verify actual grants, effective RLS USING/WITH CHECK, function execution/search path, storage non-use and every privileged service path. No caller may set actor, tenant, deadline, approval, authority or audit attribution.

### R09 — Ordering and freshness

All instance controls use one monotonic sequence and server-issued generation with fixed not-after time. Accepted updates atomically compare current instance, scope, sequence, generation and deadline. Already-issued windows cannot be extended by a different heartbeat. Lower/duplicate controls do not renew state. Expired, closed or unknown instances cannot be recreated by update/upsert, even after cleanup. A new qualified instance receives a new ID. Coalesce desired state; never queue or replay offline typing. An old Start, Renew or Stop cannot revive or clear a newer episode.

### R10 — Ambiguous control outcomes

Use one serialized control stream per reader instance. A transport timeout is not proof the server rejected the last command. On ambiguous mutation outcome, stop writes and perform a current-authorized reconciliation read of that instance's last accepted sequence, window and state; this read renews no deadline and never rotates the window. Do not replay/relabel the old body or invent the next generation. A still-live episode may renew within its original input deadline; expired/stopped state requires new qualifying input. An expired control window or unknown/closed instance requires fresh registration, without reviving the old instance. Flush a pending current Stop promptly after reconciliation. No permanent command receipt journal or new signing infrastructure is required for this expendable signal.

### R11 — Current authorization through every surface

Qualify both producer and observer against exact current source affinity, membership, identity visibility and source topology at control, snapshot and fanout admission. A continuing merged root, CRM link, shared inbox, assignment or matching email is not sufficient. Do not expose composition on inaccessible constituent B to someone permitted only constituent A. Known context/access changes invalidate local state; new reads and newly admitted wakes deny obsolete audiences. An already authorized in-flight hint or already seen screen cannot be recalled; do not claim instant erasure across disconnected devices.

### R12 — Private hints, not client Presence authority

Only the server may publish a versioned, content-free `refresh` hint to each current eligible observer's opaque private topic. The hint contains no name, actor/source ID, count, mode or activity reason. Clients cannot publish Broadcast or Presence on these topics. Verify topic ownership and private receive policies. Supabase's cached join authorization is defense in depth, not current per-event authorization. No shared conversation-room wake is used as a shortcut around current recipient selection.

### R13 — Fresh snapshots and conservative expiry

Names and deadlines come only from an authenticated current snapshot with trusted server as-of, absolute expiry and matching instance/context/request generation. Subscribe then reconcile to close the missed-event race; coalesce wakes with single-flight reads and one dirty follow-up when needed. Expiry SHALL be anchored conservatively to monotonic request start, not response arrival or mutable browser wall time. Reject late/mismatched responses and clear expired claims locally without waiting for another event. Resume from hidden/sleep/bfcache/reconnect requires fresh authorization before reuse.

### R14 — Honest availability

A current, complete empty snapshot renders no composer cue; it does not say nobody is working. While the broker is unavailable but current HTTP snapshots remain healthy, keep valid cues with quiet “Live updates delayed” text. After snapshot trust expires or current state cannot be qualified, remove names and show “Live composing cues unavailable.” Do not show transient startup warnings on every mount. These states never prevent independently qualified reading, draft editing or sending. Permission denial removes the inaccessible surface under its owning contract, not as a mere transport error.

### R15 — React and editor lifecycle

Use a small Support client island, stable human-intent listeners, non-render refs for counters/timers and the existing qualified browser Supabase client through the shared database adapter. Own/refcount exact channels; never remove all application channels or disconnect another feature. Topic/private configuration is immutable per generation. Strict Mode, remount and account changes must clean up only owned resources. Awareness SHALL NOT add draft serialization, replace the editor, use every Tiptap transaction as input, force full-thread renders or call router refresh per heartbeat. Preserve selection, IME, undo, autosave and D33 local reading state.

### R16 — Core Next/Vercel boundary

Business handlers belong in `packages/api`, transport adapters in `packages/database`, presentation in the shared supported UI path and app routes remain thin. Snapshots and control responses are private/no-store current request results, excluded from shared Next/CDN/persisted query caches and prefetch state. Follow Core's actual Cache Components and runtime-map rules; do not add prohibited route-segment exports. Qualify supported deployed runtime, actual Vercel/Supabase regions and installed versions. Supabase is chosen to reuse the current stack; current Vercel WebSocket support is not falsely declared impossible.

### R17 — CRM continuity

CRM opens the same authorized Support reader and composing capability, preserving the current source and return context. Staff working there and in Support can see each other's eligible cue without a duplicate ticket, person, draft or CRM Activity. Requester, participant, authenticated staff, contact, represented organization, assignee and record owner remain distinct. Composition performs no CRM/financial/member-care mutation. Access and consequences of contact, receipt, refund, recurring-gift or other business actions stay with their owning domains; resolution does not prove those actions completed.

### R18 — Email Studio and delivery seam

P17 Email Studio owns governed reusable wording, signature/authoring policy and immutable outbound preparation; P6 owns actual dispatch, retry, provider outcome and communication evidence. D34 owns only expiring composition metadata. Deliberate use of existing wording/signature tools may count as local activity, but D34 never reads or creates their content/preparation, shares drafts, alters recipients/quotes/signatures/attachments or emits mail. Ending a cue on reply admission is not a Sent claim. Notes keep their internal audience; no public or donor-visible typing event is introduced.

### R19 — Real collision protection remains mandatory

Two colleagues may compose at once. The existing D1/D4 current-source/reviewed-version admission check must still independently handle simultaneous sends and newly committed work, preserve both private drafts and require the appropriate updated review. Presence, absence, availability failure or a forged self-report SHALL NOT bypass or block this authority. Durable send idempotency is tied to the actual business effect and is not replaced by D34's ephemeral sequence.

### R20 — Privacy and future AI

Retain no viewing/composition history, per-person productivity metric or content-bearing awareness log. Technical observer rows are not publicly browsable viewing records. Future AI may not retrieve D34 as donor/CRM evidence, receive private draft text through it, impersonate a human composer or take actions based on it. Existing explicit AI/authoring permissions remain separate. Minimize technical logs, exports, traces and backups under actual platform retention; short row expiry does not promise deletion from every backup.

### R21 — Bounded work and capacity

Apply the exact initial per-instance, source-context and response budgets in the runtime contract. Coalesce unchanged renewals and transition wakes; no wake per keystroke or ordinary unchanged keepalive. Do not fan out to hidden/unqualified readers, preload every conversation or silently truncate a permitted set. Above a declared limit, degrade awareness honestly and preserve source work. Measure database writes, authorization, fanout, snapshot round trips and UI paint; provider message quotas and a local benchmark do not establish Core capacity.

### R22 — Expendable transport and repair

Commit each accepted lease transition atomically, then attempt bounded awaited hint dispatch. Catch HTTP rejection/timeout; a broker 202 is admission, not delivery or display. Hint failure cannot roll back the lease, fail a draft save or block a reply. Bounded snapshot reconciliation and expiry repair lost/duplicate/out-of-order hints. No durable outbox, notification engine, workflow retry backlog, database trigger on each heartbeat or new WebSocket host is added solely for this cue.

### R23 — Maintenance and cleanup

The Support capability owner maintains cue behavior; the shared identity/database owners qualify security and session handling; platform operations owns broker/runtime health. Use the existing scheduler for bounded expiry cleanup, targeting physical removal within **15 minutes after observer expiry/closure**, without a history table or cascading business deletion. Expired rows never appear even if cleanup is late. Restore, mixed versions and disablement must honor absolute expiry and current authorization, and force fresh instances rather than revive activity.

### R24 — Rollout and recovery

Deploy additive app-schema/command/policy support before the guarded client. Explicitly enable only qualified tenants after real proof. Keep new-client/old-server and old-client/new-server failure benign and cue-only. A versioned protocol rejects unsupported envelopes. A server-side kill switch stops registration, publication and snapshots; notify connected qualified clients where possible and otherwise expire visible state. Roll back code with harmless finite rows retained; do not destructively remove schema while live versions use it. Never compensate by weakening access or widening room topics.

### R25 — Accessible stable UI

Use actual shared Base UI/base-maia and semantic Zinc/theme tokens, readable contrast and typography. Names/status are text, not color/hover-only signals. The current-name disclosure works with keyboard, touch, zoom and RTL/LTR content. Use polite coalesced aggregate announcements for meaningful changes; never announce renewals or keystrokes. Preserve composer/send position, focus, scroll and reduced-motion behavior. Test mobile/IME/assistive technology and low-bandwidth conditions; visual polish is not assumed from a component library.

### R26 — Observation without surveillance

Record content-free request outcomes, timing, stale-control rejection, broker failure, freshness loss, admission-limit rejection and cleanup lag under existing restricted operational telemetry. Do not log names, draft fields, raw topic tokens or a timeline of specific staff activity. Business and security audit records retain their own meaning; D34 creates no fake communication audit. Each monitored risk SHALL have the named signal, threshold, owner and response in the proof/operations ledger; privacy/authorization failure is a release blocker, not a metric tolerated until enough incidents accumulate.

### R27 — Falsifiable release evidence

The proof ledger's positive/negative/source/tenant/RLS/session/concurrency/input/lifecycle/failure/load/migration/accessibility and Support-to-CRM groups are required before activation. The healthy connected start and explicit-stop target is **p95 at most 1,000 milliseconds**, measured input-to-peer-paint in the declared region/network/load fixture. Report cold/reconnect/degraded results separately. Source inspections, mocked SDK calls and the reference model do not pass actual database, browser or deployment proof. Trace each clause through the feature ADR, glossary and later explicitly authorized OpenSpec/tasks/tickets/tests/release evidence; no artifacts are prematurely called implemented.

### R28 — Evidence and proportionality

This decision uses verified current source/docs, documented vendor behavior and clearly labelled product judgments. No Asym tenant study or live deployment latency/permission test was performed. The need for an advisory cue follows the founder's selected workflow and credible collision patterns, not a measured duplicate-reply rate in ministries. Do not invent missionary workflows, copy commercial customer identities or build unrelated help-desk capabilities for parity. The numeric envelope is complete and testable now; changes after measurement must update the one versioned profile and affected evidence, not silently drift.

## Ruthless synthesis and ordering

1. **Before recording the answer:** settle cue meaning, privacy, identity/source ownership, exact transient protocol and bounds; correct the obsolete Vercel limitation and the assumption that private Presence authenticates payload names. This package does so. The selected direction is A; complete amendments are explicitly proposed.
2. **Capture in later authorized spec/design:** R01–R28, the UX/input/failure journeys, exact source/CRM/Email Studio seams and one versioned timing/budget profile. Record real-session binding as a required identity-owner seam, not a capability already present. Existing governing ADRs are not overridden by vendor examples.
3. **Implement in dependency order when authorized:** qualified actor/session/source predicates → finite command/snapshot boundary and grants → intent/lifecycle adapter with shared client → private hint fanout and reconciliation → stable UI → actual negative/concurrency/accessibility/load/rollout proof. Source/send authorities are prerequisites; no broad platform redesign is necessary.
4. **Before activation:** execute every proof group, publish actual installed/deployed versions/regions/quotas and measured latency. Reject leaks, stale resurrection, private draft changes, unsafe send behavior or incomplete source qualification. No monitoring substitutes for these gates.
5. **Monitor only defined operating risks:** use O01–O07 in the [proof/operations ledger](phase26-d34-proof-and-operations.md), each with signal, threshold, owner and response. Performance/availability may degrade the cue; privacy failures disable it and trigger incident handling. Preserve ordinary Support work throughout.

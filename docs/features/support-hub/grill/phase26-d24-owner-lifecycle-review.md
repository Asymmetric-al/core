# D24 independent owner, authoring and lifecycle review

Reviewed 12 September 2026 for selected **C — Curated reply-and-work shortcuts**, with the founder's future AI-augmentation direction recorded as requiring further thought and research. This is an independent scoped review, not full ratification, implementation or AI activation. Root synthesis owns the complete 23-category disposition. Core source is `7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd`.

**Disposition: Accept with required amendments.** C is viable as a private draft staging operation followed by one explicit guarded **Send and apply** admission. It is not viable as today's sequential macro runner with an extra preview, a Saved Section that executes work, or an editor that rewrites operational truth. Maintain one curated shortcut model, one pending plan per reply draft and the existing P17 content/shared-command owners.

## Exact proposed permanent contract

### L01 — A shortcut references wording; it does not own another body

“A curated reply-and-work shortcut has a stable same-tenant identity and immutable released configuration revisions. It references an exact eligible published D18 Shared Reply wording revision with qualified authored-language resolution, plus bounded typed Support work-intent parameters. It stores no alternate raw HTML/text template, personal wording ownership, live latest-content alias or executable content node. The appropriate source editor remains Email Studio. A distinct shortcut revision is required to adopt a changed wording release or materially changed plan.”

This makes the reply source useful independently of the shortcut and avoids duplicate authoring. A personal item must go through D18's deliberate contribution/publication before it can become a shared shortcut dependency; a curator cannot point the team at someone's My replies. One source item may contain an appropriately complete answer. No free-form graph of nested content references or arbitrary step sequence is required.

### L02 — Create, edit, release and use have distinct effects

“Shortcut curation and use are separate from P17 author/edit/publish rights and from every underlying operational capability. Editing creates an unpublished configuration candidate; releasing/activating the exact reviewed candidate checks its permitted scope, source dependency, current coded-command compatibility and target references. Save does not activate, P17 publish does not activate the shortcut, and shortcut activation does not publish content. Cross-surface convenience actions sequence the real owner commands with separate truthful receipts and retry reconciliation.”

For example, a curator who can select existing Shared wording but cannot publish may build a shortcut from an existing eligible publication. A wording editor without Support configuration rights may revise the wording without changing the shortcut. If a combined “Publish wording and activate shortcut” convenience exists, published-but-not-activated is a real recoverable outcome, not rollback by pretending publication never occurred. Prefer existing source-capability/review patterns over inventing a second universal review queue.

### L03 — Selecting stages one private-draft change, never conversation work

“Selecting a shortcut previews the current eligible wording and proposed changes. Explicit Use stages an exact wording copy and one pending plan together in the current private Reply draft, against its expected revision. This operation changes no live assignment, label, work status, message history, notification subscription or provider state. It preserves the existing D23 signature slot, audience, subject, attachment state and unrelated reply text.”

At most one shortcut plan is pending per draft. Do not stack shortcuts into an ordered program. D18 ordinary insertions may still add compatible wording without executing or automatically expanding the pending plan. An ineligible source, target, missing required parameter or incompatible profile fails staging without half-inserting body content or arming a hidden plan.

### L04 — Insertion, replacement and Undo remain coherent

“Use the existing D18 insertion-at-caret/selection default. Replacing the entire human body is a distinct deliberate action with current draft revision and recoverable Undo; it excludes the managed signature and preserved source metadata. Replacing a pending shortcut plan requires a clear comparison of the old and new effects. It does not automatically delete or reconstruct previously inserted wording after the responder has edited it.”

“Undo across the shortcut insertion boundary must undo or disarm the associated pending plan before Send. Redo cannot silently re-arm an invalid plan after current source/actor/audience controls changed. Remove shortcut, keep reply removes pending work intent while preserving edited text and its original wording provenance. Clearing/replacing the body, changing purpose or discarding a draft cannot leave an invisible plan armed.”

This is a material footgun: a Tiptap undo stack normally owns document edits, while a React state object might own planned work. Without a coordinated draft change, Ctrl+Z can erase the information-request text yet leave Waiting/Resolve planned. Work commands should not be embedded as Tiptap nodes merely to make undo convenient; that would turn copied/exported text into executable data. A small shared draft transaction/undo adapter or safe plan invalidation is the right seam.

**Final replacement recommendation after root synthesis:** Change shortcut defaults to **Keep current reply** and replaces only the pending work plan. Explain that the newly selected shortcut's suggested wording and attachments are not being inserted; preserve the current body, real wording provenance, pre-existing attachments and D23 signature exactly. Record the stage mode as kept-current versus inserted/replaced so source evidence never claims the new shortcut's wording was used. The responder reviews the actual body alongside the new plan; native D3 preconditions remain mandatory. An explicit **Replace reply** uses the existing whole-body replacement gate and expected revision. This avoids fragile attempts to track and delete individual old paragraphs after edits. Undo can restore the preceding draft-and-plan snapshot or conservatively disarm an ambiguous plan; it must not silently re-arm an invalid prior plan.

### L05 — Normal editing remains normal, and modified plans are visible

“Responders can edit the inserted wording in the qualified Reply profile. Ordinary writing does not require republishing the shared source or saving a personal shortcut. The pending plan remains a labelled preview of exact intended changes, never proof that the reply still says something or that a business action occurred. A deliberate change to a staged work field is shown as a modified plan and invalidates its prior review digest. Sending with no pending plan returns to the existing D4 action model.”

Changing a plan must not mutate the shared shortcut. Removing a planned status change is not silently choosing a new one. A plan with an already-satisfied idempotent Add/no-op can show that truth; an unavailable required action is not a no-op. If the final request ceases to be a valid reply-and-work operation, offer ordinary reply preparation after explicitly clearing the plan, not an unexplained partial shortcut run.

### L06 — No new composer mode or hidden audience authority

“C is a Reply shortcut purpose. It does not create an Internal note, switch Reply/Note, set recipients, change sender/Reply-To, forge public responder fields, append another signature or forward content. Reply and Internal note drafts retain their existing separation. Switching away preserves or deliberately discards the Reply draft/plan together; Add note never executes it. Current source provenance prevents internal-only wording from being relabelled for external use.”

The actual sender is the currently authorized human admitting the reply, not shortcut author, template author, assignee or CRM owner. Source/profile values remain typed descriptors resolved at qualified preparation; copying a shortcut does not store live requester/staff/CRM snapshots as reusable values. Literal incoming text and braces are inert content.

### L07 — One complete reviewed local admission

“Send and apply validates the entire current canonical reply, audience, signature, ready immutable P17 preparation and all pending work effects before admitting anything. Its reviewed digest binds the shortcut/configuration revision, exact wording/source provenance, edited complete draft, actual actor, recipient/thread context, current original-source/topology and affected operational controls. Failure, missing permission or stale review admits neither mail nor planned work. One atomic local boundary records reply intent, work/label/assignment changes, source history, command receipt and durable dispatch/recovery obligations.”

No transaction spans external Resend I/O. After admission, queued does not mean delivered. A downstream failure follows D4's current Open review and P6 recovery; it does not rerun the old planned changes or automatically compensate assignment/labels after somebody else has acted. A “stop on first error” switch is not an adequate replacement for the atomic local contract.

### L08 — Work intent is a constrained patch, not a program

“The shortcut's work portion uses only the selected decision's closed, code-owned Support command parameters and current required inputs. It has no triggers, conditions, branches, loops, custom code, delays, generic property writes, arbitrary URLs or cross-domain mutations. Contradictory operations and competing assignments/status choices fail before release/use; their order is not made meaningful by an interpreter. Required native state/reason/current-source inputs cannot be skipped by a shortcut.”

The exact allowed effects belong in root synthesis against the relevant D3/D10/D21 invariants. Do not retain legacy priority/snooze/note/send actions merely because their TypeScript union exists. Do not call nested standalone HTTP command handlers as a faux transaction. Reuse their domain validation and effect primitives inside the governing compound boundary. The [roadmap](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L2954) remains explicit: Phase 34 owns the sole configurable vocabulary, and Phase 26 neither ships a parallel builder nor waits for the entire future engine.

### L09 — Dependency changes do not rewrite staged work

“A normal wording publication, shortcut revision, name or descriptive edit affects future selection only. Existing staged copies/plans remain pinned and visible. Available newer versions may be shown without automatic replacement. Explicit refresh/replacement uses a current draft revision and shows affected text/plan changes; it preserves the user's edited body unless replacement is specifically chosen. Current safety, audience, asset, identity and command-compatibility restrictions still revalidate before use/preparation/admission.”

A changed label name is display evolution of the same identity under D21; a changed label meaning is not a safe alias update. Deleted/ineligible assignee and withdrawn wording must not silently select a substitute. A current revision requirement must check actual affected controls, not invalidate every draft because unrelated tenant configuration changed.

### L10 — Archive is distinct from safety restriction

“Routine shortcut archive stops new selection/staging and preserves permitted attribution/history. Existing safe staged drafts are not retroactively rewritten or sent. A routine D18 source archive similarly stops new source insertion; active shortcut availability becomes Needs attention for future use, while copied permitted drafts follow D18's independent lifetime. A dangerous shortcut/source uses its owner safety restriction, which can stop affected new preparation and definitely-unsubmitted work under D4/P6; it cannot recall possibly-sent mail.”

“Restore checks current ownership, source/publication/command compatibility and scope. It does not unrestrict content or reactivate old side effects merely because a historic revision exists. Shared shortcut custody survives creator departure; account/email reuse never transfers authority. Mutable operational definitions and immutable executed provenance remain separate.”

Use scoped dependency impact and owned repair, not global locks on all Support because one shortcut points to an archived label or wording source. No ordinary archive requires the broken body to compile. Routine archive should say “Unavailable for new uses”; emergency withdrawal should say what active use it stops.

### L11 — Portability and migration preserve destination authority

“Duplicate within permitted scope creates a new inactive shortcut identity with provenance and current references, not a live alias. Cross-tenant import/export is not implicitly enabled by D24. If later supplied through a qualified owner-native portability contract, content follows P17/D18 portability, operational references are explicitly remapped and validated at the destination, and import produces inactive candidates. Imported tenant/actor/permissions/action IDs, current filled values, signatures, active flags and prior approvals confer no authority.”

Legacy macro migration inventories both runners and every UI/API/automation entry. Eligible wording moves into an appropriate P17 candidate under actual ownership; eligible operational intent becomes an inactive typed preset for review. Ambiguous owners, illegal ordering, unsupported actions and private data are preserved only under the existing governed read-only remediation path; migration never sends, publishes, assigns or resolves. Fence old writers before activation. Rollback cannot reinstate the sequential unsafe runner after new staged/admitted data exists.

### L12 — Audit and retention explain effects without creating a transcript copy

“Source publication, shortcut release, staging, human edits, admission, work effects and provider delivery retain their different owner receipts. A shortcut use creates no communication history before actual reply admission. Record minimal exact IDs/revisions, actual actors, cause/result and command linkage; record complete body only in its actual qualified draft/prepared/admitted content classes. Workflow events and technical logs do not carry email bodies, broad CRM payloads or permanent public-profile snapshots.”

D16/D17 restrictions propagate to known source-derived content. Removing the pending shortcut plan does not erase wording provenance. Generic library lifetime cannot rescue an expired case-derived body. The [shared workflow specification](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/openspec/specs/workflow-orchestration/spec.md#L59) requires identifier-only envelopes and product-owned claims/dispatch truth. Inngest execution state is not a second run outcome authority.

## Future AI augmentation: useful direction, no current AI build

The founder's future direction should be kept as three separately assessable assistance opportunities, not a promise to activate all of them:

1. **Suggest an eligible existing shortcut.** The lowest-expansion initial candidate. Return an exact current authorized shortcut ID/revision with bounded source evidence and a short useful explanation. The user deliberately stages it, reviews the actual reply/work and invokes ordinary Send and apply. A model may abstain; no shortcut is a valid outcome.
2. **Suggest a wording edit for the current draft.** Return a version-bound draft change through the shared non-authoritative suggestion contract. Preview additions/removals before acceptance; never edit typed identity/protected fact/action nodes, recipient metadata, the managed signature or the pending operational plan by a prose rewrite.
3. **Help a curator draft a shortcut configuration.** Propose an inactive candidate limited to the exact existing allowed descriptors and references. Content generation still creates an eligible P17 candidate, not a body hidden inside operational JSON. The authorized curator reviews/releases; the model cannot invent commands, publish source, widen scope or activate a recipe.

The first option is the strongest future starting hypothesis because it reuses approved wording and known action semantics. It still requires data-eligibility, accuracy, usefulness and rejection/override evidence; neither this review nor vendor availability proves it valuable for Asym. Do not freeze a provider, model, package or semantic-search store now.

No per-Support key store, direct browser provider call, prompt-defined permission system or generic AI write tool is created.”

### L14 — Suggestions cannot acquire permission from content

“Before inference, apply current tenant/principal/source-field and Phase 3/10 model-egress policy. Readable does not mean model-eligible: restricted/care/high-risk data stays excluded even for a cleared worker. Inbound email, attachments, retrieved text, library descriptions and generated output are untrusted data, not control instructions. The model receives minimum permitted material and no Send, Apply, Publish, CRM mutation or external-browsing tool for these suggestion purposes. Structured output and human approval do not replace current deterministic authorization, schema and semantic validation.”

“At suggestion display, acceptance, staging and Send, recheck current source access, revisions, eligibility and policy. A stale suggestion cannot silently refresh its chosen actions or source body. User acceptance of a suggestion stages a draft; it does not authorize an external reply or operational effect. A generated title, evidence explanation, confidence score or prior accepted suggestion has no authority.”

### L15 — AI presentation stays optional, honest and correctable

“Retain the complete manual shortcut/search/composer path. AI unavailable, over budget, rejected or disabled leaves ordinary work usable. Suggestions are visibly suggested, easy to dismiss and inspect, and never steal keyboard focus or overload the ordinary Send/Tab action. Display concrete proposed changes and actual qualified sources; do not use reassuring explanations or fabricated numeric confidence as proof. Preserve original text, current draft revision and safe undo; do not stream an unreviewed rewrite into the sendable authoritative draft.”

No current AI UI toggle, embeddings, provider call, autonomous background suggestion job, new paid Tiptap service, evaluation pipeline implementation or authority is added by D24. The schema/revision/provenance/current-command seams needed for the manual product are sufficient extension points. Later AI qualification must name concrete purpose/data/provider/budgets/evaluation and false-action thresholds before activation, under the actual owning decision.

## Executed counterexample and required acceptance proof

[Two-case source experiment](phase26-d24-source-experiments.json) isolated the complete current `run-macro.ts` implementation by removing only imports/export modifiers, transpiled it with installed Bun and supplied a synthetic adapter. It ran with `--no-env-file`; no live adapter, database, provider, browser or environment-file module loaded. The file hash and exact limits are recorded.

1. Synthetic assignment rejection was followed by successful resolved-status application; final `ok:false` did not undo that later effect.
2. Canned-response send and team assignment were both skipped, yet the final result was `ok:true` with zero effects.

This proves only current loop/result behavior for those inputs. It does not prove deployed exploitability, a production incident, successful D24 validation or a future action list. No proposed implementation test was run.

Required outcome proof for this seam:

- Different source author/publisher, shortcut curator, responder and assignee retain distinct authority and attribution; one permission does not grant the others.
- Same published wording can serve D18 and multiple shortcut revisions without dual ownership; update/withdraw/archive affects the correct future/staged/admitted use class.
- Selecting/cancelling/staging never changes live work or creates communication history. Failed stage preserves both the original body and prior plan without half-state.
- Tiptap caret insertion, explicit replacement, ordinary typing, Ctrl+Z/Redo, remove-plan-keep-reply, switching mode, restoring draft and actor/source/locale changes cannot leave a hidden active plan or lose signature/provenance.
- Change shortcut with heavily edited prior wording: Keep current reply preserves the exact body/asset/signature/provenance state and changes only the visible pending plan, without claiming use of the new suggested wording. Replace reply followed by Undo restores the corresponding plan/body state or disarms the plan safely; no paragraph-region reconstruction is needed.
- A second shortcut requires deliberate replacement, with contradictory/opposing work patches rejected; only one pending plan reaches admission.
- Complete preflight failure/stale source/revoked target causes neither reply admission nor any work effect. Successful local admission is once-only with correct current-source label contributions, assignment/control and D3 transition history.
- Lost response/retry/new deliberate invocation distinguish original result from current state. Provider failure after local commit follows D4/P6 without replaying or reversing newer user work.
- Cross-tenant references, unapproved personal wording, expired assets, missing language, unknown action fields and raw HTML are rejected at current owner boundaries; endpoint/worker/direct-write entry paths agree.
- Legacy conversion is effect-free and inactive until owner review; old runners are fenced before activation; old clients/rollback cannot bypass the new compound boundary.
- Manual completion remains usable without any AI provider/library suggestion service. Before a later AI feature activates, evaluate injection, prohibited egress, cross-tenant/source inference, unsupported output, stale suggestions, false actions, dismissal and correction using the declared shared purpose and numeric release criteria.

The permanent implementation order is owner-contract qualification, immutable source/configuration references, atomic private staging and safe editing, complete admission with existing domain primitives, source lifecycle/legacy writer fencing, and independent outcome proof. AI remains a future optional consumer of those sound seams, not a prerequisite or an implementation shortcut.

## What staff see

The ordinary current conversation remains the focus. Immediately above its Reply/Note composer, the utility line can say **Maya Chen is composing**. The same location is visible while reading before opening a draft; it sits apart from the selected audience control and the Send button. D33 Reading/Find stays where it is. A reserved flexible utility row prevents a cue arriving from moving the Send action under a pointer or disrupting the current reading anchor.

Use readable existing secondary-text sizing/contrast, a small neutral composition icon if useful and the existing profile presentation treatment. Text carries meaning. No tiny hover-only avatar, red alarm, animated dots, sound or toast. Do not reduce body type or touch targets to fit several names. Initial render without a known transport problem remains calm; a short startup connection phase is not a warning on every ticket.

Drafts stay private.”** Existing same-name disambiguation may show a permitted identity attribute; never expose a hidden email/role merely because two names match. Do not split international names into an assumed first/last pattern. Isolate mixed-direction names so punctuation remains correct.

## Journey1 — Staff begins in Support

1. Maya opens a permitted request from the existing Support list. Loading and reading do not advertise her as composing. Her existing Compact/Full default and temporary expansions remain stable.
2. Arun has the same qualified source open. He is not shown as a viewer. Both receive only currently permitted peer composition metadata.
3. Maya deliberately begins a reply, dictates text, pastes wording, edits recipients or performs another qualifying composition action. The client sends a leading content-free intent independently of editor rendering. Arun sees “Maya Chen is composing” under the healthy measured latency target.
4. Arun may avoid duplicate effort, continue reading or work on a separate authorized note/draft. No automatic wait/takeover/lock appears; the cue does not decide who owns the work.
5. Maya pauses briefly or moves between formatting/link/attachment controls. The cue does not flicker on each key or toolbar blur. After30seconds without local qualifying work it stops; a lost connection may cause the server's15second liveness bound to remove it sooner. Her private draft remains saved under D2.
6. Maya submits her reply. On actual reply admission the cue stops promptly. Queued/sent/failed/provider-unknown state is separately presented by D4/P6; cue disappearance never claims Sent. On validation rejection the draft and still-eligible episode remain; if inactive/expired she starts a new episode on another edit.
7. If Arun also submits, D1/D4's actual source/version collision review independently governs. Neither a cue nor missing cue bypasses that check or discards either draft.

## Journey2 — Staff begins in CRM

1. A staff member opens the permitted Support item from its CRM-linked history/context. This uses the same canonical Support source, not a CRM copy or a new conversation.
2. CRM contact access alone grants no extra Support, finance, missionary or member-care visibility. The reader and identity projection establish exactly what may be shown. A staff member limited to originalA cannot learn someone is composing on inaccessible originalB just because both appear under a continuing merged component.
3. The same utility line and composer behavior appear. Eligible composition started in Support is visible through this reader and vice versa. It requires no duplicate person, Activity, draft, task or “sync” record.
4. Moving to an authorized CRM task preserves the return context/draft but stops Support composition eligibility when its active composer is left. Making a contact/giving/receipt action is owned and audited by that domain; this cue neither initiates nor verifies it.
5. Returning restores current authorized reader state, D33 mode and private draft. It clears stale remote cues and fetches current state. Only a fresh deliberate composition action announces work again.

These are two entry journeys into one capability, not two feature implementations. Illustrative names and donor-care situations are examples, not claimed observed ministry workflows.

Browser window blur is not identical to hidden document. This product deliberately suspends _publishing composition_ while its application window is inactive. The visible observer can still receive current peer information as long as its reader remains qualified; hidden readers stop ordinary interest renewal. Native picker/permission interruptions must preserve drafts and restart only on deliberate return interaction, not create an Away roster. IME focus transitions must be tested before treating blur as a universal event rule.

## Failure and recovery journey

A slow/missing cue must not make the editor slow. Typing, autosave and source reading have their own qualified paths. If a wake is lost, the combined5s/10s snapshot loop repairs normal awareness. If snapshots also fail, known peer claims expire from request-start deadlines and the quiet unavailable state explains that live awareness is not current.

On a lost control acknowledgement, freeze only cue publication, reconcile the exact issued state without renewing it, and either continue a still-valid episode or require fresh input in a fresh instance. Never resubmit captured old input as new. There is no error dialog demanding the staff member solve a broker issue, and no per-keystroke retry toast. Pending stop is flushed promptly when control state is known. User-facing send failure/conflict remains separate and actionable under its own contract.

If the current-name disclosure is open when an actor disappears, update its contents without jumping focus; if it becomes empty, close safely and restore the triggering control's logical location. Do not announce that work is certainly finished. New names do not reorder unchanged entries on each renewal. No count from an incomplete/over-limit response is shown.

## Mobile, accessibility and visual quality

Use the same small cue in a narrow single-column reader. Do not pin a floating badge over the keyboard, obscure reply recipients or squeeze the Send button. Preserve D33's400% zoom,320CSS-pixel reflow and44CSS-pixel primary touch targets; meaningful names/controls remain reachable without a horizontal-only interaction. Existing Base UI disclosure semantics should expose label, expanded state, focus return and Escape behavior. Tooltip text alone is insufficient on touch.

Use a polite aggregate live region only for meaningful actor-set/availability changes. Coalesce rapid changes for speech without delaying visual freshness; ordinary renewals are silent. An ending can be announced as “Composing cue ended,” not “Nobody is composing.” Never move keyboard focus for presence. Reduced-motion mode remains static; this feature needs no continuous animation in either mode. Test screen readers, IME, dictation, keyboard-only, touch, same-name and long/RTL names against the actual composed interface.

## Maintenance journey

Tenant staff do not configure heartbeats, collision locks or an activity dashboard. The default cue works in qualified readers. Support administrators retain existing staff permissions/assignment/coverage controls; membership changes apply through those owners, not a parallel presence list. No new customer/donor preference is introduced.

The Support owner sees aggregated cue-health signals and can disable only awareness for an affected tenant/context. Platform operations checks broker/runtime/region/quota failures; database/identity owners investigate authorization or cleanup failures. A content-free diagnostic correlation is sufficient; do not request private drafts or record a staff activity timeline. Test/version/rollout procedures are in [proof and operations](phase26-d34-proof-and-operations.md).

## Exact concurrency and persistence checks

**The final command is appropriately small and internally coherent.** It sets an absolute Compact/Full value against one expected preference revision; it is not a toggle or a workflow. The database must enforce uniqueness and the conditional transition under real current tenant/profile ownership. `schema_version`, client time, a generic JSON upsert and aborting an HTTP request do not replace that contract.

| Case challenged                                            | Verified final outcome                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Confirmed missing row                                      | Virtual Compact/revision0; ordinary reading performs no write.                                                                                                                                                                                                                              |
| Explicit Compact from absence                              | Creates a revision fence. A delayed Full request still carrying revision0 cannot overwrite it.                                                                                                                                                                                              |
| Explicit reset to Compact                                  | Writes Compact through the guarded command; it does not delete the row, reset revision or clear siblings.                                                                                                                                                                                   |
| Fresh same-value save                                      | Matching expected revision advances once, recording the new deliberate confirmation even when the displayed value matches.                                                                                                                                                                  |
| Lost response followed by retry                            | Stale requested value already current yields Already current and the current revision without another write. This is not misrepresented as an immutable receipt proving the exact first request committed.                                                                                  |
| Full accepted, then Compact accepted, then old Full replay | Different current value plus stale revision conflicts; no restoration of the old Full value.                                                                                                                                                                                                |
| Concurrent first saves                                     | One unique successor; same desired value converges, different desired value conflicts.                                                                                                                                                                                                      |
| Rapid choices in one client                                | The local newest intent stays visible. Writes are serialized; obsolete responses and whole-response rollbacks cannot reverse it. A queued successor proceeds only under the data contract's acknowledged local-successor rule; a known external revision/conflict stops automatic rebasing. |

These cases are explicit in R05–R07/R14/R16, the data command/race table, and P07–P12. The distinction between an accepted local successor and Already current/current-state convergence is preserved: an HTTP timeout or state lookup does not prove cancellation or a historical commit. No permanent outbox, per-toggle business event or receipt journal is needed for this desired-state preference.

## Default, local reading and unknown state checks

The menu is a clear persistent default selector. It has a separate temporary group; opening a region, revealing a Find match, returning from an attachment or choosing conversation-wide temporary Full does not save Full. The header's temporary label and saved-default group remain separate, and no persisted Mixed mode is created.

A deliberate default choice applies locally immediately while the server save remains Saving, Saved, Not saved or unconfirmed. Failure preserves the allowed local view and offers scoped recovery. Confirmed absence, loading, unavailable and unsupported state are different: temporary Compact can keep authorized reading available, but cannot be labelled a confirmed saved preference or silently written over an existing Full default. Choices made while persistence is unknown remain local until deliberate reconciliation.

Passive hydration, reconnect and updates from another device refresh the known default for a future untouched entry. They do not re-collapse active disclosures, move focus, steal scroll or erase the current draft. Source revocation remains different and takes effect despite local presentation state. The current-source gate, not the preference's availability, decides whether message content can be shown.

Resetting temporary disclosure to the confirmed default preserves an active Find target and focused region. Resetting the saved default to Compact uses the revisioned command. The two operations are not conflated in the actual UX. R03–R07/R11/R12/R16 and P10–P12/P23–P25/P29 give the necessary falsifiable journeys.

## Source, security and owner boundaries

The final data contract correctly acknowledges current source limitations: Core's existing CRM-only preference route/helper is not already a generic reading service; the actual helper drops an arbitrary reading field and replaces a columns scope as designed. The current cache key/rollback shape requires qualification, not an unsupported claim that production cross-tenant disclosure has been reproduced. Existing tenant FKs, revoked client grants and RLS are recognized.

The Supabase/PostgreSQL distinction is accurate: effective USING/WITH CHECK semantics and actual grants matter; omission of a separate WITH CHECK is not automatically an ownership-reassignment hole because PostgreSQL may reuse USING. Service-role and elevated-function paths still need their own current authorization. The actual command must enforce the valid tenant/member pair and immutable key/revision; separate FKs are not proof of that pair's current validity.

The stricter complete-region repetition rule is a defensible refinement of the earlier bounded-comparison recommendation. It uses only qualified earlier sources and keeps changed or uncertain regions open. It does not compare against hidden history to erase the only visible copy, use current P17/profile state as historical signature evidence, or store a new transcript. A source losing comparison eligibility can simply leave current permitted content fully visible; no inaccessible-source hint is needed.

D22 source matching and complete Find remain independent of DOM/fold state. D23 safe static rendering and original history remain prerequisites. D32 metadata/private file actions and current CRM return remain intact. Saving/reading produces no P17 preparation, P6 message, outgoing delimiter/quote/signature change, D24 work effect, CRM mutation or official-document artifact. Full is currently permitted safe presentation, not an authorization override or raw-original export.

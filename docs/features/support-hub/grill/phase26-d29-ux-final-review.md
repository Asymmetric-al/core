## Material finding — context loss versus full draft clearing

**Severity Medium; likelihood plausible during expired/revoked context or record changes.** R11 says to clear draft/prefill on “permission-bound context replacement,” while R12 and the app UX explicitly promise to preserve permitted visitor-authored text for deliberate **Send without account details** after context becomes invalid. Read literally, a developer can clear the whole message when only the optional context changes, defeating the user's primary contact task. The reverse mistake—preserving unqualified private references or another actor's prefill—would be a privacy defect.

Required precise correction to R11:

> Clear the complete app-managed draft, prefill and context on successful receipt, deliberate logout, account/principal change or tenant change. For loss or replacement of optional context within the same actor/tenant session, clear the unqualified context references and any prefill whose authority no longer holds, while retaining only still-permitted visitor-authored text for deliberate requalification or Send without account details. Do not silently submit or transfer that draft to a different actor or anonymous context.

Required P13/P14 proof:

> Revoke only the optional context after the requester has typed a message. The safe context-free path retains permitted visitor-authored text, removes unqualified references/prefill, and requires deliberate review/submission. Separately, real account/tenant change clears all prior app-managed private draft state and cannot show another person's values.

This aligns the two existing intentions without adding persistence, authentication requirements or a new draft system. Native public input and app-owned context retain their separate authority; browser autofill remains user/browser supplied, not verified identity.

## Final verification — Pass

**13 September 2026: Pass.** I re-read the corrected R11/R12/P13/P14, the actual requester/maintainer blueprint and the now-complete [data contract](phase26-d29-data-contract.md). The initial finding above is resolved history, not outstanding work.

- **Context-only loss now preserves the correct information.** R11 explicitly removes unqualified context references and source-derived prefill while retaining only still-permitted visitor-authored text for deliberate requalification or reviewed contact without account details. R12 and the UX use the same meaning. P14 proves that distinction; successful receipt, deliberate logout and actual account/tenant changes still clear the complete prior app-managed draft.
- **Contact remains immediate and independent.** The form opens directly, with required reply email/message and optional unsplit name. Three optional Listed guide links are secondary; their failure does not block a qualified contact closure. The data contract expressly preserves other independently qualified public email/phone contact while standard Support form setup is incomplete, without force-enabling Support or silently changing the form's Primary Outcome.
- **Limits are internally coherent.** Main/data/proof agree on newline normalization, 10,000 message/200 name Unicode scalars, 256 KiB raw-body ceiling and the actual owner mailbox parser. The data contract explicitly warns that HTML `maxlength` counts UTF-16 units and must not reject otherwise valid scalar-bounded input. Encoding examples are synthetic proof of the proposed envelope, not a production performance or universal mailbox claim.
- **Authoring and maintenance are complete and bounded.** Requester help inventories actual public/app placements; source edits, app bindings, route qualification, preview, separate release receipts, reorder/remove, maintainer replacement and optional Email Studio confirmation remain at their owners. Removing guidance does not delete a Page or disable contact. No new rule builder, public search, miniature reader, upload flow or second CMS is introduced.
- **No-JavaScript, recovery and privacy agree.** Native form validation/submission/receipt uses the same qualified owner boundary; guide links work independently. Unknown acceptance reconciles the exact intent and cannot automatically send another channel. Private answers/context/receipt authority stay outside public cache, query strings, analytics and duplicated CRM history. Current source restrictions and finite custody apply to every real representation.
- **Confirmation and continued work remain truthful.** Browser Received follows durable primary acceptance. Optional web confirmation is default Off, separately source-qualified and subject to common courtesy/finite utility; D13 receiving-email remains distinct. The later owner refinement makes web-confirmation Recent sent copy Off-only, with synthetic Template used preview and no permanent generated body. Human replies, D14 target credit and D28 feedback retain their real source rules.

**No new material UX, authoring/maintenance, navigation, limits or privacy-contract defect was found.** This is an independent documentation review of the finished grooming package. Actual browser, assistive-technology, no-JavaScript, requester/maintainer usability, database concurrency and provider tests remain required and unexecuted; no runtime proof is claimed.

# D30 — Fixed Support overview: source and owner review

**13 September 2026. A — A focused Support overview is selected. Future fuller configuration is an explicit product direction; its implementation and detailed capabilities are not selected now. D1–D29 and all their amendments are fully ratified.** This report proposes the precise owner safeguards for D30's adversarial synthesis. It is grooming, not runtime implementation or a new report engine.

**Disposition: Accept with required amendments.** A fixed, useful overview is consistent with the existing Support surface when it consumes the accepted work/report contracts rather than recomputing a plausible set of cards. The main risks are mixed time/cohort/inbox meanings, incomplete or unauthorized counts, copied metric authority and treating report output as a business action or communication. Stable code-owned report-block contracts preserve a route to future composition without a configuration product now.

## The smallest complete fixed composition

Use one fixed Overview under Support Reports, keeping normal work views and focused reports directly accessible. It contains **Work now** and **Results for a selected period**. Selected summary information must lead to its exact source work/report. It is not a universal health score, replacement inbox, workforce dashboard or claim that every obligation is visible in every summary.

Work now uses currently authorized source summaries across genuine email, staff-recorded and form-origin Support work. Its work-list counts are current continuing conversation identities under D20/D10; underlying reply obligations retain D14 identities. The existing all-age feedback Needs review and other independently qualified required recovery destinations remain reachable without a historical filter. Their counts require their own current source authority; ordinary conversation queries must not absorb or expose held intake merely to fill an overview.

Results may provide three compact report areas: **Reply performance** (the distinct target-results and completed-wait portions), **Request labels**, and **Feedback**. This groups navigation without merging their formulas, grains or date meanings. Exact displayed summaries should be chosen in the main UX synthesis from already-qualified report results, with the necessary denominator/coverage/unknown context. No full transcripts, response comments, donor names, financial metrics or employee-ranking previews are needed for this default.

## Exact selector decision

**Adopt the root synthesis: no global Inbox selector.** Work now alone has **Currently handled in**, initially **All accessible inboxes**, using D20's explicit dynamic scope. An explicit selected set remains exact; loss of required access is not silent narrowing under its old label. Results has its own period and reporting zone, with persistent explanation: **Across inboxes you can report on — Work now filters do not apply**. Each report retains its qualified audience, dimensions and narrower filters in its full owner surface. Current rights are still enforced independently per report; the overview does not invent equal accessible populations where owners differ.

**View full report** carries the Results period/zone, not the Work now predicate. Clicking an actual metric carries that metric's exact qualified cohort, kind and source/drilldown context, also without importing the unrelated Work now inbox selection. The former is destination navigation; the latter promises count/cohort parity. Both preserve a safe return reference and reauthorize on use.

The initially considered alternative was one neutral Included inboxes set with block-specific mappings: current home for work/labels, a selected historical source dimension for reply metrics and original provenance for feedback. It is rejected for this fixed overview. It adds explanation and risks making a superficially global filter mean several different things; choosing a new historical inbox dimension solely for visual uniformity creates unnecessary qualification. The separate controls avoid that cost and do not change D14/D21/D28. Future composition may deliberately qualify compatible shared scope bindings; there is no silent placeholder behavior now.

## Independent concerns and exact proposed amendments

Severity denotes consequence; likelihood is a qualitative conditional estimate, not an observed Asym incident rate. Each concern narrows or completes A rather than replacing the selected fixed-overview approach.

### O-D30-01 — Date and inbox scope cannot erase current obligations

**Material concern: yes. High severity; likely if the current shared route request is reused unqualified.** A historical range applied to current work hides old unresolved requests. A common current-inbox filter rewrites historical responsibility or changes the label/feedback population silently. D14-R21/R24, D21 and the current route/hook substantiate the failure.

**Exact language:** “Work now is an all-age current snapshot. Its Currently handled in selection affects that section only. Results has a separate period/zone and visibly covers the inboxes each report currently authorizes. Do not carry Work now filters into historical requests or full-report navigation. Every report preserves its own existing historical/current dimension semantics; no default-current-home fallback is permitted.”

**Proof:** an old unresolved A→B transferred request remains visible in current B work despite a recent Results range; historical target/response attribution and current-label cohort retain their separate owner meanings. A selected inbox becoming forbidden cannot return a silently narrowed healthy count.

### O-D30-02 — Preserve target-instance grain and incomplete coverage

**Material concern: yes. High severity; plausible when condensing reporting into a percentage.** Counting conversations, averaging inbox attainment or omitting unanswered/uncertain targets can display 100% while work is overdue or unscored. D14-R22 already fixes the denominator.

**Exact language:** “Target results consume D14 Targets due in the selected half-open interval by frozen due instant. Keep First/Next, finalized target-instance grain, on-time assessed numerator, all assessed due denominator including confirmed unanswered misses, explicit exclusions and unknowns, and separate deduplicated potential targets. Never average inbox percentages, score candidate splits or infer completeness from finalized rows alone. No qualified sample is no measured data, not 100%.”

**Proof:** combine unequal inbox populations; an unanswered confirmed miss remains in the assessed denominator; a candidate intersecting two ranges is non-additive; before-due exclusion does not become met; a historical correction changes current interpretation with provenance rather than silently rewriting an already generated snapshot.

### O-D30-03 — A completed wait is not an email, case or effort unit

**Material concern: yes. High severity; likely if current average-response/resolution helpers are retained.** One response can satisfy several waits. A current calendar or guessed acceptance timestamp changes historical duration; pooled time bases and averages of percentiles misstate performance. D14-R23 supplies exact accepted formulas.

**Exact language:** “Reply times uses Waiting periods ended by a staff reply in the selected period, with the exact D14 acceptance/completion cohort and qualified original timing. Show completed-wait and measured-sample counts, First/Next and time basis. Median and nearest-rank p90 are owner-computed over qualifying durations, not derived from rounded card values or pooled unlabeled elapsed/service samples. Boundaries intersected by uncertain acceptance remain separately disclosed; accepted coverage can fulfil work while scoring remains unknown. One reply can end several waits.”

**Proof:** one accepted email covers two waits; a period-boundary acceptance interval is not forced to a day; calendar changes leave old qualified clocks intact; zero service duration remains a real zero; unresolved scoring never returns an already fulfilled wait to reply attention.

### O-D30-04 — Label previews must preserve current component-first meaning

**Material concern: yes. High severity; plausible during shared date-filter/drilldown reuse.** A 2026 root merged with a 2024 original cannot be counted as a 2026 request merely because the surviving row is newer. Multiple labels are not mutually exclusive topics. D21's complete data contract is authoritative.

**Exact language:** “The label area shows current labels on currently grouped conversations whose earliest qualified original start across the whole component lies in the Results interval, under the report's current responsible-inbox scope. Preserve complete metadata, N/L/U coverage, overlapping label counts, archived applied labels and separate unconfirmed-start evidence. Unknown is not unlabelled; N=0 has no percentage. Use the exact report-context drilldown, never substitute D20 Created date or save that report cohort as an ordinary view without a separately qualified contract.”

**Proof:** early-original/later-root merge and Undo; two labels on the same components; archived applied membership; forbidden/missing metadata; exact chart/list parity with permission changes rechecked.

### O-D30-05 — Feedback default is issued cohort, not a mixed response period

**Material concern: yes. High severity; likely if an attractive response-rate card is assembled from separate totals.** Responses received this week may answer earlier invitations. Dividing them by this week's accepted/issued mail can exceed 100% or misrepresent voluntary feedback. D28-R24 and the data contract explicitly distinguish the two journeys.

**Exact language:** “The Overview Feedback preview defaults to invitation effects issued in the selected period, where issued means submission may have begun, using D28's qualified occurrence clock and original provenance. Responses and any response fraction refer to those same issued effects as of the report evaluation, including indeterminate submissions in the issued denominator. Response-date browsing remains a separate full-report/list mode. Show open response windows/current cohort maturity, sample size and source exclusions. Any rating distribution or satisfied share uses only its currently includable submitted ratings with its own denominator; no response is neither positive nor negative.”

**Proof:** old invitation/new-period response; response before definitive provider acceptance; issued effects with different expiry windows; redacted/expired ratings versus retained lawful body-free response evidence; duplicate provider events; merge/Undo preserves original effect counts. The preview consumes D28 exclusion/custody results and cannot reconstruct unavailable ratings from receipt counts.

### O-D30-06 — Off is not absence of historical feedback or current review work

**Material concern: yes. Medium severity; likely if the block is conditionally hidden by the policy boolean.** Off stops future invitations but does not erase authorized ratings or an outstanding review obligation. A selected Results period can also hide an old unreviewed response. D28-R09/R18/R20 and UX explicitly retain history and review.

**Exact language:** “Display Automatic invitations Off as current policy status separately from authorized historical feedback. Existing data remains available under its current source/custody rules. An all-age Needs review destination stays discoverable independently of Results range and policy Off. No-data, no currently includable ratings, incomplete data, unavailable authority and policy Off are distinct states. Do not turn policy settings into a historical eligibility rewrite.”

**Proof:** disable policy after an issued invitation and response; retain permitted history and outstanding review access; change the Results period; revoke source permission or expire source content and verify only the qualified unavailable/exclusion facts remain.

### O-D30-07 — Authorization precedes aggregates and layout visibility is not data authority

**Material concern: yes. Critical severity; plausible through shortcuts or future composition.** A tenant summary, small-group difference, hidden field predicate, cached count or shared layout may reveal restricted sources even when detail is protected. D20 and P33 require governed source/field access, not front-end hiding.

**Exact language:** “Resolve each registered report through current tenant, Support/source, classification/field-use and required owning-domain disclosure authority before filtering, counting, aggregating, labelling, caching or drilling. A report/layout capability grants no conversation, CRM or financial rights. Use existing aggregate/disclosure controls when applicable; this decision invents neither a blanket new k threshold nor permission to bypass one. Report unavailable or source-qualified partial coverage rather than a false full count. Query and result caches bind current principal/scope, exact report contract, inputs and source/safety context; stale responses cannot survive tenant or permission changes.”

**Proof:** two tenants with equal local IDs, distinct inbox readers, sensitive field predicates, forbidden source names/options, same-user tenant switch, revoked permission with in-flight results and exact selected-scope loss. No private body, rating comment, raw address or CRM snapshot is needed for the default blocks. Generic Support counts do not require unrelated CRM rights; CRM context/fields do require their actual owner rights when consumed.

### O-D30-08 — Stable fixed block contracts, without building configuration now

**Material concern: yes. Medium severity; likely if future intent is implemented as either disposable card arithmetic or a premature builder.** App-local formulas cause permanent drift; a dashboard database, DSL or generic UI now expands the chosen scope. P33 names the shared semantic/composition owner but is future planning.

**Exact language:** “Implement the fixed composition from a finite code-owned set of registered report blocks. Each has stable semantic identity, a versioned source/report contract, declared permitted inputs, unit/cohort/time and scope binding, source authorization, result-state/coverage provenance and exact drilldown contract. Reuse an existing qualified shared definition rather than copy it into Support. A layout or visual-label change does not mint a new metric; a semantic change requires owner versioning and compatibility/correction rules. Unsupported contract versions are unavailable, not silently interpreted under current defaults.”

These are logical conformance properties, not prescribed new database column names or a new block persistence table. One source contract may serve a compact block and full report. Default layout is code-owned now; ordinary existing filter/return preferences can use their qualified shared owner. Do not add drag/drop, per-tenant layouts, tenant formulas, hidden blank controls, arbitrary SQL/joins or a configuration DSL solely to prepare for the future.

**Future intent:** “Later fuller configuration should compose approved shared-report capabilities under P33, with deliberate scope, defaults/reset, visibility and compatibility qualification. D30 records that direction; it does not silently ratify or implement the later builder, recipient schedules or arbitrary metric authority.”

**Proof:** compact/full report use the same contract and values for the same evaluation; a renamed/reordered block retains identity; an unsupported version shows unavailable; a future consumer can select the registered definition without importing its own formula. Actual future builder behavior requires its own later decision and tests.

### O-D30-09 — Work origins, endings and financial outcomes remain truthful

**Material concern: yes. High severity; plausible from current email-shaped filters and generic resolution charts.** Manual and form requests disappear from email-derived workload, or a Resolved/No response count implies a donation problem was solved. D5/D26/D29 explicitly forbid those inferences.

**Exact language:** “Current work uses qualified Support identities from every accepted origin, with original source and lifecycle meaning. Staff-recorded work does not acquire incoming-email counts or response targets merely by appearing in Overview; form-origin applicability uses D29's explicit source qualification and trusted admission. No response and other endings remain their actual dispositions. Reply timeliness, ending volumes, backlog, feedback and actual owner outcomes are distinct facts. Overview neither completes a refund, receipt, recurring-gift change, task or care action nor creates a Party/Activity/P6 message from a view or click.”

**Proof:** manual-ready inbox with no configured mail, genuine form request with acknowledgement Off, later first actual human email, No response ending with a still-independent Finance task and CRM-first navigation under intersecting permissions.

### O-D30-10 — Report reads and future layout changes have no email side effects

**Material concern: yes. High severity; plausible if “overview” becomes a scheduled management summary by implication.** A page load, filter save or future layout action must not create a message, feedback opportunity, acknowledgement or deadline notice. Existing owner boundaries already resolve this.

**Exact language:** “D30 adds no message purpose, P17 template, scheduled digest, invitation, alert or P6 event. Email Studio retains existing governed email/signature/content preparation; P6 retains actual transport/reconciliation. Overview reads body-free qualified report facts and never decrypts P17 execution material to calculate metrics. If separately authorized later, P33 owns report schedule/snapshot/recipient eligibility, P17 prepares the governed message and P6 dispatches with recipient-specific authorization. No such send is included in the present fixed overview or merely by recording future configurability.”

**Proof:** page open, refresh, filter, navigation and authorized report access cause no sending/action effect; failed provider or Email Studio availability does not create a new overview sender or make existing report evidence false. Actual report-source availability is shown honestly and cannot be repaired by a template publish.

### O-D30-11 — Freshness, failure and corrections must not become positive evidence

**Material concern: yes. High severity; plausible under independently refreshed blocks.** A loading/error value defaults to zero, a late old result overwrites newer scope, or cross-block values are presented as one simultaneous snapshot. Current hook empty-array fallbacks demonstrate why future qualified states must be explicit.

**Exact language:** “Each block carries qualified As of/generated-at and evidence/coverage state from its owner. Within a metric, counts, rates and drilldowns share one coherent authorized evaluation; independently evaluated blocks must not imply a single atomic dataset or additive control total. Loading, failure, unavailable authority, stale/partial data, no population and exact zero are distinct. Preserve known source corrections with interpretation version; old generated snapshots are not silently edited. A failing optional historical block cannot block current conversation work or trigger automatic repair mutations.”

**Proof:** reply evidence changes during independent block refresh; old tenant/filter response arrives last; source correction changes current results; failed source does not display 0/100%; explicit refresh/drilldown may show a newer As of with explained differences. Apply existing finite report/query/custody budgets; do not keep restricted counts or source text indefinitely in an overview cache.

## Synthesis for the main decision

1. **Record the selected scope and future direction separately.** Fixed useful Overview now; future fuller P33-governed composition is a recorded intent, not hidden present builder work.
2. **Lock owner meanings before visuals.** Current Work now and period Results use separate controls; retain D14, D21 and D28's distinct grains and source clocks. Feedback defaults to the issued cohort and retains all-age review access/authorized history while policy is Off.
3. **Build the fixed consumer from qualified shared/source contracts.** Stable code-owned block identities and versions, exact permitted inputs, coverage states and drilldown contracts are enough. The current browser aggregation and default-calendar path cannot remain authoritative.
4. **Require source-safe access, navigation and recovery.** Current authorization precedes numbers; no aggregate or cache bypass; direct work/detail/full report journeys remain available. No claim that favorable report values prove satisfied donors, successful business work or staff effort.
5. **Preserve the communication boundary.** No new P17 purpose, P6 event, scheduled email or automatic action is added. Read already-qualified body-free facts only; protect all existing acknowledgement, feedback and reply behavior.

All stated source/query/authorization/lifecycle/browser tests are **required proof obligations**, not executed results. There is no new production benchmark, source-of-truth table, report schema, privacy retention period or runtime implementation in this review. Final verification should examine the actual reconciled D30 main/data/UX rather than treating this report's recommendations as independently accepted product decisions.

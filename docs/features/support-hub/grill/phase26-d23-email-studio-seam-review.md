## Ratification fidelity and required record treatment

The ratification includes the full clauses, every category finding and permanent prevention, complete UX/data detail, evidence qualifications, implementation proof obligations, operational controls, feature ADR and resolved glossary terms. It includes the corrections made during synthesis, not only the original option label: exact publication binding; copied managed signature; truthful Publish/Apply partial success; scoped public-profile meaning; purpose-specific Tiptap validation before parsing; omission preserved by Refresh; pinned Restore; explicit actual sending-context requalification; bounded archive recovery; and source-aware static-rendering failure.

The ratification changes the decision's acceptance status, not the evidence's execution status. The **44 proof groups remain required and unexecuted**. The seven installed-source cases remain limited historical experiments of the old schema/parser/serializer behavior; they do not become validation of the proposed workflow. Existing numeric capacity/profile/dependency/email-client/browser/assistive-technology qualification obligations stay release requirements, not monitor-only risks.

No further D23 amendment is required by this review. In particular, do not simplify the accepted seam into “Email Studio stores the HTML and Support sends it,” “the latest signature updates every draft,” “signature editing updates the staff profile,” or “publishing applies to every inbox.” Each formulation would discard accepted distinctions.

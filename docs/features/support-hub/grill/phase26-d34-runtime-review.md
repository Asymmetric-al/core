## Current external evidence and the recommended tradeoffs

**Supabase authorization.** Private Broadcast/Presence policies are evaluated on join and when a new JWT arrives; they are cached between those points. Therefore a joined channel alone is not a fresh conversation authorization decision. [Official authorization documentation](https://supabase.com/docs/guides/realtime/authorization). The local API must derive real actor/tenant and recheck the current source for every accepted producer mutation and each snapshot. Fanout selection must also reject expired/revoked observer registrations. Those are Asym contract requirements, not claims that a broker supplies them.

**Client Presence.** Clients provide their own Presence payload; high-frequency tracking creates synchronization work, and synchronization joins/leaves need not represent actual human arrivals/departures. [Official Presence guide](https://supabase.com/docs/guides/realtime/presence). Adopt transient activity semantics, reject client-authored identity, room-wide named-state broadcasts, typing contents and Presence-as-business-history. A malicious client may claim that its own authenticated actor is composing; D34 cannot prove a human's intent and is never an authorization or exclusion lock.

**Broadcast delivery.** Supabase offers REST-to-WebSocket delivery; database Broadcast stores events in `realtime.messages` for three days. [Official Broadcast guide](https://supabase.com/docs/guides/realtime/broadcast). For this advisory cue, prefer a bounded best-effort REST wake after the authoritative lease write, with polling/snapshot recovery. Do not require an outbox, database trigger on every heartbeat, durable replay or draft-bearing event. This reduces unnecessary history and coupling; lost wake-ups remain possible and explicitly tolerated.

**Vercel correction.** Vercel Functions now support WebSocket servers in **Beta on all plans**, with Fluid compute. Next.js uses the experimental upgrade helper; connections end at function duration and may reconnect to another instance/deployment, so distributed state remains necessary. [Current Vercel documentation, updated10 August2026](https://vercel.com/docs/functions/websockets). A custom endpoint is technically possible. Retain Supabase because it is already the chosen broker and avoids a second server/coordinator lifecycle for this narrow feature, not because Vercel cannot serve sockets.

**React and editor behavior.** React effects must clean up subscriptions and be safe across Strict Mode's extra development setup/cleanup; unstable object/function dependencies may cause unnecessary reconnects. [React `useEffect`](https://react.dev/reference/react/useEffect). Tiptap recommends isolation and selective subscriptions; its events distinguish updates, transactions, selection, focus, blur and destruction. [Performance guide](https://tiptap.dev/docs/guides/performance), [event reference](https://tiptap.dev/docs/editor/api/events). Apply these patterns to the actual installed source rather than blindly changing working defaults.

**Background behavior.** Browsers can throttle hidden-page timers, and blur is not equivalent to hidden. [MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API). Use declared eligibility and server expiry, not confidence that a last browser stop event or timer always arrives. Stop renewal while ineligible; refresh authorization/state before showing a resumed cue.

**Quotas.** Current published defaults include100 channels per connection, with plan-specific connections/message/join limits. The provider counts sent or delivered WebSocket events; fanout matters. [Supabase limits](https://supabase.com/docs/guides/realtime/limits). Do not assume the production project's configured plan/limits from this table or claim unlimited scaling. The chosen release fixture must record its actual quotas and headroom.

## Exact narrow contract recommended for synthesis

1. **Authority and identity.** “The composing cue SHALL describe recent activity of actual currently eligible authenticated staff on the current Support component. Core derives tenant, actor and source from trusted context. Caller-supplied name, avatar, profile, assignee, requester, CRM owner or Presence key SHALL NOT establish another person's identity, access or composing state.” A technical observer registration is transport interest only; it is not a viewing roster or durable business fact.

2. **One finite owner record.** “An opaque, server-issued, session/tab/source-bound generation SHALL own the finite observer lease and optional composing state. Server time bounds every admitted renewal. Current tenant membership, source topology and compose/read permission are checked independently. An expired/stopped generation, reordered sequence or old response SHALL NOT revive or stop a newer episode.” Combine these fields in the narrow Support capability; do not introduce a general presence engine. The exact root data model must handle late first requests as well as late renewals. **An already-issued activity report needs a fixed server-issued not-after/control window that another heartbeat cannot extend.** An unknown registration ID is rejected, never upserted from a late request. Observer/transport renewal alone cannot refresh the last qualifying input deadline. Otherwise a delayed old Start could acquire new receive-time freshness after an unrelated keepalive extends its parent lease.

3. **Privacy through delivery.** “Only the server may publish a versioned content-free refresh wake on the registered private observer topic. Names, actor IDs, conversation IDs/titles, counts, note/reply mode, text, cursor, URLs and current work facts SHALL NOT appear in the wake. Current authorization selects eligible observers and bounds topic lifetime; names come only from a fresh authorized HTTP snapshot.” Payload absence limits the harm of a queued wake arriving after revocation; it does not assert zero timing leakage or immediate erasure from a previously authorized screen.

4. **Subscribe/reconcile lifecycle.** “Mount/resume/rejoin SHALL obtain a current snapshot and close the read-before-subscribe race with post-join reconciliation. Every response is bound to the current tenant, component, actual actor/session, subscription generation and request generation. A changed context aborts/discards old responses and removes local state. Failed subscriptions or dropped/duplicated/out-of-order wakes use bounded snapshot recovery; neither socket connection nor a wake acknowledges current names.” Join may run in parallel with initial state acquisition when the opaque registration is already established; never sacrifice race closure for fewer requests.

5. **No shared cache of live names.** “Snapshots SHALL be current, private, no-store request reads behind Core's API boundary. A global Next cache, shared CDN, persisted query cache, prefetch payload or local-storage history SHALL NOT retain names/state. Memory keys and lifecycle include current actor/tenant/source/generation; auth or source loss clears visible cue state.” A query retry must not silently widen scope. Freshness expiration changes the cue to unavailable/unknown, not evidence that no colleague is working.

6. **Bounded transport.** “Producer transitions and finite renewals SHALL use one declared timing/rate profile. Unchanged renewals SHALL NOT fan out to every observer. Per-observer wake coalescing, snapshot single-flight and a bounded visible-page reconciliation cadence SHALL prevent bursts from creating parallel request storms. Server Broadcast is awaited with a short explicit timeout and handled as best effort; its rejection cannot roll back an admitted lease, fail draft saving or block sending.” No reliance on fire-and-forget promises after a serverless response, `after()` as guaranteed durability, or an outbox/replay engine solely for this cue.

7. **One browser client, scoped channel ownership.** “Reuse Core's browser Supabase client and a shared scope manager with reference-counted registrations. Preserve the topic's immutable private configuration. Clean up only the owned channel/listeners/timers when the last relevant consumer leaves; a Support unmount SHALL NOT remove other features' channels, disconnect their client or create a second cross-tab coordination service.” Repeated mount/unmount/Strict Mode must not leak subscriptions or stop a newly mounted generation.

8. **Tiptap and React.** “Observe qualifying human composition actions through stable listeners on the existing editor and composer controls. Keep last-action/eligibility/sequence/timer values outside render state where they do not affect presentation. Do not serialize draft content for D34, replace draft `onUpdate`, install collaboration/AI extensions, instantiate an editor per cue or publish cursor/keystroke events. Isolate cue presentation; update React only for an actual displayed actor-set/freshness change, not every key or renewal.” Explicit user insertion/formatting can qualify; programmatic restore, remote metadata, signature refresh due to another actor or autosave is not itself proof of current human activity. The parent UX activity matrix is the authority for concrete action boundaries.

9. **Preserve work and history.** “Cue state SHALL NOT enter P17 authoring or immutable preparation, P6 dispatch/retry/notification, search content, CRM Activity, follow state, assignment/coverage eligibility, D14 clocks or D33 reading preference. It SHALL NOT grant draft access, lock an editor, disable Send, replace current collision checks, manufacture a communication event or claim underlying donor-care work was completed.” Through CRM, the same Support component and actor authorization apply; no separate editor or shadow person state.

10. **Failure and recovery.** “A lease/snapshot/broker failure SHALL degrade only the cue. Keep draft editing and independently authorized actions usable. Hidden/crashed/offline tabs cease eligible renewal; server freshness bounds stale activity even when stop is lost. Resume requires current qualification, and a late stop applies only to its own generation. Unknown/stale state is not rendered as a confident empty roster.” No server clock is inferred directly from a mutable wall clock on the browser without a conservative freshness calculation.

11. **Qualified latency, not instant truth.** “Publish the measured healthy-client/region/load fixture and start-to-visible/stop-to-visible objectives, including all network hops and cold/rejoin conditions. Observe client action→authenticated API→lease/fanout→broker→current snapshot→paint. Network loss or background suspension may exceed the healthy objective; maintain explicit stale/unknown behavior and the existing send guard.” A stated p95≤1second target is an acceptance target for a declared supported fixture, never evidence of current conformance or a universal bound.

12. **Finite storage and rollout.** “Store only the narrow short-lived technical coordination fields. No per-keystroke history, recurring communication audit event or replay stream is created. Exclude expired rows logically on every read; bounded physical cleanup is separate. Qualify schema/grants/channel policies before activation; mixed incompatible clients fail the cue closed without breaking drafts. A kill switch disables the cue and its writes/fanout, not Support work or P17/P6. Rollback cannot turn old lease generations into current state.” Use aggregate operational telemetry without names, drafts or a staff surveillance history.

## Budget model and acceptance proof

The current parent/data direction is30seconds of local activity grace, composing renewal no more frequently than every5seconds, a15second server composing lease, and a combined observer heartbeat/snapshot every10seconds with approximately30seconds of observer lifetime. These are different clocks and are product judgments, not provider defaults. The parent must record the exact single final profile, including observer expiry, fanout and late-request fencing; this report does not create a competing timing contract. Composing expiry is bounded by the current server qualification, last qualified activity deadline and registration/session expiry; neither routine observer renewal nor an old delayed report extends an already-issued activity freshness window.

For `A` simultaneously eligible composing sessions, `V` active observer registrations, producer interval `H`, observer interval `J`, reconciliation interval `P`, and accepted transition rate `T` with mean eligible fanout `F`:

- Producer renewal writes alone are approximately `A/H` per second; observer writes add up to `V/J` unless safely combined. Entry/exit, state transitions, conflicts and cleanup are additional. At1,000 active sessions with `H=5s`, producer renewals alone are200writes/second.
- Visible reconciliation reads are up to `V/P` per second before coalescing/combined responses, plus transition-driven refresh. Wakes scale with `T×F`, not just `T`; each observer still needs an authorized snapshot. Batch REST envelopes reduce HTTP calls, not necessarily broker event/accounting work.
- No-change refreshes should not cause new React commits for the displayed actor set, spoken announcements or full-thread rerenders. Lease freshness may update an internal deadline without regenerating the main reader.
- A start traverses multiple services. Record client/server/broker/snapshot/paint timing separately; a fast local key handler does not prove remote p95.

Release proof must cover: real-session actor/tenant/source authorization; private-topic publish denial; source revoke while joined; reader and composer authorization independently; same actor multiple tabs; merge/Undo and old URLs; visibility/lost Stop/clock skew/late requests; subscription/read races; auth token refresh; Strict Mode and 100 mount/context cycles; other feature channels surviving cleanup; private draft/IME/selection/undo integrity; duplicate wake single-flight; inaccessible stale-response suppression; quota and adversarial event bursts; supported region/network and declared concurrent-load latency; rollback/mixed-version/kill switch; no P17/P6/CRM/D33 effects. Proof is required in the actual implementation, not replaced by the observations below.

## Final runtime refinement challenge — parent synthesis, 13 September 2026

The parent refined the single loop to **every5seconds while composing or displaying a peer cue; otherwise every10seconds**, with transition-only opaque wakes, a **12second snapshot trust ceiling**, request-start monotonic deadline anchoring, and a fixed server-issued control generation/not-after of15seconds. This is coherent as one protocol, subject to the following exact clarifications; this paragraph supersedes the earlier provisional separate observer cadence as a candidate, not the parent's final authority.

- **Count the actual combined work.** For `Nfast` active fast-cadence registrations and `Nquiet` quiet registrations, scheduled HTTP requests are approximately `Nfast/5 + Nquiet/10` per second. A combined call may perform both a lease write and an authorized snapshot; count both database costs. Do not add a second independent producer or observer loop. Leading transitions, source invalidation, recovery and coalesced wake refreshes add work. A five-second interval is not a global per-tenant rate limit or proof of scalability.
- **Serialize and recover without history.** An uncertain control acknowledgement triggers a current-authorized reconciliation read of the instance's last accepted sequence, control window and current state. That read does not extend observer/composing TTL or the activity frontier. Do not retimestamp or replay an old report under a recovered new window. A still-live composing episode can continue only within its original qualified activity deadline; an expired/stopped episode requires a new qualifying input to Start. The state row is sufficient for this advisory recovery; no per-command journal or new signing service is necessary.
- **Do not delay a real Stop behind a periodic timer.** A Start/Stop that arises during an in-flight serialized control becomes the current pending intent and is processed immediately after settlement/current reconciliation, subject to its valid window. It does not wait another five seconds. The local leading-edge dispatch objective is for a ready valid control window; recovery must not be falsely advertised as instant dispatch. Coalesce superseded local intents rather than replaying each keystroke or intermediate mode.
- **Anchor conservative deadlines.** Derive remaining per-actor and snapshot deadlines from server-qualified state and server time; anchor them to the request's captured monotonic start, not response receipt or a browser wall clock. Apply the minimum of the relevant returned remaining lifetime and the12second snapshot trust ceiling. A slow reply cannot acquire a fresh12seconds on arrival. Visibility/resume/reconnect and context changes invalidate stale assumptions before display. The ten-second quiet cadence deliberately leaves limited freshness margin; slow requests truthfully become unknown, without affecting work.
- **One request owner.** Event wakes, the periodic tick, reconnect and visibility recovery share single-flight and rate/backpressure control. A wake received during the in-flight snapshot marks one follow-up dirty read; it does not create parallel fetches or postpone reconciliation forever. The current actor set and freshness class alone drive visible/spoken cue updates.
- **Server channel objects are not free.** Installed `httpSend()` supports REST without subscribing, but `sharedClient.channel(uniqueTopic)` still retains a channel object. A warm server singleton must not accumulate one object per observer. Prefer a bounded REST batch inside the approved database adapter, or dispose each exclusively owned ephemeral server channel after sending. This does not authorize raw SDK use in app handlers, a second browser client, global channel teardown or a new socket server.

These are bounded correctness and capacity requirements, not an expansion of A. The actual parent package remains to be independently reviewed once written. No further runtime or provider test was executed for this refinement pass.

## Primary technical guidance

1. [W3C APG datepicker](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/), updated 12 August 2025: labelled input, optional calendar and focus behavior inform the journey. W3C explicitly warns that illustrative code is not production-ready and mobile/assistive-technology testing is essential. Reuse the pattern through Core primitives; do not copy an example as a finished component.
2. [WCAG2.2](https://www.w3.org/TR/WCAG22/) and [target-size understanding](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum): AA target minimum is 24 CSS px with exceptions; 44 px is the enhanced target. D31's 44 px primary rows are a product choice, not a misquoted AA requirement. Actual focus/contrast/reflow/touch proof remains necessary.
3. [GOV.UK dates](https://design-system.service.gov.uk/patterns/dates/) and [date input](https://design-system.service.gov.uk/components/date-input/): known dates and chosen future dates differ; documented month-name input friction supports readable formats and explicit entry. We do not import its entire form style or birth-date layout.
4. [TC39 ZonedDateTime documentation](https://tc39.es/proposal-temporal/docs/zoneddatetime.html): local calendar arithmetic differs from elapsed duration; gaps/overlaps and IANA rule changes need explicit treatment. D31 does not require Temporal or assume its default compatible disambiguation satisfies the no-silent-adjustment contract.
5. [PostgreSQL 17 date/time types](https://www.postgresql.org/docs/17/datatype-datetime.html): `timestamptz` preserves an instant, not the original named zone. Keep provenance separately; validate the narrower product input range instead of accepting every SQL timestamp/infinity. The current default docs redirect to 18, so the 17 reference matches repository configuration; deployed version remains a release check.
6. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): database grants, policies, update behavior, views and privileged code need independent evaluation. RLS cannot replace source-command lifecycle rules. No blanket claim is made that a missing explicit WITH CHECK always removes all checking; PostgreSQL policy defaults and combined policies must actually be inspected.
7. [Supabase breaking-change index](https://supabase.com/changelog?types=breaking-change): the lightweight Markdown URL failed retrieval, then the current official index was read. Public-table automatic-exposure changes reinforce explicit grants/RLS qualification. No migration or self-hosting upgrade is part of this task.

The data review records current [Inngest limits](https://www.inngest.com/docs/usage-limits). Finite provider sleep/run limits are not a business deadline limit and do not justify losing far-future due work. Qualify the actual deployment plan and use the existing product-owned dispatch/recovery contract; no provider operation was executed.

## Assumptions tested and decisions narrowed

The [23 reference checks](phase26-d31-temporal-probe.json) test the proposed arithmetic against Python zoneinfo and known calendar cases. They found/reconciled the distinction between target rounding and reference-date rounding: at 23:59:59, tomorrow means the next date at23:59, not a date after rounding into midnight. They also make visible 23/25-hour calendar days and thirty-minute shifts. They do not establish browser/server resolver equivalence, SQL/RLS, real idempotency or worker delivery.

An early suggestion to impose a 60-second preview expiry was rejected as needless friction: once reviewed, a valid future absolute candidate can remain valid. The root's final decision has no hard preview TTL. Old relative wording becomes anchored/absolute and Refresh is deliberate. Similarly, a general user-zone preference was rejected as an unverified dependency; the existing tenant default plus per-use override is sufficient.

Complete source review, independent challenge and deterministic docs/reference checks qualify the **decision package**. The [P01–P32 release ledger](phase26-d31-proof-and-operations.md) qualifies the future **product behavior**. Those two kinds of proof must not be conflated.

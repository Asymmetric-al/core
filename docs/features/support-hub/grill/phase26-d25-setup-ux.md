# Support inbox setup: both complete journeys

**D25 C and every adopted amendment fully founder-ratified, 12 September 2026.** This is the concrete product journey accompanying [D25-R01–R32](phase26-d25-adversarial-review.md). D1–D25 are fully ratified. It is a researched grooming contract, not a built or usability-tested interface. [Evidence](phase26-d25-evidence.md) and the [data/Email Studio contract](phase26-d25-data-contract.md) define actual ownership and proof limits.

## The first screen

From Support's empty state or **Settings → Inboxes → Add inbox**, open an ordinary full-page setup surface, not a modal inside another modal. Preserve the current tenant and an existing draft/candidate where applicable. The first screen says **Set up your Support email** and offers two equal accessible choices:

| Choice                              | Description shown to the administrator                                                 |
| ----------------------------------- | -------------------------------------------------------------------------------------- |
| **Use an existing Support address** | Keep the address people already use. We'll guide you through connecting incoming mail. |
| **Create a new Support address**    | Set up a dedicated address for this team's Support requests.                           |

Neither is preselected, labelled Recommended or placed behind Advanced. The administrator chooses the known situation; provider-specific instructions come afterward. Continue is explicit and a keyboard selection never activates or sends. Changing the selection before outside work is simple and preserves shared entered information. A short “Which should I use?” explanation covers existing suitable address versus new/separate intake without a technical questionnaire.

The visible progress groups are **Address → Connection → Verify → Review** after this choice. Keep completed checks when still valid, show only the current path and one next action. The labels describe the user's work, not a new workflow runtime. A candidate may be saved incomplete; **Saved draft**, **Not saved**, **Checking** and **Active** are different states.

## Existing-address journey

**1. Name the inbox and enter the public address.** For example, Maya at illustrative Harbor Mission enters Donor Care and `donorcare@harbor.example`. The internal inbox name is clearly separate from the address. Do not infer a donor-care team, CRM organization, security classification or access from either field. If the mailbox mixes private employee/care mail, explain that shared Support intake should cover the intended requests only and offer the new-address route. Do not silently forward everything in a personal mailbox.

Validate one mailbox using shared address rules. A typo, multiple addresses, unsupported international form or existing active binding produces a precise field error. If the current user can manage an existing matching inbox, offer that authorized destination rather than creating a duplicate. A conflict outside their scope reveals no tenant/person details. Do not guess aliases, strip plus tags or merge different addresses by name.

**2. Reuse the tenant's shared email connection.** Show what is already qualified and what needs the email administrator. Sending and receiving readiness remain distinct. If no receiving capability is configured, the user reaches the existing integration surface with their candidate preserved. Explain the additional receiving credential to its authorized owner: Resend currently requires Full access to read incoming mail. Asym uses a separate key for receiving and confines its use to receiving/proof operations. Do not mislabel it read-only or reuse the Sending-access key. The everyday responder never sees secrets.

**3. Establish address control and prepare the incoming target.** Preserve P17's external-mailbox access proof before forwarding where applicable, with the same initiating authorized stepped-up actor and protected code. Register candidate capture/recovery before displaying a target that can receive mail. Provider destination confirmation, mailbox access and route verification are separate tasks. A newly managed route uses the separately qualified managed-destination proof, not an Asym challenge surfaced through its own intake.

**4. Give the relevant forwarding instructions.** Ask which mail service or administrative method applies only when the instructions depend on it. Offer clear steps for the qualified Google/Microsoft/other-provider method, an exact copyable target, and **Copy setup instructions**. This preserves the public address; it does not connect an IMAP mailbox or import history. Show **I need my email administrator** as a save-and-handoff path, without emailing secrets or granting a helper inbox/CRM access.

Use wording such as **Complete these steps in your email provider, then return here**. Copy feedback confirms actual clipboard success; if denied, allow selecting the full value. An external policy block leads to its scoped owner instructions or the dedicated-address alternative. Do not tell a tenant to disable all outbound forwarding safeguards. Qualify redirect, mailbox rules, shared mailboxes and groups individually; do not claim every forwarding method preserves the same message source.

**5. Handle provider confirmation where it occurs.** Some providers send a confirmation to the new target before they permit forwarding. Show only the exact expected provider confirmation in the authorized setup step, sanitized and inert until the operator deliberately follows the qualified action. It is not a normal Support conversation, requester message or P17 external-access challenge. A spoofed sender/title, token copied into unrelated mail or browser scanner visit cannot complete proof. If a provider still requires Enable forwarding/Save afterward, keep that step explicit. Seeing its confirmation is not proof forwarding is enabled.

**6. Verify incoming new mail and ordinary replies.** The fixed qualification operation names its actual controlled target and expected outcome before sending. An approved real control mailbox supplies a new incoming message and a reply to the exact canary where required. Status refresh sends nothing. Show Checking until the expected current-generation evidence arrives, and distinguish **Message reached this inbox's receiving route**, **Reply returned correctly**, **Sending qualified** and **Action needed**. A success only proves that observed path at that time; it is not a guarantee about upstream spam filters, mailbox access forever or future delivery.

Unexpected real mail may arrive while this happens. Say, for example, **Mail is arriving while setup is incomplete. It is being held for authorized review.** Show a current safe count or Unknown/loading state and permitted navigation, never bodies to a DNS-only helper. Do not acknowledge, assign or start ordinary targets for setup input. Original source custody and expiry apply from actual receipt.

**7. Review the real recipient-facing identity.** Display:

| Preview line           | Meaning                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------- |
| People write to        | The public incoming Support address.                                                                    |
| Replies come from      | The actual P17-approved display name and From mailbox, which may use the tenant's transactional domain. |
| Their reply returns to | The exact qualified Reply-To destination.                                                               |
| Signature              | The current eligible D23 managed signature presentation.                                                |

This makes a preserved public address compatible with a different approved outgoing domain without misleading the user. Changes to source wording/signature open the existing Email Studio owner with a return path. No editing From/Reply-To strings inside a rich-text body, no new per-inbox template or implicit tenant-wide Default human replies change.

**8. Review who handles the inbox and activate.** Present the existing D6 receiving/handling and D19 intake-review coverage, plus the accepted D13 acknowledgement setting, using their qualified controls. Setup does not invent new roles or silently enable these settings. **Activate inbox** summarizes the actual binding and pending intake consequence. The server rechecks current proof, scope and candidate generation. A conflict preserves the prior good state and explains what must be reviewed; no successful-looking toast hides a failed binding.

**9. Finish with a clear staff transition.** Show the active public address, current verified path and link to the inbox. State that new Support replies are handled in Asym; forwarding does not capture replies written independently in the old mail service. Preserve that service's copy under its own policies rather than promising deletion or synchronization. Retained eligible early mail is reconciled visibly through current intake rules with original timestamps; qualification messages remain excluded. Do not say all prior mail was imported or all received mail is processed merely because activation succeeded.

## Dedicated-address journey

**1. Name the inbox and choose the new address.** For a new Harbor Mission program, an illustrative choice is `care@support.harbor.example`. Explain that this is a dedicated Support destination, not a new personal webmail mailbox or license. The approved local part/domain must be available in the actual tenant receiving registry; provider catch-all reception does not mean every address is active in Asym. Other tenants' registrations are never revealed.

**2. Select or prepare an appropriate receiving domain.** Reuse a qualified tenant-owned receiving domain when available. When ordinary root-domain email already exists, guide a dedicated subdomain. Show the intended domain and the ordinary-mail impact before external changes. Do not replace/add competing root MX records, rewrite website DNS or switch the tenant's transactional sending domain. A sending-verified domain still needs receiving-specific proof.

**3. Reuse the same connection and protected receiving setup.** The shared tenant Resend account, separate receiving credential and authenticated ingress are configured through their existing owner. No new webhook per inbox or second credentials page appears. Setup can identify missing provider plan/capacity facts without pushing an unnecessary upgrade or claiming a different key creates more quota.

**4. Register candidate custody, then show the DNS work.** Only after candidate capture/recovery is ready, display the exact provider-supplied receiving records in Name/Type/Value/Priority fields. Copy preserves bytes; narrow screens wrap or offer an accessible scroll region. **Copy setup instructions** lets the email/domain administrator act outside Asym. Do not build a generic DNS editor or ask them to upload credentials/screenshots as proof. **Check records** inspects current evidence; checking is not activation and should not repeatedly send mail.

An existing conflicting domain or a claim/region/account move has its own owner impact/replacement path. Do not make a destructive provider transfer part of ordinary Add inbox. If DNS propagation or provider proof is pending, preserve progress and show the actual next step, without claiming a universal completion time.

**5. Prove the managed route.** A new managed address has no separate external mailbox in which the owner can safely complete P17's old mailbox-access challenge. Use the typed managed Support proof: qualified domain/account/address binding, controlled new-mail and reply-return evidence, and current authorized monitoring acceptance. Qualification capture can operate before ordinary inbox activation. Only the fixed test producer may use candidate sender/Reply-To state; no donor reply or acknowledgement is enabled as a shortcut around the cycle.

**6. Review identity and operating choices.** Use the same People write to / Replies come from / Their reply returns to / Signature preview and D6/D13/D19 owner settings as the existing-address path. DNS verification does not publish content or change the organization's Default Sender/Default human reply destination. Required rights remain separate even though navigation is coherent.

**7. Activate and make the public address usable.** The same guarded activation installs the current ready binding and durable intake reconciliation. After success, offer Copy address and Open inbox. Publishing it on a website, changing a giving receipt's Reply-To or updating another source still uses that owner's authorized operation; setup does not silently edit CRM, CMS, Email Studio or previous messages. Any early real input remains accounted for under its original source lifetime.

## Complete maintenance behavior

One **Email settings** view reachable from the inbox shows the active address, receiving method, exact From/Reply destination, concise current proof/impact and relevant next action. A pending replacement appears as a candidate beside the working configuration; it does not replace the current values on Save.

| Situation                         | Complete behavior                                                                                                                                                                             |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Save and leave                    | Preserve permitted candidate/proof progress; show Saved only after reconciliation. Never retain secret fields or resend on return.                                                            |
| Switch path                       | Preserve reusable entered fields; invalidate incompatible proof; explain outside forwarding/DNS cleanup if already changed. Existing Active route remains unchanged.                          |
| Cancel setup after mail arrives   | Stop candidate operations, preserve finite custody and give exact external cleanup tasks. Cancel does not undo DNS/forwarding or delete accepted mail.                                        |
| Two administrators edit           | Conditional revision conflict; show authorized current change and preserve local permitted input for review. No last-write-wins route replacement.                                            |
| Change address                    | Create/prove a replacement, review impact and cut over atomically; retain required old-return-route handling with a finite owner plan.                                                        |
| Add another address               | Qualify that exact binding and its use; no automatic wildcard/domain default or new source permissions.                                                                                       |
| Retire an address/inbox           | Review active bindings, early/held input, old replies and pinned send/reconciliation dependencies; stop new use with clear outside cleanup. No automatic closure or retirement autoresponder. |
| Incoming path fails               | Show current known failure and its receiving owner action. Distinguish failure to observe a test from proven routing failure. Preserve accepted source and safe draft/read work.              |
| Sending fails but receiving works | Show that distinction; incoming mail remains accountable, while actual outgoing sends follow P6 gating/recovery.                                                                              |
| Pause an inbox                    | Explain what ordinary processing is paused and that external SMTP/forwarding can continue. Do not disconnect all tenant Resend or erase work.                                                 |
| Rotate or revoke a credential     | Owner-managed protected operation, current proof and bounded event overlap; compromise treats the actual Full-access scope honestly. No keys in support messages.                             |
| Provider/domain migration         | New qualified connection/route generation with owner impact review; old effects reconcile in their original account. No silent transfer/replay.                                               |
| Reconnect/restore                 | Recheck current authority and only affected proof, preserve history/received-at/expiry and never resurrect an old route or purged content.                                                    |

Where the exact source/body cannot be recovered within actual provider availability, state that limitation and retain appropriate body-free evidence. Do not ask requesters to resend as the standard recovery mechanism or imply Asym captured upstream messages that never reached its custody.

## Accessibility and validation

Use Core's exact base-maia/Base UI components, semantic tokens, typography and responsive layout. The initial cards act as an accessible single-choice group, with names and descriptions available to screen readers. Labels explain public address versus internal target. Focus returns correctly after external settings/navigation; long addresses/DNS values remain distinguishable under zoom. Error summaries link to affected fields, valid input remains, and async results are announced politely once rather than every polling tick. A persistent blocker cannot exist only in a toast.

No hover-only help, color-only readiness, automatic advancing on test arrival, clipboard-only access, arbitrary protocol syntax in the first screen, AI setup assistant or complex animation is needed. Keyboard, touch and desktop/mobile administrators receive the same declared operation. Safe low-bandwidth recovery does not weaken verification or silently activate when connectivity returns.

P01–P50 require actual both-path/new-and-existing-tenant/operator-split/negative-case/AT/provider tests before activation. P17's existing staff-proof discipline should be reused where applicable, not replaced by a polished mockup or an invented universal success rate. No live provider, inbox, DNS, message or staff study was performed for this grooming artifact.

## Logical data constraints

**Guidance selection:** stable local selection identity; non-null tenant; qualified source namespace/Site/Page/locale; Active/Removed intent; monotone current generation; trusted created/changed attribution; durable transition receipt. Enforce unique logical source variant per tenant rather than permitting duplicate active rows. Re-add is a new transition, not a new duplicate. Keep source identity immutable within a selection; replacing a source is explicit removal/addition. Preserve CMS numeric/string identifier semantics and existing Support TEXT IDs where used, rather than forcing UUID conversion.

Tenant-aware operational relationships require composite tenant qualification and supporting indexes. A curator's account removal must not cascade away selection/audit history or revive authorization. CMS deletion leaves an unavailable qualified soft reference/tombstone under owner retention, not a cascading operational delete or title-based relink. Tenant teardown follows existing domain deletion/custody requirements, including finite message-derived provenance; “append-only audit” is not permission to retain all content forever.

Source publication, derived eligibility and last proof are not client-writable authorizations. A cached `isPublic` boolean, public URL or last successful resolution cannot grant future use. Source receipts/epochs are qualified by the owner and carry only the minimum identity/generation/disposition needed by current contracts. New table names, fixed sizes, global article IDs and a universal reference registry are not mandated.

**Command boundary:** current authenticated capability plus expected selection generation plus idempotency key/payload digest → one atomic intent/history/receipt/required-continuation write. If a response is lost, query the existing receipt. If the same key carries a different payload, conflict; if source/selection generation is stale, requalify/review rather than overwriting another curator. Source proof is obtained through the owner; an operational commit does not write to Payload in the same transaction. Current source/adverse heads prevent a source that changed during selection from being returned as eligible.

## Grants, RLS and protected fields

The exposed operational model must deny anonymous catalog administration and unauthorized tenant/member access. Distinguish effective SQL grants, RLS row eligibility, column mutation privileges and the authoritative domain command. Test actual allowed reads and denials; an empty result is not proof of authorization correctness.

For mutations verify both existing-row USING and resulting-row WITH CHECK semantics. PostgreSQL 17 can reuse USING when WITH CHECK is omitted; absence of explicit syntax alone is not a vulnerability finding. The question is whether the **effective** new-row rule prevents a permitted user from changing tenant/source/actor/control state. Prefer explicit comprehensible policies while protecting control columns through grants/commands. Broad CRUD RLS is insufficient when it permits client-set actor or safety fields.

Views must preserve underlying actor authorization (for example qualified invoker semantics when suitable), and RPC/function security, execute grants, fixed safe search paths and service-role use must be reviewed together. A privileged service path must supply the same tenant/source/capability checks; calling with a service key is not evidence of user permission. No raw CMS-admin queries or browser access to secret source receipts is introduced. Public media remains subject to its source delivery policy even when the enclosing preview is passive.

## Search and preview

The query is explicit staff input. The shared owner evaluates title, summary and eligible public text over the exact Active selected corpus, ranked in that order with stable identity tie-break. D27 requires this behavior; partial title-only implementations are not silently treated as complete. Use P23's qualified Postgres search projection and batch current-head approach; extra infrastructure requires measured evidence.

Selection filtering and current tenant/Site/locale/public-generation/safety checks precede pagination, counts and snippets. An ordinary public search endpoint that deliberately excludes Shared-by-link Pages cannot be the exhaustive Guidance source: extend the **same owner** with a private staff-catalog query contract over explicitly selected sources, preserving each source's public access proof. This is a private operational selection projection, not a new public search inclusion rule or new authority for article content.

Only return safe source text and public metadata. The preview does not hydrate forms/giving components, execute CMS HTML or expose draft/editor fields. Owner-rendered safe public text/media is preferred; link insertion uses D23's existing Tiptap semantics. No Lexical-to-Tiptap article conversion. Cache keys/projection records are qualified by environment/tenant/source/Site/locale, selection/current public generations and applicable authorization scope; no forbidden hit/count/snippet can survive a favorable stale cache.

A CMS restore is not a public release. A sent link is historical message content, not an eternal promise the public Page remains available. ## Email Studio, Tiptap and P6 sequence

1. Staff chooses a qualified public source in Guidance. Support verifies current draft/purpose/access and source selection/public proof, then performs one editor transaction. Visible content is a normal link. Trusted provenance uses the existing typed source-occurrence grammar; arbitrary pasted HTML attributes cannot forge qualification.
2. Draft editing, Undo, recovery and saved wording follow D18/D23 source rules. Editing text preserves source provenance; changing href removes the approved-source assertion for that destination while known source-derived material restrictions remain. No policy pretends to recognize arbitrary manually retyped URLs. The normal link dialog must make the changed destination visible.
3. When preparing an email, P17 qualifies source occurrences/current public-purpose destination and existing signature/sender/audience/rendering. It freezes the exact resulting label/href and body into the same immutable preparation as the rest of the reply. It owns the minimal source-material manifest and current safety epoch/fence relationship. Support does not store a second article or generate a separate signature/preparation.
4. Support admits the actual reply under current conversation/inbox/audience/work authorization. P6 dispatch checks the existing qualified local source/material safety fences at its current atomic submission boundary. Adverse fence wins before submission → do not submit; possible submission wins first → reconcile exact attempt, never guess failure and resend. No CMS, URL fetch, editor render or source substitution occurs here.
5. Internal notes use their existing internal document/policy path and never enter P6 merely because they contain a public Guidance link. Guidance does not change a recipient, add CC, trigger a shortcut/work effect, choose a signature or complete a business action.

The source-family extension must specify issuer/consumer ownership, adverse-first local fence publication, version compatibility and recovery under existing P17/P23 machinery before activation. A UI disabled state or eventually removed search index alone cannot enforce withdrawal. An outage after sealing does not require fetching the CMS again; the existing local material contract is the dispatch authority.

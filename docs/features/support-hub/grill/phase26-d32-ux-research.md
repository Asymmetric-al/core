# D32 C — Broader attachment inspection: independent UX research

**13 September 2026. Founder selected C; the detailed amendments below are research proposals for the parent review, not independently ratified requirements.** This report addresses a useful, bounded read-only attachment viewer and its full staff journey. It does not implement a viewer, qualify a renderer, certify accessibility, change source permissions or create a file-management surface.

## Recommendation and scope

Accept C with required fidelity, accessibility and source-safety amendments. Provide deliberate in-Support preview of **PNG, JPEG, WebP, static GIF, PDF, DOCX, XLSX, PPTX, TXT and CSV**, each with an explicit supported reading mode. Keep **Download original** a separate, currently authorized action. These formats are a considered initial product set, not a measured statement about Asym tenant attachment prevalence. A file extension alone never establishes actual type, safety, eligibility or renderability.

The broader choice should actually deliver useful Office/text inspection before it is called complete. It should not be declared fulfilled by image/PDF previews with Office placeholders. Equally, it should not become a promise to faithfully reproduce every feature of Office or accept every historical format. Legacy DOC/XLS/PPT, macro-enabled documents/templates, encrypted files, open-document formats, HEIC/HEIF and other unqualified types receive the honest unsupported-preview treatment, with original download only where the existing source policy permits it. Adding another type later requires qualification of that type, not another tenant setting.

The strongest alternative A would avoid the Office fidelity and maintenance burden and remains simpler, but the founder has explicitly chosen the additional convenience of C. B remains useful for specialized files that require their original application; requiring it for all inspection creates avoidable context switching. Neither alternative removes the existing malware, authorization, deletion or privacy obligations.

## Governing seams checked

- [D16 R15](phase26-d16-adversarial-review.md) applies source restriction to attachment bytes, inline occurrences and derived representations. A preview is not binary redaction and does not change the original.
- [D19 R06](phase26-d19-adversarial-review.md) requires separately qualified byte access and hygiene for intake inspection. Pending or failed checks are not a clean result.
- [D22 R21](phase26-d22-adversarial-review.md) allows qualified filename discovery even when preview is unsupported. Search does not open bytes automatically, and this viewer does not add attachment-content search, OCR or AI indexing.
- [D26](phase26-d26-adversarial-review.md) preserves one authorized Support detail through CRM. Opening the same attachment there does not create a second CRM file or grant Support readers access to a separate restricted business artifact.
- [D23](phase26-d23-adversarial-review.md) uses Tiptap for rich-text authoring. A read-only Office/PDF viewer is not a Tiptap editor, and its chrome should use the shared product controls. No new editor, annotation or conversion-to-reply action is implied.
- [Phase 29 roadmap](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L3146) owns immutable bytes, private access, hygiene and file audit. The inspected source does not establish a ready, qualified general Office renderer. The narrow consumer must be qualified without requiring a whole File Manager to ship first.

These are repository/accepted-session boundaries. The preceding Q32 report remains historical option research; its earlier recommendation of A is superseded by the founder's selection of C, not silently rewritten.

## Fidelity evidence that changes the design

Microsoft's [Office format reference](https://learn.microsoft.com/en-us/office/compatibility/office-file-format-reference) distinguishes current OOXML, legacy binary and macro-enabled formats. For example, XLSX cannot store VBA or Excel 4.0 macro sheets, unlike macro-enabled variants. This supports separating the qualification paths; it does not make ordinary XLSX inert or safe by extension.

[SpreadsheetML formula documentation](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-formulas) identifies an optional saved formula-result value from the last calculation. It may be missing. Microsoft's [external-link calculation guidance](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/excel/external-links-calculated-open-workbook-earlier-version-excel), updated **30 March 2026**, shows why opening a workbook in another engine can recalculate external references. Asym's reading mode must preserve the saved evidence, not silently compute or fetch a new answer.

Microsoft's [hidden-data guidance](https://support.microsoft.com/en-us/office/collab-files/remove-hidden-data-and-personal-information-by-inspecting-documents-presentations-or-workbooks) documents hidden workbook data and comments/metadata, including cases an inspection tool may not detect. Hiding is not removal or access control. The recommendation is to state the preview's coverage and preserve the original, not to imitate Document Inspector or promise sanitization.

[Word's Track Changes guidance](https://support.microsoft.com/en-us/word/training/track-changes-in-word) distinguishes hiding markup from accepting/rejecting revisions. [PowerPoint's hidden-slide guidance](https://support.microsoft.com/en-us/powerpoint/hide-or-show-a-slide) explains that a hidden slide stays in the file while being omitted from ordinary presentation. A preview may use a declared reading mode, but must not call that mode the complete or legally final document.

[LibreOffice's PDF export reference](https://help.libreoffice.org/latest/en-US/text/shared/01/ref_pdf_export_general.html) exposes settings that affect notes, comments and hidden slides. Its whole-sheet export ignores print areas and visibility and can include hidden sheets. Conversely, ordinary print layout can omit spreadsheet data. Therefore a generic Office-to-PDF conversion is not an adequate spreadsheet contract. This is evidence to qualify renderer behavior, not a selection of LibreOffice or a specific version.

[Apple's HEIF guidance](https://support.apple.com/en-au/116944), dated **19 December 2025**, says certain sharing paths may convert media for compatibility. Conversion is conditional. An unsupported HEIC attachment must be identified honestly; the product cannot assume every email sender already converted it to JPEG.

XLSX charts, pivot behavior, comments and other features outside saved cells must not be silently called complete. Preserve distinctions between an actually empty cell, an unavailable saved formula result, a saved error and content excluded by the reading mode. Hidden rows/columns retain gaps in their original indices. There is no Unhide switch in this initial viewer. Omitting hidden content is not a security barrier: an independently authorized original download may contain it.

For DOCX/PPTX, detecting the existence of comments/revisions/hidden content is different from rendering it. A concise **Preview omits some document features** notice can expand to the detected details. When detection cannot establish a count or absence, state the supported mode instead of inventing a count or claiming there are no omissions. Generated text layers must use the same scope as the visible projection; a raw XML text dump would leak omitted content and contradict the mode.

### CSV and encoding: a small explicit control, not an import wizard

Recommendation to the parent: use **Comma** initially, with a per-view **Delimiter: Comma / Semicolon / Tab** control and **View as text**. No persisted personal/tenant delimiter settings, guessed schema, encoding wizard or column-type selector. The selected delimiter belongs to the rendering request/derivative identity. This recommendation is not an independently ratified addition.

This small control handles a real compatibility distinction: Microsoft's current [Excel text/CSV guide](https://support.microsoft.com/en-us/excel/get-started/import-or-export-text-txt-or-csv-files), applicable to Microsoft 365/2024/2021/2019/2016, documents semicolon output under decimal/list separator settings and deliberate delimiter selection with immediate preview. It also warns that ordinary opening can reinterpret dates and remove leading zeros. Asym should display strings rather than inherit that interpretation.

[RFC 4180](https://www.rfc-editor.org/rfc/rfc4180.html) is an **Informational** RFC from October 2005, not a universal mandatory CSV standard. Its comma/quote rules and acknowledged variations are useful parser evidence. Adopt explicit handling of quoted delimiters, doubled quotes and embedded line breaks; support common LF/CRLF line endings. Do not invent a header row, silently drop ragged records or auto-switch delimiters because a valid single-column file contains semicolons. A malformed selected table view falls back to an explicit parsing failure with literal Text available when decoding is qualified.

Support strict **UTF-8 with or without BOM**, and **UTF-16 LE/BE only when a BOM identifies it**, for TXT/CSV. Other valid encodings remain outside this initial supported subset. [Unicode's encoding/BOM guidance](https://www.unicode.org/faq/utf_bom.html) supports the distinction between encoding validity and byte-order identification; it does not require this product subset. Unknown or malformed decoding must not yield quietly corrupted names/amounts. A plain-language unavailable state is preferable to confident mojibake.

## Complete use journey

1. **Find the source file in context.** The message's attachment card shows currently permitted filename, type, size and availability. Source conversation/message identity remains clear when duplicate names occur. Filenames are escaped data with safe bidi handling, not HTML or commands. D22 search reaches the source occurrence without automatically fetching the document.
2. **Open deliberately.** **Preview** opens a focused shared viewer above the same Support detail. In CRM it uses that same detail and current permissions. Metadata and loading state appear promptly; heavy document code/data is requested only for the selected file. No hover-open, whole-thread prefetch or silent local download.
3. **Understand the result.** The header names the file and provides **Close** and independently eligible **Download original**. Show only the controls relevant to this format. An image does not receive a document ribbon; a spreadsheet receives a sheet selector instead of misleading PDF pages. Original page/slide/row coordinates remain meaningful.
4. **Read without side effects.** Use page/sheet navigation, fit/zoom or literal table/text reading. A compact coverage notice appears when relevant, with details available on demand. Merely opening, scrolling or closing does not mark a business task complete, acknowledge evidence as valid, change message state or add a CRM interaction. Required file-access auditing remains with its owner.
5. **Handle a problem in place.** A temporary preparation failure offers a bounded deliberate retry when the current owner still permits it. Unsupported or oversized preview explains why viewing is unavailable; original download is offered only if independently permitted. Neither failure opens the file elsewhere automatically. Closing remains available throughout.
6. **Return to work.** Close/Escape returns focus to the invoking attachment control, restores permitted conversation/list/search/CRM context and preserves the actual draft. If the source or permission disappeared, return to a safe available context with a truthful notice, not to stale content. Browser Back should have a predictable one-step return and not lose the draft.

Opening another file must not confuse file navigation with page navigation. A first implementation can open one selected file at a time and return to the existing message cards; a whole-conversation attachment gallery is not necessary to satisfy C. If adjacent-file navigation is used by shared chrome, it must stay within the currently qualified explicit source set and label **Next file** separately from **Next page**.

Original download is exactly the qualified source bytes, not the converted preview renamed as the original. No Copy public link, bulk ZIP, attach to CRM, send, print workflow or document edit action is added by D32. The browser/OS may handle a deliberate download under its settings; the product should not claim to control every external destination or revoke a previously independent download.

## Mobile, accessibility and low-bandwidth requirements

The viewer should use Core's shared visual system and focus handling. On narrow screens it can occupy the available viewport with a stable Close/file header and compact format controls, rather than nesting an unusably small preview inside several drawers. Retain visible control labels, readable type and touch targets. Do not rely on hover, drag-only pan, color, a tiny icon or a keyboard shortcut alone.

W3C's [modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) supports deliberate focus placement, keyboard containment and returning focus to the invoking control. Its [reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) distinguishes ordinary interface content from genuinely two-dimensional tables/images. The toolbar and explanations should reflow; a spreadsheet may retain contained horizontal navigation with understandable coordinates. Keyboard paging must not hijack text selection or unrelated Support commands.

A picture of a document is **not automatically an accessible equivalent**. W3C's [non-text-content guidance](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html) requires equivalent-purpose alternatives where applicable. Provide faithful existing text, reading order and table semantics from the same permitted projection; do not expose hidden/comment XML in a supposedly accessible alternative. PDF scan images without meaningful source text, images without descriptions and complex slide graphics retain an honestly identified limitation. No OCR or AI-generated description is added here, and Download alone is not proof of equivalent access. Accessibility qualification must test the supported source classes and document the residual source-content limitation without claiming universal compliance.

Use on-demand chunks/pages and bounded image sizes while keeping reading position stable. Do not create hundreds of off-screen canvases or a giant invisible accessibility DOM. Announce loading/error/page changes sufficiently for assistive technology without streaming every background event. Test keyboard-only, screen readers, high zoom, reduced motion, low bandwidth, long Unicode/RTL filenames and mobile portrait. There has been no browser prototype, assistive-technology test or tenant usability study in this research pass.

| 200 MiB expanded content              | Hard aggregate expansion budget for compressed/container content; entry count, nesting, memory, output and processing time still require separate bounded implementation guards.                                                                                                      |
| 200 pages/slides                      | Total eligible document surface as defined by the format profile, with original indexing. If total exceeds the contract, return a typed limited/unavailable result; do not silently pretend the first 200 are complete.                                                               |
| 40 megapixels                         | Specify 40,000,000 source pixels and applicable per-image/aggregate rules. Decoded memory and intermediate render surfaces need their own budget; pixel count alone is not a memory limit.                                                                                            |
| 100,000 spreadsheet cells / 50 sheets | Define whether total stored cells and sheets or only visible rendered cells count. Page/sheet/chunk navigation within a qualified total is not silent truncation. Unknown coverage, parser failure and budget exhaustion must be different outcomes from a genuine empty document. No universal latency claim is supported by these numbers. Before release, representative production-shaped fixtures, maximum-plus-one cases and malicious expansion/resource cases must establish actual memory/time budgets and usable first-preview behavior. Platform ownership should maintain these implementation budgets; tenant staff should not administer parser switches or resource quotas.

## Maintenance and recovery journey

Staff do not create, save or publish a preview. They inspect an existing source occurrence. Its source owner retains upload/replacement/removal authority; a changed file means a different immutable byte identity, never a silent mutation underneath an old viewer. Saved replies/signatures/guidance do not become file-preview owners merely because they can reference an attachment or logo.

The shared byte/rendering maintainer owns format profiles, resource guards, qualified renderer versions and failures. Support surfaces the current owner result. A broken format can be disabled for preview while separately permitted original download and other qualified formats continue. A source restriction disables all its representations independently of an ordinary renderer outage. No staff-facing Apply anyway, Ignore scan or developer database repair routine is introduced.

Operational signals should distinguish unsupported type, supported-format render failure, budget rejection, safety denial and permission change without logging document text or raw secret URLs. Owner triage uses opaque source/job identity and profile version. Replaying a conversion rechecks current source eligibility and cannot reset retention or resurrect removed content. The parent operations contract should set thresholds based on qualified launch budgets; no unsupported numerical incident threshold is invented here.

## Proof and final independent disposition

**Accept with required amendments.** C is useful when it means a bounded set of reliable reading modes with honest omissions and fast return to Support work. Its main failure would be making a screenshot of a conversion look more authoritative than it is.

Before claiming the finished experience, prove: (1) each selected format's successful reading journey; (2) source permission/restriction races; (3) exact original download; (4) Office hidden/revision/comment and cache behavior; (5) multilingual/CSV fidelity; (6) resource boundary outcomes; (7) keyboard/mobile/assistive-technology journeys; (8) Support and CRM draft return; and (9) renderer update/disable/replay behavior. These are required future implementation/release proofs, **not tests executed during this grooming report**.

No source establishes that the proposed format list, ceilings or layout is optimal for Asym users. The choices are reasoned product judgments, with explicit compatibility boundaries and independently testable outcomes. No source establishes universal legal or accessibility compliance for arbitrary received documents. The source-grounded contract is ready for parent synthesis; renderer/provider selection and actual implementation proof remain honestly unexecuted.

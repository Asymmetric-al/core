# D16 independent vendor and UX review

Checked 11 September 2026. Scope: the selected answer, **selective permanent redaction of Support conversation content**, with a clean correction journey and coherent CRM presentation. This is research and proposed design, not an implementation or accessibility/compliance certification. Existing Q16 research was read first; primary sources were opened again and targeted gaps researched. Root owns legal and repository synthesis. No account, message, provider, production, or governed document was changed.

## Disposition

**Accept with required amendments.** A is the strongest normal correction behavior: deliberately remove the selected private material while retaining useful context and admissible communication facts. Keep whole-body and whole-file removal as explicit fallbacks. Do not retain an ordinary revealable original merely to enable Undo. Do not bundle a scanner, image editor, generic privacy case system, or whole-CRM erasure flow into this capability.

The recommendation is Asym product judgment. Vendor documentation demonstrates available patterns and known failure conditions; it does not establish universal consensus, measured success, or a ministry adoption study.

## Fresh evidence: documented behavior, tradeoffs and fit

### Zendesk: primary selective-redaction comparator

Agent Workspace supports authorized selection of text and whole images/attachments, unmarking before commit and irreversible redaction. Custom-role permission varies by plan; plans without custom roles use delete-ticket permission. The May 1, 2026 guide permits several closed/archived channel types. It documents repeated-instance omissions, non-redactable copied merge notes, original-email visibility loss, external copies and stale browser summaries. Redaction can fire ticket-update triggers. These limitations make source-aware cleanup essential. [Zendesk, Redacting ticket content](https://support.zendesk.com/hc/en-us/articles/4408846470170-Redacting-ticket-content/)

**Adopt:** mark/review/unmark/commit and a correction marker. **Reject:** copied merge evidence surviving correction, automatic work-state side effects, hover-only discovery and claims of external recall. Do not import Zendesk's 75-attachment limit or its channel restrictions as Asym product requirements. The article establishes behavior, not underlying storage architecture or tested disposal guarantees.

### Kustomer: manual selection with a distinct permission

Official indexed article text, now exposing **Last Update: February 2023**, describes selecting Message Redaction, highlighting text, applying Redact and then Commit Redaction. Direct article extraction remains empty. Separate official access documentation identifies **Redact Messages** as a permanent additional conversation action. Exact current plan entitlement is not established. [Kustomer, Message options](https://help.kustomer.com/message-options-H1tSk3QOI), [Kustomer, Define user access](https://help.kustomer.com/define-user-access-S17nw7IJv)

**Adopt:** a separately authorized correction action and explicit commitment boundary. **Do not infer:** customer-wide access, attachment disposition, raw MIME disposal or CRM identity mutation from this UI. A 2023 help article still indexed today is weaker evidence for an exact current interface than a tested account.

### HubSpot: distinguish masking, scanning and Help Desk

The **July 22, 2026** CRM Inbox guide documents Enterprise-only Hide message, an inbox placeholder and removal from logged CRM timelines. The original hider or Super Admin can Unhide and restore the original record appearances. This is reversible masking. [HubSpot, Conversations inbox](https://knowledge.hubspot.com/inbox/use-the-conversations-inbox)

The **January 22, 2026** Enterprise Sensitive Data guide separately supports Super Admin scanning of CRM activities from the last 60 days, once every 30 days, with review and permanent replacement of selected detected values when Sensitive Data is enabled. This is a bounded security scanner, not evidence of arbitrary manual message redaction in Help Desk. [HubSpot, Scan and redact Sensitive Data](https://knowledge.hubspot.com/account-security/scan-and-redact-sensitive-data)

**Adopt:** corrected presentation follows the same communication into CRM. **Reject:** interpreting Hide as permanent removal, inferring current Help Desk capabilities from CRM Inbox, copying a scanner's constraints, or deleting the contact/ticket to fix a paragraph. Core should project current authorized source content rather than synchronize multiple editable copies.

### Help Scout: useful distinction, explicitly early access

The opened **September 9, 2026** article labels Advanced Privacy Controls **early access**. New incoming conversations are scanned using Amazon Comprehend; detected PII is masked while a restricted original is temporarily retained, then disposed of under configured retention. Earlier conversations are not automatically updated. Attachments bypass the masking permission until retention disposal. [Help Scout, Advanced Privacy Controls](https://docs.helpscout.com/article/1754-advanced-privacy-controls)

**Use as evidence:** masking and permanent disposal have different states. **Reject for A:** a routinely revealable original, unrestricted attachment exception, and an NLP vendor dependency. Early-access status means this is not proof of a mature default suitable for every ministry. Independent prior reads saw September 8–9; exact day is immaterial.

### Intercom: narrow API versus automatic intake rules

The current API reference selector/default is **v2.16**. Redaction addresses a conversation part with a body, or a contact-created source message; other sources return a not-redactable error. It does not expose arbitrary text ranges in this request. [Intercom, Redact a conversation part](https://developers.intercom.com/docs/references/rest-api/api.intercom.io/conversations/redactconversation)

The **March 4, 2026** rules guide describes a separate irreversible intake scanner. It warns of false positives and skips a regex rule if runtime evaluation times out. [Intercom, Custom redaction rules](https://www.intercom.com/help/en/articles/13925174-redacting-sensitive-data-in-conversations-with-custom-rules)

**Adopt:** explicit supported-object eligibility and honest unavailable outcomes. **Do not copy:** a generic regex engine or a claim that all sensitive material is detected. Do not recommend pasting actual private content into third-party regex testers, despite that guide's generic testing suggestion. Synthetic examples suffice for separately authorized detector research.

### Zoho Desk: broader erasure is a different owner workflow

Zoho's current undated primary guide supports authorized Data Subject Requests for selected or all matched records across modules, with permanent deletion and optional reference-ticket linkage. Its documented permission crosses departments. [Zoho Desk, Addressing Data Subject Requests](https://help.zoho.com/portal/en/kb/desk/user-management-and-security/compliance/articles/addressing-data-subject-requests)

**Adopt:** a support conversation can record a reference to a separately authorized privacy action. **Reject:** treating narrow redaction as complete data-subject erasure, allowing an email match to prove authority, or importing department-wide privilege into Core. No current arbitrary-text native redaction claim was verified; this is not evidence of absence.

### BoldDesk: useful whole-body fallback

The current undated official article documents authorized whole reply/note deletion, confirmation, a marker, attachment/inline-image removal, and no recall or new deletion notification. [BoldDesk, Delete a ticket reply or note](https://support.bolddesk.com/kb/article/266/how-to-delete-a-ticket-reply-or-note-message)

**Adopt:** obvious continuity marker and whole-body fallback. **Reject:** automatically deleting every attachment when the actor selected only text; deleting the entire conversation; or a restriction that requires retaining an affected public reply despite an owning-domain disposal obligation.

## Accessible irreversible correction: primary guidance

WCAG **3.3.4** permits a review/confirm/correct mechanism before final submission as an alternative to reversibility for relevant destructive data operations. It does not mandate post-commit Undo. A meaningful preview and one clear confirmation are sufficient design direction; extra checkboxes, retyped secrets and multiple warning dialogs are not necessary merely to satisfy this criterion. The Understanding document is informative guidance. [W3C, Error Prevention](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)

Use the existing accessible dialog/panel primitives. Initial focus must reveal the heading and context; for an irreversible final step, focus on the least destructive action is appropriate. Keep focus inside a modal and return it to the triggering message action or its stable correction marker. Escape cancels/closes before commitment. These are pattern recommendations, not proof that using a dialog component guarantees conformance. [W3C APG, Modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

All author-defined functionality needs keyboard operation. Do not make hover, custom drag selection or color the only path. Native text selection and a reviewed accessible text representation can avoid inventing a selection canvas. [W3C, Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)

If custom drag selection is introduced, provide equivalent non-drag single-pointer operation; keyboard equivalence alone does not satisfy **2.5.7**. Unmodified user-agent behavior is treated differently. A whole-body fallback is helpful but is not automatically equivalent to precise selective removal. [W3C, Dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

For authored targets, meet **2.5.8**'s 24×24 CSS-pixel minimum or a valid exception; larger well-spaced destructive controls are sensible. Do not mislabel 44 pixels as the universal AA minimum. [W3C, Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

Progress and completion should be exposed programmatically without unnecessary focus changes or repetitive announcements. A persistent result in the message is essential; a short toast is not the only evidence. [W3C, Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

Sticky review actions must not entirely hide the focused element, including at zoom and with mobile keyboards. [W3C, Focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

## Proposed Asym journey and exact product language

These recommendations are original design judgments and must be reconciled with root's owner/lifecycle contract.

1. **Entry in context.** Place **Remove sensitive content…** in the original message's existing action menu for currently qualified staff. Make the menu available by focus and touch. Do not expose permanent removal to everyone merely because they can read, follow or answer. Staff without that capability get the established safe route to a qualified handler, with a source reference rather than a pasted secret.
2. **One focused correction surface.** Show the original message identity, author/time and current representation. Short instruction: **Select the text or files to remove. The rest of this message will stay.** Keep the conversation scroll, surrounding context and unsent reply draft intact unless that draft itself is affected by the correction.
3. **Exact selection, no rewrite.** Selection may mark multiple occurrences in one original message and whole selected attachments/inline images. Whole-body selection is separate from attachment selection. The UI cannot be a general message editor; it cannot replace the author's words with arbitrary staff text. Expand quoted/collapsed content in selection mode so the user can inspect it. The owner must map selections to a current immutable source revision; stale mapping is a failure to review again, never best-effort substring deletion.
4. **Accessible precision.** Prefer native selection in a labelled, read-only accessible text view over an invented canvas. Keyboard users can select text using familiar caret/range controls. For HTML, the canonical text map must preserve paragraph boundaries, entities, grapheme boundaries, bidirectional content and target mapping. The final accessibility approach must support actual partial selection, not force disabled users to remove the entire body. Test native browser/assistive-technology behavior before declaring the control accessible.
5. **Link and metadata honesty.** A visible link label may conceal a sensitive URL. Selection mode must make each retained link target inspectable without opening/fetching it. Selecting a link for removal removes the affected complete link object, including its target/auxiliary text; the preview makes that expanded scope visible. Pure text-range correction is not represented as having inspected every unrelated field. Message subject or other affected metadata requires the owner's explicit field correction/removal route; do not leave it searchable simply because body text was removed. Prefer whole affected field/body removal when a precise mapping cannot be proved.
6. **Files are whole files.** List the files selected for removal with a count and ordinary metadata only while the actor is authorized to inspect them. Do not offer drawing black rectangles on PDFs/images or in-place binary editing. The file action covers inline occurrence, derivative preview and downloadable content through the owner contract. A source attachment identical to a separate owner artifact must not silently delete that other owner's authoritative document.
7. **After removal.** Provide an accessible after-state preview. Selected ranges become uniform **Content removed** markers; files become **Attachment removed**. Do not encode original character count, last digits, secrets, URLs or filenames in markers. Show selection counts and permit **Change selection** and **Cancel**. Do not echo the removed secret into reason fields, telemetry, audit or clipboard prompts. If a reason is required, use a bounded content-free category; no mandatory prose explanation or typed secret.
8. **One meaningful confirmation.** Final button: **Permanently remove selected content**. Copy: **This cannot be undone in Asym. It does not recall emails or files already sent or downloaded.** Do not add a second generic “Are you sure?” after this reviewed commitment. No automatic submit from Enter in a search/control field. No need for a second person or timer solely because the operation is irreversible; actual policy can independently require qualified review.
9. **Truthful execution.** No optimistic completion. Before server acceptance, selection is only a draft. After acceptance, closing the panel does not cancel an in-progress permanent operation; return to the source and show its real result. A lost response resolves through the durable operation identity, not a new destructive request. The state labels below must reflect actual owner evidence.
10. **Quiet continuity.** Use the same corrected source representation in Support and every authorized CRM appearance. Keep message position and permitted communication facts; do not create a duplicate CRM activity or change linked people, conversation assignment, reply target, resolution or related action completion. Ordinary readers see a neutral marker, with body-free details available only where authorized. No requester email or D15 follower alert merely because material was removed; separate incident or privacy communication remains an explicitly authorized owner action.

| Verified operation condition                                    | Main message state                                      | Qualified details and action                                                                                                                                                            |
| --------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nothing accepted; selection stale, invalid or unsupported       | Existing content remains unless independently contained | **This message changed. Review the current content before removing anything.** Or specific safe unsupported explanation. Do not imply containment happened.                             |
| Owner has enforced suppression; required disposal still running | **Content unavailable. Removal in progress.**           | Content-free operation status; expected action, not a fake completion percentage.                                                                                                       |
| Required preserved copy/hold prevents permanent disposal        | **Content restricted.**                                 | Qualified handler sees **Preservation required. Permanent removal is unavailable.** and actual owner route. Ordinary readers do not receive confidential hold facts or a reveal button. |
| Disposal needs intervention after suppression                   | **Content unavailable. Removal needs attention.**       | Named owner, safe failure reason and durable retry/reconcile action. Never restore automatically because cleanup failed.                                                                |

The precise state machine belongs to the root review. The important UX invariant is that **unavailable**, **restricted**, **in progress** and **removed** are not synonyms. Do not overwhelm ordinary readers with a storage dependency dashboard; show operational detail to the qualified handler and use a stable source marker for everyone else.

## Proof that is still required, not performed here

- Keyboard-only and screen-reader select/review/unmark/cancel/commit; pointer-only operation for any custom dragging; menu access without hover; sensible focus after all outcomes.
- Long mixed HTML/text, nested quotes, repeated identical strings, emoji, combining marks, Thai text, RTL, malicious attributes, zero-width characters and sensitive URL target with innocent visible label. Preview must equal the owner-computed after-state, including whole-link expansion.
- Touch narrow screen, 200%/400% zoom and mobile keyboard with no hidden final controls; clear truncation and a way to inspect the exact selected occurrence.
- Redaction of one file from several; inline/thumbnail/original-download routes; generic marker; unchanged unrelated file and genuine owner document.
- Simultaneous correction, send, source revision, merge/Undo, permission revocation and stale browser response; no misleading success, no restored original, no new notification storm.
- CRM appearance and Support appearance resolve to the same safe source; restricted CRM users receive no additional context or audit detail; body-free event identity and target metrics survive.
- Failure before acceptance versus failure after containment; lost response reconciliation; provider cleanup and backup restore restrictions shown accurately to qualified operators.

No browser/UI build, live tenant usability study, deletion test, performance benchmark, or legal applicability determination was conducted by this reviewer. Official docs substantiate only the behaviors described above. The blueprint is ready for root's repository/legal/lifecycle reconciliation and founder ratification, not a claim of a shipping feature.

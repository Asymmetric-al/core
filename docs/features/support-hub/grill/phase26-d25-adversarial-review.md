# Equal-path Support inbox setup

**D25 and every adopted amendment are fully founder-ratified, 12 September 2026. Historical disposition: Accept with required amendments.** C, all 32 clauses, 23 category findings, complete UX/data/Email Studio/CRM/provider contracts, four terms and required proof are accepted. D1–D25 are fully ratified as grooming, not implemented behavior or formal specification.

Both routes lead to the same qualified Support inbox. The first choice is familiar: **Use an existing Support address** or **Create a new Support address**. The consequential work is verifying the right facts, safely receiving mail during setup and keeping later repair understandable. The [step-by-step UX](phase26-d25-setup-ux.md), [ownership/data/Email Studio contract](phase26-d25-data-contract.md) and [evidence](phase26-d25-evidence.md) form the complete record with the independent reviews.

## Corrected decision clauses

### D25-R01 — Equal plain-language paths, one receiving product

Present the two initial address choices with equal prominence and no preselection, then show only the selected guide. A known suitable existing address and a fresh dedicated address are both legitimate starting points. Preserve progress when switching or returning. This selects onboarding behavior over the already-scoped forwarding and BYO receiving capabilities; it adds no Gmail/Microsoft mailbox sync, history import, telephony, public help center, AI or multi-provider mail platform.

A, existing-address-first, is strongest when an appropriate address is already known. B, dedicated-address-first, is strongest for a known fresh program or separate intake. C avoids presuming tenant prevalence and asks one understandable factual choice. This is product judgment, not measured conversion advantage or evidence that every ministry has the same workflow.

### D25-R02 — Keep the address, inbox, team and public identity distinct

An inbox is the authorized Support work destination; its name and handling team are not email addresses or CRM owners. The public incoming address, exact receiving route, outgoing From, Reply-To destination and managed signature are separate facts. Show a recipient-facing preview with each actual value before activation. Keeping `donorcare@harbor.example` as a public contact address does not promise it can be the From address under P17's approved transactional domain. No login/assignee/private profile fallback invents identity.

The founder's mission/donor-care context is the target population. Named examples illustrate possible use, not proven tenant frequencies. A personal employee mailbox or mixed confidential ministry mailbox is not presumed appropriate for shared Support intake. Select the intended Support scope and owning privacy boundary before forwarding; restricted care remains with its actual owner.

### D25-R03 — A focused, resumable setup surface

Enter from Support inbox settings or the empty-inbox state with tenant/inbox context intact. The common journey is address choice, address and route, qualified connection checks, verification, then review and activation. Show concise progress and one next actionable issue, reusing existing integration/domain settings through contextual navigation. Save safe incomplete configuration as Draft; no raw state flag can make it Ready or Active. Simple names, addresses and DNS instructions are ordinary inputs; Tiptap is reserved for the already-qualified content surfaces.

Saving, Leaving setup or returning from provider settings does not activate, send, delete captured input or erase completed valid proof. Back preserves shared fields and branch-specific candidate information. An unknown save outcome reconciles the same command before showing Saved. Secrets and challenges never enter persistent browser form state. Do not reset typed fields whenever an unrelated query refresh arrives.

### D25-R04 — Split responsibilities without transferring authority

Use current Core capabilities to distinguish Support configuration, current source/inbox access, tenant delivery/credential/domain administration, P17 reply-destination acceptance, and D19 review/coverage. Provider/DNS changes require the tenant's actual outside administrative authority. Configuration access does not reveal donor messages; permission to read Support mail does not reveal credentials or confer domain administration.

Provide copyable nonsecret instructions and an authenticated return location for another qualified administrator. Sharing instructions grants no role or challenge completion right and sends no email itself. Provider/P17 secrets use the existing protected owner handoff; no emailed key, transferable verification token or new approval-routing system. Current permissions and step-up requirements are rechecked at each consequential command and after an administrator departs.

### D25-R05 — Extend the shared Resend owner explicitly for receiving

Retain the tenant's single P6/P17 Resend account/team ownership and connection aggregate. Preserve the domain-restricted Sending-access credential for outbound. Receiving API hydration cannot use that key: current Resend documents only `sending_access` and `full_access`; OAuth also requires `full_access` for non-send routes. Add one purpose-separated inbound credential facet under the same managed encrypted revision/custody controls. Do not widen or replace the outgoing key or create a global fallback.

The receiving credential currently has provider-level Full access. State that honestly to the authorized connection administrator; it is not a provider-enforced read-only credential. Confine its use to the qualified server ingestion/repair adapter's closed read operations and exact registered connection resources; never expose a generic proxy, outbound sending, domain/key/webhook mutation or credential to ordinary Support. Same-account proof uses current exact provider objects/canary evidence linked to the shared connection, not labels, key hints or caller metadata. A pending unproved credential may perform only those bounded account-proof reads, never ordinary incoming body/attachment retrieval or exposure. Prove positive and wrong-account behavior before activation. OAuth adds no narrower privilege today and is not introduced here. This is an explicit P26 receiving-purpose extension to the outbound-only credential contract, with residual credential-compromise risk and mandatory owner controls.

### D25-R06 — Authenticate provider scope before trusting message data

### D25-R09 — Existing-address path preserves continuity with truthful limits

### D25-R10 — Dedicated-address path isolates receiving without replacing ordinary mail

Ask for a new address on a suitable tenant-owned receiving domain/subdomain in the same qualified Resend account. Prefer a dedicated subdomain where an existing domain already serves everyday mail. Reuse existing qualified domain facts but prove receiving-specific records/current ownership separately; a sending-domain check alone is insufficient. Never add competing root MX records or replace existing root mail routing as a setup shortcut. Show provider-returned exact record values in copyable fields with current status and meaningful recheck, not hard-coded regions/hosts/priorities.

Register only the intended exact public-address binding. Catch-all reception does not create arbitrary inboxes, addresses or CRM identities. Additional receiving domains do not replace P17's chosen transactional sending domain, Default Sender or default human reply destination. Provider-managed receiving addresses are technical targets where qualified, not automatically approved tenant-public addresses or shared platform senders. The new address is not an IMAP/POP mailbox, personal mailbox license or email-hosting product.

### D25-R11 — Separate the proof dimensions and their limits

Track at least current connection/account scope, receiving-domain/route, public-destination control, external new-message arrival, ordinary reply return, outbound preparation/delivery compatibility and accountable monitoring/review coverage as independent evidence. Bind evidence to candidate generation and actual source/connection/address revisions. Late, duplicate, wrong-address, previous-generation or unauthenticated proof cannot complete current setup. Material change invalidates only affected proof; ordinary internal-label edits do not cause ritual retesting. Recheck at relevant configuration change, security incident, concrete drift or owner-defined proof expiry. No invented deliverability score, global Connected truth, endless polling or periodic live canary without an actual purpose.

Add a typed **managed Support route** proof method to the existing Human reply destination owner, alongside its external-access method. Do not auto-complete them from incoming traffic or transfer a challenge to an IT helper. ### D25-R13 — Qualification traffic is bounded owner work, not a general sender

### D25-R14 — Bounded verification and anti-abuse controls

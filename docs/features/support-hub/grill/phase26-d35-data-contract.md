## Minimum model and ownership

Use the existing Support source owner. Logical names below describe invariants, not a new generic schema, table-name mandate or event-sourcing platform.

| Fact                     | Authority and constraints                                                                                                                                                                                                                                 |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Note identity            | Existing tenant plus stable original Support note/message and original conversation/source IDs. Actual note/conversation IDs are TEXT; use actual owner types rather than a UUID conversion.                                                              |
| Native human publication | Positive trusted source kind, original authenticated principal and original publication evidence. Current type=note, display JSON, email, importer or agent ID is insufficient.                                                                           |
| Current head             | Exactly one currently available editorial revision of that same tenant/note. Source restriction, topology and retention facts stay with their existing owners. An expired or unknown source is never upserted into a new note.                            |
| Revision metadata        | Stable identity/order, exact predecessor/base, trusted editor/time, canonical profile version and minimal operation provenance. Ordinary edits append; they do not revise original authorship/time or reuse a previous head ID.                           |
| Revision material        | One qualified canonical structured body and derived safe HTML/text. Source-bound reference appearances are content; file membership/bytes retain their independent occurrence owner. Material can be restricted, safely represented or purged by D16/D17. |
| Save operation/result    | One semantic business operation scoped to trusted actor/tenant/note/base/fences and desired canonical content. Minimal body-free outcome/resulting-revision evidence; no second saved candidate body in a receipt or audit.                               |
| Derived views            | Current timeline/CRM/search/compatibility body and history pages reference authoritative head/source state. They cannot write a second truth, retain extra copies beyond purpose or grant access.                                                         |

Use same-tenant/note foreign keys, unique revision sequence/identity and unique operation occurrence, valid available/restricted/disposed state combinations, immutable original provenance and deliberate delete behavior. The current pointer must resolve within its note. A migration actor cannot become the original author. Preserve required source restrictions and replay control when removing content; do not cascade through independent CRM/financial identities or retain body JSON in an undeletable audit table.

A compatible old current-body column may remain during mixed deployment only as a derived projection. Neither generic collection mutation nor a service job may overwrite canonical material/head/provenance. Business database logic remains in `packages/api`; approved collection/adapter boundaries stay in `packages/database`. Thin routes do not become another database or authorization boundary.

## Admission and replay, in order

1. **Qualify the edit read.** Resolve the actual principal and tenant from trusted context; prove current original-source read/edit permission, native-human origin and original author equality. Fetch one current canonical version and its head/source/privacy/topology fences. Opening changes no data and creates no edit event.
2. **Prepare locally.** Validate before writable initialization; keep a private candidate separate from Reply/Note drafts. Submit one absolute desired canonical document, exact note/base/fences and operation identity. Server derivation controls actor/source and generated representations.
3. **Check an existing operation under current rights.** If its immutable semantic meaning matches, return its prior minimal outcome without another mutation. Do this before treating its old expected head as a new stale save. Changed meaning conflicts. Separately retrieve whatever current head remains permitted; a past Saved result must never overwrite a later revision or privacy change in the UI.
4. **Serialize a new operation.** Coordinate the original source, note/current head, operation and relevant privacy/retention/topology controls under the existing owner's transaction/lock discipline. Acquire locks in a consistent order and refresh trusted eligibility time after waiting. At `now >= applicable deadline`, content is unavailable even if the disposal worker has not run. No transaction waits for a human or provider I/O; no blanket global serializable mode or edit lock is needed.
5. **Recheck exact base and authority.** Current author/source eligibility, expected head and source-control fences must all agree. A stale base is a conflict even if text happens to equal current content after an A→B→A sequence. Lost rights/restriction is not an ordinary content conflict and does not disclose current forbidden bodies.
6. **Validate the complete candidate.** Enforce the exact qualified Internal note schema/profile, original-source references and canonical budgets before normalization/compilation. Compute equality under that qualified canonical contract, not a lossy parser or raw body-string shortcut.
7. **No-op or atomic correction.** A current-base equivalent candidate records a minimal immutable no-change operation binding/result and creates no new revision/Edited event/counters. A genuine change appends one revision, advances the one head, records minimal edit/result history and required identifier-only source invalidation/safety-continuation obligations atomically, or none. Existing source/send-review fences advance where their actual owner requires it; this is not a new human publication, last-contact or retention event.
8. **Return and reconcile.** Known rejection preserves only still-permitted local text. Success returns the authoritative current representation separately from the immutable operation outcome. Lost response enters Checking and read-only lookup of the original operation; no blind new operation, body reapplication or fake Cancel. Deadlock/serialization/retry treatment retains the same business identity and correct requalification.

Current rights also govern replay/outcome lookup. If minimal result facts remain independently permitted after payload disposal, they can be returned without a body; otherwise return a generic unavailable/denied state without leaking source existence. A lookup never renews a receipt, content, session lease or retention clock. Every admitted Save, including No changes, binds its operation identity. Retain that minimal binding or an equivalent durable rejection fence until the note is irreversibly non-editable and restore/replay cannot re-enable its identity. Response caches and content material may be pruned independently, but their expiry never releases an operation key; this retains no extra body/diff and creates no unlimited history exemption. Candidate digests, tokens and content-derived fingerprints remain protected/minimized and cannot become a permanent low-entropy privacy oracle.

## Valid and invalid transitions

| Transition                                             | Rule                                                                                                        |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Readable current note → private Editing                | Current human-author/edit/source proof and qualified canonical source; no mutation.                         |
| Editing → Cancelled                                    | Before submission, discard only the local edit and return to current permitted reading. No revision.        |
| Editing → Saved next revision                          | Exact current base/fences, valid changed candidate, one atomic operation.                                   |
| Editing → No changes                                   | Exact current base and equivalent canonical content; no new revision.                                       |
| Editing → Conflict                                     | Base/source/topology changed; no overwrite or automatic rebase. Deliberate new review is required.          |
| Submitted → Checking                                   | Outcome unknown. Read-only original-result recovery; closing is not cancellation of a committed effect.     |
| Any state → Restricted/unavailable                     | Current privacy/permission/expiry dominates; clear forbidden local/rendered bodies and deny further writes. |
| Saved revision → ordinary mutated old body             | Forbidden. Corrections create a new head; privacy-safe representation/disposal is a separate owner action.  |
| Past revision → Restore or automatic new head          | Not offered. A new correction starts from the current base under current authority.                         |
| Note → new email/public audience/new author/new source | Forbidden through Edit.                                                                                     |
| History read → new alert/activity/AI index             | Forbidden.                                                                                                  |

## References, mentions and files

The source's attachment occurrence membership, identifiers and bytes remain unchanged by D35. The candidate may deliberately remove or move supported existing mention/inline-image appearances; its retained typed refs/target attributes must be a valid subset of those in the loaded current base. Do not create a new notifying target, retarget a node, acquire a foreign/remote asset or flatten a typed node into an authority-bearing string. Undo inside an unsaved candidate may restore only still-allowed references from that base. A later edit cannot use an old history view as a token-restoration authority.

Removing an inline picture leaves the actual existing file list; it is not privacy deletion. Every current/history preview/download rechecks D16/D32 and the exact source occurrence, including scan/restriction changes. A shared physical blob does not transfer source access. Ordinary href edits follow safe-link rules and do not fetch remote content. New supporting files or notifying mentions use an actual new note and its existing admission/attention rules.

The current creation composer immediately calls `logSupportActivity` from mention insertion; that helper posts generated text through ordinary note creation. The correction profile must not call that path during mount, editing, undo, Save, Cancel or history. New native publications must themselves acquire truthful human/generated provenance; otherwise future Edit eligibility remains unprovable. This is an existing-source qualification fix required by D35, not permission to infer source kind from message text.

## Privacy and retention across history

Current note and all revisions belong to the same original D17 content generation/deadline. Editing, history reads, CRM links, merges, late jobs or receipt lookups do not renew it. Metadata/control facts and bodies have distinct qualified purposes/retention; “immutable revision” never means permanent private bytes. No arbitrary last-N deletion substitutes for D17, and no infinite-history product promise overrides its finite custody.

Apply D16 restrictions to every current/history representation and known derivative: canonical JSON, HTML/text, indexes, snippets, previews, exports, browser buffers, source-dependent prepared notification material and restores. A current selected-span redaction cannot be presumed to map onto differently worded earlier versions. When no safe earlier representation is qualified, restrict that affected revision body and derivatives as a whole, preserving only permitted body-free facts. No fuzzy matching, first-occurrence removal or semantic redaction engine is invented.

Coordinate save versus redaction/expiry/move/merge with authoritative source controls, not independent before/after UI checks. An old candidate cannot restore restricted material after its base was withdrawn. Restored backups must apply current withdrawal/expiry fences before serving or retrying. Redaction may produce a source-qualified safe representation; it does not rewrite original authorship or claim an ordinary user edit occurred.

## Reads, history, search and CRM

Authorize exact note/source and each representation before returning bodies, metadata, counts, names or files. Same-tenant staff membership and CRM access are insufficient. A current merged root is handling/navigation context; the edited note stays with its original constituent source. Merge/Undo, unlink, move and permission changes invalidate stale reviewed context without reparenting history or authorship.

History returns at most20 permitted metadata rows, one selected body and an opaque cursor bound to the current authorized note/source plus a stable viewed frontier. A new edit can be signalled without reordering the open list; the user refreshes deliberately. Revalidate between pages and bodies, and never expose hidden revision gaps/counts. All retained permitted versions remain reachable; the page bound is not a data-retention cap. **Original** requires proven original content. An observed legacy body is **Recorded baseline**, not invented original text.

D22 current search/Find/snippets/rank/counts follow the current permitted head and its own currentness rules. Revalidate stale index matches; older versions belong only to explicit history. Identifier-only projection/safety work is durable with the edit and repaired idempotently from that edit. A failed search update does not roll back the saved note or justify showing an old positive as current. CRM uses the same source with preserved navigation and no duplicate Activity, copy or independent overwrite path. The edit changes no giving, receipt, refund, recurring, care or contact fact.

## Grants, RLS and deployment

Verify actual deployed table/column grants and exposed schemas together with SELECT, effective old-row USING/new-row WITH CHECK, function/view invoker/definer context, execute grants/search path, storage and privileged/nonhuman paths. Current migrations' broad authenticated CRUD and explicit tenant/staff UPDATE checks do not establish author-only editing. PostgreSQL can inherit USING for omitted UPDATE/ALL WITH CHECK; use actual effective semantics. Do not use service role to avoid these boundaries or trust user-editable JWT metadata. [PostgreSQL17 policies](https://www.postgresql.org/docs/17/sql-createpolicy.html), [locking](https://www.postgresql.org/docs/17/explicit-locking.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Qualify native creation provenance and close old writers before enabling revision-aware edits. Backfill only independently provable original actor/source facts and one honest observed baseline. Ambiguous/generated/imported/unsupported legacy rows remain non-editable with permitted reading, ordinary new-note clarification and D16 paths. Do not manufacture previous versions, re-author as migration worker or renew old retention.

Add compatible schema/constraints/readers first, fence old writers, then enable gated editing and history. Disable edits while preserving accepted result/revision recovery and privacy/current reads. After new data exists, a rollback cannot discard history, restore broad writers or resurrect erased bodies; use a compatible roll-forward. No package upgrade, live SQL or migration is executed by this grooming record.

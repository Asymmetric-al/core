# D21: Optional curated Support labels — independent UX and vendor review

**Research date: 12 September 2026.** The founder selected A. This is an independent research/design input to the full D21 review, not a ratified amendment, runtime change, or authorization to publish/send anything. Root separately verifies Core’s actual owner, API, schema and governing decisions.

**Recommendation remains A, with required clarity and lifecycle safeguards.** Applying an existing label should be quick; maintaining its meaning should be deliberate. A label is optional context for a conversation. It must never stand in for work status, ownership, routing, access control, a CRM fact or completion of the underlying action.

## Reporting evidence and the consequential distinction

[Front Tags report](https://help.front.com/en/articles/2152), **15 July2025**, Professional+, exposes tagged versus untagged coverage, per-tag details and a separate tag-change table. [Conversations with tag changes](https://help.front.com/en/articles/2465), **29 April2025**, counts changes during a period and warns that filtering only currently tagged conversations can omit past changes. The useful pattern is transparent population and distinct state-versus-event meaning. Asym does not need every listed Front metric or its conversation-segment model.

[Intercom Conversation tags reporting](https://www.intercom.com/help/en/articles/3267226-conversation-tags-reporting), **12 December2024**, describes counts based on conversation start date rather than tag-application date and documents 24–36-hour reporting delay; custom reporting uses Advanced/Expert. Its [troubleshooting article](https://www.intercom.com/help/en/articles/4957124-troubleshooting-custom-reports), current retrieval, explicitly explains that a conversation with several tags appears in several groups. The same troubleshooting article describes other timestamp-specific filtering discrepancies. These are reasons to publish exact semantics, not adopt its lag or claim all reports use one time basis.

**Recommended narrow reporting contract:** current lists and saved views show current eligible assignments. Label breakdowns count distinct eligible conversations per label; overall totals dedupe by conversation identity. Show **No labels** and a tagged/untagged coverage figure for the same population. Say that categories overlap. A current-label breakdown for a historical conversation cohort must say it uses current labels; it is not a frozen record of labels at resolution. If another approved report promises historical attribution, it must use actual recorded label-change history. Do not add a second reporting builder, full event report or configurable timeline taxonomy solely for D21.

## Complete, restrained recommended user journey

These are proposed exact requirements for root to reconcile with the verified shared platform contract.

### U01 — One visible context and one clear purpose

The conversation’s details include **Labels** and a visible **Add label** or **Edit labels** control. On mobile, the existing Details surface exposes the same control without hover. In a CRM record’s Support conversation preview, this section clearly belongs to the conversation; opening the full conversation preserves the record return context. Do not place a label selector on the CRM record itself or imply its labels apply to the requester.

Microcopy on first relevant use or in concise help: **“Labels help your team organize conversations. They’re optional.”** Do not repeat it below every chip. An empty state is neutral **No labels**, without red warnings or a Resolve blocker.

### U02 — Searchable selection without taxonomy work

Opening the picker shows active eligible labels and the current selected state. Search names, with brief usage descriptions available where they disambiguate. Keep the selected set understandable while filtering; searching must not remove existing selections. Navigation, Tab, Enter during IME composition, or an empty search never creates a catalog entry. Include a clear no-match state that differs from load failure. Search should reach the full eligible catalog, not only recent/popular values.

A plain multiple-selection pattern is enough. No nested taxonomy canvas, alias editor, extra tag categories, private labels, automatic suggestions or AI matching is justified by A. Similar-label detection may assist qualified creation but does not merge IDs or assert semantic equivalence.

### U03 — Keep each mutation small and truthful

Applying/removing one existing label is reversible and should not need a confirmation modal. Keep the picker open for additional selections. Show pending state per affected label and confirm persistence after durable success; failure leaves the last known stored state visible and permits retry. A timeout is not automatically failure: reconcile the original action before a new attempt. Do not overwrite the whole assignment set from a stale picker, discard another worker’s change, or claim success solely from optimistic rendering.

If a chosen label was archived meanwhile, explain that it is no longer available and preserve other selections. A failed catalog load never means the conversation has no labels. Resolve/reply remains available independently when ordinary existing rules allow it.

### U04 — Clear removal and recovery

Call the action **Remove label** on a conversation. It affects that association only; it neither deletes the label nor changes other conversations. Ensure removal can be reached by keyboard/touch with an accessible name such as **Remove Receipt question**. Allow ordinary correction of an applied archived label if the actor/source remains eligible. Reapplying an active label provides persistent recovery; an optional brief Undo may call that same command. Undo cannot reactivate a retired or forbidden label, resurrect disposed content, or rewind unrelated changes.

### U05 — Quiet presentation

Use current shared Asym components, typography and semantic tokens. Display readable text with subdued styling; do not make every label an alert color. Keep a compact initial set and an explicit **Show all labels** affordance when space requires overflow. A responsive presentation budget is a design detail to verify, not a new permanent five-label domain limit. Do not make all catalog entries permanent sidebar items—D20 views/pins already solve navigation.

### U06 — Curators and scope

One tenant-qualified Support catalog is the simplest starting point when its terms can safely be shared among its eligible Support staff; do not invent per-inbox clones by default. Preserve any stronger actual shared-owner catalog-disclosure rules. If an organization needs a narrower protected vocabulary, enforce that through the already qualified owner/resource scope and avoid showing its names, counts or usage to other staff. Do not use a label to grant that scope.

Catalog maintenance is delegated to an eligible tenant member or existing team capability; it does not require a new reviewer role, approval chain or access to all conversations. Small tenants can use one person. Staff can apply existing labels without catalog-maintenance permission. An empty curator team does not invalidate existing labels or prevent normal work; existing tenant administration can repair maintenance coverage.

### U07 — Find the maintenance surface without leaving work accidentally

Qualified users see **Manage labels** in Support settings and an unobtrusive link from the selector. Preserve unsaved composer content and return context across navigation. Others receive short no-match guidance to contact the tenant’s designated maintainer through existing internal collaboration; no special label-request workflow or automatic notification is needed. The manager has searchable **Active** and **Archived** lists, clear empty/loading/error states, and qualified usage/dependency details on demand.

### U08 — Deliberate creation and meaningful names

Create requires a readable name and concise description of when to use it; description may be optional for truly self-explanatory terms, but ambiguous labels require definition before use. Prefer a small neutral vocabulary grounded in observed work. The system should not seed donor-care assumptions as facts. Any starter examples remain editable examples, and core work can begin with an empty catalog.

The form explains that the name/description is visible within its permitted catalog audience. Do not place names, emails, gift amounts, locations, credentials or case-specific narratives in shared taxonomy. Validate finite limits visibly before save; do not silently strip unsupported punctuation or collapse two distinct IDs. A duplicate-name error offers the existing eligible entry or archived restore path without revealing inaccessible definitions.

### U09 — Rename changes wording, not meaning

Rename keeps identity and current assignments. Tell the maintainer that the new wording appears wherever that label is shown. Fixing spelling is appropriate; changing **Receipt question** to **Refund completed** changes meaning and must use a new label. Preserve attributable change history under owner retention rules, with privacy correction still authoritative. A name matching another active/archived identity must never quietly merge them. Resolve concurrent rename conflicts before replacing another maintainer’s wording.

### U10 — Archive before broad deletion

Archive means **“Stop offering this label for new use. Existing labels and permitted history remain.”** It does not mass-remove assignments. A simple confirmation may show authorized affected dependencies, with safe qualification if aggregate visibility is partial. Archived labels remain recognizable when already applied and retain supported historical query identity. Restore makes the same identity available again after current qualification; it does not reapply previously removed assignments or renew disposed data.

An ordinary unused mistaken entry may be deletable if the shared owner proves no retained assignments/dependencies require it. Used entries should follow archive unless a separately authorized privacy/disposal action requires stronger removal. Do not offer broad irreversible deletion as an adjacent chip action, or imply archival satisfies erasure. Do not freeze a novel deletion policy if the shared Core owner already governs it.

### U11 — Handle duplicates without smuggling in an enterprise feature

Curated creation and duplicate-name validation reduce accidental duplicates. Different labels with similar meanings can be clarified or retired while retaining truthful history. D21 need not add a general catalog-merge workflow merely because Zoho/Freshdesk offer it. If verified legacy data requires consolidation, perform a reviewed owner migration with explicit source/target IDs, affected references, deduplication, history and rollback/correction proof; do not make ordinary Rename perform that migration. If a future end-user merge is demonstrated as necessary, it must be an explicit separate action with the same guarantees.

### U12 — Labels describe conversations across their existing lifecycle

Resolving/reopening, inbox moves, record linking, related conversations, conversation merge and Undo must retain their ratified meanings. Do not automatically copy labels to another person, related conversation or CRM record. Merge/Undo requires original-association provenance and current source permission; broad union must not disclose protected vocabulary. A label cannot clear a held intake restriction, create a hold, stand in for Waiting reason, or make a business action complete.

### U13 — Accessible interaction, not just attractive chips

Use a tested shared component pattern. For a multiselect listbox, selection and focus are separate; keyboard navigation does not toggle other options. Do not put functional nested edit/delete buttons or native checkboxes inside a `listbox` option—the [W3C APG listbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) explains that interaction model does not support nested interactive elements. Use actual checkbox semantics in a suitable popup/dialog if that is the qualified shared component. Manager actions belong outside selection options.

Meet the relevant [WCAG2.2 target size criterion](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): 24×24 CSS-pixel minimum or its specified exceptions, while preferring larger touch controls. Tiny chip X icons cannot be the only accessible removal path. Label names/selected state must not rely on [color alone](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html). Announce meaningful [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) without moving focus, and avoid announcing every keystroke as a global alert.

### U14 — International and mobile users receive the same semantics

Support Unicode display, mixed-direction text, readable line wrapping and language-appropriate search/sort. Normalize only under the qualified shared contract; normalization for matching is not a silent rename. Test composed/decomposed accents, non-Latin and right-to-left names, punctuation, long labels and input-method composition. Do not require ASCII transliteration or artificial separators to make a label usable. Localize system copy; tenant-authored labels remain the tenant’s wording, without automatic machine translation or duplicate language identities.

The compact viewport uses the same source permissions and behavior. Selection is always visibly/semantically confirmed, mobile keyboards do not hide Save/close controls, focus returns to the triggering control, and zoom/reflow does not hide descriptions or removal. Preserve current state and provide an honest retry for low-bandwidth failures; no offline write queue is required solely for labels.

### U15 — Reporting stays honest and useful

Label-based lists use D20’s exact Any/All and No labels semantics. Define whether a report groups current assignments or historical events and show its date basis, authorized population and freshness. Distinct conversations, label assignments and label changes are three different counts. No labels is valid; missing/unavailable data is not No labels. Counts must not leak hidden associations. A label change must not fabricate a reply, last-contact, completion, priority or target event.

### U16 — Email Studio is a separate owning capability

Saved Sections in Email Studio contain reusable wording. Support labels contain organization metadata. Labels neither publish nor insert that content and do not become template merge variables, recipient audiences or rule actions merely through D21. Apply/rename/archive creates no automatic acknowledgement, email or Resend delivery. Human reply preparation and admission keep the ratified Email Studio → Support → Phase6/tenant Resend seam; typed classification work stays outside it.

## Strongest counterarguments and why A still holds

- **“Curation will become a bottleneck.”** Plausible when new categories change rapidly or maintainers are absent. Delegate maintenance to existing qualified people/team, keep ordinary work possible without labels, and use established collaboration. Adding mandatory approval or a new submission queue would worsen this problem. If actual requests are routinely blocked, revisit governance—not automatically create labels on every typo.
- **“Optional labels make reporting incomplete.”** True. Show coverage and avoid population-wide claims. [Front required tagging](https://help.front.com/en/articles/2106), 6 June2026, Pro+, is a credible competing approach but documents mobile/automatic-archive/new-Send-and-archive exceptions. A mandatory field may be justified for a specific verified reporting obligation; that is a different scope decision and does not follow from wanting a complete Support surface.
- **“AI could classify everything.”** It adds inference, source-disclosure and correction concerns and requires actual accuracy evidence. Optional human-selected labels do not authorize it. A documented product feature is not proof it should ship here.
- **“A shared tenant catalog may reveal restricted subjects.”** Correct; broad discoverability is not automatically safe. Root must qualify catalog disclosure separately from conversation read/use. Keep sensitive case-specific data out of shared taxonomy and honor source-derived restrictions rather than constructing private labels as a privacy workaround.
- **“No catalog merge leaves duplicates forever.”** The selected need is consistent optional organization. Clear rename/archive behavior and reviewed legacy consolidation can handle actual cleanup without a general merge product. Do not delete evidence or silently rebind saved views. If repeated live consolidation is demonstrated, qualify that separate command rather than bundling it into rename.

## Reported friction and limits of this review

[Intercom Required Tagging](https://community.intercom.com/ideas/required-tagging-8914?fid=None&tid=8914), January2025, records a user wanting reliable category coverage without maintaining changing keyword automations. [Moving from tags to attributes](https://community.intercom.com/reporting-21/moving-from-tags-to-conversation-attributes-question-about-fin-handling-attributes-13345), December2025, records perceived messiness/reporting friction and requests advice. These are reported experiences, not prevalence, current product defects or Asym demand evidence. The older Freshdesk article and indexed-only Kustomer sources are deliberately qualified above.

No prototype, assistive-technology run, user study or live vendor account was tested. Release evidence must include real selected-state/focus/mobile behavior and representative staff/maintainer comprehension, not simply a screenshot or automated accessibility score. Critical journeys to test are: find/apply/remove; optional Resolve with zero labels; find unavailable/no-match states; distinguish conversation labels from CRM tags; rename without meaning change; archive/restore without association loss; resist stale concurrent changes; and explain overlap/No labels in reports. No unsupported time-to-complete or satisfaction claim is made.

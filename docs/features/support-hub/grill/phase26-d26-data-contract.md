## Minimal logical shape

Retain the canonical Support original and current D10 handling model. Add a typed staff-recorded origin/brief, not a second ticket or generic encounter table family. Origin describes how Support work began; later email does not change that origin. A manual request has no incoming-email trigger. D12-related work retains its real trigger/reference; email-origin work retains its actual provider/source identity.

The manual brief has its own stable Support source identity, schema version, current content revision/restriction state, trusted author and admission occurrence. It is a staff account of the request. Optional reported occurrence information retains exact/date-only/unknown precision and zone meaning independently. Observed names/callback endpoints are minimal classified Support content, not authoritative CRM updates. Do not manufacture an anonymous CRM person or use text copied from a source as evidence of identity.

If an actual encounter already exists, reference its exact owner ID with same-tenant and current source-use validation. A separately minimized Support brief can describe the unresolved need, but it is not an editable twin of the encounter. A source unavailable later stays unavailable; the system cannot retrieve an old copied body to fill the gap. No speculative event bus, generic relationship catalog or arbitrary polymorphic target JSON is required.

Native external message counts/time/direction remain correctly absent/zero until real messages are admitted. The current `support_conversations` email/address/non-null-time assumptions and collection/mapper contracts must be changed together before admitting the origin. The [actual-source probe](phase26-d26-source-probe.json) proves current mapper incompatibility only: hard-coded email, literal null strings and changing read-time message timestamps on synthetic zero-mail input, with a valid email control.

## Admission, retry and correction

1. Authenticate inside the server handler/command; resolve trusted current actor and tenant. Parse only allowed intent fields. The route stays a thin `packages/api` boundary.
2. Resolve the durable operation and payload meaning. A matching committed occurrence returns its original safe receipt and separately current state. A changed meaning conflicts. Current permissions govern disclosure of both.
3. Recheck current inbox work acceptance, classification, handling/coverage and optional source/Party reference permissions under a consistent guarded state. Actor ID, reported caller ID and assignee are not interchangeable.
4. Atomically commit the new original request/brief/Open work, reviewed Shared or explicit eligible handling, any explicit reminder, complete reviewed links/references, attribution/history, receipt and required identifier-only invalidation/reconciliation intent.
5. Return the actual authorized identity. A CRM-first caller can open that same detail and reconcile its full list from canonical state. Projection delay is not failed admission. Durable continuation recovers secondary effects without replaying create.

A Party/source permission change rejects the compound create and preserves permitted draft content. An explicit revised create omitting that link is a new reviewed semantic operation after the first outcome is known, not automatic fallback. Concurrent requests with genuinely distinct identities remain possible; one name/date/brief is not a unique business key. Similarity can aid authorized staff judgment only.

Corrections do not rewrite original actor/time or convert the brief into an incoming email. Created-in-error cancellation first retains all D12 unused-tracking exclusions: subsequent independent activity, native/admitted/possibly submitted mail, owner/external effects, active merge or dependent continuation/referral and protected draft loss make it ineligible. Only then does the standalone additional no-obligation/accepted-current-home test apply. It cannot retire legitimately used/completed work simply because nothing remains owed. It is a non-success ending with protected retirement/evidence, not delete-and-recreate. Source and destination current controls prevent stale cancel/merge/replay from abandoning or resurrecting work.

## Complete CRM query and inline access

For the requested canonical Party, candidate membership is the union of active explicit D9 relevance and qualified actual correspondence. Apply joint Party/Support/source/field visibility, resolve current D10 handling, deduplicate by tenant/canonical conversation and then page/count. Use covering indexes for actual source/relevance and cursor predicates; avoid loading a general Support list and filtering it in the browser.

Manual zero-mail work is eligible through explicit relevance. Ended work is in All; Unfinished is a default filter, not a data deletion policy. The Overview preview remains capped at three and links to the complete view. Current financial `support` totals remain separate. When both discovery bases exist, show one row with both truthful reasons. Removing a relevance link cannot erase independent correspondence; source attribution correction is its own owner path.

Default ordering retains actual latest external-message occurrence for records with mail. Staff-origin records with no mail use original trusted recorded/created time, labeled Recorded; stable canonical ID resolves ties. Reported call time and mutable `updated_at` are not this sort. Unknown legacy evidence gets an explicit unknown class. The new fallback is a deliberate D9 amendment, not a generic last-activity model.

The CRM view opens the same canonical Support detail/read/action contracts, inline where the shared shell permits and full-page otherwise. It keeps all currently qualified content/attachments/actions and read-only limits. Both entry routes bind the same ID and policy; a drawer or client cache is never a permission boundary. Safe return locations are local/validated and tenant/Party scoped; user-controlled navigation state cannot become an open redirect or data-access instruction.

Use scoped cache/query/realtime keys and current access generations; permission/source/link change requalifies both directions. No unrestricted hidden count, transcript prefetch or integration-admin lens. An authorized Support projection outage is isolated and retryable; a denied target reveals no existence. CRM uptime must not depend on a successful Support query for unrelated data.

## Supabase authorization posture

The configured local PostgreSQL major version is17. Hosted version, grants and actual deployment policy require release verification; local config is not live-state proof. Core migrations already enable tenant RLS and explicitly include UPDATE WITH CHECK for the old Support tables, while authenticated CRUD spans19 core Support tables. Later inbound-route revocation does not by itself revoke the core conversation/message/audit grants. The defect is insufficient current resource/field/immutable/compound-command protection if reused, not simply missing RLS syntax.

Require least-privilege explicit grants for every new/protected table, column, view and function. The exposed-schema RLS floor is defense in depth; `service_role` and applicable owners can bypass it, so the same current actor/resource policy must be enforced by every privileged command/read. Deny raw browser control/provenance/audit/association access and fence direct conversation/source writers. Do not grant broad raw tables merely to make a new CRM pane work.

For any authorized browser-safe projection, prove its effective underlying and invoking privileges. `security_invoker` is available in PostgreSQL15+; it does not narrow a service role that already bypasses RLS. A required SECURITY DEFINER function must have hardened search_path, exact execution grants and current actor/resource checks; the keyword is not authorization. Review SELECT/RETURNING behavior and all applicable permissive/restrictive policies, USING and resulting-row checks, including whether updates can change protected tenant/source/author/control state. Storage access follows source and byte-owner policy, not just a visible CRM link.

**Verified correction to skill shorthand:** PostgreSQL17 reuses USING as WITH CHECK for UPDATE/ALL when WITH CHECK is omitted. Omission alone does not prove reassignment is allowed. Explicit clauses improve clarity, but effective predicates, protected columns and grants determine safety. Similarly a definer function's effective privilege depends on its owner and grants. [PostgreSQL17 CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Supabase's current default-grant rollout concerns new tables; old explicit grants remain. Therefore deployment must declare intended grants/revocations and test actual Data API access rather than relying on project creation date or a dashboard badge. No global grant workaround or assumed automatic lockdown. [Supabase Data API change](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

## Email Studio, targets, retention and search

Manual admission has no requester email preparation or transport call. Existing qualified staff assignment/attention uses D12/P6's separate actual producer and recipient policy, without making staff-email availability a work-admission gate. An authorized manager can establish a named work inbox and required access/coverage with no dummy inbound/From/Reply-To fields; the current mail-shaped inbox schema/DTO must be qualified too. Work acceptance is not D25 email activation or a generic isActive shortcut. Configure email remains D25's two equal paths, separately reachable from the same inbox.

A later first email uses the explicit manual-origin recipient branch, actual P17 identity/wording/signature/preparation, D4 admission and P6 dispatch. Existing D14 accepted Start email → subsequent Next semantics remain; unknown acceptance retains candidate First/Next and the earliest applicable possible deadline rather than forcing First. No email target/fulfillment occurs from the brief itself.

Initial published manual brief joins D17's human-content activity set once at trusted admission. Ordinary edits/context changes/late logs do not renew it. Title/brief/derived content stays finite Support material, separate from independent CRM/financial retention. D22 already has eligible Staff context brief search; this origin uses that kind. No external activity corpus or AI index is added.

## Migration and proof

Inventory old schema/defaults/DTOs/caches/list/report/source writers first. Add compatible readers and conditional constraints before enabling creation. Evidence-only legacy conversion must not infer phone origins or Party links. Fence both generic browser and service writers before exposing protected new data through CRM. A kill switch pauses only new manual admissions; existing requests and admitted effect reconciliation remain safe. Old email-only code is not a valid rollback after new data exists.

P01–P50 require actual database constraints, multi-role Data API/RPC/storage tests, joint current-policy tests, concurrent/partial-failure admission, complete queries beyond known caps, migration/backfill/restore, both UX journeys and later real email proof. All remain unexecuted in this grooming turn. SQL text review and the source probe cannot certify hosted RLS or release readiness.

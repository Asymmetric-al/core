Researched 12 September 2026. **Q26 is unanswered.** D25 and all adopted amendments are fully recorded as ratified. This artifact supplies current primary comparisons and an actual A/B/C scope fork for the next single founder question. It is exploratory grooming only: no new intake behavior, CRM model, telephony, specification, ticket, message or runtime change is authorized here.

**Single recommendation: A — Let staff directly record a Support request that needs follow-up.** Keep ordinary relationship interactions and owner-domain tasks with their actual Core owners. When a call or in-person discussion produces continuing Support work, authorized staff should be able to place that work in the same Support handling model without inventing an incoming email or requiring the requester to resubmit it. That recommendation is a product judgment about a demonstrated type of workflow, not a claim about its frequency in Asym ministries.

## Why this is a genuine remaining choice

The [independent coverage review](phase26-q26-gap-review.md) checked the current baseline `7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd`. The [coverage ledger](phase26-grill-log.md) still lists phone notes among unresolved channels/scope. [D12-R01](phase26-d12-adversarial-review.md) permits a related Support conversation only from one deliberately selected admitted incoming email; it does not yet authorize standalone staff-recorded phone/in-person intake. D12 nevertheless establishes useful adjacent invariants: staff-created work is distinct from native correspondence, its brief is not a customer-message bubble, and creation sends nothing.

[D9](phase26-d9-adversarial-review.md) makes optional CRM relevance distinct from actual correspondence and does not require a Party to exist before ordinary Support work. Its CRM Support summary and P6 communication history are composed views with different evidence; linking a conversation does not create a CRM note, interaction or last-contact update. Those accepted distinctions must survive any answer.

The reviewer also identified an important limit: the roadmap's **one shared interaction log** is a Phase28 guardrail, and P9's activity taxonomy/composed timeline does not prove that a qualified general-purpose call-logging writer already exists. The inspected missionary activity command writes legacy donor-keyed `donor_activities`; CRM reads those into a timeline, while a note-input placeholder mentions calls/meetings. That is not a qualified Party/unlinked-requester encounter owner, and P9 intends to retire the legacy table. Therefore B below means using the **currently qualified owning capabilities**; it does not promise a ready universal CRM call log. C has a genuine additional shared-owner dependency. Exact source links and limitations are in the independent coverage review.

Here, “phone or in person” describes how a human received the request. It does **not** mean disconnected-device operation, offline synchronization, dialling, a telephone integration, audio recording or transcription.

## The actual question and three credible options

**When someone asks for help by phone or in person, how should staff record a request that still needs Support follow-up?**

Illustrative example: someone asks the donor-care team to investigate a receipt question during a call. The caller should not have to send a second email merely to establish the team's follow-up work. A separate courtesy call or a question answered immediately may only need the owning relationship activity/task, not a new Support request. This illustrates a distinction, not a claim about how every ministry operates.

| **A — Record the Support request directly**                                 | Deliberately create a bounded staff-recorded Support request for ongoing team handling, from Support or an authorized CRM context. | **C — Record the shared interaction first, then add Support follow-up**     | Use the shared interaction owner to record the call/meeting once, then explicitly create/link a Support request if it needs continuing team handling.                                                                                                                | Consistent cross-product interaction history and source reuse when staff already log interactions systematically.                                 | Requires the shared interaction write/permission/lifecycle contract and adds a prior step. **Recommend A.** It addresses a specific Support gap without turning every ministry interaction into a ticket or pulling forward the entire shared interaction platform. It should reuse a properly owned source when one already exists, but not require double entry before a team can take responsibility. B remains credible if existing qualified owner tasks meet the actual need; C becomes stronger where the shared logging capability and routine are already established. No evidence justifies a universal CRM-first requirement today.

These are alternatives for the normal scope and entry sequence, not a mandate to build three systems. A does not ban future shared interaction reuse; C does not authorize a second CRM. None adds phone calls, recordings, transcription, SMS, AI, disconnected operation or automatic ticket creation for every interaction.

## A cohesive candidate journey for A

This sketches the proposed experience so the option is concrete. The founder has not yet selected it; exact clauses, limits, default assignment and clock semantics require the selected answer's adversarial review.

1. **Recognize whether this is existing work.** From the permitted Support/CRM context, show relevant existing Support work so staff can add the new information there instead of making a duplicate. Search only the actor's current scope; an unavailable record is not proof there is no existing request.
2. **Choose Record Support request.** The action means a request was received outside the admitted email path. It is separate from Send email, generic Log interaction and D12 Create related conversation. When launched from CRM, retain the permitted source and return context without silently copying a whole profile, transcript or private note.
3. **Capture a concise staff account.** Identify how the request was received, the practical request/follow-up needed and the intended Support inbox. Preserve staff recorder and server save time separately from any reported occurrence time. Do not manufacture a provider Message-ID, received email, direct requester quote or first/last message time. Use the selected Tiptap profile if rich text materially helps this authored brief.
4. **Identify the person only as far as known and permitted.** Existing Party relevance can be selected or inherited as an explicit reviewed context link; an observed caller/name/number is not verified identity or representation authority. Missing email/Party must not lead to fake addresses or automatic CRM creation. Adding or correcting real CRM data remains its owner's separate authorized action.
5. **Create internal work deliberately.** Show that creation records work and sends no email. A controlled create operation produces the new Support identity/brief/handling through the shared owner boundary, or returns a precise conflict/error while preserving permitted input. Do not assume the creator is the assignee or subscribe them to optional following.
6. **Continue in normal Support.** Show a clear staff-recorded source card rather than an incoming email bubble. Work status, assignment, internal collaboration and reminders follow their existing contracts. A later outward email is a separately reviewed D2/D4/P17/P6 send with eligible recipients and real new correspondence lineage; a typed callback number alone is not an email destination.
7. **Keep CRM navigation and history coherent.** Related-record discovery can show the current Support request under D9's permissions. It must not claim a P6 email interaction happened at creation. If there is an independently owned interaction source, retain its link/provenance once; do not maintain duplicate authoritative bodies or copy private material merely to populate both screens.

A phone update to an existing issue and a new unrelated request are different user intentions. The next review should define the minimum entry needed for each without forcing a fresh conversation per call or a generic classification form for every note.

## Consequential seams the eventual answer must explicitly resolve

- **Known versus observed identity:** requester, represented person/organization, staff recorder, CRM relevance and actual future recipients are distinct. Recording what someone said cannot bypass the identity checks for giving/contact changes or expose protected missionary/care records.
- **One history, truthful provenance:** the entry is a staff account, not native incoming correspondence. Original content/time/author remain clear. Context links do not make a CRM activity, reset last contact or multiply history across linked Parties. Existing owner-source reuse should preserve restrictions and deletion/redaction behavior.
- **Work is not necessarily email:** manual capture must not inherit email transport gating just because the destination is named an inbox. Conversely it cannot bypass the actual permission/coverage/classification needed for Support admission or enable outgoing mail when P17/P6 is not ready. The selected-answer review must reconcile D25's email activation with a genuinely manual source.
- **No surprise acknowledgment:** recording is not sending. D13's eligible new-email confirmation rules must not automatically fire on a staff entry, and D2/P17/P6 determine every later external message. Do not make an unknown email required just to pass a form.
- **Clock and reporting truth:** reported occurrence time, actual staff recording and real admitted correspondence remain separate. D14-R06 currently starts reply periods from first-time admitted relevant human Support email; staff creation alone does not. Preserve that rule unless a separately justified amendment is adopted, using existing D3 work/reminders for manual follow-up. Work-age reports, D17 retention and D22 search must handle a staff source without fabricated inbound age, zero-time responses, backdated credit or silent broader coverage. Exact compatibility belongs to the answer review, not vendor imitation.
- **Safety of rich text and sources:** staff-created content can still contain private or untrusted material. Reuse the existing Tiptap/source schema, visibility, asset, redaction and retention rules. A copied CRM note does not become safe because a staff member pasted it.
- **Reliability and repair:** duplicate submission/retry must create one intended request, while two genuinely distinct requests must remain possible. Current permission/scope/revision controls apply. Correction should not rewrite the original recorder or forge a prior caller statement; no delete-and-recreate routine to fix attribution.
- **Bounded product scope:** ordinary donor cultivation, completed routine interactions, ministry operations, care casework and finance work remain in their actual domains. Support can coordinate a qualified request but is not the required container for every interaction or proof that the owner action was completed.

## Email Studio and release evidence

This fork does not change the email architecture. Email Studio remains P17's governed wording, assets, signature, typed fields and preparation owner; P6 uses the qualified tenant Resend transport. A staff intake brief has no automatic provider template or send. If the eventual answer permits later email follow-up, it uses the already-selected D2/D4/D18/D23/D24 mechanisms with their actual audience, publication, readiness and send gates. No new generic mailer or inbox-owned template store is needed.

Before any selected option is called implemented, proof must include known/unlinked/ambiguous people, no email, represented parties, unavailable CRM context, protected care boundaries, duplicate submit, interrupted editing, actual creation without mail, future outward reply, correction, current-authority loss, source redaction/expiry and true timeline/reporting outcomes. Both Support-first and CRM-context journeys need keyboard/mobile/accessibility testing. These are consequences to test after the choice, not claims of completed runtime or user validation.

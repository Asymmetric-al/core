# Q31 evidence — Follow-up time choices

**Research date: 13 September 2026. D1–D30 are fully ratified; Q31 is unanswered.** The [question](phase26-q31-follow-up-time-choices.md) asks how staff choose a time, not whether dependable shared follow-up should exist.

## Why this fork is genuinely open

The full source/decision scan rejected several tempting repeat questions. D3-R11 already defines exact-selected-ID, per-item bulk work and recovery; D7/D20/D21 preserve those guards. D12/D26 already support real request/related-thread continuation, and inbox movement is inherited and further qualified across D1/D6/D8. Mandatory provider/RLS/migration/end-to-end proof is not an optional feature vote. A future all-decisions synthesis remains required; it is not replaced by another artificial product choice.

By contrast, [D3-R07](phase26-d3-adversarial-review.md) explicitly does **not** select a morning hour, default delay or personal preference hierarchy, while guaranteeing explicit custom date/time. The [D3 UX blueprint](phase26-d3-ux-blueprint.md) already calls for a separate labelled reminder control and honest displayed timing. D14 keeps reply-target calendars distinct; D30 preserves discoverable follow-up/recovery work. The remaining quick-choice versus personalization fork has real daily interaction and maintenance consequences without creating a new workflow model.

The question's strongest simpler alternative B is an exact date/time picker without presets, not lack of follow-up. It minimizes preference/configuration and ambiguous labels but adds repeated selection for common delays. C includes a usable baseline and personal definitions, not compulsory configuration or a separate reminder owner. A is recommended as the lowest-friction common case with bounded complexity; no measured Asym study establishes universal timing habits or a quantified time saving.

Intercom's documented reopening/office-hour/SLA settings, Front's personal/shared contexts and vendor auto-close advice are outside this fork. D3 controls due work and relevant input; D7 controls coverage; D14 controls target clocks. “Business day,” “next working morning,” holiday behavior and daylight-saving corrections cannot be casually inferred from a label. Their exact handling is part of the selected answer's forthcoming full review.

Reported user frustration with rigid snooze choices, where included in the independent research, is anecdotal and dated. It supports testing flexibility, not claiming current vendor behavior from an old comment or prevalence across ministries. Help-desk primary documentation is the main comparison; unrelated fundraising dashboards or invented ministry schedules add no authority.

## Complete scope, UX and Email Studio boundaries

All choices provide current authorization, exact resolved date/time/zone before commitment, accessible keyboard/touch/custom entry, honest validation/DST handling, safe cancellation/replacement, per-item bulk outcomes and existing shared reminder recovery. A visible preview is required, but a second confirmation modal is not automatically needed. The future review will select the precise menu and default semantics, not preserve a misleading existing label for consistency.

C's personal preset is a reusable input definition. Editing it cannot rewrite an already-admitted reminder or cause a colleague to lose shared follow-up. Its current tenant/principal custody, saved lifecycle and resolved-time evidence would need qualification; that is a reason to evaluate its cost fairly, not to dismiss customization as inherently bad.

Selecting a time sends no email, prepares no P17 material and creates no D13/D28/D29 effect. D24-R05 keeps reminder/snooze presets outside the shortcut's closed saved patch. D24 shortcuts remain unable to store or apply reminder presets. Any reminder choice while a reply is being composed is a separate deliberate use of the existing qualified D3/D4 control; it does not extend that patch or add a combined-send operation. P17/P6 email preparation and dispatch remain separately authorized and explicit. Reminder time is not scheduled-send time or a CRM/Finance task deadline. No extra reminder email or automated follow-up campaign belongs to Q31.

The exact number/names/durations, morning time and zone-default hierarchy are deliberately not selected in the question. Source hashes, actual-file checks and independent reviews validate this fork and comparison, not a completed reminder implementation. No ADR0031 or new accepted glossary term is created before the founder's answer.

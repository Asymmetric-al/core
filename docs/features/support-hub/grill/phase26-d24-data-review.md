## Recommended finite action vocabulary

This is a product/engineering judgment for root reconciliation, not a claim that source enums or competitor parity require it.

- **After sending:** one D4/D3 final choice: Keep current status, Open, Waiting for requester, Waiting on our side, or Resolved. The native D3 obligation and reminder semantics remain exact. Keep means no work-status write.
- **Labels:** explicit Add and Remove of existing curated Support label identities, through D21. Adds/removes are disjoint; no toggle, catalog creation, whole-label-array replacement or CRM tags.
- **Handling:** at most one D6 desired handling choice. Keep preserves current assignment/team; an explicitly selected eligible person, actual Me, or deliberate Shared outcome uses the native current command. Preserve the current responsible team unless a separately explicit compatible team/person selection is included. A team never implies inbox movement, access grant, round-robin invocation or distribution to every member.

Exclude inbox moves/merge/unmerge, arbitrary priority changes, snooze/reminder creation, note addition, follows/mentions, recipient/header/signature changes, review approval, delegated owner actions, financial/CRM/care mutations, protected documents and automatic sends. These remain explicit native owner journeys; existing status transition effects on a reminder still occur under D3. Including the three groups above does not require all of them in every shortcut. One existing published Shared **Reply** wording source and one bounded final action proposal suffice; D18 remains available for personal wording independently.

## Findings with exact proposed clauses and proof

### DR01 — Stage the entire intent; never act while inserting wording

**Material concern: yes. High severity, high likelihood if the current runner survives.** Existing source does exactly the wrong ordering for C: unsent text and already-applied work can coexist. A request could appear Resolved before its response even passes preparation. This changes C's admission semantics, not its value.

**Exact clause:** “Selecting a reply-and-work shortcut resolves an eligible immutable definition and stages its copied wording plus proposed work patch into the current external reply draft. It performs no status, assignment, label, note, CRM or delivery effect. One deliberate visible primary command admits the reviewed complete reply and all chosen local work effects together. Preserve D4's actual Send reply / Send and open / Send and wait for requester / Send and wait on our side / Send and resolve labels, with a clearly adjacent With this reply summary and access to the complete pending label/handling changes; a generic Send and apply label must not hide the selected work status. Selection, keyboard navigation, preview, save, draft restore, reconnect and late suggestions never execute those effects.”

**Proof:** Selecting a shortcut containing Resolved and a label leaves current status/labels unchanged; closing/reopening the draft retains pending state only; unsatisfied required wording fields block Send without work effect; keyboard selection/IME cannot execute.

### DR02 — Extend D4's atomic boundary rather than orchestrating old commands

**Material concern: yes. Critical severity, high likelihood under independent-call implementation.** One failed assignment after a successful resolve/label or after dispatch creates inconsistent work. An outer JavaScript function cannot make independent Supabase calls atomic. This is a pre-activation requirement.

**Exact clause:** “Extend the canonical D4 admission command to validate the complete desired result and atomically claim the exact ready P17 preparation, immutable reply/send intent, D3 work/reminder effects, D6 assignment/history, D21 exact label membership changes/history, command receipt and durable dispatch/secondary-effect intents. Validation, stale relevant state, permission failure or any local persistence failure commits none of these effects. Reuse owner validation and transaction-level mutation primitives; do not call public independent commands in a loop, create a parallel shortcut transaction model or put Resend I/O inside the transaction.”

**Proof:** Inject failure at each local write/receipt/outbox step; all local effects roll back and preparation remains unadmitted/no dispatch authority. A successful atomic result makes every intended domain effect visible once with correct source evidence.

### DR03 — Use a flat desired-state proposal, not an action interpreter

**Material concern: yes. High severity, high likelihood if legacy action JSON is retained.** Ordered status changes, duplicate assignments and Add/Remove conflicts can depend on array order or silently skip. Existing snooze and note actions expand C beyond its demonstrated need. This narrows the action vocabulary.

**Exact clause:** “A shortcut is a bounded preset of the existing reply form: one eligible Shared Reply wording reference, at most one work-status choice, at most one compatible handling choice, and disjoint explicit label additions/removals. Reject duplicate/conflicting/unknown action keys rather than last-write-wins or skipped success. Compile to one desired-state command. No conditions, loops, branches, external actions, custom field paths, scripts, webhooks, timers or arbitrary action ordering are available. Apply the same final-state validators as native actions.”

**Proof:** Duplicate status/assignee, same label in Add and Remove, unknown legacy kind and unsupported action input fail before staging/activation/admission. Current no-op label/status outcomes produce no phantom history or metric while the actual reply still has its normal effect.

### DR04 — Keep reusable wording with P17 and personal material personal

**Material concern: yes. High severity, medium likelihood.** A macro body store, reference to My replies or private source attachment can bypass D18 curation/retention and later publish private text. Editing wording and activating action configuration are different rights and outcomes. This resolves ownership.

**Exact clause:** “Support owns the shared shortcut definition, permitted-use scope and bounded proposed work fields. P17 owns the referenced exact eligible published Shared Reply wording revision, authored locale, assets and content controls. The shortcut stores a typed source reference, not a second editable body, compiled HTML authority, managed signature or live nested text expansion. Configure source wording through the same contextual Email Studio capability; publishing wording does not automatically activate or repoint shortcuts. A contextual publish-and-use sequence reports source publication and shortcut update separately. My replies/Internal note sources are not shared shortcut inputs; ordinary authorized draft editing and separate D18 insertion remain available.”

**Proof:** Personal source/private-note source/cross-tenant/unpublished/care-derived source cannot activate; shared source edit does not mutate staged copies; source publication succeeds while shortcut update conflicts and UI preserves both truthful states; no shadow attachment custody or body logs.

### DR05 — Scope and curation do not confer execution authority

**Material concern: yes. Critical severity, medium likelihood.** A staff-maintained shortcut can reference a label/person/source that a user cannot access or change. Broad existing staff CRUD and service-role adapter checks do not prove the selected model. This changes authorization requirements.

**Exact clause:** “Separate shortcut use and maintenance/activation from P17 source authoring/publication and actual reply/work permissions, using existing tenant/resource capability conventions. Validate tenant, inbox/source scope, current actor, current wording/source/asset disclosure and every requested final action during selection preview and again at admission. Shortcut availability never grants a permission. Missing or unauthorized actions block the affected combined admission with safe repair; do not silently skip them or leak hidden target names/counts. A user may deliberately remove an optional pending action and review the resulting authorized command; that is a new visible proposal, not success for the old one.”

**Proof:** Different capability combinations for reply/assignment/label/status/source use; tenant/inbox switches; access loss after preview; hidden labels/person/source metadata; unauthorized source use in a valid inbox; current staff allowed to reply but not administer preset.

### DR06 — Me, named staff, Shared and responsible team retain D6/D8 meaning

**Material concern: yes. High severity, medium likelihood.** Me can steal an assignment if treated as unconditional claim; a named employee may leave or not match the preserved team. An automatic workload limit can wrongly deny legitimate manual work. Review-first handoff could be accidentally completed through a shortcut. This narrows handling.

**Exact clause:** “Resolve Me to the actual current eligible human. On currently Unassigned work it uses D6's conditional claim; on already-assigned work it is a separately visible authorized reassignment, never an unconditional claim. Named staff and any explicitly changed responsible team must be currently eligible and operationally compatible. Keep preserves the actual current team. Manual assignment may exceed the automatic limit or choose someone outside the automatic pool under D6's visible advisory. It never overrides revoked/departed access, pending D8 review, D7 Keep/coverage controls or source restrictions. The shortcut cannot approve a handoff or rerun routing to make its target valid.”

**Proof:** Two simultaneous Me claims; another worker claims after preview; over-limit/outside-pool valid manual target; incompatible person/team; departed employee; pending access-loss review; deliberate Shared outcome; no private draft ownership transfer or new author on existing prepared reply.

**Existing control nuance:** D7 may require an explicit current-episode Keep decision when a reviewed assignment retains a covered person. Expose that runtime choice through the actual handling contract; a reusable preset never stores blanket Keep authority. D8 mode C blocks a handling change until its separately authorized review, but otherwise-authorized reply/status/label work with no handling patch remains possible and never approves the handoff. D8 mode A may be settled by a qualified explicit individual assignment even when automatic release is paused or independent shared cover is absent; do not turn those automatic conditions into an unjustified manual-assignment denial.

### DR07 — Final work state respects real obligations and reminder semantics

**Material concern: yes. High severity, medium likelihood.** A canned phrase such as “all sorted” cannot certify completion. Resolve could cancel a promised follow-up; a raw old status write could reset reminders or historical resolution times. This preserves D3/D4.

**Exact clause:** “The pending After sending choice is explicit and uses D3's current obligation/transition validation. Keep performs no status/reminder write. Waiting side is not inferred from message direction or wording; Resolve cannot hide known outstanding Support obligations or required review and does not complete CRM/giving/care/delegated work. Native status effects on reminder generations and work history remain exact. No new reminder/snooze timer is added by this shortcut purpose. A header status control still performs its existing immediate native action; it is visibly distinct from pending post-admission work and may invalidate a stale staged proposal.”

**Proof:** Keep on newly changed status preserves current value/reminder; resolve with outstanding required obligation denied; two waits and mixed blockers; reply queued/failed not proof requester received a question; stale timer event after resolve; no repeated resolution episode for same intent.

**Existing obligation nuance:** D11-R12 requires review of a relevant outstanding owner result but expressly allows legitimate Support completion while a merely linked independent owner process continues. Do not require every related task to finish. D5 No response is a separate guarded ending reason with exact current request/input/delivery/commitment review; it is not an extra preset status, nor can a canned closing bypass that review.

### DR08 — Merge topology means one component command with exact original effects

**Material concern: yes. Critical severity, medium likelihood.** A merged conversation can contain several original label contributors and unseen updates. Using root-only revision/label operations can erase the wrong origins, partially remove labels or allow competing sends through different URLs. This changes source addressing.

**Exact clause:** “Bind staged review and admission to exact current D10 component/topology controls and D4's source-aware target message/audience. Component work/handling changes occur once for the reviewed current component. D21 Add anchors to the continuing origin and is unchanged when already effective; Remove ends the exact reviewed authorized contributing memberships atomically. Newly changed contributors/topology or relevant unseen input invalidate stale admission. Do not follow a mutable root silently, duplicate effects on every original row, merge participants, retarget the reply or transfer a private draft. Post-admission merge/Undo preserves original message/effect lineage and changes no frozen envelope.”

**Proof:** Two drafts from separate original URLs; merge/unmerge between staging/preparation/admission; label present on two contributors; one contributor inaccessible; concurrent Add/Remove; retry after Undo; related-but-unmerged conversation stays independent.

### DR09 — One draft proposal and explicit revision changes avoid accidental stacking

**Material concern: yes. High severity, medium likelihood.** Applying multiple shortcuts can retain old work after replacing only text, duplicate attachments/signatures, or apply late results to another draft. A generic stack/undo engine is unnecessary. This is a proportional UX/data safeguard.

**Exact clause:** “Keep at most one active shortcut proposal in a draft. Selecting another requires a visible replace/review result for pending work rather than silently merging conflicting plans. Preserve existing human text and D18 provenance using explicit Insert/Replace semantics and bounded local Undo; no speculative regex removal of earlier wording. Shortcut/source revision, draft occurrence, staged patch, actual user modifications and expected relevant source/control revisions are distinct. Definition edits do not mutate staged copies. Late selection/preview/autosave responses cannot attach text/actions to a different tenant, actor, purpose or draft.”

**Proof:** Rapidly select two shortcuts; edit copied wording then replace preset; prior pending resolve cannot survive unseen under new reply text; D23 signature remains exactly one; same file references preserve D18 insertion rules; leave/reopen draft, switch Reply/Note and undo after edits.

### DR10 — Local admission success and external delivery success are separate

**Material concern: yes. Critical severity, medium likelihood.** Retrying after a lost HTTP response can send again or repeat assignment/labels after newer work. Reverting the local work on provider failure can overwrite later state. This is the decisive failure semantics.

**Exact clause:** “One permanent semantic command identity and immutable input digest cover the reviewed complete reply and final work patch. A lost admission response reconciles that identity before any new command. Same input returns the original receipt separately from current authorized state; conflicting input rejects. After local admission, show the reply as Queued and the local work changes as applied. P6 sends the frozen prepared envelope through tenant Resend. Failure/suppression/uncertainty after admission never replays or rolls back the old shortcut patch, swaps actor, rerenders wording or creates a new send identity. Fresh actionable failure opens D3 review causally under the original effect; duplicate/late evidence cannot thrash work.”

**Proof:** Lost local response, provider timeout after possible acceptance, assignment later changed by another worker, same reply retried after later label removal, signature/source updated before retry, expired provider key window, late success after adverse evidence. No compensating rollback pretends the original local effect never happened.

### DR11 — Immutable definition lifecycle and shared custody

**Material concern: yes. High severity, medium likelihood.** Mutable JSON plus ordinary delete can alter what a prior shortcut meant or lose shared definitions when their creator departs. Automatically repointing a saved definition to changed wording alters approved behavior. This changes maintenance persistence, not introduces another workflow system.

**Exact clause:** “Each shared shortcut has one immutable tenant/source identity, explicit permitted-use scope, versioned bounded definition and tenant custody independent of creator membership. Edit produces a candidate; activation validates the complete definition and exact current source/target eligibility and atomically advances the active revision with trusted audit. Ordinary metadata change is distinct from changed behavior. Publish/activate are not direct fields callers set. Archive stops new selection while existing staged copies retain their valid native owner checks; safety restriction and permission loss can block unsafe future admission. Restore creates a current validated candidate/revision, never replays actions or reactivates withdrawn rights. Source changes or unavailable target references show repair; no automatic substitution.”

**Proof:** Concurrent edits/activation/archive; creator departure; new staff reusing email; source wording ordinary archive versus safety revocation; active target deleted/archived; old staged definition still safe versus newly forbidden; restore does not reassign work or send.

### DR12 — Relational constraints and privileged paths must close bypasses

**Material concern: yes. Critical severity, medium likelihood.** Array-shaped JSON cannot prove valid enums/targets/tenants or trusted publisher/actor. A new narrow API alone leaves blanket RLS/direct writer or automation paths able to bypass atomicity. This is mandatory implementation safety.

**Exact clause:** “Store definitions through their typed owner schema and tenant-aware source/publication/label/inbox/staff references. Required IDs/revisions and valid purpose/lifecycle combinations are non-null and constrained; structured bounded action configuration is validated before persistence and after version migration. Derive actor, tenant, author, approval, command timestamps and audit attribution from trusted context. Restrict direct table/column mutation to approved native owners; expose no direct route that can partially run a shortcut or change immutable ownership/purpose/publication. Audit effective USING/WITH CHECK, SELECT visibility, permissive-policy composition, service/BYPASSRLS, invoker/definer RPCs, execute grants/search paths, storage and restored grants. Cross-row current eligibility and compound transitions belong to the authoritative transaction, not unsafe cross-table CHECK assumptions.”

**Proof:** Tenant/owner/purpose swaps, same-tenant wrong-source targets, forged actor/reviewer, raw JSON unknown action, direct REST/collection/server/service/automation calls, expired capability, old-policy OR bypass, source asset/read denial, rollback of receipt/history failure. PostgreSQL's effective USING fallback is evaluated; absence of an explicitly written WITH CHECK alone is not claimed to be a vulnerability.

### DR13 — Fixed manual presets must not become Phase34 or AI execution authority

**Material concern: yes. High severity, high likelihood if current shared macro/automation type drives design.** The code explicitly plans automatic execution through macro actions. Reusing that hook could let a future model, webhook or workflow invoke a human-curated reply without current human approval, or add general conditions/tasks. This resolves a real platform seam.

**Exact clause:** “D24 is a fixed manual Support form preset that stages one existing D4 compound command. Its bounded definition and curation belong to Support; P17 owns wording/preparation and P6 delivery. It is not a general action interpreter or tenant-authored automation: no triggers, enrollment, branches, waits, loops, automatic action execution or workflow-run ledger. Record this narrow manual distinction in the later authorized owner/OpenSpec reconciliation. Phase34 remains the sole configurable workflow owner and can only invoke separately qualified domain/message contracts under its own authority. Future AI may propose eligible definitions/wording/actions through a separately qualified permission-aware assistance contract, but neither a definition nor model output authorizes admission. The same current human review, exact source/revisions, final command and privacy boundaries must remain; no dormant AI/provider/vector/tool execution system is implemented now.”

**Proof:** Inbound message containing commands/shortcut names cannot execute; model or workflow cannot call a human-send action with borrowed actor data; suggested definition reference current-invalidated before approval fails safely; no new catalog/system template or global Resend sender; no automatic training corpus of private draft content.

### DR14 — Migration, truthful audit and operational recovery are part of the permanent fix

**Material concern: yes. High severity, high likelihood because incompatible legacy routes exist.** Retaining old macro routes or silently translating unsupported actions leaves two semantics; copying old definitions can activate private notes/raw text or recreate personal ownership. Incorrect analytics can count preset selection as a sent reply. This changes rollout and proof obligations.

**Exact clause:** “Inventory existing macro/automation/client/server/raw-action writers, definitions and source references. Convert eligible legacy definitions into reviewed inactive candidates; unsupported or ambiguous actions remain access-controlled Needs migration, never skipped into active behavior. Fence old runners/direct setters for the qualified traffic before enabling C. Preserve known source/history/privacy truth, not fabricated past approvals or action outcomes. Record minimal actual definition/draft/command/preparation/source/action-effect IDs, trusted actors and truthful local/provider outcomes; selection and definition maintenance are not CRM contact events or response metrics. Cache/index/attention work uses existing owner projections and durable secondary intents. Kill switches stop new unsafe staging/admission while leaving valid records and admitted-message recovery accessible; rollback cannot revive partial execution or stale schema/permissions.”

**Proof:** Old-client/new-schema and new-client/old-schema gates; legacy personal macro with private note/unsupported snooze; migration rerun; already admitted send during rollout; events after restore; audit/result correlation across local failure and provider uncertainty; no content-bearing debug logs or client-secret persistence.

## Minimal operational model

A guide has a stable owner-defined identifier, non-null tenant, fixed canonical language, purpose fixed to ordinary Support instructions, source lifecycle generation and maintainer reference. Its language describes its authored content; translated instructions use a separate deliberate guide identity. Titles need not be unique and never establish identity. There is no automatic locale-family synchronization, per-inbox copy or audience builder.

The working candidate is distinct from immutable published revisions. At most one current candidate and one current published head exist per guide. Publication can coexist with a candidate containing unpublished changes. A current publication is served only when ordinary source state is Published, current safety permits it and the actor has current Support-read authority. Archive denies ordinary serving even though authorized management can retain earlier revisions. A source safety restriction independently denies relevant reads/publication and survives archive/restore/new revisions until the protection owner admits a reviewed release.

Enforce tenant/guide-qualified FKs among operational candidate/revision/head records, a unique revision identity, one candidate/head per guide, valid state/head combinations, fixed language/purpose and protected publication/control fields. Actor/tenant/time/approval/control metadata comes from trusted server context. Owner references cannot be changed to a different tenant; author/maintainer departure cannot cascade-delete tenant content or erase historical attribution. The exact deletion behavior for identity references must preserve allowed body-free attribution without requiring the departed user to remain active.

Public selections continue to reference CMS by owner-validated soft identity and current public-generation/destination proof. Do not create a cross-schema FK, a polymorphic visibility switch that updates source authority, or a universal table joining internal bodies into public search. A closed source discriminator in the finder DTO tells UI which owner and actions apply; it is not a writer permission.

## Current capabilities, grants and RLS

Common Staff guide readers are the active tenant's currently qualified Support readers. This intentionally does not expose content to every generic staff/admin role, CRM record owner, inbox participant or matching-email agent. Tenant-level Staff guide authoring capability permits the ordinary common guide candidate/history work in that tenant; tenant-level publication and source-protection/deletion actions are separately qualified. The same person may hold author and publisher capabilities; there is no obligatory new reviewer role. D19's held-mail reviewer and D18's inbox-specific wording curator do not automatically gain these actions.

The common audience is suitable only for reusable non-case-specific instructions. Restricted financial/care/HR/security/missionary records remain with their respective owning domain. A guide can explain a general path without copying a restricted record, recipient token, actual donor data, private case link or live CRM field into common content. Known classified source material is rejected on inappropriate import/copy paths. Freeform prose still requires accountable author review and a real withdrawal/correction process; the feature does not claim an infallible detector.

Application authorization and SQL grants/RLS/column controls must independently enforce the read, draft/history and mutation distinction. Both USING and effective WITH CHECK must be tested; Postgres can reuse USING if WITH CHECK is omitted, so syntax absence alone is not proof of an exploit. Test the actual new-row outcome, not just that a policy exists. Privileged workers, functions/RPCs, security-definer/invoker views, API routes and any linked-storage access need the same tenant/purpose/capability boundary. Internal/backup tables with no direct reader are revoked from exposed roles. No service credential is a client authorization shortcut.

## Authoritative command and revision transitions

| Command/event                   | Required preconditions and atomic outcome                                                                                                                                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create guide                    | Current tenant authoring authority, validated original Staff guide document/purpose and valid fixed language; one guide/candidate/receipt. No published head.                                                                                 |
| Save candidate                  | Current authoring authority and exact expected candidate/source generation; overwrite only the acknowledged candidate, never the current published revision.                                                                                  |
| Publish to staff                | Current publication authority, no unresolved safety restriction, validated exact candidate, common audience and observed generation/diff; one immutable revision/head/audit/receipt/required continuation transaction.                        |
| Discard candidate               | Current authority and explicit intent; published head unaffected. Unsaved browser text cannot be silently claimed saved.                                                                                                                      |
| Archive                         | Current source-management authority; atomically deny new ordinary reads/search at the owner head. Existing candidate/history custody remains explicit; unsaved changes require save/discard choice.                                           |
| Restrict unsafe source          | Current protection authority/reason; immediate denial independent of ordinary Archive. Publication or a new revision cannot clear restriction.                                                                                                |
| Restore archived/prior revision | Current source/history authority; create a candidate and preserve current candidate/unsaved work unless explicitly reviewed replacement is accepted. No public/staff publication or safety release.                                           |
| Release safety restriction      | Actual authorized owner reviews current source/purpose and admits a new release generation; normal publisher permission alone is insufficient. The same actor can hold both permissions when allowed.                                         |
| Delete archived content         | Re-prove current delete authority, retention/hold and generation; deny serving, record durable purge/tombstone/receipt, dispose of allowed source/derived content. Required held content stays in restricted custody; completion is truthful. |
| Reassign maintainer             | Current tenant content oversight; choose eligible current maintainer without changing content/publication or historical author.                                                                                                               |

Each command binds idempotency to its durable business effect and payload digest. Identical retry returns the original outcome; a changed payload under the same key conflicts. Lost response requires receipt lookup, not a blind new effect. A stale autosave or restore cannot defeat archive/deletion, and a late index rebuild cannot recreate a deleted guide. Required projection/purge continuation is durable in the same authoritative commit; no distributed write into CMS/P17 is introduced.

Source safety and ordinary archive use the same immediate serving-denial infrastructure without collapsing their authorities. A restriction applies across retained candidates/revisions and recognized derivatives of that guide. Restoring an unsafe old revision and pressing Publish remains denied absent current protection-owner release. Neither this mechanism nor consultation-only UI promises to identify all manually retyped information.

## Validate before generic editor normalization

The original canonical input and the trusted source-purpose envelope must be checked **before** generic Tiptap/ProseMirror parsing can strip unknown attributes. Purpose derives from the stored guide and command, not `attrs.internal=true`. Validate allowed node/mark/attribute set, structural depth/node/byte bounds, fixed language/purpose, safe link destinations and known source restrictions. Unsupported input fails with recoverable author feedback and does not overwrite the last valid candidate.

The narrow profile supports structured instructional text. Do not expose media uploads/attachments, third-party embeds, raw HTML/script, recipient personalization, live CRM bindings or executable checklist nodes. Navigation links use validated HTTPS or qualified internal application destinations, never secret-bearing signed URLs, code/data URLs or arbitrary server fetches. Links to another guide or owner do not carry authorization; target reads/actions are rechecked. This shares editor/rendering primitives with D23 but not its message-publication identity or a paid collaboration service.

The [actual-source experiment](phase26-d27c-source-probe.json) used the installed shared Tiptap 3.22.3 schema: synthetic unknown purpose/source attributes were normalized away; a generic image node was admitted; a strict unsupported node was rejected. No network image fetch occurred. These observations explain why profile validation must precede normalization; they do not prove a server bypass, actual clipboard handling or the new Staff guide implementation.

## Two private/public query contracts behind one UI

Public is unchanged D27 owner-qualified selected-Page search. Internal uses operational published Staff guide heads and private text search. Both share query UI conventions, not a result corpus. Only the active tab is queried. There is no All result mode, cross-owner score fusion, hidden internal count on a public query or automatic private query extraction from a conversation.

Internal searches title/summary/body with stable identity tie-break and complete authorized corpus before cursor paging/counts/snippets. Use indexed tenant/current-head predicates and batched current authorization. Public Site filters never apply to Internal; language is explicit. No client-side first-page filtering, N+1 source calls or stale public cache is an acceptable shortcut. Positive publication/index lag can yield a visible Updating/partial state. Archive/safety/delete/revocation must deny new results before eventual index purge. Current head checks and restrictive tombstones prevent favorable stale replay.

Private browser/server caches must bind current tenant/actor policy scope/source head and safety generation. Avoid durable browser-body/offline caching. Current revocation clears an open reader on invalidation and is rechecked on subsequent reads; already viewed text cannot be recalled. A routine new revision prompts a deliberate reader refresh without moving their scroll mid-procedure. One source/tab failure does not block the other or an unrelated Support reply.

## Content custody and final disposition

Each class must have an explicit owning retention/disposal rule and tested final disposition before activation. Reusable knowledge is not transient conversation content, so no arbitrary D17 conversation timer is copied onto it. This contract deliberately uses source-purpose lifecycle; any applicable platform records policy/hold still prevails. There is no new universal legal period or promise of indefinite retention.

| Class                                    | Purpose, retention/disposal rule and serving boundary                                                                                                                                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current published guide                  | Retained while current approved reusable instructions; ordinary serving ends immediately on Archive, safety restriction, deletion or lost reader authority. Replacement does not rewrite historical revisions.                                                            |
| Working candidate                        | One current candidate for ongoing authorized editing; replacement/discard/delete is explicit, with no unlimited hidden autosave snapshot history. Applicable source retention/hold may require restricted custody after serving ends.                                     |
| Superseded published revisions           | Only the owner's declared maintenance/history/restore retention, visible to authorized management. Restoration creates a candidate under current safety; no reader endpoint silently serves a chosen historical version. Disposed body is not reconstructible from audit. |
| Archived source/candidate/history        | Retained for explicitly declared source maintenance/records custody until qualified restore or disposal; not available to ordinary finder/readers. The implementation must declare this policy before activation rather than silently retaining every revision forever.   |
| Deleted/restricted content               | Serving stops first. Durable purge clears allowed bodies/title/summary/revisions/derived text; required held copies remain isolated under the actual records owner. Release/retry resumes permitted purge with truthful progress.                                         |
| Index/cache/preview                      | Derived, short-lived/rebuildable only from currently permitted source heads; current adverse denial precedes purge. No public corpus, independent restore authority or durable private offline cache.                                                                     |
| Audit/tombstone/receipt                  | Minimal permitted body-free identity/generation/effect/actor/disposition evidence under existing audit/records custody. Avoid storing titles or reasons that would preserve content subject to deletion.                                                                  |
| Actual Support messages and P17 material | Existing D16/D17/P17/P6 custody only. Guide use does not restart conversation clocks, extend provider-request storage, or add URLs/provenance to P17 Recent sent copy.                                                                                                    |

Backups/exports follow their actual owning recovery/custody contracts; a restored backup must apply current deletion/restriction/tenant state before becoming serveable. A retention hold racing deletion must stop unauthorized disposal, not revert the serving denial. User confirmation is not hold-release authority. P31 proves allowed disposal, restricted retention, later release/retry and no stale reappearance.

# D30 — Independent UX research for a focused Support overview

**13 September 2026. Founder selection: A, with eventual full configurability kept in mind.** This is independent research and a proposed behavioral blueprint for the root's D30 adversarial synthesis. The founder has selected the direction; these additional exact proposals are not independently ratified. No prototype, runtime, formal specification, GitHub change or usability proof is produced here.

## Judgment

Accept the focused overview direction with required clarity safeguards. The best first version is an immediately useful reporting home in **Support → Reports → Overview**, not a new application home, a compulsory daily screen or a miniature dashboard builder. It should answer two different questions visibly: **What work needs attention now?** and **What did the qualified reports measure for this period?**

The difficult part is not the number of cards. It is ensuring that a familiar-looking scope selector, percentage or count does not quietly change meaning. The fixed overview should consume the already-ratified D14, D21 and D28 definitions and lead to their exact details. It should not invent a universal support score, new volume/resolution metrics, staff productivity, donor-value weighting or another reporting owner.

Future configuration is a real product intent, but the present work should qualify stable source-owned modules and simple context contracts, not ship hidden schema, a blank builder, drag handles, disabled Customize buttons or configuration settings with no current purpose.

## Concrete proposed composition

Use one calm page with ordinary headings and responsive sections, not a dense field of equally prominent KPI tiles. The composition below is a disciplined recommendation; final exact adoption belongs to the root's D30 decision.

### Work now

Place **Currently handled in [All accessible inboxes ▾]** inside the Work now header, with a clear As of/refresh state. This control affects only current work. A selected inbox is a stable qualified reference; Unassigned is a real source fact, not failed person hydration. No inherited hidden CRM, label, date or previous-view filter may silently modify the page.

Three principal summaries are sufficient:

| Summary                       | Exact meaning and destination                                                                                                                                                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **All unfinished**            | Current authorized unfinished conversations under D3, including both Waiting meanings and deferred work. Open the exact existing work list. Ordinary waiting does not become an error or urgent workload.                                         |
| **Unassigned**                | D6's complete unfinished work without an individual assignee, including Waiting/deferred work and any responsible team. Open the same exact Unassigned view. Shared mode is not failure.                                                          |
| **Replies needing attention** | D14's current all-age conversation work, with concise distinct facts for overdue, timing/evidence unconfirmed and untargeted reply work. Open D14's exact view; do not narrow to only overdue targeted requests. Its subgroup counts may overlap. |

Keep existing follow-up and qualified delivery/coverage recovery destinations visibly reachable beside this summary. An exact owner-qualified count may be useful, but do not invent a generic Problems union or count every old provider failure as current recovery. In particular, a due-reminder counter must not claim the obligation is gone merely because a worker cleared a reminder during an authoritative due-review transition. Existing source-owned work/recovery meaning decides what remains actionable.

The existing **Feedback needs review** destination also remains an all-age review entry, independent of the historical invitation period. Put this quiet action link inside the Feedback section, visibly labelled as across reportable inboxes, rather than making it appear to inherit Work now's current-inbox selector. Its existing owner retains original invitation-inbox scope. A qualified count is useful; this is not a new fourth satisfaction score. A conversation can be Resolved while its later feedback still needs review; these are separate facts.

Do not add these summaries into a grand total. Unassigned and Replies needing attention can be subsets of unfinished work and overlap each other; valid feedback review can concern ended work. Do not color every nonzero value red. Text and the exact work state distinguish ordinary waiting, due attention and actual failure.

### Results for a selected period

Give the historical area its own visible scope sentence:

> Across the inboxes you can report on. Work now filters do not apply.

The period area has date and timezone controls only. It does not reuse the current-inbox selector. The sentence means each source report's current capability, source and field restrictions, including meaningful retained historical/retired references where the owning domain permits them. It does not mean only today's active inbox directory, unrestricted tenant access, a grant to archived material or identical record populations in every report.

**This is the simplest permanent scope solution for fixed A.** D14 historical policy/custody/actor dimensions, D21 current component home and D28 original invitation inbox are not one universal Inbox predicate. For a historical inbox investigation, open the detailed report and use its properly labelled source-owned filters. The link carries the period and zone, not Work now's current-inbox predicate. Several module-local pickers would add clutter; one misleading global picker would be worse.

Use the three existing reporting families as four readable sections:

1. **Reply targets.** A small First/Next presentation of the D14 on-time assessed result with its numerator, assessed/finalized coverage and visible unknown/excluded/potential-target context. Use the exact Targets due in period cohort. No aggregate green “All on track” shield. **View reply targets** opens the owned report.
2. **Reply times.** A compact First/Next table with median and p90, exact sample count and explicit clock basis. Label the population as waits ended by a staff reply in the period; one reply can end several waits. Bounded/unknown completion times remain disclosed rather than rounded into an invented exact duration. **View reply times** opens the owned report. Do not force mixed calendars/modes into one number merely to fill a card.
3. **Topics.** A short horizontal label comparison/table with the D21 conversation cohort, current-label meaning, total/labelled/unlabelled coverage and overlap explanation. The complete report is available through **View topics** or the established Labels-report label; use one consistent final name throughout. A preview limit must say it is a preview and must not turn omitted labels into zero or an exclusive Other population.
4. **Feedback.** A concise invitation-cohort summary and the submitted rating distribution/counts defined by D28. The denominator remains issued invitations whose submission may have begun, including provider-indeterminate effects. Show actual available rating sample/coverage; preserve the small-sample caution. **View feedback** opens the full report. A response date browser and all-age review queue remain different destinations from invitation-cohort analysis.

Sections can be arranged in a responsive two-column layout on larger screens and one column on narrow screens, in the same semantic order. Exact charts are optional when a small labelled table is clearer. No previous-period percentage arrows, automated interpretations, employee ranking, custom chart types or report-email scheduling are needed for this complete first composition.

### Date and time controls without hidden state

Use a compact date-range control with a few understandable presets and Custom; the existing qualified report owner determines its allowed bounds. Display the exact chosen dates and named report timezone alongside it. If a relative range includes today, say **Includes today so far** and use the actual evaluated boundary; a calendar day is not assumed to be 24 elapsed hours across daylight-saving changes.

A default such as 30 days is a product convenience, not a researched universal standard. Do not change another user's preferences or the inbox's service-hours calendar when changing report timezone. A chosen display/report zone determines date boundaries; it cannot recalculate D14's frozen service-time policy or change stored events. Custom invalid, unavailable or unsupported periods retain input and show an inline correction, not an empty successful report.

During report → detail → Back, retain the exact evaluated interval and zone the user was investigating. A deliberate refresh or new relative-period selection may recompute it and must expose the resulting range. Avoid a full saved-layout preference lifecycle just to preserve ordinary navigation.

## End-to-end staff and lead journeys

### A lead investigates current work

1. Open **Support → Reports → Overview**. The active tenant remains the ordinary Asym tenant context. The page does not assume tenant-admin or CRM access from a lead-like title.
2. Read Work now. Optionally choose an accessible current inbox within that area; the historical area keeps its own clear scope.
3. Open an exact summary or existing recovery link. Preserve its definition, current source scope and evaluation context. Counts and the initial drilldown must agree for that evaluation and unit, subject to current privacy reauthorization.
4. Open a conversation into canonical Support detail. A target/wait report may contain several instances for the same conversation; its list must show its true unit, not disguise instances as unique conversations.
5. Use the existing Support action or permitted CRM/owner link. No action is added to a chart, no inferred customer identity is created and no support-side copy of financial or care information is saved.
6. Return to the same permitted report/list context. If work changes while open, keep the current detail/draft stable and explain changed membership. Do not replace the active conversation with the next array entry or silently reuse revoked content.

### A lead reviews historical information

1. Choose the period and report timezone under Results. Confirm the displayed date range and cross-inbox scope.
2. Read the selected existing metric's unit, sample and uncertainty; different sections answer different questions and cannot be added together.
3. Open the full report for a specific issue or inbox review. Its own filters state whether they concern original source, historical responsibility or current component home. The overview's Now filter is never carried across silently.
4. Follow the exact source-backed rows to shared detail. A new live evaluation may differ; show the later As of state, not a false count-parity promise across changing data.
5. Use existing qualified export only from its owner surface when permitted. The overview adds no export, saved snapshot, schedule, public wallboard or email digest capability.

### An everyday responder stays in their work

The usual D20 personal/shared work view remains directly accessible. Reporting is not a forced landing, daily acknowledgement, staffing declaration or requirement to classify every conversation. A responder may use Overview when useful, then return to the same work and draft. Having no report permission should not remove otherwise-authorized conversation handling.

### CRM-first investigation

From a relevant authorized CRM record, open the D26 Support relationship and the same canonical conversation detail. Reporting origin and CRM origin each retain their own return anchor; opening a CRM record from report detail must not erase the outer report context. CRM restriction does not fabricate a missing Support fact, while Support restriction removes Support counts/content even if the CRM record remains readable. Viewing a report or returning through CRM creates no duplicated communication event, contact update, consent change or business completion.

## Maintenance and future configuration

The fixed page has no tenant authoring workflow. Its ordinary controls select a read context; they do not require Save, Publish or an admin approval. A failed read is retried as a read, not as a reconfiguration. Staff should never need to edit or recreate dashboards to repair a stale metric definition.

The product/report owner maintains the fixed composition, definitions and qualified drilldowns together. If a source changes, update its versioned adapter and compatibility proof; do not calculate an attractive approximation in the browser. Current-source hydration may become unavailable after staff departure or inbox retirement without changing historical attribution. Preserve meaningful permitted historical references under the owning contract, never raw-ID display or invented active replacements.

For future configuration, keep each module's source identity, formula/version, unit, supported context dimensions, authorization and destination explicit in the design. A future shared composition owner may then arrange compatible modules without changing their authority. This is ordinary sound modularity; it does not require a plugin registry, arbitrary expression language, report warehouse, custom JSON schema editor or database tables for unused layouts now. Full configurability later remains separately scoped work, not a commitment that every conceivable metric, data join or action becomes configurable.

The [Phase 33 roadmap](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L3572) defines the intended shared reporting ownership. It is not an already-shipped general report service. A can be a bounded consumer of qualified source read contracts without waiting for the entire future platform. The same metric must have one definition wherever it appears.

**Email Studio seam:** opening Overview, changing period/scope, refreshing or preparing a future layout sends nothing. It does not trigger D28 invitations, alter D29 acknowledgements, publish reply targets, send a manager digest or subscribe staff. Any future separately authorized scheduled report belongs to P33's run/recipient policy, P17's governed message preparation and P6's dispatch/history. No email or Tiptap editor is necessary for this read-only overview; D23's existing rich-text profiles continue in actual Support authoring surfaces.

## Visual craft and required proof

Use Core's base-maia/shared UI primitives, semantic tokens and existing reporting navigation. Prefer readable sentence-case headings, restrained borders, space between the two areas and aligned numbers with explicit units. A metric should look like an actionable summary only when it has a valid destination. Avoid decorative gauges, percent arrows without a qualified comparison, animated counters, busy gradients and repeated help text around every number.

On a narrow screen, the order remains Work now, its current recovery links, then the historical controls and report sections, including Feedback's separately labelled all-age review link. Long inbox/label names and translations wrap; the overview does not demand horizontal scrolling to read ordinary prose or controls. A genuinely two-dimensional detail table may scroll within its own region while headings and controls reflow. W3C's 320 CSS-pixel reflow criterion is not replaced by a 200% zoom spot check. Shared touch dimensions, nontext contrast and both themes require effective browser measurement rather than assumptions from utility classes.

Definitions are a labelled button/disclosure usable by keyboard, touch and screen reader. Announce meaningful loaded/error outcomes without repeatedly reading every refreshed count or stealing focus. Sticky elements must not cover focused date/inbox controls. Low bandwidth should still permit readable text summaries and direct work navigation; no perpetual animation, required video, offline mutation queue or message-body download is justified.

Required user/domain proof includes: opening ordinary work without Overview; selecting one current inbox while historical scope stays explicit; an old unfinished/unassigned/waiting request surviving date changes; due-worker and late-provider transitions; First/Next target/wait units; source-specific historical inbox narrowing; merged label cohorts; issued-but-provider-unknown feedback; current Off with retained history; an old feedback response needing review; empty/error/partial/stale distinctions; a permission change between count and detail; report → Support → authorized CRM → Back with draft/focus preserved; logout/tenant switch and out-of-order read responses; mobile, keyboard, screen reader, reflow and low-bandwidth paths. Source query completeness and production-shaped performance need separate measured proof.

This research supports a complete proposed experience, not a claim of perfect UI. No browser, assistive-technology session, representative tenant usability study, runtime load test or production journey was executed. The root's synthesized D30 clauses and companion contracts must resolve final exact composition and defaults consistently before recording the amended decision.

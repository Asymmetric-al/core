## Main finding

A saved view must preserve a readable question about current work, not serialize whatever happens to be in a screen's URL. It reuses the platform's named-views capability with a qualified Support subject/catalog, personal shortcuts and one canonical authorized query contract. The main dangers are unintentional shared-definition changes, ambiguous filtering, stale results that conceal work, and scope changes that reveal metadata or silently broaden results. None requires a new workflow or publication engine.

The strongest simpler alternative remains shared-only views. It lowers personal configuration but makes recurring individual slices repetitive. Standard queues plus temporary filtering remain usable if saved views are unavailable. A is useful because personal customization is optional while shared maintenance can provide common team meaning.

## Exact minimal requirements recommended to the root

### L01 — Three independent facts

Through the governing shared named-views capability, store and present (1) the owned saved definition, (2) the current working filter draft derived from it, and (3) the person's navigation preferences. Register a Support subject/table catalog with its real owner authorization; do not maintain a second Support saved-view authority. A view definition contains the bounded predicate, explicit sort and only supported default presentation choices. It never contains selected rows, selected conversation, message draft, cursor, scroll position, refresh timestamp, resolved result IDs or a copied data snapshot. A pin references a stable view identity; it is neither a copied definition nor sharing authority. Current saved identity/revision is explicit and never guessed from the first equal predicate.

### L02 — Reuse bounded ordinary filters

Use one typed server-validated query vocabulary shared by temporary filtering, saved views, count and pagination. Preserve P9's versioned nested AND/OR stored schema and typed field/operator/value catalog; the ordinary Support builder exposes bounded facets rather than a general nested logic editor. Include only the current qualified conversation facets needed by the ratified product: responsible inbox scope, D3 work status/unfinished, assignment (Any/Me/Unassigned/named eligible worker), authorized existing labels, ordinary supported text search, D14 reply attention and D15 Following. Do not introduce arbitrary SQL, regex, scripts, configurable action rules, per-view custom fields, CRM segmentation, historical report filters or side effects. Existing labels do not authorize a new taxonomy engine. Unsupported clauses/versions fail visibly; unknown fields cannot be dropped. Shared capability storage compatibility does not mean every stored operator becomes supported in the Support subject.

Named default scope must distinguish **All accessible inboxes** (a deliberately viewer-relative source set) from an explicit stored inbox selection. Scope is always visible. Across distinct facets use conjunction. Within selected statuses/inboxes/named workers use the displayed any-of meaning. Labels expose explicit **Match any** / **Match all**, with Match any as the proposed new-definition default; represent both through the shared nested predicate schema. Existing UI/API disagreement makes opaque multi-label migration unsafe. A missing set is the shown Any state only when validly specified by the qualified schema/default; an empty or malformed payload must not silently become broad Any.

### L03 — Stable identity and parameter meaning

Store stable tenant-bound IDs for named inbox/worker/label references rather than display names, slugs or email addresses. Renaming a label keeps its meaning. A name reused for a new object never retargets an old view. Preserve typed `current_viewer` for Me and Following; resolve it from trusted current staff identity on every evaluation. A named Alex filter stays Alex when Sam opens it. Unassigned is null assignment, not a missing permission lookup. No current principal mapping is a qualified unavailable state, not another worker or all work.

### L04 — Exact save and adjustment behavior

Saving captures the explicitly reviewed effective filter state, including visible inherited/default scope and any included search query. The confirmation summary must show precisely what will persist. If any field is excluded, preview the resulting definition before Save rather than describing it as the unchanged current view. Save defaults to My views. Editing filters creates an unsaved working adjustment, never a background change to the definition. Show **Modified**, **Reset to saved**, and **Save as my view**; authorized maintainers additionally get **Update shared view**. Rename changes metadata only. Reset uses the currently qualified saved definition and does not erase a message draft.

Opening a selected saved view applies its complete explicit predicate; leftover URL filters cannot silently combine with it. An intentionally retained context constraint must be visible and labelled. CRM Party-scoped navigation remains within the D9 record context until a deliberate **Open in Support Hub** action leaves it; a view cannot silently broaden that reverse list to the tenant. Raw search text and copied URLs must follow the platform's sensitive-query/log/referrer policy; the saved-view deep link itself can use an opaque stable ID.

### L05 — Shared curation without publication machinery

Shared views are tenant-owned definitions with qualified maintainers and an explicit existing audience. D20 activates a qualified Shared audience binding for the Support subject in the existing capability; it does not globally activate P9's reserved team/everyone CRM scope or change CRM permissions. A maintainer may create a shared view directly or deliberately create a shared copy from currently allowed personal/shared criteria. Never flip a personal object's identity into shared scope behind existing links. Review name, optional description, search text and referenced values before broadening visibility; authored metadata itself may be sensitive. No automatic conversation subject/name population, sample result titles or full before/after query payloads in ordinary audit/logs. A generic second-person approval or Email Studio publication flow is unnecessary.

Sharing does not create a recipient audience, subscription, record permission or guaranteed identical results. New shared copies get a new identity and independent ownership; editing either later does not update its source copy. No personal owner transfer to a colleague on offboarding, no automatic publication and no inheritance by a later account with the same email.

### L06 — Invalid, unavailable and empty are different

When the stored predicate has a deleted/unresolvable reference, unknown operator/version or missing source qualification, return a safe **View needs attention** state without executing a weakened query. A maintainer can review/remove/replace the target; an ordinary reader can use a standard view. If the current viewer lacks required definition/field/reference authority, show only the permitted unavailable state, with no hidden names/counts or assertion that a target does not exist. An authorization-service outage is temporary unavailable and must not delete the definition or permanently remove intent.

A retained inactive worker/archived inbox is not automatically a broken ID: where the owner allows that historical/current reference, preserve it and label its actual state. A valid predicate with no currently permitted matches returns **No matching conversations**. It does not claim no matching records exist globally or that the team has finished all work. Never silently substitute Any, the creator, the first accessible inbox or a similarly named reference.

### L07 — Safe concurrent changes and uncertain success

Create/update/rename/share-copy/archive/restore use durable identities and expected definition revision where an existing object is affected. Version check, accepted changes and required audit/control state commit atomically. Exact same-input retry returns the same result; changed input under the same identity conflicts. A lost response is reconciled by identity before creating another view. Duplicate names are not duplicate operations; stable identity, scope and audience disambiguate them.

Concurrent edits return a conflict with current authorized state while preserving unsaved inputs. Do not automatically merge semantic predicates or let a late old response replace newer state. Rename must not overwrite a concurrent criteria change. If a reader has an old definition open when its maintainer updates it, show **This view changed** and an explicit **Use updated view**, preserve permitted working context, and clearly label temporary old criteria. Current authority changes still apply immediately; an old revision is no access bypass.

No long-lived database transaction, view-specific queue or workflow saga is needed for a small definition mutation. An expected revision/conditional update is enough where the invariant is one definition. RFC9110 documents conditional requests for preventing lost updates; PostgreSQL notes that separate Read Committed SELECTs can see different committed states. Adopt their concurrency principle without mandating an HTTP header or global Serializable mode. [RFC9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match), [PostgreSQL17 transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html).

### L08 — Personal shortcuts and offboarding

Pin/unpin express desired personal state, not blind toggles; concurrent changes cannot resurrect a newer unpin. Save preferences server-side under the qualified user/tenant identity so they survive ordinary device changes. Sidebar order is a personal preference with safe conditional updates; a list position is not shared identity. For Support only, pin order controls shortcuts and does not silently choose the startup view or change the D3/D14/D15 built-in defaults. P9's first-pinned CRM kind-route default remains untouched. No new Support start-view setting is needed. A maintainer changing a definition does not pin it for everyone. Pins to unavailable definitions are suppressed without leaking private metadata; safe unpin remains possible. A temporary outage is not a reason to destroy a pin.

Shared definitions survive the departure of their creator and remain maintainable by currently qualified tenant stewardship. Personal definitions stop being available when their identity/tenant membership is retired and follow the qualified preference-data retention policy; do not silently hand them to a manager. Team audience membership remains dynamic under its real owner; copying a list of current people is not its authority. No recurring manual SQL cleanup is an acceptable operating path.

### L09 — Archive and correction without deleting conversations

Recommend one reversible **Archive view** lifecycle for retained definitions, with personal **Remove shortcut** separately meaning unpin. Archive removes the definition from normal selection and prevents new application; authorized maintainers can find it in Manage views → Archived and restore after current validation. It never archives conversations or alters current Support work. The currently open permitted filter draft can remain labelled as temporary after archival; current permission loss clears protected context.

Restore is a new authorized conditional action on the current archived revision, not rollback of later edits, old permissions or old object IDs. A stale archive/restore cannot reverse a newer operation. Retention/privacy deletion of view metadata is owner-governed and terminal; no promise of restore after disposal. No automatic inactivity archive/delete, especially for seasonal work; no new arbitrary recycle-bin horizon is needed for this product decision. If the root chooses Delete for personal views, make its actual recoverability clear and use the same bounded conditional correction principle rather than introducing two subtly different storage systems.

### L10 — Current continuing work and source truth

Evaluate current scope, assignment and D3 status on the canonical continuing work item; evaluate original-scoped predicates through their actual owners. Merge results deduplicate before count/page; Undo recomputes current topology and does not clone saved definitions or follows. Related conversation links do not cause transitive membership. Inbox moves alter explicit current responsible-inbox membership; they do not rewrite the definition or D14's original target policy lineage.

Following uses exactly D15's authorized original follow scope and current viewer; initial Following defaults to All statuses, with explicit changes thereafter. Latest followed update is a distinct supported sort, not generic root updated_at. Unrelated newly merged content cannot bump it. Overdue replies and Timing needs confirmation examine all permitted underlying D14 periods, may overlap, and count each continuing conversation once. Neither browser time nor status-only filtering may erase source-owned due facts. Source expiry removes content-derived matches/counts even when the retained work record still qualifies by permitted status metadata. It does not remove an overdue obligation or improve a historical success rate.

### L11 — Deterministic pages and honest changing results

For each result/count response, use the same authorized predicate, definition revision, viewer binding, filter grammar and server-sampled time. Group/dedupe by current continuing conversation before pagination. Deterministic sorting includes a stable ID tie-breaker and explicit null handling. Query cursors bind the exact effective predicate/sort, viewer/tenant and applicable authority scope; reuse under changed filters or authority requalifies/restarts safely. PostgreSQL explicitly requires a uniquely constrained ORDER BY for predictable LIMIT results and notes that large OFFSET work still has server cost. [PostgreSQL17 LIMIT/OFFSET](https://www.postgresql.org/docs/17/queries-limit.html).

Current views are not immutable historical cohorts: do not promise a point-in-time snapshot across an arbitrarily long paging session while source records change. Keep the selected detail/draft and focus anchored by stable identity, reconcile removal/permission changes, show pending new results without reordering beneath a pointer, and offer Refresh/Use updated results. If a cursor becomes invalid because its query or authorization changed, restart from a safe anchor rather than silently mixing incompatible pages. An older response cannot replace a newer definition or source/privacy state. Source restriction is enforced on every response, including when using a cached candidate population.

Count failure is **Count unavailable**, result failure is **Could not load**, stale data carries its actual As of state, and a successful zero is **No matching conversations**. Loading must not flash success-zero. Counts for the active definition reflect exactly that definition; unrelated standard-queue counts must be explicitly separate. Do not fetch every view's count on every keystroke or minute tick. Debounce ordinary search, bound pages and accepted query complexity, invalidate only affected authorized scope, and qualify query plans against actual large/skewed tenants before Live use.

### L12 — CRM, Email Studio and bulk boundaries

The shared capability stores the Support subject's query configuration, never CRM Party facts, message recipients, linked record snapshots or copies of Support history. D9 owns CRM reverse-list membership/provenance. An authorized CRM context jump preserves the underlying view identity/filter/scroll and private draft on return without changing either domain's permission. No ambient CRM Party context is frozen into a Support saved view; entry to global Support is deliberate. A link, read, pin, save, shared update or archive emits no CRM communication, last-contact or donor-interaction event.

Email Studio owns no part of saved-view selection, configuration or refresh. It remains involved only when the person deliberately enters the already-ratified composer/preparation path; P6 and Resend only dispatch under their real admitted effect. Saved views are never a send audience or scheduled batch. Existing row actions keep their exact current-source commands. Changing a view clears bulk selection from the previous result scope; it must not silently act on hidden old selected rows. If a previously selected detail no longer matches it may remain open with an explicit out-of-view indication, as D3 permits. Do not introduce select-all-matching, bulk send, automatic Follow or a saved action macro merely because a saved result set exists.

### L13 — Migration and scope-compatible rollback

Qualify the existing named-views capability's typed/versioned definitions, correct ownership and allowed metadata gates for the Support subject before promising My/Shared privacy. Converge local Support rows into that single authority; do not synchronize two permanent stores. Inventory existing personal-null-owner and multi-label ambiguous rows; do not guess owner from a current email, promote to shared, default missing criteria to Any or discard records. Put ambiguous legacy definitions in authorized maintenance review while keeping ordinary required queues usable. Preserve stable identities where supported, otherwise explicit idempotent old-to-new mappings and safe links; retain correction provenance. New readers reject old unknown semantics safely; old writers must not overwrite newer schema with a narrowed JSON object or null owner.

Activation requires current API/direct-database/alternate entry-point parity, source predicate consistency and source-restriction/cache proof. A kill switch can disable new custom definition use/maintenance while required standard queues, source correction and existing messages remain available. Rollback must not restore broad personal-list access, stale source payload or old unsafe writers. No provider migration is required.

### PT1 — Default-delta drift can change meaning without changing a view revision

**Material concern: Yes. Severity High; likelihood plausible.** P9 B11 stores deltas from defaults. Without a pinned baseline, changing the subject's default status, inbox or sort can change an existing view while its saved revision appears unchanged. Users can miss work and a maintainer cannot explain the change.

**Required correction to R02/R05/R27:** “A saved delta binds an immutable/versioned subject-default baseline and schema identity, or an equivalent qualified representation preserving its exact effective meaning. Future system-default edits do not change existing saved criteria under the same revision. Missing/incompatible baseline makes the definition unavailable for repair; a semantics-changing migration requires an explicitly reviewed successor revision. A proved semantics-preserving schema translation may retain meaning without asking each user to reconstruct it.”

**Proof:** Save a view omitting the default status/inbox/sort in its delta, change platform defaults, then reload on another device. The saved view preserves its exact meaning. A genuinely new view may use the new displayed defaults. Old-default disposal cannot leave executable match-all fallback.

### PT2 — Archive/restore requires a pin applicability fence

**Material concern: Yes. Severity Medium; likelihood plausible under retries.** R16 says archive removes active pins and restore does not repin everyone, but this leaves the creator and delayed Save→auto-Pin ambiguous.

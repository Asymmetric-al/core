## F01 — Unknown save must not trap the person in the composer

**Material concern: Yes. Severity: Medium. Likelihood: Plausible during a slow or unavailable save/result service.** R13 explicitly offers Leave only on a _known_ failure; for an unresolved save it says preserve work while checking. R12 and P17 correctly require recovery handles through navigation, but the actual leave behavior during uncertainty is not stated. An implementation could therefore block navigation indefinitely until an operation can be reconciled. That would turn the safety mechanism into a product trap during an outage. Continuing to poll cannot prove whether an inaccessible database accepted the earlier save.

This **amends recovery wording without changing A**. Leaving the UI and proving that a durable write never happened are different actions. Existing current-authorized operation recovery can preserve the original save identity while the person explicitly abandons local unacknowledged changes. No new save/send, rollback claim, content archive or extra navigation product is required.

**Exact language for R13 and the corresponding UX failure journey:**

> After the normal quiet navigation save/check, a definite failure or prolonged unknown result exposes Stay/Retry or an explicit Leave choice with the correct consequence. For an unknown save, explain that the earlier save may still finish and the newest unacknowledged changes may be lost. A deliberate Leave preserves the minimal scoped original-operation recovery handle and never marks work Saved, proves nonacceptance, cancels a possibly accepted write, or creates another operation. Returning reconciles that original result before ordinary resubmission; current authorization still governs any restored content. Waiting for definitive save resolution is not a prerequisite for informed navigation away.

The existing leave-consequence control can express this; do not add a second modal or a separate recovery workflow. A person can choose Stay to protect unconfirmed local changes. The feature still makes no crash/OS-termination guarantee. When source permission is actually revoked, the existing mandatory clearing rule overrides this ordinary leave choice.

**Proof addition to P16/P17:** hold the save/result service unavailable after possible commit; exercise explicit Leave and return. Navigation is possible with truthful uncertainty; the body is not falsely claimed saved, the original operation handle is retained, a later ACK cannot populate another draft, and no replacement create/send or rolled-back-write claim occurs. Include the case where newer local text was never submitted.

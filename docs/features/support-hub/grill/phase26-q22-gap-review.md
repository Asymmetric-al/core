## Recommended next question

**What should Support conversation search look through?**

| Option                                                                   | Concrete coverage                                                                                                                                                                                    | Benefit                                                                                               | Tradeoff                                                                                                                                                  |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Single recommendation: A.** It addresses the immediate retrieval gap exposed by the current code: words in an actual email or internal note do not currently participate in its text search. Staff should not have to remember whether an ordinary phrase was in the subject or body to find their work. Filename lookup supports known attached artifacts while avoiding a new file-parsing requirement unless its extra value is established.

Illustrative fixture, not a claim about ministry prevalence: a staff member remembers the phrase **corrected mailing address** from a conversation whose subject was **A quick question**. A can find a permitted email or published note containing that phrase. B needs the subject/sender or another filter to narrow candidates. If that phrase appeared only inside an attached document, C could find it only when the document/type/text extraction are qualified; A could still find a remembered permitted filename.

**Strongest challenge to A:** if staff routinely receive the identifying details only in attached documents, filename search leaves an important gap and C may provide the best experience. This must be tested with actual representative attachment-heavy tasks. No Asym workload sample, supported-file readiness proof or extraction-reliability data was found that establishes this need or makes C a small free addition. B remains a serious low-volume/minimal-index alternative; it should not be depicted as broken simply because A is recommended.

A/B/C are alternative product scope decisions, not three tenant configuration modes. Whether a later UI offers message-only/note-only narrowing is a selected-answer interaction detail; it is not the main founder fork here. C does not include OCR, image recognition, archives, arbitrary file formats, AI/semantic search or platform-wide CRM search by implication.

## Why this is genuinely unresolved and timely

- D20-R06 expressly says saved criteria do not introduce full-text, attachment, arbitrary CRM or AI search. D20 does settle complete queries, current permissions, stable predicates, saved query identity and visible scope. Q22 adds a source-coverage decision to that foundation.
- D21 settles how catalog terms and label membership support retrieval. It does not make labels a complete substitute for the words in a message, and optional classification means staff cannot rely on every conversation having a useful label.
- D16 requires stale indexed content to contribute no hit, count, facet, sort or match reason after current source removal. That is a mandatory correctness contract for any chosen search scope, not a prior decision to index every source.
- D17 governs which content remains available. Broader search does not extend its lifetime or turn archived/held/expired material into an ordinary searchable archive.
- The roadmap's core Support purpose is finding and handling inbound work without loss. Domain-local conversation retrieval fits that purpose; a generic global search or document platform does not follow from it.

## C is a valid stronger alternative, with real boundaries

C does not conflict with Phase29 or Phase40 merely because those phases own shared file mechanics and generalized search. It can be framed as a bounded Support consumer of a qualified shared byte/extraction/access capability. However, the current roadmap is not proof that such extraction exists, and Phase29 must not be credited with unsupported search behavior.

If C were selected, its review would need to settle a narrow supported file set, source-qualified extraction, immutable source-byte/revision identity, file and parent conversation permission checks, bounded parser workload, extraction readiness/error/unsupported outcomes, truthful search completeness, and deletion/retention/restore parity. It should not bring the entire Phase29 feature set forward, index unrelated CRM documents, call external AI, perform OCR or parse every uploaded format. Existing independent document owners keep their own meaning and access. Search cannot copy a privately linked Finance receipt into a Support-owned permanent body index.

Those are concrete consequences of C, not alarmist reasons to rule it out. If attachment-contained identifiers are common in verified work, they may justify the extra implementation and operational obligations.

Attachment-content coverage is limited to stated formats and email attachments; other channel-integration files are not searchable. This establishes C as a real product pattern and illustrates why coverage must be explicit. Do not copy its format list, prefix/stemming limitations, proprietary syntax or account-wide scope as Asym requirements. [Official source](https://help.front.com/en/articles/2131).

**Intercom, Inbox search and filter; current page checked 12 September 2026.** The page distinguishes all-inbox search from search inside a view, records English-optimized keyword behavior and explicitly points React Inbox users to a different search article. It reinforces visible scope and version-specific qualification. It does not by itself establish internal-note/file indexing for every Intercom edition or surface. Broad matching, implicit punctuation handling and current bulk-action features must not silently replace Core's existing predicate/selection contracts. [Official source](https://www.intercom.com/help/en/articles/6516006-inbox-search-and-filter).

These are documented mechanisms, not comparative performance experiments or proof of a universal optimum. No vendor's implementation details are inferred from its interface.

## Non-negotiable boundaries for every option

1. Search current permitted source material only. Internal-note matches remain staff-only and visibly identified as such; a match is not evidence that the requester saw that text.
2. Preserve D20's explicit inbox/view/CRM-record scope and return context. Leaving a CRM record for broader Support search is deliberate; do not silently expand to all linked records or all inboxes.
3. Expired/redacted/held/private/unavailable material cannot generate indirect matches or counts. Current source and indexed revision must qualify before membership/ranking/snippet/count. Do not advertise inaccessible-match counts.
4. Shared indexes are derived read models. They do not own conversation truth, recipients, Party identity, label assignments, business outcomes, retention or permissions.
5. Draft text, Email Studio library sources, raw transport/MIME evidence, provider logs and unrelated CRM/care/financial documents are not ordinary admitted conversation text. A source's existence in storage does not make it searchable.
6. D10 merged originals retain source identity; D12 related conversations do not combine automatically. Search results and match locations need source-qualified attribution; merge/Undo cannot resurrect hidden content or double-count a continuing conversation.
7. Filename lookup and file-content lookup are distinct. Finding an allowed filename does not prove that file bytes are readable, text was extracted, or a file-only phrase was searched.
8. Saving a content search uses D20's disclosed query settings and source-coverage/version semantics. Do not reinterpret an old details-only saved query as body/attachment search without the qualified migration and visible meaning change.
9. Search never sends, follows, bulk-selects all matches, creates CRM interactions, publishes Email Studio wording or dispatches Resend. Actual navigation/actions remain separately authorized.

## Decision-tree discipline

The main question should decide **coverage**, not search engine, tokenizer, date operators, ranking weights, exact snippets, minimum query length, quotas, language normalization, page size and result layout in one bundle. These details need source qualification and a complete adversarial pass after the founder chooses A/B/C. Do not silently adopt English-only matching or arbitrary parser limits while asking an apparently simple scope question.

C is technically and architecturally possible within a bounded shared seam; it is not currently proven or automatically required.

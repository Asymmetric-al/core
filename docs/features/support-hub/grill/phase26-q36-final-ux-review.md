## Initial corrections

### 1. Embedded signature/address text versus implicit copying

**Severity: Medium; likelihood: plausible interpretation error.** Boundary 4 says that quotation cannot smuggle old attachments, signatures or raw headers into a send. Its intention is sound, but it could be read as requiring automatic removal of every historical signature/address block from B's selected full source body. The same question correctly warns that this body can contain nested earlier context and selects no clipping/extraction algorithm. The brief should distinguish source content already inside the reviewed quote from reconstructed header/signature blocks or implicit attachment acquisition.

Suggested exact clarification:

> Quote inclusion does not implicitly acquire or reattach source files, derive current recipients from historical addresses, or append reconstructed header/signature blocks outside the reviewed quotation. Any already-embedded permitted signature or address text is part of the complete source/audience review. No silent stripping or extraction algorithm is selected by this question.

This leaves every source, recipient and privacy restriction intact. It neither permits an unreviewed address disclosure nor requires new parsing before the founder chooses the policy.

### 2. Identify the reported-friction source precisely

**Severity: Low; likelihood: direct attribution ambiguity.** The forum source in the supporting research concerns **Fin-generated replies and follow-ups**, not generic human email replies. The actual brief calls it frustration when email notifications lack context. Preserve the limited weight already stated, but name the actual AI-reply context so it cannot be misread as measured evidence about the human default being selected.

Suggested phrase:

> A self-selected Intercom forum report describes missing context in Fin-generated replies/follow-ups; it is reported friction, not measured ministry preference or proof about Core's human email-first workflow.

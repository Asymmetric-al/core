## Consequential boundaries independently challenged

**P23 optional-leaf containment is explicit, not a partial-generation workaround.** R08 pins the selection and contract/renderer with a complete released Page. Current source eligibility may only narrow that qualified optional leaf. It cannot replace a guide, mutate saved selection, reroute Contact or assemble a favorable mixture of generations. The required contact closure is separate. If the Page/base/form authority itself is unsafe, any fallback route needs its own qualification. This is the exact narrow extension required because P23's initial Article dynamic-source contract does not automatically qualify Page refs.

**Public and app releases remain genuinely separate.** One Requester help maintenance entry is a navigation/coordination surface over the actual owners, not a new public head, content directory or distributed transaction. App context does not personalize CMS public output. The standard profile's required Support Primary Outcome does not remove P23's independent email-only capability from other forms, nor require Asym to fabricate Support setup before other already-qualified public contact methods can be used.

**Support responsibility at acceptance is stronger than a generic form row.** R13 requires a source-owned durable Support work/acceptance receipt and complete dispatch obligations before Received. The implementation may materialize the ordinary conversation asynchronously only after that responsibility exists and is recoverable. An executor event, raw CMS envelope or planned future call to Support is not enough. Trusted form admission time remains the source clock through delayed materialization; it cannot become the worker's current time.

The following explicit P16 fixture was recommended to the root as a precision addition to that already-required contract: crash after durable Support acceptance but before ordinary conversation materialization; prove that accepted pending intake is discoverable through the qualified Support/recovery path and materializes the same occurrence/source once, with original admission clocks, even after route configuration changes. This does not require another queue/table or change the current R13 architecture.

**Receipt recovery does not rerun new-submission routing.** The data table explicitly distinguishes a new request under current schema/route from recovery of an already accepted intent. A later route/version change cannot make a committed request appear unreceived or provide a new idempotency namespace. Receipt access still needs its exact occurrence capability/current app authority and reveals no transcript or CRM record. This is consistent with R15 and P17/P18/P35, and avoids a public ticket-history surface.

**Native form origin is propagated instead of disguised.** The first requester text is a form message. D14 is explicitly extended to trusted form admission; optional browser/automatic receipts earn no human response credit. D28 can consider completed form-origin work only after actual qualified human public email correspondence and all its established source, audience, sampling and contact guards. Those are new source qualifications to implement, not claims that email-only current defaults already work.

**The form remains small.** Three optional links, two required fields, one optional name, ordinary published email/phone and normal owner-controlled recovery are proportionate to A. No library search, file uploader, CRM identity wizard, private knowledge portal, new sender, cross-owner rules builder, generic submissions inbox or device-offline queue is introduced. Fixed bounds are labelled product judgments; the workload is a prospective qualification fixture, not measured capacity.

## Corrections verified during this final pass

1. **Context-only permission loss no longer destroys all visitor text.** Actual R11/P14 now clear the full draft on successful receipt, deliberate logout or account/tenant change. On context-only permission/revision loss, unqualified references and source-derived prefill are removed while only still-permitted visitor-authored text survives for requalification or deliberate reviewed contact without account details. R12 and the UX's explicit context-free path agree. The form never silently submits as a different principal.
2. **The web acknowledgment does not create a permanent generated-message archive.** Actual R17/P27 and the data/Email Studio custody text explicitly adopt D13-R17's Off-only Recent sent copy posture. The ordinary history is a body-free Automatic confirmation event with actual state; Template used is a synthetic publication preview, not the sent body. Restricted prepared execution bytes are not a staff content-view API.
3. **Human-reply precedence extends beyond a race won before acknowledgment submission.** Actual R18/P29 and the Email Studio sequence preserve D13-R15's full rule. A qualifying human reply for the same current request and exact recipient also terminates additional acknowledgment provider-call/decrypt authority after possible submission, including otherwise permitted indeterminate same-key follow-ups. In-flight outcomes remain reconcilable; a later failed human send does not revive the automatic receipt.

These were independently checked in the actual updated text. They are not presented as newly executed runtime behavior.

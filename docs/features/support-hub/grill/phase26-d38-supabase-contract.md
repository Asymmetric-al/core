## Current technical research and corrections to skill shorthand

The Supabase documentation connector was used and the current public documentation/changelog was checked. The markdown changelog required ordinary HTTP retrieval because web open rejected its content type. Relevant changes were inspected: the 14 July 2026 Realtime schema lockdown permits policies on `realtime.messages` but forbids creating application-owned draft/queue tables in that schema; no new Realtime service is needed. The self-hosted PG15→17 default-image change explicitly excludes hosted Supabase and CLI local development, so it is not an instruction to upgrade Core's database. [Realtime change](https://supabase.com/changelog/realtime-schema-locked-down-against-modification), [self-hosted version change](https://supabase.com/changelog/46080-self-hosted-supabase-upgrading-from-pg-15-to-17-breaking-change)

The following corrections are applied in this design; no skill file was edited:

- PostgreSQL UPDATE/ALL policies with an omitted `WITH CHECK` inherit `USING`. Omission alone does not prove a row-reassignment vulnerability. Require the intended old-row/new-row behavior and column immutability, then test the effective policy union. [PostgreSQL 17 CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html)
- `SECURITY DEFINER` uses its owner's privileges. It is not intrinsically an unconditional RLS bypass: superusers/BYPASSRLS always bypass, table owners normally bypass unless subject to FORCE RLS, and a different limited owner has its actual privileges. Newly created functions ordinarily grant PUBLIC EXECUTE, but reachability also depends on schema/function privileges and API exposure. Set precise grants and a trusted search path in the same migration transaction. [PostgreSQL 17 functions](https://www.postgresql.org/docs/17/sql-createfunction.html), [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)
- A normal view uses its owner's underlying privileges/policies; `security_invoker=true` makes supported-version views use the invoker's underlying authority. Privilege closure still requires actual grants, roles and dependent functions. RLS does not replace table/column/RPC grants. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)
- An UPDATE that reads columns in its WHERE/RETURNING/expressions ordinarily also needs corresponding SELECT access; avoid claiming every possible syntactic UPDATE universally has identical SELECT needs. Core's conditional update commands do read their revision/source rows and must have this access qualified. `auth.role()` or TO authenticated alone is not business authorization; anonymous Auth users can have the authenticated database role. User-editable metadata is never a trust root, and app metadata claims can be stale.
- A sequential scan is not inherently exponential in table size, and reference examples' 100–1000× speedups are not Core performance guarantees. Inspect actual plans and workload. FK referencing indexes are not automatically supplied by declaring the FK; choose indexes for actual joins, guards and cleanup rather than installing every speculative index. [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [Supabase RLS performance](https://supabase.com/docs/guides/database/postgres/row-level-security-performance)

## Exact proposed Supabase/data contract

### C01 — One private owner, distinct immutable purposes

“Extend the existing D37 private Support draft aggregate to admit two closed purposes, external Reply and new Internal note. Purpose is fixed at creation. Enforce at most one active draft per trusted tenant, real owner, immutable original working slot and purpose. A person can retain a Reply and a Note for the same original at once; each has its own stable ID, revision and operation generation. Switching tabs/mode resumes its existing draft without converting, overwriting or publishing the other purpose.”

This is a bounded purpose discriminator, not a generic workflow platform. Physical table names and enum spellings can follow the qualified implementation. Reuse storage/commands/receipts/metadata queries and the authoring coordinator where their behavior is actually identical; purpose-specific schema and admission must remain explicit. A posted-note correction under D35 is a different operation against a published source, never a third My drafts purpose inferred by this decision.

### C02 — Actual keys and source affinity

“Retain actual UUID tenant/auth/profile/membership relationships and actual TEXT Support source/message/agent IDs. A draft's immutable origin is its private slot. A new general note's intended publication original follows D10-R14's then-current continuing original or an already-qualified explicit source-specific action. Capture that intended destination and the relevant topology/source revision for visible current review. Merge/Undo/movement cannot silently reparent the private draft, choose a new destination, merge slots or post under stale source authority.”

Origin, current workspace root and publication source may need separate references; do not overload one conversation_id. On a material change, preserve permitted writing, show the current proposed destination and require the established source/context review before Post. No new arbitrary move/copy-note workflow is selected. Revalidate every required origin/publication/dependency floor, and preserve the resulting actual source on the published note and its D35 revision history.

### C03 — Structurally enforce valid data

“The draft requires non-null tenant, trusted owner/profile, origin, purpose, schema/profile version, stable generation, positive current revision and authoritative UTC create/meaningful-save times. Same-tenant composite PK/FK or equivalent uniquely constrained endpoints bind draft, source, file occurrences, dependencies, operation receipts and its eventual published-note result. Partial uniqueness covers active slots by purpose. Terminal generations cannot be revived through generic UPDATE, DELETE or old-create replay.”

For notes, external email target/audience/headers, email signature/publication and delivery intent fields are structurally absent or forbidden, rather than silently accepted then ignored. Legitimate note mentions and source references have their own qualified typed structures. A valid incomplete Note may save before it is postable; unsupported nodes, arbitrary raw HTML or forged provenance are not mere incompleteness. Closed JSON/profile validation precedes parsing. Known size/depth/node/asset limits are applied before costly normalization; final actual numeric limits come from the shared qualified profile, not a new guessed allowance.

Use CHECK/NOT NULL/unique/FK constraints for row-local invariants and command/transaction checks for current membership/source/retention/cross-row rules. A CHECK that queries mutable other rows is not a sound substitute for authoritative concurrency control. Do not cascade draft cleanup into conversation, CRM, published note, revision or independently owned files. This feature adds no money fields or numeric money precision change.

### C04 — Trusted current actor and complete private read scope

“Every list/open/create/save/discard/post/recovery operation derives current authenticated principal, real durable owner/profile, selected tenant and active permitted membership from Core's shared server context. The source owner verifies relevant current read/write/post capabilities and purpose. Ignore or reject caller owner/author/tenant/role/approval/publication/clock fields. Email similarity, current assignee, conversation membership and ordinary administrative role never grant another person's draft.”

Do not accidentally enforce `profiles.tenant_id = selectedTenant` if legitimate current multi-tenant membership is the actual platform mapping. Do not assume profile ID equals auth user ID. API context remains necessary on service paths; a pooled caller-set custom GUC, browser `current_setting`, user_metadata, stale claims alone or in-memory tenant string is not independently trusted identity. Current source revocation/retention checks remain effective at every authoritative operation, not only initial route entry.

Read, save, discard and Post have operation-specific capabilities. Losing Post permission alone does not remove still-lawful owner inspection/custody: allow the currently permitted saved representation to be read with Add note unavailable. Conversely, private ownership/read access cannot grant composition, update or publication authority. A general source/privacy loss still removes every newly forbidden representation, including stale cache/Undo material.

### C05 — Grants, RLS, views, functions and every access route

“Canonical multi-table draft/save/post work stays in packages/api commands behind thin authenticated routes. No raw anon/authenticated DML may change private draft bodies or immutable control fields outside these commands. Use the qualified D37 private relation and approved browser metadata read boundary; do not add the Note purpose to broad published-message policies.”

Enable RLS on exposed draft/dependency/receipt relations and preserve Core's qualified FORCE-RLS/tenant-guard posture where applicable, while recognizing bypass-role limits. Grant only required read surfaces and execute operations; ordinary clients receive no blanket private-body CRUD, TRUNCATE, role-changing or schema-changing authority. Audit effective permissive OR/restrictive AND policies, inherited grants and default privileges, SELECT/USING/new-row WITH CHECK behavior, column update permissions, view settings, API/GraphQL/exposure, SECURITY DEFINER owner/search_path/EXECUTE, and every service worker path. Restrict helper/schema exposure without assuming non-exposed means unreachable to a granted SQL role. Grant changes and function creation occur atomically during the later migration.

With service-role command execution, validate the real actor and current source explicitly before privileged access and again at the effect boundary as needed. Never expose service keys. Middleware or PostgREST-specific pre-request checks cannot establish Storage/Realtime/other-consumer parity; each actual route must enforce the same permission. A read-only metadata view is not safe if a dependent helper or cached projection leaks body/identity. Constraint errors and conflict responses must not disclose another person's slot/note/source existence. [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api)

### C06 — Atomic complete note-draft saves

“Save canonical Note document, admitted mention/source references, file-selection state and the narrow actually allowed note context as one versioned effect. Saving never calls addPrivateNote, adds a timeline row, notifies a mention/follower, changes work state, updates last contact/native content clocks, prepares mail or executes a shortcut. A saved attachment manifest does not prove local File bytes are uploaded.”

D37 whole-bundle no-op/ACK rules apply per purpose. One conditional save advances only its matching draft version, with latest meaningful-save time only on a semantic change; no-op still has an immutable operation outcome. An earlier ACK cannot mark later typing Saved or touch the other mode's state. No staged Reply actions or generic arbitrary work-plan blob is admitted into the Note bundle.

**D24-R01/R10 resolution:** there is no internal-note-and-work mode in this scope. The Note schema excludes staged Reply work plans, external audience, signature and email-send state; switching modes leaves the separate Reply plan intact and carries none of it into the Note. Purpose-qualified note wording, ordinary files and typed mentions remain the existing allowed note capabilities, not a generic plan consumer.

### C07 — Post is one atomic local admission

“Post note revalidates the exact reviewed Note draft revision, current actor, final original source, canonical profile, attachments, mentions and source privacy/retention. One authoritative database transaction admits one native human internal note, its first D35-compatible canonical revision/current head and trusted original author/publication attribution; consumes the exact private draft generation; records the immutable post-operation result; applies the source owner's required native-content/aggregate facts; and commits the required identifier-only occurrence/outbox obligations. Any rejection before admission publishes nothing and preserves the permitted draft.”

Posting is not an external email. The note is structurally internal and may become visible only to currently authorized staff, including through CRM Support context. It never gains external recipients/headers/transport identity merely because legacy code uses delivered flags. The returned posted result means the local note was admitted; it does not claim staff notices were delivered or business actions finished. If optional follower/direct-mention consumers are unavailable, durable source obligations permit recovery without reposting the note or blocking on an external provider. Existing owners decide which actual consumers apply.

Proposed postability uses meaningful qualified canonical body **or at least one ready, clean, currently permitted selected attachment**. Attachment-only notes need no dummy text. Incomplete drafts, including pending-file-only candidates, may save, but a still-selected pending/failed/unsafe file cannot be silently dropped at Post: finish it or deliberately remove it. Typed mentions that form meaningful authored content remain subject to the same canonical note validation; saving the mention does not notify anyone. This corrects the current UI's attachment-aware dirty state versus actual Note request's omitted files, without adding an upload surface or relaxing file safety.

Native-note publication is one D17-R05 admission event, not every autosave or edit. Process elapsed source expiry/frontier before admitting new content under current lawful purpose; neither worker lag nor a new note rehydrates old expired content. Use row locks/revision guards or equivalent qualified serialization over shared source/privacy/topology facts, not an app-side check followed by an unguarded insert. Transactionally increment or derive counters instead of current read-plus-one arithmetic.

### C08 — First publication versus D35 history

“The published note keeps one stable source-owned note ID and trustworthy native-human author and first-admission time. Its first canonical revision becomes the D35 Original only with proven original provenance. Private draft checkpoints are not posted revisions or audit copies; posting cannot expose all earlier unsent wording to colleagues. Later Edit note follows D35's explicit author-owned correction command, not autosaving to the private new-note slot.”

Unknown old HTML/JSON/source/author lineage is migration/repair material, not an invented Original or authorship recovered from email text. The posted note and private draft may have different retention/discovery grants. Consume the private aggregate without deleting independently admitted published evidence. Do not move caller-supplied raw HTML directly into the first revision or route system/macro-generated notes through the native-human publication provenance simply because they display as notes today.

### C09 — Durable idempotency, concurrency and operation access

“Bind create/save/discard/post operation identity to tenant, real owner, purpose, original slot, draft generation, expected revision, current authority/source fences and exact semantic command. Same key with changed purpose/payload conflicts. Current authorized replay returns the original minimal outcome; it never repeats publication, initial revision, activity or downstream admission. Receipt/material cache expiration does not release an identity while an old request or restored client could still cause that effect.”

Race two first saves, two tabs, save versus Post, discard versus Post, lost acknowledgments and old-create replay. Active-slot uniqueness and exact conditional transitions allow one winner without cross-purpose overwrites. Confirmed Post consumes only the matching Note draft; its sibling Reply remains. Unknown Post is the original local operation under recovery, not a new editable Post again affordance. An absent lookup is not definite nonacceptance until late admission is fenced; canceled HTTP is not rollback. Keep body-free original handles through supported navigation, with current read/disclosure checks before returning even result IDs. Deliberate fresh note after completion uses a new generation, not recycled receipt identity. No user-facing draft history or per-keystroke event store is required.

### C10 — Source-derived content, privacy and expiry

“D16/D17 and actual owner deadlines constrain canonical draft bodies, citations/wording/mentions, attachment occurrences, editor Undo/local buffers, caches, exports, search and later published/notification derivatives. Draft save/read/restore does not extend native source lifetime. Preserve independently safe authored text only where its own lawful custody and qualified separation are established. Current stops apply even before cleanup/invalidation workers finish.”

Unpublished private drafts and eventual published-note revisions remain separately qualified custody; no guessed 24-hour/30-day/forever policy is introduced. Actual draft/body/file/control horizons and restore barriers are mandatory activation evidence. Offboarding/reinvitation/email reuse does not hand another person the departed worker's draft. Authorized colleagues may continue the real source obligation in their own writing; exceptional records/privacy custody remains separately governed, not a general manager “see drafts” override. Backups restore source/terminal fences before replay access, and preserve truthful independently retained published/communication facts.

### C11 — Storage, attachments and derived assets

“Reuse the existing qualified private attachment/reference owner. Bind selected files and upload occurrences to tenant, real owner, purpose, draft generation and current source, then to the admitted published note only during qualified Post. A filename, arbitrary URL, bucket name/path prefix or storage owner_id alone does not establish current source access. Reject unsupported or unsafe files; never reacquire assets from pasted external URLs during autosave or resume.”

Qualify bucket privacy, storage.objects read/list/insert/update/delete policies, object identity, upload completion, preview conversion, download authorization and service-role routes. The general Storage examples are starting points, not sufficient private-draft policies. Upsert requires additional SELECT/UPDATE and can overwrite files; use immutable upload occurrences unless a legitimate replacement command independently qualifies that change. A private bucket supports authorized downloads or time-limited signed links, while public buckets bypass retrieval controls. A preissued signed URL is a time-bounded bearer capability, not proof of current membership on each use: satisfy D16's actual revocation barrier with the qualified guarded delivery route where needed, and test the issued-link case rather than promising instantaneous revocation from a policy change. [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [bucket models](https://supabase.com/docs/guides/storage/buckets/fundamentals)

Post cannot silently omit attachments as current Note code does; pending/failed/ready state is explicit and actual postability is checked. Draft discard retires only draft-owned occurrences; it does not delete source/shared/published files by cascade. Blob cleanup is a reference-aware owner obligation outside the database admission transaction, recoverable by its exact identifier-only job. Local upload navigation follows D37's saved-text/unfinished-file guard; a manifest is not a cross-device copy of browser File bytes.

### C12 — Finder projection, indexes and load

“The same My drafts metadata query includes both qualified purposes with a clear Reply/Internal note label. Every row remains owned by one person and source, regardless of shared Open/Waiting/Resolved/assignment state. Purpose must be part of row/action/response identity so Enter restores the correct composer. No new Note-only destination, body preview/index, recipient/mention search or exact sidebar count is introduced.”

Keep D37's title search, inbox scope, 20-row initial/50-row maximum requests and deterministic keyset pagination. Authorize all effective row/source/title rules before limiting; do not load full tenant histories or bodies and then filter. Support relevant `(tenant,owner,active lifecycle,meaningful_saved_at,id)` scan plus purpose-slot uniqueness and FK/dependency lookup indexes; optional purpose filtering must use actual plan evidence, not force a second unchosen UI filter. Constant identity functions may be statement-scoped; row-dependent source checks must not be cached once as though independent of the row. Record actual p50/p95, tenant/draft/source counts, payload maxima and concurrency profile; no new claimed throughput/latency SLO is inferred from vendor benchmarks.

### C13 — Email Studio, P6, CRM and attention ownership

“Support owns private Note drafting, canonical publication, source permissions and the posted note's D35 history. Shared Tiptap/P17 authoring/schema/static-rendering capabilities may support that Note profile without creating an Email Studio reusable draft or prepared email. Ordinary Note save/open/restore/discard never executes P17 preparation or P6 delivery.”

“Actual Post may create the existing qualified D15 E3 published-note occurrence and optional-follow obligations once. Direct-mention attention is separately governed by its own qualified producer, not D15 optional-follow enrollment or Stop. Each notification owner applies current note/source/member/channel permissions and its own durable recipient identity. Follow Off/Stop cannot suppress required direct attention; mentioning someone cannot enroll them as a follower. Existing owner coalescing handles overlapping reasons without a new hand-built double-count rule. If an already-governed notice has an external email step, that separate complete notice uses P17 preparation and P6 dispatch; an in-product step follows ADR0032 prepared.none without provider bytes. Do not claim a posted internal note can never lead to any staff email, and do not send the private draft body as a notification.”

CRM resumes the same currently authorized private Note draft/source and later shows the same permission-qualified published source. It gets no copied draft, private-body Activity, new contact/relationship, automatic record grant, financial mutation or completion assertion. This preserves shared context without a synchronization product. Draft privacy is owner-only, while a published Internal note has its own current permitted staff audience; these are intentionally distinct states and access rules.

### C14 — Compatible rollout and repair

“Extend the qualified D37 owner by purpose only after all old raw writers and published-note shortcuts are inventoried and closed for this new path. Deploy compatible schema/constraints/readers/commands before note autosave and My drafts exposure. Older reply-only clients must not parse Note drafts as Reply, mutate purpose, drop unknown canonical nodes, expose metadata or recreate a retired generation.”

Preserve reply data exactly; do not clone Reply fields/defaults into new Note purpose. Existing posted notes stay posted; do not backfill them into private drafts. Proven legacy unsent local material may enter the new owner only through an explicit currently qualified adoption command, never manufactured old authorship/times or HTML guessing. No automatic migration can recover unpersisted browser text after it is lost. Use idempotent migration mappings and restricted finite repair custody for ambiguous existing database rows. Kill switches disable affected new writes/exposure while leaving qualified safe read and accepted post/send/notification reconciliation intact. After new data exists, compatible roll-forward is preferred; rollback cannot reopen broad old CRUD or drop purpose/privacy/terminal fences.

### C15 — Falsifiable release proof and operations

“Prove actual owner/purpose/source semantics across UI, packages/api, raw Data API, view/RPC/service paths, storage and applicable search/Realtime/export consumers. Tests include same owner in two tenants, two owners in one tenant, multiple memberships, profile/auth IDs deliberately distinct, anonymous Auth, admin without private-owner authority, revoked source, stale JWT, old writer, mixed versions and retired identities. Test both successful access and denied row/metadata/body/asset/result existence.”

Use existing body-free operation correlation, typed failures and row-count/latency/collision evidence. Do not log draft JSON, note text, mention addresses, attachment filenames/URLs, tokens or raw database errors. Any acknowledged content loss, forbidden exposure, duplicate Post or false newest-Saved state is an activation blocker and containment event, not a monitored acceptable defect. Reuse D37 residual monitoring ownership for the now purpose-qualified draft path; the main D38 proof record should incorporate these cases without falsely treating this source review as execution.

## Ordered synthesis and remaining proof limits

First qualify the D37 purpose-aware private owner and existing source/auth mapping, then narrow canonical Note validation/whole-bundle persistence; implement atomic native publication/first-revision/consume/outbox and privacy fences; only then expose the small combined finder and same-editor resume. The critical new semantic boundary is private Note draft → posted staff-visible note, not another autosave screen.

Every architectural recommendation above is either a stated application of accepted D10/D15/D16/D17/D35/D37 or an explicitly proposed D38 extension. No exact SQL table/function name, new grant role, broker, database version upgrade, generic workflow or unrelated CRM capability is frozen here. Supabase hosted schema/privileges, actual runtime Postgres version, migration rollback, pgTAP/RLS transactions, Storage link revocation, real browser/IME and end-to-end post/notification results remain **unexecuted implementation qualification**. No production database or provider was accessed or modified. No real message was sent.

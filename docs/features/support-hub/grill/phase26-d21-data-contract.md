# Support label ownership, lifecycle and reporting contract

This fully founder-ratified D21 contract, 12 September 2026, supplements [R01–R24](phase26-d21-adversarial-review.md). Logical fields/commands describe invariants, not a mandated new physical table, framework or API spelling. Current TEXT identities do not require a UUID migration just for uniformity.

## Stored facts and database constraints

Preserve current `(tenant_id, label_id)` and `(tenant_id, original_conversation_id, label_id)` identity shapes or their proven equivalent. Same-tenant endpoint foreign keys remain mandatory. A membership cannot point to a label/conversation in another tenant even through a privileged caller. Tenant, creator/editor, admission time and relevant actor/profile attribution are trusted server values. Creator departure does not delete tenant-owned vocabulary. Identity and provenance endpoints cannot be changed through a generic PATCH.

Catalog configuration needs current lifecycle and monotonic control revision plus minimal creator/edit/archive/restore evidence under owner retention. Membership commands need current revision/control and durable receipts sufficient to reject stale or replayed intent. A logical state projection may be stored separately from append-only change facts; do not require a global event-sourcing rewrite. Where association rows are physically removed, the shared command/revision/history mechanism must still fence old Add/Remove intent. Receipt expiry cannot make an old command look new: retain the necessary compact identity/generation fence, or require an owner-issued bounded command admission context and reject expired unknown retries. A fresh user action is distinct from retrying an old effect. Never retain sensitive full payloads solely for deduplication.

Name/description bounds are measured consistently as R05 specifies. Use non-null stable identity, valid lifecycle/tone/revision constraints and a tenant-unique normalized-name key for extant active/archived definitions. Exact comparison normalization must be the same at authoring, API and database admission; versioned normalization upgrades are migrations, not silent collation changes. Legacy conflicts block only unsafe new admission until reconciled, with no hidden-data collision leaks. Compatibility slugs never determine business identity. No money precision, currency column or per-person identifier is required for this metadata.

Ordinary archive must not execute the current label-FK cascade. Membership retention follows source/metadata purpose, with live reference protection and unavailable/tombstone semantics where actual privacy disposal requires stronger removal. Parent tenant disposal remains with Core's tenant/records process; it is not a catalog maintainer's authority. History may refer to removed IDs without retaining forbidden display content. Runtime database grants, direct DML, RPC/view functions and service roles require the complete R13 authorization proof; row policy presence is not sufficient.

## Command and state transitions

| Command / transition    | Required admission                                                                                                 | Effect and recovery                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| Create → Active         | Current curator, validated general vocabulary/name uniqueness, server identity, durable admission context          | One identity and history/receipt. Same intent returns outcome; conflict preserves form.                         |
| Edit Active or Archived | Exact ID/revision and current curator/privacy authority                                                            | Same meaning, new wording/appearance revision. Does not activate Archived. Missing Update is not Create.        |
| Active → Archived       | Exact ID/revision, current curator and privacy qualification                                                       | Stops new application, preserves authorized existing membership/reference meaning. No fan-out removal.          |
| Archived → Active       | Exact ID/revision, valid name/owner/current privacy eligibility                                                    | Same ID available again; prior removed memberships and old intents stay removed/invalid.                        |
| Add label               | Current source/component and catalog lifecycle authority, exact label and control/topology revision, stable intent | One original-origin contribution if not already effective; otherwise truthful unchanged result.                 |
| Remove label            | Current source authority for every exact contributing origin, reviewed current control/topology set                | Atomic end of those contributions; no other labels or newly discovered originals touched.                       |
| Redact/restrict/purge   | Actual privacy/records authority, current source scope and dependency/retention control                            | Required unavailable/tombstone/protected history semantics; ordinary curator cannot choose this through Delete. |
| Merge / Undo            | D10 authoritative topology command                                                                                 | Derives union/partition from current original memberships; no synthetic label edit or reenrollment.             |

Commands serialize or otherwise prove current authority against catalog lifecycle, membership/control and relevant topology change. Concurrent Add/Add converges to one effective association; contradictory Add/Remove must not lose accepted intent or overwrite unrelated edits. Combined Remove is all-or-nothing across its reviewed contributors. This does not imply a whole bulk selection must be one giant database transaction.

Existing bulk label application may remain only through the same qualified owner command, using explicit bounded selected IDs, per-conversation durable sub-intents and truthful succeeded/unchanged/failed/unknown results. Retry only failed/unresolved sub-intents under their original identity; do not reapply successes or newly matching view results. The normal user journey remains a single conversation. D21 adds no all-matches bulk action or generic taxonomy cleanup engine. Publish the existing shared bulk selection budget before enabling that path; if unqualified, keep it unavailable rather than leaving an alternate writer.

## Merge and correction examples

Suppose original A carries Receipt question, and original B carries Receipt question plus Delivery question. After an authorized merge, the continuing conversation shows each label once. Add Receipt question is unchanged; it does not write another membership on the continuing origin. Remove Receipt question ends the contributions from both A and B together. Undo then shows neither side carrying Receipt question; Delivery question remains with B. A genuinely later Add belongs to its then-current continuing origin and stays with that origin when separated.

If another merge adds C between review and Remove, the old intent cannot silently remove C's membership. If one contributor becomes forbidden, no partial removal is presented as full success. Archive/Restore changes catalog availability independently; it never rewinds these edits. CRM Party merges and D12 related conversations do not participate in this association projection.

## Exact current-label report population

The report is **current conversations originally started in a selected period**, with **current responsible inbox** scope and **current labels** at one server evaluation instant. It is not historical inflow, labels applied during the period, resolved-topic completeness or a past point-in-time label snapshot.

Evaluation order is mandatory:

1. Establish current tenant/viewer permissions and current D10 components from a coherent database/query snapshot. Only components whose required source facts are eligible for the declared result may contribute. Apply current ordinary Support exclusions; held intake and inaccessible source content do not become report material.
2. For each eligible current component, preserve original identities and compute its earliest qualified original-conversation creation/start instant across the **whole component**. Do not first discard originals outside the chosen period or inbox. Current continuing root identity is the count identity; D10 merge time is never a new start time.
3. Apply current responsible-inbox and other explicit non-date scope to components. Compute the chosen reporting-period instants from the visible reporting timezone; use `[start, end)` UTC bounds. Then include components whose qualified earliest original start is in that period. Unknown start evidence is not replaced by a known later member, provider receipt, merge time or now.
4. Compute the current permitted union of label memberships for each included component at the same evaluation instant. Include ordinary archived still-applied labels. Count each label at most once per component.
5. Produce full authorized aggregates before page/limit. Bind table, chart, totals and drilldown predicates to the same semantic contract. Report-context drilldown reuses this exact component-first predicate through the shared query/list owner; do not substitute D20's ordinary root createdAt filter or silently drop the cohort. D21 adds no saved-view authoring for this report predicate. A later live drilldown or deliberate Refresh is a new current-state evaluation, shows its As of time and may legitimately differ; same-evaluation parity does not promise a historical snapshot.

An original-start-unknown component cannot be assigned to a date cohort. Show a separately qualified **Start date unconfirmed** population under the same non-date scope, explicitly not asserted to be in the selected period. Where disclosure rules prohibit a count/detail, use source-safe unavailable treatment. Missing label completeness within a known cohort gives an explicit incomplete/unavailable report state; do not quietly omit the component from N or convert it to U. The complete-percentage result is withheld until the represented metadata is qualified. No count is invented for entirely inaccessible components.

For a complete known cohort: `N` is distinct current components; `L` has at least one effective label; `U` has none; `L + U = N`. For label j, `Cj` is distinct current components carrying j; percentage is `100 × Cj / N` for N>0. Zero is a legitimate Cj when requested for an eligible label, but missing metadata is never zero. No-label percentage is `100 × U / N`; display no-population at N=0. Sum Cj may exceed N. Do not add a union label bucket total to U and call it N.

Counterexample: three conversations, two each carrying Receipt question and Delivery question, and one carrying no labels. N=3, L=2, U=1, each label count=2. The label percentages are 66.7% each and overlap; neither total labelled=4 nor zero unlabelled is correct. Another counterexample: originals from 2024 and 2026 merge. Their current component begins in 2024 under this report even if its current root was the 2026 row. Undo can return two components to different cohorts; that is why this report is labeled current grouping and cannot be used as historical request inflow.

Catalog rename may update displayed wording while retaining same-meaning identity. A new meaning requires a new ID; historical command history retains minimal qualified old-version evidence separately. Future true historical-at-resolution reporting must be separately specified against recorded source events, including correction and unavailable legacy data. D21 does not build that warehouse or retcon today's memberships into old truth.

## Queries, caching and failure recovery

Use direct current-source predicates/joins rather than unpaged tenant-wide hydration. Existing composite PK/FKs and reverse indexes are useful, but verify actual execution plans and installed PostgreSQL version. Add only indexes justified by catalog lookup, original endpoint retrieval, label reverse filtering and qualified reports. One large tenant must not exhaust unrelated tenants' resources.

Catalog/picker/report caches are projections with explicit tenant, principal, acting scope and source/configuration revision/lifecycle semantics. Late requests after a tenant switch or revocation cannot repopulate current UI. Privacy changes require current-serving gates in addition to eventual invalidation. Optional UI stale data may be presented only when still authorized and clearly qualified; never use it to decide whether a membership exists for writing. Catalog loading failures do not replace persisted chips with an empty array.

After atomic commit, a failed index refresh is secondary repair work. The API returns a truthful committed receipt if known; an ambiguous client response resolves the same intent. Reports and exports must not declare completeness while their projection is known stale/partial or outside its registered freshness contract. Use existing source-owned repair and per-tenant backpressure rather than one scheduled job per label. Diagnostic logging avoids private names/search text/source payloads.

## Retention, migration and rollout

Catalog and membership are permitted Support metadata only while their owner purpose and privacy policy allow. They do not preserve message bodies or infer indefinite CRM history. Exact finite configuration/current-membership/change-history/receipt/query-state horizons and compact anti-replay evidence must be qualified by the actual owner before activation; inherit an applicable sound Core policy rather than inventing a per-label settings screen. Privacy restriction and restored-backup barriers apply to current and archived names and all projections. Actual metadata restriction is not repaired by merely hiding one UI chip.

Inventory current labels, references, memberships and writer routes. Preserve stable IDs; unknown actors/application times remain unknown. Validate Unicode bounds and new comparison keys without silently clipping or merging old data. Classify invalid/ambiguous rows into bounded tenant-owned reconciliation and prevent unsafe new use without breaking normal unlabelled Support work. Existing descriptors may need correction by qualified maintainers, not an automatic AI rewrite.

Converge the live API, bulk/macro registry, fixtures and old browser writer paths before enabling the new behavior. Migrate compatible readers and additive schema first, then enforce commands and retire old destructive grants/routes. The stop switch disables new label changes while preserving currently permitted reads and actual privacy enforcement. After new history/lifecycle is written, old-code rollback cannot resume cascade deletion or ignore control revisions. Roll-forward and restore qualification are required. Future specifications and issues must carry R01–R24/P01–P36; none are published during this grooming stage.

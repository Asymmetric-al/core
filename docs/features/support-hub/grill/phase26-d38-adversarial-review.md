# D38 — Private autosaved Internal note drafts

**Current ratification — 15 September 2026:** The founder fully ratifies D38 A and all amendments, additions, adjustments, changes, updates and incorporated corrections. D1–D38 and all amendments are fully ratified. The [full ratification](phase26-d38-full-ratification.md) incorporates this entire record and supporting prose. Earlier proposed/pending/intent-only and no-Q39 wording below is historical, not a repeat approval gate. Original evidence and unexecuted-runtime limits remain unchanged.

**14 September 2026. Disposition: Accept with required amendments.** The founder selected **A — Automatically save note drafts in My drafts**. A is recorded at intent level; the complete detailed amendments below are proposed for ratification. D1–D37 and all their amendments remain fully ratified. Q38 is answered at intent level; no Q39 is opened. This is exploratory decision documentation, not formal OpenSpec, tickets or shipped behavior.

The permanent design is a small extension of the same private unfinished-work capability: **write an Internal note → save quietly → leave → My drafts → resume that note → deliberately Add note**. A private draft is not a posted internal note. Reusing the editor or database does not collapse that distinction.

## Exact corrected decision

Support automatically saves each staff member's meaningful, unfinished **new Internal note** as a private, source-qualified draft in Asym's Supabase Postgres, using the same qualified Support draft capability and My drafts destination as external replies. Reply and Internal note are distinct immutable draft purposes with independent content, identity and lifecycle. The list labels their purpose clearly and resumes the exact draft in the existing conversation composer. Saving is quiet and non-publishing; only deliberate, currently authorized **Add note** atomically admits the canonical note, its required initial history and asset relationships, consumes the exact draft generation, records the operation result and durably records any required downstream attention. Current source/tenant/author authorization, conditional saves, truthful acknowledgments, safe navigation, privacy/retention and original-operation recovery apply throughout. D35 corrections to already-posted notes remain local and unchanged. R01–R26 and all companion contracts form the complete corrected decision.

## Required amendments

### D38-R01 — Need, alternatives and scope

Adopt automatic private save and discovery for new unpublished Internal notes. The demonstrated product gap is interruption in an existing composition mode; no frequency of long ministry notes or new care-record workflow is assumed. The strongest alternative, B, is deliberate Save note draft with the same finder; it gives intentional durable-retention control but adds a save habit inconsistent with accepted Reply autosave. C, guarded session-only work, has the smallest storage scope but cannot support dependable later return. Do not implement all three as settings. This choice does not introduce a notebook, shared drafting, approval, scheduled posting, CRM note feature or persistent editing of posted notes.

### D38-R02 — One finder, clear purpose

Extend D37's existing **My drafts** population to eligible own external Reply and new Internal note drafts. Keep the stable entry, all accessible inboxes and work states, metadata-only rows, title-only search, separate Inbox filter, recency ordering, Refresh and complete keyset pagination. Retain 20 initial rows and a maximum 50 per request across the combined population, not a separate quota for each purpose. Show textual **Reply** or **Internal note** in each row, alongside permitted conversation context and authoritative save time. No body/mention/recipient/file preview, total count, new type filter, note tab, badge, notification or destination is added. Helper text can read “Your private reply and note drafts across accessible inboxes.” An unavailable row cannot leak forbidden existence or stale CRM context.

### D38-R03 — Independent private identities

Use one qualified Support private-draft owner with a closed purpose distinction. Enforce at most one active draft per **tenant, trusted staff owner, immutable original conversation and purpose**. A Reply and a new Note may coexist without overwriting, consuming or converting each other. An old lifecycle cannot be resurrected after post/send/discard. Multiple original conversations combined by a merge may retain separate drafts of the same purpose; do not deduplicate by current root, assignee, email or CRM Party. A new general note normally begins/resumes the current continuing original's own Note slot; direct My drafts activation opens the exact selected private slot. No silent choice of someone else's or another original's writing.

### D38-R04 — Meaningful creation and complete preservation

Opening Internal note, focusing, selecting, hydration or loading defaults creates no durable draft. First meaningful author changes to the qualified body, note wording, typed mentions or file selection may create one. Preserve structurally valid incomplete work, including only a pending attachment; save readiness is separate from post readiness. An existing draft whose content is cleared remains until deliberate Discard or actual admission. Do not silently delete it or invent a title/body from CRM. Actual Add note requires meaningful canonical body **or at least one ready, clean, currently authorized selected attachment**. It must not require dummy “see attached” text; an empty note with no such file cannot post. Every selected unfinished, unsafe or invalid file must be repaired or deliberately removed before posting; it is never silently omitted.

### D38-R05 — Draft origin and actual note destination

Preserve the original conversation where private work began as its slot anchor. Separately qualify the **actual publication original** under D10-R14: a general note posted from a combined workspace attaches to the then-current continuing original, unless an existing authorized source-specific action establishes another original. Do not copy external Reply retargeting rules or create a new destination picker. If a merge/Undo changes destination or eligible internal audience after writing began, retain permitted work, explain the changed destination and obtain targeted review before Add note; routine unchanged notes require no extra confirmation. Recheck topology/source/privacy generations atomically at admission. A B-origin draft resumed after B joins A keeps its private B slot, while a reviewed general note posts under A. A post committed before Undo keeps its lawful original affinity; an Undo committed first forces current review. No silent rehoming, duplicate draft or automatic publication under the old anchor.

### D38-R06 — Quiet saving with truthful status

Reuse D37's qualified scheduling: attempt after **750 ms of quiet**, or by **5 seconds of eligible continuous input**, in the foreground/online/authorized/valid-schema/non-IME case with no unresolved prior save. These are scheduling targets, not network acknowledgment or crash-recovery guarantees. Each purpose-qualified controller has at most one save in flight and coalesces newer committed state. Do not let the Reply controller save or acknowledge Note content. Provide Save now/Retry save without requiring a manual save habit. **Saved** or **Saved privately** means the latest complete eligible local bundle is durably acknowledged. An old acknowledgment cannot mark later typing saved, reset it or alter the other mode. Quiet success must not produce repeated toast or screen-reader announcements.

### D38-R07 — Note-specific canonical profile

Keep the existing shared Tiptap/editor and versioned canonical schema, with the code-owned Internal note profile applied before parser normalization and again at server admission. Persist canonical structured body, qualified typed mention/wording/source references, note asset selection, locale/direction and explicit source/context/version identity. Exclude external To/Cc/Bcc, sender/signature/quote-delivery envelope, P17 preparation state and **D24 staged work plans**. D24 expressly excludes internal-note-and-work mode; the separate Reply plan remains intact. Do not execute typed fill-ins or mentions while saving. Incomplete allowed values can remain typed unresolved draft values; unknown nodes, unsupported attributes, executable HTML and forbidden sources cannot be “fixed” by silently stripping and saving them. No new editor, schema language, Tiptap Cloud, Yjs or history service is required.

### D38-R08 — Mentions remain inert until posting

Mention picker selection, insertion, removal, hydration, autosave, finder reads and restoration must produce **zero posted notes, timeline activity, attention intents or external messages**. Preserve each currently qualified mention as authoring data. At Add note, resolve distinct eligible targets from the admitted canonical version through the independently governed direct-mention producer; removed mentions never notify, and repeated chips do not produce duplicate attention for the same admitted occurrence. D15 separately owns optional-follow publication eligibility and its frontier. A mention never enrolls Follow, and optional-follow Off/Stop does not suppress an independently required direct mention; qualified overlap handling remains with the existing attention owners. Ineligible targets require an honest repair/removal path, not a newly inferred CRM recipient or privacy bypass. Existing attention eligibility, self-mention handling and channel policy remain with their owning contract. The current composer-to-activity helper path that POSTs a note on mention insertion must be closed before enabling this capability, not merely hidden in My drafts.

### D38-R09 — Files have private draft custody

A draft manifest references owner-qualified asset occurrences; it is not proof that browser File bytes uploaded or a file passed scanning. Upload through the approved Storage/asset path, with current draft tenant/author/source access on original and derivative reads. Ready, pending, failed, rejected and removed are honest per-file states. Raw bucket paths, MIME assertions and signed URLs are not authorization. Require existing D32 preview/scanning/source-stop controls. Posting atomically transfers or links exactly the selected permitted occurrences to the posted note's custody; discarding removes only draft-owned occurrences through qualified cleanup. Storage object operations and the SQL transaction are not one distributed transaction: durable cleanup/finalization obligations prevent lost effects and orphaned private uploads. A pending transfer cannot vanish on navigation while text claims complete recovery.

### D38-R10 — Trusted actor and intersected current access

Authenticate through the existing Supabase server session and Core acting-context boundary. Derive real author/profile, tenant and applicable membership/capability from trusted context; input carries resource choices, not asserted ownership or approval. Actual source IDs are TEXT; profile/auth/membership identities are UUIDs with explicit real mappings. Each read/save/discard/post checks ownership plus its own current source and operation-specific authority. If only posting permission is lost while private read/custody remains valid, the eligible saved note may be inspected with Add note unavailable; ownership does not restore write/post authority. Posting additionally checks the actual current destination and every controlled dependency. Assignment, conversation participation, followers, CRM ownership, matching email or normal administrator status never grants colleague-draft access. Exceptional records/privacy custody uses D16/D17's separate narrow audited route, not a staff draft-browser feature. New CRM identity or relationship inference is not part of this command.

### D38-R11 — Structural database and authorization closure

Apply the [Supabase contract](phase26-d38-supabase-contract.md) to the shared draft owner: non-null tenant/real owner/origin/purpose/lifecycle/revision/schema metadata, tenant-aware keys and foreign keys, purpose-qualified active uniqueness, immutable owner/source/purpose fields, valid lifecycle/terminal-reference checks, server timestamps, bounded canonical document and exact idempotency relationships. Purpose changes are forbidden updates. Derived HTML/text/list metadata is not another write authority. Base-table grants, RLS reads/mutations, functions, views, Storage and service-role paths must all preserve the same boundary. Evaluate both old-row `USING` and resulting-row `WITH CHECK` plus column/function authority. Ordinary clients must not update terminal/audit/owner/source fields or bypass multi-row admission through generic CRUD. Test all effective permissive policies and privileges, not only a newly added narrow policy. No financial/money column or new monetary calculation is introduced.

### D38-R12 — Atomic saves, concurrency and durable result identity

Save the entire note bundle and its accepted revision/result atomically through a `packages/api` command and one qualified database transaction/RPC. Multiple browser `.from()` requests do not provide that atomicity. Match expected revision, immutable purpose, current tenant/owner/source/privacy and lifecycle generations. An unchanged canonical bundle is a no-op for edit time/revision but still has an exact operation result. Two tabs cannot silently overwrite; preserve a permitted losing candidate and let its author review/reapply against the new base. Bind each operation handle to exact actor/tenant/source/purpose/lifecycle/base and semantic command. An unknown acknowledgment recovers that same operation; absence is not nonacceptance until late admission is fenced. Returning an original result and reading today's draft state are distinct. No fresh-key retry or automatic content merge.

### D38-R13 — Mode switches, navigation and local work

Reply/Note switches preserve separate committed bodies, files, provenance and owner controllers. A late callback is scoped to its original identity/purpose and cannot write into the currently visible mode. Capture settled editor/IME state before changing its context; do not equate raw compositionend with a committed transaction. Keep supported CRM side context mounted where appropriate. Navigation that would destroy dirty work flushes the relevant retained controllers, including a dirty other purpose, without an unnecessary confirmation after routine success. Reuse one guard for known failure, unknown save and local pending File consequences. Permit informed Leave during unresolved saves without claiming they were canceled. Preserve body-free operation handles; no hidden offline body/file archive. On privacy/account/tenant loss, purge forbidden state and Undo even if the person had unsaved work. Browser crash/close remains best-effort, not guaranteed last-keystroke recovery.

### D38-R14 — Resume the same note with context

My drafts opens one exact currently authorized saved bundle into the existing Internal note composer. No temporary Reply-mode flash, default signature, new empty body or substitute CRM context. Show the current conversation and internal purpose before automatic desktop editing focus; on mobile reveal context before user-directed keyboard focus. Preserve the originating list query/filter/selection/scroll for same-session return. Cross-device recovery covers acknowledged content/context, not exact caret location. Newly inaccessible or incompatible content has a current-authority-safe unavailable/repair state; it is not presented as an empty draft. Changed destination/mentions/assets are review needs, not hidden automatic edits. Loading a draft does not reopen, assign, resolve, follow or satisfy a service target.

### D38-R15 — Add note is one authoritative admission

Deliberate Add note submits the newest settled candidate through the qualified Support owner. The person need not wait for a debounce or click Save first; the command may admit that exact final bundle atomically. It must settle/recover earlier dependent save operations before admitting against a known base. Under one transaction and common lock/version protocol, recheck source/destination/author/purpose/privacy, validate post readiness, admit one canonical native-human note and initial D35 history, admit selected file relationships, consume the exact draft generation, record the durable operation result and necessary source activity/attention outbox obligations. Roll back all database effects on failure. No provider I/O inside this transaction. Optimistic UI is pending until authoritative admission; reconcile one pending row to the actual note ID without duplicates. Posting never consumes the separate Reply draft/plan or means a CRM/giving action finished.

### D38-R16 — Unknown posting and downstream failure

The post operation has durable business-effect identity, not merely a request timeout key. A lost response may mean the note was already admitted. Freeze the affected post candidate while checking/recovering the original operation, preserving authorized navigation and honest status; do not offer a fresh editable draft/duplicate Add note to repair uncertainty. If posting committed, show the actual note and keep its draft terminal even when attention delivery or a later projection fails. Retry only the original downstream obligation under its own identity. A definite pre-admission rejection preserves the draft and repairable work. Note admission/consumption and source/privacy/merge transitions must share a proven concurrency boundary; two separately checked writes are insufficient. Duplicate suppression is per exact draft/post occurrence, not a heuristic that collapses legitimate separate notes from different staff or original slots.

### D38-R17 — Deliberate, purpose-specific discard

Reuse D37's single Discard confirmation, naming the **Internal note draft** and explaining that only that unfinished note and draft-owned attachments are removed. The conversation, posted notes and separate Reply remain. Discard checks the reviewed revision/generation and terminates it atomically with its result and cleanup obligations. Another tab's newer save conflicts rather than being deleted. A stale save cannot resurrect a discarded or posted generation. A possibly admitted Add note cannot be canceled through Discard; recover its original operation. No bulk discard, hidden trash, Undo timer, restore-history product or automatic draft transfer is introduced.

### D38-R18 — Privacy, retention and lifecycle ownership

Private draft rows/bodies/derivatives/operation material obey current D16/D17 source and exceptional-custody rules. Autosave, last-edited sorting, reads and restore do not renew the original source lifetime or override a restrictive stop. Current read authorization applies to caches, signed access, search metadata, exports, logs and any optional realtime path. An admitted native-human note receives D17's actual posting/admission event and its proper native clock; draft creation is not a fabricated earlier note event. Required source-derived dependencies retain their stops; independent admitted evidence keeps its own qualified history rules. No silent age eviction or invented draft lifetime. Before activation, the existing owner inventory must explicitly cover note draft bodies, assets, terminal/result evidence, backup/export treatment, author departure and source deletion/archival, with no generic cascade that removes required history or restores forbidden material.

### D38-R19 — CRM continuity without duplicate ownership

CRM-hosted Support context uses the same canonical draft and eventual note under intersected current authority, preserving return navigation. The requester, message participant, authenticated author, profile, CRM Party/person/organization, assigned responder and CRM owner remain distinct. Shared/changed email and CRM merge do not reassign private writing. Links or read projections confer no right to read restricted missionary/member-care/giving records or update another domain. CRM activity may reference the one admitted Support occurrence through its existing contract; no draft activity and no duplicated note body as another authoritative CRM note. Financial, receipt, refund, recurring-gift and contact actions remain with their own permissions, validation, approvals and history; neither saving nor posting executes them.

### D38-R20 — Email Studio, Tiptap, Realtime and platform seam

Support owns private persistence, discovery, current source/actor checks and actual note admission. The shared P17-governed canonical editor/profile and reusable wording may support authoring/validation; **a note save or note post is not an outgoing-email preparation or Email Studio template publication**. Any separately authorized internal attention notification produced after admission has its own P17 presentation and P6 delivery/reconciliation contract; in-product attention has no fabricated provider state. External Reply's P17 whole-message preparation and immutable P6 delivery remain unchanged. Supabase Postgres is durable storage; Realtime Presence/Broadcast is not saving or posting. No draft bodies/mentions/files on presence channels or automatic table-publication enrollment. The finder works through the approved bounded read model with invalidation/refetch; no new websocket server, poll-per-keystroke loop or realtime dependency is necessary. Vercel/Next.js request memory is not the durable owner.

### D38-R21 — Clear, restrained and accessible interface

Use shared Base UI primitives and exact base-maia geometry/semantic tokens. Show **Internal note** and “Private until you select Add note”; keep Add note distinct from Send and secondary Save now/Discard. Text, icon and accessible names convey purpose rather than color alone. Ordinary write/save/resume needs no modal. Reserve review/confirmation for an actual changed destination, unresolved loss risk, destructive discard or existing admission requirement. Do not animate or reorder under typing/focus, force mobile keyboards, obscure content behind status chrome or make a hover-only action essential. Verify 320 CSS-pixel reflow, 200% text resize, 400% zoom-equivalent reflow, keyboard/AT/IME, long names/Thai/RTL, local dates/zones, reduced motion, meaningful contrast and Core's 44 CSS-pixel touch target. These are required outcomes, not a claim that a specification alone proves perfect usability.

### D38-R22 — Bounded queries and responsive typing

Do not load draft bodies or mount editors per row; fetch only the opened body's authorized representation. Keep editor transactions isolated from list rerenders. Index the tenant/owner/active-purpose population and stable meaningful-edit ordering, with tenant-aware source/dependency checks applied before pagination. Exclude control/cleanup timestamps from user recency. Scope query keys, request generations and cached results to real tenant/actor and source/purpose where applicable; stale responses cannot repopulate another context. Use D37's bounded scheduling/page limits and existing invalidation/focus/reconnect behavior. Do not duplicate status/count polling or invent exact latency claims. Qualify actual shared byte/node/depth/asset/query/concurrency and measured latency budgets before activation; record the workload and endpoint limits instead of assuming a vendor default proves capacity.

### D38-R23 — Migration, rollout and rollback

Extend the qualified private owner/purpose contract through a compatible migration; do not store new drafts in today's broad published-note/message rows. Inventory every note producer, callback, renderer, Storage path, export, legacy writer and service-role route. Existing posted notes remain admitted evidence; do not reinterpret them as private drafts or invent historical draft authorship. Retained legacy private candidates require positive owner/source evidence; unknown cases use restricted repair custody. Deploy constraints/grants/commands/readers and initial note-history/asset/outbox admission first, then qualified editor/autosave and combined finder. Old clients must fail closed for unsupported purposes/schema/generations. Kill switches stop affected note-draft writes/exposure without discarding permitted local work, reviving terminal generations or canceling already admitted note/notification recovery. Use compatible roll-forward after new data exists; never roll back to the unsafe mention callback or broad writer.

### D38-R24 — Operational controls and audit

Reuse existing operation telemetry and repair mechanisms with note-purpose outcome dimensions. No canonical body, mention names/addresses, filenames, signed URLs, tokens or full exception payloads in logs. Autosaves are not CRM activity, business history or staff-productivity records. Published note history and privacy/security audit retain separate owners. O01–O05 in the [proof and operations record](phase26-d38-proof-and-operations.md) name signals, exact thresholds, responsible roles and responses. Privacy loss, premature publication, acknowledged-content loss, cross-purpose contamination and duplicate posting are release blockers and one-event containment triggers, never monitor-only concessions.

### D38-R25 — Resolve evidence and authority conflicts explicitly

Current behavior is evidence to replace where wrong: Save draft rejects Note, local navigation resets it, Note admission omits selected attachments/canonical JSON, the mention callback can POST a published note, and note insert plus conversation update are separate operations. Existing tenant composite keys and both RLS mutation predicates are useful but broad staff/superadmin access is not private ownership. Current Supabase/Postgres documentation qualifies skill shorthand: missing explicit `WITH CHECK` can inherit `USING`; definer behavior depends on its owner's rights and grants, not a blanket automatic bypass. D38 still requires explicit intended mutation checks and a reviewed narrow command boundary. ADR0001/current founder-approved Core boundaries retire Twenty; stale CRM OpenSpec backing/synchronization prose is not authority to restore it. Preserve remaining identity/native-surface/permission requirements and capture the precise formal retirement reconciliation in the later authorized specification stage. No skill, unrelated domain or formal spec is rewritten by this review.

### D38-R26 — Proof and recording boundary

Require P01–P30 on actual qualified UI/editor/API/database/auth/storage/worker paths, extending the relevant D37 groups rather than rebuilding their tests as toy mirrors. Include adversarial roles, old/new schema, wrong-source/purpose callbacks, fast posting, unknown outcomes, topology/privacy races, CRM continuity, note assets/mentions, browser/IME/mobile/AT and intended-staff tasks. Preserve documentary checks, source-backed counterexamples and finite models as limited evidence. Record A, one glossary term and a scoped feature ADR with detailed amendments proposed; do not claim they are already fully ratified, implemented or tested. No Q39, formal PRD/OpenSpec, tickets, production write or real message is introduced.

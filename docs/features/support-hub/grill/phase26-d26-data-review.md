## Governing interpretation

The founder's CRM requirement is a **complete discovery and navigation requirement for the authorized relevant population**. It does not require manufacturing a CRM Party, exposing every request to every CRM user or copying Support into CRM tables. A request can have zero, one or several explicitly relevant Parties. Every record with a D9 discovery basis must be discoverable regardless of manual/email origin, native message count or ended work status. A request with no qualified CRM relation remains valid Support work with a clear unlinked state and a later authorized linking path.

Preserve D9's explicit relevance OR qualified actual correspondence basis, joint visibility and current D10-root deduplication. Merely recording a phone number/name or launching from a donor's screen does not establish actual correspondence, legal identity, representation, household authority or permission to disclose. “Through CRM” means the existing CRM Overview/Communications entry opens the **same canonical Support detail and commands**, with contextual return. It does not mean a second CRM reply editor or broad Activity transcript.

## Findings and exact proposed amendments

Severity and likelihood below describe an unamended design or reuse of the observed path, not verified production incidents. Every item changes or narrows A; none rejects the legitimate direct-entry need.

### F01 — Complete CRM access can be misread as blanket disclosure

**Material concern: Yes. Critical severity; plausible likelihood.** A global all-conversations CRM feed, mandatory Party link, automatic household propagation or locked-card count would breach D9's separate relevance and visibility boundaries. Conversely, filtering only P6 email history would omit every new manual request. S08–S10 and D9-R01–R09 support the concern.

**Proposed clause DC01:** “Every Support original of any admitted origin participates in the same D9 discovery contract. For an authorized relevant Party, include an active explicit relevance association or independently qualified actual correspondence, apply current joint Party/Support/source/field authorization, then deduplicate current D10 roots before count/page. Manual origin, zero native mail or ended status is not an exclusion from the appropriate full view. No qualified relation means unlinked Support work, not automatic Party creation. Inaccessible records contribute no title, count, preview or existence signal. Through CRM opens the same canonical Support detail; read permission does not imply send, assignment, context-edit or owner-action permission.”

**Proof:** email-only, manual-only, mixed, resolved, related-only, correspondence-only and overlap fixtures; CRM-only/Support-only/joint viewers; multiple linked Parties; hidden notes/sources in an otherwise visible conversation; no-Party request later linked; all-origin counts and pages without leakage.

### F02 — Email-shaped data cannot represent staff-recorded work honestly

**Material concern: Yes. High severity; certain incompatibility if S01/S06 are reused unchanged.** Placeholder email, artificial native timestamps, inbound direction or a delivered message bubble falsifies request history and can invoke downstream behavior. Merely adding phone to channel is insufficient because a phone-origin request may later have actual email.

**Proposed clause DC02:** “Keep request origin distinct from subsequent communication methods. Add a typed staff-recorded request origin for the selected supported encounter methods, with trusted recording actor/time and separately labelled reported occurrence information. New work has zero native emails, no fabricated native message time/direction, no provider/source email identifiers and no delivery state. Email contact and CRM association are optional independent facts. Amend database constraints, generated types, serializers, APIs, filters, readers and rollback readers together; null must remain absence, never now or a placeholder mailbox.”

**Proof:** no email/no Party, later first email, reported past encounter, unknown encounter time, current source mapper boundary; native counts/times remain zero/null until actual mail. Original origin survives later correspondence.

### F03 — A new call log or dual-write would split ownership

**Material concern: Yes. High severity; medium likelihood.** Saving the same call into a Support “message,” CRM note and generic activity creates conflicting edits, retention and metrics. The opposite mistake is forcing all follow-up through a not-yet-qualified interaction owner. S12, ADR0001 and D9-R09 reject copied truth.

**Proposed clause DC03:** “Support owns the bounded request, its minimal staff-authored intake brief and handling. Reuse an existing permitted encounter/owner record by exact typed source reference when present; do not clone its transcript into a second editable call record. A Support-first brief is evidence of the request as recorded, not a complete call transcript. Relevant CRM display references/projects the same source fact and Support work. No new generic interaction platform, provider CRM synchronization, persisted timeline copy, inferred Party link or duplicate communication event is introduced. One encounter can justify distinct explicitly reviewed requests without making source ID alone a uniqueness constraint.”

**Proof:** create from existing logged encounter; one source visible from two permitted surfaces without duplicate activity/contact counts; two genuine distinct requests from one source; source correction/withdrawal; no new generic donor activity write on Support save.

### F04 — Two entry points must share one atomic admission

**Material concern: Yes. High severity; plausible likelihood.** Creating the request, then separately linking CRM or assigning work can leave partial success, repeated creation or a request apparently lost from the originating CRM record. S05's sequential write pattern is unsuitable; D9-R05/R20 and D12-R07 already require compound owner admission.

**Proposed clause DC04:** “Support-first and CRM-first invoke the same bounded packages/api command. CRM-first visibly stages the current existing Party as a removable Related record; it is accepted only by the explicit final Create. In one conditional local transaction, validate current authority/source release and final inbox/work plan, create the original/manual source and brief, install all reviewed D9 links and handling/reminder facts, append protected history, and record the durable operation receipt plus required continuation. Either the whole reviewed set commits or none. If a target or permission changed, preserve the draft and require current review; Create without the unavailable link is a new explicit choice, never silent partial success.”

“A lost response retries/reconciles the same tenant-scoped operation and semantic input identity. Changed input conflicts. Original outcome and current resulting state are distinct; replay cannot resurrect canceled work or a removed link. No provider I/O occurs inside this transaction, and no P9 async-provider command log is repurposed for local Support admission.”

**Proof:** failure after each logical write, duplicate tabs/retries, lost response, link revoked or Party merged at commit, source release revoked, one invalid destination in a selected set, reconnect after successful correction.

### F05 — Existing RLS protects tenants, not these command invariants

**Material concern: Yes. Critical severity; high likelihood if existing broad grants are treated as sufficient.** S03 permits authenticated same-tenant staff CRUD over protected content/audit. It does not distinguish inbox/source rights or prohibit changing recorder, origin, audience flags or audit state. The table already has explicit WITH CHECK: omission is not the issue.

**Proposed clause DC05:** “Protect raw origin, source/relevance control, operation receipts and audit from browser reads/writes; expose only purpose-qualified projections and commands. Apply the governing tenant RLS floor and required ENABLE/FORCE posture, explicit least grants, effective SELECT/USING/WITH CHECK, column immutability and current Phase 12 authorization. Inspect all permissive policies, views, RPC execution/definer privileges/search paths, service roles, storage, realtime and legacy writers. An allowed mutation must not transform a permitted row into unauthorized scope, origin, attribution or disclosure. Privileged server access is not exemption from the same current resource checks.”

**Proof:** actual migration-chain grants/policies including anon, authenticated and privileged paths; direct forged INSERT/UPDATE/DELETE, audit rewrite and cross-inbox reads; invoke any public RPC without capability; invoker/definer view behavior; storage/source derivatives and realtime access revocation.

### F06 — Recorder, requester, contact and represented Party are different identities

**Material concern: Yes. High severity; plausible likelihood.** S04 matches agent by login/email; S05 accepts authorAgentId. Manual intake could falsely attribute the statement, confuse the caller with a related donor, or pick the current Party's email for outward mail without review.

**Proposed clause DC06:** “Derive recorded-by Auth user, profile, active tenant membership and eligible Support actor from trusted current identity mappings, never caller author IDs, matching email or editable user_metadata. Keep reported requester/representative description, contact route, relevant Parties and actual recorder separate. Observed phone/name/email is an unverified observation unless its actual owner supplies stronger evidence. Related Parties neither set requester identity nor supply recipients automatically. Profile/employee email reuse or Party merge does not change historical authorship.”

**Proof:** two staff sharing/changed email, forged author ID, auth user ID distinct from profile/agent IDs, expired membership, represented organization, shared contact endpoint, no contact route, Party-only CRM launch.

### F07 — CRM needs a real reverse query, not financial support or capped local filters

**Material concern: Yes. High severity; high likelihood if S07–S11 are reused.** Existing CRM support is giving data and the legacy activity page has a 50-row cap. One-way query-string links and a browser's loaded Support rows cannot satisfy the founder's complete relationship lookup.

**Proposed clause DC07:** “Implement D9's reverse conversation query through the shared Party header/Overview and Communications contracts, preserving the separate financial support summary. Resolve actual canonical Party identity rather than treating donor/profile/person IDs interchangeably. Apply current authorized relevance/correspondence predicates at the database owner, deduplicate originals through current roots, then deterministic keyset pagination. Use indexed tenant/Party/active-association/source predicates and complete eligible scope; no application 2,000, local Data API 1,000 or donor activity 50 snapshot defines the population. Loading, denied, unavailable and no permitted results are distinct; optional Support failure does not blank the CRM record.”

**Proof:** results beyond every batch boundary; a manually recorded request with no native mail appears through its link; all relevant people/households/organizations, not donor-only; overlap/merge dedupe; unavailable dependency is not zero; finance summary unaffected.

### F08 — Zero-mail requests need a truthful sort/display basis

**Material concern: Yes. Medium severity; high likelihood.** D9-R08 orders by last-message occurrence; manual work may otherwise disappear below all email work or get a fake timestamp. S06 uses now fallback and S07 uses updated_at, both contrary to the intended quiet chronology.

**Proposed clause DC08:** “For an original with no qualifying native message, display and order by its trusted staff-recording/creation instant, explicitly labelled Recorded; do not label it Last message. Once real native correspondence exists, use the qualified existing message occurrence semantics. Apply a deterministic current-root composition and tie-break without hiding a manual original. A related link, label, assignment, note edit or query refresh does not invent correspondence or reorder the record as a new request.”

This is a narrow required D9 compatibility amendment, not an invitation to redefine all views as generic last-activity feeds. The root synthesis must resolve the displayed root's contribution basis consistently with D10.

**Proof:** manual-only work among older/newer mail, multiple originals merged/undone, stable pagination across null/native transitions and link edits, backdated reported occurrence distinct from recorded chronology.

### F09 — Manual dates must not forge email targets or retention

**Material concern: Yes. High severity; high likelihood if source dates share existing email fields.** D14-R06 expressly limits reply periods to qualified human email. D17-R04/R05 defines human-content retention clocks and currently needs an explicit fit for a newly recorded brief.

**Proposed clause DC09:** “Record trusted created/recorded/admitted instants separately from staff-reported encounter time and its stated precision/unknown state. Corrections append attributable provenance and never rewrite native correspondence. Manual origin creates no D13 acknowledgement, D14 incoming reply target, provider acceptance or contact credit. Existing D3 work promises/reminders govern follow-up. The new human intake brief is Support-owned purpose content, admitted once under the qualified D17 human-content rule; edits, source-link changes and backdated reported dates do not renew its age. Independently owned encounter content keeps its source policy; no CRM copy or citation is an indefinite retention hold.”

**Proof:** backdated/unknown/invalid occurrence, repeated save/edit, later email starts its own qualified period, manual resolution without fake response time, D17 expiry/source hold/link removal, no provider-delay rebasing.

### F10 — Correction, merge and cancellation can erase or duplicate work

**Material concern: Yes. High severity; plausible likelihood.** Existing cascade deletion in S01/S02 removes history. A broad Undo could delete dependent work or resend after an original is merged; source IDs alone cannot distinguish duplicate intent from two requests.

**Proposed clause DC10:** “Use current D10 original/root identity and D12's qualified unused-tracking correction principles for staff-recorded work. Correction changes the exact currently authorized context with body-free history; it does not restore whole snapshots, forge source mail or erase receipts. Cancel unused tracking is allowed only after checking actual subsequent content, drafts, work/review/assistance, links, merges and admitted/indeterminate external effects. Otherwise preserve work and offer current correction/duplicate merge where genuinely appropriate. Late email to an already-created original follows its qualified route; cancellation cannot silently discard accepted input or resurrect a retired original.”

**Proof:** two independent same-subject requests, repeated same-operation admission, merge/Undo during form review, accidental duplicate with later task/message, cancellation race with first send, old receipt replay after correction, Party unlink without conversation deletion.

### F11 — Manual save must not require or trigger email transport

**Material concern: Yes. High severity; plausible likelihood.** Reusing createInboundConversation or a queued-note pattern can create a false incoming event or acknowledgement; linking a CRM Party can leak its email into recipients. Requiring working Resend for a valid manual source would unnecessarily lose work during a sending outage.

**Proposed clause DC11:** “Saving in an already qualified operational inbox admits Support work only. No P6 message/event, Email Studio publication/preparation, Resend call, D13 confirmation, following inheritance or automatic first-intake assignment is created merely by saving. Use the explicit current D6/D7/D8 handling and D3 work plan. A later Start email thread is separately requested, with reviewed recipient/contactability/context and D4/D12/D23/P17/P6 authority. Existing sending failure does not prevent safe manual capture in an already operational inbox, but D25 candidate/retired inbox states cannot be bypassed. No alternative mailer or bootstrap sender is introduced.”

**Proof:** Save with no email/Party, inactive versus operational inbox, outgoing unavailable, explicit first-thread later, source recipient changed, no automatic confirmation or fake inbound count, no provider request on Create.

### F12 — Privacy follows source material through both surfaces

**Material concern: Yes. High severity; plausible likelihood.** A staff summary may contain restricted care or financial facts even without an attachment. Copying into a “neutral” brief, index, audit or CRM note does not authorize declassification. Archived/expired payload is especially likely to survive in an eager CRM preview.

**Proposed clause DC12:** “Classify the minimal manual brief and typed source references under their actual source/purpose policies. Use D23's qualified rich-text profile where appropriate, not raw HTML as authority. Reference existing sensitive owner material through current authorized projection/release; staff prose is not automatic declassification. CRM list summaries remain minimal and field-qualified, and canonical detail rechecks each content source. Apply D16/D17 withdrawal to known previews/search/exports/cache/realtime before physical purge. Keep audit body-free except the exact separately qualified owner requirement; no call transcript, phone number, full brief or source snippet in routine telemetry.”

**Proof:** restricted source summarized into general inbox, linked Party visible but source denied, allowed record with private note hidden, expired brief while minimal metadata remains, search/export/cache after revocation, source evidence withdrawn during create.

### F13 — Supabase and cache integration must represent durable truth

**Material concern: Yes. High severity; plausible likelihood.** A local collection insertion can look saved in one surface and vanish on reload; an old response can expose tenant/Party data after navigation. Same database does not make multiple REST writes atomic or make policy judgments identical.

**Proposed clause DC13:** “Use existing packages/api command/query ownership and qualified database hooks/read models. Render successful Create only from a reconciled authoritative receipt, retaining permitted draft state across retry. Scope keys/cursors/streams by tenant, Party, actor/current access generation and query semantics. Invalidation improves freshness but does not authorize serving; current read policy gates stale payloads. No app-local Supabase table query, client service key, parallel mutable CRM/Support cache authority or new polling/sync engine is added. A disconnected optional projection recovers from canonical state without reversing a committed request.”

**Proof:** full reload, tenant/Party switch with delayed response, role revocation while drawer open, dropped realtime/cache event, failed secondary refresh after commit, repeated same receipt from both entry surfaces.

### F14 — Mixed-version rollout can recreate false email history

**Material concern: Yes. High severity; certain incompatibility with unchanged S01/S06/S11.** A new writer plus old mapper or generic CRUD can still synthesize times, reject null email or erase lineage. A migration that treats all historical records as verified phone encounters would invent facts.

**Proposed clause DC14:** “Qualify D9/Party/P12 and the manual-origin/null-native readers, protected admission, scoped query and complete correction path before activation. Inventory and fence all core browser grants, legacy fixed-queue modules, generic inserts/updates, seeds/imports, old CRM query links and readers that bypass the contract. Backfill only evidenced identities/origins; ambiguous legacy data remains accountable repair. New-to-old rollback cannot lose a committed manual source, restore broad readers or recreate fake email defaults; retain compatible recovery or roll forward. Ship both Support-first and CRM-first journeys with the same correction/reload behavior.”

**Proof:** N/N-1 readers/writers/restore, legacy donor-ID mismatch, old route bypass, missing source facts, existing mail preserved, both surface gates active together, source/association/audit deletion constraints.

## Complete CRM read map

1. Resolve the requested CRM Party through its current owner, including authorized merge survivor handling. Donor/profile/agent IDs are not interchangeable Party IDs.
2. Build explicit active relevance candidates and independently qualified actual correspondence candidates. Manual work ordinarily enters through its deliberately reviewed relevance link; recording a caller is not correspondence attribution.
3. Apply current joint visibility and field/source constraints before exposing candidates, sorting/counting or projecting root membership. No hidden-row count or recipient inference.
4. Resolve visible original contributions to current D10 roots, preserving their discovery reasons, then deduplicate and keyset-page the complete qualified population. Do not use only the browser's fetched conversations.
5. Overview preserves D9's small unfinished preview and View conversations. The complete Communications view offers unfinished/all history. No-email rows have truthful Recorded chronology; expired content has only currently allowed metadata and an honest unavailable body.
6. Open the same Support detail/API/actions in the existing CRM shell with origin/filters/scroll and permitted draft preserved. Reauthorize; no more-permissive CRM copy of notes, files or send controls.
7. Unlink/retract/merge/revoke/expire changes current discovery or payload according to its exact owner. Source facts and required audit remain; no background bidirectional history synchronization.

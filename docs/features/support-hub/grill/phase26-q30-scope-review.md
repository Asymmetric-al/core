# Q30 — Independent remaining-scope review: Support overview

**13 September 2026. D1–D29 and every adopted amendment are founder-ratified by the latest instruction; the root is recording D29. Q30 is unanswered.** This is researched option selection, not an accepted D30, formal specification, implementation or release-proof claim.

## Recommended next decision

**Should Support Hub provide one ready-made operational overview, keep its existing work views and focused reports separate, or let staff configure an overview from approved report blocks?**

Recommend **A — A focused, ready-made Support overview.** It brings a small current-work summary and useful previews/entry points for the already-ratified reports into one coherent starting place. Staff can see what needs attention and open the exact underlying work/report without assembling a dashboard.

This question is about **overview composition and breadth**. It does not reopen any existing metric formula, source, clock, cohort, label coverage, feedback sampling, attribution, permission or privacy decision. It does not promise new forecasts, labor accounting, staff rankings, donor value scoring or a general BI engine.

Illustrative example, not an observed staffing study: Alex oversees two authorized Support inboxes. Alex wants to check work needing attention now, then open the existing reply-target or feedback report for a recent period. A supplies one useful overview; B requires opening the existing work/report destinations separately; C lets Alex choose and arrange approved report blocks for this recurring review.

## Three actual alternatives

These are competing Phase 26 scopes, not three mandatory modes to build.

| Option                                                           | What staff get                                                                                                                                                                                                                       | Strength                                                                                                                                                                    | Real tradeoff                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — A focused, ready-made Support overview — recommended**     | One consistent overview combining a small current-work summary with useful previews/links to the already-approved target, reply-time, label and feedback reports. Simple qualified scope controls and direct drilldowns remain.      | Useful immediately, with no dashboard setup. A common layout helps a team review the same questions and keeps the full focused reports available for depth.                 | The standard composition will not match every person's preferences. It needs disciplined selection and clear separation of current snapshots from historical report periods.                                                                                |
| **B — Work views and focused reports, without another overview** | Staff use the existing authorized inbox/work views and already-ratified reports directly. No additional consolidated overview is added.                                                                                              | Smallest additional interface and maintenance scope. Strong for a small team that already knows which view or report answers each question.                                 | Cross-cutting review takes more navigation and mental comparison. This retains all previously promised reports; it does not remove timing, labels, feedback or required recovery visibility.                                                                |
| **C — A configurable overview using approved report blocks**     | Start with a useful standard composition, then choose, show/hide and arrange bounded approved blocks through qualified shared reporting capabilities. Each block retains its source-defined formula, audience, period and drilldown. | Strongest for teams whose different responsibilities require different recurring summaries. It can reduce irrelevant information without inventing custom data or formulas. | Adds saved composition, configuration/recovery and ongoing compatibility work. The shared report/composition owner must be qualified; it cannot be an app-local SQL/formula builder, a second BI platform or a way to hide mandatory safety/work attention. |

**Why A remains best against strong C:** C can be clean and valuable; it is not inherently an enterprise mess. Its extra value depends on actual repeated differences in what staff need to review. That demand has not been established. A supplies a useful common composition while retaining direct access to focused reports. B is preferable when even that additional summary does not reduce meaningful work. Neither argument justifies weakening existing report correctness or current-work discovery.

The question should show A/B/C directly in the chat, including these differences, rather than rely on a linked artifact or an options widget alone. C must not be misrepresented as requiring arbitrary metrics or replacing standard reports.

## Shared reporting owner: actual intended boundary

The [Phase 33 roadmap, lines 3572–3615](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L3572) names **Reporting & BI / Report Studio** as the shared report owner: standard library first; one semantic definition of metrics/dimensions/joins/access consumed by dashboards; then constrained custom/saved reports and independently governed scheduled runs. It explicitly calls this future work needing a PRD. That is intended ownership, not an available configurable-dashboard service.

Consequences for Q30:

- Support owns the operational facts and each accepted Support metric. A standard overview can be a bounded consumer over their qualified read contracts without waiting for an entire generic reporting platform.
- C must use or explicitly qualify the appropriate shared report/composition capability. Its promise is bounded approved blocks; it does not authorize arbitrary source joins, SQL, formulas or a Support-only semantic layer.
- The same source metric must retain one definition wherever it appears. A new summary card cannot average ratios, change cohort dates, collapse unknowns or grant access unavailable in the underlying report.
- Scheduling/email delivery and share/export authority are separate P33/P17/P6 concerns. No scheduled digest, public dashboard, new export or permission grant is silently bundled into A or C.

## Current primary product comparisons

Official sources were retrieved on **13 September 2026**. Vendor behavior is comparison evidence, not authority over the ratified Asym semantics or proof of nonprofit demand.

- **Help Scout demonstrates a useful fixed-report product.** Its [Understanding Reports](https://docs.helpscout.com/article/385-reports), updated 31 July 2025, documents seven report types, definitions and conversation drilldowns. It expressly says in-app custom calculations/custom datasets are not offered. This supports B as credible and A as a fixed composition; it does not mean Asym should copy its metrics, individual happiness attribution or refresh delay.
- **Front distinguishes current work from historical analytics.** [Navigating Analytics](https://help.front.com/en/articles/2115), edited 18 August 2026, documents consistent report controls and an explicit freshness statement; its Live dashboard is a distinct real-time exception. This supports visible current-versus-period semantics rather than applying one date filter to all blocks. Front's role/workspace permissions and metric meanings do not map automatically to Asym.
- **Bounded configurable composition is a real larger alternative.** Front's [custom report dashboard](https://help.front.com/en/articles/3683008) is explicitly **open beta**, edited 15 May 2026, and documented for its latest Enterprise plan. It supports choosing metrics/charts and retains its own filters/layout; sharing and scheduled email are not supported there at the documented stage. This supports C's controlled composition and its independent configuration lifecycle, not a claim that Front's beta is a universal proven best practice or that Asym needs its numerical limits/plan structure.

The strongest comparisons are enough to establish the fork. Forcing every help-desk vendor into this narrow question would add names without deciding which Asym work actually needs an overview.

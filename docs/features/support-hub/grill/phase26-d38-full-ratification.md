## Exact recorded decision

Support automatically saves each staff member's meaningful, unfinished **new Internal note** as a private, source-qualified draft in Asym's Supabase Postgres, using the same qualified Support draft capability and My drafts destination as external replies. Reply and Internal note are distinct immutable draft purposes with independent content, identity and lifecycle. The list labels their purpose clearly and resumes the exact draft in the existing conversation composer. Saving is quiet and non-publishing; only deliberate, currently authorized **Add note** atomically admits the canonical note, its required initial history and asset relationships, consumes the exact draft generation, records the operation result and durably records any required downstream attention. Current source/tenant/author authorization, conditional saves, truthful acknowledgments, safe navigation, privacy/retention and original-operation recovery apply throughout. D35 corrections to already-posted notes remain local and unchanged. R01–R26 and all companion contracts form the complete accepted decision.

The accepted journey is **Internal note → write → save quietly → leave → My drafts → resume the exact note → Add note**. The strongest alternative was deliberate Save note draft using the same finder; it offered explicit retention control but added a recurring step. Session-only notes were the smaller persistence alternative. Neither becomes another setting alongside the selected policy.

## Accepted UX and content behavior

- Extend the existing stable My drafts entry and combined eligible population across accessible inboxes and ordinary work states. Keep title-only search, Inbox filtering, Refresh, keyset pagination and no body/mention/file previews, count badge, additional type filter, new destination or forced landing.
- Retain **20 initial rows and at most 50 per request** over the combined population, with no total draft cap or recent-only truncation. Sort by last accepted meaningful author edit and stable identity; reads/no-ops/cleanup do not move work to the top. Preserve active row, focus and list-return context.
- Opening/focusing/restoring defaults creates no phantom draft. Meaningful author changes to qualified content, mentions, wording or file selection may create one. Valid incomplete work can save. Clearing an existing note does not silently discard it.
- Reuse **750 ms quiet / 5-second eligible-continuous-input attempt** scheduling, with one unresolved save per controller and coalesced newer work. Foreground/network/authorization/schema/IME conditions remain explicit. These are attempt targets, not acknowledgment latency or crash guarantees. Save now and Retry save remain secondary recovery actions.
- Saved means the complete newest eligible bundle is durably acknowledged. A stale acknowledgment or hydration callback cannot replace newer text or affect another source/purpose. Reply and Note preserve independent content, files, provenance and lifecycle. The Note profile does not inherit external audience/signature/preparation fields or D24 staged Reply work plans.
- The composer states **Internal note** and **Private until you select Add note**. Mention insertion, save, restore and navigation are quiet. Add note permits meaningful canonical content or at least one ready, clean, authorized selected attachment. No dummy prose is required, and no selected unfinished or unsafe file can silently disappear during posting.
- Resume directly in the same source-qualified composer, with no Reply flash, blank replacement editor or automatic CRM-address substitution. Show source/internal purpose before opening the mobile keyboard. Preserve same-session list context; cross-device recovery promises acknowledged content/context, not exact caret coordinates.

## Accepted private ownership, sources and recovery

There is at most one active draft per trusted tenant, real staff owner, immutable original conversation and purpose. A Reply and a new Note can coexist. Original-source drafts survive merge without merging, rehoming, copying or deduplicating by current root, email, assignee or CRM Party. Each completed/discarded lifecycle stays terminal; later new work gets its own identity/generation.

The original private slot is **not** the publication source. D10-R14 governs general notes in combined work: the actual note attaches to the then-current continuing original, unless an existing qualified source-specific action says otherwise. Changed destination/topology/internal audience requires targeted current review before Add note, not a new selector for every ordinary note. A B-origin draft remains a B private slot after B joins A; a reviewed general note posts under A. Post-before-Undo and Undo-before-post preserve their different lawful outcomes.

Trusted server context derives the actual actor/profile, tenant and applicable membership. UUID identity relationships and TEXT Support source IDs remain distinct. Every read/save/discard/post operation checks its own current authority. Losing only Post permission does not hide otherwise lawful private read/custody; it does not grant editing or posting rights. Losing source/privacy authority still withholds or clears forbidden bodies, metadata and Undo. Normal administrator/assignee/follower/CRM relationship status never grants access to another author's private draft; exceptional records custody remains separately authorized and audited.

One qualified `packages/api` command and database transaction/RPC owns a complete save with expected revision, current source/privacy/lifecycle guards and an exact operation result. Same-content saves do not bump meaningful revision/recency. Concurrent tabs cannot blindly overwrite. Unknown results recover the original immutable operation; absent lookup or canceled HTTP is not proof of nonacceptance while late admission remains possible. No new key, automatic content merge or browser archive is a repair strategy.

Mode switching is frictionless when both candidates/controllers stay safely retained. Navigation that would destroy dirty work in **either** purpose flushes settled editor/IME state and includes local pending-file consequences in the same proportional guard. Routine confirmed save continues without confirmation. An unknown save permits informed Leave without claiming cancellation; retain the scoped body-free operation handle. A saved manifest cannot recreate browser File bytes. No offline body/file vault or guaranteed final-keystroke crash recovery is introduced.

Discard uses one purpose-specific confirmation and conditionally terminates the exact reviewed draft revision/generation. It does not delete the conversation, a posted note, a separate Reply or independently owned files. Stale saves cannot resurrect it. A possibly admitted Add note must be recovered, not canceled by Discard. No bulk discard, hidden trash, Undo timer or draft-transfer product is added.

## Add note, attention and Email Studio seam

Fast writing followed by Add note needs no separate Save click or debounce wait. The command uses the newest settled canonical candidate and a known/recovered base. **One authoritative database transaction** requalifies actor/source/destination/purpose/privacy and post readiness, admits the native-human note and initial D35 history, admits selected asset relationships, consumes the exact draft generation, records the immutable result and commits required source/attention obligations. Database failure rolls back the whole admission. Provider/Storage I/O is not placed inside that transaction to simulate distributed atomicity.

Unknown Post remains the original operation under recovery; it does not become another editable draft or fresh Add note. A committed note remains admitted and the draft remains terminal when later attention, projection or asset cleanup fails. Those effects recover through their existing durable obligations. Legitimate separate notes are not collapsed by content similarity. Posting does not consume a Reply plan or prove a CRM/giving action completed.

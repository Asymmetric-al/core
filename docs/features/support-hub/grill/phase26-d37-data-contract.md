## Current primary technical evidence

Reviewed Supabase [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [column privileges](https://supabase.com/docs/guides/database/postgres/column-level-security), [database functions](https://supabase.com/docs/guides/database/functions), and [Storage access control](https://supabase.com/docs/guides/storage/security/access-control) on 14 September 2026. Grants and row predicates are distinct, service role bypasses RLS, and views/functions/storage need their own access qualification. An UPDATE needs effective old-row and allowed-result predicates; missing explicit WITH CHECK can inherit USING, so absence of syntax alone is not a vulnerability finding. Here the actual broad predicates are the concern. These sources support mechanisms, not proof that Asym's intended policies run correctly.

## Exact proposed contract

### C01 — Finder identity and scope

“My drafts is a built-in private Support view over the current actor's saved external Reply drafts in the currently selected tenant. It includes all currently accessible Support inboxes and all D3 work statuses by default. It is not an assignee queue, shared saved-view definition, contact history, second authoring surface, shared draft store or a new default landing page. Do not create a draft by merely opening the composer or adding its automatic baseline signature.”

Use current permissions for every row and field. No other worker's draft, body, count or existence is discoverable by assignment, following, D34 awareness, inbox membership, CRM relation, ordinary admin role or a query guessed from a URL. Separately qualified infrastructure custody is not a product administrator's My drafts browsing capability.

### C02 — One source-owned draft and cardinality

“Maintain one active external Reply draft per tenant, real profile owner and original Support source. Its stable draft identity remains the same through saves, explicit D2 retargeting and cross-surface entry. A merged continuing conversation is a navigation destination, not draft identity: distinct originals may yield distinct drafts in one combined reader. Merge/Undo never merges bodies, transfers ownership or deduplicates by root, subject or email.”

The logical active key includes fixed `purpose=external_reply`; do not expose a generic draft-type framework merely to store that fact. Once a draft is sent/admitted or deliberately discarded, a subsequent new reply gets a new draft identity. Persist the original identity even if the displayed conversation title/root changes. Two concurrent first saves must resolve to one active draft or a real conflict, never two rows or silent overwrite of different documents. Body equality alone does not establish same human intent.

**Explicit cross-original retargeting is reconciled with D2/D10 as follows.** “The draft's original is its immutable private working-slot origin, not an instruction to file an eventual reply under that origin. An explicit D2 target change within the currently authorized combined context preserves the same draft, owner, body and protected dependencies, rechecks the actual target/audience and reviews changed context. The selected target's original owns any admitted reply, as D10 requires. Thus a draft begun at A and deliberately targeted to a message from B is admitted once at B and handled through B's then-current qualified root. Do not rehome the private slot, combine it with another draft or rewrite original message affinity.”

“Different original-bound drafts may deliberately point to the same target; their separate existence is not duplicate-send authority. Each keeps its own content and identity and the existing component-wide send-collision/review guard applies. Reply navigation that requests an existing draft resumes that exact private draft; it never silently imports another draft merely because targets match. If topology changes separate the private origin and target, preserve writing but require explicit current destination/context review before resuming Send against the target's current handling component. Revalidate necessary origin, target, content and actual current component authority; never transparently act on the stale former group. D16/D17 source dependencies remain exact, and native-reply retention admission belongs to the selected target original, not the finder slot.”

This is an application of D10-R07, its lifecycle example “Reply referencing an original B message while B is handled in A,” and D10-P13/P17. It avoids a new copy/transfer/replace-draft workflow. The implementation must retain two distinguishable references where they differ; a single ambiguous `conversation_id` must not silently stand for private draft origin, reply source and current root.

### C03 — Actual types and trusted actor

“Use UUID tenant/profile/auth/membership endpoints and TEXT original conversation/message/agent endpoints where those are the actual owning keys. A new draft ID may use the qualified source-owned ID convention, but changing existing Support TEXT IDs to UUID is not part of this decision. Derive tenant, real actor/profile, current selected acting scope, applicable active membership and attribution from trusted shared server context. Do not accept owner, author, role, approval, admitted-send or tenant-control fields from the caller.”

The durable owner is the qualified real profile, not an email address, current assignee, CRM Party, selected directory agent or transient membership row. Current membership authorizes use; it does not transfer ownership. Tenant/profile consistency must be proven through the platform's actual membership mapping, not `profiles.tenant_id` equality that accidentally excludes legitimate multi-tenant membership. Where Support agent representation is necessary, resolve the current qualified explicit profile/auth mapping and reject ambiguous legacy mappings. Shared email or email reuse proves neither identity nor authority.

Tenant, owner profile, original source, draft ID, purpose and schema/head revision are non-null on qualified active drafts. A reply-target email reference may be null for an explicitly qualified first response to a phone/form-origin source; null is not permission to guess from current contact data. Conditional checks forbid email-reply states that lack their required target. Use positive bounded revision values and trusted UTC timestamps; terminal facts cannot revert to editable through a generic update. Deleting a profile/original/inbox must not incidentally cascade away required terminal/send/source evidence or transfer a body to a new owner. Qualified offboarding performs actual custody/cleanup before any permitted endpoint retirement.

### C04 — Canonical persisted unit

“Save the draft's canonical document and compatible schema/profile version, original/target references, explicit audience and its review generation, governed signature state, attachment manifest, quote/source dependencies, staged work plan and draft revision as one atomic effect. The command never reports Saved after a body-only write. Optional local cursor, viewport and picker state are presentation aids rather than mail authority.”

Source/body/preparation objects remain distinct. Derived HTML/plain text may be caches under exact canonical generation, not independently writable truth. Reference IDs must use same-tenant foreign keys to actual owning endpoints; polymorphic strings, unchecked JSON claims or cross-tenant foreign keys by ID alone do not establish relationships. Closed schema validation and size/depth/content rules protect canonical JSON. Do not put repeated full snapshots in durable audit/operation receipts.

### C05 — Conditional save, no-op and unknown result

“Each accepted save conditions on the expected draft revision and binds a stable operation identity to the exact normalized semantic command. Retrying that identity returns its original outcome or conflicts if its meaning changed. An identical canonical no-op changes neither draft revision nor human-updated ordering time, but its resolved operation cannot later be reused to change content. Stale saves cannot overwrite newer work, a terminal draft or current source restrictions.”

Coalesce local editor changes with one in-flight save and the latest waiting canonical state, keeping the previously confirmed revision distinct from local unsaved text. Only a confirmed server outcome earns Saved. A request timeout yields save result unknown, not certain failure or permission to insert another draft. Recover the original operation before advancing the expected revision. Minimal body-free, scope-bound operation handles survive navigation and reconnect; they are not bearer permissions and must not carry recipients/body in URL or analytics.

The UI can retain newer safe local text while reconciling an older accepted revision. A server acceptance must not overwrite the newer editor generation. Record source/draft operation results with the existing owner mechanism and a qualified finite replay horizon; do not invent a per-keystroke event store.

### C06 — Resume and conflict

“Opening a row resolves the same canonical draft under current owner/source authority, then restores its exact saved composition context. Loading or failed fetches are not absence and must not create a new empty draft. Late load/save/refetch responses for another actor, tenant, original, draft or editor generation cannot hydrate the current editor. An older browser tab cannot autosave over a newer confirmed revision.”

On conflict preserve independently safe local writing, show the latest saved state for deliberate review and use the existing revision reconciliation rather than automatic last-write-wins, collaborative merging or forced lease/takeover. Opening the same draft elsewhere is allowed; ownership is not a locking protocol. Retargeting/new input/recipient changes still use D2/D4 review. Reopening a Resolved conversation through the finder does not reopen work, reset timers, assign/follow, execute the staged plan or imply successful domain action.

A missing list row is not evidence that a save failed, a send succeeded or a discard completed. Reconcile the original operation through its current authorized typed result. Exact pending recovery may be shown separately from ordinary editable drafts using the existing recovery treatment; after known accepted admission, preserve only the permitted result/continuation needed to explain the actual state. Discovery failure cannot mint replacement send authority.

### C07 — Save and Send are distinct boundaries

“A private saved draft remains unpublished writing. Deliberate Send freezes the exact reviewed draft revision through P17 preparation, then Support atomically admits the source reply, staged local work effect and P6 dispatch intent according to D4. Accepted admission consumes that draft exactly once and removes its ordinary resumable entry; provider delivery remains a separate factual status.”

Race save/discard against preparation/admission by expected generation and the shared owner fences. A stale autosave cannot recreate a consumed draft. A lost send-admission response keeps the exact operation in recovery and cannot advertise an ordinary Send again path. An admitted queued, failed, bounced, delivered or indeterminate envelope does not reappear as an editable draft merely because the provider has not confirmed delivery. A definite pre-admission rejection may leave the same draft editable; an uncertain rejection cannot. New writing after completed admission is a new draft, and never implicit retry of the consumed one.

### C08 — Discard is one guarded local-source effect

“Offer explicit Discard draft for a saved draft with one plain-language confirmation. Acceptance conditionally ends the exact current draft generation, withdraws its draft-owned body/reference grants and ends its ordinary finder entry. Retain only qualified body-free terminal/replay evidence to reject late saves and replayed creates. Do not create a trash mailbox, hidden retained body, timer-based restore service, duplicate message or normal communication event.”

A newer saved revision or send admission wins a race by conflict rather than silently discarding work or canceling a submitted envelope. An unknown discard result reconciles that operation before the client retries or clears recoverable safe local work. Draft-owned staged uploads enter the existing reference-aware cleanup obligation; originals/shared authorized blobs and independent admitted-send material are not deleted by a draft cascade. Actual content destruction remains D16/D17/owner governed, so the ordinary UI does not claim it erased every backup or shared object immediately.

Use the same already-scoped operation identity for first create/save. After discard, replay of the old create is terminal even though the active uniqueness slot is free. A deliberate new composer has a new draft intent. Removing all editable text from an existing saved draft is a user change, not automatic deletion: preserve intentional audience/attachment/quote/work-plan state until explicit discard. No meaningful initial change means no durable draft.

### C09 — Private read query and pagination

“List only permitted safe metadata: stable draft/source reference, current permitted conversation title, permitted requester label if available, inbox, human saved-update time and typed actionable state. Do not fetch the draft document, private recipient list, filenames or quote bodies to render the finder. Private bodies remain excluded from D22 ordinary search and general timeline/CRM read projections.”

The final finder searches only qualified current conversation titles, with a separate explicit inbox filter; permitted requester context is display-only here. Do not search private draft bodies, private recipients or restricted CRM fields. Resolve complete current authorization and effective filters before pagination; use deterministic ordering by actual accepted human draft update and stable draft ID tie-break. Do not use generic `updated_at` changed by cleanup/retry/refetch, whole-tenant message loading, pre-filter limits, recent-only cutoff or client filtering of hidden rows. Use keyset pagination and relevant `(tenant,owner,lifecycle,saved_at,id)` and tenant/source indexes qualified against actual plans. No initial sidebar count is required. Any later count must use the same authorized semantics and count drafts, not merged roots or Open work.

Refreshing results is not an instruction to move focus, selected draft, route or scroll. A visible filter/empty state must distinguish no saved drafts, no matching drafts, loading, access loss and failed loading. No phantom unavailable row should reveal a draft/source the actor is no longer allowed to discover.

### C10 — Effective database and Storage closure

“Canonical draft writes remain commands in `packages/api`; thin app routes and qualified `packages/database` read hooks reuse that boundary. No anonymous/raw authenticated DML may alter canonical private body, owner, tenant, original, lifecycle, source dependencies, revision or accepted-send evidence. Enable appropriate RLS, restrict grants and function execution, and prove private owner/current-source predicates for every exposed read.”

Do not overlay private semantics on current broad `support_messages` policies without retiring the conflicting paths. A source-owned draft relation is the clean minimal direction; if physical reuse is justified later, equal isolation must be demonstrated across raw Data API, timeline, search, export, Realtime and attachment routes, with direct broad writes closed. Invoker views obey RLS; any definer/function/service role path needs explicit narrow authority, fixed trusted search_path and tested grants. Effective USING and WITH CHECK must prevent transforming allowed rows into another tenant/owner/source/published-message state. Attachments and signed delivery paths need independent current draft-owner/source authority; a private row pointing at a public URL is not private.

### C11 — Privacy, source lifetime and departure

“Apply D16/D17 source restriction/expiry to draft-derived content, metadata, recipients, cached representations, editor undo/restoration and staged attachments. Draft save/open/autosave is not a native admission, real work purpose or retention renewal. Bind the draft content inventory to its original Support source generation and owner-qualified lifetime; use the existing policy and oldest-content review rather than a new indefinite private archive or a seven-day prepared-material timer.”

D4's seven-day maximum human-reply preparation is not a draft lifetime. Independently safe authored work may be retained only under its own qualified draft purpose; never keep restricted copies through a generic preserve-draft promise. When separable, remove affected source-derived material and preserve safe work for current review; when mapping is uncertain, affected material remains unavailable until clean review. Do not silently rewrite and send a cleaned sealed message.

Loss of membership/source access suppresses finder rows and future reads/writes immediately at the authority boundary, even if cached lists or workers lag. Reauthorization can restore only still-retained currently lawful material to the same durable person, not resurrect erased content. Departure or email reassignment does not transfer a private draft to an administrator/assignee/replacement user. Use actual offboarding/privacy custody; no new admin-inbox exception. Restore source stops and terminal command fences before restoring data or accepting an older browser/client.

### C12 — CRM and Email Studio seam

“Support and the CRM's authorized Support entry resume the same private canonical draft and original source. Preserve the caller's CRM record/list/scroll return context; the CRM record anchor cannot silently broaden because a draft list covers other inboxes. Deliberate Open in Support Hub may broaden navigation as already allowed, with the previous CRM return preserved. No draft discovery/save/discard creates a CRM note, Activity, contact, address update, ownership transfer, follow, assignment or giving/receipt/refund result.”

Support owns human private draft persistence, audience/source checks and admission. Email Studio/P17 owns governed reusable content/schema/signature/presentation and complete immutable preparation; it does not own a second human draft copy. P6 owns actual sealed dispatch/reconciliation and per-recipient evidence. Listing, saving or resuming creates no P17 delivery material, calls no Resend draft/send API, publishes no template and does not turn donor correspondence into a system-message catalog entry. D35 posted-note editing and unsent new-note working state remain separate.

### C13 — Outage and navigation

“Before app-controlled navigation would discard dirty writing, complete its pending qualified save or retain scoped working state and expose a recoverable failure. Do not claim server persistence from an optimistic cache, unload beacon, localStorage or closed-tab event. A browser crash or network outage before server acknowledgement can lose unconfirmed changes; Saved refers only to the confirmed canonical revision.”

A status lookup that remains unknown must not trap navigation: offer Stay or explicit Leave with the earlier-save-may-finish/latest-unacknowledged-changes-may-be-lost explanation, retaining the original scoped operation handle. Leaving proves neither cancellation nor nonacceptance. Local-only unfinished upload bytes also need the shared navigation guard even when text is saved; keep a qualified transfer alive, wait or explicitly abandon that attachment without claiming the manifest can restore it. The existing automatic-save cadence may reduce exposure, but it is not an offline guarantee. No durable browser body store/offline outbox or hidden pending send is introduced. Cancel in-flight fetches and reject obsolete results on tenant/account change. Clear or make inaccessible sensitive state including caches, editor undo and mounted content when scope or authorization changes. Same-user tenant switches need explicit handling, not only logout cleanup. Ordinary drafting continues when the finder alone is down; ordinary CRM work continues when Support is unavailable.

### C14 — Migration, activation and bounded proof

“Qualify owner/source/auth mapping, canonical draft transaction, compatibility profile, private read projection, source restriction/retention inventory and all old writers/readers before enabling My drafts. Never backfill owner from JSON author/email, current assignee or first agent, and never invent a missing original/audience from current CRM context. Proven legacy drafts can migrate idempotently with their original meaning; unknown authorship/source remains restricted reconciliation with an accountable owner and finite existing custody obligation.”

Multiple legacy draft rows cannot be silently collapsed as if they were revisions; preserve evidence and require qualified reconciliation. Migrate while inactive; fingerprint source inputs and persist mapping exactly once, preserve queued/sent facts, make old incompatible writers fail closed and verify rollback/new-code-old-schema/old-code-new-schema behavior. A feature stop disables new finder/save behavior as appropriate without deleting drafts, reopening broad readers or disabling accepted-send recovery. After new canonical data exists, roll forward rather than roll back to a serializer that strips unknown quote/signature nodes. No unsupported source or draft is silently parsed, stripped and autosaved.

## Minimal logical data footprint

This is a proposed implementation shape to validate, not new SQL or a mandate for a particular table name. One private draft relation with typed immutable tenant/owner/original/purpose identity, mutable canonical current head, closed lifecycle and revision; the existing draft-bound file/reference/dependency records; and the existing command-result/terminal evidence mechanism. Every extra persisted projection has a declared source and cleanup owner. No dedicated draft version-history product, global workflow store, Yjs document service or recipient synchronization database is justified.

Meaningful states are: locally changed but not acknowledged; saving; confirmed saved; definite save failure; uncertain save outcome; revision conflict; awaiting exact send admission result; consumed by accepted send; deliberately discarded; restricted/expired. The first six include local transport/presentation states and need not all be SQL enum values. Source availability is an orthogonal authoritative condition; it is not encoded merely by hiding the UI. Closed server lifecycle need only represent the true durable source states and immutable operation relationships.

## Required falsifiable proof

These are release requirements, **not executed runtime evidence**.

1. Same human saves/restores the same canonical reply through Support and CRM on two authenticated devices; target/audience/signature/quote dependencies/files/staged plan preserve meaning and there is one active draft.
2. Two owners in one tenant and the same owner in two tenants cannot read each other's rows, count, existence, body, attachments, commands or source metadata through UI, raw Data API, views, RPCs, service commands, caches, logs, export or Realtime.
3. Caller owner/author/tenant/membership/role/accepted-send input is rejected or ignored; ambiguous agent mapping and email reuse never change owner. User/profile IDs deliberately differ in fixtures where permitted by the platform mapping contract; membership IDs differ from both.
4. Two first saves with distinct documents race: one active row, no silent lost work. Retry exact operation returns original result; altered payload under same identity conflicts. Save no-op does not reorder the list.
5. Save writes canonical body, references and manifest atomically; inject failure before and after each write boundary. No false Saved after partial success. Unknown outcome reconciles without new insertion.
6. Save/discard/send race and stale tab autosave: no resurrection, erased newer work, duplicated message or new delivery. Accepted admission consumes exactly its reviewed draft revision; provider queued/unknown/failed remains exact original effect recovery.
7. D10 merge/Undo preserves original-bound distinct drafts, exact target and ownership. Similar subject/shared email/represented organization never combines drafts or grants authority.
   Start draft at A, explicitly target B inside their combined context, then send: one B-affine admitted reply consumes the exact A-slot draft without altering a separate B-slot draft. Undo before admission preserves text and requires current B-destination/component review; event-first and Undo-first each produce one truthful source/work outcome. No reply is filed at A merely because that was the private finder slot.
8. D16 restriction/D17 expiry crosses save, restore, undo, list/cache, preparation and dispatch barriers. Current restriction wins before future use without waiting for cleanup. Accepted/in-flight facts remain truthful; no old-body rehydration.
9. Closed/Waiting/Open/Snoozed originals remain discoverable while eligible, without reopening, following, resolution changes, fake service metrics or last-contact updates. At least two distinct original drafts under one root remain distinguishable.
10. Metadata-only complete paged query works beyond one page, stable timestamp ties, permission changes between pages, Unicode and meaningful empty/error cases. No body download/index, all-tenant scan, 2,000-row prefilter or misleading exact count.
11. Composition navigation/IME/low-bandwidth/error preserves newer safe local input and cannot apply an old result to another editor. Unknown save and unknown send are visibly different; click, keyboard and retry use one guarded command.
12. Private attachments never become public through their URL or selected row. Discard cleans only draft-owned occurrences when safe, preserving original/shared files and independently required send material.
13. Legacy unqualified rows remain contained, qualified migration is replay-safe, old writers are fenced and restoration applies source stops/terminal effects before old content. No new synthetic authorship or refreshed lifetime.
14. Measure actual query/save/restore behavior with recorded source sizes, draft counts, tenants, concurrency, network and versions. Test exact admitted maxima and one-unit-over; label engineering targets separately from observed p50/p95. The user-facing interface remains usable while large unrelated histories exist.

## Independent recommendation to parent

Keep the private My drafts direction. The material changes are the already-needed canonical persistence/author boundary, complete private discovery, deterministic save/recovery and restoration under current source authority. Accept a modest autosave plus manual recovery implementation only with truthful acknowledged state and conditional writes. Prefer the parent's single confirmation for permanent discard over Undo that would introduce hidden body custody. Metadata-only rows and no sidebar count are deliberate simplifications; expose useful source/title/inbox/time/state without fetching writing into every list.

Do not claim current source is production-safe because it already has tenant filters, or claim those filters are absent. The evidence demonstrates insufficient private-owner and atomic-draft semantics, not a proved live cross-tenant exploit. The required permanent path must qualify actual grants/RLS/API/Storage/browser outcomes before activation.

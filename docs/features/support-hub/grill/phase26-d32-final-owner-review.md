## Material findings and resolution

**F01 — Expired cache generation versus stable input key. High severity, plausible.** The initial data definition tied a generation to the stable tenant/source/version/profile/projection tuple while promising regeneration after a fixed24-hour expiry. Without an explicit distinction, a retry could stay trapped on the expired Ready result or mutate its deadline. The correction requires a stable input reuse key and separate immutable technical generation identity: expiry retires the old generation; a later deliberate eligible admission creates one new generation; concurrent opens coalesce it; old receipts/deadlines and source retention never change.

**Verified resolved in actual main R17, the data contract's logical-record explanation and proof P22.** The companion propagation has been read directly. This changes lifecycle precision, not product scope, source identity or a new workflow engine.

**F02 — Tentative-to-Ready custody transfer. High severity, plausible; corroborates the independent data reviewer.** Accepted output initially belongs to15-minute tentative custody. If Ready promotion only changes status, the tentative sweeper can later delete a valid24-hour rendition. Promotion must atomically transfer the accepted output's disposal authority to Ready/source-bounded custody while leaving scratch and unpromoted output under the original15-minute deadline. A concurrent sweeper must recheck current custody and cannot delete a promoted output under its former classification. This is a required clarification of R07/R17 and the existing staging/promotion proof, not a longer retention policy.

**Verified resolved in actual main R07, data request step5 and proof P32.** Accepted output transfers atomically to Ready/source-bounded custody. Conditional deletion claims forbid subsequent promotion; stale tentative cleanup cannot delete promoted bytes; object keys are never reused across generations. Scratch and unpromoted output retain the original15-minute bound. No runtime repair or test was performed.

The data review also identified a possible false proof claim about detecting stale spreadsheet caches. **Actual P09 is already corrected:** a deliberately stale fixture displays its exact saved value with the not-recalculated notice; the implementation does not infer arbitrary source freshness. No additional owner finding remains on this point.

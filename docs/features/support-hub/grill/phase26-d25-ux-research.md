# D25 independent UX research — equal inbox setup paths and complete maintenance

Researched 12 September 2026. Founder choice: **C — Present both email setup paths equally**. This independent research develops the consequences of that choice for the root's adversarial review. It does not mark proposed details ratified or claim implementation tests passed. No production mailbox, DNS, message, provider, GitHub or runtime change was made.

**Recommendation: accept C with required setup and maintenance safeguards.** Two plain-language starting choices can feed one coherent setup experience. The hard part is distinguishing saved configuration, actual external changes, verified evidence and live Support handling without asking a tenant to understand the architecture. The design below makes those differences visible only when they affect the next action.

## Shared first screen and navigation

Use **Set up inbox email** in the existing Support inbox-settings context. Keep the tenant and intended inbox visible. Two equally prominent selectable cards, no preselected card and no recommendation badge:

- **Use an existing address** — “Keep the address people already use. We'll guide you through forwarding its new mail into Support.”
- **Create a dedicated address** — “Use a new address for this inbox on a domain your organization controls.”

A short note can say “Both options use your organization's email identity.” Do not label one Advanced or force a provider acronym choice first. “Create” means configure the qualified address; it is not domain registration, automatic mailbox provisioning at Microsoft/Google, or permission to publish an Asym-domain address. Preserving an existing public address does **not** promise that the From header is identical: P17's fixed transactional domain/default sender remains authoritative. For example, the public incoming and Reply-To address may be `donorcare@example.org` while the qualified From address uses `donorcare@mail.example.org`. Preview **Public incoming address**, **From identity** and **Reply destination** separately, with the D23 signature below them. Adding a receiving facet does not silently replace the tenant's outbound domain, default sender or default reply destination.

After selection, use the same four progress groups: **Address**, **Connect**, **Test**, **Finish**. Completed groups are revisitable; the selected path changes only the necessary Connect instructions. Steps show their next actionable task rather than a page-long checklist. Save changes explicitly; moving Back navigates and does not undo a completed external action. Show “Saved” only after durable acknowledgment. A single pending setup can be resumed from its inbox settings by an eligible administrator; do not introduce personal competing setups that each believe they control the active route.

The initial choice should not be asked again when resuming. An explicit **Change setup path** action preserves reusable inbox details and warns only if issued instructions/proof or external work would become obsolete. An active inbox uses a replacement flow, not this initial-path toggle.

## Journey A — use an existing address

1. **Identify the intended shared address.** Enter public Support email and confirm the target inbox. If necessary, name the inbox in a separate clearly labeled field. Show the actual public address plainly, without truncating the domain on mobile. Explain that only this Support address's eligible new mail should be routed here. Do not encourage forwarding an employee's whole mailbox or a general mailbox carrying unrelated protected work.
2. **Resolve ownership and compatibility through the existing owners.** Check syntax, current tenant route conflicts and qualified sender/receiving prerequisites. Distinguish “This address is already connected to an inbox you can manage” from a nondisclosing “This address cannot be connected here.” If a different inbox is already the permitted owner, open its settings or an explicit qualified change flow; do not create duplicates. Possession of a confirmation email proves only its defined address-control fact, never tenant membership or CRM identity. Sending-domain readiness is a separate owner fact.
3. **Show a specific forwarding destination and provider instructions.** The panel says “Forward mail sent to [public address] to [internal destination].” Each value has its own copy button and label. Show selected Google Workspace/Microsoft365/other-provider guidance only as navigation aids; autodetection is a suggestion, not authority. Instructions are produced from the current candidate configuration and contain no secret/API key. The target is not shown as the address to publish to donors.
4. **Complete the provider's confirmation when applicable.** Present **Email provider confirmation** beside the Connect step, with waiting, received or action-needed status. A qualified expected setup message can be inspected by authorized setup operators through a safe, restricted presentation. If its method uses a code, provide code copy without raw HTML; if it requires a provider action, show the actual external destination and require deliberate navigation. No preview fetch or automatic link visit may authorize forwarding. Not every provider uses confirmation; don't make Microsoft administrators hunt for a Gmail-specific message.
5. **Return to the provider and finish enabling the rule.** The UI explicitly tells a Gmail user to return and enable/save forwarding after confirming the target. The user's “I've updated forwarding” action requests verification; it does not certify truth. A failure should identify where evidence stops: test reached the public mailbox but not Asym, no test seen, headers unsupported, provider blocked, or check unavailable. Give recheck/provider instructions without demanding recreation.
6. **Verify end-to-end receiving into the intended setup destination.** Use the bounded owner-qualified test mechanism with an explicit test action and identified target. “Check status” refreshes status and sends nothing; an action that sends email says so. A test must traverse the public address, not merely the secret internal target. Validate the actual tenant/inbox destination and source/thread metadata required by D1. Distinguish the command being accepted from the test message being observed and safely handled.
7. **Verify sending and ordinary replies using the qualified tenant sender.** Show a recipient-view preview with the public incoming address, actual From identity, Reply destination and selected signature. These addresses need not be identical, and a newly connected receiving route does not change P17's fixed transactional sender. Tests use safe purpose-specific material, no donor/CRM content or unreviewed library wording. If sending is not ready, retain completed receiving work and open the P6-owned prerequisite. Do not send through another tenant or platform sender to make the step green. Confirm the ordinary reply path and new-mail path independently where their routing differs.
8. **Review and activate the operating context.** Finish shows the public address, target inbox, qualified coverage/review responsibility and known sender/acknowledgment/signature settings. Existing D6/D13/D19/D23 controls remain authoritative and section-scoped. The explicit activation action rechecks current prerequisites and current permission. Technical checks alone never enable human receiving, acknowledgments or external dispatch beyond accepted settings.
9. **Show the exact result and staff transition.** If successful, say “Inbox email is active” and link **Open inbox** / **Email settings**. State that new Support work is now handled here and that the old mailbox's replies/history are not synchronized. If external mail started earlier, show its truthful protected holding/handling status and an authorized review path; do not silently auto-release a backlog or backdate activation.

## Journey B — create a dedicated address

1. **Choose the public address.** Present address name plus an eligible organization domain/subdomain, showing the full resulting email. Existing qualified choices are reusable; **Set up a receiving domain** opens the proper owner flow with return context. Do not claim availability based solely on a local text field or reserve the address globally by caller-supplied tenant identity.
2. **Check the domain's existing purpose before offering records.** If existing MX serves ordinary mail, explain: “This domain already receives your organization's email. Use a separate receiving subdomain or keep an existing address through forwarding.” Provide those two paths. Never overwrite or ask the user to prioritize a competing root MX. Preserve existing website/sending records; shared P6/P17 domains may serve other product features.
3. **Show the exact scoped receiving records.** Use copyable record type, host/name, value and any required priority as returned by the qualified domain owner. Clearly identify the receiving subdomain. Expand provider-specific host-name guidance only when needed. Do not copy a published example's concrete record value, guess provider-region values or build a general DNS editor. If the administrator lacks DNS access, offer copyable instructions and the authorized handoff described below.
4. **Retain pending progress while DNS is verified.** “Records saved in your DNS provider” is the administrator's report; “Receiving records verified” requires actual evidence. Show the last check and the next action, not a fabricated completion percentage or guaranteed propagation countdown. A new check need not restart the whole setup. The operator can leave and resume while verification is pending.
5. **Test the newly configured public address through actual intake.** DNS success proves routing configuration, not that the chosen address reaches the intended Asym tenant/inbox with required metadata, payload access and safe custody. Use the same bounded Test group as Journey A. Do not require a verification link sent to a nonexistent ordinary mailbox to bootstrap a newly provisioned receiving route; owner-qualified domain/address proof and incoming setup custody must support this path without a circular dependency.
6. **Qualify sending and the ordinary reply route.** Reuse existing approved sender identity where compatible and explicit. A dedicated receiving domain need not equal the tenant's fixed sending domain. Show the public incoming address, actual From identity and Reply destination before testing; never silently change any of their owner bindings. D23 signature and D13 acknowledgment consume their existing Email Studio sources. Neither creating the address nor verifying its DNS publishes content.
7. **Finish, activate and present publishing guidance.** Use the same final operating-context review and activation as Journey A. Only after qualified activation does the user copy the public address for use elsewhere. Do not automatically update website/contact forms, giving receipts, CRM records, Email Studio templates or previous messages merely because the new address exists. Each real owner applies its authorized binding change.

## Verification mail and early real mail: the critical shared seam

**Required proposal:** configuration must establish narrow recoverable setup custody before instructing an administrator to forward or change MX. Those external actions can start delivering real mail before final activation. A final button in Asym cannot prevent or undo that upstream effect.

Keep three concepts distinct in product behavior without making three user inboxes:

- **An expected setup challenge/test** belongs to the current bounded setup attempt and is visible through its step to currently authorized operators. It must not create a Support conversation/CRM contact, send D13 confirmation, start D14 targets, trigger follows or enter ordinary search/reporting. An email's sender/subject alone cannot qualify it as a trusted administrative command.
- **Real mail arriving while setup is incomplete** retains D1/D19 accountable custody and source restrictions. It does not gain business admission merely because an administrator completes a test. The setup page can report a safe count/status and link to authorized review without exposing message bodies to a DNS helper. Retention is inherited from the actual source owner, not restarted by wizard activity.
- **A late/duplicate/stale setup response** cannot validate a new address, changed tenant, new destination or replaced attempt. Show the current attempt's actual result, with an understandable stale-result explanation; do not make a previous successful test permanently green after material configuration changes.

This is a narrow application of the existing intake/recovery machinery, not a new public verification inbox or email-link automation service. Confirmation bodies may contain control tokens and require minimized protected retention, safe rendering and no logging/export leakage. A credential or confirmation link must not enter the copyable IT-instructions packet. Actual proof/custody implementation and exact finite budgets belong in the root's contract and release gates.

**External mail-provider confirmation is not Asym's own P17 Reply Access Challenge.** The latter retains its existing initiating stepped-up actor, code and Support-exclusion rules. Do not surface that protected Asym challenge in ordinary setup custody or automatically complete it using a message the application itself can receive. Such a self-round-trip is not independent proof of human mailbox access. A newly managed address must use an explicitly owner-qualified compatible proof path; the root's provider/contract review must reconcile that seam before activation. The narrow external-confirmation viewer described above grants no general challenge-reading permission.

## Help from IT, permissions and resuming

**Copy setup instructions** should contain the tenant's intended public address, receiving domain/target, required public DNS records or scoped forwarding task, safe explanation of impact, and a normal authenticated return URL. It must not contain tenant credentials, cookies, secret API keys, raw verification bodies or a bearer link that grants Support access. Asym does not send this packet automatically; an explicitly authorized future send would use its proper communication purpose and existing owners.

An IT colleague may complete provider work outside Asym using that packet. If they need to inspect or act in Asym, use existing tenant membership/capability management, with no automatic Support-content, CRM or giving access. Giving someone setup responsibility does not make them a reviewer or responder. Conversely an inbox reviewer need not own DNS. The current qualified integration/setup authority performs proof and activation; do not solve a permission mismatch by elevating all inbox managers to tenant admins.

Preserve completed steps, the exact candidate and the latest authoritative check on revisit. Display “Changed by [authorized actor]” when two administrators conflict; refresh the current version before continuing rather than overwriting another person's change. A resumed stale browser must not validate an old route or revive abandoned instructions. When access has been revoked, no cached challenge content is revealed and no pending administrator action gains execution authority merely from prior initiation.

## Exact proposed experience safeguards

The following wording is intended for incorporation into the root's decision/proof package after reconciliation, not a separate implementation specification.

1. **Equal choice:** “Initial inbox email setup SHALL present existing-address forwarding and dedicated receiving as equally prominent plain-language paths; neither is preselected or presented as inherently superior.”
2. **Complete return path:** “Both paths SHALL support save, leave, resume, Back and explicit path change without lost accepted progress, misleading rollback or replay of external effects.”
3. **Proof meaning:** “Configuration saved, address-control proof, receiving-route proof, sending readiness and human activation SHALL remain distinct facts; no command acceptance, checkbox, DNS-only result or unrelated prior verification substitutes for another.”
4. **No circular bootstrap:** “Expected provider confirmation SHALL be inspectable through authorized bounded setup custody before ordinary inbox activation; it SHALL not require creating a customer conversation or enabling unqualified outgoing mail.”
5. **No automatic control-link execution:** “Setup email previews SHALL remain inert. Display, indexing, URL inspection and retries SHALL not visit or execute a confirmation action; source text alone SHALL not authorize configuration.”
6. **Early mail:** “External routing MAY begin delivering before activation. Every durably accepted input SHALL retain its actual D1/D19 owner and lifecycle; setup completion SHALL not silently admit or acknowledge that backlog.”
7. **Generation correctness:** “Material address, route or owner changes SHALL invalidate incompatible proof and in-flight results. A late response SHALL not apply to a replacement configuration.”
8. **Tenant-safe handoff:** “Copyable instructions SHALL contain only permitted task information and public setup records, not credentials or control tokens. Delegation SHALL use existing capabilities and SHALL not grant inbox-content or CRM access.”
9. **Honest tests:** “A status refresh SHALL not send mail. An explicit test-send action SHALL identify its target and safe purpose, use the proper P17/P6 path and produce no customer work or unrelated business side effects.”
10. **Preserved existing mail:** “The guided path SHALL not replace or compete with ordinary root-domain MX as a shortcut. A compatible dedicated subdomain or existing-provider route SHALL be offered instead.”
11. **Qualified replacement:** “A changed active address or materially changed route SHALL be qualified before becoming current. Existing source identities, required old-reply routing and accepted custody SHALL survive replacement and retirement.”
12. **Truthful health and repair:** “Settings SHALL distinguish verified, checking, action required and unavailable evidence with context and a repair path. Last-known evidence SHALL not be represented as a continuous live guarantee.”
13. **Content/domain continuity:** “Setup SHALL consume existing Email Studio content and P6 Resend/integration authority; no new template store, editor, provider, sender fallback, mailbox mirror or CRM mutation is introduced.”
14. **Current authorization:** “Save, proof access, recheck, test, activation, replacement and retirement SHALL enforce their actual current tenant/owner capabilities server-side; previous setup membership or a client-selected tenant is insufficient.”

## Accessible and polished UI, plus proof of the real journey

Use the shared Asym form/card/status components and typography. Equal cards should have native or equivalent accessible single-choice behavior and readable one-sentence descriptions. DNS values need separate copy controls, wrapping or an accessible horizontal details region, and exact unmodified copied bytes. A long domain must remain distinguishable on a small screen. The main page should remain useful at zoom and with keyboard/screen reader; avoid a wizard nested inside successive modals.

W3C's multi-page-form guidance supports clear progress and opportunities to revisit entered information; its notification guidance calls for identifiable errors, associated explanations and meaningful success feedback. Apply these to clear group headings, an error summary with links to failed fields, preserved valid inputs, programmatic pending/result updates and returning focus to the relevant step. Announce actual state changes without repeatedly speaking a polling countdown. **A toast alone is not sufficient evidence of setup completion or a persistent blocker.** [W3C multi-page forms](https://www.w3.org/WAI/tutorials/forms/multi-page/), [W3C notifications](https://www.w3.org/WAI/tutorials/forms/notifications/).

The design is intentionally restrained: no AI setup assistant, generic DNS editor, live mailbox preview, configurable rules engine, forced many-tab dashboard, arbitrary test-recipient mailer, new guest collaboration product or preset timeout allegedly copied from a competitor. Fixed configuration test material does not need Tiptap. Existing selected Tiptap/Email Studio signature and message previews retain their own controls and context.

Required validation should prove at least these user/domain outcomes:

- A tenant can complete either path, with IT acting outside Asym where needed, then send and receive an ordinary reply through the intended public address; the exact existing domain remains intact.
- A Google-style confirmation appears to an authorized setup operator while the ordinary inbox is inactive; it creates no contact, conversation, acknowledgment, target, follow or ordinary search result. Untrusted lookalike mail cannot alter configuration.
- A helper with setup instructions cannot read held real mail, restricted CRM context or another tenant's configuration; a revoked operator cannot use a cached confirmation or old browser to complete an action.
- A user leaves during DNS/provider work and resumes without retyping or accidentally resending tests; missing or stale proof remains clearly incomplete. A failed status request is not misreported as a failed route.
- A concurrent address/path change defeats an old successful test; refresh shows the winner without erasing valid independent changes. Retry after ambiguous command success reconciles the same intended effect.
- Real mail arriving before activation remains accounted for with its original source/time and correct review permissions; cancellation or retirement does not discard it or manufacture a renewed retention period.
- A replacement qualifies before the current binding changes; old-reply continuity survives the allowed transition. A shared domain cannot be removed through Support settings while other owning-domain dependencies remain.
- Mobile, keyboard and screen-reader users can choose either path, read/copy full addresses/records, understand errors, resume, change and finish; no essential completion/control depends on color, hover or ephemeral toast.

These are required release and usability proofs, **not tests already executed**. Unknown provider capabilities should surface as qualified constraints and implementation gates; they should not be converted into discoverable-fact questions for the founder. The permanent path is a coherent two-choice front door with bounded receiving/sending tests, narrow setup custody, clear IT handoffs and qualified transitions, all carried by the existing Core owners.

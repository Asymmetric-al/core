# Reply-and-work shortcuts: complete staff and maintenance journey

**D24 C and every adopted amendment fully founder-ratified, 12 September 2026.** This is the concrete UX contract accompanying [D24-R01–R30](phase26-d24-adversarial-review.md). It is grooming, not a tested interface or an implementation specification. D1–D23 remain fully ratified.

The experience should feel like preparing one good reply and its follow-through. It must never require users to understand a workflow engine, template plumbing or transaction identifiers. The technical distinctions in the [owner contract](phase26-d24-data-contract.md) exist to keep the visible experience honest.

## Find the right combination where the reply is written

Place **Reply shortcuts** in the existing Reply composer's insertion/action area, beside or within the same labelled menu as **Saved replies**, with visibly different labels. Saved replies supplies wording; Reply shortcuts supplies wording and pending Support changes. No shortcut selector appears in the ordinary Internal note composer, no global second inbox is added and no automatic selection occurs on opening a conversation.

The initial compact picker has one search field, scoped matching names and concise descriptions. It searches authorized shortcut metadata, not conversation bodies or the CRM. Use current inbox/team eligibility to reduce the list. Do not require users to learn folders, punctuation-based categories, tags or a second filter builder. Reuse existing accessible list/picker patterns; Enter selects within the picker and can never submit a message. If the configured library outgrows the compact list, paginate/search the same bounded authorized catalog rather than truncate silently.

Each result shows a recognizable name, one-line use guidance and a concise work summary, such as **Ask for receipt details · Wait for requester**. An optional Preview opens the full proposed wording and current-context changes without touching the draft. **Use shortcut** stages the selected combination. Preview is available but is not a mandatory modal step for every repeat use because the full resulting draft and work remain visible before admission.

An unavailable source is not rendered from an old cached copy. Ordinary staff get a concise permitted reason and can use another shortcut or a normal reply. A maintainer with the appropriate source authority can follow **Review shortcut** to the actual repair. Forbidden names, hidden people or restricted files do not appear in reasons or counts. A genuinely empty catalog says **No reply shortcuts available for this inbox** and leaves Saved replies and ordinary replying clear; it does not ask every responder to create a shared recipe.

## Prepare, personalize and review

Using a shortcut creates one coherent private draft revision: actual D18 wording/asset copy plus one pending Support plan. The live conversation header, labels, assignment and status do not change. The existing Tiptap editor keeps the human reply editable. Managed signature, typed fields, one-use fill-ins, language and attachments retain D18/D23 semantics. The shortcut cannot add recipients, choose a signature, impersonate an assignee or make an official receipt.

Below the body and close to the final button, show **With this reply**. This is a compact summary, not a full second property sidebar:

| Example pending line           | Meaning and available action                                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Status: Waiting for requester  | Requested final work choice; use the qualified existing selector to change it locally.                         |
| Handling: Keep current         | No handling mutation. It does not freeze the current assignee.                                                 |
| Add label: Receipt question    | Explicit addition from the curated Support list. An existing membership is shown as Already applied/unchanged. |
| Remove label: Follow-up needed | Explicit removal, subject to all actual original-source permissions.                                           |

These are illustrative names; they are not seeded tenant classifications. Show only the dimensions relevant to the plan, with a concise Keep current explanation available. Staff can edit/remove permitted directives for this reply without changing the shared shortcut. A blocked directive has a specific inline error; it is not silently dropped. Editing a live header control still has its existing immediate meaning and causes the pending plan to revalidate. Avoid making pending values look as if they were already saved to the conversation.

Preserve D4's action wording: **Send reply**, **Send and open**, **Send and wait for requester**, **Send and wait on our side**, or **Send and resolve**. When additional handling or label changes are staged, the visible and programmatically associated With this reply summary makes the composite action clear. Do not replace the meaningful status label with an ambiguous generic Apply. Disabled controls expose the actionable reason; color or an icon alone is insufficient.

One draft has one plan. There is no action ordering or stacking. Adding labels and selecting a final status are a desired result, not sequential steps a responder has to arrange. An already-satisfied plan shows that nothing in live work needs changing; sending can still be a shortcut-assisted reply under the exact reporting definition. Removing the whole plan deliberately returns to normal reply behavior.

## Change your mind without losing work

**Change shortcut** offers the following explicit modes within the current draft:

| Mode                                                  | Body and assets                                                                                                                                                       | Pending work                                                                      |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Keep current reply; replace pending changes — default | Preserve actual current wording, assets, signature and original provenance. New suggested wording/files are not inserted.                                             | Replace the one pending plan with the new shortcut's allowed plan and revalidate. |
| Replace reply with new wording                        | Show/review the D18 whole-body replacement; preserve/remove asset occurrences under its existing rules. Do not guess which edited paragraph came from the old source. | Replace the plan in the same logical draft command.                               |
| Cancel                                                | Preserve current draft.                                                                                                                                               | Preserve current plan.                                                            |

This keeps an edited donor response safe while letting a responder change follow-through. The application records kept-current mode truthfully; it cannot credit the newly selected wording as inserted. The new shortcut and its dependencies still need to be eligible. **Remove shortcut, keep reply** removes the staged shortcut association and work only. It does not make restricted copied content safe to send.

Undo/Redo crosses body-and-plan changes as one app-owned draft-history operation. Ordinary Undo of a later sentence remains normal text editing. Undo of applying/replacing a shortcut restores both sides, or conservatively disarms the affected plan with a clear explanation if exact restoration is impossible. Redo cannot silently rearm a Resolve action or bypass current context checks. Copy/pasting body text never transfers executable work. Do not use a text-equality heuristic or every editor-update event to guess whether a plan survives.

Reply and Note keep separate drafts. Switching to Note cannot apply reply actions or carry external recipients; returning to Reply restores only the permitted prior draft. Navigating away/back preserves context through existing private draft recovery. A different tenant, account or conversation fences stale saves and async results. Visible **Not saved** or **Recovering draft** must never look like a sent reply; reconnection never sends automatically.

## Send and understand the result

1. The responder reviews real recipients, actual wording/files/signature and the compact pending work. Required fill-ins and current owner preconditions are resolved before admission.
2. The existing preparation path validates/compiles that exact reply. No live work changes yet. A recoverable failure preserves permitted draft content and says what needs correction.
3. One guarded local admission commits the message and all permitted Support changes together. A stale or denied required component commits none of them. The UI refreshes changed meaning for review rather than auto-rebasing or dropping a directive.
4. After admission, show the normal Queued reply plus actual new work values and a concise history entry. Queued is not delivered. A lost response reconciles the existing intent before allowing another send.
5. Provider failure/uncertainty follows D4/P6 recovery. It does not rerun old work or rewind today's assignment/status. A fresh causally appropriate review can open under D3 when needed.

Do not add a success dialog to every reply or send unnecessary requester notifications about internal shortcut usage. Actual admissible correspondence appears in existing Support and permitted CRM history. Selecting or maintaining a shortcut does not create a contact interaction.

## Three illustrative ministry journeys

**Donor asks which receipt is involved.** An eligible responder opens an existing request, verifies its audience and chooses a tenant-curated Ask for receipt details shortcut. They personalize the question, review any label and Waiting for requester, then send. No receipt lookup privilege is inferred and no receipt is generated or changed. A qualified unidentified requester can receive an ordinary reply without creating a CRM Party.

**Request needs an internal giving answer.** The responder first uses the actual owning-domain/D11 handoff to seek the required answer when appropriate. A shortcut may then prepare an honest progress reply and Waiting on our side. It cannot create the missing handoff or treat a label as proof it exists. If an actual result still needs Support review, Resolve is blocked. A merely linked ongoing process does not automatically prevent legitimate Support closure.

**A missionary/project question needs a different Support worker.** The responder chooses approved general wording and an eligible manual handling target, reviews that person's resulting Support role and sends. Neither assignment nor the shortcut grants access to missionary location, member-care facts, project finances or CRM ownership. If handling requires separate review, preserve the draft and resolve that review or remove the handling directive; other authorized work need not be blanket-blocked.

These are designed examples grounded in Conrad's target population, not claims about measured tenant workflows or frequencies. Each tenant curates its actual language and procedures.

## Create and maintain the library

Use **Support settings → Reply shortcuts**, consistent with current product settings navigation and access. The maintenance list has Active, Drafts and Archived views and a Needs attention filter. Prioritize name, scope, current wording version/language and compact work summary. Current health is more actionable than a large dashboard. Last recorded use/period use can be a restrained maintenance detail, not a staff leaderboard.

**Create shortcut** opens a focused form:

1. Name, optional when-to-use guidance and eligible use scope.
2. A selected published Shared Reply card showing its actual purpose, approved variant/language policy and source version.
3. The small set of final Support choices: work status, handling and curated label additions/removals. Keep current is explicit. Unsupported task/CRM/email/automation actions are not available.
4. A safe representative preview, unresolved-input/dependency checks and **Save draft** or **Review and activate**.

Do not place a second Tiptap body editor in this form. **Create wording in Email Studio** or **Edit wording in Email Studio** opens the same owning source editor with return context. Email Studio uses the ratified Tiptap purpose profile; it owns wording, typed fields, assets and publication. A maintainer without source publication rights can save the shortcut candidate and see the precise next permitted step. They are not given extra rights just to complete a wizard.

Reusable content begins with D18's deliberate generalization/contribution process. Do not harvest a live donor/care message into a shared shortcut with one click. Source-derived private facts and attachments must not become library content through copying or an AI draft later.

Incomplete but structurally safe configuration can be saved. Show **Draft — select published wording**, **Draft — choose a work change** or the real missing requirement, not a generic error toast. Duplicate creates a new unpublished candidate referencing qualified shared wording; it never makes an active copy or clones donor facts. Tenant configuration custody survives creator departure through current capabilities, without appointing a new global shortcut role.

## Publish wording, then activate the exact combination

Content publication and Support activation are separate operations and permissions. **Review and activate** shows the exact wording revision, use scope and final work choices; editing an active shortcut shows changes from its current revision. It creates a new immutable configuration version and conditionally moves the active head. Conflicting editor changes require reconciliation, not last-write-wins.

If a contextual helper guides Publish wording and return, report both results accurately. A published wording revision may exist while shortcut activation fails. Say **Wording published; shortcut still a draft** and preserve the candidate for correction. Do not say nothing was saved or repeat publication blindly. P17 publication keeps its real protected/tenant-stricter rules; ordinary Support configuration activation does not invent a mandatory second reviewer.

An active shortcut's new edit remains a candidate until activation. Staff continue using the current qualified active revision. A routine source update shows **New wording available** to the maintainer; it does not silently update active shortcuts or edited drafts. A current source withdrawal, broken target or incompatible schema shows **Needs attention** and blocks new use that is no longer eligible. Old but still valid wording is not automatically a safety defect.

Repair offers the precise action: choose an eligible target, review the newer source, narrow the audience, fix a required variant or archive. It does not silently choose a replacement person, create a missing label or downgrade the purpose. Label health depends on the operation: adding an archived label is blocked, but removing an exact authorized existing application of an ordinarily archived label remains useful and permitted. Actual restriction/missing-source gates still apply. Recheck just before activation, even if a cached health indicator was green.

## Retire or restrict even when something is broken

**Archive** must remain usable when a target was deleted or source is unavailable. It stops new selection and preserves minimal identity/history. It cannot demand a successfully executable shortcut first. A failed dependency should never force a maintainer to configure a fake team to pause use.

Routine archive and safety withdrawal are different. Routine archive does not erase admitted history or automatically invalidate every already staged copy; exact staged revisions still undergo current authorization and source eligibility. An authoritative restriction can block affected existing drafts/preparations under D16/D17/P17. The UI explains whether the reusable shortcut was archived or actual content was withdrawn, without exposing restricted details.

Restoration creates/reviews a current candidate rather than blindly resurrecting obsolete targets. Irreversible owner retention/deletion may preserve a minimal tombstone as required; a shortcut cannot recreate purged content from its source reference or a restore backup. No new indefinite full-body archive is added.

## Learn what needs maintenance

Show exact admission-based last recorded use and period use, scoped to the maintainer's current authorized evidence. A shortcut-assisted reply is one admitted reply retaining its staged association; views, selections, canceled/detached plans and retries do not count. A kept-current reply is distinguishable from wording inserted/replaced by that source. Queued usage does not claim delivery, a correct outcome or saved time.

The period's timezone and half-open boundaries are visible. Drilldown/export uses the same receipt cohort; an old conversation replied to today belongs to today's admission cohort. Merging display groups does not count the same reply twice. Retention gaps show Unknown/partial; they are not Never used. No synthetic use labels contaminate the curated Support taxonomy. Feedback can flag a specific outdated source through existing qualified maintenance attention, with minimal safe metadata rather than captured conversation bodies.

## Accessibility, mobile and recovery acceptance

Use the existing Core base-maia/Base UI vocabulary, type scale and spacing. Desktop picker/preview and a narrow-screen sheet can differ in layout while retaining every effect and disclosure. Staff can complete the same reviewed operation by keyboard, touch and screen reader; there is no mobile text-only shortcut that silently discards work.

Prove focus placement/return, labelled search and controls, accessible pending-versus-current summaries, polite save/error announcements, IME and international text handling, touch targets, zoom/reflow and plain-language errors. Avoid nested popover traps, hover-only meaning, color-only health and an error that scrolls typed text out of view. Escape closes a picker without erasing work; keyboard shortcuts do not conflict with platform/assistive behavior. Real supported assistive-technology/mobile tests remain required.

Load authorized metadata first; fetch/compile content only where needed. Reuse shared Tiptap controls and static readers. Do not hydrate a whole library, repeatedly fetch CRM context per keystroke or add a second editor runtime. Register and test actual bounds for scoped lookup, source/document size, patch size, draft history, compilation and admission before activation; no vendor quota is adopted as an Asym performance claim.

## AI later, through the same human journey

There is no AI control or model call in this feature now. The useful future first hypothesis is suggesting an existing currently eligible curated shortcut, with a visible reason and ordinary preview/dismissal. It must outperform the manual path on correct completed replies, not merely clicks. Explicitly requested wording changes and unpublished maintenance candidates are later separate research questions.

Any later implementation consumes ADR0099/Phase40's shared purpose-routed tenant AI foundation, permission/classification/egress restrictions and non-authoritative suggestion evidence. It cannot use an engineering Eve workflow as a customer-data authority. A suggestion never publishes, activates or sends, and copying text from it cannot arm a hidden plan. The manual picker and owner-controlled admission remain understandable and usable without AI.

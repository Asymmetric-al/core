## Recommendation and strongest counterargument

**Accept with required amendments.** A solves repeated filter reconstruction while letting a team maintain shared definitions. B, shared-only, is the strongest simpler alternative when roles are uniform. C, standard queues and temporary filtering, is the strongest no-build alternative. Neither weaker alternative solves the private recurring slice as directly. A should add one saved-definition capability and personal navigation preferences, not three queue engines, a public-sharing system, a publishing workflow or a replacement CRM query platform.

The chosen feature is complete when a staff member can discover a suitable view, understand its criteria, save a personal variation, return later on another device, trust its current result coverage, and correct/retire it without changing conversations. “Full featured” does not require an arbitrary nested-group authoring UI, nested folders, view-triggered automation, public links, AI query construction or custom dashboards.

**Governing shared owner, verified after the initial UX pass:** Phase9 A14/B11 and roadmap4156 require one generalized named-views capability reused by Support. Its versioned nested AND/OR stored schema, typed predicates, sort/columns/viewType, shared cursor/list infrastructure and ownership machinery govern D20. Do not build Support-only storage or flatten that schema. Phase9 says the UI may expose one level; that is the intended simple D20 presentation. Scoped Shared activation adds qualified visibility/maintenance for the Support registration, not Email Studio publishing. P9's first-pin route default is documented for CRM; a Support rule that pinning does not alter required-work landing must be recorded explicitly as the Support-specific navigation policy, not silently applied to CRM or treated as nonexistent prior intent.

Illustrative person: Alex works in Donor care. Sam is an authorized shared-view maintainer. Alex repeatedly needs **Donor care + Waiting on our side + Assigned to me**, while Sam maintains **Donor care — Waiting on our side** for the team. These are plausible illustrations of the already-ratified model, not evidence of observed ministry work or a measured time-saving claim.

## Four concrete current-source UX hazards

At unchanged inspected source commit `7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd`:

1. `apps/admin/features/support-hub/components/views/SavedViewsBar.tsx` renders every returned definition as a wrapping chip and determines active definition by the first equality match of filters. Identical My and Shared definitions can therefore imply the wrong active identity. **Fix:** active view ID/revision is explicit and separate from working criteria; a comparison may identify Modified but never chooses ownership or edit target.
2. `SaveViewDialog.tsx` writes current route-state filters even when editing an existing view; the surrounding action is named Rename in its callback. A supposed rename after temporary filtering can reshape stored criteria. **Fix:** Rename changes name only; Update criteria is a separate explicit command with visible scope/definition and expected revision.
3. The save dialog offers Just me/Whole workspace, supplies null new owner, and says “so the team can return” even for personal save. Privacy text currently outruns the inspected ownership path. **Fix:** personal actor comes from trusted context; expose Shared only to qualified maintainers and make audience explicit. Copy must fit selected visibility.
4. The UI's slugifier discards non-ASCII characters. A Thai-language name can become an empty slug or collide with another name. **Fix:** opaque stable identifiers determine identity/deep links; preserve ordinary international names. Search normalization never rewrites display content or supplies authorization.

These are static behavior observations, not reproduced production exploits. Root's database/query review owns the complete authority and source evidence assessment.

## Simplest complete access and daily journey

### U01 — Placement and first use

Keep Support Hub in its existing Mission Control surface. Required **All unfinished**, unassigned, reply/follow-up recovery and **Following** entry points retain D3/D14/D15 meanings; D19 **Needs review** remains source-qualified held-input work. A saved view cannot hide the independent indication that required recovery or review needs attention.

Place a visible **Views** selector at the conversation-list heading, accessible when the sidebar is collapsed. The selector contains searchable My/Shared sections and a route to **Manage views**. It is never possible to lose discovery by unpinning the last view or hiding a personal section. A compact **Pinned views** section can supply one-click shortcuts inside the existing Support navigation; do not render the whole tenant catalog as chips.

New staff start with the existing standard work location, no setup wizard and no seeded custom records. My views is initially empty. The shared catalog shows only currently eligible definitions. Creating or pinning a view does not silently change their home page. Existing safe last-location restoration can remain; a removed/inaccessible last location falls back to authorized standard work with a short explanation.

### U02 — Open and understand

Selecting a view loads its complete saved criteria. It must not silently combine with the previous inbox's ambient scope. Show the view name, **My view** or **Shared**, visible inbox scope and concise filter chips/summary. Names and criteria remain inspectable without hover.

The list counts current conversations/work homes, not messages, donors or reply-target periods. Where an exact full count is available label it accurately; otherwise show loaded results and More/next-page affordance, not an exact-looking page total. A view can have zero matches and still be useful.

Use contextual copy near sharing/definition details once: **“People see only conversations they can access.”** Do not repeatedly print authorization warnings on every row. A colleague can legitimately see different results from the same view.

### U03 — Filter first, save from real results

Alex opens Donor care, chooses **Waiting on our side**, then **Assigned to me**. The normal list updates after the supported filter interaction. Alex selects **Save view**, enters **My donor-care follow-ups**, and saves to **My views** by default. A name and compact read-only summary are sufficient; do not force a description, icon, folder, reviewer or separate preview screen on every personal save.

Optional description may explain an unfamiliar shared list, but is ordinary plain text subject to the same visibility/minimization as its name. Confirm save only after durable success. If network response is ambiguous, reconcile the same save intent; do not create a second definition because the person clicked again. After success, keep the current list and offer pinning in the normal control, without a second required modal.

When the current list includes free-text search, the save summary shows the complete supported query and **Include search text**, checked by default only when nonempty. This preserves the visible slice by default instead of quietly broadening it; the person can clear it deliberately and see the resulting criteria. Say **Saved in this view**, or **Visible to [audience]** for Shared. Do not extract message text, infer personal names or auto-fill a title from the query. Shared save requires deliberate review of names, descriptions and search text under the destination audience. No new sensitive-data scanner is required. Core's final Support privacy policy must qualify which query form can be persisted or serialized; hidden raw body fragments must not enter telemetry, public links or retained definitions through an implementation shortcut.

### U04 — Shared authoring and stewardship

Only qualified maintainers may choose **Shared** and the existing permitted audience (appropriate group/team/inbox membership basis determined by Core identity, not a second recipient list). Show **Available to** and the reviewed scope before **Save shared view**. Maintainability and visibility are separate: the tenant's qualified shared-view custody survives one author leaving. There is no required draft-review-publish workflow or obligatory second person for an ordinary saved list.

A maintainer may use **Save as new shared view** from their personal criteria, deliberately creating an independent shared definition. The personal item is not silently made public and remains separate; the UI makes that outcome clear. No ongoing clone synchronization. Do not provide a general employee-submission/approval queue simply to request a view; existing staff collaboration is sufficient unless a demonstrated need emerges.

### U05 — Experiment without editing the team

Adjusting filters or default sort while using a view makes local **Modified** state. Expose **Reset**, **Save as new**, and, only to an authorized maintainer/owner, **Save changes**. Shared save says **Save changes for [audience]** with the changed criteria visible. Do not auto-save shared criteria or use a misleading Rename action.

Reset restores the current authoritative saved definition, not an unlabelled old local copy; if it changed since opening, say **“This view was updated. Loaded the latest filters.”** Ordinary temporary filter changes need no leave-page warning; they are intentionally exploratory. An unsaved view editor with name/audience/criteria changes should offer Keep editing/Discard on explicit close without interfering with unrelated conversation draft persistence.

### U06 — Personal pins and visual preferences

**Pin view** / **Unpin view** change only the current staff member's navigation. Persist them under tenant+staff identity across devices using a qualified shared preference capability if one exists. Reordering offers both drag and **Move up/Move down** or equivalent keyboard/touch actions. No mandatory prefilled hundreds of pins, nested folders, pin notifications or auto-pin to all audience members.

Use the existing list/table/split presentation, density and column preferences with Phase9's qualified generalized named-view definition and shared table primitive. A shared definition may supply supported default order/columns; one viewer changing personal presentation must not change everyone's layout or mutate the saved predicate until explicit authorized save. Do not freeze a new layout builder, change the reserved viewType contract or make layout equality select a different saved view. Pinned references follow a shared view's current authorized identity; a personal saved copy is independent.

### U07 — Readable filter grammar

Use the generalized Phase9 versioned nested AND/OR schema over a finite, registered list of source-owned predicates, not arbitrary expressions or CRM SQL. Its shape must remain nested even while the D20 UI exposes one level. Start with actual responsible inbox, D3 status, assigned worker, Following, D14 reply due/overdue and established search/labels only when those source meanings are qualified. Current-user selection means the current viewer; named Alex remains Alex. **Unassigned** means missing handler, never missing requester identity or a removed CRM owner.

For ordinary multiselect fields: **match any selected values within the field, and match every configured field across fields**. Say this with a concise human summary, e.g. **“Donor care or General support · Open or Waiting on our side · Assigned to me.”** Use explicit Unassigned/Not set where needed; an empty selection means no constraint, not a hidden null comparison. Do not expose arbitrary nested All/Any/Not groups or negative general text conditions without demonstrated need. A root-selected restricted grammar should be listed in full in the final contract.

For labels, specify Contains any/Contains all if both are actually supported; never interpret multi-label selection differently from the visible operator. Rename keeps identity; deleted/unauthorized references never silently disappear from the predicate. Show an actionable unavailable-filter state for an authorized maintainer, suppressing restricted labels where necessary.

Time terms use explicit basis: **Last 24 hours** is elapsed, **Today** is calendar time in a displayed named zone. Save a chosen named zone for shared calendar boundaries, not the creator's machine zone or a changing tenant setting. D14 **Reply overdue** comes from source-qualified obligations; do not introduce **Due soon**, arbitrary color thresholds, calendar recomputation or new reply credit. Unknown target evidence remains separately discoverable, not falsely normal.

### U08 — Conversation and CRM continuity

Opening a result preserves active view ID/revision, temporary criteria, safe scroll/anchor and selected conversation ID. Going to authorized CRM context and returning preserves that context and drafts while checking current access. Changes to a source can remove its row from the matching list; retain the open detail/draft with **“This conversation no longer matches this view.”** Never replace the composing target with the next mutable array index.

The CRM record's existing Support history remains fixed to that record through D9. It does not receive a second custom-view manager or silently broaden to an unrelated global view. **Open in Support Hub** explicitly changes surfaces and preserves a safe **Back to [authorized record]** path. Do not silently save the CRM record anchor into a generic view or expose arbitrary giving/care fields. If a later approved record predicate is added, it must be a first-class typed reference with independently authorized metadata, not an ambient URL condition.

A requester, participant, authenticated staff account, CRM Party, represented organization, support handler and CRM owner are different roles. Me in a saved filter is the viewing staff identity. No shared-email match identifies a Party or a case. Merge/Undo resolves each original's current work home and deduplicates the visible work item; related conversations remain separate rows unless their own predicates match. No implied transitive related-record matching.

### U09 — Live updates without target movement

Evaluate authorized predicates before pagination. Preserve a stable row key and ordering tie-breaker. New matching conversations may update a quiet **New results available** cue while someone is typing/selecting; refreshing is explicit and must not change the recipient/conversation under an in-progress action. Removal for lost permission is immediate for cached content, even if stable-scroll presentation otherwise delays benign reshuffling.

Distinguish **Loading**, **No matching conversations**, **Could not load conversations**, **Results may be out of date**, **View unavailable**, and **Filters need attention**. A failed query is never zero. Keep the safe current criteria after retry; do not remove filters to make a timeout succeed. Server retry hints can drive Retry availability without inventing a universal interval. Do not fetch exact counts for every unused catalog item or continuously poll background views.

### U10 — Lifecycle, conflict and retirement

Use **Archive view** for a recoverable removal from normal selection. Explain **“Removes this saved view from normal use. Conversations are unchanged.”** Archived definitions stay available in a filtered management state to currently authorized owners/maintainers. **Restore view** revalidates current criteria/audience and requires explicit repair if they are obsolete. Archive/restore cannot regrant revoked source access or recover expired Support content.

No inactivity auto-delete. No Restore that swaps in stale historical conversation snapshots. Personal Unpin is not Archive; Archive Shared affects its audience and warrants a concise explicit confirmation. Keep permanent deletion in the established retention/deletion owner path rather than add a timed-only Undo promise or mandate new trash retention here. Do not hard-freeze an arbitrary view-count/pin-count retention period solely because a vendor uses it.

Concurrent shared edits use expected revision. Show **“This view changed while you were editing.”** Offer review latest and preserve authorized edits for manual reconciliation or Save as new; no silent last-write-wins or unnecessary automatic JSON merge. An archived/no-longer-visible item opened through an old link has an honest safe state and a route back to required work. A departed worker's personal items never become shared automatically; shared custody remains with qualified tenant maintenance. Reinvite by matching email does not inherit old personal ownership.

### U11 — Accessibility, mobile, visual craft

Consume existing Base UI/`@asym/ui` controls, exact Maia geometry and semantic tokens; maintain Core compact density rather than uppercase microtext, ad hoc Zinc colors and decorative folder boards. Keep a clear hierarchy: current view and scope, search/filter controls, result list. My/Shared/Modified status appears once where meaningful. Routine list motion remains immediate; reduced-motion follows Core global handling.

The Views selector works by keyboard, touch and screen reader; require no hover and do not hide its entry point behind sidebar configuration. Use an appropriate existing accessible combobox/dialog composition; do not put separate pin/delete buttons inside an ARIA listbox option with unsupported nested interactive semantics. If picker rows need multiple actions, use an accessible dialog with normal list controls or the qualified shared composite. Pin/edit can also live in the active view's labelled More menu.

Arrow keys navigate supported picker results, Enter opens the chosen view, Escape cancels without changing selection, and focus returns to the triggering control. Modal editor focus is contained and restored. Status messages announce meaningful completion/error without reading every count tick; field errors remain inline, associated and available after a toast disappears. Reorder is not drag-only.

At narrow widths, the same Views trigger and criteria summary remain available; filters/editing use the existing responsive drawer/dialog, not an inaccessible desktop table squeezed horizontally. Hide optional columns before identity/status/next-work cues. Support 200% zoom and 320 CSS-pixel reflow where applicable; long international names, translated labels and RTL content should wrap/isolate correctly. Target geometry follows Core's existing coarse-pointer minimum (44px); no shrinking hit area to match a tiny icon.

Relevant primary accessibility guidance: [W3C combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) defines keyboard selection/cancel and accessible name/value; [modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) defines containment and focus return; [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) explains communicating changes without unnecessary focus moves; [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) sets WCAG2.2AA minimum24px subject to exceptions. Core's44px touch policy is stronger and remains controlling. These are interaction standards, not proof of measured Asym conformance.

### U12 — Email Studio and side-effect seam

Save, rename, share, pin, open, archive and restore a view cause no Email Studio authoring/publication, message preparation, Phase6 dispatch, Resend email, recipient expansion, CRM last-contact or following subscription. A view is not a message audience and cannot be passed as a permission to send to “everyone matching.” Subsequent deliberate human replies use D4/D18/P17/P6 unchanged. Required operational recovery continues through its owner; this feature does not invent a message or scheduled report for each shared-view edit.

## Independent pressure-test of root's D20 decision draft

12 September2026 follow-up. Read `work/d20-decision-draft.md` in full across focused reads. The root draft incorporates the essential shared-capability, identity, temporary-edit, query-completeness, CRM and Email Studio seams. **Accept with the following small required clarifications.** No additional product feature is recommended.

### FindingUX-F01 — Creator pin versus Shared no-auto-pin contradiction

**Material concern: Yes. Severity: Medium; likelihood: High as an implementation ambiguity.** R05 says creating a view pins it for its creator; R10 says new Shared definitions are not automatically pinned. A developer could implement one rule for My but omit the creator's Shared shortcut, or could interpret R05 as permission to pin for the whole audience. Both make the documented behavior unpredictable.

**Effect:** clarify, not reject, A or creator auto-pin. Auto-pin on deliberate create is a reasonable product judgment and keeps a newly saved view easy to find without an extra question; it need not change the startup route.

**Exact replacement for R10's pin sentence:** “New Shared definitions are discoverable to their eligible audience. Only the creating staff member receives R05's creation pin; no other audience member is automatically pinned and no homepage changes.”

**Exact addition to R05/P15:** “If the definition is saved but its creator pin is not, retain the saved view as the active identity and report `View saved. Couldn't pin it.` with `Pin view` retry. Retry only the preference effect; never repeat definition creation.” Use existing inline/status feedback, not another mandatory dialog.

### FindingUX-F02 — Archive must invalidate prior pin intent, not merely hide it

**Material concern: Yes. Severity: Medium; likelihood: Medium.** R16 says Archive removes active pins and Restore does not repin everyone; a simple read filter that hides archived definitions while preserving active pin intent would automatically reveal all those pins on Restore. A queued create-pin request can likewise arrive after archive/restore and appear new even though it represents a superseded action. R17/P17 already recognizes delayed response hazards but should make this particular visible rule exact.

**Effect:** makes the chosen lifecycle coherent; does not require a new navigation system or user-facing tombstone concept.

**Exact addition to R16/P17:** “Archive ends all existing active pin intents for that definition's active lifecycle. Restore returns it unpinned to the catalog; a new deliberate Pin is required, including for the original creator. A delayed pin/reorder command from before Archive cannot become effective after Restore.” The shared preference owner chooses the minimal guard/generation representation; do not preserve a silently live pin behind an archived filter.

### Checked decisions with no additional material concern

1. **My copy:** R11 correctly defines an independent copy, not a live fork. Retention/source-authority obligations still apply to the copied values under R19. UI copy should say “Changes to the shared view won't update your copy” at creation, without permanent banners.
2. **Support versus CRM startup:** R12 clearly identifies the scoped P9 adaptation and leaves CRM defaults unchanged. No new “home view” setting is needed. Root's proposed policy is coherent with preserving required Support entry behavior.
3. **Free-text query:** R05's checked-by-default Include search text preserves the reviewed slice; displaying exact text, audience and opt-out prevents silent broadening. It is valid only alongside R19's current restrictions and minimized logs/URLs. Do not add a repeated PII warning or scanner, and do not auto-name the view from the query.
4. **Current and saved sort/columns:** R12 separates personal display preferences; R05 captures the actually reviewed supported defaults. The linked UX should state that temporary sort changes mark Modified when they differ from saved sort; no silent shared column/sort write. P06/P14 already cover the proof.
5. **Archived active detail:** R16 removes normal use without changing conversations. If a view is archived while its conversation is open, preserve the conversation/draft and replace its list context with an explicit archived-view state plus standard-work navigation. Do not automatically close the composer or execute a broader query under the old title. This is an application of R04/R14, not a new feature.
6. **Restore previous settings:** R16's “may support” is appropriately conditional; do not turn it into a mandatory custom diff/history UI when existing shared-owner history and current saved correction suffice. Any implementation must obey present source/audience restrictions.

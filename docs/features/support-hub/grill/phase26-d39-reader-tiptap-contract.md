**15 September 2026. A selected; detailed amendments proposed.** This document supplies exact grooming clauses for root's consolidated D39 decision. D1–D38 remain ratified. ## One quiet cue, in the existing journey

**UX01 — Presentation and placement.** “Display personal Unread using a restrained dot and modest title emphasis in the existing Support conversation list/card. Include the accessible meaning **Unread for you**; color or font weight alone is insufficient. Keep shared work state, priority, assignment and mandatory recovery visibly distinct. Reuse the existing row and reader **Conversation actions** menu for one state-appropriate **Mark read** or **Mark unread** action. The dot is decorative, not a tiny hidden toggle. No new unread count, filter, timer setting, bulk command, reading dashboard or shortcut family is required.”

The new action belongs with ordinary conversation utilities, separated from consequential shared actions by the existing menu grouping. It does not go inside **Reading: Compact/Full**, which is already D33's personal content-presentation setting. Use a quiet helper, where clarification is needed: **Only changes your reading status.** Do not display a toast on every automatic read. A deliberate action has a brief accessible success acknowledgment after confirmation. No confirmation dialog is needed for these reversible self-only actions.

Base UI controls and the exact **base-maia** preset remain required. Shared foreground, muted, border and focus-ring tokens carry the design; no hardcoded red unread badge, dashboard chrome or reduced type size is introduced. Current `packages/ui/components.json` and the installed shadcn `info --json` report base-maia/Base UI; that proves configuration only, not a completed visual implementation.

**UX02 — Honest initial meaning.** “A currently permitted source with eligible other-authored content and no recorded personal coverage is Unread for you, including old or newly accessible history. This does not mean received today, urgent or owed. No unread marker is fabricated for an empty or excluded-only source, and own-authored content alone does not automatically make a source unread. There is no activation-wide mark-read baseline or per-person history fanout.”

Show original content times accurately. Do not rewrite dates, replay historic notifications or sort old material as a new arrival merely because it is newly accessible. A staff member may deliberately mark eligible own-authored content unread to revisit it; this is a personal intent, not a new deadline or shared reminder. A source that no longer has applicable permitted content must not retain an unexplained dot that reveals removed material.

## Ordinary opening, viewing and returning

**UX03 — Qualified open.** “Automatic personal acknowledgment requires a deliberate opening of the actual selected conversation reader in the foreground, a visible and active reading surface, current source-qualified snapshot coverage, and successful safe presentation of its current latest eligible content region. A table focus movement, preview, prefetched request, automatically selected row, hidden mobile/desktop duplicate, background tab, loading skeleton, failed fetch or mounted empty component does not qualify.”

Opening the same authorized Support reader from a CRM link has the same effect. Merely visiting a CRM Party record or expanding a summary card does not. Pointer, keyboard and assistive-technology opening use the same meaning; no mouse-only gate or editor focus is required. Window/document activity, app-selected reader and actual presented region are complementary local signals. None is a server authorization boundary or proof of human attention.

There is no dwell timer. The user should not wait to earn a read state, scroll every old message, or put an entire tall card on screen. Only the qualified current orientation event is acknowledged. Expanding a repeated signature, changing Compact/Full, resizing, hydrating or moving focus between controls does not become a separate open or clear a newer manual-unread intent.

**UX04 — Usable content before automatic success.** “The read integration must distinguish successful current content presentation, legitimately bodyless eligible content, loading, authorization failure, unsupported/invalid document content, and rendering failure. A valid attachment-only contribution can qualify when its authorized message and attachment metadata are presented; downloading or opening every attachment is not required. An error placeholder or silently blank failed current body cannot automatically acknowledge that content.”

Qualified safe-text fallback may represent the same authorized current body when allowed by the owning content profile. Arbitrary raw HTML, guessed JSON parsing, stale text from a different revision, or a generic error label cannot be relabeled successful content. D33's already-qualified older repeated-history folds remain compatible; unique current content cannot be hidden just to obtain readiness. All-full-archive loading is unnecessary.

**UX05 — Exact represented coverage.** “Bind an automatic acknowledgment to the exact server-qualified content/source cutoff vector represented by the opened reader. Never substitute the server's newest head when the acknowledgment arrives. A newer contribution after that snapshot remains unread until a subsequent qualified presentation or deliberate Mark read covering it.”

The cutoff is a durable content-order boundary, not a client wall-clock timestamp or mutable `updated_at`. The browser reports a qualified local view, while the owning server independently validates actor, tenant, current source permissions, topology, expected personal intent and represented cutoff. Rendering or observing content never grants permission. Root's D39 data/lifecycle contract supplies that single authoritative mutation boundary.

## Mark read and mark unread without fighting the interface

**UX06 — Deliberate actions remain deliberate.** “**Mark unread** records a personal revisit intent for the currently qualified applicable content. It stays unread throughout the current reader activation, including rerenders, new fetches, ordinary focus/visibility changes and already-open tabs. A new deliberate open after that intent, or an explicit **Mark read**, may clear it with current qualified coverage. Delayed automatic acknowledgments from older activations cannot undo it.”

The usual action in an unread row is Mark read; in a read row it is Mark unread. Both desktop and mobile have a labelled menu path. Do not add an obligatory second confirmation, force a close, navigate away automatically, or save a reminder time. **Mark read** acknowledges only the exact qualified scope shown to the person; it does not certify inspection of every body/file. The action may intentionally clear a cue without visiting all old content, while a source/head lookup failure must not fabricate its scope.

After selecting Mark unread in the reader, keep the reader open, preserve focus and quietly confirm the personal change. Returning from a tab switch does not count as a new deliberate opening. Leaving this conversation and deliberately reopening it does. A known command conflict or uncertain outcome retains truthful pending/unconfirmed state and cannot silently override a later deliberate intent from another device.

## New content while already working

**UX07 — Stable reading.** “A new eligible contribution arriving while the person is looking at older history, viewing a file, composing, in another tab or behind another surface stays unread until qualified current presentation or Mark read. Show a quiet **New activity** action in the existing reader when useful. Preserve the visible message anchor, selection, draft, focus and list position. Do not auto-scroll or move a row under the pointer.”

Selecting New activity deliberately returns to the current latest readable region and preserves the composer. It does not send, readdress, resolve, subscribe or mark P17 notifications read. A new contribution arriving while the Reply or Note editor is actively being used for writing or IME composition remains unread even when the latest message region is visible. It can qualify when the person deliberately returns to current reading, including New activity, or explicitly uses Mark read. Merely retaining an inactive draft does not block normal qualified viewing. Returning from the composer does not mint a new deliberate-open epoch that overrides a prior Mark unread; UX06 still applies.

If already at the current region and actually reading it, new successfully rendered material may qualify through the same rules; a stale render, hidden pane or later arrival beyond the acknowledged snapshot cannot be swept into a previous acknowledgment. A floating action must not obscure content, the editor or mobile controls.

Do not announce every streaming/backend event or flip a live region for every message. Announce the meaningful appearance of new activity politely, without stealing focus; the visible action remains available. Repeated events are coalesced by the actual UI state. [W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) supports presenting status without an unexpected focus move; it does not require a success toast for every passive cue change.

**UX08 — Drafts and preparation remain untouched.** “A read-state update, content invalidation, newer conversation message or list refresh must never call Tiptap `setContent`, replace a Reply/Note draft, reset its selection, change its recipient/source, post it, discard it, prepare email or imply current Send coverage. D37/D38 private draft custody and D36 quote provenance remain authoritative.”

The user can read a newly arrived message while preserving both Reply and Note working states. A genuine source or recipient change still invokes the already accepted review rules; a read marker is not a substitute for those checks. The writer and reader have independent state lifecycles even when they share a visual pane.

## Merges, CRM and permission changes

**UX09 — One grouped reading journey, qualified originals.** “A qualified combined conversation open may acknowledge its exact represented authorized original-source cutoff vector when the combined current latest eligible region successfully renders. Older bodies may remain folded or paginated; there is no requirement to bring every original source head into the viewport. Sources absent from the authorized snapshot, unknown or incompatible coverage, and later topology/content are not covered. Merge/Undo preserves personal coverage on the original sources rather than inventing a shared root flag.”

This refines an initially overstrict review suggestion. Requiring a separate scroll/open for each old merged original would leave a normal reader perpetually unread and confuse orientation with body-by-body attestation. Ordinary old-body pagination is not missing source coverage when the snapshot explicitly and correctly represents that original's cutoff. Conversely, seeing source A alone does not authorize a server to guess B's existence or frontier. A server-complete component vector and current authorization are essential; a root maximum or current list counter is not sufficient.

Changing a Party link, requester identity, assignment or CRM owner cannot transfer one person's state to another or grant access to a source. Narrower CRM access and Support permissions are both respected. Return to the same CRM record/list position. No separate CRM read field, conversation copy, interaction-history entry or broad CRM write is created.

## Failure, mobile and accessibility

**UX10 — Readable and operable under ordinary constraints.** “Keep the same cue meaning and menu actions on desktop and mobile. Provide accessible textual state, native/established Base UI menu semantics, visible focus, predictable Escape/focus return, Core touch targets of at least 44 CSS px, and no hover-only or gesture-only controls. Keep language understandable at 320 CSS px, 400% zoom, large text and mixed LTR/RTL content. Reading mode does not shrink message type.”

New activity must be reachable by keyboard and AT without tabbing through every historical control. Do not trap the reader in a mandatory scroll sequence to clear a cue. The reader's legitimate scroll and source-window navigation remain; D39 does not introduce page-wide horizontal scrolling or animate history heights. Use existing reduced-motion behavior. No read pulse, blinking indicator, sound or celebratory motion is warranted.

## Tiptap's exact role

**UX11 — Shared static rendering.** “Reuse the qualified shared rich-text reader and document profiles. Read-only Support content uses `@tiptap/static-renderer`; D39 does not mount a `useEditor` per message, introduce Tiptap collaboration/presence, add Pro/AI services, or migrate the existing editor API. Compact and Full are presentation over the same permitted message content, not separate read-state owners.”

[Tiptap static-renderer documentation](https://tiptap.dev/docs/editor/api/utilities/static-renderer) describes rendering JSON into HTML/React without a browser or editor instance and exposes explicit handling for unknown nodes/marks. Core's canonical Tiptap skill independently prefers static rendering for feeds. These support the existing architecture. They do not prove arbitrary JSON is valid or that rendered content was seen.

**UX12 — Events are not reading evidence.** “Do not use Tiptap editor creation, focus, update, selectionUpdate, transaction, setContent or hydration as a read acknowledgment. Keep personal marker data out of canonical message/draft JSON and all email serialization. Expose current safe-render readiness at the reader adapter boundary, with message/source/content identity; a component mount alone is insufficient.”

[Tiptap events](https://tiptap.dev/docs/editor/api/events) describe editor and document activity. They do not supply a conversation-reading contract. The documented `contentError` is an editor/schema event, not a replacement for validating the read-only path. Preserve the existing `immediatelyRender:false` editor configuration. The official [Composable API guide](https://tiptap.dev/docs/guides/react-composable-api) still identifies `useEditor` as appropriate for simpler direct-control cases; this narrow reading feature is not a reason for an unrelated migration.

**UX13 — Visibility is a local hint, not attention surveillance.** “Use current app selection, document activity/visibility and bounded local current-region presentation signals to determine whether an already-authorized snapshot is actually shown. Do not collect per-message viewing histories, dwell measurements, screenshots, read-duration analytics or teammate receipts. Invalidate queued local acknowledgment intent when its source, actor, topology or activation no longer applies.”

The [Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) distinguishes visible/background documents; document visibility alone does not establish that a particular pane is visible, and focus alone does not establish visibility. [Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API) reports geometry asynchronously, can fire on initial observation and is not proof of perception. Avoid a 100%-of-card threshold for tall content, observer-per-history-node tracking, or a zero-area sentinel that marks content read before presentation. An app-hidden/inert reader and known covering dialog must be excluded by app state. No browser API provides a comprehension guarantee.

**UX14 — Email Studio and domain boundaries.** “Support owns the current person's qualified source-reading marker. CRM supplies only permitted shared context through its own authority. P17 owns notification engagement; D15 owns Following; D14/D31 own response/reminder obligations. Email Studio owns its already accepted templates/content tools and P6 owns delivery. Reading, Mark read, Mark unread, New activity and Compact/Full do not prepare, send, record a delivery, enroll a campaign or change any of those domains.”

## Independently testable reader outcomes

These are required later implementation proofs, not tests claimed run now. Root's integrated D39 proof groups must trace them to the final requirements.

1. Ava opening an authorized new reply clears only Ava's cue; Ben's state, work status, assignment, Follow, P17 engagement and CRM history are unchanged.
2. Old/newly accessible other-authored content with no personal marker is Unread for you without a recent-arrival timestamp, count or task transition. Self-only/empty/excluded-only sources have no automatic cue.
3. Keyboard/table focus, route prefetch, hidden duplicate pane, background tab and a failed fetch create no automatic acknowledgment.
4. An explicit active reader with qualified latest content clears the represented cutoff without a timer or complete historical scroll. Tall messages, authorized attachment-only content and D33 older folds work.
5. Valid text, unsupported node, malformed content, safe fallback and legitimate bodyless fixtures produce distinct readiness outcomes. An empty wrapper from a failed current body cannot pass.
6. Mark unread stays through rerender, focus change, invalidation, resize, Compact/Full and already-open second tab; a new deliberate reopen or Mark read clears it. Late old acknowledgments cannot.
7. A new contribution arriving before, during and after acknowledgment remains unread when outside its cutoff or current presentation. Older-history search and active composition retain position and show reachable New activity. Test active writing/IME with the latest region visible, an inactive saved/dirty draft while actually reading, deliberate return/New activity, and an already-present manual-unread override. Active writing suppresses new-arrival auto-acknowledgment; inactive draft presence does not, and returning from writing cannot bypass the existing manual-intent epoch.
8. Cue refresh cannot replace either dirty Reply or Note draft, its quote/file selection, source, recipients, selection, pending operation or Send review requirement.
9. Combined source A/B coverage can clear on one qualified combined latest-region open even with older B body paginated. An absent/unauthorized/unqualified B, new merged C or later content cannot be implicitly covered; Undo restores each original's actual personal state.
10. The same qualified Support reader through CRM updates the same marker; a CRM profile/preview alone does not. Return context survives; hidden source identities/counts and private drafts remain unavailable.
11. Known rejection versus lost response is visibly distinguished. Retry/reconciliation cannot broaden scope, overwrite a later intent, falsely confirm a read, or block otherwise authorized reading/typing.
12. Keyboard, touch and screen-reader paths reach the menu and New activity, expose Unread for you, retain focus and work at narrow width/zoom, mixed-script text and reduced motion. Test actual browser behavior; neither a static markup probe nor automated axe alone establishes this.

The permanent path is small: repair qualified shared reading readiness, join it to one private source-aware marker boundary, add the restrained existing-menu actions, preserve all accepted domain seams, and prove the outcomes above. It does not require a second reader/editor, a preference hierarchy, a notification engine or a surveillance trail.

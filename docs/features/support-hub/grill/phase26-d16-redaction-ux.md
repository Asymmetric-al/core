# Removing sensitive Support content

The normal journey is **select → review → remove** within the message already being read. Useful context stays in place. The [complete D16 decision](phase26-d16-adversarial-review.md) governs authority, source correction and cleanup. This complete blueprint is fully founder-ratified, 11 September 2026; it is not a rendered interface or completed accessibility test.

## Ordinary staff journey

Maya's receipt question includes an unrelated private paragraph and the wrong attachment. Alex has the qualified redaction capability and access to this original message. This is an illustrative scenario, not a measured ministry incident.

1. Alex opens the message's existing action menu and chooses **Remove sensitive content…**. It is reachable with touch and keyboard, not only hover. The conversation remains in place behind the focused correction surface.
2. The surface identifies the original message by permitted author/time and stable reference. Instruction: **Select the text or files to remove. The rest of this message will stay.** Alex marks the paragraph and checks the specific file. Subject removal and **Select entire message text** are separate controls; neither silently checks attachments.
3. **Review removal** shows the exact server-computed **After removal**. The paragraph is replaced with **Content removed** and that file with **Attachment removed**. The useful receipt question and other files remain. A compact summary says **1 text selection · 1 attachment**. Alex can **Change selection** or **Cancel**.
4. One final button, **Permanently remove selected content**, commits the reviewed scope. The copy states: **This cannot be undone in Asym. It does not recall emails or files already sent or downloaded.** Any real preservation/deferred-copy qualification appears here, before commitment.
5. The source shows the honest accepted state and then the safe remainder. The marker stays in the message position; no new reply, modal celebration, intrusive banner, donor email or follower alert is created. Qualified staff can inspect **Removal details**. Ordinary readers do not get a legal/storage dashboard.

```text
Remove sensitive content
Maya · Today, 10:24 · Message 482

After removal
Can you help me find my receipt?
[Content removed]

[Attachment removed]    receipt-question.pdf

1 text selection · 1 attachment

This cannot be undone in Asym. It does not recall
emails or files already sent or downloaded.

Cancel     Change selection     Permanently remove selected content
```

This is a semantic layout illustration. The unselected filename above is synthetic and remains only if actually safe and authorized. Removed filenames, secret text, length-revealing black bars and hidden before-images do not appear in final markers or DOM. Use existing Core base-maia, Base UI primitives, spacing, semantic color and typography. No new design language is selected.

## Selection without a second document editor

Use a qualified read-only text/HTML selection surface with native selection behavior where possible. It cannot accept replacement text or rewrite the original author's statement. Show exact selected occurrences with both visual and accessible state, a count, and **Unmark**. For multiple equal strings, mark the intended occurrence; no **all conversations** or hidden global find-and-erase action.

Expand nested/quoted content for inspection in selection mode. Link targets must be inspectable as text without navigation, network fetching or credential-bearing preview generation. Removing an affected link removes its full object; the after-state preview shows that scope expansion. Plain-text and HTML views must map to the same current source semantics. The current shared plain-text helper is not that mapping, as the [source probe](phase26-d16-source-probe.json) demonstrates.

If the source format cannot support dependable partial mapping, use: **This format cannot safely remove selected text. You can remove the entire message text instead.** The larger scope needs its own review. Do not truncate a long body and imply unseen content was reviewed. Whole-body fallback cannot be the only accessible path for a format that supports precise mouse selection.

Files are whole files. Selecting an inline image selects its owned file/derived appearances and makes that consequence clear. No PDF rectangles, image editing, OCR tools or automatic detection are bundled in. Removing the message text leaves unselected attachments alone. Removing a file does not delete a separate giving-domain receipt. If an original raw email cannot be safely retained, the review says **Original email download will no longer be available.** A sanitized export must not be labelled the unchanged original.

Unsafe subject display can be removed as an explicit whole field. Unsafe sender/recipient display follows qualified suppression and the identity/P6 owner route while factual routing remains protected. Do not show an arbitrary editable header grid.

These are displays of actual operation facts, not modes the user must learn or choose.

Preserve selection only when mapping is still provably exact; never guess. A permission denial reveals no hidden content.                                       |

Permanent removal is unavailable.** Route to the records owner. No ordinary Reveal; confidential hold facts are hidden from unqualified staff. |

The ordinary message marker remains content-free. Permitted actor/time/reason category belongs in qualified details, not in a public message. A reader without correction permission can send a source reference through established internal attention; they should never paste the private paragraph into a new task. Qualification determines who may restrict or erase, not merely who can open the menu.

## CRM and work continuity

A CRM record's authorized Support/communication appearance resolves the same current source representation. There is one communication, one actual author/time and one correction; visiting the CRM does not create another editable transcript. The row retains its original source link and useful safe context. Return navigation preserves the conversation's list/filter/scroll context through established Core patterns.

An actor with only Support authority gets no new CRM, giving or member-care access. If CRM access is unavailable, the correction still works within its permitted source scope and the owner invalidates derived representations without disclosing hidden records. Search hits, facets and counts from old content disappear from current result membership; a safe-looking snippet alone is insufficient.

Merge/Undo, related citations and multiple CRM links keep the same corrected original. Independent summaries and separately quoted messages have their own authority and reviewed correction; the UI must not claim they were all erased. If redaction makes an internal task's supporting context inadequate, route it for qualified work review. Do not silently complete it.

Reply targets, status, assignee, follow-up reminders, following intent, giving facts and actual delivery evidence remain truthful. A corrected email is not a new human reply. A legitimate privacy/incident response, if needed, is a separate authorized action through existing Email Studio and Resend delivery; redaction itself sends nothing.

## Draft and send behavior

Preserve unrelated authored draft text. Known source-derived quotes/attachments become unavailable after correction; block stale autosave/send and show **Some quoted content or files are no longer available. Review this reply before sending.** Do not automatically send a rewritten draft or secretly replace sealed prepared bytes. A changed safe draft needs deliberate review and qualified new preparation.

If provider submission was already authorized, show its real pending/accepted/unknown delivery state. **Removal cannot recall this email** is contextual detail, not a global alarm. Do not turn ambiguous sending into failed sending or offer a new-key resend. P6/P17 retain their exact whole-envelope recovery rules and current source stop.

## Accessibility and low-friction presentation

The [W3C error-prevention criterion](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html) allows review/confirmation/correction before commitment; it does not require retaining a revealable original for Undo. Use the [APG dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) for focus and dismissal. A component's name alone is not conformance proof.

Require real keyboard-only partial selection, screen-reader discovery/review/unmark, supported touch behavior, and an equivalent non-drag single-pointer path for any authored dragging behavior. Native user-agent behavior and authored drag controls have different requirements. [Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [Dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

Use localized labels, stable message anchors, no unnecessary network-dependent imagery, and a readable text-first mode for low bandwidth. Final controls remain visible with mobile keyboards and at 200%/400% zoom; focused content cannot be obscured. Meet the applicable 24×24 CSS-pixel minimum or valid exception, using larger comfortable controls where the existing design calls for them. Selection must not rely on color; progress must not repeatedly announce every worker retry. [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Focus visibility](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html), [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

Before commitment, Escape/Cancel discards transient selections and returns focus. After acceptance, closing only dismisses the status surface; the durable operation continues. Return focus to the stable message action/marker, not a removed selection node. No automatic destructive action from Enter inside a selection/search field. No notification sound, celebration, repetitive snackbar or attention-grabbing animation is necessary.

The actual design must pass D16 P01–P08, P24–P29 and P35–P36 before claims of exceptional usability or accessibility. The blueprint defines the intended result precisely; those browser/assistive-technology tests have not yet run.

## Browser receipt is not a message

[P23 ADR0170](https://github.com/Asymmetric-al/core/blob/9069dcad67f9630323474ca5ee8bcc85ca7bf0f6/docs/adr/0170-purpose-bounded-public-form-definitions-and-domain-owned-routing.md#L37) requires the form occurrence, exact route, Primary Outcome work, optional children and dispatch obligations to be committed before Received. D29's standard Help form uses its certified Support handoff. A P23 Verified Email Destination is a different qualified Primary Outcome available elsewhere; it is not a fallback chosen after Support acceptance or a second source of staff work.

The user's own form text belongs to the Support source after handoff. P23 retains only the required occurrence/recovery envelope under its finite purpose, not a second readable inbox. A public mailto address, staff directory address or phone listing has no authority to create a Verified Email Destination or choose server recipients. A contact link click has no P6 event or Received record.

## Optional web acknowledgement: precise new qualification

D13-R03 is explicitly receiving-owner-qualified **email** that creates an original conversation, with actual provider receipt/From authority. A web form is not that source. Do not insert fake email metadata, call both producers or use a conversation-created hook to trigger two confirmations.

Register one compatible web-Contact acknowledgement profile/catalog binding within P17, with the accepted form occurrence as producer evidence and the explicitly submitted reply endpoint as its narrow current recipient basis. A Party is optional; an asserted address does not prove identity or permit disclosure of a prior request. Reuse neutral receipt wording only by valid copying/authoring or an explicitly compatible publication. A Live email-only D13 publication/key does not gain form authority by changing a label. This is an explicit owner-conformance amendment across purpose/manifest/producer/recipient/trigger/evidence, not a new mailing system.

The P23 Route Plan owns one optional acknowledgement child, Off for newly configured standard Help forms. It uses current source-owned Contact settings, not a second Support checkbox or widget auto-response. Qualified visitor receipt text confirms only receipt and a safe next step. It never echoes the visitor's message/name/context/subject, embeds submitted URLs, claims human reading/resolution, includes marketing or runs a protected giving/identity action. No `all_fields` token or arbitrary template/body/recipient override is available.

If enabled, freeze the original occurrence and utility ending 15 minutes after trusted form admission; it never uses invented provider receipt or worker time. Share D13's tenant/qualified-mailbox 24-hour courtesy guard across both automatic-receipt source families. One occurrence cannot spend a second slot through retry; changing profile keys cannot evade the common purpose. Eligible human reply wins the existing source/current dispatch gate. Apply D13-R15 completely: a qualifying public human reply for this current request and exact confirmation recipient admitted after acknowledgement may have submitted also stops all further acknowledgement provider-call/decrypt authority, including otherwise allowlisted indeterminate same-key follow-ups. Preserve already-in-flight evidence reconciliation/no recall; later human-send failure does not revive the automatic receipt. Off, source/route revocation, contactability, abuse and sender/publication safety are current adverse gates; no old-work enrollment or utility extension follows a repair.

P17 freezes the exact publication, locale, source facts, sender/reply identity, recipient, assets/compiler and transport binding. P6 submits/reconciles that immutable effect through the existing common spine. No live rerender/recipient re-resolution at dispatch, no fresh key after ambiguous success and no late send after utility ends. Prepared-material expiry/finality and source restrictions remain intact. Explicitly use D13-R17’s Off-only Recent sent copy posture for this new profile: one body-free Automatic confirmation event with actual delivery state, no permanent generated body/subject in support_messages, and only a synthetic Template used publication preview. Restricted prepared execution bytes are not a staff content-view API. A skipped/failed acknowledgement never rolls back intake, changes work status or earns human response credit.

## Actual first reply and email continuation

Qualify a form-response recipient source in D4/P17: one reply endpoint from the exact admitted form occurrence, visible to the staff author and checked against current contactability and source authorization. No automatic CC, CRM preferred-address replacement, D13 original-From heuristic or staff-manual-origin shortcut. If an actual compatible acknowledgement has already created a qualified native outgoing thread, the first human reply may continue it. Otherwise it creates the first real outgoing lineage. A P6 provider ID is not automatically an RFC Message-ID; no incoming RFC header is fabricated to make threading appear complete.

Later real incoming email follows D1/D2/D25 correlation/intake. The acknowledgement and human reply race must preserve existing reply precedence and prevent a late unsent acknowledgement from starting another thread after the useful answer. Ordinary phone calls or separately composed emails remain separate real-world contacts; D26/D10 support deliberate recording/duplicate handling when justified, not inferred contact events.

## D14, D28 and CRM continuity

The certified form adapter must explicitly contribute true source-time semantics to D14: ordinary owed first reply starts at trusted acceptance/admission, not a Resend receive timestamp or eventual worker completion. Current calendars, holds and explicit human reply coverage/acceptance retain their existing meanings. Browser Received, auto acknowledgement and article use do not satisfy a reply target.

D28 feedback can consider an eligible genuinely completed form-origin conversation after actual accepted human public email correspondence and all normal guards. The form itself, a guide click or automatic acknowledgement is insufficient. There is no new feedback configuration, second sampling opportunity or automatic resolution. CRM exposes the same authorized canonical Support record, with source references and truthful form origin, not copied text, a fake received-email event or verified identity from the email field.

## Contact failure and guide failure are distinct

Qualify P23's Optional Help guides leaf and its current-source/empty presentation separately from the required contact closure. A guide-only failure does not disable a qualified form. If the form itself cannot accept, public contact methods are usable only when their own current publication/tenant/host/source authority succeeds. Never silently switch an already chosen Support Primary Outcome to email-only delivery or reconstruct fallback addresses from private staff data/stale artifacts.

Public Contact and app Help use separate trusted producers behind the same purpose/occurrence/intake semantics. App authority is P12/current portal/app context; the public producer uses the actual public host/Site/locale/generation. Neither submits private context through public URL parameters nor grants public CMS access based on authenticated roles. Their releases/readiness have separate receipts; a combined settings page does not make them one distributed transaction.

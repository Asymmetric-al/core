# D20: Saved views and the Email Studio seam

**Fully founder-ratified, 12 September 2026.** This addendum makes the accepted D20-R01/R24, D18 and D19 boundaries explicit. It introduces no new product decision, template, communication channel or implementation authority. The [independent seam review](phase26-d20-email-studio-seam-review.md) records the complete ownership matrix and governing source citations.

## What each capability owns

Core's shared named-view/list/preference capability owns a saved view's identity, versioned definition, lifecycle and personal pin preferences. Support supplies the permitted conversation subject, filter meanings, source authorization and eligible actions. Sharing a view shares a definition with an authorized staff audience; it does not share otherwise restricted records or identify message recipients.

Email Studio remains the Phase17 owner of reusable wording, eligible immutable content revisions, governed presentation and preparation contracts. D18's **My replies** and curated shared library remain Email Studio content reached from the Support composer. Similar My/Shared labels do not combine view custody with content custody. A Shared-view maintainer does not thereby become an Email Studio publisher, and a shared-reply publisher does not thereby gain Shared-view maintenance or additional Support/CRM access.

Support owns the current conversation and draft, the intended Reply or Note purpose, recipients, source guards and authoritative admission. Phase6 owns actual communication delivery and its evidence. Actual external delivery uses the tenant's qualified **Resend** connection; a view never selects another sender, provider template, connection or global fallback.

## Ordinary view work stays quiet

Save, Open, Pin, Unpin, Reorder, Share, Rename, Archive and Restore create only their authorized configuration, preference or query outcomes. They do not prepare or send messages, publish Email Studio assets, create follows/subscriptions, change reply targets, mark donor contact, mutate CRM records or generate routine communication notifications. They require no Email Studio render service to display a list. **No unused email template is introduced for view operations.**

Save a My copy or create a Shared copy copies the reviewed eligible criteria, not conversation bodies, current matching IDs, CRM snapshots, attachments or recipients. A saved query is not a mass-mail audience. If staff invoke an existing authorized action from results, the action uses explicit stable selected IDs and rechecks its own authority; a changing query cannot silently retarget it. D20 adds no mass-reply feature.

## When a person replies after opening a view

1. Open the selected currently authorized conversation. Keep D9 CRM navigation and return context, with current authorization in both domains.
2. Insert eligible D18 wording into the current draft as a copy with its original revision provenance. Editing that draft does not edit the library. View and library access are checked independently.
3. For a human external reply, use the existing D4/D18/P17 ready-preparation contract, followed by Support's guarded atomic admission and the Phase6 tenant delivery contract. Recipients come from the qualified conversation/source intent, never saved-view membership.
4. Phase6 records the actual per-recipient-copy/submission outcome through the qualified tenant Resend path. Support resolution is not evidence that a giving, CRM or delivery action succeeded.

An internal Note uses Support's note validation/admission and D18's applicable shared validation; it does not invoke external preparation or Resend. Opening a view, archiving it or changing its definition does not itself cancel an otherwise valid draft or admitted message intent. Current source, message, permission and retention fences remain authoritative independently of navigation configuration.

D13's eligible new-request confirmation remains the separate **Support request received** Email Studio template and qualified external path. View activity cannot restart its fifteen-minute window, release D19-held intake, establish requester identity or cause a new acknowledgement.

## The distinct maintenance exception

D20 O03 already requires attention when an active Shared view lacks an eligible maintainer. A real failed maintenance obligation may use the existing source-owned attention contract: the actual configuration/Support producer establishes the episode and repair/retire responsibility; Phase17 supplies role-safe presentation; Phase6 materializes local in-product `available` using `prepared.none@1` where qualified. This produces **no provider artifact, provider ID or Resend call**, and no default email.

The exception is the source failure, not the preceding Save/Share operation. Ordinary successful operations remain quiet. Reading attention does not repair stewardship. Reassignment, retries, grouping or worker delay cannot renew an old episode. Repair, qualified retirement or another valid source conclusion determines completion. Names, private query text and restricted source details must not be copied into broader notification audiences.

## Independent data lifetimes and proof

Saved configuration, personal preferences, authenticated query-state handles, source content, current drafts, prepared delivery material, communication evidence and minimized audit history keep their own qualified purposes and lifetimes. A view does not retain matching conversation content or override D16 redaction/D17 expiry. Conversely, ordinary view archive is not an email recall or content-disposal command.

The complete [ratified decision](phase26-d20-adversarial-review.md), [UX](phase26-d20-views-ux.md) and [data contract](phase26-d20-data-contract.md) require these boundaries to hold across UI, API, grants/RLS, privileged paths, caches, exports, migrations and restores. The [ratification validation](d20-ratification-q21-validation.json) proves documentary preservation and consistency only. The 44 runtime, authorization, concurrency, migration, capacity, browser, accessibility and staff proof groups remain required and unexecuted.

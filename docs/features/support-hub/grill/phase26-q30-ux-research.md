# Q30 — Independent research: the Support reporting home

**Research date: 13 September 2026. Q30 is unanswered. D1–D29 are founder-ratified.** This document supports the [actual Q30 question](phase26-q30-support-overview.md). It recommends a product scope; it creates no accepted D30, metric definition, formal specification, ticket, implementation or production-readiness claim.

## Recommendation and three real alternatives

Recommend **A — A focused Support overview**, with a visibly separate **Work now** area and **Results for a selected period** area. It brings together a small selection of the already-ratified work and reporting capabilities. Its value is helping someone find the next useful place to go, not increasing the number of metrics or creating a Support health score.

| Option                                           | Actual user experience                                                                                                                                                                                              | Strongest reason to choose it                                                                                                                               | Real cost                                                                                                                                                                                              |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A — A focused Support overview — recommended** | Open one curated reporting home, understand current work and selected period results, then follow an exact link to the relevant list or detailed report. Existing work views and reports remain directly available. | Useful without setup; a common composition reduces repeated navigation and gives a team consistent terminology.                                             | Product must choose the useful summary carefully and maintain its scope, freshness and drilldowns. Some specialists will prefer a different arrangement.                                               |
| **B — Work views and separate reports**          | Current handling stays in the accepted work views. A clear Reports index leads to reply/target, label and feedback reports; there is no combined overview.                                                          | Lowest additional interface and configuration burden. Credible for a small team that uses reports occasionally and already knows where to find each answer. | Cross-report review takes more navigation and mental comparison. B retains all accepted reporting and correctness work; it does not preserve flawed current calculations.                              |
| **C — A configurable Support overview**          | Start with a useful default, then qualified users choose, arrange and save combinations of approved report blocks, with governed sharing where needed.                                                              | Valuable when operational roles or several inboxes repeatedly need different combinations. C need not be a blank canvas or an arbitrary report builder.     | Adds composition ownership, saving, sharing, reset/defaults, block/filter compatibility and ongoing maintenance. It must qualify shared reporting composition, not introduce a Support-only BI engine. |

These are alternative scopes, not three modes to implement together. A is a product judgment on the available evidence. No Asym usability study or tenant-volume study establishes that every ministry needs a dashboard, that A saves a measured number of steps, or that personalized layouts are necessary. C is a serious alternative when repeated differing needs are demonstrated. B is sufficient where a new overview would mainly repeat information staff already use effectively.

## Proposed complete journey if A is selected

The following is a candidate direction for the selected answer's later adversarial review. It does not freeze a final card list, date preset, chart count, refresh interval or saved preference model.

### Person overseeing work: look, understand, investigate, return

1. **Open Support → Overview deliberately.** The ordinary conversation destination remains directly reachable. An overview need not become every responder's landing page. Begin in a clearly identified authorized tenant/inbox scope, not an unrestricted tenant total.
2. **Read Work now.** Put current actionable work first. Its meaning is current work regardless of original age, with a visible As of/refresh state. A historical period change does not remove an old unanswered request. Overlapping work groups are not an additive total or pie chart.
3. **Open the exact work.** A readable label and count lead to the qualified matching list. Explain source scope without requiring knowledge of query syntax. A count of waiting periods must not promise the same number of unique conversations; use the correct detail destination or disclose the distinct units.
4. **Handle the request in the shared detail.** Support commands retain their existing permissions and behavior. Relevant CRM context is loaded only when authorized. Report access does not permit donor, giving, care or missionary mutations. A diagram, chart or score never becomes a new authority to change a record.
5. **Return without rebuilding the review.** Preserve the permitted tenant/scope, period, report location and useful list position. Recheck current access on return; do not replay stale private results after a permission or account change. New evaluations may legitimately differ, so show the new As of state rather than promising an immutable live screen.
6. **Review a period separately.** The period control belongs visibly to Results for a selected period. Compact summaries lead to the already-qualified report families. Where their cohort meanings differ, name the difference; use a report link instead of compressing an important qualification into an unreadable tooltip.
7. **Understand unavailable information immediately.** Loading, failed, stale/incomplete, disabled feedback, no eligible sample and measured zero are distinct. A source failure cannot render a reassuring zero or prevent ordinary conversation work. A read-only reviewer can investigate permitted detail without being shown unusable mutation controls.

Illustrative nonprofit fit: a staff member coordinating donor-care or missionary/project-related requests could use this journey to find unanswered work and review what was actually measured. This does not establish a particular staffing structure, call volume, weekly meeting or donor-care performance target. Support reporting describes Support work; it is not giving analysis, ministry impact or a donor-value ranking.

### Everyday responder: get to work without a management detour

A responder can open their established work view directly, act on authorized requests, consult the overview when useful and return to the same work. The overview should not require a daily acknowledgement, ask for capacity/status declarations or create extra work just to fill its charts. Counts or assignments do not measure effort or case complexity. It should not pressure people to close requests early to improve an unqualified score.

### Maintenance differs materially across A, B and C

**A:** the product maintains one coherent composition and source mappings. Authorized scope preferences may be simple, but no tenant dashboard-design project is required. If a metric is unavailable, show a truthful state and its qualified destination instead of substituting another formula. Existing source policy changes retain their owning configuration flow.

**B:** maintain a clear report index, names, return paths and cross-links. This is smaller than A, but still requires the same accepted report definitions, samples, coverage, authorization and recovery behavior.

**C:** additionally define who can create/edit/use/share a composition, what saving changes, how to restore the default, what happens when a referenced block or filter is unavailable, and how old saved layouts upgrade. Layout sharing never grants data rights. Editing should make unsaved changes and cancellation scope clear. Those are real obligations to resolve if C is selected, not reasons to make C intentionally difficult or pretend it requires arbitrary SQL.

## Visual clarity and proof expectations

Use the established Asym shared components and typography, calm spacing and ordinary reporting navigation. Work now needs action clarity; historical information needs honest comparisons. Small tables or horizontal comparisons can be more legible than decorative gauges, donuts or competing bright cards. Charts are justified only where they help answer the specific question. Long inbox/label names, translated text, locale-aware date/number formatting and the explicit reporting timezone need space, not truncation without access to the full meaning.

On mobile, preserve semantic reading order and direct links rather than compressing a desktop grid into tiny widgets. At zoom, the scope, units, uncertainty and destination must remain readable. Tables need explicit headers and relationships; color must have a textual counterpart. Loading and retry messages need accessible status treatment without disruptive repeated announcements. These are evidence-backed design directions, not proof that a design has been rendered or tested.

After selection, proof should include: a very old unanswered request remaining in Work now while the period changes; an exact metric-to-detail journey; merge-aware label membership; an issued-but-submission-indeterminate feedback response; differing reply clock/sample units; permission revocation between summary and drilldown; unauthorized inbox totals never appearing; empty versus Off versus error states; return navigation with current authorization; and keyboard, screen-reader, mobile, zoom and low-bandwidth use. Production-shaped performance and complete pagination also need measured implementation evidence. No benchmark, usability session or browser test was executed for this research question.

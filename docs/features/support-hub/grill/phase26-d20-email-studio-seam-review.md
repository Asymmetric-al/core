# D20 independent review: saved views and the Email Studio boundary

**Reviewed 12 September 2026.** D20 is fully founder-ratified. This review makes its existing R01/R24 and D18/D19 boundaries explicit; it does not add a channel, approval flow, template key, audience builder or implementation authority. Repository observations were made in `/home/conrad/code/core-worktrees/grill-with-docs-2026-09-10` at `7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd`. Root `AGENTS.md` was read. This is documentary/source review, not database, provider or UI execution proof.

## Finding and disposition

**Accept the D20 seam with the clarifications below.** Saved views belong to Core's shared named-view/list capability. Email Studio owns reusable message content and the governed presentation/preparation contracts used when an actual communication or qualified notification occurs. Similar **My/Shared** language does not imply the same aggregate, permissions, publication engine, lifecycle or synchronization.

The consequential ambiguity to remove is an absolute statement that views can never have a Phase 6 event. Ordinary view operations have no communication effect, but D20 O03 already requires source-owned maintenance attention when an active Shared view has no eligible maintainer. A real failed source obligation may use the existing P17/P6 local attention contract. That is a separately qualified source occurrence, not a notification for saving, opening or sharing a view.

## Required seam clarifications

1. **Capability reuse stops at real ownership.** R01 reuses platform named-view/list/preference behavior. It does not reuse Email Studio Saved Sections or copy their publication tables merely because both expose My and Shared. The roadmap expressly requires one shared saved-view capability across surfaces; P9 explicitly distinguishes a live query from a membership container. [Roadmap](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L4156), [P9 A14](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/phase-09-full-crm-depth-relationship-graph.md#L498), [P9 B11](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/phase-09-full-crm-depth-relationship-graph.md#L613).
2. **Do not turn curation into publication bureaucracy.** D20's deliberate qualified Save shared view/Save changes is configuration maintenance. No template Publish button, publication status, mandatory Email Studio visit or extra content-review queue belongs in this view journey. Existing applicable policy floors still hold. A shared-view maintainer, inbox reviewer, support reply author, Email Studio publisher and CRM operator are distinct capabilities even when one human has several.
3. **Keep stable targets across navigation.** View changes or archival may alter availability of the list/definition, but do not by themselves cancel an already valid conversation draft, admit a reply, supersede a communication intent or change recipients. Actual source/permission changes still apply immediately. Existing message commands use conversation identity, draft revision, recipient authority and their own source fences—not the saved-view revision as a substitute.
4. **No implicit mass audience.** Current result membership, even an exported list or a badge count, cannot serve as future dispatch membership. D20 R14/R24/P31 require explicit stable selected targets and current authorization for existing commands. D20 does not create marketing segments, bulk sending, scheduled exports, digests or reply-to-every-result behavior.
5. **Human reply preparation remains exact.** Once the staff member is in an authorized conversation, D18 applies unchanged: eligible reusable content copies to the draft; P17 prepares the exact reviewed external message before atomic Support admission; P6 owns dispatch/evidence under actual recipient-copy/submission specificity. A whole To/Cc group is not sent again for each member. Prepared dispatch recovery cannot rerender from a changed Shared reply or consult a changed saved view. [Canonical message ADR0030](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/adr/0030-canonical-message-document-and-presentation-dependencies.md#L18), [Prepared-message ADR0032](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/adr/0032-immutable-prepared-message-and-whole-message-recovery.md#L19), [P6 A17/A18](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/phase-06-shared-communication-event-model.md#L175).
6. **Keep the quiet-default and maintenance-exception statements compatible.** Suggested exact restatement: “Save, Open, Pin, Share, Rename, Archive and Restore create no communication or notification enrollment. A separately qualified, real failed configuration-maintenance obligation may create source-owned local staff attention through the existing P17/P6 contract; it is not a side effect of healthy view activity.” An ownerless active Shared view under O03 is the concrete example already accepted.
7. **Qualify that local attention before activation.** Bind the real producer, exact failure/source episode, applicability/end rule, recipient-role authority, safe fact schema and typed repair destination, occurrence identity and correction behavior to a compatible P17/P6 contract. Do not borrow D19 intake-attention meaning, an unrelated delivery-repair key or a generic email template. Exact physical key names are implementation qualifications, not a new founder feature choice.
8. **Use the local no-artifact posture.** Source-backed required maintenance attention uses `prepared.none@1` and P6's local `available` occurrence. It creates no Resend request, external preparation, provider message ID or queued/sent/delivered status. P17 presentation must not embed private saved criteria, search literals, source bodies or inaccessible labels in notification previews. The source-owned required-work presentation policy and existing privacy ceiling apply. [ADR0027](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/adr/0027-one-notification-presentation-and-engagement-model.md#L18), [ADR0032 no-artifact posture](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/adr/0032-immutable-prepared-message-and-whole-message-recovery.md#L61).
9. **Keep end-of-work truth with the source.** A source-maintenance exception remains actionable until repaired or otherwise correctly concluded. Marking read is engagement only. Actual correction ends actionable treatment; the existing once-set source end and authorized recent-history policy cannot be extended by retries, viewing or reassignment. Permission loss removes visible projection immediately. No new per-view attention retention knob is required.
10. **No confirmation or intake coupling.** Opening a view never makes held intake Support-ready and cannot cause or restart D13's new-request confirmation. D19 intake surfaces and D13's separate Support request received template/original eligibility window remain unchanged. Views also cannot bypass D16 redaction or D17 content expiry.
11. **Tenant transport authority stays outside configuration.** An actual email sends through the established tenant-owned Resend connection and frozen delivery identity. Saved-view state contains no From, Reply-To, connection, template, raw recipient or provider override. No new Email Studio or Resend readiness requirement should block creating a normal saved view. [Tenant-owned Resend ADR0029](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/adr/0029-tenant-owned-resend-and-composed-delivery-identities.md#L18).
12. **Prove boundaries at their actual layer.** D20 P01 proves shared-capability ownership; P20/P25/P26/P29 protect source/CRM scope; P31 proves explicit command targets; P33 proves healthy view operations cause no P17 publication, P6 send, Resend call, follow or subscription. O03's separate qualified maintenance occurrence should additionally prove local-only materialization, role-safe facts, durable episode idempotency and actual source completion. D18 and D19 proof remains inherited; this document is not execution evidence.

## Review limits

No new runtime feature or provider behavior is asserted. The source corpus establishes intended platform ownership and accepted D18–D20 contracts; it does not establish that the named-view generalization, P17/P6 seams or new Support permissions already work in production. This addendum introduces no new Email Studio template, channel, role or approval policy and does not expand D20's seven operational controls.

# D37 — Private My drafts with dependable save and resume

**Current ratification — 14 September 2026:** The founder has fully ratified D37 A and all amendments, additions, adjustments, changes, updates and final corrections. D1–D37 and all amendments are fully ratified. The [complete ratification](phase26-d37-full-ratification.md) incorporates this record in full, including all supporting prose. Earlier proposed/pending/intent-only and no-Q38 wording below is historical and creates no repeat approval gate. Evidence and unexecuted runtime-proof limits remain unchanged.

**14 September 2026. Disposition: Accept with required amendments.** The founder selected **A — A private My drafts view**, with seamless UX and Tiptap-qualified technical planning. A is recorded at intent level; the detailed amendments below are proposed for ratification. D1–D36 and all their amendments remain fully ratified. Q37 is answered at intent level; no Q38 is opened. This is exploratory decision documentation, not formal OpenSpec, implementation tickets or shipped behavior.

The complete journey is **write → saved quietly → My drafts → resume in the same conversation → send or deliberately discard**. The view is a personal finder over one canonical private draft owner. It is not another inbox, conversation status, CRM note, shared document service or email outbox.

## Exact corrected decision

Support provides a stable, private **My drafts** entry for the current staff member's saved external Reply drafts across currently accessible Support inboxes, independent of ordinary conversation work-status filters. Rows show permitted conversation metadata and authoritative save time, with no draft-body preview or body indexing. Opening a row restores the same exact source-owned draft and current qualified context in the existing Tiptap composer. Quiet bounded autosave and explicit save recovery preserve one atomic draft bundle; current authorization, optimistic concurrency, cancellation and durable operation identities prevent loss, exposure or duplicate sends. Discard is explicit and conditional; send consumes the exact draft through existing Support/P17/P6 admission and immutable delivery. CRM uses the same authorized source. R01–R28 and the linked contracts are the complete proposed corrected decision.

## Required clauses

### D37-R01 — Scope, need and strongest alternative

Select A as the primary finder for saved, unsent external Support Reply drafts. Existing direct restoration on returning to a known conversation remains. B, a My draft filter within ordinary views, is the strongest smaller alternative but requires users to understand intersecting status/inbox filters; C, a compact picker, has less overview space. Neither is added as another setting or parallel finder. Preserve separate new-Note working state and D35 local posted-note edits without inventing their durable storage or adding them to this initial list. No shared drafting, approvals, scheduled sends, AI drafts, outbound prospecting or product-wide My work surface is introduced.

### D37-R02 — Stable entry and restrained information architecture

Place **My drafts** in Support's existing conversation/work navigation group, separate from shared/saved work views and Email Studio authoring. Keep it discoverable when empty; do not make the navigation appear/disappear as someone types or force it as the landing page. Use the same name on narrow screens. Start without a sidebar count, red urgency badge, global reminder or extra overview tile. A source-qualified personal **Draft** indicator on an already rendered conversation may link to that exact own draft; it is not a shared indicator or proof of unsaved local text. Do not add the unchosen global filter/picker product merely to provide this modest inline continuity.

### D37-R03 — Complete personal population, not work status

The default scope is the current actor in the current tenant and all currently accessible Support inboxes. Include every eligible active saved Reply draft regardless of Open, Waiting, Resolved, assignment or current ordinary view. Source access/privacy/retention and actual draft lifecycle still decide eligibility. One row represents one canonical draft, not one merged handling root or one CRM person. Merged original conversations may therefore have separate own drafts; preserve original source identity and enough permitted context to distinguish them. Do not hide unfinished writing merely because a colleague resolved, moved or reassigned the conversation. Opening a draft never changes that work state.

### D37-R04 — Readable rows, minimal controls

Use compact responsive rows with permitted conversation title, current qualified source/inbox identification, authoritative **Saved [time]**, and a concise existing-state label only when it changes the next action. Use an admitted conversation/requester display projection, never the draft body's first line or an unrestricted CRM lookup. Missing/permitted redacted titles use the owner's neutral label, not stale cached content. Each row opens directly; no separate Edit or Load screen. A separate accessible action menu offers **Discard draft**. Do not place Send, Send all, bulk discard, new compose, rich-text previews or mounted editors in the list. Long titles wrap appropriately, and a saved time exposes localized absolute time and zone without requiring hover.

### D37-R05 — Scoped search, filtering, ordering and pagination

Provide **Inbox: All accessible inboxes / one authorized inbox**, **Search conversation titles**, and Refresh. Search uses the existing qualified title/source search semantics and index eligibility; it does not search draft prose, private recipients, quote bodies or restricted CRM fields. Do not introduce a new draft-body corpus, direct-scan bypass or arbitrary saved-view grammar. Blank search returns the scoped personal list. Default ordering is last accepted meaningful author edit descending, then stable draft ID; reads, same-content saves, safety checks and worker callbacks do not make a draft recent. Use server keyset pagination, initially20rows, maximum50 per request, no truncation of the overall population. Those are proposed UI/query bounds, not a total draft limit. No exact total count is required. Show honest loaded-result information and Load more; preserve focused row/scroll and expose Refresh/Results changed rather than reorder under a pointer. Existing D22 200ms debounce/IME/explicit Enter behavior may be reused for this title query.

### D37-R06 — Trusted owner and stable cardinality

A saved Reply draft has one immutable original source, tenant and real staff owner plus a stable identity and current revision. Enforce at most one active external Reply draft per tenant, trusted owner and original conversation. Explicit D2 retarget changes the current target inside that same draft under review; it does not silently create a second draft. Merge/unmerge uses original identities and never collapses private drafts by continuing root, email or CRM Party. A deliberate new draft after accepted send/discard uses a new lifecycle identity/generation; old writers cannot recreate a terminal one. Preserve actual TEXT source IDs and UUID tenant/profile/auth relationships rather than assuming they are interchangeable.

The immutable draft origin is its private working-slot anchor, not published reply source affinity. D10 permits explicitly targeting a B message while working in merged A: preserve the draft's stable origin, content and identity, show the distinct current target/source, and revalidate both required source dependencies. The actual target B determines reply admission/source affinity under D10, never the draft anchor A. Two independently anchored drafts may deliberately target B; existing component-wide collision review still prevents stale double handling. Merge Undo/current access may invalidate this cross-source target and require review, without silently rehoming the draft, copying it into another active slot or publishing the reply under A.

### D37-R07 — Meaningful creation without phantom drafts

Opening Reply, focusing/selecting text, reading a source, hydration, loading a preference or seeding the normal signature creates no persistent draft and no My drafts row. First deliberate meaningful author change to the draft bundle may create it: prose/formatting, quote/wording insertion, intentional audience/target/subject/signature omission, admitted attachment selection or staged shortcut work. Preserve incomplete work rather than requiring send-ready content. Once a draft exists, clearing its body does not silently discard it, erase the audience/plan or reset its lifecycle; it remains with an honest **No reply text yet** state if needed until Send or explicit Discard. A default signature alone in a newly opened empty composer remains non-draft baseline. Exact canonical equivalence and creation intent are server-validated, not a browser text-length guess.

### D37-R08 — Quiet bounded autosave

Save eligible user changes automatically after750ms of quiet, with an attempt by5seconds after the first unsaved eligible change during continuous input. These are proposed engineering scheduling targets in a foreground, online, authorized, valid-schema, non-IME-composing editor—not durable-save latency promises. Coalesce to the latest coherent bundle, with at most one in-flight save per active draft controller. Do not start a competing save while the previous result is unresolved. A delayed, offline, background-throttled or blocked editor shows truthful status and saves when eligible again; elapsed time does not manufacture Saved. Selection/focus/toolbar inspection/hydration/no-op transactions are not saves. **Save now** flushes deliberately when changes exist, and **Retry save** repairs an eligible failure; neither sends or resets the editor. Reuse one shared private-draft controller, not a timer on every list row.

### D37-R09 — Draft-safe content is not send-ready content

The save command admits a structurally valid, purpose-qualified incomplete draft, including absent audience, incomplete authored text and explicit unresolved typed fill-ins. It does not require a final email address, complete message or executable work-plan eligibility merely to preserve writing. Conversely, arbitrary/unknown canonical nodes, invalid protected source metadata, unsafe links/assets or expired/restricted material are not harmless incompleteness. Prevalidate the full document and closed metadata schema before Tiptap normalization; retain an explicitly typed missing/invalid-for-send state where appropriate. Do not accept arbitrary raw recipient blobs or HTML as a back door. Real address, content, source/disclosure, attachment and staged-action requirements still block preparation/admission at Send. Saving never executes variables, mentions, shortcuts or source actions.

### D37-R10 — One atomic bundle and exact acknowledgment

Persist canonical structured document, explicit target/audience and action provenance, managed signature/wording/quotation references, attachment-selection manifest, staged shortcut plan, owner/schema/source generations and draft revision atomically. A body-only save cannot report Saved. Server context derives tenant/real actor and validates every reference. The browser binds an acknowledgment to the exact submitted operation and client draft generation. **Saved** means the newest eligible local bundle is durably acknowledged; an older successful acknowledgment may advance the known base but never marks later typing Saved or overwrites it. A canonical no-op produces no new content revision or recency time, while its operation/result identity still remains unambiguous.

### D37-R11 — Concurrency without collaborative editing

Save uses expected revision and current owner/source/privacy/lifecycle guards. Two devices or tabs starting from the same base cannot silently overwrite each other; one wins and the other receives a conflict with its own permitted candidate retained. Show **This draft changed elsewhere**, the currently permitted saved version and local unsaved work through the existing qualified editor/review pattern. Let staff deliberately reload current saved content or reapply their changes against the new base. Do not offer a blind overwrite, automatic merge, CRDT/Yjs service, shared editing lock or cross-user takeover. An inactive clean editor may refresh current authorized state; a dirty editor never replaces its document from a list refresh, ACK or setContent callback. D34 awareness remains neutral and is not a lock or draft authority.

### D37-R12 — Unknown results and durable effect identity

Bind each admitted create/save/discard operation to exact tenant/owner/source/draft generation, expected revision and semantic command hash. Reusing the same operation with different input conflicts. Unknown response means **Checking save** or **Save status unknown**, not success/failure or permission to create another draft. Recover the original operation under current access; an empty lookup is not proof of nonacceptance while an old request can still commit. The owner protocol must fence late admission before proving definite nonacceptance. Keep a minimal body-free operation handle/result through supported navigation; no second private content ledger. Replay returns original result separately from the current draft snapshot. Canceling HTTP or unmounting a component does not roll back an accepted write.

### D37-R13 — Navigation, IME and browser lifecycle

Navigation that keeps the composer mounted, including eligible CRM side context, does not disturb it. Before supported navigation would unmount a dirty composer, finish IME composition and flush the latest committed bundle through the draft owner. On routine confirmed save, continue without a modal. While unresolved show Saving/Checking save and preserve work. On known failure offer Retry/Stay or an explicit **Leave without saving these changes** choice; do not silently drop the candidate. The latter abandons only the local delta and cannot undo an already accepted server operation. If an outcome remains unknown, do not trap the person until reconciliation succeeds: offer the same explicit Stay or Leave choice, stating **The earlier save may still finish; your latest unacknowledged changes may be lost**. Keep the scoped original-operation handle for later recovery; leaving does not prove cancellation or nonacceptance and cannot authorize a new Send. Do not repeatedly block the choice behind a failing status lookup. Browser close/crash warnings are best-effort; no new offline outbox or guaranteed last-keystroke recovery is promised. Source/privacy loss and real account/tenant changes clear forbidden bodies/Undo regardless of navigation guards. No unbounded collection of hidden mounted editors or localStorage/IndexedDB body archive is introduced.

A navigation guard also accounts for local-only pending attachment bytes even when text is acknowledged. If leaving would destroy the current upload/controller, keep its existing qualified transfer alive, wait for completion, or offer explicit **Leave without this unfinished attachment** while preserving saved text and truthful pending/failed file state. Do not claim a saved manifest can recover a browser File. Combine text/unknown-save/file consequences in one focused navigation guard rather than stacking dialogs. No new offline attachment store is required; owner cleanup handles abandoned upload occurrences.

Keyboard Send must respect IME/composition, near-composition Enter, defaultPrevented, key repeats and active popup/editor handling. Do not snapshot/send on a raw compositionend callback before the editor's pending DOM transaction has settled. Qualify the actual installed editor/browser commit path, including microtask ordering, rather than copy a browser-specific500ms heuristic as product timing. Programmatic setEditable/setContent events are not proof of human document edits. The current hotkey path without these guards must be replaced before activation.

### D37-R14 — Resume the exact saved draft

Selecting a row performs current owner/source authorization and restores the exact saved bundle into the existing Support conversation composer. Do not first flash defaults, newest-message target, current CRM email or a blank editor and then overwrite it. Load one draft body only when opened; no body prefetch for the list. Preserve D24 pending work, D23 signature pins and D36 quotations/semantic attribution. Changes requiring review stay visible and cannot readdress or repersonalize content automatically. On desktop focus the resumed editing context deliberately after current loading; on mobile show source/recipients before user-directed keyboard focus. Same-session return restores list search/filter/scroll/selected row where available; cross-device persistence guarantees content/context, not an exact caret coordinate. A failed open leaves a truthful retry/unavailable state, not a blank new draft.

### D37-R15 — Actual source changes and incomplete eligibility

New relevant input, changed participants, relinking, inbox movement, merge/unmerge, source restriction/expiry, role changes and tenant policy changes requalify the exact retained draft under prior contracts. Metadata-only changes do not cause a gratuitous content conflict. A readable draft whose send context needs review remains resumable with **Review needed**, without pretending the source can be reconstructed from CRM. Source/privacy loss may require withholding the affected content or row; never expose forbidden existence/counts through a disabled item. Do not call all unresolved provider outcomes Review needed drafts; they use the existing operation-recovery status. Saving, viewing or drafting does not reopen a conversation, renew its retention anchor or satisfy a reply target.

### D37-R16 — Deliberate discard, no hidden trash product

Offer **Discard draft** in the row/composer's existing actions, with one concise confirmation identifying the draft and explaining that saved reply content and pending draft-only changes will be removed, while conversation/messages remain. Cancel does nothing. Confirm uses current ownership and the exact reviewed revision/lifecycle; if another tab saved newer work, show the conflict and require renewed review rather than discard it unseen. Commit terminal discard and cleanup obligations atomically. Retain only the body-free retirement/operation evidence needed to reject late writes/replays; no normal Restore, timed Undo promise, second trash inbox or bulk discard is added. Pending/possibly accepted Send cannot be canceled by discarding a draft. Ordinary editing Undo before discard remains separate. File cleanup affects only eligible draft-owned occurrences; it never deletes independently owned source files.

### D37-R17 — Send consumes the draft through existing admission

Deliberate Send uses the newest exact reviewed draft bundle with current revision, target/audience, source/quote/privacy and staged-work guards, ready P17 preparation and D4 atomic local admission. In that admission, mark the exact draft generation consumed and link the admitted intent so concurrent autosave, discard or Send cannot create divergent effects. A validation/pre-admission rejection preserves the active draft. If local admission is uncertain, reconcile its original operation; do not leave a fresh editable resend in My drafts. A confirmed admitted reply is no longer an active draft even if transport is queued, failed or unknown; delivery recovery stays in the conversation/P6 owner. Later failure does not automatically resurrect its old draft. Any genuinely new reply is explicitly new work with a new draft/intent identity after required review.

### D37-R18 — Privacy, retention and attachment custody

Apply D16/D17 and each owner deadline to canonical drafts, dependencies, attachment occurrences, controlled cached/derived representations and temporary server material. Draft creation/editing/reads/autosave are not native content admission or renewal of a linked source's lifetime. No new24-hour/30-day draft rule is copied from vendors, and no indefinite private body custody is promised. The release retention inventory must name actual draft/body/attachment/control-receipt horizons and restore barriers before activation. A source stop invalidates unsafe quote/wording/file material even if a worker is late; preserve independently safe author text only when qualified separation is proven. Upload-in-progress local selections are not completed server-saved bytes; indicate separately that the file has not finished uploading. Discard/consumption removes only this draft's custody through owners, preserving immutable sent and independent original evidence.

### D37-R19 — Enforce the private database boundary

Qualify one private Support draft store and authorized finder projection. Do not expose current support_messages draft-delivery rows and merely filter their UI. Tenant-aware primary/foreign relationships must bind original source, real owner, draft, dependencies, assets and operation receipts; non-null identity/purpose, revision checks, active uniqueness and terminal-state constraints prevent invalid combinations. No generic staff CRUD or caller author field can mutate private owner/source/approval/admission identity. Actual service-role paths repeat current actor/tenant/source checks. Use least grants, RLS on exposed data, effective SELECT/USING/WITH CHECK, safe views, RPC EXECUTE/search_path/definer closure and constrained immutable columns. Check permissive-policy combinations and all old writer routes; FORCE RLS is not protection from every bypass role. Deletion does not cascade into conversations, CRM/giving records or required intent evidence. There are no new money fields.

### D37-R20 — Tiptap is the editor, not draft authority

Reuse the shared Tiptap3 Reply profile and code-owned schema/static renderer; apps consume shared Base UI/base-maia components. SSR-safe initialization remains immediatelyRender:false. Gate every restoration before setContent and suppress synthetic update emission deliberately; emitUpdate:false alone cannot stop stale overwrite or schema loss. Isolate the active editor from list refreshes and subscribe toolbar state narrowly; selection-only transactions do not dirty the draft. Hydration runs after exact current document/source validation and cannot fire autosave, template expansion, mention callbacks or user-edit recency. Unsupported saved structure produces an explicit read-only migration/repair state, never a successfully saved stripped/empty document. No read-only editor per row, document history SaaS, Tiptap Cloud/Yjs/AI or provider draft sync is required. Package/version closure is qualified as a shared upgrade decision, never an automatic dependency change in grooming.

### D37-R21 — Source ownership and authoritative projections

Support owns the private human draft, its source/actor, revision, save/discard/consume operations and finder. PostgreSQL holds authoritative draft state; the list and caches are expendable current-authorized projections. P17 owns reusable content/schema/presentation and complete-message preparation; D18/D23 sources are pinned copies with retained adverse fences, not live mutable links. P6 owns intent/delivery recovery and actual communication evidence. My drafts is not Email Studio's Draft publications, a shared saved view, CRM activity, scheduled mail or an SLA queue. Neither the list nor draft-body HTML is a write authority; one canonical structured bundle remains authoritative.

### D37-R22 — CRM and identity continuity

A draft begun through authorized CRM Support context is the same private draft found in My drafts. Opening it preserves a qualified return route without duplicating CRM bodies or permitting restricted related-record reads. An authenticated principal, Support draft owner, assignee, requester, participant, CRM person, represented organization and record owner remain distinct. Matching email, reassignment, membership in a conversation or an administrative role does not grant another worker's drafts. A departed person's draft is not silently handed over; qualified staff continue the actual Support obligation with their own authorized writing. Viewing/saving/discarding creates no Party/contact, relationship, Activity, finance mutation or business-completion claim. CRM remains usable independently of Support.

### D37-R23 — Email Studio preparation and publication seam

My drafts discovery, restoration and ordinary save invoke the qualified editor/document validation capability but create no delivery preparation, message intent, template publication or email. Human reply content remains Support-owned and outside the finite system-message catalog. At actual Send, P17 prepares the whole reviewed canonical body, audience context, signature/footer, quote attribution and authorized assets through the existing compatible contract. It does not reinterpret literal source tokens, append history or refresh mutable signatures/CRM values. P6 seals exact material and reconciles the immutable envelope under ADR0032. Opening a draft cannot trigger D29 confirmation, D15 attention, D28 feedback or a shortcut plan; those owners retain their existing real triggers. Source/reference safety may be checked without creating a new outgoing message.

### D37-R24 — Responsive, accessible and stable interaction

Use restrained semantic rows and existing shared inputs/menu/dialog, not a card dashboard or new visual system. Heading/entry remain My drafts; helper copy explains Only you can see these saved replies without implying no exceptional records/privacy custody exists. Keyboard Enter on a row opens, never sends; menu/discard focus returns predictably. Maintain logical reading order, visible focus, touch hit areas and contrast; default no automatically raised mobile keyboard obscuring context. Qualify320CSS-pixel reflow,200% text resize,400% zoom-equivalent reflow, long international names, Thai/RTL, timezones, IME and reduced motion. 44CSS-pixel touch hit area is an Asym product target, not a claim that WCAG's24CSS-pixel minimum/exceptions require44. Save/error/result messages are accessible but do not announce each keystroke or every successful autosave.

### D37-R25 — Failure, freshness and bounded performance

Read the finder on entry, applied query/scope change, explicit Refresh and relevant foreground reconnect/invalidation. Coalesce requests and bind them to tenant/actor/scope generation; a stale response cannot replace a newer list. No per-keystroke list polling or perpetual full-tenant subscription. When refresh fails, label results out of date only while current authorization/privacy permits retaining them; otherwise clear affected metadata. No permission/missing/incomplete/error result becomes zero drafts. Body fetches occur only for an opened draft and use current checks. Index owner/tenant/lifecycle/meaningful-edit sort and source dependency lookup before pagination; enforce shared document/node/depth/asset/operation/query limits before expensive processing. Publish actual numeric profile and measured workload/latency before activation. The20/50row page bounds and750ms/5s scheduling targets do not prove server performance or total capacity.

### D37-R26 — Migration, activation and rollback

Inventory current drafts and alternate writers before enabling the finder. Current caller-author/isPrivate:false message rows cannot be relabelled private without positive trusted provenance; ambiguous legacy rows stay in owner-qualified restricted migration/repair custody, never assigned by email/text resemblance or silently destroyed. Deploy compatible private schema, grants, source checks, operation handlers and readers before new writes; then qualified Tiptap restoration/autosave and finally My drafts. Old readers/writers must fail closed on unsupported schema/generations and cannot strip unknown nodes or recreate discarded/consumed data. Backfills are idempotent with explicit source/owner evidence and preserve D16/D17 history. Kill switches stop affected new writes/finder exposure while keeping authorized safe reading and accepted-send reconciliation. After new data exists, use compatible roll-forward; rollback cannot restore the broad old writer or replay mail.

### D37-R27 — Observability, audit and residual operations

Use body-free draft/operation/version correlation, typed save/discard/admission outcomes and bounded latency/conflict metrics through existing observability. No editor JSON, source body, recipient addresses, filenames, signed URLs or raw exceptions in logs. Saving every few seconds is not a CRM Activity or employee productivity trail. Ordinary revisions provide concurrency, not a new user-facing version-history product; retain only actual owner-governed recovery evidence. Source privacy/retention operations retain their separate durable audit. O01–O05 in the proof record name residual signals/thresholds/owners/responses. Disclosure, lost text, duplicate effect, silent schema loss and unsafe send are release blockers and containment triggers, not monitor-only accepted risks.

### D37-R28 — Proof and stage discipline

Require the32release groups in the proof record on actual qualified UI/editor/API/database/role/consumer paths. Prove list completeness/privacy, meaningful creation/no-op, whole-bundle save, multiple-tab/IME/navigation/lost-response behavior, source stops, conditional discard, atomic send consumption, migration, accessibility, performance and CRM/P17/P6 continuity. Record actual dependency versions, resource limits, environment and production-shaped data. Static/source/helper probes and document checks remain explicitly limited; no live database, browser/AT, provider or staff-study result is fabricated. Trace to formal OpenSpec/design/tasks/issues/implementation/release only after those stages are authorized. The complete design resolves this decision without expanding into an enterprise helpdesk or another Asym product.

## Material findings and exact proposed amendments

### DR01 — Shared signature content must have one owner

**Concern exists. Severity high; likelihood high if current records are extended naively.** Keeping signature HTML/text in Support while also editing a signature in Email Studio creates contradictory source ownership, publishing, sanitization and retention. Existing Support body fields and P17 canonical document rules demonstrate the conflict. This changes implementation and narrows A's interpretation; it does not reject the option.

**Exact clause:** “Email Studio owns the canonical structured signature authoring source, immutable publication, locale/presentation/assets and qualified compilation. Support owns the inbox's authorized signature binding and current reply selection. Both surfaces operate the same owning source and commands. Qualify a narrow published Saved Section purpose, Reply signature, distinct from D18 Reply and Internal note wording. A new external draft or explicit Refresh copies the selected exact eligible structured revision with provenance into its managed signature slot. The complete prepared document uses the existing compatible Service message layout. Support stores no second reusable editable signature HTML/text source, provider-template mirror or synchronized contact copy. No new Layout Role, per-inbox Role Layout, system-message catalog key or runtime fragment graph is introduced. The selected source does not remain a live nested reference and does not rerender existing drafts or prepared messages.”

**Required proof:** Edit from inbox context and Email Studio reaches the same source/revision; publication and binding are independently authorized; history is not a live lookup; repeated references cannot recurse; saving/publishing creates no conversation, CRM action or email.

### DR02 — An approved public responder name is not any display name

**Concern exists. Severity high; likelihood medium.** The selected option relies on a public-name fact not proven by present profile/agent fields. Generic profile editing can also rewrite full_name. Staff may serve several inboxes, use approved public aliases, or need team-only communication. Personalization from login email, legal name, assignee, CRM owner, first participant or unqualified profile field can misidentify or disclose a staff member. This requires a narrow owner qualification before activation.

**Exact clause:** “The authenticated current tenant-membership actor is the responder. Resolve that identity through the authoritative shared identity mapping, never by matching email or equating unrelated user/profile/agent IDs. Resolve an explicitly approved public responder presentation from its owning shared profile/presentation authority. Qualify existing fields before reuse; if no existing field has the needed external-disclosure semantics, add only the smallest tenant-membership-scoped public presentation facet through that owner, not a Support identity table or CRM duplicate. The public name is display wording, not a credential, legal name, role or permission grant. Editing it must not alter authentication, legal/CRM names, contact addresses, role or another inbox's approved presentation accidentally.”

**Required proof:** Different auth-user/profile/agent IDs, email change, shared address, two tenants, one person in two inboxes, inactive membership, public alias, long/unsegmented/RTL names, no public name. A privacy-safe approved team-only signature remains possible without creating fake CRM identities. Tenant-authorized public-name maintenance has clear actor attribution; no proof of universal nonprofit naming preference is claimed.

### DR03 — Public responder fields and required identity must have distinct validation

**Concern exists. Severity high; likelihood medium.** Empty optional title/contact fields can leave broken punctuation or tempt unsafe fallbacks. An all-purpose variable picker can expose location, care, giving or private staff contacts. Conversely copying From-header validation literally onto signature body text would overrestrict legitimate international display wording. This narrows values and validation, not professional styling.

**Exact clause:** “Signature personalization exposes only approved public name and explicitly qualified public role/contact fields for the actual responder, plus approved team/organization presentation. Missing optional fields omit their complete line/separator; required unresolved values either select the inbox's preapproved team-only presentation visibly before review or block preparation with a repair path. Never fall back to login email, private phone, legal/full name, assignee or sample data. Body text uses the body-output and bidi safety contract; mailto/tel links use their separate typed destination validation. Signature wording never changes From, Reply-To, thread subject, recipients, sender authority or external-action permissions.”

**Required proof:** Optional blank title leaves no orphan punctuation; unauthorized fields absent from picker/API/export; body name cannot inject HTML or headers; staff-role changes do not silently authorize a new title; a donor-care signature cannot assert a refund/receipt/business outcome without the owning domain's real action.

### DR04 — Ordinary composition does not grant publication or inbox administration

**Concern exists. Severity high; likelihood high if broad current staff CRUD survives.** The current common route gate and RLS let the same staff posture reach signature maintenance. A malicious or mistaken staff member could change everyone else's external wording or rebind an inbox. The selected policy requires distinct capabilities, without a bespoke approval platform.

**Exact clause:** “Separate permitted use, signature-source maintenance/publication, inbox-binding administration and public-profile maintenance through existing Core capabilities and scopes. Being assigned a conversation, following it, acting as its coordinator or reading an inbox does not grant signature publication, another person's public-profile mutation, CRM data access or sender administration. Apply existing Email Studio proportional review and protected/tenant-stricter requirements; do not require a new review workflow for every ordinary human reply. Tenant oversight does not silently grant access to restricted conversation bodies.”

**Required proof:** Ordinary responder can preview/use but cannot change shared content/binding; authorized maintainer can edit within permitted asset/inbox scope; unrelated-inbox or tenant calls fail; no anonymous/read-only collection route bypass; revocation is enforced after a stale browser session/cache.

### DR05 — Default replacement and publication need atomicity and expected revisions

**Concern exists. Severity high; likelihood medium, increased by concurrent administrators.** Existing two-request default clearing can leave no default when the second step fails, silently race or produce unique errors. Owner-scoped `is_default` is not the selected per-inbox binding. This changes permanent mutation semantics.

**Exact clause:** “Each active configured inbox has one unambiguous effective approved signature presentation for the selected human-reply mode and an explicitly qualified team-only fallback policy. Source publication and changing an inbox's selected eligible publication are distinct operations. The binding update compares the expected binding revision, validates same-tenant source/purpose/locale/eligibility and commits the replacement plus attributable audit atomically; no clear-then-set sequence or first-row fallback. Concurrent stale edits preserve the prior complete valid binding and offer reload/compare. Idempotent repeats return the durable existing result; conflicting immutable input cannot overwrite it.”

**Required proof:** Two simultaneous defaults, failure between conceptual clear/set, changed eligibility before commit, response lost after commit, duplicate command and wrong-tenant publication. If publish succeeds but a later separately chosen binding action fails, the source may exist unassigned and the former binding remains; UI reports those exact outcomes. A qualified Publish and use operation may update selected eligible bindings with expected revisions through a single owner-coordinated Asym transaction. Do not pretend independent authoring and binding transactions are one distributed atomic transaction, mandate a global all-inbox graph transaction for every source save, or silently rebind unaffected inboxes.

### DR06 — Draft pins, current defaults and safety revocation are different

**Concern exists. Severity high; likelihood high if “updates every reply” is interpreted literally.** A background signature edit, changed public name or changed responder can alter an already reviewed message. Blanket invalidation for harmless updates would also violate D4 and create needless friction. This amends temporal behavior.

**Exact clause:** “A newly composed reply resolves the current eligible inbox presentation and the actual responder's approved public values. The draft review identifies the selected exact presentation and personalization snapshot/revisions. Routine source/default/profile edits affect future resolution and do not silently rewrite an existing draft. Offer explicit Refresh signature with visible changed output when needed. A material change to actual responder, admitted audience, inbox/sender context or selected presentation requires a fresh authorized review before admission. Current safety, publication compatibility and disclosure fences remain enforceable; ordinary Archive is not automatically revocation. An unchanged valid pinned draft may remain usable under D4.”

**Required proof:** Draft opened before publication, default change while typing, view change, inbox move, different staff opening a private draft, retained same-language version, safety withdrawal versus routine update; no lost body edits or silent public-identity switch.

### DR07 — A prepared reply must never be rerendered from a current signature

**Concern exists. Severity critical for incorrect disclosure; likelihood medium.** Retrying after a profile/signature update can send a different body under the same intended reply. A provider may already have accepted the original. This repeats and makes D4/P6 enforcement signature-specific.

**Exact clause:** “P17 preparation seals the reviewed body, signature, HTML/plain text, public value snapshot, presentation/assets/compiler pins and exact audience. Support admits only the qualified preparation through its guarded durable send command. P6 uses the tenant's qualified Resend connection and its existing evidence/recovery rules. After preparation no signature edit, public-name change, archive, default swap, cache refresh or retry rerenders or rekeys that prepared message. A current safety fence follows the existing definitely-unsubmitted versus may-have-submitted recovery path; it never replaces bytes inside an ambiguous existing send.”

**Required proof:** Timeout after possible acceptance followed by signature edit produces no fresh message; key-window expiry cannot trigger rerender/rekey; definite no-send invalidation permits only explicit corrected new intent under owner recovery; routine changes never mutate sent history.

### DR08 — Shared custody must survive staff departure without preserving unwanted private data

**Concern exists. Severity high; likelihood medium.** Current owner-agent cascade can destroy personal signature sources; an inbox restrict reference may instead block staff deletion. Historical rendered replies can drift if they resolve a current source. This narrows lifecycle/delete behavior.

**Exact clause:** “Inbox signature publications have tenant/shared custody independent of an individual creator's continued membership. Creator/editor/audit identity is attribution, not a cascading ownership dependency. Archive stops ordinary new selection while preserving eligible pinned dependencies according to D4/P17. Retirement of an actively required binding requires an eligible replacement or explicit disabled/not-ready state. Safety withdrawal is immediate through the existing owner fence. Restore appends a new current decision/revision and cannot reactivate revoked membership, stale binding, old delivery or expired content. Ordinary deletion must not cascade into approved shared presentation, admitted Support sources or communication evidence.”

**Required proof:** Staff departure, creator deletion/anonymization, active default archive, last safe presentation withdrawal, restore after revocation, concurrent binding/retire, foreign-key restricted delete recovery. Privacy disposal remains the records owner's authorized operation, not a forever-retain claim.

### DR09 — Database relationships must enforce real authority, not only tenant equality

**Concern exists. Severity critical; likelihood medium.** Composite keys are useful but same-tenant IDs can still identify an unauthorized asset, another inbox or an invalid type. Direct mutations could change an allowed row into forbidden publication/ownership/approval state. This is an implementation gate.

**Exact clause:** “Use tenant-aware keys/references for inbox binding, published source/revision, actor-membership reference and asset occurrences. Required identities/revisions are non-null; typed state combinations reject impossible published/bound/revoked combinations. Binding uniqueness is per true inbox/purpose scope rather than nullable-personal-owner tricks. Derive tenant, actor, author, publisher, approver, timestamps and audit attribution at the trusted command. Validate both old-row eligibility and the proposed new state. Keep RLS on exposed tables, revoke direct mutation grants for compound publication/binding/audit work, inspect permissive policy composition, and qualify views/RPC execute grants/search paths/storage/service-role paths to the same current resource/capability boundary.”

**Required proof:** Tenant swap, source substitution, same-tenant wrong-inbox source, owner mutation, forged approval/author, moving draft into published state, direct REST, invoker/definer view, service-role job and signed asset URL attempts. Evaluate the effective USING/WITH CHECK rules; PostgreSQL can use USING as the WITH CHECK fallback, so an omitted explicit clause alone is not a vulnerability finding. Caller-editable user_metadata is never permission authority. Resolve cross-row eligibility under the authoritative transaction/lock rather than assuming a CHECK constraint can safely query arbitrary tables. Index actual lookup/FK paths; no money columns or duplicated CRM facts are needed.

### DR10 — Structured editing must replace independent rich/plain sources

**Concern exists. Severity high; likelihood high if current HTML APIs remain reachable.** Replacing only the textarea with Tiptap leaves raw HTML payloads, silent unknown-node flattening and separate editable output channels. Stored links/images can outlive or bypass permission. This changes editor/renderer boundaries while honoring the user's preference.

**Exact clause:** “Use the shared qualified Tiptap authoring primitives for signature creation/editing, human reply composition, internal-note composition, D18 reusable reply/note wording and other genuinely rich Support content. Keep plain fields plain. Persist a canonical versioned structured document; deterministic server-compiled HTML/plain text are derived artifacts. Validate nodes, marks, attributes, nesting, bytes, URLs and assets against the purpose-specific allow-list; reject or explicitly repair unsupported input. Browser/editor HTML, arbitrary JSON, legacy raw-HTML endpoints and an app-local tree walker are not authoritative send input. Mention/action/variable nodes cannot acquire behavior by copy/paste or mode change.”

**Required proof:** Tiptap/client and server schema skew, malformed/deep/oversize JSON, unsafe scheme encoded/cased forms, raw HTML pasted/imported, private attachment URLs, unknown nodes, internal-note to external mode, Unicode/bidi/plain-text parity, output after schema migration. Tiptap is an editing capability, not a sanitizer, permission engine, email-client renderer, concurrency backend or legal-signature system.

### DR11 — Cache and preview scope include actual responder and current authority

**Concern exists. Severity high; likelihood medium.** Current signature query key is a fixed Support key, and present reads return all tenant signatures then filter client-side. Query-client reset elsewhere may mitigate current behavior; this review does not assert a proven cross-tenant cache leak. The intended contract cannot depend on an undocumented reset convention. Real staff values in generalized previews could leak private data to maintainers.

**Exact clause:** “Cache reusable publication material only within its tenant/resource/current-authorization scope; cache actual personalization only with the current principal, membership, inbox, selected revision and authorized context. Clear/deny on tenant, actor or permission change. Email Studio shared authoring previews use synthetic public examples; real responder/audience values appear only in the authorized current Support draft. Counts, usage lists, selectors and dependency impact do not expose hidden inbox names, private drafts, staff values or conversations.”

**Required proof:** Same-browser tenant/account switching, removed permissions, delayed request delivery into a new editor, shared preview by content editor without conversation access, candidate choices from two restricted inboxes, cache invalidation under revision and safety fences.

### DR12 — Signature assets and resolved values need deliberate lifetimes

**Concern exists. Severity high; likelihood medium.** A private profile avatar reused as a public logo/photo, hotlinked URL, open tracking pixel, or indefinitely retained personalization in audit can evade D16/D17. A live image URL mutation can change the perceived historical message. This amends content and retention design.

**Exact clause:** “Signature images use P17's explicitly public/reusable governed asset path and exact version pins, never arbitrary profile avatars, private case attachments, remote fetch-on-render, hidden pixels or recipient tracking. Text contains the useful identity/contact meaning when images are blocked. Publication source retains unresolved reusable nodes; resolved responder values belong to the current draft/prepared/admitted source under their respective lifetimes. Permanent communication and governance history retains permitted IDs/revisions/outcomes and safe attribution, not copied signature bodies, private values or protected URLs. D16/D17 source redaction/retention and D22 search gates apply to admitted signature content just as to its message.”

**Required proof:** Image blocked/deleted/revoked, expired asset access, source public-authority withdrawn, redaction across current projections, backup restore reapplying fences, no P6 Recent search fallback, historical message not rerendered using today's logo or public name. Already received external email cannot be recalled by Asym redaction.

### DR13 — Sender/template coupling must not create accidental messages or CRM facts

**Concern exists. Severity high; likelihood medium.** “Signature” can be confused with From identity or legal signing. Reusing a generic template or CRM merge picker can create recipient, consent, identity or business-action effects. This narrows scope and language.

**Exact clause:** “A Support email signature is presentational closing content, not an electronic-signature workflow, sender identity, Reply-To destination, CRM contact record or evidence of business completion. Saving, publishing, previewing, binding, refreshing or archiving it never sends a message, changes a requester/Party link, fills a CRM property, alters ownership/assignment/status/target, adds a recipient or triggers D13 acknowledgment. Actual authorized sending follows D4/P17/P6 only. Internal notes use Tiptap but do not append an external signature or enter Resend.”

**Required proof:** Each maintenance operation has zero communication/CRM mutation effect; no-Party reply works; multi-Party/represented-organization context yields only intended public responder fields; requester and assignee changes do not impersonate the actor; automated notices retain their separate appropriate template with no fabricated human responder.

### DR14 — Migration must fence old writers and preserve historical truth

**Concern exists. Severity high; likelihood high because an incompatible legacy model exists.** Blindly converting every existing signature to published shared content can expose private details. Old clients can write HTML or owner defaults after a new model ships. Deleting old rows can erase recovery evidence before compatibility is proven. This is a mandatory rollout requirement.

**Exact clause:** “Inventory actual signatures, ownership, inbox references, prepared/admitted uses, assets and old routes before activation. Treat legacy HTML/personal rows as unpublished migration inputs until canonical conversion and current reuse/disclosure/publication review succeed. Preserve legitimate historical bytes and provenance; do not fabricate approvals or rewrite old sends. Introduce additive owner fields/structures and one qualified mutation boundary, fence old raw/personal-default writers, and switch eligible inboxes deliberately after compatible shared source/binding/profile resolution and proof. A kill switch stops new unsafe resolution/preparation while preserving existing supported recovery. Rollback cannot route new structured data into an old lossy or permissive renderer; use a compatible reader or roll forward.”

**Required proof:** Mixed old/new app deployments, unknown legacy HTML, existing personal default containing private email/phone, duplicate/default conflicts, missing assets, migration rerun idempotency, partial binding activation, backfill failure, restoration from pre-fence backup. Migration inventory counts and content hashes prove preservation without exposing bodies in logs.

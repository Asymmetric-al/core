## Minimal permanent editor and persistence contract

### T01 — Existing owner, one coherent semantic draft

“My drafts reads the current person's currently authorized, server-saved external Reply drafts. Each draft remains one stable Support-owned identity with original source context and owner. The saved candidate atomically includes the versioned canonical Tiptap document, explicit reply target/audience, governed signature choice/copy, quote and wording dependencies, durable attachment references, staged D4/D24 work and the revisions necessary for later current review. HTML/plain text are derived message artifacts, not independent draft authority. Save, list and resume never invoke P17 preparation or P6 delivery.”

The UI returns to that same draft whether entered from My drafts, the ordinary Support reader or the authorized CRM entry. A new destination does not justify a provider draft, CRM activity, Email Studio reusable candidate or copied body table. Raw browser `File` objects, temporary blob URLs and expiring download URLs cannot serve as cross-device attachment references; unfinished transfer state must remain explicit.

### T02 — Meaningful changes, not every editor event

“Create a durable draft only after the first meaningful deliberate change; initialization, ordinary signature/default audience seeding, focus, selection and mere viewing do not create one. Changes to the authored body, deliberate audience/target/signature choice, staged files or work plan participate in the semantic candidate. Once a durable draft exists, deliberately making its body blank is a normal saved revision, not an implicit Discard.”

Use canonical semantic comparison to distinguish a content change from a `setEditable` update, hydration, selection, caret movement or an unchanged normalized document. Preserve deliberate body-less work such as attachment/audience/staged intent according to the source owner; empty-body send validation is a separate decision. Do not rely only on editor `isEmpty`, a text string or a debounced keystroke callback.

### T03 — A small autosave coordinator, with honest timing

“For a valid authorized foreground draft, schedule a coalesced save after750ms of quiet and attempt a checkpoint within5seconds of continuing non-composing change when online and no earlier write outcome is unresolved. These are proposed Asym implementation tuning values, not vendor standards or durable-save guarantees. Save now flushes the latest stable candidate through the same owner command. Persist no keystroke history or server-side editor transaction log.”

Keep one in-flight write per draft session and at most one latest pending candidate, coalescing obsolete intermediates. A slow write or unknown result cannot trigger concurrent speculative saves to meet5seconds. Retry a failed/ambiguous operation with its original identity; do not change the captured payload under that identity. After reconciliation, submit the newer candidate as a new conditional operation if it remains permitted. Network, server latency, invalidity and active composition suspend the attempt bound; show the truthful state instead of claiming Saved. Limits and capacity must be qualified with the final canonical document budgets before activation.

### T04 — Saved belongs to an exact acknowledged candidate

“Saving and Saved refer to the exact draft identity and acknowledged semantic revision. A response for an older local candidate may advance the known server checkpoint but cannot mark newer local work Saved, overwrite its content, move its caret or change its audience. A server refusal, timeout, offline condition or conflict remains visible with preserved currently permitted work.”

The same receipt feeds the authorized My drafts metadata projection. Update its saved timestamp only for an actual semantic checkpoint; opening, hydration, focus, no-op saves and background reads do not move a draft to the top. The view must distinguish a server-saved checkpoint from newer session-only changes. Optimistic acknowledgement is inappropriate for the Saved label even when optimistic local typing is natural.

### T05 — Conditional revision, not collaborative drafting

“Every save includes the expected owner revision and immutable operation identity; tenant and actor come from trusted server context. A same-person second tab/device cannot silently overwrite a newer candidate. A conflict preserves both currently permitted versions long enough for a focused choice or manual reconciliation of the same draft; do not introduce shared co-editing, Yjs, CRDT history or a team takeover mechanism.”

One active draft per source/profile slot does not mean one tab lease or locked editing. Compare the complete semantic bundle, not body alone. Loading current server work is explicit when it would replace dirty local work. Keeping local work requires current validation against the newly read revision; it cannot be a blind force-write or bypass a restriction/previous send. Separate permitted side-by-side text for manual reconciliation from exposing drafts to another teammate or permanently creating a version-history product.

### T06 — Restoration is gated before editor initialization

“Fetch and authorize the exact draft through the source owner; validate the original versioned envelope and JSON before mounting a writable editor. Hold the composer in a named loading state until a qualified baseline is available. An access error, failed read, unsupported schema or missing result is not an empty new draft.”

Bind responses to tenant, principal, draft identity, source topology and local session generation. A late response for another draft is dropped. Never apply a background query refresh into a dirty active editor. Set initial content once for the accepted draft baseline, using `emitUpdate:false` for any intentional hydration and a non-user-change marker in the owner coordinator. Explicit acceptance of a replacement may reset relevant editor history; silent background restore may not.

### T07 — Schema errors stop writing; original bytes remain authoritative

“Unknown schema versions, keys, nodes, marks, attributes, protected/source metadata and incompatible source profiles must fail original-input validation before Tiptap normalization. Preserve the owner's original retained candidate and show a useful read-only Needs update or repair state. A contentError handler stops writable initialization, autosave and send. It cannot persist stripped or empty replacement content.”

The official documentation describes permissive normalization for some ordinary editing use cases. That conflicts with Asym's D23/D36 protected semantics: attributes can carry quote/source/plan meaning that must not silently disappear. Server validation is independently required; editor parsing is not RLS, source-use authorization or a safe metadata validator. A later migration creates the qualified new candidate with explicit loss handling, rather than accepting an old client writer after a schema downgrade.

### T08 — Stable identity, safe mode separation and normal Undo

“Keep the editor instance stable while editing the same qualified draft; typing, saved timestamps, list refreshes, resizing and read preference changes do not remount it. Treat tenant/principal/draft/purpose/schema-generation changes as explicit identity transitions with preserved safe working state or required clearing. Do not reuse a history stack across Reply and Note or unrelated source/draft identities.”

Use the existing shared editor/context in packages/ui. A key can express identity but is not a persistence mechanism: coordinator state must survive permitted navigation before an editor unmount. Normal Undo/Redo within the active identity remains useful and D24 body/plan Undo remains coherent. Reopening a saved candidate does not require durable ProseMirror undo history or cursor synchronization across devices. Same-session caret/scroll restoration may be retained ephemerally when the exact document revision still matches; otherwise choose a stable useful position without stealing focus from review controls.

### T09 — IME and navigation flush preserve actual committed input

“Do not send, switch away destructively or programmatically replace content while input-method composition is active. Respect keyboard composition and previously handled events; use the editor's supported composition state. After composition commits, capture the resulting committed editor document before an explicit Save/Send or guarded route transition proceeds.”

The inspected ProseMirror-view1.41.8 `src/input.ts:435–450` documents Safari's near-composition Enter behavior. Its `compositionend` handler at502–511 may flush pending DOM work in a microtask, so an immediate snapshot in a raw compositionend callback is insufficient proof. Use qualified supported integration and real Chinese/Japanese/Korean/Thai input, mobile virtual keyboards and browser tests. Do not copy private internal500ms/20ms timing constants into product behavior or create a custom IME engine. Preserve original native editor handling and add a narrow qualified primary-action guard.

“Permitted in-app navigation retains and flushes safe dirty work through the same owner before calling it Saved. When only session-local unsaved work remains, provide a clear keep-editing/leave consequence rather than silently clearing it. Browser/OS termination recovery is limited to confirmed saves; visibility flush and beforeunload warnings are best-effort. No automatic offline send or persistent browser outbox is added.”

### T10 — Safety overrides recovery, without hidden reappearance

“Current access loss, tenant/principal/logout transition, source privacy restriction and content expiry win over autosave, Undo, browser state, caches and late responses. Stop forbidden writes and clear unavailable local representations; protect source-derived data under D16/D17/D36. A protected source or completed discard cannot reappear through an old save acknowledgement, stale draft list, browser back or replay.”

Preserve independently permitted authored content where the accepted source contract can safely separate it. Do not claim arbitrary text can always be separated from restricted source-derived content. Inaccessible drafts do not reveal subject, snippet, count or identity merely because the person previously authored them. Minimal owner-authorized operation recovery may remain available as already qualified by D4/D35; that is different from retaining the private body.

### T11 — Save/resume never executes staged work

“Restoring the draft preserves D2's exact reply target/audience, D23 signature, D36 quotation provenance and D4/D24 staged plan; it does not retarget to the newest message, refresh to latest wording/signature, change recipients from CRM, acquire files, assign staff, resolve the request, notify mentions or run the work plan. Deliberate Send performs current preparation/admission review against current actor, topology and dependencies.”

Changing composition mode preserves separate working drafts and neutralizes incompatible staged actions as already defined. Q37 covers saved external Reply discovery. It creates neither durable new-note drafts by inference nor persistence for D35's local edit of an already-posted note. Notes keep their existing working-state behavior.

### T12 — Submission recovery is distinct from ordinary drafts

“An unresolved Send belongs to the original D4/P6 effect-recovery path, even if safe working content is still retained. It is not a fresh unsent draft with a new Send button. Saving or opening My drafts cannot cancel an admitted email, duplicate its action, reset dispatch identity or retry all recipients.”

Definitive rejection before admission may restore ordinary editing after reconciliation. Admission closes/consumes the submitted draft revision and links the immutable operation outcome; provider delay/failure does not recreate that draft or undo its Support work. New writing after an admitted reply starts another qualified draft. My drafts may show a clearly separate owner-authorized recovery affordance where needed, but it must not become a second outbox or delivery state machine.

### T13 — Metadata-only list, one editor when resumed

“The My drafts list uses currently authorized metadata and control facts; it mounts no live Tiptap editor for each row and does not fetch full private bodies merely to show a subject, timestamp, inbox or attachment count. D22 private-body search exclusion remains intact. Open one row to load its full qualified candidate in the existing conversation reader.”

Keep the list client independent of editor transaction rendering. The active editor should have stable extensions/callback identity and small selector subscriptions; `useEditorState` is appropriate for formatting controls. Counts/list rerenders must not remount the document or interrupt input. Shared safe static rendering is for actual read-only body surfaces; a metadata list needs neither a second rich-text renderer nor a static-renderer body fetch. This reduces payload and accidental disclosure while keeping narrow/mobile navigation quick.

### T14 — One modest stack and qualified dependency closure

“Use the existing Next.js client boundary, shared Tiptap3 editor, source-owned Support API, approved browser read layer and Supabase/Postgres persistence. Do not add Tiptap Cloud, paid snapshots, Yjs, a generic workflow/draft service, provider-draft synchronization, cross-user awareness payloads containing draft text or a second Email Studio draft library for this view.”

The composable API may improve the shared editor at its normal qualified maintenance boundary; My drafts does not depend on a provider rewrite. Preserve `immediatelyRender:false`, original-input checks and exact base-maia. Resolve actual peer/version/schema/runtime compatibility before activating the writer. Test installed/upgraded closure in the implementation change; do not opportunistically install latest into the worktree during research.

## Email Studio and CRM seam in full

Support owns the private human reply draft, source identity, current tenant/principal checks, save revision/operation, complete candidate and later human admission. P17/Email Studio owns governed content schema, wording/signature publication and the shared compiler/preparation of a complete reviewed message. P6 owns sealed transport, per-recipient evidence, provider reconciliation and actual delivery history. Tiptap is an authoring implementation, not another owner or provider integration.

My drafts has no preparation side effect. Autosave must not repeatedly compile/prepare outgoing payloads, renew human preparation custody, create a system-message key, publish a Saved Section or contact Resend. P17's source-document authoring autosave and Support's human draft checkpoint use sound shared primitives where appropriate but remain separate domain aggregates. Support owns the draft lifecycle; Email Studio's reusable library does not enumerate private human drafts.

The same authorized Support reader/composer is reachable from CRM with its return context preserved. CRM stores no copied draft body or private draft activity and gains no private draft count from an association. Requester/contact, sender endpoint, authenticated draft owner, support worker and CRM owner remain distinct. A saved draft may refer to an existing source that later merges/moves; retain its original source/target and reauthorize rather than silently reassociating it. Neither the draft nor its content proves a giving/contact/member-care action occurred.

## Proof and rollout requirements

These tests are required implementation/release evidence; the eight executed source observations do not satisfy them.

1. **Ordinary resume:** start from Support and CRM, change body/audience/files/signature/quote/plan, leave after confirmed save, find My drafts, resume the same candidate on another supported device with current permissions and no effect execution.
2. **Save acknowledgement:** type through a slow save, reorder responses, time out after commit, retry the same identity, receive a no-op, and prove only the exact acknowledged candidate is Saved and ordered by a real checkpoint.
3. **Concurrency:** two tabs/devices edit the same revision; only one conditional successor wins, loser keeps safe work and reconciles explicitly without a shared collaboration service or duplicate active draft.
4. **Hydration and identity:** late A response after navigating B, background refetch while dirty, mode switch/Undo, tenant/logout changes, list refresh/resize and Strict Mode do not move/copy/erase work across identities or create spurious saves.
5. **Schema:** unknown version/node/mark/attribute, protected quote/plan metadata, incompatible old writer and parser normalization cannot produce a writable stripped candidate. Original stays owner-retained under current permissions.
6. **IME/mobile/accessibility:** real supported browsers, composition commit plus primary shortcut/navigation, paste/Undo, screen reader focus/status, virtual keyboards,320CSS-pixel reflow and200%text resize preserve content and correct action semantics. No product latency or perfectUX claim until measured.
7. **Privacy:** author-only source-qualified list/read/save/count, current revocation, redaction/expiry, stale caches and discard/late-write races preserve the same authorization as the source; no body indexing or data in logs/analytics.
8. **Admission/recovery:** pending/unknown Send, admission success/response loss, provider failure and partial recipient evidence use the original effect. My drafts cannot create a fresh resend path or repeat staged work.
9. **Capacity:** enforce the shared canonical document/assets limits and prove0/exactmax/over-limit behavior; validate autosave throughput, coalescing, one editor instance and metadata pagination at the declared tenant/actor envelope. The proposed750ms/5s timings are attempt tuning under explicit conditions, not an unbounded service guarantee.

Sequence: qualify current owner/canonical schema and immutable conditional save operations; wire one coordinator with real tests; qualify read projection and resume; add the small base-maia list; fence old draft-mode/source writers and incompatible clients; complete the runtime/security/browser/capacity tests; then activate by scoped release control. Disabling discovery does not delete saved drafts or interrupt pending effect recovery. Disabling the new writer cannot re-enable an old unsafe writer. Roll forward incompatible schema safely; rollback must not strip new documents.

Residual signals may be routed through root's final operating controls: first wrong Saved acknowledgement or forbidden identity/source render is a release-stop incident; repeated save failure/latency uses body-free draft operation timing and precise owner response. No telemetry records keystrokes, draft bodies, recipient strings or staff productivity scores. Shared editor owner handles hydration/schema/IME faults; Support owner handles save/discovery/authorization; P17/P6 owners retain preparation/delivery incidents.

**Conclusion:** the useful destination is small. Robustness comes from making the accepted private draft real and recoverable under current authority. No new editor, co-editing layer, note persistence, customer model or mail transport is necessary. All runtime proofs above remain unexecuted during this grooming task.

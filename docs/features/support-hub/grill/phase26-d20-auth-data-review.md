## Permanent shared capability shape

The shared named-view owner persists the definition, audience and individual view preferences. Support registers one closed Support-conversation subject plus its qualified predicate/sort catalog and owner query contract. The existing named-view engine is generalized additively; legacy Support saved-view writers/readers are fenced and retired after verified migration. Do not make Support require permission to read CRM merely because an older implementation directory says crm.

Settle the logical invariants now; physical table names follow the qualified shared owner. A small model is sufficient:

- **Definition:** non-null tenant, opaque stable view ID, subject/definition-schema version, revision, lifecycle, personal/shared visibility kind, bounded display name and optional description, closed typed predicate tree, supported sort, trusted creator/updater. Personal owner is a stable qualified tenant/principal identity. Shared custody is tenant-owned; creator attribution is not delete authority or lifecycle dependency.
- **Audience:** existing qualified team/inbox/tenant audience references, using actual platform group semantics; each reference is tenant-constrained. Audience controls seeing the definition; it is not source permission, assignment or an email audience. Avoid arbitrary nested groups created solely for D20.
- **Personal preferences:** one row per tenant/principal/Support surface or per definition as appropriate, storing pins/order/personal presentation. Pin references preserve tenant equality; no copied shared definition. Moving a personal pin never changes shared order/audience. Guard preference updates against concurrent device overwrites.
- **References:** immutable catalog/reference IDs in the canonical typed payload, registered through the shared artifact-reference owner when that capability applies. Do not add a second registry. Inbox/agent/team/label/field references resolve under current tenant/owner policy on save and execution. If a referenced owner is removed, the clause becomes unavailable; it is never silently removed or retargeted by matching a reused slug/name.
- **Evidence:** bounded classified mutation history/receipt through the shared mechanism, sufficient to explain an effective shared update and safe correction. No indefinite transcript-like archive of raw free-text filters or full query results.

Database requirements: composite tenant-aware relationships for definition/audience/principal/pin/control; checked visibility-owner combinations; non-empty bounded names; allowed subject/version/operator shapes; no user-defined SQL; unique stable IDs; revision > 0; timestamps timestamptz from trusted clocks; no money columns. Relational reference delete behavior must preserve shared custody and necessary audit. Direct personal-owner deletion must not cascade shared definitions. Profile/user/account lifecycle follows qualified identity owner, not email reuse or invitation address.

Names are display labels rather than identity; a rename never breaks URL/pin references. Enforce uniqueness only if the shared owner already defines the intended audience/owner namespace; avoid null-coalesce sentinel collisions or leaking another private definition through a uniqueness error. Prefer distinguishing identical shared names with audience, if needed, rather than adding a global tenant-wide private-name namespace.

## Authorization matrix

| Operation                    | Required authorization                                                                                                                                                                                                            |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| List/picker/open My          | Current qualified staff principal, exact tenant, exact personal owner; body/criteria themselves must remain currently exposable.                                                                                                  |
| List/open Shared             | Current staff eligibility, membership in shared definition audience, current authorization to interpret all criteria needed for that view; results separately authorized.                                                         |
| Save/update My               | Self-only ownership from server; source-qualified predicate catalog; no caller overwrite of creator/tenant/owner/version control.                                                                                                 |
| Create/update/share Shared   | Explicit existing shared-view maintenance capability for destination scope, qualified audience/reference exposure; current revision. Sharing is a deliberate command, never a scope field silently toggled through generic PATCH. |
| Personalize Shared           | Self preference authority plus current definition visibility; does not require shared maintenance or overwrite common criteria.                                                                                                   |
| Preview/count/query          | Same actor/tenant/filter authorization as open; source policies apply before match membership, sort, counts and pagination.                                                                                                       |
| Correct/remove/restore       | Exact owner/maintainer authority and current lifecycle revision. Restore does not regain lost source or group permission.                                                                                                         |
| Privileged repair/import/job | Narrow declared owner authority, same tenant/reference/custody fences and immutable actor attribution. No broad service-role workaround.                                                                                          |

**Recommend raw owner storage remain denied to anon/authenticated, like qualified named views, with source-qualified API/projections.** If an approved browser-readable collection is exposed, prove equivalent self/shared/audience restrictions independently in SELECT RLS and never expose raw restricted criteria. Mutations that change audience/control/history remain canonical server commands.

Verify effective database grants, public function execution, SECURITY DEFINER search_path and policy combinations. ENABLE/FORCE RLS does not constrain BYPASSRLS/service_role; those callers need equivalent owner checks. For supported UPDATE policies test old-row USING and new-row WITH CHECK plus immutable/allowed-column protection: merely qualifying both old/new rows does not prevent a self-owned record becoming a different permitted self-owned record under an unrelated identity.

Current PostgreSQL documentation confirms RLS default-deny, role bypass, permissive-policy OR combination, implicit WITH CHECK in qualifying cases, and referential constraint inference risks. Do not incorrectly claim omission of WITH CHECK always removes all checks. [PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Supabase separately documents grants versus policies and service-role bypass. [Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Material findings and exact proposed clauses

Likelihood is qualitative without measured incident prevalence.

### F01 — A second engine violates shared ownership

**Material: Yes; severity High; likelihood High if scaffold extended.** Duplication causes query/permission drift across Support and CRM and future migration debt. S01/S02/S16/S17. **Effect: changes implementation ownership, preserves A.**

> D20 shall use the qualified shared named-view capability and register Support-specific subject, predicates and actions. It shall not maintain an independent Support saved-view persistence/permissions engine, nor import CRM data access as a prerequisite for ordinary Support view use.
> **Proof:** same shared view lifecycle primitives drive qualified Support and existing CRM regression journeys without changing CRM behavior; only one active Support writer/reader authority after migration.

### F02 — Personal scope currently does not mean private

**Material: Yes; severity Critical for confidential filter contents; likelihood High under current grants.** Staff can receive/manipulate other personal definitions and forge ownership/scope through current API. S06–S11. **Effect: required privacy amendment.**

> My views shall be self-owned and private to the currently qualified staff principal. Tenant, actor and personal owner shall be server-derived. Shared maintenance and audience shall be separately authorized. No ordinary raw table, RPC, service path, export or deep link may expose or mutate an unauthorized definition.
> **Proof:** two staff same tenant, other tenant, stale owner, forged owner/scope/ID, direct table/RPC and ordinary admin lacking content privilege; denied results expose no labels/criteria/counts.

### F03 — Agent/creator lifecycle can lose or transfer views

**Material: Yes; severity High; likelihood Medium.** Email matching can pick wrong self identity; personal→workspace can retain cascade owner; employee departure destroys shared resource or lets reinvitation inherit it. S06/S11/S18. **Effect: narrows ownership.**

> Shared views are tenant-custodied independently of creator membership. Offboarding removes access immediately and preserves shared definitions for qualified maintainers; it does not auto-share personal views or transfer them to an email/name successor. Personal custody shall use the existing qualified principal identity rather than support-agent email matching or arbitrary first membership.
> **Proof:** deactivate/delete creator; role change; multiple memberships; same email new user; shared definition/pins remain correctly scoped without data inheritance.

### F04 — A readable result can still leak an unreadable predicate

**Material: Yes; severity Critical; likelihood Medium.** “Has related restricted missionary” and count differences can reveal hidden CRM attributes even when each returned conversation is readable. Definition name/description and unauthorized named-person/team values also reveal information. S03/S19. **Effect: narrows filter exposure.**

> Predicate eligibility and referenced values shall be authorized independently of result rows. An unavailable or unauthorized clause shall stop execution of that view and hide forbidden detail; it shall not be ignored or approximated. D20 enables only the qualified Support catalog, not arbitrary CRM, giving, location or member-care segmentation. A generic error does not reveal hidden count or existence.
> **Proof:** accessible conversations containing differently protected related records give no oracle through counts/order/error details; cannot use negation, missing-value or joined relationship existence to infer forbidden data.

### F05 — Preview and saved query currently disagree

**Material: Yes; severity High; likelihood High in multi-label use.** ANY/EVERY divergence and cap-before-filter mislead staff into missing work. S10/S12/S13. **Effect: requires canonical query semantics.**

> Preview, saved execution, transient filters, counts and paging shall use one versioned server predicate compiler. Inbox scope, conjunction/disjunction, null/unassigned/current-viewer and time semantics shall round-trip exactly. Every predicate shall apply to the complete authorized population before cursor paging; no loaded-row cap may define membership.
> **Proof:** matching rows beyond 2,000; labelsA/B with A-only/B-only/both; expected stable sort/paging; non-Latin names and punctuation `, % ( )`; identical preview→save→reopen query truth.

### F06 — Generic upsert allows lost updates and resurrection

**Material: Yes; severity Medium/High for shared meaning; likelihood Medium.** Two maintainers overwrite each other; timeout retry creates duplicate; PATCH on deleted ID recreates it. S08/S09/S17. **Effect: changes command contract.**

> Create, update, sharing and lifecycle commands shall bind exact semantic payload, stable operation identity and expected current revision where applicable. A retry returns the original outcome and current state separately. Changed payload with the same operation identity conflicts. Update cannot create; stale update cannot restore an archived/removed definition; opposing commands serialize on the same authoritative control.
> **Proof:** concurrent saves one succeeds/one retains draft with conflict; lost response retry one view; delete/update races; idempotent applied result differs from later state without restoring old revision.

### F07 — Stale caches, URLs and offline clients can expose old scope

**Material: Yes; severity Critical; likelihood Medium.** Actor changes, revocation, source redaction/expiry and slow responses outlive cached safe result. S14/S15/S19. **Effect: requires all-access-path fencing.**

> Queries/caches/cursors shall bind tenant, qualified principal, relevant permission generation, definition revision, canonical criteria and source restriction generation as applicable. Inflight responses from old scopes shall not repopulate a new scope. Offline/reconnect and expired authority shall not restore sensitive results; unknown authorization is unavailable, not empty or permitted.
> **Proof:** sameuser tenants, signout/userchange, scope revocation while fetch pending, reconnect, restored cache, source redaction between list/count and render. [TanStack](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys) supports including query-changing dependencies, but cache keys alone are not authorization.

### F08 — Saved free text can become a privacy archive

**Material: Yes; severity High; likelihood Medium.** Names/search literals copied from sensitive sources outlive D16/D17 or leak in URLs, logs, shared definitions and audit diffs. S19. **Effect: narrows storage/telemetry.**

> View metadata and free-text predicates shall be classified as user content, bounded and protected by the definition audience and owner retention/correction policy. Do not store returned rows, message snippets, identities or query result snapshots in a view. Avoid raw predicates or names in telemetry. Identified source-derived copies observe D16/D17; independently authored text retains its owner correction path and is not silently rewritten.
> **Proof:** redact/expire source vs independently typed literal distinction; shared free-text preview; safe copied link/URL logging; author/admin erasure never requires inspecting inaccessible personal content.

### F09 — Shared views can be mistaken for work ownership or completeness

**Material: Yes; severity High; likelihood Medium.** A group hides its normal queue behind an empty custom subset, excludes held intake or assumes saving follows/calls CRM/send. S01/S19. **Effect: scope boundary amendment.**

> A saved view changes only discovery/preferences. It shall not change conversation state, assignment, Following, reply targets, CRM relevance, communications history or Email Studio/Resend state. Standard work/recovery remains reachable; empty means no current matching authorized conversations, not all work complete.
> **Proof:** save/open/share/pin leave all domain mutation/event counts unchanged; intake remains separately visible to qualified reviewers; CRM timeline/lastcontact unchanged.

### F10 — Unverified migration and scale can silently change meaning

**Material: Yes; severity High; likelihood Medium.** Null-owner legacy personal rows cannot be assigned by guesswork; copied old slugs reinterpret renamed labels; unsupported payload drops clauses; all-view live counts produce tenant-wide expensive fanout. S06/S12/S16/S17.

> Migration shall inventory and map only proven owner/audience/criteria semantics; ambiguous rows are withheld for qualified correction, not converted to tenant-shared. New readers/schema precede writers; old writers are fenced before new scope data. Unknown schema versions fail closed. Preview/page/count paths have measured bounds and complete-or-unavailable responses; sidebar lists do not continuously compute every saved query.
> **Proof:** nullowners, invalidslugs, multipleprivate names, unknownversions, mixeddeployment, rollback aftersharedwrite, largeauthorizedtenant, expensivezero-match, and fairness/cancellation. No capacity number is claimed from static inspection.

## CRM and Email Studio consequences

CRM Party identity, per-message observed participant, qualified correspondent, explicit related Party, Support assignee and CRM owner remain distinct. A Support saved view does not create a Party or turn a candidate match into known identity. Opening a CRM record from a result uses the normal owner route under D9 joint authorization and returns to the same preserved view/filter context; losing permission returns an honest unavailable state without falling back to broader record search.

No result row copy is stored in CRM; no last-contact, activity or communication event is emitted from view actions. Conversation merges count one currently permitted canonical work row, while original content restrictions still apply. Related conversations remain independent current work. CRM merge/unmerge and context relinking invalidate only affected owner-derived discovery; they do not rewrite the saved filter by today's emails or inherit relationship graphs.

Where the view is opened inside a specific Party's CRM Communications surface, preserve the owner-imposed Party discovery constraint as an explicit non-removable base context for that surface. A personal/shared Support predicate can only narrow that authorized cohort. Moving to full Support is an explicit navigation action, not silent removal of the Party context.

Email Studio has **no view execution role**. Shared-wording curation and shared-filter maintenance may share native UI primitives and plain language but do not share publication semantics. Save/open/share/pin neither prepare a message nor call Phase 6/Resend, instantiate a recipient audience, schedule mail, or alter a prepared reply. If future bulk communication ever uses a source query, its owning domain must independently define/authorize that workflow; D20 gives no implied authority.

## Root synthesis recommendations

Resolve before proposed recording: shared engine ownership, self principal, shared custody, criterion/source visibility, fixed predicate semantics and no side effects. Capture these as exact D20 clauses and map to proof. Shared owner qualification, SQL/RLS, conflict/retry, migration/capacity and integrated journeys are release gates, not monitor-only items.

Monitoring after gates: confirmed unauthorized disclosure/mutation (threshold any; security+sharedviewowner; fence affected reader/writer, preserve classified evidence and re-prove); reproducible preview/list/count/paging discrepancy (any; sharedquery+Supportowner; stop affected query shape, retain canonical definition, repair/re-prove); schema/reference/custody drift (any confirmed; sharedviewowner; withhold invalid execution and repair through authorized tools); timeout/error rate (use measured release SLO thresholds, not invented here; platformqueryowner; cancel/degrade optional counts, preserve complete results contract). No automatic user notifications, new incident model or dedicated scheduler is needed merely because a view exists.

## Residual pressure test of root decision draft — 12 September 2026

The draft adopts the substantive original corrections: shared platform capability, narrow Support subject, source-gated definitions/predicates/results, privacy/custody, exact filter semantics, source lifecycle, server query completeness, guarded save, rollout and no Email Studio effect. The remaining material refinements are below. These are precision fixes, not a rejection of A or a recommendation to expand scope.

### V01 — Full-workspace view scope versus fixed CRM anchor

**Material: Yes. Severity: High; likelihood: Medium.** R04 says opening replaces complete scope and must not inherit a record, while R20 correctly requires a fixed owner record anchor inside CRM. P04 currently asks for no inherited CRM anchor without distinguishing surface. An implementation could use R04/P04 to drop the CRM Party boundary while still appearing inside that record. **Exact correction:** start the R04 rule with “In the full Support workspace…”; add “Within a CRM record surface, the owner-imposed Party context remains fixed under R20; applying a full-workspace saved view requires explicit navigation into Support Hub first.” Qualify P04 likewise and retain P26 as the fixed-anchor proof. This resolves the contradiction without inventing a second per-record view store.

### V02 — Sensitive URL state needs a required encoding contract

**Material: Yes. Severity: High; likelihood: Medium.** R23 requires shareable modified query state but says opaque references “may” protect sensitive literals “where the owner contract permits.” That can leave the actual safety decision to a serializer that writes q/name/address into URL query strings. Logs/referrers can be minimized but browser history and pasted links still carry raw literals. **Exact correction:** “Sensitive query literals shall not be serialized into URL text. Shareable state containing them shall use a qualified authenticated, non-bearer shared query-state reference with explicit audience, schema, permission revalidation and finite owner retention. If that shared contract is unqualified, its unsafe encoding/share path shall not activate; normal authorized filtering remains available. Public links never confer query or source access.” This is a required shared capability qualification, not permission to build a feature-local token store. P25 must include browser history/pasted-link contents and expired/revoked state handles.

### V03 — Duplicate-name contract conflicts with current platform uniqueness

**Material: Yes. Severity: Medium; likelihood: High if existing RPC/table reused unchanged.** R22/P03 accept duplicate human names as separate identities; existing named-view table has UNIQUE(tenant_id, profile_id, table_id, name). Reusing it unchanged would reject those definitions; removing the constraint globally would change other subject semantics contrary to R27. **Exact correction:** “Support name/disambiguation behavior shall be implemented through subject-qualified shared storage/validation. If Support allows duplicate names, adapt its uniqueness namespace without relaxing the existing CRM name/default contract; stable IDs remain unique and no name conflict may disclose inaccessible definitions.” Alternatively narrow the product rule to unique personal names within self/Support subject and explicitly define duplicate Shared names by audience; root should choose and document one, not leave contradictory tests. Existing root draft appears to choose duplicate names, so subject-qualified adaptation is the consistent path.

### V04 — Shared foundation must not force CRM permission on Support users

**Material: Yes. Severity: High; likelihood: Medium.** R01 says generalize the shared engine, but current named-view routes explicitly invoke crm.table_preferences.read/write. Ordinary Support staff should not need unrelated CRM record access to save filters. **Exact correction:** “Support registration resolves Support view/use/maintenance capabilities through the shared capability, independently of CRM read/write permission. Existing CRM subjects retain their own policy. Reuse the shared owner, not the CRM-specific route's capability gate.” Add Support-only/no-CRM and CRM-only/no-Support cases to P01/P18.

### V05 — Stable command identity must not leave upsert resurrection

**Material: Yes. Severity: Medium/High; likelihood: Medium.** R15's guarded revisions and exact retry are sound, but current Support PATCH calls generic upsert. It is worth making absence and changed-input retries explicitly falsifiable. **Exact correction:** “Update, rename, archive and restore shall operate only on the exact existing current lifecycle identity and shall not create an absent definition. A changed semantic payload under the same command identity conflicts. An exact retry returns the original durable outcome and current state separately; the old outcome cannot restore a definition archived/removed after that operation.” P16/P17 add PATCH absent ID, mismatched same-operation body and save→archive→old-save retry.

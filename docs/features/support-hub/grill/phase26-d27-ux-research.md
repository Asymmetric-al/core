# D27 independent UX research — approved public guidance finder

**12 September 2026. Founder selection: A — Find approved public guidance in Support.** This artifact pressure-tests the selected direction and proposes precise UX amendments. It is independent research for the parent synthesis, not a claim that the amendments are already ratified, implemented or usability-tested. No Q28, formal specification, source-code, CMS, provider or message change is made here.

**Disposition: Accept with required amendments.** A is a useful, proportionate addition if the finder discovers deliberately selected public sources and inserts ordinary links into the existing draft. Its safety and usability depend on making four facts clear: what is selected for Support, what is actually public now, what will be inserted, and what changes when the source is updated or withdrawn.

## Evidence and architectural footing

The [Q27 vendor report](phase26-q27-vendor-research.md) and [coverage review](phase26-q27-gap-review.md) provide the earlier research and source pins. This pass rechecked the canonical WSL worktree, read the actual frontend/Base UI instructions and continued current primary vendor research. Root and scope reviewers are refreshing the shared source baseline; this report does not independently claim that a runtime guidance finder exists.

The governing frontend is **base-maia with Base UI, shared `@asym/ui` components and semantic Maia/Zinc tokens**. This is directly specified in `docs/ai/rules/frontend.md`, `packages/ui/AGENTS.md` and `packages/ui/components.json`; a visually attractive alternate component system would still be incorrect. Read-only guidance preview should use the qualified published-content projection, not a Tiptap editor. Link insertion stays inside D23's accepted Tiptap profile and the existing D4/P17 draft/send boundary.

The shared public reader and reference-not-copy ADRs remain load-bearing. CMS/Web Studio owns source content, versions, public presentation, locale, site and URL lifecycle. Support owns the deliberately curated source selection and this usage context. Selection does not grant editorial permission. The current reader has page/navigation/update methods, not a ready approved-guidance search; qualification is real work. The found code does not establish an internal knowledge owner, and selected A does not introduce one.

## The permanent UX model

Use **Guidance** for the working finder and **Manage guidance** for the curated selection. In ordinary explanatory text, say **published pages selected for Support**. “Approved” means deliberately admitted to this workflow by the authorized curator while its source remains public-eligible; it is not a guarantee that the page never changes or legal approval of each fact.

There is one tenant-owned curated reference set, not a personal guidance library, duplicated inbox article copies or another taxonomy. The source title and summary remain source-owned. A curator selects an exact eligible source/site/language scope; future translations, different sites and unrelated pages are not silently added because they have similar titles. P23/P24 source identity, active public site generation and the primary public-domain owner qualify that reference. A source eligible for public access by link may be deliberately selected even when its owner omits it from public discovery; selection must not change the public search or sitemap policy. Actual source identity comes from the CMS owner, never title or URL string equality alone.

Keep three persistent concepts separate: **selection retained**, **selection removed**, and **current source eligibility**. UI may summarize them as Available, Unavailable and Removed, but unknown state during an outage is not proof that a source was unpublished. Ordinary source updates stay with the maintained source; this should not become a per-revision Support reapproval queue. A change of purpose still requires the responsible curator to remove unsuitable guidance.

### Journey 1: find and use from Support

1. Open the existing conversation, keeping its work state, people, sending inbox, Reply/Internal note choice and private draft intact. The **Guidance** action is manual. It does not auto-open because a message mentions a topic and does not extract a query from the conversation.
2. Open a compact finder beside or over the composer using the shared surface pattern. Keep the conversation identifiable. Put a clearly labelled search field first; show a restrained paginated list when blank. Use current source title and concise description. Show site/language where they distinguish items. No cards with decorative hero images, tag clouds, usage leaderboards or forced setup.
3. Search within selected guidance only. The public owner qualifies matching title/summary and eligible body text; the UI must not promise body matching if its implemented owner contract only supplies titles. Prefer clear matches and stable ordering over a tunable search language. Search is literal user input, not SQL, a prompt or filter syntax. IME composition must not trigger navigation or insertion.
4. Use explicit **Language** and **Site** filters only when the eligible set has meaningful choices. Show their current values, allow individual clearing, and make a deliberate **All languages** or **All sites** choice visible. Start with the current reply language only when the platform has a resolved language; otherwise use a clearly labelled broader scope. Never infer a person's language from their name, nationality or CRM relationship. Zero results must not silently widen scope.
5. Select a result to preview. Show title, language, site/public destination and the current public text. Provide **Open public page** and **Insert link**. A staff member with only Support read access can consult guidance, but cannot create or modify a draft through the finder.
6. Keep preview passive. Render qualified public text and permitted static media without mounting a full interactive site, forms, donation widgets, scripts or third-party embeds inside the staff workspace. If a page contains unsupported interactive material, show an explicit notice and Open public page. Do not imply the preview is a complete rendering while silently discarding consequential sections. A normal explicit public-page navigation remains subject to the source's ordinary behavior.
7. On **Insert link**, recheck the selected source and target draft context. At a valid caret, insert a normal human-readable link using the source title. For a normal link-eligible text selection, visibly change the action to **Link selected text** and preserve the worker's wording through the existing link semantics. Never replace selected wording with the article title. If the selection spans protected/unsupported content or the caret cannot be safely restored after a draft change, return focus and ask the worker to choose an insertion position; do not overwrite text or insert into another conversation.
8. Return to the draft with focus beside the insertion. Preserve preceding/following text, saved-reply provenance, managed signature, attachments, recipients and staged shortcut. A single Undo removes this insertion and its source-use association together. It must not cancel unrelated work or leave hidden source state attached to a link no longer present.
9. The worker can write a short relevant explanation and send through the existing D4/P17/P6 flow. Insertion is not sending, replying, meeting a target, completing a refund or resolving work. The source link is supplementary help, not a reason to dismiss a requester with a wall of documentation.

For a D26 manual request with no email yet, guidance remains consultable. Insertion requires the deliberately opened qualified draft; it must not create correspondence, select a recipient or make the work inbox email-ready. Public guidance can also be linked in an existing Internal note; the finder never silently switches its destination to Reply.

### Journey 2: use through CRM without losing place

1. From the CRM record's permitted Support entry, open the same canonical Support detail already required by D26. Do not make a separate CRM guidance picker with a broader source query or a second email composer.
2. Use the same Guidance/preview/insert steps. Existing CRM read access and current Support access are independently rechecked. Source public eligibility does not grant access to hidden conversations or CRM financial/care context.
3. Closing the finder returns to the same editor, mode, selection and scroll position. Opening a public source or an authorized CMS editor preserves the permitted draft and conversation route. Returning to CRM restores its list/record context instead of resetting the worker to the Support home page.
4. If access is revoked or the conversation moves while the finder is open, stop insertion and clearly explain that the conversation changed or is no longer accessible. Preserve only input still permitted under the existing draft/access lifecycle. Never keep a hidden copy merely to promise universal draft recovery.

### Journey 3: select existing pages

1. An authorized curator opens **Support settings → Guidance**, also reachable through Manage guidance from the finder. State: **Pages selected here appear in Support. Publishing stays in Web Studio.** Ordinary workers need not see editing controls.
2. Select **Add published page**. Search through the qualified owner boundary for eligible published pages within the tenant. This curation search may be broader than the worker's selected set; its role and scope must be explicit. It is not a general URL-entry box or an external-site importer.
3. Inspect the actual page, site, locale and public destination. Pick the exact source scope. If already selected, show **Already in guidance** and open the existing entry; retries/concurrent additions do not create visually duplicated entries.
4. Save with **Add to guidance**. This changes selection only, sends nothing and does not publish a page. Confirm the durable result and return to the retained list/search. If the source became unavailable or permissions changed, preserve the selection context and show a specific failure; do not report success for a rejected save.
5. The management list displays current availability and source identity, not copied article bodies. A concise issue filter exposes unavailable selections. Use source title/site/language instead of a second editable title, body, author, approval workflow or category hierarchy.

Selection and CMS publishing are independent authorities. Do not automatically give D19 inbox reply reviewers tenant-wide guidance curation or CMS publication rights because their roles sound similar. Use the actual qualified tenant permission model; a user may hold one, both or neither capability.

### Journey 4: create a needed public page

1. If no appropriate published page exists, the authorized author uses the existing **Web Studio** creation flow. Support may provide a contextual handoff but no new editor, page type, template key or automatic article generated from the conversation.
2. The CMS owner governs draft, site, language, preview, approval/publish and URL. A pending draft is not an eligible guidance result. The handoff carries at most the intended source task/return context; it must not prefill private requester history, CRM values or attachments into a public page.
3. After actual publication and public eligibility, return to Add published page and deliberately select it. Publication alone does not add every new public page to Support.
4. Staff lacking CMS authorship see that publication needs the website/content editor. They can continue answering with existing wording; do not force a blocked create flow, request credentials, invent a Support ticket for editorial work or quietly send a message on their behalf. Any implemented handoff uses an already qualified owner capability.

### Journey 5: update, remove, withdraw and restore

Public content withdrawal and a transient lookup outage are not the same event. The UI needs both **This page is no longer available** and **We couldn't check this page. Try again**. Neither should silently erase the worker's message. A withdrawn linked source must be reviewed before a source-bound link is admitted for sending; the root data/preparation contract should define the exact fresh-check and retry boundary.

Routine article edits do not live-rewrite authored drafts or historical messages. Link-label changes should retain source provenance; changing the destination must not preserve a misleading qualified-guidance claim for a different URL. Ordinary pasted/manual links remain the existing P17 link capability, so this feature must not promise global withdrawn-link detection or add an arbitrary URL crawler. Explicit source-bound versus ordinary-link behavior needs one coherent implementation contract, not a client-only badge.

## Empty, loading, error and changed-context microcopy

Suggested wording is product judgment and should be tested in the actual shared UI:

| State                                | Visible copy and action                                                                                                                 |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Nothing selected for Support         | **No guidance has been added yet.** Staff can continue with Saved replies. Authorized curators see **Add published page**.              |
| Filter/query has no match            | **No guidance matches this search.** Keep the query and visible filters. Offer Clear filters only if filters exist.                     |
| Lookup failed                        | **Guidance couldn't load. Your draft is unchanged.** Retry. Do not show a successful zero count.                                        |
| Page withdrawn before insertion      | **This page is no longer available to share.** Return to results and retain the draft.                                                  |
| Preview source changed               | **This page changed. Review the latest version before inserting its link.** Keep the chosen result and refresh only the preview.        |
| Requested language absent            | **No selected guidance is available in [language].** Offer a deliberate language choice; do not claim the English result is translated. |
| Draft moved/changed during insertion | **Your draft changed. Choose where to insert the link.** Return to the current authorized editor.                                       |
| Source removed from selection        | **Removed from guidance. The published page is unchanged.** Undo, where current authority permits.                                      |
| Guidance source needs CMS work       | **This page must be published in Web Studio before it can be added.** Authorized owner handoff; ordinary composition continues.         |

Avoid routine success modals, forced tutorial tours and alert banners for healthy guidance. A quiet confirmation and the visible changed draft/list are enough for reversible actions. Destructive source actions remain in their owning surface and follow that owner's confirmations.

## Accessibility, visual quality and production-shaped proof

Keep the list compact and text-led: source title first, description second, quiet site/language metadata and clear action hierarchy. Use the existing Maia spacing, radii, typography and semantic tokens. Selected rows, focus, unavailable states and errors must be distinct without relying on color. Keyboard opening should be immediate under Core's motion rules; no animated sorting or focus-stealing refresh.

The search field is a simple labelled form. Rich result previews belong outside listbox option text if the chosen shared component pattern requires it. Announce settled result/error status without reading the entire result body on each keystroke. Escape closes the current overlay level and returns focus; Enter in search/results does not activate the conversation Send button. Respect IME input, right-to-left content, long titles/URLs, zoom/reflow, reduced motion and touch keyboard space. Do not force three side-by-side panes on mobile; use list → preview → retained draft with explicit Back controls.

Required independently falsifiable journeys before release:

1. Find an eligible source by title and by a supported body term; prove the UI's stated search coverage matches the actual owner contract.
2. Distinguish same-title pages in two sites/languages, clear a filter and deliberately choose another language without hidden fallback.
3. Search with IME and keyboard, inspect preview and insert without ever sending or changing recipients/mode/status.
4. Insert at a caret, with selected text, after focus leaves the editor, after the draft changes and after conversation switching; prove no lost text or wrong target.
5. Undo/redo insertion while a saved reply, managed signature, attachment and D24 plan exist; verify true document/source provenance and unrelated state.
6. Repeat from CRM, navigate to CMS/public page, then return to the same permitted draft, list/record context and scroll position.
7. Use a read-only actor, curator without CMS rights, CMS author without curation rights and actor whose rights are revoked mid-flow; verify precise allowed actions and no hidden data.
8. Add the same source concurrently/retry after an uncertain response; show one durable selection and a truthful result.
9. Create draft in CMS, preview, publish and select; verify no draft/preview URL is offered, no case content is prefilled and no publication implies automatic selection.
10. Remove selection, republish source, restore selection, unpublish/restore source and retire a locale/site; prove the state distinctions and actual public eligibility.
11. Withdraw the source after preview, after insertion and before final admission; retain permitted draft text and show the exact repair path without a misleading success state.
12. Fail lookup, preview and eligibility checks independently; do not report no results as an outage or block unrelated ordinary Support work.
13. Preview pages containing forms, scripts, embeds, long content and unsupported blocks; prove passive behavior and honest partial-preview notices.
14. Test the full flow at narrow width, zoom, with touch and assistive technology; automated checks supplement manual focus/order/announcement verification.
15. Inspect logs, traces, counts and source-use reporting for raw search/private text, incorrect insertion-as-send counts and claims that guidance caused resolution.

These are **required future proof**, not tests executed in this grooming task. No screen, browser implementation, real tenant workflow or email client was tested. Primary documentation and independent reasoning support the design direction; they cannot establish perfect UX, quantitative time savings or legal sufficiency. The parent synthesis should record the exact selected amendments and keep unexecuted implementation/release obligations visible.

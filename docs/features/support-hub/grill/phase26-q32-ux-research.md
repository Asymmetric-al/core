# Q32 — Attachment inspection: independent UX research

**13 September 2026. D1–D31 are founder-ratified. Q32 is unanswered.** This is one proposed product choice about how broadly staff inspect existing conversation attachments within Support. It is not a new file manager, an upload-policy vote, an extension of attachment-content search or a new authorization model. No format allowlist, size/page limit, renderer, package or accepted D32 is selected by this research.

## Genuine remaining decision

The accepted contracts establish attachment custody and safety but do not settle inspection breadth:

- [D16 selective removal, R15](phase26-d16-adversarial-review.md) requires source-aware private delivery/restriction across attachment bytes, thumbnails and previews. It rejects binary region editing as redaction and preserves distinct owner artifacts.
- [D19 intake review, R06](phase26-d19-adversarial-review.md) permits only separately qualified attachment preview/download with current permission and scan state. Its ordinary review cannot open unscanned files.
- [D22 search, R21](phase26-d22-adversarial-review.md) permits qualified filenames even where a file is unsupported for preview. A filename result must not open or download bytes automatically; attachment-content search/OCR/AI remains outside current scope.
- [D26 CRM continuity](phase26-d26-adversarial-review.md) uses the same canonical Support detail with current joint authorization, rather than a separate CRM transcript/file copy.
- [Phase 29 roadmap](https://github.com/Asymmetric-al/core/blob/7abd2c11ffd4ed70c6775c4fd6f51c996e4350dd/docs/prds/sitestacker-parity/roadmap.md#L3146) owns immutable byte identity, storage/access, malware hygiene and audit. It does not prescribe an already-qualified image/PDF/Office viewer. Support retains attachment meaning and relationships; no entire future File Manager is required merely to qualify a narrow private-byte consumer.

Current source inspection and the parallel scope review found metadata-oriented attachment presentation rather than an established qualified viewer; the composer `AttachmentChips` component explicitly describes itself as staging stub UI. This is an implementation fact, not authority to retain that experience. Conversely, keyboard accessibility, complete query behavior and ordinary source safety are already mandatory quality obligations, not credible optional product forks. Existing priority behavior is already incorporated in D10 and should not be reopened as if unselected.

## Three meaningful choices

| Option                                                                                   | Actual experience                                                                                                                                                                                                                                                | Strongest benefit                                                                                                                                     | Real cost or limit                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Preview common images and PDFs in Support, with qualified download — recommended** | Staff deliberately open eligible common image/PDF attachments in a focused viewer while retaining their conversation and draft context. Download remains a separate qualified action. Other eligible file types have metadata and their qualified download path. | Reduces opening/saving files elsewhere for common visual inspection while keeping the first viewer scope bounded.                                     | Requires a declared supported subset, private source-aware rendering, useful controls, accessibility and clear unsupported/failure states. It does not promise every image or PDF can be rendered.                           |
| **B — Attachment details and download only**                                             | Clear attachment cards show permitted filename/type/size/source and actual availability. Staff deliberately download a qualified file and inspect it with an appropriate local/browser application. No new in-Support attachment viewer.                         | Smallest rendering and maintenance scope. Strong when attachment inspection is occasional or staff already require specialized external applications. | More context switching and local file handling for routine inspection. It retains all existing authorization, malware, retention and truthful-state requirements; download is not automatically the safer route.             |
| **C — Common previews plus broader document previews**                                   | Includes A, then supports a bounded additional set of document formats through qualified shared byte/rendering capabilities, with the same deliberate open/download distinction.                                                                                 | Helps teams that repeatedly need to inspect supported office/text-style documents without leaving their work.                                         | Additional renderers or conversion fidelity, private processing, version/access lifecycle, type/platform limitations and maintenance must be qualified. It is not arbitrary-format support, an editor or a new File Manager. |

These are competing current scopes, not three tenant modes that all ship. B concerns this additional attachment-inspection surface; it does not undo already-qualified inline message-image rendering or authoring. C includes a useful common baseline and is not deliberately burdensome. “In Support” means a coherent viewer with preserved context; it need not expand every file into the conversation body or create a permanent multi-pane workstation.

**Single recommendation: A.** It serves the practical task of checking an attached screenshot or document without asking staff to assemble a document system. A is a proportionate product judgment, not a measured Asym usage result or proof that all ministries mainly use these formats. B is compelling when inspection is rare/specialized. C is compelling when repeated additional-format demand justifies its full source/rendering contract. No evidence yet establishes that broader previews are necessary for this release.

## Reported friction and interpretation

Zendesk's [PDF-preview community request](https://community.zendesk.com/ideas/preview-pdf-within-the-ticket-4930) and Zoho's [Desk community listing](https://help.zoho.com/portal/en/community/zoho-desk) contain reports that downloading documents to inspect them interrupts support work, including a reported change from preview to automatic download. These are self-selected and partly historical reports, not measured prevalence or confirmed current capability. They support testing context switching and surprise downloads; they do not prove that all Asym teams need office-document preview or that any browser preview is secure.

For nonprofit users, an attached screenshot or PDF in an existing donor-care/missionary-related conversation is a reasonable illustrative inspection task. It is not evidence that staff may inspect restricted care records, identity documents or giving artifacts merely because someone attached a file. The authoritative business record and its current access rules remain separate.

## A's practical journey, without preselecting its full implementation

1. **Find the attachment where it belongs.** A message or authorized Support detail shows permitted file identity and truthful availability. Preserve which original message/occurrence it belongs to; equal filenames do not mean equal files. A D22 filename search locates that metadata and does not itself open bytes.
2. **Choose Preview deliberately.** For a qualified supported attachment, open a focused viewer preserving conversation/draft/list/CRM return context. The staff member does not need to download it to a local folder just to look. Preview still transfers/uses bytes or a derived representation in the viewing environment; it is not a guarantee of zero local memory/cache exposure.
3. **Inspect the actual material.** Show readable filename and source context with necessary image zoom or PDF page/navigation controls. Preserve original aspect, legibility and page meaning. A thumbnail is not the whole file. No document editing, annotation, binary redaction, signature validation, attachment search, OCR or AI interpretation is implied.
4. **Download only when useful and currently permitted.** The separate action follows current source/private-byte rules. It does not automatically run an external application, expand archives, produce public links or add the file to CRM. A browser/OS may handle a deliberate download according to its settings; product copy should not claim control of every destination.
5. **Close and continue.** Return to the same permitted message, draft, search/list and CRM context. Viewer close is navigation, not deletion, Mark reviewed, Resolve or confirmation that the contents are correct. Required file-access audit remains with its actual owner.
6. **Handle unavailable material honestly.** Unsupported preview may still allow qualified Download; blocked/held/unscanned/restricted/expired bytes may allow neither. Do not put a generic Download fallback behind every error. A failed preview is not a missing source file, and a permitted filename is not proof of byte access.

If B is selected, steps 2–3 become explicit qualified download and external inspection while the Support context remains available for return. If C is selected, the same journey extends to its expressly qualified additional formats; it does not add a general document editing or organization surface.

## Consequences that must remain bounded

| Concern                                                  | Direction for the selected answer's full review                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Preview breadth confused with upload/receive support** | A file can be accepted but not previewable. Unsupported preview is not permission to discard admitted bytes or widen accepted file types. Exact formats/limits belong in the selected answer's qualification.                                                                                                              |
| **Unsafe rendering or accidental execution**             | Current original-source rights, immutable byte version, classification and hygiene gates apply to each preview/download/derived read. A clean scan is not an unlimited execution grant. Rendering cannot enable active file behavior or load arbitrary remote content.                                                     |
| **Source removal and stale previews**                    | D16/D17 restriction/expiry/restore rules govern thumbnails, rendered pages, cached metadata and originals. A previously obtained URL or display must not become a revocation bypass. No promise to erase an independently downloaded file remotely.                                                                        |
| **Wrong file or lost context**                           | Preserve original occurrence/version and clear filename/type/size where permitted. Close/back restores the active conversation/draft rather than moving to the next request or creating a CRM copy.                                                                                                                        |
| **A bigger viewer becomes a document product**           | No folders, document authoring, annotation, comparison/version-control product, binary redaction, public sharing or bulk ZIP export is implied by A/C. Reuse qualified shared bytes/rendering where sound; do not wait for all of future P29 or implement it inside Support.                                               |
| **False universal browser/mobile support**               | Test the chosen supported subset across Core's actual browser/mobile matrix. Broader formats require declared conversion/fidelity and failure behavior. No exact vendor limits or operating-system capabilities are imported.                                                                                              |
| **Accessibility and low bandwidth**                      | Named controls, readable current page/file, keyboard focus/close/return, text/accessible source support where available and restrained on-demand loading are needed. A scanned page is not magically accessible text; no OCR is smuggled into A. Preserve truthful qualified fallback without forcing automatic downloads. |
| **CRM access laundering**                                | Support-origin files remain attached to their source conversation. CRM entry needs current joint rights. No relationship, assignment or same-email identity grants file access; independent official records are neither deleted nor overwritten through Support inspection.                                               |
| **Email Studio and composer coupling**                   | Viewing/downloading an existing file prepares or sends no message. Actual attachment selection into a reply stays with D4/D18/D23/P17/P6, under current source and audience checks. No saved-reply or shortcut action automatically republishes a viewed file.                                                             |

A pleasant first viewer can be complete without every format. The later detailed review must settle supported formats, fidelity/active-content constraints, exact controls, metadata states, loading/failure behavior, mobile/accessibility, current authorization, cache/revocation, renderer/dependency qualification and measured boundaries. Those are necessary consequences of the selected scope, not all requirements already selected by asking Q32.

## Final recommendation and stage

Recommend **A — Common image/PDF previews in Support plus qualified download**. Its strongest benefit is deliberate inspection while keeping the work context. B remains the smallest legitimate alternative; C remains a broader legitimate alternative where additional document formats justify their actual rendering and lifecycle obligations.

Q32 remains unanswered. No exact image extensions, PDF profile, Office formats, byte/page limits, renderer or new platform dependency is chosen here. No file was opened from a real conversation, provider or inbox; no prototype, browser usability test, runtime security test, product edit or external mutation was performed. Source research and independent scope checks justify the question, not a claim that the proposed viewer is implemented, universally safe or empirically optimal.

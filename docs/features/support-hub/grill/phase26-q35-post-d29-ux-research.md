**Recommendation: A — Authors can edit their own ordinary internal Support notes, with visible currently permitted revision history.** Current primary evidence still supports this as a useful low-friction pattern, but does not establish a vendor consensus or prove the complete proposed Asym history contract. B is a serious alternative prioritizing unchanged published chronology. C is a legitimate compromise with an additional timing rule; no grace duration has been selected or established as a universal standard.

## Why the question remains genuine

D17-R05 explicitly says **if note editing is supported**, its saves retain the existing content deadline. It settles retention, not whether ordinary edits are offered. D16's privacy redaction is not an ordinary correction/history feature. D15 E3/R08 already distinguish first publication from routine edits and preserve delivered notification facts. Those accepted constraints apply to every option.

The previously inspected source exposes private-note creation/presentation, not a qualified author-edit/revision command. This report rechecked the actual accepted D15/D17 wording and existing Q35 scope/evidence; it does not claim a new runtime implementation or independently refreshed GitHub state. The root's current source evidence owns that separate verification.

The policy concerns human-authored posted **internal Support notes** only. Incoming/sent correspondence, generated events, CRM-owned notes, D26 staff-recorded request briefs and D16 sensitive-content removal retain their existing owners. Viewing a Support note through CRM does not make it a second CRM note or broaden its permissions.

## Three real policies, with the same concrete example

Example only: Maya records that the requester asked for a Tuesday callback, then notices she transcribed the request incorrectly: they said Thursday. If the requester **later changes** Tuesday to Thursday, that is a new event and gets a new note in every policy.

| Policy                                                    | Maya's actual action                                                                                                                                                                              | Best reason to choose it                                                                                                                             | Real tradeoff                                                                                                                                                                                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Author edits with visible history**                 | Edit her own still-permitted note, correct Tuesday to Thursday, and save. The current note keeps its original author/posting time, shows Edited and offers currently permitted earlier revisions. | Correct information remains easy to read without a separate entry for each typo or transcription repair. Changes remain attributable and reviewable. | Requires a narrow, reliable revision/save-conflict/privacy contract. An edit cannot recall what another person already read or received.                                                                                                |
| **B — Linked corrections only**                           | Add a new correction linked to the original. Both entries make their relationship clear; the original wording remains unchanged except for independently governed privacy action.                 | Gives the clearest unchanged published chronology and avoids ordinary in-place rewriting.                                                            | Adds entries even for small mistakes. Readers must be able to discover the correction from the original, not act on an isolated stale sentence.                                                                                         |
| **C — Brief author-edit window, then linked corrections** | Use A shortly after posting, then B after a single defined grace window. Earlier permitted revisions remain visible for edits within the window.                                                  | Allows immediate typo repair while stabilizing older posted notes.                                                                                   | Adds a timer and two workflows; an interruption can move the same correction into a different path. If selected, the duration and expiry/save-conflict behavior must be decided in the answer's full review. No number is selected now. |

These are three alternative product policies, not three settings every tenant must configure. C must not be described as whatever the implementation considers “brief”; selection would require one explicit rule. Its timer does not solve privacy, already-read copies or the need to notify someone deliberately about a consequential correction.

## Why A is the single best recommendation

For ordinary staff collaboration, a clear current note plus accountable changes is a better default than requiring a second message for every recording mistake. Author-only editing avoids a new administrator power to rewrite colleagues' attributed statements. Qualified history avoids adopting Help Scout's loss of earlier note text. The proposed action is local to the existing note and preserves the canonical Support source through CRM.

The strongest case against A is that readers may have acted on its earlier wording. Visible history alone does not solve that. The permanent distinction is **correction versus new event**, coupled with the already-approved deliberate staff-attention path when a material correction needs action. Do not claim Edited means a teammate noticed, add automatic edit emails, or ask AI to classify whether a correction is important. New facts, decisions and performed work retain a new dated note.

B would be preferable if the founder prioritizes unchanged publication over routine correction friction. C would be preferable if the founder accepts its extra time boundary to stabilize older notes. Neither is a decoy. A remains the recommendation because it handles both immediate and later-discovered recording errors consistently without introducing a grace-period cliff.

## Conditional A journey, not a selected design

If A is selected, the full adversarial answer should make these outcomes precise:

1. Reach the exact current-authorized Support note from Support or CRM. Offer Edit only to the trusted original human author with current source/edit permission. Assignment, a matching email or tenant oversight does not confer authorship.
2. Edit through the shared qualified Tiptap/Internal-note controls. Keep the internal label, separate reply draft, source, reading mode/Find, position and focus intact. Edit and history must be discoverable by keyboard/touch, not only a hover pencil.
3. Save or Cancel deliberately. Distinguish saving, definite failure, unknown result and version conflict. Preserve safe unsaved text without reviving expired/redacted material or silently overwriting another device's change. Do not expand D34's published composing meaning or share the edit draft by implication.
4. Keep original author/posting time and chronological position. Show the edit's truthful actor/time separately. A bounded history disclosure exposes only currently permitted earlier revisions, clearly labelled as earlier versions; no persistent document-diff interface is needed by the question.
5. Use a fresh update for later circumstances and existing deliberate attention for a material correction that needs action. Routine edits do not renew D17's deadline or emit a new D15 publication alert. Delivered notification bytes remain historical facts.
6. Apply current source privacy, retention, access and attachment/mention policies across detail, history, search, previews, pending notifications and CRM entry paths. Sensitive-content removal remains D16; ordinary history cannot become a way to retrieve forbidden text.

The post-selection review must settle exact revision/cardinality/command bounds, legacy-author qualification, mentions/attachments, offboarding, concurrent save/expiry/redaction, correction-link behavior where needed and actual mobile/accessibility/release proof. It must not assume a general versioning platform, co-editing service, native-mobile feature or delegated editing is necessary. This question does not freeze those details before the founder's choice.

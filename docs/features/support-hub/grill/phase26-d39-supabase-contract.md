## Primary technical evidence

PostgreSQL `nextval` supplies distinct numbers but is not rolled back with its calling transaction. A lower number can therefore belong to a transaction that commits after a later-numbered row. Using the maximum allocated ID as “everything before this was visible” is invalid. Read Committed SELECT sees the statement's committed snapshot; separate statements may see different snapshots. A source-local row update protected until transaction completion can serialize content admission. [Sequence functions](https://www.postgresql.org/docs/17/functions-sequence.html), [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [explicit locks](https://www.postgresql.org/docs/17/explicit-locking.html)

The Supabase documentation connector and current public docs were consulted, and `changelog.md` was fetched via ordinary HTTP into the work area. Channel authorization is calculated on join and its policy cache refreshes on join/new JWT; it is not a database recheck for every Broadcast/Presence message. Realtime authorization does not prove a person viewed content or replace the personal-state transaction. No application reading tables belong in the provider-owned `realtime` schema. [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization)

Previously identified skill shorthand is corrected here too: omitted UPDATE/ALL WITH CHECK can inherit USING; SECURITY DEFINER uses its owner's actual rights rather than universally bypassing RLS; grants, view ownership/invoker semantics and effective policies must be checked together. No skill or formal specification is edited. [PostgreSQL policy semantics](https://www.postgresql.org/docs/17/sql-createpolicy.html), [function privileges](https://www.postgresql.org/docs/17/sql-createfunction.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

## Exact proposed contract

### C01 — Personal meaning and source ownership

“Support owns a self-only reading aid over original conversation sources. One person's view or explicit personal action changes only that person's markers. It never changes shared Open/Waiting/Resolved work, assignment, reminders, reply targets, due timers, native-content clocks, notification engagement, delivery evidence or CRM business truth. No reader roster, named last-seen time, analytics or requester receipt is exposed.”

Store state by trusted tenant, real staff owner and immutable original source; do not key by current merged root, email, assignee or Party. The combined conversation cue is a current-authorized projection of its relevant originals, not a second mutable counter. Markers are inexpensive personal UI state, not P6 semantic delivery intents.

### C02 — Eligible content and the honest absent-state baseline

“Derive automatic unread from currently readable, first-qualified human content authored by somebody else: admitted human requester input, qualified recorded initial request content, published native-human internal notes and other staff's admitted human replies. A locally admitted human reply may be queued; its content is new while delivery is separately truthful. Do not wait for the optional-follow acceptance event merely because D15 has its own timing.”

Exclude private drafts, generated/system rows, unqualified/quarantined bodies, source edits, redaction/expiry, assignment/status changes, timers, attachment progress, automatic confirmations and later provider callbacks. Count a genuine source contribution once at first reading eligibility; late provider dates and imports of duplicates do not rewrite that clock. Prove native provenance rather than trusting `type:note` or caller author JSON. Trusted same-person authorship can suppress self-generated automatic unread; matching email cannot.

No personal marker means unvisited/unacknowledged: show Unread only if currently permitted eligible other-authored content exists. Empty/self-only sources have no automatic unread cue. Existing and newly accessible unfamiliar history is not fabricated as already viewed. There is no enrollment cutoff, read-all migration, per-member source backfill, aggregate unread burden or requirement to visit every historical source. A separate deliberate manual marker has the meaning specified in C07, not a claim of new external input.

### C03 — A compact state model, not a readership ledger

“Use one personal original-source state with a stable incarnation/current manual-intent epoch, optional manual-unread override and a source-qualified covered frontier. The common homogeneous-access source needs one cutoff. Where actual source visibility is heterogeneous, retain the smallest bounded coverage representation that distinguishes already covered authority from newly admitted coverage; never silently reduce it to an uncomparable hash.”

The minimum authoritative facts are tenant/owner/original, current state incarnation/intent epoch, covered source/visibility basis and cutoff, and the manual override. Operational updated time is not shown as a reader surveillance record. No per-message-per-person receipt table, every-keystroke event, global reader roster, per-arrival personal fanout, notification intent or durable prepared-read artifact is required. State is created lazily by a qualified view/manual command, not by merely listing an unread source.

### C04 — Commit-ordered source content frontiers

“Every first-qualified eligible contribution receives an original-source reading ordinal under the same locked source transaction that admits its actual content/eligibility. The normal source-row counter and content row commit together. A later ordinal cannot become visible while an earlier allocated eligible contribution in that original can still commit behind the reader's cutoff. No counter advance on reads, ordinary edits, redaction, arrival retries or provider callbacks.”

Reuse an existing qualified source-admission ordinal only if its eligible classes, timing and commit discipline actually satisfy this rule. Do not reuse D15 optional-follow acceptance ordering blindly, a PostgreSQL sequence, auto-increment/UUID sort, transaction ID, client clock, email Date, created_at or generic updated_at as commit order. Sequence gaps are not the only problem: later commit is the counterexample. Per-original locking avoids one tenant/global serial counter and uses the already-required source admission transaction. Any source-import/backfill must preserve first qualification and cannot insert newly eligible content invisibly below a previously acknowledged live cutoff.

Read snapshot body/projection and its offered cutoff must come from one coherent committed snapshot or equivalent proved source protocol. Fetching an old body and then the latest head in a later statement is unsafe. PostgreSQL isolation choice must be tested with the actual query/lock protocol; merely declaring Repeatable Read or Serializable without handling conflicts/retries does not prove the application behavior.

For existing content that predates this control ordinal, establish a **source-local migration baseline before any personal marker can be admitted for that source**. Gate all relevant source-eligibility writers and marker commands, capture the complete already-committed qualified eligible content under the source protocol, assign stable internal reading-control ordinals, and serialize every later eligible admission above that boundary. Preserve original content IDs, native admission times and provenance. This does not reconstruct or claim actual historic COMMIT order, create a native content/D15/D17 event, or mark any person's history Read. It is not the rejected per-user enrollment cutoff. An incomplete/unproved baseline cannot activate personal acknowledgments; later first-eligible material never slips behind live cuts because it has an old email/content date.

### C05 — Server-bound snapshots and acknowledgment

“A reader or explicit manual action uses a bounded server-issued snapshot token binding tenant, real owner, exact original set, source cutoff(s), current visibility coverage, topology/context generation and personal state/view-intent epoch. The client cannot claim an arbitrary future cutoff or another source/member. Revalidate current source access at acknowledgment; a token is context, not a grant.”

The UI sends a qualified automatic acknowledgment only for the actual deliberate visible conversation reader under the selected UX rules. Prefetch, hidden panes, API fetch, CRM-profile loading, Tiptap mounting/focus, composing awareness and programmatic background refresh cannot themselves mint a new deliberate-view activation. A read acknowledgment is a product cue, not attestation of comprehension, all historical paragraphs or file inspection. Server validation does not pretend it can prove human attention.

Active composition is not qualified viewing of a newly arrived contribution even when the latest message region happens to remain visible beside the editor. Keep the new content unread and offer the established intentional return-to-current-content path without interrupting the draft or IME. A merely saved/inactive draft does not block ordinary reader qualification. Intentional return still uses the valid original view-activation/manual epoch; it cannot silently defeat a later Mark unread that requires a new conversation opening or explicit Mark read.

Keep raw source ordinals, hidden coverage entries and prior forbidden authority references server-side. The browser receives an opaque, integrity-protected bounded context token or equivalent owner reference plus only current-authorized display state; a merely base64-encoded signed object can still disclose its contents. Do not expose raw ordinal gaps as an accidental hidden-message count through the token, direct state relation, URL, analytics or error detail. Use existing scoped context mechanisms rather than a new per-view durable material store.

Apply only the token's offered cutoff, never “whatever is latest when ACK arrives.” If H+1 commits while H is being viewed/acknowledged, H+1 remains unread until separately included in qualified current viewing. The ordinary combined reader can acknowledge its complete currently authorized original/visibility snapshot vector after the latest eligible combined region is rendered. Older bodies may remain folded, paginated or offscreen; no per-original reading chore or all-history inspection is implied. Missing/unproved/truncated/inaccessible coverage or failure of the required current reader load cannot be included by guessing. Slow/out-of-order responses bind their original owner/source/session; they cannot clear a later source or account's marker.

### C06 — Authorization coverage: preserve contractions, expose expansions

“The source authorization owner supplies a bounded, control-only coverage basis and a sound comparison: current eligible coverage is unchanged/contained in acknowledged coverage, or it contains newly admitted coverage. The representation references existing source visibility/grant episodes, not new permission groups created by this feature. A hash/version mismatch alone cannot determine which case occurred.”

Retain acknowledged cutoffs for proven retained coverage. Redaction, expiry, hiding or loss of access removes eligible contributors; it does not reset the remaining already-covered source to unread. Newly readable coverage that was previously hidden has no acknowledged cutoff, even when its content ordinal is below another scope's old cutoff. A regrant starts a newly qualified access episode unless the owner can prove the prior retained coverage is still valid under its actual rules. Neither a grant expansion nor merge can inherit a hidden source's Read state from unrelated content.

A compact vector of cutoff plus existing visibility/grant-episode basis is the narrow implementation direction for actual heterogeneous sources; the ordinary source remains one entry. It must be bounded by a measured source contract, with subset/added-scope checks provided by the actual authorization owner. Where no such owner contract exists yet, implementing and qualifying this narrow coverage contract is a prerequisite, not permission to ship a hash-only approximation. Do not create a message-reader ledger, user fanout on publication, arbitrary ACL language or new policy-history platform to obtain this proof. Where coverage cannot currently be established, return a truthful unknown/needs-current-view state and deny automatic catch-up; do not claim Read or reset all remaining material merely because an opaque epoch changed. Activation must qualify the supported policies and expansion/contraction cases, rather than monitor an unproved implementation.

### C07 — Manual Read/Unread is a small conditional personal command

“Explicit Mark unread changes only the caller's personal override and advances the current intent epoch with an expected-epoch comparison. Mark read advances that epoch and covers only the exact offered source snapshot. Repeating an old command cannot reverse a later manual choice. Automatic ACKs never advance the manual-intent epoch; they only monotonically extend the currently valid covered cutoffs when their deliberate-view activation epoch still matches.”

A manual Unread while a source is already open must survive that view's later effects, rerenders and background refetches. Existing views/tokens remain tied to their earlier activation epoch; only a fresh deliberate opening or explicit Mark read after that choice can clear it according to the selected UX. New content never clears the manual override. A user's self-authored contribution never silently marks older other-authored content Read. The manual flag is not an unread-message count or workload obligation. An explicit revisit marker can apply to a readable source containing qualified human content, including self-only content; an empty/inaccessible/excluded-only source supplies no content to mark. The main decision may narrow that action without changing automatic baseline rules.

Use self-only CAS and max operations, not one forever receipt per click. Unknown response refetches the currently authorized state and reports that state; never blindly retry the old intention under a newly fetched epoch. A stale comparison may be a conflict/no-op even if the desired boolean happens to match; do not infer the exact earlier outcome from today's value. No outbox, email preparation or business audit event is created by these personal commands.

### C08 — Bounded identities and anti-replay through cleanup

“Snapshot/view activations and manual requests are scoped to current source/access and personal-state incarnation with a bounded admission validity. Current state and minimum rejection fences live long enough that an issued old request cannot match an erased-and-recreated epoch-zero row. Regrant/retirement/restore must invalidate old access/view generations before accepting new personal state.”

Reuse existing bounded authenticated command/context primitives. This does not require durable body snapshots, per-click result history or permanent reading receipts. Server-side expiry/generation checks, conditional creation and current self/source authority fence delayed duplicates; cancellation of HTTP is not server rollback. Clearing UI storage is not this fence. The exact token/recovery window and state/control retention belong to the qualified release contract and actual privacy owner, not a new guessed forever/30-day rule.

### C09 — Merged conversation projection and commands

“A merged UI cue is computed from currently admitted visible original-source reading states. Read/unread belongs to each original and is not copied into the current root. Undo preserves each original's own state, and a source newly combined with read work cannot become read just because the root was read.”

Automatic acknowledgment covers the complete authorized original/visibility cutoff vector represented in the qualified combined reader snapshot when its latest eligible combined region is presented. Representation does not require every original's head/body to be separately mounted or visible: A+B may be covered while B's older body is folded or on another history page. An A-only or incomplete/unproved snapshot cannot acknowledge B. Explicit Mark read can cover the displayed authorized component snapshot, including its precisely offered original/cutoff/coverage vector; it cannot claim later membership. Apply the reviewed personal updates atomically across that bounded set with deterministic row-lock ordering, or reject the changed scope and refresh; never sweep in newly merged/hidden members at commit. A narrower authorized view acknowledges only its actual admitted source scope, not missing or inaccessible data. Current source authority is checked before exposing even aggregate boolean/count metadata. There is no cross-tenant command and no all-inbox bulk Mark read introduced by this model.

### C10 — Database relationships, types and mutation limits

“Use actual UUID tenant/auth/profile relationships and TEXT Support original IDs. Derive the real owner/profile and active selected tenant from Core context; membership authorizes use but is not the durable owner. A tenant-aware unique original/owner key prevents duplicates. Same-tenant relationships bind coverage/source references and state; wrong owner/original/tenant/incarnation cannot be changed by a generic update.”

Use bounded nonnegative/positive integer revisions and cutoffs, preserving exact values through the API rather than unsafe JavaScript Number conversion of unbounded bigint. Cutoffs cannot exceed server-offered admitted frontiers. Closed coverage schema and valid override/epoch combinations are checked; caller timestamps never establish ordering. A manual command needs current self/source-read capability, not another domain's write/refund/note-publication permission. No client-supplied reader identity is accepted. Deleting a personal marker cannot cascade into messages, source history, CRM or notification state. This feature adds no money field or financial arithmetic.

### C11 — Grants, RLS and current acting context

“Personal-state reads/mutations use packages/api commands and approved packages/database read projections. Apply least grants and RLS/self-owner/current-source predicates on all exposed relations. Check effective SELECT/USING/resulting-row WITH CHECK, column immutability, permissive-policy unions, function EXECUTE/search_path/owner, invoker views and every privileged service path. A normal admin or broad tenant staff policy cannot enumerate others' reading state.”

Current source/data access is independent of the private personal marker: own marker possession cannot reveal a now-forbidden original or hidden content. Do not emit state bodies, usernames, times, failure details or constraint errors that leak another actor/source. App-metadata claims can be stale, user_metadata is caller-editable, and caller-set database context is not inherently trustworthy; reuse the real current Core membership/source authorization rather than wrapping `auth.uid()` around an unchecked agent ID. Service-role bypass requires the same explicit source/self checks. FORCE RLS does not constrain every bypass role. A custom PostgREST pre-request check cannot stand in for Storage/Realtime/other route enforcement.

### C12 — Privacy, restriction and retention

“Treat personal markers, covered source/grant references and operational times as potentially identifying metadata under an actual owner purpose and finite retention/cleanup policy. Exclude them from ordinary CRM Activity, staff productivity reports, viewer rosters, public APIs, donor/missionary portals, search bodies and generic exports. No read-time history is needed.”

Ordinary successful view/ACK/manual-state operations must not create durable actor-plus-original-source-plus-time activity or diagnostic history. Use aggregate latency/error/conflict counts with bounded non-identifying dimensions; do not log success request bodies, coverage/view tokens or resource-identifying paths correlated with a principal. Qualify application, gateway and tracing configuration, not only one logger. Keep current self-state and necessary bounded command fences, not a succession of every previous reading state. Narrow security/incident events may retain minimum actor/resource facts under the existing restricted audit purpose and actual retention; this exclusion does not delete required security evidence or authorize general reading analytics.

D16/D17 restrictions govern ordinary source visibility and must invalidate forbidden cached metadata/contexts before use even when physical cleanup lags. Source contraction/redaction cannot manufacture new unread for retained covered content; a marked-unread source that becomes wholly unavailable shows no forbidden dot or existence. Independently valid metadata survives only under its declared purpose, not because it once identified a read note. Regrant restores no erased content. Privacy/offboarding cleanup handles self-state without transferring it to a replacement user, assignee, CRM owner or reused email. Source data restoration must restore its current source/privacy/access and personal-state invalidation barriers before old requests are accepted.

### C13 — Failure, efficient queries and optional Realtime

“Compute the personal boolean from bounded existing conversation rows, self-state and an indexed existence/frontier query over currently eligible source contributions. Do not scan whole histories into the browser or return raw global unread_count. Index current owner/original state lookup and original/eligible ordinal/visibility predicates; authorize before LIMIT/pagination. Sparse markers grow with actual personal interactions, not every message times every staff member.”

No per-keystroke polling, per-row editor or eager body/attachment load is needed. Coalesce same-view acknowledgments; a stable covered cutoff requires no duplicate write. Realtime may carry minimal private invalidation to refetch through current authority, but it is optional and neither ACK transport truth nor a complete permission guarantee. Do not broadcast another person's reading state or enroll the relation into public table streams. Connection-time channel policies and cached JWT authority must not leak forbidden source activity after revocation. Current API/database checks remain authoritative.

On failure, retain only currently lawful existing state with an explicit stale/unknown cue; never fabricate zero unread or Read. Personal-state failure does not stop independent authorized drafting, posting, CRM inspection or actual work handling. Measure actual row/source volume, visibility-scope bounds, page size, concurrency, lock duration and p50/p95 before activation. No benchmark multiplier, instant-sync guarantee or new numeric unread count is inferred from vendors.

### C14 — Email Studio, P17 notification engagement and CRM

“Reading-state changes never publish/prepare/send/rerender email, alter P6 delivery evidence, read/archive P17 notification groups, change Follow membership or acknowledge mandatory source review. P17's notification engagement is a separate capability; D34 composing presence does not attest to reading. A qualified Support reader reached from CRM updates the same self/source reading state without CRM copies or an Activity.”

CRM-only profile loading, list prefetch or a hidden Support panel cannot count as the selected reading action. Actual source content remains owned by Support and adjacent business facts stay with CRM/giving/care owners. External tracking pixels, requester receipts, shared-team read switches, read analytics, document/attachment acknowledgment and generic workflow triggers are not added. Reading says nothing about responsibility, comprehension or business completion.

### C15 — Migration, source qualification and safe rollout

“Do not import the old shared unread_count as every staff member's marker, divide it among agents, backfill fake read times or mark all old history read. Qualify source-first-human-content provenance and commit-ordered reading ordinals before activating personal cues. Retain accepted original source identities; unsupported legacy/generated content gets the owner's honest qualification treatment rather than guessed author/eligibility.”

Deploy source ordering/coverage and private-state commands/readers first, then current UI semantics; retire old global marker reads/writes for the new cue. Old clients cannot submit unbounded future cuts, set another owner, drop coverage proof or restore stale epochs after schema changes. Initial enabling is on-demand absence semantics, not a global personal-state fanout. Scope kill switches disable the affected optional cue/state commands without changing real work, destroying personal intent or rolling back into shared-read semantics. Compatible roll-forward retains source/epoch/privacy fences. Source ordinals and exported control metadata must preserve semantic identity across safe migration; no provider-mailbox read synchronization is introduced.

Existing qualified legacy content uses C04's gated source-only ordinal baseline before personal state is enabled, rather than invented historical commit order. The boundary must cover all relevant writers and a complete committed source population; future/live eligibility then serializes above it. Real content/provenance/time and existing D15/D17 activity remain unchanged, and every unvisited person's content still follows C02's ordinary Unread baseline. Test interrupted/repeated migration, late old writers, incomplete qualification and activation ordering; do not generate a reader-by-source backfill or fake read audit.

## Facts and identity ownership

Current Core `getAuthContext` resolves authenticated user/profile/tenant but does not return a qualified actual auth-session ID. Current Support helper agent/email matching does not prove the publisher's real internal identity or exact original-source access. These are verified source gaps, not allegations of an exercised exploit. The identity owner must supply the real-session predicate before activation. Token refresh preserves an actually continuing session; logout/revocation or a changed real session cannot reuse its old cue instance.

Do not introduce a second staff/contact table. A requester can be unidentified, use a shared email, represent an organization or write on another person's behalf; none of those facts identifies the authenticated composing staff member. A staff profile is not its public reply signature, CRM record owner or support assignee. The same real staff identity may hold different roles across tenants. All current source/role/identity visibility checks remain explicit.

## Minimal logical data shape

Use regular logged application rows. Do not add an append-only activity history, custom managed-realtime objects or raw-row subscription publication. Index tenant/context plus observer expiry and cleanup expiry to support bounded active selection; use the actual source owner predicates/indexes. Avoid a fresh index per UI condition. Unique instance/topic and same-tenant relationships are database constraints, not only conventions.

Deadline arithmetic/state-combination CHECK constraints can compare stored columns; do not pretend a CHECK using current time expires a row automatically. Active selection and commands compare current authoritative server time. Freeze trusted attribution, source and topic after insert. An allowed UPDATE must not transform a row into another tenant/profile/source or extend a deadline without a fresh qualified command.

Deletion of ephemeral technical rows has no cascading business effect. Source/member deletion must invalidate/remove or safely orphan-ineligible these rows according to the actual owning domain contract; prefer same-tenant FK restriction and ordered technical cleanup where physical deletion exists. No cascade from a lease to conversation, profile, CRM record, message, audit or file is permitted. Archived/restricted/merged sources lose eligibility by current policy even if the FK still exists. Cleanup failure can leave only expired unreadable technical state, never live authority.

## Closed commands and SQL security

The browser submits an issued instance, expected sequence/window and a closed intent (`observe`, `input`, `renew`, `stop`, `close`); exact transport names are design detail. It does not submit trusted actor/tenant/source changes, names, roles, deadlines, arbitrary JSON state or session attribution. Initial registration accepts a source locator as an untrusted requested target, then resolves current owner authority before binding it. Caller-controlled source IDs are never authority by themselves.

Use the qualified `packages/api` boundary plus database adapter/transaction; app route files remain thin. In one transaction, authenticate actual identity/session, qualify current source and command permission, compare instance/sequence/window/state, update deadlines and return accepted current control state. Coordinate with source-owner revisions/locks so a racing source mutation cannot admit a control under a source state that was already invalidated at the command's linearization point. Do not assume a frontend permission badge does this.

Clients have no direct SELECT/INSERT/UPDATE/DELETE grants for lease rows and no raw-row Realtime publication. Inspect actual exposed schema grants, policies, views/RPCs, function execute grants and search paths. Prefer invoker semantics where appropriate; a necessary privileged/definer path needs explicit trusted current authorization and bounded operations. Service-role bypass is not caller authorization. Test both old-row admission and new-row validity. PostgreSQL may reuse USING when WITH CHECK is omitted; missing explicit syntax alone is not proof of a vulnerability. No Storage policy is added because D34 stores no files or attachments.

`realtime.messages` policies only authorize the correct authenticated real session's issued active private observer topic and allowed receive extension. Browser Broadcast/Presence publishing and unrelated topic joins are denied. Cached join policy cannot replace the application fanout/snapshot check. A privileged REST publisher uses a qualified server-only credential path that never reaches the client, source or logs.

## Ordered control protocol

1. A visible qualified reader registers: new opaque instance/topic, sequence0, generation0, fixed window expiring15s later, observer deadline30s later, inactive composing state. Registration is not composition and is not performed by SSR/prefetch.
2. The client sends one control at a time with the issued generation, a strictly advancing sequence and current intent. Intervening input is a coalesced dirty flag, not an event queue. A ready first input/stop dispatches in the leading edge; a pending transition flushes after the in-flight control settles, not after another timer interval.
3. The server requires current time strictly before both the window and observer expiry, exact current generation, sequence greater than last accepted, current real session/source rights and supported protocol. Duplicate/lower sequence is a no-effect rejection, not a renewal. Accept atomically updates last sequence, rotates generation and issues its new15s window. Snapshot-only/read-reconciliation does not rotate it.
4. `input` means new human intent since the last accepted/known report. It may start a new composition episode or extend an existing one. It updates the fresh-input frontier to server acceptance time. `renew` extends only a still-active episode's liveness and cannot restart an inactive/expired/stopped episode or change its input frontier. `observe` renews observer interest only. Every accepted eligible control can return the fresh authorized peer snapshot, avoiding redundant refresh.
5. `stop` ends only this instance's current episode; the observer may remain live. A later actual input in a valid window may start a new episode. `close` ends the entire instance. A lower older Start/Renew/Stop cannot affect the newer sequence/episode. Any unknown, closed, expired-window or expired-observer update is rejected; it never upserts.
6. On ambiguous ACK, freeze writes and reconcile through a fresh authorized read of that exact instance. It returns last accepted sequence/generation/window/state but extends nothing. If its current window and episode remain live, a fresh eligible renewal may continue within the unchanged input deadline. Do not replay an old input or claim it became fresh by reading. If the window/instance is dead, close where possible and register a new inactive instance. New human input after recovery is required to announce again.
7. Stop/close remains best effort at page exit. Server expiry removes stale claims even when the browser never sends another packet. Logout/current-source denial never causes re-registration until legitimate current authority exists.

One generation plus one last sequence is enough. No permanent receipt journal, message queue, cryptographic-token service or per-keystroke events are required. A control received close to its not-after time may represent older self-reported activity; the fixed window bounds this but cannot prove what a human was actually doing. An authorized malicious client can claim its own composition. It cannot claim another identity or gain/deny business authority.

## Exact timing and snapshot interpretation

All server duration arithmetic uses trusted elapsed-time semantics and timezone-independent stored instants. Do not use business-hours/D14 calendars. The proposed profile:

| Parameter              | Exact meaning                                                                                                                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Leading dispatch       | Begin a ready start/stop request within150ms of qualifying local transition; this is an implementation target, not the remote visibility claim or a guarantee during an in-flight request/recovery. |
| 5s fast loop           | One combined control/snapshot loop while local composition or a current displayed peer cue exists. Ordinary keepalives, not an extra loop per purpose.                                              |
| 10s quiet loop         | One combined observer/snapshot loop otherwise, only while eligible. Transition/wake reads may occur sooner.                                                                                         |
| 15s control window     | Fixed not-after for each issued generation; later changes do not retroactively freshen an old report. At equality it is expired.                                                                    |
| 15s composing liveness | Upper bound after accepted eligible input/renewal, shortened below.                                                                                                                                 |
| 30s local idle         | Stop after30 elapsed seconds since last qualifying local input; focus/renew/autosave do not reset. Server also enforces its independent input frontier.                                             |
| 30s observer lease     | Upper bound after accepted observer-control activity; read-only reconciliation cannot extend.                                                                                                       |
| 12s snapshot trust     | Maximum local age measured from request start; a response does not get12 fresh seconds upon arrival.                                                                                                |

For an active episode:

`composingUntil = min(serverNow + 15s, lastAcceptedFreshInput + 30s, observerUntil, applicable session/source deadline)`.

Without fresh input, ordinary renewals cannot move the30s frontier. Publisher liveness can disappear earlier than the30s idle grace under network loss. The ideal connected grace is30s; it is not a claim that a lost client's actual last keystroke is known to server precision. A late fresh-input report can add up to the15s control-window age before the server frontier; this is bounded self-report uncertainty, not literal live typing. Under compliant client behavior Stop is leading edge; the worst case remains expiry. A stale valid report never becomes unbounded because of repeated keepalives.

Snapshot returns trusted `asOf`, absolute per-contribution expiry and context/generation. At client request start `m0`, derive `mappedExpiry = m0 + max(0, expiry - asOf)`. This subtracts the entire request transit/processing time conservatively rather than trusting browser wall-clock synchronization. Display a peer only before `min(mappedExpiry, m0+12s)` and only in the matching current context. If a response arrives beyond that bound, discard it. Same-profile aggregation uses the latest still-qualified contribution expiry; it cannot inherit an inaccessible contribution's lifetime.

The snapshot itself becomes unknown after `m0+12s`, including an empty result. Expiring the last peer locally does not prove a fresh empty set; schedule a current read and use unavailable if trust is lost. Response order is fenced by request/context generation. **Control acknowledgements and peer projections have separate gates:** a newer snapshot request may supersede an older combined response's peer projection without discarding its valid accepted control sequence/window. Conversely a valid control ACK cannot overwrite a newer peer projection. Both remain bound to the same current instance/context. Browser clocks may not progress consistently through sleep on every platform: clear on visibility/pageshow/focus/reconnect before reuse and refresh. Never persist these clocks/names in local storage, SSR globals or query dehydration.

## Source changes, fanout and the unavoidable network boundary

The server snapshots and dispatch admission evaluate current producer/observer real session, original source, membership, identity display and relevant topology. Keep candidate selection and authorization bounded, complete and indexed. A CRM reader limited to one original may see only composition actually qualified on that source; a shared continuing component is not a room-wide authorization key. A target change needs fresh binding, preserving the private draft under its owner.

A valid current fanout decision followed by a later revocation may leave a content-free hint in flight. That is not a claim of perfectly atomic database-plus-network revocation. No new dispatch is admitted on an already revoked basis; the hint provides no authority and its snapshot rechecks. Already delivered names may remain until a known invalidation/fresh read or their conservative12s trust expires. This finite disclosure-after-prior-authorized-read is explicit; instantaneous erasure from a disconnected screen is impossible. Never keep names visible indefinitely in an offline cache.

Same-profile tabs/devices use separate issued instances. Aggregate after filtering; hide the viewer's own profile. In a controlled context change, clear old local cues immediately and asynchronously close the old instance. A stopped/expired row cannot be repurposed by source merge, unlink, Undo or physical cleanup. Registration/snapshot denies inaccessible links without saying whether another hidden source/person exists.

## 2. Best practices worth applying

- **Description, not a mandatory "purpose".** Salesforce's design-standards template requires descriptions and classification (S: https://architect.salesforce.com/1/asset/immutable/s/d6327ee/assets/pdf/design-standards-template.pdf). HubSpot documents "how a user should fill in values" (V: https://knowledge.hubspot.com/properties/create-and-edit-properties). _Apply:_ prefill the description with source, header and date, editable. A required purpose field across 40 fields becomes rubber-stamp text.
- **Stable keys.** HubSpot cannot edit "object type or internal name" (V). _Apply:_ use system-generated, immutable keys for fields and options.
- **Type locking.** HubSpot: a type change "can invalidate current values" (V). In Salesforce, an incompatible conversion nulls the data (S: https://developer.salesforce.com/docs/atlas.en-us.244.0.change_data_capture.meta/change_data_capture/cdc_field_conversion_single_event.htm). _Apply:_ drafts are editable until commit; afterwards, create a new field and retire the old one.
- **Sensitivity at creation.** HubSpot: "Once a property is created, its Sensitive Data setting cannot be changed" (V: https://knowledge.hubspot.com/properties/store-sensitive-data). _Apply:_ the tier is set in the draft. Raising it later is allowed; lowering it once values exist is not (U, Q14 check).
- **Calculated fields** are a separate, capped class in HubSpot that cannot hold sensitive data (V). Recompute them; don't import them.
- **Multi-select** values report as one delimited string and cannot be grouped (S: https://www.salesforceben.com/salesforce-multi-select-picklist-limitations/). Offer it only for genuinely multi-valued cells.

## 3. Sensitive identifiers

- **Banned even by permissive CRMs.** HubSpot's Sensitive Data feature still excludes "Government-issued numbers" such as SSNs, "Full card numbers and card security codes" and full bank account numbers (V: https://developers.hubspot.com/sensitive-data).
- **PCI.** "It is not permitted to retain card verification codes", and donor consent "has no validity" (V: https://www.pcisecuritystandards.org/faqs/1280/).
- **No ministry need.** IRS: "It isn't necessary to include either the donor's Social Security number or tax identification number" (V: https://www.irs.gov/pub/irs-pdf/p1771.pdf, Rev. 11-2023). OPC: "no private sector organization" should request the SIN unless required by law (V: https://www.priv.gc.ca/en/privacy-topics/sins-and-drivers-licences/social-insurance-numbers/02_05_d_21/).
- **Breach exposure.** A name plus SSN, licence or account number is notifiable under state laws (S: https://www.ncsl.org/technology-and-communication/security-breach-notification-laws).
- **Custom fields lack native protection.** Raiser's Edge masks and encrypts its built-in SSN and card fields (S: https://webfiles-sc1.blackbaud.com/files/support/downloads/re7/re_781_release_notes.html). Users report card numbers typed into notes (S: https://community.blackbaud.com/discussion/comment/203348/).
- **Detection.** Microsoft Purview flags 14–19 digits that "must pass the Luhn test" and match issuer formats. Pattern plus checksum alone is only _low_ confidence (V: https://learn.microsoft.com/en-us/purview/sit-defn-credit-card-number). Salesforce separates declared classification metadata from Data Detect, which scans "actual field content" and only reports what it finds (V: https://trailhead.salesforce.com/content/learn/modules/data-detect-quick-look/get-to-know-data-detect).
- **Tension resolved.** _Classification_ infers a tier from content, which Asym forbids. A _refusal guard_ is a fixed, deterministic validation, like date parsing, that assigns no tier. A header synonym (SSN, SIN, card, CVV, routing, passport) is a hard stop. A format match (card by Luhn plus issuer prefix, SSN `###-##-####`) blocks the column with a logged "not card numbers" override, because 16-digit donor IDs can pass Luhn by chance (U).

## 4. UX patterns

- **Attio** offers "+ Create new attribute" while mapping. "Create missing select options" is an explicit choice. The preview count of what "will be created" is an estimate. Imports are capped at 100 columns (V: https://attio.com/help/reference/imports-exports/csv-imports/import-data-into-attio-via-csv).
- **Airtable** lets only Owners and Creators add fields or options during import (V: https://support.airtable.com/docs/csv-import-extension).
- **Pipedrive** creates fields from mapping. Its preview is the "last chance", and admins can revert within 48 hours (V: https://support.pipedrive.com/en/article/importing-data-into-pipedrive-with-spreadsheets).

_Apply:_ show one review table with a row per draft: name, type, fit %, fill %, distinct count, tier and samples. The bulk action is "Create selected as text, staff-only". Field creation is gated by the custom-field capability (Q5).

## 5. Field sprawl controls

Salesforce allows 500 custom fields per object on Enterprise, 800 on Unlimited and 100 on Professional (S: https://resources.docs.salesforce.com/208/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf). HubSpot's cap varies by tier (V; numbers U). There is no native "last used" timestamp, so cleanup pairs fill rate with reference checks (S: https://trailhead.salesforce.com/content/learn/modules/data-cleanup-fundamentals/clean-up-unused-fields-and-field-configuration). Legacy fields are cited as a _trigger_ for migrating (S: https://syncmatters.com/blog/why-crm-data-migration-is-still-the-biggest-bottleneck), not shown to be caused by migration (U). The import-driven evidence is option bloat (r2).

## Corrections to Option B

1. **Add a refusal list.** Government IDs, payment credentials, bank account numbers and passwords are refused by header synonym plus the format guard. A refused column still sits in the retained source copy, so Q15 needs redaction or shorter retention for it.
2. **Steer derived values** (giving totals, age, last gift, counts) away like core facts.
3. **Switch-created fields get no default.** Otherwise records created later get "No" while imported ones stay blank, which skews reports.
4. **Atomic commit:** limit check before, every target re-checked, all drafts or none.
5. **Stable IDs** for fields and options. Q11 maps store IDs.
6. **Type locked after commit.**
7. **One source column per target.** No splitting, merging or household fan-out.
8. **Blank handling for every source,** not only SiteStacker.
9. **Bulk "add these N values"** only after grouping is reviewed. Many distinct values suggest text.
10. **Free-text drafts default to the most restrictive tier offered.**

## Simplest robust defaults

1. **Type** defaults to text. Typed fields need a 100% fit after named blank tokens.
2. **Partial dates** go to text and are never padded.
3. **Delimiter** is picked by the person. Commit is blocked if a label contains it.
4. **Draft settings:** staff-only, no default, description prefilled, key generated.
5. **Name clashes** are checked across existing, retired, in-batch and native names.
6. **Refusals:** header synonym is a hard stop; the format guard allows a logged override.
7. **Post-Switch list:** source header, fill %, option count, tier and a "retire" action.

## What not to build

- Dependent picklist, lookup, file, formula or roll-up types created by a Switch.
- Column splitting, merging, or household fan-out.
- Content-based sensitivity classification or tier suggestion.
- Editable keys, type changes after data exists, or option deletion once used.
- Synonym mapping beyond the fixed yes/no list.
- A required per-field owner or purpose form.
- Partial-date or three-state boolean types in v1.

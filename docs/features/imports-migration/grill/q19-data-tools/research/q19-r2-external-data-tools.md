**Summary for Q1.**

- **The most common shape is hybrid:** a start button in context plus a central history in an admin hub. HubSpot, Intercom, Attio and Givebutter work this way. HubSpot also keeps a full import flow in the hub [H1][IC1][AT1][AT2][GB1].
- **Some products are hub-only.** Their hub sits under setup or tools: Zoho, Pipedrive, Zendesk and core Salesforce [ZO1][PD1][ZD1][SF1].
- **Nonprofit CRMs tend toward one named hub,** and that hub often appears in the main navigation. Examples are Bloomerang **Data Tools**, Virtuous **Import Tool** and LGL **Flex Importer**. Gift and constituent imports share the hub [BL1][VI1][LG1].
- **Hubs hold more than import.** Bloomerang's Data Tools holds Imports, Bulk Updates, Bulk Delete and Merge Constituents [BL3].
- **In-context-only with no history is the minority.** Shopify is the example [SH1].

**What a migration workspace looks like, where one exists in-product.**

- **Ordered task guide plus per-step screens.** HubSpot has a User Guide tab with tasks listed in order [H3].
- **Re-runnable audit or preview before writing.** HubSpot can run a new audit. Zoho shows a "pre-migration status". Stripe shows a validation summary [H3][ZO2][ST1].
- **A results table with job-level controls.** These include pause, resume, cancel and error-log download [H3][ST2].
- **A practice environment.** Stripe uses a sandbox. Blackbaud does test runs into a hosted test database [ST2][BB3][BB4].
- **Explicit approval before the real run.** Stripe: "After your explicit approval, Stripe executes the import" [ST1].
- **A short reversal window.** Stripe allows 10 hours. Zoho allows undo from history [ST2][ZO2].
- **Owner per step appears in documentation, not in the product UI.** Stripe's step table is the example [ST1]. Blackbaud uses an issues log handed between customer and conversion analyst [BB3].
- **No product found shows GOV.UK-style task statuses with named owners inside the app (U).**

**Summary for Q2.**

- **The industry separates one-time migration from routine import.** It does so in one of two ways: a vendor-run service (DonorPerfect, Blackbaud, Bloomerang, Neon, Stripe payments) or a dedicated in-product migration flow (HubSpot Smart Transfer, Zoho Data Migration, Stripe Billing toolkit, Shopify app).
- **In-product migration flows sit next to the everyday importer.** HubSpot puts both under Data Integration. Zoho puts both under Data Administration > Import [H3][ZO2].
- **They are usually locked to the top admin role.** HubSpot requires Super Admin. Zoho requires Administrator [H3][ZO2].

## 5. UX guidance

### 5.1 Long, multi-session work: task list and "complete multiple tasks" (VP)

- **Only for long transactions.** "Only use a complete multiple tasks page for longer transactions". Show it "at the start of the transaction and at the start of each returning session". Simplify first: "If you're able to reduce the number of tasks or steps involved, you might not need one" [GV1].
- **Statuses.** Start with "Completed" and "Incomplete". Add "Not yet started" and "In progress" only if research shows users need them. "Cannot start yet" uses grey text and an **unlinked** row. Avoid a "There is a problem" status by showing errors where they occur. Use "short adjectives in sentence case rather than verbs" [GV1].
- **Ordering and grouping.** "Where possible, allow users to complete tasks in any order". Group tasks into steps such as "Check before you start" [GV1].
- **User-declared completion.** For tasks with optional questions or "answers needing someone else's check", ask "Have you completed this section?" and offer "Yes, I've completed this section" or "No, I'll come back later". "Always allow users to go back into a task to change their answer" [GV1].
- **When the component fits.** Use it only with evidence that users cannot finish in one sitting or need to choose their own order. Don't use it for a long service that must be done in a fixed order [GV2].
- **Accessibility.** Keep task names short for screen readers. Hint text is read in full, and links inside hint text won't work [GV2].
- **Check answers per section.** For very large multi-section transactions, it "may help to include a check answers pages at the end of each section", especially where "different users might be completing each section" [GV3].

### 5.2 One thing per page (VP)

- "Start by splitting the form across multiple pages with each page containing just one thing" [GV4].
- **Exception:** "User research will tell you when you can merge pages together". The example is an internal service for government users who repeat and switch between tasks quickly [GV4]. This matters for staff doing everyday imports.

### 5.3 Wizards (VV, NN/g 2017)

- "Use wizards for novice users or infrequent processes (e.g., configuration or setup)" [NN1].
- With repeated use they "can quickly become annoying and overly controlling". "consider offering them another faster alternative" for experts [NN1].
- Show "a list or a diagram of the steps involved and highlighting the current step". "Allow users to exit the wizard midway and save state". Name the target step rather than using generic Next or Previous [NN1].

### 5.4 Placing infrequent admin tasks (VV, nearby NN/g articles; specific guidance **U**)

- **Utility navigation** (2015): secondary tools "can be relegated to a secondary (less prominent) visual placement" only if conventions are followed. Hiding them behind gear icons or drawers "can backfire" [NN2].
- **Progressive disclosure** (2006): put frequently needed items in the initial display. Base the split on "frequency-of-use data". Keep to two levels at most [NN3].
- **Staged disclosure** (wizards) suits tasks with distinct steps and "little interdependence" [NN3].

### 5.5 Background jobs and status (VV, VP)

- **Over 10 seconds:** use a percent-done indicator and "a general time estimate". Label progress steps ("Updating address 3 of 50"). "give users the option to stop the process" [NN4].
- **Cloudscape (AWS):** for operations over 10 seconds, "Allow the user to perform other tasks (such as navigate to other pages) while the operation is in progress". Use flashbars for "errors, success, in-progress, and info" [CS1].
- **Product practice:** completion emails (Salesforce, Zendesk, Givebutter, Shopify) [SF1][ZD1][GB1][SH1]. HubSpot opens a review page with "a timeline of the import's status" [H1].

### 5.6 WCAG 2.2 SC 4.1.3 Status Messages (VP)

- A status message is a "change in content that is not a change of context" that reports "the waiting state of an application, on the progress of a process", or success, results or errors [W3].
- Techniques: `role=status` for results and state, `role=alert` for errors that are important and time-sensitive, `role=log` or a live region for progress updates.
- Listed failures are F103 (status messages not identified through role or properties) and using `role="alert"` or `aria-live="assertive"` on content that is not important and time-sensitive [W3].

### 5.7 Progressive disclosure of row-level errors (VV, VP)

- **HubSpot's layered model:**
  1. Summary card.
  2. Errors table grouped by column and error type, with an impact count.
  3. "View details".
  4. "View rows with errors".
  5. Downloads.

  Sensitive values are redacted at every level [H4].

- **GOV.UK error summary:** link each error to its field, move focus to the summary, and use the heading "There is a problem". It gives no guidance on grouping many errors (U) [GV5].

## Dominant patterns

1. **One named data hub, with shortcuts in context.** Imports, bulk updates, bulk delete and merge live together. Bloomerang's hub is even called "Data Tools" [BL3]. HubSpot and Intercom add an Import button on the record list that leads into the same flow and history [H1][IC1].
2. **Central import history with per-import detail.** Detail pages show counts, the person, the time, error groups, a failing-rows download and the affected records [H2][ZO1][PD1][ZD1].
3. **Migration kept apart from everyday import.** It is either a vendor service or a dedicated admin-only migration flow next to the importer [DP1][H3][ZO2][ST1][ST2].
4. **Migration flows are staged.** They audit or validate, show a summary, wait for explicit approval, run, and allow a short cancel or undo window. Practice runs use a sandbox or test database [H3][ST1][ST2][BB3].
5. **Revert starts from the import record** and is limited to records the import created, within a time window [ZO1][PD1][H2][ST2].
6. **Import permission is import capability plus create or edit on the object.** Admins see all imports. Non-admins see their own (where documented) [H1][SF7][AT2][ZO1].

## Implications for a ministry CRM with a one-time Switch plus everyday imports

Everything in this section is _(inference)_ drawn from the patterns above. None of it is a finding.

1. **Make Data Tools one hub, and add in-context doors.** _(inference)_ Market practice, and the nonprofit CRMs in particular, supports one Data Tools area that holds the Switch, imports, history and reversal preparation. Add in-context entry points that open the same flow and write to the same history: "Import people" from the People list, and "Import gift file" from gift entry [BL3][H1][GB1]. Because the Givebutter-style split (start in context, history in Settings) scatters audit work, keep history in the hub, not in Settings [GB1].
2. **Give the Switch its own workspace inside Data Tools, not a longer import wizard.** _(inference)_ No surveyed vendor treats a multi-week conversion as "a bigger import" [DP1][H3][ST1][BB3]. The GOV.UK task-list pattern fits work that is multi-session, any-order where possible, and checked by others [GV1][GV2]. Use statuses such as "Cannot start yet" for gated steps like sign-off and go-live. Put a check-answers summary at the end of each section, because different people own different sections [GV3]. Show an owner per step, as Stripe does in its docs table [ST1]. No surveyed product shows owners in the UI, so this would be ahead of the market. After go-live, the workspace should become a read-only record rather than disappear.
3. **Keep practice runs and the real run separate, and put approval in between.** _(inference)_ Stripe's sandbox and explicit approval, HubSpot's re-runnable audit and Blackbaud's test runs with an issues log all point to a validate > summary > approve > run sequence. Reconciliation counts belong on the approval screen [ST1][ST2][H3][BB3].
4. **Hand gift files to gift entry, but keep the import record in history.** _(inference)_ Gift imports landing in a batch that the gift area owns is established practice: Virtuous Import Tool batches and the NPSP Data Importer settings shared with Gift Entry [VI4][SF4]. The import history row should link to the resulting batch and show its state. It should not duplicate batch editing.
5. **Review matches before commit, especially for gifts.** _(inference)_ Gift-focused tools review matches before writing (Virtuous Match Needed and Update Needed, NPSP dry run) [VI4][SF4]. Post-commit merges are "permanent" in Bloomerang [BL5]. A ministry CRM should put possible-match review inside the import preview for both People and Gift files, and keep a post-commit duplicates tool for leftovers [BB6].
6. **Split permissions more finely than the market does.** _(inference)_ Most products bundle import with create/edit [H1][BL3]. Only HubSpot separately restricts original files and redacts sensitive values [H2][H4]. With donor PII and gift amounts at stake, consider separate permissions for:
   - running an import;
   - viewing your own history compared with all history (the Zoho and Attio model) [ZO1][AT2];
   - downloading original or error files;
   - preparing a reversal (Pipedrive limits revert to admins) [PD1];
   - running or signing off the Switch (HubSpot requires Super Admin, Zoho requires Administrator) [H3][ZO2].
7. **Make "Prepare reversal" a page off each import record, with its scope stated.** _(inference)_ Revert always starts from the history row or detail page, and products state its limits plainly: "only added records", "cannot reverse the changes by deleting", time windows [ZO1][H2][PD1][ST2]. A preparation page that lists what will and will not be reversed matches that honesty.
8. **Set retention deliberately.** _(inference)_ Market retention is short (7 days to 6 months) [SF6][ZO1][H2]. That is too short for ministry audit of the import record itself. Raw and error files carry PII, though, so set a separate, shorter retention for files than for the import record and its counts.
9. **Treat imports as background jobs with status.** _(inference)_ Let staff leave the page [CS1]. Show percent done and rough time [NN4]. Notify on completion (product norm) [ZD1][GB1]. Announce progress and results with `role=status`, and reserve `role=alert` for failures [W3].
10. **Use faster flows for repeat staff tasks.** _(inference)_ Everyday People and Gift imports are repeated by data staff, so NN/g's warning about wizards for repeat use and GOV.UK's internal-user exception argue for saved mappings or templates (as Bloomerang has) and a compact flow [NN1][GV4][BL1]. The slower one-thing-per-page treatment fits the Switch.

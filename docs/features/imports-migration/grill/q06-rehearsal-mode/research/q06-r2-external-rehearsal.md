**Findings.**

1. **Three patterns:** (i) a separate copy holding production data (Salesforce, Blackbaud, Chargebee, Virtuous partner); (ii) staging inside the live account behind a commit gate (Planning Center); (iii) import, then fix or delete (Bloomerang, Givebutter, LGL).
2. **Test copies hold real donor data.** No vendor page found masks donor data for conversion testing.
3. **Lifetime and access are rarely published.** Only Salesforce publishes refresh limits; nobody publishes disposal. Access is typically customer admins plus vendor conversion staff.
4. **Customers check** counts against source (Blackbaud), the same queries in both systems (Virtuous) and duplicates (NPSP). Gift totals by year and fund appear only in practitioner sources (§6).
5. **The nearest giving platform (Planning Center) stages behind a commit gate:** admin-visible, donor-invisible, no receipts. That is option B's shape, not C's.

**Findings.**

- **A good preview** shows sample rows rendered as records, per-outcome counts (create, update, unchanged, merge, skip), per-row match status, and a downloadable error file with reasons.
- **Every preview is single-file and single-object.** None shows associations, rollups or households. Salesforce and Stripe send users to a sandbox for those.
- **Validation is often sampled** (HubSpot: 1,000 rows), and error files arrive after commit.
- **Undo is narrow:** 48 hours to 30 days, admin-only, sometimes created records only (Zoho). This supports r10 F8.

**When is a full copy acceptable?** PCI 6.5.5, EDPS and ISO 8.33 converge: only when the copy is **treated as production**. That means equal security, minimised scope, need-to-know access, authorised and logged creation, and deletion after testing. Masking is the default alternative (Salesforce, CNIL).

**Unverified inference for Asym:** a ministry validating its own migration processes data **for the migration purpose**, which weakens CNIL's purpose objection. Minimisation, retention and safeguards still apply to C's second copy. Masking would defeat C, because staff must recognise real donors. Asym's policy keeps production data out of Preview (r10 §6.1), so C must run in production infrastructure.

## 5. Measuring cutover duration

- Microsoft: rehearse with "the same data, tools, and people. You should follow the same steps and timing." Exit check: "You finished everything within your time window for the cutover." verified-vendor-doc: https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/prepare-go-live-cutover-strategy
- Microsoft AX mock cutover: "performance and reliability testing of the data upgrade process, to make sure that it meets the business's downtime limit." Every manual step records "How long does it take?" Rollback needs "a tested process". verified-vendor-doc: https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/migration-upgrade/upgrade-cutover-testing
- Utility filing (Liberty/NH PUC): dress-rehearsal task times were "used to finalize the timeline for the actual cutover". secondary (snippet; 403).
- **Can a no-write rehearsal estimate duration?** Only partly. Salesforce: with Private sharing "the system calculates sharing as the records are being added"; triggers and rules "slow inserts to a crawl"; more lookups mean more checks. verified-vendor-doc: https://trailhead.salesforce.com/content/learn/modules/large-data-volumes/load-your-data. A plan cannot see these write-path costs. _Unverified inference:_ B times parse, validate, match and plan on real volume. It cannot time commits (writes, RLS, projections, ledger postings) or interrupted-chunk recovery. Those need C or a non-PII synthetic-volume load test.

## 6. What full test loads catch that previews miss

- Hidden association errors: "The wrong association can coexist with the correct record count and the correct amount." Rehearsals should include "an interrupted import". Also: "A file labeled "backup" is not proof of recoverability." secondary (2026-09-07, commercial author, hypothetical examples): https://hackernoon.com/a-green-import-report-is-not-a-crm-cutover-test
- "You need a real instance of the destination CRM, not a spreadsheet comparison". In the article's example, "association lookups" behaved differently than the dry comparison suggested. "Relationship QA is where migrations break." Skipping cost: "The cutover was postponed for five days". Runtime: "2–3 hours". secondary (Rework, 2026-03-23): https://resources.rework.com/guides/data-migration/shadow-import-testing
- Nonprofit specifics (secondary snippets only): "control totals by year and campaign", per-type counts and a discrepancy register. Duplicate IDs make one donor look like "one lapsed donor and one new donor". Soft credits are called a hidden migration risk. A Blackbaud thread reports appeal-date exceptions in converted recurring gifts: https://community.blackbaud.com/discussion/comment/270248
- NPSP's dry run misses formatting defects (zip codes) that only loaded records reveal (§1).
- **Gap:** no independent study quantifies defects caught by full test loads versus previews. The evidence is vendor guidance and anecdote.

## Common pattern

1. **Platform and billing vendors rehearse in a separate copy** holding real data at full volume, repeated, with timings recorded.
2. **Self-serve donor tools import, then fix or delete**, with narrow undo. Planning Center instead **stages inside the live account** behind a commit gate.
3. **Previews are universal but shallow:** single-file, sampled, blind to cross-object meaning.
4. **Outward-effect safety comes from layered defaults**, not one flag.
5. **Real data in a test copy is tolerated only when treated as production**, minimal, short-lived, logged and deleted.

## Implications for A/B/C

- **A alone falls below observed practice** for multi-file migrations, because previews miss cross-object effects. This confirms r10 §6.2(2).
- **B matches the nearest giving platform** (Planning Center) without a second copy. It covers mapping, matching, cross-file relationships, totals by year and fund, issues and record previews. It cannot show real app screens, real write timings or interrupted-commit recovery.
- **C is what Salesforce, Blackbaud, Microsoft and Chargebee do, but only with conditions:**
  - production-equivalent security (PCI 6.5.5, EDPS, ISO 8.33);
  - creation authorised and logged;
  - need-to-know access, defaulting to admins (Stripe Private);
  - layered outward-effect suppression: mail off or allowlisted (Salesforce System-email-only, HubSpot), no live payment credentials (Stripe, Shopify), integrations disconnected (HubSpot);
  - impossible to promote to live (Shopify);
  - published lifetime and deletion proof. Nobody publishes this; Asym would have to define it.
- **Timing evidence favours real writes** (Microsoft, Salesforce). To measure rather than estimate cutover time, B needs C or a non-PII commit benchmark (_unverified_).
- **Unverified synthesis:** B as default; C a later, gated option for large or complex ministries, only with the controls above; A stays the per-file inner loop inside B.

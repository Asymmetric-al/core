## 2. The shared AI execution foundation ("D10")

- **What it is (ratified).** ADR-0099 (`docs/adr/0099-…md:37-48`): "one minimal shared tenant-owned AI execution foundation for this and later product domains." A closed, code-owned **AI Feature Purpose** binds through one immutable **AI Capability Binding Version** to an exact provider connection, credential revision, "capability-certified provider/model/region, input/output contract, data-use posture, schema/prompt family, and budget/rate envelope." Every call needs a "minimum-data AI Egress Manifest and immutable AI Invocation Evidence." Ruled ownership row: `phase-01-source-of-truth-ownership-matrix.md:66` and prose `:397-401` ("It cannot accept a suggestion for a domain or widen Phase 3/10/12 authority"). Glossary: root `CONTEXT.md:6075-6112`.
- **Where it runs (ratified).** On the tenant's own provider account (BYOK: "Tenant-supplied credentials do not weaken Phase 3/10 classification", ADR-0099:56) through Asym's certified server-side adapter. `phase-21-field-accounts-decision-log.md:3384-3390`: "Provider and model choices are bounded to currently capability-certified adapters. Arbitrary base URLs, free-form model identifiers, browser-side provider requests, tenant-authored system prompts, and silent cross-provider fallback are out." No owner text offers a self-hosted or Asym-run model, or an Asym platform key for tenant data (bounded grep, **new**).
- **Defaults (ratified/published).** "A credential test does not activate a purpose. Every activation is prospective and previews the exact purpose, provider/model, region, data classes, retention/training posture, billing owner, expected limits, budget, and manual fallback" (P21 DL:3387-3390). Admin surface "Settings → AI features" (ADR-0099:65-72). Phase 22 US22-091: "off until an exact Phase 21 BYOK purpose binding is configured" (`phase-22-public-ministry-pages.md:204`). Phase 28 REQ28-M33: the purpose "starts Off" (`phase-28-…/communications.md:949`). Manual path always complete (ADR-0099:58-61).
- **Purposes that exist (ratified, none built).** Receipt extraction and expense-match suggestion (P21 D10); public-profile drafting (P22 D16, ADR-0133); newsletter writing help (P28 D18, ratified 2026-10-16, published REQ28-M33…M40). - **How a new purpose is approved (precedent, ratified).** Founder decision in the consuming phase, then dated owner amendments: D10/ADR-0099 registration and certification; a Phase 10 egress amendment fixing manifest contents and exclusions (D16 example `phase-10-…md:754-776`); Phase 12 separate powers (manage connection, activate binding, view diagnostics, invoke, apply: `phase-12-…md:2751-2760`); Phase 3 purpose projection. ## 3. Field catalog and deterministic mapping: what exists, and how much each Q3 path needs

- **implemented: nothing for column mapping.** `packages/api/src/crm/mapping/{normalize,duplicates,types}.ts` (229 lines) holds identity normalization and duplicate scoring (`normalizeEmail`, `scoreDuplicateCandidate`), not column mapping. Its schema origin `supabase/migrations/20260508000413_crm_identity_mapping.sql` is Twenty-era (`crm_record_links`, DL D9); nothing there may be restored as an integration. No field-catalog code: `git grep` for `custom_field|field_catalog|import_template` over `supabase packages apps` is empty. Phase 11 #650 (`getFieldCatalog`) and #660 (import exposure contract) are open. No parser is installed (DL:677).
- **ratified (unbuilt)** C15 (DL:515): templates "come from the Phase 11 field catalog keyed by stable value keys; … unknown dropdown options rejected by default". Phase 11 D4 (`phase-11-…md:179`): the import template is "generated from `getFieldCatalog`, never hand-maintained". Phase 11 C2 (`:159`) gives every field an "AI/LLM context" egress door; "Any unregistered egress → strictest (`internal`) → omitted".
- **published** #2347 (Ready, D17 reader) B2: "No plan is produced while any nonempty column is unresolved"; the plan binds "parser, catalog and mapping versions". It contains no AI and no alias text.
- **Path 1, import templates (Q3 cl.3-4, DL:91-92; `CONTEXT.md:65-67`).** Column names match by design: an exact key match with nothing to suggest. The remaining work is value validation (IDs, dates, option keys), which is deterministic. AI adds nothing for columns here (inference).
- **Path 2, SiteStacker preset (Q3 cl.2).** Standard columns get a fixed Asym preset built from header captures (Q2 cl.3(iii)); "Columns undocumented" for CRM grids (`q01-r1-sitestacker-inventory.md:181`). But each installation has its own Record Types, Entity Groups → Entities → Fields, and Data Groups (`q01-r1:186-188`). These need per-tenant mapping to Asym custom fields and values. That is F10, still open (DL:640). Header pre-flight against the register is deterministic (Q2 cl.2, 5).
- **Path 3, "mapping columns at upload" (Q3 cl.3: "The ministry maps its own export's columns onto template fields at upload (with remembered mappings)").** This is the only path with real column-mapping work, and the Q3 monitor fires on "Any template-path switch needing developer help" (DL:106). It is where AI help would pay off most (inference).
- **Value transformations.** Dates: ambiguous dates are rejected (Q3 cl.4(a)), and format detection can be deterministic. Option and code values: unknown values are rejected by default (C15). Gift types, funds and designations: money owners decide (C1, DL:501), and O4 resolves the legal issuer "from reviewed mapping evidence". Fund names are treated as possibly restricted free text (Q5 cl.4, DL:192; Phase 10 A4 :98). A headers-only model cannot help with any value mapping, because value mapping needs the cell values (inference).
- **In-Asym heuristics are already allowed.** ADR-0173 item 15 allows deterministic aliases and labelled heuristic/fuzzy suggestions with no egress. So "deterministic-only" can still include fuzzy matching inside Asym, labelled "Suggested — review required" (inference from ratified text).

## 5. Data classes in import files

- Religious belief: "essentially every person record reveals religious belief by mere presence (GDPR Art. 9 special-category data), with member care adding health/counseling/crisis data" (`phase-10-…md:9`). A real export is "classified restricted by default" until narrowed (Q2 cl.5(e), DL:71; Q5 cl.4).
- **Headers can leak.** Q2 says so (DL:68). SiteStacker Record Types, Entity and Field labels, Data Group names and fund labels are written by the ministry, and can name countries, teams or restricted programmes (`q01-r1:186-188`, inference). If the header row is misdetected (the first row is data, or there are several header rows), names and emails get sent as "headers" (inference; D17 asks for the header row "only when needed", `d17:129`). There is no Phase 10 ruling on whether header strings or tenant custom-field labels may be sent to a model (g7 Unverified, still true).
- **Sample values and rows** are cell content from a restricted-by-default file. They are PII where the column is personal, and barred "merely to improve mapping" (`owner-constraints.md:361-362`). The D16 manifest precedent excludes donor data. Enumerated code columns (for example payment-method codes) are not PII, but they are still un-narrowed content until a cleared member narrows them (Q5 cl.4).
- **Phase 29 custody (published, unmerged spec #2429/PR #2430).** #2494 P29-067 (Ready): extraction or suggestion over P29 bytes needs an "approved code-owned purpose/egress/provider policy"; "Restricted/care bytes never enter an unapproved corpus". Headers parsed from a P29-held file are therefore a P29-governed derivative too (inference).

## 6. Q2/Q6 environment and processor constraints

- Real exports need a signed agreement naming "subprocessors (including any AI tool)" and the hosting region, with counsel deciding the special-category basis (Q2 cl.5(a)), plus an Approved environment with a recorded region (cl.6(6)). "Today no environment qualifies" (DL:72); D13 and D24 are still open (DL:543, :557).
- Q2 cl.4 explicitly leaves Asym's own AI tool use on real exports to **F6**. Q11 must answer it or the clause stays open (**new**). Under Q5 cl.4-6, Asym staff see only headers, counts and summaries, never SQL or service-role data, so a "never" answer is consistent with Q5.
- **BYOK vs subprocessor (inference, new).** Under D10 the ministry owns the provider account and pays for it; Asym's adapter sends the data. Counsel must decide whether that provider counts as the ministry's own processor or as an Asym subprocessor in the Q2 agreement. Either way, the public list (`openpolicy.ts:36-62`) has no AI entry today.
- The Practice environment refuses AI (Q6 cl.3), so any mapping help runs only in production practice runs. The Practice copy then reuses "the current mapping version" (Q6 cl.2, DL:229).
- Asym help access allows "mapping" (Q5 cl.5) and forbids granting permissions. A specialist therefore could not turn on an AI purpose. Whether a specialist may _invoke_ one, at the ministry's cost, is not decided.

## What is settled

- AI is never a prerequisite, and the manual or deterministic path must be complete (`roadmap.md:4347`; ADR-0099:58-61).
- D17 self-import: deterministic, no source content (headers included) to external AI (C12).
- Any AI output is a non-authoritative suggestion, labelled and decided by the authorized reviewer, and committed through Phase 30's own plan with fresh authority (ADR-0173 item 15; `CONTEXT.md:6107-6112`; `owner-constraints.md:1376-1384`).
- Any AI runs only on D10: tenant connection, certified adapter, closed purpose, egress manifest, invocation evidence, off until activated, no silent fallback. It never runs on Eve, on a vendor's own keys, or from the browser.
- Restricted, high-risk, care and security content never leaves; imported PII never leaves "merely to improve mapping"; imported text is untrusted input.
- AI is refused in the Practice environment. Asym cannot enable it or grant the permission. No real export reaches any processor before the Q2 agreement names it.
- There is no Phase 40 cycle.

## Gaps and hazards (ranked)

1. **"Headers-only" is not automatically safe.** Q2 calls headers confidential. Ministry labels can name restricted programmes or places. A misdetected header row sends PII. No Phase 10 ruling covers header or label egress. A purpose without a confirmed header row and a Phase 10 amendment would breach C17 in practice.
2. **Q2 cl.4 is open-ended until F6 answers it.** If Q11 decides only the product question, Asym's own AI tool use on real exports stays undefined.
3. **The foundation is unbuilt and likely to be shaped by prose writing.** #2128 (Ready) may build the first D10 slice for newsletter text. A mapping purpose needs closed-list structured output (catalog keys only) and table-shaped input. Unless these are named early, the foundation may not fit them.
4. **Eve is the only working model path**, and it is the wrong vehicle (platform keys, gateway fallbacks). Implementers under schedule pressure could route import mapping through it.
5. **Owner wording is unreconciled** (`owner-constraints.md:360`, "later … Phase 40's"; D15). Choosing B without editing that clause leaves conflicting authority.
6. **The value-mapping gap.** Users struggle most with funds, gift types and codes, which headers-only AI cannot help with. Pressure to add sample values would collide with C17 and the Q5 restricted floor (fund names are restricted).
7. **BYOK and subprocessor status is unclear** for the Q2 agreement and the public policy (`openpolicy.ts:36-62`). Counsel must settle it before any activation.
8. **An alias list may conflict with "No vendor presets"** (Q3 cl.3). A deterministic alias list built from vendor header names needs an explicit statement that aliases are suggestions, not presets or "supported" claims.
9. **There is no authoritative D10 purpose registry** (D18 is not reconciled). A Phase 30 purpose would join a list nobody maintains.
10. **Vendor AI is often on by default.** OneSchema sends headers and samples to OpenAI, Anthropic or Google, with 30-day provider retention and use "to improve the features for all customers". Flatfile learns across customers (`r09:71`, `:80`). Any adopted vendor would need its AI switched off by contract.
11. **Prompt injection through header text** (`roadmap.md:5290`). Output must be validated against the closed catalog key set, with no free-text instructions.

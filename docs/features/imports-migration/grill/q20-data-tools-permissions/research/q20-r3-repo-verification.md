## 0. Findings in brief (decision-relevant)

1. **New.** **Q20's "Sensitive" is not Phase 12's "sensitive".**
   - Q20Q:36 says sensitive means "granted to a named person, never bundled into a general template".
   - That matches Phase 12's `explicit_only` class: "absent from friendly module rungs and seeded templates" (P12:342-359).
   - Phase 12's own `sensitive` flag only keeps a capability out of View and Manage. It may still sit at the Admin rung, inside seeds (P12:1483, :1595, :1599).
   - Phase 12's D38 precedent says an explicit-only atom is "seeded nowhere; Owner, administrator … never imply it" (P12:354-356).
   - So Q20Q:40, "Owners hold every permission", contradicts Q20Q:36 under the `explicit_only` reading. The two readings are set out in §1.1.
2. **Corrected / New.** **"Owner" does not exist before Phase 12.**
   - Owner is a Phase 12 seeded group: "Owner (locked, ≥1)" (P12:1595), built in BUILD-V1 together with the grant product (P12:1844).
   - Code has no Owner. `hasRole(admin)` is true for **every** staff membership (`packages/auth/permissions.ts:64-71`), so "admin" is not a proxy for Owner.
   - Q20Q:50, "Before Phase 12's grant screen exists, only Owners can use Data Tools", therefore has no referent. It could only be built on role names, which DL:1209 and P12:1545 forbid.
   - The only fail-closed interim in ratified text is to leave every import kind switched off (DL:1211-1212).
3. **New.** **"Full access" has no Phase 12 meaning.**
   - No seed holds view-all, "including Owner" (P12:1595), and "No capability equals 'see all fields'" (P12:1599). Clearance is never baked into a seed (P12:1495, :1595).
   - Reviewing a restricted match needs clearance, because dedupe is clearance-gated (P10:122, P12:1622). A region-scoped match needs that region's scope (P12:1595).
   - Because Q20Q:48 uses one wording for staff, deceased and restricted matches, every held row needs a reviewer who holds Prepare **and** can see that candidate.
   - A ministry with no cleared preparer cannot clear even staff or deceased holds.
4. **Verified, with sharpening.** **The restricted-by-default floor is Switch-only in ratified text.**
   - Q2 cl.5(e) and Q5 cl.4 speak only of "a real export" (DL:83, :211).
   - Q11 cl.4 applies to every preview (DL:549-552). Its "before narrowing" sentence names only Switch roles (helpers and Asym help access), but "Fund names are shown only to cleared members" (DL:552) has no condition.
   - Read literally, that blocks an uncleared Gift-file preparer at the Funds step (DL:1104). Q12 is silent (Q12R has no narrowing or clearance text).
5. **New.** **Narrowing is missing from Option B.**
   - ADR-IM-05:21 says "F7 defines the capability map and narrowing step."
   - Q5 cl.1 makes attestations decisions held by "that decision's capability" (DL:198), and declaring that a file names no restricted person is an attestation (DL:211).
   - Q20Q:27-34 has no row for narrowing.
6. **Verified / New.** **Losing a capability mid-operation.**
   - Phase 30 text re-proves the capability per batch or chunk: Q18R:115, :150, :532; Q1R:2132 ("pause visibly as authority_lost"); O26 at DL:1373; Q5 cl.5 at DL:221.
   - Phase 12 itself says:
     - deferred work re-resolves at fire time (P12:1556, :1587; IAC:220);
     - "a long stream re-checks expiry per chunk" (P12:1647);
     - D37 "stops later uncommitted effects" once authority is gone (P12:414-416).
   - **New consequence:** a Just-in-time (JIT) sensitive grant (P12:1483, :1494, :1506) can expire partway through a long import, which then stops as "Needs attention" (DL:1164).
7. **New.** **Held rows decided by a cleared colleague cannot be committed under an uncleared confirmer.**
   - A background job re-proves the confirmer's authority (C16 at DL:1245).
   - `edit(field) ⟹ view(field)` is a resolver invariant (P12:1619).
   - A row matched by a cleared reviewer to a restricted person would therefore fail under an uncleared confirmer. Making it succeed would breach the floor.
   - Such rows need their own commit under the reviewer's authority.
8. **New.** **"Ask {names}" clashes with Phase 12.**
   - Holding a capability is "neither necessary nor sufficient to administer it" (P12:1670).
   - Access requests go only to `permissions.manage_grants` holders or D44 coordinators. The routing "never guesses or broadcasts to the original grantor, Owner, administrator, every grant manager, a role, a group, or the requester" (P12:623-630, :668-674).
   - "Other holders" stay governed (P12:597-599). A Phase 24 review precedent "never … exposes hidden staff" (P24-D14R:678).
   - Naming clearance holders to uncleared staff is a security disclosure in this setting.
9. **New.** **Downloads mean two different things.**
   - An everyday problem-row download returns the uploader's own rows.
   - A Switch Waiting-row download returns part of a raw export containing restricted workers, which "Phase 12 blocks" (DL:828).
   - Leaving hidden-match rows out of a download changes its row count. That shape change is an existence signal (P28R:66, :404, :409).
   - Making every download sensitive removes the ratified "download, fix and upload again" path (DL:1131) for default Importers. It also falls short of the owner bar of "annotated error downloads" (OC:359-360).
10. **New.** **What "See imports" holders would see.**
    - Import names default to file names (DL:1090) and are listed for every holder (Q20Q:46). A file name can carry a restricted worker's legal name.
    - The Imports list shows "rows" and "outcome counts" (DL:1095-1096). For a Gift file, that outcome includes money ("214 gifts, $18,440.00", DL:1137). A holder without `finance:view_contributions` (P13:1952) would see it.

### 4.2 Consequence for Q20Q:48 (New)

- **"Full access" cannot mean a role or Owner.** The only workable definition is per row: a member holding Prepare (and Run the Switch, for Switch decisions) who **can see that candidate**. For a restricted candidate that means clearance or a named grant for that worker (P12:1496). For a scoped candidate it means scope covering that person.
- **Uniformity raises the bar for staff and deceased rows.** Q20Q:48 deliberately gives staff and deceased holds the same wording, so an uncleared preparer cannot tell them apart. To keep that uniformity, **those rows also wait for a reviewer with clearance**, at least when the preparer is uncleared. The alternative is that holds become an oracle.
- **No cleared preparer means stuck rows.** A ministry with no member holding both clearance and Prepare can never clear these holds. The import ends "Needs attention" (DL:1163). Its draft is discarded after 14 days unchanged (DL:1213). Phase 12 seeds never carry clearance (P12:1595), so this is the **default state** of a new tenant.

### 4.3 Residual oracle (New)

The uploader knows their own file. If they know "Jane" is neither staff nor deceased and her row is held, they learn she is restricted or outside their scope.

- P12 R7 requires denied ≡ not found "on every surface" (P12:1650).
- Phase 28 forbids hidden matches altering "result shape" (P28R:66).
- Small-cell suppression (P12:1664) does not help: the uploader names the row.

Phase 28's self-import avoids this by creating private restricted preparation (P28R:68, :73). A staff People import cannot do that without creating a duplicate Party, which P10:97 and Q20Q:48 forbid.

**The residual is unavoidable under "hold".** It can only be diluted by folding more reasons into the same bucket: uncertain matches, shared email (DL:598), NCOA (DL:597). Q20 should state the accepted residual explicitly.

### 4.4 Commit authority for held rows (New)

- Background writes run under the confirmer's re-proved authority (C16, DL:1245; P12:1556).
- `edit ⟹ view` (P12:1619) means a row resolved by a cleared reviewer to a restricted Party **fails** if an uncleared colleague confirms the import.
- Showing the uncleared confirmer a blocked Confirm would itself be an oracle.

**Repository-consistent option:** commit reviewed held rows as a separate step under the reviewer's authority after the main import, with the rows "waiting" until then. That fits Q19's "Needs attention" (DL:1163).

### 5.2 Can a download be "generated on demand, never stored" and still use actor-bound grants? (New, analysis)

**Yes, if generation streams within the authenticated request.**

- Phase 23 and ADR-0037 require reauthorization at download time. A streamed response re-proves capability and scope before the first byte and has no stored object and no URL.
- There is then nothing for an actor-bound grant to bind, and no bearer link exists (DL:1264).

**Caveat: size.** Q15 allows ≤ 20 million rows per Switch (DL:866), and XLSX sheets are capped near 1 million rows (format limit; not repo text).

- A large Waiting-row download cannot be built synchronously.
- Building it in the background means **storing** it, which DL:836 forbids. Any stored artifact would need Phase 29 custody plus an actor-bound grant (O64), and expiry (P23-DL:7946-7948).
- Q20 should either cap on-demand downloads or say that large ones become a stored, actor-bound, short-lived artifact. The second option amends Q15 cl.4.

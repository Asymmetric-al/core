## 0. Bottom line

1. **What we will actually receive: user-shaped CSVs, not database tables.** Every documented SiteStacker export is a grid or report download.
   - The user chooses filters and ticks columns. What a restricted User Group can see limits the rows (inferred).
   - Reports are defined per installation and are often built by WMTEK.
   - No relational, Historic Giving, payment-method or user export is documented. Expect, per ministry:
     - CRM People and Groups CSVs;
     - Contributions Transaction, Campaign, Recurring, Recurring Campaign and Batches CSVs;
     - newsletter list CSVs;
     - Statements and other report CSVs (PDF optional);
     - entity "Export For Import" definition files;
     - possibly BI dataset CSVs if an approved admin exists;
     - a Change Log save.
   - Outside SiteStacker: Mailchimp and processor or PayPal reports. (§2)
2. **New hard evidence from vendor screenshots.**
   - The CRM grid can show an **"ID"** column, plus "Household ID", "Household External ID" and "External ID".
   - The Transaction View shows "Donor … Amount, Payment, Last Four, Exp Date, **Transaction Code**, Status, Date/Time", and has an **"Is Testing"** filter.
   - The Recurring View shows "… Status, Recurrence, Start Date, Next Run, Last Run, End Date, Runs …".
   - The Batches grid shows "Batch ID … Status, Batch Code, Deposit Date".
   - Date display differs between grids, and report views show "$400" and "($8,000)".
   - Encoding, delimiter, CSV date and number formats, time zones and multi-value serialization remain **undocumented**. (§2.1–2.2)
3. **The fake-record step is safe only for CRM data, and only after a Spark check.**
   - Spark has folders for Person Update, CRM Entity Create/Update, Person Type Assignment and Person Relation Assignment.
   - Website sign-ups and "Export to Mailchimp" push to Mailchimp.
   - **Fake gifts are unacceptable** in a live installation. New Contribution automations send messages, add record types and relationships, and can create users. Campaign-goal triggers can cancel real donors' recurring gifts. Gifts flow into Historic Giving, missionary dashboards and year-end sends. Reversals are permanent.
   - No customer data sandbox is documented. "Is Sandbox?" is a code setting.
   - Safe set: about 6 fake people and 1 group, with reserved-domain emails, no record types in real use, no newsletter or Mailchimp, no users, no workflows, no gifts. Delete them afterwards ("gone forever"). (§3a)
4. **Header lines are feasible for every CSV surface.** Statement and CRM print templates are PDF-only; no XLSX-only surface exists. Each header must come with:
   - the editor's encoding and line-ending readout;
   - the SiteStacker version, filter and on-screen count;
   - a screenshot of the column chooser. (§3b)
5. **Questionnaire.** 37 no-personal-data questions in §3c. Most need a SiteStacker administrator. **D1 (Spark tree screenshot) must come before the fake-record step.**
6. **What stays unprovable until the real run:**
   - Contributions↔Historic Giving overlap (R5) and ledger separation (R6);
   - join values and refund linkage (R4);
   - gift linkage after delete or merge (R13);
   - reconciliation (R18);
   - restricted-exporter truncation at volume (R3);
   - every byte-level and number-format fact about **giving and report** files (R17);
   - processor-reference meaning (R10).
     Staged evidence settles R12 and R17 for CRM files only. (§4)
7. **Risks that could change the Q2-A choice, or refine it:**
   - (a) Giving-file formats, the Minimum Switch Kit's riskiest part, stay dark until LATER. The kit's mapping must be driven by the header line and reviewed per installation, never fixed in advance.
   - (b) Reports and dashboard columns differ by installation, and installations update monthly. One ministry's real run proves the method, not a fixed profile.
   - (c) The fake-record step writes into the ministry's production system. It needs the ministry's written consent, a named admin, the Spark check and a dated deletion.
   - (d) A middle path the founder may consider: header-only exports of the ministry's pre-existing "Is Testing" transactions. Their rows are staff personal data, so under the current rule they wait for LATER.

## 1. How SiteStacker works, in plain language

Everything in this section comes from public vendor training articles (most dated Sep 2023 – Sep 2025) and vendor screenshots of WMTEK's own demonstration installations. Every article carries the banner "Make sure these features are added to your Site Stacker installation": what a given ministry has depends on its version and purchased features (r07 §1). Screenshots show vendor example data, not a customer's schema.

**Installation.** Each customer runs one SiteStacker installation: a CakePHP 2.x / MySQL-family web application (g3 §3.4 item 6, snippet-only). WMTEK hosts most installations; some are self-hosted (q01-r1 V60). The customer updates or rolls back its own installation monthly in the **System Manager** component, and can run code **branches** to try features ([151000122013](https://training.sitestacker.com/support/solutions/articles/151000122013), modified 13 Sep 2023; verified-vendor-doc). The System Manager **"Is Sandbox?"** switch is a code-update setting: its screenshot reads "If this is selected more update options will be available instead of just tags", and the article says it "should be turned off for ANY live site" (same article; verified-vendor-doc, screenshot). It does **not** mark test data. Only WMTEK has the source code ([151000183508](https://training.sitestacker.com/support/solutions/articles/151000183508), 4 Apr 2024; verified-vendor-doc).

**Sites and Site Channels.** An installation holds one or more **Sites**. Each Site has its own checkout settings, default sender and payment processor gateways. A new Site is used for siloed content or "an entirely different payment processor". Each Site has **Site Channels** (one per language or offering), and each channel has its own thank-you page, System Messages, domains, templates, content and contributions (q01-r1 V10, V11; verified-vendor-doc). Every gift belongs to a Site and a Site Channel. Batch entry requires Site, Site Channel and Currency (vendor screenshot in [151000115113](https://training.sitestacker.com/support/solutions/articles/151000115113), 6 Oct 2023; verified-vendor-doc).

**CRM people, groups and households.**

- The CRM has **People** and **Groups**. Churches, schools and organizations are Groups (r07 §2.1).
- Each person has an internal numeric **ID**. A vendor screenshot of a CRM record shows "ID: 3578", "Record Types", "Groups", "Created: 2018-08-17 17:04:51", "Modified: …" and "Record Owner" ([151000122135](https://training.sitestacker.com/support/solutions/articles/151000122135), 25 Sep 2023; verified-vendor-doc, screenshot).
- A person may also have an optional staff-assigned **External ID** (q01-r1 V57).
- Email must be unique: "Site Stacker does not allow duplicate emails" (r07 §1.3).
- A **household** is not its own record type. It is a shared household ID and name on each member, plus a head-of-household flag. Statements and some reports group by household (r07 §2.1).
- People can have many emails, phones and addresses, each with one default (q01-r1 V31).
- Records also carry typed **relationships** (Spouse; Parent/Child), **activities**, **notes** and **files**.
- Duplicates are merged by hand. "Merge" and a "Scan Duplicates" button appear in the 2023 CRM grid screenshot ([151000122134](https://training.sitestacker.com/support/solutions/articles/151000122134); verified-vendor-doc, screenshot).
- Deleting a record is permanent: "they will be gone forever!" ([151000122181](https://training.sitestacker.com/support/solutions/articles/151000122181), 7 Sep 2023; verified-vendor-doc).

**Custom data.** Custom fields are organised as **Entity Groups → Entities → Fields**. Fields can hold several entries ("Multi"). There are also Linked Entities and, from 2.47, "Link Set" fields (g3 §3.3, snippet-only). **Data Groups** are typed lookup lists (r07 §2.1). The Import component lists one template per entity, for example "CRM Entity - Child Enrollment - Health Info" (vendor screenshot, [151000122055](https://training.sitestacker.com/support/solutions/articles/151000122055), 19 Sep 2023; verified-vendor-doc).

**Record Types: labels that drive automation.** Record Types are CRM labels used for "sorting or permissions purposes, like Motion 2, web page visibility, or Spark events" ([151000098611](https://training.sitestacker.com/support/solutions/articles/151000098611), 25 Sep 2023; verified-vendor-doc). They also become Mailchimp tags (q01-r1 V46). Many are **set by automation, not staff**. The vendor's Spark screenshot shows "New Contribution" events that "Add Online Donor record type for Donor", "Add Recurring Donor record type", "Add Large Gift record type" and "Add Sponsor record type" ([151000121954](https://training.sitestacker.com/support/solutions/articles/151000121954), 28 Sep 2023; verified-vendor-doc, screenshot).

**Spark (instant automation) and Motion 2 (workflows).**

- Spark runs instant cause-and-effect automation. Its action folders, from the vendor screenshot in [151000121951](https://training.sitestacker.com/support/solutions/articles/151000121951) (18 Sep 2023; verified-vendor-doc, screenshot; the list is cut off after item 25 and items 9–15 are partly hidden), are:
  - New Contribution, New Transaction
  - New Recurring Schedule, Update Recurring Schedule, Failed Contribution
  - New Recurring, Update Recurring, Cancel Recurring, Hold Recurring
  - Recurring Designation Reminder, Recurring Schedule Reminder
  - Add To Cart, Remove…, two "Contribu…" folders, "Historic…"
  - Letter Status Change
  - **Person Update, CRM Entity Create, CRM Entity Update, Person Type Assignment, Person Relation Assignment, Person Assigned To Workflow**
  - Task Complete, **Report Export**, Content Item Move
- Each event has an "Active" checkbox: "You can disable this event, which means none of its outcomes will trigger" (screenshot in 151000115113).
- Outcomes include Send Message, Add or Remove Record Type, Add or Remove Relationship, Construct Entity Field, Update CRM Record, Assign Task, New Process, Create User, Add User to Group, Remove User from Group, and Site Planner content changes (screenshot in 151000121954). Outcomes can also "cancel contributions" (r07 §4.4 item 7).
- Two goal triggers, "Contribution Campaign Goal Reached (Active Recurring Donor)" and "(Campaign)", exist so a ministry can "cancel recurring gifts and notify donors when a campaign goal has been reached" ([151000119746](https://training.sitestacker.com/support/solutions/articles/151000119746), 29 Sep 2023; verified-vendor-doc).
- Motion 2 runs multi-step workflows. Its forms write to the CRM, and it creates relationships automatically (q01-r1 V36, V76).

**Contributions (native giving).**

- A **transaction** is one checkout total. It has one or more **designations**, one per campaign (Transaction View vs Campaign View).
- A **campaign** is a Site Planner content item in a category (missionary, project, child, opportunity). Each campaign has an External ID and an Accounting Code (r07 §2.2).
- The **Recurring View** lists recurring schedules. SiteStacker's own scheduler charges stored processor tokens, while PayPal Standard subscriptions run inside PayPal (q01-r2 §0). Editing a schedule leaves an archived clone behind (q01-r1 V9). **Offline Recurring** works like a pledge.
- **Batches** hold offline gifts, with statuses Entered, Deposited, Receipted and Draft (q01-r1 V15).
- Gifts can carry source codes, soft credits, an "Affiliated Giver", tributes and a fee-cover campaign. Refunds and reversals create new rows (q01-r1 V2, V12; r07).
- The Transaction View filter panel has an **"Is Testing"** filter, so test transactions are flagged. The flag's meaning is not documented in text (vendor screenshot, [151000115177](https://training.sitestacker.com/support/solutions/articles/151000115177), 6 Oct 2023; verified-vendor-doc, screenshot).

**Historic Giving.** Historic Giving is a separate store "where all of the gifts ever given, refunded, etc. live" ([151000115175](https://training.sitestacker.com/support/solutions/articles/151000115175), 20 Mar 2025; verified-vendor-doc). Native Contributions income is copied into it automatically. It also holds gifts imported from an earlier donor system and `ledger` lines (expenses and transfers) for missionary dashboards (q01-r1 K19, K20). The Financial Report in a 2024 vendor screenshot mixes negative "Ministry expenses" rows into the same grid as gifts ([151000198870](https://training.sitestacker.com/support/solutions/articles/151000198870), 26 Sep 2024; verified-vendor-doc, screenshot). That is consistent with K20.

**Newsletters and Mailchimp.**

- The **Newsletters** component has "Subscribed People" and "Newsletter Lists" tabs (vendor screenshot, [151000122072](https://training.sitestacker.com/support/solutions/articles/151000122072), 19 Sep 2023; verified-vendor-doc).
- The Mailchimp integration (2.30.x and later) sends people who sign up on the website straight into the Mailchimp list. Admins push other records with "Export to Mailchimp". After that, a cron of at least 30 minutes keeps SiteStacker → Mailchimp in sync, one way only. Records that were never exported do not sync ([151000121992](https://training.sitestacker.com/support/solutions/articles/151000121992), 11 Nov 2024; [151000122073](https://training.sitestacker.com/support/solutions/articles/151000122073), 25 Sep 2023; verified-vendor-doc).
- Missionaries can connect their own Mailchimp accounts (q01-r1 V47).

**Reports and BI.**

- The Admin Reporting / BI tool builds datasets with MySQL-style joins. Only "approved admins" get it, and WMTEK often builds the reports (q01-r1 V29–V31).
- The **Reports** component shows reports that carry a tag, to the User Groups granted that tag ("Report Tags"). Users "filter it, and export it as needed" (151000198870).
- Standard reports, including **Statements**, are installed on request (q01-r1 V25, V27).
- A newer **Year End Statements** page (Contributions → Year End Statements) bulk-emails statement links. It keeps a per-recipient send log and has a "Testing Mode" and "Send to Myself For Testing" ([151000206184](https://training.sitestacker.com/support/solutions/articles/151000206184), "Thu, 22 Jan", no year; verified-vendor-doc).

**Users and logins.**

- Users are CRM records that have a login. "All Users are CRM records, but not all crm records have to be users" ([151000093882](https://training.sitestacker.com/support/solutions/articles/151000093882), 14 Aug 2023; verified-vendor-doc).
- **User Groups** combine permissions additively and form a hierarchy. "CRM/Entity Permissions" decide which CRM profiles a group can see ([151000122300](https://training.sitestacker.com/support/solutions/articles/151000122300), 3 Mar 2025; verified-vendor-doc).
- Recurring donors generally have donor-dashboard logins (q01-r1 K22).
- Creating a user may email the person unless the admin ticks "verified" (151000093882).

## 3. Are the three "now" steps feasible and safe?

### 3a. Planting clearly fake test records in a live installation

**Is there a sandbox or demo to use instead?**

1. WMTEK recommends testing checkout settings "on a sandbox site before publishing them to a live site" ([151000114254](https://training.sitestacker.com/support/solutions/articles/151000114254), 19 Sep 2023; verified-vendor-doc). So separate sandbox installations exist as a vendor practice.
2. Nothing public says every ministry has one, what data it holds, or what it costs. A sandbox **copied from production would contain real donor data**, which puts it under the "LATER" rules, not "NOW" (inferred).
3. System Manager branches and "Is Sandbox?" govern **code**, not data (§1).
4. WMTEK's own demo installation has test-looking records and emails rewritten with a `.test` suffix. The 2025 Year End Statement send-log screenshot shows such addresses (151000206184; verified screenshot). This suggests WMTEK neutralises email addresses in non-production copies (inferred).
5. There is **no documented customer sandbox for data**. Treat the live installation as the only certain venue. Ask in the questionnaire (Q-A4) whether a separate test installation exists.

**Pollution if the rules are followed.** Fake people with no gifts do not reach Statements, Year End sends, Financial Reports or missionary giving dashboards (inferred: these select by gift). They do appear in:

- All Contacts counts and the census screen counts;
- the Change Log;
- "Scan Duplicates";
- the **Mailing List** and **Household** reports (q01-r1 V27). A ministry that prints mailings from the Mailing List report could post to a fake address.

**Mitigation:** use reserved-domain emails (`…@example.org`, reserved by RFC 2606, undeliverable), unique per person because SiteStacker enforces email uniqueness. Use plainly fake postal addresses. Keep the records for days, not weeks, and delete them on a dated checklist.

**Proposed fake-record set (no gifts; about 6 people and 1 group).** It is designed to exercise serialization, not volume.

- **Household:** a head and a spouse, plus one adult relative with "Parent/Child". The spouse has no email of their own, to show how SiteStacker handles a missing email. Try a second person with the **same** email and record the rejection message, to show uniqueness enforcement.
- **Multi-value data:** two emails, two phones and two addresses on one person, with one marked default.
- **Hard characters:** names with an apostrophe, an accent (é, ñ, ü), a comma ("Smith, Jr."), a leading-zero ZIP ("02134") and an External ID with a leading zero ("007").
- **Custom data:** one value of each entity field type in use (text, text area, date, checkbox, number, Data Group value, multi-entry with two entries, linked entity, Link Set).
- **Organization:** one CRM Group with one fake person related to it.
- **Timestamp-zone probe:** the admin records the wall-clock time and zone when creating one person, then compares it with the exported Created / Modified value.
- **Exports:** CRM People and Groups grids with **every** column ticked, as raw files, plus a screenshot of the column chooser. Export twice with no change in between (reproducibility). Merge two fake duplicates, export again, then delete all fake records.

**Can fake gifts be done safely?** **No, not in a live installation, by any documented method.** Refunds and reversals leave permanent rows; deletion after refund is documented only as fraud cleanup (q01-r1 V14). The New Contribution automations and campaign-goal triggers would already have fired. The only safe gift-shaped evidence now is:

- (i) header lines from the existing grids; and
- (ii) the ministry's own **pre-existing** "Is Testing" transactions, if any. Those rows can carry staff names and card last-four digits, so treat them as personal data. Send header-only, or defer them to LATER unless the founder rules otherwise.

**What migration vendors and consultants ask for first (evidence-based):**

1. **An untouched master export and an editing pause.** Neon One, above.
2. **A test plan and several test-import iterations before the final load.** Bloomerang's migration guide shows "Run test file? → Test import results → Re-Import → Test again". It says "Sometimes most thorough way to analyze the data is to export it first", tells readers to "Write a test plan … Do not wait until after the migration has been attempted to figure out how you will measure success", and to budget for "Multiple rounds of testing and re-loads of updated import files" and an archive of data "that did not migrate" ([Bloomerang guide PDF](https://bloomerang.co/wp-content/uploads/2023/06/The-Ultimate-Guide-to-Nonprofit-Donor-Data-Migration.pdf), uploaded 2023-06; verified-vendor-doc).
3. **Expected record counts, a processor contact and a definitive stop date for recurring transfers, delivered processor-to-processor by SFTP**, "Please do not send this file to us via email". Bloomerang also asks for "at minimum, two weeks' notice" and at least 25 recurring donors ([help.bloomerang.com 13382796](https://help.bloomerang.com/en/articles/13382796-how-do-i-transfer-recurring-donor-data-to-bloomerang-fundraising-from-another-provider); verified-vendor-doc).
4. **Field mapping documents.** Neon One, above. Virtuous publishes vendor-to-vendor mapping guides (DonorPerfect → Virtuous; title and snippet only, page 403).
5. No vendor-published migration **questionnaire** was found for DonorPerfect, Virtuous, Neon or Blackbaud (search 2026-11-01; negative result).

**Lessons that apply to SiteStacker evidence gathering (inferred from the above):**

- (a) Every mature vendor treats **counts plus a test import against a real copy** as the acceptance step. That supports the founder's rule that only the real run meets the representative gate.
- (b) Header lines and fake records match what vendors do in **scoping**, before contract. Real exports come after contract, which also matches Q2-A.
- (c) Asym should produce a **SiteStacker omissions and sentinels sheet** as a kit deliverable, following Bloomerang's example.
- (d) Encoding and line-break behaviour must be **measured**, because SiteStacker, unlike Salesforce, offers no choice.
- (e) Any vendor package (WMTEK, like RE NXT and eTapestry) needs its scope stated in writing, and its delivery window and encryption planned for, before it is relied on.

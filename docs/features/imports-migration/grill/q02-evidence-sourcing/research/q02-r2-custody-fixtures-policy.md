### 1.3 What would have to land before a real export may be accepted (inferred)

For an Asym-held real SiteStacker export under the ratified rules, at minimum: (a) the P29 foundation chain #2434 → #2437 → #2444 (retained-copy/independent-use and hold fences); (b) a staff-migration private-input custody profile equivalent to #2368's acceptance (upload completeness, immutable input, bounded hygiene, temporary-copy handling, current access) — **not yet ticketed**; (c) owner-supplied retention/hold/disposal rules for import sources (F11 open; P29 will not invent them, `founder-brief.txt:289`); (d) temporary-copy and disposal lanes #2457/#2497 if disposal is promised; (e) adapter qualification with "exact environment/protocol evidence" (`proof.md:229`) in a named environment; (f) the Phase 12 authority components; (g) P30's own session/staging records (D11). **The repo does not say whether a real export may be _held_ (not imported) before this, e.g., in a ministry-controlled or contract-governed location outside Asym** — see §9.

### 2.2 Findings

- **"Approved environment" is not defined anywhere in the repo** (grep of `docs`, `openspec`, `AGENTS.md` for "approved environment", "qualified environment", "production data": only the rules above). Phase 29 requires "exact environment/protocol evidence" for a custody adapter (`P29/proof.md:229`) but never names which environment. (repo-published absence; verified by search)
- **D13 is real and unresolved**: the ops guide treats production as holding real donors; the founder ruling, roadmap and ADR-0179 say no users / not in production. Both are dated; neither is reconciled. (repo-published vs repo-ratified)
- **inferred:** none of the four environments is fit for a real export today on the repo's own evidence. Preview and development are test/demo-only by rule. Production, as recorded, lags 58+ migrations, still carries anon `USING (true)` reads on donor tables (per `tenant-read-floor.md:23` and H5), is the default target of a destructive demo-seed script, and has no Phase 29 custody, malware scanning or Phase 10 restricted tier. Local machines are "fully disposable" and outside any custody model.
- **inferred:** Asym is pre-customer; there is no tenant-onboarding procedure in the repo that would make production "approved" for a first ministry. ADR-0179 shows the founder's preferred discipline (re-prove environment identity, census, classify) but for destroying non-production state, not for admitting real data.

### 3.2 Findings on the founder's fixture plan

- **The founder's "synthetic never marks a SiteStacker profile supported" rule is consistent with, and stricter than, repo text.** `roadmap.md:4395` bans "synthetic source success"; `delivery-contract.md:41` says a structural fixture cannot substitute for source behavior; P21 D27 keeps synthetic evidence distinct. The D17 research is _more permissive_ ("reproducible synthetic equivalents tied to the documented schema" can precede "supported"), but it is D17-scoped research, not a ratified rule, and SiteStacker export formats are undocumented (r07 V10, cited in r10-gap-g3 §2), so "tied to the documented schema" cannot be met for exports anyway. (inferred)
- **Fake records exported from a real SiteStacker are not "synthetic" in the r10-gap-g3 sense.** r10-gap-g3 §2 option 3 defines a synthetic corpus as one "built from documented import templates". An export of fake records produced _by the real SiteStacker exporter_ shows real headers, encodings, ID columns and quoting — real exporter behavior over fake content. The decision text labels these "synthetic" ("Fixtures not drawn from a real export are labelled synthetic"); whether a real-exporter/fake-content file is "drawn from a real export" is ambiguous as worded. (inferred; see §9)
- **Committing to the repo.** No repo rule forbids committing fake-record CSVs or header lines, and no rule permits it. But: (a) the repo is public and AGPL-licensed, so committing is publication; (b) the only explicit "no donor records in Git" rule is Web Studio-scoped; (c) a header line is not guaranteed personal-data-free (custom field labels, fund/designation names, a misplaced data row — g7 `:106`, Phase 10 `:30`); (d) a fake record created inside a live SiteStacker installation is exported by a filter over a database holding real donors, so a filter mistake can put real rows in the file (inferred). Vendor IP in SiteStacker column names or file layouts: **the repo records nothing**; this is a legal question and out of scope.
- **Prior labelling vocabulary exists** (synthetic / sandbox / production-shadow, P21 D27; fixture / derived / retained / unresolved, ADR-0179). Nothing in the repo yet defines a label like "real-exporter, fake content". (inferred)

**Implications for LATER real exports (inferred).** A SiteStacker export can carry missionary records, designation/fund names that name workers or countries, addresses and (separately) photos. Until Phase 10's restricted tier and Phase 12's restricted-export hard block exist, the platform cannot hold such rows in the required separate restricted store or enforce alias-on-import. The Q2 decision gates the real export on "agreement + Phase 29 private storage built" but **not on Phase 10/12**; the Phase 10 import clause (`:174`) implies a restricted-worker row cannot be _imported_ without an alias, but nothing says whether a real _file_ containing restricted identities may be _held_ before Phase 10 lands. Phase 29's general storage-object model requires a "Phase 10 classification" on every stored object (`owner-constraints.md:171-175`), which Phase 10 must supply.

**Implications for NOW fake records (inferred).** Fake records should not reuse any real missionary's name, real field location, real photo or a real restricted-country assignment of a real person; a deliberately fake "restricted" record (fictional name, fictional alias) is useful because it shows how SiteStacker exports security-related fields. Fake fund/designation names should not name real workers or countries (secondary-vector rule). The repo's existing fake-identity convention is the reserved `.test` domain and an explicit "Demo" organization name (`supabase/seed.sql:65-68`).

**Additional NOW risk (inferred from Q1 research, not a repo rule).** Creating fake donors and fake gifts inside the ministry's _live_ SiteStacker can trigger that installation's outward surfaces (System Messages, workflows, organization Mailchimp sync, receipts) and can enter the ministry's real income reports — Historic Giving "auto-copies native income" (decision-log §9 SiteStacker row; WMTEK's Data Migration Plan says "make sure that all the System Messages are disabled", `docs/features/imports-migration/grill/research/r00-index.md:674`). The decision does not say how fake gifts are entered, kept out of statements/receipts/Mailchimp, or removed afterwards.

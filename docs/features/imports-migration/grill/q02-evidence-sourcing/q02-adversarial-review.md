## 1. Disposition

**Accept with required amendments.** Staging evidence is the right answer and stricter than the repo's existing rules (`roadmap.md:4395` "no synthetic source success"; `delivery-contract.md:41`). It matches how nonprofit CRM vendors work — scoping before contract, data copy after — and avoids holding a ministry's donor file in an ungoverned place. It cannot be recorded as worded because: (1) "approved environment" and "built" are undefined while hosted projects are recorded as still carrying anonymous `public read` policies on donor tables; (2) the two-way synthetic/real label misclassifies SiteStacker-produced exports of fake rows; (3) the gates are circular with Q1 (a switch needs a supported profile; a profile is supported only by a real run); (4) nothing governs where NOW material lives, though grill folders are committed to a public AGPL repository; (5) the fake-record step can fire a ministry's live automations; (6) the LATER gate omits tenant onboarding, the staff-migration custody profile, Phase 10 restricted handling and the retained-state census.

## 3. What will actually come from SiteStacker (plain summary of r1)

SiteStacker produces **spreadsheet-style CSV downloads from its screens and reports, not database tables.** The administrator filters a list, ticks columns and clicks "Export as CSV"; their User Group's visibility rules decide which records they see, so a restricted exporter likely gets fewer rows without warning (inferred). Expected files per ministry: CRM People and Groups lists; Contributions transaction, designation, recurring and offline-batch lists; newsletter subscriber lists; the Statements report and other reports (CSV or PDF); custom-field definition files ("Export to Import"); possibly Reports/BI datasets if an approved admin exists; a saved Change Log; plus Mailchimp exports and processor/PayPal reports from outside SiteStacker. **Not documented anywhere:** an export of Historic Giving, saved payment methods, logins, or a full relational database. On-screen labels seen in vendor screenshots include CRM "ID", "Household ID", "Household External ID", "External ID", and transaction "Donor, Affiliated Giver, Recurring, Type, Amount, Payment, Last Four, Exp Date, Transaction Code, Status, Date/Time" (whether CSV headers match is inferred). Encoding, delimiter, CSV date/number formats, time zones and multi-value serialization are documented nowhere; report screens show amounts like "($8,000)", which could lose cents and signs if copied into CSV. No customer data sandbox exists ("Is Sandbox?" governs code updates only). The staged NOW evidence settles only file format and multi-value serialization, and only for CRM files; everything about giving files, Historic Giving overlap, join columns, deleted/merged donors and full-volume truncation waits for the real run.

**Comparable systems (r1 §6, r08):** Bloomerang publishes its export's omissions and sentinel values (Asym should write the same sheet for SiteStacker); Salesforce's Data Export Service is a weekly/monthly ZIP of CSVs; Raiser's Edge NXT backups are "database view information only"; eTapestry sells a Final Data Export; migration vendors ask for an untouched master export, an editing pause, a written test plan and several test imports. No vendor-published migration questionnaire was found.

## 5. Corrected decision (to record after founder confirmation)

**Q2 — How Asym gets SiteStacker evidence, and when real donor data may enter Asym.** Staged evidence (Option A), amended.

1. **Evidence classes.** Every artifact is exactly one of: (a) _synthetic_ — authored by Asym; (b) _vendor-format sample_ — produced by a real SiteStacker installation or by WMTEK but containing no real person or gift data (fake-record exports, zero-row or header-only exports, pasted header lines, vendor samples); (c) _representative real export_ — a ministry's real data exported under the LATER gate. Only (c) can qualify a profile; (a) and (b) inform design and fixtures but never "supported" or the release gate (`roadmap.md:4395`, `:4403`).
2. **Profile status: unavailable → pilot-qualified → supported.** _Unavailable_ until class (c) evidence runs. _Pilot-qualified_ when the first design-partner ministry's real export passes Q1 practice runs (manifest checks, plan, two-level reconciliation) in qualified custody; this permits scheduling that ministry's switch under the Q1 gates. _Supported_ when the pilot switch has gone live with reconciliation signed off and recovery exercised, which meets `roadmap.md:4403`. Supported status is scoped to the export surfaces, SiteStacker version range and exporter permission level actually exercised; every later installation still runs header pre-flight and its own practice runs. The first ministry is a named design partner on pilot terms.
3. **NOW — no real donor data.** With a willing ministry, after Asym names a relationship owner and an evidence custodian, the ministry names its admin, and the ministry consents in writing having been told the effort and risks:
   - (i) **Discovery declaration** in two tiers: a short tier answered in one guided 60–90 minute session, and a detailed admin worksheet allowing "I don't know". It covers version and hosting; Sites and channels; modules in use; processors per Site and currency; recurring executors and PayPal; Historic Giving use; how statements are produced; record types and custom fields; visibility restrictions; Spark, Mailchimp and integrations; and local volume figures (row counts, file sizes, export durations and errors measured by the admin on their own machine — no rows leave the ministry). It never asks for or accepts credentials, card, bank or account numbers, or donor data. It is not the Q1 readiness census, which is taken fresh before the first practice run.
   - (ii) **Fake-record exports** only after the ministry admin reviews the installation's Spark configuration — including Person Update, CRM Entity Create/Update, Person Type Assignment, Person Relation Assignment and Report Export events — and confirms in writing that creating and exporting the test records fires nothing. CRM only: about six marked fake people and one organization covering a household, several emails and addresses, a non-Latin script, a 4-byte character, embedded quotes and line breaks, long values and every custom-field type; undeliverable `example.org` emails; no real worker names, locations or photos; no gifts or transactions; no logins; no newsletter lists or Mailchimp; no record types or workflows used by automations. Each export is filtered to the marked records and its row count must equal the planted count; each is exported twice; creation time is noted for time-zone evidence; the records are deleted by a recorded date. A marked record later found in a real export is a visible exclusion.
   - (iii) **Header capture** for every kit export surface (CRM; Contributions transaction, designation, recurring and batch; newsletter; Statements and reports; entity definitions; the Mailchimp export): preferably a zero-row or marked-row export file, otherwise the header line copied from a text editor with its encoding and line-ending readout. Each records the SiteStacker version, filter, exporter permission group and on-screen count. Headers are confidential because labels can name workers, places or programmes.
   - The ministry's existing "Is Testing" transactions are real records and wait for LATER.
4. **Custody of NOW material.** All NOW material is ministry-confidential. It lives in a private, access-controlled store named by the evidence custodian — never in the public repository or GitHub issues — and the ministry is referred to by a pseudonym in anything committed. The custodian screens each received file in a text editor before any other person or tool sees it; an unmarked real row means quarantine, deletion of every copy, notice to the ministry and an incident entry. AI tools may process NOW material only after screening shows no personal data, and never real exports until F6 and the agreement name the processor. Screen-share sessions show no person data and are not recorded or transcribed. Committed fixtures are Asym-authored synthetic files derived from reviewed evidence with generic labels, each citing an evidence-register id; no received file is ever committed. A private evidence register records for each artifact: id, class, installation pseudonym, SiteStacker version, surface, filter, exporter group, on-screen count, encoding readout, collector, date, screening result, state (received → screened → accepted or quarantined → superseded → disposed) and disposal date. Material is disposed when superseded by real-run evidence or when the engagement ends.
5. **LATER — real donor exports** only when all hold: (a) a signed agreement with data-processing terms, reviewed by counsel and signed by named people, covering at least roles, purpose, export scope, subprocessors (including any AI tool), hosting region, access, retention including backups, deletion and breach notice, with counsel deciding the special-category basis; (b) the ministry onboarded as its own Asym Tenant with the Q1 single-installation checks done; (c) an approved environment (clause 6); (d) a Phase 29 custody profile for staff-migration source files qualified in that environment — a new profile the Phase 30 spec defines with the Phase 29 owner, since #2368 covers only the missionary self-import; (e) the whole file classified restricted by default under Phase 10/12 until proven otherwise; (f) the retained-state census (D13) complete; (g) a fresh Q1 readiness census. The export set follows the kit's export checklist (only families the kit needs; others recorded as exclusions). The first real export enters only as a Q1 practice-run input; at intake its headers, encoding and version are compared with the register, and any difference re-opens the related findings.
6. **Approved environment.** An environment is approved for real personal data only when a named approver who did not build it confirms by live read-back that: (1) applied migrations match the release under test; (2) no anonymous or unscoped (`USING (true)`) read policy exists on any table holding person or money data; (3) the Phase 29 staff-migration custody profile is qualified there; (4) no destructive script (for example `scripts/seed-demo.sh`) defaults to it; (5) its real-data status is recorded (D13 resolved); (6) its hosting region is recorded for the agreement. Today no environment qualifies. Non-production environments never hold real exports (ADR-0153 precedent).
7. **WMTEK.** Asked only generic questions unless the ministry consents to being named. Anything WMTEK supplies is class (b), or class (c) if it contains real data, in which case clause 5 applies in full. Asym never depends on WMTEK for the kit; surfaces only WMTEK can produce are handled under F3 as a separate source or an accepted exclusion.
8. **No willing ministry.** If none consents by the checkpoint the founder sets, the profile stays unavailable (never "beta"), source-agnostic kit work continues on class (a) and (b) evidence, and the founder re-decides.
9. **Roles.** Named before each stage: NOW — relationship owner, evidence custodian, ministry admin; LATER — environment approver (not the builder), legal owner and signatories.

## 7. Adversarial check

**What could go wrong?** A ministry's live automations fire from fake records or report exports; a "fake" export carries real rows; ministry files land in the public repo or an AI tool; real data is accepted into an environment that still allows anonymous reads; the first customer becomes an unplanned pilot; no ministry agrees and the kit stalls.

**Hidden assumptions.** That a willing ministry exists; that it has an admin with full visibility; that its Spark self-review is accurate; that header labels equal CSV headers; that a zero-row export emits a header (unverified); that production's state can be verified and fixed before real data.

**Whole product.** Touches Phase 29 (a new staff-migration custody profile), Phase 10/12 (restricted handling), D13 (environment truth and the public-read hazard, which affects every surface, not just imports), tenant onboarding, and the Q1 switch gates.

**End-user experience.** The ministry admin gets a guided session, a worksheet and a short, safe checklist instead of a data dump; donors are never exposed before an agreement and governed storage exist.

**Modern best practice.** Matches vendor practice (scope first, data under contract, test imports) and privacy-by-design (minimization, confidentiality, no ungoverned copies). No conflict with a governing repo rule; the repo's rules are applied strictly.

**Repo fit.** Consistent with C11, C17, C23, `roadmap.md:4395`/`:4403`, ADR-0153 and the Phase 29 spec; adds D24/D25 and O19/O20.

**Adjust.** Record with the amendments above after founder confirmation; raise the hosted public-read hazard immediately.

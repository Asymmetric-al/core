Applies to the first release that offers a SiteStacker switch. Evidence: `q01-switch-model/` (research r1–r6, reviews v1–v6, `q01-adversarial-review.md`). Disposition after review: accept with required amendments; the founder ratified the amended text below with all six recommended choices (★). ADR: `docs/features/imports-migration/docs/adr/0001-one-planned-switch-with-external-legacy-recurring-tail.md`. Terms: `docs/features/imports-migration/CONTEXT.md`.

**Decision.** Option A: one planned **SiteStacker Switch** per ministry. Option B (area by area) and Option C (side by side with refresh imports) are not offered; any partial or side-by-side arrangement needs a new founder decision and owner amendments.

1. **Scope and eligibility.** One Asym tenant is fed by exactly one SiteStacker installation; installations or merchant accounts shared with another organization are outside v1. ★ Each legacy merchant account maps to exactly one Legal Entity through a reviewer-accepted assertion, never inferred from Site. A switch can be scheduled only when: (a) every **Minimum Switch Kit** family — Parties and households; contact points with consent and suppression evidence; one-time giving history including reversals; recurring evidence for the Phase 16 classifier — is committable through its owner's typed import command; (b) every other family is committable or a ministry-accepted visible exclusion marked "history not yet covered", importable later only from the retained final manifest under the same Switch Boundary, with SiteStacker never remaining its writer; (c) every legacy recurring cohort has a Phase 16 external/read-only target; (d) the readiness census is complete; (e) ★ a SiteStacker module that will keep writing to migrated people (for example child sponsorship) is allowed only as a declared residual system with no sync either way, a stated count of overlapping people and the ministry's written acceptance. No exception lets a switch proceed with a kit family missing.
2. **Authority.** From the Switch Boundary, Asym is the system of record and the only writer for supporter identity, contact data, consent and suppression, relationships, custom data, imported giving history and all staff work. Legacy executors (SiteStacker's scheduler, PayPal subscriptions, gateway-native schedules) stay externally controlled/read-only under Phase 16 until each formal cutover or recorded end. The original processor stays authoritative for settlement, refunds, disputes and returns on charges it executed. **Switch live** = supporter authority has moved; **Switch closed** = every legacy executor proved stopped, formally cut over or ended, and the Legacy Recurring Tail closed. Until closure the ministry keeps SiteStacker licensed with its recurring engine and recurring donor messages running.
3. **Steps.** Readiness census (before the first practice run and again at final export) → practice runs writing only Phase 29 custody and Phase 30 session/plan/staging/run records, with no target-owner write and no outward effect → go/no-go with a declared maximum editing-pause length (default on a missed deadline: abort before commit and resume SiteStacker) → the recorded Switch Boundary (exact UTC instant shown in the tenant giving zone, default the first moment of a civil date; governs Phase 30 classification only and never sets a Phase 16, Phase 20 or Phase 21 boundary) → editing pause and legacy surface states set by the ministry → one final Source Snapshot Manifest (may be several files) taken after the boundary → import through owner commands with no outward effect → reconcile → go-live → Legacy Recurring Tail with Legacy Tail Backfills → tail closure and decommission checklist.
4. **Giving continuity.** ★ A short, declared online-giving pause whose length is measured in rehearsal. Parties, contacts and suppression evidence commit and reconcile first; Asym giving and exact redirects then open; remaining families commit with no outward effect before the switch is declared live. Asym checkout opens only after a verified Phase 13 Settlement Account Binding exists; anyone who gives in Asym before the final import completes is resolved in match review with no automatic merge.
5. **Exact repeat import** (a founder narrowing of `roadmap.md:4387`, `:4401`). Replaying the same sealed manifest under the same mapping does nothing and recognizes prior work. Any other snapshot converges on stored Source Record Bindings and never creates a second identity (`roadmap.md:4363`); identity never rests on a file digest or manifest. In v1 differences are shown as source-changed conflicts for reviewed correction, never applied source-wins. A row missing from a later snapshot is reported, never treated as a deletion.
6. **Legacy Tail Backfill** (replaces "gifts-only catch-up"). Facts recorded after the boundary by a legacy executor enter only through a bounded series of separately reviewed backfills on a fixed cadence until the tail closure date recorded at go/no-go — ★ by default no later than 12 months after go-live (an assumption to recalibrate after the first switch). Each backfill carries append-only money facts (settled charges; refunds, returns, chargebacks and dispute outcomes linked to the imported original by an exact scoped reference), schedule-state and stop evidence for Phase 16, and ★ adverse contact facts (unsubscribe, do-not-contact, deceased, erasure) applied only to restrict. It never creates or updates supporter details and never overrides an Asym edit; a fact with no exact binding match waits in match review. Each executor and period has exactly one authoritative gift source (SiteStacker exports for gifts SiteStacker runs; the ministry's own PayPal or processor reports for executors SiteStacker does not record). Every fact keeps its import origin; SiteStacker's receipt is carried as evidence; no Asym receipt, thank-you, welcome or first-support work follows unless F5 and Phase 7 later allow it. ★ At closure each legacy arrangement is handed over through Phase 16, ended by the ministry with donor notice and a restart invitation, or reclassified by Phase 16 as an ongoing external arrangement whose later facts enter only through a Phase 13/15 owner intake; any extension is a recorded ministry decision with a reason. Phase 30 runs no backfill after closure.
7. **Legacy Surface Dispositions** (replaces the three-item "off" attestation). Before any Asym sending or automation activates, the ministry records one state per surface per Site, Site Channel or list: Off at boundary; Kept on through tail (owner and end condition); Not used; Outside the ministry's control. Off: giving forms and checkout; giving links, QR codes and text-to-give targets; appeal and record-changing automations; organization Mailchimp sync; SiteStacker imports and rollbacks; staff CRM editing. Kept on until each cohort is handed over or ended: the recurring engine; receipts for legacy charges; recurring confirmation and reminder messages; the declined-payment message and update link; the donor cancel and update path. Outside control: missionary-owned Mailchimp lists, gateway-sent emails, PayPal notices. Exactly one system is responsible for each donor-facing duty per cohort, and SiteStacker alone receipts what it charges. States display as "ministry attested", are re-confirmed at every backfill, and an overlap-and-gap check runs each cycle; Asym never claims SiteStacker was frozen or switched off and states "No known overlap in the inspected scope" with the inspected scope recorded.
8. **Recurring gifts and processors.** No recurring gift moves on switch day. Moving one is a Phase 16 formal cutover: proof the old executor stopped plus applicable fresh IDs and collection authorization; without that proof the arrangement stays external/read-only and nothing runs active-active (P16 `:1314`). This applies to ministries that already used Stripe. ★ v1 accepts the current Phase 16 rule (a donor-completed step; lightest form one hosted confirmation of an already-copied payment method) and measures handover attrition at the first switch before any amendment is considered. Vault copy (Stripe self-serve copy or processor-to-Stripe import) is the preferred path where available; otherwise donors re-enter details. PayPal Standard subscriptions stay external until each donor restarts in Asym; their tail gifts come only from the ministry's PayPal reports; each is cancelled only after the replacement is active and the old one proved stopped. Phase 30 never coordinates processors, transfers vaults, handles card numbers, bank numbers or credentials, runs re-authorization or proves an executor stopped; those stay with the Phase 13/16 migration workstream until owners are named (O12). Legacy provider identifiers are inert source evidence only.
9. **Reconciliation.** Counts and native-currency totals by Legal Entity × original currency × source basis (`roadmap.md:4369`) at two levels: (1) every final-manifest row has exactly one disposition and accepted totals tie to export totals; (2) export totals tie to independent controls — on-screen counts captured at export, the Statements report, processor reports for periods the ministry can supply — with unavailable periods declared, never assumed. Exactly one source basis per gift population and period with an overlap proof (Historic Giving copies native income; ledger lines are never gifts). Unexplained variance blocks sign-off; sign-off binds to a report version.
10. **Reversal.** Abort only before go-live: plans discarded, committed rows stay invisible and are never deleted, and a later attempt converges. After go-live, system-of-record authority never returns to SiteStacker without a new founder decision. Batch reversal follows `roadmap.md:4371` and `owner-constraints.md:378-385` unchanged. Every switch and every run can be halted.
11. **Keeping Option B possible.** Records carry Switch, manifest, run and Source Record Binding identity plus one boundary per source family (all equal in v1). Nothing else is built for B.
12. **Privacy during the tail.** Opt-outs, do-not-contact and erasure requests recorded in Asym after the boundary are listed "pending in legacy systems" until a named ministry user marks each executed in SiteStacker, each legacy processor and each connected missionary mailing account. Backfills never restore contact, consent or identity data for an erased or suppressed Party. A ministry-attested decommission checklist covers SiteStacker access reduction, credential rotation and the SiteStacker data deletion or retention decision. Tail closure and decommission sign-off are blocked while any item is open.
13. **Research status.** The bring-over inventory and processor analysis (`q01-r1`–`r4`) are complete to the limit of public evidence (2026-11-01) and provisional until a representative real export is observed.

**What this does not imply.** It does not choose the source of real exports (F2), money scope in the first release (F13), rehearsal mode (F4), retention (F11), who operates a switch (F18), whether tail gifts earn Asym acknowledgments (F5), or any Phase 13/16/7/19 owner rule; owner requirements O12–O18 are requests, not decisions. It authorizes no spec, ticket or implementation.

**Decision.** Staged evidence (Option A), amended:

1. **Evidence classes.** Every artifact is exactly one of: (a) _synthetic_ — authored by Asym; (b) _vendor-format sample_ — produced by a real SiteStacker installation or by WMTEK but containing no real person or gift data (fake-record exports, zero-row or header-only exports, pasted header lines, vendor samples); (c) _representative real export_ — a ministry's real data exported under the LATER gate. Only (c) can qualify a profile; (a) and (b) inform design and fixtures but never "supported" or the release gate (`roadmap.md:4395`, `:4403`).
2. **Profile status: unavailable → pilot-qualified → supported.** _Unavailable_ until class (c) evidence runs. _Pilot-qualified_ when the first design-partner ministry's real export passes Q1 practice runs (manifest checks, plan, two-level reconciliation) in qualified custody; this permits scheduling that ministry's switch under the Q1 gates. _Supported_ when the pilot switch has gone live with reconciliation signed off and recovery exercised, which meets `roadmap.md:4403`. Supported status is scoped to the export surfaces, SiteStacker version range and exporter permission level actually exercised; every later installation still runs header pre-flight and its own practice runs. The first ministry is a named design partner on pilot terms.
3. **NOW — no real donor data.** With a willing ministry, after Asym names a relationship owner and an evidence custodian, the ministry names its admin, and the ministry consents in writing having been told the effort and risks:
   - (i) **Discovery declaration** in two tiers: a short tier answered in one guided 60–90 minute session, and a detailed admin worksheet allowing "I don't know". It covers version and hosting; Sites and channels; modules in use; processors per Site and currency; recurring executors and PayPal; Historic Giving use; how statements are produced; record types and custom fields; visibility restrictions; Spark, Mailchimp and integrations; and local volume figures (row counts, file sizes, export durations and errors measured by the admin on their own machine — no rows leave the ministry). It never asks for or accepts credentials, card, bank or account numbers, or donor data. It is not the Q1 readiness census, which is taken fresh before the first practice run.
   - (ii) **Fake-record exports** only after the ministry admin reviews the installation's Spark configuration — including Person Update, CRM Entity Create/Update, Person Type Assignment, Person Relation Assignment and Report Export events — and confirms in writing that creating and exporting the test records fires nothing. CRM only: about six marked fake people and one organization covering a household, several emails and addresses, a non-Latin script, a 4-byte character, embedded quotes and line breaks, long values and every custom-field type; undeliverable `example.org` emails; no real worker names, locations or photos; no gifts or transactions; no logins; no newsletter lists or Mailchimp; no record types or workflows used by automations. Each export is filtered to the marked records and its row count must equal the planted count; each is exported twice; creation time is noted for time-zone evidence; the records are deleted by a recorded date. A marked record later found in a real export is a visible exclusion.
   - (iii) **Header capture** for every kit export surface (CRM; Contributions transaction, designation, recurring and batch; newsletter; Statements and reports; entity definitions; the Mailchimp export): preferably a zero-row or marked-row export file, otherwise the header line copied from a text editor with its encoding and line-ending readout. Each records the SiteStacker version, filter, exporter permission group and on-screen count. Headers are confidential because labels can name workers, places or programmes.
   - The ministry's existing "Is Testing" transactions are real records and wait for LATER.
4. **Custody of NOW material.** All NOW material is ministry-confidential. It lives in a private, access-controlled store named by the evidence custodian — never in the public repository or GitHub issues — and the ministry is referred to by a pseudonym in anything committed. The custodian screens each received file in a text editor before any other person or tool sees it; an unmarked real row means quarantine, deletion of every copy, notice to the ministry and an incident entry. AI tools may process NOW material only after screening shows no personal data, and never real exports until F6 and the agreement name the processor. Screen-share sessions show no person data and are not recorded or transcribed. Committed fixtures are Asym-authored synthetic files derived from reviewed evidence with generic labels, each citing an evidence-register id; no received file is ever committed. A private evidence register records for each artifact: id, class, installation pseudonym, SiteStacker version, surface, filter, exporter group, on-screen count, encoding readout, collector, date, screening result, state (received → screened → accepted or quarantined → superseded → disposed) and disposal date. Material is disposed when superseded by real-run evidence or when the engagement ends.
5. **LATER — real donor exports** only when all hold: (a) a signed agreement with data-processing terms, reviewed by counsel and signed by named people, covering at least roles, purpose, export scope, subprocessors (including any AI tool), hosting region, access, retention including backups, deletion and breach notice, with counsel deciding the special-category basis; (b) the ministry onboarded as its own Asym Tenant with the Q1 single-installation checks done; (c) an approved environment (clause 6); (d) a Phase 29 custody profile for staff-migration source files qualified in that environment — a new profile the Phase 30 spec defines with the Phase 29 owner, since #2368 covers only the missionary self-import; (e) the whole file classified restricted by default under Phase 10/12 until proven otherwise; (f) the retained-state census (D13) complete; (g) a fresh Q1 readiness census. The export set follows the kit's export checklist (only families the kit needs; others recorded as exclusions). The first real export enters only as a Q1 practice-run input; at intake its headers, encoding and version are compared with the register, and any difference re-opens the related findings.
6. **Approved environment.** An environment is approved for real personal data only when a named approver who did not build it confirms by live read-back that: (1) applied migrations match the release under test; (2) no anonymous or unscoped (`USING (true)`) read policy exists on any table holding person or money data; (3) the Phase 29 staff-migration custody profile is qualified there; (4) no destructive script (for example `scripts/seed-demo.sh`) defaults to it; (5) its real-data status is recorded (D13 resolved); (6) its hosting region is recorded for the agreement. Today no environment qualifies. Non-production environments never hold real exports (ADR-0153 precedent).
7. **WMTEK.** Asked only generic questions unless the ministry consents to being named. Anything WMTEK supplies is class (b), or class (c) if it contains real data, in which case clause 5 applies in full. Asym never depends on WMTEK for the kit; surfaces only WMTEK can produce are handled under F3 as a separate source or an accepted exclusion.
8. **No willing ministry.** If none consents by the checkpoint the founder sets, the profile stays unavailable (never "beta"), source-agnostic kit work continues on class (a) and (b) evidence, and the founder re-decides.
9. **Roles.** Named before each stage: NOW — relationship owner, evidence custodian, ministry admin; LATER — environment approver (not the builder), legal owner and signatories.

   - the reviewer's pick.

   - imports without that email;
   - is shown as "shares a mailbox with {name}";
   - is asked for their own address when they next give or sign in;
   - ★ has the shared address kept as evidence, added as their contact email once Phase 4/9 allow two people to share one (O48).

   - A block on a shared mailbox applies to whoever holds it.

   - ★ Household members recorded as children import as people like anyone else, and Phase 30 adds no age rule. Restricted-tier workers' family links follow Phase 10 (C17).

4. ★ **The checks for People results**, applied again at the moment each item is changed:
   - **Values.** A value, including a custom field value, goes back to what it was only if nobody and nothing has written that field since the import, including a later import. If it was empty before, it becomes empty again, and the page counts these. Putting a value back also puts back which write it came from, so reversing a newer import and then an older one works.
   - **Tags** count as one field. They go back only if the person's tags haven't changed since.
   - **Contact details, list memberships and household links the import added** are removed as "entered in error" only if they are unchanged since and nothing was sent to that contact detail or household.      - they weren't merged on either side;
     - nothing was sent to them;
     - they got no portal account;

7. ★ **The window.** 30 days: from commit for everyday imports, and from go-live for a Switch run.
   - **Display:** an absolute date and time in the ministry's time zone, for example "You can reverse this import until 3 December 2026, 5:00 PM Eastern Time", with "in 30 days" as a hint.
   - **Deadline:** a reversal confirmed before the deadline finishes. Deleting prior values waits for it.
   - **Legal hold:** a hold keeps prior values but doesn't extend the window.
   - **Erasure:** erasing a person removes their prior values. The reversal skips them ("Erased since") and never writes to an erased person.
8. ★ **Effects stay dark.** A reversal's own changes fire no automations, field-change triggers, sends, welcomes or goodbyes, the same as an import's. Only Phase 15's reversal of a posted gift batch has donor-visible effects, under Phase 15's rules.
9. ★ **History and evidence.**
   - **Attributed changes:** each change is a new attributed change, for example "Restored by reversal of import 12, confirmed by J. Smith". The import's own history is never erased.
   - **Reversal record:** it keeps who prepared and who confirmed, when, counts and each item's outcome code, with no row content.
10. ★ **A wrong file is a privacy matter, not only a reversal.** This covers a file that should never have been in Asym: another organisation's data, the wrong people, or sensitive columns.
    - **Reverse it** to take it out of use at once.
    - **Erase:** the ministry's privacy role then erases those people through the erasure path, which also reaches the held file and the prior values.
    - **Breach log:** the import and reversal records give the ministry the counts, times and actors its breach log needs. Asym builds no separate incident system.
    - **Asym-caused:** if Asym staff caused it under an operator grant, Asym tells the ministry without undue delay.
11. ★ **Words.**
    - **The action** is "Prepare reversal".
    - **The term** is always "import reversal", never a bare "reversal", which means a payment reversal elsewhere.
    - **Buttons for people results** name the result ("Restore … values", "archive … people"), never "reverse" or "undo".

Clause 3 settles Q5's Switch decision capability and narrowing; clause 4 scopes Q11 cl.4's fund-name rule to Switch real exports; clause 6 refines Q12 cl.4's "always go to review"; clause 8 amends Q15 cl.4's downloads; clause 9 amends Q19 cl.3's default import name; clause 12 sets Q5 cl.3's helper end date. Terms: `docs/features/imports-migration/CONTEXT.md` (Data Tools access, Held for review, Narrowing, Hide values).

**Decision.**

1. ★ **One Data Tools row with three levels.** Phase 12 adds a Data Tools module.
   - **What ministries see:**

     | Level      | Lets you                                                                                              |
     | ---------- | ----------------------------------------------------------------------------------------------------- |
     | **View**   | Follow imports: the menu, the Imports list, statuses, counts and who. No values.                      |
     | **Manage** | Prepare (upload, columns, values, decisions, fix cells, download your file's rows) and Run (confirm). |
     | **Admin**  | Everything above, plus **Replace and Clear**, **Reverse imports** and **Run the Switch**.             |

   - **The Admin-level permissions** are Phase 12 `sensitive`: never on the View or Manage level, granted through Phase 12's sensitive-grant flow, and audited.
   - **The individual permissions** stay grantable on their own for advanced cases, for example Prepare without Run for a helper.
   - **Keys** are dotted and minted by Phase 30 under Phase 12's rules.
2. ★ **Starting sets.**
   - The Owner group holds Data Tools Admin. No other seed holds Data Tools.
   - A ministry adds Data Tools View or Manage to any group, or to a person, in one step.
   - When it launches, existing users get nothing new.
   - **Clearance** is never part of any Data Tools level (Phase 12).
3. ★ **Run the Switch** is Q5's Switch decision capability.
   - **It covers:**
     - starting a Switch;
     - census answers, dispositions and attestations;
     - plan and match decisions;
     - reconciliation controls and sign-off;
     - commit, tail closure and decommission;
     - reassigning the lead;
     - Practice copies and legal hold.
   - **Also needed:** money commits need the money owner's permission (C16), history correction keeps its own (Q13), and creating fields needs Phase 11's.
   - **Narrowing** a Switch file needs Run the Switch **and** clearance.
   - **The Start action** appears only once Asym's preconditions are met (Q2, Q6; Q19 kind switch).
4. ★ **Money.**
   - **Gift files:** Manage is enough to prepare one. Confirm also needs Gift entry's `finance:record_contribution`.
   - **Amounts** in the Imports list and on pages show only to people who can see contributions; others see counts.
   - **Funds step:** shows the file's own labels and the designations the person can see (Phase 10 aliases apply).
   - **Q11 cl.4's "fund names only to cleared members"** applies to Switch real exports.
5. ★ **What people see of records.**
   - **Asym-side facts:** a match, which record, current values and the outcome detail for a row are shown only to people who can see that record.
   - **File cells:** your file's own cells are shown to Manage holders.
   - **Counts:** whole-file and the same for everyone.
   - **Restricted-file floor:** the Switch real-export floor (Q2, Q5) is unchanged. Everyday imports are not restricted until narrowed, because they are the ministry's own files.
6. ★ **Held for review.**
   - **Which rows:** any row matching a record the preparer can't see, a staff member, or someone marked deceased (Q12 cl.4).
   - **The wording**, the same for every reason: "Held for review: someone who can see the matching records will review these rows. Nothing has changed for them."
   - **What never happens:** a held row is never created as a new person, never shows the match, and never changes the counts. The rest of the import goes ahead.
   - **Who reviews:** after commit, any Manage holder who can see the matched record, including the preparer if they can. The reviewer commits those rows under their own permissions, on the same import record. A Tasks Hub item reaches eligible reviewers without naming anyone (O97).
   - **Deadline:** held rows not reviewed by the file's deletion date (30 days after commit, Q15) become "Left out: not reviewed in time". The date is shown.
   - **Setup notice:** Data Tools Admins see one when nobody with Manage has clearance.
   - **Accepted residual:** someone who knows a held row's person isn't staff or deceased can infer they are protected or outside their access. Held protected matches count in Phase 12's restricted-access audit and budget (O104).
7. ★ **Fields you can't edit.**
   - The Columns step offers only fields the person may edit.
   - If someone else confirms, Review lists "Won't be written: you can't edit {field}", and those columns are left out.
   - The write path re-checks.
8. ★ **Downloads.**
   - **Your file's rows** (problem, left-out and held rows) need Manage. They contain the file's own cells and reasons only, never Asym-side values. Held rows are included with the same reason.
   - **Downloads with Asym data** (results lists, Switch Waiting rows) need the ministry's existing export permission plus on-screen visibility. Protected people are never included.
   - **Every download:**
     - is streamed on demand and never stored;
     - is text-typed and formula-safe, with one encoder (ADR-0212);
     - is audited by identifiers only;
     - is limited to 1,000,000 rows; larger sets are filtered first (amends Q15 cl.4).
9. ★ **Seeing each other's work.**
   - **View holders** see every import's status, counts and who started it.
   - **Manage holders** can continue any draft, with every change attributed.
   - **Import names** default to the kind plus date and time ("People import, 4 Nov 2026, 10:42"), not the file name. The file name shows on the import page to Manage holders (amends Q19 cl.3).
10. ★ **People without access.**
    - No menu entry and no shortcuts.
    - Any Data Tools address shows "You don't have access to Data Tools." with **Request access**, which goes to Phase 12's Access requests. It names no one, and the page is the same whether or not the import exists.
    - **View holders** see one line on an import page, "You can follow this import. Preparing and confirming need Data Tools Manage access.", plus Request access. Actions they can't take are absent.
    - **Holders** opening another ministry's import get not found.
11. ★ **Authority while running.**
    - **Per-batch checks:** each batch re-checks the confirmer's permissions and clearance.
    - **On loss:** the import stops after the current batch as Needs attention: "Stopped: {name} no longer has permission".
    - **Resuming:** anyone holding the needed permissions can resume the rest under their own name.
    - **Time-limited access:** if the confirmer's access is time-limited, Confirm shows when it ends.
12. ★ **Helpers and Asym help.**
    - **Helpers (Q5):** ordinary Data Tools grants (usually Manage, or Prepare only) with an end date, by default the day the Switch closes (O105). They cover Data Tools, not only that Switch.
    - **Asym help access:** sees only the Switch tab and its preparation actions. Never the everyday Imports list, import names, values before narrowing, or downloads. No Asym identity holds a Data Tools permission.
13. ★ **Hide values.** A switch on Data Tools pages hides every value for the current session, for coaching on a shared screen (Q5 cl.2). It never reveals more.
14. ★ **No interim access.** Data Tools stays switched off until Phase 12 can grant these permissions (O102). There is no role-name gate, and #2281's platform approval is not used.

Acceptance criteria AC1–AC24, invariants P1–P6, edge cases E1–E30, monitors M-Q20-1 to M-Q20-6 and rejected alternatives: `q20-data-tools-permissions/q20-adversarial-review.md`.

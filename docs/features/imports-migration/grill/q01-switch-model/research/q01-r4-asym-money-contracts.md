**Consequences for a migration (inferred from 2.1–2.7; none is an owner rule):**

- **H1 — naive import of `sub_`/`cus_` IDs is implicit adoption.** If any import wrote SiteStacker-era `sub_…` into `donor_pledges.stripe_subscription_id`, and those events reached the platform endpoint, `invoice.*` / `customer.subscription.*` events would mutate Asym pledge rows (possibly via the unscoped lookup) — "adoption by metadata", which P16 K.1/K.2 and #711 forbid. Writing `cus_…` into `donors.stripe_customer_id` would let a migrated donor open the whole-account Billing Portal and cancel or change a SiteStacker-created subscription from inside Asym (2.5): Asym would become a competing controller of an external executor without proof (P16 K.1 "Externally controlled/read-only … never adopt by metadata or start a competitor"; T.2 "whole-account Stripe Billing Portal … do not use as the authoritative recurring editor"). _(Resumed-pass nuance: q01-r2 found no evidence that SiteStacker creates Stripe Subscriptions, so `sub_` IDs may be rare for SiteStacker Stripe tenants. The `cus_` → Billing Portal hazard and saved-`pm_` hazards remain. Any `sub_` that does exist would belong to another application.)_
- **H2 — the current tenant-key path is the topology the ministry's own Stripe account would plug into.** A ministry that already owns a Stripe account could paste its secret key today and Asym would act as that account (P13 `:687` describes this as the shipped, to-be-retired path). That is technically "same account", but it is not a Settlement Account Binding, has no connection epoch, no application-ownership evidence and no Connect routing — so none of the P16 K.5 reconnect proofs can be satisfied on the current path.
- **H3 — fallback to the platform key** (2.2) means a mis-configured migrated tenant could take live donations into Asym's own account. Any migration rehearsal that enables giving must prove the tenant key or binding exists first.
- Phase 30 must therefore treat every imported provider identifier as **inert evidence** (stored only in staging/provenance, never in `donors.stripe_customer_id`, `donor_pledges.*`, or any column a live handler reads) until the Phase 13 binding and Phase 16 classifier exist. This is consistent with C14 ("a provider/source ID is a link, not an identity") and P13 story 169.

## 5. Payment scenarios: what Asym's contracts permit and forbid

### 5.0 Facts that apply to every Stripe scenario (verified-vendor-doc, accessed 2026-11-01)

- Connect Onboarding for Standard/full-dashboard accounts starts with `POST /v1/accounts` (a **new** account) plus an Account Link; "If you're an extension or an application that needs access to an existing account … you can still use OAuth." — https://docs.stripe.com/connect/standard-accounts
- "OAuth isn't recommended for new Connect platforms … Starting in June 2021, Platforms using OAuth with `read_write` scope won't be able to connect to Standard accounts that are controlled by another platform." OAuth `scope` defaults to `read_only`. — https://docs.stripe.com/connect/oauth-standard-accounts
- Self-serve copy between two Stripe accounts copies Customer objects plus cards and **US ACH** (bank-account or PaymentMethod objects) and SEPA PaymentMethods; customer IDs stay the same, payment-method IDs are new, and a mapping CSV goes to the recipient. It cannot copy Charges, PaymentIntents, Invoices, Plans, **Subscriptions**, Events, Bacs or **ACSS PADs**. Sender and recipient exchange account IDs; the recipient must be activated. — https://docs.stripe.com/get-started/data-migrations/pan-copy-self-serve?copy-method=full
- Processor → Stripe import: Stripe Data Migrations runs it; the old processor encrypts to Stripe's PGP key over SFTP; Stripe returns a mapping file; about 10 business days after valid data; CVC never imported; "Subscriptions, invoices, and other billing data" are not imported; the intake form requires being logged in to the Stripe account. A platform migrating connected accounts requests "a PAN data import, which migrates your payment and customer data to them." A new MID can raise declines; Stripe recommends sending "one-time and customer-initiated payments before recurring ones". — https://docs.stripe.com/get-started/data-migrations/pan-import ; https://docs.stripe.com/connect/migrate-to-stripe
- ACH import: the merchant certifies it holds "mandates that specify the terms for recurring payments", collected online and Nacha WEB-debit validated, with evidence on request; otherwise "you must collect new authorizations". PAD import requires held mandates and PADs may be limited to on-demand use. — https://docs.stripe.com/get-started/data-migrations/payment-method-imports
- Stripe's subscription migration guidance is create-new, then "cancel old subscriptions before they charge so you don't double-bill"; toolkit subscriptions stay scheduled for 24 hours before going live. — https://docs.stripe.com/billing/subscriptions/import-subscriptions-toolkit ; https://docs.stripe.com/billing/subscriptions/migrate-subscriptions
- Phase 16 research (repo, citing Stripe ACH docs): "A mandate authorized for one connected account cannot simply be used with a different connected account." — `phase-16-pledges-recurring-commitments-research-evidence.md:590-595` (repo evidence; the Stripe page itself was not re-read here).

**Key inference (high confidence):** under M1 (Account Links, no OAuth) Asym's binding is **always a new `acct_`**. Stripe's own page says Account Links onboarding starts by creating a new account, and "If you're an extension or an application that needs access to an existing account … you can still use OAuth" (https://docs.stripe.com/connect/standard-accounts, accessed 2026-11-01, verified-vendor-doc). A ministry's pre-existing Stripe account, however SiteStacker used it, is therefore a _different account_. M8 makes every move of an existing recurring gift onto an Asym executor a **formal cutover, not a reconnect**. "Reconnect → Reconciling" (P16 K.5, first half) applies only to a binding Asym itself once held; it never applies to a SiteStacker-era account.

**Second, independent reason (resumed pass):** even if an owner amendment let Asym attach to the ministry's _same_ Stripe account, the SiteStacker-era **executor** is SiteStacker's scheduler (or PayPal). P16's transition table maps "another application/operator owns executor" to "Externally controlled/read-only" (`phase-16-…md:2085`). K.5 lists "replacement executor" alongside different account as formal cutover (`:1314`). So moving a schedule from SiteStacker's cron to Asym is formal cutover **even on the same account**. _Correction to sibling q01-r2 §0 point 7(a)_, which says same-account reuse is "reconnect → Reconciling, not Managed": under P16 that applies only to an Asym-held binding being restored. It does not apply to taking over another operator's schedule. ADR-0015 says the same: "A different account, merchant, or mode is a cutover" (`docs/adr/0015-…md:38-41`).

### 5.2 What this means for the founder's question ("how the integration with their previous processor works")

1. **There is no zero-touch recurring migration under the ratified contracts.** Every SiteStacker recurring gift either (a) keeps running on the old executor as external/read-only until it ends or is proved stopped, or (b) is replaced by an Asym recurring gift after a formal cutover that needs old-stop proof and **fresh donor authorization** (M6, M8, REC-23, #809 "cutover never copies authority because method/customer metadata looks similar"). This holds even when the ministry already used Stripe, because M1 always creates a new account.
2. **Vault transfer is allowed but only buys convenience.** A Stripe self-serve copy (scenario A) or a processor → Stripe import (scenario C) can place the donor's card or US bank account on the new account without Asym touching PAN (consistent with P13 `:543-545`, `:745`). Under M6/M11 it does not authorize collection. Its value is that the donor confirms an existing method in a hosted step instead of re-entering details, and that is itself an open owner ruling.
3. **This is stricter than vendor practice.** Stripe's own guidance is to import the vault, then "begin charging all of your customers on Stripe" (pan-import), and to create new subscriptions then cancel the old ones before they charge (toolkit). r10-gap-g4 X4 (Bloomerang help centre) describes a single dated handoff from the old processor with no donor action. Asym's ratified text forbids both continuation-without-authorization and create-then-cancel. Expect donor attrition in a re-authorization campaign; whether to accept that, or amend P16 to admit a narrowly "proved continuation" (same Legal Entity and merchant, unchanged terms, evidenced original authorization, vault moved provider-to-provider), is a **founder decision with Phase 16 as owner** (§8 G4).
4. **The recurring handover is naturally staggered even under Option A.** P16 K.5 releases "cohort-by-cohort", and external/read-only is a legitimate steady state. So "one planned switch" can hold for supporter and history truth while recurring executors move over weeks or months. That matches founder refinement (4) and means the "catch-up" in refinement (2) is not a short tail: it lasts until the last external recurring gift ends or moves, and for ACH it cannot start until M14 ships.

## 8. Gaps and contradictions for the founder or an owner

Each item says which Q1 refinement it touches. "Owner" is the party that must rule (C1/C3).

**G1 — The post-switch "gifts-only catch-up" (refinement 2) has no money owner, and as framed it collides with three rules.** (a) M19: "recurring intake of one operational source artifact … is owned by that source domain, not by this general migration workbench", and "Reviewed backfill is a separate bounded operation". A catch-up repeated every week or month until the last external recurring gift ends (§5.2 point 4) is recurring intake. (b) P13 D.6 (M3) is written for _pre-Asym_ gifts ("stamped with a pre-Asym provenance boundary"); a gift SiteStacker charges after Asym became the system of record is not pre-Asym. (c) For offline tenders, Phase 15 is the sole writer (r03 D-3). _Ratified home that fits:_ a P16 `manual_external` recurring line (M13) with `structured_feed` review basis, money entering through a Phase 13 owner command for externally-collected gifts, with D11 applications linking gifts to expectations. _Owner:_ Phase 13 + Phase 16 (command); Phase 30 (transport only). _Founder:_ is the catch-up a bounded number of runs (for example, one per month until the tail ends, each a separate reviewed backfill) or a money-domain feed?

**G2 — Nobody receipts gifts SiteStacker charges after the switch.** M16 forbids receipts for _pre-platform_ imported gifts; the Phase 7 import fact has only two values ("a pre-Asym receipt exists or … no Asym receipt is permitted", P13 `:1031-1034`); Phase 7 E3 says imported gifts "can be receipted" (r03 D-1). SiteStacker itself tells ministries a receipt must go "after every billing" for card-network compliance (verified-vendor-doc, §4). If refinement (3) turns off SiteStacker messaging (r07: the 2020 Data Migration Plan says disable all System Messages for import), the donor gets no receipt; if SiteStacker keeps sending, receipts are SiteStacker-branded and point at a donor dashboard the ministry may retire. _Owner:_ Phase 7 (fact), Phase 13 (D.6 scope). _Founder:_ during the tail, who receipts SiteStacker-charged gifts? Either SiteStacker does (keep Contribution Receipt on and narrow refinement 3 to Spark, forms and Mailchimp), or Asym does prospectively.

_Resumed-pass refinement._ An Asym prospective receipt may not need a new Phase 7 rule. Phase 7 E3 already lets "manual/imported/historical gifts without a staged-gift record … be receipted" under "prospective plan/policy-admitted issuance" (`phase-07-…md:339`). The missing pieces are narrower:

- The undefined Phase 7 import fact (D4 in the decision log) needs a third case: a post-boundary externally collected gift with no prior receipt.
- That classification has to be fixed when the gift enters. The roadmap says "A source event marked historical cannot become prospective by changing a displayed timestamp" (`roadmap.md:4395`).
- Phase 14 says import-origin acknowledgment requests "remain held and never pass that gate" (`phase-14-…md:1485-1490`). If catch-up gifts enter as _imports_, they can never get an Asym thank-you, even when a receipt is permitted.

Double-receipting is the hazard if SiteStacker's Contribution Receipt stays on _and_ Asym receipts prospectively. Exactly one receipting system per gift must be declared.

**G3 — Refinement (3) removes the donor's cancellation path and some failure handling.** SiteStacker's article says "Merchants must provide an online or electronic cancellation method" (verified-vendor-doc). Spark outcomes "can … cancel contributions" (r07 via r10-gap-g4 S-a), so disabling Spark may also disable automations a ministry relies on for failed-card handling. If the SiteStacker donor dashboard is retired at switch, Asym must accept cancellation of _external_ arrangements (M12) and staff must execute the stop in SiteStacker. _Owner:_ Phase 16 (cancellation-first for external executors), Phase 25 (donor surface), ministry runbook. _Founder:_ keep the SiteStacker donor dashboard reachable until the tail ends, or make Asym the cancellation front door for external arrangements?

**G4 — Fresh authorization for every moved recurring gift (refinement 4).** See §5.2. Ratified text (M6 "never backfill … collection authorization"; REC-23; #809) makes a donor action mandatory. P16 K.5 says "applicable fresh IDs and collection authorization" (`:1314`) and ADR-0015 says "any required fresh authorization" (`docs/adr/0015-…md:39-40`), but REC-23 (`:2696`) and M6 (`:2581`) drop the qualifier. P13 adds a further constraint: "do not silently create a gap, overlap, duplicate charge, or fresh mandate" (`phase-13-…md:740-741`). A fresh mandate is not forbidden, but it must never be silent. P25 RC12 says "Proven continuity does not transfer authorization" (`contracts/recurring.md:105`). P16 J.3 routes "replace/bind method" to **Complete with donor now** and says "No bulk action may … bind methods … or restart donors" (`:1225-1236`). Every moved gift therefore needs its own donor-completed step. _Owner:_ Phase 16. _Founder:_ accept campaign attrition, or authorize a narrow "proved continuation" amendment?

**G5 — Ordering: Asym is stop-first; Stripe is create-then-cancel.** M9 forbids create-then-cancel, while Stripe's toolkit creates the new subscription (scheduled 24 hours) and cancels the old "before they charge". Stop-first with P16's "no catch-up/backcharge" (`:1316`) can make a donor miss one occurrence if the stop proof and the new first occurrence straddle a due date. _Owner:_ Phase 16 (#809 runbook). _Inferred mitigation:_ prove stop between occurrences and anchor the first Asym occurrence to the next scheduled civil date.

**G6 — Missionary balances across the switch (Phase 21).** If Field Accounts activate at the switch, gifts SiteStacker charges after the through-boundary must enter only through the Asym contribution path, never in the opening residual. The Opening Source Package's through-boundary must equal the gift snapshot boundary, or the same gift is counted twice. ADR-0106 treats post-activation prior-writer activity as overlap to monitor (M18). If Field Accounts do not activate at the switch, missionaries have no authoritative balance and must see a limitation, not `current_funding`. _Owner:_ Phase 21. _Founder:_ must Field Account activation coincide with the CRM switch, or follow it?

**G7 — Accounting double-posting.** Under M17 the SiteStacker-processed deposit stream is a separate source family. It should stay previous-owner (bookkeeper or existing connector) until its executor stops; catch-up gifts must not be posted by Asym as new work. _Owner:_ Phase 20. Whether SiteStacker posts to QBO/Xero at all is unverified.

**G8 — Cutover-year statements and loss of SiteStacker access.** Option A says "Asym becomes the only place". Once the SiteStacker contract ends, nobody can produce the SiteStacker-period part of a year-end statement. Phase 19 cumulative coverage admits only gifts "frozen as `annual_cumulative_cash`" (`phase-19-…md:944`, US19-12 `:1288-1295`), and imported gifts are not. A Canadian ministry on annual receipting would have no issuer for the pre-switch portion of the year. r03 raised the US variant. _Owner:_ Phase 7/19. _Founder:_ recommend the switch date sit at a calendar-year boundary, or require the ministry to issue the pre-switch portion from SiteStacker before leaving.

**G9 — Current code would turn imported IDs into live control (§2 H1–H3).** _Owner:_ Phase 30 spec (inert-evidence rule) plus Phase 13/16 (remove the metadata routing, unscoped lookup, platform-key fallback and Billing Portal before any migrated tenant goes live). This is a sequencing dependency: no SiteStacker tenant should take live gifts on the plaintext-key path.

**G10 — ACH/PAD donors cannot move until M14 ships.** ACH recurring is the longest external tail. Copying PADs between Stripe accounts is not possible (verified). _Owner:_ Phase 13/16.

**G11 — Re-authorization messages have no Live contract or consent basis.** P16 D.9 has no migration transition; imported opt-ins grant nothing (C10). _Owner:_ Phase 16/17/6.

**G12 — Merchant of record and legal issuer for SiteStacker-era gifts.** If SiteStacker or a partner was merchant of record (scenario B), the issuer of historical receipts and the Legal Entity for imported gifts cannot be inferred from the processor (C19; O4; P13 `:1738` "never caller input"). _Owner:_ Phase 7/13/20.

**G13 — Refunds and disputes on pre-switch and catch-up gifts.** Asym can only refund through its own binding (`refunds.create` via `Stripe-Account`, P13 `:845`). Refunds of SiteStacker-processed gifts must be done in the old processor and then imported as append-only facts (C6). The old merchant account must stay open through the dispute and ACH-return windows (the exact durations were not verified here). _Owner:_ Phase 13 plus the ministry runbook.

**G14 — Rehearsal must not touch live money.** "Practice runs that change nothing" must also never bind a live Stripe account, never hit the platform-key fallback, and never write provider IDs to live columns (§2). _Owner:_ Phase 30 spec; Phase 13.

**G15 — Missionaries may see support drop on switch day.** Proved recurring commitments whose executor is external/read-only are qualified, not dependable: "quarantined future support moves to a qualified attention bucket" (P16 `:1316`; #809 copy "Organization is checking this automatic donation"). Without a deliberate projection rule for _planned_ external tails, every SiteStacker recurring gift could look at-risk on day one. _Owner:_ Phase 16 D13 / Phase 28.

**Not contradicted:** refinement (1), exact repeat import as replay of the same snapshot, raises no money conflict, provided replay is idempotent on source identity (P14 shows the pattern, `phase-14-…md:1862-1866`) and Phase 13 adds import-identity columns (r03 D-4). Refinement (4)'s "records designed so Option B can be added" is compatible with P16's cohort-by-cohort release and ADR-0058's per-source-family boundaries.

## 10. Further gaps found in the resumed pass (continues §8 numbering)

**G16 — Several legacy merchant accounts per ministry vs one binding per Legal Entity.** SiteStacker attaches gateways per Site, and possibly per Site × currency × method (q01-r2, inferred). The Phase 13 binding is one account per Tenant × Legal Entity × environment × purpose (`phase-13-…md:663-664`), and its schema list contradicts that with a single `tenants.stripe_account_id` (`:1892`). A ministry with, for example, a USD processor and a CAD processor for one Legal Entity, or two Sites on two processors, must collapse onto one Asym binding per Legal Entity, or have a second Legal Entity proved. _Owner:_ Phase 13 (binding model), Phase 2/24 (Site never selects Legal Entity, C19). _Founder:_ does v1 accept only ministries whose legacy processors map one-to-one onto Legal Entities?

**G17 — PayPal has no Asym topology at all.** Phase 13 is Stripe-only. PayPal-through-Stripe does not support Connect direct charges (verified, §5 scenario D). SiteStacker PayPal Standard subscriptions keep running after SiteStacker is turned off (q01-r2, inferred). There is no owner for (a) ingesting PayPal-collected tail gifts as money facts, (b) proving a PayPal subscription stopped, or (c) telling PayPal donors to switch. _Owner:_ Phase 13 + Phase 16 (money and control), customer-success runbook. _Founder:_ in v1, are PayPal recurring donors simply told to cancel in PayPal and start again in Asym, with PayPal tail gifts entered as reviewed external gifts?

**G18 — Same-account reuse contradicts M1 (sibling disagreement).** q01-r2 §0 7(a) lists "same account reused → reconnect → Reconciling" as a path. This track finds it unavailable for two reasons. First, Account Links always creates a new account, and existing accounts need OAuth, which P13 D1 forbids (verified Stripe doc; `phase-13-…md:659`). Second, even on the same account, taking over SiteStacker's schedule is a "replacement executor" → formal cutover (`phase-16-…md:1314`, `:2085`). _Owner:_ Phase 13 (whether any existing-account attachment is ever allowed, for example a migration-only `read_only` observation grant). _Founder:_ none unless Phase 13 is reopened.

**G19 — Stripe's current docs mark legacy account types deprecated and steer new platforms to Accounts v2.** The Standard-accounts page now carries a "Deprecated feature" banner. It points new platforms to Accounts v2, or to Accounts v1 with controller properties (https://docs.stripe.com/connect/standard-accounts, accessed 2026-11-01, verified-vendor-doc). P13 ratified v1 controller properties (`phase-13-…md:659`), which the page still names as the fallback. This is not a contradiction. It is a build-time refresh item: whether Accounts v2 changes migration mechanics (for example vault copy into a v2 account, or attaching existing accounts) is unverified. _Owner:_ Phase 13 at build time.

**G20 — Old-executor stop proof for non-Stripe executors is not modelled.** #809 (OPEN, `status:blocked`) designs stop proof around a Stripe adapter (`stopFutureCollection`, "current-object/source evidence census under the exact tenant/account/mode/application scope"; #809 body lines 19, 25, 54). For a SiteStacker cron executor or a PayPal subscription, Asym cannot read or stop the executor. Stop proof can only be _source evidence_: a SiteStacker Recurring export showing ended schedules, processor or PayPal reports with no charges after the STOP date, and ministry attestation. #809 allows a "source evidence census" when event retention is insufficient (line 19). It does not define what source evidence qualifies for a foreign executor. _Owner:_ Phase 16 (#809 / #834).

**G21 — The existing production tenants question (decision-log D13).** If production really holds real donors on the plaintext-key path, those tenants need a Settlement Account Binding move. P13's "delete-and-replace" fresh-build posture (`:2257`) would then be unsafe for them. This is outside Phase 30. It shares the same P16 formal-cutover rules, because an Asym-created new `acct_` differs from the tenant's keyed account. _Owner:_ Phase 13 / founder (production status).

## 12. Summary

**(a) Who does what on switch day** (§7, §9). The ministry declares the freeze and turns off SiteStacker forms, Spark and Mailchimp; Phase 30 records that declaration. Phase 13 must already have a _new_ Settlement Account Binding. Phase 30 imports the final snapshot through owner commands: Phase 13 D.6 for one-time history, and the Phase 16 classifier (#834) for recurring and pledges, which defaults every executor to external/read-only. Phase 7 decides receipts and Phase 14 holds acknowledgments. Phase 20 keeps the old deposit stream with its previous posting owner. Phase 21 activates Field Accounts only at an exact through-boundary. Phase 25 and Phase 28 show imported history under honest coverage. Under the ratified texts nothing moves a recurring gift on switch day. Recurring moves happen later, cohort by cohort, through Phase 16 formal cutover.

**(b) The "separate migration workstream"** (§6). Nobody owns it. Phase 13 names it three times (`:159-165`, `:743-746`, `:2192-2199`). Phase 30's roadmap text never mentions processors, vaults, re-authorization or freezes. It would need to own seven things:

1. processor coordination;
2. connected-account readiness;
3. vault-transfer mapping evidence;
4. old-executor stop proof;
5. a re-authorization campaign;
6. freeze coordination;
7. tail reconciliation.

Recommended split, which needs owner edits: items 2–3 to Phase 13, items 4–5 to Phase 16, items 6–7 to Phase 30, item 1 to an operations runbook.

**(c) Payment scenarios** (§5.1). None allows adoption via reconnect: under P13 D1 Asym always creates a new account, and SiteStacker's cron or PayPal is another operator's executor. Moving any recurring gift is a formal cutover that needs old-stop proof plus fresh, donor-completed authorization, even when the ministry already used Stripe.

- **Ministry's own Stripe account:** vault self-serve copy is allowed and saves re-keying only.
- **SiteStacker platform Stripe:** may not be portable without SiteStacker's cooperation.
- **Non-Stripe vault gateway:** processor → Stripe import is allowed if Asym never touches the file.
- **PayPal:** stays external until the donor switches.
- **ACH/PAD:** blocked until P13 D.7 ships, and PADs cannot be copied.

Forbidden in every scenario: adopting by metadata, create-then-cancel, copying authorization, bulk method binding, Asym handling PAN/bank data, and active-active collection.

**(d) Gaps** (§8 G1–G15, §10 G16–G21). The most consequential:

- The post-switch catch-up has no money owner and collides with the "recurring intake is not Phase 30" and "pre-Asym" rules (G1).
- Nobody receipts or thanks gifts SiteStacker charges after the switch (G2, A9).
- Every moved recurring gift needs donor action, and the texts disagree on "applicable" (G4).
- Current code would turn imported IDs into live control and can fall back to the platform key (G9, G14).
- Several legacy merchant accounts per ministry versus one binding per Legal Entity (G16).
- PayPal has no topology (G17).
- Stop proof for foreign executors is undefined (G20).

**Current vs intended vs best permanent path.** Current code is a plaintext-key, metadata-routed prototype that must not carry a migrated tenant. Intended (ratified) behaviour is Connect direct charges, proof-gated classification and formal cutover. The best permanent path, inferred, is Option A for supporter and history truth, a _planned external tail_ for recurring, a donor-confirm campaign backed by vault copy where available, and a possible migration-only `read_only` observation grant on the old Stripe account. That grant would need a Phase 13 amendment.

## 0. Question and method

**Founder input under examination (Q1, 2026-11-01).** Option A, "one planned switch per ministry", with the four refinements, plus the founder's addition: "we need to figure out and make sure we fully research and understand what needs to be brought over from SiteStacker including how the integration with their previous payment processor ... Also think out the edge cases." This file answers the "what needs to be brought over" half for every SiteStacker data family. Processor portability is the subject of the sibling tracks `q01-r2-sitestacker-payments.md` and `q01-r3-processor-migration-practice.md`; this file records only the SiteStacker-side payment facts that belong in the inventory.

**Method.** (1) Re-read the decision log and r07, g3, g4, g5, g8 and r03. (2) Crawled the public `training.sitestacker.com` Freshdesk knowledge base with plain HTTP GET (folder listings, the site's own `/support/search/solutions?term=` search, and article bodies), plus `sitestacker.com` marketing pages. (3) Downloaded and read the vendor's public 40-page "Report Admin Documentation.pdf" attachment. (4) Searched for newer release notes. (5) Checked the repo for target owners. No login, no database, no app server, no tracker writes.

**What a "disposition" means here (proposed vocabulary, not owner text).**

| Disposition                 | Meaning in this file                                                                                                                                                                                    |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Authoritative**           | Imported as the live Asym record of truth through the target owner's typed command; after the switch Asym is the only writer (Option A).                                                                |
| **Historical reference**    | Imported as dated, already-happened facts (e.g. settled gifts under Phase 13 D.6) with source lineage; never re-executed, never fires effects.                                                          |
| **Evidence only**           | Kept as source-bound evidence attached to the run or to a target record (prior-receipt facts, consent evidence, adverse suppression evidence); never becomes Asym configuration or authority by itself. |
| **Census-only**             | Counted and described in the pre-switch census (what exists, how much, what it does) so the ministry can rebuild or switch it off; not imported as data.                                                |
| **Exclude, visible reason** | Not imported; every source record still gets a visible exclusion disposition in the run evidence (C13 pattern; `roadmap.md:4395` "quarantine unresolved records for a visible disposition").            |
| **Real export decides**     | Disposition cannot be set until a representative export shows what the source actually contains.                                                                                                        |

**Common facts for every scenario.**

- SiteStacker holds tokens, not credentials (V3).
- SiteStacker's own cron is the recurring executor for vault-token schedules (K7).

**Inventory-side edge cases specific to processors** (complementing `q01-r4` §11):

1. A ministry changed processor during its SiteStacker life. Older gifts reference processor X and newer ones Y, and X's account may be closed, so external reconciliation of old years is impossible. History is still importable; the reconciliation report must say which periods were checked against a processor (A3).
2. "Move Payment Method" rewrote which donor owns historical gifts and schedules (V4). Processor customer records may still name the original person, so the processor is not an identity authority (#711).
3. Fraud clean-up deleted refunded transactions (K8). Processor totals then exceed SiteStacker totals, and the difference must be explained, not imported.
4. Donor-covered fees (D21) and processor fees: SiteStacker records the donor-covered portion only; processor fees and net settlements exist only at the processor (D20).
5. The ministry's processor contract may forbid exporting vault data, or charge for it (unverified per processor; `q01-r3` §3).

## 5. Minimum export checklist for a ministry administrator (proposed)

## 9. Summary

**What a SiteStacker ministry holds.** The inventory covers 81 data families in eight groups:

- installation (A1-A6)
- CRM (B1-B15)
- users (C1-C5)
- giving (D1-D27)
- communications (E1-E10)
- forms and events (F1-F7)
- content (G1-G9)
- reports (H1-H2)

Every row cites public vendor documentation or prior verified research. Only a handful of export surfaces are documented, and **none documents its columns**:

- CRM grid CSV
- Contributions Transaction, Designation and Recurring grid CSVs
- per-list newsletter CSVs
- the Statements report
- entity definitions
- the gated Reports/BI tool

Relationships, notes, activities, Historic Giving, Person Owner and Person Site can be reached only through the BI tool or a WMTEK extract (K4). Content, media and files have no documented export.

**Proposed dispositions (none decided):**

- **Authoritative after the switch:** People, Groups, households, contact data, custom-field values, Data Group options, mappable relationships. All go through owner commands with in-plan match review.
- **Historical reference:** succeeded transactions and designations, refunds and reversals, soft credits, tributes, notes and activities (if F16 allows). All dated, settled and dark.
- **Evidence only:**
  - recurring schedules, offline recurring and payment-method references (for the Phase 16 classifier)
  - receipt and statement history
  - batch identity
  - source codes (until O5)
  - newsletter membership and Mailchimp suppressions (as adverse evidence)
  - ledger lines (for Phase 21)
- **Census-only:** logins, roles, SAML, API keys, automations, system messages, workflows, menus, print templates, reports, dashboards, domains.
- **Exclude, visible reason:** child sponsorship (per row, **including per designation and per schedule**), failed transactions, draft batches, pre-login tokens.
- **Real export decides:** Record Types, Person Owner and Person Site, Affiliated, pledges, CRM files, form submissions, events, prayers, all content.

**Findings that change earlier research.**

1. **Historic Giving double counts by design (K19).** Native income "will populate in Historic Giving automatically" (V67). Adding Contributions and Historic Giving double counts for every SiteStacker-managed ministry, not only for DMS-migrated ones. The kit needs one basis per period and an overlap proof.
2. **Ledger lines can be negative and come from accounting (K20).** They are Phase 21 evidence, never gifts.
3. **Child sponsorship money runs through ordinary Contributions (K21).** Forced-recurring categories, child gifts at checkout, and mixed checkouts mean C13 must be applied per designation and per schedule. Whether historical sponsorship payments stay as giving history is a new founder question.
4. **Recurring donors generally hold SiteStacker logins (K22).** Moving to Asym therefore means a Phase 4 claim step for exactly the donors whose payment continuity is most at risk.
5. **Motion 2.5 creates and removes relationships automatically (K23).** Exported relationships are partly workflow side effects.
6. **The newer help centre is still unreachable.** Releases 2.53-2.56 remain unverified (K17, V82).

**For the founder's addition (processor integration).** SiteStacker holds tokens only. Its own cron charges vault-token schedules. PayPal Standard subscriptions (inferred from code) keep charging outside it. Several processors can run per Site. The inventory therefore captures **references and a census per processor × Site × currency** and never credentials (§4). The moving itself belongs to Phase 16 and the separate migration workstream (`q01-r2`/`r3`/`r4`).

**Practical deliverables.**

- §5 is a proposed step-by-step export checklist for a ministry administrator: vendor and processor questions, census, 19 exports with practice-run vs final timing, and eight freeze steps.
- §6 lists 20 propositions (R1-R20) that a real export must settle before the kit can be called representative (C23).
- §7 lists 20 cross-cutting edge cases with proposed handling and owners.

- r10-gap-g6 already mapped the administrator journey J0-J10 across Mission Control surfaces, the hand-offs to Phase 4/8/9/40 and the Tasks Hub (ADR-0183). This track does not repeat that map. - r10-gap-g4 §7 already gathered Microsoft Dynamics cutover (mock cutover, go/no-go, rollback plan), Salesforce Knowledge "stop changes", the MigrateMyCRM delta overwrite warning and the Bloomerang recurring-transfer STOP date. This track cites those findings and does not refetch them.

They are ratified **for CMS content only**. This track reuses their patterns as the default for the CRM switch and says where the CRM switch needs more.

### 2.1 What the external evidence establishes (and does not)

1. **Staff-led vs self-serve split (evidence-backed).** Every payment-data move in the sources is staff-led by the receiving processor with a merchant approval gate (X8: Stripe executes, merchant approves a validation summary). Subscription re-creation is self-serve with guard rails (X7). Nonprofit CRM conversions are marketed as staff-led services with unpublished procedures (X11). Platform guidance treats business sign-off as a required checklist item (X9). **Inference:** a ministry switch will in practice be a supported (assisted) migration with a self-serve workbench, not a pure self-serve wizard. Who the "assistant" is (Asym staff, a partner, the ministry's own admin) is a founder/commercial question this track cannot settle.
2. **Review-before-commit is universal; the depth varies (evidence-backed).** NPSP's dry run checks only some errors (X5); HubSpot fixes in-tool only from the first 1,000 rows (X4); Stripe's toolkit review is a short summary (X7). The repo's sealed-plan standard (R7) is stricter than all of them. This matches g4's finding that Asym's rules are stricter than common practice on deltas.
3. **A visible "you can still cancel until <timestamp>" window is shipped practice (evidence-backed, X7).** The Stripe toolkit's scheduled 24-hour state with a 10-hour cancel window shown as a timestamp is the closest shipped analogue to "Cancel import before writes" (R8). Asym's equivalent is the pre-write state, not a time-boxed window, because the repo forbids promising time-window undo (R4).
4. **Error downloads carry the row plus a reason code, and redact sensitive values (evidence-backed, X4, X7).** This matches R6's "downloadable formula-safe report" and r09's formula-injection findings.
5. **What the sources do not show.** None of the fetched sources shows a cross-file _readiness dashboard_ for a whole-organization cutover as a product screen. Dynamics expresses readiness as a checklist document (X9); GOV.UK gives the task-list pattern (X1). A product readiness view for the switch is therefore **judgment built from those two patterns**, not a copied precedent.

## 4. The administrator's switch journey (proposed; judgment unless cited)

Option A turns Phase 30's per-file import into a **ministry-level switch** with a before, a moment and an after. Repo text covers each file's plan, commit, run and reversal (R6-R9). Nothing covers the switch as one thing. The proposals below build on R6-R10 and the external patterns in §2.

### 4.1 One switch record above the runs (owner gap, proposed)

Refinement (4) already proposes run identity, source-snapshot identity and per-record lineage. The journey also needs a **switch record** that ties together, per ministry: practice runs, the freeze declaration, the final export snapshot(s), the final runs, the reconciliation sign-off, the go-live action, and later catch-up runs. Without it, "are we ready?", "when did we freeze?" and "what changed after the switch?" have no single answer. This is **inferred** from the five-answer screen rule (R9) applied at ministry scope, and from X9's practice of signing off cutover as a unit. No repo text defines it.

### 4.2 Stages and what must be true before each gate

The proposal is a status page with ordered stages, each holding an any-order task list, rather than a new wizard (Phase 29 forbids a "blanket new wizard", R10). No shared step indicator or task-list component exists in `packages/ui` today (grep finds none; `number-field.tsx` is the only "stepper" match), so it would be composed from existing base-maia parts (repo-integrated absence; judgment on composition).

### 4.3 Status vocabulary (proposed; judgment anchored in R6/R8)

Derive labels from facts rather than a stored enum (D29 benchmark "Derived state model", `phase-23-d29-content-portability-ux-benchmark.md:779-783`). Statuses are text plus icon, never color alone (R9, X1).

- **Readiness tasks:** Done · Needs attention (N issues) · Not started · Waiting for {owner/person} · Can't start yet — needs {stage}. GOV.UK's current guidance only shows "Completed" and "Incomplete" (X1), so the extra states are **judgment** and need usability testing.
- **Per-record outcome (final and practice runs):** Added · Updated · Already up to date · Matched to an existing supporter · Not imported — by decision (with reason, e.g. child sponsorship, C13) · Not imported — needs fixing · Waiting for review · Not sure yet — checking. - **Practice runs are visibly practice:** every practice screen and download says "Practice run — nothing was changed in Asym" (judgment, extending ADR-0173's "No content has changed", R7).

### 4.4 Plain-language progress and outcome

Reuse D29 clauses 27-28 (R8) unchanged: factual phases, exact counts when known, indeterminate when not, no time promises, "Stop after the current safe batch" once writes start. Binding: R2, R8, r10-gap-g6 J5 (a run list is needed to find a run again). ### 4.8 The freeze moment and time zones

- Keep four times distinct: freeze moment chosen; declaration recorded; export taken; final run committed (judgment; mirrors Phase 25's distinction of recorded-at, external date and fetch time, `financial.md:145`).

## 5. Donors affected by the switch (proposed; judgment unless cited)

### 5.1 Default: the data move is invisible to donors

Imports send nothing (R5); historical import creates no donor bell item (R15); donors are contacted only when **their own arrangement** crosses a meaningful boundary (R16). So moving supporter records and history produces **no donor message**. Any donor communication about the switch is a separate, ministry-authorized message owned by Phase 17 (content) and Phase 6 (delivery), never an import effect.

### 5.2 Recurring donors during a processor move

The cases in §3.1 decide the experience. UX recommendations:

1. **No action needed (tokens moved, or the same processor account continues).** Stay silent unless something the donor will see changes: statement descriptor, receipt sender or look, or where to manage the gift. Then send one short notice: what changes, what does not, and "we will never ask for card details by email" (M1, P9 descriptor, M2). Judgment on the trigger; evidence-backed on content.
2. **Action needed (Google Pay, PayPal, refused token release, no ACH mandate).**
   - **One secure link to a single-purpose page on the ministry's verified domain**, bound to that donor's exact arrangement; the page also says "or sign in at {ministry site}" so cautious donors need not click (M2, M5; Phase 25 IC05 brand/verified host, `identity.md:45`).
   - **Prefilled and confirmed, not re-typed:** amount, currency, frequency, designation (missionary or project), next date and the next two or three projected dates (Phase 16 amendment, `phase-16-cross-prd-congruence-2026-07-13.md:179`).
   - **Wallets and bank options** offered through the processor's hosted fields (P3, P10 show wallets often cannot migrate, so the new authorization is where Apple Pay/Google Pay belong).
   - **A plain reason:** "We have moved to a new giving system. To keep your monthly gift of $50 to the Smith family going, please confirm how you'd like to pay."
   - **A dated deadline and the consequence of doing nothing:** "Your last gift through our old system is on 1 March. If you don't confirm by 15 March, your monthly gift will stop. Nothing else changes, and you can restart at any time." No catch-up or back-charging (Phase 16 D5 "No debt, catch-up, or ordinary-save charge", `phase-16-...md:90`; restart "never a resurrection or catch-up", `:293`).
   - **Cancel as easy as continue** (Phase 16 "Cancel is direct and does not require a pause detour", `:678`).
   - **No double charge:** the first Asym-collected date must follow the proven last charge by the old system (Stripe toolkit "schedule the new Stripe subscription to start after the last charge from the old subscription", X7; decision-log C9 old-stop proof). Show both dates to the donor.
3. **Cadence (evidence is weak).** Practitioner sources agree on several touches over weeks and more than one channel (P6 "emails, phone calls, and letters"; M3 announce → ask → two reminders → dated close). Bacs requires a formal letter within the notice period (P3). No source gives tested response rates. Proposed default (judgment): announce; personal ask with link; two reminders a week or more apart; final dated notice; then a "not yet confirmed" list for personal follow-up by staff or the missionary.
4. **Messenger.** Many partners know their missionary better than the organization (assumption about ministry relationships; no source found). Whether missionaries may see which partners still need to act is a privacy and Phase 16/28 question (§12).
5. **Expect failed payments after a processor change** (new merchant ID, P2). Phase 16 already forbids treating soft misses as lapse and forbids donor-facing "Lapsed" (R16), which protects donors from premature alarm.

### 5.3 First login to the donor portal

- **No auto-created logins and no claim by email match** (R14; `roadmap.md:4365` "no ... account grant"). Imported supporters simply exist; a donor who later signs in with email-first sign-in sees their history once Phase 4/25 claim rules connect them. Evidence-backed (repo).
- **History coverage is stated, not implied.** Imported gifts appear as normal gifts with honest provenance; where coverage is partial the page says so ("Gifts before {date} were recorded in our previous system and may not all appear here") instead of an empty or partial list that reads as never-gave (R15). Exact wording is judgment.
- **Receipts and statements.** Pre-switch gifts get no new receipts (decision-log C7). The portal says where earlier receipts came from and how to get a copy (judgment). In the switch year, donors may receive two statements (M4, snippet); whether Asym's statement covers pre-switch gifts is Phase 19/7 (F13). The donor-facing rule is to say plainly which statement covers which months.

### 7.2 Large grids and screen readers

- **Read-only review uses table semantics; `role="grid"` only where cells are edited.** APG: a grid "Requires the author to provide code that manages focus movement inside it" (https://www.w3.org/WAI/ARIA/apg/patterns/grid/, fetched). Evidence-backed.
- **Virtualized grids must expose total size and position.** APG: when rows are not all in the DOM, set `aria-rowcount` to the total and `aria-rowindex` per row. The shared `data-grid` virtualizes but sets neither (R12). Using it for staged rows needs that fix in `packages/ui` first (repo-integrated gap + verified spec).
- **Navigate by issue, not by row.** Group issues by code with counts and links into filtered views; offer the download for bulk work (R6, X2, X4). A screen-reader user should reach "Contributions: 14 must fix — missing Legal Entity (9), unknown fund (5)" in a few keystrokes (judgment).

### 7.3 Mobile and low bandwidth

- **No hard desktop block.** Repo rules require 320 px reflow (R10) and 400% zoom (R9), and WCAG excepts only the grid itself. Recommend that status, readiness, freeze declaration, progress, results summaries and finance sign-off work fully on a phone; heavy mapping and in-grid fixing may say "easier on a larger screen" but must still work (judgment, bounded by R9/R10).
- **Weak networks.** Resumable uploads (M7 shows TUS with 6 MB chunks and 24-hour URLs; Phase 29 owns the choice); server-side paging and filtering so the browser never loads every staged row; status polling that resumes after a dropped connection; downloads prepared server-side (judgment; R8 "weak networks").

### 7.4 UI system constraint

Everything above composes from existing base-maia/Base UI parts (`Table`, `DataTableResponsive` card view, `progress`, `meter`, `alert`, `badge` with text, `field`, `combobox`, `sheet`/`dialog`) plus two shared additions that `packages/ui` lacks: a native-file-input upload control (R13, already required by Phase 29) and a stage/task status pattern. No new component system, no embedded vendor importer UI (r09 build-vs-adopt; R11).

### 8.1 What the new evidence changes

1. **Staff-led conversion remains the norm for nonprofit CRMs (strengthened).** Virtuous (X14) and DonorPerfect (X15) describe specialist-run migrations; Neon has a separately named "assisted self-import" track (title only, 403). None publishes a self-serve readiness dashboard, freeze screen or reconciliation sign-off. This confirms §2.1 items 1 and 5: Asym's switch page would go beyond published nonprofit practice, so its design is judgment that must be proven by the moderated usability testing R9 already requires.
2. **Freeze before the final import is published nonprofit advice (new, X16).** Neon One's "pause any new manual data entry" plus an "untouched master copy" matches Option A's ministry-declared freeze and final export. It is advice, not a product control, consistent with g4 F4 (Asym cannot freeze SiteStacker).
3. **"Turn off notifications during import" is shipped commerce practice (X17).** Shopify tells merchants to switch off staff new-order emails while importing historical orders. Asym goes further by making imports outward-effect-dark by rule (R5), so the admin has nothing to switch off in Asym. The admin should still be told in plain words that nothing will be sent.
4. **Re-enrollment UX evidence is consistent but unmeasured.** WeGive (P12), Givebutter (P4, P5) and the church plans (M3, M10) agree on: imported plan details shown so the donor only adds a payment method; at least two reminders; personal follow-up; the old plan stopped by staff when the new one activates. None publishes completion rates. The only retention benchmark (M8, about 79% annual recurring retention) is the **baseline without a switch**; it does not measure switch loss.
5. **Attrition claims for forced re-authorization remain unsourced** (P7: 70-80% loss; P14: 20-30% drop). They agree that loss is material but differ roughly threefold, so neither is a planning number.
6. **Date-only gift dates are "floating" values (X19).** This supports §4.8: a gift dated on the freeze date cannot be ordered against a zoned freeze instant, so it is matched by source identity or reviewed.

## 12. Open founder questions raised by this track

1. **Who runs a switch:** the ministry's own admin with a self-serve workbench, Asym staff, a partner, or a mix? All nonprofit CRM evidence is staff-led (X11, X14, X15). This decides how much guidance the switch page needs and who signs off.
2. **Finance sign-off:** is a named ministry finance sign-off on the reconciliation report a required gate before go-live, and can the same person commit and sign off?
3. **Practice freshness:** how recent must the last practice run be before go/no-go (N days), and must it use the same export layout as the final export?
4. **Switch calendar:** should Asym advise against, or block, a freeze between mid-November and the year-end statement run?
5. **Attestation scope:** accept the wider go-live checklist in §9 (System Messages, declined-payment links, recurring reminders, text-to-give, per-missionary Mailchimp, PayPal subscriptions, SiteStacker statements, SiteStacker logins) in place of refinement (3)'s three items?
6. **Missionary role in re-authorization:** may missionaries see which of their partners still need to act before the deadline (privacy, Phase 16/28), and may they send the personal follow-up?
7. **Do-not-contact recurring donors:** when a re-authorization is needed and the consent gate blocks all email, does the gift simply end, or is there an owner-approved path (for example staff phone call)? Phase 30 must not decide this.
8. **Who sends donor communications about a processor move:** the ministry outside Asym, or Asym on the ministry's behalf through Phase 6/17 templates, and is that in the first release?
9. **Mobile scope for administrators:** confirm that freeze declaration, progress and sign-off must work on a phone, with heavy mapping allowed to be "easier on a larger screen".

## 14. Summary

1. **Repo rules already cover the per-file mechanics.** The ratified Phase 23 D29 rules (ADR-0173), currently scoped to CMS content, already give Phase 30 a strong pattern: a sealed plan, four issue classes, exact counts, truthful progress, partial outcomes, recovery after a closed browser and full accessibility (R6-R9). The roadmap requires the shared accessible grid and file controls and cause-owned next actions (R1, R2). What no owner text covers is the **switch as one thing**: readiness, the freeze moment, a finance sign-off, the go-live attestation and post-switch catch-ups (§4.1).
2. **A switch page with ordered stages is the right shape, but it is judgment.** No vendor publishes a whole-organization readiness dashboard. Microsoft's go-live checklist (X9) and GOV.UK's task list (X1) give the parts. Nonprofit CRM migrations are staff-led with unpublished procedures (X11, X14, X15), so Asym would go beyond published practice. Moderated usability testing (R9) is the proof.
3. **The finance lead needs a report tied to independent evidence.** Use per Legal Entity × currency tables against SiteStacker's own control totals, explicit exclusions, variance notes, a coverage statement, spot checks and a versioned, signed artifact (§4.5).
4. **Donors should notice nothing from the data move.** Imports are dark (R5, R15). Recurring donors are affected only by the processor handover, which Phase 16 owns. When tokens move or the same account continues, vendor docs say donors need do nothing (P1, P9, P13). Wallet and PayPal recurring cannot move and need re-authorization (P3, P4, P10). SiteStacker's PayPal subscriptions keep charging until cancelled in PayPal (`q01-r2`).
5. **Re-authorization UX has consistent practice but no measured outcomes.** Practice agrees on a prefilled one-purpose page, several reminders and personal follow-up (P12, M3, M10). Donor-loss figures (70-80%, 20-30%) are unsourced; the only solid benchmark is about 79% annual retention **without** a switch (M8).
6. **SiteStacker can still reach donors after the switch through more surfaces than refinement (3) names.** These include declined-payment links, recurring reminders, System Messages, text-to-give links, per-missionary Mailchimp, pre-login links, statement sends and SiteStacker logins (§9). The attestation should name each one.
7. **Missionaries face a live false-signal hazard.** Live code renders "Lapsed"/"At Risk" from a stored status, and schema defaults make imported partners look "joined today" (R19, R20). Both contradict the Phase 28 rules (R18). Coverage labels and "Status updating" for SiteStacker-charged gifts are required.
8. **Do-not-contact donors cannot be sent a re-authorization request** through Asym's shipped consent gate (UD5). This needs an owner ruling, not a Phase 30 workaround.

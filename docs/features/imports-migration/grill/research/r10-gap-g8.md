### 1.b The live `'import'` labels (r01 verifier finding), placed against Phase 2

- `packages/database/types/database.ts:39-40` reads `export type DonationSource = "direct" | "one_time" | "pledge" | "import" | string;`. The `| string` arm means the type constrains nothing. The column is `donations.source TEXT … DEFAULT 'direct'` (`supabase/migrations/20260214090000_foundation_1_schema.sql:301`, `:325`, `:338`), and no CHECK constraint was found.
- `packages/api/src/admin/contributions/model.ts:83` types `entryMethod: "api" | "manual" | "import"`. That is a three-value vocabulary that matches neither Phase 2's seven values nor Phase 13. At `:243-254`, `normalizeEntryMethod` maps `import` to `import`, `cash`/`check`/`bank_transfer` to `manual`, and **everything else, including the `'direct'` default, to `api`**.
- **Classification.** This is integrated legacy source. Phase 2 calls it "historical migration/removal evidence only" (`phase-02-…md:376-378`, `:702-704`), and Phase 13 drops `donations` in one atomic cutover (`phase-13-…md:573`, `:753`). It is not the Phase 2 `import` entry method. Its fallback to `api` breaks Phase 2's rule that unknown history maps to `legacy` (`:533`, `:549-550`): a row with no evidence is shown as an API gift. A retained-state census (`roadmap.md:4403`) should record any non-fixture `donations.source='import'` rows as candidate "explicitly proven `import`" evidence (`phase-02-…md:550`). Under Module 4 it should record every other value as `legacy`, never `api`.
- **No conflict with Phase 13's "no imported status".** Phase 13 D.6 says "there is **no special `imported` status enum**" (`phase-13-…md:1023-1026`). That rule concerns payment, posting and review _status_. Entry Method is an _attribution axis_ and is kept separate from gift type and status (`phase-02-…md:523`). An imported gift therefore has status "already-succeeded"/"posted" like any other gift, plus `entry_method='import'` (or `legacy`) as provenance. r01's question resolves by layering, not by choosing one rule over the other: the label lives on the attribution axis, never in the lifecycle.
- **Stale ticket text.** Issue #484's body still says "Repurpose `donations.source` into an entry-method enum … Lossless backfill … preserve any existing `import`" (gh issue view 484, body lines 3, 9 and 20). The amended PRD has since moved target ownership to the Phase 13/15/16 contracts and made `donations.source` removal evidence only (`phase-02-…md:376-378`, `:546-551`, `:702-704`). ### 2.2 What this means for SiteStacker source codes (fact vs owner choice)

- **SiteStacker fact (verified 2026-11-01).** The SiteStacker article [How to setup & use Contribution Source Codes](https://training.sitestacker.com/support/solutions/articles/151000115117-how-to-setup-use-contribution-source-codes) (modified 6 Oct 2023) says codes sit in categories, each has a Name and a short one-word Code, "?t=" applies the code to the transaction and "?c=" applies it to designations, and "Source Codes are session-based". The article says nothing about import or export. Historic Giving rows carry a `source_codes` column (`r07-sitestacker-sources.md:164`), and the Transaction View export should carry a source-code column (`r07:312`, an unverified expectation).
- **Noteworthy repo fact.** Phase 2's capture allowlist starts with `t` and `c` (`phase-02-…md:534`, story 21), the same parameter names SiteStacker uses. Phase 13 keeps them on the allowlist next to the canonical `?sc=` (`phase-13-…md:1606`, `:1616`). A legacy SiteStacker link carrying `?t=CODE` that reaches a Core public route would be captured as a raw value and match-or-null resolved against the registry. That works only if the path itself resolves (see §3) and only if query attribution survives the redirect step. Phase 22 D8 says "Redirect responses drop query strings and fragments by default. Only allowlisted, revalidated, non-routing attribution may survive" (`phase-22-public-ministry-pages-decision-log.md:1392-1395`).
- **Release 2.49 source-code import (snippet-only).** A search snippet from help.sitestacker.com, "Site Stacker Release 2.49" (Core Setup - Internal Release Documentation, dated 13/04/2026), lists under Contributions an added ability to import source codes, under Sites an ability to import redirects, and a fix to campaign data not saving when updated through the import component. A direct fetch failed again on 2026-11-01: WebFetch returned `TLSV1_ALERT_UNRECOGNIZED_NAME` and curl returned `SEC_E_ILLEGAL_MESSAGE` (HTTP gives 301 to HTTPS). **Unverified.** Even if accurate, this is a SiteStacker _import_ feature. It shows source codes are a first-class SiteStacker object a tenant may have bulk-loaded. It does not show they can be _exported_. The kit still needs a Source Codes grid or report export (`r07:316`, checklist item 16).
- **Reading that resolves the apparent conflict** (established by text, not yet owner-confirmed). Phase 2 story 39, A6 and Module 4 set `source_code = null` as the honest default _when no source evidence exists_. The rule exists to stop "fake precision" (`phase-02-…md:204-206`) and "fabricating attribution" (`:551`). Phase 13 D14 then supplies a registry and a mandatory seed/bulk-import path, so an evidenced legacy code (a code present on the source gift row) can be carried as a registry entry. OA-08 adds a third state Phase 2 never named: **unknown legacy coverage**, as distinct from **known absence** ("no code was applied"). A bare `source_code_id = NULL` cannot tell these apart, and Phase 13 reports NULL as "Unknown / Direct" (`:1613`). That label merges exactly the two states OA-08 says must stay separate.
- **Owner questions, not Phase 30 choices.** (a) Does an evidenced SiteStacker source code become a P13 registry row, created through the D14 seed/bulk-import path, probably `retired` so it cannot be chosen for new links? Or does it stay import provenance only, with `source_code_id = NULL`? Phase 2's literal text says null; Phase 13 D14 and OA-08 allow evidence. **P13 owns this.** (b) Where does P13 record "unknown legacy coverage" versus "known no code" on an imported line, given NULL alone cannot carry it? (c) Does the D14 seed/bulk-import path count as the Phase 30 import target for codes, or is it a separate P13 bootstrap? Phase 30's role is limited to transport and staging (`roadmap.md:4377`).
- **SiteStacker's two-level codes.** SiteStacker can put one code on the transaction (`?t=`) and another on each designation (`?c=`). Phase 13 freezes `source_code_id` **per designation line** (`phase-13-…md:578`, story 202; `:1608`). A transaction-level code with no designation code has no transaction-level home in P13. Mapping it onto every line is a defensible owner rule, but nothing ratifies it. **P13 must rule.**

### 3.3 Consequences for Phase 30 (derived from the clauses above; not separately ratified)

1. **An import can never create an Issued Giving Address.** Issuance happens only through the authorized human public-publish command (D11-R18, D10-R3). A SiteStacker giving URL was never "exposed" by Core, so it fails D10-R1's definition and is not a D10-R19 backfill candidate. D10-R19 backfills only addresses _Core_ issued and inventories Core's own route families (`/give`, `/donate`, `/checkout`, short/QR links) at `:518-519`. Phase 30 may bring giving-page _content_ in only as private drafts (Phase 23 D29, `phase-23-web-studio-cms.md:799-821`; `roadmap.md:4379`). Under D11-R6 such drafts reserve nothing, and staff must publish and issue each address. D14 adds that every Giving-enabled locale needs its own issued address.
2. **An import cannot burn, release or stop addresses** (D10 accepted, D11 footgun, D12-R11). A migration that loaded thousands of legacy slugs as reservations would be the "bulk-burn" the clauses forbid.
3. **A legacy SiteStacker giving URL survives only by one of three routes, none of them automatic:**
   - (a) **Same path re-issued by a human.** If the legacy path happens to be `/give/{slug}` on an origin Core now serves, staff may type that slug when publishing (D11 standard shape `{verified-site-public-base}/give/{staff-chosen-slug}`, `decision-log:1541-1545`). Any other legacy shape (for example a SiteStacker content-item alias path) cannot be re-issued as a Giving address.
   - (b) **Exact ordinary-Page or ministry-page continuity.** Phase 23 D3 / ADR-0147 (Accepted, founder-ratified 2026-08-15) allows "one exact unused historical path" bound to "one eligible ordinary Page in the same Site and locale" and states that "Phase 30 only transports exact legacy mappings through the same validator" (`docs/adr/0147-generation-bound-automatic-ordinary-page-route-continuity.md:3`, `:33-46`). It excludes a "reserved application path, or Phase-22-owned route". The research evidence adds "Phase 30 may stage large exact legacy mappings, but they pass through the same D1–D2 validation and release contract" (`phase-23-d3-ordinary-page-route-continuity-research-evidence.md:253-254`). Missionary and project giving pages are Phase 22 Page Families. Their legacy routes go through Phase 22 D8 (Ratified 2026-08-04), whose migration clause says "Only exact, reviewed, collision-free mappings enter production-shaped shadow resolution; no legacy page is inferred public … and no history is fabricated" (`phase-22-public-ministry-pages-decision-log.md:1247-1249`, `:1447-1451`). r04 already recorded the Phase 23 transport-only seam (`r04-files-content-comms-workflow.md:115`).
   - (c) **Not carried.** The legacy URL returns Core's neutral not-found, and the tenant must distribute new links or QR codes. D10's founder answer accepted this cost for Core-issued addresses ("A successor must create and distribute a new Giving URL", `phase-24-d10-…md:7-8`).
4. **Query-string attribution on legacy links.** D10-R2 excludes query strings from address identity (`phase-24-d10-…md:103-108`). Phase 22 D8 drops queries on redirect except "allowlisted, revalidated, non-routing attribution" (`phase-22-…-decision-log.md:1392-1395`). ADR-0147 preserves incoming query parameters on ordinary-Page continuity responses but never lets them route (`:39-41`). A SiteStacker `?t=`/`?c=` code can therefore survive only through (b), and only if the Phase 22 allowlist includes those parameters. **Not specified anywhere; owner question for Phase 22/P13.**
5. **Redirect imports are not a Phase 30 authority.** The SiteStacker Release 2.49 snippet "import redirects" (§2.2, unverified) and the per-Site-Channel "Redirects" tab (`r07:279`; [How To Redirect a URL](https://training.sitestacker.com/support/solutions/articles/151000114986-how-to-redirect-a-url)) tell the kit where to find a legacy redirect inventory. In Core, every such row needs exactly one typed disposition: an exact ordinary-Page continuity candidate (Phase 23 D3), a Phase 22 D8 case, a Giving item (human re-issue only), an exclusion, or quarantine. Wildcards, external targets and chains are rejected (ADR-0147 `:35-38`, `:51-53`; D3 evidence `:358-359`).

### 3.4 Gap in the predecessor contracts

No owner has decided whether a **migration-time legacy giving URL inventory** may enter Core at all, and if so as what. Two readings exist: as adverse "never reuse" evidence (D10-R19's "quarantine ambiguous legacy collisions" applies only to Core's own pre-existing routes), or only as a staff worklist that feeds human issuance. ## 4. Multi-site SiteStacker tenants: Site to Legal Entity, Site to currency, and the imported gift's Site

### 4.1 There is no Site-to-Legal-Entity mapping to assert (ratified owner intent)

The question "who asserts Site to Legal Entity" (`r07:380`) assumes Asym keeps such a mapping. Asym does not, and must not:

| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------- |
| 4.1.1 | Phase 24 D1, founder answer "Ratified": "Site identity never owns or selects Legal Entity, Stripe, settlement, bank, or accounting identity." "Site as Tenant or Legal Entity" is listed as a rejected alternative. | `phase-24-multi-site-management-decision-log.md:45`, `:67-71`, `:107-109` | ratified owner intent                          |
| 4.1.2 | Glossary: "Sites may present a Legal Entity but never define one. _Avoid_: one entity per Site or fund … the Tenant default as historical or runtime ownership". The Site entry says the same.                      | `CONTEXT.md:6780-6792`; `:197-208`                                        | published glossary                             |
| 4.1.3 | Phase 2 A2: a second Legal Entity "must not silently split a cart, change an old gift, or follow a Site boundary"; "persistence never falls back to a mutable tenant default".                                      | `phase-02-…md:243-258`                                                    | published spec                                 |
| 4.1.4 | Phase 30 retained obligation: "Every imported financial root also pins exact Tenant, Legal Entity, currency, source system, and stable external ID. | 4.1.5 | Phase 13: `legal_issuer_id` is "server-resolved from the verified legal-issuer authority, never caller input".                                                                                                      | `phase-13-…md:1738`                                                       | ratified owner intent                          |
| 4.1.6 | Phase 24 migration: "Unknown or ambiguous historical facts quarantine; they are never inferred from current default, title, URL text, traffic, country, currency, provider, or majority use."                       | `phase-24-multi-site-management.md:495-497`                               | published spec                                 |
| 4.1.7 | SiteStacker documents no Legal Entity concept and has no Legal Entity column in Historic Giving.                                                                                                                    | `r07-sitestacker-sources.md:170`; verifier V5 at `:421`                   | verified vendor-doc absence (r07)              |

**Established fact.** For a multi-site SiteStacker tenant, the import must pin Legal Entity **per financial root from evidence**, not per Site. Because SiteStacker carries no Legal Entity, that evidence must come from outside the SiteStacker export. Candidates include the processor or merchant account that took the money, the bank account it settled to, the issuer named on the historical receipt, and the organization's books. All are tenant-supplied.

**Who decides the evidence standard.** Legal Entity is "Phase 7 canonical; consumed by source phases and Phase 20" (`CONTEXT.md:6780`). Phase 13 owns contribution issuer resolution (4.1.5), Phase 20 owns posting-ownership cutover (`phase-13-…md:1035-1038`), and Phase 21 D17 owns the Tenant × Legal Entity × currency opening cohorts (`r00-index.md:239`). The Phase 30 chapter defers explicitly: "Any uncertainty in historic finance … is decided by its existing owner, not by this transport phase" (`roadmap.md:4409`). **Phase 30 consumes the rule; it does not define it.**

**Unresolved predecessor gap (owner, not founder-product).** Phase 13 D.6 (`:1023-1039`) never says how `legal_issuer_id` is resolved for an _imported_ gift. The "never caller input" rule (4.1.5) has no import variant. Two questions follow. (a) May a reviewed, evidenced _source-cohort assertion_ (for example, "all rows settled through processor account A belong to Legal Entity Z") count as the "verified legal-issuer authority"? (b) Is a cohort keyed by a SiteStacker `site_id` an acceptable explicit assertion, or the inference from Site that `owner-constraints.md:376` forbids? The text supports reading (a) as allowed, provided the assertion is explicit, evidenced and reviewer-accepted per cohort. It does not settle (b). **Owners: P7 (Legal Entity), P13 (issuer resolution on contributions), P20 (cutover).**

**One-entity tenants.** Under Phase 2 A2 the seeded default "prefills setup, but persistence never falls back to a mutable tenant default". The glossary rejects "the Tenant default as historical … ownership". The consistent reading is that an import plan may _preselect_ the sole Legal Entity, but each financial root stores an explicitly accepted Legal Entity. A silent default is not allowed (derived; owner confirmation needed).

### 4.2 There is no Site-to-currency mapping either

- Site currency facets cover only presentment for _new_ giving intent and reporting display: a Site "owns one explicit default and a bounded enabled Donor Presentment Currency ceiling for new giving intent" (Phase 24 D61 clarification in `phase-02-…md:270-282`), and `sites.reporting_currency` "remains a display/reporting preference" (`:682-683`). Neither is evidence of a historical gift's currency. `owner-constraints.md:375-377` forbids inferring the currency of an imported financial root from Site, and Phase 24's migration rule forbids inference from "currency" or "current default" (4.1.6).
- Imported currency is therefore **per-row evidence**. Historic Giving rows carry `currency` ("USD or CAD", `r07:164`). The Contributions grid export columns are undocumented (`r07:186`, `:365`). Where a row has no currency column, the same owner question as for Legal Entity applies: a cohort-level evidenced assertion, or quarantine.
- Reconciliation is "by Legal Entity, original currency and source basis", never one converted scalar (`roadmap.md:4369`; `owner-constraints.md:434-437`).
- **Implemented support.** Currency validation and minor-unit parsing exist: `packages/api/src/money/index.ts:22` (`minorUnitExponent`), `:33` (`parseMoneyToMinorUnits`), `:57` (`formatMoney`), `:85` (`assertTransactable`), mirrored to `public.currency_metadata` (migration `20261003051630`; #480 CLOSED). These are the only Phase 2 primitives on `develop` that an importer could use today. `assertTransactable` restricts _new_ transactions to the settlement currency (`phase-02-…md:404-406`). A historical import must not run through it as if the gift were a new transaction. Which validator applies to historical currency is a P13 question; my reading is ISO validity plus exponent, without transactability.

### 4.3 The imported gift's own Site attribution ("where")

- **Phase 2 says** `site_id` is `NOT NULL` with a default-Site default (story 36, A6), and its test list includes "default-site assignment for portal/offline/import" (`phase-02-…md:811`). Issue #484 repeats this in its body (lines 25-26).
- **Phase 24 D4 (ratified) overrides that for historical records.** The recommendation reads: "Production public requests, checkout, callbacks, and historic records must always carry or resolve an exact Site. They never fall back to the Default Site." The adversarial result reads: "The main residual risk is developers using Default Site to fill a missing required `site_id`. Structural contracts and negative tests must reject that in public, money, provider, and historical paths." Rejected alternatives include "Using Default Site to repair nullable or invalid Site ownership". Its affected contracts list "Phase 2 default-Site provisioning and provisional resolver language" (`phase-24-multi-site-management-decision-log.md:404-405`, `:412-415`, `:438-442`, `:447`, `:449-455`). The "Current evidence" section adds: "Migration evidence assigns existing data explicitly rather than relying on a permanent runtime default" (`:467-468`).
- **Consequence (derived).** An imported gift's Site must come from an explicit mapping of SiteStacker `site_id`/`site_channel_id` to an Asym Site (Phase 2 A1 treats Asym Site as roughly a SiteStacker site channel, `phase-02-…md:217-218`, `:773-774`). It must never come from the default. The Phase 2 Module 3 test line and #484 conflict with D4 on this point, and Phase 2 records no D4 amendment (grep for "D4" in the Phase 2 PRD finds none).
- **Owner questions (P13 attribution plus P24 Site lifecycle):**
  - (a) If a tenant folds several SiteStacker site channels into one Asym Site, does the import keep the source channel as provenance, so "where" is not overstated?
  - (b) May staff create a private, never-public Asym Site, or retire one, purely to hold attribution for a SiteStacker site that is not carried forward? D5 (new Site starts private and inert) and D8 (retirement is permanent; history survives) make this possible, but no decision addresses it.
  - (c) A row with no Site evidence cannot be committed, because Phase 2 forbids a "no site" row and D4 forbids defaulting. It must therefore quarantine. Should the kit treat that as a blocking exception class?
- **This is not Legal Entity.** A Site mapping is attribution only. Even when several SiteStacker sites map one-to-one to Asym Sites, the Legal Entity for each gift is still resolved under §4.1.

## Resolution

**Mostly resolved.** The predecessor rules decide most of the gap, and Phase 30 should consume them, not invent them:

- Imported gifts carry `entry_method = import` (or `legacy` when entry is unknown) as an **attribution axis**, with no special status (Phase 2 A5/Module 3, Phase 13 D.6). The live `'import'` labels are legacy removal evidence, and their `api` fallback must not count as census evidence.
- Site, Legal Entity and currency are **independent**. Asym keeps no Site-to-Legal-Entity or Site-to-currency mapping to assert (Phase 24 D1, Phase 2 A2, `CONTEXT.md:6787`, `owner-constraints.md:373-377`). Each imported financial root pins Legal Entity and original currency from evidence, and each gift's Site comes from an explicit source-site mapping, never the Default Site (Phase 24 D4).
- An import can never issue, release, stop or bulk-burn a Giving address (D10, D11-R6/R18, D12-R11, D14). Legacy SiteStacker giving URLs survive only through human re-issue of a matching `/give/{slug}`, or through exact, validated Phase 23 D3 / Phase 22 D8 page-continuity mappings that Phase 30 merely transports. Otherwise they are not carried.
- Imported content locale maps exactly to an enabled Site Locale with no default guessing (ADR-0173 clause 24). Translated imports land as "Legacy · source unclassified".

**Remains open:** five owner rulings and two founder choices (§7). Implementation of every Phase 2 attribution primitive and every Phase 24 Giving-address primitive is absent at `629cb71dc` (§1a, §3.1). Only `currency_metadata` and the money helpers exist.

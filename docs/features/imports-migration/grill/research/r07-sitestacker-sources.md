### 1.1 Import Tool Overview (S1) — verified facts

- Bulk import is CSV only; templates live in the Imports component **Documentation** tab; required columns are bold; each file needs a heading row. (S1, verified)
- **The file-name number is the mapping key** (example "12. Person"); text after the period is free. S4 repeats: "DO NOT change the number in the import file template" because SiteStacker uses it to map the import. (S1, S4, verified)
- Flow: upload in Imports tab → right-click → run import in background → check result → "show errors" on failure. (S1, verified)
- All-or-nothing per file: "Should an error be made while importing, the entire import will fail as a safety protocol." (S1, verified quote)
- Rollback: right-click a successful import → rollback, "which will delete the data in that import." (S1, verified quote). The article does not say rollback restores before-images of updated rows, or how rollback treats records later edited/merged. (unverified / not documented)
- Size: "Keep files at a reasonable size not more than 25,000 lines in the event there are errors or a rollback is required." (S1, verified quote)
- Excel strips leading zeros (ZIP). Content without a template needs an **Architect > Data Maps** data map. Image imports need the File Manager path after upload. (S1, verified)
- **Side effects:** "System messages will not be sent based on import like address update" **and** "Spark automation will be triggered and could have emails triggered on both import and rollback." (S1, verified quotes)
- S1 is silent on required permissions, matching/duplicate logic, create-vs-update semantics and relationships. (verified absence in S1 only)

### 1.3 Importing CRM Records (S2) — verified facts

- Path: Import component **under Data Tools** → Documentation tab → select templates → "Download Selected". (S2)
- Mandatory order: "it is required that you must start at the very top and work your way down to the bottom of this documentation!" Order: CRM Person → Address → Phone → Photo → Activities (+ Activity People) → Note → File → Entities → Record Types → Relationships. (S2, verified quote + order)
- Person: required `firstname`, `lastname`; optional `title`, `middlename`, `nickname`, `maidenname`, `suffix`, `gender` (m/f/blank), `birthday` (Y-m-d), `email`, `description`. (S2)
- **Email uniqueness:** "This must be unique as Site Stacker does not allow duplicate emails." (S2, verified quote) — consequence: a shared couple/household email cannot sit on two Person rows (inferred; a real export is needed to see how customers worked around it).
- **External ID is the join key:** "The External ID is the 'connecting piece' to associate data imports to a CRM." It can hold an account, donor or missionary ID. (S2, verified quote)
- Household columns on Person: `household_id`, `household_name` (defaults to full name), `household_external_id`, `is_household_head` (0/1); `household_id` blank → "it will create its own household." (S2, verified quote)
- Sub-records link via `external_person_id` + `external_person_is_group` (Person vs CRM Group). Address: required `address1`, `city`; `country_code`/`state_code` must be valid codes; lat/long auto-geocoded if blank; do not delete Geo Location columns. Phone: required `number`; `is_outside_us`, `area_code` (derived if blank). Photo: path to a File Manager file uploaded first. Activities (Chat/Conversation/Email/Phone Call/Text/Social Media share one template): required `subject`, `external_person_id`; `date`, `body`, `from_external_person_id`; plus an "Activity People" link file (`external_activity_id`, `external_person_id`). Note: required `body`, `external_person_id`; `type`, `subject`, `important`, `external_from_person_id`. File: required `import_path` (from "Import - Secure File Uploads"); `label`. (S2)
- Entities (custom fields): entity groups/entities/fields must be created in CRM Configuration first; the template "is only available after entities exist"; one column per entity field keyed by `external_person_id`. (S2)
- Record Types: created first in CRM Configuration (Person Type / Group Type / Both). "We also use Record Types to trigger an event into Spark or Motion 2." (S2, verified quote)
- **Donor warning (verified quote):** "IMPORTANT: If you are importing the Donor record type, please make sure that you DISABLE the Spark Events labeled:" (Person Type Assignment where type = Donor; Person Type Unassigned; Person Assigned to Workflow where Workflow = Donor Management and role = Donor; Person Type Assignment) "... before you do so! If you do not, then this will create a HUGE mess so please do this!"
- Relationships: relationship type created first (label, opposite label, person/group membership, alias); required `external_person_id`, `external_person_is_group`, `related_external_person_id`, `related_external_person_is_group`; optional `description`. (S2)
- **Not documented in S2:** create-vs-update behavior when a Person with the same `external_id` or email already exists; organizations as a separate type (organizations appear to be CRM **Groups** — inferred from `external_person_is_group` and Historic Giving `donor_type = group`); donations and pledges (covered elsewhere). (verified absence)

### 4.2 Matching and duplicates

- Linking is purely by **external ID** (person, group, campaign, batch, transaction, data-group value). (verified)

### 4.3 Rollback

- Per-file, all-or-nothing import ("the entire import will fail as a safety protocol"); rollback of a successful import "will delete the data in that import". (verified quotes, S1)
- Not documented: before-image restoration for updated rows, behavior after later staff edits or merges, cascade to dependent imports (e.g. rolling back Person after Relationships were imported), or effects on gifts. (verified absence)
- The vendor's mitigation is operational: keep files under 25,000 lines and test a small sample first. (verified)
- **Implication for Asym (inferred, binding by repo rule):** SiteStacker's model — delete everything the batch created — is the exact hazard Asym's owner text forbids: "Reversal must not delete a real Party after merge, erase later staff edits or rewind financial history" (roadmap.md:4371) and "The undo-after-merge hazard ... is explicitly blocked" (owner-constraints.md:384-385). The kit should not offer a SiteStacker-style "rollback this file".

### 4.4 Documented side effects (the key finding for batch-origin suppression)

Verified official statements:

1. "System messages will not be sent based on import like address update" — S1 (Sep 2023).
2. "Spark automation will be triggered and could have emails triggered on both import and rollback." — S1.
3. Record Types are used "to trigger an event into Spark or Motion 2." — S2.
4. Before importing the Donor record type, staff must "DISABLE the Spark Events" (Person Type Assignment, Person Type Unassigned, Person Assigned to Workflow / Donor Management) or "this will create a HUGE mess". — S2.
5. Child sponsorship: "Due to the rich automation features in Site Stacker, child records must be imported in a careful manner" and afterwards "check the Active boxes of any Spark events that you previously disabled so that they can function correctly." — Child Sponsorship Data Import Outline (Mar 2024).
6. Data Migration Plan: "Before importing data into Site Stacker, make sure that all the System Messages are disabled" (to avoid emailing Site Stacker users). — S4 (2020 footer).
7. "An outcome can send messages, add users to groups, cancel contributions, and more." ([Outcome (Spark)](https://training.sitestacker.com/support/solutions/articles/151000098602-outcome-spark-), Sep 2023, verified quote); Spark events can trigger "assigning tasks in Motion 2" or "changing record types" ([Event](https://training.sitestacker.com/support/solutions/articles/151000101374-event), Sep 2023, verified). Spark Message is itself a System Message type ([Understanding System Messages](https://training.sitestacker.com/support/solutions/articles/151000122018-understanding-system-messages), verified).
8. Mailchimp sync is SiteStacker → Mailchimp, and "Record Type" changes in SiteStacker appear on the Mailchimp record. (verified, Mailchimp article)

**Why suppressing only the importer's own emails is insufficient (documented, not speculative):**

- SiteStacker's importer _does_ suppress its own direct system messages (item 1), yet the vendor still documents email and data side effects, because **the effects come from downstream event consumers** (Spark events, Motion 2 workflows) reacting to the _data changes_ the import makes — record-type assignment, workflow assignment, contribution creation — not from the importer itself (items 2-5).
- **Rollback is a second side-effect source**: deleting imported rows fires the same automation ("on both import and rollback", item 2). An undo path that is not origin-tagged re-creates the problem.
- Effects are **not only emails**: Spark can change record types, assign workflow tasks, add users to groups and cancel contributions (item 7, verified), and record-type changes propagate to an external system (Mailchimp, item 8, verified) — an outward effect with no email involved. That an _import_ specifically triggers the Mailchimp propagation is inferred, not documented.
- The vendor's mitigation is **tenant-global, manual and reversible-by-memory**: disable named Spark events (and all System Messages) before the import and remember to re-tick "Active" afterwards (items 4-6). During that window live donors on the same tenant also lose automation, and a forgotten re-enable silently breaks production; a forgotten disable spams. The docs even disagree on whether System Messages need disabling (items 1 vs 6).

**Asym implication (inferred; aligns with existing binding text):** batch-origin suppression must be a property of the _origin_ carried on every domain event and honored by every consumer (automations/journeys, receipts/acknowledgments, first-gift and welcome triggers, account/user grants, external sync such as email-provider audiences, webhooks, notifications, search/public projections) — including events produced by reversal/undo — rather than a global toggle or an importer-only mail switch. Existing repo anchors: owner-constraints.md:386-388 ("batch-origin event suppression (an import must not fan out ten thousand automation emails)"), roadmap.md:4365 ("Historic data stays outward-effect-dark: no mass welcome, first-gift trigger, account grant or new receipt"), roadmap.md:4395 ("No ... mass outward replay"), CONTEXT.md:4679-4684 (Phase 15 Send-acknowledgments gate: "Imports stay `held`; nothing auto-sends").

## 7. Evidence checklist — artifacts Asym needs from a real SiteStacker customer

Each item says why it is needed and what only it can answer. "Needs a real export" applies to every item. Ask the customer to export with an administrator whose User Group has unrestricted CRM, Entity, Contributions, Historic Giving and Reports access, and to record that group.

**A. Installation census (before any export)**

1. Site Stacker release/version and installed components (System Manager) — features are version-gated per installation.
2. Sites and Site Channels: IDs, names, domains, languages; the customer's written assertion of Site → Legal Entity and Site → currency(ies). (SiteStacker documents no Legal Entity; owner-constraints.md:373-377 forbids inference.)
3. UI control counts captured at export time: CRM People, CRM Groups, households, Contributions transactions/designations/recurring schedules (by status), batches, Historic Giving rows (by `record_type`), newsletter lists and subscribers, content items per folder/type, File Manager files, users.
4. Exporting user's User Group and its CRM/Entity/component permissions (to detect permission-filtered partial exports).
5. Inventory of active Spark events, Motion 2 workflows, System Messages and Mailchimp settings (census of automations the tenant relies on — not data to import).

Handling: treat SiteStacker as having no reliable import-side suppression; do not model Asym on either; and when censusing a tenant, expect historic data to contain side effects of earlier imports (e.g. automation-assigned record types).
2. **Currency:** sitestacker.com claims "150+ international currencies through one checkout"; the Historic Giving import template documents `currency` as "USD or CAD"; the Contributions export columns are undocumented. Handling: treat training docs as possibly stale; re-verify against help.sitestacker.com before grooming locks presets.

A SiteStacker unsubscribe also needs to be treated as separate evidence from Mailchimp status.

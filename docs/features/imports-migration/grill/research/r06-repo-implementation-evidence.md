## 12. Synthesis

### What an importer can reuse (durable patterns)

1. `csvSafeCell` and CRLF/BOM constants for every annotated download (`packages/lib/csv.ts`; ADR-0212).
2. The workflow dispatch ledger, identifier-only envelope, tenant-keyed concurrency, guarded work claims and recovery scans (`packages/api/src/workflows/*`; `openspec/specs/workflow-orchestration/spec.md`).
3. The tenant guard (`withTenant`) for no-JWT work, plus the CI-enforced RLS catalog, deny-by-default list and service-role gate (`docs/security/tenant-guard.md`).
4. Tenant-scoped idempotency keys with unique constraints and advisory locks (donation saga, ledger).
5. The canonical `public.normalize_email` and generated identity keys on `donors`.
6. Composite tenant FKs, ENABLE+FORCE RLS on new tables.
7. Real-stack PG17 acceptance tests in the CI `migrate` job; Playwright + axe; `@inngest/test`.
8. TanStack Table v9 shared data-table and the code-authoritative capability registry (for new `imports.*` atoms).

### Useful precedents (adapt, do not copy)

Contribution bulk batches (preview → persisted items → chunk CAS claim → per-row outcomes → follow-up tasks → re-authorize every chunk); offline-gift orchestration seam; document-cutover counts-only census; CRM report export (audited, tenant-scoped); custom editable `DataGrid`; duplicate scorer's rules/actions split; Eve private bucket + short signed URLs; image upload magic-byte checks; `ServiceAccountPrincipal` typing.

### Temporary bridges / accidents / conflicts to avoid

- Browser `donors` insert in `packages/missionary/components/add-partner-dialog.tsx:73-74` and unused `findOrCreateDonor` (`packages/api/src/donate/queries.ts:12-50`).
- Second email normalizer, US-default phone and `USD` default currency in `packages/api/src/crm/mapping/normalize.ts`; `donations.tenant_id` default tenant and `'usd'` defaults in migrations.
- `donations.source = 'import'` display label as pseudo-provenance.
- Two parallel donor matching vocabularies and unconsumed `donor_merge_*` tables.
- Twenty-shaped `crm_record_links`/`crm_merge_candidates` as an external-ID store.
- Denormalized `donors.total_given`/`last_gift_*` and `donor_pledges.total_paid` scalars as import targets.
- Contribution batches' browser-driven loop on the service-role client as the import executor.
- Public-bucket upload primitives for import files.
- Payload's generic import/export plugin (not installed; vendored copy is v3.77.0 vs installed v4.0.0-beta.3; rejected by ADR-0173).

### Readiness facts (what does not exist)

No parser library, no parser code, no import tables, no Party/Household/Organization/Relationship/custom-field targets, no historic gift or commitment command (offline gift returns 501), no Legal Entity column, no external-ID/source-system columns, no private import-file custody, no malware scanning, no Data Tools route/nav/capability, no stepper/wizard or generic file control, no live outward fan-out (so no suppression flag yet), and no mechanism for a background job to carry a human actor's authority.

### Discrepancies

1. **Parser ownership.** `owner-constraints.md:395-397` gives Phase 30 "replaceable parsing, mapping mechanics, chunked resumable staging, and review mechanics"; Ready Phase 28 tickets #2347 / #2087 / #2352 specify the reader, planner and XLSX handling under Phase 28 in `packages/lib/import/text/**`. Recommended handling: have Phase 30 adopt that module as the single shared parser/plan contract (one parser, profile-parameterized) rather than publish a second one.
2. **Two email normalizers.** DB `public.normalize_email` (NFKC) vs TS `normalizeEmail` (trim/lowercase) in `packages/api/src/crm/mapping/normalize.ts:1-6`. Use the DB function as the only identity key producer.
3. **Two matching vocabularies.** `crm/mapping/duplicates.ts` + `public-giving/donor-match.ts` vs `donate/guest/donor-matching.ts` + `donor-merge.ts`. The Phase 4 identity owner must name one rule set before imports consume it.
4. **Inferred defaults vs "none is inferred".** `donations.tenant_id DEFAULT '0000...0001'` and `currency DEFAULT 'usd'` (`20250101000000_init_schema.sql:177,182`), `begin_donation_saga(p_currency DEFAULT 'usd')`, `normalizeCurrency` → `USD`, vs `owner-constraints.md:373-377`.
5. **Executor and client.** Owner wants Inngest background processing (`owner-constraints.md:386-388`) and recovery after a closed browser (`roadmap.md:4387`); the closest precedent (contribution batches) is browser-driven on the service-role client, and the service-role gate forbids new such sites without a security ruling (`docs/security/tenant-guard.md:232-239`).
6. **Tenant guard vs authority.** `docs/security/tenant-guard.md:3,82` requires Inngest jobs to use `withTenant`; proposed Phase 29 spec says "a client setting, service token or workflow tenant guard is not authority" (PR #2430 spec `:3043`). Treat the guard as isolation only and re-prove actor authority separately.
7. **"Use the shared accessible grid and file controls"** (`roadmap.md:4389`) — no shared file control exists; the shared editable grid has no consumer and no qualification.
8. **Payload sources.** Vendored upstream is 3.77.0 (`vendor/payload-upstream/packages/payload/package.json:3`); installed is 4.0.0-beta.3.
9. **CSV round trip.** `csvSafeCell` prefixes `'` (including on negative numbers); annotated error files re-uploaded would carry that prefix into the parser.
10. **Legacy shared emails vs `donors_tenant_email_normalized_uidx`.** A legacy file with two people at one email cannot land as two `donors` rows.

### Open founder questions (product choices)

1. Should Phase 30 make the Phase 28 `packages/lib/import/text` reader/plan (#2347) and XLSX reader (#2087) the one shared engine for every profile, including staff migration and SiteStacker?
2. Native build vs embedded importer (Flatfile/OneSchema/Dromo): is any vendor-hosted processing of imported PII acceptable, given Phase 29's least-privilege, no-external-submission parser rule and the owner's "imported PII never leaves its governed boundary"?
3. How should corrected error files round-trip: strip the formula-escape `'` on re-upload, or issue corrections as XLSX/another format?
4. When a background import commits, whose authority does each chunk run under: the committing staff member re-proved per chunk, or a delegated service-account principal bound to that person's assignment — and what happens to an in-flight import when that person loses access?
5. Is the first "low-risk source-to-Party import" allowed to target the legacy `donors` model, or does Phase 30 wait for the Phase 9 Party target?
6. Who may run staff imports: all staff (today every staff subrole has identical capabilities) or a dedicated data-steward capability? Where does Data Tools sit in Mission Control navigation?
7. For legacy households sharing one email, what should the first profile do: one record, separate records with a held duplicate, or quarantine for decision?

### Missed items (within the code-evidence track)

- **M1. #2347 uses fixed limits and leaves plan storage to #2083.** Its acceptance bounds are fixed values, each accepted at its limit and rejected one over: 10,000 rows, 500,000 slots, 32,768-byte cells and 16,384 columns (body line 22). A staff or SiteStacker migration will routinely exceed 10,000 rows, so "adopt #2347 as the single engine" also requires the bounds to be set per profile. Plan storage, superseded marking, review commands and their tenant-guard `GUARDED_RPCS` were moved to #2083 by ruling, with migration `20261025210000` reserved (body lines 49 and 65). Phase 28 therefore already plans a staging and plan store built on guarded RPCs, which overlaps Phase 30's "staging, plans" ownership (`roadmap.md:4377`) as well as parsing.
- **M2. ADR-0212's export policy, not just `csvSafeCell`, governs annotated error downloads and templates.** The Decision makes `exportable` authoritative and says "serializers ... cannot grant export from visibility alone". It also says CSV and JSON "share authorization, row scope and identifiers-only audit of actual emitted rows". Error files echo uploaded PII back to the user, so they are exports under this policy and need field-policy resolution plus emitted-row audit. The client-side `packages/ui` data-table CSV download (digest §1.2) is not a compliant precedent for them.
- **M3. More inferred `donations` defaults that a historic-gift import could hit.** `20260214090000_foundation_1_schema.sql:333-338` sets `gift_date NOT NULL DEFAULT CURRENT_DATE` and `source DEFAULT 'direct'`, besides currency `NOT NULL DEFAULT 'usd'`. A historic row that omits a date would silently become today's gift. That contradicts `roadmap.md:4395` ("A source event marked historical cannot become prospective by changing a displayed timestamp"). Separately, the contribution-batch browser loop is capped at `MAX_CONTRIBUTION_BATCH_PROCESS_REQUESTS = 50` (`apps/admin/app/(app)/contributions/batch-continuation.ts:13`), which is at most about 1,250 items per browser session. That is further evidence it cannot serve as an import executor.

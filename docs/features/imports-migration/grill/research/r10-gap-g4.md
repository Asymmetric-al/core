**What all the ratified money and content rules have in common** (a fact about the sources, not a recommendation):

1. Staging and dry runs are private, discardable and side-effect-dark before an authority boundary (ADR-0106:83-84, :98; D29 clause 19).
2. After the boundary, exactly one writer owns each scope. Asym never claims to have frozen or locked an external writer it does not control. It inspects a bounded population and monitors for overlap afterward (ADR-0058:22-24; ADR-0106:94-96; `CONTEXT.md:5040-5043`).
3. Late source facts after the boundary become successors or corrections and never overwrite (ADR-0106:101-104; D29 clauses 21-22).
4. A changed target or changed source makes the plan stale (D29 clause 19; `roadmap.md:4349`).

## 3. What a still-live SiteStacker source means for later exports

All vendor facts below come from r07, whose quotes the r07 verifier confirmed (r07 V8, `r07-sitestacker-sources.md:424`). Pages were accessed 2026-10-31. I did not re-fetch them. Every vendor article is dated 2023 or 2024 (2020 for S4), so none proves how a current installation behaves (`r07:53`).

### 3.1 Correcting the premise about Spark

The gap statement says Spark "fires on import and rollback". That is accurate, but it describes imports **into** SiteStacker: "Spark automation will be triggered and could have emails triggered on both import and rollback" (S1, Import Tool Overview, https://training.sitestacker.com/support/solutions/articles/151000122058-import-tool-overview; `r07:64`, `:237`). An Asym import reads an exported file and never runs SiteStacker's importer, so **an Asym import or Asym undo cannot fire SiteStacker Spark**. No source says that exporting from SiteStacker triggers anything. The Data Migration Plan page does not mention Spark at all (r00:659-660, verifier correction).

Spark matters to G4 for four other reasons, all derived from documented behavior:

### 3.2 Mailchimp

- Sync runs one way: "Making any changes in Mailchimp will not be brought over into SiteStacker!" and "Only changes in SiteStacker will be reflected in Mailchimp" (Using Mailchimp, Nov 2024, https://training.sitestacker.com/support/solutions/articles/151000121992-using-mailchimp-with-your-sitestacker-installation; `r07:175`).
- A contact deleted (not unsubscribed) in Mailchimp "can NEVER resubscribe using the Mailchimp API, only through SiteStacker", and SiteStacker has its own unsubscribe action that pushes to Mailchimp (`r00:669`, verifier addition).

Consequences for G4 (inferred from those facts):

1. **Suppression drifts between exports.** Every unsubscribe, bounce or complaint recorded in Mailchimp after the first export is missing from SiteStacker and therefore from any later SiteStacker export. A supplemental import of SiteStacker data alone would carry stale subscription state. r07 checklist item 22 (`r07:325`) already makes the Mailchimp audience export (including unsubscribed, cleaned and complained members) a companion artifact. G4 adds that it has to be **taken again at every supplemental import and at the final cutover**, not once.
2. **Who writes to Mailchimp is a competing-writer question.** Until the tenant turns off SiteStacker's Mailchimp sync, SiteStacker keeps pushing record-type and subscription changes into the audience. If Asym later sends email (Phase 6/17) or syncs its own audience, two systems write consent-relevant state for the same people. No repo text decides this. Historic provider flags are "evidence to classify, not automatic SMS consent" (`roadmap.md:4381`), which covers interpreting old flags but not ongoing ownership of the audience.

### 3.3 What this establishes

- **Asym cannot freeze SiteStacker.** Freezing is a tenant action: stop editing, disable Spark events, disable Mailchimp sync, stop online giving forms. Asym can only record a **tenant-declared freeze point** and inspect a bounded population. This matches the owner's money wording, which never claims Asym "locked an external writer it cannot control" (`CONTEXT.md:5040-5043`; ADR-0106:94-96). This is an established constraint, not a choice.
- **SiteStacker has no rehearsal or cutover procedure to copy.** The Data Migration Plan page has no rehearsal, cutover or reconciliation content (`r07:258`, `:267`). Asym's runbook is new design.
- **Online giving is the hardest live writer.** While SiteStacker giving forms and recurring schedules stay live, new gifts keep landing in SiteStacker. Those are money facts governed by P13 D.6, P16 and the P20/P21 cutovers (§2), not by a Party-level delta rule. Processor "cutover freezes" sit with an unnamed "separate migration workstream" (Phase 13 PRD `:743-746`), and r03 Q-5 already asks the founder who owns that work.

### 4.2 What can be established

1. **"Exact repeat import" most plausibly means identical-input replay, not a newer export.** R1 ties it to recovery "without requiring a fresh import identity". R2 lists "exact reimport" **separately** from "changed mapping" and "concurrent target edits". R7 and R8 give the same behavior in the two profiles whose owners have written it down: identical bytes in the same qualified scope recognize prior work and propose only the effects that remain. This is an inference from consistent texts. No P30 text defines the phrase, so a short founder confirmation would close it (see the founder questions in the Resolution).
2. **For an exact repeat, Asym edits made after the first import are not a conflict and are not overwritten.** The source assertion is unchanged, so prior acceptance is recognized and nothing is proposed for those rows. R3 forbids overwriting "newer work", `roadmap.md:4371` forbids erasing "later staff edits" on reversal, and R7 says "previously imported" does not mean "currently equal". The expected result is a plan with "unchanged / previously accepted" outcomes and zero writes for already-committed rows. This follows directly from the published texts.
3. **R3 on its face covers the gap between dry run and commit, not edits since the last import.** The plan binds "target revisions" at plan time and re-proves them at commit. A target that changed **after the plan** is a stale plan (R9; D29 clause 19). The sentence does not itself define what happens when a **new** plan finds that the target differs from what the previous import wrote. That is the supplemental-import case in 4.3.
4. **The owner texts disagree on what a changed source does.** R5 says re-import "updates". R7 (D17 profile) says current values are preserved and differences go to ordinary correction. R8 (content) says an update becomes a reviewed successor revision. R6 leaves the per-target mode open. r01 (`r01:375`) and r02 (`r02:271`) already flagged this tension. G4 adds no new source that resolves it.

### 4.3 The supplemental case needs a three-way comparison

When a newer SiteStacker export is planned against Parties that an earlier batch created, each bound field falls into one of four cases. **A** = value the last accepted import wrote (the base). **S** = value in the new export. **T** = current Asym value.

| Case | Condition                              | Disposition the existing texts support                                                                                               | Basis                                               |
| ---- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| 1    | S = A, T = A                           | Unchanged, no write.                                                                                                                 | R4, R7                                              |
| 2    | S = A, T ≠ A (only Asym changed)       | Keep T. No write and no conflict. Optionally note "Asym value differs from source".                                                  | R3 "newer work"; `roadmap.md:4371`; R7              |
| 3    | S ≠ A, T = A (only the source changed) | **Founder/target-owner choice:** apply as an update (R5), propose it for review (R8 style), or report a discrepancy only (R7 style). | R5 vs R7 vs R8; open per R6                         |
| 4    | S ≠ A, T ≠ A, S ≠ T (both changed)     | Conflict. Do not overwrite. Staff review or ordinary correction.                                                                     | R3 and R8 in spirit; no text authorizes source-wins |

Implementation facts that follow (derivable, not yet specified anywhere):

- Cases 2 and 3 can only be told apart if Phase 30 **keeps the last accepted source assertion per bound field** (the base A), in addition to the before-image that owner text requires for undo (`owner-constraints.md:378-380`) and the "per-record lineage" in `roadmap.md:4363`. Neither text requires a per-field base. Without one, every difference between S and T looks like case 4, and every supplemental import collapses into conflict review.
- Retaining A interacts with private-custody retention limits for staged rows (Phase 29) and with source erasure. This was not examined further here.
- Rows **missing** from the newer export cannot be read as deletions (§3.1 S-c). The texts support disposition "absent from this snapshot, no action", with any archive or merge left to ordinary owner commands. No text authorizes deletion by absence. `roadmap.md:4371` and the Planning Center undo-after-merge hazard (`owner-constraints.md:384-385`) point the other way.
- Identity for a supplemental import comes from the **qualified source binding** (Tenant, source system and instance, entity kind, external ID; R7 AC28-R21-02; r02 §b, `r02:32`), not from file bytes. A newer export is a new source snapshot and a new plan (D29 clause 22). An exact repeat is the same snapshot replayed. That gives three identities the session model must keep apart: **import run** (one plan and commit; recoverable after the browser closes), **source snapshot** (one artifact digest; replaying it is an exact repeat), and **source-record binding** (stable across snapshots; drives convergence).

### 5.2 Established operational constraints, whichever reading applies

2. **Asym cannot enforce the legacy system's stop.** The truthful claim is a bounded inspection plus monitoring afterward (ADR-0058:22-24; ADR-0106:94-96). For SiteStacker, the stop is a tenant action (§3.3).

### 7.1 What the external evidence shows

1. **Rehearsal at full scale in a separate environment is the mainstream practice** among platform vendors (X1 "same data ... several times"; X2 full-copy sandbox; X5 hosted test database with count checks and sign-off). Asym's documented environments forbid production data in Preview and hold demo data in Development (§6.1). The industry pattern therefore **conflicts with Asym's current environment policy**, which is why the rehearsal mode needs a founder or security ruling rather than a copy of common practice.
2. **The source freeze is a customer action limited to the cutover window**, not something the target system enforces (X1 cutover weekend; X2 "Stop changes"; X3 "no changes ... at the moment you start delta"; X4 STOP date set by the old processor). That matches the repo's owner position that Asym does not claim to lock an external writer (§2, §3.3).
3. **A delta is usually one final catch-up before go-live, not a recurring feature** (X3: optional, one run per wizard, before go-live). The one vendor that addresses it warns that a **source-wins delta after go-live overwrites target edits** (X3). That is exactly the hazard `roadmap.md:4349` ("not permission to overwrite newer work") and §4.3 case 4 exclude. No vendor source describes a three-way per-field merge. This is the point where Asym's published rule is **stricter than common practice**.
4. **Deletions are not carried by deltas** in the only source that mentions them (X3 "without deleting anything"). This matches §3.1 S-c.
5. **Recurring payments move at one dated handoff** (X4). This matches Phase 16's rule that formal cutover needs proof the old executor stopped (r03:107).
6. **No nonprofit CRM vendor publishes a full rehearsal-freeze-delta-cutover runbook** that could be fetched (X5-X7 are snippets or silence). The nonprofit-specific evidence is therefore weak. The general pattern rests on Microsoft and Salesforce primary pages plus one migration-service vendor.

### 8.3 Proposed default model (PROPOSED, research synthesis only, not owner intent)

Stated so the grill has something concrete to accept, amend or reject. Each step cites the settled point it relies on.

1. **Census and rehearse without writes.** Run the r07 evidence checklist, including the automation inventory (`r07:299`) and Mailchimp export. Produce plan-only dry runs for every file. If C3 allows it, run a discardable staged shadow of the full sequence with reconciliation totals (F1, F8; ADR-0106 precedent).
2. **First commit = baseline snapshot.** Commit Parties from one source snapshot through the reviewed plan. Exact replays of that snapshot are idempotent (F2).
3. **Optional supplemental snapshots before cutover.** Each newer export is a new snapshot and a new plan with three-way dispositions (§4.3). Case 3 follows C1. Case 4 always goes to review. Absent rows get no action (F7). Mailchimp is re-exported every time (F9). This needs Phase 30 to keep a per-field base (A).
4. **Tenant-declared freeze and final snapshot.** The tenant stops SiteStacker editing, disables Spark events and Mailchimp sync, and records the freeze time. Asym imports the final snapshot and records "no known overlap in the inspected scope" (F4; X1-X4).
5. **Authority switch per scope.** Asym becomes the writer for each scope (CRM first if C2 is phased). Money scopes switch only through their own cutovers (F6). Asym automations activate only after C4 is satisfied.
6. **After cutover.** Late SiteStacker facts found later come in as a new snapshot whose differences go to review or ordinary correction, never a source-wins overwrite (X3 hazard; ADR-0106 late-fact precedent by analogy).
7. **Published procedures before tenant use** (`roadmap.md:4403`): target-specific reversal and reconciliation procedures as required, **plus** (proposed) a cutover checklist covering the freeze attestation, final-snapshot reconciliation and automation handoff. The roadmap does not require the cutover checklist; adding it is part of C2/C4.

### 8.4 Implications for the session and identity model and the first-release slice

- The model needs three distinct identities: **import run**, **source snapshot** and **source-record binding** (§4.3). The first-release "exact repeat import" exercises run plus snapshot. Supplemental imports exercise the binding plus a three-way base.
- `roadmap.md:4363` "historical/cutover disposition" needs a defined **cutover boundary per scope** before it can be filled in. Before cutover, every imported fact is historical. After cutover, a SiteStacker fact found late is still legacy-sourced and dark (F3). No text defines the boundary for Party data (§0 B2).
- The acceptance list (`roadmap.md:4401`) has no case for **source drift between two snapshots** or for **two concurrent import runs on the same targets**. If C1/C2 admit supplemental imports, the grill should consider adding both, along with a Party analog of D29 clause 25's one-committing-run rule.

## Resolution

**Partially resolved.** The facts are established. The remaining gaps are product choices that research cannot settle.

- **Rehearsal:** Phase 30 guarantees only a per-file, no-write plan (`roadmap.md:4349`). A full-sequence rehearsal needs cross-file planning or discardable staging. Ratified precedent for discardable staging exists for Field Accounts only (ADR-0106:83-84, :98). A non-production rehearsal tenant with real data conflicts with `docs/ops/environments.md:41` and has no provisioning contract. Industry practice favors full-data rehearsal (X1, X2, X5). The mode is founder choice C3.
- **Source freeze:** Asym cannot freeze SiteStacker. The owners' own wording refuses to claim it has locked an external writer (ADR-0058:22-24; ADR-0106:94-96; `CONTEXT.md:5040-5043`). Vendors treat the freeze as a customer action during the cutover window (X1-X4). The runbook therefore needs a tenant-declared freeze, a final snapshot and a bounded inspection. Whether a freeze is required before Asym takes over CRM editing depends on C2.
- **Supplemental exports while SiteStacker stays live:** an Asym import cannot fire SiteStacker Spark. The real risks are new Spark-generated source facts and duplicate outward effects if both automation engines run (§3.1 S-a), hard deletes that show up only as absences (S-b, S-c), no documented change feed (S-d), and Mailchimp suppression drift, which requires a fresh Mailchimp export at every import (§3.2). The only owner-ratified delta rule (Phase 23 D29 clause 22) covers content: a delta is a new checked plan, never a blind upsert.
- **Exact repeat import versus later Asym edits:** an exact repeat recognizes prior work and never overwrites (F2). That reading is strongly implied but never defined (C6). A newer export needs a three-way comparison per field (§4.3). Case 3, where only the source changed, is founder/owner choice C1, because R5, R7 and R8 conflict. Case 4, where both changed, is a conflict under every text. The only external source on deltas warns that source-wins overwrites target edits made after go-live (X3).
- **"No permanent dual writers":** the best-supported reading is that Phase 30 is not an ongoing sync product (`owner-constraints.md:424-430`). Every ratified cutover puts one writer on each scope. The text neither authorizes nor bounds a temporary overlap (C2, C4).

The founder rulings that would close the gap are C1-C7 in §8.2. The most load-bearing for the first release are C6 (confirm "exact repeat" means snapshot replay), C3 (rehearsal mode) and C2 (overlap model). C1 is needed before any supplemental import is admitted.

### 1.3 Implications for Phase 30 (analysis)

1. **One MPDX/Tnt file holds two kinds of authority.** Contacts, tasks, notes, tags and appeals are the missionary's _personal relationship records_. Gift and commitment summaries in MPDX are _derived from the organization's donor system_ (FAQ; Cru sync rules). An MPDX "Lifetime Donations" or "Commitment" column copies another system's financial truth; it is not source-authoritative historic giving. Phase 30 should exclude these columns or keep them as provenance-only evidence, and route historic gifts only from the organization's authoritative donor/finance export through the Phase 13/14/16/21 owners (`owner-constraints.md:373-377`, `:389-413`).
2. **Separate profiles are justified by structure, not branding.** MPDX contacts are households containing people (D17 SP02). Tnt rows carry primary/spouse names and three address groups (D17 S03: 37 columns). The Tnt→MPDX path is a whole-database XML, not a flat sheet. A "TntConnect XML" profile would need a different parser, a different object graph (tasks/history/appeals) and a different custody risk from the D17 flat CSV/XLSX profile.
3. **Do not copy vendor transformations.** Sentinel year 1900 for unknown years, household-wide Deceased, stuffing unmapped fields into Notes, groups→tags and "override all fields" re-import are documented vendor behaviors that conflict with Asym rules (D17 FMT-06 "Do not auto-create custom fields or stash unknown data in notes", `file-format-safety.md:135`; FMT-07 no fabrication, `:137-150`).
4. **MPDX import has no undo, and Tnt status values carry meaning** (Never Ask, Not Interested). Under Phase 30 these are adverse contactability evidence for their owner (D17 C08). They are never dropped and never converted into consent.

### 2.2 Vendor facts (external, accessed 2026-10-31)

**Flatfile** (company page now says: "We've renamed our company to Obvious, which is also the name of our newest AI agent", https://flatfile.com/)

- Mapping uses "a machine learning model" trained on "mapping choices recorded from 1.8 billion (and counting!) rows" and works "alongside memory of your and your colleagues' past selections." "Any source fields that are not mapped to a destination field will be excluded from the import." Some destinations offer "Add as New Field". Unmatched option values get "Keep this value as is" (imports and then shows an error) or "Do not import" (blanks only that cell). (https://support.flatfile.com/articles/8569925090-mapping-data, "Last updated 1 year ago")
- Review: transformed cells are underlined; yellow = "it will still be accepted, but you may need to review it first"; red = "requires your manual change"; filters All/Valid/Invalid; FFQL search; bulk edit. (https://support.flatfile.com/articles/2093153444-reviewing-data, "Last updated 1 year ago")
- Security page: "SOC 2 Type II, ISO 27001 certified", "HIPAA ready", "region-specific data hosting options"; regions are not named. Pricing page shows "Talk to sales" (sales-led; no public price captured). AI data handling, subprocessors, retention and accessibility were **not found** in readable content. (https://flatfile.com/security/, https://flatfile.com/pricing/)

**OneSchema**

- Warnings: in the embedded Importer, "warning rows are considered error rows" by default and go to `error_records`; this setting "affect[s] only JSON imports. CSV and Excel output file formats are not affected"; FileFeeds default is the opposite ("treat warning rows as clean rows"), with partial-import on/off producing IMPORT_SUCCESS / ERROR_ROWS_REMAINING / PARTIAL_IMPORT. (https://docs.oneschema.co/docs/importing-warnings, updatedAt 2026-08-24). **The same warning has different semantics across products and output formats**, which shows why Asym must own warning/error meaning.
- Unmapped columns: included only "If the 'include unmapped columns' customization setting is active"; "Unmapped columns won't be validated"; webhook marks them `is_unmapped: true` and sends values under `$unmapped` keyed by column index. (https://docs.oneschema.co/docs/unmapped-columns, updatedAt 2026-04-21)
- Importer webhook: JSON POST; batches default 1,000 rows with `sequence_number`/`sequence_count`; "Each webhook call has a timeout of 30 seconds", batch global timeout 10 minutes; retries "up to three times with exponential backoff" on timeout/connect failure and 408/429; "Other HTTP error responses (including 5xx) are not retried"; `request_id` "will be the same for every retry"; `event_id` joins multi-request exports; auth is Basic (secret as password) or the SDK user JWT as bearer; no HMAC signature documented; retention after delivery not stated. (https://docs.oneschema.co/docs/importer-webhook, updatedAt 2026-09-25). **So a 5xx from Asym is not retried and a final failure has no documented redelivery; the receiver must be idempotent on `request_id` and must not treat delivery as durable acceptance.**
- AI bundle: AI-suggested mappings for columns and picklist values ("Users review suggestions"); NL transforms, AI validations, document extraction. Named LLM partners "OpenAI (GPT), Anthropic (Claude), and Google (Gemini)", also via AWS Bedrock and Azure OpenAI. Data sent: headers/column info/template config for mapping; "A sample of the rows" for transforms/validations; "the entire file" for document extraction. Providers "retain prompting data (including context) for 30 days"; "your data is never used to train the underlying models"; but "We may use data to improve the features for all customers in the future". AI can be disabled instance-wide via the Customer Success Manager. Regional processing is not stated. (https://docs.oneschema.co/docs/ai-bundle, updatedAt 2026-05-23)
- Pricing "Contact us"; self-hosting in customer cloud (AWS/GCP/Azure) is an enterprise option; homepage claims retention "configurable, default 7 days and programmatically deletable via API" (search-result summaries of https://www.oneschema.co/pricing and https://oneschema.co; not fetched directly). Accessibility statement targets WCAG 2.2 AA, self-rated "partially conformant" on 2025-08-11, with the ACR/VPAT available on request (https://www.oneschema.co/accessibility, search summary).

**Dromo** - headless flow: create import → presigned PUT upload (URL valid 30 min) → auto-processing → states `AWAITING_UPLOAD, PENDING, RUNNING, SUCCESSFUL, NEEDS_REVIEW, FAILED`; `NEEDS_REVIEW` returns a `review_url` to Dromo's UI; results via presigned download from a bucket named `dromo-user-imports` (https://developer.dromo.io/getting-started/headless, undated). **CSVBox** - delivery to webhook/API/DB; "Private Mode" in which "no row, no file, and no PII ever reaches CSVBox servers"; otherwise US or EU region with configurable retention "from hours to days"; usage-based pricing from $19/month with a free sandbox; AI column matching and AI pre-import transforms; server-side validation via webhooks (https://csvbox.io/, vendor homepage).

**Version-sensitive differences found by reading the `v4.0.0-beta.3` tag source and docs directly (GitHub API, tag SHA `846e0809`):**

1. **Local API `overrideAccess` default flipped.** The public 3.x docs say Local API operations "override access control by default" (https://payloadcms.com/docs/local-api/access-control). At `v4.0.0-beta.3`, `docs/local-api/access-control.mdx` says operations "now default it to `false` — they **respect Access Control by default**", warns "In Payload 3 this property defaulted to `true`", and `packages/payload/src/collections/operations/local/create.ts:198` / `update.ts:227` set `overrideAccess = false`. Without a `user`, "Payload evaluates access as an anonymous request." Any Phase 30/23 adapter written from the public docs would get the wrong default.
2. **Import plugin still defaults imported documents to published.** At `v4.0.0-beta.3`: `getImportCollection.ts:15` `const FALLBACK_VERSION_STATUS = 'published'`, and `createImport.ts:60` `defaultVersionStatus = 'published'`. This is unchanged from D29's finding and conflicts with "private D12 draft successors only" (`roadmap.md:4379`) unless the adapter sets the status explicitly.
3. **Plugin target writes use `overrideAccess: false`** (`batchProcessor.ts:251,264,282,317,396,409,442`), but plugin bookkeeping uses `overrideAccess: true`: the import-document status/summary updates (`getImportCollection.ts:201,260`), job queueing (`:358`), and re-hydrating the queued user by ID (`createImport.ts:71-77`). The batch clears `transactionID` and "Continues processing remaining documents even if individual imports fail" (`batchProcessor.ts:152,168-175`).
4. **Plugin limits default to unlimited**: "`importLimit` ... Set to `0` for unlimited (default)" (v4.0.0-beta.3 `docs/plugins/import-export.mdx:108-109`). Import modes are `create`/`update`/`upsert`, default `create`, with `matchField` (e.g. `email`) (`:856-881`). ### 3.4 Implications (analysis)

- **Strapi's restore-by-wipe and Payload's upsert are both incompatible with Asym's CMS import contract.** These are backup/restore or bulk-write tools. ADR-0173 requires a no-write plan and private successor revisions, and `roadmap.md:4379` forbids replacing current CMS content from a developer database. Phase 30 should treat a CMS backup archive as a _source artifact to parse_, never as a restore mechanism.
- **Media is never inside WXR.** A WordPress adapter must either fetch remote media URLs (SSRF surface; see §4) or accept a separately exported media archive (ZIP surface). Both must land in P29 private intake and D27 qualification (ADR-0173 item 9). Requiring "the original site must stay public" is a WordPress.com convenience, not an Asym guarantee.
- **Authors and users:** WXR carries authors by default, but ADR-0173 says source authors "never become users automatically". A WXR author is display attribution or provenance only, consistent with the Phase 43/44 rule that historic directory mappings do not create staff membership (`roadmap.md:4381`).
- **Timestamps:** Sanity's import moves `_updatedAt` for referenced documents. Asym must keep source occurrence/recorded times as provenance (`roadmap.md:4363`) separate from the Asym revision time, and "A source event marked historical cannot become prospective by changing a displayed timestamp" (`roadmap.md:4395`).

## 4. Security controls for CSV / XLSX / ZIP / WXR intake and remote media

### 4.1 OWASP (external, accessed 2026-10-31)

- **CSV/formula injection** (https://community.owasp.org/attacks/CSV_Injection, undated, © 2026): trigger characters are `=`, `+`, `-`, `@`, Tab `0x09`, CR `0x0D`, LF `0x0A`, **and** "Full-width (double-byte) variants of formula-initiating characters such as ＝, ＋, －, and ＠, which may be interpreted as formulas in some locales (e.g., Japanese environments)." Mitigation: wrap in double quotes, prepend a single quote, double embedded quotes; "To reliably prevent formula execution in Microsoft Excel, prefix any cell starting with =, +, -, or @ with a tab character (0x09) inside the quoted field"; "The above techniques are not reliable in Microsoft Excel after saving and re-opening the CSV file." Separator/quote injection can start a new cell.
- **File upload** (https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html): allowlist extensions; "don't trust the Content-Type header"; signature checks "should not be used on its own"; generated (UUID) filenames; "the file size limit should be considered after file decompression is conducted"; names "ZIP bombs, XML bombs (otherwise known as billion laughs attack)" and parser exploits including XXE; store outside webroot or on another host; AV/sandbox and CDR "if applicable"; "ZIP files are not recommended since they can contain all types of files"; authorized and identifiable uploaders only. The sheet does **not** cover zip-slip, CSV or XLSX specifically.
- **SSRF** (https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html): "Deny-lists are bypass-prone. Prefer allow-lists"; validate the resolved IP with a vetted library and "ensure the HTTP client connects only to validated addresses" (DNS rebinding), including on retries; "Disable the support for the following of the redirection"; allow only HTTP/HTTPS; block loopback, RFC 1918, link-local and `169.254.169.254`; cover IPv4 and IPv6 and encoding bypasses (hex, octal, dword, mixed); "Do not accept complete URLs from the user ... build the request yourself"; network-level segregation; IMDSv2 as defense in depth.
- XXE: D17 already cites the OWASP XML External Entity Prevention Cheat Sheet: "Prohibit DTD/entity processing and network/resource resolution in workbook parsing" (`d17-evidence/file-format-safety.md:57`).

### 4.2 What the repo already ratifies (binding intent)

- D17 C12 inert parsing, no formula/macro/embedded-object/external-link execution, no trust in MIME/extension/ZIP declarations, and actual byte/cell/member/row bounds (`phase28-d17-contact-import-adversarial-review.md:278-285`), plus the ratified numeric profile: 10 MiB upload, 10,000 rows, 500,000 slots, 128 MiB expanded, 4,096 members, 32 KiB/cell, one worksheet, 16,384 columns, seven-day window, 24 h purge (`:402-413`). These limits are **ratified for the D17 profile only**; `:396-400` says they are "not demonstrated capacity or universal P29 limits" and "A larger migration belongs in qualified P30 staff tooling".
- D17 FMT-10 (pre-ratification research text, then ratified via the review): normalize/validate XLSX relationships and member names, reject duplicate normalized parts, traversal, DTD/entities, unsupported encryption, macros and executable content; "Sparse dimensions SHALL NOT trigger allocation of a maximum rectangular worksheet" (`d17-evidence/file-format-safety.md:171-180`).
- ADR-0173 item 13 (private quarantine before parsing; compressed and decompressed size, entry, nesting, row/node, string and image budgets; reject traversal and polyglots; never execute macros, HTML, JavaScript, templates or archive contents) and item 14 (remote media: HTTPS only, resolve and pin public addresses, block private/link-local/metadata networks and redirects to them, limit bytes/time/type, move into Phase 29 intake) (`docs/adr/0173-...md:134-152`).
- ADR-0212: one shared `csvSafeCell` for all CSV output; "No second escaping implementation is permitted" (`docs/adr/0212-one-export-policy-and-shared-csv-safe-cell.md:22-26`). D17 C20 prefers an XLSX correction artifact "with explicit text cells and no formulas/active links" and says CSV escaping "SHALL NOT be represented as guaranteed safe after spreadsheet save/reopen" (`phase28-d17-...md:346-352`).
- Phase 29 (unmerged PR #2430 head `1483a349`, "Q01–Q67 fully ratified"): P29 owns "bounded upload initiation, finalization, integrity checks, malware scanning/quarantine" and "Phase 30's staging-only role" (`roadmap.md` at PR head, Phase 29 chapter; same text on develop at `roadmap.md:4262` and `:4268`). The full spec says "hostile content and AI-facing extracts remain untrusted data" and to "Preserve existing source-specific format, fidelity, time and capacity contracts rather than adopting a universal upload profile" (`phase-29-files-documents.md:732` at PR head).

### 4.3 Implemented code fact and a gap against current OWASP text

- `packages/lib/csv.ts:20-28` neutralizes `=`, `+`, `-`, `@`, TAB, CR, LF after skipping leading spaces/NBSP (`:30-33`, `:67-80`), prefixing a single quote and always double-quoting. Tests: `tests/unit/packages/lib/csv.test.ts:17-98`.
- **Gap:** neither the helper nor its tests handle the full-width variants `＝ ＋ － ＠` (U+FF1D, U+FF0B, U+FF0D, U+FF20) now listed by OWASP (grep for `FF1D|FF0B|FF0D|FF20|＝` returned no hits). ADR-0212's ratified character list matches the code, so closing this would change the ADR and the shared helper, not Phase 30 alone. OWASP's Excel-specific tab-prefix advice also differs from the helper's single-quote prefix. OWASP says both techniques fail after save and reopen, which is why D17 C20 prefers XLSX text cells for correction files.

### Missed items (within this track's scope)

1. **A second, non-neutralizing CSV encoder already exists in `packages/api`.**
   - `packages/api/src/admin/contribution-batches/results.ts:6-11` defines a private `csvEscape`. It quotes only when the value contains a double quote, comma or LF, does no formula neutralization, and ignores CR.
   - `buildContributionBatchCsv` (`:44-81`) joins records with LF, emits no BOM, and serializes the donor-controlled `donorName`, `donorEmail` and `failureReason`.
   - It is a public export (`packages/api/package.json:54`, `./admin/contribution-batches`), but at 629cb71dc only `tests/unit/packages/api/admin/contribution-batches.test.ts:1861` calls it.
   - This breaks ADR-0212 ("All existing CSV consumers use one shared `csvSafeCell` ... No second escaping implementation is permitted").
   - The same module's batch status `complete_with_issues` (`results.ts:28`) is the kind of aggregate that ADR-0173 item 18 forbids for content imports.
   - So §4.3's picture of `csv.ts` as the only CSV path is incomplete. Any Phase 30 error or correction download that reuses the batch substrate would inherit an unsafe encoder.
2. **Payload's plugin brings its own CSV parser and encoder, both unsafe by Asym rules.** `npm view @payloadcms/plugin-import-export@4.0.0-beta.3` lists `csv-parse 5.6.0` and `csv-stringify 6.5.2` as dependencies. At the tag:
   - **Encoder:** `export/createExport.ts:405-409` and `:595-599` call `csv-stringify` with only `bom`, `header` and `columns`. There is no formula neutralization, so this is a second encoder that ADR-0212 forbids.
   - **Parser:** `utilities/parseCSV.ts:20-54` runs with `trim: true` and `skip_empty_lines: true`, and its `cast` changes values silently:
     - `"true"`/`"false"` become booleans.
     - `"null"`/`"NULL"` become `null`.
     - Any numeric string containing `.` becomes a number, so `"1.50"` becomes `1.5`.
     - Empty cells become `undefined` "to preserve existing data during updates", so a blank can never clear a value.
     - It loads every record into memory.
   - These conflict with D17 FMT-07 (no fabrication or coercion), the ratified rule against inferring locale semantics, and ADR-0173 item 4.
   - The digest re-qualified the plugin's status, access and transaction behaviour but not its parse/encode behaviour. Any "adapter" use must replace both libraries' defaults or bypass them.
3. **No shared file-upload control exists yet, and P29 already names the pattern family.**
   - `roadmap.md:4389` requires "the shared accessible grid and file controls".
   - `packages/ui` has a data-table (`components/shadcn/data-table`) but no file-upload or dropzone component (grep for `file-upload|dropzone|FileUpload` in `packages/ui` finds nothing).
   - The ratified P29 spec at PR head (`phase-29-files-documents.md:736`) binds file UI to "the shared exact base-maia/Base UI components and qualified ReUI file patterns". It also requires keyboard and touch equivalents to drag, 320 CSS pixel reflow, and weak-network recovery.
   - The build-vs-embed "Design-system fit" and "Accessibility" rows (§2.3) should cite this. The native option starts from a P29-owned, not-yet-built file control rather than from scratch, and a vendor iframe would also bypass P29's ratified UI rules.

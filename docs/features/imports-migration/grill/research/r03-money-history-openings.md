### 2.1 What Phase 13 owns for imports (and what it does not)

- Goal: "Lay only the Phase 13 import-aware money seams (tenant/account/mode-scoped external provider references and the `already_receipted` boundary)" (`phase-13-…md:150-154`).
- Non-goals: cross-processor PAN/ACH migration, re-authorization, recurring-object adoption and bulk cutover tooling are "a separate dedicated migration workstream governed by Phase 16" (`phase-13-…md:159-164`). "Full CRM data migration at scale (people/relationships/notes/tags/consent/historical giving) — the migration workstream (deps Phases 4/9/11); Phase 13 owns the payment/ledger seam and linkage model (D25)" (`phase-13-…md:165`). The "migration workstream" is not named as Phase 30 in the PRD. Roadmap v3 puts it in Phase 30 (`roadmap.md:4367`).
- §C (superseded recipe, retained seams): imported contribution and posting facts "with immutable legacy external references scoped to the exact tenant, connected account, livemode, source object, and known Party where one is proved"; the `already_receipted` pre-Asym boundary "so imports cannot duplicate a prior receipt or statement"; signed provider-event, correction, idempotency and reconciliation inputs Phase 16 may consume "without converting them into authorization" (`phase-13-…md:721-729`). "Historical gifts remain importable behind `already_receipted`; GDPR-erased donors remain pseudonymized and must not be re-identified from provider metadata" (`phase-13-…md:745-747`).
- Never infer commitments from `sub_`/`cus_`/`pm_` objects, never match authorization by email/name/phone/fingerprint, never reuse a payment method or cancel/recreate a subscription without current proof (`phase-13-…md:713-719`).
- **D.6 Import/adopt** (`phase-13-…md:1023-1039`): imported gifts use the same Phase 13 payment/review records and append-only posting fold, "pre-advanced — there is no special `imported` status enum":
  - PAYMENT = already-succeeded (externally sourced marker; no Stripe reconciliation attempted);
  - POSTING = eligible immediately, "stamped with a pre-Asym provenance boundary";
  - RECEIPT BOUNDARY = "a separate Phase 7 import fact records that a pre-Asym receipt exists or that no Asym receipt is permitted"; Phase 13 stores no receipt status and "never re-issues or voids a historical receipt the previous system sent";
  - ACCOUNTING OWNERSHIP = pre-Asym provenance plus previous-owner provider evidence for the Phase 20 D17 cutover; "An import never asserts `exported` from a legacy flag alone and never replays work without gap-only proof";
  - REVIEW = bypassed unless donor match or allocation is ambiguous.
- The fail-closed review predicate routes "an import-sourced gift whose donor-match or allocation is ambiguous" to review; with no tenant configuration it defaults to review (`phase-13-…md:987-990`). Story 115 lists "imported gifts" among risky cases (`phase-13-…md:415`).
- Stories 169–173 and 223: references bound to exact tenant/account/mode/Party/source object; historical receipt evidence recorded "as an exact source-bound already-receipted fact"; unmatched records quarantined, "rather than linked by email, name, phone, or payment fingerprint"; never handle raw PAN/bank credentials; a hosted re-authorization fallback; imported gifts "enter the existing payment, posting and review axes with exact pre-Asym provenance, while prior receipt and accounting evidence remain related owner records" (`phase-13-…md:534-546`, `:634`).
- Ledger invariants an import must respect: header/lines/postings are wholly immutable after the initial `draft → posted` freeze (`phase-13-…md:790`); the lines are the money source of truth (`:785`); corrections, refunds and reversals are append-only postings with `kind ∈ {initial, refund, void, write_off, ach_return, chargeback, …}` and `reverses_posting_id` (`:1767`); `contribution_headers.legal_issuer_id` is "server-resolved from the verified legal-issuer authority, never caller input" (`:1738`); a fund merge "resolves at intake only — it never repoints a historical FK" (`:1900`); retired source codes keep historical gifts pointing at them (`:1605`); posted reporting reads frozen source-code snapshots (`:1611`).
- Tenders: `card, ach, check, cash, securities, in_kind, church_remittance` (`phase-13-…md:1806`). Securities is one gift with a lifecycle; noncash proceeds are `non_contribution` facts (`phase-15-…md:912-918`, `:928`). Describe-never-value: in-kind posts `recognized_value = 0`, enforced "across grid entry, CSV paste, API, and import" (`phase-15-…md:922-926`).
- Phase 2 reserves entry-method `import` ("data import/onboarding") and `legacy` ("pre-Phase-2 / unknown historical") and "The honest-import pattern (`entry_method = legacy`/`import`, `source_code = null`) is reserved for future real-data onboarding" (`phase-02-…md:383-384`, `:524-533`).
- **Gap (D-4):** the Phase 13 data model (`phase-13-…md:1724-1830`) names Stripe link columns on `contribution_headers` but no concrete import-identity columns (`external_source`/`external_ref`, source system, pre-Asym boundary, imported-at) and no uniqueness for exact re-import. The only `external_ref` in Phase 13 is the frozen designation snapshot (`:796`, `:1749`). Phase 14 by contrast ships concrete columns (`phase-14-…md:1862-1864`).

### 2.2 Currency and precision (ADR-0208, Accepted)

- Money is "checked integer minor units plus a validated ISO-4217 currency code"; parsing must "reject invalid precision or values rather than silently round" (`docs/adr/0208-currency-aware-minor-units.md:18-22`). Exponent comes from metadata (`:23-36`); the ADR "records the settled target contract … not implementation, provider qualification, or activation evidence" (`:5`).
- "Comprehensive metadata is not comprehensive transactability." Phase 2 permits only presentment = resolved settlement currency; Legal Entity and Settlement Account Binding govern the financial context; "financial roots freeze their owner-resolved facts" (`0208…md:44-50`).
- Consequence for import (inference, not stated by any owner): an imported historical gift in a currency the Legal Entity never settled in can be represented but not transacted. No owner says whether historical import must pass `assertTransactable`. Founder question Q-3.
- The Phase 13 cutover rule "`sum(minor)/100` = pre-migration dollar total per tenant" (`phase-13-…md:574`, `:772`) concerns the internal `donations` → ledger replacement. It is two-decimal arithmetic and must not be reused as the Phase 30 reconciliation formula; Phase 30 requires per-Legal-Entity, per-currency totals (`owner-constraints.md:431-437`).

## 12. Discrepancies and contradictions

- **D-1 Receipts for imported historical gifts.** Phase 7 E3 says "manual/imported/historical gifts without a staged-gift record can be receipted" (`phase-07-…md:339`), while Phase 30 says importing a historical gift never creates a new tax receipt (`roadmap.md:4395`; `owner-constraints.md:441-442`), and Phase 13 D.6 relies on "a separate Phase 7 import fact" that Phase 7 never defines (`phase-13-…md:1031-1035`). Handling: read E3 as covering staff-entered or imported gifts that are prospective Asym-era receipt candidates, not pre-platform gifts. Ask the Phase 7 owner to define the import fact (pre-Asym receipt exists / no Asym receipt permitted) and its boundary. Phase 30 must not define it.
- **D-2 #711 "Phase 36" misreference.** See Section 2.3. Phase 36 is P2P; historical import belongs to Phase 30. Correct the ticket wording; keep its safeguards.
- **D-3 Writer for historical offline money.** Phase 15 D1, the kill-door guard test and Phase 16 A14 make the Phase 15 batch commit the sole offline-money writer (`phase-15-…md:72`, `:836`; `contribution-operations.md:418-433`; congruence A14). Phase 15 excludes formal import (`phase-15-…md:144`), and Phase 13 D.6 describes a pre-advanced import path (`phase-13-…md:1023-1039`). Either a historical-import command must be explicitly allow-listed by Phase 15's guard, or historical offline gifts must enter as batches (needing deposit evidence they may not have). Owner decision required (Q-1).
- **D-4 No concrete import-identity columns on contribution roots.** Phase 30 requires source system + stable external ID on every imported financial root (`owner-constraints.md:373-377`), but the Phase 13 data model defines none (`phase-13-…md:1724-1830`), unlike Phase 14 (`phase-14-…md:1862-1864`). This must be specified by the Phase 13 owner before a Phase 30 gift adapter can converge reimports.
- **D-5 Statement late facts versus historical import.** Phase 19 converts any post-Start source fact into a Late Fact Obligation (`phase-19-…md:976-990`) and names import retries explicitly (change spec `:138-146`). No owner text exempts `already_receipted` / pre-Asym imports, so a migration into a year with a started Asym run could raise supplemental-statement obligations. This conflicts with outward-effect-dark (`roadmap.md:4365`). Phase 7/19 owners must state the exclusion.
- **D-6 External-ID uniqueness scope.** Phase 14 credits/tributes are unique on `(tenant_id, external_ref)` while expectancies use `(external_ref, external_source)` (`phase-14-…md:331`, `:802`, `:865`). Phase 30 requires source system + ID (`owner-constraints.md:373-377`). Minor; resolve in Phase 14 schema review.
- **D-7 "Review bypassed" versus "imported gifts are risky".** Phase 13 D.6 says REVIEW is "bypassed unless donor-match or allocation is ambiguous" (`phase-13-…md:1039`). Story 115 lists "imported gifts" generally among risky cases that must fail closed (`phase-13-…md:415`), and the forward predicate is narrower: "an import-sourced gift whose donor-match or allocation is ambiguous" (`:987`). Story 115 reads broader than the ruling; the D.2/D.6 text should govern. Note that large-gift and restricted-ministry predicates still apply to imports (`:984-989`).
- **D-8 Legal issuer resolution versus explicit import pinning.** `contribution_headers.legal_issuer_id` is "server-resolved from the verified legal-issuer authority, never caller input" (`phase-13-…md:1738`), while Phase 30 requires each imported root to pin the exact Legal Entity, never inferred from a default (`owner-constraints.md:373-377`). These are reconcilable only if the server resolves the Legal Entity from reviewed mapping evidence. That evidence class is unspecified (Q-4).
- **D-9 Phase 30 starting dependencies omit money owners.** Phase 30 starts after Phases 9, 13, 11, 29, 4, 3 (`roadmap.md:4341`; `phases.json` Phase 30 entry), yet historic gifts need Phase 7 (receipt import fact), Phase 14 (credits) and Phase 15 (offline writer), commitments need Phase 16, openings need Phase 21, and accounting needs Phase 20. The roadmap handles this by per-target activation (`owner-constraints.md:389-393`). The inconsistency is only apparent, but the grill should confirm money targets are later, separately gated profiles.
- **D-10 Phase 13's two-decimal cutover assertion.** Story 198 / §D(a) proves the internal cutover with `sum(minor)/100` (`phase-13-…md:574`, `:772`), which contradicts ADR-0208's exponent rule if reused for migration reconciliation. Phase 30 must use exponent-aware per-currency totals.

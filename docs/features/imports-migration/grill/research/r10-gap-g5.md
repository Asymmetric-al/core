Reading of section 2: the consumers agree on two separate things. (1) **Dark:** an imported historical fact must reach the Studio already marked `historical=true`, and the event is written by the source module's outbox (D14), not by Studio. (2) **Coverage:** P35 needs a named completeness-qualified projection (D1, D9), owned by P33 (D9, D12), fed by "history coverage" that P30 supplies (D8). When coverage is missing, the specified outcome is _unknown → recipe blocked_ (D6, D19, D20), not "first gift". So missing coverage, if the spec is followed, is a usefulness problem (recipes stay blocked for migrated tenants), not by itself a send problem. The send risk comes from a missing historical marker, or from someone building a naive "no earlier rows = first" query, which D6 forbids.

Findings from section 3:

1. **The import-origin signal already has a specified owner and carrier.** For acknowledgments, P14 derives the hold from "the gift's existing frozen entry-origin metadata" and forbids a new origin column (T6). The only frozen per-gift "how it entered" attribute P13 defines is `entry_method`, whose glossary values include "data import" (T3). Phase 30's job is therefore to make the P13 import command record the import entry method and the pre-Asym provenance. It does not add its own origin flag to financial rows. Caveat: P14 does not literally name `entry_method` as the field. "Entry-origin metadata" equals `entry_method` plus the T1 pre-Asym provenance stamp by inference only.
2. **Correction to the r07 verifier (index :667, :865).** The import path does **not** depend on the Phase 15 NF3 button. NF3 releases _batch_-origin rows; _import_-origin rows "never pass this batch gate" (T6, T9, T10). The real dependency is the **P14 `held` derivation for import-origin requests** plus the P13 frozen entry-origin metadata. Neither exists in code (section 4). NF3 being unbuilt matters only if someone tries to reuse the P15 batch commit as the importer, which r03 already flags as an open writer choice (index :251, :264).
3. **Coverage is specified per domain, never for contribution history as a whole.** P14 has a per-tribute `notified_through` watermark (T7). P20 and P21 have their own manifests (T13). P13 has unknown-coverage rules for campaign attribution only (T5). No document defines a contribution-history coverage record per tenant, source and donor scope, which is what P35's first-gift and inactivity rules need (D2, D3).
4. **"Coverage" means two different things.** In owner-constraints.md:378-385, "immutable downstream coverage" means a downstream artifact (issued document, Field Account entry, release) that _covers_ a fact and therefore blocks undo. In roadmap.md:4363/4675 and P35, "coverage" means _source-history completeness_. Orientation must keep the two terms apart.

## Resolution

**Partially resolved.** Ownership is now traceable end to end (section 6). Two links remain unwritten in owner text, and three product choices remain.

- **Phase 30's own producer obligations, already assigned but undefined:** (1) freeze each row's historical/cutover disposition at plan approval and keep it in run evidence; (2) batch identity and batch-origin provenance, carried in P30 run/link evidence or the target's external-reference carrier, never as a new origin column on financial rows; (3) P30 emits no outward-effect events of its own; (4) supply "history coverage" per run and fact family, the input that P33 and the contribution owner need. Sources: roadmap.md:4363, :4365, :4377, :4395, :4675; owner-constraints.md:378, :386-388. Orientation should name all four as P30 deliverables. Section 7 gives a proposed minimum shape.
- **Not Phase 30's to write, and must be placed as cross-phase requirements:** the `historical=true` flag on the outbox event, which the source module writes (WS 03:23-25), and the first-qualifying-gift fact, which the contribution owner certifies (WS 07:1157, :1195; P28 finance-stewardship.md:271-276). Both fall to P13, and the P13 PRD defines neither (A3, O1, O2).
- **Already owned elsewhere:** P14 import-origin `held`, STOPPED tribute streams and the `notified_through` watermark; P34 historical-dark subscriptions; P33 completeness-qualified inactivity projection; P35/P34 "missing coverage blocks the recipe"; P20/P21 accounting and Field Account coverage manifests.
- **Safety reading:** if the specs are followed, missing coverage yields _unknown → blocked_, not a false "first gift". The send risk for "zero unintended send" comes from a missing historical carrier (O1), the `gift_date DEFAULT CURRENT_DATE` hazard (C5), or a naive projection like the existing `donors.first_gift_date` (C4).
- **Sequencing:** P30 money targets cannot activate before the P13 typed import command and P14 import-origin hold exist (owner-constraints.md:389-392). The P15 NF3 button is not a prerequisite (K1). For migrated tenants, P28 first-support activation needs P30's coverage declaration (section 8).

## 1. Authority rules and process

### 1.1 Authority order (what wins when sources conflict)

Repository-wide order (`AGENTS.md`, "Authority and evidence"):

1. Current user request plus safety/approval boundaries.
2. Accepted domain-owner intent and explicit later ratified amendments, reconciled through OpenSpec. Active changes do not prove implementation.
3. Root `AGENTS.md`, then nearest nested `AGENTS.md` and rulebook.
4. Current source, tests, manifests, lockfiles, installed docs, runtime evidence.
5. Current official external docs for the installed version.
6. General model knowledge last.

`docs/ai/document-authority.md` refines this:

- Answer intended behavior from the owning domain, explicit founder ruling, ratified amendment and superseded clauses. "A later consumer phase cannot acquire a producer's authority by shorthand" (`document-authority.md:10-13`). This is the key rule for Phase 30. Phase 30 is a consumer of P4 identity/merge, P9 Party/relationships, P11 custom data, P13/P14/P16 money, P21 Field Accounts, P23 CMS and P29 custody. It cannot redefine any of them.
- Current implementation comes only from source, migrations and tests. "Never implement an old design merely because old code still exists" (`:14-16`).
- Generated Markdown/OpenSpec views are not independent decision sources. Edit the canonical source and regenerate (`:17-24`).
- The "why" comes from the accepted ADR and final decision log. Earlier questions and research are dated provenance (`:25-26`).
- Publication status comes from actual GitHub state and commit ancestry (`:27-28`).
- Explicit supersession beats stale prose. A superseded clause must be edited in place; a banner is not enough (`:30-35`).
- An unresolved conflict with no owner ruling preserves "the last agreed behavior" and records the decision. File mtime, the highest phase/ADR number or a bot timestamp cannot establish authority (`:37-40`).
- `openspec/project.md:6-19` repeats this order and distinguishes intended from current behavior. An active change "does not prove the behavior shipped."
- Owner map (`document-authority.md:62-88`): roadmap v3 (45 phases, adopted 2026-09-22) owns phase architecture, and `phase-map.md` mirrors it (`:71`). ADR identity is resolved by `docs/adr/registry.md` (`:85`). The detailed record ownership matrix is `phase-01-source-of-truth-ownership-matrix.md` (`:87-88`).
- Program packet: Roadmap v3 owns "phase numbering, scope, starting floors and priority". Exact source owner contracts, not roadmap shorthand, own existing business facts. Runtime truth comes only from code and environment evidence (`docs/prds/program-roadmap/README.md:23-34`).
- "Part I phases 27–44 are adopted in full… Detailed predecessor owner obligations are retained separately and linked per phase" (`README.md:47-50`). For Phase 30 that means `owner-constraints.md#phase-30`, which is binding alongside the roadmap chapter (`roadmap.md:4416-4418`).

### 1.2 State vocabulary (how evidence levels are distinguished)

`document-authority.md:42-54` defines nine states: Proposed, Ratified, Published, Integrated, Merged, Implemented, Qualified, Activated and Superseded/retired.

- "Ratified" means the product decision was accepted for its stated scope.
- "Published" means an exact issue, PR or repository packet is available.
- "Qualified" means the exact provider/environment/cohort passed its gates.
- "Activated" means a proved release enabled the behavior in a named environment.

The delivery contract adds an audit trail. It requires separate evidence for "authored, accepted specification, ticketed, implemented, locally tested, provider-qualified, enabled and observed-live" (`delivery-contract.md:274`). It also separates "Built / Live / Confirmed" (`:167`). Release must "keep definition publication, tenant enablement, build availability, business acceptance and actual live confirmation distinct" (`:45`). "A mock, structural fixture, schema check or passing documentation test cannot substitute for required source behavior" (`:41`).

### 1.6 What a phase specification package must contain

There is no single template file. The requirements below are assembled from the delivery contract, the program README and the Phase 28/29 precedents.

- **Before implementation (delivery contract):** for each consuming capability, record "the actual owner/command, exact subject and scope, required version, current permission, input/output meaning, classification, effect identity, failure/unknown behavior, evidence and safe recovery". Classify existing code as durable pattern / precedent / temporary bridge / accident / source conflict (`delivery-contract.md:9-13`).
- **Dispatchable slice handoff:** name "actual source symbols/versions and scope, authorized commands, expected heads and receipts, the stable acceptance cases, real adverse-path tests, retained-data migration, mixed-version behavior, disable/recovery and exact release criteria" (`program-roadmap/README.md:86-90`).
- **Release:** "retained-data census, version compatibility, scoped rollout/containment, source-linked recovery and a representative user pilot" (`delivery-contract.md:45`). The definition of done is at `:47`.
- **Section template (`/to-spec`):** Problem Statement, Solution, User Stories (long numbered list), Implementation Decisions (no file paths), Testing Decisions (seams and prior art), Out of Scope, Further Notes (`docs/ai/skills/to-spec/SKILL.md:21-75`). Phase 29 follows it exactly (`PR2430:phase-29-files-documents.md` headings at lines 1, 5, 11, 21, 725, 740, 752, 760). Phase 28 checks "All seven required template sections" (`phase-28-…/publication.md:37`).
- **Traceability:** every US/REQ/AC identifier maps to the decision/completeness clause, owner contract and a future test/release artifact (`phase-28-missionary-workspace-depth.md:719`). In Phase 29, user stories link to `REQ29-*` with `AC29-*` ranges (`PR2430:phase-29-files-documents.md:21-30`), and `traceability.json` is generated.
- **Owner reconciliation:** a separate hand-maintained file that splits current code from intended behavior. It names gates (R-POL, R-LEGACY, R-OWNER-BIND and others) with class S/Q, plus evidence and permanent resolution. It also gives the whole-phase implementation order, monitored residuals (signal / threshold / owner / response) and the publication boundary (`PR2430:phase-29-files-documents/owner-reconciliation.md:1-57`).
- **Consumer registers:** Phase 29 maps "23 existing and 11 future consumers… individually named" in `custody-and-integration.md` and `custody-source-map.json` (`owner-reconciliation.md:9`). The roadmap-level "Owner/consumer" map is at `delivery-contract.md:204-221`.
- **Qualification gates:** listed per gate with an S (source decision) or Q (qualification) class. "Missing actual value" is an activation gate, not a reopened product vote (`owner-reconciliation.md:11-13`). OpenSpec tasks remain unchecked (`:44`).
- **Testing evidence:** existing seams and their limits (`phase-29-…/testing-evidence.md`). The user must confirm the testing seams (`to-spec/SKILL.md:15-17`; Phase 29 status line `PR2430:phase-29-files-documents.md:3`).
- **Preservation/provenance:** a hash manifest of the grill corpus, a source census and a founder brief, checked by `verify-evidence.mjs` (`PR2430:…/tools/verify-evidence.mjs:20-38`).
- **Authority registration:** a bullet in `document-authority.md` "Canonical authoring and evidence", an `openspec/project.md` validation note, a `CONTEXT-MAP.md` row, the `phases.json`/roadmap status line and a root `CONTEXT.md` amendment where needed (PR #2430 changed-file list).

### 1.7 Rules about publishing specs as GitHub issues

- Tracker: GitHub issues on `Asymmetric-al/core` via `gh` (`docs/agents/issue-tracker.md:1-20`). Each skill-created issue needs exactly one `type:*` and one `complexity:*` label. `/to-spec` defaults to `type:feature` + `complexity:hard` for broad specs (`issue-tracker.md:66-82`).

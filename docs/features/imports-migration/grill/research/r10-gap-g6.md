### 2.3 Contribution bulk batches: the closest integrated "run" journey

r06 covered the server mechanics. Only the journey facts are added here:

- **Entry.** A bulk action inside the Contributions page (`apps/admin/app/(app)/contributions/main-body.tsx:369-391`), not a separate tools surface.
- **Progress and resume.** The browser drives the loop: up to 50 process POSTs, then "Contribution batch processing paused after 50 process requests. Retry to continue the same batch." (`apps/admin/app/(app)/contributions/batch-continuation.ts:13`, `:121-183`). The continuation handle lives only in a React ref (`main-body.tsx:276`, `:391`). The batch API exposes only `POST` create and `POST .../process` (`apps/admin/app/api/admin/contribution-batches/route.ts:1`, `[batchId]/process/route.ts:1`). There is no list or GET route, so **a closed browser cannot rediscover the running batch from the UI**. Server-side stale-item recovery exists (`packages/api/src/admin/contribution-batches/process-batch.ts:287`, `:366-372`), but it runs only when a client calls process again. This precedent does **not** satisfy `roadmap.md:4387`.
- **Results and escalation.** A terminal state of `complete_with_issues` (`process-batch.ts:200`; `results.ts:24-28`). Each failed row creates a Mission Control task titled "Resolve bulk contribution action failure", with the failure `reason` copied into the description (`packages/api/src/admin/contribution-batches/route.ts:301-318`, `:372-391`). ADR-0183 names exactly this pattern (copying reason text into a mutable task with generic status and completion controls) as a non-precedent migration input (ADR-0183:597-605).

## 4. The four boundary questions, answered from evidence

### 4.1 Where do a plan's "queue for merge" outcomes land?

**Established (published text, consistent across five owners):** in the **Phase 4 dedupe queue and Merge UI (#514)**, reached through Phase 9's `/crm/duplicates` and the record-header banner, and counted (never worked) on Phase 8's `/crm/operations`. Phase 30 owns no merge queue and no merge action.

- Phase 30: "Phase 4 owns identity/merge" (`roadmap.md:4377`); "source-owned merge command" and no "alternate path around ... duplicate controls" (`:4351`); "reusing the Phase 4 merge contract and Phase 9 duplicate surfaces" (`owner-constraints.md:371-372`).
- Phase 4: the dedupe queue populates `crm_merge_candidates` and "never auto-merges" (phase-04:222). The Merge UI is the single "duplicate-triage workbench", with actions Merge / Not a duplicate / Defer (phase-04:299-306).
- Phase 9: "routed to the Phase 4 merge workbench, so that cleanup has one home" (phase-09:212-213, :516-517, :699-700).
- Phase 8: count and link only, "without a second merge tool living here" (phase-08:73, :110, :209).
- Phase 40: data-quality queues "Reuse ... Phase 4 merge" (`roadmap.md:5274`).

**Not established. These sub-points block a complete answer:**

1. **"Queue for merge" mixes two different identity operations.** ADR-0216 merge is a staff decision between _two existing_ same-Tenant records (ADR-0216:17-22). A source row that has not been committed is not yet a record. Before commit, deciding whether a row matches an existing Party (attach/update, create new, or hold) is r02's identity operation (d), "match to an authorized existing identity", not merge (e). The roadmap's plan outcome "queue for merge" (`:4349`) only makes sense as a merge-queue item if the import first **creates** the row as a new record and then files a candidate pair. That pattern deliberately creates a duplicate, which sits uneasily with "Reimport converges on the same permitted target identity instead of creating another copy" (`:4363`) and Phase 40's "prevent-at-entry" (`owner-constraints.md:1373`). The other reading keeps unresolved match decisions **inside the Phase 30 plan review** (or quarantine, `:4395`), and only genuine post-commit duplicate pairs reach Phase 4. Which reading applies per profile is a product or Phase 4 owner choice (see §7).
2. **No Phase 4 command exists for an external producer to file a candidate.** Phase 4 defines `dedupe.scan` (its own matcher) and `previewMerge / executeMerge / unmerge / purgeShell` (phase-04:221-222). It defines no "submit candidate with evidence" command for import, API or Phase 40. Phase 30 must not write `crm_merge_candidates` directly. That table is still Twenty-shaped (`20260508000413_crm_identity_mapping.sql:126-144`), has no Asym-to-Asym candidate columns (phase-04:264 and the :379 build-verify item), and is directly writable by any active staff member (r02 M2). The Phase 4 owner would need to publish that command, or confirm that its scheduled scan, run after commit, is the only intake.
3. **Durable "Not a duplicate" suppression (phase-04:303, :306) has no stated interaction with reimport.** A reimport that resurfaces suppressed pairs would undo staff triage. Whether Phase 30 match evidence must consult Phase 4 suppression is a Phase 4/30 contract detail. It is not published.
4. **Restricted or inaccessible candidates.** For D17 the rule is published: "ambiguous results use the target's permitted explicit choice without exposing inaccessible candidates" (`roadmap.md:4359-4360`). For staff profiles there is no rule; this is already r02's open founder question.

### 4.2 Where do stalled or dead-lettered import runs escalate?

**Established for the dispatch layer (published MUST plus integrated runtime):**

- Every Phase 30 hand-off to Inngest must be recorded in the shared `workflow_dispatch_requests` ledger (`openspec/specs/workflow-orchestration/spec.md:72-73`; Inngest is required by `owner-constraints.md:386`).
- A dispatch dead-letter therefore (a) escalates by default to **urgent staff notification** through the tenant notification policy (`openspec/contracts/workflow-orchestration.md:16-22`); (b) appears on the integrated but unlinked **`/workflows`** page (§2.2); and (c) once Phase 8 ships, becomes **one deduped `crm_escalations` item** on `/crm/operations` (phase-08:107, :149, :171). Phase 8 reads that ledger without filtering by product area (phase-08:105-106, :151). Point (c) is an inference: Phase 8 never mentions imports (§1.1).
- None of these three layers may recover, re-drive or resolve import business state. The dispatch recovery scan "MUST NOT define business outcomes" (spec:76-77). Phase 8 "triggers no recovery of its own" (phase-08:171), and its acknowledge/snooze cannot resolve a cause (phase-08:112; for money, :259-262). Phase 8 escalation bodies are redaction-by-construction (phase-08:109), so they cannot carry row detail.

**Established for the business layer (published Phase 30 text, ratified D29 precedent):**

- The cause-owned next action and per-row counts belong to the **Phase 30 run** (`roadmap.md:4389`). Unresolved records are quarantined "for a visible disposition" (`:4395`). Recovery must keep the same import identity after the browser closes (`:4387`).
- The D29 precedent, ratified for CMS, places this on the **run detail**: durable across browser closure; terminal states include paused-after-partial-write and dead-lettered; retry/resume "reuses the same plan and idempotency records" (decision-log:8101-8118). Operator-level signals (queue age, oldest run, dead letters, mismatches) are a separate audience (:8133-8137).

**Not established (genuine gaps):**

1. **A person's queue.** If a stalled run needs a specific human (the importer, a target owner, or a holder of a reviewer capability), the only ratified cross-domain mechanism is a Phase 30 _Source work projection_ into the Tasks Hub (ADR-0183:24-36, :645-648). No document registers Phase 30 as a producer. Copying the contribution-batch per-row Mission Control task is explicitly not a precedent (ADR-0183:597-605; §2.3).
2. **A Phase 8 catalog signal for import health** (for example, "runs paused longer than N" or "quarantine backlog") would require amending Phase 8's enumerated catalog. Its reserved sockets name only Phase 9 and Phase 6 sources (phase-08:106, :128). Nothing proposes such an amendment.
3. **Actor loss mid-run.** Background jobs cannot yet carry a staff actor's authority (r06; r00:517-519). What the escalation should say when the committing staff member loses access is r06's open founder question. It is not a surface question.

### 4.3 Who owns the Data Tools information architecture?

**Fact:** **no document owns it.** Evidence:

- "Data Tools" appears in the roadmap only as the primary-surface label for Phase 30 (`roadmap.md:4335`) and as one of three Phase 40 surfaces (`:5260`). Earlier roadmap versions say the same (`docs/prds/program-roadmap/source-2026-09-22/previous-roadmap-v2.md:176`, `:186`; `supplied-roadmap.md:1040`, `:1892`).
- No ADR, OpenSpec spec, `CONTEXT.md` term, PRD or Phase 29 spec file defines Data Tools, its sections, its nav placement or its capability (repo-wide markdown grep, 2026-11-01; Phase 29 PR head `1483a349` grep of `docs/features/files-documents/*.md`, `CONTEXT.md`, `CONTEXT-MAP.md` and `openspec/*.md` returns nothing).
- No document owns the Mission Control navigation either. The sidebar is a hard-coded array (`mc-shell.tsx:88-118`). A second, role-keyed list feeds search (`packages/config/navigation.ts`). Phase 12 rules that role names never authorize (phase-12:1545). In specific domains it also rules that "UI visibility ... import" can never mark a route ready (phase-12:227-228) and that "UI visibility, ... imports ... grant neither capability" for Site role commands (phase-12:305-307). A nav entry is presentation, not authority.
- Phase 12 already assumes a "Phase 30 import role" that "never widens" target authority (phase-12:2249, :2327). D29 sets the ratified capability-separation pattern: request, prepare, view plan, commit, repair/resume, prepare reversal, download artifacts (decision-log:7884-7892). Neither defines a Data Tools capability; the registry has none (§2.4).

**Inference from dependency order (not ratified):** Phase 40 depends on Phase 30 (`roadmap.md:5266`; `phases.json:289`), so Phase 30 will be the first phase to _build_ the Data Tools surface. Phase 40 will add data-quality queues and the operator workbench to it, or beside it. Unless someone decides otherwise, Phase 30's choices will become Phase 40's inheritance by default. That is the implicit-design risk this gap names.

**Boundary already ratified around Data Tools:** these import journeys do **not** start in Data Tools.

- CMS content: Web Studio → Content portability (Phase 23 D29).
- Missionary self-import: missionary workspace (Phase 28 D17).
- Recurring operational source intake, for example Phase 21 D14 organization-card activity: that source domain owns it (`owner-constraints.md:424-430`; phase-12:2034-2043).
- Phase 21 D17 opening and D28 travel census: Phase 21 owns the meaning, admission and activation. Phase 30 supplies transport/staging mechanics only (`owner-constraints.md:394-423`). Whether those staff screens appear inside Data Tools or in Phase 21's own surface is not stated.

Whether CMS migration should _also_ be launchable from Data Tools is r00's existing open question (r00:380). D29 ratifies Web Studio as the single content-portability product (decision-log:7870, :8167-8168). A second Data Tools entry for content would need a founder amendment to D29, not a Phase 30 decision.

### 4.4 How entry, resume-after-close, results, reconciliation and reversal sit across surfaces

See the journey map in §5. Summary: every step from entry to reversal is **Phase 30-owned surface work on its own run record**. Neighbours receive only the following hand-offs:

- duplicate pairs → Phase 4;
- dispatch-level failures → workflow policy, `/workflows` and Phase 8;
- correction of accepted target facts → each target owner's command;
- financial certification → Phase 20/21;
- optional human work → Tasks Hub through a registered projection;
- after go-live, continuing data quality → Phase 40 queues built on Phase 8 signals and Phase 30 provenance.

## 7. Facts vs genuine founder choices

**Facts established here (not founder questions):**

1. Phase 30 owns no merge queue or merge action. Duplicate pairs go to Phase 4's single workbench, surfaced by Phase 9 and counted by Phase 8 (§4.1).
2. Phase 30 run dispatches must use the shared dispatch ledger. Dispatch dead-letters therefore already escalate through the published notification-policy contract and appear on `/workflows`, and will appear in Phase 8 once it ships. None of these may resolve import state (§4.2).
3. Entry, plan review, commit, progress/resume, results, reconciliation and reversal are Phase 30-owned surface work on Phase 30's own run record (`roadmap.md:4377`, `:4387-4389`, `:4371`; D29 precedent).
4. CMS content, missionary self-import and recurring operational source intake are ratified to start outside Data Tools (§4.3).
5. No document owns the Data Tools IA or the Mission Control navigation. No Data Tools route, nav entry or capability exists (§2, §4.3).
6. The integrated contribution-batch flow is not a valid journey precedent. It has no resume after a closed browser, and per-row copied tasks are an ADR-0183 non-precedent (§2.3).

**Owner-contract gaps (researchable or owner-decidable, not founder product choices):**

- O1: Phase 4 must publish a candidate-intake command, or state that its post-commit scan is the only intake. It must also replace the Twenty-shaped, staff-writable `crm_merge_candidates` before it becomes an import landing point (§4.1 point 2; G6-D2).
- O2: Phase 4/30 must decide whether reimport match evidence respects durable "Not a duplicate" suppression (§4.1 point 3).
- O3: Phase 8 must fix its duplicate-backlog reader (G6-D1).

**Genuine founder product choices (proposed for the frontier; each must be checked against r02/r06 questions before asking, to avoid duplicates):**

- **F1 — Data Tools IA and entry point.** Is Data Tools a dedicated Mission Control area that Phase 30 creates now and Phase 40 extends later? What does v1 contain (for example: New import, Runs, Saved mappings/templates, Reconciliation reports)? Where does it sit in navigation, and which capability shows it? This overlaps r06's "Where should Data Tools sit in Mission Control navigation?" and r02/r06's permission questions; merge them into one question.
- **F2 — What "queue for merge" means for staff profiles.** (a) Unresolved matches stay in the Phase 30 plan review or quarantine and no duplicate record is created; only genuine post-commit duplicate pairs reach Phase 4. Or (b) the import creates new records and files candidate pairs into Phase 4's queue. Either answer needs Phase 4 owner agreement (O1). It interacts with r02's attach-on-single-match question.
- **F3 — How stalled or quarantined runs reach a person.** v1 = run detail + run list + notification-policy escalation only, or Phase 30 also registers as an ADR-0183 Tasks Hub source producer for runs or quarantined rows that need a named human.
- **F4 — Where operators see import-specific health** (oldest paused run, quarantine backlog, reconciliation mismatches). Options: an operator view inside Data Tools, or a proposed Phase 8 catalog amendment adding import-run signals. Dispatch dead-letters are already covered by fact 2.
- (Lower priority) **F5 — Placement of Phase 21 D17/D28 opening-census staff screens:** inside Data Tools (Phase 30 surface with Phase 21-owned meaning) or in Phase 21's own surface. Phase 21's meaning and authority are unchanged either way.
- (Existing, not new) CMS from Data Tools (r00:380) would need a founder amendment to D29.

## Resolution

**Partially resolved.**

- **Boundaries: resolved from published text.**
  - Phase 30 hands genuine duplicate pairs to Phase 4's single merge workbench, surfaced by Phase 9 and counted by Phase 8. It builds no merge queue.
  - Its dispatches use the shared ledger, so dispatch dead-letters already escalate through the published notification policy and appear on `/workflows`, and will appear in Phase 8 once it ships.
  - It owns every journey step on its own durable run record: entry, plan, commit, resume after a closed browser, results, reconciliation and reversal.
  - Continuing data quality belongs to Phase 40, built on Phase 8 signals and Phase 30 provenance.
  - CMS content, missionary self-import and recurring operational sources are ratified to start outside Data Tools.
- **Not resolved: these need decisions, not more research.**
  - Who owns the Data Tools IA. No document owns it; F1.
  - What "queue for merge" means before commit, and the missing Phase 4 candidate-intake command. F2, O1.
  - Whether stalled or quarantined runs reach a person through the Tasks Hub. F3.
  - Where operators see import-specific health. F4.
- **What would close them:** a founder ruling on F1–F4; a Phase 4 owner contract for candidate intake and suppression (O1, O2); a Phase 8 reader correction (O3).

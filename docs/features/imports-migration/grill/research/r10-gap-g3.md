**What this settles.** As far as the repo and tracker show, the Phase 30 acceptance gate (`roadmap.md:4403`) has no supplier. There is no consenting tenant, no sample export, no vendor sandbox and no WMTEK exit-package answer (r07 checklist item 25, `r07-sitestacker-sources.md:334`). The roadmap's open decisions already list "the first supported source export profiles" (`roadmap.md:4409`). The repo cannot answer three things:

- whether any prospective Asym tenant runs SiteStacker today;
- whether such a tenant would consent to give Asym a de-identified or full export for kit development;
- whether WMTEK offers a sandbox or a database package.

Only the founder or the tenant relationship owner can answer these.

**Three ways the gate could be met, and what each proves.** Choosing among them is a founder question; listing them is not.

1. **Consenting customer export.** This is the only path that can answer the "coverage questions only real exports can answer" (`r07-sitestacker-sources.md:336-347`): headers, ID columns, row caps, encodings, currencies actually present, overlap between Historic Giving and Contributions, and merged or deleted donors. It needs a data-processing basis, a custody location for the bytes (Phase 29 private custody is unbuilt, see `r00-index.md:400` and PR #2430) and a retention rule. Before any byte arrives, that turns kit development into a live-PII handling event.
2. **Vendor-supplied sample or sandbox from WMTEK.** It could show real export formats without customer PII. No public evidence says one exists (`r07-sitestacker-sources.md:198`, "unverified; must be asked of WMTEK").
3. **Synthetic corpus built from documented import templates.** It can exercise only the _import-template_ formats SiteStacker documents. The _export_ formats are undocumented (r07 V10). A synthetic corpus would therefore test Asym's own assumptions, not SiteStacker's real output. Whether it counts as "representative" under `roadmap.md:4403` is an owner interpretation. Read plainly, the gate's wording ("fresh-build assumptions are not a substitute for evidence") points against relying on it alone.

### 3.4 Corrections and refinements to r07 and its verifier

1. **Export time limits fail loudly, per the snippets. Silent truncation is not supported.** The r07 verifier wrote that time limits "can silently truncate a complex Reports/BI extract" (`r07-sitestacker-sources.md:437`). The 2.48 snippet says long exports "will result in an error", and 2.49 raises the limit for complex reports. The real risk is different. A customer who hits the limit narrows the filter and exports in several pieces. That produces a **partitioned extract whose pieces must be proven complete and non-overlapping**. Checklist addition: record every export's filter, row count and any failed attempt, and reconcile the union of the pieces against the UI control count (r07 item 3). Whether some older version truncated silently is unverified.
2. **"Update-by-import" is narrow and recent.** Snippets show address updates via import (2.47) and campaign updates via import (implied by the 2.49 fix). Nothing shows CRM person, contribution or entity-value updates keyed by `external_id` (r07 §4.2, `r07-sitestacker-sources.md:222`). One effect matters to Phase 30: a source tenant may have **re-imported over its own data**, so SiteStacker's current values may already be the product of earlier imports (inferred). This strengthens r07 discrepancy 1's advice to expect side effects of earlier imports in historic data.
3. **Export encoding varies by version.** The 2.47 fix for CSV characters in Excel suggests that exports from earlier versions may differ in encoding or BOM handling (inferred). Checklist addition to r07 item 1: record the installation version **at the time of each export** and the detected encoding of each file.
4. **The Link Set value format is unknown.** It is a fourth entity-value form after single, multi-value and Linked Entity. Its serialization in grid exports is undocumented (verifier missed item 2, `r07-sitestacker-sources.md:437`, stands).
5. **Redirect and source-code imports.** They show that SiteStacker has redirect and source-code _import_ templates. The snippets document **no** redirect or source-code _export_. Redirect capture for Phase 23 D29 and source-code capture for attribution still depend on a vendor package or a crawl (r07 §6, `:279`).
6. **The platform family is confirmed as CakePHP 2.x** (2.47 snippet). That is consistent with r07's inference of a PHP/MySQL-style hosted database (`r07-sitestacker-sources.md:198`). It proves nothing about whether a customer is entitled to a database export.

### 4.3 Repo precedents for how a census is done (these are not Phase 30 decisions)

- **ADR-0179 / Phase 23 D35** (founder-ratified 2026-08-24). Re-prove environment identity. "Census repository artifacts and named non-production state in dry-run mode". Classify state as fixture (discard and regenerate), derived (rebuild), deliberately retained (transform) or unresolved (blocks the environment). Stop destructive work if a target is production or customer-relied-upon (`docs/adr/0179-…:26-32`, `:84-89`). Ticket #1420 (P23-80) requires "Stage, validate, checksum and reconcile counts without source mutation" for retained state.
- **AL-491 field-policy census**: read-only metadata capture bound to project, timestamp, Postgres version, latest migration and repo SHA, with SHA-256 digests and no business values (`docs/security/field-policies/README.md:7-16`; `census-v1.json:3-14`).
- **#2067 document-cutover reader**: a dedicated NOLOGIN Postgres role over private-schema, counts-only `SECURITY DEFINER` functions (`schema_version`, `auth_user_count`, `table_census` returning `row_count` and `tenant_count` for an allowlisted table set) with `row_security = off` so a filtered read raises instead of under-counting (`supabase/migrations/20261021064500_document_cutover_reader.sql:1-20`, `:84-112`; `packages/api/src/document-cutover/database-contract.ts:1-80`). Its allowlist covers only PDF/receipt prototype tables. It is integrated source; whether it is applied to any hosted database is unverified, and under H5 production would not have it.
- The Phase 13 "fresh-build, no-migration-ceremony posture" needs scoping against this gate (r01 verifier, `r00-index.md:96`). The 2026-08-18 and 2026-10-05 observations show that "fresh build" is not the hosted reality.

## 5. What a hosted census needs (specification only; nothing here was run)

This is the minimum evidence that would satisfy "Census actual retained state before migration" (`roadmap.md:4403`) for Asym's own target. It is built from the repo precedents in §4.3. The mechanism and the operator are owner choices (§7).

### 5.1 Preconditions

1. **Authorization and operator.** Someone with hosted access, as in the Phase 0 "Lane 2 … pending a human with hosting access" (`2026-07-03_sitestacker-parity-phase-00-baseline.md:5-6`), or an approved read-only role. This research had neither and ran nothing.
2. **Named targets.** Production `btewedpsxwsjczvmegby` and development `pnmlrbgjiqzzsthsoikm` (named in `20260818010000_retire_twenty_crm_runtime.sql:2`), plus any preview branch that is a Phase 30 rehearsal target. Each must be re-proved production or non-production before any destructive step (ADR-0179 step 1, `docs/adr/0179-…:26-28`).
3. **Output policy.** Counts and catalog metadata only. No business values, identifiers or credentials beyond tenant IDs and their classification (AL-491 precedent, `docs/security/field-policies/README.md:15-16`).
4. **Binding.** Record query text, raw-response SHA-256, `captured_at`, Postgres version, operator and the repo commit compared against (AL-491 form, `census-v1.json:3-14`).
5. **Timing.** "Before migration" means per target and immediately before each tenant's first import, bound to the schema version then present. It is not a one-off. Under H5, production must also take the 58+-migration backlog. #2083 plans "the backlog, as its own deploy" first (spec r1 §13). That backlog drops tables (`20260818010000:14-19`) and normalizes currency (`20261003051630:217-222`). A census taken before it describes a schema about to change. A census taken after it is still required, because the backlog does not empty retained rows.

## 6. What this means for how the grill frames Phase 30

1. **The first-source and export-profile question comes second.** `roadmap.md:4409` lists "the first supported source export profiles" as open, and r07 Q1 offers three profiles (grid CSVs, export pack, vendor package). An earlier question sits in front of it: _where will the first real SiteStacker export come from, and under what consent and custody?_ Three facts force this ordering:
   - there is no artifact (§2);
   - SiteStacker's export formats are undocumented (r07 V10);
   - the newer docs are offline or customer-login-gated (§3), and installations change monthly (§3.2).

   Whatever profile is chosen, the first kit deliverable can only be an **evidence intake** (r07 §7 checklist plus the §3.4 additions). Presets come after it.

2. **Kit scope: every named component waits on an artifact.**

   An honest grill can rule on _what_ each component must do. It cannot lock formats or presets until one artifact set exists.

3. **"Source basis" needs a definition.** `roadmap.md:4369` requires totals "by Legal Entity, original currency and source basis". The roadmap uses the term in several phases (`:4542`, `:4643`, `:4876`, `:5278`), but CONTEXT.md has no entry for it (ripgrep, 2026-11-01). For SiteStacker, documented candidate bases include Contributions transactions, Contributions designations, Recurring schedules, Historic Giving `donation` rows vs `ledger` rows, the Statements report and processor reports (r07 §2.2-§2.3, checklist #12-#19). Which bases a tenant actually has, and whether Historic Giving duplicates Contributions, is an export fact. _What the term means_ for Phase 30 reconciliation is a definition an owner must ratify, preferably aligned with the Phase 33 semantic layer, which also preserves "source basis" (`roadmap.md:4643`).
4. **The acceptance gate can be stated honestly.** Phase 30 cannot be accepted until two things exist:
   - (a) at least one real SiteStacker export set, obtained under an agreed consent and custody basis;
   - (b) a census of each target's retained state, bound to a recorded schema version (§5).

   Both depend on things outside engineering: a source relationship, and hosted access with authorization. Neither is sourced in the repo today.

5. **Retained state is a cross-owner disposition, not a Phase 30 cleanup.** The objects a census may find belong to other owners:
   - Twenty-era link tables: CRM-retirement invariant, P4/P9;
   - `backup_money_*`: money history;
   - `donations.source = 'import'` labels: P13 entry method;
   - demo tenants: release owner (the ADR-0179 pattern).

   Phase 30 can require the census and block on unresolved state. Deciding what happens to each class is routing for the founder and owners. This is consistent with the r00 completeness critic's open conflicts on `crm_record_links` and `donor_merge_redirects` (`r00-index.md:855-856`).

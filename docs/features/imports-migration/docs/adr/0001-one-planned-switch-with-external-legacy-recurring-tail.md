## Context

A ministry leaving SiteStacker keeps receiving gifts, edits and opt-outs while it moves. No owner text defined a switch model for supporter (CRM) data, although `roadmap.md:4363` requires every imported record to carry a historical/cutover disposition and `:4395` forbids promising permanent dual writers. SiteStacker stores only processor tokens and runs its own recurring scheduler; PayPal subscriptions run in PayPal; Asym cannot lock or observe SiteStacker. Phase 13 says "observation is not control" (P13 :735-741), and Phase 16 makes moving any recurring gift a formal cutover that needs proof the old executor stopped plus fresh collection authorization (P16 :1314; "replace/bind method" is _Complete with donor now_).

## Decision

Each ministry leaves SiteStacker through one planned SiteStacker Switch: practice runs that write nothing to target owners, a recorded Switch Boundary with a ministry editing pause, one final multi-file Source Snapshot Manifest, owner-command imports with no outward effect, two-level reconciliation by Legal Entity × original currency × source basis, then go-live. At the boundary Asym becomes the system of record and only writer for supporters, consent, relationships, custom data, history and staff work. Legacy recurring executors are **not** switched off: they stay externally controlled and read-only under Phase 16 through a bounded Legacy Recurring Tail (default no later than 12 months after go-live), whose money, stop and restrict-only contact facts arrive through separately reviewed Legacy Tail Backfills that never write supporter details. The switch is _live_ when supporter authority moves and _closed_ when every legacy executor is handed over, ended or reclassified and the tail is closed. After go-live, authority never returns to SiteStacker without a new founder decision. Exact repeat import means replaying the same sealed manifest; any other snapshot converges on Source Record Bindings, never source-wins and never deletion by absence.

## Considered options

- **Area by area (B):** rejected for v1. It needs per-family live authority and identities Asym creates that SiteStacker would have to reference; no owner text defines either. Records keep one boundary per source family so B can be added later without a retrofit.
- **Side by side with refresh imports (C):** rejected. It needs per-field three-way memory and drift review, risks two automation engines contacting the same donors, makes reconciliation against one snapshot impossible, and drifts toward the permanent dual writer `roadmap.md:4395` forbids.
- **Token migration with no donor step:** common vendor practice, rejected for v1 because Phase 16 requires fresh authorization; attrition is measured at the first switch before any Phase 16 amendment is requested.

## Consequences

- SiteStacker stays licensed, with its recurring engine, receipts, reminders and cancel path running, until tail closure; the "turn automations off" instinct is replaced by per-surface Legacy Surface Dispositions.
- Phase 30 never coordinates processors, transfers vaults, handles card or bank numbers, or proves an executor stopped; the Phase 13/16 "separate migration workstream" needs named owners before any ministry with recurring giving can switch (decision-log O12).
- A switch cannot be scheduled until every Minimum Switch Kit family is committable through its owner's import command.

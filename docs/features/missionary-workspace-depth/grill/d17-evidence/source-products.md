# D17 source-product interoperability evidence

Research date: **2026-10-16 UTC**. The founder selected missionary self-service
contact-list intake and requested broad source-tool interoperability, custom
Excel sheets, clean data and simple UX. This is research and a proposed bounded
profile, not a ratified field contract, adapter implementation or tested migration.
Only public documentation and public example files were read. No accounts,
authenticated exports, uploads, imports, messages or live mutations were used.

## Recommendation and authority

Provide one native, reviewed **CSV/XLSX contact-intake journey**, with helpful
source-specific mapping suggestions and export instructions. Advertise the
supported contact fields and formats, not complete migration from every named
product. A source selector can improve instructions; it must not become a list
of supposedly verified integrations. A custom spreadsheet uses the same review.

This is proportionate to the selected job: preserve useful existing contact
information without retyping. Source-tool interoperability is a property of
qualified formats, field mappings and actual fixtures. A vendor's ability to
export data does not establish an Asym adapter or permission to import every
exported field.

The [Q17 frontier](../phase28-q17-contact-list-intake-research.md) identifies the
bounded P30 missionary actor extension. [P30](../../../../prds/sitestacker-parity/roadmap.md)
already owns CSV/XLSX transport, reviewed plans, mapping, provenance, recovery
and target-owned acceptance; its current staff actor is not blanket missionary
authority. The [founder brief](../phase28-founder-brief.md) requires source-owned
validation and forbids inferred consent and historical outreach. D1 restricted
preparation, D2 deliberate staff availability and D5 field-specific corrections
remain controlling. Import is not a route to broader shared-record edits.

No new library, embedded importer, source API connection or continuous sync is
selected here. Use the current P30/P29 seams and existing shared base-maia/Base UI
language; source presets are not separate import applications.

## Evidence classifications

- **D:** current public official documentation read on the research date; actual
  authenticated behavior was not tested. A date below is the page's stated date,
  not an inferred release date.
- **S:** public sample bytes retrieved and inspected in memory. These are vendor
  import templates/examples, **not authenticated exports or complete schemas**.
- **M:** current official marketing claim; does not establish formats or fidelity.
- **H/U:** historical evidence or an unresolved current capability. Failure to
  find public instructions is not proof that the product lacks the feature.

## Minimal useful UX

Use one coherent **Import contacts** entry and progressive disclosure. A native
file picker must work; drag-and-drop is optional. Do not require an account
connection, source-tool login or a vendor logo selection before a generic file
can be reviewed. Offer a small template and verified export instructions nearby.

1. **Choose the file.** Show supported formats and actual limits. Explain the
   destination in the existing restricted-preparation vocabulary. Select a sheet
   or header only when needed; simple files proceed directly to review.
2. **Review the proposed intake.** Show source column, example value and proposed
   destination; clearly identify unused columns. Put ambiguous person/household
   mapping, malformed contact data and apparent duplicates where the user can
   correct or exclude them. Normal rows need not require individual approval.
3. **Import the eligible selection.** Show the actual eligible count and any
   held rows, and recheck source authority at commit. Do not present a global
   overwrite-existing switch or a default merge-all choice. A no-write preview
   must not change contacts or subscribe anyone.
4. **Show durable results.** Distinguish preparation saved, unchanged/skipped,
   rejected and pending identity resolution. Keep source row references and
   clear cause-specific next actions. Reopening a closed browser resumes the
   same run; a timeout is not an instruction to upload again.

Suggested concise copy, contingent on the exact owner-qualified states:

- Before selection: **“Bring contacts from a spreadsheet or another tool.”**
- Scope help: **“Review the contact details before importing. This won't send
  messages or sign anyone up for your newsletter.”**
- Unused data: **“These columns won't be imported.”** Name them; do not imply the
  whole record transferred when important fields were excluded.
- Mixed outcome: **“86 contacts added to your preparation. 7 rows need attention.”**
  Use this only if both counts and the target state are actually established.
- Unknown progress: **“We're checking this import's progress.”** Offer the same
  run's status, not a fresh import that might duplicate accepted work.

On phones, preserve a readable row-detail view for mapping and correction rather
than compressing dozens of columns into an unusable table. Desktop may show a
denser shared grid. This is a design recommendation, not evidence of tested
usability or a requirement for a new spreadsheet editor. Existing keyboard,
focus, error association and status-announcement requirements still apply; a
vendor screenshot or template download proves none of them.

## Strongest simpler alternative and unresolved evidence

The strongest simpler implementation is a **single canonical CSV template plus
staff-assisted conversion**. It minimizes parsing/mapping variants and can be
safer for complex historical migrations. Its costs are real for the selected
job: more handoff/reformatting, a poor fit for custom Excel sheets and avoidable
loss risks when source XLSX is converted casually. Given the founder's rider and
existing P30 CSV/XLSX intent, the bounded native profile is preferable; that does
not authorize a universal workbook/database importer.

Before any named preset is described as supported, obtain sanitized authorized
export fixtures or reproducible synthetic equivalents tied to the documented
schema. Qualify exact field aliases, namespaces, person/household representation,

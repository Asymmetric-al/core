Managed partnerships and accepted source obligations are outside this particular choice. The exact qualified source/state/command is not installed in the inspected runtime.

## Material archive-specific hazards and candidate clauses

1. **High integrity/privacy, conditional on choosing the wrong source:** using donor status, deleting a donor, clearing primary missionary association, or moving content into a general CRM note would affect a shared contact/history/audience rather than one voluntary preparation item. The existing status reader/writer mismatch is proven above; a D4 implementation does not yet exist. **Clause:** archive changes only the qualified preparation state for the currently authorized actor/context; canonical contact identity, other missionaries' work, already shared facts, consent/suppression, giving records and task obligations remain source-owned. Restoring does not create a new Party/contact or broaden audience.

2. **Medium/high correctness and usability, likely if the current list filter is copied unchanged:** filtering after offset pagination can show an empty active/archive view while eligible rows exist on later pages, and can tempt duplicate creation. Changing membership of an offset-sorted result set while appending pages can skip/repeat rows. **Clause:** apply authorized active/archive eligibility before paging; give search/counts their real scope and reconcile page membership when archive/restore or sort changes. Keep stable IDs, bounded reads and current tenant/context in the query/cache boundary. This does not prescribe a new search service or a specific cursor design before a source is chosen.

3. **Medium/high correctness, conditional on ambiguous success/concurrency:** a network failure can follow a committed archive; naive retry/Undo or whole-array rollback can show a false result or undo newer work. Current donor client discards the successful response body. **Clause:** the qualified command has a recoverable, idempotent result for the same intent, checks current state/authorization and handles a concurrent edit/archive/restore without blind overwrites. Distinguish a committed archive from a failed refresh and an unknown outcome. “Archived” or “Restored” requires authoritative success; a restore checks current access and does not recover expired permission.

4. **High privacy, conditional on bypassing the original read boundary:** an Archived filter, search result, count, toast, detail deep link, stale cache, export or activity/audit text can accidentally become a broader read path. Archival state alone is not a security grant. **Clause:** archive/restore and retained discovery preserve D1's restricted audience and D2's explicit sharing boundary, including current authorization on detail/actions and late responses. Do not use an unredacted browser donor query, a global CRM activity or a generic staff-visible log payload as archive storage/feedback. Previously received data cannot be made unknowable; this clause concerns further system delivery and honest open-page handling.

5. **Medium UX/accessibility, conditional on treating disappearance as the whole interaction:** disappearing selection/focus, a transient toast as the only recovery path, or an empty view that recommends creating a duplicate makes a reversible action practically destructive. **Clause:** expose one understandable archive action and a discoverable retained-items path; keep concise pending/error/success feedback, preserve unrelated filters/drafts, and move focus predictably when a row leaves the active list. Undo is optional UI convenience only if backed by the qualified restore operation; no countdown, forced reason, new workflow builder or mandatory confirmation is implied by D4.

6. **High integrity, conditional on legacy writers or scope drift:** the four-status form/API can overwrite a reused shared status; active donor counts use different semantics; task/delete pathways and future lifecycle jobs can treat an archived item as removed. **Clause:** enumerate readers/writers of the chosen source state before enabling it, including old clients/imports and derived summaries. Do not backfill private/shared/archive provenance from mere donor association or status. Unknown/legacy state must not silently mean an authorized active prospect. Keep D3's retention/hold/current-access rules separate: archive does not start a deletion timer or create indefinite-retention authority.

These safeguards can be implemented within the smallest existing qualified source operation once that owner/state is established. The source gap is a qualification requirement, not a new founder question or permission to build a general archive subsystem.

## Smallest meaningful later checks

Confirm contact status, shared facts, consent, giving and linked task obligations do not change. After access/retention eligibility ends, restoration/read fails with an honest unavailable state; there is no duplicate contact or automatic reassignment.

Confirm source state and UI agree and rollback never resurrects unauthorized or newer data. One targeted integration fixture is more valuable than tests that merely mirror a new boolean setter.

Preserve unrelated drafts and redaction. Use the existing shared Base UI/Sonner/list patterns without claiming visual fixtures establish authorization.

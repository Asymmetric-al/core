## Fixed periods, current values

The hypothesis uses a server-captured September range, initially `[2026-09-01,2026-10-01)`, and one deliberate preview adding August. A captured `2026-10-01` upper ceiling keeps the example historical. These are illustrative whole-month source profiles, not selected product defaults, a maximum lookback or an access-expiry date. The fixture does not implement a separately authorized current-period module.

After saving August and September, the admitted dates stay August and September. A relative “last two months” calculation evaluated in November instead becomes September and October; the unsafe control demonstrates that it both drops one month and adds another. Reopening a page, a new import, the wall clock, a chart viewport or a URL must not make that permission change implicitly. A future rolling/accumulating product would require an explicit owner-qualified meaning; this research implements no future-period rights.

The source facts have both `source_date` and `created_at`. September's source total is 300 minor units, even though those facts were recorded in October. Two August facts recorded in September total 100. An intentionally unsafe creation-time query therefore returns 100 for September instead of 300. The source table is an already-qualified effective designated-money stand-in, not real contributions, P7 dating facts, fee-cover handling or P13 correction machinery.

A new synthetic source revision moves the 60-unit fact's authoritative date from August 1 to September 15. Current August/September values become 40/360 instead of 100/300. The old source revision and snapshot remain retained, but the old snapshot is not a current financial answer or permission to disclose. The source revision is a fixture publication boundary; the probe does not derive a P7 successor chain or a P13 effective money fold.

Each requested month also needs complete coverage at the current source revision. A selected July with no coverage record yields unavailable; only after the fixture explicitly supplies complete empty July coverage can July be zero. This models the need for source-certified completeness, not proof that a missing source import, old cache, empty query or selected date range establishes it. Incomplete/suppressed/unknown source states must not be represented as zero, poor effort or a gap joined by an invented chart line.

## Bounded roles and concurrency model

The real login roles `coach_a`, `missionary_a` and `source_manager` are nonsuperuser/non-BYPASSRLS. `command_executor` is NOLOGIN, nonsuperuser/non-BYPASSRLS and does not own tables. All six tables have enabled and forced coarse tenant RLS. The coach has only the bounded history function and intentional comparison function; the missionary has only preview-apply execution. Neither has base-table access. Default PUBLIC function execution is removed in the setup transaction. Actual roles, table permissions, function owners, search paths and ACLs are captured in [roles.json](postgres-probe/roles.json) and [privileges.json](postgres-probe/privileges.json).

The fixed login-to-tenant mapping is test identity. The `active` boolean and grant revision stand in for a current exact source/P12 decision, not real additive grants, context admission or a global Coach role. Reset and source-publication steps are explicitly recorded synthetic fixture operations. In particular, a test reset is not a proposal to reactivate a revoked D8 sharing episode by setting a boolean.

A preview is server-recorded and binds actor, exact tenant/subject/module, proposed period range, expected grant revision and source revision. Apply accepts only its identifier, rechecks the current grant under a row lock, then source revision, containment and captured ceiling. It cannot accept caller-supplied replacement dates. A changed exact grant or source revision causes conflict; a revoked grant is unavailable. The proof does not implement the full P12 authorization decision, preview producer, audit, expiry, command identity or durable retry receipt.

History release locks the current exact grant, source head and each coverage row. It checks the requested finite whole-period subset before arithmetic and keys retained snapshots by exact tenant, subject, module, coach, grant revision, source revision and requested range. A later narrowing or source change cannot select an old snapshot as current. The executor has narrowly granted UPDATE privileges necessary for locking SELECT; the tested functions do not expose source/grant changes to the coach.

This multiple-read/month loop is deliberately small and is not a production query plan or satisfaction of P12's R6 budget. The actual source must use the approved set-based projection, current read audit, privacy floors and source-currentness mechanism. The tables in this folder are not migrations or a proposed second projection framework.

## Proposed technical clauses

**DB10-01 — Capture dates, not a moving label.** Resolve approved earlier-period choices server-side into exact finite source-calendar periods attached to the exact current share/profile. Preserve their identity across navigation and calendar rollover. Query ranges may select a permitted subset but cannot widen authority. Adding dates is a deliberate qualified share change; it does not follow from cache retention or current-period access.

**DB10-02 — Source dates and current effective history.** Received history retains D9's qualified current-effective designated-money and authoritative gift-date definition. Import, creation and correction timestamps do not select the reporting cohort. Dating/money corrections propagate through their owners, with current source evidence; old snapshots are neither a frozen official statement nor current disclosure authority. Historical expected support uses a separately qualified P16 historical population, never today's active terms projected backward.

**DB10-03 — Preview identity and reduction fences.** A widening command binds the reviewed exact subject/module/period meaning and relevant source/authority evidence. Requalify current authority at apply and serialize against revocation/narrowing through the adopted source-command mechanism. Stale preview, browser Back or retry cannot restore removed dates. A legitimate later extension is a new deliberate qualified change; reactivation of a terminal sharing episode follows D8. The full product still needs its existing semantic idempotency and audit contract; this CAS fixture does not replace it.

**DB10-04 — Current release evidence for every historical point.** Before serving, use the exact still-authorized period subset, source/admission revisions and source-certified coverage. Missing, incomplete, suppressed and stale are not zero. Bind materialized results and all chart/table/accessible alternatives to the same current evidence. Actual source changes need reliable invalidation/rebuild; an old cache key is not permission.

**DB10-05 — Preserve inherited privacy and finite product scope.** Earlier periods add longitudinal disclosure, not raw gift/donor/commitment access. Apply D9/P3/P10/P12 input admission, derived sensitivity, tenant-tunable small-cell floor and combined/repeated-release assessment before arithmetic and egress. No SQL date predicate proves privacy. Use existing source profiles and sharing commands rather than a custom query builder, new policy engine or universal invented lookback/privacy threshold.

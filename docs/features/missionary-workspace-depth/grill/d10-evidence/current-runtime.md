# D10 — earlier support-summary history: current runtime evidence

**Subsequent status — October 16, 2026 UTC:** the founder explicitly ratified
the [D10 corrected decision and amendment](../phase28-d10-adversarial-review.md),
including C01–C20/P01–P28. The research below preserves its pre-ratification
reasoning and candidate language; only the reconciled main review defines the
ratified amendment. No runtime or source qualification is implied.

Research only, 2026-10-16 UTC. D10 selects the ability to deliberately share eligible earlier financial summary periods within the organization's permitted scope. It does not make every retained record or every previous coaching activity visible. This note owns runtime evidence only, not the final product decision or formal owner amendments. No application, dependency, database, account or external communication was changed.

## Main result and verification scope

The existing Last 6m / Last 12m analytics control works as a local display selector. It does not request or enforce a server-authorized history range. The underlying endpoint returns individual donation rows for a rolling 13-month creation-time window; it has no coach history-floor, reviewed period selection, historical metric version or as-of input.

A new [actual-hook probe](history-probe/README.md) executed unchanged repository code through installed real React/Testing Library/jsdom with controlled fetch input and a fixed clock. **6/6 assertions passed**, confirming current behaviors, including defects: final-day exclusion, creation-date attribution, local-only selectors, stale period after rollover, retained data after clearing subject, and UTC+14 month-window drift. It did not execute HTTP/Supabase, a real browser, authorization or notification delivery. Existing D9 math and D8 auth probes were not rerun.

Eight concern dimensions below separate observed behavior, static source findings and proposed launch requirements. Earlier periods amplify existing D9 money/privacy risks; this note links those findings rather than repeating their arithmetic tests.

## HR01 — Security: a display range is not an authorized history projection

**Critical impact if reused for coaches; certain missing contract in the inspected path.** The analytics selector changes React state and calls `selectGivingTrend(..., 6|12)` (`page-client.tsx:60–77`). That helper simply slices an already-present array (`analytics-data.ts:32–48`). The hook requests only `/api/missionaries/{subject}/metrics` (`use-donation-metrics.ts:186–189`). The handler reads the subject path parameter but no from/to, approved-period selection, historical floor, source metric version or authorization epoch (`metrics.ts:161–254`). Its own/staff subject checks are not a bounded coach-history grant.

The probe confirms both selections return six/twelve local points without another fetch. This is **not** a claim that an accepted API date parameter is broken or a real UI selection is ignored: no such server parameter exists. Appending guessed bounds would not make them authoritative because this handler does not consume them.

**Clause candidate:** “The server derives the exact permitted represented periods from the current reviewed share, organization ceiling and source-qualified history projection. A client period selector only selects among those choices. Validate the requested period, context, subject, metric and current floor before enumeration and again at protected result release; unsupported or stale choices do not silently widen or redefine the result.”

**Proof:** Tampered bounds/period identifiers, stale bookmark, another subject/Tenant, removed earlier period, internal coach's unrelated staff powers and concurrent grant narrowing. Inspect all returned data, not only the visible six bars. No raw donor history or current missionary permission may substitute for the selected coach history grant.

## HR02 — Financial meaning: historical attribution is currently creation time

**High impact; actual-hook behavior plus exact query evidence.** The API selects and filters `created_at`, not source gift date/effective date (`metrics.ts:251–254`); the hook groups the same field (`use-donation-metrics.ts:65–69,98–102,254–260`). In the UTC probe a gift with March `gift_date` and October `created_at` is counted in October, with March zero. The extra gift-date fixture is intentionally ignored by the real hook; the real endpoint omits it altogether. A newly imported older gift could therefore look current under this legacy read path.

The portal uses `gift_date || created_at` for a displayed gift date (`model.ts:235–236`), so its label and the analytics cohort can disagree. Neither existing path provides a source-qualified historic expected-support metric. Current funding/goal counters and today's commitment state do not establish past expectation or past goal history.

**Clause candidate:** “A history choice governs the period represented by the qualified source metric, not record creation, import, correction, invitation or read time. Older source records may contribute to an eligible current metric without granting their private old terms; a recent import/correction cannot move older represented facts inside a current-only boundary. Expected, received and independently permitted goal comparisons retain their own exact basis.”

**Proof:** Backdated/imported receipt, late correction, prior-period recovery, amended commitment, retired designation and source effective-date change. Check attribution against the actual source fold/occurrence, including cases where a late change affects an earlier eligible period. Do not fabricate historical schedules from today's totals or infer access to old goal revisions.

## HR03 — Date correctness: month ends and timezone disagree in actual execution

**High impact; reproduced in the real hook.** Last-month end is `new Date(year, month, 0)`, meaning the last day at local midnight; the filter is inclusive `<= end` (`use-donation-metrics.ts:236–258`). With fixed UTC time October 16, a September 30 noon receipt is excluded from `lastMonth.total` but included in September's monthly breakdown. The probe records zero versus 10000 for the same input.

Month buckets are seeded at local first-of-month midnight then converted to UTC `YYYY-MM` (`82–101`). With the same fixed instant in `Pacific/Kiritimati` (UTC+14), the generated 13-month breakdown ends in September, omits an October receipt and contains only zero totals, even while `thisMonth.total` counts that receipt as 10000. This is actual unchanged hook execution in jsdom under Node's explicit TZ, not a browser timezone matrix.

**Clause candidate:** “Use the source-governed giving timezone and exact supported reporting-period boundaries consistently for query, aggregation, labels and comparisons. Calendar intervals are start-inclusive/end-exclusive; do not mix browser-local boundaries with UTC bucket identity or give two widgets different periods for the same label.”

**Proof:** First/last instant, final-day noon, UTC+14/negative offsets, DST, leap day, month/year rollover and date-only source facts. Validate the server metric and actual rendered accessible date explanation together. No source-wide timezone or financial-period change is implied by a coach preference.

## HR04 — Historical truth: current corrected totals are not a preserved past view

**High impact; certain semantic gap if an old-period result is described as “what was shown then.”** Current queries read mutable/latest donation values and status, with no version/as-of selector or coherent financial cutoff. The refund writer can change status/refund facts after the original period (`refunds.ts:162–176`); D9 already establishes that current gross/status totals are not the qualified effective ledger fold. This source evidence proves no as-was snapshot capability. It does not mean historical source versions cannot exist elsewhere.

The alternate cached `getMissionaryMetrics` also sums current rows by `created_at` (`reads/missionary-metrics.ts:139–152,197–220`); naming a cached result “history” cannot make it source-versioned. `getDonorHistory` is a paginated individual transaction list, not a historical coaching measure or a permission to expose its rows.

**Clause candidate:** “Every historical summary declares whether it is the source's currently corrected value for an earlier represented period or another explicitly qualified historical metric. Do not claim it reproduces what someone saw or expected at that earlier time unless the owner can prove that exact version. Preserve source cutoff, metric version and correction semantics; unavailable history remains unavailable.”

**Proof:** Same earlier period before/after correction; changed commitments; re-designation, refunds and incomplete imports; old published versus currently corrected source views. Show a coherent qualified result without mixing old denominator/new numerator, or say unavailable. Retention of old source/audit facts never grants coach access or creates an editable historical ledger.

## HR05 — Reliability and revocation: current period and selected subject do not invalidate all hook state

**High correctness impact; critical disclosure risk under unsafe future reuse. Actual hook evidence is narrower than a demonstrated access incident.** Fetch is keyed only by `missionaryId` and memoized metrics only by the donation-array reference (`use-donation-metrics.ts:172–228,230–290`). In the UTC probe, advancing the clock to November and rerendering the same subject preserves October's breakdown and `thisMonth.total=20000` without a new request. Clearing the subject to an empty string then retains that data with `isLoading=false` and no error because the early return clears only loading (`173–175`).

This does not prove production grant revocation uses that empty-input transition, nor that every navigation avoids remount. It does show why a future history selection/current-grant boundary cannot rely on the existing hook to clear or refresh itself. Existing cancellation (`224–227`) and explicit permission-limited errors (`205–207`) are positive behaviors and must be retained. They do not supply a historical floor or epoch.

**Clause candidate:** “Period rollover, selected-history change, context/subject change, restriction, expired access and current grant narrowing invalidate the affected display and in-flight work. Cached or local values cannot remain presented as currently authorized/current-period data after the context is absent. Source corrections trigger the qualified refresh policy; rejoining does not restore revoked history.”

**Proof:** Open view across reporting rollover; remove the selected context; narrow old-period rights while a request is in flight; delay a former context's response; correct a historical source; browser back/forward and another tab. Prove server release fencing and client clearing with real authorization. Do not claim recall of screenshots or previously disclosed human knowledge.

## HR06 — Completeness and cost: more displayed history is not more complete source coverage

**High accuracy impact; deterministic caps in source, deployed data-volume effect unverified.** The portal caps donations at 250 before in-memory settled filtering (`service.ts:194–203`). The live metrics route retrieves ascending raw rows without pagination or coverage metadata (`metrics.ts:249–279`); checked-in Data API configuration caps returned rows at 1000. Selecting twelve months just slices the existing browser array. Neither choice requests complete qualified period aggregates or reports a partial result.

The rolling API interval cannot support the hook's full previous-year YTD comparison at many dates: at the fixed October 16, 2026 clock, its rolling lower bound is September 16, 2025, while the comparator starts January 1, 2025 (`metrics.ts:246–247`; hook `246–270`). This is a static query/coverage deduction; the probe did not execute the endpoint or model database caps. The rolling query also returns some history earlier than the 13 displayed calendar-month buckets, reinforcing that fetched rows and selected display periods are different scopes.

**Clause candidate:** “Earlier-period availability requires complete, source-qualified aggregation for that exact authorized range, currency and cutoff. A capped row response, available browser cache or padded zero bucket is not complete history. Bound supported ranges, output cardinality and query cost through the existing source read path; return explicit unavailable/partial state when completeness is not established.”

**Proof:** 250/251 and 1000/1001 boundary datasets, pending rows consuming a cap, missing older partitions, partial imports, late corrections, incompatible comparison windows and repeated period switching under realistic load. Measure the actual aggregate query; do not remove caps and send the entire financial row corpus to browsers as the fix.

## HR07 — UX and accessibility: labels must reveal the real period and financial basis

**Medium–high impact; exact current UI evidence, no new usability claim.** Existing 6m/12m controls have a named combobox and the UI test exercises the real Select with mocked metric results (`analytics-period.test.tsx:90–144`). That is useful evidence that the selector is implemented, not proof of a historical authorization boundary. The actual chart data carries only short month names (`use-donation-metrics.ts:119–138`), losing year and exact date bounds. The overview has 13 points, so a month name repeats across years.

Analytics intentionally drops offline gifts and divides recurring/one-time sums by 100 (`analytics-data.ts:10,19–48`), while the dashboard's broader breakdown includes offline data and its tile unit defect is separately recorded in D9. Thus “Support Overview” or “No giving activity yet” can obscure that this particular historical view covers only online categories. This is not a repeat claim that Analytics has D9's tile 100× bug; its converter exists. The hardcoded currency conversion remains a D9 owner concern.

**Clause candidate:** “Before sharing and while viewing, show actual represented dates/year, governed timezone where relevant, metric basis, currency, coverage/freshness and whether the range is fixed or moves. A finite supported selector may be simple, but its label cannot conceal a different source period, omitted category or future range behavior. Accessible tables, tooltips and announcements disclose only the same approved combined result.”

**Proof:** Coach and missionary can explain the selected dates and whether an old period is corrected; keyboard/screen-reader period selection; ambiguous repeated month labels; online-only versus all-received comparison; withheld cells and unavailable history. Do not add arbitrary date-query builders, old goal history or every retained category merely because earlier summaries are allowed.

## HR08 — Operations and integration: source history, cache and notices retain separate owners

**High impact under shortcut integration; no current history notification producer identified.** Current historical-looking readers expose read-cache tags and minutes-based caching (`reads/missionary-metrics.ts:74–94`; `reads/donor-history.ts:37–66`). The cache tag module itself says these read tags have no current mutation invalidator (`cache-tags.ts:65–80`); a bounded API-tree search found only the definitions/readers. Next cache arguments still contain their Tenant/subject arguments—tag naming alone is not evidence of a cross-Tenant cache collision. Neither reader demonstrates the future reviewed-history version, current grant epoch, financial cutoff or restricted-output release rules.

The current analytics hook/selector is read-only local computation; the inspected path does not enqueue notifications. D9's local display alerts are not communication intents. Access duration remains different from represented period, and changing an earlier-period selection is not a new task, reminder or fundraising-performance event.

**Clause candidate:** “Use existing source owners for historical truth, P12 for current access/floor/version, and the qualified cache/read path for bounded projection. Keep a content-minimal audit of the reviewed history scope and consequential changes without copying raw financial rows into logs, notices or a second historical store. A selected range neither extends access duration nor starts a notification subscription.”

**Proof:** Source correction, narrowed history, expired access, cache restore, deployment rollback and retried reads preserve current fences and honest source cutoff. Changing/reading a range creates no new email, notification or task. Any later independently selected message still requires its own source meaning/preference and P6/P17 recipient/content/send-time qualification; D10 cannot use a history snapshot as permanent delivery authority.

## Executed evidence and remaining gates

The [probe pack](history-probe/README.md) contains the exact script, two exact JSON outputs and run manifest. It imports unchanged `useDonationMetrics` and `selectGivingTrend`, uses installed real React/React DOM/Testing Library/jsdom, and supplies only synthetic fetch rows and controlled clock/TZ inputs. Source/probe/output SHA-256 digests and installed package versions are retained. Both runs exited zero with empty stderr and unchanged imported source hashes. Six passing assertions establish observed existing behavior, not a ready D10 implementation.

No D9 model check or D8 auth check was repeated. No full Vitest suite, database migration/query, applied RLS, real HTTP call, deployed service, real browser/assistive technology, provider or notification path ran. The successful jsdom seam avoided unrelated application test configuration. Static findings retain their limits; no live financial error, leaked record or deployed history-grant behavior is alleged.

Before launch, qualify one bounded existing-owner historical summary path with explicit represented period, current authorization, financial basis, currency, completeness and cutoff; enforce current review/revocation at release; then prove the exact UI behavior and error/partial states against real source data. This is a concrete integration gate, not a new history database, forecast engine or blanket requirement to finish every upstream phase.

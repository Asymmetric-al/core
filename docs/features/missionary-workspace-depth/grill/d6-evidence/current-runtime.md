## Tenant identity, caches and privileged boundaries

- **CMS identity is not automatically operational identity.** `packages/api/src/cms/public/context.ts:11` deliberately separates operational tenant ID, CMS tenant ID and reserved site ID. The current public resolver nevertheless assigns `operationalTenantId: String(tenant.id)` and `cmsTenantId: tenant.id`, leaving site null (`apps/admin/src/cms/public/resolve-tenant.ts:22`). By contrast giving-source validation resolves the CMS tenant through its slug into `public.tenants` (`page-builders.ts:76`, `:109`) or uses trusted context `publicTenantId` (`:124`). Copying the public resolver's string into a privileged subscription writer without qualifying this mapping could select no/wrong source. No live mismapping was demonstrated.
- **Current public reads have useful boundaries.** The resolver prefers `x-forwarded-host` over `host` (`resolve-tenant.ts:134`), looks up domain/slug, and permits `?tenant=` only in dev/preview/local contexts (`:68`, `:169`). Production query-tenant admission is not alleged. `published-content-reader.ts:128` filters CMS tenant and published state, uses `overrideAccess:false` (`:154`), verifies active tenant (`:184`) and serializes the public projection (`:236`). Platform trust/sanitization of forwarded headers and deployed domain ownership were not tested. A public submit needs its own trusted host→site/tenant→published Page→exact newsletter-source qualification; body IDs and the Page URL are untrusted selectors, not authority.
- **Public caching is already active.** `apps/donor/lib/cms/client.ts:78` fetches with forwarded host and cache policy. `packages/lib/cms/public-page.ts:129` builds host/descriptor tags with 60-second revalidation (`:145`). `packages/api/src/cms/public/cache-tags.ts:7` expressly says tags are invalidation, not cache-key isolation. The mock profile updates use `"use cache"` (`page.tsx:168`); donor Next config enables cache components (`apps/donor/next.config.ts:36`). No recipient email, personal enrollment state or private token was found in the inspected cached public shell. Adding such values would introduce a new exposure, not reveal an observed leak.
- **RLS is necessary but does not authorize a service command.** Suppression tables are browser-inaccessible under the later migration above. `packages/database/supabase/admin.ts:23` obtains the service-role key and `:38` creates that privileged client. A new public handler using it must explicitly enforce source/tenant/field/purpose authority and bounded writes; RLS cannot compensate for a trusted writer accepting arbitrary public IDs or clearing suppression. Do not infer current protection from the old RLS-disabled foundation or from a mocked client test.

## Material hazards and candidate safeguards

1. **RT6-01 — High authorization/tenant integrity; conditional on copying existing Page resolution or adding only a toggle.** The current source shapes and authoring gates are different from the selected public signup/contributor action. **Clause:** the visibility mutation is authorized for the current missionary's exact eligible Page with bounded source fields, current contributor authority, concurrency control and attributable minimized history. The submit resolves trusted tenant/Page/newsletter identities server-side and rejects cross-tenant, stale/replaced source, unavailable Page and extra fields. Qualify operational/CMS mapping and reverse-proxy host trust. Do not give general CMS/staff rights or accept a client-provided tenant as proof.
2. **RT6-02 — High communication permission; near-certain if existing consent helper/flags are used as enrollment.** Negative-gate success and the raw `emailMissionary`/newsletter flag cannot prove an affirmative exact subscription. **Clause:** a native request records the exact selected newsletter/topic, channel and destination with source-qualified intent/evidence and a truthful state. Activation uses the adopted destination/permission evidence; the requester cannot silently subscribe an unrelated address, household or donor. Preserve donor anonymity, private-contact restrictions and account/content access boundaries. Newsletter signup alone creates none of donor, follower, collaborator, public identity or general CRM admission.
3. **RT6-03 — High abuse/privacy; conditional on unauthenticated submit/confirmation.** A public form can be used for list poisoning, address enumeration or repeated confirmation mail even before ordinary newsletter sending. **Clause:** minimize input, validate/cap body and field lengths, use owner-qualified anti-abuse limits and same-intent replay handling, and bind confirmation/withdrawal capabilities to the exact source/destination/purpose with bounded validity and replay semantics. Neutral public results must not disclose existing donor/contact/subscription/suppression status. Do not log tokens, full form payloads or suppressed-recipient explanations. The code census does not establish any existing signup rate limiter or token protocol.
4. **RT6-04 — High durability/recovery; concrete placeholder precedent, prospective signup risk.** Existing donor settings reports success after a timer. **Clause:** distinguish form submission accepted, any confirmation still required, active subscription and communication delivery. Show success only for the durable state actually committed; persist source receipt/effect and any required dispatch intent under the source's transaction/replay contract before reporting accepted. Lost responses/repeated clicks recover the same operation; retry cannot reactivate an older withdrawn intent. Confirmation delivery failure cannot fabricate activation or erase the recorded request. Do not promise email arrival from an enqueue/accept result.
5. **RT6-05 — High permission/lifecycle coupling; conditional on unsubscribe, suppression or Page changes.** The current suppression schema is tenant/address/type, not exact-newsletter enrollment, and `consent.ts:124` picks at most one donor by matching email if no donor ID is supplied. Multiple same-email donors with conflicting flags could therefore give an arbitrary negative-gate view; actual duplicates were not queried. **Clause:** source owners define exact withdrawal versus channel/tenant/global suppression and destination changes; re-signup must not silently clear a stronger/later restriction. Check current send eligibility at the adopted send boundary, not only signup. Visibility controls new public availability; they do not by themselves grant sending, erase prior enrollments or cancel existing ones. Qualify the stale-form/visibility-change acceptance order without broadening the UI into a lifecycle console.
6. **RT6-06 — High privacy/cache; conditional on adding personalization to cached Page output.** Current shells/cache policies are public. **Clause:** cache only public form configuration and safe Page content. Isolate private prefill, enrollment status, destination-specific receipts, tokens and response/error bodies from shared HTML/RSC/CDN caches and logs; do not encode email into URLs or tags. A cached visible form is not current source authority: acceptance rechecks the applicable live visibility/source constraints. Verify host/site separation and actual invalidation after the missionary changes visibility; cache tags alone are not isolation.
7. **RT6-07 — Medium/high UX/accessibility and product truth; likely if the placeholder is copied.** The old CTA is inert and hidden on small screens; existing local flags have broad labels. **Clause:** one clear native signup action identifies whose newsletter will be received and the exact intended destination; show the missionary a simple visibility control with truthful saved/failed/conflicting state. Use shared Base UI labels, keyboard/focus behavior, field error association, pending/status announcements and mobile layout. Preserve valid input after retryable errors and avoid duplicate submission. Pending confirmation, active, unavailable and recoverable uncertainty use plain language; do not expose internal grants, provider codes or a generic success when only a request exists. No app-wide preference matrix, donor login requirement or contact-admission ceremony follows from D6.
8. **RT6-08 — High migration/debt; conditional on treating existing rows as legacy consent or reopening browser access.** Following, feed flags, organization newsletter UI and donor matching represent different facts; the feed handler conflicts with later server-only grants. **Clause:** inventory reached request/activation/withdrawal/send readers and writers, including imports, provider suppression events and old flags. Do not backfill affirmative permission from historical gifts, contacts, following, page views, raw toggles or apparent success. Preserve current browser-denied sensitive tables; qualify exact privileged commands and applied roles. Use the existing owners with explicit compatibility fences instead of parallel flags that disagree.
9. **RT6-09 — Medium performance/operations; conditional on native traffic/retries.** Current public read caching is useful, but adding per-visitor form work to every public render or repeated full donor/list scans would discard that advantage. **Clause:** keep public content reads cacheable, bound request/lookup work, qualify tenant/source/destination keys and indexes for the adopted identity rules, and bound queued/retry attempts without losing accepted outcomes. Monitor minimized counts and source identifiers for accepted/pending/active/failed/withdrawn states; no public or missionary dashboard may expose an unqualified recipient list. No load, query-plan or provider-limit evidence was gathered.

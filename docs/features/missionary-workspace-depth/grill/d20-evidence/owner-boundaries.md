# D20 owner boundaries — one current special-gift follow-up

Research date: October 16, 2026 UTC. Baseline:
`9cada8f3d8ab59db391d3fd20df77fcadeb09813`.

**Status:** the founder selected A: compatible special-gift follow-up is one
current human task, with the gifts reviewed for completion explicitly identified.
D19 and its amendments are ratified. D20's detailed recommendations below remain
unratified. This is research only: no formal owner, application, schema, task,
grant, provider, dependency or ticket was changed.

## Minimum permanent model

Extend the existing **Independent follow-up task** contract with exact admitted
gift-purpose membership and attributable reviewed-set outcome receipts. P28 owns
the special-gift follow-up meaning and grouping compatibility; the existing
shared task owner owns the human task, membership/disposition and correction.
P13/P14/P16 own gift/recognition/commitment qualification. Do not create a parallel
P28 task ledger, financial fold, generic grouping engine or source-correction
case just because several source references belong to one human deliverable.

There are three different identities:

1. **Gift-purpose work:** the stable source-qualified occurrence and intended
   follow-up purpose. Group changes, completion, retries and reassignment do not
   create another occurrence or erase its covered outcome.
2. **Current shared task:** the useful human work grouping. Compatible unhandled
   members can join it; their exact source references and earlier outcomes remain
   traceable. One current compatible gift group is not a lifetime single task.
3. **Reviewed-set command/receipt:** the exact members, relevant source/member
   revisions and human disposition deliberately accepted together. The receipt
   proves what this command covered, never “whatever belonged to the group later.”

These are logical facts within the existing owner. They do not prescribe three
new tables or authorize copying gift bodies into task storage. P9's ordinary
pointer-grade task links are useful navigation but cannot alone prove purpose
coverage, current source eligibility or reviewed-set acceptance.

### The smallest coherent lifecycle

| Event                                                                               | Recommended source/task behavior                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1 qualifies, then compatible G2 qualifies                                          | Admit their stable gift-purpose identities once and show them on the same current task T1. No second active copy of either member.                                                                                                                                                    |
| Maya reviews G1/G2; G3 arrives before she completes                                 | Accept the unchanged, still-authorized reviewed G1/G2 set. G3 remains unhandled on T1. Do not close T1 and create a successor merely for this arrival; report the exact covered set and authorized remaining work.                                                                    |
| A reviewed member is corrected, withdrawn or no longer authorized before acceptance | Reject the reviewed-set command without applying part of it. Explain a safe refresh/review path. Do not silently drop, substitute or cover a different member.                                                                                                                        |
| Only an unrelated unreviewed member was added                                       | That addition alone does not invalidate otherwise current reviewed members. Avoid a whole-group revision fence that makes busy groups impossible to finish.                                                                                                                           |
| All reviewed gift work and every other admitted task obligation are resolved        | Close the human task under its existing contract. Retain its member/outcome history and permanent gift-purpose coverage.                                                                                                                                                              |
| A genuinely later special-gift occurrence qualifies after T1 closed                 | Admit the new occurrence into the next current compatible task T2. Do not reopen T1, repeat its handled members or reset D19's first-support coverage.                                                                                                                                |
| Undo the latest mistaken Done or Not needed with no newer current group             | Conditionally correct exactly the affected members on the same independent task, retaining the original outcome and correction receipt. Current eligibility/authority must still allow it.                                                                                            |
| Undo when compatible T2 already exists                                              | Reuse the same current-group resolver: restore only the affected eligible members into T2, preserve T1/completion/correction/transfer lineage, and keep T1 historical. Never reopen a second active compatible group. This is a bounded correction, not a general task-merge feature. |
| Undo has conflicting later member handling, source or responsibility changes        | Reject with a truthful conflict and an existing qualified correction/handoff path. Do not erase the later action, choose an arbitrary assignee or create a spare task.                                                                                                                |

**All-or-none means the reviewed set**, not all gifts currently attached to the
task and not an atomic transaction with finance, P9 interaction recording or a
provider. Exact native task/member/receipt updates use their one owner boundary;
independent source effects retain separate receipts and recovery.

The one-current-group rule applies only to compatible pending special-gift work.
It is not a rule that a supporter can have only one task of any kind. A separately
promised call or other independent obligation remains actionable when its gift
reason ends; if a task remains open solely for that other purpose, it does not
silently enroll future gifts or acquire a new completion meaning.

## Corrected decision candidate

> Group compatible, source-qualified special-gift follow-up for the same supporter
> and ministry/project into one current human task. Show the gifts clearly and
> preserve each gift-purpose occurrence and current authorized source evidence.
> Grouping neither changes financial truth nor combines unrelated first-support,
> receipt, commitment-review or other follow-up purposes.
>
> Complete only the exact eligible gifts the missionary reviewed. A later arrival
> is never silently marked handled: when reviewed members complete and other
> members remain, keep the same task open with an honest result. A genuinely
> later occurrence after closure begins the next current compatible follow-up;
> completed history does not grow retroactively.
>
> Use the existing independent shared-task owner for membership, human outcomes,
> exact coverage receipts and conditional correction. Undo corrects the specified
> mistaken disposition without erasing history, duplicating active work or
> undoing/repeating a financial, interaction or sending effect. Current source,
> responsibility, disclosure and contact rules still govern every action.

The first paragraph preserves A. Exact subset atomicity, current-group restoration
and the remaining clauses are review recommendations awaiting ratification.

## Material concerns — all eight requested dimensions

Severity/likelihood describe unmitigated design risks, not observed incidents.

### O01 — A visual bundle hides independent outcomes or creates a second ledger

- **What:** Collapse several separate tasks into a card while keeping competing
  Done states, or build a new P28 group/episode engine beside shared tasks.
- **Why:** Neither provides the selected one human job; status and recovery drift.
- **Severity:** High integrity; Medium maintenance/friction.
- **Likelihood:** Likely without an explicit owning contract.
- **Evidence:** S01–S06; ADR0183 `:622–628`; P27 P07.
- **Answer impact:** Preserve A but extend one existing task profile, not just UI
  grouping or a second source-controlled correction lifecycle.
- **Permanent fix:** Persist exact member/coverage and outcome receipts within
  the shared-task owner; source gifts remain references to their own truth.
- **Exact proposed clause OC01:** “D20 SHALL be one admitted Independent follow-up
  task profile with explicit gift-purpose members and reviewed-set human outcomes
  in the existing shared owner. No parallel P28 task ledger or generic grouping
  engine may independently own membership, completion or coverage. Source gifts,
  ordinary links and communication records retain their own authority.”

### O02 — Compatibility silently merges people, scopes or purposes

- **What:** Group by display name, email, household, contributor or current login,
  or merge first-support, receipt and special-gift duties merely because they
  concern one gift/person.
- **Why:** Financial context and consent differ; a convenient group may expose
  another person's gift or wrongly satisfy a separate obligation.
- **Severity:** Critical for privacy; High for work integrity.
- **Likelihood:** Plausible.
- **Evidence:** S02 C02/C05/C08/C14; S06; S09.
- **Answer impact:** Group only source-proved compatible work, not all activity
  under one person or one task label.
- **Permanent fix:** Closed compatibility predicate for exact Tenant/Legal Entity,
  canonical supporter, typed ministry/project, follow-up purpose and currently
  compatible responsibility/source/action authority. Distinct money lanes remain explicit.
- **Exact proposed clause OC02:** “Only source-qualified compatible members SHALL
  join a current group. A label, mailbox, household/church relationship, worker or
  UI filter cannot establish compatibility. First-support, special follow-up,
  receipts and commitment/service reviews SHALL retain separate purpose evidence;
  D20 does not automatically combine them. Grouping SHALL not sum currencies,
  infer legal giving from recognition or grant visibility/contact rights.”

### O03 — A new gift is accidentally completed or causes endless stale reviews

- **What:** Completion reads dynamic current membership and covers G3 that arrived
  after review, or rejects G1/G2 whenever any unrelated group member is added.
- **Why:** The first loses real work; the second makes a busy group hard to finish.
- **Severity:** High.
- **Likelihood:** Likely under ordinary concurrent gift intake.
- **Evidence:** S01 dependent safeguards; S06 P07/AC27-P07-03; S02 C13/C19.
- **Answer impact:** Exact reviewed-set scope is necessary; a generic “complete
  all current members” API is insufficient.
- **Permanent fix:** Bind exact member IDs and relevant current revisions; accept
  unchanged reviewed members only, then recompute current residual applicability.
- **Exact proposed clause OC03:** “A human outcome SHALL bind the exact reviewed
  member set and relevant source/member revisions. Unreviewed later members SHALL
  remain unhandled on the same current task. A newly added unrelated member alone
  SHALL not invalidate otherwise current reviewed evidence. No timestamp cutoff,
  loaded page, group-wide current query or mutable client list may substitute for
  the accepted reviewed set.”

### O04 — Partial acceptance is hidden or leftover work disappears

- **What:** One stale/withdrawn selected member is silently skipped while the
  remaining set completes, or G1/G2 completion closes the task containing G3.
- **Why:** The user cannot know what the action achieved and may wrongly assume
  all displayed work finished.
- **Severity:** High.
- **Likelihood:** Plausible.
- **Evidence:** S06 `:197–219,423–425`; S02 C11/C13/C19.
- **Answer impact:** Recommend all-or-none reviewed-set acceptance and precise
  residual feedback; not a global transaction with finance/provider outcomes.
- **Permanent fix:** One owner command commits exact selected outcomes and receipt
  together. Any selected stale/ineligible member rejects that command; unselected
  current work is untouched. Safe result recovery identifies covered members.
- **Exact proposed clause OC04:** “The reviewed-set disposition SHALL be atomic
  within the shared-task owner. A selected member's conflicting revision or loss
  of eligibility/authority SHALL reject the set without silent omission. A task
  with remaining eligible members or other independently required work SHALL stay
  actionable under its owner. Completion of a subset is not whole-task completion;
  results/counts SHALL disclose only currently authorized covered/remaining work.”

### O05 — Temporary task grouping becomes permanent occurrence identity

- **What:** Moving groups, new workflow runs, reassignment or the next current
  task resets a gift's covered state; alternatively one lifetime group prevents
  genuinely later special gifts from creating useful work.
- **Why:** Special gifts can recur, unlike D19's one beginning-of-support purpose.
- **Severity:** High.
- **Likelihood:** Likely if group/task IDs are used as full deduplication keys.
- **Evidence:** S02 C08/P21; S09–S12 permanent source effects and distinct purposes.
- **Answer impact:** Preserve each occurrence across groups while allowing a later
  legitimate occurrence; do not copy D19's lifetime coverage grain blindly.
- **Permanent fix:** Stable source-certified gift-purpose identity and immutable
  covered outcomes, separate from task membership/current-group identity.
- **Exact proposed clause OC05:** “Gift-purpose coverage SHALL survive task/group,
  workflow, assignee and transport changes. Native and optional callers SHALL
  converge on the same occurrence effect. Completed groups SHALL not absorb new
  occurrences; a genuinely later eligible special-gift occurrence may enter the
  next current compatible task. Neither operation resets first-support coverage
  or treats an import/replay as a new live gift.”

### O06 — Undo creates two active groups or erases a later action

- **What:** Undo reopens T1 after T2 exists, duplicates members in both, or reverses
  source/send/interaction facts because the human disposition was mistaken.
- **Why:** Correction must repair the stated mistake without undoing real events
  or creating conflicting accountability.
- **Severity:** High.
- **Likelihood:** Plausible in normal use.
- **Evidence:** S02 ratified C13; S03/S04 independent-task distinction; S06 P13.
- **Answer impact:** Add a narrow current-group correction; no blanket irreversible
  Done and no generic group-merging/rewind product.
- **Permanent fix:** Expected latest disposition/member history, current source
  authority, same current-group resolver, atomic member restoration and correction
  receipt. Restore into a compatible current task instead of reopening a second.
- **Exact proposed clause OC06:** “Conditional Undo SHALL correct only the exact
  latest eligible reviewed-member disposition and preserve its original receipt.
  With no current successor it may restore the same independent task. Where a
  compatible current task exists, restore the affected members there with original
  task/outcome/correction lineage and keep the former group historical. Conflicting
  later handling or current authority/responsibility SHALL fail with a qualified
  correction path. Undo SHALL never reverse or repeat an actual gift, interaction,
  send or unrelated member outcome, nor create two active copies.”

### O07 — Withdrawal or grouping destroys an independently promised call

- **What:** Refund/reattribution or group completion clears every reason on a
  task, including a separately accepted promise, or removes P27's last next action.
- **Why:** A gift condition and a human promise have independent applicability.
- **Severity:** High.
- **Likelihood:** Plausible if task status substitutes for reason-level coverage.
- **Evidence:** S02 C11; S06 `:197–219`; S07 C27/C28.
- **Answer impact:** Preserve independent work without making every comment a
  promise or creating duplicate replacement chores.
- **Permanent fix:** End only the source-generated member/reason; retain actual
  independently admitted undertaking and its owner. Reconcile P27's next-action
  floor to surviving work or an owned actionable exception.
- **Exact proposed clause OC07:** “A member's source invalidation SHALL remove
  only that qualified automatic requirement. Separately accepted calls, promises
  and unrelated valid reasons SHALL retain current accountability and a usable
  route, on the same task where its contract permits. Reading, claiming, commenting
  or editing a reminder alone creates no independent undertaking. Group closure
  SHALL neither conceal P27-required next work nor invent duplicate replacement
  work merely to preserve an already valid obligation.”

### O08 — Handoff, current access or dates are silently broadened

- **What:** Add a new member under the wrong responsible person, grant access by
  task assignment, shift an existing due date, or leak a hidden gift through a
  changed count, title, group result or historical receipt.
- **Why:** Grouping is not permission, acceptance of new responsibility or a
  rescheduling instruction. A single hidden member can be sensitive.
- **Severity:** Critical for disclosure; High for responsibility loss.
- **Likelihood:** Plausible.
- **Evidence:** S03 `:57–68,109–139`; S06 P05/P13; S07 A08; S02 C06/C15/C16.
- **Answer impact:** One useful current task still requires exact current source
  access and qualified handoff. No new member-wide ACL or routing engine follows.
- **Permanent fix:** Current member-level eligibility and source-qualified shared
  responsibility; preserve task identity on handoff. Minimize projections and
  maintain independent deadlines/undertakings without silent date shifts.
- **Exact proposed clause OC08:** “Group admission, read, outcome, correction and
  handoff SHALL re-prove current member/source/actor authority. Responsibility
  changes alone SHALL not create a second purpose or active copy. Ineligible,
  indeterminate or conflicting ownership SHALL use the qualified existing repair
  path, never a guessed recipient. New members SHALL not silently postpone a
  prior obligation or widen contact/export rights. Counts, titles, results and
  receipt recovery SHALL exclude unauthorized existence/detail.”

### O09 — Grouped completion manufactures thanks or hides partial sending

- **What:** Mark done sends a combined thank-you, a provider response completes
  every member, or one optional recorded conversation is copied per gift.
- **Why:** The selected unit is human follow-up, not one automatic message or a
  financial receipt. Provider uncertainty cannot be converted into a completed task.
- **Severity:** High; Critical if prohibited outreach results.
- **Likelihood:** Plausible.
- **Evidence:** S08 C10; S11 P6 and ratified D15 C11; S02 C13/C14.
- **Answer impact:** Preserve simple task completion and optional truthful records;
  no new group sender, interaction type or required narrative.
- **Permanent fix:** Keep task member outcomes, actual encounter and send receipts
  separate. One encounter may reference exactly the covered source purposes once.
- **Exact proposed clause OC09:** “Done/Not needed SHALL affect only the reviewed
  human follow-up members. They SHALL not send, issue receipts, subscribe, change
  money or fabricate an encounter. A deliberately recorded actual encounter may
  cover the exact evidenced compatible work without duplicate encounter rows or
  compulsory prose. D15/P6 sending, consent and unknown-outcome recovery remain
  independent; neither a send nor group membership auto-completes the task.”

### O10 — A grouping decision silently chooses eligibility policy or rollout

- **What:** Treat any larger payment as special, apply one FX threshold, inherit
  P35 reminder clocks or activate historical groups during migration.
- **Why:** Grouping neither explains gift intent nor supplies missing owner facts;
  it can produce noisy, inaccurate or retrospective work.
- **Severity:** High.
- **Likelihood:** Plausible when a recipe is mistaken for native authority.
- **Evidence:** S01; S09/S10; S12 prospective effect-dark intake; D19 C10/C23.
- **Answer impact:** Grouping is selected; special/above-commitment qualification
  and any permitted policy configuration remain separate owner/product work.
- **Permanent fix:** Qualify exact native source profiles and prospective activation,
  with manual work intact. Keep broad engine, thresholds, timers and new channels
  out of this amendment.
- **Exact proposed clause OC10:** “D20 SHALL consume only independently qualified
  special-gift/above-commitment occurrences. It SHALL not infer them from payment
  size, missing commitments, unmatched money or imported labels. No threshold,
  FX conversion, due-date default, outward reminder or P35 dependency follows from
  grouping. Historical migration remains effects-dark and cannot replay covered
  work. Release requires actual owner, concurrency, authorization and UX proof.”

## Required falsifiable proof

1. G1/G2 reviewed, G3 arrives before acceptance: only G1/G2 disposition changes;
   T1 remains current for G3. Reverse the ordering; no late member is absorbed.
2. Selected G2 corrected/revoked/withdrawn during completion: the exact reviewed
   set fails atomically. An unrelated G3 addition alone does not block valid G1/G2.
3. Retry after lost success returns the same exact currently disclosable member
   receipt; changed set or disposition under the same command identity conflicts.
4. Closing T1 then receiving a genuinely later special occurrence creates one
   current T2 without reusing covered G1/G2 or D19 first-support work.
5. Correct latest Done and Not needed: safe no-successor case restores the same
   task; compatible-current-successor case restores only affected members into
   that task with full lineage. Race Undo with admission, member completion,
   withdrawal and responsibility change; never two active copies or erased history.
6. Source withdrawal preserves a separately accepted call and P27's next-action
   duty. A read/comment/reminder edit alone does not manufacture such a promise.
7. Handoff and departure retain one current shared responsibility without granting
   source access. New/current/removed recipients see only their allowed members;
   hidden gifts do not leak through counts, outcomes, old receipts or task status.
8. Distinct first-support, special, receipt and commitment-review purposes remain
   separately meaningful. Actual encounter recorded once; task completion and
   provider acceptance emit no invented interaction or automatic send.
9. Native/workflow duplicate delivery, merge/identity correction and historical
   migration preserve occurrence coverage. Restore cannot revive old gifts,
   completed members, revoked access or outward effects.
10. Actual source/task API, role enforcement, database acceptance, materialization,
    failure recovery and phone/accessibility behavior prove these outcomes. A
    synthetic state machine or isolated SQL fixture is narrower supporting proof.

No runtime, database, provider or real-user test was executed by this owner pass.
No measured capacity, monetary threshold, retention duration or timer is claimed.
The sibling D20 PostgreSQL fixture reports 38/38 assertions across nine races;
neither no-successor Undo nor successor-group restoration is implemented there.
Both remain required proposed qualification scenarios. Its immutable original
group reference proves that raw retargeting is forbidden in that fixture; it
does not prove a product prohibition on qualified restoration or transfer that
preserves original lineage. The fixture supports retaining newly arrived
residual members on the same task after the reviewed subset finishes.

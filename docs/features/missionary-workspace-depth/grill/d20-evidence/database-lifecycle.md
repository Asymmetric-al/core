## What the fixture demonstrates

### Durable gift coverage differs from the current work group

A unique member key covers `(Tenant, gift, qualified scope, special-follow-up purpose)` across all groups. A separate immutable group ID names the shared human task. A partial unique index permits at most one open group for the fixture's qualified compatible scope. These are complementary constraints: an open-group index alone cannot prevent redoing an already handled gift after the old group closes.

The source worker checks current qualified eligibility and origin. Historical-only and ineligible inputs create no task. Missing required admission audit rolls back both the task and membership. Existing gift coverage returns its original group even after a later gift creates another open group. Simultaneous **distinct** gift admissions create one group with two members; same-gift replay is tested sequentially. Concurrent same-gift admission is not separately claimed as an executed race.

The fixture admits only the already-selected special-follow-up purpose. It does not collapse first-support, receipting, commitment review or arbitrary organizational communications by gift ID. Nor does it prove canonical merge/unmerge, multi-allocation adapter deduplication or shared native/workflow producer convergence.

### Review captures exactly the set that can be completed

The bounded review command normalizes order and duplicates, validates every requested member, and writes immutable review rows with exact gift revisions and current task responsibility revision. An empty, NULL-containing, foreign or nonexistent set cannot silently become a smaller accepted set. Reusing the review key with a different selection conflicts. The caller cannot set review actor, Tenant, group scope or captured revision.

Completion rechecks current actor/gate, current task assignee, responsibility revision, each reviewed gift's exact relevant version/eligibility and each member's still-open coverage. It then writes all selected dispositions, one semantic receipt and required audit atomically. An injected audit failure rolls back all these effects. A single reviewed member's material correction conflicts the whole human completion; there is no silent partial success or inferred source withdrawal. The financial correction proceeds independently.

A newly admitted unreviewed member does not change the captured responsibility revision and does not by itself invalidate the review. If G1/G2 were reviewed and G3 arrives first, G1/G2 finish while G3 stays open on the **same task**. The task stays Open. The receipt identifies the completed set; it does not claim that every current member or the whole task is Done.

When the last open member is completed in this fixture, the same group becomes Done. If that completion commits before a genuinely later gift is admitted, the later gift creates the next open task; old coverage and receipt remain. This closure assertion has an important limit: **the fixture has no separate independent undertaking or unresolved source-reconciliation obligation**. Production must include such obligations in its own closure predicate and must not use this toy member count as the complete task contract.

### Retry is historical evidence, not a new selection

A same-review replay, including a new transport key, returns the original disposition receipt. It never reevaluates “all current gifts” or consumes G3. Changed disposition conflicts; a previously accepted finish key cannot be rebound to a different review. Two actual concurrent finish sessions yield one receipt and one coverage change. Prior evidence and audit are immutable.

The tested endpoint requires current gate and current assignee even to disclose the old receipt. This is a conservative endpoint hypothesis, not proof of the production distinction between task-read, receipt-read and completion capabilities. A prior success is not a current access grant. Post-commit lost-response behavior is modeled by replaying an accepted command; the probe does not simulate a real transport disconnect or worker crash.

### Current authority and source corrections are fenced

The fixture uses a short transaction-level row lock on its qualified scope, plus current-gate locks, to serialize admission, review, completion, source-version change and handoff. Read uses a compatible scope lock and rechecks assignee after waiting. This is a test mechanism, not a prescribed production lock table, contention budget or replacement for P12/source-owner invalidation.

Actual races show both orders:

- Addition first: reviewed members complete and the same task retains the new member. Completion first: old task is Done and later admission creates the next one.
- Source correction first: the stale reviewed command conflicts with no member consumed. Completion first: human coverage/receipt remain after the later financial correction.
- Revocation first: completion denies. Completion first: the accepted result remains, while subsequent protected read and receipt replay deny.
- Handoff first: the former assignee's protected read and completion both wait, then deny. Returning responsibility A→B→A does not validate A's old review; a fresh review is required by the tested responsibility-version hypothesis.

No financial recalculation reopens human Not needed coverage. This is ordinary replay behavior, **not a ban on explicitly qualified correction of an accidental disposition**.

## Undo and source lifecycle are deliberately unproved

The fixture implements neither no-successor Undo nor restoration into a later compatible open group. The shared-task owner must qualify an exact latest outcome correction, current member/source/actor authority and any successor collision. Where its qualified contract restores members into the current group, preserve their original admission/completion/correction lineage and avoid two active duplicate tasks. Conflicts require the existing correction/handoff path, not arbitrary fallback. Nothing here establishes a new generic merge or recurrence engine.

The fixture's original `coverage.group_id` is immutable to prevent raw retargeting. That is **not** a product prohibition on an owner-qualified restoration/transfer with preserved lineage; a production representation must support the selected correction contract and cannot copy this toy shape as complete.

Source correction only appends a synthetic gift version and moves its head. It does not implement withdrawn/held-member reconciliation, timeout, re-admission, required independent undertaking, or source-generated task ending. Thus a stale reviewed command safely conflicts, but this probe does not demonstrate the refreshed source-withdrawal UI or prove that the remaining valid gift is subsequently offered. Historical repair remains effect-dark in the tested admission path; broader import/replay and correction ownership require real producer qualification.

## Proposed clauses and consequential gaps

**DB20-01 — Separate group identity from gift-purpose coverage.** Use source-qualified business contribution/Party/typed subject/purpose identity, not allocation/revision/event identity. Resolve one current compatible human group without losing permanent per-member coverage. Preserve genuine independent purposes. Register actual canonical collision/merge behavior with source owners.

**DB20-02 — Complete the reviewed set atomically.** Bind exact normalized memberships, material source revisions, completion meaning, task responsibility and trusted current authority. A material reviewed-member change conflicts the entire completion. Independent source reconciliation remains possible. Unrelated arrivals do not invalidate or enter the command; the same task stays open for required residue.

**DB20-03 — Preserve receipts without replaying work.** Accepted member outcome, required audit and semantic receipt co-commit. Lost-response retry recovers the original outcome under current disclosure authority and cannot rebind its key or sweep up later members. Completing a task neither records a conversation nor sends a message nor changes money.

**DB20-04 — Qualify the full current task lifecycle.** Source-withdrawn or uncertain requirements, independent undertaken work, personal Not needed, accidental completion correction, Undo into an existing current group and explicit task handoff require the shared-task owner's bounded contract. Preserve lineage and one current compatible task; no unconditional reopening, swallowing residual work or copying per-gift tasks.

**DB20-05 — Verify every actual producer and disclosure door.** Prove financial/recognition/commitment adapter coherence, P12 trusted context and service-owner ceiling, real task/audit/outbox implementation, all protected projections, canonical merges, rollout and restore. Database uniqueness or a passing synthetic role test is not sufficient release evidence.

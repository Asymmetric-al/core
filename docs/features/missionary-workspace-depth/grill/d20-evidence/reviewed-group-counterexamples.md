# D20 evidence — exact reviewed gift coverage

Checked October 16, 2026. Scope: the selected **one current follow-up** for
compatible, already source-qualified special gifts. This note tests grouping,
review, completion, corrections and recovery; it selects no financial threshold,
recognition policy or definition of a special gift. It changes no application,
schema, formal owner document, dependency or provider state.

**Conclusion: accept with required amendments.** One shared independent task is
the right unit for one current compatible follow-up. Its current membership and
the exact gifts Maya has reviewed are different facts. A successful action must
cover the latter, while unrelated new arrivals remain in the same current task.
This distinction supplies the essential safety without a new workflow system.

## Verified authority and current-code boundary

- The [Q20 frontier](../phase28-q20-special-gift-follow-up-grouping-research.md)
  explicitly distinguishes a real grouped obligation from visually collapsing
  independent tasks, preserves each gift's evidence and leaves special-gift
  criteria separate.
- Ratified [D19](../phase28-d19-first-support-follow-up-adversarial-review.md)
  preserves independent human task completion, separate interaction/send facts,
  current permissions, conditional correction and permanent semantic coverage.
  D19's once-per-first-support identity does **not** mean one lifetime task for
  every later special gift. New qualified special-gift occurrences need their
  own durable coverage even while compatible unresolved work shares one task.
- [ADR-0183](../../../../adr/0183-source-owned-work-projects-into-one-shared-tasks-hub.md:622)
  distinguishes an Independent follow-up task from source-controlled closure.
  Its source projection intent, semantic receipt and current-state claim rules
  support reliable shared tasks; they do not already implement D20 membership.
- [Workflow OpenSpec](../../../../../openspec/specs/workflow-orchestration/spec.md:77)
  requires product-owned work claims and durable dispatch. A workflow run or
  transport ID cannot substitute for business coverage.
- [MPD-01](../../../../prds/workflow-studio/07-core-workflow-catalog.md:2667)
  lists grouping as a later configurable preference while retaining unresolved
  exact source qualification. It is evidence of a product choice, not an active
  source binding or permission to make P28 depend on P35.
- Current [task PATCH](../../../../../packages/api/src/missionary-portal/task.ts:25)
  accepts ordinary status and task fields; its status handling derives
  `completed_at`. Current [manual create](../../../../../packages/api/src/missionary-portal/tasks.ts:30)
  exposes no reviewed gift set. This bounded static inspection does not establish
  an implemented D20 command or hosted vulnerability. Extending the ordinary
  `status = completed` write alone cannot prove reviewed coverage.

This evidence was coordinated with the governance, source/UX and database
workstreams: retain the same current task for unreviewed residue; reject the
whole reviewed-set command if one selected member materially changes or fails
current authority; do not reject solely because an unrelated new member arrived.
The isolated database workstream has its own evidence and limitations. Its
results are not claimed by the synthetic probe here.

## The smallest reliable behavior

Maya opens a task containing gifts A and B. The review names those gifts with
permitted dates, reasons and amounts/currencies. She chooses **Mark these gifts
done**. If gift C arrives meanwhile, A and B can still be handled when their
reviewed facts and authority remain valid; C stays on the same task. A truthful
result is **2 gifts handled. 1 new gift remains**, but only when all those facts
are currently disclosable. If the residue is restricted or unresolved, do not
publish its existence/count as a supposed convenience.

The shared task becomes Done only when its owner proves there is no remaining
actionable or unresolved coverage and no separately accepted independent
undertaking keeping it open. A later genuinely new qualified gift, arriving
after that terminal task, can create the next current task. A replay of A or B
cannot. There is no arbitrary seven-day window, delayed batching timer, donor
ranking or separate task per technical retry.

If A or B changed materially, the entire selected command fails without partial
coverage; refresh the relevant review with a plain reason. The refresh must not
silently add C to a later retry. Ordering the same members differently is not a
material membership change. The UI needs one comprehensible review and action,
not a per-gift completion ritual or a mandatory second confirmation dialog.

## Exact proposed clauses

**GRP-01 — Compatible current work.** The grouping owner SHALL resolve compatible
work by exact Tenant, Legal Entity, canonical supporter, typed ministry subject,
follow-up purpose, responsibility and current permitted source context. Donor ID,
name, address, display label or amount alone SHALL NOT establish compatibility.
First-support, special-gift, official receipt and other purposes SHALL remain
distinct unless an exact owner contract explicitly admits one action covering
their separate obligations. Grouping grants no visibility or contact permission.

**GRP-02 — Durable member coverage.** Each member SHALL reference a source-owned,
qualified gift/purpose occurrence and preserve its source lineage. Neither a
physical header nor every allocation line is universally the complete occurrence
identity. Redelivery, provider events, workflow runs, source revisions and renamed
labels SHALL NOT independently create another coverage obligation. A genuinely
new qualified special-gift occurrence remains eligible for new work even when
the same supporter/ministry had earlier completed special-gift follow-up.

**GRP-03 — Exact review.** A review SHALL bind the exact selected permitted
members, their material source revisions and the relevant task/responsibility
context. Only this set is eligible for the resulting human disposition. The
server SHALL derive or verify that binding through the qualified owner command;
caller-supplied member IDs, counts, totals or an editable snapshot SHALL NOT
authorize additional coverage. A paginated viewport SHALL NOT silently stand for
unseen members. Presentation order SHALL NOT change set meaning.

**GRP-04 — Current selected-set authorization.** Immediately at the consequential
boundary, the command SHALL re-prove every reviewed member, material revision,
source eligibility, current actor capability and responsibility. A material change
or denial affecting any selected member SHALL reject the whole command without
partial coverage or a misleading success receipt. An unrelated new eligible
member SHALL remain outside the reviewed set and SHALL NOT alone invalidate the
otherwise unchanged review. A group-wide revision comparison SHALL NOT substitute
for the actual selected-set and shared-context checks.

**GRP-05 — Residue and truthful task status.** An accepted disposition SHALL record
only its exact reviewed members. Unreviewed arrivals SHALL remain unresolved on
the same current task; do not close/recreate that task merely because a gift
arrived during review. Task terminalization SHALL be serialized with membership
admission and SHALL require owner proof that no actionable or unresolved member
or separately accepted undertaking remains. Zero currently visible/actionable
rows SHALL NOT be treated as proof that unresolved work is absent. New work after
actual terminalization may use the next current task under the same owner rules.

**GRP-06 — Immutable result and bounded retry.** The accepted command receipt
SHALL retain its exact member coverage and disposition. A retry of that command
SHALL recover that result; it SHALL NOT evaluate the current group again or cover
new residue. Reusing the same command identity for a different reviewed set or
disposition SHALL conflict. Return only currently permitted receipt information;
refresh the current task separately from the immutable historical result. Lost
responses, worker restarts and transport-cache expiry SHALL NOT repeat coverage.

**GRP-07 — Correction and independent work.** Source correction or loss of
eligibility SHALL affect only the relevant source requirement under D19's
qualified correction contract. Preserve accepted member dispositions, actual
interactions and deliberately accepted independent undertakings. A changed source
must not erase performed work, create a new member identity merely to replay it,
or automatically dispose of unrelated members. Temporary unknown status is not
proved withdrawal or human completion.

**GRP-08 — Conditional exact Undo.** Undo SHALL target the exact latest personal
disposition receipt and its covered set, re-prove current source/member/actor
authority, and append a correction without deleting prior history. It SHALL NOT
undo an interaction, send, financial correction or unrelated later disposition.
Restored eligible members SHALL resolve through the existing source-owned current
group resolver: use the same task when it remains the valid current task, or the
one compatible current task if later work already created it. Retain original
task/receipt correction and transfer lineage; never reactivate two compatible
current tasks. If the owner cannot prove safe restoration, reject with a truthful
current correction/handoff route rather than infer a generic merge. This is a
qualified task correction, not a configurable group-merging engine.

**GRP-09 — Privacy and money presentation.** Member details, totals, counts,
“new gifts” messages, notification text and receipt projections SHALL independently
respect current access. Hidden members SHALL NOT leak through total-minus-visible
arithmetic, errors or stale receipts. Keep amounts in their source currency lanes;
grouping SHALL NOT create an unlabeled cross-currency sum, allocate a header total
or infer a financial relationship. A no-longer-authorized view SHALL remove
protected content while retaining only its permitted generic recovery state.

**GRP-10 — Completion remains personal work.** Done and Not needed SHALL record
their exact task/member disposition only. They SHALL NOT infer contact, an actual
interaction, provider sending/delivery, donor response, receipt issuance or a
financial fact. Optional interaction recording or deliberate sending retain
their existing owner contracts. A group of three gifts handled in one task is
neither proof of three interactions nor proof that one message reached anyone.

## Lifecycle checks without a second state machine

| Boundary                                                                   | Required result                                                                                                                               |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| First eligible member                                                      | Admit under its exact source purpose and resolve/create the one current compatible task.                                                      |
| Eligible member arrives while task open                                    | Add unresolved membership once; refresh the permitted task, not the already accepted review binding.                                          |
| Reviewed subset succeeds with residue                                      | Record exact covered set and keep the same task open; success copy describes the actual handled set.                                          |
| Reviewed member changes                                                    | Reject the full command and refresh permitted evidence; do not silently shrink or expand coverage.                                            |
| Reviewed set succeeds with no actionable/unresolved residue or undertaking | Record exact covered set and terminalize through the shared owner contract.                                                                   |
| Genuine later eligible occurrence after terminal task                      | Create/resolve the next current task; historical terminal task remains historical.                                                            |
| Transport replay or old completed member after terminal task               | Reconcile existing source coverage; create no new obligation or task.                                                                         |
| Temporary source/permission uncertainty                                    | Preserve unresolved owned work safely; do not infer completion or emit a protected residue count.                                             |
| Source invalidates one member                                              | Apply qualified source disposition to that requirement; keep unrelated members and independent undertakings intact.                           |
| Personal Undo                                                              | Correct exact latest eligible coverage via current-group resolver; preserve historical receipt/task lineage and distinct real-world outcomes. |

These are domain outcomes on the shared task and source contracts. Do not add a
second configurable task engine, duplicate financial ledger, timed aggregation
service or separate completion model solely to represent the table.

## Executed counterexamples and limits

Ran [grouping-probe/probe.py](grouping-probe/probe.py) with Python 3.12.14:
**22/22 synthetic counterexamples reproduced**. The exact observations are retained
in [results.json](grouping-probe/results.json).

The probe intentionally demonstrates broken shortcuts using finite lists, sets,
maps and explicit operation ordering. G14 is a specified interleaving, not a
real database race. G15 shows why unconditional Undo is unsafe; it does **not**
implement or certify the proposed owner-qualified restoration into a later group.
G11 models a changed permission fact; it does **not** test RLS or the P12 resolver.
The observation counts are not a coverage percentage, workload estimate, proof
of financial eligibility, test of actual Core, provider experiment or UX trial.

Required next proof belongs to the actual owners: source-qualified occurrence
mapping, scoped uniqueness, current authorization and selected-set revisions;
real concurrent join/finish/Undo behavior; durable response-loss recovery; mixed
version/restore behavior; and a usable mobile/accessible reviewed-set presentation.
This research does not fabricate results for any of those release obligations.

The permanent solution is compact: keep source occurrences distinct, group
compatible unresolved human work, bind the reviewed set, commit only its truthful
disposition, retain residue and recover exact accepted results. That is enough
to honor the selected answer without making missionary users operate an audit
console.

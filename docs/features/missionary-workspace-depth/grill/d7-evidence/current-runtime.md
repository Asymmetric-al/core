# D7 — missionary-authorized newsletters: current runtime evidence

Research-only review, 2026-10-16, baseline `9cada8f3d8ab59db391d3fd20df77fcadeb09813`. Only this evidence note was edited. Root/scoped missionary/API/auth/database/Supabase/UI instructions and repository Supabase guidance were read; there is no `packages/email/AGENTS.md`. No app changes, installation, hosted reads/writes, provider calls or actual sends. D6 evidence supplies signup, consent, public Page and dependency context; D1–D5 supply existing role/source/lifecycle limitations. References are repository-relative file:line. Source presence is not a deployment or real-role qualification.

**Selected intent:** the missionary authorizes each newsletter, with clear control and an excellent newsletter experience informed by Epistle parity. The selected authorization is a distinct action on the exact newsletter being sent. Saving a draft, selecting a template, publishing a Ministry Update, enabling signup, approving a follower or an AI suggestion is not that authorization. This note establishes current code and candidate safeguards; it does not claim Epistle feature parity or decide every parity feature's release boundary.

## Privileged send, grants, queue and asset details

- **Explicit per-newsletter source authorization is absent from these test sends.** `template-test-send.ts:224` generates `template-test-send/<tenant>/<template-or-draft>/<random UUID>` per request. The provider is called at `:254`, then a best-effort send log is inserted at `:273`; failure merely adds warning at `:305`. General connection test-send also uses a fresh key (`email/test-send.ts:142`) and logs after the provider (`:150`). This is not a durable source outbox/receipt or a recoverable same-newsletter operation. HTTP retry creates a new key even if the provider accepted the previous request.
- **Message type is caller-controlled in this admin test surface.** Schema allows transactional/marketing (`template-test-send.ts:60`). Draft testing defaults to transactional (`:375`); stored testing permits an override before its campaign→marketing default (`:421`). The admin adapter sends no message type (`email-studio-api.ts:110`), so a draft campaign test uses that transactional default. D6 established that consent is only negative gates; marketing unsubscribe requirements also depend on message type (`packages/email/merge-tag-render.ts:83`). Reusing this as newsletter send would allow the wrong permission/footer semantics. This is not a claim that current missionaries can call these admin handlers.
- **Do not overstate the conditional consent skip.** Template test-send checks donor/suppression only if its later admin client exists (`:228`, `:235`). However its earlier settings read requires an admin client (`settings-store.ts:52`, `:93`), so a stable environment lacking that client already fails. The conditional skip is a poor future template, not a demonstrated ordinary no-admin fail-open exploit. Negative-gate errors otherwise fail the handler; no new permission source is present.
- **SDK idempotency helps within one attempt chain.** `packages/email/resend/send.ts:123` requires a nonempty key; `:245` retries with the same key and a fresh 30-second AbortSignal, preserving it in provider options (`:247`). Returned errors/timeouts can end as `success:false` (`:296`); there is no durable provider-acceptance-unknown state in that result. `constants.ts:77` bounds retries at three, while rates at `:97` are constants, not evidence of an enforced global scheduler. Cancel/AbortSignal is not evidence that the remote provider did not accept the email.
- **Do not use the multi-address `to` array as newsletter fanout.** The SDK accepts multiple recipients and maps all into the same provider `to` field (`send.ts:217`, `:231`), up to 50 (`constants.ts:90`). Current inspected template tests use one recipient. A future production caller passing an entire subscriber list could disclose recipient addresses to each other and reuse one rendered recipient's merge values. No current newsletter leak is claimed.
- **Existing queue schema is not a safe send authority.** `20260214090000_foundation_1_schema.sql:36` defines `notification_queue` with donor-required recipient, arbitrary payload, nullable dedupe key and queued status; the partial uniqueness index only applies to non-null keys (`:687`). `20260226113000_authz_memberships_foundation.sql:317` grants authenticated CRUD; staff tenant policies gate reads/writes, with UPDATE USING and WITH CHECK (`:347`). D2's dormant-queue finding remains: no current API worker consuming this table was located. A future sender trusting every row as missionary authorization would activate old staff-writable rows as an equivalent send path. Requalify full migration/role precedence and source provenance before connecting any worker; do not claim the dormant table currently sends.
- **Email templates are browser-denied even though their migration disables RLS.** `20260511023547_email_studio_react_email_builder.sql:76` disables RLS but `:79` revokes all anon/authenticated table access; scoped later migration searches found no regrant. This is not a proven browser-read/write hole. The server's service-role operations still need complete source authorization. D6 covers later RLS/browser revokes on suppression/send-log/provider-secret tables. No hosted applied permissions were inspected.
- **Email media is public by design.** `packages/api/src/email/assets.ts:22` is admin-gated, validates allowed MIME and 5 MiB size (`:13`, `:50`), uploads under tenant/template path, then returns a public URL (`:146`, `:162`). `20260511024000_email_assets_storage_bucket.sql:5` makes the bucket public and `:14` adds public read. Cloudinary upload similarly returns `secure_url` (`assets.ts:129`). Private draft storage or private Page visibility does not protect already public images. The current route does not prove an exact private newsletter asset entitlement; qualification must occur before uploads/exports/public URLs expose content.

## Material findings and candidate safeguards

1. **RT7-01 — High authorization/source integrity; conditional on wiring the new missionary UI to existing test/template/queue paths.** Require a current authorized missionary's deliberate action on the exact newsletter revision, sender/reply-to, selected audience rule/snapshot and send time. Record the accepted source authorization and required durable dispatch intent/result together under the adopted P6/communication owner. Saving, AI editing, signup and template activation never authorize sending; staff-writable legacy queues, test endpoints, imports and service-role helpers cannot become equivalent bypasses. D3 departure/revocation constraints and D6 positive subscription/negative restriction rules remain independent conditions.
2. **RT7-02 — High content correctness/concurrency; concrete separate-write source risk.** The existing version counter does not compare expected revision, and its version row can fail after the current template changed. Authorize an immutable send snapshot containing the actual exported/renderable content, subject, sender and rendition version; use source-controlled concurrency and a recoverable operation result. Subsequent edits/restores/renames create a new draft or invalidate unsent authorization according to the adopted source order; they must not mutate authorized content silently. Test-send version metadata must not masquerade as a content hash or proof of final authorization.
3. **RT7-03 — High duplicate/unknown-delivery risk; conditional on retry, process failure or timeout.** A random key per HTTP request and provider-before-log cannot recover a lost response safely. Use one stable source/recipient/delivery identity with identical accepted payload for retries and preserve unknown outcome explicitly. Separate accepted, scheduled, processing, provider-accepted, delivered, failed, suppressed and cancelled states according to actual evidence. A cancel action must stop only work still cancellable and truthfully report the already accepted/unknown portion; it cannot promise recall. No blanket “retry all” that resends successful recipients or clears suppression.
4. **RT7-04 — High recipient privacy/permission; conditional on using raw recipient filters or SDK arrays.** Resolve exactly eligible native newsletter recipients from the adopted source, deduplicate by the qualified destination rule, and recheck current permission/restrictions at delivery. A later signup cannot silently expand an already authorized fixed audience; any dynamic audience semantics must be explicit in the authorization owner. Never infer permission from gifts/following/contact sharing or expose hidden donor identities. Individual recipient rendering and delivery must not reveal the list through To/CC, preview, logs, exports or other recipients' merge values. Missing/failed permission resolution blocks affected delivery; user-controlled transactional classification cannot bypass newsletter restrictions.
5. **RT7-05 — High draft/media confidentiality; conditional on reusing browser storage, public assets or public post defaults.** Durable drafts need actor/tenant/source isolation, meaningful autosave status, conflict recovery and scoped caches; the dormant global localStorage keys are not an acceptable private source. Preserve attached media when reopening/editing, qualify content and uploaded assets before publication, and distinguish draft, email, public archive and printable audience. Public image URLs are not private merely because the draft is. Do not automatically publish or grant public Page access when sending a newsletter, or turn an email unsubscribe into content-access changes.
6. **RT7-06 — Medium/high UX and user control; likely if current feed/test dialogs are copied.** Present one coherent compose → preview/review → deliberate authorize experience using shared Base UI/editor patterns, with sender/reply-to, audience scope, exclusions, subject and timing clearly understandable. Keep draft saving/recovery separate from sending; preserve edits and attachment state through refresh, failure and ordinary navigation. Use clear focus/keyboard/mobile states and accessible status announcements. Make scheduling/rescheduling/cancellation and history truthful, with time zone/DST interpretation shown if scheduling is offered; do not expose database revisions/queue internals. Existing admin UI says “Test email sent” while description says queued (`page-client.tsx:731`) and adapter drops audit warnings (`email-studio-api.ts:127`); do not copy that ambiguity into newsletter success.
7. **RT7-07 — High source-boundary/retention integrity; conditional on adding print, web archive or replies as automatic side effects.** Print/PDF or public renditions use the authorized content and their own audience/asset/retention qualification; downloads must not contain recipient rosters or personalized unsubscribe tokens unless explicitly required and authorized. Reply routing must use a qualified mailbox/workflow and current access, not broad Support Hub admission or automatic CRM identity merge. Retain useful minimized send evidence under existing owners; deleting a draft/template cannot rewrite historical delivery truth. Current template-version FK cascade and log SET NULL (`20260511023547_email_studio_react_email_builder.sql:34`, `:54`) require source retention qualification before serving as a newsletter archive.
8. **RT7-08 — Medium/high performance and operations; conditional on campaign scale.** Current template listing returns full design/HTML/text rows without pagination (`template-store.ts:370`); inline provider retries can hold requests for multiple timeouts. Keep lists/history bounded and use summary projections; defer full content until needed. Adopt owner-controlled durable fanout, bounded concurrency/retries/rate budgets, per-recipient outcomes and minimized observability. Existing inbound Inngest retries are a useful pattern but do not establish an outbound newsletter engine. Reuse established owner infrastructure rather than treating status types/queue columns as implemented delivery guarantees.

Smallest useful later qualification: (1) real-role two-tenant author/draft/template/asset/send matrix including old queue/test/direct writers; (2) one authoring fixture covering autosave, reopened attachments, simultaneous editors and edit-after-authorization; (3) one delivery race fixture covering lost response, same-operation retry, permission withdrawal, cancellation versus acceptance and partial recipient outcomes; (4) one browser journey covering preview/merge values, mobile keyboard flow, schedule time zone, truthful history and distinct print/public/reply audiences. Run these against the actual adopted source owner, with mocked-provider probes only qualifying mechanics and explicit applied-role/provider evidence where required.

Unqualified: deployed routes/data/config and grants; complete migration replay; actual queue worker registration; full P6 producer inventory under differently named functions; all template/render sanitization and storage policies; unsubscribe/provider callback convergence; real rate/cancellation guarantees; browser accessibility/rendering/email-client fidelity; Epistle parity validation; load/performance and legal retention. The evidence establishes a placeholder missionary Email Studio, partially active post editing, real admin template/test delivery, reusable low-level infrastructure and specific hazards if those pieces are promoted unchanged. It does not establish a working native missionary newsletter service or a deployed exploit.

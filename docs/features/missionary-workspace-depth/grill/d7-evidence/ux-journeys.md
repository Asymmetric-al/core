## Proposed UX clauses

**UX7-01 — One issue, one understood authorization.** Keep one newsletter workspace with drafts, scheduled work and history. The ordinary path is **Prepare → Preview → Review recipients and timing → Send newsletter / Schedule newsletter → Result**. These are understandable destinations/sections, not a mandatory modal stack. Saving, restoring, assembling a draft or publishing an Update never sends a newsletter. A one-off schedule authorizes the exact issue; it does not authorize future issues. Recoverable drafts, templates, eligible reuse, replies, print and results remain included jobs requiring concrete owner qualification.

**UX7-02 — Independent consequences stay visible.** The missionary sees only the controls currently relevant to the job. Do not put every control into a giant matrix. Preserve this meaning behind those surfaces:

| Control or fact                           | Meaning it can establish                            | Meaning it cannot establish                                                                              |
| ----------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Public Page live/published                | Exact admitted public content is available          | Subscriber enrollment, email permission or a newsletter send                                             |
| Public newsletter signup available        | New eligible public intake can be attempted         | Stopping existing subscribers, cancelling already accepted confirmation, or sending an issue             |
| Update audience release                   | Exact public/supporter rendition is released        | Permission to email all of its text/media or reveal it to every subscriber                               |
| Issue Send/Schedule                       | Exact current source accepts this issue instruction | Guaranteed inbox delivery, readership or a recurring future-content rule                                 |
| Show in my Updates                        | Source-specific feed visibility                     | Post-email or newsletter consent                                                                         |
| Email me about new posts                  | Qualified post-notice choice                        | Native newsletter choice, receipt choice or protected reading access                                     |
| Newsletter Email / Physical / Both / None | Exact qualified newsletter channel preference       | A valid address, positive topic consent, suppression override, postal custody or an automatic CRM record |

The public-signup row carries D6's reviewed interpretation, not newly ratified D6 policy. An exact source-purpose withdrawal or safety block can have different effects from hiding signup; the UI must use the owner's actual result.

**UX7-03 — Useful authoring without staff administration.** Start with a readable letter layout and an approved reusable layout choice. Keep subject, optional preview text, content and media close together. Show the currently qualified sender and reply destination; changing an administrative sender domain is a separate authorized task. Reuse shared editor primitives and owner-rendered email layouts, not the entire staff configuration surface. Offer eligible Update reuse as a deliberate insertion of exact admitted source revisions with visible provenance. It must not mutate the Update or copy private CRM/Support/care material. A prepared roundup remains a draft. Documented Epistle video coverage requires a bounded media-owner extension: P22 D9 currently accepts still images only. Standalone audio is not established by the Epistle evidence; a privacy-policy data category is not a feature requirement.

Draft status describes persistence: **Saving…**, **Saved**, **Changes not saved**, or **Checking saved version…**. Do not clear the editor after autosave. Preserve authorized attachments and recoverable work through refresh and ordinary navigation. Do not use unscoped localStorage or promise offline protection that has not been qualified. Source-owned retention/recovery limits must be settled without copying P22 Page debounce/retention numbers into a new newsletter contract.

Concurrent editing uses source evidence. A stale draft cannot silently replace a newer one. Show **“This draft changed elsewhere. Review the latest version before saving.”** with **Review latest** and a source-qualified way to recover the user's changes while access still permits them. Do not invent collaboration presence, shared locks or automatic merges merely because competitors have them. Restoring a prior version creates a recoverable current draft decision; it never changes an already authorized or delivered issue.

**UX7-04 — Preview the actual disclosure.** Provide email desktop/mobile and plain-text previews, plus the admitted print output. Preview contains the actual source-approved subject, preheader, sender, reply destination, footer and media representation. Synthetic recipient examples are the safe default; authorized recipient-specific preview must apply current field and purpose access. Distinguish a preview from a real test. **Send test email** is a governed outward action to a narrowly qualified destination, with the actual rendition and outcome recorded. An arbitrary test address cannot bypass protected content or consent/delivery rules. No production audience authorization follows from a test.

Public and protected content cannot share a casual “Preview as anyone” shortcut. For protected reading, use an owner-approved notification-only message and an exact currently authorized reader destination where that is the applicable contract. Check subject, preheader, sender alias, alt text, thumbnails, filenames, URLs, attachments, print and quoted replies as well as body text. Never label this “secure email” as a guarantee of secrecy. Previously delivered email/downloaded material cannot be recalled.

**UX7-05 — An audience that the missionary can understand.** Show the named newsletter purpose and the currently qualified selection, with separate email and physical delivery implications. Permit exclusions through the owning source; do not default to all CRM contacts, givers, followers or a tag as evidence of permission. A missing destination or withdrawn permission excludes that channel; “Both” cannot disguise a failed email or missing postal address. Explain safe causes and offer a qualified repair destination without exposing hidden identities or protected suppression details.

Use exact counts only when the source has a complete authorized denominator. Otherwise say **“Recipient review is unavailable. Try again.”** rather than displaying zero, stale success or a false total. An accepted audience ceiling can narrow for withdrawal/current restrictions; newly eligible people cannot silently join it. Do not copy Mailchimp's dynamic expansion behavior without a deliberately changed owner contract. Recipient lists, testing, logs and To/CC fields must not expose other subscribers; individual recipient rendering cannot reuse another person's personalization.

**UX7-06 — One final review, one clear action.** The review presents the actual issue, sender/reply destination, permitted audience, exclusions, email/print consequences and time. The primary action says **Send newsletter** or **Schedule newsletter**, never a generic **Publish** that hides the effect. Link directly back to edit each item; ordinary Back/Preview is navigation, not a write or cancellation. One action-adjacent sharing explanation may bind the exact approved audience without turning it into a checkbox that supposedly grants rights. Avoid a second generic “Are you sure?” after a complete meaningful final review.

For one-off scheduling, use a named time zone and an unambiguous date/time, showing the resolved offset where needed. Resolve nonexistent/duplicated DST times explicitly. A device time-zone change cannot silently retarget accepted work. Recipient-local-time delivery is not implied by the presence of a date picker. Do not promise completion at the chosen start time or import vendor timing limits. Changes to content, audience ceiling or material sender/reply meaning require newly understood issue authorization; current exclusions narrow without asking the author to approve each unsubscribe.

**UX7-07 — Honest history and repair.** History answers what happened, what is still uncertain and what the user can do. Source-supported words may include **Draft**, **Scheduled**, **Preparing**, **Sending**, **Completed with exclusions**, **Failed**, **Stopped**, and **Status unavailable**; these are display proposals, not a new state machine. “Accepted for sending,” provider acceptance, delivery evidence and actual response stay distinct. Do not show “Read” from tracking pixels or turn newsletter volume into missionary activity/coaching scores.

**Cancel scheduled send** is available only for genuinely cancellable source work. Pending copy: **“Stopping scheduled sending…”**. Confirmed copy explains exactly what was stopped. If some submissions are already accepted or unresolved, say **“Some messages may already be on their way. Those cannot be recalled.”** with only the qualified result details. An HTTP abort is not cancellation evidence. Editing scheduled content must first resolve the source-owned pending authorization or create a clearly authorized successor; the running issue never reads a mutable draft.

After a lost response: **“We haven't confirmed the result yet. Check status before sending again.”** Keep the same accepted operation identity for reconciliation. Do not offer a new blind resend, rekey unknown work or resend successful recipients during partial repair. If acceptance is known and a dependent history refresh fails, preserve **“Send accepted”** and separately show **“Delivery status is temporarily unavailable.”** An old successful receipt does not mean the current newsletter/subscription is still active.

**Read, respond and print**

The email remains understandable with images off, with logical heading order, descriptive links and a text rendition. Media uses approved small derivatives and an admitted linked destination when the email client cannot play it. Do not require autoplay, a huge attachment or a modern interactive email client to understand the main news. Protected links restore only the exact currently authorized reading target after authentication; a forwarded link checks each opener independently. An unavailable story does not reveal its protected title, thumbnail, count or audience.

Make the real reply route apparent: **“Reply to this email to contact <qualified destination>.”** Use it only after the destination and responsibility are qualified. It must not silently resolve to a mutable profile address or Support Hub's generic intake. Ordinary external email reply and in-product Update comments/prayers are distinct: no claim that Asym recorded a reply merely because a mail client opened. If a native response is included, reuse the admitted P22 source and current response ceiling; no second social graph or general inbox.

For missionaries, include an authorized **Prepare print** destination: exact issue rendition → selected physical recipients → approved salutations/household handling → missing-address repair → print list/label preview → download/export result. Preserve international address structure and mixed direction; do not force US country/state formatting. Do not merge households merely because emails, surnames or street addresses match. Every label and combined salutation needs the source-approved grouping and address authority. Email membership does not grant postal addresses. The source can retain a qualified export result; **downloaded**, **printed**, **mailed** and **delivered** are separate facts. Do not auto-mark mailed when a PDF is generated. The reader's ordinary email Print command is an additional convenience, not this physical-distribution workflow.

## Recipient cadence and overlap

The selected A model intentionally differs from Epistle's automatic future-content digests. Preserve useful low-effort work through approved layouts, recoverable drafts and eligible issue preparation; each issue is still explicitly authorized. A one-off schedule remains within A. It is not the same as daily/weekly/monthly standing permission to assemble and send future material.

Do not advertise reader frequency choices until the exact owner can honor their meaning without unapproved recombination, silently dropping issues or unexpected backlog. Do not create an arbitrary newsletter frequency registry. If future review includes delivery deferral of already authorized issues, its windows, recipient expectation, expiry, immutable content and unsubscribe behavior need explicit owner reconciliation; it is not implemented by this UI proposal. This is a capability/meaning gap to resolve, not permission to claim literal feature-for-feature parity or to abandon the complete native newsletter job.

A donor may legitimately opt into both post notices and newsletters. Reusing an Update does not make those source purposes identical. Review should disclose known overlap in understandable terms where current source evidence supports it. Do not silently switch off post notices, suppress a separately authorized issue or show a default “avoid duplicates” toggle with unspecified meaning. Semantic delivery retries deduplicate the same accepted effect; editorial overlap is a separate owner decision.

## Shared design and accessibility acceptance

Use exact `base-maia`, Base UI, Figtree and Zinc semantic CSS-variable tokens from `packages/ui`. Reuse the shared rich-text editor, Field components, Button and established Dialog/Sheet patterns. Use DataTableResponsive for genuinely substantial history/audience grids; simple preferences remain ordinary fields. No app-local primitive, theme, new dependency or administrative dashboard is proposed. Email HTML and print renderers need their own qualified output, rather than assuming browser CSS/components render correctly in every inbox.

Keep a calm single-column reading and composing path on phones. Put secondary formatting and long details in progressive disclosure without hiding essential recipients/time/cancellation states. Keyboard operation includes toolbar controls, media alternatives, date/time entry, recipient review, final action and focus return. Core's actual comfortable 44-pixel hit-area convention is stronger than WCAG's minimum; small icons need real targets, not a comment asserting size. At 320 CSS pixels and enlarged text, labels, dates, status and consequences wrap without horizontal reading. Test long international names/addresses and supported RTL. Sticky controls must not cover keyboard focus or the final line above the on-screen keyboard.

Announce saved/error/accepted status once, proportionately, without moving focus on every keystroke or combining duplicate toast/banner/live-region announcements. Stable switch labels describe the choice; status is separate. Errors retain input and connect labels, descriptions and repair. No hover-only essential actions, gesture-only reorder, nested clickable cards or color-only status. Reduced motion follows the existing shared baseline.

Low-bandwidth proposals are hypotheses to measure: load useful text/status before optional imagery, use bounded media derivatives, avoid prefetching private content or every recipient, preserve admitted unsaved input through a transient failure, and make network uncertainty actionable. An offline banner must not imply a durable offline queue or private local mirror. Actual budgets and rendering/client coverage require evidence; no invented latency or payload target is adopted here.

## Proof cases required before claiming the experience works

These are proposed acceptance cases, not executed tests:

1. A missionary on a narrow phone screen creates an issue from an approved layout, inserts an eligible Update, adds admitted media, leaves/reopens and recovers exactly the permitted draft including attachments. No email, public release, interaction log or coaching event occurs.
2. Two editors save from the same version; one accepted update survives, the other sees a useful conflict and can recover admitted changes. A restore cannot overwrite an already authorized issue. Permission loss removes private recovery access rather than exporting it automatically.
3. A keyboard and screen-reader user completes editing, preview, recipient review, a one-off schedule and permitted cancellation; focus remains visible and returns predictably. Errors and status announce once. Test mobile keyboard, 320-pixel reflow, zoom, long labels, RTL and reduced motion.
4. Slow/reordered responses and disconnects occur before save, after source acceptance, after provider submission and while cancellation runs. The UI distinguishes no-write, pending and unknown; retries never create a second effect or undo a committed success because history refresh failed.
5. Signup closes, consent withdraws, address changes, suppression appears, an active hat changes or a recipient's reading access disappears between preview and execution. A currently forbidden recipient/rendition is not sent, old results do not revive it, and other authorized work remains intelligible.
6. Recipient selection has legitimate defaults, an incomplete page, hidden identities, no eligible recipients and a source outage. Counts/summaries are truthful; errors cannot enumerate a hidden address. To/CC, sample personalization, previews, logs and exports reveal no other subscriber.
7. The same approved story reaches public, supporter, newsletter, notification-only and print contexts. Deliberately exercise unsafe title/preheader/filename/thumbnail/alt text/URL/quoted-reply cases. Each surface admits its exact rendition; public media URLs and test sends cannot bypass protection.
8. Schedule around DST gaps/folds, across device-zone changes, and just as sending begins. Review and history show the same understood time; change/cancel outcomes do not promise that already submitted mail was recalled. New subscribers do not join a frozen authorized ceiling silently.
9. A donor uses each independent Show/post-email combination and the qualified newsletter controls. Signup/off/read/gift/contact edits do not mutate another purpose. Public-off and explicit source withdrawal have their documented different consequences. Old request-only occurrences are not migrated to consent.
10. Confirm/withdraw links are prefetched or scanned; GET is inert. Actual qualified POST honors current scope and never becomes broad preference access. Indeterminate withdrawal gets honest status; a later fresh withdrawal fences stale On/confirmation retries.

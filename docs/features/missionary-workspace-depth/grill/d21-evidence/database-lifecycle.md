# D21 — Source-qualified admission, not a caller's explicit flag

Research date: **October 17, 2026**, Asia/Bangkok; primary documentation fetched at `03:56:38–03:56:53 UTC` / `10:56:38–10:56:53 +07:00`. The founder selected A: permitted giving history remains context, but comparison with prior giving alone does not create automatic attention. This note reviews database, authorization and lifecycle consequences. Proposed clauses below are not a formal owner amendment, implementation or financial eligibility definition.

**Recommendation:** enforce A at the existing source-owned purpose-admission boundary and every automatic producer that can reach it. A browser, importer, privileged worker, workflow or AI caller cannot manufacture qualifying evidence by submitting `explicit: true`, `special: true`, a reason label, a source name or a hash of its own payload. Keep ordinary deliberate manual follow-up usable without calling it a source-certified financial event. No new SQL permission engine, criterion registry or classifier is needed.

“Explicit” means accepted source-qualified meaning, not raw, non-derived or merely persisted data. Legitimate P13 effective folds, P14 permitted recognition, P16 health and existing explained history-assisted matching suggestions, and D19 completeness-qualified firstness retain their own contracts. The excluded deciding reason is a gift-versus-past-giving pattern, even if stored as `special` or conjoined with a true Received flag. No native threshold, special marker or blanket no-commitment classifier is inferred from A.

**No new database experiment was warranted or run.** D21 narrows which input meaning is allowed; it introduces no new transaction, key, RLS or concurrency mechanism beyond D19/D20. Repeating D20 with an `explicit` Boolean would merely seed the answer and falsely imply financial-source proof. The retained [D20 probe](../d20-evidence/postgres-probe/README.md) remains **38/38 outcomes with nine actual concurrent races**, executed October 16. Its executed SQL/runner/source/helper hashes were rechecked here without changing or rerunning it. It proves bounded mechanics using seeded eligibility/origin/authority, not that a real source qualifies a gift or enforces D21.

The applicable conclusions are precise:

- For an ALL/UPDATE policy, **omitted `WITH CHECK` inherits `USING`**. Both current Supabase documentation and PostgreSQL say so. Omission alone is not proof of row-relabeling permission. An adequate coarse Tenant predicate still cannot certify that an `explicit` field is true in the business sense or protect every field on an otherwise editable row.
- Effective table/column privileges, SELECT policy, old-row predicate, proposed-row check and every permissive policy must be evaluated together. Permissive policies combine with OR. A second restrictive-looking permissive policy cannot repair an existing broad grant/policy by appearance.
- Superusers and BYPASSRLS bypass row security. Ordinary table owners usually do too unless forced; FORCE RLS does not remove BYPASSRLS. SECURITY DEFINER runs with its function owner's actual privileges; it does not inherently bypass RLS. Definer/view ownership, invoker behavior, EXECUTE ACLs, exposed schemas and trusted search paths need actual qualification.
- PostgreSQL grants PUBLIC function EXECUTE by default. A privileged command must expose only its intended callers and protect name resolution; create/revoke/grant atomically. A callable definer command still needs trusted current subject/actor/permission and source qualification.
- The API grant-default notice schedules existing-project changes for **October 30, 2026** and preserves existing table grants. It does not prove the current Core table is inaccessible or make its privileged commands safe. The PG17.11 notice is version evidence; D21 does not perform an upgrade or assert hosted patch state.

These facts correct overly broad skill shorthand; they do not authorize a SQL fine-grained permission engine. The accepted P12 boundary remains authoritative.

## Consequential findings — all eight dimensions

The likelihoods below are conditional implementation judgments, not measured incidents. Each proof item is a required future qualification case, **not a new test executed here**.

### DB21-F1 — A caller launders inference into an “explicit” fact

1. **Harm:** forbidden history-only attention enters native follow-up, falsely claims financial qualification, and may leak a donor inference.
2. **Severity:** high; potentially critical if protected recognition/history is exposed.
3. **Likelihood:** plausible if an enum/Boolean/tag or signed/hash-wrapped caller payload is treated as source truth.
4. **Cause:** validating syntax or caller identity instead of the source owner's exact current occurrence and criterion; treating “explicit” as a user-editable classification.
5. **Evidence:** current POST is strict/manual; D20 SQL seeds `eligible` and `origin`; P16 excludes generic notes/import flags as application authority. None proves a general staff special flag exists.
6. **Effect on A:** accept A with a semantic admission boundary; do not add a marker field or assume commitments-only eligibility.
7. **Exact clause:** “Automatic special-gift admission SHALL resolve an owner-qualified source occurrence and its current relevant evidence through the existing authoritative command. Caller-supplied flags, labels, metadata, hashes, source names or descriptions SHALL NOT substitute for qualification. This decision SHALL NOT create a staff-marked special field or define a new financial criterion. Ordinary deliberate manual follow-up SHALL remain distinct from source-certified financial qualification.”
8. **Proof:** submit forged `explicit`/`special`/reason values via every future input path; alter a referenced source to another Tenant/subject; offer a history-score result relabeled as a fact. Each must fail to admit automatic coverage while an authorized manual task remains usable without claiming special-gift truth.

### DB21-F2 — Browser restriction leaves a privileged alternate producer

1. **Harm:** a worker, admin client or RPC generates forbidden attention or rewrites trusted provenance despite a safe UI.
2. **Severity:** high; critical for cross-Tenant/source disclosure.
3. **Likelihood:** plausible because the inspected wrappers supply privileged clients and the older dialog has a competing direct writer.
4. **Cause:** confusing role authentication/service credentials, coarse RLS or function definer status with business authority; permitting same-Tenant field relabeling.
5. **Evidence:** wrapper/admin-client lines above, browser revoke migration, primary PostgreSQL role/policy/function rules and P12's one-PDP/coarse-RLS contract.
6. **Effect on A:** enforce at the owner command reached by automatic callers, not only in a feature flag or frontend. Preserve legitimate manual edits and owner-qualified handoff/correction.
7. **Exact clause:** “Every automatic native, import, workflow, repair and service caller SHALL use the same source-purpose qualification and current P12 authority. Coarse Tenant RLS, effective grants, function privileges/ownership/search paths and immutable scoped references SHALL backstop that boundary. Generic writers SHALL NOT author or relabel generated qualification, purpose coverage or source provenance. Explicit owner-qualified correction/handoff commands SHALL preserve their independent authority and lineage.”
8. **Proof:** test actual anon/authenticated/worker roles, role memberships, raw REST/table/RPC/view/service routes and same-Tenant protected-field patches; verify old and resulting row invariants and alternate permissive policies. A fresh service credential, spoofed actor setting or own-row UPDATE must not manufacture source qualification.

### DB21-F3 — Valid earlier evidence is stale at admission or disclosure

1. **Harm:** corrected, reattributed, newly restricted or no-longer-qualified work is created or exposed; a late response leaks revoked detail.
2. **Severity:** high/critical depending source sensitivity.
3. **Likelihood:** plausible under ordinary source correction, queued retries, handoff and permission changes.
4. **Cause:** passing cached eligibility, a source label, stale JWT claims or a captured tenant-wide “allow” Boolean as permanent authority; checking one owner's revision while another material owner changed.
5. **Evidence:** P12 current context/service-owner ceiling; P16 multi-owner application/correction facts; D20's actual correction/revoke/handoff races prove only the seeded mechanism.
6. **Effect on A:** keep D20 current-source/authority fences and safe result disclosure; do not introduce a global epoch that rejects unrelated changes or a shadow SQL PDP.
7. **Exact clause:** “Acceptance and disclosure SHALL re-prove exact current Tenant/Legal Entity, subject, processing purpose, service-owner ceiling and relevant qualification evidence under their owning invalidation fences. Relevant source or authority changes SHALL invalidate stale intent without rewriting accepted human history. Unrelated changes SHALL NOT alone create attention or invalidate otherwise qualified work. No cached classification or prior receipt SHALL grant current access.”
8. **Proof:** race material source/recognition/commitment change, revocation and handoff against admission, completion and protected read in both orders; check current NHI owner ceiling and stale response generations. Preserve accepted pre-change history while refusing later unauthorized effects. D20's races are a reusable pattern, not this integration proof.

### DB21-F4 — Historical reconstruction is mistaken for fresh admission

1. **Harm:** imports or criterion deployment flood old follow-up, replay handled gifts, or suppress delayed legitimate live work because it arrived late.
2. **Severity:** high.
3. **Likelihood:** plausible where origin is editable metadata or processing time substitutes for source occurrence.
4. **Cause:** treating a new event/revision/import flag as a new business gift, or equating every delayed source fact with historical import.
5. **Evidence:** founder effect-dark history and permanent purposes; ADR-0183 durable source intent; D20 history-only admission test seeds its origin and does not qualify an importer.
6. **Effect on A:** preserve authoritative history and deliberate context while keeping historical-only reconstruction free of automatic task effects. Do not disable existing source-qualified live recovery or D19 first-support qualification.
7. **Exact clause:** “Historical-only import, backfill, replay and criterion deployment SHALL NOT mint retrospective attention or repeat covered gift-purpose work. The owner SHALL distinguish that reconstruction from delayed reconciliation of a qualified live occurrence using authoritative occurrence/provenance and durable intent, never a caller-editable origin label or arrival timestamp alone. Permitted historical facts may still support existing source qualification and human context; comparison alone SHALL NOT become an additional automatic attention trigger.”
8. **Proof:** reimport/reorder the same past gifts, change import labels, restore old queues, deploy a criterion version and replay old receipts; no historical task flood or covered-effect recurrence. A genuinely delayed qualified live occurrence must recover its same effect exactly once. Verify the real importer/admission adapter, not just a fixture Boolean.

### DB21-F5 — “No automatic task” becomes a donor dossier or false negative fact

1. **Harm:** durable no-op rows accumulate sensitive history comparisons, hidden-donor existence or a misleading “not special/no commitment” conclusion; unnecessary writes create operational burden.
2. **Severity:** high for privacy/false financial meaning; medium for avoidable cost.
3. **Likelihood:** plausible if every evaluated donor receives an audit row, rejected-candidate record or inferred classification.
4. **Cause:** confusing mandatory governance/security audit and accepted business evidence with a new requirement to persist every non-event. Missing/inaccessible/unknown source coverage is mistaken for a definitive negative.
5. **Evidence:** P12 governed processing/audit remains its own contract; D20 no-op admission behavior does not define a negative-donor registry; A adds no historical classifier or dossier.
6. **Effect on A:** retain required existing security/governance audit and durable accepted-effect evidence, but avoid new per-donor negative records merely to prove that no attention was created.
7. **Exact clause:** “D21 SHALL NOT require per-donor classification, rejected-candidate storage or business audit for every ordinary non-trigger. Existing required governance/security audit and accepted source/effect/correction receipts SHALL remain authoritative and minimized. Unknown, absent-from-view or incomplete evidence SHALL NOT be recorded as a definitive financial negative. Operational telemetry SHALL not retain protected comparison bodies or disclose hidden subjects.”
8. **Proof:** process ordinary nonqualifying input and incomplete/restricted evidence; inspect writes/logs/metrics and disclosure. No new donor score, negative classification or task appears; required P12 audit still occurs where its governing contract requires it. A retry of accepted work retains its real receipt.

### DB21-F6 — An optional rule path restores the excluded product under another name

1. **Harm:** history-only comparison silently creates badges, priority, queue order, suggested tasks or messages while the headline says no automatic follow-up.
2. **Severity:** high for policy/privacy drift; medium for maintenance/noise.
3. **Likelihood:** plausible if enforcement tests only INSERT into the task table or an optional workflow gets a separate rule path.
4. **Cause:** recreating a classifier as a SQL function, dynamic criterion registry, view, materialized score or “passive” attention label; confusing history access with permission for automated inference.
5. **Evidence:** A's boundary concerns proactive attention, P12 separates purpose from access, and P35 optional machinery cannot replace or widen native owner contracts. Current source inspection supplies no approved classifier.
6. **Effect on A:** keep ordinary authorized charts/context and deliberate human choice; no new product flag/DSL/threshold engine is needed to enforce absence of this feature.
7. **Exact clause:** “A gift-versus-past-giving pattern SHALL NOT be the deciding reason for additional automatic attention through tasks, suggestions, badges, ranking, notifications or equivalent derived outputs, including when persisted as an explicit label or conjoined with an otherwise true source fact. Native and optional workflow paths SHALL preserve that boundary. This exclusion SHALL NOT remove permitted history context, ordinary manual follow-up, P16's existing qualified explained match suggestions, or separately qualified existing first-support, special-gift, fulfillment and recurring-attention contracts.”
8. **Proof:** vary historical average, visible-history length, missing old imports and currency while keeping the qualified current source facts constant; no excluded automatic attention changes across any producer or projection. Deliberate human follow-up and independently qualified existing contracts remain available. This is an owner/integration semantic test, not a new RLS primitive.

## Minimal acceptance boundary and remaining gaps

The minimal route is: an existing trusted source command resolves its exact occurrence and current evidence, admits the already-selected purpose, atomically retains required local acceptance/effect evidence plus identifier-only intent, and lets the shared task owner materialize/reconcile that effect. Current P12 governs the real principal, Tenant/Legal Entity and every result. D20 membership, reviewed-set completion, source correction, no automatic communication and immutable coverage survive unchanged. This is an owner seam, not a proposed new generic ledger or physical schema.

A reference or closed result type can represent qualified evidence, but cannot establish truth by itself. Source identity/scope/version references should be non-null and Tenant-aware where required, protected from generic mutation and checked against actual owners. Derived local flags can be implementation caches only when clearly nonauthoritative and invalidated/recomputed through those owners. A passed database check that a Boolean equals true proves neither financial truth nor that historical inference was excluded.

No new database test was necessary because the missing proof is **real source and producer qualification**, which cannot be supplied by inventing another seeded schema. Before activation, require the future implementation to demonstrate the six proof groups above through actual current commands, real grants and all reached automatic producers. Reuse the established D20 race patterns; add tests where a real integration introduces a new failure mode. No additional blanket task pause, staff approval ceremony, no-op audit stream, dependency or database framework follows from A.

Unproved: the exact special/above-commitment criterion and adapter; full P13/P14/P16 coherence and history completeness; real P12/session/service-owner enforcement; complete producer census; hosted grants/migrations; actual source-intent/task atomicity; canonical aliases/merges; privacy of every derivative; performance; restore and worker failure recovery; actual user/a11y behavior. The retained D20 fixture proves none of these. Its artifacts were preserved, not copied or relabeled as D21 results.

# D24 — Activity-summary sharing: database and current-authority review

Research only, **October 17, 2026 UTC / Asia/Bangkok**. The founder selected optional, organization-permitted, read-only coaching summaries of eligible activity counts and targets for shown periods. D23 is ratified. The founder subsequently selected continuing into future periods of the same chosen target while sharing remains active. This note recommends the database/source/projection contract and explicit standing scope; it does not independently ratify its proposed amendments, implement a producer or inspect hosted state.

**No new PostgreSQL experiment was warranted or run.** D8/D9/D10 already exercised aggregate-only readers without raw SELECT, current-grant/source fences and relevant revocation orderings; D16 exercised target-version mechanics. A new toy with seeded activity identity, privacy and authority would not establish the missing real composition. D24's consequential new proof is the actual coherent **target definition + source-count cohort/coverage + exact sharing grant + current disclosure** boundary. Prior experiments remain bounded evidence; none was rerun, modified or promoted to D24 implementation proof.

**Temporal choice resolved:** future periods of the same selected target continue while sharing remains active. The proposed amendment binds an exact first reviewed period and retains previously admitted periods for review while current rights, access duration and qualified source/retention bounds permit. It admits neither periods before that start nor newly created targets, replaced measures or changed ministry purposes. A matching label or canonical measure alone is not the selected target lineage. This explicitly reviewed standing scope requires no fresh approval for each ordinary rollover; no second individual-period mode is proposed here.

## The authorization unit is the admitted summary, not every raw source row

There are three distinct gates:

1. **Who can choose the share:** current organization ceiling, Maya's exact sharing authority and the existing active coach/subject episode.
2. **Which source facts may contribute to this summary purpose:** the owner-qualified aggregate profile, exact participant/target lineage, typed ministry purpose, measure, dates, current source classification and coverage. This can authorize a body-free aggregate input without exposing individual source rows to the coach.
3. **Which result may be released now:** exact current coach context, module/field/history grant, expiry/reduction fences, aggregate privacy qualification and still-compatible source/target evidence.

These are uses of the existing P12/source projection, not three new permission engines. “Authorization before aggregate” does not mean “require raw coach SELECT first.” Nor does it permit an unrestricted tenant-wide count followed by hiding its detail rows. The source projection must admit the cohort and derived fields for the exact summary purpose before calculation/release. Public data, financial-summary access, personal target ownership and possession of a shared URL supply none of these gates by themselves.

**Aggregate-only access must not grant raw source-row SELECT, participant/recipient joins or body access.** A PostgreSQL `security_invoker` view checks permissions on underlying relations; granting those base privileges to make the view run is an unsafe architectural shortcut for this profile. Use the existing qualified bounded server reader/source projection. Any justified privileged function has minimum actual privileges, tightly scoped EXECUTE, a trusted search path and explicit current context/source checks. A materialized count table must not be browser-readable solely because it omits names.

The initial output profile should contain only source-qualified canonical measure, admitted target quantity, permitted recorded count, exact period/calendar meaning and necessary status/currentness. **Exclude personal target names and free-form context**, supporter identities, initials, source event IDs/URLs, narratives, message subjects/bodies, exact contact times and individual activity rows. Labels can themselves contain sensitive people or location information. Use canonical measure labels and the independently permitted coaching-subject presentation. No detail link, count tooltip, JSON expansion or export may recover hidden fields. Paused/ended state, source freshness and existence are still classified fields, not automatically public operational metadata.

## Target and count must describe the same thing

The numerator/denominator binding needs the same admitted measure, actual participant, exact typed purpose/scope, period/calendar and source-cohort definition. Quantity is the applicable **P28 target version for that period**, including D23's deliberate current-only/current-and-future/future-only changes. Recorded count comes from the current qualified occurrence/correction projection. Equal integer values do not prove the same cohort. The following are not equivalent:

- Maya's personal full-period count is five, and the coach is separately permitted that same aggregate fact without raw source access.
- The coach is permitted a subset of two occurrences, while the saved target of eight was defined over Maya's broader personal cohort.

The first can produce **5 recorded / target 8** if the combined disclosure is qualified. The second must not silently produce **2 / 8**, “25%,” “six remaining” or “not met” as full target attainment. The simplest safe result is comparison unavailable, with independently permitted target information retained where that does not disclose restricted existence. A separately approved partial-count presentation would need clear compatible meaning and privacy proof; it is not selected by convenience. Never silently reduce the target quantity to compensate for privacy exclusions.

Complete zero means a complete query of the exact admitted recording cohort, not proof that Maya performed no real-world work. Missing sources, unknown dates, partial coverage, stale projections, source withholding and denied access are not zero. Avoid reason-specific errors or hidden-exclusion counts that disclose why a summary is unavailable. Different measures overlap; no cross-measure total, conversion score, effort ranking or donor-quality inference is created. Multiple coaches can have different qualified projections; difference testing and combined releases must remain inside the existing privacy owner, without an invented universal small-cell threshold.

## Coherent revisions and final release

A useful result binds, internally, the exact share/module/profile version and current context, selected target lineage and applicable period definition/quantity revision, canonical calendar boundaries, source occurrence/correction generation, admitted cohort/coverage and field/privacy projection. Those references establish meaning; they are not all automatically safe fields to return. The profile must explain any permitted as-of semantics rather than disguising stale data behind a fresh HTTP timestamp.

PostgreSQL Read Committed gives each ordinary SELECT its own snapshot. “Fetch target, fetch count, fetch grant” can therefore mix different states inside one transaction. For example, an old count selected for a prior target scope/period cannot be paired with a newly changed target definition merely because both calls individually succeeded. Rebuilds must also use the matching source cohort and coverage. The actual owners need one qualified coherent source/read-model boundary or explicit relevant-version validation. This is not a requirement to make all revision numbers equal, hold a global tenant lock, introduce distributed transactions or invalidate valid reads on unrelated changes.

A consistent database snapshot alone does not prove **current authorization at release**. A long-lived repeatable snapshot may preserve a previously allowed state after a revoke commits elsewhere. Serializable isolation does not automatically define the product's disclosure ordering. The actual P12/source mechanism must establish the applicable acceptance/release fence against reduction, expiry, target-scope change and source restriction. Test both orders: a reduction that wins the fence prevents the later release; a valid earlier release can remain historical evidence but cannot authorize a subsequent read. Already delivered bytes cannot be recalled. Do not hold database locks across external HTTP/provider/user waits as a supposed privacy guarantee.

Cached and materialized results remain derivatives. Before serving them, requalify current admission and relevant target/source/coverage meaning. A cache key containing a revision prevents accidental collision but does not establish that the revision is current. Permission-safe invalidation/rebuild and late-response rejection are required; server render caches, browser query caches, Realtime subscriptions, API responses, print/export and result recovery must follow the same scope. A previously shown count may be retained only if its continued disclosure and explicit freshness meaning remain permitted; a source privacy restriction cannot be handled by leaving the old count visible with an Updating badge.

The current pure projection helper only compares supplied evidence; it cannot acquire the fresh grant/source facts that make this guarantee true. Its caller must be the qualified producer. Passing a coach ID, `currentRevision` string, static field-policy row or same-looking source object from the browser is not current authority.

## Sharing mutation, period choice and structural integrity

Extend the existing coaching sharing owner rather than creating another invitation/ACL ledger. Exact accepted intent binds tenant, grantor and coach, canonical coached subject, activity module/profile, chosen target lineage/measure and the product-selected period semantics. Trusted context derives actor/tenant and the owner validates grantor scope. The share command uses the existing mandatory revision, atomic local state/evidence/result and semantic retry contract. Changed meaning under a reused operation conflicts; an old accepted receipt is historical evidence and must not restore a removed measure or period. Current read-only receipt authority is separate from authority to widen a share.

**Selected standing scope:** admit the same chosen target lineage from the exact first reviewed period onward, including qualified future periods while sharing remains active. Previously admitted periods remain reviewable within current rights, duration and qualified source/retention bounds; they do not fall out merely because the calendar rolls over. No period before the reviewed start, new target, other ministry, changed measure, financial history or free-form check-in follows implicitly. A one-off custom-date target has its one exact admitted period and supplies no recurring future periods. D11 expiry bounds duration; it does not independently widen this scope. Fixed admitted dates contain current corrected source facts, not frozen screenshots. A normal source correction inside an admitted period is not a new period grant, but source privacy and current qualification still govern the corrected result.

Routine target edits must retain D23's exact meaning. An authorized quantity correction/current-period adjustment is a content revision inside the same selected target/period when the standing profile permits current values; it does not automatically require a new sharing grant. It also supplies no authority to change the coaching profile or disclose private target labels. Previously accepted target revisions remain history, not an entitlement to expose every edit. A measure/scope replacement requires the exact owner-qualified sharing consequence; it cannot be treated as ordinary rollover. Pause/end of target and removal of sharing are distinct: target history may remain independently shareable only within the actual grant, while coaching access can end without changing personal records. Ending the source sharing episode must not be undone by re-enable, old tabs, retry, restoring a backup or a new target with the same label. Independently valid additive grants remain the PDP's responsibility; never claim one removed row proves all authority ceased.

Database backstops include non-null same-tenant typed references from share/profile/target/period to their actual owners, immutable origin/actor/subject, valid lifecycle/expiry/range states, stable accepted-effect identities and constraints preventing forbidden retargeting. Null or an empty scope must never mean all targets/periods. Read-only coaches receive no target/source/grant mutation through generic PATCH, view, RPC, collection or service endpoint. Coach self-leave and qualified own preferences remain separately scoped. Routine assignment removal must not cascade-delete required lawful history; retention/restriction/erasure follows existing owners.

Review actual table/schema/column/function grants as well as all effective policies. A permissive policy can combine by OR; tenant RLS does not freeze mutable actor/owner fields. Applicable omitted `WITH CHECK` inherits `USING`; absence of duplicated syntax is not a demonstrated bypass. Table owners normally bypass RLS unless FORCE applies; superuser/BYPASSRLS paths still bypass. SECURITY DEFINER uses its actual owner's privileges and is neither automatically unsafe nor automatically authorized. New functions default to PUBLIC EXECUTE unless revoked; create/grant changes should avoid an unintended public window. The service path must preserve the same P12/source decision despite database bypass rights. Pooled sessions cannot reuse a previous tenant context.

## Material findings — eight dimensions each

### DB24-F1 — Aggregate permission is confused with raw activity access

1. **Harm:** invited coach sees individual participants, event dates or bodies, or an unrestricted total reveals other scopes.
2. **Severity:** critical.
3. **Likelihood:** plausible with raw table reuse, aggregate-first redaction or an invoker view “fixed” by broader grants.
4. **Cause:** summary-purpose admission is confused with either raw row visibility or a post-aggregation check.
5. **Evidence:** D8 C12/C14/C15, D9's explicit source-purpose distinction, primary CREATE VIEW rules and current existing owner/staff activity policy.
6. **Effect on A:** retain useful aggregate-only sharing through the exact qualified source projection; no coach elevation or raw SELECT.
7. **Exact clause:** “Activity-summary input and output SHALL be admitted for the exact current coaching purpose before calculation and release. A separately qualified aggregate MAY exist without raw source-row/body access. The implementation SHALL NOT grant event/participant/base-table SELECT merely to support an aggregate view, and SHALL NOT compute an unrestricted total then redact its source details.”
8. **Production proof:** actual coach/other-coach/other-tenant roles, same source under different summary profiles, denied raw event/participant SELECT and all joins, invoker/definer paths, source-denied totals, RPC/service/browser/GraphQL/Realtime/export paths. Prior D8/D9 synthetic readers do not prove the real profile.

### DB24-F2 — A privacy-filtered numerator is presented as personal attainment

1. **Harm:** coach draws a false conclusion from a subset paired with a broader target, or a subtraction/remaining count reveals withheld activity.
2. **Severity:** high; critical if hidden identity or restricted work is inferred.
3. **Likelihood:** plausible if personal dashboard data is filtered and reused mechanically.
4. **Cause:** target cohort, admitted source cohort and coverage are not checked together; equal counts are mistaken for equal meaning.
5. **Evidence:** D23 exact measure/participant/period contract, P27 protected count meaning, D9/D10 unknown-versus-zero limits and owner semantic review.
6. **Effect on A:** share only a compatible comparison, with an honest unavailable state when the ordinary target relationship cannot be preserved.
7. **Exact clause:** “A shared activity-versus-target comparison SHALL prove compatible measure, participant, typed purpose, period/calendar and cohort meaning with current coverage. A restricted subset SHALL NOT be shown as attainment of a broader personal target. No percentage, remaining amount, met flag or hidden-exclusion reason SHALL restore the missing inference. Independently permitted target information MAY remain available without a false comparison.”
8. **Production proof:** full aggregate with no raw access; subset with same and different numeric totals; missing/unknown-date/withheld source; target-only rights; repeated/combined period and metric releases. No arbitrary threshold or universal anonymity claim substitutes for the privacy owner.

### DB24-F3 — Individually valid reads form a contradictory result

1. **Harm:** old-scope count pairs with new target/period or expired grant; a cache returns a coherent old snapshot as currently authorized.
2. **Severity:** high for false comparison; critical for revoked disclosure.
3. **Likelihood:** plausible with separate Read Committed fetches and cache-only currentness.
4. **Cause:** no qualified joint target/source/coverage/grant binding and no final release fence.
5. **Evidence:** primary isolation rules permit different snapshots between SELECTs; current resolver performs no I/O; D9/D10 prior version guards are seeded mechanics only.
6. **Effect on A:** require coherent real owner evidence and safe updating/unavailable states without inventing a global lock or permission engine.
7. **Exact clause:** “Every released summary SHALL bind its exact target-period revision, qualified source/cohort/coverage, current share/profile and authorized projection. Relevant concurrent changes SHALL be serialized or revalidated through the existing owner boundary before release. A consistent historical snapshot, matching cache key or caller-supplied current revision SHALL NOT establish present disclosure authority.”
8. **Production proof:** target edit versus count read, source correction versus rebuild, period rollover versus grant read, revoke/source-restrict versus release in both orders, stale cache and late response. Verify the actual P12/source producer and release path, not only database snapshot consistency.

### DB24-F4 — Date navigation silently widens the grant

1. **Harm:** selected current summary becomes all past/future targets, or extending duration secretly adds activity history.
2. **Severity:** high.
3. **Likelihood:** plausible with “latest”/“all targets” queries or copying financial-history controls.
4. **Cause:** target lineage, selected period semantics, module and access validity are collapsed into one UI filter.
5. **Evidence:** D8 C08, D10 explicitly excludes activity history and explains advancing scope, D11 duration does not extend history; the founder now expressly selected future periods of the same chosen target, requiring an explicit start and retained-admitted-period contract.
6. **Effect on A:** record the selected same-target standing scope explicitly; future rollover admits no new target and no pre-start history.
7. **Exact clause:** “Sharing SHALL bind the exact selected activity module, person, ministry purpose, target lineage/measure and first reviewed period. Qualified future periods of that same target SHALL continue while sharing remains active; admitted periods SHALL remain reviewable only within current rights, duration and qualified source/retention bounds. Query parameters and retained caches SHALL only narrow that authority. Periods before the reviewed start, new targets and changed purpose/measure SHALL NOT enter through rollover, label matching or duration extension.”
8. **Production proof:** selected periods across rollover, old links, new same-named targets, target replacement, duration extension, expired episode, caller widened range and two coaches with different scopes. Verify retained admitted history after rollover, denied pre-start periods and no implicit recurring periods for one-off targets; no second temporal product is needed.

### DB24-F5 — Existing plumbing is mistaken for current P12 qualification

1. **Harm:** a static field flag, privileged API or supplied revision authorizes an external coach without the actual source context/floor.
2. **Severity:** critical.
3. **Likelihood:** plausible when adapting existing missionary/staff paths to a new viewer.
4. **Cause:** pure projection validation is mistaken for a live authority producer; role elevation or a second SQL resolver fills the gap.
5. **Evidence:** implemented resolver comment/no I/O, static baseline field reader, current role-only wrappers and owner/staff RLS versus P12's target contract.
6. **Effect on A:** reuse sound enforcement components behind the qualified producer; neither promise deployed readiness nor create a fallback role.
7. **Exact clause:** “The actual coaching producer SHALL acquire current source/P12 evidence for the exact validated Active Tenant Assignment and summary purpose. Static field policy and pure projection validation SHALL only constrain that evidence, never mint it. Coach access SHALL NOT require staff/missionary identity, borrowed sessions, raw browser authority or an independent SQL fine-permission engine.”
8. **Production proof:** real principal/membership/current hats, source-grant removal, organization Off, stale JWT, supplied revision forgery, service-worker owner ceiling where used, missing field classification and all effective policy combinations. No current hosted implementation is claimed by this source inspection.

### DB24-F6 — Share retries or read-only paths mutate the wrong resource

1. **Harm:** a retry restores removed periods, same-number cross-tenant subjects bind, partial acceptance persists, or coach can change personal target/source history.
2. **Severity:** critical for unauthorized mutation; high for duplicate/lost sharing state.
3. **Likelihood:** plausible with generic CRUD and transport-key-only deduplication.
4. **Cause:** absent trusted-context/composite identity, immutable fields, expected head, semantic receipt and atomic required evidence.
5. **Evidence:** D8 C13–C16, D23 C15–C17 and prior D16 target mechanics; new D24 command integration remains unimplemented.
6. **Effect on A:** extend the existing source sharing command; preserve exact read-only and current result-recovery permissions.
7. **Exact clause:** “Accepted share changes SHALL atomically bind current authorized actor/tenant/coach/subject, exact module/target/period meaning, expected source revision and durable outcome/evidence. Reused intent with changed meaning SHALL conflict. Historical receipts SHALL not reopen ended or narrowed sharing. Structural same-tenant references, immutable attribution and least effective grants SHALL prevent retargeting or coach business writes through every reached path.”
8. **Production proof:** same-intent concurrent Save, changed payload, lost response after narrowing, required-audit failure, Save/revoke/expiry both orders, direct actor/tenant/target updates, cross-tenant FKs, denied coach target/goal/source/grant mutations, permitted self-leave and still-authorized read-only receipt recovery.

### DB24-F7 — Body-free snapshots become a permanent disclosure channel

1. **Harm:** personal labels or historical counts leak through JSON/logs/cache/exports after source restriction, privacy expiry or backup restore.
2. **Severity:** critical where sensitive work or people are exposed.
3. **Likelihood:** plausible with whole-GoalVersion serialization, globally cached results or a materialized view treated as an authorization boundary.
4. **Cause:** absence of bodies is confused with harmlessness; retention/rebuild and current release are not integrated.
5. **Evidence:** P27 C08/C12; D8 minimum projection/egress; current generic field surfaces; primary materialized-view behavior.
6. **Effect on A:** canonical minimal fields, source-qualified derived classification and bounded operational recovery; no second coaching ledger.
7. **Exact clause:** “The activity module SHALL release only its explicitly classified minimal fields, excluding personal target labels, supporter identities, individual source references and bodies. Cache/materialization/Realtime/export/log/restore paths SHALL preserve current source and sharing restrictions before disclosure. Retained history SHALL not become a public or permanent access grant; repair SHALL use owner correction and bounded derived rebuild, not a copied writable coaching activity ledger.”
8. **Production proof:** malicious/private target name, nested serializer fields, paused-status classification, source body expiry versus independently permitted fact, old cache/subscription/print link, restored revoked data, role switch and multiple-tenant cache collision. Measure actual source/P12 query budgets and recovery behavior; no load or inference safety is established here.

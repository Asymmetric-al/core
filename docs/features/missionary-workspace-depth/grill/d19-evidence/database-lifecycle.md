## Hypothesis and what is deliberately absent

**The source signal is already qualified.** Immutable synthetic versions contain a current cursor, eligibility `eligible / unknown / ineligible`, completeness, live versus history-only admission origin and an opaque source reference. A separate head selects the current version. Incoming events are wakeups: they do not supply financial truth. Processing an old event reads the current head; an event ahead of that head waits. No `MIN(gift_date)`, loaded-page inference, money sum, local recognition fold or conversion is performed.

The intended production predicate must distinguish received effective support from pledges, pending payment attempts, payout, fee cover, noncash valuation, recurring-instruction labels and roster membership. P14 attribution, legal donor versus recognition subject versus recipient, church-member acknowledgment exclusion, anonymity and current contactability remain owner constraints. A seeded `eligible` value does **not** prove any of them. The fixture uses integer ministry IDs and one tenant/Party/ministry/purpose key; exact typed subject/Legal Entity/recognition scope remains unqualified.

**Permanent coverage is separate from transport identity.** One first-support task is unique for the fixture's canonical tenant/Party/ministry/purpose. Two different event IDs cannot create two tasks. Event replay returns its historical acceptance receipt, not another effect. A later out-of-order wakeup can point to the same task under the current source head. A worker, year, currency, provider event, designation label or source correction is not part of the key.

The fixture represents one admitted independent task directly. It does not add a P28 review case before the task or a second ledger owning human Done. The task's bounded source-reference and outcome tables represent required provenance/receipts. They are not proposed application table names or a new shared-task architecture. Actual asynchronous shared task/outbox materialization is not exercised.

**Human completion is only task completion.** The Done and Not needed commands write an authorized task disposition, immutable outcome and required audit atomically. An injected audit failure rolls them all back. Two different completion transport keys produce one human outcome. Changed replay meaning conflicts; missing meaning/revision is rejected. The source giving fact remains unchanged. No interaction, email, conversation, donor response, contact consent, gift or cultivation enrollment is created by marking Done.

The fixture's free text is a fixed synthetic meaning marker, not a selected required reason field, privacy policy or proof that thanks happened. Recording an actual encounter or communication remains a separately qualified P9/P6 action, with source evidence, audience and one actual encounter identity. Neither this probe nor the task state proves the human performed that action.

## Correction, holds and responsibility

Before admission, missing/incomplete qualification does not consume first-support coverage or create a task. History-only events and history-only current sources likewise create no task. They may retain an identifier-only processing receipt. Replaying them is not catch-up authority.

An existing unhandled task becomes **held** when the source is unknown or incomplete. It remains the same task. History-only repair does not make it actionable; separately qualified live evidence can restore the same still-unhandled task to Pending. This is resolution of a temporary hold, not reopening a terminal predecessor or creating a new first-support effect.

A definitive source invalidation marks a pending/held task **withdrawn** and preserves its original creation basis and correction evidence. A later eligible wakeup returns Needs source resolution instead of automatically reopening or creating another task. The owner may qualify a narrow explicit correction of an erroneous withdrawal on the same independent task, with current authority, original live admission, no intervening human disposition and a retained correction receipt. **That repair is not implemented or prohibited by this fixture.** Neither a successor-occurrence engine nor irreversible terminal-withdrawal policy is selected here.

A valid withdrawal of a **misattributed gift that never actually supported this ministry** also must not permanently consume genuine first-support coverage. A later newly live, owner-qualified first gift can require re-admission on the same purpose/task identity if there was no human handling, independent undertaking or genuine prior support. This differs from genuine support followed by a refund, which does not restart welcome work. The financial/task owners must distinguish these cases; the fixture's safe Needs source resolution result does not decide them. This later-live re-admission is unproved, not forbidden and not historical catch-up.

Human Done/Not needed remains recorded through later financial correction or renewed eligibility. These events do not replay personal work. A separately authorized conditional Undo of mistaken Done or the actor's own Not needed is compatible with the independent-task contract; it must identify the exact latest outcome, current applicability and no conflicting later disposition. **Manual Undo of either disposition is unimplemented and unproved here.** Immutable original receipts do not imply that no append-only correction could ever exist.

Source invalidation and completion serialize on the current source head and task. Correction-first withdraws the pending action and refuses the old completion. Completion-first preserves the human task outcome and then records the financial correction. That ordering establishes database acceptance, not when an unrecorded real-world conversation occurred. The ordinary manual interaction path remains a separate owner requirement.

The creation recipient is a prequalified candidate, checked against the current effective gate. Missing or unauthorized candidates do not cause guessed fallback. Handoff is a deliberately invoked, exact-task expected-revision command to a currently eligible named recipient. It changes neither the ministry/Party representative nor other tasks. Assignment itself grants no permission. In the real handoff race, the old assignee's read waits and then denies disclosure; their subsequent Done is also denied. The qualified new assignee completes the **same** task.

Revoke-first blocks completion. Completion-first preserves its accepted receipt before the later reduction. After revocation, both task read and replayed Done receipt are unavailable through the tested endpoint. Current-authority/source-body disclosure is not inferred from an old accepted operation. The complete production separation between task-read, receipt-read, historical source access, handoff and task-completion capabilities remains unproved.

## Merge and identity limitation

The merge case starts with an existing canonical task. A privileged fixture step supplies an already-qualified P4-style alias mapping from another observed Party to that canonical Party; a later event through the alias returns the existing task. No source or task is recreated. The fixture does not decide who should merge or infer identity from email, name, household, advisor or designation text.

This is **not** a proof of a real merge, unmerge or two-existing-task collision. If both pre-merge Parties already have open tasks, or both have completed human work, production must reconcile coverage and current applicability through P4/shared-task owners while retaining both historical receipts. It cannot erase actual work to manufacture retrospective uniqueness, blindly rekey one unique constraint, or let unmerge/reassignment replay first thanks. Concurrent merge admission, canonical ministry remapping and historical ownership repair remain explicit release gaps.

## Proposed clauses and qualification limits

**DB19-01 — Qualified source admission, never event inference.** Consume the financial/recognition owners' exact current first-support predicate, coverage/completeness and occurrence references for the stable typed subject. History-only imports remain effect-dark. An event wakes the current resolver and cannot replace the source head, prove First from an empty page or revive an old right.

**DB19-02 — Permanent canonical purpose coverage.** Reuse the same intended first-support effect across native missionary work, organizational callers and optional workflows. Preserve genuinely different purposes. Worker/assignee changes, new keys, corrections, labels, imports, merges and unmerges must not manufacture another ordinary task. Register canonical-collision reconciliation with P4/shared-task owners before activation; a naive raw Party-ID unique key is insufficient.

**DB19-03 — One shared independent human task.** Use the existing closed Independent follow-up contract for this admitted deliverable. Atomically preserve its source basis, authoritative task, required audit and semantic outcome. Human Done/Not needed never author gift, contact, encounter or communication truth. Qualified actual interaction recording remains separate and can reference the same work without duplicate logging.

**DB19-04 — Current task authority and exact handoff.** Enforce the existing P12/current source projection at creation, task list/detail/count, receipt, completion, handoff and every worker/export/recovery path. Recheck the destination's exact authority; assignment grants nothing. Fence reassignment against both read and write. Missing responsibility produces a truthful authorized repair need, never an invented fallback recipient or false completion.

**DB19-05 — Correct applicability without replaying people.** Distinguish unknown hold, definitive withdrawal and human disposition. Preserve original admission and later correction evidence. Ordinary replay never reopens human Done/Not needed or an ended task. Any manual Undo, erroneous-withdrawal repair or later-live re-admission after an invalid first-support cause must be qualified by the financial/independent-task owners, preserve historical receipts and the same purpose/task coverage, and change no gift, interaction or send. Invalid attribution must not burn an unhandled genuine first-support opportunity; a refund after genuine support must not restart welcome work. Histories and receipts do not grant access after revocation.

**DB19-06 — Prove the reached producers and restoration.** Qualify real source/recognition mappings, shared task contract, semantic uniqueness, actual service identities, real events/outbox and all effects. Restore and mixed-version rollout must reapply current authority, canonical identity, source/correction and consumed-effect fences before reads or execution. No restored snapshot or absent provider dedupe cache can repeat old thanks.

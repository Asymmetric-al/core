# D25 — Optional check-in questions: lifecycle and counterexamples

Research date: **October 17, 2026 UTC / Asia/Bangkok**. The founder selected **A —
Optional organization-provided questions**. This evidence note proposes the small
lifecycle needed to preserve that choice; it is not an implemented service or a
formal owner amendment. Only this note and its new synthetic probe were changed.

**Disposition: Accept with required amendments.** Question maintenance, private
writing and deliberate disclosure are separate effects. Preserve each answer's
actual question meaning, keep ordinary saves private from coaches, and use one
current shared revision with its exact named audience. Later changes remain
private until an explicit, reviewed update. A plain written check-in remains
usable without any configured questions.

## The smallest coherent model

The following are semantic states, not a demand for new tables or a large state
machine. Reuse qualified native ownership and commands.

| Situation                     | What the missionary sees                                                                                                                  | What a coach may receive                                                                   |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Private draft                 | **Draft · Not shared with your coaches**; honest saved/saving/not-saved state.                                                            | Nothing from that draft. Existing unrelated shared check-ins are unaffected.               |
| Shared, no private changes    | Current shared version and exact recipient names/context.                                                                                 | That current accepted revision, only through currently valid exact rights.                 |
| Shared, with private changes  | **Draft changes · Not shared yet**, with a clear route to review and **Update shared check-in**.                                          | The previously accepted revision, until the reviewed update succeeds.                      |
| Withdrawn                     | **No longer shared** once confirmed; private content remains only as its owner and retention rules allow.                                 | No access through this withdrawn publication. Previously seen information is not recalled. |
| One recipient's episode ended | Truthful access state without revealing inaccessible context. Other recipients and the author's own rights remain independently governed. | No access through the ended episode, even if a retained publication still names it.        |

One check-in has **one current shared content revision and one exact named
recipient set**. Review an update against every retained recipient, any deliberate
addition and every removal; commit content and audience together. Different
wording for different recipients is a separate check-in, not independently mutable
versions hidden behind one item. Old accepted revisions remain governed evidence,
not a general coach-accessible version browser.

This model is a reasoned proposal, agreed for the parent's draft review. It does
not claim the founder separately selected every lifecycle detail. It prevents
silent disclosure without adding a separate approval workflow or general CMS.

### Question edits while someone is writing

An answer must remain attached to the question actually answered. A stable question
ID alone is insufficient if its wording changes. Retain the exact question wording
or immutable source revision with each accepted draft/shared representation, plus
stable identity and intended order. The design can choose the smallest existing
source representation that satisfies this; a global versioning platform is not
required.

Reordering questions cannot move one answer under another. Editing a question
cannot relabel an old answer. Removing a question from the current reusable set
cannot erase an existing safe draft or lawful check-in record. New check-ins use
the currently offered questions; existing drafts keep the meanings they started
with. Do not auto-upgrade a draft or make Maya reconcile a template diff merely
because staff changed tomorrow's guidance. A modest notice, when useful, can say
**“The organization’s questions have changed. Your draft keeps the questions you
started with.”**

Retiring a question and restricting unsafe content are different actions. A
current safety restriction or lawful erasure can still prevent release/retention
of older text. Preserve meaning/history only within those governing limits. If
a question-and-answer pair is no longer eligible, do not silently substitute a
new question or imply the original content was shared unchanged.

Skipping prompts, using only personal context and starting while no template is
configured must remain ordinary successful paths. All-empty input is not a
meaningful shared check-in; keeping an empty draft or leaving without sharing is
not a failure. Do not invent mandatory answers, completion percentages, reminders
or a “missing check-in” record. A new template appearing later cannot replace
already written freeform text or force conversion into questions.

### Draft recovery, preview and publication

Autosave must acknowledge the exact draft revision actually persisted. A response
for earlier text cannot label newer visible text **Saved**. Ordered writes from
one editor and genuine concurrent edits in two tabs are different problems:
prevent stale writes from overwriting later accepted work, and expose a genuine
conflict instead of guessing a merged private narrative. Preserve still-authorized
unsaved text for review/recovery; do not introduce protected offline storage or
put bodies into URLs/diagnostics to avoid losing them.

Preview binds the exact prompt/answer/content revision, subject, named recipient
episodes and expected publication/audience state. **Share** or **Update shared
check-in** must submit that reviewed meaning. A newer autosave arriving between
preview and commit cannot silently become the publication. If necessary, complete
the intended draft save and refresh review; never share an older body while
claiming the visible unsaved text was sent.

If one selected recipient becomes ineligible after preview, reject the requested
publication atomically and preserve still-authorized private work for an updated
review. Silent partial delivery changes the user's intended audience. By contrast,
reads of already shared content always intersect current rights immediately;
revocation need not wait for the author to update a stored recipient list.

An accepted operation with a lost response is not a new Share. Recover its exact
receipt under current authority. If publication was subsequently withdrawn or
narrowed, show the accepted historical result and current state truthfully;
never reapply the old desired state. Body equality alone is not the business
operation identity: two intentionally distinct check-ins may have identical text.

Withdrawal/removing access must work independently of invalid private edits and
must not publish those edits. A stale content update cannot restore a recipient
removed since its preview. A new coach, a reassigned coach, or the same account
in a new episode receives no existing narratives automatically. Deliberately
adding an eligible recipient to one existing check-in is an explicit historical
disclosure of that reviewed current revision, subject to current history limits;
it is not a grant to all older check-ins.

## Exact proposed requirements

**LC01 — Voluntary plain path.** The check-in editor SHALL remain usable with no
configured template, an empty/retired template or all optional questions skipped.
Personal context MAY be sufficient. No answer SHALL be required merely because
staff provided a question, and no blank or missing check-in SHALL imply failure.
Only a deliberate meaningful nonempty submission may establish a shared check-in.

**LC02 — Durable question meaning.** Draft and accepted shared content SHALL bind
answers to stable question identity and exact answered wording/revision, not
display index or the latest mutable question. Template edits, reorder and removal
SHALL not rewrite or erase existing answer meaning. Reuse current questions for
new drafts without automatically converting existing drafts. Current source
restrictions and lawful retention/erasure remain superior to historical display.

**LC03 — Separate authority.** Maintaining questions SHALL grant no response,
private draft or coaching-history read authority. Draft saves SHALL not disclose
to coaches. UI SHALL describe actual audience truth, such as **Not shared with
your coaches**, rather than make an unsupported **Only you** promise. Independent
governing rights remain separate and must be accurately represented.

**LC04 — Exact private save.** Autosaves SHALL preserve accepted draft ordering
and reject conflicting stale writes; acknowledgments SHALL correspond to the
exact revision acknowledged. Unknown, failed and pending saves SHALL not be shown
as saved. Genuine concurrent edits SHALL not be silently overwritten or merged.
Recovery SHALL preserve only still-authorized work and require no new offline
store, body-bearing URL or unredacted diagnostic log.

**LC05 — Explicit shared revision.** One check-in SHALL have at most one current
shared content revision with its exact current named recipient set. Ordinary
edits remain private until the author deliberately reviews and updates sharing.
An update SHALL replace that revision/audience atomically for the exact reviewed
set; different recipient-specific wording requires a separate check-in. Retained
accepted revisions SHALL not become general coach history by implication.

**LC06 — Preview equals proposed effect.** Share/update SHALL bind the exact
reviewed content and question revisions, tenant/subject, recipient episodes,
expected current publication/audience revision and current source qualification.
Newer draft content SHALL not substitute after review. A material mismatch or
ineligible selected recipient SHALL reject the requested effect atomically,
preserving still-authorized draft work and requiring refreshed review rather than
silent partial sharing, changed dates or a replacement coach.

**LC07 — Durable effect recovery.** Repeated transport attempts for the same
deliberate operation SHALL recover the same accepted business effect. A reused
operation identity with changed meaning SHALL conflict. Content hashes alone
SHALL not erase intentionally distinct check-ins. A lost response SHALL not create
a duplicate revision, share or secondary action. Recovery SHALL report the
original accepted effect and current state under current rights, never reapply
an old audience or withdrawn publication.

**LC08 — Independent removal.** Withdrawal or recipient removal SHALL operate
without saving invalid/unshared draft changes and SHALL apply through current
authoritative source commands. An older preview, autosave, publication retry,
restored cache or delayed response SHALL not restore withdrawn access. Unknown
outcomes SHALL offer status/recovery rather than false success or forced new
publication. Any future deliberate sharing after withdrawal requires a fresh
currently authorized review and cannot reactivate an ended coaching episode.

**LC09 — Exact episode and history.** Reads SHALL require the exact current
tenant, subject, coach context/episode, selected check-in revision and applicable
history/source rights. Coach reassignment, the same account in a new episode,
invitation acceptance, numeric-summary continuation or organization enablement
SHALL not disclose existing/future narratives. Deliberate sharing of one existing
check-in SHALL identify that historical item and its current revision, without
granting a broader archive.

**LC10 — Current release and retention.** Saved content, audit evidence and
template history SHALL not themselves establish ongoing audience rights. Enforce
withdrawal, expiry, restriction and context changes on read and asynchronous
release, including preview, lists, search, Realtime, errors and caches. Retention
and erasure remain source-governed; stopping disclosure SHALL not promise to
recall previously viewed text or delete every lawful evidence copy.

**LC11 — Bounded implementation and truthful UX.** Use the existing private
writing/coaching source, shared design system and exact authoritative commands.
Show saved state, current shared revision, unshared changes, intended audience and
confirmed withdrawal clearly. Do not add a survey/approval/merge engine, per-coach
content branches, automatic notification, reminders, coach replies, task creation,
AI, compulsory cadence or broad prior-answer copying through this decision.

## Executed counterexamples and limits

The new [standard-library probe](counterexample-probe/probe.py) reproduced **17/17
finite counterexamples**, Python **3.12.14**; exact constructed inputs and
observations are in [results.json](counterexample-probe/results.json). It does not
implement the proposed commands or test them against a hand-built database.
An independent temporary-directory rerun produced identical parsed results;
all nine local links resolved, and repository Prettier formatting passed. These
are reproducibility/document checks, not production qualification.

The only enumerated ordering experiment is three full-body saves from a single
editor: six arrival permutations exist, and four leave older text as the last
arrival. This disproves an unrestricted last-arrival-wins shortcut for that
synthetic scenario. It is **not** a four-in-six production failure rate, an
arbitrary multi-client ordering solution or an actual network/concurrency test.

Other cases show information the shortcut cannot distinguish: stable question ID
versus changed wording; display position versus answer identity; draft ID versus
accepted shared revision; transport request versus intended effect; same body
versus separate intended check-ins; old successful operation versus currently
withdrawn state; account identity versus coaching episode. Their seeded assertions
demonstrate those ambiguities, not that any proposed permanent fix passes.

No prior D24 or other probe was rerun. No PostgreSQL, hosted Supabase, provider,
browser, accessibility, load or real-user tests ran here. No latency, capacity,
autosave interval, retention period, template-size ceiling or optimal copy length
is claimed. Those limits should be measured/qualified in the actual owning design,
not invented to make this note appear complete.

Before implementation activation, qualify question/answer ownership and current
permissions, then the private draft/publication commands and disclosure races,
then real user comprehension and recovery. The proof obligations above are future
release evidence, not monitoring substitutes. The simple solution requires no
new questionnaire platform, live collaborative editor or privacy system.

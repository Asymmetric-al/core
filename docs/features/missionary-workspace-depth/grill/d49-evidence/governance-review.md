# D49 scoped governance and implementation review

October 18, 2026. Read-only source inspection for Q49 answer A, except creation
of this evidence file. No formal owner document, ADR, OpenSpec, application,
schema, live configuration or GitHub state was changed. No earlier executable
model, checker or probe was executed or imported. This review supplies the
governance portion of the broader D49 review; it does not claim deployed proof
or independent user-research findings.

## Disposition and exact decision

**Accept with required amendments.** The selected answer is coherent and keeps
ordinary setup changes understandable. The strongest alternative, live regrouping,
would support organizational reclassification without correcting each earlier
gift, but would also change earlier-date results after a mapping edit. That is
precisely the tradeoff Q49 asked; it is now selected, not another founder fork.

> Reassigning a source code changes the campaign association for new ordinary
> gifts at their qualified attribution event. Earlier gifts retain their recorded
> effective campaign association, including a recorded absence of a campaign.
> Correcting earlier attribution requires a deliberate, authorized, audited
> Phase 13 correction. Such a correction may change the effective campaign
> association without changing a truthful source code. Preserve original capture,
> prior correction evidence and financial facts. A mapping edit, report rebuild,
> import retry or label change is never that correction. Show the actual scope
> and effect before accepting either action.

This is an owner-contract extension where necessary, not permission to invent a
mutable campaign field on a posted line. No additional approval or product
question is needed to make the already-selected correction path truthful.

The campaign-only correction is an **effective attribution fact owned by P13**.
It is not a separately writable competing campaign field, P14 donor-credit repair,
or a financial adjustment that transfers money between funds. The source-code
registry owns prospective setup; the captured attribution plus append-only
correction lineage owns an existing gift's effective reporting association. The
report is a projection, not write authority. A bulk correction, if provided by
existing owner tooling, must name the admitted source set and preserve the same
per-line authority, result and correction history; D49 does not require a new
bulk workflow.

## Current implementation evidence and limits

The inspected [contribution detail reader](../../../../../packages/api/src/admin/contribution-operations/operations.ts:316)
queries legacy `donations` with flat `campaign_id` and `source` fields, then maps
`campaignId` directly at line 101. This proves a current reader shape, not that a
live report behaves safely or unsafely under a campaign remap.

The [action type list](../../../../../packages/api/src/admin/contribution-operations/types.ts:7)
contains amount, designation, allocation, receipt and payment-state corrections;
it does not define a source-code or campaign-attribution correction action. The
inspected [correction payload adapter](../../../../../packages/api/src/admin/contribution-operations/operations.ts:777)
handles those limited effective-value types and otherwise rejects an unsupported
adapter. Bounded searches for `source_code_id`, `source_codes`,
`giving_campaigns` and `campaign_attribution` in `packages/api`,
`packages/database` and `supabase/migrations` returned no matches. This is
evidence that the target path was not found in those searched locations, not a
repository-wide absence assertion, runtime audit or permission proof.

Existing effective-correction machinery is a reuse candidate, not qualification
of the needed extension. The [D48 decision](../phase28-d48-tenant-correction-approval-decision.md)
governs tenant approval choice. Its current-authority, pending-work and
same-human checks also apply to a newly admitted attribution correction; D49
does not invent a different approval policy or inherit unsafe legacy defaults.

## Remaining owner meaning and implementation proof

The [prepared Q49](../phase28-q49-campaign-remapping-history-research.md) deliberately
limits the answer to ordinary remapping's retrospective effect. These remaining
questions are not silently answered by that choice:

- **Existing recurring arrangements:** [P13:1606](../../../../prds/sitestacker-parity/phase-13-campaign-designation-contribution-ledger-giving-cart.md:1606)
  freezes source-code origin, while [P16:1569](../../../../prds/sitestacker-parity/phase-16-pledges-recurring-commitments.md:1569)
  derives campaign through that code and permits explicit prospective term
  versions. Neither unambiguously decides whether later installments follow a
  later campaign mapping. Preserve the settled source-code origin and ask only
  the remaining campaign-association question when the session reaches it.
- **Hierarchy and historical reporting:** Moving a campaign under another parent
  is distinct from moving a source code. P13:1630's effective-dated reparenting
  and closed/archived restrictions survive. The owner must state the hierarchy
  basis for current and historical measures; D49 does not reopen closed results.
- **Capture and late-arrival seam:** Cart source capture, posting, imports and
  accepted recurring occurrences need one qualified owner temporal contract.
  This is a source-contract integration requirement; do not ask users to choose
  database clocks, locks, tables or migration guesses.
- **Correction/refund and report basis:** Qualify how a current adjusted report
  differs from preserved dated evidence, including corrections after closure.
  No history deletion or silent rewrite is an admissible implementation.

Before activation, prove original-campaign and known-no-campaign gifts remain
unchanged after reassignment; truthful campaign-only correction works; original
code/snapshot and all money facts stay unchanged; first/last-touch lenses are
labelled; archived codes remain historically readable; late arrival, stale cart,
duplicate submission, lost response, concurrent remap/correction/refund and restore
preserve the exact accepted result; source revision changes invalidate dependent
projections; missing evidence stays unavailable; wrong-tenant and unauthorized
old/new state fail at every database/API/service path; and explicit no-campaign
reconciliation conserves the admitted per-currency line set.

Use the existing gift history and correction review. Before saving a mapping,
explain that new eligible gifts use the new campaign and earlier gifts keep their
recorded attribution. Before correcting an earlier gift, show old/new campaign,
truthful unchanged source code, reason and the action required by current policy.
Show Applying/Awaiting approval/Applied only from the owner outcome; preserve
input and reconcile after uncertainty. Exact last-day or recurring claims must
wait for the relevant qualified source rule. Reuse the shared accessible form
and status patterns; no new missionary correction surface is implied.

No acceptance threshold, throughput claim or observed failure rate is inferred
from this source inspection. E7's affected native measures remain gated until
the remaining owner meanings and exact source adapter are qualified; this is
not grounds to disable unrelated permitted relationship work or remove required
financial reporting from scope.

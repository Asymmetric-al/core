# D26 governance and task-ownership evidence

Reviewed October 17, 2026 UTC against repository baseline `9cada8f3d8ab59db391d3fd20df77fcadeb09813`. This is bounded repository research for the selected Q26 A. It changes no source contract, runtime, schema, provider, formal ADR/OpenSpec or implementation ticket. The founder's [scope](../phase28-founder-brief.md:25) permits research and decisions and reserves formalization for the explicit later command. Root instructions, the grilling/domain-modeling skills, the general rulebook and [OpenSpec's authority index](../../../../../openspec/project.md:8) were read. Claims below distinguish intended authority, inspected current source and recommendations.

## Conclusion

**Accept with required amendments.** A live selected-task summary is compatible with current domain intent if it is an additional exact read projection of the existing task/source authority. A task's creation, assignment, title, link, status, invitation or coaching role does not grant sharing authority. The coach gets no task mutation or underlying task-detail access. No task clone, coaching checklist, second task status or generic privacy-redaction engine is needed.

The most important distinction is between an **Independent follow-up task** and a **source-controlled task**. The first can truthfully finish while its linked source remains open; the second closes only from its source's authoritative outcome. Both can potentially supply a qualified coaching projection. Neither is automatically eligible merely because it appears in Maya's task list.

## Initial eligibility without arbitrary narrowing

The economical requirement is a finite admission predicate on the existing task/source contract, not a separate D26 task taxonomy or a tenant-authored rule builder.

1. A candidate is one exact existing task occurrence in the currently selected Tenant and canonical missionary/ministry context. Maya currently holds the producer's allowed sharing authority for that subject and work; visibility, authorship, assignment, household/team membership or old ownership alone is insufficient.
2. The producer has a qualified `coaching next-step summary` purpose admitting exactly the description publication, due-date semantics and status mapping required by D26. Its source facts, privacy/classification and recipient context must permit each output. An unknown task kind or unsupported field/status is not eligible.
3. Ordinary manual tasks and **Independent follow-up tasks** are positive intended candidates when those conditions hold. They are not automatically qualified by the current missionary endpoint. A donor-linked ordinary follow-up is not excluded solely because a link exists; its coach projection must omit donor/source identity and prove that safe wording, dates/status and combinations do not disclose protected facts.
4. Source-controlled tasks are possible only through their source's separately qualified coach projection, current purpose grant and truthful source outcome mapping. Task assignment never grants that projection. Protected finance/care/security/approval work cannot be made shareable by renaming it or writing a generic caption.
5. A task concerning a shared ministry/project needs current exact project/participant sharing authority; Maya cannot share a teammate's work by selecting the project. Reassignment or scope change does not silently move a selected task to another person's coaching view.

**Recommendation:** describe the selected product scope as “eligible ordinary tasks and independent follow-ups, with any other producer admitted only through its exact qualified source contract.” This provides a useful positive journey without promising every task source or arbitrarily declaring every automated/donor-linked task impossible. No current producer is claimed production-qualified. Qualification is per reached producer; D26 does not depend on implementing the whole future cross-domain task platform.

## Wording, identity and live changes

The selected wording “approved description” needs an explicit stability rule. Merely holding an immutable task UUID does not preserve the meaning of what was approved. An ordinary title such as “Call Grace about the sensitive travel plan” must not become coach-visible because the previous title “Prepare for Friday” was safe.

A small safe contract is:

> One sharing item binds the exact Tenant, subject, coach episode/recipient, task occurrence and source projection contract, plus the explicitly reviewed description revision and source content/eligibility revision. Only the admitted due date and truthful current status update automatically while that binding remains valid. The ordinary task remains authoritative; coaching stores disclosure intent and its approved wording, never a second writable task status or due date.

> Any title/description, task meaning, classification, ministry scope, linked protected-source context or assignee/responsibility change invalidates the previous description/eligibility approval deterministically and withholds that item's summary pending a current authorized review. There is no AI or human guess that two meanings are “close enough.” Private notes or other unshared fields need not invalidate approval if they cannot change source eligibility, purpose or disclosed meaning. A new reviewed description does not sanitize an otherwise forbidden source.

The final exact contract should choose whether the approved description is the approved source title revision or a new purpose-specific coaching sentence. Either is workable; the latter can support a privacy-safe short action without copying internal task prose, but must retain the same invalidation and current source checks. It is not a second task deliverable. A cosmetic source text change may ask for review; this is a deliberate, explainable privacy tradeoff, not semantic equivalence inference. Show Maya an inline “Review shared description” route on the ordinary task; preserve her task edit even if sharing must be withheld. Do not block core task work to repair optional coaching.

Due/status changes must refresh from the source under current rights and output qualification. “Stays current” means the next authorized read/revalidation can reflect current source truth; it does not authorize a WebSocket provider, instantaneous-delivery promise, polling all projects or a push payload carrying task bodies. Show refresh/unavailable truth without a fabricated status.

## Lifecycle implications

| Event                                                      | Required D26 effect                                                                                                                                                                       |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create ordinary task, duplicate task or copy from template | No share is created. Each new task occurrence needs deliberate selection.                                                                                                                 |
| Due date changes within admitted source semantics          | Current source due date can update; no rewrite of previous check-ins and no guessed “rescheduled” outcome or audit history.                                                               |
| Source date is date-only / has a time / absent             | Preserve precision. “No due date” is valid; do not synthesize midnight or transform travel timezone into a shifted calendar day. Source contracts must supply precision before admission. |
| Independent task completed                                 | Show the admitted task status only. Do not increment calls/conversations, mark a donor message sent, end an appeal or settle a gift.                                                      |
| Independent task reopened                                  | Only its owner-authorized same-task reopen may change its status while still validly selected. This does not reopen an ended sharing grant.                                               |
| Source-controlled work satisfied                           | Show the source's admitted completion meaning; Tasks Hub/coaching cannot close it generically.                                                                                            |
| Source work canceled, superseded, withdrawn or reassigned  | Preserve the source's distinct semantic state if currently permitted. Reassignment invalidates prior sharing approval; never retain old person's authority by task ID.                    |
| Source access, classification or source-purpose changes    | Fence disclosure before stale cache or delayed projection can release it. A source-safe unavailable state is not completion or proof the hidden task exists.                              |
| Recurrence                                                 | ADR0183 says source recurrence creates a successor. Share does not transfer to successor/series, even if title, due pattern or parent are identical.                                      |
| Source deletion / retention expiry                         | Preserve whatever restricted business evidence its owner requires; stop coach disclosure. Do not cascade-delete unrelated grants or fabricate a completed task.                           |
| Remove this task / Stop next-step sharing                  | Independent narrowing path works even with an invalid draft. Preserve source tasks and unrelated modules.                                                                                 |
| Episode expires, coach leaves, organization Off            | D8/D11 fence affected shares. On, reissue, restore, old request or date edit cannot revive them.                                                                                          |
| Temporary source outage/review withholding                 | Distinguish temporary unavailability from terminal share removal; no automatic grant widening, stale status disguised as current or source conclusion from absence.                       |

Completion may remain visible while the exact item is still admitted; it is not permission for unrestricted completed-task history. No ordinary list should enumerate unshared former tasks or old recipients. Task status may be useful context without a performance score, streak, ranking, punitive overdue color or notification obligation.

## Current implementation evidence and limits

These are inspected-code facts, not a live exploit, complete runtime audit or delivered source contract:

- [`tasks.ts:13`](../../../../../packages/api/src/missionary-portal/tasks.ts:13) admits `not_started`, `in_progress`, `waiting`, `completed`, `deferred`; the API supports generic manually chosen task type/status. Creation supplies the profile identity from server context at [`tasks.ts:84`](../../../../../packages/api/src/missionary-portal/tasks.ts:84), but supplies no D26 share/recipient/contract revision.
- [`task.ts:25`](../../../../../packages/api/src/missionary-portal/task.ts:25) permits title/body/status/due/donor changes. [`task.ts:44`](../../../../../packages/api/src/missionary-portal/task.ts:44) resets `completed_at` from the new generic status. [`task.ts:83`](../../../../../packages/api/src/missionary-portal/task.ts:83) scopes mutation by task/profile; [`task.ts:113`](../../../../../packages/api/src/missionary-portal/task.ts:113) deletes a task directly. Those generic operations cannot be adopted for source-controlled closure.
- [`service.ts:79`](../../../../../packages/api/src/missionary-portal/service.ts:79) reads task title/body/donor link plus donor name/email/avatar/giving preferences. [`service.ts:252`](../../../../../packages/api/src/missionary-portal/service.ts:252) list scopes by profile and optional donor, not a qualified coach episode; [`model.ts:261`](../../../../../packages/api/src/missionary-portal/model.ts:261) returns title/body and applies existing missionary donor redaction. Hiding donor UI would leave raw prose as an uncontrolled disclosure path. A dedicated minimal coach-purpose projection is required.
- [`MissionControlTaskStatus`](../../../../../packages/api/src/admin/mission-control-tasks/types.ts:1) uses a different vocabulary: `open`, `in_progress`, `completed`, `dismissed`, `suppressed`. It is not interchangeable with the missionary vocabulary or ADR0183 typed outcomes.
- The baseline [`missionary_tasks` schema](../../../../../supabase/migrations/20250101000000_init_schema.sql:287) has nullable profile/donor relationships, no direct Tenant column, and timestamp-only due date. Later migration [`20260625002117`:265](../../../../../supabase/migrations/20260625002117_canonical_tanstack_db_realtime_rls.sql:265) revokes anon/authenticated table privileges. The baseline schema and default `pending` are not evidence of a delivered current D26 canonical model; a complete migration/grant census belongs to the database qualification before activation.
- The reached creation/update schemas supply no recurrence contract. This does not prove the whole repository lacks recurrence; it means D26 cannot infer series semantics from these endpoints.
- [`ADR0183:653`](../../../../adr/0183-source-owned-work-projects-into-one-shared-tasks-hub.md:653) expressly identifies these source fragments as migration inputs. They are evidence to reconcile, not precedent to preserve blindly.

No production database, membership, coach role, provider send, real user study, source-write experiment or load test was run for this governance note. No existing endpoint has been widened. A static source mismatch is not a claim of a production incident.

## Proof obligations for the owning review

- Positive exact manual/independent task share gives Jordan approved description, admitted due precision and truthful status, and Maya edits the ordinary task only once.
- Actor with read/edit/assignment but no sharing authority cannot create/expand a share; coach with read projection cannot edit, assign, complete or inspect raw task.
- Two tenants, two subjects, two coaches and two roles/hats cannot cross in list/detail/preview/count/late response/cache or privileged path.
- Title/body/context/reassignment/classification change before or after preview invalidates old approval; same-task admitted due/status update alone stays live.
- Source-controlled cancellation is not completion; independent completion leaves linked source unchanged; connected sending or call task completion does not count an actual send/conversation.
- Same task UUID with changed semantic scope cannot retain old grant; new recurring successor cannot inherit the previous grant.
- Stop versus Save, revoke versus read, source mutation versus preview acceptance, retained-result release after membership loss and provider/outbox delay obey the existing current authorization boundary.
- Due precision, no-date, reschedule, DST/travel, completed/reopened/deferred/unavailable and retained task deletion produce distinct truthful outcomes.
- Existing projection-policy widening takes its owner approval path; ordinary user sharing under the approved policy does not create a needless supervisory approval step.
- Source and task contracts remain usable if optional coaching is disabled or unavailable. Removing sharing cannot delete the task or affect other coaching modules.

These are future acceptance obligations, not claimed passing implementation tests. This note introduces no numeric throughput/latency guarantee or universal retention period.

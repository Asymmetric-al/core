# D26 database and authorization evidence

**Observed October 17, 2026, UTC.** This is a static source and public-primary-document review for D26, not an implementation, SQL migration, deployed-project assessment or claim that coaching access exists. No database, provider account or live user data was accessed. The [finite counterexamples](disclosure-counterexamples.py) exercise deliberately unsafe and guarded design sketches; their [results](disclosure-counterexamples.json) are not Core authorization tests.

## Disposition at this seam

**Accept with required amendments.** Selected read-only next-step summaries are compatible with the existing owner direction. The permanent path is a small, purpose-bound projection of an exact eligible task occurrence, carrying an explicitly approved description and current permitted due/status facts. The current missionary task DTO, legacy table shape and generic staff-task store are not qualified coaching access boundaries. Adding a coach role or an RLS predicate alone would not qualify them.

The [Supabase skill](skill://plugin_asdk_app_69d3e5ee6a708191baa733f7b8931995/supabase/SKILL.md) and [Postgres best-practices skill](skill://plugin_asdk_app_69d3e5ee6a708191baa733f7b8931995/supabase-postgres-best-practices/SKILL.md) were read. Current official documentation takes precedence over shorthand in a skill. In particular, an omitted `WITH CHECK` does **not** automatically permit ownership reassignment: PostgreSQL uses `USING` for the proposed row when `WITH CHECK` is omitted on `ALL`/`UPDATE`. Explicit, independently reviewed old-row and new-row predicates remain appropriate, but omission alone is not a demonstrated vulnerability.

The Supabase skill shorthand that every definer function bypasses RLS is also too absolute: a definer executes with its owner's rights; owner/superuser/BYPASSRLS and `FORCE ROW LEVEL SECURITY` determine actual bypass. Likewise an invoker view over raw source tables is not sufficient when granting underlying table privileges would exceed the coaching purpose. Prefer the existing qualified server boundary and a minimal safe result; if an RPC/definer is needed, constrain its exact input/output, owner, schema, grants and current checks explicitly.

## Required authorization and schema contract

The following is proposed exact spec language, not permission to mutate the current schema. Physical table names and a new generic permissions engine are unnecessary to settle D26.

1. **Exact projection purpose.** D26 SHALL expose only a currently admitted task kind and exact task occurrence within the selected tenant and ministry/project subject. A source-owner contract SHALL enumerate eligible fields, current authority, classification, retention and meaning-changing revisions. Sharing SHALL NOT grant raw task, linked supporter, source detail, comment, attachment, contact, message, financial, export or mutation access. A type lacking such a contract remains ineligible. Personal tasks and source-controlled tasks SHALL preserve their different completion semantics.
2. **One task authority.** Source task identity, due value and status SHALL remain source-owned. D26 SHALL store only selected occurrence reference, immutable reviewed description revision, exact coaching-episode/recipient scope, approval/revocation metadata and minimal audit/semantic receipt facts. It SHALL NOT maintain a second mutable due date, status, task checklist or contact record. Approved wording is projection content, not an alternate task authority.
3. **Safe wording and live values.** Coach output SHALL use the approved plain-text description revision, never a mutable source title/body join. Only permitted due/status values for that same occurrence refresh through a current read. A title/body or other contract-defined meaning revision, tenant/subject/owner transfer, or classification/eligibility change SHALL withhold the projection pending deliberate new review. Reverting old wording SHALL NOT restore old consent. An ordinary due/status change alone SHALL NOT require repeated sharing approval.
4. **Trusted identity.** Actor, tenant/context, owner, sharer, recipient eligibility, timestamps, policy/approval versions and audit attribution SHALL be resolved or verified by the trusted command context; caller-supplied IDs are selectors, never authority. Ownership/scope/recipient identity SHALL NOT be mutable through a generic patch. Source and sharing authorities SHALL validate the entire proposed state, not merely the old accessible row.
5. **Tenant-aware integrity.** Every sharing relationship SHALL have nonnull tenant and exact subject/episode/source-occurrence references. Use composite foreign keys to matching `(tenant_id, id)` keys and subject-inclusive keys where the source contract supports them. Optional end dates and absent source due values may be null; an owner, episode, source occurrence or tenant may not be null in an active share. There SHALL be at most one active sharing record per exact tenant/subject/task occurrence/coaching episode, enforced by database uniqueness rather than a UI check.
6. **Finite state and revisions.** Sharing SHALL distinguish active, withheld pending review and terminal ended/revoked/expired access. Source status is separate; Completed is not revoked and reopened is not a new recurrence. A successor/recurring occurrence needs separate deliberate selection. Revocation/expiry/access-ending policy changes SHALL fence the authorization generation; regrant or re-enable SHALL NOT reactivate an old grant or validate its pending results. A temporary read error SHALL show unavailable, not manufacture revocation or a completed status.
7. **Bounded data and indexes.** Description SHALL be bounded plain text under the D26 profile, with deterministic length validation and no HTML/link/source-body passthrough. Status SHALL be a finite source-owned code with a registered presentation mapping; unknown/unmapped status SHALL not default to Completed. Due date representation SHALL preserve source date-only versus instant/time-zone semantics; null means no due date. D26 introduces no money or numeric activity counter. Index current episode/subject/source lookup paths and uniqueness predicates; bound cursor queries rather than scanning all missionaries' tasks for a coach.
8. **Command atomicity.** Share/update/stop commands SHALL atomically commit the approved exact source/recipient/policy revisions, current eligibility check, sharing state and minimal durable audit evidence or commit nothing. Semantic idempotency SHALL bind the durable business effect and expected generation; replay SHALL neither double-share nor resurrect ended access. A stale command SHALL return a safe review-needed/conflict result with no partial new audience. Stopping sharing SHALL not depend on valid pending wording or successful source-content loading.
9. **Deletion and retention.** Source deletion/end-of-retention SHALL remove body access and terminate the corresponding live projection without deleting required minimal sharing evidence. Retention for a projection SHALL never exceed the qualified source/purpose ceiling. Do not use blind CASCADE on audit evidence or retain task bodies in audit rows indefinitely. A narrow tombstone/reference may preserve the fact that access ended where the owner retention policy permits; it is not a coach history grant. Restore/backup recovery SHALL replay current fences before serving restored sharing data.

### Grants, RLS, API, RPC and storage coverage

Keep raw source and sharing storage server-only unless a separately qualified safe browser contract is deliberately introduced. For exposed tables, revoke automatic grants first and enable RLS in the same migration. `anon` receives no D26 access. A signed-in coach receives only the purpose-specific read path, never raw source mutation grants. RLS authorization must incorporate exact tenant, subject, episode, current share generation, current eligibility and expiry—not merely `auth.uid()` ownership or `TO authenticated`.

For any actual mutation policy, review both old-row `USING` and proposed-row `WITH CHECK`, plus SELECT requirements. Do not allow an update to change owner/tenant/episode/task selectors into a different permitted or forbidden relationship. RLS cannot by itself make these fields immutable, and multiple permissive policies must be checked together. Direct Data API, PostgREST RPC, GraphQL, service-role commands, jobs and recovery tooling must all preserve the same authority. Domain routes belong in `packages/api` under the [data-access boundary](../../../../guides/architecture/data-access-boundary.md:9).

A narrowly justified definer function must have safe fully qualified references/search path, a nonpublic bounded execution surface, minimal owner privileges, explicit revocation of default PUBLIC EXECUTE, caller identity verification and a fixed output shape. No raw object names/dynamic SQL or caller-chosen actor/tenant claims. An invoker function/view must be checked for its actual underlying-table privileges and RLS behavior. Broad `service_role` exists in current code; do not mistake RLS for defense against that path.

D26 needs no new Storage object, signed download, calendar feed, Realtime task-body publication, webhook, AI processing or public share URL. Existing stores and caches must not inherit summary permission by association. Private cache responses must be scoped by tenant/subject/actor/episode/generation and invalidated on access loss; cache hits do not replace current authorization. Realtime invalidation, if ever added, should carry no protected body and does not itself authorize a fetch. Clearing the UI is useful but cannot retract data already delivered.

## Race contract: the hard boundary is disclosure

“The request was allowed when it started” is insufficient. A share review can race with task edits, a coach can be removed during a query, and a stale cached response can arrive after a fresh regrant. Separate permission and content queries without a coherent revision fence are especially hazardous in the current administrative-client architecture.

**Exact requirement:** protected disclosure and share commit SHALL have an explicit authorization linearization point coordinated with policy/episode/share/source changes. If revocation wins before that point, no body is released; if disclosure wins first, its already released bytes cannot be recalled. New requests after revocation SHALL fail closed. Every pending result SHALL be bound to the episode and authorization generation that admitted it; it SHALL not be installed into a changed browser context. This does not promise that no packet authorized before revocation can arrive afterward.

For implementation, establish the owner-approved database transaction/locking or equivalent serialization strategy at the actual release seam. Use a stable lock order and bounded short critical sections; do not hold a database lock across slow provider/network calls. An old Repeatable Read snapshot or authorization timestamp is not proof of fresh revocation state. An application-level final check with an uncoordinated gap before disclosure is not a proof either. Generation/expected-head checks must be enforced where the authoritative state can change, not only encoded in a client cache key.

## Finite falsification performed

The executable model produced **9 negative counterexamples and 3 positive controls**. Each negative demonstrates a deliberately unsafe old-authorization/raw-source strategy releasing or committing something that a corresponding guarded contract sketch rejects:

- changed wording after review;
- source moved to another ministry;
- a recurrence-series pointer resolving to an unselected successor;
- stale response from before revoke/regrant;
- read at exact expiry;
- a late result from an old permission query after revocation;
- policy Off then On reviving old consent;
- original wording restored after an intervening meaning revision;
- preview before expiry followed by Share commit at expiry.

Positive controls retain live due/status updates, permit a source-authorized ordinary reopen of the same occurrence, and acknowledge a legitimate release that precedes revocation. Reopen here proves only the model distinction, not that every Core task type allows reopening. The comparator has no database, SQL policy engine, asynchronous HTTP scheduler, storage layer, provider, browser or real permissions resolver. It therefore **does not** verify any implementation or justify a concurrency-safety claim. It falsifies simpler designs and gives concrete required test histories.

## Required implementation proof, not performed here

Before activating D26, test real role/grant/RLS/API/RPC paths with anonymous, unrelated authenticated, wrong tenant, wrong subject, revoked coach, current coach and independently authorized staff identities. Prove authorized results are nonempty when expected; a query that succeeds with zero rows is not an allow proof. Test direct underlying-table writes/reads, malicious selector reassignment, source type boundaries, stable IDs, DTO field allowlist and source/recipient deletion. Test two transactions racing Share versus revoke/expiry/source edit, stale response after regrant, same-command retries, idempotency receipt conflicts and crash after commit before response. Include nullable due, unknown status, date-only versus instant/timezone, hard-delete/retention, migration old/new versions, restore fences, portfolio pagination and database query plans at the documented limits.

This review does not supply a signed-off source-task registry, actual P12 capability mapping, production locking design, migration/backfill, live RLS catalog, performance evidence or deployment qualification.

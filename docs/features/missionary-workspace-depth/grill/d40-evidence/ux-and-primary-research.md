# D40 — UX and current primary research

Reviewed **October 18, 2026 (Asia/Bangkok)**. Scope: the founder selected **A — Keep it informational** for one source-confirmed missed automatic recurring occurrence whose recovery has ended while the next ordinary occurrence remains scheduled. This evidence note proposes the UX and amendments for the root review; it does not independently ratify them or implement a component, permission, notification contract or task producer.

## Finding

Accept A with precise boundaries. Put the missed occurrence and the current next ordinary gift together in the existing authorized recurring-support detail. Preserve a quiet factual entry in history, a source-owned current lifecycle statement, and the ordinary deliberate **Add follow-up** action when permitted. The missed occurrence does not itself create obligatory work. Existing source-qualified action-needed work remains intact.

Optional notification delivery and optional workspace presentation can be controlled through their existing owners. Turning off a notice cannot erase a financial fact or change collection; hiding a financial module is an access/publication decision, not a second definition of what happened. Avoid a new per-supporter preference, missed-count threshold, review scheduler or automatic-task switch in this decision.

This is a product judgment informed by comparable documented patterns. It is not a measured claim that all missionary organizations prefer fewer tasks or that this arrangement improves donations. No ministry interviews, live authenticated competitor tests, user study or benchmark performance measurements were performed.

## Complete proposed journey

### Staff configuration

Use the existing organizational recurring-support publication and notification settings. Explain each control in terms of its effect. The following labels are proposed product copy, not a claim that these exact settings already exist:

- Existing publication/access setting: **Recurring-support information**. Helper: “Choose which currently authorized missionary roles can view recurring-support information.” This controls the whole qualified module/profile. It must not provide a per-fact switch that lets a tenant falsely report Received or hide a miss inside an otherwise complete financial history.
- Existing optional notice setting, if the exact P16/P17 contract is qualified and Live: **Missed recurring-gift notices**. Helper: “Show an informational notice when a scheduled gift is confirmed not received. Gift history stays available according to access permissions. No task or message to a supporter is created by this setting.” Use the existing channel controls; do not add email/SMS/digest or force a parallel setting simply for D40.
- Existing task permission controls govern deliberate task creation. D40 adds no separate mandatory-review or auto-task preference. If the organization disallows deliberate tasks in the applicable scope, omit Add follow-up and still show permitted factual information.

Recommendation: retain existing configured defaults; for a new optional terminal-miss notice profile, do not enroll recipients merely because this founder answer was recorded. Do not turn existing organizational access on as a migration side effect. The root decision should explicitly resolve any notice default it intends to add, rather than treating vendor defaults as approval. A disabled or Reserved notice does not prevent source truth from working.

Configuration is organization-wide within the existing publication/role and notice owners. Avoid per-missionary/project exceptions, thresholds, timing fields and duplicate enablement flags unless an existing owner contract already requires them. Permit finite supported customization such as saved views and approved copy/branding, while preserving the factual label, currency/date, no-debt meaning, channel limits and permissions.

The settings summary must make existing-data behavior clear: **“Changes affect future eligible notices. Existing gift records and your tasks are kept.”** Previously delivered items remain subject to normal retention and current access, not automatically erased by the delivery switch. Re-enabling must not backfill old terminal misses. If the organization revokes financial visibility, current-access enforcement applies to existing notices, source links, caches and task source summaries as well; copied sensitive strings cannot be a bypass.

### Maya discovers the fact

Use the normal recurring-support view reachable from the supporter or existing support summary. A missed occurrence is an entry with a factual text status and scheduled date. The current recurring line has its own lifecycle statement. Do not label the supporter, household or whole supporter list **Failed**, **Lapsed**, **Overdue** or **Owes**.

If an optional qualified in-product notice exists, it links into this same record; it does not create a new destination. Group only under the current authorized communication/source contract. A grouped count is not a count of donors or an instruction to contact every named person. Do not manufacture a notification as a client-side banner while its catalog key is Reserved.

The homepage's required-work queue does not gain an item or badge merely from this fact. Users who want to inspect occurrence outcomes can use existing source-qualified filters or saved views. This is visibility without a compulsory check-off.

### Maya opens the detail

Use a compact vertical summary with explicit labels and ordinary type hierarchy. Example numbers and dates below are illustrative, not defaults:

```text
Recurring support continues

Scheduled gift · 1 October 2026
USD 100.00 · Not received

Next scheduled gift
USD 100.00 · 1 November 2026

View gift history                         Add follow-up
```

Use the source's current lifecycle wording if it is more specific, for example **At risk — recurring gifts continue**. Do not replace a source-qualified risk with blanket reassurance. A sentence available in the source detail can explain: **“This scheduled gift was not received. The next scheduled gift remains USD 100.00 on 1 November 2026.”** Preserve P16's no-debt/no-backcharge meaning in the underlying source explanation; do not suggest that Maya should collect a missing balance.

The next amount/date is explicitly scheduled, never guaranteed, received, forecast cash or an extra catch-up charge. Show currency with the monetary amount using the approved formatter and source precision; no hard-coded dollars, two-decimal fallback or FX comparison. Use actual date precision and appropriate locale. When the schedule has a source zone, show it where date interpretation can differ; do not render a civil date as a UTC instant and shift its day on travel.

Essential facts and actions must be visible without opening a tooltip. A small **Details** disclosure can contain permitted source freshness and factual history. Technical retry slots, card/bank/payment-provider details, private staff notes, hidden sibling lines, exact decline causes and payment-control actions are absent.

No warning animation, red page background, toast on arrival, modal acknowledgement or **Resolve gift** button. A normal text badge may use the existing informational semantic treatment. A source-qualified action-required state elsewhere can use its own higher-priority treatment; D40 does not dilute it.

### Deliberate follow-up

**Add follow-up** opens the existing qualified task composer with the permitted relationship/source already linked. It creates nothing on open or cancel. Do not prefill “Collect missed payment,” a call/email method, an urgent priority or a source-invented deadline. Maya chooses the actual purpose/title and can use ordinary optional due-date/notes controls. Do not force her to describe why she viewed a financial fact.

After confirmed save: **“Follow-up added.”** Include **View task** and a persistent link in the permitted related-work area; a fleeting toast is not the sole evidence of success. Task creation does not send a message, promise a charge, update financial truth, count an interaction or share coaching content.

If a task for this exact source context is already visible, expose **View follow-up** beside or before Add follow-up to discourage accidental duplicates. Do not silently deduplicate all intentional tasks forever: distinct human purposes remain possible. A double tap, network retry or lost acknowledgement must resolve to the same durable submitted action; no second task. A deliberate new task after observing the prior one is a separate user action under the ordinary owner rules.

When source facts later change, update the permitted linked source summary. Preserve Maya's authored task purpose and completion history. Do not automatically complete, delete or cancel her deliberate relational work because the next gift succeeded. The source-linked facts cannot remain silently frozen as a false current status; show relevant current correction and offer the ordinary task edit/cancel path when she decides it is no longer useful.

### Failures and constrained access

- **Status updating:** preserve only independently valid facts. Do not assert a confirmed miss, current schedule, zero support or renewed collection from stale/contradictory inputs. Do not auto-open a follow-up composer or queue negative outreach while state is uncertain.
- **Save pending:** use the ordinary pending button and keep input. On timeout say **“We couldn't confirm whether your follow-up was saved. Check your tasks before trying again.”** The implementation must reconcile the same operation identity and return the existing result; the instruction is not a substitute for idempotency.
- **Save rejected:** show inline specific safe reason, retain still-authorized inputs, and let Maya correct/retry. Never display successful creation before server acknowledgement.
- **Access changes:** clear unauthorized source information and reject the dependent mutation; use neutral **“This information is no longer available to you.”** Do not reveal a donor name in an error or a hidden task's existence. Preserve unsaved text only if current retention and disclosure rules permit it.
- **Tasks unavailable:** omit Add follow-up on normal detail rather than showing a dead disabled button. If an already-open composer loses permission, explain the change inline. Settings may explain policy to authorized staff; ordinary users need only the actionable, safe message.
- **Low bandwidth:** text-first detail, bounded history pages and explicit loading/error/retry. No network polling animation, auto-refresh focus jumps or offline claims of financial state. No locally persisted financial/contact payload by default.

## Accessibility and polish acceptance notes

These are implementation acceptance criteria, not passed tests:

1. At 320 CSS pixels and 400% zoom, both dates, status, amount/currency and primary links remain readable without horizontal page scrolling; long translated labels and international names wrap rather than displace the status/action.
2. Existing Base UI dialog behavior provides a named heading, sensible initial focus, Escape cancellation, focus containment and return to the trigger. Keyboard users can create or cancel without pointer input. Save errors keep focus predictable and are associated with their fields.
3. Mobile controls use Core's 44px minimum hit area; concise visible labels and enough spacing avoid activating View history instead of Add follow-up.
4. The screen reader reading order matches the visible sequence: current line state, historical occurrence, next ordinary scheduled gift, source details/actions. A decorative status icon is not read twice; the text carries meaning independently of color.
5. Announce a completed task save or relevant failure through the existing accessible status mechanism. A quiet background source refresh does not repeatedly announce the entire history or steal focus.
6. Dates remain explicit rather than only “last month,” “tomorrow” or “30 days overdue.” Supported locale/zone and currency rules apply uniformly to source detail and task link.
7. Current light/dark semantic tokens preserve contrast; no alternate style preset, bespoke red/yellow palette, animation or new dependency. Reduced motion remains under Core's shared owner.
8. Distinguish empty, unavailable and loading: **No recurring gifts in this view** only after a complete authorized empty result; **Couldn't load recurring support** offers Retry; hidden scope is not reported as zero.

## What is proved and what remains to prove

Verified: current official pages document the compared patterns; repository source intent separates financial truth, notice and required work; current supporter/task UI offers reusable navigation/components but does not prove the intended P16 model. The proposed minimal flow handles the listed states without inventing a new work item or financial authority.

Reasonable inference: preserving information inside existing detail should reduce the steps needed to understand one occurrence, and avoiding a new mandatory task avoids one additional obligation. Neither is a measured usability result.

Product judgments: calm factual copy, no extra alert surface, ordinary Add follow-up, no count/threshold settings and use of existing tenant controls are the recommended permanent design.

Release proof still required: the exact source-projection/API/RLS path, tenant publication and Live notice profile, task-owner mutation/idempotency, current-access cache behavior, source correction behavior, automated and manual accessibility, representative phone/low-bandwidth tests, and observed comprehension. Do not claim a notification or migration is available merely because this note describes it.

For formative usability, ask missionaries and authorized staff to identify: what happened, whether the next gift is guaranteed, whether money is owed, whether anyone was contacted, and how to choose follow-up. Include settings-Off, stale-state and corrected-occurrence cases. Any misunderstanding that a donor owes money, the system already contacted them, or a scheduled gift is received blocks copy/interaction release. The proposed test design is a release gate, not evidence that participants have already passed it.

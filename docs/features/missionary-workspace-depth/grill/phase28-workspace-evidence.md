## Revalidated investigation leads

### 1. Bounded reads are real, but differ by surface

**Temporary.** Dashboard service loads 250 donations, 250 donor rows, 100 tasks, and ten posts, with no completeness/cursor fields in the snapshot: `packages/api/src/missionary-portal/service.ts:194`–`:231`; snapshot type at `model.ts:112`. Gifts are ordered by gift date, donors by last gift date, tasks by sort key, posts by creation time. The dashboard subsequently treats every non-completed loaded task as attention, including deferred tasks (`packages/missionary/components/dashboard-view.ts:73`), and displays only the first four (`dashboard-home.tsx:437`). A count here is a loaded count, not proof that no other obligation exists.

**Useful, incomplete for requested search.** Partners endpoint pages 50 by default, maximum 100; obtains one extra row to prove `hasMore`; activities/pledges are capped at 2,000 each for the current donor page (`packages/api/src/missionary-portal/donors.ts:450`, `:497`, `:532`). Hook exposes load-more (`packages/database/hooks/missionary-donors.ts:149`). UI explicitly says “Partners loaded” and “Lifetime (loaded window)” (`apps/missionary/app/donors/donors-page-stats.tsx:113`, `:128`). Search/filter/sort are applied to loaded rows (`use-donors-page-view.tsx:166`; `donors-list-model.ts:94`), not a complete authorized server search. Related-row truncation has no separate completion flag in the inspected DTO.

Standalone task list has no explicit application limit or pagination (`service.ts:252`). Metrics has a 13-month date filter but no explicit pagination (`packages/api/src/missionaries/metrics.ts:246`). Neither fact proves complete results under deployed Data API row limits. No production limits were queried.

### 2. Monthly support and received money are not yet owner-qualified measures

**Conflict if retained as Phase 28 financial meaning.** `recurringMonthlyCents` is the sum of every loaded settled gift labeled recurring, without a calendar-period, cadence, Legal Entity, or currency grouping (`packages/api/src/missionary-portal/model.ts:357`). `raisedCents` prefers `missionaries.current_funding`, otherwise sums loaded gifts; denominator is `funding_goal` (`:360`). Dashboard labels these values “Monthly Support Goal” (`packages/missionary/components/dashboard-home.tsx:248`). The snapshot contains no provenance, source revision, currentness, scope, or completeness envelope for this comparison.

The schema originally declared those missionary fields as numeric defaults of zero (`supabase/migrations/20250101000000_init_schema.sql:44`), then converted them to BIGINT cents (`20260214090000_foundation_1_schema.sql:520`). This documents retained column meaning, not a Goal Version or an authorized balance source.

Partners' monthly pledge summary takes only the first active legacy pledge, returns monthly unchanged, quarterly divided by three, and every other cadence divided by twelve (`apps/missionary/app/donors/donors-page-model.ts:217`). The detail can display multiple recurring rows but maps old total-paid/expected/payment-method fields (`packages/api/src/missionary-portal/donors.ts:308`; `apps/missionary/app/donors/donors-page-detail-recurring.tsx:78`). Those are not proof of multiple qualified Phase 16 commitments.

Owner clauses already settle the engineering direction: Phase 16 owns cadence normalization/commitment truth; compatible Phase 28 Goal Versions are denominators; explicit adoption from a Phase 21 plan retains provenance without live synchronization (`phase-16-pledges-recurring-commitments.md:3033`). Phase 21 keeps approved need, goal, activity, commitments, confirmed balance and reserve distinct (`phase-21-field-accounts.md:421`). No founder choice is needed to preserve these distinctions.

### 3. Currency/date assumptions are visible and must not become source truth

Metrics endpoint selects only ID, amount, donation type, creation timestamp and status (`packages/api/src/missionaries/metrics.ts:251`); client uses `created_at`, accepts only status `completed`, and groups numeric amounts without currency (`packages/lib/hooks/use-donation-metrics.ts:65`, `:98`, `:254`). ### 4. Relationship identity is still a single legacy donor link

Original FK/comment: `supabase/migrations/20250101000000_init_schema.sql:66`. Current service deliberately uses profile ID for donors (`service.ts:209`) and missionary-record ID for gifts (`:200`). Legacy browser mapper documents the mismatch (`packages/database/hooks/missionary-donors-model.ts:257`), but no current app import of that mapper was found; the active hook is the redacted endpoint.

Pledges on the Partners endpoint are scoped by tenant and donor IDs; they are not filtered to an independently qualified ministry/commitment purpose (`donors.ts:542`). This donor-primary-association model cannot establish Phase 9 Ministry Assignment, Phase 27 continuing partnership, multiple ministry participation, household rights, or Phase 21 access. Retain existing IDs/data as migration evidence; do not simply reinterpret or delete them.

**Conflict with accepted narrow shared-context meaning.** Named donor DTO includes general `notes`, all loaded donor activities and a `score` default (`donors.ts:372`, `:427`, `:429`). Existing named-row fields cannot be relabeled as the accepted exception. Transported `score` is not evidence that the UI displays a rating; no such qualified rating was demonstrated.

### 5. Server redaction is useful, but the complete anonymity story is not proved

**Durable/useful.** Redaction is performed before the roster reaches the browser. Missing, null or non-false recipient preference fails anonymous; pure helper supports per-gift overrides and unknown-offline precedence (`redaction.ts:38`). Anonymous partner rows remove contact fields, free text, activities and recurring details (`donors.ts:378`). Profile/tag writes independently require explicit boolean false at the server mutation boundary (`donor.ts:149`, `:174`). Preserve this server-side principle and fresh checks.

**Qualification gaps.** Portal donation select does not load per-gift anonymity or donor-identity status (`service.ts:47`); the model explicitly says only donor defaults are currently applied (`model.ts:306`). Gift redaction builds its anonymous-ID set from the separately capped donor list (`:309`), so an absent donor is not evaluated by the fail-closed helper. Task mapping scrubs joined donor name/email/avatar but passes through task title, description, and donor linkage (`model.ts:261`; `redaction.ts:101`). The current redactor itself intentionally retains relationship/task IDs. These facts require source-qualified treatment of per-gift policy, missing scope, derived text, links, notifications, exports and history. They do not establish that an exploitable production identity leak currently exists.

Current task schema has no cancelled/attempted outcome, source-purpose effect identity, responsible-person separation, or actual-interaction transaction (`tasks.ts:13`, `:30`).

**Accident/conflict:** task creation/editing through `TaskDialog` directly calls browser Supabase and selects a raw donor join (`packages/missionary/components/task-dialog.tsx:181`, `:202`). The correct conclusion is an unqualified divergent path, potentially failing under the documented grants, not an assumption of working create/edit or a proven live bypass.

`missionary_tasks` is a separate legacy table keyed to profile ID, with donor ID and mutable status (`supabase/migrations/20250101000000_init_schema.sql:287`). API selects/inserts `is_auto_generated`, but a search of committed SQL did not find that column added; initial task DDL lacks it. Treat this as schema-alignment evidence needing later verification, not proof of current database state. No source-qualified automatic stewardship producer was found in the inspected missionary API/UI/hook paths.

## What is reusable and what remains missing

Retain the canonical server business boundary, scoped redacted DTOs, explicit permission checks, honest loading/error states, loaded-window labeling, shared UI controls, recoverable profile drafts, and the rule that a task tick does not fabricate a conversation. Reuse these only with the correct domain-owned sources and current authorization.

The inspected current workspace does not establish qualified Phase 9 Party/Ministry Assignment/referral/shared-task integration; Phase 27 continuing partnership/Request/appeal projections; versioned goals; Phase 16 expected-support and attention adapters; Phase 13/14 allocation and recognition semantics; Phase 21 authorized per-currency modules; permanent source-purpose stewardship task effects; independently scoped coaching; or Phase 6/17/25 eligible newsletter preparation/dispatch. This is a statement about inspected paths, not a repository-wide proof that every producer is absent.

Highest-leverage product unknowns for grooming:

1. **Private prospects:** when a missionary first records someone they hope to contact, who can see the new record before deliberately sharing it, what restricted organizational administration is permitted, and what explicit action promotes it into shared relationship work? Current Add Partner cannot answer this. Household/team/shared-mailbox edge cases depend on this boundary.
2. **Daily starting point:** how should the workspace balance deliberately managed support-raising work with ordinary long-term relationship maintenance while keeping voluntary shared history voluntary? Accepted Phase 27 already rules out compulsory logging/coaching and financial value rankings.
3. **Deliberate completion:** which optional outcome prompts make “record what happened once” useful on a phone without making task completion imply a call, message delivery, donor response or financial change? Exact source obligations remain owner-defined.

Do not ask the founder whether to sum mixed currencies, invent zeroes, use raw donor tables, or copy protected notes: inspected owner contracts already answer those engineering questions. No issue graph, new specification, live cutover, or external communication is authorized by this note.

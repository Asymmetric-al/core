## Meaning of the synthetic model

The fixture uses fixed source profiles binding tenant, subject, currency, half-open period, giving timezone and admitted cohort. A caller chooses only a pre-seeded profile identifier; it cannot submit an arbitrary cohort or SQL predicate. Profiles are immutable through tested actors and the command executor. This is a small hypothesis fixture, not a new production registry, custom cohort builder or permission engine.

`expected` represents already-qualified, non-overlapping dated expectation facts. `received` represents an already-qualified effective designation-line fold. Neither input is a gift/payment header repeated for each allocation. The fixture does not derive these facts from real commitments, gift dates, refunds, redesignations or fulfillment applications. Its calendar boundaries and cohort labels test exact scoping; they do not prove timezone conversion, DST, source-date precision or P13/P16 eligibility.

The [financial owner review](financial-truth.md) governs the proposed product meanings: expected is a dated plan; received is effective recorded gifts through an as-of cursor. Even with the same named month and currency, these are not the same horizon or fulfillment population. No default received/expected ratio, expected-minus-received shortfall, receivable, spendable balance or goal comparison follows. A source-qualified monthly-equivalent measure remains separate. The unsafe ratio in this probe is only an information-disclosure example, not a valid financial metric.

The `facts` table stands in for the **already purpose-admitted input projection**. Its fixed profile predicate is applied before SUM. The test does not execute per-line P3/P10/P12 classification, anonymity, entity scope, source admission, or small-cell rules. In production, a trusted producer must obtain that admitted input through the source owner; access to all tenant rows with a service credential is insufficient. Separately, a coach must be entitled to the exact output profile. This does not require giving the coach raw input-row permissions.

The effective-grant boolean and revision represent the result of the existing P12 decision for one exact profile/module. They do not model additive grant sources, the four active-context types, permission floors, or a new tenant-wide DENY. A revision change in this fixture concerns the tested exact grant; it does not mean every unrelated tenant policy change must invalidate all summaries. Actual owner-approved requalification can establish the same original intent under current authority.

## Actual roles, privileges and currentness

Real login roles `coach_a`, `coach_b`, `coach_tenant_two` and `source_manager` are nonsuperuser/non-BYPASSRLS and cannot create roles or databases. A NOLOGIN executor owns the functions but does not own tables. All seven tables have enabled and forced coarse tenant RLS. Coaches receive bounded function execution only, with no facts/history SELECT or source UPDATE. Default PUBLIC execution is revoked in the same setup transaction. Search paths and actual ACLs are retained in [roles.json](postgres-probe/roles.json) and [privileges.json](postgres-probe/privileges.json).

A fixed `session_user`-to-tenant mapping supplies identity inside the isolated test. It is not Supabase Auth, JWT verification, a Core Active Tenant Assignment or a proposal to add a global `profiles.role`. Structural CHECK/FK cases deliberately run as fixture administrator so their errors isolate constraint behavior; actor access cases and races run under the stated real nonsuperuser roles.

The bounded reader locks current exact grant, source head and completeness record. Before generating or serving a snapshot it requires the current grant, exact profile/target, complete coverage and matching source revision. The stored snapshot key includes exact tenant, principal, profile, module, grant revision and source revision. Old snapshots remain retained but cannot be selected as current by the reader. This is an ordinary synthetic snapshot table, not a PostgreSQL MATERIALIZED VIEW implementation.

The executor receives limited UPDATE privileges on lockable columns because PostgreSQL locking SELECT requires an UPDATE privilege on at least one column. Tested functions do not expose those updates; coaches cannot assume the executor role. No actor can insert source facts through the bounded reader. Source publication steps use fixture administrator control and are explicitly captured in the results, rather than being claimed as a qualified P13/P16 mutation path.

Exact whole finite NUMERIC values reject fractional minor units and NaN in the test. A zero-exponent JPY profile remains separate from USD. A value beyond JavaScript's safe integer range is serialized as a decimal JSON string. This proves that SQL can preserve that value through this output; it does not qualify the actual BIGINT adapters, currency exponent registry, overflow bounds, TypeScript driver, rounding rules or display formatter.

## Proposed clauses and remaining qualification

**DB9-01 — Exact source profile and grain.** Each supported output identifies owner metric/version, purpose, typed subject, tenant/entity scope, currency, period/dating basis, allowed grouping/history and source cursor. Expected and received retain separate meanings. Count each qualified source fact once; neither join multiplicity nor amount-based DISTINCT may define financial identity. Unsupported source composition is unavailable under an honest label, not locally approximated.

**DB9-02 — Exact numbers through the boundary.** Preserve owner integer minor units, ISO currency, bounded exact aggregation and lossless serialization. Do not combine currencies, assume every currency has two decimal places, or introduce float ratios/rounding in the dashboard. A compatible source-qualified monthly-equivalent goal comparison needs its own defined metric; it does not authorize a default shortfall or fulfillment percentage.

**DB9-03 — Admit inputs before arithmetic; keep raw tables closed.** Obtain the source-approved post-floor input projection for the coaching-summary purpose, then apply the registered output disclosure profile and current coach authority. A bounded reader or qualified projection may return aggregates without raw coach SELECT. Granting raw finance SELECT to support an invoker view is unacceptable. Service rights, hidden names and tenant-only RLS are not input admission.

**DB9-04 — Coverage and revisions determine currentness.** The source producer certifies complete/partial/unknown/suppressed coverage for the exact metric and revision. Only complete, permitted, current empty input can mean zero. Bind cached results to source/admission/current-context evidence and reject stale or revoked output before serving. Preserve source history without exposing old snapshots through an alternate door; do not confuse historical acceptance with current disclosure permission.

**DB9-05 — Treat combinations as disclosure.** Consume P12's existing tenant-tunable small-cell floor and P3/P10 derived sensitivity rules. Qualify the finite output profile as a combination, including ratios, counts, multiple currencies, adjacent periods and prior releases. Do not invent a universal N or claim that removing names, rounding a number, or passing this small fixture proves anonymity. Safe suppression/coarsening follows the owner and must never be rendered as financial zero.

**DB9-06 — Qualify the actual source and every reached door.** Implement through the existing source/P12 projection boundary with its audit, read budget, uniform errors and governed egress. Verify real P13/P7 effective gift dates/corrections/fee-cover exclusions, P16 non-overlapping dated expectations, consent/classification floors, exact D8 relationship/history and all API/cache/job/export paths. The toy reader's multiple locking reads do not satisfy or benchmark P12's R6 budget. No new projection framework or permission engine is authorized by this probe.

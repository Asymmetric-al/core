# D35 — direct continuation, existing permissions and honest results

Research date: **October 18, 2026 Asia/Bangkok**. All seven official sources below were freshly opened on October 18, 2026. Publication/update dates are recorded separately. The founder selected **A: missionary continuation when the organization permits it**. This is research for the answer review, not ratification of proposed amendments, an implementation specification or runtime proof.

## Conclusion and selected boundary

Recommend a single contextual **Continue referral** action for a currently authorized missionary and an otherwise eligible ordinary expired referral. Use the existing permission administration system to authorize that bounded action. Avoid a second approval, a compulsory explanation or a referrer-reconfirmation form for every ordinary continuation unless the source owner establishes an actual requirement. No examined source demonstrates that such blanket ceremony is necessary.

The recommendation is product judgment, not measured missionary preference. Direct actions are documented elsewhere, but their retained access, status meanings and side effects differ. The strongest contrary example is a restore operation that also restores membership and resets permissions. Core should not import either blanket restoration or blanket resetting of unrelated state.

The [original Q35 snapshot](q35-before-answer.txt) records the preceding unanswered question; the current founder answer selects A. [Ratified D34](../phase28-d34-expired-referral-history-adversarial-review.md#exact-corrected-decision-to-record) remains a limited historical-read purpose. Seeing that history is not permission to continue it. D35 does not turn withdrawal, invalidation, privacy revocation, reassignment or departure into ordinary expiry. Staff retain only their independently authorized action scope.

## What to adopt, what to resist

**Keep the action explicit and narrow.** A dedicated Continue referral label communicates the intended work better than asking Maya to edit a generic contact status. This is a recommendation, not a vendor comparison result. Reading the D34 entry, receiving a gift, opening a link or waiting must not silently continue it. Do not silently relabel the person globally, reopen cultivation or infer that an interaction occurred.

**Use the existing authorization system.** Represent the exact action and its scope through the existing P12 permission machinery and administration surface. A named capability may need to be added to that owner; this research does not establish that it already exists. Example administrator wording: **Continue eligible expired referrals**. Supporting text can explain that this permits a deliberate return to active referral work while current access/contact rules still apply. Keep it separate from **view expired referral history**. Configuration authority need not disclose the underlying referrals.

Customizable tenant permission does not require a new referral policy builder, per-referral ACL, parallel approval table, third permission hierarchy or missionary personal setting. Reuse the owning system's actual inherited/effective permission behavior rather than inventing an extra default. The founder's selection does not itself choose a global On/Off default, new inheritance semantics, broad contact access or overrides of source/privacy floors.

**Preserve source truth, not every old side effect.** Continuing the same eligible source work should preserve its historical evidence and re-evaluate current authority. It must not restore revoked private context, consumed tasks, old notifications or former responsibility. Equally, it should not clear independently valid access, notes or promised follow-up just to make everything look new. The exact source contract decides which independently valid records remain; a blanket reset would create avoidable work and lose meaning.

**Do not import bulk operations.** S01 and S04 document them, but they are a separate scale and error-recovery problem. The selected ordinary journey needs one referral action. No demonstrated demand here justifies a bulk continuation flow, all-selected checkbox, automatic renewal, timer editor or cross-ministry transfer.

## Strongest simpler alternative and remaining uncertainty

Staff-only continuation would centralize judgment and reduce missionary action rights. It remains the legitimate operational path where the organization does not grant the action or the missionary path is unqualified. Its cost is an extra handoff for otherwise authorized ordinary work; no measured frequency or delay is asserted. It is not selected as a mandatory second step after A.

The selected direct-action path is proportionate only if there is a meaningful authorized result. A button that claims continuation but leaves the source unchanged, fabricates a deadline or offers no understandable next state is not useful. Conversely, useful continuation does not require displaying every historical field or sending a message. Exact eligibility and future-window semantics belong to the qualified source, not to a copied CRM status dropdown.

Open questions not answered by these pages include the source's precise renewed-window rule, any genuinely required fresh evidence, collision handling when an eligible referral has changed, which current fields are readable after continuation, and organization permission defaults. The main review should state which are already owner-decided and which require later explicit resolution. Do not ask the founder to choose technical implementation machinery merely because the producer is not yet qualified.

# D35 adversarial review: deliberate referral continuation

**October 18, 2026 UTC.** The founder selected missionary continuation when the
organization permits it; independently authorized staff may still act. This
review proposes exact owner boundaries for that answer. It is research, not a
deployed permission grant, formal source specification or implementation proof.
The proposed single organization-wide missionary setting starts Off for a new or
unconfigured organization. No per-ministry settings hierarchy is implied; current
P12 scopes still govern each actor and target. The new-window policy remains
unsettled and is represented only by explicit source-qualified synthetic inputs.

| A03 | On→Off→On or a background retry silently revives the previously unaccepted command. | A changed reviewed policy basis requires a fresh deliberate review/intent. Re-enabling does not queue or upgrade the old command. This does not cancel previously accepted work. |

| A08 | A response is lost, so retry repeats the continuation or an Off check falsely reports that the accepted action never happened. | Recover the original accepted effect for the same intent and unchanged payload under current safe response authority. New-admission policy cannot roll back accepted source history. |
| A09 | An accepted command is retried after the renewed window expires and opens a third cycle. | Recovery returns evidence of the original accepted cycle, never a new transition. | A10 | Missionary and staff both see Expired and each append a new active cycle. | Their overlapping commands serialize against the same reviewed source/cycle. Exactly one continuation is accepted; the losing stale command has no effect and must not claim success. Prove both possible orderings. |
| A11 | Reusing an intent key with changed source/window terms changes the accepted work. | Same-intent recovery requires the same bound payload. A conflicting payload cannot amend or repeat the original effect. This is a semantic requirement, not a new generic command journal or provider ledger. |

Acceptance creates the lawful active source state; subsequent reads still use their own current rules. |

A conflict introduced after review invalidates that basis. |

## Orders that must remain distinguishable

1. **Off first:** review On → Off commits → continuation reaches acceptance →
   definite stale/no-effect outcome. A later On does not automatically submit it.
2. **Acceptance first:** continuation commits → response is lost → Off or action
   revocation occurs → same accepted intent recovers its original receipt only if
   current response authority permits. The source remains accepted.
3. **No source acceptance:** transport fails before the source receives a request
   → client outcome is unknown → unchanged same-intent retry may resolve once if
   its original reviewed basis is still current. Unknown transport is not an
   explicit rejection, and an explicit rejection is not queued work.
4. **Later expiry:** cycle 2 was accepted → cycle 2 expires → old cycle-2 intent is
   retried → only historical acceptance is recovered. A separately reviewed new
   intent may qualify cycle 3; the old one cannot.
5. **Two actors:** both review cycle 1 → either staff or missionary accepts first
   → the other encounters the changed source/cycle and has no effect. A generic
   success response would conceal which action actually occurred.
6. **Correction before acceptance:** current source privacy, identity or window
   changes after review → stale source basis is rejected. Reauthorization must
   occur after any wait, not only when the action first appears.
7. **Window or conflict changes:** review an absent/present window-policy basis or
   no incompatible active occurrence → that qualified basis changes → the old
   intent cannot accept against newly supplied facts. Even unchanged window
   evidence must still provide a future end at acceptance, not only at review.

No database lock shape, receipt table, extra provider ledger, approval inbox,
automatic task or referrer confirmation step is selected here. P9's existing
identity/lifecycle/audit owner must demonstrate the actual command and recovery
seam before activation. The `crm_command_logs` asynchronous provider-intent seam
is not repurposed into a generic continuation journal by this review.

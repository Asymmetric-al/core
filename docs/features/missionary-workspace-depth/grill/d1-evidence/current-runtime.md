# D1 restricted start — current runtime and data-boundary evidence

Research only, 2026-10-16. Source baseline: `9cada8f3d8ab59db391d3fd20df77fcadeb09813`. This is an adversarial static review for the user's restricted-start decision, not an implementation, a live security test, a PRD, or a claim of deployed behavior. No live data, credentials, external writes, or supporter communications were used. Paths and lines below are repository-relative. Earlier surface tracing is retained in `../phase28-workspace-evidence.md`.

## Decision and authority

The user chose ordinary early visibility limited to the missionary inside the organization's native CRM. This is not a second personal CRM, absolute secrecy from separately authorized organizational functions, or a way to hide facts the organization already knows. Existing access to a Party does not itself grant access to the newly authored context. Creating a tentative prospect does not mean gift, subscription, managed development admission, or coaching enrollment. Hidden-existing and absent must have the same bounded defer/deny result when the requester lacks the minimum authority needed to reuse a Party. See `../phase28-session.md:125` and `:146`.

Accepted intent is stronger than today's code. P27's coordinated P9/P3/P12/P28 amendment prohibits general Party notes/private activity/scores in missionary projections and allows only newly authored qualified sharing-eligible interaction context for the exact partnership/current audience/fields/purpose/history (`docs/prds/sitestacker-parity/phase-27-donor-development/owner-reconciliation.md:11`). Every read, derivative, and recovered result must use current audience; linking/assignment does not confer history (`:15`). Participation is voluntary, separate from managed admission/coaching (`:17`). These are planning contracts with real RLS, concurrency, replay, mixed-version migration and user evidence explicitly still unqualified (`:61`). P3/4 identity and CRM authority do not make the current `donors` table a complete Party/relationship implementation. Exact upstream identity ownership remains as recorded by the sibling relationship-finance review; this note does not re-decide it.

Read instructions: root and scoped `AGENTS.md` for missionary, API, database, auth and Supabase; document-authority/data-access guidance; Supabase skill. The findings below distinguish durable intent, useful existing mechanisms, temporary compatibility, and actual conflicts. They do not treat every missing future feature as a present vulnerability.

## Migration precedence and effective permissions expected from committed SQL

This is a source-order reconstruction, **not** a `pg_catalog` result. It excludes `rollback_*.sql` as forward migration authority. Migration application history, environment-level grants/default privileges, publication membership, schema drift and production role claims were not queried.

1. Initial `donors` has nullable tenant, separate donor profile and primary missionary profile FKs, free text `notes`, `{}` giving preferences (`20250101000000_init_schema.sql:62`). `donor_activities` has a donor FK but no tenant/author/audience/source (`:222`). `missionary_tasks` has separate profile-owner and donor FKs but no tenant or constraint that donor belongs to owner/tenant (`:287`). Later foundation adds contact-suppression defaults and financial counters (`20260214090000_foundation_1_schema.sql:375`) but no prospective-context audience.
2. Demo-readonly migration enables RLS, drops existing policies for its table list, adds `public read TO anon USING true`, revokes anon/authenticated grants, then grants SELECT (`20260216153000_demo_readonly_rls.sql:14`). This is superseded for donor/task tables below; citing this migration alone as current public access would be wrong.
3. Authz membership foundation defines active tenant memberships and `SECURITY DEFINER` membership helpers (`20260226113000_authz_memberships_foundation.sql:45`, `:158`, `:181`). Its later platform-policy section concerns notification queue/PDF/audit tables, not a new donor write grant (`:309`).
4. Canonical collection migration drops the named demo public-read policy for donors/activities/tasks, keeps RLS enabled (`20260625002117_canonical_tanstack_db_realtime_rls.sql:21`), and grants authenticated SELECT on donors, donations, activities and pledges (`:160`). Donor SELECT allows superadmin, **any active staff membership for the donor tenant**, or donor's linked authenticated profile (`:165`). Activity SELECT allows tenant staff or the donor's linked profile (`:211`). It explicitly revokes all anon/authenticated privileges on missionary_tasks (`:261`). No later forward donor INSERT/UPDATE grant or task grant was found in the searched migration corpus. No public-schema blanket `GRANT ON ALL TABLES` / `ALTER DEFAULT PRIVILEGES` override was found; CMS default privileges concern a separate schema.
5. Donor matching migration adds unique `(tenant_id,id)` and nonunique `(tenant_id,lower(email))` indexes, composite tenant/donor FKs on match candidates/redirects/audit, and server-only tables (`20260704140000_donor_matching_merge_candidates.sql:13`, `:52`, `:69`, `:103`, `:120`, `:161`, `:178`). These are useful safeguards, not uniqueness by person/email, a complete Party model, or authority to reveal match candidates.
6. `current_user_memberships` is a narrow, fully qualified `SECURITY DEFINER` function with empty search path, uid/active/tenant predicates, PUBLIC execution revoked and authenticated execution granted (`20260802041500_current_user_memberships_rpc.sql:22`). `authz` is intentionally not an exposed Data API schema. This is a positive mechanism to retain.
7. `crm_notes` enables and forces RLS; revokes PUBLIC/anon; grants authenticated SELECT/INSERT. 8. `crm_command_logs` permits authenticated SELECT/INSERT. SELECT admits superadmin or tenant staff. INSERT checks current user against actor_user_id and tenant staff, but not actor_profile_id, action/resource provenance or actual command completion (`20260507234343_crm_command_logs.sql:31`). ## Material findings and candidate safeguards

Severity below is impact if the stated condition holds. “Current source” means the behavior is visible in present code/SQL, not that it was exploited or observed in production. “D1 adoption hazard” is a conflict if existing paths are reused for the chosen restricted-start design.

### R1 — Restricted note content is copied to a broader staff-readable audit table

**High; current source; high conditional confidence if these migrations and the note writer are deployed.** The note source restricts content to admin/superadmin (`crm_notes.sql:45`, `packages/api/src/admin/crm/notes/service.ts:88`). After inserting, the service sends full `body`, `title`, linked ID/type and visibility to `logCrmCommand` (`notes/service.ts:256`). Its redactor removes keys matching authorization/credential/password/secret/token/api-key; `body` and `title` survive (`packages/api/src/crm/commands/log.ts:46`, `:83`). The audit table has authenticated SELECT and any tenant staff SELECT policy (`20260507234343_crm_command_logs.sql:33`). Thus a staff caller denied the restricted note can, under the committed policy, read its copied contents through the table API. No separate UI is needed for this capability. No later relevant policy replacement was found.

**Candidate safeguard:** “Audit, retry records, summaries and operational logs must not broaden the source context's current audience. Record minimal command metadata; retain any necessary protected payload in a source-authorized store.” Address historical copied payloads as well as future writes without silently destroying audit obligations. Qualification: real staff/admin/missionary/anon sessions; insert a synthetic restricted sentinel; deny it from notes and log/diagnostic/export/recovery paths to staff; retain authorized audit metadata. This is a concrete existing discrepancy deserving separate remediation planning, not authority here to implement a fix.

### R2 — Native donor storage and current staff projections do not implement restricted early context

**High; D1 adoption hazard; near-certain if context is put into current donor.notes/activity without changing consumers.** Donor RLS explicitly permits any tenant staff; API list/detail bypass RLS and scope only tenant. General activities are loaded wholesale by donor link in both staff and missionary paths. Using `donors.missionary_id` as “private owner” would not change any of that. Giving preferences' anonymous flag is about donor disclosure to a recipient; it is not a grant for missionary-authored relationship context. The donor profile itself may also be readable by the authenticated donor under RLS, which makes using it as a missionary-private note envelope especially unsuitable.

**Candidate safeguard:** “An early-context record has source-owned tenant, author/relationship context and audience; Party identity reuse never expands that audience. All privileged projections authorize the context separately from Party visibility. Restricted context cannot enter general notes, general activity, donor-visible fields, scores, sharing-eligible context, or aggregate derivatives by relabeling.” The physical source/table choice remains upstream ownership work, not a settled schema proposal. Qualification: missionary A and B, staff with pre-existing Party access, donor linked to that Party, staff with separately authorized exceptional access, and unrelated tenant; cover list, detail, search snippets/counts/sorts, activity, task linkage, CSV, API and direct Data API.

### R3 — Browser note/log INSERT can bypass trustworthy authorship and audit provenance

**Medium; current source; high conditional confidence under committed grants.** `crm_notes` accepts a standard note from any tenant staff using browser Data API. Its check does not bind `author_profile_id`/`author_name`; linked ID/type/label are unconstrained text with no qualified target lookup (`20260818000000_crm_notes.sql:5`, `:63`). Server code stamps the actor (`notes/service.ts:207`) but direct INSERT need not use that code or create the associated audit log. Command-log direct INSERT similarly lets staff self-assert success/action/resource, though actor_user_id must be current uid. This does not itself grant access to a hidden linked record; it corrupts attribution and can create false associations or unaudited workflow history.

**Candidate safeguard:** “Author, tenant, source association and audit provenance are trusted command outputs, not browser-supplied facts. If a direct-write path exists, its database constraints enforce the same contract; otherwise revoke it and retain one server command.” For mutable records, qualify both UPDATE USING and WITH CHECK; an old-row predicate alone cannot prohibit changing tenant/audience/owner. Qualification: forged author, cross-tenant/link-type mismatch, unresolvable hidden link, direct INSERT and audit spoof; assert rejection or trusted attribution, no hidden-record explanation, and atomic mutation/audit outcome.

### R4 — Existing UI writers are incompatible with current grants; reopening grants would reactivate unqualified paths

**Medium current reliability; High D1 migration hazard if permissions are widened to make the dialogs work.** TaskDialog and AddPartner write directly using public-key browser Supabase. Latest task privileges are all revoked; donor privileges are SELECT only. Therefore their writes should fail in the reconstructed schema. TaskDialog updates by id only, and donor picker uses raw identity rather than the portal redactor. AddPartner omits tenant and starts an Active/Monthly donor with score70. This is an implementation/boundary conflict, not evidence that authenticated users can currently write arbitrary tasks or donors.

**Candidate safeguard:** “Every supported client version uses an authorized command for creating/changing prospective context and its tasks. Stale clients fail safely without creating partial records. A grant change cannot silently re-enable legacy direct writers.” Qualification includes active UI, older shipped JS, raw table writes, existing API hooks, profile-only missionary, staff+missionary, anonymous donors and no-email prospects. UX must explain failures and preserve a safe draft without claiming success; never fabricate Monthly/Active/score merely to satisfy old form fields.

### R5 — Primary donor linkage, general activity and tasks lack the source/tenant constraints D1 needs

**High D1 integrity/visibility hazard; current bounded API writes contain useful checks.** A single `donors.missionary_id` refers to a profile, whereas donations refer to a missionary record; these IDs are not interchangeable (`init_schema.sql:66`; `packages/api/src/missionary-portal/service.ts:159`). Activity has no tenant/author/relationship audience, tasks have no tenant or composite owner/donor guarantee. Current API donor checks protect ordinary task creation, but read/write methods rely on that past check and independent FKs; activity access-check then INSERT is not one transaction with current audience verification (`donor.ts:129`). General donor edits replace identity/notes/status/frequency without a source version (`:174`). Future sharing, transfer, merge, departure or two simultaneous editors would introduce authority and lost-update races if this structure were simply extended.

**Candidate safeguard:** “The command and database bind tenant, exact source relationship and permitted target together. Source revisions or equivalent concurrency controls reject conflicting edits. Current authorization is checked at the same commit boundary as the write and again on recovered results.” Tests: two missionaries referencing one Party, same Party in separate purposes, cross-tenant donor-task ID substitution, revocation during save, merge during note/task creation, stale form after correction, double submission and retry after failure. Preserve private context lineage when Party identities merge; do not turn merge or transfer into historical sharing.

### R6 — Generic roles and caches cannot yet guarantee same-user revocation of context access

**High D1 hazard; Medium current revocation ambiguity.** Active memberships are read freshly, but `hasRole` also accepts stale legacy profile roles (`permissions.ts:61`). An account with a retained staff/missionary profile role can pass server role checks after membership deactivation; service-role queries may still return tenant data. This is conditional on a revocation workflow changing memberships but leaving profile role, not evidence such a workflow currently promises complete revocation.

Browser query cache clearing correctly covers signout/user change (`packages/auth/client-session.ts:56`), and ignores stale async auth loads (`:139`). It does not clear on same-user tenant/role/audience changes. Portal query key is constant (`packages/database/hooks/missionary-portal.ts:100`); roster key has missionary profile but no authz/context revision (`missionary-donors.ts:149`). Defaults keep stale data 60s, cache 5m and do not refetch on focus (`providers/query-client.ts:81`). Already-delivered data cannot be made unknown, but new navigation/recovery must not present stale authorization as current access.

**Candidate safeguard:** “Source-specific context grants, not legacy role or assignment alone, authorize subsequent reads and writes. Revocation invalidates in-memory projections, open dialogs, subscriptions and recoveries for the same authenticated user; late responses cannot repopulate revoked data.” Tests include membership-only deactivation, legacy-role fallback, same-user tenant switch, multi-tab revocation, open task picker, stale response after revocation, browser back, cache hydration and command replay. TanStack DB collection teardown beyond QueryClient.clear was not runtime-qualified; no durable query persistence was found in the scoped search, which is not proof all client persistence is absent.

### R7 — Current note create can persist despite an error and duplicate on retry

**Medium; current source; conditional on command-log failure after note INSERT.** Note INSERT completes before the separate log write (`notes/service.ts:224`, `:256`). A log failure is thrown to the caller (`:277`), even though note exists. The route supplies per-request `requestId`, not a stable client retry key (`notes/index.ts:52`; random UUID is generated by `packages/api/src/shared/with-operation.ts:128`); note service uses it as idempotency key (`notes/service.ts:190`). A retry can create a second note. Same-key recovery returns the existing note without new audience filtering (`:192`, `:230`), but current route does not expose a user-selected stable key, so this is **not** established as a current unauthorized replay endpoint.

**Candidate safeguard:** “A saved prospect/context command has one durable outcome for one actor/source/payload-bound retry identity, and data plus required audit commit atomically. Recovered results reauthorize current audience. Unknown outcome UI does not invite blind duplicate creation.” Tests: network loss after commit; audit failure; simultaneous same-key request; same key changed payload/actor; retry after access revoked; UI distinguishes saving, saved, uncertain, retryable conflict and denied without losing safe draft or leaking hidden records.

### R8 — Matching helpers and old donor writers are not a qualified safe prospective identity workflow

**High D1 data-integrity/side-channel hazard if reused without a new authorized boundary.** `resolveDonorMatch` filters candidates to tenant and exact-email attachment is explicitly a giving/guest-checkout rule (`packages/api/src/donate/guest/donor-matching.ts:1`, `:176`). Search found its implementation and unit-test callers, not a wired prospective CRM entry command. Match metadata tables have useful composite FKs and server-only access, but no prospective capability follows from their presence. Current donor creation also exists through donation saga tenant/profile lookup+INSERT (`20260820001000_begin_donation_saga_fee_extras.sql:90`) and older TS helper (`packages/api/src/donate/queries.ts:12`). Neither requires prospective audience. No donor person/email uniqueness invariant was found; the email index is nonunique. The saga lock is by idempotency key, so different keys for an unrepresented profile do not serialize identity creation.

**Candidate safeguard:** “Canonical identity resolution runs within its P3/4 source authority; context creation does not reveal hidden candidate existence, IDs, labels, counts, or collision reasons. Matching cannot grant contact permission or broaden context history. A canonical match and its permitted context creation are race-safe across all active writers.” Qualification: hidden-existing vs absent responses/timing/metadata, shared-email household, no email, corrected email, duplicate matching candidates, concurrent gift/prospect writers, old client without audience fields, redirect cycles and cross-tenant merge rejection. Exact names/emails are signals, not universal identity uniqueness rules. Unresolved source identity/reuse is a bounded defer/deny path, not a second Party store.

### R9 — Existing public storage and disabled realtime settings are not privacy guarantees

**High D1 hazard if attachments/previews use public storage; no current prospective attachment upload was found.** Initial buckets `profiles` and `document-uploads` are public; object SELECT is bucket-wide and authenticated INSERT checks only bucket/authenticated status (`20250101000000_init_schema.sql:461`). Owner UPDATE/DELETE does not make public URLs private. No later change to those bucket policies was found in the searched migrations. Therefore these are unsuitable defaults for restricted notes, voice notes, photos or exports. This is not a claim that current private prospect files are publicly exposed.

Realtime is explicitly disabled for donor/profile/missionary and giving collections (`packages/database/collections/tables/people.ts:10`; `tables/giving.ts:11`). Latest publication migration adds only funds/posts/interactions/locations (`20260625002117_canonical_tanstack_db_realtime_rls.sql:280`); it does not establish a complete runtime publication inventory. **Candidate safeguard:** “Protected content and derivatives use private source-authorized storage and authorized subscription channels, with bounded URLs and reauthorization appropriate to current audience. Do not upload restricted content to public buckets.” Qualification: private object authorization, guessed keys, revoked links, thumbnails, cached URLs, download/export artifacts, source deletion/retention, publication membership and row payloads under real roles. Design attachment support deliberately or leave it absent in the minimal release.

### R10 — Donor-oriented defaults and partial reads can misrepresent tentative prospects

**Medium UX/data integrity; present code with D1 incompatibility.** AddPartner requires email/location and defaults Monthly, Active, score70. Missing giving preferences fail anonymous in the portal, so using that path for a known personal contact can produce an anonymous row or blocked edits, not a clear restricted prospect (`packages/api/src/missionary-portal/redaction.ts:38`; `donor.ts:167`). Snapshot caps donor/gift reads at 250 and tasks100 (`service.ts:194`); roster is paged but activity/pledges capped separately (`donors.ts:450`, `:532`). Local search over loaded roster is not an exhaustive identity search. Dashboard sums loaded recurring gifts and uses `current_funding`/`funding_goal`, not a qualified prospective commitment or Goal Version (`model.ts:357`).

**Candidate safeguard:** “A tentative prospect can be saved with the identity facts actually known and an honest neutral relationship state. Creation does not imply recurring financial support, contact consent, donor score, newsletter inclusion or task obligation. Incomplete/loading/limited results are distinguishable from none, and search cannot be used as an oracle for hidden identity.” Tests: first-time missionary, prayer-only relationship, no email, non-US address, large roster, existing hidden Party, slow/offline save, keyboard/mobile flow, unknown result after submit, and receipt/goal metrics remaining unchanged. Missionary-first vocabulary and visibly separate save/share/send actions are needed; precise sharing UX remains a product question.

## Minimum durable design versus open implementation choices

Required by the user's choice and adopted owners: native identity authority; independently authorized context; no admission/consent/coaching by contact creation; no projection or derivative widening; trustworthy tenant/author/source; current authorization on commit/read/recovery; race-safe identity and context creation; explicit history grants for later collaborators; safe old-writer cutover; understandable save/error/retry behavior.

Useful existing mechanisms to preserve and qualify: verified Supabase user, membership RPC, tenant predicates, deny-by-default recipient redaction, donor UPDATE anonymity predicate, server-only task privileges, service-only donation RPC, composite donor-match tenant FKs, QueryClient signout isolation, stable server pagination, generic command audit structure with protected-content correction.

Temporary/accidental compatibility: profile-role fallback, single primary `donors.missionary_id`, donor status/score defaults as prospective relationship state, direct browser task/partner mutation UI, generic donor notes as relationship history, broad MVP staff grants for every future context, mock settings/notification state. These are not permanent product promises.

Still open: exact source schema and canonical Party reuse command; self-authored private context correction/retention; staff exceptional access and accountable reason; what later “share” authorizes at field/history level; departure/reassignment/merge behavior; draft persistence on shared devices; whether restricted attachments, offline work and exports are supported at launch. This review recommends safeguards but does not silently choose those policies.

## Evidence quality, tests and limits

Inspected source includes missionary portal/service/model/redaction/donor/tasks, active task and AddPartner dialogs and hooks, admin CRM list/detail/notes/report export, auth context/permissions/session cache, browser/admin Supabase clients, collection registry/realtime flags, initial schema through latest relevant donor/authz/notes/log/storage/matching migrations, donation saga donor writer, matching/merge pure helpers, and targeted GraphQL alternate path. Repository searches covered later relevant policies/grants/default privilege overrides, note/log writers, donor-table writers/matching call sites and scoped persistence/storage references. Earlier note records dashboard/profile/settings/communication coverage.

Existing tests inspected or located: `tests/unit/packages/api/crm-notes.test.ts:200` tests note-list restricted filtering and `:275` create rejection; it uses an in-memory client, not real RLS or command-log read authorization. `crm-command-log.test.ts:38` exercises redaction/attribution, not restricted body leakage. `tests/unit/auth/client-session.test.ts` covers session isolation but does not qualify context grant revocation. `tests/unit/packages/lib/use-tasks-api-boundary.test.ts` covers the hook, not TaskDialog. `packages/api/tests/unit/donor-matching.test.ts:46` exercises pure matching, not caller authorization or concurrency. Located migration tests are source assertions, not proof of deployed role behavior.

No tests or exploitation were run in this research step. No local DB reset/migration, authenticated Data API/RPC call, role impersonation, browser journey, timing test, external index/cache/storage inspection, load test or live migration audit occurred. Not exhaustively inspected: every admin generic CRUD/import command, every Eve/agent/tool/export connector, GraphQL schema validity and deployment exposure, all workers/notification consumers, all database triggers/functions, external search indexes, email providers, CDN/service-worker behavior, support/care sources, database backup/retention policy, runtime publication membership, actual default privileges, schema drift, token refresh behavior, browser collection disposal, stale deployed clients and real user/device accessibility. These are explicit qualification work, not assumed safe or unsafe.

The source evidence supports the hazards above. It does **not** prove a deployed vulnerability, complete repository-wide security coverage, a complete future privacy design, or acceptance of a particular storage schema. Initial release qualification must demonstrate the full user journey and actual grants/RLS/privileged commands together; mocked route tests or a checked-in policy alone are insufficient.

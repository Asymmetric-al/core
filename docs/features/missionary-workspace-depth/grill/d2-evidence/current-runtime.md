## Decision being evaluated

The latest user answers make explicit sharing place the contact in the ordinary CRM for **all staff in the same organization**, with an optional notification that the contact is available for follow-up. The founder's subsequent explicit async answer settles recipient selection: **choose the staff to notify; no broadcast**. This removes a need for a per-collaborator contact ACL in this flow. The selected notification recipients do not limit the ordinary staff visibility of the shared contact. Eligibility, channel and the exact qualified producer remain implementation/owner requirements, not a new question about whether selection or broadcast is intended. Do not substitute finance approvers, platform owners or an assigned follow-up task for the chosen staff.

D1 still controls preparation before sharing and protected private history. D2 makes the shared contact generally available; it does not imply that private early notes, another person's protected facts, care history, contact consent, financial facts, or managed development admission become ordinary contact fields. Exactly which information the share command exposes must follow the source/owner contract. This note does not approve a schema, reversible-unshare promise, future edit authority, new intake owner or new contact lifecycle. Staff selection is settled; its presentation is not frozen. A direct optional staff field may replace a separate checkbox and picker without changing the decision.

## Notification implementations actually present

### General-looking notification queue is donor/campaign storage, not a staff notice service

`supabase/migrations/20260214090000_foundation_1_schema.sql:36` creates `notification_queue` with mandatory `recipient_donor_id`, optional campaign/donor/profile references, defaults `campaign_update` and `email`, arbitrary JSON payload, optional dedupe key, text status, attempts/scheduling/processed/error fields. The same migration backfills then enforces non-null donor recipient (`:192`, `:269`). Its dedupe uniqueness is `(tenant,recipient_donor,notification_type,channel,dedupe_key)` only when a dedupe key exists (`:686`). It is not “no recipient means all staff,” and inserting a null donor recipient is not a supported internal broadcast representation.

Permission precedence matters. Demo-readonly first revokes internal-table browser access (`20260216153000_demo_readonly_rls.sql:64`). Later membership foundation explicitly grants authenticated **SELECT/INSERT/UPDATE/DELETE** and adds tenant-staff-or-superadmin policies (`20260226113000_authz_memberships_foundation.sql:313`). INSERT WITH CHECK and UPDATE USING/WITH CHECK test only tenant membership/superadmin, not trusted producer, recipient relation, actor, event authority, allowed payload/channel or delivery-status transition. DELETE also permits tenant staff (`:367`). Initial queue FKs are separate IDs, not composite tenant/recipient FKs. No later queue policy/constraint replacement was found in the forward migration search.

Search for `notification_queue` across packages/apps found no enqueue, worker, route, hook or inbox consumer; references were SQL. Thus this is dormant **in inspected application source**. It is not verified that no deployed external worker exists. Do not activate a worker that trusts these existing rows as an authorized contact-share event: browser staff can currently create/change them under committed grants. A queue with scheduling columns is not evidence of reliable delivery, idempotency, read receipts or safe status authorization.

### Admin bell and missionary preferences are UI demonstrations

Mission Control shell mounts `NotificationDropdown` and a static dot (`apps/admin/app/mc-shell.tsx:384`). These screens cannot truthfully be cited as saved preferences, notification delivery, or a current staff-recipient/channel policy.

### Contribution approval notifications are real, source-specific infrastructure

`packages/api/src/admin/contribution-operations/approval-notifications.ts:38` states the exact contract: correction-request approval task, in-app on by default, email off unless tenant and approver opt in, preferences do not grant approval capability. `planApprovalNotifications` makes records per eligible approver/profile/channel, source request/kind dedupe keys (`:99`). Current recipients are tenant profiles whose legacy role is admin or super_admin (`:213`), filtered for separation-of-duties policy (`:256`). It is not all staff, an assigned CRM owner, or a general follow-up team. Creating a task requires eligible approvers (`:136`); actual workflow creates a queue-only correction review task (`:477`).

Notification rows are upserted under `(tenant,dedupe_key)` and only newly inserted keys are sent (`:279`). SLA updates and that round's notification insertion use a dedicated atomic RPC (`:386`). `contribution_approval_notifications` requires a correction request and restricts kind to approval_requested/reminder/escalation/outcome (`20260611150000_contribution_approval_notifications.sql:27`). Tenant reference guards check recipient/profile links (`:128`). RLS enabled, browser privileges revoked and service-role table/RPC privileges granted (`:537`). These are useful mechanisms, not a valid contact-sharing event type.

Email has separate connected tenant Resend settings and current tenant-profile email resolution (`approval-notification-email.ts:59`, `:190`), sends with a stable provider idempotency key (`:239`) and counts failures instead of failing the durable approval workflow (`:169`, `:255`). It is best-effort, not a guaranteed staff notification delivery promise. The table has no general read/dismiss/status lifecycle, and scoped package/app search found its writes here but no general recipient inbox consumer. Code comments referring to an in-app feed do not establish that UI is implemented. A persisted row is not equivalent to “the staff member saw the contact.”

### Eve operator notifications provide stronger delivery patterns for a different product

Eve channels are email and Discord; envelope sourceKind is engineering_monitor; email recipients are opted-in superadmin profiles (`packages/api/src/eve/notifications/types.ts:7`, `:21`, `:52`). Defaults are disabled/paused, platform-owners or discord:ops-primary, bounded attempts and dedupe windows (`registry.ts:8`). Route GET is admin/superadmin and PATCH superadmin; source identity is stamped from authenticated audit context (`route.ts:57`, `:79`, `:109`). Recipient configuration validates tenant, superadmin role and email (`store.ts:153`, `:208`). These exact rules must not silently become a CRM notification-owner contract.

Producer `enqueueEveEngineeringFindingNotifications` derives a safe envelope, governance policy and eligible destinations, explicitly suppresses no destination, and upserts a deduped durable record (`delivery.ts:145`, `:200`, `:216`). Delivery checks current gate/policy and reloads eligibility before sending email (`:391`, `:427`). Record store carries pending/delivered/retryable/terminal state and recovery; claim/complete RPCs use lease tokens (`store.ts:271`, `:321`, `:343`). SQL limits envelopes to engineering-monitor meaning and rejects donor/payment/raw material (`20260718093000_eve_email_discord_notifications.sql:94`), revokes all public/browser table/RPC access and grants service role (`:151`, `:279`). Actual source callers are Eve monitor and notification sweeps (`packages/eve-runtime/src/monitors/sweep.ts:254`; `src/notifications/sweep.ts:63`), not CRM.

The reusable ideas are source-specific event identity, minimal envelope, dedupe, current-recipient checks, bounded retries, leased delivery, separate outcome and no-destination result. Reusing this product's operator recipients, Discord channel, engineering severity, governance release toggles or event type for a contact is incorrect. This review inspected the cited API/store/SQL and located runtime call sites; it did not inspect or execute complete Eve sweeps or provider delivery.

### Workflow urgency is a status policy, not the optional contact notice

`packages/api/src/workflows/notification-policy.ts:23` classifies workflow failures/dead letters as urgent or visible. The tenant policy route only edits bounded retry/failure overrides (`packages/api/src/admin/workflows/notification-policy.ts:7`). It neither selects a contact-notice recipient nor creates an Information inbox item. “Available for follow-up” must not be mapped to urgent failure or mandatory work simply to reuse a visible surface.

## Minimum reusable design and remaining product choices

For D2, the simplest truthful implementation target is a source-qualified **Share with [organization]** action that exposes the permitted contact to ordinary staff, with a separate optional notice intent/result. The ordinary tenant staff CRM path can be reused after qualification. It is not necessary to build collaborator ACL selection. It is necessary to keep private preparation and shared-contact facts distinct, to resolve identity safely, to authorize the source transition and to make one durable result survive retries.

Optional notice delivery is additional work, not a hidden permission grant. The inspected code offers useful primitives but no existing general contact-sharing producer, staff Information inbox or persisted user preference contract. Recipient selection is settled by the founder: notify chosen staff, no broadcast; no selection means no notice. Eligibility, channel and exact producer must be qualified through the owner contract, without reopening that decision or substituting defaults from finance or Eve. Exact exposed fields, source admission authority, notice availability/read semantics and treatment of later share corrections retain their owner requirements. Missing or ineligible selected recipients cannot silently become the current primary missionary, another default recipient or a queue task.

A minimal release may deliberately support only the qualified in-product Information path if the adopted owner contract provides it. That is a candidate scope decision, not an assertion this path exists today. External email/Discord/SMS setup is not the core blocker for an internal availability notice. Conversely, a reusable email sender does not implement local acceptance, source identity, in-app visibility or current recipient status authorization.

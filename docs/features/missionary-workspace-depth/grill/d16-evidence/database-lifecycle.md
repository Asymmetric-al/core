Immutable goal versions, expected-head checks, exact captured intent, atomic audit and current authority can enforce the tested mechanics. These results do not qualify Core's P12 resolver, goal source, hosted Supabase or any production permission configuration. ## What the fixture represents

The fixture contains two same-numbered but type-distinct subjects, one missionary and one project, plus an other-tenant subject. Composite keys carry exact tenant, Legal Entity, subject kind/id and version. This demonstrates identity mechanics only. **The project fixture does not establish that P28 owns a production project goal.** A real project adapter must use the qualified P13/P28 owner, capability and canonical identity; displaying it in multiple workspaces must not create duplicate goals.

One test slot per subject has a current head and append-only Goal Versions. This is not a proposed production cardinality: recurring and separate special-gift goals, currencies and purposes need their owner-defined identities. A version binds exact amount, currency, monthly-equivalent or finite-period basis, applicable dates and author. A current head advances atomically with one acceptance receipt and audit. No function overwrites the prior version. Triggers reject UPDATE/DELETE on versions, intents, receipts and audit; actor grants also deny direct version writes.

Each **captured test intent** fixes actor, exact subject, expected head, exact effective-authority revision and proposed meaning. Its ID is the semantic operation identity; a request key identifies an attempt. Two attempts with different request keys for that same original intent create one version/receipt/audit. A different intentional edit is not deduplicated merely because the amount looks similar. Reusing a request key for a different intent conflicts. No generic request framework or automatic server-preview workflow is proposed by this test table.

Save obtains the current effective edit gate under a shared row lock, then the goal head under an update lock. It verifies exact intent/current authority before an effect. A current accepted receipt may be returned without repeating the effect, but it says whether that accepted version is now superseded. Permission-off blocks the tested receipt path as well as a new Save; a prior success is not authority to write now. The actual product may qualify a separate bounded receipt-read permission; this fixture does not decide that UX or reconstruct real P12 access from its boolean.

Money is stored as BIGINT minor units with explicit USD/JPY fixture lanes. Unconstrained NUMERIC is used only in captured test input so fractional, nonfinite and overflow values can be rejected before casting. Positive targets are a **candidate new-input rule**; null/zero rejection does not establish that zero means disabled, required, cleared or intentionally unset. An initially absent goal head returns `unset`, not zero. No progress ratio is implemented. Currency changes in the fixture are explicit full new-version intents; this proves there is no implicit FX calculation, not that a casual amount edit may reassign an existing production goal's currency or purpose.

The two ordinary source roles, `missionary_a` and `staff_a`, have nonsuperuser/non-BYPASSRLS logins and only bounded function execution. `policy_manager` can mutate the synthetic effective authority. `command_executor` is NOLOGIN, nonsuperuser/non-BYPASSRLS, does not own tables and has no public-pin or finance privileges. All ten tables use enabled and forced coarse tenant RLS. Default PUBLIC EXECUTE is revoked; function search paths and actual ACLs are retained. Fixed login-to-tenant mapping is trusted harness identity, not Supabase Auth/JWT verification or the real four-context P12 model.

The public binding is a composite FK to Goal Version 1; the finance sentinel is separate and inaccessible to the executor. These are intentionally small negative-effect witnesses, not Core P22/P21/P13/P16 integrations. No notifications, page releases, approved-plan adoption, goal ending, backdating, proration or payment operation exists in this fixture.

## Proposed technical clauses and remaining proof

**DB16-01 — Exact owner and identity.** Route goal create/change/read through the actual typed source owner and exact tenant/subject/Legal Entity scope where applicable. P28 missionary editing does not silently authorize writes to a P13 campaign/Designation target, P21 Plan or P22 binding. Use one canonical shared-project identity after owner qualification; do not derive ownership from workspace membership or copy the goal into each missionary row.

**DB16-02 — Current editing authority, separate from use and visibility.** Resolve the existing P12 capability/floor decision for the exact source action and fields at apply. Organization-controlled editing remains optional permission, not an obligation to edit or a new Required/Optional/Not-used policy. Preserve otherwise permitted goal viewing when only editing is off. Keep fine permission decisions in the owner/P12 boundary and RLS coarse; no role-string checks, client-only toggle or second permission engine.

**DB16-03 — Immutable version and atomic acceptance.** Append the qualified prospective Goal Version, advance one expected current head, and durably record acceptance/audit as one source transaction. Preserve original attribution and same-scope references. Concurrent editors cannot silently overwrite each other; failure must not leave a new head without its version or audit. Goal-use/end and historical correction semantics require their own owner-qualified intent, not zero or destructive deletion.

**DB16-04 — Semantic retries and current meaning.** Bind retries to the exact original action, scope, actor and payload, independently of transport attempt keys. Reuse of an accepted semantic operation creates no duplicate version or audit. An old acceptance receipt is historical evidence, not current authority or current-head truth. Policy reduction and source-head changes are rechecked/fenced; restore does not replay stale queued work. The final implementation must qualify global request-key scope, receipt disclosure, rejected/no-op retention and all concurrent paths; this fixture only covers its exact bounded paths.

**DB16-05 — Exact monetary and temporal contract.** Preserve validated finite minor-unit input, bounded exact storage/serialization, ISO currency, goal kind, measurement basis, effective boundary and applicable period. Unset differs from zero; unsupported or zero denominators have no ratio. No implied FX, proration, current-goal rebasing of historical periods or comparison against incompatible received/expected/monthly-equivalent measures. The source owner defines positive-input, clearing/ending and currency-change rules explicitly.

**DB16-06 — Independent source effects.** A goal edit does not edit money, commitments, approved Plans or a released public denominator. Public adoption follows P22's prospective release; approved-plan adoption is explicit with exact provenance. Compatible source numerator corrections remain live under their own contract. Qualify actual API/RPC, database grants, audit, caches, jobs and public/finance readers; synthetic sentinel stability is necessary mechanism evidence, not integration qualification.

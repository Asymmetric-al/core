**Selected intent:** direct correction of eligible ordinary shared contact details, controlled by tenant settings. This does not by itself define the initial tenant setting, exact settings-manager capability, every editable field, represented-person authority, a generic approval queue or a new permission system. Current actor/tenant/source/field/purpose authority remains required. Enabling the setting cannot admit protected identity, Auth, consent, financial, private-note or unrelated CRM fields; disabling it cannot invalidate independently authorized donor/staff corrections or rewrite accepted history.

## Concurrency, history, result recovery and cache

- **No source compare-and-swap:** `donor.ts:182` updates by identity/association/anonymity only. A stale snapshot can win over a newer correction; a retry after a lost response can overwrite intervening work. `updated_at` is assigned server time, not compared to an expected revision. No operation key, payload digest, source receipt or audit call exists in this handler/route helper. Targeted donor-trigger searches did not locate a compensating correction-audit trigger; this is not an exhaustive deployed-trigger assertion.
- **Generic success loses authoritative state:** server returns `{ok:true}` (`donor.ts:225`); `donor-mutation-client.ts:40` discards response body and flattens non-2xx/network errors (`:36`). Dialog toasts success, closes and calls refresh (`edit-donor-dialog.tsx:337`). Refresh starts unawaited donor/activity/pledge invalidation (`use-donors-page-view.tsx:150`). An accepted save, stale display and unknown transport outcome therefore have no source-qualified distinction in this adapter.
- **Draft recovery is incomplete:** while open, changed initial values reset the form (`edit-donor-dialog.tsx:77`), so a query refresh can replace an unsaved draft. Cancel/close resets immediately (`:83`); Cancel remains enabled while Save is pending (`:165` versus `:179`). No cancellation/idempotency receipt is wired, so dismissing the dialog does not prove that a sent request was cancelled. No browser experiment was run; the state/reset and request behavior are source facts.
- **Cached visibility is not current write eligibility:** roster query key includes profile ID but no tenant/policy generation and is stale for 30 seconds (`missionary-donors.ts:152`). Client cache clears on signout/user-ID change (`packages/auth/client-session.ts:64`), not same-user policy changes. Auth server resolves current user/profile/active tenant memberships each call (`packages/auth/context.ts:249`, `:287`, `:305`), but D5 policy is absent. A new UI toggle must never be the only write gate; a save racing policy disablement needs an explicit source acceptance order, not an unaudited earlier check.
- **Other existing writers/readers matter:** donor self-service writes name/phone to both profile and donor in separate operations (`packages/api/src/donor-portal/index.ts:90`, `:130`, `:146`). Missionary editing writes donor only. Donor portal display prefers donor name but profile phone/email (`donor-portal/model.ts:444`). Thus legitimate writers may disagree and a Clear can fall through to an older value. Do not add automatic mirroring to “fix” D5; qualify the owner and accepted correction/clear semantics across reached readers. The generic profile route separately writes profile before checking missionary access for mirrored phone (`packages/api/src/profile/index.ts:105`, `:135`, `:147`), an existing owner-convergence concern rather than permission for D5 to edit Auth/self-profile facts.

## Material hazards and candidate safeguards

1. **RT5-01 — High authorization; near-certain if only UI/settings storage is added.** There is no enforced tenant contact-edit policy in the current correction command, and static `editable:true` is expressly not authority. **Clause:** resolve trusted current tenant, active actor/context, actual target source and exact selected field/purpose permission plus the tenant control at acceptance. A disabled, missing or unavailable qualification cannot fall back to old role-only editing. The policy is an additional bounded condition, never a bypass of classification, source grants or anonymity.
2. **RT5-02 — High tenant/governance; conditional if the old settings route or coarse admin map is copied.** Hardcoded tenant and all-staff-as-admin semantics can target the wrong policy or widen who can change it; a zero-row update can look saved. **Clause:** only the qualified tenant-policy manager may change the exact setting in their authorized tenant; persist source revision and minimized attributable audit together, prove affected state, and reconcile conflicting/lost-response settings saves. A single clear setting can remain simple without a new per-user/per-contact policy builder. Exact default/manager authority must come from the owner/ratified review, not this legacy map.
3. **RT5-03 — High integrity; concrete source path, conditional on affected values.** Whole-form saves overwrite unrelated/newer values, default hidden frequency and force US country. **Clause:** submit/authorize explicit selected corrections; omission means unchanged and Clear is explicit/source-valid. Validate all selected fields before one atomic effect; reject unqualified extra fields instead of silently applying or stripping a denied member of a supposed successful save. Preserve untouched data and allowed international input; a no-op must not create a correction/interaction fact or surprise normalization.
4. **RT5-04 — High integrity/recovery; conditional on overlapping edits or lost response.** Missing expected revision and replay identity permit stale overwrite or an old retry to undo a newer correction. **Clause:** bind the correction intent to exact source identity/version and selected payload, use the source's concurrency and recoverable same-operation result, and distinguish stale conflict from transport uncertainty. Recovered results obey current read authority; retry does not regain a revoked right or reapply a consumed old intent. Policy edits and correction acceptance have a defined serialized order.
5. **RT5-05 — High privacy/source coupling; plausible if current “Internal Notes”/profile behavior is reused.** Ordinary contact correction is broader than no-op UI wiring but narrower than this editor. **Clause:** keep private assertions/history, shared contact facts, legal/verified identity, Auth/account data, consent/suppression, finances and relationship lifecycle separate. D5 neither shares preparation nor grants read access to values needed only by an unqualified update. No inferred household representation or automatic sync to another person's/profile/public/receipt fields. Reuse P9/P4/P12 correction owners and retained provenance.
6. **RT5-06 — Medium/high usability; conditional on refresh, closing or settings drift during editing.** Existing reset/close/toast paths can lose drafts or show a generic failure despite a committed effect. **Clause:** preserve valid unsaved edits through ordinary refresh, clearly explain shared impact and current edit availability, show precise field errors/conflicts, and recover the same submitted operation after interruption. A disabled setting should explain why correction is unavailable without exposing hidden policy/record details or silently creating staff work. Saved and refresh-failed are distinct; closing is not cancellation. Use the existing shared Base UI form/dialog/status patterns without copying the full field set or a routine approval ceremony.
7. **RT5-07 — High migration/debt; conditional on mixed writers/readers.** A new safe command alone leaves this old broad PATCH and self-service mirrors/fallbacks operating on the same facts. **Clause:** inventory and converge reached missionary, donor/staff, REST/GraphQL/RPC, imports and browser writers under the source owner before activating D5; fence incompatible legacy payloads. Preserve read-only browser grants, valid distinct source values and later restrictions. Do not backfill new edit permission from `missionary_id`, shared visibility, old field ceilings or historical write success.

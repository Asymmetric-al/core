## Authority model and interpretation limits

`effective_authority` represents the **result of current effective authorization for this actor, exact active hat, tenant and contact-field scope**. It is not a new permission engine, a tenant-wide Boolean override, individual grants or a per-grant DENY rule. P12's additive grants must be resolved by their owner first; the fixture removes a field only as an input assumption that the actor's resulting effective authority no longer includes it. `can_read` is a separate synthetic assumption. Revoking phone-edit authority in these cases leaves current contact-read authority intact.

Its revision advances for the modeled effective field/hat authority transition. This does **not** imply that every unrelated tenant-role change must invalidate an edit or force a user to review unchanged rights. The A→B→A case demonstrates how stale evidence can be detected. A real source may instead freshly requalify the exact original intent and current context under its qualified contract. No mandatory new review flow is chosen by this probe.

The correction function locks that effective-authority row before the source row, checks every input key against both a static command allowlist and the current allowed field set, validates the exact active hat and source revision, then writes source, required audit and retry receipt in one transaction. All cooperating policy changes use the same authority row. Audit stores actor, hat, source identity, version and changed field names rather than copied values. The receipt binds normalized JSONB input with a SHA-256 digest plus original source/authority evidence; a digest is **not anonymization, encryption or a retention policy**.

Historical receipt recovery is evaluated under current authority before returning any accepted result. The fixture's correction-command retry requires current authority for the original selected fields. It does not decide whether another source-qualified receipt/history read route could disclose a bounded result under different current read authority. The returned historical revision is not presented as the current contact version. There is no notification, task, consent, money, identity, sharing or other downstream consequence in this fixture.

All correction/denial/counterexample actions and concurrent mutations use actual nonsuperuser login roles (`missionary`, `staff`, `policy_manager`). The function owner is NOLOGIN/NOSUPERUSER/NOBYPASSRLS and does not own its tables; RLS applies. PUBLIC function execution is revoked. [roles.json](roles.json) captures the attributes. PostgreSQL `session_user` supplies fixture identity; this does not qualify JWT claims or production hat selection. Superuser initializes the fixture and observes internal results; the final audit/receipt aggregate is explicitly an administrative assertion. The fixture-only audit fault trigger is not an application feature.

## Primary technical evidence

[sources.json](sources.json) records fresh PostgreSQL 17 primary URLs, fetched-body/text hashes, inspected sections and their implications:

- [GRANT](https://www.postgresql.org/docs/17/sql-grant.html), Description/Notes: a column privilege can come from either a column grant or a table grant; a column revoke leaves the table grant unaffected. Privileges also accumulate through memberships and PUBLIC. Hiding a field in UI cannot repair an available broader database write path.
- [Row Security Policies §5.9](https://www.postgresql.org/docs/17/ddl-rowsecurity.html): RLS controls eligible rows; mutable authorization subqueries can race. The documented lock discussion supports testing a common cooperating authority fence. RLS alone is not a selected-field patch contract.
- [Read Committed §13.2.1](https://www.postgresql.org/docs/17/transaction-iso.html): conflicting row locks wait and re-evaluate updated rows. This underlies both policy/save ordering and detection of a newer contact revision.
- [Transactions §3.4](https://www.postgresql.org/docs/17/tutorial-transactions.html): transactional steps commit together or have no effect after failure. The test checks committed results through fresh SQL sessions; it does not simulate a storage crash or qualify hosted recovery.

Not qualified: the current Core full-form writer, actual P12 grant composition or active-hat producer, all alternate write paths, Supabase RPC/PostgREST/service roles, real tenant settings, hostile raw JSON parsing, all data validation, cross-record same-key races, locked-row throughput, browser cache/optimistic UI, accessible/mobile editing, lost network responses, real audit/receipt retention, or contact-purpose consequences. Phone correction does not establish an email-proof reset or a postal stop; any such effects require their own source-specific rules. A bypass writer or a policy-change path that ignores the common fence invalidates this fixture's synchronization assumption.

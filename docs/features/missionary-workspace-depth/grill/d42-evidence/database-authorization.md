# D42 evidence — database, authorization and concurrent intent

October 18, 2026. Fresh source inspection at Core `9cada8f3d8ab59db391d3fd20df77fcadeb09813` plus the research working tree. This is a bounded design/source audit for Q42 B, not a runtime security assessment, schema migration, live configuration inspection or proof of an exploitable defect. No earlier program, migration or test suite was executed. The Supabase and Supabase Postgres best-practices skills were applied, subordinate to Core governance and current primary documentation.

## Conclusion

**Accept B with required amendments.** Reusing qualified current same-address proof can remove a redundant mailbox step without removing the deliberate newsletter-specific instruction. A signed-in badge, a profile address, an arbitrary `confirmed_at` timestamp, an absent suppression row or membership in the reader's home organization is not this proof. Core needs a narrow public-reader admission command using its existing Auth, native consent/source and communication owners; it must not turn its staff-context resolver or legacy suppression table into a newsletter authority.

The original D6 C05 all-mailbox-confirmation recommendation is expressly superseded for this qualified branch only. Pending-after-Page-Off policy and finite proof/retention schedules remain separately unresolved, not settled by B.

## Current primary evidence and a skill correction

- [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html) describes old-row `USING`, new-row `WITH CHECK`, policy composition and `ON CONFLICT` behavior. When `WITH CHECK` is omitted for an applicable update/all policy, `USING` supplies the check. Missing literal syntax alone is therefore **not** an authorization vulnerability. Review effective predicates, grants, command type and permitted state transformations. Referential integrity checks can also reveal existence, so public APIs must normalize constraint errors rather than expose raw uniqueness/FK failures.
- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) currently confirms that inheritance rule, explains grants versus policies, and recommends proving allowed writes with returned values. A denied zero-row update must be paired with proof the protected row remained unchanged. This corrects the loaded skill's unconditional statement that omitted `WITH CHECK` permits reassignment. Prefer explicit clauses for maintainability; evaluate semantics rather than syntax.
- [Supabase getUser](https://supabase.com/docs/reference/javascript/auth-getuser) obtains authentic user details from Auth. It establishes a suitable existing authority seam, not proof that profile email, browser state or every historical confirmation method satisfied D42's assurance requirement.
- [Supabase sessions](https://supabase.com/docs/guides/auth/sessions) explains that an access token can survive sign-out until expiry; stricter session validity can be checked against the Auth session identity. Do not claim JWT signature verification alone proves non-revocation. A current-address branch must use the Auth owner's qualified current-session policy and must not create a new product-wide session mechanism just for newsletters.
- [Supabase signup](https://supabase.com/docs/reference/python/auth-signup) documents that disabling email confirmation permits a returned signed-in session without that mailbox step. [Admin user creation](https://supabase.com/docs/reference/kotlin/auth-admin-createuser) also supports auto-confirmation. These are provider-level assurance facts, not recommendations to replace Core's JavaScript client.
- The [current changelog index](https://supabase.com/changelog.md) was fetched directly after the web renderer failed. Relevant breaking-change notices were checked: [HTTP TLS cipher removal](https://supabase.com/changelog/cbc-tls-ciphers-deprecated) and [Postgres minor upgrade](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes). Neither changes the newsletter rule. Deployment owners must qualify actual runtime compatibility; this audit does not infer Core uses affected old ciphers or database extensions, nor prescribe an unrelated upgrade.

## Minimal data invariants, without freezing a schema

The source owner must choose the concrete schema once, not add a shadow table merely because this review needs a UI. Whatever the implementation:

1. Non-null trusted Tenant, exact newsletter-purpose and source identity; tenant-aware referenced relationships prevent same-ID/different-tenant bindings. Purpose is immutable for an accepted operation. Site/display name changes are not new consent.
2. At most one current active membership for the same tenant, exact newsletter purpose and canonical destination identity. Distinct purposes/tenants stay independent. A global email/person unique key is forbidden. An Auth user ID is not sufficient: guests need no Auth record, and multiple Auth users may represent the same mailbox.
3. Admission evidence binds the exact destination/address revision, verification method/provenance, current source and disclosure revision, deliberate actor-or-guest instruction and server acceptance time. Optional actor IDs and expired proof payloads need explicit null/deletion semantics; an absent ID must not erase evidence or claim a named actor.
4. Current consent is authoritative native source state; provider lists, cached UI and delivery logs are consumers/evidence. Separate current consent, delivery eligibility and observed delivery; no single green “verified” Boolean may stand for all three.
5. Legal state combinations are constrained: no active membership without accepted purpose intent and qualified proof; no pending proof whose accepted old generation can bypass a newer withdrawal; no duplicate accepted business effect under distinct transport keys. Past withdrawal/admission evidence is immutable; corrections append new meaning rather than rewriting history.
6. The guard/counter/version mechanism is implementation detail, but a tested serialization point is mandatory. A long-lived browser nonce or a freshly invented HTTP idempotency key does not establish a fresh human rejoin. Unsupported or revoked source cannot be resurrected by retry or reenable.
7. Proof secrets are scoped, expiring and safely stored; current signed-in branch needs no new confirmation secret or email merely to duplicate already-qualified evidence. Shared egress owners handle only required communication. Timestamps are server UTC instants; locale is presentation. No money column or financial arithmetic changes.
8. Public self-service is a narrow command, not a generic RLS policy such as `TO authenticated USING (true)`. Existing ordinary row RLS remains active. Privileged API tests are mandatory because the service role can bypass ordinary policies.

**Important feasibility limit:** a `getUser` call followed by an unrelated write does not by itself demonstrate atomic handling of a simultaneous Auth email change or session revocation. The Auth owner must qualify the current proof/guard binding at the admission seam, including its linearization point and deployed Auth behavior. Do not invent a second Auth store or claim a distributed transaction. If current assurance cannot be established, retain the deliberate intent and use the existing confirmation/recovery path with clear feedback; do not silently activate. Exact tenant/source closure and consent guards must be checked in the authoritative mutation transaction, not only before it.

## Falsifiable release proof

These are future implementation acceptance tests, not executed results.

- Verified same current address and deliberate named Join admits exactly one native membership without confirmation delivery; refresh and duplicate submission produce no extra effect. Same account joining another qualified public organization succeeds without granting any membership in that organization.
- Unconfirmed, locally auto-confirmed, imported/admin-marked without qualified proof, anonymous Auth, missing email, forged metadata and edited destination never take the shortcut. A different email uses confirmation without updating Auth or CRM.
- A cookie request from an unauthorized origin cannot enroll. GET, prerender, scanner, email-open and callback arrival cannot enroll. Ordinary confirmation capabilities cannot become login or general preference capabilities.
- Reader with no operational profile remains a legitimate public participant; absence of profile never defaults destination to demo/home tenant. Wrong Page/tenant/site/source IDs and CMS/operational ID confusion fail without disclosure.
- Race two fresh Join commands, one Join with withdrawal in each commit order, stale Join retry after withdrawal, fresh deliberate rejoin, old confirmation after rejoin, late provider event and restore: one exact current outcome, no resurrection or duplicated communication. Preserve withdrawal evidence.
- Race Auth address change, completed logout/current-session invalidation, Page-entry disable and purpose closure against acceptance. Validate the documented acceptance point; changed email is never substituted. An already accepted operation's recovery reveals only currently permitted result.
- Same address used by two tenants, two lists or two Auth identities stays scoped. Case/Unicode/support-policy variants follow owner comparison; plus/dot aliases do not merge silently. Pending guest entries cannot monopolize a real reader's address forever.
- Confirm positive database mutations via `RETURNING` and readback of authoritative state. Denied missing-grant, `USING` zero-row and `WITH CHECK` errors each assert their actual semantics and unchanged protected state. Test all applicable roles, effective policies, grants, views, RPC grants and service-role command paths on the actual migration chain.
- Fail before transaction commit, after commit before response, before required queue publication and after ambiguous provider acceptance. The first case has no membership; accepted cases recover the same result. No false sent/delivered status or second provider effect from retry.
- Auth deletion, explicit source erasure, privacy purge and backup restore preserve applicable restrictions under the owner-approved retention schedule; raw secrets/PII do not survive merely to make dedupe easy. Turning new intake Off does not break login-free unsubscribe or retroactively invent consent withdrawal.
- Mixed-version deployment cannot route old writers around new invariants; activation requires qualified producer plus actual Auth proof configuration. Rollback disables new admission safely while preserving accepted history and withdrawal access; no automatic data reversal.
- Production-shaped role/tenant volumes, hotspots and pending retries prove bounded queries and lock behavior. Record query plans, operations/concurrency, dataset size and measured latency. This review sets no unsupported throughput number or arbitrary expiry/retention constant.

## Recommended order

First reconcile B's exact D6-C05 exception and the owner proof contract. Then implement one source-owned admission/withdrawal lifecycle and public-reader mapping, including constraints and receipt recovery. Qualify grants/RLS/privileged paths, actual Auth methods/configuration and migrations before enabling entry. Lastly qualify end-to-end UI, confirmation, suppression and delivery effects. Monitor invariant violations rather than replacing missing proof with monitoring: one confirmed wrong-scope disclosure, unauthorized immediate admission, resurrection or duplicate durable effect triggers immediate admission-path containment by the identity/consent owner and incident review; existing withdrawal remains available.

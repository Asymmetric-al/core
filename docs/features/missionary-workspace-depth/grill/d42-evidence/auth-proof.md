# D42 — Auth proof and current-address qualification

Status: fresh research and implementation requirements for Q42 B; not runtime qualification or a new Auth implementation. Reviewed 2026-10-18. Scope is newsletter Join/Rejoin, with Supabase Auth, Phase 4 identity and Phase 12 authorization remaining their existing owners.

## Conclusion

**Accept B with a precise server-owned proof boundary.** A current signed-in reader can deliberately Join/Rejoin the named newsletter using the exact current address that the qualified identity owner can attest was actually verified. No second newsletter confirmation is needed for that case. Authentication success, `email_confirmed_at`, an editable metadata flag, an administrative confirmation, a profile email and donor claiming are not interchangeable facts.

The permanent implementation includes a real qualified fast path backed by identity-owned mailbox evidence. It does not implement B by sending confirmation to every reader forever. Unknown historical provenance takes the ordinary newsletter confirmation path while the identity owner qualifies and records future mailbox-verification evidence. A newsletter signup never creates an Auth account, creates membership, claims a donor record, changes the account email, links an OAuth identity or widens protected access.

## Fresh primary technical research

1. [Supabase general Auth configuration](https://supabase.com/docs/guides/auth/general-configuration) explicitly says disabling Confirm Email implicitly confirms the address in the database. That is direct evidence against treating a non-null confirmation timestamp as universal possession proof.
2. [Admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser) documents `email_confirm: true`. Administrative confirmation is supported but does not itself show a mailbox challenge was completed.
3. [getUser](https://supabase.com/docs/reference/javascript/auth-getuser) performs a request to the Auth server and returns authentic current user data. [SSR advanced guidance](https://supabase.com/docs/guides/auth/server-side/advanced-guide) distinguishes this from locally validating claims when an otherwise valid JWT may outlive its session. It also warns about caching refreshed auth responses. Core's Cache Components policy means its own request-level cache controls apply; do not copy that page's incompatible route-segment `dynamic` example into Core.
4. [User sessions](https://supabase.com/docs/guides/auth/sessions) defines the `session_id` association and explains strict current-session checks and the delay inherent in JWT expiry/session settings. Require actual revoked/deleted/banned/session-timeout tests on the deployed lane; SDK pinning does not prove them.
5. [Identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking) documents automatic linking by matching email and manual linking of a different provider email. This reinforces the repository's outstanding A10/G01 gate rather than resolving it. Do not accept whichever linked identity happens to contain an address or `email_verified` property.
6. [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp) is an authentication API. Anonymous newsletter confirmation must not be implemented as a login/auto-account-creation shortcut. [updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser) is the separate credential mutation path, not newsletter address selection.
7. [User management](https://supabase.com/docs/guides/auth/managing-user-data) says the Auth schema is not exposed through the generated API, warns that non-primary-key Auth objects may change and that failing triggers can block signup, and distinguishes account deletion from outstanding JWT validity. Keep application proof records in application-owned private scope; do not modify managed Auth schema objects for convenience.
8. [RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) distinguishes grants from policies and old-row `USING` from new-row `WITH CHECK`. Reusable Auth identity does not authorize a client to insert an arbitrary active subscription or change a row's tenant, audience, recipient or proof fields.

The [Supabase changelog index](https://supabase.com/changelog.md) was freshly fetched and scanned (231 entries in the fetched index). Relevant follow-ups were read: [managed schema restrictions](https://supabase.com/changelog/34270-restricting-access-on-auth-storage-and-realtime-schemas-on-april-21-2025), [default Auth email template restrictions](https://supabase.com/changelog/46599-changes-to-email-template-customisation-on-free-tier), [Node 20 support ending](https://supabase.com/changelog/45715-deprecation-notice-dropping-support-for-node-js-20), [future TypeScript minimum](https://supabase.com/changelog/47812-deprecation-notice-supabase-supabase-js-will-require-typescript-5-0), and [November 2026 TLS cipher change](https://supabase.com/changelog/cbc-tls-ciphers-deprecated). None supplies a new generic mailbox-proof flag or justifies bypassing P4/P6/P17. The committed TypeScript 6.0.3 already exceeds the announced future 5.0 minimum; no new dependency upgrade is proposed here. Deployed Node/TLS and delivery configuration were not inspected.

Current upstream `supabase/auth` source at `internal/api/auth.go` and `internal/api/user.go` was also read as corroboration: authentication loads the session identified by a nonempty `session_id`, rejects a missing session, and the inspected `requireAuthentication` rejects a banned user. This is a mutable upstream observation, not evidence of the deployed version or every application access path. Use the official [session documentation](https://supabase.com/docs/guides/auth/sessions) and deployed-lane acceptance tests as the contract.

## The smallest permanent proof contract

The required boundary is an identity-owner assertion, not a browser Boolean and not a newsletter-owned copy of Auth users. It must answer only whether the current caller may reuse verified mailbox evidence for this requested address now, with a proof reference and revision sufficient for audit/currentness checks.

Illustrative contract inputs/outputs below are requirements, not frozen function or table names:

- Trusted caller: current validated native subject, session identity/currentness and environment, excluding anonymous/demo/test identities from production qualification.
- Requested destination: the exact normalized address explicitly shown when the reader pressed Join. The browser may return an opaque view/intent revision as a precondition; it cannot assert the authoritative address or verification.
- Owner response: eligible/not eligible, exact native subject and current-address revision, minimal mailbox-evidence reference/method, and source qualification version. Do not return other identities, providers, contacts or tenants to the newsletter client.
- “Current” means that evidence still applies to the current address revision and qualified identity/session; it does not invent a new newsletter-specific proof-age limit, MFA prompt, repeated login or fresh inbox challenge for every Join. B intentionally reuses eligible prior verification; P4's stronger fresh-possession rule for an initial donor claim remains separate.
- Eligible evidence: a recorded, successful, source-qualified mailbox verification bound to that exact subject and address revision. A normal qualified native email confirmation/change/login challenge can establish it when the server knows the issued challenge purpose and destination and records successful redemption. A separately qualified provider assertion may establish it only when P4 admits the exact native/provider lane; a generic provider flag never substitutes for that gate.
- Ineligible evidence: autoconfirm, administrative confirmation, demo fixtures, imported verification with unknown provenance, a mutable profile/CRM email, client metadata, an arbitrary linked-identity email, or a historical claim whose address revision is no longer current.
- Storage stays within the P4-owned proof/current-contact implementation. If the owner has no suitable record yet, add the minimum private proof/revision record there; do not create a second newsletter identity directory or separate access engine. The final schema is implementation design, with explicit owner qualification before activation.

The ordinary qualified mailbox path is mandatory for release of B. A rollout may qualify that path before optional social paths, while preserving all selected P4 social scope and its explicit gates. Existing records can be classified using actual verification provenance; equal emails and current Auth confirmation timestamps are not a safe backfill. Unknown legacy evidence is not a permanent failure of the product: the reader can complete the normal newsletter email confirmation, and later source-qualified Auth mailbox verification makes future eligible Join actions immediate. Newsletter confirmation itself must not silently upgrade Auth credentials, claim a donor or create a cross-purpose verification grant.

## Mutation and concurrency design

1. Resolve the trusted tenant, named newsletter and public signup availability from the current canonical target/host contract. Treat a supplied newsletter ID or URL slug as lookup input, never tenant authority. Staff settings use their separate membership/capability boundary.
2. On intentional POST/Server Action, validate origin/CSRF protections, input bounds and the current Auth session through the shared boundary. A cached `getSession` object, JWT email claim or browser identity is not a fresh current-address check. Preserve a genuine no-account confirmation path.
3. Get P4's exact current-address proof assertion and compare the address/revision with what the reader actually approved. If the account/email changed since the UI was shown, do not silently subscribe the new address. Present the current address and require the deliberate Join action again, or let the reader choose the independent email-confirmation path for a different address.
4. At durable subscription acceptance, serialize on the canonical `(tenant, newsletter, normalized destination)` consent aggregate, using its revision and durable action identity. Recheck signup policy, subject/address-proof currentness, suppression and outstanding withdrawal generation. Insert/update consent and its durable evidence together. Idempotency is tied to this Join intent/business effect, not merely a fetch request or provider ID.
5. The implementation must give identity invalidation/email-change and consent acceptance a demonstrable order. An assertion or stale materialized cache cannot race a completed address change and then resurrect eligibility. Prefer the existing P4/P12 revision/currentness fence. If the implementation requires locking/read admission against current native Auth state, encapsulate that supported adapter in the identity owner and qualify its native mutation paths; never scatter direct `auth.users` access through newsletter code or assume application-only locks intercept direct native Auth writes. A shared/private authoritative transaction or equivalent linearizable owner command is acceptable; an asynchronous invalidation event alone is not proof.
6. A change occurring after accepted Join does not move that subscription to a new email or rewrite its consent history. The subscription belongs to the chosen destination/purpose; later account changes provide no new consent. Existing address-change, unsubscribe, retention and suppression owners govern later effects.
7. A later unsubscribe/withdrawal invalidates older outstanding Join/confirmation intents for that same consent scope. A new explicit Rejoin can create a later permitted consent generation. Retried pre-withdrawal requests cannot silently reactivate it. Two simultaneous Join submissions create at most one current subscription; concurrent administrative edits cannot change the approved tenant/audience/destination under a valid old request.
8. Return success only after authoritative consent acceptance. A lost response is recovered by the same operation identity and a narrow current outcome query; repeating Join must not emit duplicate confirmations or welcome effects. Any secondary delivery uses the existing durable P6/P17 seam and its own idempotent business effect.

These requirements do not demand a general distributed transaction framework. The source owners must choose one small authoritative acceptance boundary and prove the contested races; they may not promise atomicity that their actual implementation lacks.

## RLS, grants and public-reader admission

- Public signup permission is purpose-specific. `TO authenticated` only names a database role; it does not mean staff membership, verified mailbox, tenant access or permission to edit active consent.
- Do not require a financial donor record or membership to join a public newsletter. Do not let a signed-in employee subscribe another recipient immediately by choosing an arbitrary email. Staff import/addition remains its separately governed source.
- Active consent, proof/actor attribution, suppression changes and identity currentness fields are server-command owned. Revoke direct public/authenticated writes to those authority fields/tables; if a source permits narrow direct writes, prove both existing-row access and allowed resulting-row state, immutable authority fields and field-level grants.
- Tenant-scoped subscription, purpose, target and evidence relationships use tenant-aware keys/FKs. Nullable native subject supports genuine anonymous subscribers; NULL must not mean open tenant access. One current subscription per canonical newsletter/destination; preserve earlier consent and withdrawal evidence according to the owner retention schedule.
- Auth principal linkage, if retained, references only the stable Auth primary key and never becomes an access grant. Deleting an Auth account must not cascade-delete an anonymous-capable subscription's consent/suppression evidence. Detach or minimize identity linkage under the relevant retention owner rather than silently resubscribing or erasing withdrawal history.
- For mutations, test `USING` and `WITH CHECK` plus column/function grants and the allowed transition—not only row ownership. A permitted pending row must not be forgeable into active, move to another tenant/audience, or acquire caller-supplied verification/audit identity.
- Views must preserve invoker authorization or remain private; privileged functions have narrow execution grants, fixed search paths and explicit source admission. Privileged service-role paths must preserve the same tenant, subject, intent and suppression checks. No public proof-table enumeration, Realtime publication or address/token logging is authorized.
- No money precision changes are needed. This decision writes subscription/consent evidence, never a gift, commitment, donor claim or financial aggregate.

## Exact clauses for the D42 review

**Auth-1:** “Immediate Join/Rejoin MUST require an intentional action for one named newsletter and the identity owner's current, source-qualified proof for the exact address shown to and approved by the reader. Native login, `email_confirmed_at`, administrative confirmation, editable metadata and contact matching alone MUST NOT satisfy this requirement.”

**Auth-2:** “The server MUST derive native actor, verified destination, proof revision, tenant, newsletter and audit attribution from their authoritative owners. Caller-provided values are selectors or preconditions only. A valid public reader need not hold a donor/staff profile or membership, and subscription MUST create neither.”

**Auth-3:** “The release MUST implement and qualify at least the ordinary native mailbox-verification proof path for immediate Join. Unknown evidence uses the newsletter confirmation flow; it MUST NOT be backfilled from equal emails or autoconfirm flags, and the fallback MUST NOT be used to claim the selected immediate path was implemented.”

**Auth-4:** “Auth-email or identity changes MUST invalidate reuse of stale address evidence for new actions without moving existing subscriptions, propagating contacts across tenants or rewriting prior consent. Acceptance MUST check the same address the reader approved and prove ordering with currentness/withdrawal changes.”

**Auth-5:** “Newsletter confirmation MUST remain a non-authentication, purpose-bound action. It MUST NOT establish a session, create credentials, attach a provider identity, claim a donor record or admit private account data. P4 A10/G01 and provider-specific activation gates remain unchanged.”

**Auth-6:** “Application commands and database grants/RLS MUST preserve equivalent tenant/purpose/recipient boundaries on every read and mutation, including views, RPCs, service-role paths, retries and resulting-row changes. No consumer may directly manufacture active consent, verification provenance or actor attribution.”

**Auth-7:** “A returned success MUST mean accepted consent for the approved address and purpose. Recovery from lost responses MUST reuse the durable operation identity; an older Join or confirmation MUST NOT override a later withdrawal. Existing suppression remains owned by P6 and MUST NOT be cleared merely because Auth proof is valid.”

## Required proof cases

1. Qualified email-login reader presses Join for the displayed current address: one active purpose subscription and one consent record; no additional confirmation required.
2. Same reader with a profile in another tenant, or no donor/profile membership: permitted public Join for the target tenant works without private cross-tenant disclosure or provisioning.
3. Confirm Email disabled account, admin-confirmed fixture, unknown imported evidence and user-edited `email_verified`: no immediate activation merely from those facts.
4. Fresh actual qualified verification establishes the reusable proof path; a later Join for the same still-current address is immediate. This positive case prevents the implementation from disguising always-confirm behavior as B.
5. Qualified already-bound provider subject follows its qualified proof contract; a newly attached/unqualified provider email, changed provider email, absent address or relay mismatch cannot bypass A10/G01 or exact destination checks.
6. Email changes between page load and Join: no silent substitution. Email change races final acceptance: the specified ordering holds; accepted prior subscriptions keep their original destination and evidence.
7. Stale JWT after logout, deleted user, ban, revocation and applicable session timeout: immediate lane fails its deployed session/currentness contract; no profile/demo fallback supplies eligibility.
8. Another browser account signs in while a form is open: the old address/actor approval is not reused for the new user. A slow previous response cannot paint success for the new context.
9. Reader chooses a different email: confirm that exact mailbox without changing Auth email; a valid account email does not authorize the other address.
10. Existing active subscription: idempotent success without new consent inflation. Previously unsubscribed reader deliberately rejoins: fresh permitted intent; stale earlier retries cannot undo a later withdrawal.
11. Suppressed/hard-bounced/complaint address and tenant signup Off: no immediate activation from valid Auth proof, no suppression clearing and no sensitive public reason leakage.
12. Lost response after commit, duplicate taps and concurrent confirmation/Join: one current subscription; correct operation receipt and no duplicate secondary communication effect.
13. Direct table/RPC mutation tries cross-tenant ID, active-state forgery, owner/recipient change, invalid proof, or arbitrary timestamps: denial at all exposed and privileged boundaries.
14. Personalized success/address UI and Auth refresh responses cannot be served from another reader's cache; tokens and full recipient data are absent from URL analytics/logs.
15. Deleting Auth identity preserves required consent/withdrawal history without granting another user access by a later reused email. Guest newsletter confirmation creates no Auth account or session.

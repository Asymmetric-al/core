## What the fixture actually models

**Request meaning.** One invocation pins a tenant, requesting actor, closed fixture purpose, draft and source revision, immutable binding, relevant gate/route revisions, bounded voice and 60 reservation units. Binding rows contain synthetic credential revision/model/region/prompt identifiers. They contain no credential, secret, certified adapter or actual data-use certificate. Voice values `neutral` and `warm` demonstrate exact intent binding; they are not the selected product catalog or evidence of style preservation.

Tenant/actor/purpose plus a deliberate intent identity is unique. Retrying that identity returns its existing receipt and cannot reserve again. Changing voice or other pinned meaning conflicts. The initial request checks current source revision before reservation. A same-meaning receipt can remain evidence of an earlier request; it does not authorize another dispatch. Changing the currently selected route never retargets an older suggestion or credential binding.

The input is one already-qualified saved synthetic draft. There is no CRM lookup, donor/list input, hidden page context, selected-facts classifier, source-package compiler, prompt or actual Egress Manifest in this proof. Classification and the separate invoke/read/accept capabilities are represented by one effective-gate result solely to test fencing. Production must use the existing P12/P3/P10 owners, including the exact active context and current source/field ceiling. A SQL role name is harness identity, not the authorization model.

**Budget reservation.** Request acceptance locks the tenant budget, then its purpose budget, in a consistent order. It inserts immutable invocation meaning and reservation evidence while updating both held counters in one transaction. Required evidence failure rolls all these changes back. A competing request either fits both ceilings or reserves nothing. One race uses two actors under the same purpose; another uses two purposes under one tenant ceiling.

These are fixed **integer reservation units**, not money, tokens, a billing period or actual provider charges. Every invocation retains its 60-unit hold in this bounded fixture, including successful ones. There is no settlement, release, refund, budget window rollover, currency conversion, rate limiter or reconciliation service. Final totals equal the sum of invocation holds in both budget levels. Real money caps need the owner's certified worst-case request envelope, actual price/usage semantics, consistent units/currency/window, token/output limits, reconciliation and bounded handling of provider uncertainty. Database reservation arithmetic alone cannot promise a provider invoice cap.

**Uncertain provider work.** Dispatch and result observations are separate transactions using a synthetic worker command. No call reaches a model. An unknown observation retains the original invocation and reservation; the same request returns Inspect, and the worker cannot mechanically transition it back to dispatch. With the remaining capacity held, a fresh request cannot spend it again. This proves the hold and local transition mechanics only. It does not prove that a provider honored idempotency, that the first request was sent, that a timeout was uncharged, or that a new user-intent key is a safe retry. Recovery needs the actual certified provider's inspection/correlation contract. The fixture does not implement that recovery.

The result stub checks the current gate and pinned route. It is **not** a complete current-source/classification egress gate, capability-certified output validator or network dispatch protocol. In particular, it does not qualify every late source change before real egress. That work remains with the shared AI and source owners. Request/read/application checks below must not be advertised as proof of the missing provider boundary.

**Private comparison and Use.** A ready suggestion is separate from draft truth. The owner can read its body only under the current gate, original binding/route, unchanged source head and live expiry. Another actor or tenant gets Unavailable. Raw body/table reads are denied to ordinary actors. A function call represents deliberate Use; this is not proof that a human actually compared, understood or approved the text.

Use locks current authority and the source head, validates the original source revision and output marker, and atomically creates one ordinary successor, application provenance and required evidence while deleting the suggestion-body row. An injected evidence failure leaves the original draft, suggestion body and application count unchanged. Two Use calls with different transport keys create one successor. A subsequent retry returns the original application receipt even after a newer manual successor exists: receipt revision 2 is explicitly tested while the current head is 3. Changed replay meaning conflicts. No receipt is a promise that the draft still contains that text, remains readable or has been sent.

Expiry is checked using `clock_timestamp()`, including after locks. An already expired body cannot be read or applied. In a real race, Use waits behind a manual edit until the body deadline passes, then returns Expired without an application; the independent manual edit remains. Ordinary source editing is modeled only as a synthetic successor command; the complete manual editor and its separate P12 authority are not tested.

**Revocation and binding changes.** Revoke-first blocks Use; Use-first commits before the waiting revocation. Current revocation also blocks suggestion read and prior application receipt through this fixture endpoint. Restoring permission does not automatically revive suggestions pinned to the obsolete exact gate evidence. Production may freshly requalify unchanged intent where the owners permit; an unrelated tenant epoch change does not inherently require repeated user review. Re-enabling a permission is not backup restoration.

## Actual grants, constraints and sensitive-body limits

The five LOGIN roles are `missionary_a`, `missionary_b`, `other_tenant`, `provider_worker` and `policy_manager`. The separate `fixture_owner` and `command_executor` roles are NOLOGIN. All seven are nonsuperuser, non-BYPASSRLS, non-CREATEROLE and non-CREATEDB. The executor does not own tables. All fourteen tables use enabled and forced coarse tenant RLS. Ordinary actors and the worker have no raw table rights; the policy manager has explicit gate/route rights. The executor has bounded table/column privileges and no send-sentinel rights. PUBLIC function execution is revoked in setup's transaction; source commands fix their search path. See [roles.json](postgres-probe/roles.json) and [privileges.json](postgres-probe/privileges.json).

Composite keys bind a request to its tenant, purpose-specific binding, owned draft and source version. Application provenance binds the exact invocation/source version and resulting successor. Binding, invocation, version, suggestion metadata, application and evidence rows reject UPDATE/DELETE. Explicit NULL argument refusal is necessary in addition to these constraints: SQL comparisons can evaluate to unknown rather than true. The grouped negative case exercises NULL voice, output marker and expected source revision against a live unapplied suggestion.

The separately stored body is **synthetic plaintext**, not encrypted storage. SQL deletion on Use does not prove cryptographic erasure, disappearance from WAL/backups/replicas, provider deletion or browser-cache cleanup. Expiry denies access; this fixture does not sweep expired bodies or erase them on Discard, source supersession or revocation. Those are consequential production lifecycle obligations. Exact digest strings are markers, not tested cryptographic hashes.

Body-free evidence here means the fixed fixture evidence rows contain only kind and a safe synthetic correlation note, while invocation/application metadata contains references and markers. That column is not a general-purpose redaction policy, and the runner intentionally records its synthetic inputs/outputs. This proves neither prompt/log redaction nor a production evidence-access policy. Metadata, digests and provider references also need current protection; they are not automatically public because the body is absent.

The send-sentinel count stays zero and the executor cannot write it. No newsletter scheduler, email provider, publication or audience producer is connected, so the result is not end-to-end proof that real acceptance cannot trigger sending. D7's deliberate send control remains independently authoritative.

## Proposed safeguards and remaining qualification

**DB18-01 — One qualified request meaning.** Consume the existing shared control plane with an explicitly approved newsletter purpose and source contract. Pin exact permitted source/target revision, actor/context, selected action/voice, Egress Manifest, immutable capability binding and credential revision. Resolve current admission before request and before real egress; no hidden context, arbitrary provider endpoint, silent credential/model fallback or cross-purpose reuse.

**DB18-02 — Atomic bounded reservation and honest unknown.** Reserve the applicable shared and purpose capacities with the idempotent invocation/evidence in one short transaction. Use exact owner-defined units/windows and a certified request ceiling. Complete external work outside transaction locks. An uncertain provider outcome retains its original correlation and conservative capacity until qualified reconciliation; timeout is not cancellation, free retry credit or proof of no charge.

**DB18-03 — Suggestion-only, private and short-lived.** Keep a ready result separate from source truth. Apply current read/classification/revocation/expiry controls before body or derivative disclosure. Define D18's actual encrypted body deadline and early-erasure triggers through its owners. Durable evidence contains only necessary protected metadata; no prompt/body/secret leakage through telemetry, errors, support exports or provider references.

**DB18-04 — Deliberate exact application.** Use one source-owned acceptance command with current accept authority, original source/target/selection/digest checks and CAS. Atomically create at most one ordinary successor plus required provenance and the governed body disposition. Retries return the same bounded historical outcome; altered intent conflicts. Concurrent manual work is preserved. No application receipt is a send, publication, factual accuracy, language quality or review result.

**DB18-05 — Reductions and restore fence all protected doors.** Disablement, source restriction, credential/capability revocation, expiry and restoration must be respected at request, deferred egress, result admission, read, Use, cache/export and recovery boundaries. Existing bindings are prospective and never silently retarget old work. Restore cannot resurrect a body, key revision, authority or uninspected provider attempt; restoration qualification remains outstanding.

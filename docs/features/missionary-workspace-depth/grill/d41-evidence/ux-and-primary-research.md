# D41 — native contact work and honest external-tool boundaries

Reviewed **October 18, 2026 (Asia/Bangkok)**. The founder selected **B — Keep contact work in Asym**: no additional external contact-update feed in this release, while the separately governed giving feed retains its existing scope. This note is independent UX/research evidence for the answer review. It does not ratify amendments, implement UI, activate permissions or change an integration.

## Finding and strongest alternative

B is a coherent release decision. Make the native contact job complete through the already ratified D5 editor and D17 intake. Do not compensate for the absence of a contact feed with a dormant toggle, a permanent warning banner, a new export button, another migration wizard, or instructions to maintain two contact databases manually.

A remains the strongest alternative: a qualified one-way contact update could reduce duplicate entry during a real transition. MPDX's own documentation reports problems when external old values reappeared after local edits, so the ownership problem is credible. However, no design-partner requirement, qualified destination, measured transition workload or Asym usability evidence establishes that this release needs that additional purpose. B avoids adding the disclosure and stale-copy responsibilities before such a need is established. This is a scoped product judgment, not a claim that integrations are generally poor design.

The UI should explain the absence only where a user expects a connection: the existing integration scope/help and relevant transition documentation. It should not insert an explanation of an omitted integration into every successful native contact edit.

## Repository constraints and current implementation evidence

- [Ratified D5](../phase28-d5-adversarial-review.md) already selects direct correction under current tenant/source/field permissions, a focused entry into existing permission administration, only selected changes, atomic acceptance, correction consequences, conflict/retry recovery and international accessible forms. It explicitly rejects routine staff approval, universal missionary grants, another permission flag, broad identity/giving changes and a compulsory correction-request queue. D41 must not reopen these choices.
- [Ratified D17](../phase28-d17-contact-import-adversarial-review.md) already selects supported CSV/data-only XLSX intake with review, restricted start and exact owner acceptance. It adds or safely reuses eligible records; it does not bulk-overwrite, merge, import histories or establish consent. D41 must not turn repeated file import into a contact synchronization workaround or withdraw the selected import capability.
- [ADR-0097](../../../../adr/0097-source-authoritative-missionary-support-feed.md) separates the accepted P21 financial projection/closed field floor and P31 transport from any later independently ratified P28 relationship/contactability family. B adds no such family. Existing approved identity/display fields and source-required consequences retain their own rules; “no new contact-update feed” does not mean all existing giving-feed fields are frozen.
- [Q41 research](../phase28-q41-external-contact-continuity-research.md) asks exactly the additional-purpose question. No prior selection authorizes a live destination or universal third-party compatibility.
- [Current contact editor](../../../../../apps/missionary/app/donors/edit-donor-dialog.tsx) uses shared Base UI/form components and an API mutation client, but still contains a wider donor form with financial-style statuses, preferred-contact options and other fields. Its component-level submission treats an exception as a failed update. This static read establishes reusable components and unresolved qualification questions, not a demonstrated runtime incident or a completed D5 implementation. D41 does not bless the entire current form as the target native editor.
- [Frontend rules](../../../../ai/rules/frontend.md), [shared UI contract](../../../../../packages/ui/AGENTS.md), [responsive design](../../../../guides/ui-design/responsive-design.md) and [accessibility review](../../../../ai/skills/accessibility-review/SKILL.md) govern visual and interactive quality: exact base-maia, shared Base UI, semantic tokens, keyboard/focus/recovery, phone reflow and manual verification. ## Complete recommended journey

### 1. Tenant staff configure the native job

Retain D5's focused **Contact details** entry into existing permissions, using the actual established settings hierarchy. Show the current organization, configured role/group/assignment scope, eligible actions/fields and effective versus pending result. Setting administration remains separate from the ability to edit contacts. Removing one grant must not promise that every independent valid grant disappeared.

Do not add **Contact sync: Off**, **Connect your fundraising tool**, a disabled “Coming soon” card or a contact-feed permission. An excluded capability has no tenant setting to disable. Existing giving-feed setup, defaults, destination qualification, privacy preview and Stop sharing continue through their current owners.

Where an existing giving connection's scope is explained, use wording such as:

> “This connection shares only the approved information listed here. This release does not include a separate contact-update feed.”

Use its exact coverage preview for the actual fields, recipient and currentness. Do not shorten this to **Nothing leaves Asym**, **All your contact information stays private**, **Contact edits never affect this connection** or **All external contact updates are disabled**. Each of those claims could be false under independently governed existing fields, manual exports or another authorized product purpose.

Do not add a reminder to update the other tool after every correction; that would create a second maintained workflow with no demonstrated need. Transition help can explain the release boundary when relevant, without suggesting that staff bypass export authority by copying restricted information.

### 2. Maya finds and views a contact

Use the existing authorized supporter/contact list, search and detail. Search only the current permitted scope; lack of a match does not reveal that a hidden organizational contact exists. Keep the current user's search/filter position when returning from detail.

Eligible details show **Edit contact details**. Visible but non-editable information remains readable; forbidden values are not serialized into disabled controls. Permission checking is distinct from read-only access and from service unavailability. D5's safe explanation remains useful: **“You can view these details, but your current access doesn’t allow changes.”** Do not imply staff approval is available or required.

No external-sync status, provider icon, last-contact-sync time or connection warning belongs beside an otherwise native value. If an imported assertion has permitted provenance, show that provenance in the existing details/history, not a falsely live “Linked to MPDX” badge. A completed import is not an ongoing connection.

### 3. Maya corrects an ordinary eligible value

The short editor shows the permitted source values and changes only selected editable fields. Read-only values remain plain text and are not submitted. Before Save, use D5's shared-effect explanation, suitably scoped to the current source: **“Changes update the contact details available to your organization's staff.”** This must not imply restricted preparation is being shared; D1/D5's exact source category determines the applicable copy and action.

Preserve D5's ordinary single **Save** and **Cancel**. No integration prerequisite, sync review, obligatory note, consent checkbox or second confirmation is added. A source-specific action that requires proof or a withdrawal fence keeps its distinct pending/applied meaning; B does not remove it.

Use a neutral accepted result: **“Contact details updated.”** Do not show **Synced**, **Verified**, **Everyone notified**, **Updated everywhere** or **Ready to email**. The accepted native correction proves only its exact authoritative effect and separately required source consequences.

Do not couple contact entry to newsletter membership, donor login, gift status, giving frequency, household merge, fundraising rating or a sent-message record. Do not manufacture email or location values merely to satisfy a legacy form.

### 4. Handle failure and interruption honestly

| State                                  | Existing native experience to preserve                                                                                                                                                             |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Checking permission                    | Stable layout and a brief checking state; no enabled Edit flash or confirmed-denial claim.                                                                                                         |
| Permission service unavailable         | **“Editing is temporarily unavailable. Try again.”** Preserve separately authorized reading; no stale write fallback.                                                                              |
| Validation error                       | Associated field error and useful correction; retain still-authorized input. Do not translate permission failure into an invalid-email error.                                                      |
| Concurrent correction                  | **“These details changed while you were editing. Review the latest information.”** Show only currently permitted differences; no silent overwrite or merge wizard.                                 |
| Save pending                           | Stable focus and duplicate-submit protection. Closing the form after submission is not evidence of cancellation.                                                                                   |
| Accepted Save, refresh fails           | Preserve the accepted result; offer refresh. Do not report the correction failed or issue a new mutation.                                                                                          |
| Lost acknowledgement                   | Resolve the original operation; use **“Checking whether your changes were saved…”** while checking, then a clear unresolved state and Check again. No indefinite spinner or fresh effect identity. |
| Edit access removed                    | Stop stale submission and explain confirmed rejection; do not assert nothing saved while the outcome is unknown.                                                                                   |
| Read access removed or tenant switched | Remove affected values/drafts, reject late responses and use a non-disclosing unavailable message. No Copy draft/export recovery bypass.                                                           |
| Giving connection unavailable          | Native contact work remains available if its own dependencies permit. Connection error stays with its source; no contact-sync status is invented.                                                  |

The user's authored draft can remain only while its continued display/storage is authorized. Do not add a private offline contact cache or automatic resubmission when permission/network returns.

### 5. First use, empty data and import

If no permitted contacts exist, show a calm empty state and only the actually authorized **Add contact** or **Import contacts** actions. If access is unavailable, say so; do not claim the organization has no contacts. If a filter has no results, offer the ordinary clear-filter action rather than connector setup.

D17 remains the complete supported-file route. Its preview and results explain added/reused/skipped/problem rows and source provenance. Its partial results, retries and current authority follow its ratified contract. Reimport must not be presented as **Refresh from external tool**, because it does not synchronize corrections or bulk-overwrite existing facts. No “full migration supported” claim follows from accepting CSV/XLSX.

### 6. Accessible phone use and visual polish

Preserve shared Maia rhythm, semantic colors, ordinary section headings and clear labels. The useful job is a short native form, not an integration dashboard. At 320 CSS pixels and equivalent 400% zoom, controls and helper/error copy remain readable without horizontal page scrolling. Core's 44px mobile target guidance applies; no tiny hover-only pencil.

Keyboard operation, dialog naming, initial/returned focus, Escape cancellation and screen-reader result announcements use established shared primitives. Essential authority or conflict meaning must not rely on color, opacity or a tooltip. Save feedback is announced without moving focus unnecessarily.

Preserve Unicode names, casing and order; accept qualified international phone/address/email forms. A phone keyboard and email keyboard can help; browser autofill must not substitute Maya's own personal details into a supporter record. Source dates and provenance use governed temporal meaning and localized display, not device-clock authority. Low-bandwidth operation retains pending/error/recovery clarity without promising offline writes.

## Material risks and exact proposed clarifications

1. **Overbroad privacy promise — High impact / medium likelihood.** “Keep contact work in Asym” can be misread as banning every approved outbound field or promising all prior copies were erased. Add: **“D41 adds no P28 external contact-update/contactability resource; it does not widen, freeze, remove or relabel the independently governed P21/P31 field floor, export purposes or required source effects.”** Explain only relevant exact scope in UI.
2. **Dormant feed controls imply availability — Medium / medium.** An Off toggle suggests administrators can enable the excluded feature or that a failed connection blocks editing. Add: **“No contact-feed activation control, connection credential, contact cursor, background delivery job or contact-sync status is added by this release decision.”** Existing financial controls remain independent.
3. **Native correction is treated as an entirely new feature — High / medium.** Reopening D5 can accidentally add approvals, default-deny presets or blanket edits. Add: **“D5's ratified tenant/source/field permissions, minimal Save and correction consequences remain authoritative. D41 neither grants nor withdraws those powers.”**
4. **Import becomes a synchronization workaround — High / medium.** Periodic imports may overwrite newer corrections or imply live linkage. Add: **“D17 remains bounded add/reuse intake; repeated import is not synchronization, bulk correction, consent, merge or full historical migration.”**
5. **Client success language overclaims outcome — Medium / medium.** “Updated everywhere” or failed toast after accepted Save can lead to duplicate edits and mistaken expectations. Add: **“Feedback shall distinguish native acceptance, pending owner effect, unresolved outcome and failed refresh; no external delivery or universal propagation claim without that exact owner's evidence.”**
6. **Mobile/old-client bypass — High / medium without enforcement.** Vendor evidence shows permission parity can break with client age. Add: **“All reached clients shall use current source authorization and compatible commands; client affordances are not enforcement, and unsupported writers cannot silently widen fields or revive revoked edits.”** This is implementation qualification, not an Asym incident claim.

## Evidence limits and proof obligations

**Verified external facts:** the official sources above document native correction, permission differentiation, synchronization confusion and accessible data entry patterns.

**Repository facts:** D5 and D17 already select the native jobs and boundaries; ADR-0097 requires separately ratified P28 feed families. The current editor contains familiar reusable controls but does not itself prove full D5 qualification.

**Reasonable inference:** excluding a new contact feed removes one possible external-copy/correction path from this release and avoids setup work for people who do not need it. It does not prove there are no external dependencies or privacy risks anywhere in Core.

**Product judgment:** keep ordinary native work visually focused; explain connection scope only at integration/transition touchpoints; add no controls for the absent feature.

**Unresolved proof:** qualified D5/D17 runtime, actual permission/field inventory, supported source effects, old-client and retry behavior, existing feed coverage inventory and UI usability remain owner release gates. No prior probes/verifiers were rerun. This note creates no application tests or certification.

For formative UX validation, ask a missionary and authorized staff member to correct a permitted phone value, recognize a read-only field, recover a conflicting edit, and explain whether the change was saved in Asym, whether it verified consent and whether an external tool necessarily changed. Any claim that a successful Save verified contactability/consent or updated an external tool is a blocking copy/interaction defect. This is a proposed proof task; no participant results are claimed.

# D22 owner policy boundaries — optional amount-based follow-up

Research date: October 17, 2026. **A is selected**, including tenant control,
optionality and a simple experience. The founder subsequently explicitly chose
**one organization-wide policy, without workspace overrides**. The remaining configuration and temporal
contract below are proposed review amendments, not separately ratified choices.
D19–D21 remain ratified. Research only: no formal owner/ADR/OpenSpec, application,
schema, dependency, permission, ticket, provider or live-data changes.

## Recommendation and scope

Use one tenant-owned **Amount-based follow-up** policy in existing settings.
Recommended initial controls are Off/On and a positive amount for each supported
original currency, with the fixed plain comparison **at least**. Start Off with
no guessed amount or currency. An unconfigured currency supplies no amount-rule
reason; it is not zero, a conversion instruction, or an exclusion from other
qualified follow-up. Add/edit/remove a currency and enable/disable the rule are
the bounded customization of this initial feature.

The founder's request for complete tenant control does not select arbitrary
formulas, per-donor rules, separate staff/missionary toggles, automatic messages,
custom lifecycle states, or configuration of financial truth. Fixed inclusive
comparison and the initial Off/empty-amount profile remain review recommendations.
One organization-wide policy without workspace overrides is now founder-confirmed.

Do not import D16's goal-permission inheritance. Its tenant default and exact
subject override solve a different, expressly selected editing-policy problem.
For D22, the selected one tenant policy applies separately to each eligible exact
source scope; no default→Legal Entity→project→missionary→donor hierarchy. Tenant
scope does not combine money across Legal Entities, subjects or currencies, nor
grant a configuration editor those subjects' financial records. Future exceptions
would require an actual product need and exact precedence, not an empty framework.

The amount criterion is **additional**, not a minimum for other native purposes.
All optional means this amount feature is optional. D19 first support, D20 exact
gift-purpose grouping, separately qualified special/above-commitment reasons,
P16 attention and ordinary manual work keep their own contracts. D21 continues
to exclude automatic attention based only on comparison with prior giving.

## Exact proposed temporal contract

The recommendation is **prospective numeric edits and prospective Off**. This is
a D22 product judgment using existing source/task mechanisms; it is not inherited
from P27 ratings, whose Off contract withdraws solely automatic rating reviews.

**Admission** means the authoritative source acceptance of the exact qualified
amount reason and its durable task-projection intent. It does not mean a worker
dequeued an event, a task card appeared, a notification was read, or the user
opened the task. A committed intent is existing work even while materialization
is pending.

The source must bind the applicable policy at its qualified original live
occurrence boundary through trustworthy source ordering/lineage and immutable
policy history. A captured gift date, browser clock, provider delivery time,
worker execution time or caller-supplied version cannot substitute. The exact
source seam must be qualified before activation; this note does not prescribe a
new clock, event store or universal transaction spanning financial/task owners.

For a held candidate, numerical policy revision and enabled continuity are
different facts. A numeric edit need not discard original live work. An effective
Off or currency removal ends that unadmitted eligibility; later re-enable cannot
revive it. A draft edit that was never accepted is not an Off transition. Existing
policy history/current fences can prove these facts; no physical generation-table
design is selected here.

Settings copy should be direct:

> **Changes apply to new gifts. Existing follow-ups keep their original rule.**
>
> **Turning this off stops new amount-based follow-ups. Existing follow-ups
> remain. Previously accepted work may still appear or be corrected.**

Existing work can be deliberately marked Not needed through its qualified task
action. Do not add bulk cancellation to the settings Save or make Off wait for
a historical impact count, financial preview or task cleanup. Off must remain
usable when an unsaved amount draft is malformed: validate current administrative
authority and accepted policy head, stop the existing rule, and do not save the
invalid draft as a side effect. Ordinary Save has
expected-revision conflict and lost-result recovery; it is not an approval wizard.

### Governing automation guards still apply

`openspec/specs/platform-boundaries/spec.md:428–446` requires declarative Mission
Control automation, `automation:manage`, preview, test run, activity-log setup and
shared domain services. Calling D22 a native setting does not establish an
exemption. Its small fixed rule can satisfy these guards without a general
Workflow Studio builder or waiting for P35.

Before activation or changing the effective rule, show the exact bounded rule
preview and run the real predicate against stored synthetic cases in an inert
test path. Persist the reviewed policy/source-contract revision and test evidence
with its attributable activation/activity record. Test results create no live
gift, task, business intent, donor history or communication. Source-authorized
financial previews, if separately provided, retain independent read permissions
and are not required to display protected records merely to configure an amount.
Simple below/equal/above examples and immutable test evidence are not proof of a
qualified real financial producer; release proof still has to establish that seam.

The persisted definition can reference the code-owned trigger, condition,
shared-task action, run mode, source-resolved responsibility/reviewer and failure
policy, alongside the configured amounts and activity evidence. These fields do
not require editable workflow nodes, another approver picker or per-gift approval.
Use the existing current P12 authorization contract; the exact formal mapping of
the platform's `automation:manage` requirement to D22's source-setting operation
must be recorded before activation, not silently replaced with generic staff
access or a newly invented permission key. If the owning formal amendment changes
that applicability, it must explicitly reconcile this clause and preserve the
guarded outcome rather than claim a rename has already superseded it.

An invalid amount draft, failed preview or unavailable test service blocks new
activation/effective numeric changes, **not Off**. A pure draft save can remain
inactive. The preview/test can be inline and bounded, preserving a clear ordinary
Save/Enable action without a new configuration wizard or historical-data scan.

## Corrected decision candidate

> Offer the organization an optional amount-based follow-up rule. Authorized
> settings staff can enable it and choose amounts for supported currencies;
> eligible gifts meeting the exact rule can create or join the existing
> compatible native follow-up. Explain the organization's amount rule without
> calling the gift extra support or rating the donor.
>
> Use the founder-selected one organization-wide policy without workspace
> overrides. Recommend Off initially, no assumed currency/amount and a clear
> at-least amount per currency. The feature does not change money, other
> native criteria, history-based attention restrictions, access or sending.
>
> Numeric changes apply prospectively. Turning Off stops new admissions;
> already accepted follow-ups and their queued projections remain under their
> captured rule and current source/permission checks. Re-enable does not revive
> old unadmitted work. Actual source correction and deliberate task outcomes
> retain D20's exact coverage, independent obligations and history.

## Material concerns — eight dimensions each

Severity/likelihood are conditional design judgments, not measured incident
rates or research into optimal fundraising behavior.

### O01 — Optionality repeals required work or becomes a new permission switch

- **What:** All optional is treated as disabling first-support/other special work,
  or On grants missionary/financial access and Off removes unrelated work.
- **Why:** The selected optional feature is only the amount criterion; other
  purposes and current authority are independently owned.
- **Severity:** High lost work; Critical if access expands.
- **Likelihood:** Plausible with a generic stewardship toggle.
- **Evidence:** S01–S02, S05–S08; Q22 contrasts one additional criterion.
- **Answer impact:** Preserve A with purpose-specific optionality.
- **Permanent fix:** Source-owned amount enablement separate from financial facts,
  other purposes and P12 grants.
- **Exact proposed clause OC01:** “D22 optionality SHALL apply only to the amount-
  based follow-up criterion. It SHALL NOT disable D19 or other independently
  qualified native/manual work, make the amount a minimum for other reasons,
  relax D21, or grant/revoke source, contact, coaching, communication or settings
  rights. The amount rule SHALL explain attention, not classify extra support,
  donor intent or generosity.”

### O02 — Full customization produces a rule engine or hidden inheritance

- **What:** Add per-person exceptions, nested overrides, formulas, different
  closure modes, due-date graphs or inherited old tenant amounts.
- **Why:** These are different product policies and make a simple amount rule
  difficult to predict, test and administer.
- **Severity:** Medium maintainability/UX; High wrong task scope.
- **Likelihood:** Likely if broad customization wording is unbounded.
- **Evidence:** S01/S03, S08; D16 inheritance was explicitly scoped to goal editing.
- **Answer impact:** Bound the initial configurable values without removing tenant
  ability to enable/disable and select supported currency amounts.
- **Permanent fix:** One tenant policy, finite currency entries, no hidden fallback.
- **Exact proposed clause OC02:** “The initial D22 configuration SHALL be one
  tenant-owned optional rule with explicit positive amounts per supported currency
  and an understandable inclusive at-least comparison. Missing currency SHALL mean
  no amount criterion for that currency, never zero or FX fallback. No assumed
  amount, imported finance threshold, subject/donor inheritance, formula builder,
  custom task lifecycle or permission hierarchy is introduced. One organization-
  wide policy without workspace overrides is founder-confirmed; the initial
  defaults/comparison choices remain review recommendations.”

### O03 — Configuration authority becomes financial access or extra approval

- **What:** A role label or task owner edits organization policy, settings access
  leaks donor previews, or ordinary amount saves demand a new approval workflow.
- **Why:** Administration, financial reading, human task action and actual access
  policy widening are distinct P12 authorities.
- **Severity:** Critical disclosure/unauthorized configuration; Medium friction.
- **Likelihood:** Plausible when a new panel is implemented as a generic flag.
- **Evidence:** S08–S09; current scope/ceilings and ordinary versus widening saves.
- **Answer impact:** Use the existing settings/permission owner; no blanket staff
  right or new missionary permission is selected.
- **Permanent fix:** Exact current source settings authority and separate preview
  projection, with attributable versioned Save and conflict recovery.
- **Exact proposed clause OC03:** “D22 settings commands SHALL require the
  source-qualified P12 administrative capability and exact tenant scope. A role,
  participant, task assignment or gift-read grant SHALL NOT confer it. Managing
  the rule grants no donor/financial preview rights. Ordinary permitted parameter
  saves use one attributable expected-revision command and durable result; actual
  permission/disclosure changes retain their existing separate approval rules.”

### O04 — Worker timing or lowering a threshold creates retrospective work

- **What:** A delayed event uses the newest lower threshold, or enabling/editing
  the policy scans older history and creates a backlog.
- **Why:** Delivery time is not the gift's original live eligibility. Rule edits
  would silently manufacture an occurrence or select historical work.
- **Severity:** High task integrity and misleading policy.
- **Likelihood:** Likely if only the latest settings row is read by workers.
- **Evidence:** S03–S07, S10–S11; live/import distinctions and captured source meaning.
- **Answer impact:** Keep A, explicitly select prospective rule application.
- **Permanent fix:** Bind the original source-live policy using owner ordering and
  retain immutable rule evidence; no new task identity from a rule revision.
- **Exact proposed clause OC04:** “Numeric policy edits SHALL govern later
  qualified original live source occurrences. Source ordering/lineage SHALL prove
  the exact rule applicable to each occurrence; gift date, browser/provider/worker
  time or caller version SHALL NOT substitute. Existing admitted reasons retain
  their captured rule. Editing, enabling, import/backfill or replay alone SHALL
  NOT create retrospective admission or a new business effect for an old gift.”

### O05 — Off is ambiguous about admitted work and queued projection

- **What:** Off deletes accepted tasks, suppresses their durable queued intent,
  or lets unadmitted stale candidates commit because they captured On earlier.
- **Why:** Source acceptance precedes UI appearance. Confusing these boundaries
  either loses existing work or defeats the tenant's stop command.
- **Severity:** High durable work loss or unauthorized admission.
- **Likelihood:** Likely unless the acceptance boundary and copy agree.
- **Evidence:** S04–S07; P27's different Off behavior in S09 is not an inherited rule.
- **Answer impact:** Adopt prospective Off as an explicit D22 design judgment.
- **Permanent fix:** Serialize Off with source admission, preserve accepted intent,
  and terminate unadmitted eligibility without a bulk task cleanup workflow.
- **Exact proposed clause OC05:** “Off SHALL stop new amount-reason admissions at
  its authoritative commit. An admission is committed exact source reason plus
  durable task intent, not card appearance. Already admitted work SHALL remain
  and may finish materializing; Off SHALL NOT cancel or complete it. Unadmitted or
  held candidates from the ended enabled interval SHALL NOT commit after Off or
  revive on re-enable. Copy SHALL disclose that existing/queued work remains.”

### O06 — Currency removal or held work bypasses prospective activation

- **What:** Removing/re-adding a currency revives old candidates, numerical edits
  incorrectly cancel held live work, or an unsaved draft is treated as policy.
- **Why:** Numeric value, effective enabled continuity and authoritative Save
  are separate facts. Conflating them creates hidden epochs or replay loopholes.
- **Severity:** High lifecycle integrity.
- **Likelihood:** Plausible with per-row UI state or one undifferentiated version.
- **Evidence:** S01/S03, S04–S07; current policy/source fences and no historical revival.
- **Answer impact:** State complete per-currency behavior without a new hierarchy.
- **Permanent fix:** Existing policy history proves uninterrupted relevant enablement;
  amount edits and effective removal have different consequences.
- **Exact proposed clause OC06:** “A held originally live candidate MAY qualify
  under its captured amount rule while the applicable currency remains in the
  same uninterrupted enabled interval and current source/authority permits it.
  Numeric edits do not end that interval. Global Off or effective currency removal
  SHALL end it for affected unadmitted candidates; later enable/re-add is
  prospective. Unsaved drafts have no effect. No new physical generation engine
  or override tree is prescribed.”

### O07 — Policy edits replace current source truth or forbid legitimate repair

- **What:** New amounts reclassify old tasks; refunds are ignored because old
  eligibility was captured; an outage is treated as invalidity; Off blocks every
  correction of previously admitted work.
- **Why:** Captured policy establishes the applicable criterion, not permanent
  validity of the financial/source facts or continued actor authority.
- **Severity:** High false work/coverage and lost legitimate repair.
- **Likelihood:** Plausible with one eligibility Boolean.
- **Evidence:** S05–S07, S10; D20 source correction and originally live restoration.
- **Answer impact:** Preserve captured policy and current source validation together.
- **Permanent fix:** Recheck exact current evidence against original admitted rule;
  separate source correction from policy-triggered new admission.
- **Exact proposed clause OC07:** “Current source and actor evidence SHALL remain
  mandatory for existing work. Genuine source changes revalidate the captured
  amount criterion and withdraw only an invalid reason; unknown/unavailable SHALL
  NOT mean disproved eligibility. D20 may repair the same previously admitted,
  originally live unconsumed purpose under that rule even while Off, preserving
  lineage. This SHALL NOT admit a different Party/subject/purpose, revive handled
  coverage, or use re-enable itself as a repair event.”

### O08 — Reason/version becomes a duplicate task or destroys independent work

- **What:** Amount and above-commitment reasons create two same-purpose tasks;
  a rule edit changes the dedupe key; removing one reason cancels a promise.
- **Why:** Reasons explain qualification; the intended gift-purpose work and
  separately accepted human undertakings have their own stable identity.
- **Severity:** High duplicate/lost work.
- **Likelihood:** Likely if using rule ID/version/job as effect identity.
- **Evidence:** S04–S07, S09; D20 membership/coverage and P27 preserved obligations.
- **Answer impact:** Extend existing qualification, not the task engine.
- **Permanent fix:** Same gift-purpose member, distinct reason lineage, exact
  reviewed outcome and preserved independent work.
- **Exact proposed clause OC08:** “Rule identity/revision, enabled interval,
  executor and qualifying reason SHALL be evidence, not a new gift-purpose
  effect identity. Compatible reasons for one intended action SHALL share the
  existing member/coverage; distinct first-support/receipt/other purposes remain
  distinct. Reason invalidation SHALL preserve other qualified reasons, manual
  promises and P27 duties. D20 reviewed-set and D21 manual/native coordination
  remain authoritative; no parallel task or intent registry is introduced.”

### O09 — All-path policy handling leaks data or substitutes optional workflows

- **What:** Native settings are Off but a workflow admits the same amount purpose;
  protected task amounts/counts leak through previews; configuration requires P35.
- **Why:** Caller and surface cannot override a source-purpose boundary or confer
  access; optional consumer readiness is not native source ownership.
- **Severity:** Critical privacy; High boundary/availability.
- **Likelihood:** Plausible during later integrations.
- **Evidence:** S02–S04, S07–S09, S11.
- **Answer impact:** Preserve native capability and unrelated staff purposes.
- **Permanent fix:** Shared source admission/current authority for all reached
  callers; explicitly distinct purposes retain their owners.
- **Exact proposed clause OC09:** “Every caller of this P28 amount purpose SHALL
  honor the same applicable policy, enabled-continuity admission fence, stable
  effect identity and current source/P12 limits. Optional P35/AI/import paths
  SHALL NOT bypass it or become prerequisites. Other separately qualified staff
  purposes remain independent. Policy previews, task reasons, counts, receipts,
  notifications and logs SHALL expose only currently permitted source facts.”

### O10 — Apparent settings success or a toy probe replaces complete qualification

- **What:** A local toggle looks saved, unknown numeric defaults activate a rule,
  or a policy race fixture is presented as actual financial/user proof.
- **Why:** The user must know what is active and what their changes affect;
  seeded values cannot certify real source policy capture or effect admission.
- **Severity:** High false control; Medium operability/UX.
- **Likelihood:** Plausible given earlier cosmetic settings/source gaps.
- **Evidence:** S01, S04/S08/S11 and D21's classified runtime limits.
- **Answer impact:** Keep a small UI with real source control and falsifiable gates.
- **Permanent fix:** Exact settings/activation/source traces, recovery, measured
  bounded lookup and real-role/user proof; no invented timer/throughput.
- **Exact proposed clause OC10:** “Settings SHALL distinguish saved draft,
  effective On/Off, unavailable qualification, conflict and unknown Save outcome.
  No old local preference or finance threshold SHALL activate D22. Off SHALL not
  depend on a historical preview, test service, cleanup or validity of an unsaved
  amount draft; it stops the accepted rule without saving that malformed draft.
  Qualify actual source-live policy
  capture, source/Off races, durable recovery, current permissions, migration and
  accessible user comprehension before activation. Research fixtures prove only
  their declared mechanisms, not deployment or complete owner qualification.”

### O11 — Native naming bypasses existing declarative activation guards

- **What:** Treat a native settings panel as exempt from the platform's explicit
  automation management, preview/test/log and shared-domain requirements, or
  satisfy a test run by creating actual follow-up tasks against donor records.
- **Why:** Current governing OpenSpec supplies real activation safeguards. A
  renamed surface is not a scoped owner amendment, and a test must not pollute
  source/task history or expose records to settings-only administrators.
- **Severity:** High authority/effect integrity; Critical if protected data leaks.
- **Likelihood:** Plausible because P28 must remain independent of optional P35.
- **Evidence:** S12, S04/S08/S11; native independence does not supersede safeguards.
- **Answer impact:** Preserve the small native feature; reconcile guard applicability.
- **Permanent fix:** A bounded declarative policy, inline preview, inert test and
  persisted activation/activity evidence using current source/P12 authorities.
- **Exact proposed clause OC11:** “D22 SHALL satisfy or explicitly reconcile the
  current platform declarative-automation management, preview, test and activity-
  log contract before activation. The fixed native policy may reference its
  code-owned trigger/condition/action/run-mode/responsibility/failure definitions;
  no general builder or whole-P35 prerequisite is required. Preview/test evidence
  SHALL bind the exact candidate policy and source-contract revision. Inert tests
  use the real evaluator and synthetic inputs with no live task, business intent,
  gift/history or communication effects. Failed/missing proof blocks activation
  or an effective changed rule, not the authorized Off command. The exact P12
  mapping of `automation:manage` SHALL be formalized rather than guessed.”

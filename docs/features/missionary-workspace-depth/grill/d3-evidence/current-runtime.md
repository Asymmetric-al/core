# D3 — departure/incapacity, retained data and current lifecycle behavior

Research-only static evidence, 2026-10-16, source baseline `9cada8f3d8ab59db391d3fd20df77fcadeb09813`. No application/GitHub changes, hosted queries, migrations, deletion, account changes or notifications. Root and applicable API/auth/database/Supabase instructions were read; D1/D2 trust-boundary evidence is reused rather than rescanned. References are repository-relative file:line. These are committed-source facts and conditional consequences, not observations of deployed behavior.

The founder chose **no new access right when a missionary departs or cannot act**, with clean useful data and simple clear UI. This does not authorize automatic sharing, successor/private-note access, deletion of useful records, indefinite retention, a new administrative review permission, or a new lifecycle subsystem. Already shared contacts remain subject to the ordinary organization CRM authority selected in D2; unshared preparation does not become shared because its author is unavailable. Ending an authorization and disposing of data are separate source-owned operations.

## Committed FK effects: mixed retention, not a uniform cascade

Actual `pg_constraint`, migration application history, triggers and environment changes were not queried. With an ordinary PostgreSQL DELETE statement, a blocking FK causes the statement to fail and its cascaded changes to roll back; it is incorrect to claim that every cascade below necessarily commits when a blocker exists.

## Material D3 risks and minimal safeguards

1. **High, conditional unintended loss or blocked cleanup:** a simplistic “remove missionary” implementation using auth/profile/missionary DELETE can either remove tasks/care or fail on donor/finance/history references. The exact effect depends on populated edges. This is a proven schema distinction, not proven production loss. **Candidate clause:** ending current access does not delete, relabel or reassign retained source records. Any disposition uses the source's qualified retention/hold/correction contract; do not relax FKs merely to make offboarding succeed. Keep a clear inactive/unavailable presentation when supported by the owner, without inventing archival access.

2. **High, conditional incomplete revocation:** active-membership reads are useful, but the legacy profile-role fallback can still admit the departed missionary/staff to service-role API handlers if only membership is disabled. Missing profile fails auth (`packages/auth/context.ts:260`), but hard-delete to force that result invokes the FK risks above. Browser cache clears on signout/user switch, not same-user permission/assignment loss (`packages/auth/client-session.ts:56`). **Candidate clause:** prove current authorization termination across server roles, source grants, pending mutations/recovered results and open UI without making physical deletion the revocation mechanism. Do not promise revoked users can never remember or retain previously delivered content.

3. **High, conditional history disclosure through reassignment:** current missionary roster scopes `donors.missionary_id` (`packages/api/src/missionary-portal/donors.ts:502`) and loads general donor activity/notes (D1 R2/R5). Changing that pointer to a successor would change which existing rows/history the successor's present projection receives. No transfer endpoint was found here; this is a concrete consequence **if** someone repurposes primary donor association as a continuity action. **Candidate clause:** departure or incapacity never automatically changes the audience of unshared preparation, and a successor association cannot silently confer historical access. Preserve D2's already shared contact availability through existing organization authority; do not create a second contact/history store.

4. **Medium/high integrity, conditional misleading retained state:** no installed departure state, general archive or lifecycle receipt was found. Retained notes can outlive an author FK; immutable receipt/merge/audit identities differ from current display names. A departed owner can also remain on an apparently active task/primary association until an authorized source changes it. **Candidate clause:** distinguish “retained record,” “current access,” and “current responsible actor” in the minimum useful UI. Do not label unknown historical ownership as active work, delete it to clear a count, or create a new person with access just to fix an orphan label. Need for historical attribution does not require live account access.

5. **Medium/high privacy/correctness, conditional on pending work:** selected D2 staff notices, cached read models, generated files and audit copies can outlive current membership or source availability. Existing general queue has broad staff CRUD; current finance/Eve recipient eligibility follows different rules (D2 evidence). **Candidate clause:** departure does not broadcast, select a replacement notification recipient, create mandatory follow-up or admit development work. Source-qualified pending work either remains valid for its current authorized audience or reaches its bounded unavailable/cancelled outcome. Do not erase a valid shared contact because its sharer leaves.

These are not reasons to add exceptional-access UI or a large lifecycle builder. The smallest user-facing behavior should communicate whether their access ended and whether a record/action is currently available; authorized staff retain ordinary access to shared contact facts. Unshared content should not appear in staff search, orphan summaries, task previews or cleanup screens merely because its author cannot act.

## Retained-data census needed before any destructive migration or cleanup

Inventory **metadata and source authority first**, without treating inventory access as permission to display protected content. For each category identify tenant, canonical source/IDs, current audience, lifecycle state, retention/hold owner, FK/restrict/cascade behavior, copies/derivatives and pending work:

- Auth user, profile, active memberships and any actual Ministry Assignment/context grants; distinguish account access from canonical CRM person and source relationship identity.
- Unshared preparation, already shared contact facts, general donor notes/activity, linked tasks and their source obligations, score/derived rows, unresolved identity matches/redirects. The future restricted source is not installed, so do not pretend current donor rows carry reliable private/shared provenance.
- CRM notes and command logs, including free text copied to log payloads (D1 R1), author-name snapshots, unconstrained historical IDs, corrections/retry receipts and link labels.
- Donations/designations/funds/pledges/campaigns/issued receipt snapshots and merge audit; source financial retention/correction duties remain independent. `20260704120000_gift_receipt_records.sql:5` explicitly preserves issued snapshots, with donation RESTRICT (`:17`).
- Protected care and support records with author and subject FKs; notification recipient/preference/delivery records and pending workers; storage objects/exports/caches and external provider copies. Core's public bucket policies (D1 R9) are not a deletion/retention contract, and auth-user deletion's live storage behavior was not inspected.

“Clean useful data” should first mean accurate current state and discoverability for authorized users, with duplicates/stale pointers handled by their source contracts. It does not pick a retention duration, authorize indefinite retention, approve blanket deletion, or permit examination of otherwise unavailable content.

## Smallest meaningful evidence checks to qualify later

1. **One FK/retention fixture matrix:** inspect actual applied FK definitions in an isolated representative schema; exercise separately auth/profile/missionary deletion with (a) tasks/care only and (b) donor/post/finance/author blockers. Record before/after counts, SQLSTATE and statement rollback. Add one author-note/log and recipient-notice case to show retained IDs, SET NULL and RESTRICT. This narrowly tests the material mixed graph; no need for a broad new deletion suite before a disposition contract exists.
2. **One revocation journey:** retained profile + disabled membership, then current API reads/writes, open-page cache and late response/retry. Include legacy profile role and same-user tenant change. Verify source grants separately when implemented. An auth unit test alone cannot qualify real Supabase RLS/service-role/cache behavior.
3. **One no-new-audience continuity fixture:** one unshared sentinel, one already shared contact, and one successor with no prior restricted grant. End authorization without changing content audience; verify staff still see the shared contact, successor cannot see private history, no notice/task/enrollment is created, and no source identity is duplicated. Changing the primary donor pointer must not become the test's assumed correct action.
4. **One user-visible unavailable-state check:** keyboard/mobile + reload after access ends; truthful action/result, no fake archive success, no hidden record count/content in cleanup messaging, and no blind repeat after unknown outcome. Present only the minimal state required by the accepted source contract.

These are recommendations, not tests run in this task. No current D3 lifecycle implementation exists in the inspected paths to qualify end to end yet. Existing cleanup test `packages/api/tests/unit/cleanup-demo-users.test.ts:45` covers fail-closed endpoint auth, not the FK/retention graph.

Scope limits: no live `pg_catalog`/role/constraint/state inventory, full migration replay, auth ban/token/session experiment, storage-owner deletion test, hosted cleanup invocation, full external export/provider purge analysis, exhaustive care/support/Eve FK graph, or real user/browser testing. Targeted searches covered profile/missionary lifecycle writers and relevant FK changes; they do not prove absence of external administrative jobs. Preserve these limits when discussing source hazards: committed FK behavior and compatibility fallback are evidenced; actual data distribution, deletion success, production exposure and proper source disposition remain unqualified.

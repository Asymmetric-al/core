# D8 — current runtime, account and invitation boundaries

Research only. Inspected 2026-10-16 UTC. The founder chose tenant-permitted external coaches, each using their own account, with read-only access. That selection establishes eligibility and the interaction mode; it does not select every visible field, history window, financial module, recipient notification or administrator power. This note does not implement those choices or claim that the adopted Phase 12 authorization target already runs.

## Conclusion

The inspected runtime has no coach-specific route, projection, grant model, invitation producer or test. Adding a coach navigation item or mapping a coach to staff/missionary would not safely implement D8. Current role gates, the single profile-tenant context, full portal projections, mutation endpoints and cache keys all need a qualified path through the existing identity/authorization owners. This is a concrete integration requirement, not a reason to create another account, private task table, communication pipeline or broad staff role.

Five read-only assertions against the actual repository auth modules passed. They confirm existing behavior, including broad staff powers and legacy profile-role fallback after membership deactivation. They do not prove an end-to-end coaching flow, deployed RLS, browser isolation, invitation redemption or provider delivery.

## Material findings and exact amendment candidates

### RT01 — A staff or missionary alias would exceed read-only coaching

**Critical impact; highly likely if implemented as a role alias.** Staff subroles explicitly get full Mission Control access (`permissions.ts:32–52`), and staff has donor/donation reads through canonical SQL policies (`20260625002117_canonical_tanstack_db_realtime_rls.sql:160–194`). Missionary APIs include source writes. A read-only page is not a read-only principal; read-only finance can itself be excessive disclosure.

**Clause candidate:** “A coach uses their own proved Principal and one current Tenant context. Each authorized coaching subject/projection is granted through P12. Coach eligibility never grants staff, missionary-owner, donor-finance, contact-edit, task mutation, participant administration, invitation administration or dispatch authority. Existing independently held powers remain in their own contexts and do not enlarge the coaching view.”

**Proof:** Exercise the actual route, API, server command, direct Data API/RPC and storage paths as a coach. Read the permitted projection; deny omitted fields, another subject/Tenant, all create/update/delete verbs, task completion/reassignment, donor edits and exports without an independently qualified export grant. Repeat as an internal staff member entering the same bounded coaching context.

### RT02 — Multi-Tenant coaching cannot reuse the scalar profile tenant

**High impact; certain functional gap for a coach admitted to two organizations.** Current `getAuthContext` validates the actual Supabase user (`context.ts:249–264`) but derives only the profile tenant (`279–301`). Edge resolution does the same. The membership RPC is a positive boundary: it pins to `auth.uid()`, requested tenant and active rows, sets an empty search path, and limits execute privileges (`20260802041500_current_user_memberships_rpc.sql:22–50`). That RPC does not select or validate the full new coaching authorization context.

`authz.current_tenant_id()` separately reads server-managed JWT `app_metadata` (`20260226113000_authz_memberships_foundation.sql:130–140`); this is not mutable user-metadata authorization. Its existence also does not prove consistency with a newly selected profile-independent context. No demonstrated cross-Tenant exploit is asserted here.

**Clause candidate:** “One login may hold multiple independently admitted contexts. The server selects and validates one exact current Active Tenant Assignment and subject/projection for each operation; client route, query, header, remembered Tenant and membership list are selectors, never authority. Switching context neither rewrites the person's home profile tenant nor imports another hat's powers.”

**Proof:** Same Principal is donor in A, staff in B, and coach for two exact subjects in C. Switch contexts without logging out; ensure no union of capabilities, search results, counts, prefetches, response caches or queued effects. Tamper with selected Tenant/subject, revoke one assignment, and verify unrelated valid contexts continue. Test mismatch between JWT metadata and the selected authoritative context fail-closed where relevant.

### RT03 — Membership deactivation alone currently leaves profile-role access

**Critical impact for D8 revocation; observed current compatibility behavior.** `hasRole` accepts legacy admin/staff and donor/missionary profile roles even if corresponding membership rows are absent or inactive (`permissions.ts:61–95`). `derivePrimaryRole` retains those fallbacks (`102–117`). `tests/unit/auth/permissions.test.ts:53–68` deliberately asserts the inactive-membership/admin fallback. Two actual-source assertions reproduced this behavior for admin and missionary profiles.

This is not evidence that all deployed database paths ignore membership state. It is evidence that route/service role gates cannot by themselves satisfy D8's current-grant revocation requirement, especially with service-client handlers.

**Clause candidate:** “D8 authorization always requires the current source-qualified grant and current Tenant assignment. Legacy profile compatibility, previous successful access and remembered routing cannot satisfy or revive that grant. Global assignment deactivation and exact grant revocation fence later reads, derivatives and queued disclosures without deleting or disabling unrelated valid associations.”

**Proof:** Revoke the coaching grant, deactivate Tenant membership, expire invitation and re-enable membership independently. Exercise current session, refreshed JWT, a second tab, service route, export, pending request and queued notification. No old grant revives. Historical actors/audit remain factual; already received data is not falsely described as recalled.

### RT04 — The existing portal response cannot be relabeled a coaching projection

**Critical privacy impact; highly likely under response reuse.** The broad snapshot intentionally includes donor identity/contact/giving details and source task descriptions/joins. Its subject is the caller's own missionary context. `withOperation` supplies the service client after an identity/role check; it cannot automatically add a missing row/field/projection policy (`with-operation.ts:145–165`).

**Clause candidate:** “The coach read is a server-produced, field-allowlisted projection for the exact authorized subject, purpose and history boundary. Resolve authorization before source enumeration or aggregation, including related tasks, contacts, notes, updates, media and historical facts. Source owners retain truth and restrictions. Omitted or restricted facts cannot survive in payloads, search, counts, tooltips, joins, logs or fallback demo data.”

**Proof:** Capture the actual JSON and browser storage, not only screenshots. Include private prospect, restricted notes/tasks, anonymous donor, co-owned subject, changed history floor and source withdrawal cases. Attempt arbitrary profile/missionary IDs and joined donor IDs. Verify “not available” is not fabricated zero or a financial assessment. Exact visible modules remain a bounded P28/P12/source-owner qualification, not inferred from D8 eligibility.

### RT05 — Same-user cache reuse needs a context and revocation boundary

**High privacy impact; highly likely if current hook is reused for switching subjects.** `missionary-portal.ts:100–121` supplies one static cache key. `client-session.ts:64–83` isolates different auth users; its existing test at `tests/unit/auth/client-session.test.ts:129–165` checks user change and deliberately leaves same-user token refresh intact. This is not a current coach leak because no coach flow exists.

**Clause candidate:** “Protected coaching data is partitioned by the validated context, subject/projection and applicable authority version. Context change, access loss, restriction or history-floor narrowing clears affected client state and defeats stale in-flight responses. Realtime is an authorized refetch signal, not a raw private-data channel. Cache possession never authorizes a fresh disclosure.”

**Proof:** Delay A's response, switch to B, let A complete; A must not appear. Revoke while a tab is open and during refetch; clear affected state and deny subsequent fetch. Test query cache, server cache, router prefetch, browser back/forward, exports and thumbnails. Do not promise that the platform can erase screenshots or human memory.

### RT06 — Invitation-only copy is not a qualified admission lifecycle

**High integrity/privacy impact; certain missing path in inspected source.** New auth users currently receive a donor profile by the hardened trigger (`20260227060000_auth_role_hardening.sql:62–83`), regardless of editable metadata role. This replacement supersedes older triggers that read a role from user metadata; do not report the older trigger as the current behavior. The current trigger is not a coach admission or grant command and does not demonstrate Party/Principal binding for an invite.

**Clause candidate:** “The source creates a purpose-bound invitation intent for the exact intended recipient and reviewed access request, with finite expiry, replacement/revocation and semantic replay rules. Acceptance proves only the intended Principal binding. A separate owning access command re-proves current inviter authority, organization eligibility, target scope and selected grant before activation. Forwarded, wrong-account, expired, revoked, superseded or indeterminate attempts disclose no protected coaching data and grant nothing.”

Use P4's own-account and scanner-safe handoff, with the original source invitation authoritative; do not create a raw Supabase invite sender or shortcut P6/P17. P4's legacy donor-claim seven-day default (`phase-04…md:243`) is not a selected coach expiry. A finite native coach source profile, safe resend/replacement and retention need explicit qualification before activation. No extra login, shared credentials, fake donor/contact, household union or forced staff conversion follows from admission.

**Proof:** Existing Principal, new Principal, different current login, forwarded link, shared mailbox, changed email, merged/split Party, departure and recovered account. GET/HEAD/prefetch cannot accept or grant. Deliberate POST alone is not proof of a human or the intended Principal. Concurrent acceptance/reissue/revocation and retried commands preserve one source outcome and unrelated valid associations. Compare safe inviter statuses and public responses without enumerating account, email or prior-access existence.

### RT07 — Known-role auth redirects currently discard invitation continuation

**Medium functional impact; certain on this callback path.** `callback.ts:49–55` selects role home before safe `next`. `callback-handler.test.ts:112–130` tests `next` only with an unmapped role; the mapped donor success case returns donor dashboard (`82–109`). A legitimate signed-in donor invited as coach would need a qualified return to the invitation flow, not an assumption that existing callback behavior already provides one.

**Clause candidate:** “After authentication, preserve an opaque, source-validated invitation continuation through the ordinary safe routing path. The continuation cannot grant access, select arbitrary Tenant authority or become an open redirect. The intended account and source state are checked again at acceptance.”

**Proof:** Existing donor/staff/missionary Principal, wrong logged-in user, expired invitation during login, missing/tampered continuation, cross-origin return and same-origin unrelated target. Preserve existing callback private/no-store headers (`callback.ts:6–17`). The Supabase PKCE callback protocol is not itself the invitation acceptance command; do not mistakenly apply an inert-GET rule by disabling necessary protocol exchange.

### RT08 — Invitation delivery and read-only source work remain separate

**High integrity/privacy impact; likely if generic queue or notification is treated as access/task state.** The current donor/campaign queue cannot establish the source occurrence, identity binding, permission or task obligation. P17's deferred invitation keys prohibit inventing a stable generic template before the exact owner meaning exists. P6 compilation remains all-before-any for the complete bounded occurrence; source invitation persistence and provider delivery are different outcomes.

**Clause candidate:** “Local invitation intent and any selected access-request records are accepted only after required source validation and durable recording. External email is a separately qualified P4/P17/P6 outbox effect. Preparing, requesting, submitting, delivery failure and provider-unknown states never activate coach access, complete a task, or imply that the recipient read or accepted the invitation. After local acceptance, a delivery failure does not undo unrelated valid source records; recovery retries only the exact eligible communication under its source fence.”

**Clause candidate:** “Invitation delivery contains only the minimum purpose-approved, alias-safe facts and protected handoff. It does not embed the proposed coaching dashboard, donor identity, giving totals, private notes, task descriptions or history. A coach designation does not subscribe anyone to progress notices. Every later notice requires its own source meaning, authorized recipient projection/preference and current send-time reproof.”

No all-staff announcement, automatic missionary/coach task, reminder series, welcome workflow or inbound conversation follows from D8. If a permitted next-step task is displayed, use the existing source task and an independently permitted read projection; do not create a coach task store or turn “read” into acknowledgment/completion. Optional future notices are not a prerequisite to the basic bounded dashboard.

**Proof:** Persisted invitation with mail unavailable, rejected preparation, provider timeout after submission, duplicate worker, revoke-before-dispatch, accept/revoke race and stale replacement. Retry must not issue a new access grant, send to an alternate address, use another tenant's sender, manufacture a task or reanimate an old invitation. Inspect payload, logs, history, inbox preview and tracking for protected facts/secrets. Hosted provider and identity-hook proofs remain deferred.

### RT09 — Current public collections and buckets cannot carry protected coach derivatives

**Critical potential disclosure; plausible under reuse, no existing coach artifact leak demonstrated.** The canonical browser migration removes old demo-wide reads from protected tables and enables RLS (`20260625002117_canonical_tanstack_db_realtime_rls.sql:17–69`); reporting the original profiles-disabled RLS as the current posture would be wrong. It also deliberately grants public reads for ministry-content tables. Posts/interactions are publication-filtered, while missionaries/funds/follows/assets use `true` in that loop (`81–150`).

Storage migration definitions make `profiles`, `document-uploads` and `email-assets` public (`20250101000000_init_schema.sql:460–487`; `20260511024000_email_assets_storage_bucket.sql:5–16`). No later privacy flip was found in the migration search. No SQL `CREATE VIEW`/`security_invoker` definition was found in the inspected migration tree; this is not proof about deployed views or dynamically created objects.

**Clause candidate:** “No protected coaching fact, attachment, export or derivative is written into a public collection, public asset or public storage object. A dashboard gate is not an asset gate. Protected retrieval, expiry and revocation remain under the appropriate source/media owner and current P12 context; any chosen derivative requires exact independent eligibility.”

**Proof:** Inspect applied schema grants/policies, security-definer functions, any actual views, bucket flags, object policies and Realtime publications in an isolated qualified database. Test anonymous, authenticated ungranted, wrong Tenant, revoked coach and service-command paths. Verify raw object URLs, stale signed URLs, transformed thumbnails, generated PDF/CSV, CDN cache and public metadata cannot bypass the source boundary. D8 does not silently add exports or prescribe a new storage system.

### RT10 — Demos and current unit tests cannot certify external coaching

**High assurance impact; likely if screenshot or shared-role tests are accepted as proof.** `context.ts:169–224` implements a bounded E2E identity bypass with datasource allowlisting and only when no valid Supabase session exists; it should not be described as an unrestricted production bypass. It is also not proof of real identity admission or P12 enforcement. `packages/database/collections/support-workspace.ts:1–71` is a Support Hub ticket/read-model type and fixture surface, not the Phase 21 support subject or a coach dashboard.

`tests/unit/auth/permissions.test.ts:82–109` exercises one-login multi-dashboard roles in the same `tenant_1`, not multi-Tenant coaching. Current resolver tests cover the narrow public membership RPC and failure paths, not source grants/history floors. No coach tests were found.

**Clause candidate:** “Release evidence uses real own-account sessions and the qualified context/grant source with production-equivalent authorization paths. A demo user, hardcoded role, allowlisted bypass, disabled mutation button, mocked policy response or existing multi-dashboard unit test cannot establish D8 security or usability.”

## Executed verification and remaining proof

Executed a read-only `node --input-type=module` probe with Node v24.19.0, importing the actual `packages/auth/permissions.ts` and `packages/auth/roles.ts`, with `node:assert/strict`. The [reproducible evidence pack](auth-probe/README.md) preserves the exact script, captured JSON result and a timestamped run manifest with source/probe/output SHA-256 hashes. The same five-check script was rerun once to persist that evidence, without broadening its scope. **5/5 checks passed:**

1. `routeForProfileRole('coach')` is null and the unsupported value does not derive a primary role.
2. A `member_care` staff membership admits the admin dashboard and its configured capability list contains CRM, gifts and reports.
3. An inactive missionary membership still permits missionary through the legacy missionary profile role.
4. An inactive staff membership still permits staff through the legacy admin profile role.
5. The pure role helper unions active memberships supplied from two Tenants because it has no context-selector argument. This fifth input demonstrates its required caller precondition; the current loaders filter to the profile tenant, so the probe does **not** demonstrate a live cross-Tenant exploit.

The probe itself writes no files and needs no installed dependencies; only research evidence files were saved after the original run. Existing test sources were inspected but no Vitest suite, running app, browser, authenticated HTTP request, database migration/RLS execution, identity provider, email hook or external delivery was exercised in D8. Bun is unavailable in this workspace; this note does not claim an unattempted suite failed. Source migrations show intended checked-in posture, not actual hosted schema or storage state.

Before implementation can claim D8 readiness, run the meaningful tests attached to RT01–RT10 against the qualified owner implementation. Add representative coach/missionary usability checks for invitation explanation, choosing an authorized context, understanding bounded/historical/withheld information, and recovering from wrong-account or delivery failure without privilege expansion. This note intentionally makes no claim of whole-repository security audit, provider configuration readiness or completed P4/P6/P12/P17 runtime.

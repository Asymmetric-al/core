# D8 — database, authorization and lifecycle evidence

Research-only review, 2026-10-16. The founder selected organization-permitted, deliberately invited external coaches using their own identity and read-only access. This note does not ratify the detailed external-human admission policy, create a fifth P12 context, or implement that policy. It tests a bounded set of PostgreSQL mechanics needed by the proposed lifecycle.

**Result:** 35/35 final synthetic outcomes passed on PostgreSQL 17.11, including seven controlled two-session races with observed `Lock:transactionid` waits. Two intentionally unsafe counterexamples also behaved as predicted. The final container and its anonymous volume were removed and absence verified. No Core database, hosted Supabase project, Auth session, provider, application route, migration or dependency was changed.

## Bounded model and what the real roles mean

The fixture has two synthetic tenants, two missionary targets in one tenant, two independently scoped coaches, an inactive coach, and a coach in another tenant. It contains organization effective-gate output, current membership, invitations, accepted grant rows, minimal audit rows and already-minimized projection inputs. A separate private-record table is not readable by coaches or the command executor. All names and values are synthetic.

`session_user` maps a real PostgreSQL login to a fixed harness tenant. This is trustworthy inside this disposable test because a login cannot become another tested login; it is **not** a Core Auth/JWT/active-assignment implementation. The word `coach` in a fixture role name is not a proposed `profiles.role`, global permission or context class. A browser-provided GUC deliberately fails to change the safe reader's identity or scope.

The organization boolean stands in for the result of the existing owner/P12 admission decision. It is not a production tenant-setting schema, per-grant DENY system or replacement permission engine. The only fine-scope logic lives in bounded test commands standing in for the qualified source/PDP seam; RLS remains coarse tenant defense. The lifecycle uses exact tenant, invitation, coach and missionary target; the module list is a tiny synthetic closed vocabulary, not a new resource registry.

Acceptance serializes against the gate, current coach membership and the invitation. Source state, grant and acceptance audit commit together; an injected audit constraint failure rolls all three back. Invitation and grant scope are bound by a composite FK. Real coach logins have only the explicitly granted accept/read entry points, with no raw state or projection-table writes. A read-only coaching projection does not mean the intended recipient is forbidden to perform the separate invitation-acceptance action.

Revocation is a distinct reduction operation, available in the fixture even when the widening gate is off. It ends pending or accepted invitation/grant authority without deleting the acceptance history. Replaying an accepted invitation after explicit revocation returns unavailable; toggling the organization gate off/on does not restore a revoked grant. Pending acceptance uses an illustrative gate revision to reject stale A–B–A evidence. This does not require rejection for every unrelated tenant epoch change: the actual owner can freshly qualify the same original intent where its current exact authority still holds.

The fixture's 2000/2100 dates merely produce expired versus unexpired invitations without sleeping. They are not a proposed invitation TTL, access duration, retention limit or policy threshold.

All seven races use two actual login sessions with explicit transactions, hold the first transaction open, observe the second waiting through `pg_stat_activity`, then commit and inspect final state. They are not a sequence of separate single-session calls. The harness asserts application-name length so its wait lookup matches PostgreSQL's stored name.

Two development attempts are retained in [development-attempts.json](postgres-probe/development-attempts.json): the first FK assertion initially collided with the existing primary key before reaching the intended FK; the second used a 65-byte application name, preventing the helper from matching the wait observation. The assertion and label were corrected. Both earlier containers/volumes were removed. The final complete run has no failed outcome.

## Proposed technical clauses and remaining proof

**DB8-01 — Exact admission, not a role label.** Register the actual external-human tenant relationship and coaching purpose through P12's existing context model and P3/10 floors. Organization permission, deliberate invitation, identity assurance, acceptance and current projection entitlement remain distinct. Do not manufacture staff/donor/missionary identity, copy the missionary's session, accept a client tenant/target, or union unrelated hats to make access work.

**DB8-02 — Source-bound, independently revocable grants.** Bind exact tenant, human, coaching target, purpose/modules, permitted history, source revision and applicable access expiry to the current owner. Preserve additive grant semantics: revoking one source cannot claim final loss if another independently valid same-scope source survives. The fixture's overlapping temporary test grant is explicitly revoked before the read/revoke race; it does not prove the complete additive-source decision algorithm. Scope identities and accepted attribution need structural constraints plus immutable write privileges, not RLS predicates alone.

**DB8-03 — Atomic transitions and current fences.** Invitation/acceptance/grant history must use stable semantic identity and source-owned currentness. Resolve current authority at every consequential acceptance/read/export/queued effect; use the adopted owner serialization/fencing mechanism against reduction and expiry. Acceptance cannot restore revoked access, and failed notices cannot undo accepted source state. The fixture proves one accepted-invitation identity and atomic acceptance/audit, not a complete invitation reissue/token/outbox product or all interleavings.

**DB8-04 — Project before grouping.** The sole qualified resolver/source projection must admit exact rows and fields before aggregates, counts, trends, grouping, pagination or serialization. Coaches must not receive raw giving/supporter SELECT just to make a convenient invoker view run. A privileged bounded reader still needs exact current admission, controlled grants/search path, current source revision, safe output/error behavior, and alternate-path tests. Definer ownership is a mechanism to inspect, not a safety verdict.

**DB8-05 — Materialization does not become authority.** Production projections need explicit source/coverage/currentness evidence, policy/context identity and reliable invalidation/rebuild semantics. In particular, a missing row set must not be mistaken for a complete zero, and old materialized totals must not remain visible after a source restriction. D8's simple revision mismatch guard does not prove completeness, empty-set coverage, incremental maintenance, deletion propagation, historical redaction or cache/Realtime behavior. No performance or P12 read-budget claim follows from these tiny fixture rows.

**DB8-06 — Prove every reached door.** Retain no raw browser grants merely to support this UI. Qualify actual PostgREST/Data API, GraphQL, RPC/function/view, service-key, Storage, Realtime, export, AI and background-job paths; key/role bypass paths require the same source/PDP decision. A SQL login test is not a hosted Supabase route test. Invitation notification subject/body, target name, alias, URLs and preview metadata must use P17's neutral qualified projection; this probe sends no invitation and tests no token.

Additional untested boundaries remain explicit: external email possession/account linking/session/AAL assurance, actual four-context admission, same-human multiple active hats, source-controlled accepted-access duration/expiry (only pending invitation expiry was executed), missionary departure and inviter-authority changes, multiple surviving grants to the identical scope, review-history policy, protected-resource redaction, cache/invalidation/late responses, hidden FK/unique error normalization, hostile SQL input search-path corpus, repeatable-read/serializable or failover behavior, and production workload/query plans. These are affected owner qualification tasks, not reasons to invent a second authorization system or require unrelated future phases.

Severity is **high** for stale grant acceptance or after-the-fact aggregate filtering and **critical** if such paths disclose protected people/care information. Likelihood is **plausible when implementing a new coaching projection**, supported by the concrete unsafe synthetic counterexamples and the documented owner requirements; no incident rate or current Core exploit is claimed. The proposed clauses above identify the required prevention and the precise limits of this proof.

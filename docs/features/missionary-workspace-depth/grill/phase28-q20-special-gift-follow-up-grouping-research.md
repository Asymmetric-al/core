## The single product choice

Grace makes two separate qualifying special gifts to the same ministry before
Maya has handled the first follow-up. Each gift is already qualified by its
owning source; this example does not infer special generosity from its size or
from missing commitment data. It is an illustrative scenario, not user research.

**Should Maya see one current follow-up covering both gifts, or a separate
follow-up task for each gift?**

- **A — One current follow-up (recommended).** Show both eligible gifts clearly
  in one task for that supporter and ministry. Maya can handle the reviewed gifts
  together, with each gift's source evidence and covered outcome retained.
- **B — One follow-up per gift.** Each qualifying gift creates its own task and
  requires its own disposition, even when several arrive before Maya follows up.

A keeps the daily queue focused on useful relationship work and avoids repeated
completion for one intended personal follow-up. B makes every gift individually
prominent and may suit a separate-action practice, but can create repetitive work.
No measured time saving, donor preference or fundraising improvement is claimed.
These are strongest plausible alternatives, not different financial policies.

This is a choice about which gifts a personal follow-up covers, not merely
collapsing several independent tasks into one visual card. Both options retain
actual gift evidence, current access/contact rules, honest independent-task
completion, optional interaction recording and deliberate separate sending.

## Why this was a genuinely open decision

- The [founder brief](phase28-founder-brief.md:123) requires a useful daily queue
  without duplicate cards for one obligation, but does not say that two different
  gifts are one or two human obligations. Its [native stewardship section](phase28-founder-brief.md:165)
  requires special/above-commitment work, exact purpose and preserved history.
- [P28 owner constraints](../../../prds/program-roadmap/owner-constraints.md:74)
  keep task purpose with P28 and source financial/recognition/commitment facts
  with their owners. We are not reopening whether native special-gift tasks exist.
- The canonical [MPD-01 catalog](../../../prds/workflow-studio/07-core-workflow-catalog.md:2667)
  expressly lists a grouping preference among the later configurable recipe's
  choices at line 2681. Its exact source binding still requires qualification.
  This proves a grouping decision exists; it neither selects P28's initial policy
  nor makes native tasks depend on P35 or its optional engine.
- [P28 implementation/UX](../../../prds/sitestacker-parity/roadmap.md:4197)
  reuses shared tasks and phone-friendly current-state presentation.
  [P35 source ownership](../../../prds/sitestacker-parity/roadmap.md:4859)
  keeps source-purpose identity and genuinely different intended effects distinct.
- The [ratified D19 review](phase28-d19-first-support-follow-up-adversarial-review.md#lifecycle-and-ownership-synthesis)
  preserves distinct purposes and requires exact coverage when one actual action
  satisfies compatible work. It does not select the unit of future special-gift
  follow-up. First-support coverage remains its own ratified purpose.
- [ADR-0183's independent task contract](../../../adr/0183-source-owned-work-projects-into-one-shared-tasks-hub.md:622)
  supplies human completion authority; grouping does not justify a second task
  system or turn a personal task into financial-source correction work.

Two independent owner reviewers identified grouping and special-gift criteria as
separate open choices. Grouping is chosen for Q20 because it changes an immediate,
understandable daily journey without asking the founder to supply financial facts.
Historical-pattern detection and any permitted criterion configuration remain a
separate frontier; no threshold or inference policy is silently selected here.

## Dependent safeguards to resolve after the answer

If A is chosen, define which compatible gift reasons can join the same still-open
follow-up and how the UI shows the exact reviewed gifts. A gift arriving while
Maya reviews or completes work must not be silently marked handled. Already
completed work must not absorb later gifts. Keep tenant, ministry, supporter,
responsibility, purpose, permission and source eligibility boundaries explicit;
do not aggregate across currencies or hide a restricted gift behind a count.

If B is chosen, preserve each qualified occurrence while preventing duplicate
transport/workflow tasks for that occurrence. Do not imply each task requires a
separate donor message or invent an interaction from a bulk completion action.

Both options require current source correction, reassignment, partial outcomes,
safe retry and clear Done/Not needed/correction behavior. The financial source
decides eligibility; a reduced commitment, advance/catch-up payment, fee cover,
unmatched amount, pending recognition or processing payment cannot become a
special gift merely through task presentation. Do not reuse finance review-risk
thresholds or impose a new reminder deadline through this question.

The completed D20 review resolves these dependent details against D19 and the
shared owners: exact reviewed-set coverage, same-task residue, material-change
conflict, durable receipts and qualified correction. The frontier wording above
is retained as the pre-answer question. No time window, automatic communication,
privacy right or implementation claim follows from choosing A. Source criteria
and historical-pattern detection remain a separate frontier, not a new question
asked during this review turn.

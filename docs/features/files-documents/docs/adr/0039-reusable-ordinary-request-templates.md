## Ratified decision and amendments

Q39 SHALL allow authorized staff to create, maintain and use optional Document Request Templates: reusable source-owned sets of ordinary item definitions and instructions for independent, never-issued request drafts. Start from scratch remains equally available. The actual ordinary request source owns supported definitions and their compatibility; P29 custody, a folder, template name, generic administrator status or an adjacent email/CMS/workflow template does not grant that authority. Template use, maintenance, draft authoring and issuance remain distinct current source/P12 powers. No general form builder, executable recipe, automated issuance, bulk amendment, template marketplace or whole-Studio prerequisite follows.

Templates SHALL contain only explicitly source-admitted reusable definition fields. Save from a permitted never-issued draft or directly authored template deliberately identifies the reusable item set and its actual sharing scope. Do not clone arbitrary request JSON, subject/recipient/record identities, answers, evidence, private review/conversation history, acceptance, participant assertions, access proofs/grants, actual reviewer assignments, clock ends or communication plans. Resolve actual instance facts through the new request's current trusted context; valid current defaults may prefill them without repeated manual entry. A field allowlist cannot remove case-specific facts embedded in names or instruction prose: staff must see and review the actual reusable content before saving. No automatic sanitization guarantee or new AI classifier follows.

One deliberate Save template SHALL make a validated, nonempty, source-compatible definition set available as one coherent saved revision. Separate working editor input or autosave from the shared usable basis; do not expose half-edited sets. A material saved change, retirement or deliberate make-available correction is attributable and uses a current expected basis. Concurrent maintainers cannot silently overwrite each other or reuse a revision identity for different content. Retirement stops new application; it does not cancel requests. Correct mistakes through a supported authorized current successor or make-available action over still-lawful content, with preserved history. Making content available again establishes a current availability basis; it does not automatically revive a previously stopped or uncommitted application against the retired basis. Matching committed effects still reconcile first. No additional Publish ceremony, second approver or recurring review bureaucracy is required by Q39.

A genuinely new application SHALL consume the exact saved usable revision and current availability basis staff reviewed, together with the expected never-issued target draft basis, under current template-use and target-source authority. Validate known definition compatibility and current restrictions at that authoritative boundary; recheck relevant facts after waits. Edit/retire/restriction-first gives an honest conflict, refresh or unavailable outcome; copy-first produces an independent draft. Do not silently substitute the latest template, drop invalid items or claim partial application as success. Preserve existing lawful draft input and instance choices; never implicitly append or overwrite. Choosing a starter before typing is the default simple journey. Any supported replacement of existing definitions must show its impact and be deliberate, coherent and recoverable; Q39 does not require a generic merge system. Same names do not by themselves prove duplicate items.

Application SHALL coherently persist the complete intended copied definitions, fresh source-owned draft/item identities as applicable, exact origin revision/member attribution, required history and recoverable operation outcome. Copied request content is independent of template content: request editing does not edit the catalog, and later catalog editing, renaming, retirement or author departure alone cannot rewrite/delete existing copies or require a perpetually active template. Current applicable source/privacy restrictions still govern every copy. Existing qualified operative references must preserve their admitted exact meaning/version and current access; an untracked mutable URL cannot silently change copied instructions or become a grant. No new attachment corpus or external fetching system follows.

Durable operation identity SHALL bind the actual save/application/retirement intent and its material basis, including tenant/source, selected revision and target where applicable. Reconcile a matching committed effect before checking eligibility for a new one, while independently checking current disclosure of the result. A lost-response replay after retirement, role change, later draft editing or issuance returns the original permitted outcome without recreating items, overwriting later edits or resurrecting retired content. Changed material under the same identity conflicts. A genuinely intended second draft is a separately authorized new operation; equal template content does not collapse it. Unknown outcome requires reconciliation, not a fresh key presented as repair. Mandatory facts and recovery cannot be lost between authoritative write and secondary work; optional projections recover without undoing a valid copy or issuing work.

Template preparation/application SHALL remain inert. Lawful drafting need not already satisfy first-issuance review readiness or require a recipient to be online. Actual issuance validates the current adopted draft, source/record/purpose/recipient, item restrictions, Q24/Q25 responsibility, access timing and applicable communication rules through the existing source boundary. Issuance-first fences a new stale template application; application/edit-first requires issuance to use and validate the changed draft basis. Later issued changes use their own qualified commands, including Q33/Q34/Q36/Q37 where eligible. Template editing never changes requiredness of existing requests or overrides source-required constraints, and never changes submitted evidence, acceptance, fulfillment, cancellation or access periods, and creates no new notification purpose or default.

Catalog names, descriptions, instructions, history and provenance SHALL retain their actual current tenant/source/field visibility. Template curation does not grant access to derived requests; draft access does not automatically disclose restricted origin history or other uses. Trusted context supplies tenant, actor, actual occurrence time and audit attribution, and the server validates selected targets and definition fields. Enforce tenant-aware template/revision/member/draft/item relationships, coherent current basis, typed identifiers/content/state/occurrence values, required null/default/uniqueness/check/delete rules and non-retargetable attribution. Historical ordering uses the qualified source occurrence/revision, not client time or locale-formatted dates. Qualify effective grants and combined RLS USING/WITH CHECK across reads, inserts, updates, upserts and deletes, plus views, RPCs, functions, triggers, storage references and owner/service/admin/import/worker/Local API paths. An allowed mutation cannot transform a permitted row into a forbidden tenant, source, definition type or authority-bearing state. Existing template privileges and a version integer are not sufficient proof.

Retirement SHALL remain distinct from retention/disposition. Preserve required copied meaning and minimal provenance under each actual source policy without cascading template deletion into requests or keeping an unlimited archive of private text. A mistaken reusable private fact requires a supported maintainer/privacy path: stop future use, correct the reusable basis and assess/remediate affected copies under their own current source authority. Do not automatically rewrite issued work, disclose all derived uses, restore disposed data or claim retirement recalls information already lawfully delivered. Technical logs contain safe identifiers/outcomes, not private template bodies, secrets or participant details; business history and security audit remain distinct. Q38's general metadata-only discovery boundary is unchanged.

The UI SHALL offer a scoped optional Choose template/Start from scratch path, a readable preview of the selected items and normal draft adaptation with current valid defaults. Show actual sharing when saving and distinguish Saved template, Draft prepared and Request issued. Do not require repeated confirmation of unchanged valid fields or expose internal revision machinery unless needed to explain a conflict. Preserve lawful input, focus and return context through validation, conflicts and slow networks; invalidate private state on relevant tenant/permission changes. Support keyboard operation and, where item reordering is offered, a non-drag single-pointer alternative, plus assistive technology, visible focus, mobile reflow/touch, long Unicode names, IME/RTL and localized text/date presentation. Render source-admitted text and references through qualified safe rendering; template content is never executable markup or code. Recipients and reviewers use the normal source-qualified request journey without a template step, extra account or inherited approval. No broad private URL/log/analytics/cache or durable offline archive is introduced by default.

Implementation SHALL reuse the smallest qualified source authoring, storage, API and shared UI mechanisms. Native design must declare finite catalog/query/page, item/text, history, mutation/concurrency, recovery and retention budgets with units and owners, then prove representative tenant workloads and resource use before activation. No vendor limit, unmeasured speed claim or zero-cost promise is imported. Use bounded server queries and measured indexes, avoiding full-catalog body transport and unbounded history scans. Do not migrate adjacent email/CMS/PDF templates or old person-specific requests into this catalog by name or indiscriminate copying. Any explicit legacy conversion validates its actual source meaning and records truthful provenance.

Rollout SHALL fence incompatible old writers/readers and preserve copied content, exact operation lineage and current restrictions across mixed versions, backfill and restore. Stop affected new template saves/applications without erasing admitted drafts or issued facts; roll forward when downgrade would lose required safety or history. Supported recovery must not require routine production SQL. The exact clauses, proof groups, lifecycle/journey checks and controls below form the required amendment package. Formal canonical owner/OpenSpec publication and tickets remain their later authorized stages; this selected-answer review is not implementation or release qualification.

## Ratified glossary definition

Full Q39 ratification adds the following exact term to CONTEXT.md, preserving
all24 prior definitions. The feature glossary now contains25 ratified terms.

**Document Request Template**:
A reusable, source-owned set of ordinary Document Request Item definitions and
instructions used to prepare an independent, never-issued request draft.
It is distinct from an issued request, submitted evidence, an access grant and
an executable workflow or form definition.
_Avoid_: live request, copied evidence, inherited approval, access grant, executable workflow

## Consequences and qualification

Staff may choose a template or start from scratch, see the actual reusable items,
adapt an independent draft and use normal issuance. Valid current defaults stay
useful; no repeated entry or extra approval is imposed. External participants
and reviewers receive the same source-qualified request experience.

Templates need a small genuine maintenance and authorization lifecycle. They
cannot promise private prose is automatically sanitized or that retirement
recalls already-delivered content. Existing copies retain their own meaning;
actual current privacy/source restrictions still govern them. Supported current
correction and exact outcome reconciliation avoid routine database repair.

No new provider, general form/workflow engine, live synchronization, automatic
notification, bulk issuance, template marketplace or body-search scope follows.
The strongest B remains suitable for bespoke work and is retained as the ad-hoc
path. A is not claimed free, faster by a fabricated percentage or already built.

Native activation requires actual source/role/RLS/API/service proofs, source
ordering/failure/replay/mixed-version/restore tests, composed accessible user
journeys, finite workload/resource budgets and accountable operational owners.
Mocked adjacent template tests and these documentation checks cannot supply that.

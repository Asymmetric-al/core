# ADR-0003: Recipient corrections with exact review lineage

**Status:** Ratified by Conrad, 2026-10-20: Q03 A, the exact corrected
decision and all required amendments, including Q03-C01–C20 and Q03-P01–P24.
The adversarial disposition was Accept with required amendments; those
amendments are now adopted grooming intent. Q01/Q02 remain unchanged.
This is not a formal PRD or implementation/release authority.

Conrad chose to let recipients correct pending submissions and required a
clear, easy UX/UI journey. For the ordinary native request, allow a currently
authorized recipient to send a correction for the exact unaccepted item while
its source permits it. This avoids staff unlocking every routine mistake;
staff-opened-only correction remains a legitimate stricter source process.
Overall request openness and preview access do not grant this mutation.

## Ratified decision

Record a new immutable submission linked to the exact corrected occurrence.
Preserve other supporting files, independent uses of the bytes and prior
decisions. Once finalized bytes and current source authority permit durable
correction admission, atomically record receipt, successor relation, the
relevant review-set change and required history/effect intent. The predecessor
then cannot be accepted as the current candidate, even while the new file is
being checked. This admission-time fence and no-silent-revival policy are
substantive Q03 amendments included in ratification, not inherited universal behavior.

A rejected new file does not automatically restore the earlier candidate.
A checker outage recovers the same received attempt where possible, rather
than requiring needless resubmission. Preview readiness and source acceptance
remain separate. Correction and review compare the exact target and every
relevant evidence-set dependency; stale operations cannot silently retarget.
Local selection/transfer start does not change review selection or acceptance,
though governed intake reservations, quota accounting and audit may occur.

Keep the interaction in the existing task: clear item, accessible file choice,
inline target/selection review, one deliberate Send corrected file action,
truthful progress, persistent receipt and safe recovery. No ordinary mandatory
reason, repeated identity form, extra confirmation modal or drive screen is
added. Staff retain their reading context and exact version; a correction notice
does not replace content under them. Only qualified authorized content can open.

## Consequences and preserved boundaries

- Source-owned permission, deadlines, freeze/closure, financial/application
  decisions, official artifacts, publication, retention and holds remain
  authoritative. This is not a universal Reopen or Replace command.
- A correction grants no original download, previous-version archive,
  deletion, indefinite access or deadline extension. Viewing is not a lock;
  closing a browser is not cancellation of a committed operation.
- Durable effect identity survives transport retry/key expiry. New input gets
  new qualification; earlier approval and safety results cannot transfer.
- Shared commands, custody, task/communication owners and Base UI/base-maia UI
  are reused. No new workflow engine, permission system, provider or editor is
  selected. Real source/role/concurrency/browser proof is still required.

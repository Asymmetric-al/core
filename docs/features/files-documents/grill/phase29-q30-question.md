## Historical question and alternatives

**While an ordinary document request is unfinished and the recipient has valid
source-authorized access, should they be able to ask questions and reply to
staff inside that request?**

The founder brief already requires useful exact-version, purpose-bound staff
review comments. Q23 already requires actionable participant-safe guidance and
an owned help route. Neither is optional in this question. Q23 expressly did
not add recipient text-only replies. The unresolved choice is a narrow native
participant clarification capability, not exposing the internal review thread.

| Option                                                            | Practical experience                                                                                                                                                                         | Benefits                                                                                                                                         | Costs and boundaries                                                                                                                                                                                                   |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Allow item questions and replies (recommended)**            | An eligible recipient can choose Ask a question beside an item, including before uploading, and reply to safe staff responses in the same request context. Authorized staff answer there.    | Resolves ambiguity where it occurs, without making the participant invent a new file or switch channels. Staff retain the relevant item context. | Requires a genuinely staffed, source-authorized clarification route and safe participant-visible message history. Adds inbound work; cannot be an unmonitored comment box or another general inbox.                    |
| **B — Allow staff-invited replies only**                          | Staff deliberately invite clarification for an item; the recipient can reply within that exchange but cannot initiate an item question. Otherwise the existing approved help route remains.  | Keeps native conversation initiation under staff control while supporting a focused response without a new upload.                               | Still needs most of the same secure messaging/recovery capability, plus clear invitation eligibility. Someone confused before staff contact must use the separate help route.                                          |
| **C — Keep clarification on the existing approved contact route** | Native collaboration remains authorized staff review comments and deliberate participant guidance. Participants use the source's existing contact/help route for questions and explanations. | Avoids a new native participant messaging surface and can suit an organization with an effective established communication channel.              | Participants must leave the item context; staff may need to reconnect the explanation to the correct request. The help route must really exist, be owned and be usable; no forced re-upload or dead end is acceptable. |

**Recommend A.** The small useful product is an item-level question and answer,
not a chat platform. A participant should be able to explain that an apparently
missing page is already in the submitted file, or ask which document is wanted,
without producing meaningless replacement bytes. A directly supports Q23's
lawful same-evidence reassessment and Q21's deliberate staff review while keeping
those decisions distinct from messages.

B is a real middle choice, supported by products that distinguish initiation
from replies. It limits unprompted native traffic but retains most qualification
cost and adds a staff invitation dependency. C is a credible simpler alternative
when the existing source contact route already serves people well. No observed
Asym volume, response-time or task-success study proves A universally better;
this recommendation is a product judgment about contextual assistance.

## Concrete example and user journeys

Illustrative example, not a documented ministry workflow: Elena requests a
document from Nora. Nora is unsure whether an existing certificate is suitable.
With A she chooses **Ask a question** beside that requested item, writes her
question and chooses **Send question**. She sees that the question was received
and is awaiting a staff response, without implying that a person has read it
or promising an immediate answer. Elena sees the question with the
correct item and responds using the source-approved staff route.

Later Elena requests a clearer second page. Nora replies, “The second page is
already on page 3 of the file I sent.” Elena can inspect the exact permitted
version and, if the evidence meets the current requirement, use the existing
Q21 acceptance. The reply itself neither accepts the item nor resolves the
formal requested change. With B Nora can reply only after a deliberate invitation;
her earlier document-choice question uses the help route. With C both exchanges
use that existing route.

| Journey                           | Required boundary for whichever option is chosen                                                                                                                                                                                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Before the first upload           | A permits an item question when the source authorizes clarification. No fake upload, full portal enrollment or file-version reference is required to ask about an existing requested item. B/C expose the actual approved help route.                                                             |
| Explaining existing evidence      | Staff can read the explanation and inspect eligible exact evidence; Q21/Q23 own any fresh review decision. No new bytes, automatic acceptance or hidden evidence edit.                                                                                                                            |
| New correction during discussion  | The message retains its intended item and, when relevant, exact referenced version. A newer file cannot inherit the comment's approval or silently become its subject.                                                                                                                            |
| Staff internal discussion         | Internal review notes and participant-visible clarification remain visibly distinct. Staff do not publish an internal thread by replying, mentioning a person or switching tabs.                                                                                                                  |
| Staff absence or reassignment     | Questions reach an accountable currently authorized source route. Q24 review responsibility is not automatically permission, the help route or an email recipient list.                                                                                                                           |
| Expired or completed request      | This choice does not extend unfinished access, add writing to completed read-only access, reopen work or reset any clock. Offer only an existing source-approved help or recovery path.                                                                                                           |
| Mobile, keyboard and poor network | Use the current item layout, a labeled text field and clear send/retry result. Preserve permitted draft/context while operating; distinguish received from sending or unknown outcome and recover the same message without duplicate posting. No typing indicators or real-time chat expectation. |
| Restricted or mistaken context    | Recheck tenant/recipient/request/purpose for reads and sends; prevent stale drafts/responses crossing contexts. Do not reveal another recipient, internal comment, historical file or confidential reason through the exchange.                                                                   |

Use Core's existing shared Base UI/base-maia controls and contextual layout.
Make the recipient audience apparent without making participants configure
privacy or select staff from a directory. Staff need a clearly labeled outward
reply action distinct from internal notes. Actual message-content accessibility,
supported languages, safe rendering, feedback and return focus must be qualified;
existing controls or screenshots do not establish that proof. Do not force a
third pane alongside paired reading; preserve comfortable access and return.

## Repository reconciliation and scope boundaries

The [owner research](phase29-q30-owner-research.md),
[runtime research](phase29-q30-runtime-research.md) and
[comparative research](phase29-q30-comparative-research.md) retain exact anchors.

1. **A real open scope choice.** The founder brief requires exact-version review
   comments, while Q23 explicitly does not add recipient text-only replies or
   general discussion history. A or B would explicitly extend that selected
   ordinary-request scope. C preserves it. None removes staff version comments,
   safe Q23 guidance or the already-required capable help route.
2. **Source authority, not a file-wide discussion.** The ordinary source owns
   clarification eligibility, current recipient, item context, outward audience
   and staff route. Permission to read a file, review responsibility, matching
   email, a folder or a mention does not grant conversation access. No general
   thread follows a reused file into another source. Internal staff comments
   and protected historic discussions do not become participant history. A/B
   include enough currently authorized shared-text context to understand the
   exchange; this is not a general message archive or file-history entitlement.
3. **Finite access stays finite.** A/B concern eligible unfinished-request
   clarification only, including currently authorized fresh unfinished periods.
   Q06–Q19 deadlines, revocation and completed read-only scope remain. Message
   sending/reading does not renew access or establish a new source-access admission.
   Post-completion conversation would be a separate scope change, not implied here.
4. **Messages are not evidence-state commands.** A clarification does not submit
   or correct a file, satisfy a requirement, resolve formal requested changes,
   accept evidence, fulfill a request, waive instructions or certify identity/
   consent. Receipt alone neither blocks nor forces Q22 fulfillment. Staff must
   still consider relevant new information through the source's existing review
   and decision process; the absence of automatic state changes is not permission
   to ignore facts that materially affect the current review. Real requirement
   changes and decisions use existing source commands.
   Files continue through their qualified upload/evidence routes; no attachment
   bypass is added to this text-only capability.
5. **Reuse communications without copying authority.** Apply P6/P17 content,
   delivery and privacy boundaries and the owning source's actual message/work
   route. Do not create an automatic Support conversation, second inbox, general
   CRM feed or configurable Workflow Studio dependency. A received question needs
   a durable visible route to authorized staff even when external email is off.
6. **No notification-default decision is smuggled in.** Q26 covers genuine
   Request changes notices; Q27 covers its selected source-actionable document
   events with staff email opt-in. Text clarification is neither event. A/B need
   an explicit owner binding for any new outward notice; email/SMS/bell defaults,
   reminders, escalation and read/typing receipts are not selected by this question.
7. **Protected history and recovery matter.** Use trusted actor/time/context,
   durable message identity, current disclosure on replay, safe content rendering
   and governed retention. Lost-response recovery cannot duplicate a sent message
   or leak it after scope loss. No unapproved private offline cache or ambient
   provider URL follows from retaining a draft or replying.
8. **Do not require a new configuration platform.** Reuse established source
   policy and authority boundaries. The question chooses native clarification
   scope; it does not select a tenant setting default, unlimited conversations,
   new universal permission atom, general chat/annotation system or arbitrary
   timing/character limits. Keep specialist owner restrictions intact.

# Phase 29 Q13 — fresh access for an expired, unfinished request

Researched **21 October 2026, Asia/Bangkok**. The parent reports Q01–Q12 and their full amendments ratified. Q12 fixes the new ordinary initial unfinished profile at up to 1,440 elapsed hours from original authoritative issuance. **No Q13 option is selected.** This is comparative research and a recommended founder question, not a new permission, canonical contract, implementation or activation.

Public primary documents and existing Q08–Q12 research were inspected. No private account, message, recipient, request, file or provider state was exercised. Only this note was written.

## Recommended next single question

> After ordinary access expires while a private document request is still unfinished, may specifically authorized staff approve fresh, finite access to continue that same otherwise-eligible request, or should that request's access remain ended?

Recommend **A — Permit a fresh, scoped source decision on the same unfinished request.**

The continuing task, recipient and source context remain the same. The expired original authorization and its original end remain historical facts. This is a new prospective authority decision, not editing the old deadline, treating expiry as if it never happened, or allowing a sign-in link to revive permission.

A should include a coherent completion outcome: **eligible normal fulfillment while the fresh unfinished authority is valid can prospectively admit Q07's read-only stage for at most 720 elapsed hours from that fulfillment, under all genuinely applicable current limits.** This is an explicit proposed part of A, not a claim that the old expired episode already qualified. Work completed in the unauthorized gap cannot be backdated into eligibility. At the fresh decision, the request must still be unfinished; a completed request is not reopened through this action.

The recommendation is product judgment. It provides an accountable way to finish an existing permitted task without inventing another request solely for a new clock. No current source proves that all ministries need it, that it saves a measured number of support contacts, or that modern products universally use immutable fresh authorization episodes.

Two options are sufficient. Automatic renewal conflicts with the ratified boundary and is not a meaningful third option. Mandatory duplication is also not a neutral compromise: it creates another task/history and may copy sensitive information without reducing the need for current authorization.

## Why not require a new request every time?

A genuinely new request can be appropriate when the owning source establishes a different purpose, recipient, requirement or application. It must use that source's existing procedure. It should not be created merely to make an expired request appear new or to reset the original sixty-day end.

Forcing a second request for the same continuing task has plausible costs: split receipts and reviewer context, uncertainty about which version is current, repeated uploads, duplicated sensitive records and incorrect lateness. These are design consequences to test, not observed Asym incident rates. Fresh authority on the existing request still needs all current permission checks; retaining a record identity does not make authorization simpler by itself.

Content Snare documents both restoring an existing request and duplicating a request, and specifically warns that copying answers can expose sensitive information. That supports treating restoration and copying as different actions. It does not prove that Asym needs its duplication UI or that duplication is always improper. [Restore a request](https://contentsnare.com/help/knowledge-base/can-i-change-a-request-from-completed-archived-back-to-published/), [duplicate a request](https://contentsnare.com/help/knowledge-base/duplicating-requests/).

## Preserve Q08–Q12 rather than stretching an existing power

**Q08 is different.** Its fresh read capability follows an actual prior ordinary completed-view admission and stays read-only. Q13 concerns a request that is still unfinished after original ordinary access expiry. Its proposed fresh authority may permit currently eligible intake/correction as well as the necessary currently authorized own-request context. Q08 cannot be used as a substitute when its prior-admission condition was never met.

**Q09 still owns requested-by targets.** A passed, edited or newly assigned target does not itself qualify fresh access. Fresh access does not rewrite original receipts or make earlier late work on time. Any new target relationship is whatever the source actually declares; no automatic new response interval follows.

**Q10's completion rule needs explicit prospective mapping.** Under proposed A, a fresh authorization admitted while the request is still unfinished can support eligible normal fulfillment and a new completed-view admission from that actual fulfillment under Q07's maximum. It does not resurrect the old unfinished grant or qualify completion that occurred after old expiry but before any fresh authority existed. A completed request is not changed back to unfinished simply to enter this path. A race in which the source completes before fresh admission must be resolved against current source truth.

That proposed completed view does not automatically broaden Q08's existing original completed-admission lineage. A later fresh read grant following this continuation's completed view needs its own explicit compatible owner decision; do not infer it merely because both stages use Q07's read-only maximum.

**Q11's original facts stay fixed.** Preserve the original issuance/result and restrictions. The fresh decision needs its own semantic intent and outcome, current issuer capability and current exact recipient/source context. Retry or an unknown response recovers the same fresh act; it does not create another act or reuse the original grant as if it never ended.

**Q12's sixty days is not the fresh period.** Neither sixty days nor Q07's thirty-day completed maximum automatically selects a new unfinished interval. The original derived less-than-ninety-day original lifecycle bound is not silently reinterpreted as a fresh-access cap or permission to exceed a true overall cap.

The capability should be bound to the same continuing request, intended recipient and source purpose. Changed purpose, recipient or authoritative business scope requires its own existing procedure. A shared mailbox, matching address, broad staff role or ability to read/review files is not sufficient grant authority.

## What ordinary time expiry does not erase

The fresh action must not clear a revocation, binding purpose deadline, independently closed intake, adverse security/privacy condition, frozen or accepted item, quarantined representation, legal/records restriction or changed recipient identity. These retain their actual scopes and governing procedures. A records hold is not automatically a read prohibition, but it is also not permission to grant access; preserve whatever it genuinely governs rather than flattening all restrictions into one date.

Retained bytes, existing source review permission and a continuing business need are inputs to the current decision, not sufficient recipient authority by themselves. A fresh original-download capability still respects Q04 exact-version/current eligibility. Q05 still excludes superseded content. A current safe preview does not imply every original or related file can be delivered.

All private status, filenames, dates, histories, counts, help context and resulting files remain source-gated. An expired link cannot reveal private existence through a newly added “Request more time” button or badge. A fresh grant is not permission to disclose other requests, grant site membership or build a general drive.

## Small recipient and staff journeys

These are proposed interaction directions to evaluate, not implemented screens or newly selected communications.

### Recipient: help, then the same qualified task

1. The existing entry route shows the permitted neutral/ended state. Only if disclosure authority allows it should the page say **Access has ended** and identify this request. Expired proof or unknown source state must not be misreported as expiry.
2. The person uses the existing source-owned help route. A request for help does not grant access or guarantee approval. Avoid another portal, forced account creation or retyping a request identifier already safely known to the authorized context.
3. After a real fresh authorization and any independently authorized communication, the person returns through Q01. Once the selected future timing policy resolves current usable authority, show the actual end and currently permitted remaining actions. Do not say “another sixty days.”
4. Keep previous source-confirmed receipts and current files in context where authorized. Do not require already-received material again solely to populate a new request. Pending correction still targets the exact eligible member and preserves Q03's immediate successor fence.
5. If normal fulfillment qualifies during fresh authority, transition to the prospectively declared Q07 completed view and actual end. Do not require downloading, an extra confirmation or another sign-in solely to start that stage; current proof/source rules still apply.

The recipient-facing action should be about continuing the task, not managing grants. A source can provide the approved fresh path without reviving an old bearer credential; URL and token behavior remain a later qualified implementation detail. The stable request experience must not be confused with unchanged authority.

### Staff: one contextual review and one deliberate action

1. Open the existing source request/help context under the actual staff capability. Establish that the request is still unfinished, the original ordinary opportunity ended, the intended recipient/purpose remain eligible and the proposed actions are still allowed by their owners.
2. Show permitted recipient/context, remaining work, relevant prior outcomes and restrictions, plus the approved finite timing terms and any already-known controlling cutoff. Do not force the issuer to read file bodies when their grant capability does not require body-read permission. Do not require a free-text justification essay or second approver unless an existing actual source rule already does.
3. Take one deliberate **Grant fresh access** action, with descriptive context. No editable old expiry or arbitrary recipient picker. Changed material state/permission is handled as a real source conflict, not hidden behind a stale review.
4. Read back the fresh result and applicable timing truth. A future timing anchor may not yet resolve a final end; show approved timing terms/known caps until it does. This note does not select that anchor. Grant committed, currently usable, recipient notified and recipient entered remain separate facts.
5. If the outcome is unknown, reconcile that same fresh act. Do not approve twice, create a duplicate request, backdate a gap or tell the recipient access is restored before that is established.

A restored opportunity is not guaranteed task completion or permanent approval. The current source can still deny a file action, end intake or restrict use. Explain the supported next step without exposing sensitive restriction reasons.

### Declined, prohibited or no longer needed

- If a current source restriction forbids the desired action, do not offer fresh permission as a bypass. Use the actual owner path.
- If review is all that remains and staff already have the necessary authority, fresh recipient access is not automatically necessary to finish source work. Any grant still needs a legitimate remaining recipient purpose.
- If the source has already completed, this is no longer the Q13 unfinished case. Resolve its existing valid admission/current rights; do not manufacture an earlier admission or reopen solely for a new clock.
- If B is chosen, provide truthful help and preserve independently authorized staff work. Do not imply that “no fresh grant” requires deleting the request, rejecting the submission or losing its evidence.

## Timing and repetition remain explicit open boundaries

Selecting capability A must not silently select:

- A fresh unfinished duration or calculation/activation anchor.
- A one-time allowance, unlimited repetitions, cumulative lifetime cap or overlap/stacking policy.
- Pre-expiry extension, automatic renewal, grace, pausing or compensation for outages.
- A sender date editor, policy builder, new role, second approver or mandatory explanation field.
- Automatic notification, a reminder cadence or a new help-message workflow.
- Disposal, retention, payment/application changes or broader historical-file access.

The relevant finite timing, repetition and operational boundaries must be explicitly resolved before enabling A. Their absence is an activation gate, not implicit infinity or authority for an implementer to choose another sixty days. At the same time, this capability question should not be fractured into a founder interview about each hypothetical UI control: state the prospective completed-stage behavior now so the intended journey is coherent, then resolve genuinely separate policy choices deliberately.

Any genuine independent overall/purpose cap still binds the fresh grant. Ordinary elapsed expiry is not a security prohibition, but merely calling a restriction “ordinary” cannot remove its original real scope. Clearing a true shortening cause does not automatically restore a later old end.

## Accessibility and useful recovery

Use the existing Core Base UI/base-maia design system, not a new library or application. Essential end, state and next action belong in normal content. Keyboard, touch, screen-reader and narrow/zoomed views need the same understandable current result; no tooltip-only deadline or focus-stealing status chatter.

The Q01 return flow should support permitted paste/autofill and safe context recovery. A refreshed session is not the fresh grant. Conversely, an expired proof token must not be confused with ended source permission. [Accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html), [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

WCAG 2.2.1 is Level A; actual content-set time limits and applicable exceptions still need assessment. It does not require an unbounded grant or select a fresh duration. Reauthentication/context preservation does not revive source authority. A later chosen long business period does not prove shorter proof/session/upload timers usable. [Timing Adjustable](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html).

No actual AT, mobile, browser, source-state race, provider serving or user-comprehension test was performed. Proposed copy and steps are design hypotheses grounded in current rules and guidance, not tested success.

## Material questions for the eventual adversarial pass

1. Can only the exact authorized issuer make this fresh decision, under current tenant/source/recipient/purpose constraints, without requiring or granting unrelated body-read power?
2. Does ordinary time expiry remain distinguishable from a true current action/purpose/security restriction, an invalid proof or unknown source state?
3. Is original I/U and every adverse/history fact preserved, while one fresh semantic intent survives retries and uncertain replies?
4. Does fulfillment racing fresh approval use current source order, without qualifying a gap completion or reopening a completed request?
5. Are currently accepted/frozen members, independent intake stops and unsafe representations preserved while permitted remaining work can continue?
6. Can recipients understand that help requested, fresh decision approved, access currently available and invitation delivered are different outcomes?
7. Does the prospective completed-stage transition use genuine eligible fulfillment during the fresh episode, with Q07 caps and no new thirty-day guarantee?
8. Are finite fresh timing and repetition boundaries genuinely resolved before activation, without a hidden sixty-day default or repeat forever loophole?
9. Can the intended cohort finish without forced duplicate requests, repeated uploads, unsafe email attachments or staff promises of unowned remedies?
10. Can B provide a clear final boundary and accountable help without being caricatured as deleting evidence or refusing all legitimate source work?

These are research questions for the full review, not a completed implementation or test checklist. Parent owns the final Q13 framing and any ratification.

## Recommendation to the parent

Present A and B as a capability choice. Recommend **A**, because a specifically authorized fresh decision can preserve the context of a still-legitimate unfinished task and offers a controlled response to a known gap after ordinary expiry. Keep B strong: simpler finality and less grant administration are real benefits.

Include A's proposed prospective completion behavior explicitly, preserve the expired original episode and all actual restrictions, and state that fresh timing/repetition/notifications remain unselected. Do not claim Box, Dropbox, Tresorit or applicant platforms implement Asym's immutable history or prove this option optimal. Do not make mandatory duplicate requests the default recovery mechanism.

# Phase 29 Q26 — Default-on Request changes notices with tenant and staff control

**Disposition: Accept with required amendments.**

**Status:** Conrad selected Q26 A and fully ratified its complete required
amendment package on 2026-10-22, Asia/Bangkok, including tenant configuration of
who/how and the explicit Q26 Off rule. Q01–Q26 are ratified grooming intent.
This preserves the adopted decision and proof obligations; Q27's answer is not
inferred. No implementation, activation, provider action or formal owner/OpenSpec
publication follows.

The intended common path is small: staff request a correction, see whether the
recipient will be emailed, and commit once. The tenant has a real event-specific
configuration in the existing System Messages/Delivery Plan surface. Permission,
source truth and the platform's existing communication machinery do the hard
work underneath; the user does not manage a workflow graph.

**Strongest alternative:** use the same tenant configuration and same integrated
review control, initially off. B reduces unnoticed outward mail and makes sense
for repeated reviews or live staff assistance. It does not require a separate
composer. A wins narrowly as the selected product default because it reduces
the chance that actionable corrections remain undiscovered; its risks are
addressed by visible consequence, tenant disabling, per-action opt-out, truthful
outcomes and actual comprehension evidence. Mandatory email, arbitrary contacts,
a generic rules engine and a new digest scheduler are weaker alternatives.

**Repository conflicts resolved:** Q26 independently resolves only Q23's ordinary
review-notice reservation. Q20 retains its fresh-access scope. The added tenant
configuration follows P17's finite choices, not a new audience builder. SMS is
structurally unavailable under platform ADR-0028; tenant configuration cannot
activate it. P17's staff access-request default-off, staff 7-day material class
and financial 30-day material class are different meanings and cannot be copied.
Source guidance is not automatically a P6 in-product notification. Q24's team
does not become a staff-email cohort merely because it owns review.

**Explicit new Off amendment:** platform ADR-0026:56–61 and P17:1837–1843,1930
normally make plan edits future-only while existing intents keep their pins.
For this exact Q26 optional recipient-email step, C06 additionally makes a
published Tenant Off a current dispatch-eligibility narrowing. Order it with
the existing P6 submission linearization boundary through the qualified source/
delivery gate. It stops affected work that has not crossed that boundary, while
retaining immutable plan/content pins and unrelated notice behavior. Turning
On later cannot revive the stopped work. This is a ratified meaning-specific
owner amendment, not an assertion that every existing Delivery Plan already
has this behavior or a new generic cancellation engine.

## Ratified corrected decision

> For a genuinely new ordinary native Request changes review, initialize its
> visible optional Request recipient email choice on when the current source,
> actor, recipient, qualified message contract, effective tenant Delivery Plan
> and delivery path permit it. Staff may turn it off for that review. Show the
> permitted destination and outward consequence in the existing review, and
> preserve the chosen value through validation and safe recovery. Missing,
> legacy or ambiguous input must never be interpreted as a choice to notify.
>
> Provide a real event-specific tenant configuration through the existing
> System Messages/Delivery Plan model. The initial audience is the source-owned
> Request recipient; its optional email is enabled in the qualified system
> default and authorized tenant staff may disable it. Show what source setting
> determines the person, with the existing authorized recipient-management route
> where available. Changing that person or contact is source/identity work,
> never a notification address override. Expose only this exact contract's
> permitted content, locale, sender, reply and independently qualified named
> audience/channel choices. Do not pretend additional choices exist when the
> qualified contract declares only one audience and email. No arbitrary To/CC,
> team broadcast, new staff-notice purpose or unsupported channel is implied.
>
> Tenant configuration, per-review choice, recipient preferences and current
> source/communication authority remain separate. Apply their actual governing
> intersection: a staff choice cannot override Tenant Off, protected required
> steps, suppression or access restrictions. Label the per-review control for
> the step it affects; it does not silently disable other independently
> authorized plan effects. Tenant publication uses the existing complete-plan
> review, not per-step shadow settings. Widening applies only to future eligible
> occurrences. As an explicit Q26 exception to general future-only plan edits,
> Tenant Off also stops this step's affected work before P6 submission admission,
> without changing its recorded plan or content. Later On cannot revive it;
> work already admitted for submission may be in flight and is not recallable.
>
> Persist the source review, safe current guidance, exact reviewed intent and
> required durable handoff coherently. Replay recovers the same review and
> complete communication occurrence, including a proved zero-member result;
> it cannot acquire new mail or recipients after defaults or configuration
> change. A later legitimate review after correction is a distinct occurrence.
> Keep committed review truth separate from requested, suppressed, queued,
> accepted, delivered and uncertain notice outcomes. A later mail failure must
> not erase the review or require another Request changes action.
>
> Re-prove source applicability, recipient/destination, suppression, protected
> action and delivery authority at the governing preparation, submission and
> use boundaries. Use only minimal approved content and the existing protected
> doorway. No stale upload instruction, fabricated account, raw staff-note
> email, file attachment, new grant or access-clock reset follows. Lawful review
> after recipient expiry remains possible; only an exact qualified useful
> notice/help variant may survive that change. Reuse P6/P17 recovery, privacy,
> history and operations. Add no notification engine, general composer, digest,
> reminder or routine extra approval.

## Ownership, invariants and lifecycle

Authoritative facts stay with their existing owners: the request source owns
review/evidence basis, safe participant guidance, explicit per-review choice,
recipient revision and purpose/action fences; P12/identity/contact owners prove
current authority; P17 owns registered meaning, approved facts/content, complete
plan and publication; P6 owns exact communication occurrence/member/submission
and provider evidence. Provider evidence belongs to the provider's exact attempt,
not the review. Tasks, history UI, source guidance UI and notification UI are
purpose-specific projections. A common email address never merges persons.

Cardinality is the source's exact admitted Request recipient, not whoever can
receive forwarded mail. One source review occurrence has one exactly replayable
whole-plan result with a finite complete member set or proved zero. The first
optional email step must not manufacture an all-team audience. Each later
genuine review is distinguishable from replay even if bytes or outcome match.

| State or boundary                                   | Required behavior and forbidden shortcut                                                                                                                         |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Draft review with eligible default                  | Show selected optional email and truthful consequence; no send on toggle, render or preview.                                                                     |
| Tenant email Off                                    | Explain effective tenant policy. A reviewer cannot silently enable it through a local checkbox. Source review-only remains available where lawful.               |
| Staff chooses Off                                   | Preserve false for this exact intended action. Do not call it globally muted or copy false into unrelated future actions.                                        |
| Required current proof unavailable                  | Preserve permitted work, explain actual uncertainty and offer capable recovery; no guessed true/zero/recipient. Do not pretend an uncommitted outcome succeeded. |

### What could go wrong with this answer?

Default-on mail may still surprise staff or create noise. Tenant configuration
could be mistaken for permission to choose anybody. The permanent answer is a
conspicuous exact consequence and bounded source-owned configuration, supported
by real comprehension evidence—not a broad notification engine.

### What hidden assumptions are we making?

That a useful qualified source recipient/contact and action/help path can be
established, and that action-needed email benefits actual users. Those are
explicit native qualification and intended-user tests, not facts inferred from
vendor manuals. A team responsible for review is not assumed to need a copy.

### How does this affect the whole product?

It adds one governed native source purpose and its bounded tenant configuration,
consuming P6/P17 instead of creating another sender. It preserves recipient,
review, source fulfillment, source access and communication truth separately.
No financial, public CMS, giving checkout or broader account policy changes.

### How does this affect the end-user experience?

Staff perform one clear review action. Tenants choose supported delivery policy
once, recipients find current safe instructions, and failures have honest
recovery. Roles retain different appropriate depth. No compulsory new account,
private roster display, unnecessary setup screen or fresh access is introduced.

### Does this follow modern best practices?

It follows bounded configuration, actionable feedback, progressive disclosure,
server authorization and durable communication ownership. Preselection remains
a deliberate deviation from GOV.UK's general advice; the selected default must
earn its place through actual composed-user proof. External general-purpose
automation and group-mail practices that conflict with Core are rejected.

### Does this fit Asym's existing repo and product direction?

Yes, with C01–C10: current platform priorities, P17 fixed plans, P6 one spine,
Q01 private recipient and Q21–Q25 source review all remain. Native capabilities
still require explicit adoption rather than being assumed from finance code.
No new glossary term is needed; preserve all twenty definitions unchanged.

### Should we adjust the recommendation?

Keep A, with explicit tenant configuration and exact constraints. Do not replace
it with mandatory email or arbitrary audience choice. Do not quietly regress to
B merely because channel readiness is unknown: preserve the actual state and
the reviewed choice while offering lawful review-only behavior.

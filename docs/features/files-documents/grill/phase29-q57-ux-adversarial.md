## Recommendation and the strongest simpler alternative

Keep A. A useful report is one short observation bound to the resource the reader actually encountered, with a durable receipt, capable curator handling and a truthful result on a lawful return. It must not become a public comment, ordinary Support conversation, resource-authoring right, correctness vote or new automatic notification. Keep the normal resource Open/Download and Help journeys quiet and usable independently.

Recommend a three-state source lifecycle: **Pending, Handled, Withdrawn**. Report received is the admission receipt, not a fourth handling state or evidence a person read it. The reader may correct or withdraw their own pending report; an accidental ordinary withdrawal has a persistent qualified Restore action. Current authorized curators can mark a report handled, correct the audience-safe outcome or reopen mistaken handling without being the original publisher/handler. No assignment claim, In progress status, reply thread, status designer, SLA, reminder or additional approver is needed. These are proposed bounded capabilities, not powers inherited from another phase.

One practical return path is essential. Recommend **Your reports within Resources**, a bounded projection of only the current reader's permitted reports, alongside a contextual Your report entry at the resource. This is not a global inbox, task feed, unread counter or new app. A toast/bookmark alone cannot support a person returning on a phone later, especially when the resource was withdrawn. Where resource metadata is now forbidden but the report remains independently disclosable, show the allowed report data with a neutral resource-unavailable label. If report permission also ended, show no protected report details. This source-local return projection is an explicit amendment proposal; do not disguise it as already implemented.

The strongest B remains a capable existing contextual Help/coordination process. It is attractive when concerns are rare, typically require discussion, or an existing qualified team already handles them well. A introduces private text, report ownership, concurrent actions and repair obligations; it is not free. We have no observed Asym frequency, staff capacity, response-time, abandonment, cost or time-saving measurements. Recommend A for direct context and accountable maintenance, not because documentation proves universal superiority. Actual reporting and curator tasks must be tested with intended users before activation.

## The smallest complete UI

**Placement.** Keep Report a problem as a secondary textual action in the actual resource's information/actions, including the source information shown before following a qualified external destination. Do not require a PDF overlay or fetch the full file to reveal it. A reader returning from a separate external viewer uses the retained safe Resources context; no browser-history scraping, external page reading or remote snapshot is implied. Report can work when body/download fails if current reporting authority and safe metadata still identify the intended publication. Unknown authority is not a technical download failure.

**Compose.** A compact existing shared form/panel is enough: permitted resource context; label **What is wrong with this resource?**; hint **For example, a broken link or an instruction that is out of date**; one plain-text field; **Send report** and **Cancel**. Explain the true audience, for example **Your report and identity are visible to the people authorized to maintain this resource**, only where that disclosure is actually admitted. Do not promise anonymity. A brief hint such as **Do not include private details about other people** helps purpose clarity but is not a sanitizer or warning ritual. Trusted identity comes from the current source context, not re-entered email. No mandatory category/title/screenshot/reason essay, rich editor, AI quality score, acknowledgment checkbox or extra confirmation.

**Submit and return.** While the request is in flight use **Sending report…**, not Sent. After coherent source admission: **Report received** with **View your report** and the ordinary resource/list return. The persisted record is Pending; it is not a human read receipt. On an unknown result: **We could not confirm whether your report was received. Check status before trying again.** Check status recovers the original operation under current scope. A known success survives a failed later refresh. A genuine pre-admission failure can say **Your report was not received. Try again.** Do not invent that certainty after timeout.

**Own record.** The resource's contextual Your report link and Resources' minimal Your reports view return to the same source record. Show current permitted report text, submitted time, a clear state and allowed handling outcome; distinguish old observed publication from current resource. Do not display a currently prohibited resource title just because it was previously received. No other-reader list, report-popularity count, curator directory, private notes or continuous resource access follows from the receipt. Unknown/denied output is not No reports or blank saved text. The own-record view persists after refresh under actual authority; it need not promise offline access.

**Pending correction.** **Edit report** uses the existing field and explicit **Save changes**. It edits the report description through an attributed current revision; it cannot switch resource/publication, reporter or original submission time. Unchanged canonical input is a no-op after original-result reconciliation. **Withdraw report** stops ordinary pending handling; it does not delete required source history, recall what people saw or withdraw the resource. Show its meaning with the action; do not require another routine confirmation or reason essay. The resulting record offers a persistent **Restore report** where current restoration rights and lawful retained current text/context permit it. Restore is a new state revision, not history rollback or revival of a privacy restriction.

**Curator handling.** Existing resource management exposes a bounded Pending reports view and direct report detail, only to the actual authorized handling audience. Any currently qualified handler may act; original authorship/publisher status or being first to open the report is not an exclusive ownership rule. Read the current report revision, investigate using actual content permissions, and choose **Mark handled**. Recommend one concise field **Outcome for the reporter**, clearly labeled **Visible to the reporter when they have access to this report**. A sentence can suffice. Do not prefill Fixed or require a hidden internal essay. A truthful outcome can explain an update, no change needed, an already addressed issue or a completed lawful handoff; it must not claim a fix merely because work was sent elsewhere. A meaningful complete disposition is required, not a classifier or mandatory review of every resource byte.

**Handling correction.** **Edit outcome** corrects the current handled outcome under current handling/disclosure rights, preserving attribution. **Reopen report** corrects a mistaken Handled state and returns it to Pending, while the earlier handling remains historical rather than presented as current. These are available to qualified current handlers, not just the original handler; no new approval queue. A reader with new information after genuine handling can submit a new deliberate report about the currently qualified target. This does not reopen the old report automatically, create a conversation or erase the outcome previously made. If that old target is no longer reportable, show actual safe context and a capable lawful alternative rather than copying hidden material into a new report.

**Privacy correction.** Sensitive input/outcome needs an actual scoped operator route to restrict current disclosure and apply the owner's lawful correction/disposition policy. Ordinary Edit, Withdraw or Reopen is not guaranteed erasure. A privacy-restricted body cannot be restored by the ordinary state controls. Staff cannot impersonate the reporter or silently rewrite their original claim. Curators can preserve a necessary safe handling fact without retaining or exposing forbidden original text. Retention/holds and redaction still need the actual owner contract; no universal retention duration is invented.

**Changed publication.** A report remains about its actual observed publication/reference. A new version or Q55 review does not automatically handle it. Independent current report authority may support own-record access, pending correction/withdrawal and continued curator handling even when the original resource is withdrawn; it never revives its title/body/bytes. New report creation must qualify its actual target. If the context changes before Send, show the change and revalidate safely without silently moving the claim. The proposed report authority must expressly support these continuing maintenance paths, not infer them from past readership.

## Adversarial check

### What could go wrong with this answer?

Reports can become an ignored complaint sink or leak more sensitive text than the resource itself. A reader may mistake Handled for Fixed, or Edit/Restore may revive an old claim after staff acted. Require coherent capable intake, current scoped records, precise revision races, truthful outcome and actual privacy/source recovery.

### What hidden assumptions are we making?

We assume a reader can notice a useful resource issue and that a capable current curator/source route can assess it. Frequency, response capacity and benefit are unmeasured. Neither a curator's existence nor a polished form proves reliable handling. No reply/SLA/daily-check habit is inferred.

### How does this affect the whole product?

It adds one bounded P28 producer/lifecycle. Publication, Q55 review, P12 access, P29 custody and existing Help keep their owners. It does not broaden all-staff resource readership or borrow Q45/Q51 comments/attention, Q48 reminders, a public feedback form or a generic support pipeline.

### How does this affect the end-user experience?

The reader makes one short contextual submission, can repair an ordinary pending mistake and can later find the allowed result. The curator sees actual pending source work and handles the current report without ownership ceremony. Clear return, failure and privacy paths matter more than more statuses or auto-email.

### Does this follow modern best practices?

Current primary products document contextual feedback and owned handling; they also reveal irreversible closure, subscriptions and unassigned destinations to avoid. W3C supports predictable input, meaningful labels/status and error recovery. This is evidence-informed product judgment, not universal consensus or a passed Core accessibility test.

### Does this fit Asym's existing repo and product direction?

Yes only with explicit P28 source adoption, current P12 decisions and shared Base UI/base-maia reuse. The source-local report views are small record projections, not a second inbox/platform. Existing demo Support Knowledge and native ticket APIs do not prove the missionary report/curator route is qualified.

### Should we adjust the recommendation?

Keep selected A with the complete bounded lifecycle and persistent own-record return. Preserve B's actual capable Help alternative. Do not import a status/assignment/chat/notification engine. Bring the explicit Restore, outcome correction and report-specific continuing-authority amendments into the parent package for review, rather than implying they were already authorized by the initial button choice.

## Required amendments and attack outcomes

These are concrete consequences of A and inherited contracts. Severity/likelihood below describes a failure if implemented without the boundary, not a newly demonstrated production vulnerability. High likelihood means a routine implementation shortcut; medium means a plausible race or privileged path. No measured incident frequency is claimed.

### RT01 — Both readable inputs do not automatically authorize the composition

**High impact / medium likelihood.** An actor may have access to two items through different purposes or histories while the source does not permit this relationship or paired-review context. A current file entitlement also does not grant the predecessor's metadata or content. A successful earlier open must not preserve a denied comparison relationship.

Require current source permission to discover/select each exact occurrence and version, inspect its metadata/representation, and use the source-defined pair relationship/purpose. Derive actor/tenant on the server. An opaque ID, equal digest/name, client pair descriptor or staff role is never authority. Reauthorize at generation admission, source fetch, Ready promotion, and every subsequent full/range/conditional representation read. Cache hits and HTTP 304 handling cannot skip that check. A combined endpoint must validate the combination before releasing its envelope; A need not create such an endpoint.

If the relationship/purpose stops being permitted, end the composed pair even when each file can be read elsewhere. Any standalone continuation must pass fresh authorization in an actual allowed source context; it cannot manufacture a fallback purpose. If only one pane becomes unavailable, keep a still-permitted pane only where the continuing source context allows it. Do not disclose a denied filename, existence, page count, search result, thumbnail or error detail through the other pane. Current restrictions dominate technical Ready. Already delivered knowledge cannot be remotely recalled.

Evidence: D32 data contract `:11–21,25–31,74–80,98`; Q29 question `:112–121`; current route/adapter boundaries above. Later proof: deny each input separately, deny the relationship only, change tenant/role/purpose during reads, and confirm discovery, metadata, range/conditional responses and privileged handlers all enforce the same decision.

### RT02 — RLS and private storage must close every reachable path

**High impact / high likelihood if the metadata seam is copied.** Adding a source-aware API while leaving direct table reads, permissive policies, client-editable authority fields, views, RPCs or raw object URLs exposed leaves an alternate route around it.

At implementation, inspect actual grants and all applicable SELECT/USING/WITH CHECK policy combinations, composite tenant/source/version references, immutable fields, view invoker/definer behavior, RPC EXECUTE grants and fixed search paths, plus service-role handler checks. Generations, profiles, owner/restriction/result fields, promotion, audit and custody remain server-command owned. An authorized row must not be patched into a different source/version/tenant. Use genuine SQL/RLS/storage negative tests with relevant roles, not only route mocks. Existing broadly staff-scoped attachment RLS is not evidence for these narrower rights.

Protected originals/renditions use the source-authorized private gateway with no-store delivery and safe content headers. No public `email-assets`, raw provider URL, reusable signed URL, public CDN cache, iframe external viewer or automatic original download is a fallback. The isolated reader must have no application credential/DOM access, with a narrowly validated source-bound bridge only as needed. No new browser storage lifecycle mutation is introduced.

Evidence: current SQL/adapter/email storage anchors above; D32 data contract `:29–33,76–80,98`; P20/P30/P35. This amendment does not claim current hosted policy state or require a new table by default.

### RT03 — Stable exact inputs and exact displayed representations

**High impact / high likelihood.** A pane keyed by a filename, array position, moving `latest` reference or byte digest alone can silently display the wrong occurrence, projection, restriction generation or profile. A new correction may change the current review target without changing what staff intended to inspect.

The pair carries an ordered selection of exact source occurrences/immutable byte versions and their truthful source roles. Each pane binds its exact eligible representation generation, profile revision/options, digest and coverage. Orientation and a user-controlled pane swap change presentation only; they do not make an older pane current, establish ancestry, choose Q21's review target or reverse Q03 correction meaning. Source owner lineage supplies earlier/later/candidate labels, including unrelated or unavailable relationships; timestamps cannot invent it.

The shared generation reuse key is per authorized source occurrence + exact byte version + restriction generation + profile/options, with tenant separation. Do not key generation work by the entire pair: `(A,B)` and `(A,C)` should reuse eligible A work without sharing access. A pair identity for UI request coordination is not a durable product record, permission grant or combined rendition. An old eligible rendition cannot silently acquire a new renderer/profile or CSV delimiter. Deliberate projection changes update pane identity and disclose coverage; page/row position never proves correspondence. Same bytes do not erase provenance or authorize cross-tenant/source reuse.

Evidence: D32 data contract `:11–21,39–43,47–51,94–100`; Q29 question `:54–59,117–127`. Later proof: same names/digests under different owners, reversed panes, `(A,B)/(A,C)`, profile/delimiter changes, source correction while both versions remain historically readable, and stale callbacks for old selections.

### RT04 — Async invalidation must cover both panes and every derived fragment

**High impact / high likelihood.** Aborting a request alone does not stop a completed response, parser worker message, cached page, thumbnail, find result or prior session state from repopulating a newer view. A changed tenant can reuse local identifiers; an unchanged file can have a changed authorization context.

Use an effective request/selection epoch that distinguishes actor/session, tenant, source context and purpose, ordered pair selection, pane's exact version/representation/profile/options, and current restriction state. This is logical identity, not a mandated global token service. Apply it when accepting every async result, including range/page loads, find, images, workers and readiness events. Cancellation saves work; matching the current epoch before rendering is the correctness check.

On restriction, context switch, logout, loss of pair permission, reconnect/visibility revalidation or selection change, stop affected reads and clear relevant displayed/cached content, object URLs, search fragments and worker state. Preserve permitted non-content navigation/notes under their existing owner; do not preserve restricted snippets merely to keep a reading position. Back/forward and remount must not restore protected content from an obsolete epoch. Clear or partition local caches across sessions/tenants, keep protected responses no-store and avoid persistent content caches. Reading positions belong to the exact pane identity and cannot be applied to a new version as if unchanged.

Evidence: D32 `:30–31,78–80,98`; P21/P29/P34; adjacent query/helper anchors above. These are required Q29 behaviors, not claims that the adjacent message hook is itself a proven vulnerability.

### RT05 — Partial success is usable reading, not a successful complete pair

**Medium-to-high impact / high likelihood.** A blank failed pane can resemble an empty source, and a global success flag can conceal one unsupported, expired, blocked or partial representation. A global retry can duplicate a healthy generation or silently select newer evidence.

Keep each pane's identity, availability, loading/failure/limited coverage and search completeness explicit. One successful pane is not evidence that both were inspected. Missing content is not deletion; no matches requires completed search of that pane's declared represented scope. Do not produce Changed/Unchanged, same-content or review-complete status from A. Differing profiles/coverage must not imply omitted content is equal or absent. Retry only eligible failed work while preserving exact inputs and the other pane's permitted reading state. Do not replace either input automatically.

If current source review permits acceptance through independently sufficient qualified inspection or another authorized path, paired-reader failure does not impose a new business rejection or mandatory compare ritual. Conversely, partial paired viewing cannot bypass Q21's actual inspection requirement. Source guards, not pane focus/open telemetry, determine the current acceptance action.

Evidence: D32 `:37–51,94–96`; Q29 question `:38–71,107–127`. Proof must include absent bytes, blocked/unsupported/expired one side, queued cold plus warm side, both failures, later-page search interruption, and Q03/Q21 correction/acceptance races.

### RT06 — Coalescing, cancellation, retry and expiry retain their original owners

**High impact / medium likelihood.** Two panes or several users can share a generation. Treating one viewer's close as permission to cancel/delete it harms other readers; treating an active pane, lease or refcount as retention authority leaks data indefinitely. Reopening a pair can also accidentally evade the attempt budget.

Concurrent eligible opens coalesce at most one live generation per existing semantic input key. Each reader retains independent authorization. Pair close stops its own view requests/subscriptions and releases only its own ephemeral resources; it does not delete original/shared Ready bytes, cancel a shared job indiscriminately or rewrite another caller's receipt. A cancellation optimization must preserve other authorized consumers and all custody/recovery rules. No refcount, active tab, access lease or cache hit extends source/Ready/scratch deadlines. Persistent-reference deletion remains the existing qualified per-owner model; no new pair reference owner is introduced merely for viewing.

Distinguish successful Ready expiry from failed-budget exhaustion. After an eligible Ready generation expires, a new deliberate authorized open may admit a new technical generation under the same stable input key; old generation/receipts/deadlines remain immutable and concurrent opens coalesce. By contrast, timeout, lease expiry, reconnect, pair rearrangement, repeated opens or two exhausted attempts do not permit unlimited new automatic generations. Classify failures, reconcile/fence prior work before retry, allow a second parser attempt only for a transient failure, and require deliberate audited operator recovery after cause correction for exhausted work. A changed profile must be an actually approved new profile lineage, not a manufactured retry bypass.

Evidence: D32 `:19,29,39–43,66–82,100,106`; actual work-claim/ledger seams above. P22/P31/P33 remain required. The shared work-claim TTL is an attempt coordination mechanism, not proof that the old process stopped or that its output can be promoted.

### RT07 — Promotion versus cleanup still needs one winner

**High impact / medium likelihood.** A timed-out worker can finish after a new claim, source restriction, deletion claim or expiry. A successful upload or a callback can falsely make output Ready, while a stale tentative sweeper can delete content already transferred to Ready custody.

Use pre-I/O staging inventory and immutable per-generation object identity; reconcile uncertain writes by that identity. Validate current source/purpose/restriction, exact bytes/profile/options, attempt/claim, digest, coverage and limits at conditional Ready promotion. Promotion and cleanup claim the same custody transition with one winner: deletion-claimed output cannot promote, and old tentative cleanup cannot delete promoted bytes. Late output is cleanup-only when stale; retries never reuse a deleted object's key. Ready has its own source-bounded fixed expiry. One pane's expired rendition can be deliberately regenerated if the source remains eligible, but another live pane cannot refresh its deadline or mask its invalidity. A hold preserves only owner-required restricted custody, never ordinary reader access.

Evidence: D32 `:19,27–31,39–43,69–82,100`; P21/P22/P31/P32/P36. Existing generic claims/dispatch are useful implementation seams, not proof that these private-preview transitions already exist.

### RT08 — Pair resource budgets are composed, not copied or guessed

Per-file conformance alone does not qualify that composition; rejecting every previously valid maximum input by dividing its ceiling in half would silently narrow D32.

Retain D32's exact per-file/per-attempt/per-generation limits below. Declare and measure finite aggregate pair scheduling, queues, concurrency, decoded browser working sets, network/request/output buffering, search/render work and tenant fairness for the actual implementation. Do not invent a numeric pair cap here or silently authorize twice a single-file resource allocation. Count shared generation work once in actual capacity accounting while preserving each request's authorization; do not multiply jobs for two panes, prefetch all history, or do expensive conversion in list rows, keystrokes or database locks.

Under pressure, queue/serialize/defer a pane or use the deliberate single-pane presentation with truthful loading/availability. Do not truncate a valid file into a fake complete preview, lower D32's supported profile without an explicit decision, or claim the old healthy-load targets already measure paired readiness. Qualification must establish useful paired inspection under declared capacity, with bounded maximal/overload behavior and preserved independent controls. No exact new pair latency promise follows from A.

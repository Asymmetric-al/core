# Phase 29 Q08 — a clear, deliberate fresh-read-access journey

Researched 20 October 2026, Asia/Bangkok. The parent reports Conrad selected **Q08 A: specifically authorized staff can approve fresh, scoped, finite read access after ordinary completed-request expiry**. Q01–Q07 and their amendments remain ratified. This note proposes Q08 UX and authorization refinements for review; it does not ratify them, implement the feature or select its new duration, repeat limits or notifications.

Evidence is current public primary documentation plus bounded read-only inspection of Core at local commit `3d85897ebf1515008ef5c676b1c58a15422fb9ab`. No recipient account, private row/file, authenticated comparator workflow, actual permission command, message, browser/assistive-technology journey or participant test was exercised. No product/dependency/provider change was made.

## Recommended experience

Keep one source context and one deliberate authorization action:

1. The recipient reaches the already-qualified neutral ended/help state and uses the existing real source help route.
2. Authorized staff review the intended recipient, request purpose, exact eligible prior scope, permitted actions and concrete finite end together in the existing source workspace.
3. Staff deliberately choose **Grant new read access**. The server commits or rejects that exact current proposal; uncertainty is reconciled without issuing another grant.
4. The recipient uses Q01's qualified entry to the same completed request and sees only the current new scope and actual end. The old grant stays ended and submission/correction remains closed.

Do not add a second identical confirmation dialog, new applicant account, new queue, file-by-file manual ritual, arbitrary recipient picker, required justification essay, default second approver or a policy builder. This is a permission-changing act, so a clear contextual review and an intentional action are useful; a multi-page ceremony is not established by the evidence.

The source must still know why the purpose is currently permitted and record its decision. Reusing governed request/help evidence is preferable to demanding that staff duplicate it in a new text field. Any additional approval or stronger assurance must come from the actual source policy, not this generic UX recommendation.

## Exactly what staff should review

Use the existing request identity and purpose as context. The review should contain:

- **Recipient:** the source-bound intended recipient and enough permitted identity context to distinguish them. This is a confirmation of the established target, not a free-text new email or person search. A different recipient belongs to another source-controlled decision.
- **Request and current purpose:** the already-completed work and the basis for allowing this new read act. Reuse existing governed help/case evidence; do not require a duplicated essay by default.
- **Exact permitted material and actions:** a readable summary of eligible own current members within the previously admitted scope, and what preview/original-download actions are actually allowed. Use bounded progressive detail when there are many members; no implicit “everything in this folder” or hidden record inheritance.
- **Actual new finite boundary:** what the resolved fresh-access policy will permit. No “another 30 days,” arbitrary date picker or live countdown is chosen. The capability cannot activate with placeholder or unresolved time/repeat policy.

“Previously admitted” refers to the historical permission scope, not proof that the recipient actually viewed or downloaded a file. Requiring prior download telemetry would incorrectly exclude a recipient who never had an opportunity to use valid access. Conversely, a filename in a staff list or retained storage is not proof it belonged to the prior recipient scope.

Staff do not need to open every file to authorize a known source-governed scope. Do not force unnecessary viewing of sensitive content or make an optional renderer outage block a decision that can otherwise be safely evaluated. The source still qualifies each representation; neither a review card nor a future end makes an unsafe original downloadable.

A material change to recipient, item membership, actions, end, policy or source restrictions after review must not silently expand, retarget, substitute or misrepresent the resulting grant. Refresh the relevant proposal and require deliberate review of the changed scope. The command may not claim the reviewed whole scope succeeded when only an uncommunicated subset was granted. The exact owner contract must define any partial-result behavior; this note does not silently choose it.

## Deliberate action and truthful result

Opening the review is a read. Clicking **Grant new read access** expresses a specific issuance intent. The UI should retain an accessible pending state and prevent accidental repeat clicks, while the server remains responsible for the stable command identity and current authorization. A disabled button is not an idempotency guarantee.

Keep these facts separate:

1. **The command was committed** — one new source decision exists.
2. **The grant is currently usable** — current recipient/purpose/permission and finite end still allow it.
3. **A file representation is available** — its independent safety/custody/render rules allow that action.
4. **A message was delivered** — only when a separately authorized communication actually succeeded.
5. **The recipient saw or saved a file** — not established by granting, sending a message, clicking or emitting bytes.

A grant can have committed just before a newer restriction makes it unusable. Preserve that source fact and show a current permitted state; do not claim “no access was granted” merely because the current view is denied. A lost response can make the outcome unknown. Resolve the same command through its owned recovery path before retrying an issuance; do not mint a second grant to obtain a clean UI response.

Closing a review **before** issuance can abandon the local proposal without effect. Closing, navigating away or losing connectivity **after** dispatch does not establish cancellation. Do not label a close button “Cancel grant” unless an actual separately authorized cancellation/revocation command exists and its outcome is known. An “Undo” cannot promise recall of information already delivered.

## Accessibility and mobile behavior

Prefer a compact section in the existing source workspace or one shared dialog if that fits the real surface; this research does not mandate an overlay. If a dialog is used, give it a meaningful title/description, keep long scope detail scrollable within the viewport and verify focus entry/containment/return. Do not trap a user behind a spinner or let focus disappear when permission loss removes a control.

Use meaningful action names, normal click/keyboard activation and existing touch targets. The permitted scope and end must be readable on small screens, at zoom and in RTL/long-name layouts. They must not depend on hover, status color or an icon. Avoid per-file checkbox labor when source policy already defines a coherent exact scope; equally, do not hide an unexpectedly broad selection in a generic count.

Keep pending and unknown results distinct and programmatically understandable. Status should persist in the source context beyond a transient toast. Avoid duplicate assertive announcements when a dialog/context change already communicates the result; manual AT testing must determine the appropriate feedback.

Keep valid same-process context when correcting actual input errors. Refresh or clear stale/unauthorized facts rather than auto-filling them forever. Q01 supported authentication assistance and Q06/Q07 timing distinctions remain in force. A proposed finite access period does not prove every session/proof or review timer accessible, and no new review-time timeout is invented here.

On poor connections, do not fetch every original/preview simply to review permission. Result reconciliation must not require resubmitting the same grant as a new act. A shared-device sign-out should invalidate current app authority through the existing mechanism without claiming removal of locally saved files.

These are future acceptance outcomes, not evidence that any screen has been tested or that Base UI automatically qualifies the complete workflow.

## Proof outcomes for later implementation

These are proposed proof requirements, not tests executed in this review:

1. Staff with read permission but no issue permission cannot create a grant by UI, direct command, stale form or service-path misuse.
2. Issuer authority lost before commit yields no issuance; authority lost after a confirmed commit preserves history but prevents unauthorized result disclosure. Unknown ordering is reconciled.
3. Material review-to-submit changes in recipient, scope, member currentness, action eligibility, policy or end cannot grant a silently different proposal.
4. Similar names, changed/shared email addresses, recipient reassignment and other tenant/request contexts cannot retarget this action.
5. Previously admitted current members remain distinct from superseded, newly added, disposed, unsafe or independently held content. Lack of a prior download event does not itself disqualify an otherwise valid historical scope.
6. Multiple clicks, retries, reloads and lost responses converge on one issuance effect without changing its end or consuming another repeat allowance.
7. Pending, confirmed-not-committed, committed, currently-restricted and outcome-unknown states yield truthful staff feedback. No false sent/read/saved outcome is inferred.
8. Closing before issuance has no source effect; closing after dispatch does not falsely report cancellation. Reopening the source context reconciles the exact result under current authority.
9. Entry/session expiry with still-valid fresh authority uses Q01 recovery without another grant. Fresh-grant expiry and hard source restriction do not.
10. Neutral ended/help states do not leak request existence or private metadata to an old/forwarded/unauthorized link. Approved current entry reaches only the exact permitted completed view.
11. Actual keyboard, speech, screen-reader, touch, zoom/reflow, long/RTL names and low-bandwidth review/result/re-entry journeys work without hover-only instructions or focus loss.
12. Existing source help has a real responsible actor and can explain the permitted outcome; a recipient help action does not approve access or send an unselected message.
13. Exact newly resolved finite policy and repeat constraints are enforced once selected, with no automatic reuse of Q07's 30 days or silent broadening after a policy change.
14. Representative staff and recipients can distinguish granting access, sending a link, signing in, reading a file and ending access. Document sample limits and unresolved comprehension issues; do not claim satisfaction or workload improvements from desk research.

## Remaining boundaries

The selected capability still needs its actual finite period/anchor, repetition/cumulative constraints, exact issuance delegation and compatible source policy resolved before activation. Notification behavior remains unselected. This review adds no numerical default, second permission engine, staff override, new help queue or source-independent authority.

No source-specific outcome should be optimized by weakening the recipient boundary. A safe, genuinely useful short interaction is possible with the existing primitives, but only after the backend permission/effect contract and the complete real-role/browser journey are qualified. Current documentation and source inspection demonstrate available concepts and controls, not a working grant flow.

## Recommended single decision

**Once every actual current requirement of an ordinary native document request is satisfied, should the source record the request as fulfilled without a second staff completion click, or should staff make a separate final completion decision?**

Recommend **A — source fulfillment without a redundant final click**, bounded to the ordinary native cohort and its fully qualified current predicate. Q21 already requires meaningful deliberate staff acceptance for file-evidence items. If every required review and other real source condition has been satisfied, an additional Complete request click should have a distinct purpose to justify another unresolved work state.

This is **product judgment, not a universal industry rule or measured Asym efficiency finding**. Direct document-collection comparators provide strong evidence for a separate manual completion action. A must not be sold as “how all modern tools work.” Its case is that this particular native request has already captured the meaningful decisions, while its source can reliably record fulfillment from them. Where a source requires genuine aggregate reconciliation or another decision, that remains an actual unsatisfied condition rather than being skipped by A.

## Consequences that must be visible in either option

### Fulfillment is a source effect, not a label

For A, “automatic” means the owning source evaluates and records qualified fulfillment when all actual current prerequisites hold. It does not mean browser arithmetic, a scanner callback, an item acceptance count or a workflow projection declares success. Staff decisions retain their exact provenance; a source-owned fulfillment effect retains its own basis and attribution. The last staff reviewer need not be falsely recorded as having personally made a broader final judgment.

The last satisfying change might be a valid item acceptance, an already-authorized non-file outcome or another actual source condition. It is not necessarily a last file upload. Missing or unknown required conditions cannot be treated as satisfied. No-required-file or existing waived/not-required cases retain their owner semantics; this question does not choose a naive empty-list-is-complete rule or invent a new waiver.

For B, readiness is not fulfillment. The final action must represent a real qualified source decision, not a global override of missing evidence, stale acceptance or adverse conditions. One final staff action need not mean another person, a mandatory essay, a new routing queue or several confirmation dialogs. Its actor/responsibility and review scope would need exact owner binding before activation.

### Closure and access are real consequences

Under the inherited decisions, normal fulfillment closes ordinary request submission/correction and may admit the bounded read-only completed view when historical eligibility permits. It does not close unrelated work, delete files or make the wider application accepted. The UI must make that ordinary request consequence understandable before an action that can finish the request, without adding a new mandatory confirmation ceremony.

Q03 already makes an accepted item ineligible for ordinary recipient correction. **B's extra completion wait does not reopen accepted items or give a general extra correction window.** At most, unaccepted work still eligible under the actual source can remain correctable while the request remains unfinished. A can close such remaining optional/pending work when the real full source predicate permits fulfillment; it must not silently accept, discard or relabel that work. Which pending/optional conditions legitimately block fulfillment must come from the source, not from an invented “every stored file must be accepted” rule.

The completed-view clock is anchored to the actual qualified fulfillment occurrence. With A, that may follow the final satisfying source operation; with B, it waits for the actual final completion decision. Either can produce less remaining unfinished work time or a different completed-access end than a user expects. Explain the actual transition and resolved end. Do not promise a fresh full 30 days through genuine earlier limits or restrictions, or extend access merely because staff delay continues.

If the source records a valid timely occurrence and a downstream observer is late, Q10 allows qualified recovery of that occurrence. If the source only later completes the request after access expiry, do not backdate completion to the earlier accepted item or “ready” time to manufacture recipient eligibility. This question chooses no new timestamp-reconstruction rule, delayed-grace period or recovery permission.

### Whole-request review can be real, but it must be named

B is strongest where independently acceptable parts can still fail a cross-item purpose: a meaningful final reconciler checks whether the overall evidence meets the request as a whole or whether another required decision is ready. This is an illustrative possibility, not a discovered ministry workflow. If such a judgment is required, A cannot erase it by saying every item is accepted. The source must represent and enforce that genuine remaining condition; it does not have to appear as an arbitrary generic Complete button.

Conversely, if the final step checks nothing that has not already been decided, B creates a possible forgotten administrative tail. That is a reasoned usability cost, not a measured error frequency. Do not build a new final-review framework just because another product has a manual action. Choose B if Conrad wants deliberate final closure to be a real ordinary product decision, and explain its additional responsibility honestly.

For A, an existing review summary can state: **When all requirements are satisfied, this request completes automatically.** This is proposed product copy, not a claim that the last visible item is certainly the last source condition. Do not mark the participant overdue merely because the final reviewer has not acted, or require a recipient to submit again to refresh the staff queue.

## Recommended founder framing and boundary

**When all current requirements of an ordinary document request are satisfied, should Asym complete it automatically, or should staff make one final completion decision?**

- **A — Complete through the source once all conditions are satisfied (recommended).** Keep Q21's human item review, then avoid an additional completion click that only restates finished work. Show the closure/read-only-access consequence clearly.
- **B — Require one final staff completion action.** Keep a deliberate whole-request handoff after the item work, accepting an extra responsibility and possible wait. The action cannot bypass source conditions.

“Automatically” must immediately be explained as **qualified source fulfillment after all actual current conditions**, not automatic acceptance of uploads. Do not phrase A as simply “last file accepted → complete,” or B as an inherently pointless second click. The final action is useful when it represents a distinct judgment; the founder is choosing whether the ordinary native profile requires that extra decision.

The question need not bundle collection-only mode, reviewer assignment/pool, extra reviewers, negative outcome taxonomy, reopening, optional-item admission policy, bulk acceptance, new grant periods, notifications, reminders, timers, final export, public sharing, retention changes, universal CMS rules or a workflow builder. Preserve existing source-owned required behavior. Any necessary exact predicate or capability binding is a qualification obligation, not permission for a hidden second policy decision.

## Recommendation and remaining evidence limits

**Recommend A for the bounded ordinary source**, provided its full predicate contains every real requirement and it can durably record the outcome with the already-ratified concurrency and timing rules. That recommendation fits the selected deliberate item-review model and minimizes a redundant completion tail. It does not claim faster outcomes, fewer errors, lower support volume or universal nonprofit preference. B's real final-reconciliation/control benefit is supported by direct collection products and must remain explicit.

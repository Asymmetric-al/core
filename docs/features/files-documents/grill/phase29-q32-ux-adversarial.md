## Judgment, counterargument and evidence limits

A direct participant question can arrive while its qualified staff handlers
are away from the native source work. A minimal supplementary cue can help them
discover it. Default On is defensible for this distinct occurrence, but it does
not guarantee attention or repair missing staffing, poor native discoverability,
an incorrect recipient cohort or a suppressed mailbox.

**B remains the strongest alternative:** the same optional capability initially
Off avoids unnecessary mail for teams reliably operating from native work and
for high-volume exchanges containing acknowledgments. It also avoids default
external metadata exposure. Its cost is lost timely awareness if staff or the
administrator assume mail is active. **C** remains credible when native handling
is sufficient and the organization accepts having no new supplementary notice
capability. Neither alternative is technically unsophisticated. A includes real
tenant disablement rather than a compulsory channel or a new personal preference
platform.

The Q27 evidence-review Off decision is not a universal staff preference. The
Q31 participant-notice On decision does not demand symmetry. Q32 has a different
audience, occurrence and operating need. Unlike Q31's per-reply choice, Q32 is
initial tenant-plan policy: do not import a participant Notify checkbox or use
GOV.UK preselected-form-checkbox guidance as if it directly prohibited a saved
default configuration. The material issue here is discoverable, understandable
effective policy and its real operational consequences.

No Asym message volume, native-work monitoring frequency, mail-reading rate,
response time, cohort size, desired notice frequency or intended-user result
was measured. Source records and vendor defaults are not observations of ministry

## Useful UI and copy without another platform

These examples are proposed test copy, not new mandatory screens or frozen labels.

**Participant:** preserve the existing deliberate Send and the truthful
**Message received** result only after native durability/handling is established.
For an ambiguous send, **Checking whether your message was received…** is more
accurate than Failed. Do not replace a known receipt with an email error, display
**Staff notified**, add a recipient picker, or tell the participant which staff
mailbox bounced. Any existing safe expected-response/help guidance remains
source-owned and must not invent a guaranteed time.

**Tenant settings:** use a distinct title such as **Staff email for participant
questions and replies**. Show its current **On/Off** state. Describe Who as
**Staff qualified to handle this clarification through its source-owned route**,
with an authorized management link where the source supports it; How is **Email**.
A short explanation can say **Turning this off stops this supplementary email.
Questions and replies remain in their existing work route.** The actual effective
date, pending-work rule and possible in-flight limitation must match the owner
contract. Do not represent an unpublished edit as effective. The existing
publication affordance is enough; do not add a second approval wizard.

**Staff cue:** a possible minimal subject is **New message in a document request**,
with body **A participant message was received. Open the request to view the
current context.** Use a descriptive action such as **Open request** only when
the exact source still qualifies it. This avoids claiming that every reply is a
question needing another answer. Context that is sensitive under source policy
cannot be included merely to help distinguish mail in a crowded inbox.

**Staff landing:** show the correct currently permitted item and admitted message
in the existing work surface. Display actual current handling/access status,
including a source-established already-handled condition, without creating
another Resolve or read-tracking workflow. If participant reply access has ended,
do not offer a false available-response action. If staff authority has ended,
deny safely rather than reveal text, names or historical routing. A forwarded
email confers no authority.

**Authorized repair:** native Received, policy Off, no eligible delivery under
proved authority, unresolved proof, queued, provider-accepted, delivered, failed
and unknown have different meanings. Operators need these facts through existing
authorized history/repair. Participants do not need the technical state machine,
and ordinary staff should not get an interruptive notification for every provider
callback. No one should fix mail by reposting the participant's text or inventing
a new contact address.

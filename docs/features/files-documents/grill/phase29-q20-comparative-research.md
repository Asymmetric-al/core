# Phase 29 Q20 candidate — recipient handoff when fresh access is granted

Research date: **21 October 2026, Asia/Bangkok**. The parent reports Q19 and its full amendments ratified; **Q01–Q19 are the accepted baseline**. This is a proposed next question **awaiting source-owner validation**. No Q20 answer, notification permission, canonical decision or runtime behavior is selected by this note.

Only this research note was written. The founder's Phase 29 brief, grooming coverage/decision history, Q08/Q13 notification and handoff boundaries, and subsequent fresh-access choices were inspected. Public primary product documentation was refreshed. No real message, private record, provider, permission, UI, account or dependency was changed or exercised. No authenticated competitor test, native grant/dispatch test, accessibility pass or intended-user study is claimed.

## Best next product fork

**In the existing fresh-access review, should “Email the recipient about this access” start selected, or should staff explicitly select it for each new grant?**

This is more useful than another access-clock question. Q08/Q13 already require a real source-qualified entry/help/handoff route while deliberately separating and reserving notification behavior. The fresh unfinished and completed-read profiles now have meaningful scope, timing and repetition decisions. A staff-only success with no understandable recipient handoff remains an obvious journey gap. Notification is the immediate product choice that can close that gap without reopening the clocks or building another portal.

The proposed scope is **the initial notice for a newly admitted fresh unfinished or fresh completed-read period**, including later separately approved periods. It is not a blanket rule for original requests, corrections, business completion, receipt emails, revocations, reminders, digest subscriptions or future campaigns. Those events and their owners remain separate. A retry of the same grant is not a new grant notice merely because the UI was opened again.

The broader Phase 29 brief still has unresolved staff organization/search, review/version semantics, processing formats, sharing/library, disposition and custody/provider work. They remain important. This handoff decision is a useful bounded closure of the request-access journey before moving to those areas; it does not justify an indefinite series of delivery micro-questions. Exact dispatcher engineering and already-owned operational controls should be investigated rather than posed as founder choices.

## Provisional recommendation

Recommend **A — a visible email choice in the existing meaningful grant review, enabled by default where the exact source/P6/P17 notification is eligible**, with a clear grant-only alternative where source policy permits it. Confirming that combined review deliberately authorizes the chosen action and notification; it is not a hidden side effect of any grant mutation.

The useful product value is that the normal review visibly includes the proposed recipient handoff while retaining the ability to omit redundant email when an existing qualified handoff is appropriate. Both options can finish grant and notification authorization in one purposeful interaction. A changes which notification choice is initially selected; it does not uniquely provide integration. This is a design judgment, not measured proof that Asym staff routinely forget messages or that every recipient wants email. The tradeoff is consequential: a default-on outward communication can be overlooked, can be inappropriate for a sensitive context, and must never imply missing send authority or an approved destination.

**B — email starts unselected in the same review; staff explicitly opts in** is the strongest alternative. It protects deliberate control over outward communication without forcing a separate post-grant step. Its cost is that staff must select email when wanted, and an omitted selection can leave the grant admitted without a notice while its fixed source clock is already running. It is not proven inferior, and a clear checked state and combined action can remain just as compact as A. Neither choice may hide automatic email behind a grant-only label.

This recommendation is **conditional on owner validation**, not an instruction to treat permission to issue access as permission to send. If the ordinary profile has no qualified source-specific message purpose, eligible destination or actual P6/P17 dispatch authority, A cannot safely become its default by inference. B still needs that exact qualified communication authority when email is selected; an unchecked default is not a bypass for missing authority either.

## Small proposed experience

Keep the existing unfinished-request or completed-request context and its own access action. Preserve the different recipient capabilities: a fresh unfinished period may allow only currently permitted continuation work, while fresh completed access stays read-only. Reuse the interaction pattern without conflating the permission types or business status.

For either option, the meaningful review can contain **“Email the recipient about this access”**, with the destination shown only to the extent the issuer may inspect it. A starts the eligible choice selected; B starts it unselected. The confirmation action should make the final chosen consequence clear—for example **“Grant access and send email”** when eligible and selected, and **“Grant access”** when it is not selected. These are proposed labels, not a requirement to install a new component or add a second screen. Use an approved source-specific message, not a mandatory custom-writing task.

If the source does not permit the email, do not leave a checked control suggesting it will be sent. Explain the actual unavailable notification state in authorized staff context. A grant-only choice can proceed only if that source profile and its real handoff path permit it; do not silently substitute grant-only after the actor explicitly chose a combined outcome. Source issuance and subsequent delivery still have independent results and cannot be made atomically successful by wording.

After a qualified source result, the same context can state **“Access granted. Ends [actual date, time and zone].”** Then show the notification's truthful state: selected/queued, dispatch accepted or failed only where supported by actual evidence, or **“No notification sent”** for deliberate omission. “Email sent” must not stand in for recipient delivery, reading, current proof or usable content. A separate notification failure does not roll back or reset the admitted grant.

When staff leaves email off under either option, the result exposes the real eligible next action rather than promising that someone was told. A later **Notify recipient** or existing qualified handoff action may be useful where actually available; it is a bounded recovery/manual alternative, not a newly claimed built feature or an obligatory second step. It may also be appropriate where a different authorized actor owns communication. There is no automatic follow-up merely because the issuer navigates away, and no requirement to paste raw storage URLs, email attachments or credentials.

The recipient notice should lead to the existing source-qualified entry route, with current proof and source checks still required. Approved minimal context, clear intent and useful contact/help are preferable to filenames or private evidence in the subject/body. Exact permitted wording and contextual disclosure belong to P6/P17/source owners. The email's existence or its link is not itself sufficient authority, and a delayed old notice must not resolve to a new grant merely by looking up the latest period.

When safe to state in the approved message, communicate the actual admitted end, not thirty days from email receipt. In-product current terms remain authoritative when restrictions change. Staff can repair a separately failed eligible notification under existing communication authority; resend does not create another grant, extend time, change identity or imply a new approval. This choice selects no resend cadence or automatic alternate channel.

## Owner validation required before presenting a final Q20 choice

1. **Exact notification purpose and scope.** Confirm the P6/P17 source-owned purpose for fresh unfinished and completed-read access, including both valid completed origins and repeats. Their shared UX must not import marketing, ordinary contact, newsletter or specialist official-document authority.
2. **Who can authorize the combined act.** Verify whether the exact issuing actor may also authorize this approved notification, or whether existing source/P6/P17 automation/approval supplies a qualified mapping. Grant authority alone, generic staff status, file-reading rights and a service token are not send authority.
3. **Recipient and route qualification.** Reuse the intended source recipient and approved destination/entry path. Confirm closed external/no-Party document-recipient support where required, allowed contact data disclosure, suppression/communication preferences and stronger assurance. Do not infer these from an email string or create an arbitrary replacement address field.
4. **Required notices versus optional access notice.** Preserve any genuine source-mandated communication; the opt-out candidate must not promise permission to suppress it. Conversely, an optional notice cannot become a mandatory gate solely because a vendor uses email.
5. **Actual outcome and safe recovery.** Keep stable source effect, chosen message intent and independent dispatch/delivery evidence. No pre-commit grant-success message, duplicate notice from same-effect replay, blind retry after an unknown provider outcome, or dispatch of stale/forbidden access information. Use current owner mechanisms rather than proposing an exactly-once provider guarantee.
6. **Compatibility and readiness.** If owner validation cannot establish a qualified combined notification lane, correct the candidate before asking. Both options still require a real source-owned handoff route; no documentation wording proves native entry, dispatch, delivery or browser/AT qualification.

These are engineering/authority checks to investigate, not six new founder questions. They may narrow the supported default or reveal that a particular source profile cannot offer grant-only. The product choice should stay about the normal deliberate interaction once its legitimate scope is known.

## Recommended founder framing after validation

**When staff grants fresh access, should “Email the recipient about this access” start selected or unselected?**

- **A — Selected by default, with a clear off switch (recommended if the ordinary source lane qualifies).** Show the recipient and email choice before confirmation. Staff can omit the optional notice when an existing permitted handoff is more appropriate.
- **B — Unselected by default; staff opts in.** Show the same choice in the same review. Staff selects email when wanted; leaving it off grants access without sending that notice.

Both support one deliberate combined action when email is selected and a qualified grant-only action when it is not. Both keep source/message outcomes separate and preserve the existing fixed period, permissions and proof. No reminder schedule, new account, sender/calendar configuration or automatic renewal is included. This is a decision about the initial notice for that deliberate fresh grant, not a default for every document event.

## Evidence limits and next step

The recommended default-on choice is a practical UX judgment supported by bounded comparable mechanisms. Both proposed options are integrated; no source proves the optimal checkbox default, reduced support volume, delivery success, recipient preference or current Core implementation. Default-off is genuinely stronger for affirmative control of outward communication. Separate post-grant notification remains a bounded alternative/recovery path where the actual timing or authority requires it, not a competing equal mode in this question.

Complete the owner validation and resolve any material conflict before final founder framing. Then ask one meaningful choice; perform the full adversarial review only after the founder answers. This note selects no Q20 answer and changes no canonical document, permission, provider or runtime.

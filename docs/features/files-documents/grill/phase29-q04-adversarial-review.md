## Adversarial check

### What could go wrong with this answer?

The download could disclose hidden content omitted from the preview, deliver an earlier or newer file than the one selected, bypass current restrictions through a saved URL/cache, or claim success when the browser did not save anything. A superficially polished download button can hide all four mistakes.

### What hidden assumptions are we making?

Uploaded by me is not current original-download permission. Original does not mean first-ever submission. A preview-safe representation does not authorize every byte of its input. A browser click or completed server stream does not prove a saved or read file. No-store and revocation do not erase an intentional device copy. A source read is not a new submission, acceptance, export package or communication.

### How does this affect the whole product?

The ordinary native request gains one distinct source-qualified read action over existing private custody. It does not acquire a library, universal uploader ownership, historical archive or longer access. P18/P21/P22/P26 and resource/media owners keep their existing identities, disclosure, filename, currentness and retention rules. A general file manager cannot widen those sources by exposing the same button.

### How does this affect the end-user experience?

Place **Download submitted file** in the exact submitted-file row beside View, with a safe filename, useful type/size and current status. Keep it usable by keyboard and touch without opening the viewer first. One deliberate ordinary action is sufficient. The browser handles saving; the app gives only truthful preparation/error/handoff guidance. Pending, prohibited and unavailable originals have clear safe states; preview and correction remain independent.

### Does this follow modern best practices?

Yes, as a deliberate product choice rather than a universal rule. Submittable documents individual submitted-file downloads separately from a PDF summary. Microsoft file requests instead use upload-only collection. Asym can adopt contextual retrieval without either product's wider permission model. [Submittable](https://submittable.help/en/articles/2814108-how-can-i-download-a-copy-of-my-submission), [Microsoft](https://support.microsoft.com/en-us/onedrive/create-a-file-request).

Official web guidance supports meaningful link purpose, clear file context and native browser behavior. MDN documents that download handling and filenames vary with browser/settings; `Response.blob()` reads the body to completion. A page-owned Blob is not inherently a better or safer download path. These facts support a simple qualified native delivery baseline, not an unqualified transport mandate. [Link purpose](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html), [HTML links/download behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a), [Response.blob](https://developer.mozilla.org/en-US/docs/Web/API/Response/blob).

### Does this fit Asym’s existing repo and product direction?

Yes. Q02/Q03 explicitly reserved original download as a separate action. D32 already distinguishes Preview from Download original for its own source, while P12 supplies the single permission/egress owner. The no-general-drive direction remains intact. Core's exact Base UI/`base-maia`, semantic tokens and shared UI ownership remain binding. Existing code must be qualified at the new recipient/source boundary rather than treated as proof by resemblance.

### Should we adjust the recommendation?

Keep A with explicit whole-original disclosure permission, exact-version private serving, inherited stream expiry/revocation rules and honest browser feedback. Prefer the ordinary browser download mechanism when it fits qualified authentication. Do not add routine confirmation forms, a download manager, an export job or a new provider merely to deliver an already-held file.

## Corrected decision to record

> The ordinary native private-document request provides a separate, deliberate **Download submitted file** action for the recipient's exact currently authorized own-submission occurrence/member, when its entire unchanged original is permitted and qualified for delivery. Ordinary eligible downloads do not require staff to unlock each file.
>
> Submitted original means the immutable bytes received for the specifically selected submission, including a corrected submission. It is not the first historical attempt, a moving latest pointer, converted preview, summary, sanitized/redacted copy or independently issued document. Do not silently transform or substitute it.
>
> Original disclosure and safety are qualified independently of preview and business acceptance. Current source/PDP/classification/purpose rules protect metadata and every new full, range, conditional, resumed or recovery request. Long streams recheck expiry at the inherited boundaries; source restriction stops new grants and terminates in-flight delivery where feasible. Already emitted or saved bytes cannot be recalled.
>
> The UI presents a visible contextual action with useful permitted file information, accessible interaction and truthful unavailable/recovery states. It does not automatically download on page entry, preview failure, sign-in return or a retry loop. Browser handoff and server transfer evidence must never be represented as proof that the file was saved, read or accepted.
>
> The action grants no previous-version archive, other-person/staff files, post-closure continuity, public sharing, bulk export, deletion or general drive. It changes no review outcome, correction eligibility, source retention or clock. Existing source-qualified document downloads remain governed by their own owners.

### Accessibility, mobile and localization

The visible label remains within the accessible name; add the permitted filename/item context to distinguish repeated actions. Associate type/size information without forcing a screen reader to recite unrelated metadata. Use Core's touch-target convention, keyboard and speech activation, visible focus, responsive stacking, zoom/reflow and reduced motion. Long/Unicode/RTL names need safe readable presentation and more than a hover tooltip. Do not use a fake `href`, an unlabeled icon or `aria-disabled` alone on a still-active link.

An accessible control does not make the original document accessible. Exact-byte delivery does not add tags, OCR, reading order or spreadsheet semantics. Preserve the qualified Q02 preview and any separately authorized accessible alternative; name each representation honestly. Do not silently convert the original. Low-bandwidth users should see useful file size before choosing; no eager fetching of all files. Browser resume support must be measured, not promised universally. [WCAG label in name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html), [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

## Architecture and authority implications

The smallest permanent design is one original-download action/projection in the native request owner, reached through Q01-compatible current identity/PDP and the existing governed egress boundary. Shared custody supplies exact immutable copies. No new context, permission engine, binary repository, export domain or native filesystem permission is selected.

**Whole-file authorization:** a binary original cannot be treated as though the safe preview's field projection still protects omitted material. The source must permit all unchanged delivered bytes, including metadata, hidden sheets, comments and embedded features. Applicable sensitivity/parent restrictions and residency remain binding. If that original is not permitted, withhold it; a separately qualified alternative must be labelled as such. A scan alone cannot settle disclosure, authenticity or all active-content risks.

**Serving and names:** attachment disposition, a truthful qualified media type, no sniffing/active execution in the privileged app origin, safe filename handling and private non-cacheable delivery must be verified together. Use a source-approved safe download-name suggestion; do not expose local paths, provider keys, forbidden source names or header-control characters. Browser/OS name adjustment does not change the immutable original bytes. RFC 6266 treats supplied filenames as advisory and discusses path and extension hazards. [Content-Disposition](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Disposition), [RFC 6266](https://www.rfc-editor.org/rfc/rfc6266).

**Identity before emission:** establish a trusted binding from the selected received version to its immutable provider copy and verified length/digest before releasing bytes. A hash computed only after a live transfer can detect corruption too late to prevent wrong bytes reaching the recipient. Ranges require trusted whole-object/version or appropriate chunk-integrity binding. Do not turn this requirement into mandatory whole-file buffering on every download; qualify immutable custody and the delivery adapter.

**Ranges and recovery:** support only qualified bounded request forms. New full/HEAD/range/conditional requests authorize before protected metadata or results, including 304/416/error paths. Correct range lengths, validators and representation identity must prevent mixed-version resume. A server may have different standards-compliant range behaviors; the actual supported behavior must be explicit and tested, rather than claimed from an SDK method name. Error/login/JSON/HTML responses must never be served or labelled as the original. Interrupted transfers may leave partial browser-managed files; do not promise erasure or successful saving. [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html).

**Expiry and active streams:** P12 requires long-stream expiry checks per chunk and the established metered egress. Its managed-realtime 60-second allowance is not a download grace period. D16 stops new grants at restriction and treats previously authorized streams as in flight, terminating where feasible. Provider/CDN buffering and termination must be measured. Do not promise per-byte recall or allow a reusable bearer URL to outlive current source authority.

**Audit:** consume P12's existing tier-specific audit/budget contract: restricted/break-glass requires the applicable audit-before-serve gate; other applicable tiers use their durable outbox semantics. Do not invent a synchronous general database write per byte/chunk. Record actual technical outcomes in the protected access history. Grant issued, request admitted, bytes transmitted and stream completion are distinct; none proves browser saving, reading, agreement or external-custody verification.

The reached `withOperation` creates an audit logger; that does not itself write access evidence. The inspected logger skips a missing client, does not inspect a returned insert error and catches thrown errors. Consequently, merely awaiting that helper is not proof of required durability. Qualify the existing tier's actual durable path and inject those failure cases; do not assume every audit subsystem shares this helper's limitations.

**Transport:** prefer a compatible authenticated application attachment path that hands delivery to the browser and supports bounded server streaming/backpressure. A preparation command is justified only where the architecture needs it; it cannot mint enduring authority. Fetch-to-Blob can be valid for a separately justified bounded case, but reads the complete body before that handoff and adds status validation, interruption and object-URL lifetime work. Browser backing storage varies; do not claim all Blob bytes always occupy the JavaScript heap. No particular provider or implementation is certified here.

## Category-by-category adversarial review

Each category states materiality, severity, qualitative likelihood, evidence/reasoning, effect on A and exact correction. High means substantive confidentiality/integrity/authority impact; Medium means meaningful usability, reliability or maintenance impact. These are design risks, not observed production incident rates.

### 1. Problem validity, necessity and alternatives

**Material concern: yes — Medium / plausible.** A can become unnecessary export machinery if the real need is simply an exact copy within an existing task. Preview-only is the strongest alternative and reduces original-byte disclosure, but cannot provide original-only details or use in another tool. Comparator products support both models; user demand frequency is unmeasured. **Effect:** retain A as a bounded product choice, not universal storage ownership. **Fix:** C01/C05/C16/C20; one contextual read action, no drive/archive/job platform, and participant proof of useful task completion.

### 2. Brittleness

**Material concern: yes — High / plausible.** Latest-file resolution, changing storage keys, assumed browser Save behavior or an old signed URL can return the wrong content or outlive authority. Q03 corrections and MDN's browser-dependent behavior make these assumptions fragile. **Effect:** require exact selection and honest outcome boundaries. **Fix:** C02/C06/C08/C09/C15; immutable version/copy binding, current access, supported browser qualification and no fixed saved-folder or perfect resume promise.

### 3. Technical debt

**Material concern: yes — High / likely under blind reuse.** Current receipt generation buffers output; the public Blob adapter's caching/error behavior has a different purpose; a helper reports Downloaded after anchor activation. Reusing these wholesale would mix business generation, public delivery and unverifiable UX status. **Effect:** reuse only the qualified parts. **Fix:** C06/C07/C14/C18; one shared private read seam, truthful shared interaction and versioned adapter qualification. No dependency upgrade or duplicate app-local downloader is justified merely by a new button.

### 4. Edge cases

**Material concern: yes — High / plausible; frequency unknown.** Similar names, multi-file items, a new correction, expiration during a slow stream, browser-declined saving, partial local files, range restart or a checker outage can confuse identity and success. These are test scenarios, not asserted ministry habits. **Effect:** A needs state-specific recovery. **Fix:** C02/C04/C06/C08/C09/C15; exact row targeting, independent preview/download states, truthful browser help and current reauthorization. Same names do not imply same files; a local duplicate suffix is not a new Asym version.

### 5. Footguns

**Material concern: yes — High / likely with common shortcuts.** A filename hyperlink may unexpectedly download, hover-only icons hide the action, speculative prefetch begins delivery, or a login/error response is saved as a document. A Continue anyway warning can bypass forbidden originals. **Effect:** make interaction and representation explicit. **Fix:** C04–C07/C13; visible labelled action, no automatic fallback, validated private response and safe errors. Raw untrusted filenames are not header values or storage identities.

### 6. Tenant safety

**Material concern: yes — High / plausible.** Guessable IDs, cached metadata, cross-source hash reuse, a service-role route or range/304 differences can leak another tenant, recipient or restricted occurrence. Preview permission is not full-original authority. **Effect:** tighten scope rather than reject A. **Fix:** C01/C03/C08/C10–C12; current exact source/principal/tenant context before metadata/body/error, same-scope references, no permission pooling through shared bytes and no alternate serving bypass.

### 7. Database, RLS and authorization safety

**Material concern: yes — High / plausible.** A gateway may use privileged storage access after only a generic authenticated check; mutable pointers or clearance fields can redirect a permitted file row into forbidden bytes. Existing specialized service policies do not qualify the new recipient. **Effect:** C08/C10/C11 are release gates. **Fix:** required same-scope source/version references, immutable byte identity, controlled disposition/qualification fields, server-derived attribution and exact source predicate. Test effective grants, permissive policy combinations, old/new-row checks on supporting mutations, views/functions/storage and privileged workers. A missing explicit WITH CHECK may inherit USING; function naming alone does not prove bypass. Q04 adds no money writes/calculation; source financial precision and posted facts remain untouched.

### 8. Overengineering

**Material concern: yes — Medium / plausible.** An export job, archive generator, custom download manager, filesystem permission, repeated reason/confirmation form or per-file staff approval adds friction and operational state. Conversely, forcing a native link without compatible authentication is not simplification. **Effect:** prefer the smallest qualified path. **Fix:** C01/C05/C14; direct contextual resource delivery when possible, bounded preparation only when necessary, existing source assurance and shared controls. No new provider or universal configurable permission matrix is selected.

### 9. UX/UI and user friction

**Material concern: yes — Medium–High / plausible.** Ambiguous Original labels, tiny icons, viewer prerequisites, false success badges and unexplained unavailable states prevent reliable use. Official link/accessibility guidance and the current click-based export toast substantiate the risk. **Effect:** adopt the complete journey above. **Fix:** C05/C06/C13; Download submitted file, visible filename/type/size context, one ordinary action, keyboard/touch discovery, stable focus and honest recovery. Test behavior on supported devices and with actual people; aesthetic similarity or a component test is insufficient.

### 10. Source of truth, ownership and invariants

**Material concern: yes — High / plausible.** Original may accidentally mean first historical version, regenerated PDF or sanitized output; download audit may become proof of acceptance or verified custody. P18/P21/P22/D32 explicitly separate these meanings. **Effect:** define the artifact and the read precisely. **Fix:** C02/C03/C11/C16/C17; source occurrence owns meaning/currentness, custody owns exact bytes/copies, browser owns local save choice, and access evidence owns only observed delivery facts. No derived projection becomes permission or currentness authority.

### 11. Hidden coupling

**Material concern: yes — High / plausible.** Download tied to preview-ready makes converter outages block a permitted original, while preview failure as an automatic trigger exposes unqualified bytes. Reusing a generated-document endpoint can regenerate instead of retrieve. **Effect:** independent capability and state are essential. **Fix:** C02/C04/C06/C14; original delivery requires its own qualification, neither dependent on optional preview success nor unlocked by failure. Current underlying custody/integrity failures may correctly block both; independence is not a bypass.

### 12. Failure modes

**Material concern: yes — High / plausible.** A storage adapter returns no body or the wrong status, a proxy buffers bytes after revocation, a connection drops, or JavaScript saves an HTML error as the file. Current public adapter and buffering patterns are not proof of private recovery. **Effect:** specify honest outcomes and adapter validation. **Fix:** C06–C09/C14/C19; distinguish failure classes, validate actual responses, maintain exact-version retries and repair missing/corrupt copies. No plausible regeneration, public URL or preview substitution may masquerade as the original.

### 13. Lifecycle, temporal correctness, concurrency and idempotency

**Material concern: yes — High / plausible.** Correction/revocation/disposal can race with read admission, and resume can join old and new bytes. Treating a read like a one-time mutation can either block legitimate retry or erase actual access evidence. **Effect:** use relevant source/read fences, not a new global workflow. **Fix:** C08/C09/C15/C17; correction-first rejects stale selection, already admitted streams stay immutable with inherited expiry/termination, all new ranges reauthorize, and repeat reads consume real budgets/audit. No deadline/retention renewal, auto-rebase or borrowed realtime grace.

### 14. Data integrity risks

**Material concern: yes — High / plausible.** Mutable provider keys, misleading ETags, incorrect range offsets, silent compression/repair/redaction or a later version substituted during retry can corrupt the promised exact copy. **Effect:** original identity must be provable end to end. **Fix:** C02/C07/C09/C10; preserve verified immutable byte/copy lineage, correct lengths/validators and reconstructed-file integrity. A safe filename suggestion may change while the bytes remain exact; a changed file body must have a distinct representation identity and label.

### 15. Security and privacy risks

**Material concern: yes — High / plausible.** Original bytes can reveal comments, metadata, hidden worksheets or active features absent from a preview. Public caching, raw bearer URLs, unsafe names, telemetry or external viewers create further disclosure paths. **Effect:** require explicit whole-original permission and delivery qualification. **Fix:** C03/C04/C07/C08/C12; enforce source floors and permitted format/features, withhold unqualified originals, prevent privileged-origin active execution and minimize egress. No scan/disclaimer guarantees harmlessness. Revocation cannot erase an intentional local copy; do not add DRM or device surveillance as a false solution.

### 16. Scalability and performance risks

**Material concern: yes — Medium–High / actual workload unknown.** Full-file buffering, repeated ranges, eager downloads, slow clients and leaked object URLs can exhaust memory, egress or connections. The installed SDK's stream primitive is useful but not a qualified gateway. **Effect:** finite resource handling is required. **Fix:** C09/C11/C14/C19; bounded streaming/backpressure, cancellation, exact source limits and fair budgets, with representative slow-client and concurrency tests. Do not borrow D32's 20 MiB preview cap, two parser attempts or preview latency targets as universal download rules.

### 17. Operational burden

**Material concern: yes — Medium / plausible.** Vague download failures send users to staff for manual links, raw provider-console recovery or duplicate uploads. A permanently unavailable button can hide missing implementation. **Effect:** require owned, visible recovery. **Fix:** C06/C18–C20; diagnose permission, checks, source integrity, provider and browser separately; use the existing source/custody repair route without emailing private attachments around controls. Implement and qualify the declared ordinary capability rather than claiming completion from an unavailable placeholder.

### 18. Observability and auditability gaps

**Material concern: yes — High / plausible.** Grant issued, transport completed and human saving/reading can be conflated. Metering or required audit might be skipped on HEAD/range/cache paths; logs may become a private archive. **Effect:** existing tiered evidence must be applied accurately. **Fix:** C06/C08/C11/C12/C19; protected source/actor/version/purpose and technical-stage evidence, actual budget effects, minimized ordinary telemetry and named controls. Do not deduplicate away repeated real reads or create consent/CRM events from them.

### 19. Dependency and integration risks

**Material concern: yes — High / plausible.** SDK stream wrappers may hide response status/headers; CDN route rules can override private cache intent; browser settings alter save behavior. A public adapter's range support does not imply private authorization. **Effect:** qualify the installed complete path. **Fix:** C07–C09/C14/C18; pin proven adapters, inspect actual deployed responses and buffering, validate browser support and upgrade only with evidence. Source inspection found extension-wide public image/font cache rules; a new private route must prove they cannot override its required behavior.

### 20. Migration, rollout and upgrade risks

**Material concern: yes — High / plausible.** New private controls coexist with reusable old URLs; filename-based backfill misidentifies originals; restore revives access or rollback returns to public serving. **Effect:** containment and compatibility precede activation. **Fix:** C16–C20; inventory retained source/copy identities, reconcile unknowns without deletion, contain alternate routes and old grants, test mixed versions and apply adverse history before restored delivery. Disable affected new download safely instead of falling back to weaker access.

### 21. Testability, traceability and proof

**Material concern: yes — High / known qualification gap.** The reached source lacks a qualified generic native recipient original-download service. Ten mocked receipt tests prove only a different seam, not this route or browser experience. **Effect:** no completed-feature claim. **Fix:** C20 and P01–P24 below; trace selected intent through glossary/ADR and later authorized source/OpenSpec/tasks to real-role, HTTP, provider, race, browser and participant evidence. Test exact bytes and usable recovery, not merely whether clicking a control called a function.

### 22. Other development hazards

**Material concern: no additional independent concern found.** The review checked accidental creation of an office suite, public sharing, generalized backup, post-closure archive, external transfer, signature/acceptance effects and device-control promises. These remain excluded or governed by the specific findings above. No extra legal guarantee, provider migration or broad account permission is needed for A. Future implementation still requires the stated proof.

# Phase 29 Q02 — purpose-bounded custody and own-submission preview

Owner-contract adversarial research, 20 October 2026. This is a supporting grooming review, not a PRD, new owner specification, implementation, ticket publication or release qualification. It was requested after Conrad selected receipt/status/**View my submitted file** and explicitly said Asym is not the user's new Dropbox/Google Drive: the files/media are needed for use on Asym or produced by Asym.

## Provenance and conclusion

**Explicit new founder direction:** Asym is not general personal/cloud-drive storage. Its file/media capability serves use within Asym and Asym-produced material. The founder also selected the bounded own-submission viewing journey. These statements are product intent. They do not themselves specify a storage schema, universal attachment rule, legal retention policy, preview engine, file format, library owner or automatic purge command.

**Recommended interpretation for ratification:** admit and retain bytes through a real, authorized Asym source purpose and its lifecycle. Valid purpose can be an exact document request, a reusable media item, a curated resource/draft, an official generation/export, a governed import session, or a qualified development capture/build. It need not already be attached to an active CRM record or published page. After its active use ends, required evidence, recovery and holds still govern retention; access can end independently.

This is the smallest permanent interpretation consistent with existing owners. Requiring every file to have a current business-record placement would break already accepted catalogs, drafts, staging, recovery and records duties. Conversely, an editable label such as “for Asym,” “general files,” “my documents” or a folder name cannot authorize otherwise ownerless drive storage. Ordinary users should not fill in a governance form: the actual source entry normally supplies purpose and scope. A genuinely ambiguous File Manager entry can offer a short set of supported destinations, not arbitrary policy creation.

The preview choice remains separately permissioned, exact-version, currently source-authorized reading of the submitter's admitted item. It grants no personal drive, broader directory, original download, correction/replacement, editing, staff-review visibility or perpetual access. The original file and the limited technical preview remain distinct.

“Known owner and purpose” does not mean exactly one business owner/use for every physical byte identity. Several independently admitted typed source references may use the same bytes while retaining separate meaning, currentness, audience, rights and retention. Byte equality does not merge those authorities. Likewise, excluding generic drive-style public sharing does not remove source-approved public-media release or authorized external document delivery; excluding a standalone personal drive does not prohibit a user's legitimate source-owned draft/request work.

## Permanent product boundary in ordinary language

“Files in Asym support work the organization does in Asym, or are outputs/evidence that Asym must produce or keep. A communications person can prepare a reusable photo before placing it; a curator can draft a resource; finance can retain a closed receipt; an import can keep its reviewed source file; development can retain the exact build needed to recover a website. These belong to their Asym purpose even when no page is currently using them. Personal computer backups, unrelated archives and arbitrary cloud-drive storage do not become supported merely because someone uploads them or puts them in a folder.”

This wording is a **proposed interpretation to ratify**, grounded in existing duties. It does not claim Conrad separately enumerated every example. If “needed for use” were intended to forbid pre-placement reusable catalog preparation, retained source evidence or governed staging, that would require an explicit owner change and would conflict with the currently accepted contracts; do not silently make that narrower interpretation.

## Minimum admission behavior — no governance platform

1. The owning operation supplies trusted tenant/environment, actual source purpose/family, source occurrence or admitted draft/catalog/intake/generation identity, current actor authority, allowed content/processing/delivery profile and applicable custody/retention policy. The file service validates this exact operation; it does not accept client claims of owner, purpose, scan outcome or review state.
2. Normal entry is contextual: **Attach requested document**, **Add media**, **Add organization resource**, **Import source file** or a source-owned generation/export. Context carries ownership so the user ordinarily chooses the file and source-relevant details. No universal checklist, arbitrary retention editor or forced link to a different business record.
3. If File Manager offers an upload outside a known context, require selection of one supported actual purpose/destination for which the actor has authority. This is a small code-owned set of source adapters, not tenant-authored policy scripts or a free-text “for Asym” field. It can create the relevant pending catalog/resource/intake source before bytes arrive; it need not fabricate a CRM record.
4. No route for “store anything for me” or unbounded folder/computer sync follows from this scope. A real future connector imports only deliberately selected source-qualified items; connecting a provider does not grant access to all of its files or make every remote file an Asym record.
5. Purpose admission and content acceptance remain distinct. A wrong, malicious, oversized or out-of-scope file can arrive during a legitimate attempt. It stays restricted under bounded intake/quarantine/reconciliation custody rather than being presented as an accepted useful document or being instantly destroyed against an incident/hold obligation.
6. After admission, removing a placement, withdrawing a resource, completing a request, losing membership or disconnecting a provider changes only the relevant owner state. Exact source policy, uses, holds and backup/restore obligations determine retention/disposition. “Not a drive” is not a deletion rule.

**General resources:** P28 already owns missionary resource publication. Any additional general organization resource family must receive a narrow semantic owner and supported use in subsequent Phase29 grooming; do not create an ownerless “General” escape hatch, and do not quietly remove the original requested general-resource outcome. A private organizational catalog can be a legitimate source identity; a folder alone cannot.

## Q02 preview source-adapter requirements

These are proposed safeguards to include in the parent's ratification package, not new source implementation.

- **Read source:** the currently authorized native document-request submission occurrence/version. Do not select by filename, provider key, digest alone, Person/Party membership or “all uploads by this email.” The current source determines the admitted read audience; replacing the requester does not inherit earlier submissions automatically.
- **Evidence source:** exact bytes durably received/verified under that occurrence; associated safety/readiness proof. Source business review remains independent. A pending local upload or metadata row cannot be represented as a confirmed stored file.
- **Preview source:** the shared qualified profile and immutable rendition generation with exact source/version/profile/options/restriction binding and coverage manifest. It is not an official generated document or source replacement. Reuse shared UI under Base UI/base-maia and keep the user in the same lightweight request page.
- **Authorization:** confirm current participant request admission before metadata, preview admission and each byte/page/range/conditional read. Worker preparation/promotion rechecks operation-appropriate current source/worker authority, not the old browser session. A source restriction invalidates all applicable generations and late responses; already seen information cannot be recalled.
- **No automatic side effects:** opening preview does not submit, replace, accept, sign, notify staff, make public, create a CRM copy, enroll in a resource library or introduce OCR/AI/search. Access evidence may be recorded by its lawful owner; it is not a communication/business-completion fact.
- **Failure:** checking, limited, unsupported, blocked, failed, missing bytes, ended access and source review states stay distinct and safe. Do not show Download original as fallback where not separately admitted. Same-state retries recover the original outcome; reopening cannot create unlimited new generations.

### Inherited P26 profile bounds when reused

ADR0032:49 and data-contract:53–82 supply exact **preview-only** limits: original20MiB; expanded package200MiB; 10,000entries; XML depth128/no DTD/entities; 200outputpages/visible slides; 40,000,000pixels perimage/256MiB decoded-image working data; 50totalsheets/100,000populatedcells includinghidden; 1,000,000text/CSV Unicode scalars/100,000CSVcells; 50MiB totaloutput; 60elapsedseconds/30process-treeCPU seconds/2GiB memory/512MiB scratch; atmost2attempts with second only transient; tentative/scratch15minutes fromattemptstart; Ready24hours fromfirstReady or earlier source deadline. Binary units remain binary. Their later ratification supersedes the historical companion wording “proposed.”

These values cannot silently become universal document upload/storage rules, nor may Q02 weaken them when consuming that exact profile. Their substantive purpose/format behavior is ratified; actual parser, provider, DB, browser, capacity and recipient-audience qualification remains required. Current-source safe profile selection may decline unsupported structure inside size bounds. Unknown format does not automatically mean malicious; known unsafe/unsupported retrieval cannot be repaired by raw download.

## Proof obligations to carry forward

1. Add a qualified reusable Media item and resource draft before any live placement; creation succeeds within owner authority. A free-form “for Asym” upload lacking supported source admission fails without leaking unrelated data.
2. Import staging and exact development capture work before their final domain/publication acceptance; they never manufacture target truth or public availability.
3. Complete/unlink/withdraw an active use; held, historical, scheduled and recovery-required bytes survive according to exact owner policy, while former participant access ends independently.
4. Make usage projection stale or incomplete; it cannot report Unused or authorize purge. Restore retains negative access/disposition fences before reads or jobs resume.
5. Receipt/status and own-submission preview return the exact durably received source/version, not a local thumbnail, mutable latest path or another same-name file. Adverse/limited/unsupported results are honest.
6. Test another principal, same mailbox string, another request/tenant, replacement recipient, expired grant and staff without source access across metadata/full/range/conditional/rendition paths; no accidental reader transfer.
7. Reuse a qualified P26 profile through the new request-source adapter without widening staff Support reads, changing originals, overriding resource ceilings or adding a Download original escape.
8. Exercise concurrent opening, retry, processor expiry, source withdrawal, late output and cleanup-versus-promotion; one semantic generation/current-authority result, bounded work and no retained-data deletion by stale cleanup.
9. Catalog/resource/import/generation entry supplies purpose without a technical form; mobile, keyboard and assistive-technology users can complete receipt/readback and understand preview versus business acceptance. No original-download/replacement promise appears accidentally.
10. Migration classifies known source ownership and safe unknowns without broad public-URL grandfathering, identity rewrites, arbitrary private copying or deleting real legacy records under the new product slogan.

## Boundaries of this review

No private content/provider storage was read, no connector was activated, no file uploaded, no access/retention changed, no parser/provider/DB/browser test run and no benchmark result inferred. The source review is deeper for the listed owner passages, not a claim that every Phase18–44 document or issue was exhausted. Future general-resource owner scope, exact shared profiles, deletion schedules, download/replacement/history decisions and representative workload remain their proper later grooming/qualification work.

The recommended disposition is **accept the selected preview journey and explicit no-general-drive boundary with the source-preserving amendments above**. The precise interpretation is proposed for ratification; it must not be silently recorded as if the founder independently specified every mechanism. A coherent purposeful File Manager remains required; the boundary prevents unrelated storage expansion while preserving legitimate Asym preparation, outputs, history, evidence and recovery.

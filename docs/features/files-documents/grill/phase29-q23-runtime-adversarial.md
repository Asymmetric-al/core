## Conclusion and scope

Accept A with the narrow safeguards below. An authorized staff return is an exact source review outcome on a still-eligible, unaccepted item/evidence basis. It leaves actual required work unsatisfied and makes the safe next action understandable. It is not a new submission, acceptance, waiver, rejection of the larger process, permission grant, deletion or automatic message. Q03 remains the participant correction mechanism; Q21 remains meaningful acceptance; Q22 remains the complete source fulfillment predicate.

The most important incremental rule is **history versus current effect**. Preserve the exact committed return, actor, time and feedback basis, but never let an old retry or delayed projection make that return current again after a successor, acceptance, actual source closure or later governing outcome. Reassessment need not manufacture different bytes: where the current source permits and Q21 is satisfied, staff can accept the same exact current evidence after resolving a mistaken or no-longer-applicable concern. That is a new qualified acceptance outcome, not erasure of the return or a generic Undo. Q23 does not itself introduce a recipient text-reply channel or arbitrary feedback-edit permission.

Use the existing canonical API/source boundary, private custody, protected action, P12 authorization, P9 work projection and durable handoff infrastructure. No new workflow platform, universal review lease, per-file mandatory task, bespoke permission system, SQL schema or enum is prescribed here.

## Exact required technical clauses

These R identifiers are this note's proposed technical traceability, not a published schema or extra founder decisions. The consolidated review can map them into Q23-C/P identifiers.

**R01 — Bounded source outcome.** Request changes is a recoverable source review result for the exact currently eligible unaccepted item/evidence basis. It leaves actual required work unsatisfied. It does not terminate ordinary correction, manufacture satisfaction/waiver, invalidate accepted siblings, reject the enclosing process or change existing specialist finality. A non-remediable source situation needs its truthful owned path before activation, not an endless unexplained return loop.

**R02 — Exact authority and relationships.** Resolve actor, tenant, recipient/source binding and the exact review capability on the trusted server path; assignment and source access administration are not substitutes. Validate requirement/evidence relationships beyond mere tenant equality. Preserve non-null mandatory identity/actor proof and immutable historical attribution using the chosen source contract; do not invent fake profiles or broaden Q01 membership. Current permissions gate new action and current disclosure. Later staff role loss alone does not retroactively erase a lawful historical outcome.

**R03 — Shared current-basis boundary.** Fence the relevant requirement revision, exact current submitted members and source state together with Q03 correction, Q21 acceptance, adverse source changes and Q22 fulfillment. A current aggregate can include several independent supporting members; a file hash/name or latest timestamp is not the basis. Admission of a targeted correction removes predecessor candidacy immediately, even when safety/preview remain pending. No stale return or delayed result applies to the successor. Respect real aggregate dependencies without locking all unrelated work.

**R04 — Durable history, current applicability and reassessment.** Preserve exact original return actor/time/basis and permitted feedback. Clearly distinguish that historical fact from the currently actionable result. A valid new correction supersedes the relevant current review basis without satisfying it or clearing unrelated feedback; other supporting members remain. If the current source permits legitimate Q21 acceptance of the same exact evidence, do not require a fake changed file or duplicate receipt merely to resolve a mistaken concern. That acceptance preserves the prior return in history and qualifies present applicability; no generic Undo, arbitrary feedback rewrite, forced reupload, automatic acceptance or new text-reply channel follows from Q23.

**R05 — Stable intent and recovery.** A durable operation has exact source/basis, trusted actor attribution and immutable selected review/feedback/effect intent. Recover an already committed same operation before treating its now-stale basis as a new mutation conflict; authorize any returned details against current disclosure rights. Replays preserve original actor/time and effects. Same identity with incompatible intent conflicts. A later deliberate review is a separately qualified occurrence, not an old retry with refreshed targets. Concurrent distinct keys cannot create contradictory current outcomes or duplicate required follow-up for one source effect. Equivalent already-applied outcomes may converge only where the exact source semantics prove equivalence; outcome label alone is insufficient.

**R06 — Coherent mandatory evidence and follow-up.** Business outcome, required minimal decision/audit evidence and durable selected handoff must be coherently admitted, atomically where sharing the database. External work follows commit. A task projection or optional notification is not the business record, and best-effort logs cannot substitute for required evidence. Recovery distinguishes definitely failed, known committed and unknown commit; no unbounded lock/provider wait or blind new decision. Current read/lookup failure is not absence or success. A failed UI refresh cannot discard a known receipt.

**R07 — Current feedback and safe projection.** Provide meaningful recipient-safe guidance for the exact issue and permitted next step. Do not send internal assessment/raw audit through the financial reason payload or show an unavailable confidential reason as an empty successful response. Current source filtering applies to status, history, counts, task snippets, search/export/help, cached responses and result recovery before disclosure. Delayed projections reconcile source currentness; they may retain authorized historical evidence without overwriting newer current guidance. No review-email default, generic comments feed or forced essay/character count is selected.

**R08 — Q22 and technical-state separation.** A required returned item remains unsatisfied until a real applicable source outcome resolves it. Truly optional work is not a hidden completion hold; actual dependencies remain required. Review return does not itself create a corrected receipt, approve it, complete the request or reopen a fulfilled source. Quarantine/confirmed unsafe, unknown checker, preview unavailability and business insufficiency remain distinct. Do not turn an outage into a business rejection or demand another upload merely to cure processing failure.

**R09 — Current time and access.** Review occurrence is a trusted source occurrence/linearization qualified after relevant waits and whose effect commits; a timestamp sampled early or generic task update is not physical commit proof. Preserve receipt, source review and Q22 fulfillment times separately. Review does not change requested-by target, original/fresh access ends, session/proof TTL or completed-read anchor. Independently authorized source work may continue after recipient expiry; current private feedback and correction remain gated. There is no implicit regrant or retroactive eligibility in the gap.

**R10 — Database and privileged mutation qualification.** Enforce immutable scope/basis/actor/history and permitted transition fields, not only same-tenant row visibility. Test effective browser grants, all applicable RLS old/new-row checks, relevant SELECT/RETURNING paths, constraints/triggers and every authorized service/definer/worker/import path. Same-tenant reparenting, null trusted fields, changed evidence memberships, purpose changes and protected deletion must be rejected or routed through the actual source command. Parent-reference updates must not invalidate preserved relationships. Do not infer protection from a trigger on NEW child rows or an append-only comment alone.

**R11 — Lean bounded operation.** Use indexed scoped item/current-revision/operation lookups, bounded permitted history, existing source intake/processing limits and owned retry/failure recovery. No all-tenant/full-history scan for each return, no per-open permanent lease, no mandatory per-file task, no arbitrary human correction quota. Keep locks narrow and no external rendering/provider call under them. Record measured source/UI budgets before claiming workload support. Internal diagnostics use opaque identifiers and safe codes, not body text, filenames, tokens or private URLs.

**R12 — Release and restoration.** Before activation, all current and older participating writers/readers must recognize exact review/currentness boundaries and preserve source authority. Do not backfill Request changes from finance rejection, generic task dismissal/completion, malware flags, email text or filename/date guesses. Restore source decisions, later restrictions and dispatch identities before resumed outward work; old task/outbox replay cannot reinstate a superseded current result or regenerate a grant. A scoped stop preserves known source receipts and current private rights; this does not require building the full future Workflow Studio.

## SQL precision and privileged-path limits

The inspected adjacent migrations are service-command designs. Their RLS-enable and browser-revoke statements are meaningful; service-role ALL is not a participant policy and must not be mistaken for immutable history protection. No hosted role, effective grant graph, trigger deployment or Postgres version was queried.

For a later native implementation, evaluate effective old/new row checks and privileges, including relevant SELECT and RETURNING. For UPDATE/ALL, an absent explicit WITH CHECK can inherit USING. Applicable permissive policies combine with OR; restrictive policies with AND, and permissive access is still required. Thus neither missing text nor one apparently strict policy proves the whole result. [PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html).

SECURITY DEFINER runs with function-owner privileges. Table owners normally bypass RLS unless forced; superusers and BYPASSRLS roles bypass independently. A set search path, callable roles and trusted arguments matter. Do not call the adjacent SLA function public: its migration expressly revokes PUBLIC/anon/authenticated execution and grants service_role. The service client has no forwarded user token at construction; confirm the actual invoked role/path, not just the SDK label. [PostgreSQL row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Same-tenant existence checks are not immutable evidence/actor/purpose relationships. SQL CHECK allows null unless non-null is separately required, and a check against other rows does not provide continuous cross-row integrity. Use source-appropriate enforced relationships and transition rules rather than assuming a JSON payload or child-only trigger proves them. [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html).

Read Committed rechecks a waited-on target row but does not make arbitrary multi-row source facts one coherent snapshot. Row locks cover retrieved rows, not an absent return row or all future requirement members. Per-key dedupe/lock does not serialize incompatible keys targeting the same source basis. Qualify the actual invariant with appropriate source revision/transaction/constraint protection and bounded retry, without prescribing a universal schema or lock implementation. [Transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html).

NOW/CURRENT_TIMESTAMP denote transaction start; statement_timestamp denotes statement start; clock_timestamp reports the instant called. None is by itself proof of physical commit, and sampling before an authority wait can be stale. Keep the already ratified qualified source occurrence rule rather than prescribing one SQL function as a complete correctness solution. [PostgreSQL time functions](https://www.postgresql.org/docs/17/functions-datetime.html).

## Recommendation and dependency order

**Repeat/overlap policy is the highest-value next unresolved choice.** Q13 authorizes a fresh unfinished capability but deliberately left repeated use open; Q14 now fixes each such effect to a 720-hour nominal unfinished period from its own source issuance. Issuers cannot safely decide whether another fresh effect is allowed after that period without a repeat rule. Q08 completed regrant timing and later operational details are independent and need not precede this fork.

Recommend A: permit another deliberate source-approved finite admission after the preceding relevant unfinished admission has actually ended by eligible ordinary expiry, while the same request remains unfinished, the same intended recipient/purpose/original requirement scope remains eligible, and current authority passes. Apply the already-ratified Q14 profile each time. No automatic renewal, pre-expiry overlap, silent extension or fixed numerical lifetime quota is implied by necessity; if A is offered as **no fixed quota**, state that explicitly as the proposed product choice.

B is credible: at most one lawfully committed fresh unfinished admission per original request context, even if it was unused or expired while staff reviewed. It is simpler and limits repeat exposure, but leaves a still-legitimate request without further recipient access after that fresh period. The help route may use only genuinely authorized other source procedures, not a copied request or changed date to evade the limit.

The preference for A is product judgment: preserve the same business work and immutable evidence while reviewing current need each time. No observed ministry repeat demand or quantitative risk curve supports an optimal count. A removes a fixed lifetime quota; it does **not** guarantee unlimited future approvals. Many deliberate finite grants could nevertheless keep an otherwise eligible request accessible for a long overall span. That cumulative tradeoff must be visible rather than disguised as a single bounded period. Genuine overall/purpose limits still constrain it.

## Scope wording needs one careful distinction

“Same scope” should mean this same intended recipient/request/purpose and the **original admitted requirement/action ceiling intersected with current eligibility and the newly reviewed subset**. It must not mean automatically copying every previous grant's rights, nor silently restricting all later grants to the immediately preceding grant's narrower subset.

Q13 did not make a narrow individual grant a permanent global restriction. A deliberate later review may propose a different otherwise-eligible subset within the original ceiling only through the real current administration/source rules; it does not inherit widening for free. If the founder instead wants every successor to be same-or-narrower than its predecessor, that is an additional substantive policy choice and should be stated, not hidden inside the word “same.” New requirements/purpose/recipient work remains outside this lane either way.

## Minimal sequential-admission contract if A is chosen

Use the existing Q13 source command and P12 mutation boundary. Its input expresses a deliberate new intent against the currently reviewed source/effect lineage. Keep earlier admissions/ends immutable, attach the new effect to its exact eligible predecessor/original context, and retain the required review/outcome evidence. No new renewal queue, counter service, rules engine, periodic auto-grant or grant-settings screen is needed.

The authoritative predecessor/current source state must not be guessed from MAX(id), newest created_at, a client-provided “last grant,” a worker's cached status or the most recent successful email. Source state and the actual ordered admission/effect lineage decide which predecessor matters. A small source-owned head/version or equivalent constrained relation can support this; exact tables/columns are not prescribed.

Before a genuinely new admission, establish that its relevant predecessor ended by eligible ordinary expiry, that no valid unfinished admission for this same repeating context would overlap, and that the source is still unfinished/currently eligible. Apply the already-required source/P12 concurrency fences to those predicates and relevant recipient/requirement/adverse changes. At the old exclusive end the old authority is ended; no positive cooldown is selected merely by saying “after expiry.” Do not invent a global no-other-permission rule for unrelated contexts.

Separate three cases:

1. **Retry of an already admitted intent:** recover that exact original effect/end and current safe result. This remains true even if that grant later expired and another has since been issued. Do not return the newest grant as though it were the original outcome.
2. **A distinct intentional repeat reviewed against the current predecessor:** apply the adopted repeat/overlap and current authorization rules, then admit one new Q14 effect. Different HTTP keys alone do not establish different deliberate business intent.
3. **A stale distinct intent reviewed against an older predecessor:** do not silently advance it to an intervening grant that has now expired. Re-resolve the material source context and require the appropriate fresh review. A long queue wait is not permission to issue the next generation the actor never reviewed.

Concurrent issuers who reviewed the same ended predecessor must not produce overlapping fresh authority. One source outcome wins or the conflict is safely resolved under the selected policy; the other attempt gets the actual authorized outcome/conflict, not an invented retry grant. A row lease or disabled button is insufficient. No provider work happens under these source locks, and no additional global serialization beyond owner-required fences is needed.

An expired status need not await a periodic sweep: actual source time/terms govern. Conversely, changing a status bit early does not create eligible expiry. Current post-wait authority and qualified occurrence/commit semantics remain Q13; this note adds no new clock. Required effect/lineage/audit/follow-up is coherent, and failed lookup/unknown commitment cannot be treated as available repeat capacity.

## Practical boundaries for either option

It has its original Q14 end.                                                                                                                                     |
| Grant never used or recipient proof stayed incomplete                                                | It still was a committed source admission and elapsed on its actual end. | Source outcome cannot be established                                                                 | Reconcile safely. | Prior end reflects genuine revocation, purpose/security cap, source withdrawal or binding shortening | Repeat policy is not an override, including after an adverse cause clears.                                                                                                                                  |
| Only proof or a provider URL expired while current source rights remain                              | Qualified existing recovery, not another fresh source admission.                                                                                                                                            |
| Source completed in a gap after all unfinished authority ended                                       | Source completion stands; no fresh unfinished admission or retroactive completed access. Q08 remains separately bounded by its actual eligibility.                                                          |
| Timely completion happened but a projection still says unfinished/expired                            | Recover the actual original completed result; do not issue a repeat based on stale display.                                                                                                                 |
| A new repeat exists while old callbacks arrive                                                       | Earlier admitted results keep their own lineage; unadmitted old operations cannot borrow the new effect. Retained-byte reuse needs its own current deliberate source admission, as already required by Q13. |
| Another requirement is pending but this item is accepted/frozen                                      | Only currently eligible pending writes; no repeat-driven acceptance reversal or historical-byte rights.                                                                                                     |

For B, “at most one fresh admission” should count a **lawfully committed source admission**, not button clicks, sent messages or recipient visits. A failed delivery does not refund it; definite rollback does not consume it; unknown commitment must reconcile before counting. Wrong issuance/remediation keeps its real history and owner procedure; the count must not be bypassed by deleting records or claiming an unfavorable committed outcome never existed. If B is selected, its exact error/remediation treatment needs explicit qualification rather than a hidden exception policy.

## What this question should and should not settle

The coherent fork is A deliberate sequential re-admission with no numerical lifetime quota versus B at most one fresh admission for this original request context. Both retain Q14's fixed 720-hour profile, current source need, exact eligibility, no overlap/pre-expiry extension, no automation and Q13's completion consequence. A should not be phrased as “unlimited renewal”; B should not be pitched as automatic safer correctness if operators must evade it to complete legitimate work.

Nothing else must precede this fork. Concrete state/schema choices are implementation work under the selected source contract, not another founder questionnaire. No new cooldown, rolling window, cumulative lifetime, escalation/approval ladder, notification cadence, staff date editor, recipient self-service renewal or Q08 expansion should be introduced incidentally. A complete cumulative numeric cap would be a different explicit product alternative, not something the implementation can guess.

If A is selected, later adversarial review should focus on exact predecessor/intent distinctions, concurrent/no-row races, eligibility at source time, recovery of old intents after newer effects, original ceiling versus reviewed subset, history/restore and useful real-world journeys. Existing Q13/Q14 security and serving proof remains binding. No source code, live SQL/RLS, native repeat behavior or browser usability was tested or qualified in this research.

## The practical question

**Which real ordinary document-request workflow should anchor the first retention-policy profile?**

We have settled how an approved policy is applied (Q62), and when its expressly authorized automatic disposal can run (Q63). The missing input is the actual purpose of the records: what staff need the documents to do or decide. A file type, folder, request status or general label such as “missionary documents” does not establish that purpose or its retention rules.

| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Start with one real workflow (recommended when one is known)** | Name one representative existing or genuinely planned ordinary request and briefly explain what staff use its documents to do or decide. If an approved records policy already exists, its name or reference is useful; absence is a valid answer. | Lets us walk one complete staff/participant journey and establish the actual owner and applicable policy before generalizing. Keeps the next step concrete and small. | A single workflow can miss differences elsewhere. It is a reference case, not the only supported launch workflow or a policy applied to everyone. | **B — Start with a short purpose inventory**                         | Give a short list of the ordinary requests actually intended for launch, with a few words on their purpose. Use this route if selecting one representative case would be a guess.                                                                  | Makes materially different purposes visible before choosing the reference case. Useful when the intended scope spans several real workflows.                          | Requires more initial context. **Recommendation: A if you can name the workflow; otherwise B.** Prefer an evidenced, representative ordinary workflow over a hypothetical example chosen merely because it sounds plausible. An existing approved schedule can shorten the investigation, but an unverified schedule is still evidence to reconcile, not automatic authority. The answer can simply be **“A — [workflow], so staff can [outcome]”** or **“B — [short list of intended purposes]”**. A high-level description is sufficient; personal records and sensitive operational details are unnecessary.

This is one context choice. It does not ask Conrad to name database tables, supply an arbitrary number of years, certify legal compliance or solve every exception now. After identifying the real purpose, repository-discoverable facts remain the agent's work. Any material policy decision that genuinely needs its responsible owner will be presented with that concrete context and researched alternatives.

You do not need to classify the workflow as ordinary or specialist. Describe the real work in your own words; the agent will check its owning domain before applying an ordinary policy. If every intended use belongs to another source, record that finding rather than inventing an ordinary use to fit this question.

## Adversarial check

### What could go wrong with this answer?

An attractive example could be mistaken for a real need or generalized into every tenant's policy. Require a real intended use; keep source and applicability explicit. A reference workflow is not a universal class, launch scope reduction or automatic policy approval.

### What hidden assumptions are we making?

We do not yet know the first actual ordinary purpose, whether a policy exists, or whether one example represents the intended launch uses. A is conditional; B makes an ungrounded choice unnecessary. An unknown policy remains unknown, with its responsible owner and affected gate recorded.

### How does this affect the whole product?

It grounds the ordinary policy work while preserving every already-ratified source and consumer. Specialist workflows stay with their owners. Engineering source/native/migration obligations continue and are not deferred until the founder supplies database details.

### How does this affect the end-user experience?

It lets us test whether the normal request, review, summary and recovery language fits real work before adding controls. Staff and participants retain the adopted simple paths; selecting a reference case adds no user-facing step or console.

### Does this follow modern best practices?

Yes, as a research approach: real user outcomes and explicit records purpose/event/action precede configuration. Primary product guidance informs distinctions without becoming legal authority or proof that Asym users have tested the journey.

### Does this fit Asym’s existing repo and product direction?

Yes. It addresses the explicit R-POL input while retaining R-LEGACY and native evidence gates, source ownership, P12/Tenant separation and shared server/UI patterns. It avoids another policy platform, guessed periods, provider ownership or policy-by-filename.

### Should we adjust the recommendation?

Recommend A when a real representative workflow can be named; use B otherwise. Record the user's actual context before proposing the concrete source-policy fork. Do not invent an ADR, glossary term, policy value or answer merely to continue numbering questions. No new answer is selected in this preparation.

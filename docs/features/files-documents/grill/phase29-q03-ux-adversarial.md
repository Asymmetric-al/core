# Phase 29 Q03 — correction journey and UX adversarial review

Inspected 20 October 2026, Asia/Bangkok. Conrad selected Q03 A according to the parent: the intended recipient may send a corrected file for the same unaccepted, correction-open item. This document proposes amendments for review; it does not independently ratify them or create a formal specification. Scope is the ordinary newly admitted native private document request. Existing financial, application, issued-document, publishing and other source regimes retain their rules.

This is official-documentation research and product reasoning. No authenticated comparator product test, real upload, message, permission change, implementation, browser accessibility test or usability study was performed. Recommendations are not evidence that Core currently implements or passes them. Current local owner research and the Q03 question were read to keep the UX within the selected scope.

## Recommendation

Make correcting a pending item a short action inside the existing request: **Send corrected file → choose the file → review the named item and selection → Send correction → truthful receipt and next step**. Keep the request, item, recipient and available context in place. Do not ask for a new account, another request, a mandatory reason, or repeated confirmations for this ordinary correction. Those additions would need a source requirement or user evidence, not an assumption that more friction is safer.

This is a deliberate Asym product choice, not a universal industry default. Dropbox documents sending the correct file again through the same file request, with both uploads reaching the requester. Submittable instead requires the organization to reopen an already submitted application for editing, where edit requests are available; it may decline when review has begun. These are different legitimate product boundaries. Neither proves Asym's exact-version, immutable, source-owned acceptance behavior. [Dropbox](https://help.dropbox.com/share/received-file-request), [Submittable](https://submittable.help/en/articles/904890-how-can-i-edit-my-submission).

Do not make the journey superficially shorter by hiding whether the correction was received, losing the previous result, or letting a reviewer act on a different file than the one they inspected. Clear states and recovery are part of ease of use.

## Recipient journey: precise action, little ceremony

The following is proposed interaction and copy, conditional on the source facts described. Bracketed text is supplied from the authorized item/source; it is not an invitation to expose internal identifiers or unrestricted metadata.

| Moment              | Proposed experience and copy                                                                                                                                                                                                                                                                                                                                        | Important constraint                                                                                                                                                                                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Find the mistake    | In the current item's submission area: its recognizable name, safe filename, received time with understandable timezone, current review status, and **Send corrected file** when admitted. The action may remain available even when preview is unsupported.                                                                                                        | Do not bury a normal repair route in a version-history menu. Overall request-open status does not override item acceptance, freeze or closure. Never infer correction permission from preview permission.                                                                                                          |
| Start correction    | Heading **Send a corrected file for [item]**. Show the earlier submission being corrected and concise text such as **The earlier file will stay in the request record. Staff will review the correction.**                                                                                                                                                          | The second sentence only applies when that source promises review. Retained does not mean the recipient gets permanent history/download access. Use the actual source's terminology for the item.                                                                                                                  |
| Choose the new file | Label **Corrected file**; **Choose file** with optional drag/drop; show the allowed types and actual limit before selection. Preserve the request/item context. Offer a clear **Remove selected file** or **Choose a different file** action.                                                                                                                       | A local selection is not a received submission. Capture actual supported formats from the source/intake contract, not a component demo. Mobile camera/gallery choices are options only where supported; camera capture cannot be the sole path.                                                                    |
| Check and send      | Keep the item name, selected filename, size and any useful format information visible immediately above **Send correction**. Optional local preview can help, explicitly distinguished from server-received readback. Secondary action **Cancel** before sending.                                                                                                   | No mandatory reason or confirmation checkbox for the ordinary profile. A source-specific required declaration remains. Do not force preview completion or scroll-to-the-bottom as proof of inspection. Do not add a second generic “Are you sure?” modal.                                                          |
| Transfer            | Show **Sending correction…** with measured transfer progress where available. Keep the target visible. Prevent repeated sends while this same attempt is being resolved. Provide a legitimate stop/recovery route where supported.                                                                                                                                  | Do not fake percentages or display **Received** at browser transfer 100%. Leaving the page is not automatically a server cancellation. A disabled send button needs a visible explanation, not an unexplained dead end.                                                                                            |
| Receipt and checks  | Under the proposed amendment below, after durable source admission: **Correction received** with the specific file, received time/reference and **Checking file safety**, when true. The correction is the new candidate immediately; the earlier corrected member is no longer eligible for acceptance. Once required checks finish: **Awaiting review**, if true. | Receipt, safety processing, preview readiness and source acceptance are different facts. Technical scanning success is not staff approval. A new correction has no inherited approval. Mere transport completion is not durable source admission. Preserve unrelated supporting files in a multi-file requirement. |
| Return or finish    | Lead with the current authorized result and next useful action. **Back to request** is sufficient when nothing else is required. Provide the approved help route and a reference when relevant.                                                                                                                                                                     | Do not call the entire request complete if other items remain. Do not promise an email, response time or permanent access that the source has not committed to. A bookmarked return must reauthorize and handle expiration without leaking metadata.                                                               |

The filename should be readable, safely rendered and not the only way to recognize the requested item. Long or localized names must wrap or expose their full accessible text without breaking the mobile layout. Multiple requested items need unambiguous targeting; correcting one document must not drop other supporting files. The product should not ask a recipient to understand “CAS,” “superseded object,” “rendition,” or “idempotency” to complete the task.

## Recovery must tell the truth

| Situation                                                 | Proposed message/action                                                                                                                                                                                                                                                                                                    | What must not happen                                                                                                                                                                                                                                     |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wrong type, size or empty selection                       | Explain the exact supported requirement beside the file input and in the submission error summary; return focus appropriately. **Choose a [supported type] file** or **Choose a file smaller than [actual limit]**.                                                                                                        | Generic “invalid file,” silent removal, invented limits, or requiring the entire request to be completed again. Client feedback is a convenience, not security authority.                                                                                |
| Technical upload failure with confirmed non-receipt       | **The correction was not received. Try again.** Retain safe context and the selected file while the browser permits.                                                                                                                                                                                                       | Claim non-receipt if the server result is actually unknown. Do not generate a new correction merely because the same attempt is retried.                                                                                                                 |
| Lost response or network interruption with unknown result | **We could not confirm whether your correction was received. Check status before sending it again.** Provide **Check status** and resolve the existing attempt. If that check is unavailable, explain that limitation and the safe help route.                                                                             | Displaying a green success, a definite failure, or creating a second submission from an ambiguous first outcome. A blanket “just upload again” is insufficient here.                                                                                     |
| Browser refresh/restart loses local selection             | Restore currently authorized request/result context. If there is no durable receipt, explain **Choose the file again to continue**.                                                                                                                                                                                        | Pretending every browser can restore a private file input, or caching confidential bytes persistently on a shared device just to remove a click. Resume is a capability that must be qualified, not promised by copy.                                    |
| User cancels before sending                               | Return to the unchanged request context; no confirmation is normally needed for discarding a simple local file selection.                                                                                                                                                                                                  | Treating cancel as deletion of a previously received file. If meaningful unsaved required text exists, its discard behavior needs separate consideration; do not add such a form solely to justify a dialog.                                             |
| User stops transfer / leaves during an uncertain result   | Resolve whether the correction was committed. Say **Correction not sent** only when confirmed; if committed, show its actual receipt/status.                                                                                                                                                                               | **Cancelled** falsely implying no retained receipt. No generic Undo after receipt that secretly deletes or reverts source state.                                                                                                                         |
| File fails required safety checks                         | **Correction received, but this file cannot be used because it did not pass the required safety checks.** Offer another correction only if currently permitted, or the approved help route. Add a more precise reason only when supported and safe. Keep the genuine received/blocked status and earlier evidence history. | Offering an unsafe download/preview, asking the person to bypass scanning, or claiming deletion. Do not label an unclassified scanner failure as a virus finding. Infrastructure failure is not proof of malicious content.                              |
| Preview alone fails or is unsupported                     | **Preview is unavailable for this file. [Actual receipt/review status].** Keep correction available if currently permitted.                                                                                                                                                                                                | Rejecting otherwise allowed evidence merely because preview failed, claiming the file was never received, or automatically downloading the original as fallback.                                                                                         |
| Same filename                                             | Show the selected file and exact item normally; a filename collision need not be an error.                                                                                                                                                                                                                                 | Treating a name as byte identity, replacing the wrong predecessor, or assuming a suffix is a version relationship.                                                                                                                                       |
| Same bytes as the authorized current submission           | If reliably known and useful: **This appears to be the file already submitted for this item. Choose a different file if you meant to change it.** Treat retries as the same attempt. Do not expose cross-request matches.                                                                                                  | A universal “duplicate, forbidden” rule. Identical bytes can represent a deliberate distinct source act or context; the source, not a global hash, decides whether a new command is meaningful. Do not add a reason form as an automatic exception gate. |
| Acceptance, freeze or closure wins the race               | **This item is no longer open to correction. [Authorized current state and next step].** If bytes arrived without correction admission, state that accurately without implying the source decision changed.                                                                                                                | Blaming the file, silently reopening the item, resetting deadlines, or telling the person to email private attachments to bypass intake. A page view by a reviewer is not itself a freeze.                                                               |
| Session/permission changes                                | Reapply Q01 and the source's current access policy. Preserve only safely recoverable context and show the permitted recovery route.                                                                                                                                                                                        | Broad request or filename disclosure on a denial screen; authentication loops that silently resubmit; automatic extension of source deadlines.                                                                                                           |

**Proposed material amendment, requiring Conrad's ratification:** for this ordinary native profile, once the source durably admits the correction against immutable received bytes and current authority, it atomically records the new candidate/successor and immediately fences acceptance of the exact corrected predecessor member. Hygiene checks and preview generation may still be pending. If required checks fail, show **Correction received — file cannot be used** with the accurate cause and recovery route; do not automatically revive the earlier member or imply that no attempt occurred. Unrelated members/supporting files remain intact. This is a proposed source rule, not a statement of an already implemented capability or a rule for financial/application source regimes.

“Your earlier submission is unchanged” is safe only for the appropriate confirmed pre-admission branch. Selecting a local file, beginning transfer or a failed uncommitted attempt does not establish this amendment's cutover. An unknown result must be reconciled. Following admission, “earlier file retained” must not suggest “earlier file can still be accepted.” The item remains unresolved until the authorized current candidate qualifies and receives the relevant source decision, or another explicit source outcome applies.

## Reviewer journey: no surprise changes under an open document

1. **Enter through the existing request/item task.** Lead with the currently admitted candidate, its attributable submission time and correction relationship, and the real processing/review state. Earlier evidence remains appropriately available, not intermingled as indistinguishable same-name rows. Currentness is a source fact, not “most recent file in a folder.”
2. **Open an exact version.** The viewer label and decision area identify the same file/version. Preview unavailability and safety readiness remain distinct. The reviewer can tell whether the current task is actionable without consulting technical logs.
3. **Handle a correction arriving during review.** Keep the currently open document stable. Under the proposed amendment, show persistent nearby text such as **A correction was received. This earlier file can no longer be accepted for this item.** If it is still undergoing required checks, add **The correction is being checked**. Provide **Open correction** when the permitted view is ready, or the accurate current status/recovery route otherwise. Do not silently replace the viewer bytes or clear unsent notes. Historical readback does not grant current acceptance; this ordinary correction path has no hidden override that accepts the fenced predecessor while the new file is pending or unusable.
4. **Commit an exact decision.** Server authority must reject a stale operation even if no live notification reached the browser. A conflict should refresh the relevant facts and offer the next useful action, not return a generic toast or silently approve another version. If the review committed first, the later attempted correction gets the truthful recipient outcome above.
5. **Preserve useful work without misattribution.** Draft notes remain tied to their original version. A reviewer may intentionally reuse their text, but it cannot silently become a review of the correction. A previous decision never moves to new bytes. Do not build a second review inbox or require a new workflow run just to expose the change.
6. **Return to a comprehensible task result.** Show accepted/needs correction/other source result only after that decision succeeds. Do not convert an upload or scan event into a review decision. Keep read-only history and current action controls visually distinct; use the source's actual correction-request/contact route where needed.

This is an interaction recommendation, not proof that a live push channel, comparison viewer, annotation system, or semantic document diff already exists. A reliable state refresh plus server conflict detection is the minimum truthful behavior; optional live updates must never be the only correctness protection. No automatic line-by-line or AI content comparison is required by Q03.

## Accessibility and low-friction acceptance evidence to require later

Use Core's existing shared UI and source task frame. This recommendation does not authorize a new design system or alternate application shell. A separate page, sheet or dialog must earn its complexity through task fit; do not force a cramped modal because the component preview looks polished.

- Walk the whole correction with keyboard only, touch without dragging, and relevant screen-reader/browser combinations. Check file selection, removal, submission error, progress, confirmation, return navigation and stale-review recovery. The content's accessibility is a separate concern from operable viewer controls.
- Verify useful focus after opening/closing the correction surface, failed submit, successful route transition and stale-state recovery. Background progress should not move focus. Do not allow sticky actions or overlays to conceal the field/action being used; confirm zoom/reflow and long translated strings in the actual shared UI.
- Exercise mobile app switching, slow/unstable connection, refresh during transfer, browser back, duplicate activation, a lost success response, expired session, and concurrent correction/acceptance. Inspect the authoritative result rather than trusting the loading animation.
- Demonstrate correct text for a type error, size error, blocked unsafe file, infrastructure processing failure, unsupported preview, same name, same authorized bytes, and closed item. No generic error should erase the distinction between “not received,” “received but unavailable,” and “not admitted as a correction.”
- Confirm that currentness and decision targets remain exact when another submission arrives while the reviewer is reading. Verify draft notes do not become annotations on different bytes and that stale commands cannot succeed via an old tab.

These are proposed qualification cases, not newly invented numeric SLOs. Existing source qualification limits and operational monitors remain applicable; this note adds no ungrounded file-size, expiry, response-time or alert-count thresholds. A named owner must decide any remaining state/cutover rule before the copy is finalized. No need to make Conrad decide transport mechanics or storage terminology to ratify the product behavior.

## Proposed amendments for the parent to consider

1. Commit to one clear contextual correction action, with enough inline review to establish the target and intended new file. No default mandatory reason, new account, extra request or generic confirmation modal.
2. Ratify the proposed cutover for this ordinary native profile: durable source admission atomically makes the new exact member the candidate and fences the predecessor's acceptance, even while required checks are pending. Failure remains received-but-unusable without automatic revival; preserve other supporting members. Make selected, sending, received/checking, review-ready and source-decided visibly distinct.
3. Treat uncertain results and cancellation as recovery problems. Reconcile the existing attempt; never turn uncertainty into false failure, success, deletion or a duplicate correction.
4. Protect reviewers from silent replacement and stale decisions while preserving their useful work. A correction notice and exact-version server checks belong to the same user promise.
5. Make the correction route usable without successful preview, dragging, a mouse, or stable connectivity. Content accessibility, intake safety and source acceptance remain separate qualification concerns.
6. Keep the scope small: no universal self-service claim, original-download right, permanent history, broad notification program, AI document comparison, general drive, or new workflow platform follows from Q03 A.

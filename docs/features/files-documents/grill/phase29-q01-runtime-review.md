## Conclusion

Use the existing shared Supabase Auth identity/session foundation and source-owned request authority. Extend that foundation's missing neutral-identity/limited-participant slice; do not create a second password/session system, encode request participation as donor membership, or widen Mission Control roles. Authentication proves which account/contact channel is acting; a current request participant grant separately permits a specific action for a specific source/request. Mailbox control is not automatically proof that the actor is the person described by an uploaded document, a legal representative, or allowed to inspect any other file.

The biggest demonstrated blocker is the current account-creation contract: the latest source migration creates a **donor profile role** for each new Auth user. It does not implement a neutral verified participant. Shared context currently requires a profile/tenant/role for application authentication. That must be reconciled through the existing identity owner before A can honestly deliver “verify and submit without becoming a donor.” This is source-confirmed; the hosted trigger deployment is unverified.

## SQL and actor review discipline

- Evaluate actual grants, all permissive/restrictive policies, roles and operation type together. A single policy in isolation is not the effective authorization result. Hosted state was not queried.
- For UPDATE, inspect both the eligible old row and permitted new row plus immutable fields/transition rules. Absence of an explicit `WITH CHECK` keyword alone is not a vulnerability: applicable policy semantics can reuse `USING`. Presence of both keywords alone also does not stop same-tenant reparenting or privilege-changing columns.
- SECURITY DEFINER runs with function owner's privileges. RLS bypass depends on owner/table ownership, FORCE RLS and role BYPASSRLS; do not label every definer function a universal bypass. Here current-user-memberships deliberately supplies a caller-bound window with `auth.uid()`, fixed search path and narrowed grants. Service-only Eve functions instead rely on trusted server actor assertions; those assumptions must remain explicit.
- Service client parameters are not verified user facts merely because TypeScript calls them `AuthenticatedContext`. New browser inputs cannot construct that object. Worker service identity, initiating human, source owner and current recipient grant are distinct facts.
- Same-tenant composite FKs are a reusable database invariant. Also constrain exact request/participant/source/byte-version linkage and prohibit semantic retargeting after issue. A new storage object key must not change business document identity.
- Pure projection contracts can narrow what an already authorized producer emits. They cannot mint an actor, authenticate a request, freshen a stale grant, or substitute for the source permission decision.

## Simplest durable implementation direction (proposal, not a specification)

1. Add the needed neutral authenticated-identity and limited-participant context to the **existing identity foundation**, under its source owner. Keep Supabase Auth as the sole credential/session provider. No donor role as onboarding workaround, custom OTP database replacing Auth, or secondary File Manager login.
2. Let the requesting domain issue the request and own its recipient, purpose, required document/slot, expiry, review/acceptance and withdrawal. Custody handles private transfer, immutable accepted bytes, processing, authorized delivery, physical copies and owner-directed disposition.
3. A small shared command boundary resolves verified actor plus current participant grant, then source permission. Public landing only identifies an opaque continuation. Shared callback/verification resumes it without role-home diversion. The request does not create access to the donor portal, full Party record, other participants, past documents or other source uses.
4. Reserve a new pending object for a finite submission; transfer privately; finalize under exact request/grant/byte constraints. Use source command/outbox and existing workflow claims for retryable processing. Inspection clearance is separate from source acceptance; neither a successful upload nor a valid email changes business facts.
5. Keep participant upload-only access minimal. If the accepted journey later permits viewing submitted files or requesting corrections, introduce only that explicit source-qualified read/revision capability. Do not infer it from ownership of the upload key or “verified” badge.

This slice should not wait for every future identity/file consumer to ship, but it must use the accepted identity contracts rather than establishing a parallel identity model. Any change to who verification proves, whether guests can view submissions, or how recipients are replaced is a genuine founder/owner decision, not minor hardening.

10. **No collateral affiliation:** taking part in two requests from different sources/tenants does not merge Parties, grant a donor portal, reveal other uses or choose a default tenant. Reassigned contact/email does not inherit old access merely by matching a string.

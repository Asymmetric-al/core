## Current primary technical facts resolved

The Supabase skill, nested backend/Supabase guidance and Auth/Postgres skills were read. Their implementation/mutation steps are inapplicable to this read-only task. No install, SQL or reset was performed. Current docs override overbroad shortcuts:

- PostgreSQL17 `ALL`/`UPDATE` policies can derive WITH CHECK from USING when omitted; permissive policies OR and restrictive policies AND. Resulting rows include BEFORE-trigger changes; actual command requirements and grants matter. We preserve Core's one fine-grained PDP and prescribed coarse Tenant RLS, not a tutorial per-user policy engine. [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html)
- DEFINER executes with its actual owner's privileges; owners normally bypass table RLS unless FORCE applies, while superuser/BYPASS remains different. PUBLIC/named/inherited/default EXECUTE, schema usage, overloads and search_path must be inspected; “all DEFINER bypasses” and “all public functions callable” are not universal truths. [Row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html)
- Supabase sessions/JWT policy changes may not take effect until refresh/expiry; current sensitive source authorization cannot be inferred solely from retained claims. The session_id check is a credential-session fact, not a source permission. [User sessions](https://supabase.com/docs/guides/auth/sessions)
- Storage RLS grants upload/overwrite operations; overwrite additionally needs SELECT/UPDATE. Public bucket bytes are public independently of a private-looking app route. Storage metadata is not object bytes; write/copy/delete through the API, not SQL deletion. [Access control](https://supabase.com/docs/guides/storage/security/access-control), [schema](https://supabase.com/docs/guides/storage/schema/design)
- Supabase database backups exclude Storage object bytes. A metadata restore does not restore deleted objects. Supabase S3 compatibility currently lacks bucket versioning/Object Lock, so a native bucket-version/WORM assumption is false. This does not prove the existing adapter cannot meet an exact app-owned immutable/hold protocol; it requires actual design and proof, not a new vendor by default. [Backups](https://supabase.com/docs/guides/platform/backups), [S3 compatibility](https://supabase.com/docs/guides/storage/s3/compatibility)
- Resumable upload URLs are per upload, valid up to24hours; same-path concurrency differs with upsert, which makes last completion win. Those are transport facts, not a current source-admission grant. The example6MiB chunk is a current protocol requirement/example constraint, not an ordinary-file size policy. [Resumable uploads](https://supabase.com/docs/guides/storage/uploads/resumable-uploads)
- Signed Storage URLs are separate from Auth signing keys. Current SmartCDN documentation states token expiry and cache TTL are independent; cached delivery can outlive token expiry and invalidation has propagation delay. Core must prove its required current read/cutoff on every actual serving path. Deleting independently held/shared evidence merely to revoke a single reader is not a lawful shortcut. [Serving](https://supabase.com/docs/guides/storage/serving/downloads), [Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn)
- Cloudinary's private delivery type protects the original while derived outputs can be public by default; authenticated delivery has different behavior. Neither label supplies Core's current source permission or safe transformation/egress profile. [Cloudinary access control](https://cloudinary.com/documentation/control_access_to_media)
- Current Supabase remove API accepts at most1,000 objects per call; ordinary cleanup must use a smaller/equal qualified bounded batch plus reference/hold/writer/admission fences, not SQL metadata deletion or a whole-bucket sync recipe. [Delete objects](https://supabase.com/docs/guides/storage/management/delete-objects)

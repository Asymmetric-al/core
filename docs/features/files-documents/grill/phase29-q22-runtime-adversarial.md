## Verdict and narrow meaning

Accept A with the existing source-owned boundary strengthened for aggregate safety and recovery. The substantive new contract is: **the source must reliably establish one durable fulfillment outcome when the admitted ordinary request's full current rule is satisfied, while refusing unknown, incomplete or inapplicable predicates**. No extra final staff acknowledgment, automatic evidence approval, global completion flag, task-based writer or general workflow engine is needed.

Q21 staff acceptance remains necessary for ordinary file evidence and insufficient to bypass other conditions. Exact source-authorized non-file/waived/not-required outcomes remain. “All” means the complete source predicate for that request, not all visible files, all rows a particular viewer can see, a received count, historical accepted flags, a task list or every optional piece of work. A changes the ordinary source's completion policy; it does not remove a genuine separately required specialist final decision.

Source fulfillment, participant completed-read admission, current access and later task/notification presentation remain separate. A lawful business fulfillment can exist without participant read admission. No timestamp or successful background job can manufacture the missing admission.

## The new aggregate risks

| Failure                                                              | Severity / likelihood      | Exact prevention                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Two concrete future race cases are particularly important:

1. **Missed completion:** T1 accepts required item A while its snapshot sees B pending. T2 accepts B while its snapshot sees A pending. Both commit. If neither source path performs a properly ordered aggregate recheck or guarantees qualified durable reevaluation, the request can remain unfinished despite true conditions. This is a liveness failure under A, not a reason to add a fallback manual Complete button.
2. **False completion:** A finalizer sees all current members satisfied, then another permitted mutation adds a required item, changes instructions/current applicability, admits a relevant correction or cancels the request before the finalizer writes completion. Without a common relevant source boundary, the finalizer can complete the wrong state. This is a safety failure; a generic per-run worker limit or per-key dedupe does not solve it.

These cases are reasoning counterexamples, not executed native SQL tests. Implementation may use a suitable source revision/CAS/short transaction or other proven owner-compatible mechanism; this review does not mandate a table layout, isolation level or distributed lock framework.

## Nine essential technical clauses

### S01 — Complete actual predicate, not a visible aggregate

The ordinary source MUST explicitly own the selected automatic fulfillment policy and the complete current predicate for its admitted request. Evaluate current lifecycle/eligibility, definition and material revision, applicable required item/condition membership, exact current accepted evidence and remaining source conditions. Q21 staff acceptance stays necessary for ordinary file evidence, with existing qualified non-file/waived/not-required alternatives preserved. Neither custody nor a workflow/task projection can invent that predicate or waive a condition.

Differentiate true, false and unknown. Unknown/failed/partial reads, absent definitions, filtered or paginated results, inaccessible metadata and stale caches cannot establish fulfillment. A draft, canceled/withdrawn or otherwise ineligible request cannot fulfill because its required-row query returns zero. A legitimately known no-file/all-waived source outcome can qualify only under the explicit source predicate; do not impose a new universal minimum file count or silently treat every empty set as valid.

### S02 — Optional work and existing source closure

Only actual current completion conditions may hold the ordinary request open. Optional submissions, independent supporting work, a failed task projection, email delivery or renderer work are not made required by this decision. Conversely, work genuinely required by the source remains required even if it is not a file or visible to the current reviewer.

When fulfillment wins, preserve Q06's ordinary participant mutation closure and source-owned treatment of pending/optional work. Do not automatically accept an optional file, turn a technical outage into rejection, erase an admitted receipt, delete promoted bytes, revive the predecessor or fabricate a waiver. Already admitted evidence/processing can continue only under its independent source/custody authority. A temporary transfer or browser selection is not a committed submission. Explain relevant consequences within the existing context without selecting a new optional-work policy or new remedy.

### S03 — One source aggregate boundary with no lost transition

All relevant mutations that can change the complete predicate or request eligibility MUST participate in the source's qualified concurrency/recovery protocol: final item acceptance, other required condition resolution, changed requiredness/instructions/membership, permitted waiver, correction admission, current evidence invalidation, cancel/withdraw/freeze and source-authority changes. Preserve Q03/Q21 exact evidence semantics; no stale finalizer can count the superseded predecessor or silently rebase a decision.

Prove both false-completion prevention and eventual automatic fulfillment once the full valid predicate holds. Include concurrent final changes, no-row/first/empty cases and membership phantoms. A worker concurrency limit, only item-row locks, per-key unique record or isolated `status = pending` update is not enough by itself. Use no broader lock scope than the real aggregate requires; independent reading/review and unrelated requests/tenants remain independent.

A delayed wake is a locator, not authority. Recheck exact current source facts unless reconstructing an already committed historical outcome from sufficient proof. Where deferred processing is actually needed, use the existing durable handoff and qualified recheck/reconciliation pattern so neither registration order nor a lost wake strands work. Do not install a new timer or generalized scheduler to compensate for an incomplete mutation boundary.

### S04 — One coherent durable fulfillment effect

Record the qualified source fulfillment effect, exact predicate/revision/evidence basis, trusted causation/time, intake closure/current source transition, historical recipient-admission decision/evidence where applicable, required audit/history and required follow-up intent coherently before claiming fulfillment. Prefer the owning source boundary that establishes the final condition where those facts share a transaction; qualify any actual split boundary rather than assuming sequential application calls are atomic.

A proven item acceptance remains a valid item fact if later fulfillment is blocked or unresolved; do not falsely undo it or ask for repeated review. But an “all conditions true” projection is not itself an admitted fulfillment effect. If the required fulfillment write fails or commitment is unknown, preserve the actual source state, record/recover under the same semantic intent and show truthful finalization/unresolved status. Providers and expensive processing stay outside locks. Known source fulfillment survives downstream task/communication/refresh failure; no new completion email follows from Q20.

### S05 — Qualified F and eligibility, not observer time

F is the one qualified actual source fulfillment occurrence whose effect durably commits, with the historical conditions needed by Q07/Q10 and later fresh-source policies. Do not substitute browser click, upload receipt, scan completion, final item timestamp, mutable task `completed_at`, transaction-start time, queue time or consumer refresh. Re-prove current source state and any time-sensitive predicates after relevant waits under the qualified linearization convention. A sampled SQL function does not automatically identify physical commit time.

If the final source-condition transition establishes fulfillment coherently, delayed consumers may recover that original proven F and original recipient-admission outcome. If it did not establish a fulfillment occurrence, a later complete-looking snapshot cannot retroactively create one; qualify the actual later transition. Prove boundary cases spanning the unfinished end, later material waits, rollback and unknown commit. No arbitrary new clock/precision or universal SQL function is prescribed.

Business fulfillment can remain lawful after participant authority ends. Record it without backdating or creating a completed-read admission that was not valid at the actual qualifying occurrence. Existing original/fresh eligible fulfillment routes, independent caps and present disclosure restrictions remain. No retry, copied task timestamp, readback repair or notification can reset F or its access end.

### S06 — Stable replay and trusted authority

The source's automatic consequence must be explicitly qualified for this exact purpose; item-review authority is not a standalone capability to complete arbitrary requests. Derive tenant/environment/source/request, causal condition/actor or source-service identity and permitted action from trusted context. A queue payload, task assignment, string subject ID or claimed staff actor is not authority. Preserve the actual human acceptance actors separately from source/worker causation; an asynchronous fulfillment is not a fictitious extra human Complete action.

Use permanent semantic fulfillment identity and immutable material comparison. Recover matching committed work before applying new-admission/current-unfinished checks, with current permission for the response. Different tabs/keys/workers/condition events cannot create duplicate fulfillment, change original F or repeat source side effects. Changed material cannot silently reuse an unrelated effect. A fulfilled request is not reopened by reset, retry or a new event; later invalidation follows owned remediation without rewriting historical truth.

### S07 — Effective data and privileged-path protection

Qualify exact same-scope request/requirement/accepted-occurrence/condition/fulfillment relationships, required values and state transitions, semantic uniqueness and immutable original outcome fields. Review final rows after BEFORE-trigger transformations, UPDATE/upsert, allowed deletes/cascades and parent moves; an ID existence or tenant-only check is not the full relation. Current authoritative head/state and historical evidence must remain coherent.

Evaluate actual table/column/function grants, RLS old/resulting-row predicates and policy composition, views/RPCs/SECURITY DEFINER owner and EXECUTE/search path, service clients, jobs and storage. UPDATE/ALL can inherit USING as effective WITH CHECK when omitted; missing text alone does not prove bypass. Definer bypass depends on owner/table/role/FORCE/BYPASSRLS posture. Service-backed source commands require their own trusted authorization/invariants; browser-deny RLS or mocked roles are not complete proof.

RLS and row CHECK constraints do not automatically establish the cross-row full predicate or its timing. Qualify insert/delete membership paths, empty-set races, current authority changes and any stored summary used for completion. A summary/counter used for authorization must be owner-maintained and transactionally consistent with the relevant source changes; no stale or client-maintained count is sufficient.

### S08 — Honest bounded presentation and operation

Show actual item acceptance, remaining source work and known request fulfillment separately. Where a final meaningful action can complete the request, make that consequence clear without an unqualified promise from a stale screen or a new routine confirmation. Preserve already-known acceptance when request finalization is unresolved, and recover the original outcome after lost response. Current history/status/metadata disclosure remains gated even after business completion or participant expiry; a safe generic remaining-work explanation need not disclose hidden conditions.

Use bounded indexed current predicate/semantic-effect lookup and authorized paginated history, with the existing source/transport workload and recovery owners. Avoid request-time full-history reconstruction, per-condition provider I/O under locks, unbounded fan-out and tenant-wide mutexes. Overload or an exhausted handoff budget cannot mark a request fulfilled or erase source work. No fallback manual Complete override, automatic evidence acceptance, arbitrary grace period or new dashboard is introduced; implement source-owned repair of a failed automatic path.

### S09 — Prospective activation, retention and restore

Activate only an exact qualified native cohort and source policy. Old UI/worker/schema paths cannot bypass the predicate or infer historical fulfillment from accepted/file/task booleans. A migration/default must not retroactively complete old requests or invent F, actor, exact required set or recipient eligibility; adopt any historical migration only through separately authorized source evidence and policy.

Preserve accepted evidence, source outcomes, minimized required history and later adverse facts under retention/hold/disposal owners. Fulfillment is not deletion or indefinite storage. Backup/restore/import/compaction cannot revive a canceled request, superseded evidence, expired recipient rights or already-applied effects. Reconcile authoritative source state and later restriction/fulfillment evidence before new mutation or serving; unknown lost proof is not an unfinished blank slate. Existing scoped stop/roll-forward controls preserve actual receipts/acceptances/completion and safe independent operations rather than “rolling back” business history.

## Official technical verification and limits

Current primary PostgreSQL17 pages were re-read; they establish platform semantics, not a queried hosted version or a tested native implementation.

- [Transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html) explains snapshot/serialization behavior. Separate condition reads and updates cannot be assumed to observe one common aggregate state; retrying an aborted transaction must preserve semantic intent and avoid external effects.
- [Explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) explains row-lock behavior and wait effects. Selecting existing members does not lock a nonexistent future member. The invariant needs a qualified source protocol rather than an arbitrary “add FOR UPDATE” prescription.
- [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html) confirms effective USING/WITH CHECK, composition and BEFORE-trigger ordering. Role/grant/privileged qualification is still required.
- [Date/time functions](https://www.postgresql.org/docs/17/functions-datetime.html) distinguishes transaction-start/statement/actual clock values. It does not define Core's F or physical commit time; the source must qualify causal occurrence and durable commitment.

No runtime test, artificial mirror model, real-role SQL, provider/custody operation, browser/AT or intended-user exercise was performed. The concrete code observations and prospective race cases are explicitly separated. Only this research note was written. No extra completion mode, requirement/waiver/routing/remediation taxonomy, notification, time value or infrastructure choice is selected here.

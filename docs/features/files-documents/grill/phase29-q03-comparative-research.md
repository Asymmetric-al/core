# Phase 29 Q03 — correcting a submitted file

Research inspected 2026-10-20, Asia/Bangkok. Q02 A and its amendments are ratified according to the parent. This note prepares the next founder decision; no answer is presumed. Scope is the ordinary newly admitted private document-request profile, not changes to official receipt, expense, publishing or other established source regimes. Research only: no real messages, submissions, provider writes, account changes or product tests.

## Recommendation and question priority

Correction is a useful next decision. Q02 now lets a recipient inspect what arrived; the natural next situation is discovering that it is the wrong scan or an incomplete document. A viewer without an understandable repair route leaves the chosen journey unfinished.

The highest-leverage issue is **when the recipient may submit a correction without staff permission**, rather than whether the old bytes should be overwritten. Immutable received evidence and source-owned acceptance already constrain the latter. “While the request is open” is not sufficiently precise: a multi-item request can remain open while one document requirement has already been accepted or frozen. Tie the default correction opportunity to the particular requirement and current source authority.

Recommended default: let the intended recipient send another immutable submission for the same unaccepted, correction-open requirement. Preserve the earlier submission and its decisions; label the relationship and the new pending candidate clearly. After that requirement has been accepted, frozen, closed or its correction authority ended, require an accountable source-owner reopening/new correction opportunity. This is a product judgment, not a behavior established by every comparator.

Do not silently add a rule that merely opening a document for review permanently prevents correction. That would introduce a hidden staff-presence cutoff. If the source needs such a freeze it should be explicit and visible; otherwise exact-version review and race handling must prevent a decision on an old candidate from silently becoming approval of the new one.

## Practical founder alternatives

| Option                                                                        | Ordinary recipient experience                                                                                                                                                                                                 | Tradeoff                                                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Self-correct before acceptance; staff reopens afterward (recommended)** | While this requirement is still correction-open and unaccepted, choose a clearly named correction action and send the right file. After acceptance/freeze/closure, ask the source owner to reopen the correction opportunity. | Fast recovery from simple mistakes with a clear point of stability for staff decisions. Requires exact-version review and correct handling when acceptance and correction race.                                                                                                                                |
| **B — Staff opens every correction**                                          | After any submission, ask staff for permission before sending a replacement candidate. Staff explicitly opens the correction window.                                                                                          | More stable review packets and simplest recipient permissions, but ordinary mistakes create delay and staff workload. Useful for source processes that intentionally freeze at submission.                                                                                                                     |
| **C — Propose corrections throughout an open request**                        | The recipient can send a new correction candidate even after the individual item was accepted, while the overall request continues to admit corrections. Staff decides whether to change its accepted selection.              | More flexibility when documents evolve; more concurrent candidates, review obligations and potential confusion about whether an accepted requirement is still satisfied. Needs especially clear distinction between accepted evidence and pending correction. Not an automatic change to the earlier decision. |

Every option preserves current permission and exact immutable submissions. None permits overwriting/deleting the original, automatically changing an accepted business fact, or altering another person's submission. Stricter existing source contracts remain in force. C is a genuine broader option, not an unsafe strawman, but adds lifecycle work that the ordinary wrong-scan case may not need.

If two options are preferable for cognitive load, A versus B covers the main product tradeoff. C can remain a researched alternative rather than widening the first question unnecessarily.

## Meaning that must remain clear

- **Same-name renaming:** avoids filename collision. It does not say which requirement a file satisfies, which submission it corrects, or which version staff accepted.
- **Another submission:** a newly received act with its own bytes, actor, time and result. Its relationship to the earlier submission must be explicit where it is a correction.
- **Correction candidate/revision:** a new submission offered to address an earlier submission or the same requirement. It does not erase history or automatically inherit approval.
- **Replacement in the current working view:** the product may lead with the relevant new candidate, but that is a source-owned presentation/currentness choice, not overwriting received bytes. Prior decisions remain tied to the version actually reviewed.
- **Withdrawal or deletion:** different operations. Reporting “I sent the wrong file” or “please do not use it” does not necessarily authorize erasure of retained evidence. Source privacy/retention/disposition rules decide the outcome; avoid promising immediate irreversible deletion.
- **Another supporting file:** can supplement rather than correct. The interaction should make the recipient's intended effect clear without forcing technical version terminology. A correction must not accidentally remove a separately required supporting document.

Q01 identity confirmation and Q02 own-submission preview do not grant this mutation by implication. The source authorizes the new correction command; the byte intake still passes its own scanning/processing qualification. A recipient may be allowed to correct a submission even if its preview is unavailable, so successful preview must not become a new prerequisite to safe correction.

## Necessary consequences of the recommendation

These are implementation/product implications to pressure-test after the founder answer, not a formal specification:

1. Show the exact item being corrected and preserve the earlier submission reference. A filename or digest alone cannot choose the target or merge separate evidence.
2. Do not switch the active candidate on file selection or failed transfer. Distinguish correction started, received, processing, available for review and accepted. Preserve the prior truthful outcome if transfer/processing fails.
3. A correction does not restart a business deadline, extend access, reopen a closed requirement or make a late submission timely. Those remain source decisions.
4. Staff decisions bind exact versions and relevant requirement revisions. When a new candidate arrives during review, staff must not unknowingly approve different bytes. Resolve concurrent acceptance versus correction through one authoritative outcome with useful recovery.
5. Retry/lost-response recovery must return the original correction result without creating another submission. A deliberately new correction has a new intended effect; identical bytes may still have distinct provenance/context.
6. Correction and earlier-submission visibility remain separate. Retaining an old submission internally does not automatically give the recipient permanent version-history/download access. No new public or cross-recipient access follows.
7. Where correction is not currently admitted, show the source-approved route for requesting it. Avoid “email the file to staff” as the default bypass of private intake or a requirement that staff impersonate the participant.

## Suggested question context

“Someone opens the scan they just submitted and sees that they sent the wrong page. Should they be able to send a corrected file themselves while that particular item is still awaiting acceptance, or should staff have to open every correction? I recommend letting them correct it themselves until the item is accepted or explicitly closed. The new submission would be clearly linked to the earlier one, which stays in the history; staff would never approve one file and unknowingly have it changed underneath that decision.”

This offers one meaningful founder-level decision. It does not ask them to design storage APIs, choose a revision schema or decide every retention rule at once. The exact source review/acceptance state must be named before implementation, but that clarification belongs with this question rather than an unrelated vendor/architecture detour.

## What might outrank this next question?

If the parent finds that the ordinary native request has no accountable source owner or no defined acceptance authority at all, that ownership must be resolved before a correction policy can be ratified as an operational contract. The existing Q01/Q02 source-owner seam may already provide enough direction for this bounded decision. General-resource stewardship and platform-wide retention remain important later branches, but they do not automatically outrank finishing this immediate recipient journey. No broad future application product should become a prerequisite for native correction intake.

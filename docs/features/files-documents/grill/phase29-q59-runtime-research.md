# Q59 runtime research — personal resource saving

27 October 2026. Q01–Q58 are ratified. Q59 is an unselected researched question, not an ADR, implementation or new permission. Only this task-local note is written. The lifecycle cautions below are research inputs for a later selected-answer review, not independently ratified safeguards.

## Recommendation and remaining fork

The strongest bounded next choice is **A — optional private Save for later for organization resources**, alongside normal search/navigation, versus **B — use the qualified library's search, filters and navigation without an in-product saved-resource list**. A can help a reader return to particular guidance without rebuilding a query or remembering its title. B avoids another personal preference and its recovery/maintenance behavior. No measured Asym demand, repeat-use frequency or time saving has been established.

The source object should be an actual P28/Q58 organization-resource publication, not a storage object, generic file, Support guide, CRM row, search result snapshot or personal copy of content. The natural proposed meaning is a private reference that resolves the publication's **current permitted source state** when reopened. It is not an old-version byte archive, offline download, automatic successor grant, subscription, task, training acknowledgment, report, review or proof of reading. The precise saved-identity/current-head, loss-of-access and personal-scope behavior must be settled in the selected-answer review if A is chosen; a browser bookmark icon does not settle them.

This is distinct from existing capabilities. P23 already permits favorite **Saved Library View definitions**, P26 has Support views/replies, Q42/Q43 cover organization/views for ordinary request evidence, and CRM has personal gift-history view settings. None selects a reader's private list of P28 resource publications. Broader resource readership, publication ownership and common-versus-independent editions were just settled by Q58 and should not be reopened. General reminders, automatic recommendations, staff popularity analytics and a new collections platform would be larger unrelated choices. A small private save/remove/list convenience is therefore the better next question.

## Technical evidence and limits

Current [MDN localStorage documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) was read on 27 October. It describes origin-specific browser storage, persistence across browser sessions, private-session clearing and possible policy-denial errors. That explains why local persistence and a UI saved state do not establish authenticated cross-device source behavior or current authorization. This is not a prescription to add a new storage system; exact native persistence can reuse qualified shared mechanisms.

No schema, hard quota, retention period, sorting default, toast/undo policy or exact unavailable-resource state is selected here. Those are bounded details for the full review after the founder chooses the capability. A reference-based personal list can be modest, but actual source/identity integration, private data handling and current queries remain required engineering. No implementation, Supabase mutation, provider action, browser test, synthetic model, repository test or live billing inspection occurred. Full consolidated-question review is pending.

## Historical question and alternatives

**When staff share a clarification reply, should an optional email telling the
request recipient about it start On, start Off, or be omitted from this phase?**

Q30 supplies the native item conversation and accountable handling. It expressly
does not select an email notice. A/B below would add that exact participant
awareness capability; they are not switches on an already-authorized Q30 event.
Incoming participant questions and supplementary staff alerts remain a separate
unresolved decision. Q27's evidence-review email default does not answer it.

| Option                                                         | Everyday experience                                                                                                                                            | Benefit                                                                                                                   | Tradeoff                                                                                                                                   |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **A — Notify by default, with staff control (recommended)**    | When an eligible staff reply is shared, a visible “Email the request recipient about this reply” choice starts selected. Staff can turn it off for that reply. | Someone who left while waiting for an answer can learn to return without staff remembering a separate contact step.       | Preselection can be overlooked; short acknowledgments can create unnecessary email. Even a neutral notice can reveal a relationship.       |
| **B — Keep this email opt-in for each reply**                  | The same optional notice is available, but its per-reply choice starts unselected.                                                                             | Staff consciously choose each outward cue; useful when they already communicate through another effective approved route. | Staff may forget to notify an absent participant. It requires essentially the same delivery and recovery capability as A.                  |
| **C — Keep replies in the request without a new email notice** | Participants see the answer on returning while authorized. Staff use an existing approved contact/help route when needed.                                      | Avoids this additional outbound purpose and its delivery burden.                                                          | Participants must return or staff must deliberately follow through elsewhere. It cannot mean an invisible answer or an unowned help route. |

**Recommend A.** An asynchronous question often outlives the visit in which it
was asked. A useful return cue belongs beside the staff reply, with a simple
way to skip it. This is a product judgment supported by comparable patterns,
not a measured Asym outcome or a universal rule that email should start On.

For a fair A/B comparison, both propose the same optional notice capability:
the initial qualified tenant plan offers the eligible step, and authorized
tenant administrators can disable it through existing bounded System Messages
controls. A/B differ in the initial **per-reply** choice. A staff checkbox cannot
override Tenant Off, suppression, source restrictions or an unavailable recipient.
These three options are product alternatives, not three new tenant modes.

## Concrete example and user journeys

Nora asks which dates a certificate must cover and leaves the request. Elena
answers the next morning in that item's existing conversation. A can send a
minimal approved cue to return to the protected request. It does not email the
answer, certificate name, private explanation or attachment. If Elena has just
spoken with Nora, she can uncheck the notice while posting the same reply.

| Journey                                                                                            | Required experience in the proposed choice                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Participant has left while awaiting an answer                                                      | A offers a permitted return cue; B requires staff opt-in; C depends on return or approved manual follow-through. No option claims the participant has read anything.                                                                   |
| Staff send a brief acknowledgment or already contacted the participant                             | A/B have one clear per-reply control in the source composer. No second message wizard or obligatory confirmation modal.                                                                                                                |
| Tenant disables mail, contact is missing/suppressed, or sensitive source rules prohibit the notice | Explain availability to authorized staff without exposing private recipient data. Lawful native reply and accountable source work remain usable.                                                                                       |
| Notice was requested but becomes blocked                                                           | Preserve the actual choice and show the independent notice result. Do not relabel requested-but-blocked as staff choosing Off.                                                                                                         |
| Reply succeeds but the response is lost or email fails                                             | Recover the original native result and notice status. Do not make staff post the reply again to retry email. No duplicate message or renewed access.                                                                                   |
| Access ends before dispatch                                                                        | Do not promise that an unavailable answer can be read. Suppress the inapplicable notice unless an independently qualified useful variant actually exists; no automatic help variant or fresh-access grant is selected.                 |
| Access ends after the notice is submitted for delivery but before the recipient opens email        | The protected entry point gives the current truthful outcome and existing approved help path. An already in-flight notice cannot be recalled and does not preserve access.                                                             |
| Participant returns with email Off                                                                 | Currently authorized shared replies remain available through the native request. Email Off changes awareness, not the source record or fulfillment criteria.                                                                           |
| Staff use a small screen, keyboard, screen reader or an unreliable connection                      | Use existing accessible controls; make the outward consequence clear, preserve permitted draft/choice/focus on recoverable failure, and distinguish posting from queued/failed/unknown email. No offline private draft store is added. |

Use a clear label such as “Email the request recipient about this reply,” with
only an authorized destination summary. Keep it beside the existing deliberate
reply action. Native reply success, notice requested/queued, provider acceptance,
delivery and unknown outcome are different facts. Neither delivery nor a click
means reading, review acceptance, resolution or completion. The email must make
clear that the conversation is in the request; replying to email is not newly
supported. Apply current locale/time-zone presentation and international text
handling without inventing a separate notification design system.

## Current primary research and strongest alternatives

- [FileInvite's client-message controls](https://help.fileinvite.com/edit-your-email-sms-messages-to-clients)
  explicitly include **Message Reply Received** and allow client messages to be
  turned On or Off. This is direct precedent for a configurable reply notice.
  It does not prove a per-reply checkbox or its default. FileInvite's separate
  knowledge-base editions must not be combined into one tested behavior.
- [Submittable's submitter notifications](https://submittable.help/en/articles/4926006-what-notifications-should-i-expect-to-receive-from-submittable-as-a-submitter)
  include organization replies and permit ordinary email notifications to be
  turned off, with activity checked in the product. This supports reply
  awareness and an email-off path. Its account-level recipient preference is
  different from the proposed staff choice and does not justify adding a new
  Core preference center.
- [Content Snare's publish choices](https://contentsnare.com/help/knowledge-base/step-5-publish-send/)
  distinguish stopping automatic reminders from sending no messages at all;
  [its FAQ](https://contentsnare.com/help/knowledge-base/reminders-faq/) makes
  manual follow-through explicit when client email is off. C is therefore a
  credible narrower product alternative, with a real operational cost.
- [Content Snare's comments](https://contentsnare.com/help/knowledge-base/comments/)
  establish contextual questions and replies, but do not establish that every
  staff clarification automatically emails the participant. Its staff email
  preferences are also not evidence for a participant default.
- [Submittable Messaging](https://submittable.help/en/articles/2489806-how-does-submittable-s-messaging-feature-work)
  includes body delivery and email replies. Those broader capabilities require
  their own source, disclosure and intake contracts. Q31 proposes only a minimal
  awareness cue and preserves body-free communication history.

The strongest alternative is B: the same useful capability with deliberate
opt-in protects against inattentive preselection and acknowledgment noise.
Its disadvantage is missed awareness, not technical inferiority. No source or
observed Asym usage proves the optimal default, email-reading rate, completion
improvement or acceptable notice volume. Test actual participants and staff on
useful replies, already-contacted cases and low-value acknowledgments before
claiming those outcomes. Keep privacy-sensitive source cases in that proof.

## Repository reconciliation and scope boundaries

The [owner research](phase29-q31-owner-research.md),
[runtime research](phase29-q31-runtime-research.md) and
[comparative research](phase29-q31-comparative-research.md) contain the source
anchors, full incorporated contract checks, examples and limitations.

1. **A new exact meaning, not a borrowed trigger.** A genuine newly committed,
   deliberately shared staff clarification can own this notice occurrence.
   Q20 fresh access, Q26 Request changes and Q27 first-actionable evidence stay
   distinct. Drafts, autosave, private notes, reads, retries and incoming
   participant text do not create this staff-reply notice. Q30-C11/P20's
   reservation would be narrowly resolved only for this participant purpose.
2. **Source authority first.** The native source owns reply, item, participant,
   current sharing scope and purpose. P12 supplies current trusted authority;
   P17 owns the qualified meaning/plan/presentation; P6 owns delivery and
   body-free history. Matching addresses, source assignment, Support routes,
   a caller-supplied tenant/recipient or provider credentials confer no right
   to disclose or send. Qualify Q01's exact closed participant branch without
   manufacturing a Party, account or new access grant.
3. **A minimal cue with a qualified protected action.** Source-approved subject,
   preview, body and metadata must exclude private reply text, file content,
   filenames, private notes, sensitive request/item labels and attachments.
   Even neutral sender/relationship information needs source permission. Use
   the actual qualified protected doorway, never an arbitrary storage URL or
   public deep link. Reprove relevant authority and useful action at admission
   and use. Do not extend a clock, reopen completed work or expose completed
   conversation history to make a notice useful.
4. **One native act, independent notice outcome.** Commit source truth and the
   selected intent with its required recoverable handoff. Use the original
   semantic occurrence, choice, plan and recipient binding on replay. Missing,
   legacy or ambiguous input is not guessed On. Optional email suppression,
   delay, failure or uncertainty cannot erase native success. A proved zero
   notice result differs from unknown handoff or compilation. P6's complete
   bounded release and exact prepared-provider recovery remain required.
5. **Tenant policy is not a mutable replay instruction.** General P17 plan
   edits are future-only; admitted work retains its pins. Q26/Q27 separately
   ratified purpose-specific Tenant Off narrowing for unsubmitted work. Q31
   does not inherit either exception. A selected-answer review must explicitly
   settle and reconcile this notice's pending-work Off rule, with the real
   submission boundary, in-flight truth and no later-On historical revival.
   Current source/access/suppression fences remain independently binding.
6. **No new engine or speculative features.** Reuse existing bounded tenant
   controls and source UI. No arbitrary To/CC list, generic inbox, new bell,
   reminders, digests, escalation ladder, read receipts, email-reply ingestion,
   auto-online suppression, SMS or attachment channel follows. Transport
   batching cannot silently become product-level coalescing. Incoming staff
   clarification notices remain undecided; no Q27 default is imported.
7. **Native qualification, not whole-product gating.** Exact source/P12/P17/P6
   binding, optional external-recipient material/utility/Recent-copy posture
   and protected action must qualify. No borrowed financial/staff retention
   number, mandatory bell sibling, request-access duration or complete Workflow
   Studio prerequisite. Native conversations remain useful independently of
   whether this optional email capability is activated.

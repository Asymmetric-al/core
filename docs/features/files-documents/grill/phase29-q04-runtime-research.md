## Is the proposed question genuinely unresolved?

**Yes.** The ordinary native private-document request now has ratified recipient-confirmation, exact-submission preview and bounded recipient-correction intent; this does not establish implementation. None grants original download. Q02 explicitly reserved original download, history and post-closure access; Q03 repeats that correction grants no download. The founder can now choose whether an explicit **Download original** action belongs in the ordinary currently authorized recipient experience, or whether that default remains preview/status/correction only.

Scope the question to **the exact own-submission occurrence the source currently permits the participant to access**, with current eligibility and qualified original-byte delivery. It must not silently decide older versions, post-closure continuity, staff-added files, other participants' evidence, sharing, retained archives or a general My Files service.

The meaningful distinction is deliberate delivery of the unchanged original file versus an in-product qualified reading rendition. Do not present preview-only as copy prevention; displayed information can already be copied/captured. Conversely, original download may disclose full embedded metadata, comments/revisions/hidden sheets or active content outside the preview's declared representation and creates an external device copy Asym cannot recall.

## Options and practical consequences

### Explicit original download in the ordinary native profile

Participant sees **View my submitted file** and a separate **Download original** for the exact currently authorized submission when that operation is qualified. It can help recover a copy on another device, inspect original-format details or keep a personal record. Those are plausible uses, not observed participant research. This remains a bounded Asym request action; one original download is not automatically a general drive.

Costs: an additional original-byte delivery capability and safety matrix; exact headers/full/range/conditional authorization, access evidence and currentness; clarity that the original can contain material not represented by preview; honest external-copy limits. It must not imply content acceptance or that the file is safe to execute. Existing source policies can prohibit it or require stronger assurance.

### Preview-only ordinary recipient default

Keep the newly chosen task focused on confirmation, inspection through the qualified reading view and correction. An independently defined source may still grant original download; existing P18/P21/P26 rights are untouched. This is the narrower default and has fewer routine actions/delivery lanes to qualify.

Costs: participant may lack a convenient saved original, cannot inspect original-only features through Asym, and may need a source-approved help/access path. A preview limitation must stay truthful and cannot be used to claim original-file fidelity. Do not assume everyone still has the local file, or claim this option prevents copying/safeguards every disclosure.

**Engineering judgment:** either option is compatible with Q01–Q03 when separately authorized. The source evidence does not mandate the new default. Offering deliberate exact-original download is a reasonable bounded product capability, not inherently scope creep; preview-only is the lower-scope choice. The founder's product preference—not the current missing endpoint or a misleading “already their file” assumption—should choose the ordinary default. If recommending original download, explicitly constrain it to current own-source access and qualification; if recommending preview-only, explicitly preserve source-owned original rights and unmet-copy-use tradeoff.

## Safeguards that do not depend on which option wins

1. **Separate capabilities:** preview, original read/download, previous history and sharing remain distinct. A download button does not authorize the backend; uploader/email/hash match does not qualify a source occurrence.
2. **Exact bytes:** serve the immutable source-original generation/length/digest. Never regenerate, recrop/recompress, change extension to imply safety, export the preview under the original label or silently select latest provider object.
3. **Current source:** check participant/request/item/occurrence/grant/restriction state on all relevant metadata, full/HEAD/range/conditional and retry paths. A correction may change candidate eligibility without giving ordinary archive access. Do not infer ordinary access solely from retained bytes.
4. **Safety and availability:** original download needs its own declared permitted-format/hygiene/security posture. It may be unavailable for unsafe/unverified/restricted files even if received; unsupported preview alone neither grants nor forbids download. No user bypass of known unsafe content or automatic fallback to original/external viewer.
5. **Deliberate navigation:** preserve request context, clear action label and exact version, and separate preview versus download status. No auto-download on page load, preview failure or error-retry. Never infer success/understanding from merely issuing a URL.
6. **Private response:** appropriate attachment disposition/safe filename, no MIME sniffing, private no-store/non-public delivery and correct bounded HTTP semantics. Provider URL, cache hit or304 cannot bypass authorization. Header behavior needs actual deployed route/CDN proof, not only unit construction.
7. **No permanent access promise:** ending authorization blocks new delivery; it cannot erase downloaded device copies. Browser closing is not necessarily logout. Download does not renew deadlines, retention, preview life or request session.
8. **Source-owned audit:** technical access outcome, exact actor/source/version/purpose under restricted owner policy. Not a new communication, accepted evidence, signature, CRM interaction or external custody proof by itself.

## Is this the best next question?

It is a sound next branch because Q02 distinguished preview from original and Q03 preserved that separation. Answering it completes the ordinary current-session action set before discussing what survives closure. Keep it narrow so source review/acceptance, historical access and retention are not bundled into one question.

Other plausible next questions:

- **What happens after staff accept or close the request?** High value, but it controls duration/history/contact rather than the original-download format. Easier to explain after deciding which current actions exist. Neither choice justifies indefinite archive access.
- **Which correction versions can the participant see?** Also unresolved and now concrete, but it should not accidentally reopen Q03's immutable retention/no automatic history grant. It can follow closure/history discussion.
- **Review outcomes and source acceptance responsibilities.** Necessary later. Much is already source-owned; a generic file-state rule cannot replace it. It need not block choosing deliberate original read for a currently permitted occurrence.
- **Withdrawal/deletion requests.** More complex retention/source obligation branch; not a prerequisite to original download and not implied by it.

Suggested framing: “You have sent a document and can view it safely in Asym. While you still have access to that request, should Asym also let you deliberately save the unchanged file you submitted, or keep this ordinary screen to viewing and correcting it?” Explain that this does not decide old versions, access after closure or anyone else's files. Avoid treating download as a security-free entitlement or preview-only as copy prevention.

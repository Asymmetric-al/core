## Recommended frontier

**Should the general staff File Manager find documents through their permitted
names, source context and approved metadata, or also search text inside separately
qualified documents?**

Recommend **A — Names, source context and approved metadata for this general
search surface.** Keep practical folders, labels, typed metadata, filters, saved
views, sorting, recent work and exact source navigation. Preserve existing
qualified Find within an opened document. Do not add a general cross-document
body-text index through this choice. A also excludes using direct body scans or
preview text to select or rank results in that general search; the boundary is
the matching capability, not merely the existence of a persistent index.

**B — Also provide separately qualified body-text search** is a strong alternative
when staff remember a phrase inside a document but not its title or source. It
can avoid opening many candidates. B means deliberate extraction/indexing/search
and current disclosure qualification for an explicit source/version/format
scope, rather than every previewable or downloadable file becoming searchable.
It need not include OCR, semantic/AI search, embeddings, external connectors,
historical-version search or a new provider.

The recommendation is a bounded product judgment, not evidence that body search
is undesirable, unusually complex, or never worth building. The current brief
already gives the baseline rich source context and expressly makes full-text
extraction separately purpose-qualified. No Asym usage study in this session
establishes frequent unknown-title/body-only retrieval, the relevant corpus, or
a measured time saving. That uncertainty supports A for the initial general
surface, while the real cost of A must be visible: an otherwise permitted document
cannot be found there from words that appear only inside its contents.

This is a capability decision, not two tenant modes, a permission editor or a
question about whether search should exist. Neither answer cancels a separately
governed existing source-specific search requirement.

## Concrete scenario

Illustrative scenario, not an observed ministry workflow: Elena is authorized to
work with several ordinary equipment inventories. She remembers that one
inventory mentions **solar controller** but does not remember its filename.

Under A, Elena can search an inventory's permitted name, source request or approved
labels, narrow the date/type/source, then inspect plausible exact documents.
Searching for solar controller alone will find a document only if those words
also occur in the admitted searchable metadata. The UI must not suggest that its
contents were searched.

Under B, the phrase may locate the exact inventory if that source/version and its
body-text representation are qualified and indexed. An image-only scan, omitted
spreadsheet content, a not-yet-indexed update or a prohibited source will not
silently become covered. A match is a discovery lead, not evidence acceptance,
proof that the whole document says what the excerpt suggests, or permission to
act outside Elena's source role.

If the phrase appears only in an earlier superseded version, whether that version
is searchable is a separately declared source/version scope. Neither option
means latest bytes are always business-current or all historic versions should
appear. Q37's historical instruction basis likewise remains a source-owned
historical fact, not a new general body-search corpus.

## Simple and truthful user experience

These are proposed interaction principles, not selected pixel designs or a new
settings system:

- Keep one ordinary **Search files** entry point with a visible scope. Under A,
  nearby copy can say **Search names and file details**. Source/date/type filters
  should use plain domain labels and preserve the current tenant/source context.
  Do not call this **Search all contents**.
- Under B, make body coverage apparent without a long technical checklist. For
  example, a scope control can distinguish **Names and details** from **Document
  text** where the latter is genuinely available. Exact default/control design
  is not settled here. A body match should be recognizable as such, and a safely
  permitted minimal excerpt can help explain relevance; snippet disclosure needs
  its own current qualification and is not an unconditional requirement.
- A truthful empty state is **No matches in this search**, with the active scope
  and filters evident. Under A it must not imply document contents were checked.
  Under B, visible authorized coverage limitations should explain that some
  permitted content may not have been searched. Never expose the existence/count
  of inaccessible files to explain incompleteness.
- Distinguish no matches from failed or still-running search. Preserve permitted
  query/filter input and a capable retry/source-navigation path. A partially
  loaded first page is not the entire result set. Do not silently widen the
  tenant, source, history or body scope to make an empty query look successful.
- Preserve a useful return to the search/source after opening a result. Open
  through the exact current qualified viewer/source route; no automatic original
  download, new external service or authority-bearing public link follows.
- Keep input/focus stable, cancel or ignore obsolete query responses, respect IME
  composition and make counts/loading/error messages available to assistive
  technology without disruptive announcements on every keystroke. Use existing
  Base UI/base-maia patterns, readable wrapping and usable touch/zoom/reflow.

An explicit Search action can be perfectly usable on slow connections. Instant
suggestions, private-query history, semantic ranking, synonym management, a
faceted analytics console and cross-source saved-query sharing are not implied
additional features. Existing required discovery should be implemented well;
Q38 should not turn into a search platform design committee.

## Qualifications and proof without premature implementation design

For A, the actual approved fields, source occurrences, scope controls, matching
semantics, current permission checks and accessible result journey still need
qualification. “Metadata only” is not a security exemption: a title, association,
facet or count can be sensitive. Do not satisfy A by quietly storing body text
in an unbounded metadata field or indexing private comments/clarifications.

If B is selected, its minimum meaningful contract must name the initial admitted
source family/purpose, exact version/currentness basis, extraction profile and
text coverage, disclosure rights for matches/excerpts, finite processing bounds,
derived-data lifecycle and current authorization throughout search and opening.
A useful bounded text profile may reuse qualified mechanics where genuinely
compatible, but preview qualification is not automatically index qualification.
No result that depends on inaccessible body text should survive merely because
its title is public or its cached access bit is old. Unknown authority is not a
temporary indexing delay; ordinary operational failure should not erase lawful
source facts or metadata discovery.

No native proof was run in this research pass. Future checks should cover actual
roles and alternate/private paths; cross-tenant/source and changing-rights
fixtures; limited/unsupported/partial/language/profile cases; old/new/version
races; lifecycle and restore; bounded query/index load; and composed mobile/AT
journeys. A search hit proves a qualified match in declared coverage, never
authenticity, review, acceptance, legal completeness or that staff read the file.

The choice can be recorded using existing source/document/version/discovery
language. A new domain term is not needed merely for this scope distinction.

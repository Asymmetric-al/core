## Disposition and narrow product meaning

Accept A with the boundaries below: ordinary native **file-evidence satisfaction requires a deliberate acceptance by currently authorized staff of the exact current requested item and relevant submitted evidence set**. Acceptance is necessary for that path, not sufficient to bypass the source's remaining conditions. Preserve existing authorized non-file/manual/waived outcomes; Q21 does not create waiver authority or force those outcomes through a fictitious file acceptance.

Acceptance of an item, source requirement satisfaction and whole-request fulfillment remain distinct facts. They may be recorded together when an already-qualified source command legitimately establishes them, but this question does not choose an extra Complete button, automatic whole-request completion, reviewer pool/assignment, two-person approval, bulk approval, negative-outcome taxonomy or additional email. P29 custody and a task projection cannot become the acceptance owner.

The permanent implementation should be a small source command using current identity/P12, immutable custody references, existing transaction/replay and task/communication boundaries. No second approval engine, long-lived review lock, general event platform or content-judgment AI is justified.

## Nine required technical clauses

### S01 — Staff acceptance is necessary, with exact source semantics

For the ordinary native file-evidence path, only a deliberate, currently source-authorized staff acceptance may establish the acceptance needed for satisfaction. Receipt, scan, preview/download, task completion, notification engagement or machine-extracted facts do not supply that acceptance. The exact accepted item may contain multiple relevant supporting files; no universal one-file-per-item rule or one-click-per-file ceremony is introduced.

Acceptance is not a waiver of other source conditions, a legal/authenticity certification, an application/financial decision or permission to disclose bytes. Existing authorized non-file/manual/waived outcomes remain owned separately. Requirement satisfaction and whole-request fulfillment follow their existing explicit source predicate. Q21 does not select collection-only, whole-request completion UI or a new negative-outcome taxonomy.

### S02 — Preserve the exact reviewed meaning and shared Q03 fence

The source command binds the exact tenant/environment/request/item, relevant request/instruction/purpose revision, admitted submission occurrence(s), submitted-original identity/version and complete relevant evidence-set identity. Include only semantically material dependencies; a generic `updated_at` that changes for unrelated projection work is not automatically the right review revision. A file digest/name alone cannot identify the accepted use or audience.

At the authoritative decision boundary, re-prove that this is still the eligible review set and that the actor/source/safety predicates remain current after relevant waits. Serialize correction admission, staff acceptance, relevant requirement edits, closure/waiver/freeze and adverse authority changes through the existing owning boundary at the scope needed by the invariant. A row lock on one file is not enough if an independent member changes the set; a missing row is not locked by selecting it.

If correction admission wins, the old candidate cannot be accepted as current while the new one is checking or unsafe. If acceptance wins, subsequent ordinary pending correction cannot override it merely because the overall request remains open. A failed correction never silently restores the predecessor. Preserve unrelated supporting members, accepted siblings and independent uses; do not make a whole request globally locked because one reviewer opened an item.

### S03 — Trusted actor, current capability and historical validity

Derive actor/tenant/source attribution from trusted server context and exact owner relationships. Task assignment, a shared email address, a broad admin role, file-read/download permission or participant upload authority is not the review capability. Client selectors and submitted “accepted by”/time/status fields do not grant authority. A decision records the staff actor who actually committed it, not the uploader, worker, task creator or later retrying actor.

Current authority to make a new acceptance, permission to read an old acceptance, and current applicability of that old acceptance are separate checks. Later reviewer departure/role loss does not erase a valid historical decision merely because today's membership differs; any continuing grant/qualification dependency must come from the exact source contract. Preserve minimized historical attribution and original policy/evidence under owner retention. Do not fabricate missing historic eligibility from a current role lookup, nor use historic eligibility to authorize present serving.

### S04 — One immutable effect and coherent required durability

Record the source acceptance effect and exact reviewed binding, required trusted history/audit, satisfaction consequence where actually established, and required durable follow-up intent coherently under the source's transaction/recovery contract. A successful API response cannot be the only acceptance evidence. A best-effort technical audit or a future queue attempt cannot defer a required invariant. If a required source transaction fails before commit, no acceptance is reported; a lost reply/unknown commit is reconciled before issuing a replacement.

Use existing idempotent task/communication/projection workers outside source locks. Follow-up failure does not undo a committed acceptance or require staff to accept again. No review-result email or extra task is authorized just by Q21; Q20's fresh-access email policy does not cover it. If acceptance and fulfillment legitimately co-commit under the source predicate, record their distinct meanings and apply the existing recipient-admission rules; do not introduce a redundant Complete step or silently assume all accepted items automatically mean fulfilled.

### S05 — Exact replay and prior acceptance reuse without new effects

Identify stable semantic acceptance intent and compare its immutable material meaning. Recover matching committed work before interpreting its target as no longer pending, while re-proving current permission for any response. Same-key/different item, evidence set, instructions, decision or material actor/command meaning conflicts. A new transport key or expired transport dedupe window cannot reapply the same admitted source effect. Two different staff keys targeting the same eligible item are governed by the source's one-winner invariant, not per-key dedupe alone.

An exact earlier acceptance may remain applicable to a later authorized evaluation only when the owner explicitly proves the same relevant accepted facts/requirement semantics and current applicability. That is a reference to historical evidence, not a new staff action, automatic cross-item acceptance, impersonation or replay of downstream effects. Same bytes in another request, a changed requirement or a different recipient do not inherit approval. A later actor who can inspect that acceptance does not become its original reviewer. Missing/corrupt/uncertain acceptance lookup is not “unaccepted/no effect” authority to retry; distinguish absence from dependency failure.

### S06 — Current evidence condition does not rewrite past truth

Accept only through the source's qualified inspection/decision path with required safety, integrity and source conditions. Preview availability is not the acceptance predicate: an unavailable preview can have another separately qualified authorized inspection method, but cannot justify unsafe/public/original fallback or acceptance based solely on a filename. Do not enforce arbitrary viewing telemetry, page scroll or preview-click ritual as proof of a human judgment.

If accepted evidence later becomes unsafe, missing, restricted, disposed of or unverifiable, preserve the original acceptance and what it actually attested at the time. Current custody/source restrictions block affected new use and inform the source's defined continuing satisfaction/remediation rules. Historical acceptance is not permission to serve unsafe bytes; loss of bytes is not automatically rejection, reopening, deletion of business facts, revival of a predecessor or a reason to accept a replacement under the old decision. Repairing an exact permitted physical copy/rendition does not by itself change semantic acceptance; new original bytes need their own source qualification.

### S07 — Effective SQL/privileged boundaries and finite time

Qualify required non-null/closed states, same-scope references, exact original/evidence-set links, semantic uniqueness and constrained allowed mutations. An ID-only FK or child trigger checking tenant does not prove the complete source/item/recipient/version relationship or parent-move safety. Check resulting rows after BEFORE-trigger transformations, UPDATE/upsert, deletes/cascades, direct routes, views, RPCs, SECURITY DEFINER owner/EXECUTE/search-path behavior, service clients, jobs and storage. Prevent trusted acceptance fields and lineage from being rewritten through an otherwise allowed update.

Inspect actual table/column grants and effective RLS policy composition. USING constrains applicable old rows; effective WITH CHECK constrains inserted/resulting rows, with UPDATE/ALL inheritance where omitted. Permissive policies may OR together; a broader policy can matter. Definer execution runs as the function owner, with bypass depending on actual owner/table/role/FORCE/BYPASSRLS configuration. Browser revoked grants and service mocks do not prove all privileged transitions safe. RLS is not a replacement for the cross-row source transaction.

Use trustworthy source acceptance time and current state after relevant waits under a qualified linearization convention, and require its effect to durably commit. Browser click, file receipt, scan callback, original transaction-start `NOW()` or worker-retry time cannot be substituted to backdate a decision. A sampled SQL clock is not automatically physical commit time. If acceptance fulfills the request under its existing predicate, qualify the established Q07/Q10 occurrence and boundary behavior; otherwise acceptance time is not whole-request fulfillment. Source work may continue independently after participant access ends, without recreating recipient admission or moving an end.

### S08 — Read models, reviewer continuity and bounded work

The UI may show the exact item and its safe current review state, but the source owns acceptance. Keep the displayed original/version and any draft notes stable when a correction arrives; announce changed evidence without silent content substitution, focus theft or moving the draft decision to a successor. A stale action returns a safe changed-evidence outcome and the existing qualified review path. It cannot report success merely because a generic status update affected a row.

Separate received submissions, current review candidates, accepted/satisfied requirements and whole-request completion. Apply current metadata permissions before counts/history/projection; unknown source state is not zero or completed. Retained history and cached acceptance responses do not bypass current disclosure. Use bounded exact source/evidence references and authorized paginated history, preserving owner limits and tenant fairness; do not introduce a full-history replay on every view or per-reviewer lock service.

### S09 — Migration, restore and qualification

Activation requires an exact native source/audience/profile whose writers, readers, acceptance/correction commands and recovery all enforce the adopted invariant. Do not infer historic acceptance, actor, time, evidence membership or requirement meaning from a filename/hash, task status, storage available flag, fabricated default or current membership. Old rows missing necessary proof remain explicitly unresolved for the affected action; they do not justify blanket deletion or false rejection of independent source facts.

Mixed-version and restore paths must preserve admitted immutable effects, relevant successor/current state and later restrictions before authorizing new decisions or serving. Restoring old metadata cannot revive a superseded candidate, replay acceptance side effects, renew access or republish disposed content. Existing controls can stop unsafe initiation/acceptance while preserving evidence and source-owned recovery. Formal owner/OpenSpec reconciliation and actual role/source/concurrency/provider/storage/browser evidence precede activation; the research itself supplies none of that deployment proof.

## Primary technical documents and actual verification

Current PostgreSQL 17 primary documentation was refreshed read-only for this review. Versioned docs support semantics; no hosted database version was queried.

- [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html) confirms old/resulting-row predicates, inheritance and BEFORE-trigger ordering. Policies and grants must be considered as an effective set, not keyword checks.
- [Transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html) explains snapshots and concurrency anomalies. Separate read/check/write statements or a per-key unique record do not automatically serialize the full item/evidence invariant. Any chosen transaction strategy needs real collision and retry proof.
- [Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html) separates NOT NULL, row checks, uniqueness and relationship integrity. A null-true check or a cross-row application assumption is not a permanent source invariant.
- [Date/time functions](https://www.postgresql.org/docs/17/functions-datetime.html) distinguishes transaction/statement/actual wall-clock timestamps. It does not choose Core's business occurrence convention or supply an exact physical commit time.

The prior same-day [PostgreSQL RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) and [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) reads support role/owner/service qualification. No simplified skill claim about missing WITH CHECK or automatic definer bypass is relied on.

Verification consisted of exact ratified Q03/source readback, current local source/migration/UI/test inspection, local HEAD recheck, primary documentation and concrete failure analysis. No native tests, real-role SQL, provider/byte operation, browser/AT or intended-user test was run. There is no basis for claiming the new acceptance service, current RLS, race safety or release readiness already works. No extra completion, routing, waiver, negative-outcome or notification policy was selected by this report.

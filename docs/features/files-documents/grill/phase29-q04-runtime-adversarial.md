# Phase29 Q04A — original-download runtime and UX adversarial review

Research date: 20 October 2026. Checkout: `/home/conrad/code/core`, HEAD `3d85897ebf1515008ef5c676b1c58a15422fb9ab`. Q04A selects an explicit original-download action for the ordinary currently authorized native request participant. This review proposes qualifications for that decision; it does not implement or qualify the feature.

Only source, installed packages, public documentation and one existing isolated unit file were inspected/executed. No credentials, private rows, original file bytes, provider changes, installation, startup, production operation or cleanup occurred. Existing user/parent changes were preserved. References below are relative to the stated checkout unless identified as external.

## Judgment

The chosen action is compatible with Q01–Q03 and can stay in the existing request task. It needs a source-authorized exact-original delivery path. Neither the current receipt endpoint, Eve's short-lived signed URL nor Payload's public media route is that path.

Prefer a deliberate same-origin native attachment transfer through the shared private gateway, with a qualified accessible failure/recovery experience. Do not make the browser fetch and assemble an entire remote original merely to obtain a progress bar or trigger a Blob download. The installed Supabase SDK already supplies a stream primitive; no new provider or dependency upgrade is justified by this review. That primitive still needs exact response, source authority, integrity, HTTP, cancellation, audit and capacity qualification.

“Download requested,” server transfer started, bytes emitted, server transfer completed, browser download completed and “saved/opened by the recipient” are different facts. A normal page cannot infer the latter facts from a click or a successful server response. Downloading also does not accept evidence, create an official version, renew access, or grant history.

## Current code and installed adapters

### Receipt endpoint: useful gate and attachment shape, not a retained-byte stream

- `packages/api/src/admin/contribution-operations/route.ts:340–387` wraps the receipt GET with staff/admin roles. It checks the tenant-configured receipt capability before reading the snapshot (`349–359`), sanitizes the filename (`367–370`) and emits `no-store`, attachment disposition and PDF type (`372–377`).
- The response is **`Buffer.from(rendered.pdf)`**, not a provider-backed bounded stream. The preceding “Streams” comment (`335–338`) and route-contract test title do not change the implementation.
- `receipt-pdf.ts:203–208,251–274` reads a tenant-scoped snapshot, calls `renderSync` and returns a full `Uint8Array`. The tenant/snapshot idempotency metadata correlates rendering. It does not prove a persisted immutable artifact, digest, exact original read, generation-pinned range semantics or no rerender on access.
- `apps/admin/app/(app)/contributions/operation-shell.tsx:237–246` uses a native anchor to a first-party receipt route, with a new browsing context and `rel="noreferrer"`. `receipt-delivery-model.ts:23–28` constructs that route. This avoids a browser Blob assembly but is not a complete qualified error/revocation/download UX.
- `tests/unit/packages/api/admin/contribution-operations-route-contract.test.ts:147–165` checks source strings for capability/header/role presence. It does not execute a streaming route.

### Eve: useful private custody metadata; issued URL is a different access model

- `packages/api/src/eve/retention/control.ts:157–178` resolves the artifact by ID, tenant, owning profile, available status and expiry before issuing a 60-second Supabase signed URL. It selects only bucket/path and does not verify original digest/length/version at delivery. The selected row check and URL issuance are separate operations.
- The expiry can pass between selection and actual use; the fixed 60 seconds is not bounded by the row's remaining expiry. A source change after issuance does not produce a fresh application permission check on that URL request. This is a concrete reason not to transplant the helper into Q04, not evidence of an exploited generic request feature.
- `packages/api/src/eve/retention/route.ts:33–83` returns the URL in JSON for an admin-only action. The reached download branch does not call `audit.log`, and does not set private-cache headers itself. `apps/admin/app/(app)/admin/eve/retention-panel.tsx:119–178` lists metadata/status/expiry and has no original download control.
- `control.ts:94–134` uses a fresh object ID, computes SHA-256, uploads without upsert, and completes metadata. Useful custody precedents, but the content is deliberately redacted replay/debug text. It must not become the generic “unchanged original” transformation pipeline.
- Current official Supabase documentation distinguishes JWT-authenticated private reads from signed URLs. Signed URLs use an internal signing key and remain valid to their expiry despite Auth signing-key changes. A short URL lifetime is therefore not application-current authorization or immediate revocation. [Supabase download documentation](https://supabase.com/docs/guides/storage/serving/downloads)

### Installed Supabase stream primitive: available, with important limits

Current installed `@supabase/supabase-js` is **2.117.3**, and its dependency specifies storage-js **2.117.3** (`packages/database/node_modules/@supabase/supabase-js/package.json:3,83`). Two storage-js versions exist in the Bun store; this review inspected the one used by this package, not the unrelated 2.103.0 copy.

All paths in this paragraph start at `node_modules/.bun/@supabase+storage-js@2.117.3/node_modules/@supabase/storage-js/src/packages/`:

- `StorageFileApi.ts:822–912` documents/accepts `versionId`, cancellation/fetch parameters and `cache: "no-store"`; a transform selects an image-render endpoint. An original-delivery adapter must prohibit transforms. Merely having a `versionId` SDK option does not prove deployed object-versioning support.
- `BlobDownloadBuilder.ts:42–49` awaits `response.blob()`, materializing the full response as a Blob. `.asStream()` at `14–15` creates the stream builder.
- `StreamDownloadBuilder.ts:39–46` returns `result.body`; it does not expose the successful response's headers/status in the result. This is not, by itself, enough to validate a provider's 200 versus 206, Content-Range, byte count or immutable identity. It also type-asserts the body instead of proving it non-null.
- Therefore reuse or adapt the supported client under the shared server provider adapter only after proving the required metadata, range/error/cancellation behavior. Do not claim `.asStream()` alone supplies a complete gateway, and do not send a privileged storage client/token to the browser.

The browser standard confirms `Response.blob()` reads the body to completion. Exact memory residency is browser-dependent; the concern is whole-file materialization and delayed download handoff, not a claim that every Blob necessarily lives entirely in JavaScript heap. [MDN Response.blob](https://developer.mozilla.org/en-US/docs/Web/API/Response/blob)

### Payload public Blob: real streaming and ranges, wrong source/access boundary

- Installed Payload and its Vercel Blob plugin are **4.0.0-internal.1f9ae9a** (`apps/admin/node_modules/payload/package.json:3`, plugin `package.json:3`); the plugin pins **@vercel/blob 2.3.1** (`package.json:40`). Next is **16.4.0** (`apps/admin/node_modules/next/package.json:3`).
- `apps/admin/node_modules/@payloadcms/storage-vercel-blob/dist/getFile.js:21–84` reads object metadata, calculates a URL/time-derived ETag, handles ranges, returns 304, and transfers `response.body`. It really is a streaming response path.
- The same code sends public cache headers (`46`), accepts the public adapter's URL identity, and converts upstream non-OK/no-body to **204** (`74–78`). It sets a partial status from its range calculation rather than demonstrating a matching upstream Content-Range (`65–83`). None is a qualified private exact-original error/integrity policy.
- `payload/dist/uploads/parseRangeHeader.js:14–43` selects the first requested range for a multi-range request; `getRangeRequestInfo.js:15–48` builds full/partial/416 headers. These current SDK details must not be described as universal lack of range support, nor copied as the new contract without qualification.
- Plugin defaults are public access and a one-year cache lifetime (`dist/index.js:5–9`). Its optional public-CMS integration remains separate from private source access.
- The underlying Blob SDK itself is not universally public-only: installed `node_modules/.bun/@vercel+blob@2.3.1/node_modules/@vercel/blob/dist/index.d.ts:126–219` has private `get`, `useCache: false`, a returned stream and headers. Its declared result is 200/304. This is another primitive, not a reason to migrate providers or assume qualified range support.

### Error, cache and audit boundary gaps

- `packages/api/src/shared/with-operation.ts:128–167` establishes authenticated context, creates an audit logger and passes it to handlers. Creating that object does **not** write an access audit. It is not an implemented P12 metering/expiry/stream guard.
- `packages/lib/audit/logger.ts:73–85` skips logging if the admin client is unavailable, awaits an insert without inspecting a returned Supabase error, and catches thrown errors. Copying `await audit.log(...)` is not proof of the tiered durable audit/outbox requirement. This is source evidence about the helper, not an assertion about all audit infrastructure.
- `shared/http-errors.ts:119–130` returns JSON with status and optional request ID, without no-store/disposition hardening there. `with-operation.ts:77–109` normalizes errors but does not add those missing private-delivery rules. Successful receipt headers do not establish failure/redirect headers.
- Current admin Next config has no explicit application `headers()` block (`apps/admin/next.config.ts:27–106`); plugin/platform behavior remains unverified. The donor config sets global nosniff, but also extension-shaped **public immutable** image/font caching (`apps/donor/next.config.ts:114–174`). A future private path with a filename-looking suffix needs route/platform override proof; this is not evidence that an existing private request currently leaks through that rule.
- Do not put a blind `download` attribute over an endpoint that may redirect to a sign-in page or return error JSON and then treat the result as the original. Native failure behavior must be qualified with browser tests. Browser handling varies by user settings and can open a downloaded file externally; a download label is not a guarantee that external active content cannot execute. [MDN anchor download behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a#download)

## SQL and concurrency assessment

`supabase/migrations/20260718022535_eve_retention_replay_tracer.sql` is the only migration matching the inspected Eve artifact table/bucket. It supplies:

- Artifact ID, tenant/profile FKs, constrained bucket/path, byte count, digest, status/expiry and unique bucket/path (`35–69`).
- A private bucket plus RLS enabled, revoked PUBLIC/anon/authenticated table privileges, and service-role CRUD (`120–135`).
- Definer actor helper checking supplied role and profile/tenant correspondence (`137–155`); service-only callable business functions (`548–567`). The application must derive actor parameters from trusted context. They are not independently attested by an `auth.uid()` check in that helper.
- Upload completion transitions only the pending owner/tenant artifact and appends a lifecycle event (`218–247`). Expiry uses row locking and SKIP LOCKED, then a second hold/deletion-lease check (`373–447`).

These are useful state-transition patterns. They do **not** provide generic request/requirement/participant grants, download delivery attempts, source-policy epochs, immutable byte reads or revision/reference checks. Browser table denial plus a private bucket is not a complete proof for storage object policies, service-privileged routes, legacy URLs and provider consoles. Production effective grants, function ownership, FORCE RLS/BYPASSRLS and deployed storage policies were not queried.

No finding here is based merely on an omitted WITH CHECK: UPDATE/ALL policies may inherit USING. No claim is made that every SECURITY DEFINER function bypasses RLS: owner role, table ownership, FORCE and BYPASSRLS matter. The Q04 release proof must inspect effective composed policies, grants and old/new values under actual roles, and cannot rely on a migration keyword count.

The minimum currentness model is the server-resolved tuple of participant + tenant/context + request/requirement + own occurrence + immutable original generation + source permission/restriction state. The download must never resolve a caller-supplied provider URL or change this tuple because a newer upload shares a name/hash. Repeat requests and resumed ranges reauthorize it. The source's correction/acceptance/closure/restriction transition owns the serialization boundary; downloading neither locks review nor delays a correction.

For an already running stream, pin the byte generation, recheck expiry per chunk as P12 requires, and implement the qualified source restriction termination/fencing mechanism. Do not perform a new heavyweight per-chunk database transaction by assumption; the exact trusted mechanism and measured enforcement bound must be established before activation. It must not become unlimited authority from a single initial check, nor promise retroactive recall. A later range/conditional request is new delivery and cannot inherit the old stream's authorization.

## Recommended recipient and staff experience

1. Keep **View submitted file** and **Download original** separate on the permitted submission in its requirement. Show safe filename, verified type/size and meaningful submission identity. Do not show internal storage IDs/paths, access tokens or another participant's metadata.
2. One explicit download action is enough when currently allowed and qualified. No mandatory second identity form, reasons form, repeated confirmation or general file browser. Use native semantic controls, accessible names, keyboard operation and visible focus from the existing UI system.
3. An unavailable action should have a short truthful explanation only when the source permits disclosing it: checking, temporarily unavailable, unsupported delivery or no longer available. Security-denied/nonexistent resources retain the required uniform response. A restricted source must not leak filename/type/size merely to explain a disabled button.
4. Keep source state and transfer state separate. Evidence can be submitted but not accepted; preview can be ready while original delivery is disallowed; original delivery can be qualified while preview is unsupported. None should counterfeit the other's readiness.
5. Use a native first-party transfer, with safe errors/re-authentication/return-to-request behavior proven on supported browsers. A native `<a>` precedent exists, but copy neither a blind download attribute nor a Next.js-prefetched link that could start an audited transfer without intent. If a preparatory status request is used for UX, the actual GET still reauthorizes; a preflight is not authority.
6. For native transfers the application ordinarily knows request/handoff, not the browser's save outcome. Keep the request page stable, avoid a “100% saved” toast, and let the browser manage its own transfer display. If an error surface is a separate first-party page, it must be accessible, minimal, non-cacheable, free of private original content and capable of returning to the exact request safely.
7. A correction or restriction discovered from another tab does not replace the file under an open viewer or turn a failed download into the successor. Stop/deny as required and refresh permitted task state. The recipient must deliberately select the currently allowed original again. Staff acceptance remains tied to the exact reviewed evidence set.
8. Retry resumes/restarts a technical delivery of the exact authorized version where supported; it does not create another submission, reset source deadlines or promise restoration of an expired grant. Browser session expiry and closing a tab are different; neither cancels a previously admitted submission worker.
9. No blanket prompt about danger is needed for every download. However, the action cannot promise the original is a sanitized rendering, omit relevant original-format limitations, or offer a user bypass for content known unsafe. Bytes stay unchanged; “safe preview” does not mean “safe to execute original.”

## Byte and HTTP requirements that need implementation proof

- Resolve only the admitted immutable original generation with its persisted digest, length, verified type and provenance. Original identity is not its filename, URL, preview, provider modification timestamp, or current candidate shortcut.
- Establish identity before serving through a qualified immutable storage/version mechanism. A hash calculated only after streaming completes cannot prevent already-emitted wrong bytes; it is detection, not pre-delivery assurance. A range cannot independently prove a full-object hash without trusted generation/chunk integrity. Qualification must state how metadata and the selected stored bytes are bound.
- Do not recrop, recompress, watermark, rerender, decode/reencode or silently use a thumbnail. Keep transport Content-Encoding/range mapping exact; set non-transforming private response policy and verify intermediary behavior.
- Safe attachment disposition, correctly encoded filename, trusted MIME, nosniff and source-appropriate private headers must hold for the deployed route. Browser filename normalization and external-app behavior remain outside an absolute server guarantee.
- Explicitly qualify GET/HEAD, full response, supported ranges, conditionals, invalid/unsatisfiable ranges and redirects. Authorization precedes a 304/416 or size/validator response. A wrong If-Range validator normally causes a full selected representation, not permission to switch to a newly current submission. [RFC 9110 sections 13.1.5, 13.2 and 14.2](https://www.rfc-editor.org/rfc/rfc9110.html)
- RFC range support permits defined simplification/rejection of abusive requests; do not invent complete multi-range support as a requirement. Whichever subset is qualified must produce truthful status/body/headers and finite work. No implicit 206 for a provider's full body.
- Before successful attachment headers, reject missing/unsafe/mismatched originals and provider failures safely. After headers/partial bytes, interruption is a failed or incomplete transfer, not a chance to append an error document under the original name. No automatic alternate provider/public URL/renderer fallback.
- Validate content length and observed bytes; do not overstate what a server's completed stream proves about the browser's disk. Persist technical outcomes through the existing source-governed access-evidence model, excluding file bodies and raw sensitive provider errors.

## Finite original-download limits

This review does **not** set numeric limits. D32's 20 MiB preview input limit, Eve's 5,000,000-byte replay cap, native-render budgets and provider maximum object limits are different contracts; none automatically becomes Q04's original-download limit.

Before activation record finite, measured values for the exact accepted source formats/sizes and deployment: maximum admitted original size; simultaneous streams per participant/context/tenant and service; aggregate bytes/rate budgets in the existing metering system; maximum range count/span/work; initial response and idle/total transfer deadlines; bounded buffering; cancellation propagation; authorization/expiry recheck mechanism and enforcement bound; denied/failed attempt rate; and technical evidence/outbox saturation behavior. Use existing qualified platform/source budgets where present, and identify the missing values as release blockers rather than choose arbitrary numbers in the UI.

A supported slow connection must either complete within this envelope or receive an honest retry/recovery outcome. Do not make a quiet client an indefinite provider/worker reservation, extend an access deadline to finish it, or solve overload with a signed/public bypass.

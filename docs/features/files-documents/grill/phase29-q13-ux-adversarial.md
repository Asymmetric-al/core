# Phase 29 Q13 — usable, deliberate access to continue an unfinished request

Research date: **21 October 2026, Asia/Bangkok**. The parent reports Conrad selected Q13 A. Q01–Q12 are ratified. **Q13's full amendment package remains pending ratification.** This is a read-only UX/comparative contribution, not permission implementation, runtime qualification or activation.

The updated Q13 question, comparative note and owner research were read alongside the preserved Q01–Q12 boundaries. Current public primary documentation was inspected. Only this file was written. No private account, recipient, source request, upload, download, message, provider state or canonical document was changed. No browser, assistive-technology, source race or intended-user test was run.

## Verdict and strongest alternative

**Retain A with the refinements below.** A deliberate fresh finite permission for the same still-legitimate unfinished task is a coherent product capability. It can preserve current work and receipts without forcing a duplicate request. It must remain distinct from changing the original deadline, automatically granting another sixty days or reopening a completed request.

B remains credible: keeping this request's expired access final avoids another consequential permission command and the complexity of repeated access. Some legitimate recipient work would remain impossible through this request; that cost is unmeasured. B does not mean deleting evidence, refusing all help or preventing independently authorized staff review. A is a product preference, not an industry consensus or a claim that ministries commonly need a particular renewal interval.

The key user-facing distinction is:

> A request for help, a committed access decision, usable current access and notification are separate outcomes. Show only the outcome established by current evidence.

Do not make people learn all of those internal distinctions at once. Give them the actual current result and next supported action.

## What A includes and leaves open

A proposes a new prospective source admission for the same intended recipient, continuing purpose and originally admitted requirement scope intersected with current eligibility. That scope can include first submissions and Q03 correction successors for eligible pending requirements; it is not frozen to files already uploaded before expiry. Accepted/frozen items remain protected, while currently authorized reading of an accepted current file is a separate action.

The expired original grant and original I/U remain historical facts. The fresh decision has its own semantic intent and outcome. Retries reconcile that act; they do not edit the original end or create another fresh act merely because the first response was lost.

A includes an explicit prospective completion consequence: normal fulfillment while the fresh authority exists and is eligible in the qualified source order may admit Q07's at-most-720-hour read-only stage from that fulfillment, under genuine caps and current checks. Completion in the gap before fresh admission cannot be made retrospectively eligible. A source already complete is outside this unfinished lane; an allowed atomic admission/fulfillment operation must prove causal eligibility rather than impose arbitrary ordering on equal-precision timestamps.

Fresh unfinished duration, activation anchor, unused-admission bounds, repeat/overlap rules and cumulative limits remain unselected activation gates. Neither Q12's sixty days nor Q07's thirty days supplies the fresh unfinished period. This continuation's completed view does not automatically widen Q08's existing lineage for later fresh read grants.

No automatic mail, reminder, new help inbox, mandatory essay, second approver, sender date editor, per-request policy menu, new member/account, generic role or broader file repository is selected.

## Keep these states distinct without burdening the user

| Established fact                                                     | May communicate, within disclosure authority                                            | Must not imply                                                                                       |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Old source access ended                                              | A permitted ended-access state and actual help route                                    | Request rejected, file deleted or a fresh grant already approved                                     |
| Help/contact request was actually recorded through an existing route | The actual help result and supported next step                                          | Approval, a new access end, guaranteed reply time or a newly invented help case                      |
| Staff is reviewing a proposed fresh act                              | Current scope/timing terms and deliberate action                                        | Permission committed, notification sent or a reservation against changes                             |
| Fresh source act committed                                           | The exact approved result and timing terms/known caps                                   | Present usability, resolved end, recipient notification or human reading unless independently proved |
| Current fresh authority usable and exact end resolved                | **You can continue this request. Access while it is unfinished ends [date/time/zone].** | Another sixty days, permission for every file/action or protection against true later restriction    |
| Communication succeeded at a known transport layer                   | The corresponding transport status                                                      | Inbox placement, recipient comprehension, successful entry or source completion                      |
| Fresh outcome unknown                                                | **We couldn’t confirm whether access was granted.** and supported reconciliation        | Definitely failed, definitely granted, create another request or approve again                       |
| Normal fulfillment qualifies under the fresh authority               | Current completed read-only view and actual Q07 end                                     | Extended writes, a guaranteed full thirty days or automatic future Q08 eligibility                   |

An end that has not yet resolved under the unselected activation policy is not an erroneous missing date to fill with sixty days. A true observer failure must likewise not be disguised as a deliberately unresolved anchor. Distinguish those causes in the authorized source context; keep recipient wording brief and actionable.

## Journey 1 — recipient returns after old access ends

Use Q01's existing qualified doorway. An old URL alone cannot disclose a private title, recipient, requirement, prior receipt, count, end date or fresh-access eligibility. A visible “Request more time” action can itself disclose existence; do not add one automatically.

When authorized to show it, concise copy is:

> Access has ended. Contact [the existing source help route] if you still need to complete this request.

This does not promise approval. Where private existence cannot be disclosed, use the already-required neutral entry/help response instead. Do not expose internal revocation reasons or require the person to send the private token or attachments to support.

If only proof/session expired while source access remains valid, use qualified re-entry. If current stage is unknown, reconcile it; a lost projection may hide an existing valid completed transition. Neither case calls for a Q13 fresh grant solely to make the page work.

No new recipient request form, tracking queue, automatic message or repeated identity questionnaire is selected. If an existing help interaction is used, preserve safely known request context without exposing it to an unauthorized channel.

## Journey 2 — support and sender identify the actual problem

The person who originally sent a request, a support worker, its current reviewer and a fresh-access issuer may be different actors. Their permissions are not interchangeable.

The current support/source view should distinguish:

- A valid grant with expired or broken entry proof.
- Unknown source outcome or a delayed projection.
- Original ordinary elapsed expiry with a genuinely unfinished eligible task.
- A source restriction, changed recipient/purpose, accepted/frozen item or independent hard intake stop.
- A request already completed, with or without a valid completed-view admission.

Only the third is a candidate for this specific fresh unfinished lane. It still needs the actual issuer capability. Retained bytes or a continuing staff-review duty do not create recipient authority.

If all recipient work is received and staff review remains, say so. Do not ask for another upload to “restart” the task. Staff can continue independently authorized review without first granting recipient access. Any fresh grant needs a real permitted recipient purpose, not a fabricated need to make an administrative workflow advance.

Original time, receipts, restriction history and the access gap remain truthful. Support cannot resolve the issue by editing a date, altering an email address, copying a request or changing a status to incomplete.

## Journey 3 — issuer reviews once, then acts deliberately

Show the existing source request context with:

1. The permitted intended recipient/purpose and still-needed original requirement occurrences.
2. Current eligible actions and meaningful exclusions, such as accepted/frozen items or a source-owned intake stop.
3. The approved finite timing terms, known caps and current stage.
4. One **Grant access to continue** action.

Use an understandable summary rather than forcing staff to select every file or retype the recipient. The source may offer a narrower scope where its contract permits; Q13 does not invent a scope editor. Do not require the issuer to preview private bodies merely to make an authorization decision when their actual grant capability does not include body-read access.

A request is not just the collection of old file IDs. If an originally admitted requirement has never been submitted, fresh access may permit its first eligible submission. If a pending file needs correction, the exact Q03 successor path can be eligible. Newly added requirements or a changed recipient/purpose do not silently enter through the same button.

Current material state must be rechecked at the authoritative mutation boundary. If recipient, source purpose, remaining requirement scope, real timing constraints or authority changed materially, explain the relevant conflict and refresh the meaningful review. Ordinary time advancing under unchanged approved terms should not force a reconfirmation loop. A routine second “Are you sure?” adds no authority.

Do not introduce a mandatory essay, second approver, administrative role, date picker or duration menu. Existing real source requirements remain; the product cannot invent additional ceremony from a vendor example.

## Journey 4 — committed, failed, unknown and cancelled outcomes

Disable or otherwise guard duplicate dispatch appropriately in the UI, but treat source semantic idempotency as the actual protection. Two tabs, a refresh or weak connection must not create two fresh grants.

| Outcome                                                 | Recommended behavior                                                                                                                                    |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Not dispatched; issuer cancels                          | Leave source permission unchanged and return to the prior context.                                                                                      |
| Source proves the fresh act did not commit              | Explain the actual cause; a supported new attempt rechecks current authority.                                                                           |
| Source committed; response lost                         | Recover the same fresh result under current disclosure. Never calculate another period because the first response was missed.                           |
| Outcome remains unknown                                 | State uncertainty and offer the supported status/recovery path. Do not display success, a permanent denial or a second approve command as the solution. |
| Dialog closes or network request aborts after dispatch  | Closing UI is not proof of source cancellation. Reconcile the same act on return.                                                                       |
| Grant committed but delivery failed                     | Preserve the grant and explain delivery separately. Any permitted communication retry keeps the original fresh act and admitted terms.                  |
| Source completes/revokes/changes before fresh admission | The actual source order wins; do not hide a denied or changed result under an optimistic success toast.                                                 |

Meaningful committed results should be findable later in the authorized source context, not only a toast. This does not create a new dashboard or expose all grant history to every reviewer.

Only offer retry where it retries the right thing. **Check access status** is different from reissuing a grant; **Retry invitation** is different from fresh permission; **Try verification again** is different from either. Labels are proposed explanatory directions, not new commands authorized by this note.

## Journey 5 — recipient uses currently available fresh access

After an actual fresh decision, the recipient returns through the current Q01 proof route. Compatible proof reuse follows the source contract; there is no new account enrollment or ceremonial timer-start step.

If authority is usable and the end resolved, show:

> You can continue this request. Access while it is unfinished ends [localized date, time and zone].

Until those facts exist, show only the truthful current state, approved timing terms and any known cutoff that this viewer may see. Do not promise immediate use or manufacture an end. A protected page must not display internal “activation pending” mechanics that do not help the user decide what to do.

Show the actual remaining recipient work, authorized current files and concise Q05 history. Original receipts retain their timestamps and lateness. Fresh approval is not approval of the files and does not make old late submissions on time. Requested by remains separate; a new target does not reset fresh authority.

Do not require already-received usable material again to rebuild context. If a current requirement genuinely needs another file or correction, state that actual reason. Avoid claiming the browser preserved an unsent local file after navigation or session changes.

Safe preview, original download and history each keep their own current eligibility. A fresh pending-work grant must not expose superseded bytes, other requests or every file in a folder. Accepted/frozen evidence can remain read-only where current scope permits; it cannot become editable simply because the request overall is unfinished.

## Journey 6 — correction, review and race handling

Q03 remains the correction contract. Only the eligible pending target member is replaced; immutable source admission fences its predecessor immediately, even while safety/preview checks are pending. A later unusable successor does not automatically revive the old file. Unrelated supporting members remain.

Transfer completion is not receipt. Starting before a boundary is not a reservation. A lost receipt response is reconciled from the same source intent. Fresh access does not allow a previously uncommitted gap upload to be represented as received earlier.

Reviewers must see that the exact candidate or available actions changed. A reviewer who opened the old file cannot accept it using a stale screen after a correction fence. Conversely, do not freeze all unrelated review merely because fresh access exists; vendor-wide feedback pauses are not the Core contract.

When recipient work is done, show received/awaiting review and the actual next actor. Fresh authority is not an SLA for staff completion, a reason to falsely fulfill the request early or a basis to blame the recipient for staff delay.

If a new independent restriction affects one item or representation, stop that action and retain other independently authorized work. If current authority itself cannot be established, affected protected use fails closed. A partial preview/history outage is not proof that the whole request expired or that files disappeared.

## Journey 7 — normal fulfillment under the fresh episode

The new completion mapping is prospective and must be adopted explicitly. A fresh act must exist with the necessary eligibility in the source causal order at normal fulfillment. An earlier staff click, pending approval or backdated record is insufficient.

When that condition holds, ordinary writes stop and Q07's at-most-720-hour completed view can be admitted from the actual source fulfillment, subject to real caps. Its end may be earlier or later than the fresh unfinished-only end. Explain the mode/end change without calling every transition an extension.

If completion happens in the gap before fresh admission, preserve the legitimate source completion but do not invent recipient completed admission. A completed source cannot be cosmetically reopened to use this lane. An owner-permitted atomic admission/fulfillment operation is judged by actual causal eligibility, not an arbitrary requirement that displayed timestamps differ.

If a valid fulfillment is observed later, recover original eligibility/end and check current access. Do not use discovery time as a fresh thirty-day start. If that original completed end is already over, projection repair does not revive it.

A later request for completed-file access must not automatically use Q08 solely because this continuation completed. Q08's existing original-admission lineage remains unchanged until its exact compatible extension is separately adopted.

## Journey 8 — restriction, repeated expiry, refusal and changed purpose

Fresh permission cannot clear genuine revocation, cancellation, binding purpose/overall limits, accepted/frozen state, hard intake prohibition, unsafe representation or disposal. Preserve each restriction's scope: a records hold is neither automatic read permission nor necessarily a universal read prohibition.

If fresh authority ends again, there is no automatic repeat entitlement or assumed one-time prohibition. Apply only the repetition policy once explicitly chosen. Before that policy is settled, the lane remains unqualified for activation; the UI must not default to endless grants.

A declined or currently prohibited act needs a safe explanation and actual next step. Internal security reasons may not be disclosable. “We can’t grant access through this request” can be clearer than falsely labeling the document rejected. Do not promise a future exception or ask for sensitive email attachments.

New recipient, purpose or wholly new requirements use their real owner process. Same email, contact record or copied source ID cannot inherit the fresh scope. A stable link is merely a route; it does not revive old bearer authority.

Original and fresh access facts remain attributable while retained under the records owner. Ending access does not delete source evidence, erase copies already downloaded or guarantee perpetual storage. No mandatory export/download is needed to finish.

## Accessibility, mobile and recovery constraints

Keep Base UI/base-maia and existing source surfaces. Static component presence does not prove composed keyboard, speech, screen-reader, touch, zoom/reflow or mobile-file-provider behavior.

Critical details belong in main content: current state, meaningful next actor and permitted end/timing terms. Avoid a countdown-only signal, hover-only reason, color-only status or toast-only result. Dynamic status should not repeatedly steal focus or chatter on every poll. When a material conflict returns a form to review, preserve focus/context coherently and identify the changed actionable information.

On small screens, long recipient names, filenames, dates and zones must wrap without hiding scope or the decisive action. Sticky controls must not obscure focused content. Use descriptive labels for repeated file/help actions; essential unavailable reasons cannot depend solely on hovering a disabled control.

Use accessible existing proof entry, including supported paste/autofill. Do not add a CAPTCHA, security question, identity essay or forced reauthentication as a substitute for current authorization. Actual higher-assurance requirements still win.

Avoid redundant within-process context entry where safe, but do not overclaim WCAG 3.3.7: it neither requires cross-session storage nor forbids every repeated file upload. Confirmed source evidence should remain available under current permission because that is the product's continuation contract. New browser persistence of private files is not implied.

Provide predictable existing help placement. WCAG 3.2.6 does not require twenty-four-hour staff, a new help screen or confidential request metadata on every error page. Show real contact availability where the actual service provides it; do not invent response promises.

Under weak connectivity, reconciliation must replace guessing. Do not spin forever, repeatedly autoapprove or force another full upload merely to determine whether a receipt exists. Preserve server-confirmed state and explain when a local selection must be chosen again; no unsupported offline capability is promised.

Actual short proof/session/upload time limits still need WCAG analysis. SC 2.2.1 is A, SC 2.2.5 is AAA; neither grants new source time or certifies this flow. Q13's still-unselected fresh lifetime is not an accessibility conclusion.

# Phase 29 Q09 — useful late intake without false lateness or false success

Researched 20 October 2026, Asia/Bangkok. The parent reports Conrad selected **A: the ordinary requested due date is a target; otherwise-authorized late submissions and eligible pending corrections remain available**. Q01–Q08 remain ratified. This note proposes exact UX refinements and proof outcomes for Q09's adversarial review. It does not ratify amendments, choose a numeric duration or establish implementation.

Evidence: the prepared Q09 question, the current ratified files/documents ADRs (especially ADR-0003's admission-time correction fence), and current primary external documentation. The local authority lives under `/home/conrad/code/core/docs/features/files-documents/`; no authority is inferred from the question's still-prepared status when the parent reports the later selection.

This is read-only source/documentation research. No private record, authenticated comparator account, real upload, message, source permission, recipient study, browser/assistive-technology journey or runtime test was exercised. Only this note was written.

## Recommendation

Keep A. The requested date should help recipients understand when work is wanted without creating an unselected hard stop. After it passes, show the **actual outstanding recipient work**, the applicable target and the currently permitted next action. An overdue label is timing information, not a failed input field, automatic rejection or a second approval queue.

Keep the ordinary journey small: identify the requested item, choose a file or Q03 correction, review the relevant target/selection once, deliberately send, and receive truthful persistent outcome feedback. Do not add a late explanation essay, an “I accept that this is late” checkbox, a staff unlock, repeated sign-in or confirmation modal just because a target date passed.

The corresponding boundary is equally important: **A is not more permission**. Source closure, normal fulfillment, binding intake/access ends, current recipient authority, accepted/frozen item restrictions and independent safety rules still control. Q07/Q08 fresh completed-read authority does not reopen intake.

## Preserve the ratified Core contract

ADR-0003 permits an authorized correction only for its exact unaccepted item while source correction eligibility remains open. Overall request openness, preview access or lateness does not supply that mutation right.

Once immutable bytes are finalized and current authority permits durable correction admission, the source records receipt and successor/review-set effects and immediately fences predecessor acceptance. Hygiene/preview may still be pending. A rejected correction does not silently revive the old candidate. Selecting a local file or starting transfer does not change the review candidate.

Q09 must preserve that model for a correction sent after a requested date. “Late” cannot defer the predecessor fence, create a staff-approval waiting room before admitting the effect, or transfer the prior candidate's safe/approved status to new bytes. It also cannot excuse a stale correction target.

Q01 current recipient/action proof, Q02 exact source purpose, Q04 independent preview/original permissions, Q05 current files and safe metadata history, Q06 true normal fulfillment, Q07 fixed completed access and Q08 explicit fresh **read-only** issuance remain independent. A date passing does not reopen, complete, delete, renew or supply any of them.

## Make the actor and the state clear

The most important question on the page is **who needs to do what next**, not whether a broad request status says complete.

An admitted on-time receipt is a historical fact, **not proof of substantive requirement satisfaction**. The source may legitimately require another usable file or an explanation. It must express the actual next work and due relationship rather than using absence of acceptance as a generic “recipient overdue” signal.

A correction can have an applicable existing item/request date if the source actually governs that work with it. Do not require a newly invented date for every correction. Conversely, a later separately assigned task cannot inherit an unrelated date simply because it belongs to the same broad request. Missing due semantics must remain unresolved, not become a default interval.

## Keep receipt and timeliness honest

Keep local selection, transfer progress, durable source admission, hygiene result, preview readiness, review and fulfillment distinct. The chosen due-target rule can attach accurate timing to the source admission; it must not use the browser clock, file modification date, scanner completion, email delivery or user-reported send time as if they were that source event.

This does not decide every business rule about “complete requirements by a date.” A stricter source may define substantive eligibility separately. Preserve the exact receipt and applicable due-policy evidence so the source can explain its decision without fabricating another timestamp.

### Lost and ambiguous responses

If a file was durably admitted before the target but its response is lost and recovery occurs afterward, the original admitted effect/time remains. Do not create a second later receipt or label it late solely because the UI finally learned about it later.

If the result is unknown, say so and reconcile the same attempt. “We have not confirmed whether this file was received yet” is different from “The file was not uploaded.” A second click, page refresh or successful sign-in is not a new deliberate submission. Preserve Q03's exact target/effect recovery rather than using the current latest item opportunistically.

If failure is known to have occurred before admission, the UI can offer a safe retry with the same selected file where supported and still authorized. Do not promise browser file-selection persistence across navigation, OS suspension or a closed tab. If re-selection is necessary, explain it accurately and do not imply earlier work was received.

## Small recipient and reviewer journeys

### Recipient with outstanding work after the target

1. Open the already-qualified request and see the exact outstanding item, its requested date and current allowed action. A concise **You can still send this file** message is appropriate only when current intake allows it.
2. Use the existing accessible file picker. Give known source-format/size guidance before selection. Drag-and-drop can be supplementary; it cannot be the only path. No extra late reason or identity form is required by Q09.
3. Review the relevant target and local selection inline, then deliberately send. A pending correction keeps Q03's exact item target and one **Send corrected file** action.
4. Receive persistent feedback: received, received but being checked, received but unusable, not received, or result still being reconciled. Only current qualified reads become available.

### Staff

Keep timing evidence adjacent to the exact submission and source review state. Distinguish **outstanding after target** from **received after target**, and both from **awaiting staff review**. Use exact receipt events, not a global red “late” status on every file in the request.

When a correction arrives, retain the reviewer’s reading context and exact old version rather than silently swapping content. Explain the changed review candidate and current eligibility. Do not let a stale acceptance action certify the fenced predecessor; do not make the recipient wait for staff to view the correction before its already-admitted effect becomes true.

No new late-review queue, exception ticket type or reminder automation is justified. Source-required business review remains; ordinary lateness does not create another gate by itself.

## Dates, changes and precision

A requested date may be meaningful to a source as a date-only target or an exact instant. Q09 does not choose which all sources must use. Before deriving machine lateness, the source must define the applicable precision/calendar/zone and boundary semantics. Do not manufacture UTC midnight, local 11:59pm or an exclusive/inclusive rule from a bare stored date.

Display a readable localized date and, where applicable, time/zone. Use the relevant date's timezone rules; a browser timezone change cannot rewrite the underlying target or receipt. Exact time labels must not round into a false promise. The same instant can show a different local calendar day; it should not produce contradictory lateness on two devices.

Moving a target later may change the current outstanding-work projection under a source's explicit policy; moving it earlier can affect expectations. Neither operation may rewrite a durable receipt timestamp. Preserve which due-policy version applied to a recorded admission or later decision. This note does not choose retroactive reclassification semantics, bulk date-edit authority or required communications. If those are not defined, do not silently recalculate historical labels using only today's target.

Newly assigned work needs its actual source-declared relationship to dates. Record it as new work, not as evidence the person missed an earlier unrelated demand. A date change, scan delay or staff delay cannot itself fabricate a new recipient act.

## Accessibility, mobile and low bandwidth

Keep the shared Base UI/base-maia controls and ratified accessible request flow. The past-target state must not introduce another primitive system or require a desktop-only layout.

- Provide meaningful labels and programmatic description/error associations; include the relevant item context for repeated file actions.
- Make receipt/check/review changes available to assistive technology with appropriate non-repeating feedback. Do not move focus on every progress update or poll.
- Keep the actual file action and status operable with keyboard, speech and touch. Test mobile file providers and re-selection after interruption; source code alone does not establish those interactions.
- Reflow long translated dates, filenames and errors with zoom/RTL. Essential information must not require hover or color recognition.
- Preserve already-admitted facts when the connection drops. Avoid all-file previews or needless retransmission just to refresh status.
- A source hard stop or current permission loss still applies on mobile/slow networks. Do not silently grant upload-start grace or store an unselected private offline copy to make recovery convenient.
- A soft due target does not settle accessibility of short session/proof timers. Q06/Q07's criterion-specific timing and source-authorized recovery assessment remains necessary.

The general usability rationale is plausible for people with intermittent connectivity or device constraints, but no Asym field study establishes its frequency or magnitude. Do not invent a bandwidth target, timeout, reminder cadence or minimum grace interval as a research finding.

## Strongest alternative remains legitimate

B gives a real intake cutoff and a stable ordinary submission boundary. That can be appropriate for a source whose purpose depends on a defined received set. Public Omnipress documentation provides a genuine example; it is not inherently poor UX when the cutoff and authorized help path are clear.

A trades that automatic stop for continued receipt within current finite source authority. It must not promise staff a frozen review set at the requested date, nor assume every arriving late file is substantive evidence worth accepting. Preserve receipt and review separately. The chosen default does not supersede B-like specialist contracts already owned elsewhere.

## Future proof outcomes and present gaps

The following are independently meaningful acceptance outcomes, **not tests passed**:

1. A target passing alone leaves eligible ordinary intake/corrections available; the identical action is denied when a real current source cutoff/closure/permission end applies.
2. An on-time complete set awaiting scan/review produces no recipient-overdue prompt. A genuinely missing item after its applicable target does.
3. On-time admitted but unusable bytes preserve receipt while the source identifies any actual next recipient work without falsely claiming sufficiency.
4. A late correction retains original receipt/history, changes the current candidate at Q03 admission, fences predecessor acceptance and never silently revives it after check failure.
5. New clarification/additional/correction work uses its true source date relationship, with no retroactive unrelated lateness or automatic interval.
6. Lost response, delayed check, refresh and retry reconcile one exact admission/time; a failed-before-admission attempt and an unknown result have different truthful recovery.
7. Date-only and exact-time source profiles, timezone/DST/locale changes and supported precision give consistent timing facts. Unknown semantics cannot manufacture a classification or authority.
8. Due-date edits preserve event/provenance history and apply only qualified source reclassification rules; no silent prior-event rewriting.
9. Completion, accepted/frozen item state, revocation, intake closure and recipient reassignment racing a late send/correction obey current source ordering and existing Q03 fences.
10. The source's business reviewer can see receipt timing separately from check readiness and acceptance, with a stable exact-version reading context when a correction arrives.
11. Current status/history/read actions survive a mere target passage and remain separately gated after actual intake closure; Q08 fresh reading cannot upload.
12. Actual keyboard, speech, AT, touch/mobile file selection, zoom/RTL/long dates and poor-network recovery work without extra late ceremonies or unclear focus.
13. Appropriate neutral states prevent metadata leakage when current authority is absent; a late badge does not disclose a private request through an old or forwarded link.
14. Representative recipients and staff understand requested-by versus cutoff, received versus reviewed, and the next required action. Report sample limits; no unobserved support savings or satisfaction claim.

This review ran no feature tests and does not establish a qualified native request. Exact source adoption, initial finite access/intake policy, date-change/classification semantics, backend admission ordering and the real browser/AT journey remain required before activation. The parent's owner/runtime passes supply their evidence separately.

No numeric active/fresh period, repetition limit, new grace, reminder, late approval, second confirmation, offline archive or full scheduling engine follows from Q09 A.

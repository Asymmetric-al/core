## Recommended practical fork

For an eligible ordinary Private Document Request evidence entry, staff can give the exact source use a useful descriptive display name. Should that name be **shared among eligible staff only** (A, recommended), or should the **same current name also appear to the currently authorized participant** (B)?

Both options use one source-use name, not personal aliases or a mutable global asset title. Both preserve any source-permitted received-name provenance and exact evidence identity. The participant's current source rights still govern every field; B does not give the participant editing power, historical file access or another person's evidence. Neither option selects a notification, changes download delivery naming or reopens custody/retention policy.

| Option                                              | Useful outcome                                                                                                                                                               | Honest tradeoff                                                                                                                                                                                                                |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A — Shared staff-facing descriptive name            | Eligible staff can recognize an entry as, for example, “2025 address evidence,” without automatically changing the participant's source-approved received-file presentation. | Staff and participant may use different names in conversation. Staff must still identify the exact file through permitted receipt/type/date context; a staff-only name is not a substitute for clear participant instructions. |
| B — Same name also shown to the current participant | The participant and staff can use a common descriptive name for that exact permitted evidence entry.                                                                         | The authoring command must treat the name as participant-disclosable content. Existing internal wording cannot be silently exposed, and participant projections/caches/history must carry the same current field restrictions. |

A is the smaller confidentiality boundary for organizational wording, while B can reduce naming mismatch in a collaborative request. This is a product judgment, not measured Asym usage or a claim that B is inherently unsafe. Avoid calling this field simply **Label** in the interface: Q42 already uses Labels for organizational tags. “Display name” or “Descriptive name” distinguishes this title from tags, the requested-item label, file type and original filename.

## Minimum shared consequences, without choosing a schema

1. **Bind one actual evidence use.** An authorized edit targets the exact current source reference in the tenant/environment/request/item context. It does not rename an entire multi-file item, all same-byte uses, a person, storage key, immutable original, digest, accepted basis, share or public asset. A correction/new Q28 use remains a distinct source fact; no name inheritance from matching bytes, old filename or folder is assumed. Any later carry-forward rule needs explicit source qualification, not an accidental mutable shared pointer.

2. **Keep title, provenance and delivery distinct.** Preserve received-name provenance only where the source permits retention and disclosure; do not rewrite the original receipt or restore a forbidden/disposed name. A useful safe fallback must still identify the entry when no authored title exists. Neither option requires altering the original file extension, bytes or stored locator. Q44's already sealed member names/manifest remain exact result facts; a later title edit does not silently rewrite an old package. Ordinary download-name transformation is not selected by this audience question.

3. **Make the chosen audience real.** Under A, the descriptive name is shared only among staff currently eligible to see that field; staff-only does not mean every tenant member. It must not leak through participant search, download headers, manifests, share metadata, notifications, history, logs or caches. Under B, the author must have actual authority to supply participant-disclosable wording for this use, and the participant still needs current access to that entry and field. Neither option copies names into sealed messages, exposes previous uses or creates recipient editing rights. Existing communication purposes retain their own rules; Q50 itself authorizes no new send.

4. **Use the sole source/P12 decision and its coarse Tenant defense.** Derive actor/tenant/source attribution from trusted context. Read, review assignment, uploader identity or a generic staff role is not rename power. Native constraints should preserve existing immutable scope/relationships; current mutable permission belongs at the source command. Do not prescribe an unnecessary new naming-lineage service or a second authorization engine.

5. **Qualify actual database and alternate paths.** Before activation, test the effective table/function/schema grants, owners, RLS state and combined policies under real supported roles. A permitted name update must not retarget tenant/use/version, alter received provenance, approval or source outcomes. Prove old-row selection and resulting-row checks for supported DML/SELECT/RETURNING/upsert paths and every API/RPC/view/service/import/trigger path. Do not claim omitted WITH CHECK is always permissive, SECURITY DEFINER always bypasses RLS, or the current grant migration proves this feature. No hosted SQL is needed for this question-stage observation.

6. **Keep edits small and recoverable.** One deliberate current-source edit, relevant expected state, safe canonical validation and coherent attributable history suffice. A lost response recovers the original effect; an old replay must not overwrite a later title. A later correction is a new authorized edit. Routine rename need not require preview, body download, a second approver, notification or source re-review, because it changes no evidence meaning. If a proposed edit is actually a requirement/content change, use that owner's qualified command instead.

7. **Treat names as untrusted, confidential text.** Render as text; preserve readable international names and qualify Unicode, controls, bidi, whitespace, length and collision behavior in the actual UI. Equal display names need not merge evidence or establish duplicate identity. File type/icon comes from qualified file facts, not a staff-entered suffix. Do not silently turn title text into a URL, path, SQL/search grammar, HTML or notification template. No AI classification/extraction is required to author a helpful name.

8. **Preserve lawful work during derived failures.** An optional metadata editor/search projection outage must not undo receipt, acceptance or independent current reading. Unknown required authority still denies the affected act. Approved name-search/current caches must update or safely report unavailable without leaking stale forbidden fields. Use existing bounded source/API/query/UI mechanics and measure actual indexing/query/storage costs before activation; no free, instantaneous or globally consistent search claim follows.

9. **Keep rollout prospective and honest.** Existing CMS filename, provider path or inferred common digest must not initialize a shared ordinary title or participant audience without exact source mapping. Inventory actual fields/consumers, define safe initial absence/fallback, qualify old and new writers/readers, and reconcile current restrictions after restore. A scoped disable should stop affected editing/disclosure while preserving admitted evidence and lawful repair. Do not build a generic metadata-schema platform, title-per-view system or provider synchronization layer for this fork.

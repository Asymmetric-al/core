## Recommended single question

**For the ordinary native document request, should a recipient who currently has permission to view their own submitted file also have an explicit, separately authorized `Download original` action, or should that ordinary request remain preview-only?**

The situation: someone submitted a document, can now check the received file, and may correct a pending mistake. They want an exact copy of what Asym received—for their records, to inspect content a static preview does not represent, or to use their normal accessible document tools. Should the request provide that deliberate download itself?

Define _original_ in the question as the exact immutable bytes Asym received for the permitted submission version, not the converted preview, an edited/redacted copy, a newer file with the same name, an official document created by another source, or every previous attempt.

Assume the recipient **currently has permitted request access**. This question does not decide when that access ends. Scope the action to the exact current source-approved own-submission version/member already eligible for Q02 readback; it does not open superseded-version history, other recipients' files or a file library. Current source permission and independently qualified original delivery remain necessary under either answer.

| Option                                                                   | Recipient experience                                                                                                                                                                                                            | Practical tradeoff                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Explicit download of my current submitted original (recommended)** | Alongside View, provide a deliberate Download original action when this ordinary source profile and current rights permit delivery of that exact file. No per-file staff unlocking is the default.                              | Gives a useful exact-copy path and avoids unnecessary staff exchanges. Adds an independently qualified byte-delivery capability and makes an intentional device copy possible. It does not make Asym a backup/archive service.                                      |
| **B — Keep ordinary requests preview-only**                              | The normal request shows receipt, status, View and eligible correction; it does not offer original download. A different source purpose may provide original delivery only through its explicitly qualified policy and journey. | Smaller default disclosure/processing surface. Users must retain their local copy; preview omissions or accessibility limitations need a genuine source-approved alternative. Hiding Download cannot prevent photographing/capturing information already displayed. |

**Recommendation: A**, narrowly. Q02 already admits these files for Asym work and deliberate own-submission reading; useful exact-copy access inside that same task is distinct from a general Drive. A participant need not repeatedly ask staff for a file they just provided. This is product reasoning, not a measured user demand or a permission derivable from having uploaded the file. The new explicit original-download capability still requires founder choice and later source adoption.

Do **not** offer “download only if preview fails” as a third policy. A converter failure cannot create a disclosure permission. A may offer its independently authorized action even if preview is unavailable; B must provide a safe alternative without secretly becoming A.

## Scope guards to present with the question

1. **No new audience.** A applies only to the exact authorized submission source/recipient/principal lineage. Upload attribution, matching email, shared mailbox, digest or possession of the request link cannot create the permission. Another member's submission, staff attachment, other request or business record stays out.
2. **No hidden entitlement inheritance.** Original read/download is an explicit source-qualified action; permission to preview, correct, comment or hold does not imply it. Existing stricter source profiles remain stricter, and their legitimate existing original downloads are not removed by B.
3. **No automatic download fallback.** Converter failure, preview expiry or limited fidelity neither grants download nor justifies an external viewer. The UI may explain an independently available original action; it must not execute it automatically.
4. **No wrong representation.** A returns the exact intended original version with truthful filename/type and lineage. A sanitized/redacted or accessible derivative must be named as such, not mislabeled original. A preview's omitted comments/hidden sheets/metadata can matter when qualifying original disclosure; clean scan alone is not a disclosure or authenticity decision.
5. **No safety bypass.** Known unsafe, restricted or unqualified original delivery remains blocked under the source profile, even if the recipient originally supplied the file. Preview and original byte delivery have different qualification needs; the browser must not execute an active original in the app's authority.
6. **No lifetime/history decision.** Current request access is an assumption for this action. Acceptance/correction/closure does not silently extend access, grant prior-version browsing or change retention/holds. Multiple currently admitted supporting members remain distinct; there is no universal single latest-file pointer.
7. **No recall or verified-possession claim.** Original download permits a device copy. Future revocation blocks new delivery but cannot recall that copy. No-download UI also cannot prevent capturing a preview. A response, grant, started stream, completed stream and human reading are different access facts.
8. **No new outbound sharing or external service.** Download does not authorize email sending, share links, public assets, reuse by other records, export to Drive, source deletion or a general backup product. No new account, file explorer, provider or paid block is needed to decide this policy.

## Practical implementation consequences, without choosing implementation

For A, the later owner/specification package must name a narrow original-download capability and exact request-source projection, qualified original file profiles, current authorization on every protected representation/stream continuation, reliable immutable delivery, restricted access evidence, safe filename/content headers, failure recovery and browser/assistive-technology proof. It can reuse shared private custody; it must not copy Support permissions or expose reusable provider URLs.

## Source meaning must be narrower than raw upload

The practical situation is: Nora has submitted initial evidence, or corrected evidence after a return; the ordinary source now has current actionable work for the already-qualified responsible review path. Whether that path receives an extra email is open. The source must distinguish current reviewability from receipt, technical processing and acceptance.

1. **Q03 correction admission precedes technical readiness.** `docs/features/files-documents/docs/adr/0003-recipient-corrections-and-exact-review-lineage.md:18–31` atomically records receipt, exact successor, relevant review-set change and required history/effect intent once finalized bytes and current source authority permit admission. The old candidate cannot be accepted even while the new file is checking. A rejected successor does not silently revive the predecessor. A transfer start or scan callback is therefore not an email-worthy review decision by itself.
2. **The meaningful review unit is the item and its evidence set.** Q21 ADR `0021-staff-acceptance-of-ordinary-requested-items.md:28–53` requires exact current item/requirement/purpose/evidence and sufficient authorized inspection; an item may have several supporting files and does not require acceptance per file. Do not define one mail per blob, uploaded supporting file, scan retry, rendition or raw technical event.
3. **Staff may have several kinds of actionable source work.** Safe evidence ready for substantive review differs from checking/unsafe material, assignment recovery, missing contact, source cancellation and a genuinely complete source. Only the exact declared source occurrence can define the message meaning. Avoid presenting a checking file as ready to approve or suppressing real recovery work merely because email is off.
4. **Readiness is not a new completion barrier.** No inferred recipient “Done uploading” button, all-request-files-required-before-review rule, mandatory personal claim or batch-review ceremony follows. If product later needs an explicit submit-for-review stage, that is a distinct decision and cannot be smuggled into a staff-mail default.

The default question should use plain language such as “When new or corrected documents are ready for the responsible staff to review, should staff email start on or off?” with both options preserving current work and source authority. Exact occurrence/batching/noise qualification is necessary implementation work, not authorization for a digest or notification per file.

## Practical tradeoff and recommendation scope

My recommendation is the supplemental email **Off default with useful tenant enablement**, not “do not tell staff.” The existing current-work surface and capable recovery remain required. This fits the distinction between the recipient, who may have no reason to reopen a private request, and staff, whose declared review work already belongs in their work surface. This distinction is a product inference, not empirical proof of actual habits.

The strongest case for On is small-team responsiveness: a staff member wearing several hats may not monitor My Work regularly, and a new correction may otherwise wait unnoticed. That is credible, and a tenant with that workflow should be able to enable the exact safe channel. Neither option may claim that email guarantees response or add an unselected SLA/escalation. Actual representative workflows and repeated-review noise need later qualification.

Do not solve either option with a mailbox for every team, a new subscribers model, recipient-controlled staff-send choice, optional reviewer claiming, personal duplicate tasks, per-file alerts or a generic digest scheduler. Leave current staff responsibility, source review basis and item acceptance intact. Tenant configuration must be the real bounded P17 surface, with honest unsupported choices and current permission boundaries; no invented exact role list is selected here.

# Phase 29 Q24 — Ordinary review responsibility

**Research date:** 2026-10-21, Asia/Bangkok. Q01–Q23 and their complete amendments are ratified according to the parent's current instruction. Q24 is a candidate question with no selected answer. This is comparative product/UX research; exact Core owner bindings, current implementation and the final question remain with the parent and owner/runtime reviewers.

## Recommended single fork

**May an ordinary private document request be responsibly handled by an explicitly designated existing team as well as a named staff member, or must every request have a named individual responsible for review?**

Recommend **A — Support a named individual or a qualified existing team**, subject to source-owner validation. Use an existing, valid source responsibility where it already supplies the exact ordinary request's required accountability. Otherwise an authorized person must establish a valid responsibility through the existing source path. This is a proposal for a small capability, not a new configurable assignment engine or permission system.

The strong alternative is **B — Require a named individual for each request**, while permitting other staff to help whenever the existing source authorizes their particular actions. B is not “only one person may ever review.” A is not “every administrator owns everything.” Both need discoverable responsibility and lawful coverage when people leave or cannot act.

| **A — Named staff member or qualified existing team (recommended)** | The source identifies a responsible person or real team. A team can remain responsible while its currently authorized members do the work; the actor of every actual review remains a person with current source authority. A named owner remains available where individual continuity matters. | Accommodates individual casework and shared work without forcing a fictitious personal assignment or a reassignment merely to allow another already-authorized colleague to help. | Team ownership must mean an operationally monitored responsibility, not just a group label. This recommendation is a proportional product judgment, not measured Asym/ministry demand, a universal industry standard or proof that team routing is implemented. FileInvite demonstrates a close document-collection use for team ownership; Content Snare demonstrates a credible named-person model. Neither chooses Asym's policy.

Do not weaken B into an exclusive-person lock. Do not weaken A into an ownerless pool. A team-only model would unnecessarily remove legitimate individual responsibility; adding it as a third choice would make the question less useful. A model requiring both a person and team on every request is credible in organizations that actually require both, but introduces another mandatory field and responsibility distinction not yet justified for the ordinary profile. Existing specialist source requirements for multiple roles remain intact whichever option is chosen.

## Baseline and authority limits

The founder brief's “Requests and fulfillment” section already calls for a responsible reviewer, versioned request instructions and source-owned satisfaction. It also says native requests and shared review tasks must operate without installing a configurable workflow, reusing Phase 9 tasks and Phase 6/17 messages. This question resolves who may carry ordinary responsibility; it does not decide whether responsibility is needed.

The current Files and Documents glossary defines Private Document Request, Document Request Item and source-specific authority. Q21 establishes meaningful exact-current-item staff acceptance; Q22 establishes fulfillment when all real source conditions hold; Q23 establishes recoverable ordinary changes requested and an actual owner route for non-remediable work. Their current review capability, exact evidence basis, preserved history and concurrency rules remain.

The candidate is request-level coordination for the ordinary native private-request profile. A request can contain several items, but this does not merge item-specific review qualifications or create a universal reviewer for specialist evidence. If an existing owner contract instead requires responsibility at an item or separate review-task boundary, preserve that unit; the parent's owner research must resolve it before final framing. A generic parent-record owner, a contact, uploader, request creator or tenant role is not automatically the qualified review owner.

An inherited default should mean a current source-qualified responsibility, not a guessed mapping or an automatic overwrite of a later deliberate assignment. If no valid inherited target exists, the honest state is unresolved responsibility with a capable source-owned next step. This research does not select creator fallback, team-first precedence, a default tenant administrator, or an empty-team assignment. Those would require their own exact authority evidence; they should not be silently bundled into an otherwise useful person/team decision.

## Practical flow with little extra UI

The example is illustrative, not observed ministry practice. Ana creates a document request in an existing source context. That context has a qualified Operations team responsible for ordinary document review. Under A, the request can display **Responsible for review: Operations team**, using the existing source/work surface; Ana need not invent a nominal personal reviewer just to create a usable request. When Omar lawfully reviews the current evidence, the acceptance or changes-requested history identifies Omar and the exact item, not an impersonal team actor. Where Ana is the real continuing owner, A can instead display her name.

Under B, the same request must identify a responsible individual, for example Ana. Omar may still help if separately authorized; his action remains his. If responsibility genuinely moves to Omar, an authorized handoff changes the responsibility record while preserving Ana's and Omar's previous actual review acts. Neither option requires the recipient to choose a staff member, create an account, upload again or repeat already completed work.

For either option:

1. Show current responsibility in the existing request/task context with enough text to distinguish a person from a team. Reuse the source's existing qualified value where valid; do not add a required setup screen merely to repeat it.
2. Make a permitted change one deliberate save in context. Search results and candidate labels themselves obey current tenant/source disclosure. Do not leak hidden departments, staff or sensitive relationships through autocomplete or counts.
3. Let actual review use the established Q21/Q23 actions. Assignment does not accept evidence, start a private read grant, satisfy a requirement, extend a deadline or create a review lock. Do not insert a mandatory Claim before every action without a separate need/decision.
4. Preserve every historical actor, exact reviewed basis, receipt and fulfilled fact through responsibility changes. A changed owner does not reset review progress, erase prior concerns or reopen an accepted item.
5. If the target becomes unavailable or loses the required qualification, expose the actual issue and a capable authorized handoff route to appropriate staff. Do not silently broaden membership/access, drop work or claim “assigned” proves somebody can act. Existing valid independent work may continue under current authority.
6. Recover a lost save result using the same source operation. Show a truthful saved/unknown/failed state without sending duplicate notifications or creating duplicate review tasks. An ancillary list refresh failure is not proof the source assignment failed.
7. Keep the participant view focused on current work and its permitted support route. Internal ownership, contact identity and message sender need not be the same; Q24 does not automatically disclose them or send recipient/staff emails.

The suggested words are provisional UI copy, not a new canonical domain term. A single useful responsibility display/change action is the intended experience. It need not produce separate “team owner,” “assignee,” “watcher,” “queue,” “claim” and “contact” controls simply because a comparator exposes them.

## Tradeoffs to explain before the founder answers

- **A fits different organizational working models, but is not free.** Real team membership, qualified current access and coverage need to be understood. Shared responsibility can diffuse attention if no one watches the existing work surface. That is a credible design risk, not a measured failure rate. A requires an operationally accountable team; it does not require a new queue service, watcher subsystem or compulsory personal coordinator on every request.
- **B is easier to point to, but a name is not coverage.** It can provide continuity and ownership without a second target type. It still needs reassignment and departure recovery and cannot turn the designated person's absence into a permanent inability for other qualified staff to help. It may be the better initial scope if current owner bindings only support people and no genuine team-work responsibility can be qualified without disproportionate new infrastructure.
- **Responsibility and authorization interact but are not interchangeable.** Some sources may deliberately use assignment as one input to their authority decision; this research does not forbid that. It forbids claiming a display value, membership, contact role or watcher selection alone supplies every relevant permission. Reassignment can require current source re-evaluation without globally invalidating unrelated valid work.
- **A source-level default is valuable only when the source actually has one.** The recommendation favors reuse, not a universally invented team. No blanket “inherit parent owner” behavior, silent ongoing synchronization or precedence among multiple eligible groups is selected by this research.
- **Coordinating all items does not imply approving all items.** A request coordinator may need to arrange specialized reviewers. The existing source still decides inspection coverage and exact item authority. No multi-stage board, all-team vote or second approver is added.

## Exclusions and qualification gaps

Do not bundle into Q24: round-robin or skill-based routing, assignment algorithms, workload balancing, numerical SLAs, automatic escalations, reminders, emails on assignment, watcher subscriptions, recipient-visible personal contact, staff availability calendar, mandatory claim-before-review, exclusive editing locks, item-by-item overrides, a new configurable workflow builder, bulk assignment, or expanded review/byte-read capabilities. Existing source features remain governed by their own contracts.

Before activating the selected model, the actual source must identify who may set/change responsibility, the target qualification and usable coverage, current-authority reads/writes, departure recovery, actor/history preservation, source/task projection and recovery, and accessible intended-user behavior. A dashboard label, working picker, imported component or vendor screenshot is not this proof. No real Core assignment, provider write, browser/assistive-technology test or intended-user study was performed in this research.

The parent's owner/runtime findings may require narrower framing. In particular, if exact responsibility is already settled by an adopted source contract, do not re-ask it as a free product choice; ask only the genuinely open ordinary-profile extension. Nothing in the vendor research overrides source ownership or the ratified Q01–Q23 chain.

**Recommended parent framing:** two credible choices, A person-or-qualified-team responsibility and B a required named individual with authorized collaboration. Explain the shared-work benefit and accountability cost, then obtain one founder answer. Save notification, automatic routing and assignment-as-exclusive-authority choices for demonstrated needs rather than inventing them now.

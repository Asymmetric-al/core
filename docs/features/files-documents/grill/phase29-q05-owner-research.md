## Recommended question and framing

**After a recipient corrects a submitted file, should the ordinary request show the current eligible file plus a concise receipt/correction history, or also let that recipient open and download the superseded files?**

Use a concrete situation: the recipient sends the wrong scan, then successfully sends its correction. The corrected file is now the one awaiting review; Asym keeps the earlier submission as required. When the recipient returns, should they see what happened without reopening the older file, or have deliberate access to the older file too?

Here, **superseded** means an earlier submission in the exact correction lineage whose current review candidacy ended under Q03. It does **not** mean every chronologically older attachment. An item can have several independent supporting files, including an older accepted or current member. Those members keep their existing authority and must not disappear when another member changes.

Assume the recipient currently has permitted request access. Decide historical **content scope** now, not access duration. A history entry, retained original, preview and original download are different representations/actions; each remains source-authorized.

| Option                                                     | Recipient experience                                                                                                                                                                                                                                                       | Benefits and costs                                                                                                                                                                                                                                               |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Current files plus a concise history (recommended)** | Keep View/Download for eligible current members. Show a small source-approved record of receipt and correction, but no ordinary preview/download of superseded files.                                                                                                      | Keeps the next action clear and avoids routinely resurfacing a wrong or sensitive attachment. Preserves accountability without a participant archive. Someone who genuinely needs an earlier file uses the source's permitted help/evidence route.               |
| **B — Also allow earlier submitted files**                 | A clearly secondary Earlier submissions area lets the same currently authorized recipient deliberately open/download exact superseded own submissions where each action and file remains qualified. Each is plainly marked as earlier and not the current file for review. | More transparent content history and self-service checking of exactly what was previously sent. Adds historical-byte disclosure, more versions to distinguish and ongoing qualification/access work. It grants no restore, undo, approval or infinite retention. |

Recommend **A** for this ordinary profile. It preserves the focused request experience and Q03's clear current candidate while still explaining why the visible file changed. This is a product recommendation, not an inherited prohibition or measured ministry preference. B is a legitimate bounded history design; it is **not automatically a general Drive** and should not be rejected by that label. The cost worth choosing consciously is greater historical disclosure and complexity in a simple recipient task.

Two alternatives are enough. Do not add “show only the last three versions” without an actual product need, or a generic per-file staff toggle/tenant policy builder as a third option. Those add limits/governance unrelated to the central founder choice.

## Why Q05 should precede the access-duration question

Q01 settled confirmation; Q02 settled exact preview and purpose; Q03 added correction; Q04 added the current submitted-original action. All explicitly reserved previous-version participant access. Correction now creates a normal encounter with history, so deciding whether historical bytes are visible is the strongest adjacent unresolved branch.

The next duration decision needs to know what continued access would include. It can later distinguish current-file access, minimal receipt/history and any historical-byte rights without accidentally bundling them into a single arbitrary expiry. Q05 itself must not decide a 14-day/30-day/forever period, closure rule, retention schedule, refresh mechanism or new proof frequency.

The source-review-outcome branch remains important but is less sharply isolated right now: upload/scan/review/acceptance separation and exact source authority are already settled. Asking a broad acceptance question risks revisiting those invariants or importing financial/application statuses into a native request. The still-required broader staff File Manager/version-history outcome remains unaffected by either Q05 answer.

## What is settled versus genuinely open

- **Settled:** preserve exact submission lineage and source decisions; a newly admitted correction ends the predecessor's current review candidacy and failed successor checks do not silently revive it; preserve siblings and other independent uses; current access and source safety govern every representation.
- **Settled:** original means exact received bytes for the selected submission, not the first historical file; Q04's current-file read cannot silently substitute a different version, resume into a successor or acquire historical permission.
- **Open:** whether the ordinary participant gains an explicit historical-content selection/action for superseded own submissions.
- **Proposed common baseline:** a concise source-authorized receipt/correction history that explains current work without reproducing staff assessments, diagnostic audit or forbidden metadata. Retaining audit already follows owner rules; the precise participant projection remains part of the Q05 review, not a claim that a full history UI is implemented.
- **Not being removed:** source-specific staff/evidence history and any existing independently qualified historical rights. A chooses an ordinary participant default, not a platform-wide history ban.

## Necessary scope and lifecycle invariants for either answer

1. **History follows exact source lineage, not upload order.** Bind request, recipient/principal revision, item, submitted occurrence and correction relation. No grouping by filename/digest, changing “latest” pointer or entire tenant user account.
2. **A source transaction establishes history.** Show receipt/correction as completed only after its authoritative result exists. Local selection, started upload, abandoned staging, scan callback or failed pre-admission correction is not a received successor. Reconciliation retrieves the same durable result.
3. **Keep currentness visible and unchanged.** The current member is clear even while checking. Older historical viewing, if B is chosen, cannot restore its candidacy, inherit acceptance, replace the new file or satisfy a requirement. Failed successor checks never revive its predecessor.
4. **Metadata is not harmless.** Under A, historical filename, type, size, count, actor, date, correction reason, status and linked record may reveal a wrong sensitive upload. Return only the current source-approved participant projection; a minimal `Earlier submission corrected` event may be appropriate without an old filename. No staff notes, hidden requirements, audit diagnostics, other-recipient identities or raw provider facts.
5. **No automatic identity succession.** Current proof and permission control historical projections. Recipient reassignment, mailbox change, merge, principal relink or new request identity does not automatically transfer old history. Use the exact source-owned continuity policy; uncertainty does not retarget.
6. **B is two independent permitted actions on historical scope.** Historical preview and original download each need current qualification and their existing Q02/Q04 safety/disclosure boundaries. It does not promise both for every file. Explicit historical selection is different from retrying a stale current-file URL.
7. **No unsafe or removed content revival.** Retained, quarantined, redacted, restricted, unqualified or disposed evidence cannot be made viewable through historical thumbnails, cached previews, downloads, counts or a new processing generation. Current source restrictions dominate old qualification.
8. **Preserve current-read race rules.** A correction winning before a current-file read still makes that target stale. Under B, a separate deliberate historical action must prove the newly admitted historical purpose. Any already-started stream stays exact and follows ratified expiry/termination rules; no history right follows from a partial download.
9. **History access does not require retaining every rendition.** If B admits a current qualified historical preview, the shared D32 regeneration/generation rules apply; it cannot renew old deadlines, resurrect source access or force indefinite derivative retention. A must not delete historical bytes/derivatives merely because its UI omits them.
10. **No hidden new mutation.** Neither option adds Restore this version, compare/diff, undelete, choose-old-as-current, resubmit-old, reviewer approval, original editing, source deletion, full audit export or bulk ZIP. Such actions need their own source contracts.
11. **No duration or records-policy shortcut.** Access after closure, expiry, renewal and retention remain separate. An immutable receipt can be governed/redacted/disposed under its proper owner; a historical view is not a legal records guarantee or proof that bytes will remain downloadable forever.
12. **Use one calm participant projection.** Prefer current files first and a secondary concise history disclosure if useful. A generic full File Manager/version graph is unnecessary. Reuse authoritative source events/links rather than copy raw audit or create a second archive. Pagination, summaries and disclosure must remain currently permission-filtered.

## What adoption would need, without drafting a specification

**If A is selected:** define the minimal native recipient receipt/correction projection and history availability under current authority; keep byte actions limited to eligible current members and qualified owner-specific exceptions. Provide a source-approved help route when a legitimate need concerns old content. Preserve staff/evidence history and original retention.

**If B is selected:** add explicit native historical-recipient read scope/actions and exact historical selection semantics. Preserve Q04's stale-current-target denial; a history action cannot be an old URL or a bare byte ID. Distinguish current versus superseded clearly, and qualify historical metadata, preview and full-original access independently. This is a substantive access extension to ratify, not implementation polish.

Both need accessible clear labels, safe ordering, current-state/race tests and participant validation in the eventual authorized delivery work. Neither requires choosing a provider, constructing a universal version graph or implementing all of Workflow Studio.

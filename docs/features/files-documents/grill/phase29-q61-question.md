## Plain-language situation

We have agreed what the main document experiences should do. For example, staff can request evidence, a limited participant can submit it, staff can review the exact material, and a mistaken acceptance can now be corrected without erasing history or making the participant start again unnecessarily. Separately, an editor must be able to prepare and release a public asset through its actual publishing owner, then withdraw it without exposing the private original.

The remaining challenge is joining those promises to the actual owners and mechanisms: which source owns each fact, which users can act, which exact files are preserved, how a failed operation recovers, and what evidence proves the entire journey works. Sixty choices do not establish that all those connections are specified or implemented.

The current source/owner/UX review found no further required feature fork justified by the inspected frontier. That is a bounded finding, not proof that every product question is exhausted. We should not invent another library setting just to keep numbering questions. Q61 is about **which kind of work to prioritize before formal specification**, while mandatory research and source reconciliation continue under the existing instruction.

**Recommendation: A, followed by focused validation of the highest-risk journeys.** The most concrete current gaps are ownership, complete source/consumer coverage, recovery and qualification evidence. A addresses those first without adding capability or replacing the later pilot. This is a product/work-order judgment from the present evidence, not a universal rule that documentation must precede user research. B is the strongest plausible alternative and is reasonable when there is a concrete suspected comprehension problem and access to appropriate participants. Small comprehension checks need not wait for every unrelated source adapter to be reconciled.

Neither answer waives required work, authorizes a formal `/to-prd` publication, publishes tickets, starts runtime implementation, contacts participants, uses production/private material or asserts release readiness. Real participant research must be honestly distinguished from an agent walkthrough. User authorization for mandatory source investigation already exists; Q61 chooses emphasis/order rather than asking permission to do that investigation.

## Seven founder checks on the recommendation

### What could go wrong with this answer?

A could turn into document expansion and postpone feedback; B could validate an attractive fiction. Finite register/task deliverables, exact source gates and separate human/native evidence prevent either result.

### What hidden assumptions are we making?

The inspected frontier has no justified new required feature fork after Q60. This is bounded review evidence, not proof of exhaustive product discovery. Participant availability, native integration, provider qualification and production workloads remain unverified.

### How does this affect the whole product?

It prioritizes coherent ownership across ordinary requests, public media, resources, specialist documents and future consumers. It changes none of their facts, access, retention or activation gates and does not back-gate narrow foundations on whole later products.

### How does this affect the end-user experience?

Both paths target complete tasks, including errors, access changes and recovery. A reduces contradictory handoffs before prototyping; B tests comprehension sooner. Neither can skip eventual intended-user/AT/mobile/weak-network validation.

### Does this follow modern best practices?

Current primary service-design/accessibility guidance favors real user problems, whole journeys, simple outcomes and iterative evaluation. It supports both methods; selecting A first is this review's contextual judgment, not a claimed universal standard.

### Does this fit Asym's existing repo and product direction?

Yes: canonical owner/source authority, P12, shared UI, separate specialized meanings and explicit `/to-prd`/`/to-issues` stages remain. Current adjacent CRM hardening is respected without claiming it implements Phase29.

### Should we adjust the recommendation?

Recommend A with tightly bounded deliverables and focused validation next; choose B first if Conrad prioritizes resolving a specific user-comprehension uncertainty now. Continue mandatory source research under either answer. Do not invent another feature or silently authorize formal publication.

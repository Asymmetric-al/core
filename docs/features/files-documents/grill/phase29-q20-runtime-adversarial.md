The useful permanent addition is small: preserve the reviewed choice with the source operation, reliably hand the selected meaning to the existing communication owner, and report the grant and message honestly. No new email engine, permission store, notification ledger, queue, reminder policy, per-user timer or grant-renewal mechanism is needed.

## Nine exact technical safeguards

### S01 — One coherent source outcome, independent communication execution

The owning grant command MUST preserve its immutable source effect, original reviewed notification selection, trusted actor and exact selected communication-occurrence/handoff evidence as one coherent durable outcome. When selected, use the existing atomic source-to-identifier-only handoff/outbox pattern or equivalent qualified owner mechanism. The source MUST NOT commit a claimed selected notice that exists only in browser memory or a best-effort post-commit callback. If the required source write fails before commit, it does not succeed; if commitment is unknown, recover the original operation.

This does not put email rendering, P17 readiness, provider I/O or delivery into the grant transaction or make optional provider success a prerequisite for a valid grant. Once grant commitment is proved, later communication problems cannot undo it or move its deadline. Optional notification may have a typed blocked/unavailable outcome while an independently valid grant survives. If an unshared optional email dependency fails, do not pretend the person opted out; if source authorization itself is unknown, no source grant may be inferred.

### S02 — Preserve selection and distinguish recovery from a new notice

The original checked/unchecked choice is material command meaning. An exact committed grant retry recovers the same effect and choice under current disclosure. Changed true/false, recipient, source or action meaning cannot overwrite the original choice or silently create another message. Missing/legacy/unknown input MUST NOT inherit the new default and count as a reviewed true choice. Reopening a form must not automatically recheck what staff explicitly unchecked.

If the committed source evidence proves true selection and its exact communication occurrence, recovery may complete a missing handoff/materialization for that already-authorized occurrence under current safety. That is different from manufacturing a previously omitted notice. The P6 exact replay returns the prior member/outcome; it cannot add an omitted member to an already released plan or change its immutable meaning. A separate later notification or credential successor is allowed only under its own governed contract, never assumed by this checkbox decision, and never creates another access period.

### S03 — Stable semantic identity across transport and concurrency

Use exact source effect plus qualified recipient/channel occurrence identity, immutable command comparison and existing P6 uniqueness/fences. Distinct browser attempts, queue IDs, worker leases, actor tabs or provider keys MUST NOT create two logical notices for the same selected source occurrence. Preserve exact meaning after long delay beyond provider idempotency retention. A missing-row read alone does not prevent concurrent insert; qualify the existing owning transaction/unique slot including no-row races. Do not infer permanent no-duplicate behavior from `ON CONFLICT DO NOTHING` without checking semantic collision, from Inngest event IDs, or from a provider key.

No new 24-hour cleanup rule is introduced. Keep necessary minimized occurrence/outcome proof under P6/source retention; do not keep plaintext bodies or credentials forever. If required proof is gone or uncertain, do not recreate eligibility from absence.

### S04 — Current source and message authority, exact immutable relations

Qualify source-grant administration separately from the exact selected communication capability and recipient eligibility. Preserve live recipient/destination authority, exact tenant/environment/request/grant type/admission ID, relevant recipient epoch, source revision, contract/plan/member/action and delivery-owner relationships. Browser-provided fields are identifiers or intent, not trusted authorization/attribution. Current checks must survive meaningful waits and concurrent restrictions at the sole owning mutation/dispatch fence, not just the initial review page.

The default is available only within the exact eligible Live contract and Delivery Plan. It does not change those plans, turn required notices off, choose a new address, bypass suppression/readiness or permit different channels. Revalidation may report the selected notice unavailable while preserving a valid source outcome; it cannot silently send later because a previously omitted/closed occurrence becomes newly eligible.

### S05 — Effective database and privileged-path protection

Required relationships, choice, occurrence identity and finite source/end references need appropriate types, NOT NULL/closed constraints, semantic uniqueness and same-scope reference protection, including parent changes and deletion/restore behavior. A same-tenant UUID existence check is not an exact grant-recipient-action relationship. Prove result rows after BEFORE-trigger transforms and all allowed UPDATE/upsert paths cannot retarget identity, flip choice, widen scope or rewrite original outcome/actor attribution. Current head and source facts remain owner-maintained, not caller metadata.

Evaluate actual table/column/function/view grants, roles, policy composition, USING and effective WITH CHECK, service paths, SECURITY DEFINER owner/execution/search-path behavior, jobs and storage. Omitted WITH CHECK for UPDATE/ALL can inherit USING; missing text alone is not a vulnerability. Permissive policies can combine with OR; inspect the effective set. RLS-enabled service tables do not remove the need for trusted command authorization and invariant constraints. Definer behavior follows the actual function owner and table/role/FORCE/BYPASSRLS posture; no blanket claim is justified from the keyword.

### S06 — Submission uncertainty, cancellation and ordered evidence

Adopt P6/P17's immutable prepared message and provider-submission envelope before I/O, exact connection/recipient correlation, bounded qualified same-key retry and monotonic evidence. A send timeout, worker death, expired lease, missing response or malformed success is not definite failure. No changed key/payload/address/publication or split/replacement can solve uncertainty. One logical notice is not a promise of exactly one physical email or human receipt/read.

Cancellation/source restriction that wins before submission prevents the affected unsubmitted send. If the submission fence already crossed, preserve accepted/unknown evidence and stop further unsafe I/O or use under the owner rules; do not claim recall. Late/out-of-order/duplicate authenticated webhooks may refine evidence but cannot rewind stronger facts, mint a new notice, infer reading/acceptance, renew a grant or retarget tenant. Verify raw bytes, then establish scope from the qualified connection/submission identity; payload address/tags alone cannot select authority. Contradictory evidence remains a governed incident/reconciliation state.

### S07 — Access and protected transport remain separate clocks

Q14/Q18 source issuance/end stay unchanged by review, preparation, notification delay, retry, delivery, link open, proof repair or credential reissue. Current source eligibility governs every protected operation. A delayed notice must not promise a fresh full period; expired/revoked or otherwise no-longer-useful work ends/suppresses according to the exact adopted message contract without creating new access.

Adopt the no-Party recipient branch already ratified by Q01 through the existing producer-owned doorway. Preserve frozen qualified tenant origin, inert GET/HEAD, deliberate verification POST, recipient/source binding, current proof, cache/referrer/CSP/observability fences, and short-lived non-authorizing landing state. No raw attachment, public URL, provider retrieval link, alternate origin or old-token-to-latest-grant fallback. Template, preview, editor, tag, raw event, recent copy, history and logs cannot acquire protected credentials. Qualified new credential issuance can need a new communication/prepared identity without changing grant identity or end.

The optional external notice's exact material-retention/utility class is a qualification gate. No unselected numeric TTL, extra access stage, reminder or grace period is created here.

### S08 — Truthful partial outcomes and bounded recovery

The result must distinguish confirmed/unknown grant commitment, original notice choice, communication request/handoff, preparation/dispatch/provider state and currently usable participant access. Do not call grant success “recipient notified,” treat a lookup error as proved suppression/no configuration, or label provider acceptance human awareness. Recover selected-notice work through existing source/P6 repair, not another grant or a new dashboard. Safe grant-only handling must remain useful where the source supports it, without inventing an alternative disclosure path.

Use bounded indexed exact effect/occurrence/submission lookup and authorized paginated history. Existing fair bounded dispatch/reconciliation owns capacity, current usefulness and cancellation; no correctness-critical full grant-history scan, per-recipient resident timer, unbounded send fan-out or second queue. Operational pressure may defer/suppress truthful delivery within contract rules but cannot widen authority, move access ends or trigger duplicate grants.

### S09 — Prospective rollout and evidence-preserving restore

Activate only the exact qualified source/contract/default cohort. Old clients, missing selection, historical grants and migration defaults do not generate new mail. Existing source effects and selected notice facts cannot be rewritten on policy change or rollback; old/new workers must not disagree on immutable command/schema identity. Keep one writer per authoritative boundary.

Restore/import/export/compaction must reconcile required source/P6 occurrence, provider fence and later restriction/disposal facts before serving or resuming. A restored older “unsubmitted” snapshot cannot authorize I/O when later evidence might show submission. Preserve necessary body-free proof without restoring expired restricted material. Existing controls may stop unsafe new notice dispatch while legitimate source access and unrelated communication retain their own policy; no kill switch silently revokes grants or enables another channel.

## Primary documentation and verification limits

- [PostgreSQL 17 CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html): current-row USING and resulting-row WITH CHECK, omitted-check inheritance, policy combination and BEFORE-trigger ordering. These exact semantics supersede oversimplified skill shorthand.
- [PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) and [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): grants/RLS are separate; role/owner bypass and service-client versus user-token behavior require inspection. The current service client construction was read; no deployed role attributes were queried.
- [PostgreSQL 17 constraints](https://www.postgresql.org/docs/17/ddl-constraints.html) and [locking](https://www.postgresql.org/docs/17/explicit-locking.html): NULL and relationship rules need real constraints; row locks protect retrieved rows, not an absent future row. No particular new schema/lock framework is prescribed.
- [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), checked during the Q20 research today, documents a 24-hour provider window. [Webhook introduction](https://resend.com/docs/webhooks/introduction) documents replay, and [verification](https://resend.com/docs/webhooks/verify-webhooks-requests) requires the raw body. These support transport assumptions only, not Core deployment or actual delivery proof.
- The Supabase markdown changelog fetch was attempted but the browser tool rejected its content type; no changelog-complete or version-upgrade claim is made. Current relevant official RLS/PG documentation was available. No implementation was changed, so no CLI/config migration investigation was required.

This review ran no native suite or synthetic model. The material claims above follow directly from inspected source transitions and authoritative contracts; a mocked grant/notice model would merely restate the proposal. Actual source transaction, role, concurrency, provider-boundary, restored-state and composed user proofs remain activation gates. The exact source/message mapping is still to be designed under the current owners, not invented by this report.

An untrusted query is not inherently an unauthorized query. The server may accept a filename, identifier or digest as data while independently deciding whether any resulting candidate may be disclosed and used. **The browser fingerprint does not establish which incoming bytes the server has received.** A candidate based on that input must not be called a server-verified duplicate of the incoming file. The selected existing version can still be independently verified and deliberately reused through Q28; that act uses its held bytes, not a falsely certified new upload.

A server-verified equality check could instead occur after qualified private transfer/preparation, but that is not an instant pre-transfer check and adds real latency/work. It must not silently insert a pause, mandatory duplicate modal or second completion click into Q53's already-deliberate Upload and add. Once that intent starts, a late suggestion cannot retarget, replace or reinterpret it. After source admission, no hint can undo the contribution or invent a physical cleanup right. If B cannot qualify a useful pre-intent candidate path, A remains a complete permanent choice; a future owner decision may consider an explicit optional preparation/check action rather than a hidden workflow change.

## Current primary technical evidence and its limits

Context7 resolved `/mdn/content` and returned the current `SubtleCrypto.digest()` documentation. Direct current [MDN digest documentation](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest) confirms SHA-256 support, secure-context availability and use in Web Workers, but **no streaming input**: the whole input must be in memory. This makes a browser fingerprint feasible for a qualified bounded cohort, not free, instant or safe at unbounded file sizes. Worker support alone does not bound memory or prove supported-device performance. A native incremental implementation would need its own qualification; no new hashing dependency is selected here.

[PostgreSQL 17 multicolumn-index documentation](https://www.postgresql.org/docs/17/indexes-multicolumn.html) explains how leading equality constraints can limit a B-tree scan. That supports investigating a scoped indexed lookup, but says nothing about this application's workload, source filter cost, effective authorization or billing. A query plan and realistic current-role data distribution remain necessary; no schema or capacity number is frozen here.

Current [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) distinguishes table grants from row policies and warns that creating policies does not revoke existing grants. The current assets source above makes that distinction relevant. Apply actual role/policy composition and privileged-path evidence, not a generic “RLS enabled” assertion or a second database copy of P12's permission logic.

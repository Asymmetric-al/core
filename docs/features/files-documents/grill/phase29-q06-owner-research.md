# Phase29 Q06 — normal fulfillment versus recipient read-only access

Bounded owner research, 2026-10-20. Conrad has explicitly ratified Q05 and all its amendments; the parent is recording that unchanged. Q01–Q05 are settled grooming intent. This note recommends the next question only: no Q06 choice, duration, permission or implementation is selected.

## Recommended single founder decision

**Once an ordinary document request is normally fulfilled and no longer accepts submissions or corrections, what should a returning recipient still be able to see while their source-authorized request access remains valid?**

Use a recognizable situation: the organization has completed its approved review of what it requested. The recipient returns to confirm the outcome or obtain the exact current file. Should the finished request remain a limited read-only page, show only receipt/status/history, or end protected access at completion?

The scope is **normal source-confirmed fulfillment**, not every state labelled Closed. It does not include security revocation, cancellation, withdrawn access, a rejected application, an expired invitation or a lost browser session.

| Option                                                      | Returning recipient experience                                                                                                                                                                                                    | Benefit and cost                                                                                                                                                                                                                            |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Keep limited read-only access (recommended)**         | Show the completed request's source-approved status, Q05 concise history and eligible current-file View/Download. No ordinary upload/correction. Every read remains authorized, qualified and bounded by the source's access end. | Preserves confirmation and useful exact-copy access after normal work ends, with little new interaction. Requires an explicit access-end policy and continued private serving; it is not a permanent archive.                               |
| **B — Keep confirmation/history, stop file access**         | Show currently permitted receipt/status and Q05 history, but no ordinary file preview or download once normal completion commits.                                                                                                 | Retains proof of what happened with less continuing byte disclosure. People needing the current file must use an independently authorized source help/delivery route or their existing copy. Metadata still requires private authorization. |
| **C — End protected recipient access at normal completion** | A later visit cannot retrieve protected request status/history/files. Provide only a safe neutral unavailable/help route where allowed.                                                                                           | Smallest continuing disclosure surface, but recipients may be unable to verify completion later and will need more assistance. It is a deliberate stronger ordinary policy, not something inherent in marking work complete.                |

Recommend **A**. Completing ordinary work should normally stop further contributions without making its useful confirmed outcome disappear while the recipient still has legitimate bounded access. That matches the established separation of source work, action scope, identity, current read permission and retained evidence. The usefulness/support reduction is a product judgment, not measured ministry demand.

Do not frame C as “safer by definition,” or B as a universal compromise: both reduce ordinary access and can be valid source policies, but they impose real recovery costs. A preserves the no-Drive boundary because it remains one exact task, current eligible files only, no superseded-byte archive and no unlimited retention/access.

## The decision is scope at fulfillment, not a duration

No universal 14-day, 30-day, grace, forever or “until someone remembers to revoke it” rule is established. Before activation, the native source must have a finite, explicit access-end policy with qualified lifecycle/renewal behavior. Unknown end policy cannot silently mean indefinite access.

Q06 need not select the numeric period, its anchor, renewal ceremony or whether separate source actions have narrower eligibility. Those can be researched next once the founder chooses which post-fulfillment capabilities exist. Normal completion, opening the page, downloading, signing in again or regenerating a preview must not accidentally reset or extend an existing source-access deadline.

The term **remaining permitted access** does not mint a new grant. A continues only reads that the current source/PDP still authorizes. If access already expired or was withdrawn, ordinary completion cannot revive it. A later deliberate, qualified source renewal is a separate access decision; it does not reopen upload/correction or historical bytes automatically.

## Why this is the highest-leverage next branch

Q01 selected recipient confirmation; Q02 exact preview and purpose; Q03 correction; Q04 current-original download; Q05 current content plus concise history rather than superseded bytes. These define the active request's actions and historical scope. The remaining immediate lifecycle question is whether normal fulfillment itself removes those read actions.

This question comes before choosing an expiry length because the duration needs a known capability scope. It also avoids asking the founder to choose a generic workflow status model. The source's exact accepted completion evidence remains authoritative; this question does not redefine application acceptance, official document validity, staff review outcomes or financial truth.

## Scope guards needed with the founder question

1. **Narrow normal completion.** Use the ordinary request owner's exact successful fulfillment predicate/receipt. Do not define a generic “all files uploaded means done,” or extend this decision to P18 receipts, P21 claims, P26 conversations or P41 application rejection.
2. **Read-only really restricts commands.** Under A or B, no ordinary new upload/correction follows fulfillment. Source-owned correction/reopening/remediation retains its existing explicit authority; a new proof or access renewal is not that authority.
3. **Only currently eligible current content.** A retains Q02/Q04 reads and Q05 concise history, not superseded bytes, staff assessments, another recipient's files or a downloadable archive. If safety/currentness/permission makes a particular file unavailable, show only its permitted state and source recovery.
4. **Known finite source end.** Choose no number here, but require an explicit bounded access policy before activation. Do not use `null`/missing expiry to turn “until source ends it” into indefinite personal storage. No arbitrary per-tenant policy builder is implied.
5. **No automatic renewal or resurrection.** Completion/sign-in/read/download/history refresh does not reset existing deadlines. Prior expiry/revocation still wins. Any later extension needs its own qualified source policy and current proof, not an old token or favorable task status.
6. **Separate metadata and byte consequences.** B preserves private receipt/status/history under current permission, not public indefinite metadata. C must not leak protected completion details through its unavailable page. A does not imply that metadata and every byte remain available after a stricter source restriction.
7. **Race-safe source semantics.** Completion, correction, access-end and revocation need the same relevant source ordering already required by Q03/Q04. A late upload cannot be accepted because transfer began earlier; a stale status cannot authorize a new read. Existing in-flight delivery remains exact, bounded and honestly non-recallable.
8. **No retention or notification side effect.** None of the options changes source custody, holds or disposition, sends an automatic email, reopens a task, generates a new official artifact or claims the recipient has read anything.
9. **Truthful and calm return experience.** Where access remains, say the request is complete and whether any source action is still needed; remove unavailable mutation controls. Distinguish completion from access ending, and provide the already-qualified help route without promise of renewed access. Do not show an expired-login error as a rejected application.

## Adoption and evidence implications

The later authorized native source contract must express normal fulfillment separately from write eligibility, recipient read eligibility, security restriction, admission/session validity and source retention. These can be independent facts behind simple UI labels; no new universal state machine, global workflow or permission engine is needed.

A requires a purpose-bound post-fulfillment read policy using the existing Q01-compatible context/PDP, Q02 preview, Q04 original delivery and Q05 history. B additionally narrows ordinary file actions at the fulfillment boundary. C narrows all protected recipient actions there. Each needs exact source transition/read race and recovery proof; none can be implemented by hiding buttons or relying on token TTL alone.

The numeric duration/anchor, any future renewal policy, source-specific cancellation/rejection handling and actual profiles remain unselected. They are required later decisions/qualification inputs, not gaps to conceal with an unlimited fallback. No runtime-completion, provider behavior or real-user usability claim is made here.

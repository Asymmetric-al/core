## Small new platform experiment: exact scope and results

Ran `/home/conrad/.nvm/versions/node/v24.21.0/bin/node` through **bubblewrap 0.9.0**, with a read-only `/`, temporary `/tmp`, working directory `/tmp`, cleared environment containing only fixed PATH/HOME/TZ, and an unshared network namespace. TZ was `America/New_York`. The script arrived over stdin, imported nothing, read no project/config/credential files and made no service calls. It used built-in Date arithmetic, string formatting and one timeout. Command exited 0; these are observations, **not product tests or native permission proof**.

The script first calculated the exact 720-hour constants and confirmed that 2,592,000,000 ms exceeds 2,147,483,647 ms. It then added that exact duration to five synthetic source instants and compared local `setDate(+30)` and raw `setUTCMonth(+1)` behavior:

Every exact-duration difference was 720 hours. `setUTCMonth(+1)` is the specific JavaScript operation observed; its January overflow is not a claim that every calendar-month library uses identical rules. Both comparisons demonstrate why a calendar operation cannot silently implement this chosen elapsed profile.

Finally, `setTimeout(callback, 2592000000)` emitted `TimeoutOverflowWarning`: the delay was set to 1 ms. The callback was observed after **1.833 ms**, before a 100-ms cleanup watchdog; the watchdog was then cleared. The 1.833-ms measurement is one platform observation, not a scheduling guarantee, performance benchmark or real permission expiry. No month-long wait was scheduled or left running.

The exact [Node v24.21.0 timer documentation](https://nodejs.org/download/release/v24.21.0/docs/api/timers.html) documents that delays above 2,147,483,647 ms become 1 ms and that callback timing is not guaranteed. PostgreSQL likewise documents that calendar-day addition can differ from elapsed-hour addition across DST. [PostgreSQL date/time arithmetic](https://www.postgresql.org/docs/17/functions-datetime.html)

This experiment does **not** test PostgreSQL arithmetic/roles/locks, the source timestamp producer, fractions beyond Date's supported representation, production timezone data, browser timers, durable schedulers, current grants, request serving or intended-user usability. ## Precise SQL/authorization semantics retained

- PostgreSQL supports nonfinite date/timestamp values; a required TIMESTAMPTZ alone is not finite-end proof. CHECK can pass when its expression is null, and it does not re-evaluate merely because time advances. Enforce required finite valid state and current authorization at the owned boundary. Cross-row CHECK is not a durable relational invariant. [PostgreSQL date/time types](https://www.postgresql.org/docs/17/datatype-datetime.html), [constraints](https://www.postgresql.org/docs/17/ddl-constraints.html)
- CURRENT_TIMESTAMP/NOW use transaction start. Timestamp capture after a lock in code does not make that value current after the wait. The qualified source occurrence must lead to a durable valid effect; wall-clock reads do not automatically certify physical commit. [PostgreSQL time functions](https://www.postgresql.org/docs/17/functions-datetime.html)
- For UPDATE/ALL, omitted WITH CHECK may inherit USING. Inspect combined permissive/restrictive policies and BEFORE-trigger resulting rows, actual roles/column/function grants, parent relationships and privileged callers. Do not claim a vulnerability from a missing keyword. A definer's actual owner authority and BYPASSRLS/FORCE behavior matter; source-owned service paths still need explicit enforcement. [PostgreSQL policies](https://www.postgresql.org/docs/17/sql-createpolicy.html), [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)
- Locks on returned rows do not protect a missing future effect; per-key dedupe does not serialize distinct source intents. READ COMMITTED cannot automatically validate a multi-row permission snapshot, and empty ON CONFLICT DO NOTHING return is not absence proof. Apply Q17's owned shared invariant and stable recovery once the still-open repeat policy is adopted. [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html), [isolation](https://www.postgresql.org/docs/17/transaction-iso.html)

## Recommended frontier and fair choice

The strongest next bounded question is **who sees a staff-authored descriptive name for an ordinary request evidence use**. Rename itself is already a founder requirement. The new choice must not ask whether staff can rename at all or whether a storage blob has a global name.

For example, Nora supplies `IMG_2047.jpg` for an equipment-inventory item. Elena can give that exact admitted use a helpful display name such as “Equipment inventory photo.” The file's exact identity, received act and bytes stay the same. Should Nora's currently authorized file view also use Elena's new name, or should that name remain a shared staff label while Nora keeps the source-approved received-file identification?

A is a product judgment, not an inherited ban on participant-visible names or a measured claim about Asym mistakes. B is feasible and meaningful if explicitly adopted. Existing source classification and disclosure floors bind either option; neither is a public label, a new share, participant edit permission or a new notification purpose. The first question should cover the existing request participant, not silently select Q41 external-share, email, archive-member or specialist naming behavior.

## Why this remains open

- The founder attachment §8 requires identity-preserving rename/move and useful metadata. It does not decide whether a staff-authored ordinary file display name is internal or participant-facing.
- Q02 declares independently admitted source uses and source-authorized metadata; a filename does not own purpose or permission. It does not choose this rename audience.
- Full Q05's current-file/history decision requires minimized participant source facts, current disclosure and meaningful receipt/status. It does not say a later staff-authored display name is automatically participant-visible, nor prohibit a separately adopted current display label.
- Q38 decides the information scope of general staff discovery: approved names, typed metadata and source context, with current field disclosure before search effects. It does not grant renaming authority or choose the participant projection.
- Q42 chooses the ordinary organizational entry: an exact admitted contribution/use. Its tags, folders and saved views do not select an evidence display-name command. A correction is a new admitted use; the home-only initialization decision is not a document-wide naming lineage or automatic title transfer.
- Q44's safe ZIP member names are delivery labels mapped to permitted provenance. That does not rename the business source or select live participant display naming.

Thus the practical fork concerns **audience and recognition**, not the schema location of a field. A global asset-wide rename alternative would be unfair: source independence is already required. Likewise, “original filenames only, no rename” would discard the founder baseline.

3. Distinguish the current descriptive name from source-required received provenance. Retain/reveal original filename facts only where the actual source permits; do not promise universal raw filename retention or expose discarded or restricted names as fallback.
4. Stable use/version identities, receipt time, original bytes, embedded document titles, accepted basis and correction lineage do not change. Do not rename a whole multi-file item or every occurrence merely because one entry is selected.

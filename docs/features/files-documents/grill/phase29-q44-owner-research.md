# Phase 29 Q44 — Owner research: delivery shape for selected ordinary request files

**Date:** 2026-10-25, Asia/Bangkok. **Stage:** researched, unselected question. Q01–Q43 remain ratified; this note selects no Q44 answer, new glossary term, formal owner/OpenSpec change, implementation or provider. Only this assigned note was written.

## Finding and recommendation

The next useful question is **one bounded private ZIP versus a prepared list of individual original downloads for the same finite selected ordinary request-evidence set**. Recommend the ZIP experience, while retaining ordinary individual Download and deliberate smaller selections. It keeps several intended files and their permitted contents/outcome record together. This is product judgment, not measured Asym staff preference or proof that an archive is faster, cheaper or easier on every device.

Both options must have the same current source/export authority, exact selected versions, integrity evidence, protected manifest, short private staging where material is staged, truthful partial results and recovery. The alternative is credible: a prepared list lets staff retrieve or retry one original at a time without ZIP generation or extraction, at the cost of more interactions and manual collection management. It must not automatically launch a browser download storm. A manifest and bulk selection are not exclusive benefits of the ZIP option.

The founder already requires authorized bulk download. The open decision is its ordinary browser-delivery shape. Neither a new export permission nor a ZIP implementation library is the question.

## Boundaries common to both options

1. **An actual source export purpose comes first.** First-cohort staff download/export must be explicitly qualified under the ordinary source and P12. Neither participant Q04 access, Q41 sharing, a prepared capability registry nor a visible Export button establishes it. Stronger originating-source restrictions survive Q28 reuse.
2. **Select exact uses and versions.** The command uses a finite explicit selection. It cannot rerun a live view later and include new matches, infer all item attachments/history, recursively include folders or replace selected bytes with a later correction. Source currentness can deny obsolete material without changing the intended selection silently.
3. **Do not invent source lifecycle rules.** No universal acceptance, preview-ready or unfinished-request prerequisite follows. Actual source authority determines which current or historical original may be exported. Retention alone is not access, and participant completion/expiry timers do not define staff export periods.
4. **Protect manifest and file metadata.** Names, source references, outcomes, sizes and counts are subject to current disclosure. Unknown or unavailable evaluation is not proven complete/empty; definite exclusions do not require leaking the denied item's identity. Ordinary manifests do not inherit D26's broader coverage semantics by accident.
5. **Keep current authorization through delivery.** Preparation creates no enduring grant. Qualified release/full/range/recovery boundaries must enforce the current exact authority for included bytes and metadata. Revocation can stop future delivery; it cannot recall lawful local copies. No universal lock or false promise to erase previously emitted bytes is implied.
6. **Preserve exact originals.** No PDF merge, preview substitution, flattening, office execution, source-byte transformation or silent re-render. Delivery-member collision handling must retain permitted provenance without renaming the business source or making two files overwrite one another.
7. **Keep outcome facts separate.** Selected, admitted, prepared, offered, started, transferred and known incomplete are not interchangeable. A valid ZIP or HTTP success is not intended-set completeness; browser transfer is not human reading, saving, custody transfer, fulfillment or official-record completeness.
8. **Use short private staging without changing source retention.** Actual finite budgets need qualification, not guessed 7/30-day or vendor limits. Expiring package material does not dispose of source records, release holds, erase required minimal outcome evidence or automatically extend access. No public fallback under load.
9. **Recover through supported commands.** Lost responses, duplicate clicks, cleanup failure, changed authority and interrupted transfer need truthful current-authorized recovery. Neither option promises automatic resume before qualification. A remains compatible with deliberate smaller selections and ordinary individual downloads.
10. **Keep scope small.** No email delivery, cloud destination, new connector, public link, recipient addition, offline replica, new archive-format menu, universal file manager or generic export engine is selected. No new glossary term is needed for this question.

The full selected-answer review should settle exact partial/retry/release behavior and finite launch budgets against implementation evidence. This question does not prematurely choose silent omission, all-or-none byte transfer, a new provider, a worker architecture or a permanent export-state taxonomy.

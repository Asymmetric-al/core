# Phase 29 Q02 — purpose-bound documents and safe own-submission viewing

Inspected2026-10-20, Asia/Bangkok. External research and proposed clarification only. The parent reports Conrad selected Q02A and explicitly bounded Asym to relevant files/media used in or produced by Asym, rather than a new Dropbox/Google Drive. No product implementation, account sign-in, purchase, real upload, message, or permission change performed. Public official documentation was read; Stripe documentation was retrieved with the existing CLI. No competitor or provider account behavior was tested.

## Conclusion

Q02A remains defensible: a request recipient can receive truthful submission/status information and inspect a source-permitted qualified view of the exact version received. This is a bounded way to finish an Asym task, not an entitlement to a personal drive, full folder, all documents about that person, or permanent download access.

Conrad's scope boundary should be interpreted as **an accountable Asym purpose**, not **an already active placement or attached business row**. A reusable ministry image or approved resource can be prepared before a page/event uses it. A request must also accept its first submission before the downstream application/workflow is complete. Existing CMS patterns explicitly distinguish reusable media records from their later references. Rejecting all unplaced assets would contradict these ordinary workflows and could delete valid retained material.

The necessary distinction is purposeful intake/catalog custody versus arbitrary personal storage. A filename, folder or free-form “for Asym” note does not itself establish purpose, authority or retention. The source owner, admitted purpose and intended use must be accountable without forcing staff to fabricate a campaign, publish a page or complete a future product merely to reserve an asset.

## Proposed scope clarification

These are product judgments to reconcile with accepted owners, not new founder decisions or a universal file schema.

**In scope:** documents/media received for an authorized Asym request, attached through an authorized source use, produced by an Asym business process, or admitted as a source-owned reusable resource/media asset intended for Asym use. Preparation, validation and temporary intake can precede active use. Generated receipts, expense evidence, conversation attachments and publishing assets retain their respective source meaning, audience and retention.

**Not made in scope by Q02:** personal drive storage, arbitrary organizational backups, unbounded file synchronization, general desktop-folder sharing, a replacement office suite, or a reusable public-link service for material unrelated to an admitted Asym purpose. Existing user-owned material must not be purged merely because this boundary is clarified; legacy ambiguity requires owner classification/migration handling.

Do not equate these states:

- **Not yet placed:** a legitimate reusable item awaiting use.
- **No currently visible use:** an authorization-filtered result, potentially incomplete.
- **No remaining business use:** still potentially subject to retention/hold, recovery or historical obligations.
- **No justified purpose:** an intake or stewardship problem needing a source decision.
- **Disposable:** a separate qualified disposition decision based on complete obligations and current state.

A general reusable resource that lacks an existing specialized domain still needs a narrow accountable owner. Q02 does not assign that owner or authorize Phase29 to absorb every document domain. Avoid a mandatory active-record foreign key that forces fake business records; equally avoid an ungoverned “general files” exception. The exact source-purpose admission can be implemented using existing owners without a new universal workflow/policy engine.

## Safe view: security, exactness and accessibility are separate

[OWASP File Upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), living source, recommends layered file validation, authorized operations, bounded sizes and processing, isolated storage, scanning/CDR where appropriate, and safe retrieval. MIME headers and extensions alone are not sufficient, nor is one magic-number check. Private data must not be sent to public scanning services casually. These controls support a qualified processing pipeline; they do not certify the truth of the document's contents.

[OWASP SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), living source, addresses server requests to attacker-selected destinations. Applying that lesson here: renderers/importers must not fetch arbitrary embedded URLs, internal network locations or metadata endpoints just because a file was accepted. A purpose-owned ingestion path must qualify any required outbound access. A competitor's “upload from URL” button is not a safe default.

Proposed view contract, in normal product terms:

- Show which received submission/version the view represents. Bind processing results to those exact bytes and the qualified processing profile; never silently point an earlier receipt or review at a later upload.
- State meaningful omissions. A cover thumbnail, truncated sheet, omitted attachment, first video frame or partial OCR is not a complete review of the document. Processing success, visual fidelity, accessibility and owner acceptance are distinct facts.
- Preserve current source authority for metadata, previews, original bytes and alternatives. Scope by exact use/request, actor and version, not simply uploader email or folder membership. Do not infer that access through one use reveals all other uses.
- Keep unsupported, encrypted, malformed or still-processing content unavailable through unqualified rendering. The receipt of bytes remains true. No fallback to public URLs, raw active HTML/SVG/macros, or an arbitrary external office viewer.
- A permitted viewer may copy visible information. Hiding download controls is not DRM. Original download remains a separate source choice; screenshots/copies already delivered cannot be recalled after revocation.
- A new rendition does not replace an official canonical artifact. OCR/conversion must not rewrite legal/financial meaning or the preserved source bytes. Source-required provenance restrictions still apply; generic custody cannot retain forbidden source metadata merely for convenience.

## W3C implications for embedded document viewing

[WCAG2.2 conformance](https://www.w3.org/TR/WCAG22/#conformance-reqs) applies to full pages and complete processes and relies on accessibility-supported use of technology. A conforming outer dialog does not excuse an unusable embedded viewer. Do not claim conformance solely because a component has an accessible name or a browser can open a PDF.

[W3C H64](https://www.w3.org/WAI/WCAG22/Techniques/html/H64), updated2026-01-12, explains that a descriptive iframe title labels the frame, not the content inside it. [No Keyboard Trap](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html), SC2.1.2 LevelA, requires keyboard users to be able to leave the component; nonstandard exit methods must be explained. The viewer and surrounding request need workable focus, navigation, zoom/reflow, loading/error status and a safe return to the task. Techniques/Understanding pages are informative guidance, not standalone certification.

[W3C PDF7](https://www.w3.org/WAI/WCAG22/Techniques/pdf/PDF7), updated2025-07-15, explains why image-only scanned text is inaccessible and describes OCR plus tags/reading-order verification. Merely generating OCR is insufficient: output completeness and correct reading order need checking. This research does not authorize a broad OCR/search/AI corpus. Accessible extraction remains limited to the source-approved purpose and exact version.

The supported-format qualification must therefore distinguish **accepted for custody**, **available in a qualified technical preview**, and **available in an accessible equivalent representation**. Do not promise every file is viewable or that a PDF extension assures accessibility. If an essential format lacks an accessible safe path, show honest unavailability and the source-approved alternative; do not silently widen download permissions. Supported families and limits require concrete qualification in later work, not copying another vendor's numbers.

Preserve available native text and semantics in qualified display paths. Rasterizing a text document into image-only pages can make the preview less accessible than its source; a filename used as image alternative text is not an equivalent to the document's contents. When an accessible equivalent must be produced, retain it as a source-approved derived representation bound to the exact source version, rather than silently changing the original or asserting canonical status. Disclose an inaccessible original truthfully. This does not promise OCR, AI transcription, office editing or complete accessibility of arbitrary uploads. Qualification requires actual content and assistive-technology tests, not only keyboard tests of the viewer controls.

## Material tradeoffs and adversarial conclusions

Purpose-bound reuse reduces repeated uploads and gives staff context, but only if links do not collapse distinct legal/business identities or widen audiences. Preparation before placement is necessary; unrestricted storage is not. Central custody can track exact bytes while specialized sources continue to decide currentness, rights, business acceptance and retention.

Own-submission preview provides continuity and a way to catch the wrong scan; that is an expected usability benefit, not measured evidence. It also creates a sustained read pathway vulnerable to stale access, changed mailbox control, incorrect actor attribution and unsafe conversion. Q01 confirmation is necessary admission evidence but does not eliminate these risks. The simpler upload-only option remains a fallback profile where the source intentionally does not admit read access; it should not silently replace Conrad's chosen ordinary experience everywhere.

The permanent boundary should permit the first native request, reusable asset intake and source-generated documents without demanding the complete future workflow/application/file-manager suite. It should also prevent a generic file screen from issuing receipts, accepting expenses, publishing a public media generation, approving an application or adding broad search/AI access. Those are source commands and decisions.

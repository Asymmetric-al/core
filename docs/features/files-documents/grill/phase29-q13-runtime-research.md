# Phase29 Q13 — fresh unfinished access after ordinary expiry

21 October 2026, Asia/Bangkok. Read-only source research after Conrad ratified Q12 A and its amendments. Core HEAD remains `3d85897ebf1515008ef5c676b1c58a15422fb9ab`. Only this research note was written. No product/configuration/schema/dependency/provider/auth changes, private queries, credentials, test runs or live grant operations.

**Recommendation: ask whether a currently authorized source staff action may deliberately admit new bounded unfinished access for the same intended recipient, same still-unfinished request and same continuing purpose after ordinary access expires.** Recommend permitting that narrow capability, with an explicit prospective Q10 amendment: actual eligible normal fulfillment while this new unfinished authority is valid may enter Q07's up-to-720-hour completed read policy under genuinely applicable caps. Current source eligibility and later complete finite-policy qualification remain required. The alternative is no further recipient access through that expired unfinished request, with existing source-owned help. Neither option authorizes resetting the old end, cloning an otherwise identical request, reopening completed business work or sending private attachments as a workaround.

This is a product recommendation, not evidence of measured demand or an implemented feature. The code offers adjacent identity, service, projection and durable-dispatch mechanisms. It does not establish a qualified native request, grant-reissue command or complete P12 enforcement path for this capability.

## Why this is the next useful fork

Q11 and Q12 now fix original issuance and its ordinary nominal 1,440-hour interval. Q10 distinguishes unfinished from completed stages. The next consequential uncertainty is whether a genuinely expired unfinished source can receive a new prospective recipient authorization at all. That determines whether the eventual product needs a deliberate source grant command, how help can truthfully respond, and how a later fulfillment can relate to access history.

Choosing Q08's fresh completed-access duration next would settle a smaller independent setting, but would leave this ordinary unfinished failure/recovery boundary unresolved. Choosing another initial-clock detail would reopen ratified decisions. Recipient identity replacement, new purposes and business reopening are different owner procedures and should not be smuggled into this question.

The practical reason for A is continuity of the same pending work and its already-admitted receipts/corrections, without erasing original expiry or fragmenting evidence across duplicate requests. That is a design inference. No ministry cohort, help-volume measurement or production incident was inspected to claim it is empirically necessary. B remains coherent if the source's genuine policy makes ordinary expiry terminal for that request's recipient lane and the owned help route is useful without hidden bypasses.

## Minimal shape for option A

The existing source context can expose one deliberate grant action only to a currently authorized issuer. It reviews the exact expired source effect, continuing purpose, same recipient binding, current pending requirement/action scope and eventually qualified finite timing terms. It preserves the old effect, its original issuance/end, all adverse history, receipts, correction lineage and acceptance state. No generic grant panel, policy builder, new auth engine, new membership or duplicate request is needed merely to express this capability.

At the actual mutation, the source must still be unfinished and the current authority to issue must pass independently of the expired recipient read permission. Do not require the old expired grant to authorize the staff's administrative review, and do not give that staff the original private contents merely because they can administer a grant. Separate protected administrative facts and file-reading scope.

The new effect needs its own stable deliberate semantic identity and exact prior-effect/source/recipient lineage. Its material reviewed input is distinct from outputs resolved on first admission. Repeated transport attempts recover the same new effect; lost reply, lookup failure, changed button UUID or expired provider dedupe must not authorize another grant. Genuine separate issuance attempts, repetition and overlap require their adopted rules; this question should not invent a one-per-lifetime or unlimited-renewal policy.

The original ordinary 1,440-hour result remains historical. A new grant is not changing `U0`, un-expiring a credential, setting an old `is_active` flag, clearing a completed date or replacing a task. A grant can admit no action before its own valid prospective admission, and receipt/finalization workers cannot backdate missed activity into the expiry gap. Reconciliation of a proved earlier admitted effect is different and remains allowed under its original facts.

Grant creation must be coherent with current source completion, cancellation, requirement acceptance/correction, recipient revision, adverse restriction and grant-admin changes. A source that completed while staff reviewed the screen is no longer eligible for an unfinished grant; stale UI cannot select the old branch. Source admission, required evidence and durable follow-up have a coherent commit/recovery outcome. Notification/proof/delivery remains separate and cannot shift its end.

### Two dependencies the question must state explicitly

1. **Scope is continuing work, not Q08's fixed completed-file set.** A recipient who has not yet submitted a required file needs to submit it; a Q03 correction necessarily creates a new immutable version. A static list of original file IDs would make an unfinished grant unusable. Bound the capability to the same continuing source purpose and originally admitted requirement scope intersected with current eligibility, then admit future submissions/correction successors through existing Q03 rules. Preserve unrelated supporting files that remain current. This does not authorize new requirements, new purposes, accepted-item edits, historical originals or general file browsing.
2. **Later completion needs an explicit prospective contract.** Q10 currently describes fulfillment while applicable unfinished authority is valid; Q12's strict-before-90 consequence describes the original ordinary lifecycle only. A newly authorized unfinished interval after original `U0` must not silently manufacture a fresh completed period. The root's revised proposed A makes the required amendment explicit: first actual eligible normal fulfillment while the new unfinished authority is valid may transition to Q07 completed reading for at most 720 elapsed hours from that qualified fulfillment, under genuine caps and current disclosure. This is a proposed part of A, not already selected Q13 policy. It preserves one actual business fulfillment; it does not reward complete/reopen cycles or duplicate grant attempts with new completed clocks. Never retroactively admit completion that happened in the expiry gap. A source already completed before fresh admission is outside this lane. Duration/anchor and repetition of the fresh unfinished grant remain separately unselected activation gates; no repeated 1,440-hour default is imported.

## Feasibility and proof limits

Nothing inspected requires a replacement stack. The intended narrow path is source-owned admission through P12's registered capability/current-context and grant mutation boundary, the qualified native participant contract, existing durable follow-up and existing private serving/UI seams. Exact table/function layout is not chosen. The current broad auth wrapper and pure projection function are insufficient evidence that those owner contracts have shipped.

If A is selected, adversarial review should prove exact prior source lineage, ordinary versus adverse expiry, current same recipient/purpose, pending-item scope, accepted/frozen exclusions, competing completion/issuance, duplicate attempts and unknown commit, historical/current disclosure, valid finite terms, trusted attribution and same-tenant relationships on service/RPC/storage paths. Preserve correct effective PostgreSQL policy semantics; omitted `WITH CHECK` alone is not a bypass, and service/definer privilege must be inspected in the actual invocation. No new SQL or live-role claim is made here.

No tests ran: another nearby projection/dispatch unit pass would not settle this product fork or qualify missing native grant behavior. Previous Q01–Q12 tests and Q12's pure Node experiment are prior evidence only. No fresh duration, anchor, cooldown, extension count, self-service request process, automatic reminder, business reopening or Q08 completed-stage regrant is selected by this note. The fresh unfinished capability and its explicitly proposed Q10/Q07 transition await the founder's choice.

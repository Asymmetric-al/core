## Suggested next dependency

Finish the **recoverable negative-review journey** before choosing a reviewer assignment model. Q03 already lets a currently eligible recipient correct an unaccepted item; Q21 defines exact staff acceptance, and Q22 defines successful whole-source fulfillment. What remains unspecified is the native source-owned result and next action when staff determine the current submission does not meet the requirement.

The practical ordinary recommendation is an actionable **return for correction on the same item**, leaving the unmet requirement and its source/access constraints intact, preserving the exact reviewed evidence and useful feedback. This is a source decision, not a file delete, new request, automatic regrant or application rejection. It should fit the existing request context and Q03 correction command rather than creating a new inbox, mandatory duplicate upload task or broad workflow.

There is a framing hazard: “Reject the submitted attempt” and “Request changes” can mean the same recoverable action. If both leave the same requirement open for a new immutable correction, they are not a meaningful founder fork merely because the labels differ. The real scope choice could be **ordinary recoverable return only**, versus **also introduce a distinct terminal item/request rejection outcome for genuinely non-remediable cases**. The latter is a substantive additional source power with explicit intake and whole-request consequences, not an incidental Reject button. Existing specialist terminal decisions remain with their owners under either answer.

Do not force a bad alternative that requires a new logical request for every wrong scan or automatically ends the whole request. That would collide with the established correction journey and could become an expiry/authority bypass. If the owner pass concludes ordinary recoverable return is already sufficiently prescribed by the brief/accepted contracts, record the source application of that obligation instead of re-asking whether correction exists. The next clearly open founder fork is then **review responsibility**: one named accountable reviewer with qualified backup versus an eligible shared review queue. Both are plausible; assignment never grants review authority.

This ordering recommendation is independent judgment, not a Q23 selection. It deliberately flags where a proposed negative-review question might be vocabulary rather than policy. A new recipient text-clarification channel, mandatory replacement file, ability to reverse a return without new bytes, terminal rejection semantics, recipient notifications and their defaults are not assumed here.

## Practical ordinary return, without smuggling in powers

For a repairable issue such as a missing page or unreadable requested evidence, the useful journey is staff records the source-authorized outcome against the exact reviewed item/evidence, with recipient-appropriate actionable feedback; the recipient sees what remains needed and can use the already-permitted same-item correction path while their source authority permits it. Existing received bytes and accepted siblings remain intact, and no new account or duplicate logical request is needed merely to fix that submission.

That description still leaves several genuinely substantive semantics to qualify; they should not be silently supplied by a Reject label:

- **Disposition target:** the submitted attempt, current evidence set, requirement or whole request are different targets. Rejecting an attempt need not mean that the requirement is terminal, waived, canceled or satisfied.
- **Current acceptance eligibility:** source state must say whether/how the returned basis may subsequently be accepted or needs a successor. No blanket new rule for withdrawing feedback or accepting without new bytes is selected here.
- **Recipient response scope:** Q03's new immutable correction exists. A text-only clarification, additional unrelated file, per-file requested replacement or generic chat is not automatically the same capability. Avoid creating another Support inbox.
- **Safe feedback:** show only source-approved recipient-facing instructions, not internal reviewer assessment, care notes, other recipients' details or raw audit text. An exact version-bound internal reason and its safe recipient projection are not automatically identical fields.
- **Current access:** a return must not extend the unfinished period, revive expired authority, reset proof or imply notification delivery. Staff can record an authorized source result while a recipient presently lacks access; the exact owned help/fresh-access route remains separate.
- **Race and recovery:** a newer correction, another review decision or Q22 fulfillment can change the current target. Preserve version/evidence references and safe conflict handling; do not attach stale feedback to successor bytes or erase a committed result when delivery/task projection fails.

These are constraints for the eventual source design, not a proposal to ask all of them as separate founder questions or construct a new state machine now.

## Proof needed later, not claimed now

The first native slice needs exact staff capability and recipient scope, original evidence/revision binding, current source/access/closure checks, coherent durable decision/history/follow-up, safe recipient feedback, and meaningful same-item recovery. It must distinguish returned-for-correction from a technical processing failure or an unaccepted receipt. Effective real-role RLS/service paths, acceptance/return/correction races, delayed messages, expired access and composed accessible staff/participant flows remain unqualified.

# Phase 29 Q04 — own submitted file download versus preview-only access

Research inspected 20 October 2026, Asia/Bangkok. The parent reports Q03 A and all reviewed amendments are now ratified. This note prepares the next founder question; no Q04 answer is presumed. Scope is the ordinary native private-document request, for a currently authorized recipient and their own source-authorized submitted occurrence. It does not alter financial, issued-document, application, publication or other specialized owners.

Official documentation only: no authenticated comparator testing, provider action, real download, upload, message, account change or code change occurred. Dates below are page dates where exposed, not a claim about when each capability first shipped.

## Recommended next decision

Ask whether this ordinary request should provide **Download submitted file** alongside the existing qualified preview, or remain preview-only unless the source explicitly arranges a copy. Recommend allowing deliberate download of the exact own submitted original while its current source permission and original-delivery qualification allow it. This is an explicit capability of this native profile, not an inference from Q02 preview or Q03 correction permission.

The recommendation is a product judgment: a person may need the received file for their records, to use their own accessible software, or to inspect it in an application that supports its format. That benefit does not require a general file drive, folder sharing, bulk archive, sync client or permanent personal library. It also does not justify turning a failed preview into an automatic original download.

The strongest alternative is preview-only by default with a source-owned copy/help route. It reduces routine original-byte export, hidden-content exposure and accumulation of private local copies. It may suit sensitive requests, but adds friction when a permitted recipient needs the file itself, and is not a guarantee that visible content cannot be copied. Neither choice is a universal industry standard.

## Do not promise that preview-only prevents copying

Dropbox's [shared-link permissions guidance](https://help.dropbox.com/share/set-link-permissions), current page inspected today, says its download-disable option blocks downloading through its own interface but does not prevent saving through other methods. It separately documents that preview availability constrains its download-disable behavior for unsupported types. This is a shared-link feature on specified paid plans, not a Dropbox file-request capability.

The Asym consequence is a bounded claim: withholding the original can reduce original-byte delivery and may avoid exposing information absent from a safe rendition. It cannot promise that a person cannot screenshot, transcribe or otherwise retain information already displayed. Conversely, delivering an original creates a local copy outside ordinary future server access revocation; revoking access cannot reliably recall that copy. These are product/security implications, not a proposal to add DRM or surveillance.

Do not copy Dropbox's unsupported-preview fallback into Asym. Q02 already requires truthful unsupported-preview handling; original delivery must be a separate deliberately selected, currently authorized and qualified action.

Both retain Q01 identity/permission boundaries, Q02 qualified own-submission readback and Q03 immutable correction semantics. Neither grants all previous versions, files supplied by someone else, arbitrary source records, exports of internal review notes, public share links, deletion, bulk ZIPs, synchronization or access after closure. Neither changes an acceptance decision merely because a copy was obtained.

A source-specific narrower policy remains possible under either option, but do not present “administrators configure every combination for every request” as the default user experience. A should be a clear native-profile capability with meaningful enforced exclusions, rather than a nominal yes that silently makes every ordinary download require staff approval.

## Why download is the next useful question

Q02 answered what the recipient may inspect, and Q03 answered how to correct the wrong file. The next discrete capability is whether the person can obtain the file itself. Download introduces a meaningful additional exposure boundary even while the request is currently accessible, so it can be decided without inventing a retention period or opening all historical submissions.

Historical access and post-closure continuity are separate axes:

- **Download capability:** what may the person do with a currently accessible exact occurrence?
- **History:** which earlier occurrences, if any, may they see or retrieve after a correction?
- **Continuity:** for how long and under what source state may access remain available after completion/closure?

Choosing A does not settle the latter two. For this question, use a simple case where the exact submitted file is presently within the recipient's existing authorized readback scope. Do not sneak in a “download every version forever” rule through the phrase “my files.”

If current owner research shows that the product cannot identify even this presently readable occurrence—such as unresolved recipient reassignment or which item a submission belongs to—resolve that ownership ambiguity before offering any new export. Otherwise download is a smaller and more practical next decision than combining a history policy with an arbitrary post-closure access duration. The later history/continuity question should use the now-ratified correction lifecycle.

## Requirements to pressure-test after the founder answer

These are implications for the eventual adversarial review, not prematurely ratified implementation clauses.

1. **Own means source-authorized occurrence, not global uploader ownership.** Current recipient/request/tenant and source rules govern. A matching email, actor ID or digest does not authorize every copy across records. Reassignment, delegation, correction and reused bytes must not widen access.
2. **Name the returned artifact accurately.** The original is the exact received immutable bytes for the chosen occurrence. A generated receipt, application PDF summary, safe rendition, redacted copy or accessible equivalent is a different artifact and must not be silently labeled original. Do not substitute the newest file between button rendering and retrieval.
3. **Qualify original delivery independently.** Required intake checks, current restrictions and the source's delivery profile apply. A safe preview or an accepted business decision alone is not a license to serve every raw format. Pending, unsafe or technically unqualified original delivery stays unavailable with truthful status/help. Do not demand successful optional preview when the original path is independently permitted and qualified.
4. **Treat the whole original as disclosed.** It may include metadata, formulas, comments, hidden sheets or other information not represented in a preview. Do not claim sanitization while returning unchanged bytes, or silently alter bytes and still call them original. This needs real profile qualification, not a generic disclaimer checkbox.
5. **Reauthorize delivery and any resumed request.** Q01 identity confirmation and current exact source authority remain required. Private authenticated serving, temporary delivery references, caches, range/resume behavior and revocation must be qualified for the actual implementation. No permanent bearer URL, public bucket or browser-hidden token counts as proof of private delivery. Avoid inventing transport details or promising instant recall of already delivered bytes.
6. **Keep the action explicit and accessible.** Label the file, type/size where useful and **Download submitted file**; do not require hover or hide the action only inside a viewer. Explain a disabled/unavailable action safely. No forced download on preview failure, no automatic device opening, and no compulsory reason/confirmation ritual without a real source requirement.
7. **Do not overstate success or audit.** A request to serve bytes does not prove the browser saved a complete file, that the recipient opened/read it, or that they agree with its contents. Ordinary telemetry remains opaque. Download events do not create acceptance, correction, consent or a generic CRM interaction.
8. **Keep the product purpose bound.** Retrieval occurs in the native request/task for a relevant submission. It does not add arbitrary uploads, a personal storage allocation, folder sharing, generalized asset management or a new attachment library. Reusable Asym media/resources continue under their existing purposes; they are not forced into a request merely because this question is narrow.

No size cap, delivery-token lifetime, download-count limit, review SLA, retention period or post-closure duration is proposed here. Those must come from the relevant source/qualified profile, not examples in competitor documentation.

## Suggested founder question

“A recipient can now see the file they submitted and correct it while that item is still open to correction. Should they also be able to download their own submitted file from that request, or should it remain preview-only unless staff arrange a copy?

I recommend allowing **Download submitted file** while they still have permission and the file is cleared for delivery. That lets them keep the exact copy Asym received or use their own software. It would stay inside the request, without granting a personal drive, everyone else's files, all historical versions or permanent access. The tradeoff is that a downloaded copy cannot be recalled just by closing access later.”

If needed, explain the researched contrast in one sentence: Microsoft/Box file requests are collection-only, whereas Submittable documents downloading individual submitted files. Do not overload the question with storage implementation or ask the founder to choose file-delivery headers. After the answer, adversarially review both usability and the extra original-byte exposure before ratification.

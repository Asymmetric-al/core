## Recommended question

For an eligible ordinary request's source-provided evidence entry, should staff file that entry in **one home folder or Unfiled**, using labels and source views for other ways of finding it (A, recommended), or also place **explicit nonowning references to that same entry in additional folders**, preserving one home or Unfiled (B)?

The first unit is one admitted file contribution/use for a particular request and item: a participant receipt or a Q28 staff-supplied use. It is not the whole potentially multifile requested item, a digest, provider object, storage path, every use of those bytes, or a new universal mutable Logical Document. The actual source must supply a stable organization reference and its qualified exact/current-version and correction mapping. Foldering itself must not choose that mapping, confer history access, or infer that new uses and correction occurrences inherit placement.

A is the smaller and more predictable starting model: “Move to folder” changes one filing location, while labels, approved metadata and source views support cross-cutting discovery. B is a legitimate alternative where staff want the same source entry under several organizational headings. It requires clear add/remove-reference semantics, location display, deduplication and counts, and recovery when one placement changes. Neither option copies bytes or combines permissions. This recommendation is product judgment informed by the contract surface, not measured Asym filing frequency, a benchmark, or a claim B is intrinsically unsafe.

| Option                                                            | Practical result                                                                                                                                                                        | Cost and limitation                                                                                                                                                                                                                          |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A — One home or Unfiled, plus labels/source views                 | Staff can move an eligible evidence entry to one folder. The same entry can still be discoverable through authorized labels, source context and views.                                  | There is one primary filing location to understand and maintain. Someone who wants the same entry physically listed under several folder branches uses the other discovery tools instead.                                                    |
| B — One home or Unfiled plus explicit nonowning folder references | Staff can deliberately place a reference to the same eligible source entry in additional folders; removing one reference does not remove the home, other references or source evidence. | More flexible folder browsing, but more placement state and clearer distinctions between removing a reference, moving the home and ending a source use. Multiple appearances must not imply multiple receipts, copies, acceptance or rights. |

The cardinality decision applies only within the admitted ordinary organization scope; it must not silently pick a cross-tenant tree, personal-versus-shared authority model or inherited folder permissions. The selected-answer review should bind the actual scope and commands. Existing Media and Content Library folder contracts keep their own scopes and rules.

## Identity examples and source boundaries

A request item may contain several file contributions. Filing one admitted file entry does not move the whole item, another contribution, the request or a person's record.

The same exact bytes can lawfully be admitted as two different uses—for example, a participant receipt for request A and an independently authorized Q28 use for request B. A permits those two source entries to have different homes without requiring B or byte duplication. A matching digest does not collapse the entries or their filing rights.

Q03 creates a new immutable submission linked to the exact corrected occurrence; it does not overwrite its predecessor. Q28 creates a new independently authorized target use bound to source, target, subject, purpose and exact version; it does not inherit the source use's approval or other rights. The folder contract must preserve those facts. The source's stable organization reference and qualified mapping must establish what a displayed entry means as a correction/version is adopted. Do not assume either a new home for every byte version or automatic placement inheritance from a predecessor. Do not make placing the current occurrence in a folder a grant to read earlier occurrences.

Relevant existing decisions are `0003-recipient-corrections-and-exact-review-lineage.md:17–30` and `0028-staff-supplied-existing-document-evidence.md:28–70` in the Phase29 ADR set. Founder §7, lines125–141 and §8, lines147–153 distinguish custody, source meaning, use rights, version selection and independent obligations.

## Minimum consequences to carry into either option

1. **Organization does not authorize.** A folder, label or view changes no source use, current version, receipt, acceptance, requiredness, request status, person/tenant ownership, share grant, participant period, byte custody, retention or deletion. Moving a file entry must not move provider bytes or change public/source URLs. This follows the founder contract; it is not a new permission model.

2. **Precisely bind the entry.** Admission to the ordinary organizer needs a real source-provided stable reference to the eligible evidence entry, same-scope destination and actual current filing capability. A source item's whole file set, digest, provider ID or arbitrary source JSON cannot stand in for that relationship. Preserve the exact/current/correction interpretation supplied by the owner.

3. **Unfiled remains useful.** Filing must not become a mandatory step in receiving, reviewing or lawfully using evidence. A missing optional placement or temporarily unavailable organizer must not fabricate an unreceived file, reopen a request or block independent source work. Do not convert failed or unknown folder lookup into a confidently complete empty result.

4. **Separate metadata visibility from child authority.** Folder labels, breadcrumbs, counts, suggestions, references and errors may disclose private context. Current authorized discovery must precede counting, pagination and serialization. Seeing one evidence use does not reveal its other uses or their folders. Seeing a folder does not grant its entries. Unknown source/coverage cannot be marketed as a complete no-results or unused answer.

5. **Use real commands and current state.** Moving or adding/removing placement needs current actor/source/scope checks, stable entry/folder identities, expected placement state and coherent receipt/history. Exact retries must recover a committed operation without applying it twice; a later deliberate move is a new command. Concurrency with source correction, removal, restriction and folder changes must preserve source truth and report a stale/conflicting command rather than guess a new target.

6. **Keep folder lifecycle separate from evidence lifecycle.** Removing a folder or a B reference must not delete/trash evidence, end a source use, remove other placements, discharge retention or revoke an independent share. The selected-answer review must specify practical behavior for a nonempty folder and collisions without borrowing P23's exact removal algorithm as if already chosen. Restore and migration cannot revive denied source access or reinterpret provider paths as business organization.

7. **Bound actual work.** Pagination, tree traversal, labels, search, bulk selection and placement writes need an owner-qualified finite launch envelope and measured queries/roles before activation. A requires one-home structural enforcement; B requires unique same-entry/same-folder reference enforcement and truthful dedup/count behavior. Neither justifies a new general hierarchy engine or invented quota. P23's five levels and its view limits are precedents, not Q42 defaults.

8. **Preserve adjacent decisions.** Q38 metadata-only discovery stays in force; folder names or approved metadata are not a loophole for body extraction. Q41 read shares retain exact source/recipient/action/version/end qualification; moving an entry neither revokes nor widens a share by itself. No new notification, bulk export format, inherited folder ACL, cross-source relocation, public folder URL or automatic correction-placement rule is bundled into Q42.

## Native proof that remains prospective

A selected answer should be made concrete and reviewable through the actual owner adapter and runtime. The proof should identify the stored organization identity and its source relationship, real tenant/environment scope, exact folder command, all write paths and effective database/access boundary. A privileged CMS connection is not protected merely because other application tables use Supabase RLS.

The bounded native journeys should include two independent uses of the same bytes; several files in one request item; original and corrected occurrences; current versus historical source access; move/add/remove races; cross-tenant or foreign-source references; actor/source permission loss; hidden labels/counts; lost acknowledgement with committed retry; nonempty folder removal; mixed successful/blocked bounded bulk work where supported; restart/restore; and usable Unfiled behavior. These are required evidence targets, not tests run by this research.

The practical question can remain A/B. Detailed row schema, provider adapter, folder depth, capacity numbers and deletion algorithm should be qualified after the founder's cardinality choice, with exact source boundaries and a small complete user journey. No measured capacity, billing neutrality, blanket code correctness or implemented native folder product is claimed.

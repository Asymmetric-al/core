# Phase 29 Q38 — Purpose-qualified metadata discovery and the cost condition

**Disposition: Accept with required amendments.** Conrad selected A and
delegated whether to add qualified document-text search only if it introduces
little complexity and does not increase either Vercel or Supabase billing.
The ratified scope is **A: approved names, metadata and source
context; no added general document-body search**. Neither condition for the
optional addition is established. This is a decision under the delegated
condition, not a claim that text search is inherently expensive or impossible.
Conrad fully ratified Q38 A and every required amendment on2026-10-23,
Asia/Bangkok. Q01–Q38 are ratified grooming intent; all24 glossary definitions
remain unchanged. No new term, Q39 answer, implementation or formal
owner/OpenSpec publication follows.

The useful product is a small, clear **Search files** experience with safe names,
source context, filters, recent work and existing saved views. It should find
relevant Asym files without turning Asym into a general drive, requiring a
metadata-cleanup ritual or suggesting that document contents were searched.

## Evidence and the final cost decision

Evidence labels: **repository fact** identifies an inspected governing record
or code; **provider fact** identifies retrieved official documentation/account
metadata; **inference** identifies a consequence, not measured behavior;
**product judgment** identifies the selected scope; **unknown** remains unproved.
Risk likelihoods below are qualitative design likelihoods if the hazard is left
uncontrolled, not observed incident rates.

### What is verified

- **Repository facts:** Q02 requires useful source-purpose File Manager discovery
  but selects no general search/OCR/AI service. Founder §8 separately qualifies
  extraction, current access, exact version/coverage and incomplete results.
  P29 owns custody; source owners retain semantic identity, currentness, rights,
  discovery eligibility and retention. P22/P23 can forbid original filenames or
  sensitive metadata. Existing Support conversation/Staff-guide/public-page
  search has its own authority. D32 Find concerns one qualified representation,
  not a reusable general attachment corpus.
- **Current code:** navigation search, legacy Support fields, CRM note search,
  CMS image metadata, Eve memory text search and P18 renderer-validation tools
  are distinct mechanisms. Their existence does not qualify File Manager
  discovery or a general extractor/index. In particular, loading tenant rows
  and filtering bodies in application memory is not an appropriate generic
  search precedent. The [runtime review](phase29-q38-runtime-adversarial.md)
  retains exact inspected paths, snapshot and limits.
- **Provider facts:** Supabase includes PostgreSQL text-search primitives; a
  separate search vendor is not required for a suitable `tsvector`/GIN design.
  GIN still has storage, update and maintenance work. Metadata search may use
  those same primitives without becoming document-body search. [Supabase FTS](https://supabase.com/docs/guides/database/full-text-search),
  [PostgreSQL17 text indexes](https://www.postgresql.org/docs/17/textsearch-indexes.html),
  [PostgreSQL17 GIN](https://www.postgresql.org/docs/17/gin.html).
- **Actual account metadata:** read-only discovery identified Core's three
  Vercel apps and Supabase development/production projects. Supabase reports
  organization plan Pro and PostgreSQL17.6.1.063. This establishes neither
  compute/disk utilization nor uncommitted allowance. Vercel's scoped billing
  request for September23–October23 returned404 `Plan not found`; team metadata
  exposed no plan/usage detail. No usable Vercel CLI was present in native WSL.
  No credential repair, private-row/byte query, account change or paid resource
  creation was attempted. Supabase's available creation-cost tool is not an
  existing usage/invoice API and was not misused as one.
- **Unknown:** attributed baseline usage, actual Vercel billing terms, remaining
  shared allowances, expected corpus/growth, extraction coverage, search demand,
  representative query plans, maintenance load and incremental invoice totals.
  No local toy benchmark would establish those missing facts, so none is
  presented as a cost-neutrality proof.

For each provider independently, the relevant comparison is
`invoice(A + body-search, declared workload/terms) − invoice(A, same baseline)`.
The user's condition requires no positive attributable increase on **either**
provider; savings on one do not excuse a charge on the other. Compare realistic
steady use, growth, backfill, retries, rebuild, restrictions/disposal and recovery,
including possible reduced file opening/downloads, without double-counting those
potential savings. No actual delta is known. This is a finite workload assessment,
not a demand to prove an unchanged bill for infinite growth or future prices.

**Product judgment:** retain A. Low-complexity body search and a zero additional
invoice are plausible in some bounded deployments but unverified here. Do not
add a hidden “enable if cheap” branch, an empty content-search switch, a new
billing governor or a dormant extraction platform. A itself still consumes
resources; it must be designed and measured within the approved metadata-search
budget. This decision makes no promise that the entire File Manager is free.

### Strongest alternative, not a straw man

The strongest B is bounded keyword/phrase search over an actually qualified set
of digital-text documents, preferably using existing authorized extraction and
native Postgres primitives. It need not use OCR, embeddings, AI, a second parser
or a new vendor. It can materially help staff who remember words inside a file
but not its name or source; fewer file openings could offset some usage. Those
benefits and offsets are not measured for Core. Reusing a temporary preview's
text without its source/retention qualification is not legitimate reuse.

Client-side extraction/indexing is not a free substitute: it adds file transfer,
device CPU/memory, privacy and inconsistent coverage. A direct server scan avoids
an index but still examines bodies and repeats work. Limiting B to TXT or a tiny
character prefix would still need source eligibility, disclosure and truthful
coverage; an arbitrary narrow scope cannot be advertised as complete text search.
None satisfies the delegated conditions on the evidence available.

### Comparable products and UX evidence

[Blackbaud Grantmaking](https://help.blackbaud.com/docs/0/assets/grantmaking/content/manage-documents.html)
distinguishes the document record from its file and documents related-record
discovery plus names/tags/dates; it does not specify every indexed field or prove
that it lacks body search. [Box](https://support.box.com/hc/en-us/articles/360043696314-Search-for-Files-Folders-and-Content)
and [ShareFile](https://docs.sharefile.com/en-us/sharefile/sharefile-app/sharefile-web/full-text-search)
demonstrate useful document-text matching with explicit limits and asynchronous
indexing. [SharePoint](https://learn.microsoft.com/en-us/sharepoint/make-site-content-searchable)
separates search inclusion from reader access; its settings are not Core's exact
purpose contract. No vendor's default, quota or security claim overrides an owner.
[W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
supports meaningful search-status announcements without moving focus. The
[UX review](phase29-q38-ux-adversarial.md) preserves source dates, counterevidence
and complete journeys. These are documented patterns, not user-study results.

## Ratified corrected decision

> General staff File Manager discovery SHALL match only currently source-approved names, typed metadata and permitted source context for admitted Asym work. Provide the already-required folders, labels, filters, sorting, recent work, saved views and practical source navigation. The source declares the eligible uses, fields and version/currentness rule; a filename, folder, provider object, uploader or generic staff role does not confer discovery authority. Original names, sensitive provenance and linked-use information excluded by their owners remain excluded. Approved authored catalog descriptions may remain eligible fields, but request instructions, conversations, notes, extracted text or generated summaries do not become general file metadata by relabeling them.
>
> Q38 SHALL NOT add general document-body matching, ranking, suggestions or snippets through an index, on-demand scan, cached preview text, client-side extraction or another indirect body-derived path. This is an information-scope boundary, not a prohibition on efficient Postgres full-text/trigram/index primitives over approved metadata. Preserve existing separately qualified source search and Find within an opened authorized representation, including its declared coverage; do not aggregate or broaden those corpora into the general finder. No new OCR, AI, translation, search vendor, body-search switch or speculative extraction framework follows.
>
> The conditional addition of qualified document-text search is not admitted because both low added complexity and no attributable increase to either Vercel or Supabase billing have not been established for an actual qualified workload. Native SQL features, free libraries, existing routes or current allowances alone do not establish those conditions. This choice makes no zero-cost claim for required metadata discovery. A later scope change requires an explicit evidence-backed owner decision and qualification; it cannot auto-enable because a quota temporarily has room. No new cost-control platform or speculative prototype is required to implement A.
>
> Resolve tenant, actor and current source context through trusted server boundaries. Enforce search eligibility and current field/disclosure restrictions before any hit, contribution to rank, count, facet, suggestion, duplicate cue, grouping, pagination or serialized output, and reauthorize every subsequent source, preview, download or other action independently. A shared byte object or visible association cannot reveal other uses or union their permissions. Permission to discover metadata and permission/readiness to read bytes are separate; a failed preview does not universally hide otherwise permitted metadata, and a metadata hit does not promise readable or accepted evidence.
>
> Source facts remain authoritative; any search projection is rebuildable derived data bound to the exact permitted source/use and qualified version/currentness rule. Results SHALL NOT silently substitute latest uploaded bytes for the source-selected current or exact historical version. Relevant restrictive facts must fence serving before asynchronous cleanup; absence or delay of fresh authorization cannot be treated as continued permission. Late events, replay, cache reuse, reindex and restore cannot revive withdrawn fields, older access or disposed content. Preserve valid source writes and independently lawful discovery during recoverable projection failures, with durable recovery or a proved equivalent bounded reconciliation path.
>
> Search uses a small documented plain-text matching contract over an explicit field set. Inputs are data, not SQL, regular expressions or an undeclared advanced query language. Preserve source-approved original display values and qualify Unicode, accents, case, punctuation, long names and identifier behavior against representative fixtures; do not copy another domain's query grammar or silently discard significant characters. Exact approved searchable identifiers/names within the declared field scope must be findable under that documented contract; display permission alone does not admit a field to matching. Apply current tenant/source filters and stable pagination before exposing results. Do not fetch an entire tenant corpus for browser/application filtering or use forbidden fields to produce relevance scores. Any cap, broad query or failure that prevents a complete declared search has an honest refinement, continuation or unavailable state; it must not become a definitive zero or exact total.
>
> Definite policy exclusions remain undisclosed and need not turn a valid search into an error. Failure to evaluate a required current authorization or coverage boundary is different and cannot establish a successful complete zero. Use the source's qualified current read-admission/serving boundary, without inventing a globally locked search snapshot. Changes after lawful delivery cannot recall already displayed information; they govern subsequent serving, actions and qualified client-state invalidation. Pagination across changes must declare its consistency behavior without preserving old permission.
>
> The UI SHALL clearly identify that it searches names and file details, show useful permitted source/type/date context, make filters visible and removable, and preserve lawful query/filter/scroll return state. A phrase only inside a file will not locate it through this finder. Offer source navigation and a qualified reader where available, without forcing renaming, repeated upload, manual tagging, body-text copying, bulk downloads or an external viewer. Distinguish loading, completed no matches, incomplete/unavailable search and independently unavailable preview. No confidential file or hidden-match count may be disclosed to explain absence. Do not silently widen tenant, source, version/history or body scope to obtain a match.
>
> Keyboard, assistive-technology, mobile, reflow, touch, IME/RTL, localized date/time and slow-network journeys SHALL remain usable within the shared Core design system. Search-status announcements do not steal focus or announce an entire result list on every keystroke. Query changes, tenant/role switches, permission changes and navigation fence obsolete responses and cached private state. Saved views/recent work organize current authorized discovery and grant no rights. Treat private query/filter/history values and result fragments as sensitive; do not place them in general analytics, logs, public URLs, shared caches or durable offline stores by default. Shared views may share approved query definitions only through their actual owner and never freeze access.
>
> Native implementation SHALL use the smallest compatible source/API/metadata/view/query seams, with bounded server-side queries and appropriate measured indexes. Persist only data justified by the selected scope. Qualify effective grants, RLS, views/functions/RPCs, storage links, privileged jobs and every alternate read/write path. Projection attribution, tenant/source/use relationships and currentness cannot be caller-controlled or retargeted by an allowed update. Use tenant-aware referential/uniqueness/null/delete rules where applicable, preserve required source history and disposition, and distinguish business audit from operational telemetry. Do not create financial facts, money fields or new approval/workflow states for search.
>
> Before activation, declare finite source/field/query/page/selection/corpus/concurrency and recovery budgets, prove actual query plans and composed user outcomes, and verify baseline and incremental resource usage on the existing approved infrastructure. Record dimensions, units, scope, owners and thresholds rather than claim unmeasured speed or a fixed invoice. Migration/backfill and mixed-version writers/readers must preserve source authority and semantic scope; stop affected new search serving/projection work without undoing admitted source facts or disabling independently qualified source capabilities. Restore must reconcile later restrictions before serving. A failed or ambiguous search is safely retryable without creating source business effects; repair is available through a supported owner path rather than routine SQL intervention.

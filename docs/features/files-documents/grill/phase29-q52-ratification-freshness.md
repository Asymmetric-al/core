Two details must not be generalized into Q52 proof:

1. **Reference validity is not immutable attribution.** A composite FK rejects a reference without a matching parent pair; the additional CHECK closes its nullable-Tenant bypass. It does not itself forbid every privileged retarget/re-home: clearing the optional reference, moving to another valid pair or an equally identified parent pair is a different case from the particular failing fixture. Q52-C12/P23/P24 still require actual immutable actor/source/basis enforcement through every allowed mutation path. This is a qualification limit, not an observed cross-Tenant production exploit.
2. **Do not inherit the migration's lock-duration prose as a guarantee.** The forward file adds and validates constraints inside the same BEGIN/COMMIT. The guide's statement that no lock is held for a full scan, and the SQL comment implying the earlier strong lock is no longer held during validation, are not established by NOT VALID alone. PostgreSQL normally keeps acquired locks until transaction end; `lock_timeout` limits each wait to acquire a lock, not total lock holding or transaction duration. Existing Q52-C07/C13/C15 and B03 require actual ordering, bounded total work and migration evidence. See current primary [PostgreSQL 17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html) and [lock_timeout](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-LOCK-TIMEOUT), read for this check. No duration, production load or deployment impact was measured here.

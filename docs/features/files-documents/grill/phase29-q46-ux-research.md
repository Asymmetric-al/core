## One understandable decision

**Should authorized staff be able to deliberately change the current requested-by date for outstanding recipient work in an eligible unfinished ordinary Private Document Request?**

This date says when the source wants the remaining documents. Under ratified Q09, its passage alone neither locks the participant out nor makes timely material awaiting staff review overdue. Access ends and binding source limits remain separate. Q46 decides whether the source gets the new ordinary target-edit action, not whether late work can be accepted or whether access can be extended.

| Option                                                          | What staff and participants experience                                                                                                                                                                                                | Strongest reason to choose it                                                                                                                                                                                  | Real limitation                                                                                                                                                                                             |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Allow deliberate authorized target changes; recommended** | Staff change the actual current requested-by target for eligible outstanding recipient work. Current staff/participant views show the source's new target; earlier receipts retain the target terms and timing that actually applied. | The system can reflect a changed plan in the same request without rebuilding evidence or making staff maintain a contradictory date elsewhere.                                                                 | Introduces a real source mutation, history and concurrency boundary. A poorly explained edit can be mistaken for more access, or an earlier target can surprise the participant.                            |
| **B — Keep issued requested-by targets fixed**                  | The issued target remains the recorded plan. Staff can coordinate through actually qualified existing source communication/help; that communication does not silently edit the official target. Late intake still follows Q09.        | A stable issued plan has fewer changing states and less opportunity to move the date merely to make overdue work look better. It fits organizations that intentionally preserve the original requested timing. | If the plan changes, the displayed target and later coordination differ. Staff must interpret that distinction, and a participant may keep seeing a date that no longer describes the desired working plan. |

**Recommend A.** It supports an honest current plan while Q09 already preserves historical receipts and access boundaries. This is product judgment, not a measured Asym time-saving or a universal best-practice rule. B is credible and does not mean blocking late uploads, forcing a new request or denying existing source communication. Its stability benefit should be weighed against maintaining a known out-of-date target in the main request view.

There is no artificial third option or new tenant mode. A is permission-bound capability, not permission for every staff reader to change every date. The question does not choose mandatory dates, adding/removing a date where none is currently supplied, arbitrary per-item calendars, a new due-date default, automatic reminders, change notices, approval queues or an extension-request system. Existing source-specific binding deadlines remain owned and enforced separately.

## Illustrative current and historical journey

Elena asked Nora for the remaining equipment inventory documents by **28 October**. The request is still unfinished. They now plan for the remaining documents to be supplied by **4 November**. These people and dates illustrate the choice; no ministry usage pattern is claimed.

With A, Elena uses the qualified change action, reviews the old and new requested-by date and saves. Nora sees **Requested by: 4 November** on her next currently authorized visit. Any actual access end is separately shown and unchanged. A file durably received before this change retains its original receipt time and applicable target; moving the current date does not rewrite whether that earlier receipt was timely. Material already waiting only on staff processing does not become missing recipient work.

With B, **28 October** remains the issued target. An actually authorized source message may explain the later working arrangement, but neither the message nor a task-date edit changes the official requested-by field. Nora can still submit late if independently authorized under Q09. B does not require cancellation/reissue just to coordinate timing, and no such universal replacement shortcut should be promised.

Moving a target earlier has an equally real consequence. The current requested timing becomes more urgent, but earlier received acts are not retroactively relabeled. The deliberate review must show the actual old/new date and applicable work. Whether a particular candidate date is valid follows the current source's qualified calendar/time/authority rules; a date picker alone cannot invent that policy.

## Governing scope and safeguards for a fair question

These preserve the one fork; selected-answer adversarial review must settle its full native command/lifecycle details if A is chosen.

1. **Q09 is the explicit reservation.** The full ADR states that no date-edit capability is selected, while preserving authorized edit history. A proposes this new ordinary source action. A generic task editor, source access control or existing date field is not already that authority.
2. **The requesting source owns the date.** Current source/P12 qualification governs the actor, exact request, actual target scope and applicable outstanding recipient work. Authoring, reviewing, shared-view maintenance, comment rights or staff rank alone do not confer this new edit power.
3. **Same request, current work.** The proposed action is prospective target revision for an eligible unfinished ordinary request. Do not use it to change recipient/purpose, rewrite items/instructions, revive a No longer required item, unaccept evidence, reopen fulfillment/cancellation or alter a completed historical plan. Q36/Q37 changes remain their own actions.
4. **Preserve history.** Keep attributed target changes and the actual earlier receipt/time/target basis. Current target display and historical timeliness are different facts. Do not erase lateness by moving today's target, make a prior timely receipt late, or treat an unknown historical target as absent/zero. Governed correction of erroneous historical facts is separate.
5. **Access is independent.** Requested by is not Access ends. An edit neither extends original/fresh admission, renews proof, grants a new item, removes a hard limit nor restores expired/revoked access. Show actual current availability. A new requested date later than the existing access end cannot silently promise the participant can act until then; a real qualified access remedy is separate.
6. **Only recipient work is recipient-overdue.** Already received material awaiting checks/review is not overdue recipient work merely because staff have not finished. Corrections and newly required work use their actual applicable terms; unrelated items and earlier receipts must not inherit retroactive timing.
7. **Calendar meaning is source-qualified.** Retain actual date-only versus instant semantics, zone/calendar/precision and source interpretation. Do not convert a date to arbitrary browser midnight or rewrite meaning across daylight saving, time zones or locale formats. Show understandable dates and relevant zone/context without asking staff to manage UTC offsets unnecessarily.
8. **One deliberate simple edit.** Show old/new requested date and affected work in the existing request context, with separate actual access end. Save performs the authorized change; selecting a date, tabbing away, reopening a calendar or refreshing must not. No mandatory reason essay, extra approval or confirmation ritual follows from this proposal. Preserve lawful input after validation failure/conflict.
9. **Current state and result truth.** Concurrent date edits, closure, receipt/correction admission and relevant source change need an ordered current boundary. A lost Save response reconciles the original operation before creating a new edit; no-op saves should not invent change history. A refreshed display is not the evidence of source success, and a failed refresh is not proof Save failed.
10. **Do not bundle messages.** On-return current date visibility is needed. Away-from-product awareness is not guaranteed. Q20/Q26/Q31/Q35/Q40 purposes are not generic notices for this event; no new date-change email, reminder schedule, digest, acknowledgment or automatic repeated communication is selected. Existing qualified source communication remains available under its own purpose.
11. **Keep earlier evidence usable.** Date editing needs no reupload, duplicate file copy, new request, provider change or preview conversion merely to change requested timing. It cannot alter accepted evidence, review responsibility, source retention or exact read/share/export permissions. B also cannot force cancel/reissue as an invented ordinary workaround.
12. **Prove the whole small flow.** Date UI uses Core Base UI/base-maia and shared source commands. Keyboard/AT, mobile reflow, long localized labels, valid/invalid dates, low bandwidth, authority change, unknown receipt timing and actual current historical views need native proof later. A vendor date picker or current demo task field proves none of it.

# Phase 29 Q04 — clear, accessible download of the submitted file

Inspected 20 October 2026, Asia/Bangkok. The parent reports Conrad selected Q04 A, **Download submitted file**. This note supplies researched UX amendments for adversarial review; it does not ratify them, authorize implementation or certify a working feature. Q01–Q03 remain ratified. Scope is the exact currently source-authorized own submission occurrence/member in an ordinary native private-document request.

No real private file was downloaded, no authenticated comparator session was tested, and no source code or provider state was changed. The Q04 question was read for the precise scope. Official documentation describes capabilities; the journey and risk judgments below are recommendations needing implementation and participant/assistive-technology proof.

## Recommendation

Keep the action beside the file, inside its request: the understandable item name, safe filename, actual type/size, current status, **View my submitted file**, and **Download submitted file** when each is independently available. One deliberate download action is sufficient for an ordinary eligible file. Do not require opening the preview first, finding a hover menu, entering a reason, accepting a repeated disclaimer, or confirming a second generic dialog.

The strongest UX requirement is honesty about control. Asym can know which exact bytes it authorized and served. An ordinary web-page click or successful server response does not prove that the browser saved the whole file, that the person opened it, or that an external application read it. Do not display **Saved**, **Downloaded successfully**, **You have a copy**, or a completed task tick solely from those events.

Use the existing Core Base UI/base-maia system and source task context. This is an additional purposeful file action, not a new downloads library, personal archive, sync product or Drive screen.

A disabled anchor is not a complete unavailable-state design. ## Native download link versus fetch-to-blob

The documentation supports a **preference for the simplest qualified browser-native delivery path**, not an absolute technology mandate.

| Approach                                                                                   | Strength                                                                                                                                                                                                                   | Cost / qualification boundary                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Real link to an authenticated application download route for the exact version             | Native link semantics and browser download handling; avoids first assembling the entire response as a page-owned Blob merely to launch a download. Can preserve ordinary keyboard/context-menu behavior where appropriate. | The server must enforce current authority and file qualification on the real request, not merely a preceding metadata check. Error responses need useful recovery without being saved as the document. Link attributes do not secure a route, and cross-origin disposition behavior needs actual testing. |
| Real button for an application command/preparation, followed by qualified browser delivery | Appropriate when the architecture must authorize/prepare a bounded delivery and needs inline state/errors. A button truthfully signals an action rather than pretending to be a navigable URL.                             | Adds async states and user-activation/browser-handling concerns. The eventual bytes still require current enforcement; a successful preflight is not a permanent permission lease. Do not use popup workarounds that create blank tabs or weaken the private route.                                       |
| Fetch complete body, create Blob/object URL, initiate browser save                         | May suit an independently justified bounded implementation and offers application-level response/error handling.                                                                                                           | Waits for the full body before this handoff and requires status/content validation, interruption handling, bounds and safe object-URL cleanup. Browser-managed backing storage can vary. It does not prove saved-to-disk, make a public provider URL private, or eliminate source checks.                 |

Recommendations derived from the documented platform behavior:

- Do not choose fetch-to-blob merely to animate progress or show a success toast. If a qualified native path fits existing authentication, it is the simpler baseline to test, especially on mobile and poor networks.
- Do not weaken authentication to make a link convenient. If the current design relies on authorization unavailable to navigation, use an appropriate authenticated application path/command; never place reusable credentials or private provider grants in a public-facing URL as a shortcut.
- If fetch is used, validate the actual response before treating it as file bytes. Fetch resolving successfully is not sufficient for HTTP success, and a redirected login page must not become a bogus document.
- Release object URLs only after their legitimate use is over. Premature release can break interaction; never-released URLs retain backing resources. Blob URLs are client-side references, not a business permission or revocation system.
- A name suggested by HTML or response headers can be adjusted by the browser/OS. Keep the UI's submission identity explicit instead of pretending the local filename proves exactly what was delivered.
- Do not invent a universal maximum Blob size, perfect background resume, or cross-browser save-completion API. Decide transport within actual source limits and verify the supported browser/device matrix. No new provider, filesystem API or download-manager library is selected here.

These are architecture-sensitive recommendations, not code or proof that the current Core serving route meets them. Parent/source review owns authorization, range/conditional requests, active-content policy, response headers, cache isolation and transport capacity.

## Accessibility and device-copy clarity

**Link/control meaning.** Keep the visible label within the accessible name. Additional filename/item context should disambiguate repeated actions without producing a screen-reader recital of unrelated metadata. Type/size can be an associated description, and should remain visible for people on slow connections. An optional decorative icon must not create a duplicate focus target or replace the text label. Filename, icon and color alone must not carry the action's meaning.

**Interaction and focus.** Test keyboard, speech input, screen reader and touch activation. Reuse Core's touch-target convention rather than shrinking the action into an unlabeled icon for dense rows. Use shared focus visibility and responsive layout; avoid a new tab unless it has a real need and is explained. Inline asynchronous statuses should be appropriately announced without moving focus. A new error view must be understandable and provide a route back to the request.

**Downloaded content.** An accessible button does not make the original accessible. Exact original delivery preserves what was received; it does not create tags, OCR, reading order, descriptions or semantic spreadsheet structure. Preserve Q02's distinction between original, qualified preview and source-approved accessible equivalent. Where an alternative exists, label it separately and associate it with the exact version. Do not automatically convert the original and still label it unchanged.

**Shared devices and privacy.** A concise device-copy explanation can help a person choose whether to download. Do not claim browser private mode, closing the tab, revoking a link or signing out deletes a saved file. Do not build telemetry to inspect the person's filesystem or prove they removed the copy. Preview-only likewise cannot guarantee that visible content was not copied; [Dropbox's official explanation](https://help.dropbox.com/share/set-link-permissions) makes that limit explicit for its own download-disable control.

**Proportionate friction.** Ordinary eligible download is one deliberate action. Stronger source-required assurance remains legitimate, but do not turn each download into identity re-entry, another consent ceremony, a reason form, or a staff request. When no additional assurance is required, keep the recipient's existing safe session and task context. A warning that repeats on every click is not a substitute for withholding unqualified original bytes.

## Evidence required before calling the journey usable

1. A representative recipient can identify the intended file, distinguish View from Download and activate the correct action without opening a drive or preview first. Test several files with similar names and a corrected member in a multi-file item.
2. Prove behavior on supported desktop/mobile browsers with keyboard, speech input and screen readers, including links lists, filenames/type-size context, focus, zoom/reflow, long Unicode/RTL text, empty/error views and unavailable states. Check real content accessibility separately from controls.
3. Exercise pending checks, actual rejection, unavailable checker, unsupported preview with qualified original, qualified preview with blocked original, expired session, revoked authority and a correction race. Show only the exact currently authorized result.
4. Exercise slow/interrupted transfers, repeated activation, back/forward, refresh, user-declined browser save, error/redirect responses and range/resume where supported. Verify exact version integrity and that no new source submission or false business completion appears.
5. Verify transport limits and retained client resources in the actual chosen approach. Inspect real filename/header behavior across supported browsers. Do not accept a mocked “click download” test as proof of browser delivery.
6. Test the recovery copy with people: they should know which file was requested, what the app knows, and where to go if the browser did not produce a usable copy. Report the sample and limitations; do not manufacture a success percentage or SLA.

This note creates no new numerical file limit, download count, browser-retention period or monitoring threshold. The source and serving qualification package must supply operational bounds; the UX must not disguise them. History, post-closure continuity and general file-library powers remain separate decisions.

# Phase 29 Q39 — runtime research for reusable ordinary request item templates

2026-10-23, Asia/Bangkok. Q38 A and all amendments are fully ratified; root owns recording. Q39 is researched and unselected. Only this work note is authored. No runtime/schema/provider/canonical mutation, implementation, private-data access or test execution occurs.

## Recommended product choice

**A — Let authorized staff maintain reusable ordinary request item templates and apply one to a new independent draft (recommended).** A template supplies a deliberate set of reusable item definitions/instructions. Staff choose it, see the resulting editable draft and tailor it for the actual work. Original request issuance remains a later, separately authorized source action with its current recipient, purpose, access and review-readiness checks. Editing or retiring the template does not update prior copied drafts or issued requests.

**B — Compose each new request individually, without a tenant request-template catalog.** Staff use the normal item/instruction editor and can reuse suitable wording through whatever copying the editor already allows. This avoids catalog management and obsolete reusable sets, and is credible where requests are infrequent or highly bespoke. It does not remove ordinary drafts or add a new duplicate-request/reissue action. Its cost is repeated entry and more opportunity for inconsistent wording or omitted items.

A is a useful bounded authoring aid; it is not a workflow engine, form builder, reusable email template, specialist requirement authority or automatic recurring request. It can reduce repeated assembly while preserving human choice and per-request source truth. No measured Asym request frequency, template demand or time saving proves the benefit; the recommendation is a scope judgment. If requests are mostly bespoke, B's lower maintenance burden is real. Neither option inherits Q38's conditional body-search cost test as a universal zero-cost promise for all later features.

Illustration only: a staff member regularly requests an ordinary equipment handover checklist and supporting documents. A lets them start with the maintained item set, remove an inapplicable draft item, adjust instructions and then configure/review the actual request. B makes them assemble that set each time. No recipient is contacted, access clock started, review task created or evidence accepted merely by choosing the item set. This is not evidence of an observed ministry workflow or permission to bypass any equipment/source specialist rule.

## Minimum complete boundaries for A

1. **A content starting point, not an active request.** Keep a named tenant/source-qualified set of reusable ordinary item fields. Applying it creates an editable independent new draft. Do not auto-issue, schedule, send or publish participant obligations; do not silently apply it to an already-issued request.
2. **Explicit safe fields.** Copy only the selected reusable item names/type/instructions and any other fields the ordinary source actually admits as reusable definition data. Never clone whole request JSON, source record/recipient identifiers, evidence/files, submission/review state, acceptance, grants, proof, access timestamps, private comments, reviewer assignment, notification plan or prior dates. A template is not a new custom schema/form engine. Source-required fixed policy remains policy rather than editable prose.
3. **Authoring, reuse and issuance permissions remain distinct.** Resolve current tenant/source eligibility and actual staff authority through P12/source contracts. A person who may use a template need not receive power to change the shared catalog; catalog curation does not grant request issuance. Do not require one new administrative role/approval workflow if existing qualified capabilities suffice.
4. **No hidden personal-data harvest.** Saving a draft as a reusable set, if offered, must deliberately select/review the permitted reusable content rather than harvest a person's previous request. Item instructions themselves can contain names or case facts; field allowlisting alone cannot make all prose appropriate for broad reuse. Do not invent an AI redactor/classifier or assume a generic template name makes content safe.
5. **Independent, attributable copy.** Preserve what template revision/content supplied the draft and the staff act, with new draft/item identities. Subsequent draft edits change only that draft. Do not resolve instructions through a live template pointer at issuance or participant view. Selecting a changed template must not silently substitute different material from the reviewed choice.
6. **Ordinary maintenance without live propagation.** Authorized staff can correct a reusable set and retire it from new selection. Prior drafts/issued requests keep their copied meaning and history. Retiring a template alone is not cancellation of those requests; actual current source/safety/privacy restrictions still govern later draft issuance and reads. No universal forced refresh or invisible update to every draft.
7. **Current validation at use and issue.** A template may be stale or incompatible with the current source profile. Detect invalid fields/requirements safely, retain lawful draft work and explain the capable repair path. Applying a template is not a permanent certificate: actual recipient/purpose/current source terms, applicable Q24/Q25 review coverage and Q01–Q19 access admission are resolved through ordinary issuance. A team/template label is not readiness proof.
8. **Coherent application and honest recovery.** A copy must not appear complete with only half its intended item set. Concurrent edit/retire/apply and repeated clicks/lost response need one exact recoverable copy outcome; an intentional second draft is distinct. Never recover a technical failure by issuing a request, sending again, duplicating items in an existing request or silently dropping selected requirements.
9. **Keep UI proportional.** A familiar Choose template or Start blank in new-request preparation and modest authorized template maintenance are enough. Show actual copied items before issue, preserve staff edits and offer clear repair/removal in the inert draft. No mandatory template, lengthy wizard, second approver, workflow installation, merge-language designer or task-per-template.
10. **No unmeasured promises.** Storage, catalog query size, reusable text/number of items, concurrent revision/copy and retention/history need finite native budgets. Q38's metadata-only scope remains; no content-search pipeline is necessary. No blanket performance, cost-neutrality, translation or cross-tenant sharing claim follows.

These are research boundaries for the question, not a prescribed table design or a substitute for the selected-answer adversarial review. Ordinary drafts, template lifecycle and issued requirement revisions are different states; a small implementation can preserve those distinctions without making a universal versioning platform.

## Practical cases and later proof direction

| Case                                                       | Required direction if A is selected                                                                                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Staff uses a routine set and adjusts one item              | Produce an independent draft whose current content is visible before ordinary issuance. Editing it does not alter the shared template.                                                     |
| Staff starts a unique one-off request                      | Start blank remains equally valid; no catalog ceremony or required template.                                                                                                               |
| Template changes while a colleague is choosing it          | Preserve the deliberate version/basis or explain the conflict; do not silently copy newer material.                                                                                        |
| A reusable set is retired                                  | Stop new selections under its current qualification. Existing copied drafts/issued work keep their actual history and independent source rules.                                            |
| Recipient, source profile or reviewer availability differs | Template content supplies no old authority. Resolve the actual request context and current issuance readiness.                                                                             |
| Staff reopens an old draft                                 | Show the retained copied content, validate current source constraints and repair only the affected work. No automatic live-template synchronization.                                       |
| Instructions contain a prior person's case details         | Do not silently publish them in a shared catalog; use deliberate authorized reusable authoring and current content visibility. No copied evidence, hidden notes or recipients.             |
| Lost response during Apply                                 | Reconcile the exact copy; report known created draft vs uncommitted/unknown. Do not create an issued request or repeated item set to repair the UI.                                        |
| Template or request source is temporarily unavailable      | Preserve lawful existing draft content and a capable retry/edit route. Do not call partial or unknown copy complete.                                                                       |
| Donor/missionary/participant                               | No changed enrollment, extra proof step, new grant or notification occurs from staff choosing the draft starting point. Only actual later source issuance has those existing consequences. |

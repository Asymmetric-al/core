# Phase 29 Q49 — Different-person recipient correction: continuity shape

2026-10-25, Asia/Bangkok. **Research and question recommendation only. Q01–Q48 are fully ratified; Q49 is unselected.** This note does not create an ADR, new glossary term, source permission, notification policy, implementation or provider action. Only this assigned research artifact was written.

## Recommended next question

**When an eligible issued ordinary document request needs to go to a different intended person, should Asym guide staff through a linked replacement request every time, or offer a same-request recipient change when nobody has ever responded?**

Recommend **A — One guided linked replacement-request flow.** Reuse only source-approved, currently appropriate request definitions in a new reviewed request; preserve the old request's truthful history and end the old affected recipient authority through the actual source correction path. This is not a demand that staff recreate every item manually. The old and new records should be connected where the viewer is authorized to see that relationship, making the correction understandable and recoverable.

The strongest alternative is **B — Add a same-request shortcut for a genuinely pristine, unresponded request; use linked replacement otherwise.** This keeps one operational request reference in a common early mistake case, but adds a second correction shape and requires trustworthy proof that no contribution or clarification was ever admitted. A currently empty request after withdrawal is not pristine. Unknown history is not proof that nobody responded.

This is a choice about changing the **intended person**. A source-proved correction to the same person's mailbox/contact revision remains a distinct identity/recovery case under Q01. Matching names, email aliases, an email-verified flag, contact-list editing or a staff checkbox cannot establish that it is the same person. Neither option promises that forwarding an existing invitation changes its authorized recipient.

## A recognizable example

**Illustrative, not an observed ministry workflow:** Elena asks Nora for an equipment inventory. Elena then learns that Luis is the person who should supply it. The request may already contain Nora's private question or a file that Nora uploaded. A recipient field that merely changes to Luis would make it dangerously unclear who supplied what, what Luis can see, which link still works and whether old messages will go to the wrong address.

Under A, Elena starts **Replace recipient** from the request. The flow proposes a new linked request containing only instructions/items that are authorized and still suitable for Luis. Elena can correct those definitions, sees the intended recipient and actual access/communication consequences, and deliberately completes the qualified source operation. Nora's request remains a truthful source record; Luis does not inherit Nora's file, questions, proof or accepted evidence merely because definitions were reused. Exact labels and command composition are implementation design after selection, not fixed UI wording in this question.

Under B, if the source proves that the old request has never received a contribution or clarification, Elena can use an explicit versioned recipient change on that same request. Old recipient authority still ends, and Luis must receive independently qualified authority/proof. If any response exists, was withdrawn, or cannot be ruled out authoritatively, the same guided replacement path applies. A viewed invitation, a provider-open event or an unfinished label is not a substitute for the actual predicate.

Preparing a replacement is inert. It must not quietly cancel the original just because a form was opened, a name was typed or draft fields were copied. Conversely, an actual known unsafe old recipient must be containable through the existing qualified source/privacy action without waiting for the new request to be ready. Whether a single final command can coherently complete both effects is a source/transaction qualification obligation, not a reason to expose a fragile manual chain or claim atomicity without proof.

## Fair practical options

| Option                                                             | What staff and recipients experience                                                                                                                                                                                                                                    | Best case and tradeoffs                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Guided linked replacement, recommended**                     | A consistent correction flow prepares a new request from safe reviewed definitions, qualifies the new recipient, preserves the old record and exposes the linked correction outcome to authorized staff. Existing source commands end the obsolete recipient authority. | One understandable separation between old and new people, including requests with prior response history. Reuse avoids needless typing. The cost is two linked request records and careful navigation/operational reporting so the old one is not mistaken for unfinished work still assigned to the new person. This is not automatically fewer implementation lines or cheaper operation.                                                                                   |
| **B — Same-request shortcut when pristine; replacement otherwise** | For an eligible issued unfinished request with proved no ever-admitted contribution or clarification, staff publish a new recipient/purpose revision under the same request reference. Other cases use A's guided linked replacement.                                   | Preserves a familiar request reference and avoids a second record for an early correction. Particularly credible where one known business request is the continuity users care about. The cost is two paths, an authoritative pristine-history boundary and more explanation when a response races with correction or makes the shortcut unavailable. It still requires fresh recipient qualification and obsolete-grant fencing; it is not editing an email string in place. |

Both alternatives offer a capable correction journey. B is not an unsafe forwarding link, automatic data transfer or strawman manual rebuild. A is not a generic Duplicate request command: safe definition reuse must be explicitly qualified for this correction purpose. Q39's template-to-new-draft contract does not automatically authorize cloning arbitrary issued requests, and new request identity is not a mechanism to evade existing source restrictions or communication limits.

I favor A because a single correction story can cover both early mistakes and prior-response cases while making different people and their evidence legible. The best reason to prefer B is the practical value of preserving one request reference in a truly early, unresponded case. Vendor documentation supports both shapes; it does not measure that tradeoff for Asym. The original request's source and the actual user journey, rather than a database-key preference, should determine the choice.

## Twelve boundaries needed for an honest question

These define the A/B comparison and preserve existing decisions; they are not a selected Q49 amendment package or an implementation specification.

1. **Different person, same genuine source need.** The source must authorize the new intended person for the actual continuing ordinary purpose. A change to another business purpose, a representative role or a collaborative multi-recipient request is not hidden inside this feature. Same-person mailbox recovery requires its own proved identity/contact basis.
2. **A reuses safe preparation, not old authority.** Safe source-approved definitions can seed a reviewed new request without copying submitted files, acceptance, private clarification, internal notes, previous access, signatures, recipient preferences or delivery material. Authored instructions may themselves be person-specific or private and require review. Do not blindly clone every non-file field.
3. **B proves pristine history at admission.** No ever-admitted contribution or clarification, including withdrawn material, is the bounded shortcut's proposed cohort. A blank screen, filtered list, zero current files, missing data or unknown outcome cannot prove that predicate. A late response and correction must have a coherent source result; otherwise use linked replacement.
4. **No silent identity overwrite.** Record who changed what, the actual old/new recipient revision and result. A same-record successor is still an attributable source act, not updating a mutable email column. A linked replacement does not relabel previous receipts as Luis's submissions.
5. **Old access ends; retained source duties persist.** Obsolete grants/proofs/pending promotion are fenced by the actual correction. Already admitted independent custody, review, retention and remediation continue only under their own authority. No recall of prior emails/downloads is promised. Source-approved closure/containment is not physical deletion.
6. **Containment and preparation are separate facts.** Opening or discarding an inert replacement draft causes no cancellation or send. An actual unsafe-recipient stop must not depend on a new request being ready. The final supported handoff must show real old/new outcomes and capable recovery rather than a half-complete success banner or manual database procedure.
7. **New access is newly qualified.** Q01 proof/current identity reuse applies only where genuinely qualified for the new recipient/address/request purpose. No forced donor/missionary membership or fake Party. Q13/Q15 fresh access cannot simply be redirected; a new independent request or same-record successor needs its actual declared admission terms and end. Existing or future completed-view scope is not transferred.
8. **Old/new disclosure remains separate.** The replacement recipient sees only their authorized request and permitted context. The old recipient does not learn the replacement's identity, address, files or private reason through an old link or status. Staff lineage navigation is itself permission-checked. Q30/Q45 history does not leak across that link.
9. **No notice or cadence policy by implication.** Exact existing required invitation/follow-through owners still apply; an optional new cancellation/reassignment notice is not silently selected. A request replacement cannot retarget a queued message, refund an old possible-send count or manufacture consent. Q48 automatic plans and recipient stops retain their real scope; deriving new enrollment/count/courtesy handling requires explicit integration, not copying Docusign's reset behavior or inventing a blanket Off rule.
10. **Accessible review, not ceremonial friction.** Show actual permitted old recipient, intended new person, request purpose, safe reusable items and meaningful consequences before one deliberate final source action. Keep Cancel, usable validation, keyboard/AT/touch/reflow/RTL/IME and weak-network recovery. Do not require body preview, a reason essay, another account or a routine second approver merely for correction.
11. **Mistakes and uncertainty have capable recovery.** Lost responses reconcile the original exact operation and current safe result; changed intent must not be silently replayed. A wrong replacement is corrected through current qualified source action, not an old snapshot rollback, restored old invitation or fresh-key duplicate. Revoked authority and valid-but-failed delivery are different states.
12. **Specialized and terminal scope stays governed.** This question concerns eligible unfinished ordinary requests. It does not reopen fulfilled/canceled requests, reassign specialist financial/official/Support records, transfer submitted ownership or automatically accept evidence. Outside scope, actual source/privacy remediation remains necessary; no powerless generic Contact admin substitute.

## Focused proof and implementation consequences to explain plainly

Both options need real source commands, current role/recipient qualification, exact old/new lineage, supported recovery and a UI that distinguishes preparation, authority change, issuance and delivery. Neither can be implemented by changing a contact field or by treating a successful email as permission. A needs a carefully allowed definition-prefill contract and coherent linked outcomes. B additionally needs authoritative historical-response eligibility and its race boundary; “currently zero uploads” is not sufficient.

The important proofs are understandable: no new person receives old private responses; old proofs cannot be reused after correction; a response racing with correction is not lost or misattributed; a lost response does not produce two requests; known unsafe old access can be ended promptly; a valid replacement has a complete usable path; staff can correct another mistake; and every meaningful step works on mobile/AT without redundant ceremonies. Source, proof, communication, review and current serving owners must all agree on that same story.

No additional provider, general ownership-transfer system, collaborator editor, automatic forwarding, bulk reassignment engine, profile-merging feature, notification inbox, new mailbox-proof system or universal request clone is needed to ask or answer this choice. This note does not choose the detailed post-selection clock/notice/reminder integration by omission. If the chosen shape requires a substantive amendment to one of those existing owners, surface it explicitly during the selected-answer adversarial review rather than quietly borrowing a comparator's behavior.

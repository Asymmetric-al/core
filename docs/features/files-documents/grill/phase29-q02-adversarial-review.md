## Adversarial check

### What could go wrong with this answer?

The apparent convenience of View my submitted file could accidentally create permanent My Files access, render hostile originals, show a different version than the one received, or imply acceptance from a green preview. Conversely, interpreting the new scope as every file must already be attached to a live record would block legitimate media preparation and could destroy valid retained evidence. Both errors come from treating a file browser as the authority rather than a view of source-owned work.

### What hidden assumptions are we making?

Uploading is not a continuing read grant. Email confirmation does not prove a unique human or ownership of all related files. A clean scan, valid file extension, successful converter, familiar URL or accessible outer dialog does not prove safe, faithful, accessible content. No current placement does not mean no purpose, no obligations or safe disposal. Existing public image machinery and PDF-template previews are useful pieces, not a qualified uploaded-document reader.

### How does this affect the whole product?

The boundary becomes **files for accountable Asym work**. Each admitted use has a known source owner and purpose; shared byte custody can support several separately authorized uses without merging their meaning, rights or retention. Embedded record/request/media/resource/generated-document work remains primary. Mission Control's File Manager supplies coherent discovery and operations over permitted source records, not a new permission or business-document owner. Existing resource catalogs, media libraries, folders, saved views, bulk controls and operator recovery remain where their contracts require them.

### How does this affect the end-user experience?

The ordinary recipient returns to the same request, sees what was durably received and its participant-visible status, and deliberately opens a qualified view of that exact submission. They receive a small task experience rather than staff File Manager. Staff normally upload inside the task that supplies purpose and authority automatically. A standalone File Manager entry uses a short contextual choice among admitted Asym uses when necessary; it does not demand a free-text business justification or expose storage-provider settings.

### Does this follow modern best practices?

The direction fits contextual CRM attachments, source-generated giving documents and reusable CMS media. Salesforce separates document, version and record link. Raiser's Edge and CiviCRM place attachments within record/activity work. Payload and Strapi allow reusable media to exist before insertion into content. Those are useful patterns, not permission models to import unchanged. [Salesforce](https://developer.salesforce.com/docs/platform/mobile-offline/guide/use-images-upload-file-representation.html), [Raiser's Edge](https://webfiles-sc1.blackbaud.com/files/support/helpfiles/rex/content/en-ca/content/attachments.html), [CiviCRM](https://docs.civicrm.org/user/en/latest/case-management/everyday-tasks/), [Payload](https://payloadcms.com/docs/fields/upload), [Strapi](https://docs.strapi.io/cms/features/media-library).

HubSpot documents that selecting an existing Files-tool item does not automatically apply its Sensitive Data protections. That is a concrete warning against believing that attaching a file to a restricted record upgrades the existing bytes' protection. [HubSpot](https://knowledge.hubspot.com/account-security/sensitive-data-in-hubspot-tools).

Layered validation, isolated processing and safe serving are supported by OWASP; no one scan or MIME check certifies content. W3C requires usable contents and complete processes, not merely a labelled iframe. These are qualification requirements, not evidence that Core already passes. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), [WCAG conformance](https://www.w3.org/TR/WCAG22/#conformance-reqs).

### Does this fit Asym’s existing repo and product direction?

Yes, with explicit distinctions. ADR-0171 already provides a reusable tenant Media catalog, separate placements, authority-free Media folders and retention that does not auto-purge unused items. Phase28 owns curated missionary resources and publication, including unpublished/withdrawn states. Phase18 keeps official artifacts/currentness; Phase21 keeps evidence/package meaning; Phase30 owns import staging; Phase42 owns development admission and execution. Phase26 D32 supplies the accepted bounded preview architecture, but its staff authority does not transfer to request recipients. Q01 is the recipient-admission prerequisite; Q02 adds the separately authorized read.

### Should we adjust the recommendation?

Keep A. Implement it as **contextual, exact-submission readback within an admitted Asym purpose**, with truthful confirmation/status even when a preview is unavailable. Apply the new boundary to product entry, source admission, UI and reuse. Do not turn it into an active-link requirement, arbitrary retention shortcut, competing Media catalog, universal file owner or generic user drive.

## Corrected decision to record

> The ordinary new private-document request experience provides a source-authorized submission confirmation, participant-visible status and a deliberate **View my submitted file** action for the exact received submission/version while the source currently permits it and a qualified reading rendition is available.
>
> Asym manages files/media to support its admitted product work or preserve the outputs and obligations of that work. Each admitted use has a known source owner and purpose. Valid preparation, reusable library intake, generation, import staging, retention, holds and recovery do not require an already-live placement. The File Manager organizes and operates on those permitted source records; it is not a general-purpose personal or organizational drive.
>
> Submission confirmation, safe-preview readiness, source review and business acceptance remain distinct. Own-submission preview is a request-bound read capability, not a global uploader-ownership rule or a grant to other files, original downloads, replacements, deletion, public sharing or indefinite history. It does not amend independently authorized capabilities in existing source domains.
>
> A preview is bound to exact immutable input and qualified profile/output lineage, with meaningful limitations disclosed. Unsupported, unsafe, inaccessible or incomplete content receives an honest state and its source-approved recovery/accessible path; there is no automatic original-download, public-URL or external-viewer fallback. Viewer controls and represented content both need accessibility proof.
>
> Current authorization protects every metadata and byte representation. Source authority—not the lifetime of the viewer's browser session—governs independently admitted processing of received intake. Revocation blocks new affected reads; source withdrawal/expiry fences promotion where required. No visible use, an ended request or an expired rendition is not authority to delete original evidence or override retention.

This is **Accept with required amendments**, not rejection of A. The explicit no-general-drive direction is recorded as a founder constraint. The exact source/profile, delivery, migration and proof consequences below are reviewed amendments, with formal owner/PRD/OpenSpec integration reserved for the authorized stage.

## Category-by-category adversarial review

Each category explicitly states the material concern, impact, severity, conditional likelihood, evidence, effect on the answer and exact prevention. **H** means high confidentiality/integrity/authority impact; **M** means meaningful UX/reliability/maintenance impact. Likelihood labels describe plausible design failure, not production prevalence.

### 1. Problem validity, necessity and alternatives

**Material concern: yes — M / plausible.** Turning one useful readback action into a file portal would solve a larger unrequested problem; restricting everything to upload confirmation would remove the chosen way to check what arrived. Microsoft/Box/Dropbox documentation supports the simpler collection alternative but does not establish Q02 readback as an industry default. **Effect:** retain A and narrow it to the current request's exact submitted content. **Fix:** C01/C04/C05/C07. A small contextual viewer is the strongest path; no-build receipt/status-only is simpler but fails the selected content-inspection outcome. The expected reduction in wrong-file uncertainty is a product judgment requiring pilot evidence, not a measured benefit.

### 2. Brittleness

**Material concern: yes — H / plausible.** A provider pathname, filename or latest-version pointer can change underneath a prior confirmation. Assumptions that every accepted file previews identically fail for fonts, saved spreadsheet values, hidden content, encrypted files and source reclassification. D32 explicitly addresses those differences. **Effect:** A becomes exact-version and profile-bound. **Fix:** C03/C08/C10/C13; stable IDs, immutable inputs, pinned coverage, explicit unavailable states and requalification after processing changes. Do not promise perfect original fidelity from a static reading rendition.

### 3. Technical debt

**Material concern: yes — H / expected if current preview-looking code is reused blindly.** Current Support renders filename chips; PDF Studio renders trusted structured-template HTML; neither is uploaded-PDF/Office processing. Public Payload media and 60-second Eve signed delivery carry different authorities. Runtime review gives exact files/lines. **Effect:** preserve useful components but reject false equivalence. **Fix:** C05–C10/C20: one shared qualified custody/preview seam with source adapters, no per-app renderer/store or generic URL-based viewer. Do not upgrade dependencies simply to match a demo.

### 4. Edge cases

**Material concern: yes — H / plausible; frequency unknown.** Same-name files, repeated uploads, shared mailboxes, changed recipients, newly restricted evidence, hidden spreadsheet content, blank/malformed documents and lost response can show the wrong item or imply submission failed. These are test scenarios, not asserted ministry practice. **Effect:** strengthens exactness and safe recovery. **Fix:** C04–C06/C08/C10–C13; retain server confirmation independently of preview, current source-bound admission and clear limited/unavailable states. Unsupported preview never silently retries the upload or substitutes local browser bytes as received proof.

### 5. Footguns

**Material concern: yes — H / likely under naive reuse.** UI examples may use public URLs, fake permissions, local progress, raw inline originals or free-form purpose fields. Dragging a confidential file into a media folder may appear to upgrade/downgrade its access. Current public assets and ReUI sample state are not authorization. **Effect:** restrict mutations and UI meanings. **Fix:** C02/C06/C09/C12/C16; server-derived purpose, explicit source operations, qualified renderer and no view/download/publication side effects from move, upload or preview. A hidden Download button is not copy prevention.

### 6. Tenant safety

**Material concern: yes — H / plausible.** Caching/deduplicating by digest or uploader could reveal a match or share a rendition across tenant/request restrictions. A source-purpose lookup or global File Manager list could leak counts, names or other uses. **Effect:** A must be scoped beyond identity. **Fix:** C03/C05/C06/C13/C15/C17; authorize before every projection and read, isolate scratch and caches, preserve independent source references and prevent cross-tenant duplicate discovery. Coalescing work does not pool permission.

### 7. Database, RLS and authorization safety

**Material concern: yes — H / plausible.** A permitted UPDATE could retarget an occurrence, set Ready/accepted, change classification or attach bytes to a less restricted source. Same-tenant FKs alone do not prevent that. Current service clients and public asset policies cannot certify private requests. **Effect:** requires effective database and command-boundary proof. **Fix:** C02/C05/C06/C13–C15: use non-null required scope, same-scope FKs, immutable authority-bearing references, bounded size/digest checks, unique semantic effects and one mutation owner; deny unsafe cascades. Evaluate all effective grants/permissive policies, USING and resulting-row checks, view execution, function owner/search path and service trust. Omitted WITH CHECK may inherit USING; definer naming alone does not prove bypass. The source's current policy must apply through RPC/storage/realtime and every private route. Preview values create no financial amounts; display exact source precision rather than floating-point reinterpretation. Actual proposed schema/RLS does not yet exist and needs real-role proof.

### 8. Overengineering

**Material concern: yes — M / plausible.** An elaborate universal file ontology, new workflow engine, per-user drive, generic ACL hierarchy, AI relevance classifier, settings matrix or office editor would burden a simple task. The opposite overcorrection forces fake parent records and unnecessary governance forms. **Effect:** narrows the architecture. **Fix:** C01–C03/C07/C16/C20: known source contexts supply admission, small code-owned profiles, existing shared commands/queues, and optional source-owned organization. Separate facts need not become separate services. Keep the requested File Manager capabilities without building arbitrary storage collaboration.

### 9. UX/UI and friction

**Material concern: yes — M / plausible; measured benefit unknown.** A drive shell, vague success badge, eager conversion, long spinner, inaccessible embedded content or lost return context makes users uncertain and encourages repeat uploads. **Effect:** A needs a complete small interaction. **Fix:** C04/C07/C10/C11: clear received version/status, deliberate View action, meaningful processing/limited/error state, stable keyboard focus and return, no re-upload to recover a result. Preserve Unicode/RTL names without using them as identity; show safe human time/zone while server instants govern security. Low-bandwidth mobile paths avoid fetching every page/file. New purpose capture is normally automatic from the task. Controls and contents both require AT testing; accessible framing cannot excuse unreadable content.

### 10. Source of truth, ownership and invariants

**Material concern: yes — H / expected if generic file ownership becomes semantic authority.** A central record could overwrite Phase18 currentness, Phase21 evidence meaning, Phase23 publishing rights or Phase28 resource publication. Shared digest may falsely merge retention. **Effect:** the new boundary must preserve multiple independent typed uses. **Fix:** C01/C03/C08/C12/C16/C17. Source owners determine meaning/currentness/audience; custody proves bytes/copies/processing; providers prove their exact operations; File Manager and Used in are governed projections. A rendition is not the original or official generated document, and a source link is not an audience grant.

### 11. Hidden coupling

**Material concern: yes — H / plausible.** Requiring a live placement before upload makes content preparation circular. Depending on all Phase34/41/42 functionality blocks the file foundation those products consume. Copying Support reader authority into a participant viewer silently widens access. **Effect:** requires exact reusable seams, not full-product dependencies. **Fix:** C01/C05/C07/C10/C20: admit a genuine draft/catalog/import/request purpose now, preserve its owner, and qualify a new audience adapter. Existing P28 resources and P23 Media remain distinct products. Do not turn file staging into a general execution environment.

### 12. Failure modes

**Material concern: yes — H / plausible.** Storage write succeeds with lost response, converter times out, output is partial, one page fails, queue dispatch is lost or a source becomes restricted. A naive viewer may claim not received, full Ready or business acceptance. **Effect:** makes status/recovery part of A. **Fix:** C04/C08–C10/C13/C14/C19; independent durable intake outcome, output validation/coverage, atomic intent/outbox, exact-copy reconciliation and persistent classified failures. Never substitute raw/private/public URLs or another renderer silently. A source-authorized processing failure does not erase receipt of the original.

### 13. Lifecycle, time, concurrency and idempotency

**Material concern: yes — H / plausible.** New upload, revoke, profile update, lease expiry, Ready promotion and cleanup can race. Repeated opens can multiply jobs or renew retention indefinitely. **Effect:** adds exact generation and custody fences. **Fix:** C08/C13/C14/C16: one semantic input with distinct technical generations, bounded attempts, current source/worker proof, one winner between promotion and deletion claim. Ending, revoking or expiring the authenticated participant session stops reads under that ended admission but does not cancel independently authorized processing. Merely closing a viewer, tab or browser is navigation and does not necessarily end persistent authentication. Original, scratch, rendition and access lifetimes are separate; a new eligible generation never rewrites old receipts/deadlines.

### 14. Data integrity

**Material concern: yes — H / plausible.** Mutable object paths, unverified completion, provider ETag mistaken for content digest, preview conversion or inaccurate spreadsheet values could misrepresent what was submitted. **Effect:** exact source evidence must survive. **Fix:** C03/C04/C08/C10/C13/C15: independently verify byte identity/length, preserve originals according to source, bind all outputs and maintain immutable history. CSV stays literal; saved spreadsheet values retain raw precision/date system and missing cached results are unavailable, not zero. Preview never imports rows or updates money/CRM facts.

### 15. Security and privacy

**Material concern: yes — H / plausible.** PDF scripts, Office external relationships/macros, archive expansion, malicious fonts/images, viewer-origin privileges, SSRF, private metadata in logs or alternate downloads can bypass a clean-looking screen. **Effect:** A requires isolated qualified rendering and current serving. **Fix:** C06/C08–C11/C17; real process/no-egress isolation, bounded resources, inert outputs, private no-store delivery, safe headers and narrow bridges. Do not submit private files to public scanners or vendor repro systems. Document text is untrusted data, not authority for AI/tool execution. A preview discloses information and can be copied; revocation cannot erase received copies.

### 16. Scalability and performance

**Material concern: yes — M/H / actual workload unknown.** Conversion amplification, giant sparse sheets, many page/range requests, unbounded bulk intake and repeated generation can exhaust workers or starve other tenants. **Effect:** carry exact inherited ceilings and realistic qualification, not marketing capacity. **Fix:** C02/C09/C13/C19/C20; bounded profiles, coalescing, fair queues, backpressure and indexed exact-scope lookup. Retain D32 units/limits below; do not turn preview caps into universal upload limits or infer current production capacity from synthetic image tests. Operator-visible quota/cost remains useful even though user-facing personal-drive storage is excluded.

### 17. Operational burden

**Material concern: yes — M / plausible.** Stuck generations, ambiguous legacy owners, lost versions and incorrect-source uploads could require SQL repair or manual sharing. A vague relevant-file rule could also create a review bureaucracy. **Effect:** requires source-owned recovery and clear intake. **Fix:** C02/C04/C13/C14/C18/C19; task-derived purpose, bounded owner classification/reconciliation, safe reprocessing after cause correction and exact source links for exceptions. No generic override exposes known unsafe content. Ordinary recovery is available in product operations, without turning every upload into a committee approval.

### 18. Observability and auditability

**Material concern: yes — H / plausible.** Upload count, URL issuance, converter exit or view telemetry may be represented as safe receipt, complete preview or human reading. Logs can become an unintended document archive. **Effect:** requires precise evidence. **Fix:** C04/C08/C17/C19; separate technical traces, source history, restricted access audit and business decisions. Record opaque operation/source/version/profile, actual actor/service and result; no raw contents/secrets. The controls below name signals, thresholds, owners and responses. No preview event automatically becomes a CRM interaction or email.

## The next decision

**When a reader finds an organization resource inaccurate, outdated, unclear or broken, should they be able to report that problem directly from the resource?**

Recommend **A — Add an optional Report a problem action, with real curator handling.** Keep it small: one short note attached to the exact resource/publication context, a truthful received result, and source-owned handling in existing resource management by a currently authorized curator. Reporting is feedback about this resource, not permission to edit, withdraw, publish, access hidden content or create a discussion thread. It does not mark the resource reviewed, change its review date or automatically hide it.

The first cohort is P28's already-governed missionary reader and qualified organization-resource curator. A person who independently holds staff powers uses those in the proper context; this decision does not invent broader staff-reference readership or a new general library. That broader coverage remains explicitly unresolved for Phase 29 completion.

## A concrete journey

Illustration, not an observed ministry workflow: Maya opens a resource she is currently permitted to read and notices that one of its instructions points to a broken destination. She chooses **Report a problem** beside the resource's ordinary actions. The form already identifies the permitted resource; she writes one short note and selects **Send report**. She does not retype a filename, paste a private download URL, upload a screenshot or select a staff member from a directory.

After durable source acceptance, she sees **Report received** and can continue reading or return to her prior list position. Sending does not claim that someone has read the report, that a fix has been made or that a response will arrive by a promised time. A failed or unknown result preserves safe text and recovers the original attempt rather than creating duplicates. If the resource changed or access ended, the interface explains the safe current state without silently attaching her old observation to a different version or exposing hidden details.

Alex, the currently authorized curator, sees the exact permitted publication context and the note in existing resource management. Alex can investigate, use actual publication/correction/withdrawal actions where needed, and record a truthful handling outcome. The original reporter is not made the owner of the resource. A departed curator cannot strand the report; current qualified stewardship must have a supported takeover route. Handling a report is not Q55's Record review unless the actual review command and its requirements are deliberately satisfied. On a permitted return, the reporter can see their own minimal receipt and handling state/outcome under current disclosure. Handled does not imply Fixed, and this grants no internal notes, historical resource bytes or continuing resource access. It adds no inbox, conversation or automatic notice.

For B, Maya uses the existing qualified Help/source route instead. A context-aware handoff is preferable where that route can lawfully carry it, but no protected title, content or link is copied to a person who lacks the relevant purpose. B needs a real capable destination and honest receipt/recovery too; it is not merely a Contact us label.

## Twelve proposed boundaries if A is selected

1. **Optional and contextual.** Offer Report a problem within the actual qualified resource journey. Keep normal Open/Download/Back usable without reporting, rating, acknowledgments or a forced modal. Successful preview/download is not a prerequisite when current source/report authority and safe publication metadata still identify the target; a body or download failure can itself be reported. Missing or denied source authority remains blocked. Report about this resource is separate from asking for personal help, requesting access or submitting new resource content.
2. **A small useful form.** Prefer one concise text note with the permitted resource context already attached; no mandatory recipient picker, attachment, screenshot, phone/address, rating or category questionnaire. Source-appropriate limits and misuse controls must be qualified, not copied from a competitor. The page need not make reporting its primary action.
3. **Exact owner meaning.** The resource source owns the report and handling history for the exact organization/publication/version or approved external-reference basis. Trusted context binds actor, target and time; a client link/title cannot select hidden material or silently retarget to a replacement. For external references, report the approved reference observed, not pretend Core snapshots or verifies the mutable remote page.
4. **Real current authority.** Reader-report permission and curator report-handling/disclosure are explicitly adopted, separate from resource read, publication, staff role and P12 capability membership. Every body, title, count, list, history, response and result stays in its actual current scope. Reporting never grants access to missing/hidden resources or private evidence, and a broad Help audience cannot receive restricted context by default.
5. **Capable destination and durable result.** Accept a report only with a qualified source-owned handling route, required durable fact/history and honest result recovery. Put the work where the authorized curator already maintains resources; add no new general inbox or task-per-report platform. Supported stewardship handles departed/ineligible curators. An unresolved owner mapping cannot be disguised as Sent to the team.
6. **Assessment is separate from resource change.** Reports can be mistaken. Staff investigation and a truthful handling outcome are distinct from publication correction/withdrawal and Q55 actual review/date changes. Reporting or marking it handled never automatically hides a resource, resets a review target, sets Last reviewed or closes every report when a newer version appears.
7. **Safe repeat and failure behavior.** One deliberate submit records one intended report despite double clicks, transport retries and lost responses. Recover the original result under current disclosure before a new attempt; a new report with materially different information must not be globally suppressed merely because the resource/reporter matches. Keep safe unsent text on recoverable failure; no silent offline submission or unqualified durable private draft storage.
8. **Current context across change.** Reconcile publication replacement/withdrawal, permissions, curator changes and report handling without rewriting what the reader observed. Do not silently attach an old complaint to a successor, resurrect removed material, leak a protected previous title or grant historical bytes. A neutral unavailable state and an actually capable qualified Help route cover cases outside admitted reporting scope.
9. **Minimal private history.** Preserve needed actor/context and truthful handling evidence under actual source retention. Reader text can itself contain sensitive details; disclose it only to its admitted handling audience, not all staff, coaches, other readers, analytics/session replay or broad search. Existing safe plain-text rendering, bounded input and effective grants/RLS/functions/service paths remain required. No new binary store, body-search corpus or public comment thread.
10. **No automatic communications or surveillance.** Durable Report received is not email delivery, human reading or promised resolution time. New email, reminders, subscriptions, staffing metrics, coach visibility and response conversations are not assumed. Any actual source/P6 communication purpose would need its own explicit qualification; a page event creates no message by itself.
11. **Accessible full journeys and operations.** Use Core's shared Base UI/base-maia and known patterns. Support keyboard, touch, AT, narrow screens, long/RTL/IME text, visible focus, meaningful status/error, low bandwidth and safe return context. Qualify the real reader and curator tasks, bounded queries/rates/history/recovery, source-safe migration/restore and a stop that preserves lawful existing handling. Current source failures require capable recovery, not a powerless button or raw SQL.
12. **Keep the decision at the right level.** The choice is whether to add this contextual reader/curator action. It does not pick a table schema, queue vendor, ticket tool, mandatory notification, broad audience, new glossary term or general workflow platform. If A is selected, the full adversarial review must settle its precise admission, handling, correction and recovery requirements against the source before ratification. Until then these are researched boundaries, not an adopted Q57 answer.

## Adversarial check of the recommendation

### What could go wrong with this answer?

An unowned form becomes a complaint sink; a general ticket leaks a restricted resource; reader feedback silently becomes a review or withdrawal decision. A must include capable source handling, exact private context and separate publication/review actions. If those cannot qualify, do not ship a decorative report control.

### What hidden assumptions are we making?

We infer that some readers can notice resource problems that periodic curation misses. No demand frequency or measured time saving is claimed. The first actual pilot must include reader reporting and curator resolution/recovery, rather than only testing a textbox. Existing Help quality is an alternative to evaluate, not assumed absent.

### How does this affect the whole product?

It adds one bounded resource-source reader action and handling responsibility. It does not change ordinary document comments, request clarification, P6 sending, P12 identity, P29 custody or public CMS ownership. The new source-purpose projection must be explicit rather than assembled from generic role and ticket helpers.

### How does this affect the end-user experience?

A can remove copying and route-finding while keeping the reading surface quiet. A truthful receipt and a real handler matter more than a new badge or five-state workflow. B can remain effective where Help already carries the context safely; both need useful failures and accessible completion.

### Does this follow modern best practices?

Current primary knowledge-product documentation supports contextual feedback and accountable handling. It also exposes overbuilding and unassigned-work hazards. Use the proven pattern at Core's smaller scope; do not import automatic verification, votes, public comments, large queues or marketing claims.

### Does this fit Asym's existing repo and product direction?

Yes as an explicit proposed P28 extension with current P12/source authority and existing curator management. It honors D12's requirement for a real workflow before showing such a button and Q55's separation of reported concern from review facts. Existing Support code does not prove either alternative already works for this audience.

### Should we adjust the recommendation?

Recommend **A — Optional contextual resource-problem reporting with real curator handling**, retaining existing qualified Help for personal assistance and cases outside this scope. It is a focused addition with an honest cost: a small, complete report/handling contract. **Q57 remains unanswered.** No new glossary term or formal publication is inferred.

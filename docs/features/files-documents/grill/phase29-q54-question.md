## One decision

**When staff prepare a local file for an ordinary request item, should Asym keep reuse deliberate through Add existing file, or also offer an optional suggestion that an eligible existing file may match?**

This concerns a staff-facing discovery aid. Both choices keep Q28 deliberate existing-file reuse and Q53 Upload and add. It does not decide physical storage deduplication, public Media matching, visual similarity, OCR, general document-text search or automatic merging.

| Option                                                          | Practical experience                                                                                                                                                                                                                                | Benefit                                                                                                                      | Real tradeoff                                                                                                                                                                                                                                            |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Keep Add existing file as the reuse route (recommended)** | Staff choose Add existing file when looking for something Asym already holds, using approved names, metadata and source context. Otherwise they use Q53 Upload file. No new content-derived matching cue or check is added to this ordinary intake. | Clear two-path experience, fewer background checks and no additional matching permission or fingerprint pipeline to qualify. | Staff may miss an eligible existing file, especially when they do not know its approved name or context, and may upload an independent copy.                                                                                                             |
| **B — Also offer optional exact-file reuse suggestions**        | Before Upload and add is committed, a quiet hint may identify a currently eligible existing-file candidate. Staff can review it and deliberately choose Q28 reuse, or continue their selected upload.                                               | Can surface a useful existing file the staff member did not know to search for, including differently named copies.          | Adds a narrow matching/discovery purpose, bounded file fingerprint work, current candidate authorization, truthful timing and recovery. Suggestions may be unavailable or arrive too late to be useful; neither transfer nor bill savings is guaranteed. |

**I recommend A as the complete baseline for this ordinary intake.** It already delivers a useful reuse route beside the newly ratified staff upload. We have documented examples of helpful duplicate suggestions, but no measured Asym evidence that missed manual reuse warrants the additional matching work and privacy surface. A is a product scope choice, not a placeholder feature that silently enables later when someone judges it cheap. B remains a credible convenience if its discovery benefit is important enough to include now.

## Concrete example and user experience

Illustration, not an observed ministry workflow: Nora prepares `inventory-final.pdf` for Elena's eligible request item. Asym already holds an eligible exact version under the approved name “Equipment inventory — October.” Nora may not know that name.

With A, Nora can choose **Add existing file**, find the document through permitted metadata/context and deliberately add it. If she does not discover it, **Upload and add** supplies her local file with its truthful new staff-origin receipt and normal review. We accept that some reuse opportunities will be missed; no existing evidence or approval is overwritten.

With B, while Nora is still preparing the file, Asym may show **An existing file may match** and **Review existing file**, using only approved candidate metadata. The selected file remains selected. Nora may choose **Use existing file** through Q28, or continue **Upload and add**. No modal demands an answer, no hidden candidate is announced and no extra finalization click is introduced. A match arriving after Nora commits Upload and add cannot pause, replace or reverse that operation.

B can use a bounded browser-computed fingerprint as an **untrusted discovery query**, provided it searches only independently authorized, currently reusable existing versions. It is not proof that new bytes have arrived, match the claimed fingerprint, are safe or belong to the participant. The server still qualifies the exact held version and source use before Q28 admission. That avoids requiring a full incoming upload solely to make a candidate lookup lawful, without pretending a browser value supplies custody or authorization. Exact transport, digest and performance choices remain engineering qualification work, not a new founder algorithm choice.

A would not add a hidden on-demand “check this file” command, local fingerprint engine or conditional automatic switch. Those are forms of the same extra matching capability, even if initiated by a button. Neither choice removes independently qualified Media behavior or requires a physical duplicate to be deleted.

## Ten proposed boundaries for the choice

1. **Complete manual baseline.** Under A, implement/retain actual Q28 Add existing and Q53 Upload and add with current Q38 metadata/context discovery. No extra hash-derived candidate check, automatic warning, on-demand match button, similarity service or hidden auto-enable in this ordinary cohort. This does not remove a separately qualified source's matching or decide physical deduplication.

2. **Fair useful B.** B adds a quiet optional candidate hint while the staff member is preparing the local file, before their Upload and add intent. It may reveal a reusable exact version they would otherwise miss. Staff may ignore it, inspect permitted metadata or choose deliberate Q28 reuse. A narrow matching aid is not inherently overengineering; its actual value and qualified cost must be measured.

3. **Explicit narrow purpose and authority.** B needs ordinary-source/P12 discovery and reuse-candidate qualification beyond Q38's general metadata search. Resolve trusted Tenant/environment/actor/context, permitted candidate set and target eligibility; file possession, claimed digest, staff rank or technical storage access grant nothing. Never disclose a hidden candidate's existence, count, name, origin, rights, source association or timing-dependent signal through a “duplicates found” shell. Fingerprints and queries are purpose-sensitive even when no candidate is displayed. Keep their raw values and candidate metadata out of URLs, generic logs/analytics, shared caches and unapproved durable client storage; any qualified protected state follows actual source privacy and retention.

4. **Candidate input is not custody proof.** A bounded client fingerprint may be untrusted lookup input over already-authorized existing versions. Declare compatible algorithm and byte coverage, and bind trusted held-side fingerprints to the exact original version; thumbnails, renditions, normalized output and sampled resume fingerprints cannot silently stand for original-byte equality. It is not server-certified incoming equality, receipt, authenticity or participant intent. Label only the actual assurance (for example, An existing file may match), and verify the exact held version's current custody/eligibility through Q28 before adding it. No MD5-as-certainty, filename/size-only equivalence, visual similarity, general OCR/text matching or new proof-of-possession authority. Exact equality remains distinct from business identity/provenance.

5. **No new wait or late switch.** Neither lookup nor candidate review blocks the normal Upload and add path or creates a second finalization decision. If candidate proof arrives after that intent is committed, it cannot pause, cancel, replace, reinterpret or reverse the upload/admission. Do not add a running-check modal, mandatory check, post-add cleanup prompt or new notification. Missing/failed/late checking means no usable suggestion, not a claim that no duplicates exist.

6. **Explicit source choice and recovery.** Choosing a held version creates the existing Q28 intent and its truthful staff-use attribution, not a fresh incoming-file receipt or inherited acceptance. Bind the exact candidate and current target; no automatic selection of a different version. Any already-prepared upload remains tracked and is safely canceled/reconciled through Q53 custody ownership; do not delete it on a UI switch. If new-upload commitment is uncertain, recover it before a new reuse action that could duplicate the intended contribution. Context/authority changes fence late candidate results and current admission rechecks remain mandatory.

7. **Useful minimal UI.** Keep Upload file and Add existing visible in the ordinary item. With B, show a small nonblocking suggestion using safely distinguishable approved metadata, Review existing file and an explicit Use existing action where allowed. The current upload selection stays intact until staff choose otherwise. No forced preview, full-screen duplicate manager, mass removal, blanket reason or new settings matrix. Support keyboard/AT/non-drag/touch/mobile/RTL/long names and low-bandwidth state without focus theft or unapproved local byte persistence.

8. **Independent meaning and effects.** A match never merges documents, versions, provenance, subjects, rights, uses, retention, holds, labels, comments or approval. Different eligible acts may legitimately use equal bytes. Reuse does not become a participant upload, waive personal requirements or renew access. Current Q21/Q22 review/fulfillment and existing Q24/Q27 work/notification semantics remain; no file-found email, reminder reset or Q51 cue follows.

9. **Bounded cost and safe failure.** B must declare actual finite fingerprint bytes/CPU/memory, concurrency, query/candidate/page/retention/time budgets and tenant fairness before activation. Use qualified existing digest metadata and bounded permission-aware candidate retrieval rather than downloading every potential match, scanning unbounded history or exposing bodies to another provider. A is not a zero-storage-cost promise; B is not a zero-bill or guaranteed transfer-saving promise. A failed optional lookup does not break independently qualified upload or manual reuse. Do not freeze an untested schema, new provider, index or global content store into the founder decision.

10. **Proof and stage.** The selected option must receive the full adversarial amendment review. A needs proof that the useful two routes remain and no extra matching obligation is smuggled in. B additionally needs exact purpose/authority, same-scope/current candidate semantics, collision/false-input and stale-result tests, upload-versus-reuse races, native query/resource evidence and intended-user comprehension. Every serving path—including raw/direct database or API access, RPC/service paths and cached/projection readers—must preserve current candidate disclosure or remain closed; endpoint-only filtering is insufficient. This preserves the single P12 source authority and prescribed coarse tenant defense, without creating a second permission engine. Preserve Q01–Q53 and the 31 current terms. No new glossary term or ADR is created by asking the question; formal owner/OpenSpec/ticket stages remain separate.

## Adversarial check

### What could go wrong with this answer?

A can miss a reuse opportunity. B can disclose a protected file, falsely imply equality or change an already-authorized upload. Current candidate authorization, truthful assurance, deliberate Q28 selection and no late switch are essential. A's tradeoff is stated rather than disguised as complete duplicate prevention.

### What hidden assumptions are we making?

The example assumes an independently reusable existing version; equal bytes alone do not establish it. Asym's rate of missed reuse, acceptable local fingerprint work, query performance and actual bill impact are unknown. Current source does not prove a native matching feature.

### How does this affect the whole product?

It chooses whether to add one ordinary staff-discovery aid. Q38 search, Q28 reuse, Q53 upload, public Media, shared custody, source rights and physical disposition keep their boundaries. No general similarity, extraction, deduplication or resource-library decision follows.

### How does this affect the end-user experience?

A keeps two explicit contextual choices. B can reduce manual discovery effort for differently named copies, with a quiet pre-intent suggestion. Neither should add a routine wait, interruption or misleading “nothing exists” claim. Actual file and source context matter more than a duplicate badge.

### Does this follow modern best practices?

Current CRM and DAM documentation supports both deliberate existing-file selection and optional matching. It also exposes performance tradeoffs and privacy mistakes. Core should adopt a useful interaction with its governing protections, not a universal vendor default or collision claim.

### Does this fit Asym’s existing repo and product direction?

A directly preserves Q28/Q38/Q53. B can fit only as an explicitly admitted narrow purpose with current candidate disclosure and unchanged source commitment. ADR-0171's Media scope and a custody digest do not grant that purpose automatically. Exact Core UI and packages/api ownership remain.

### Should we adjust the recommendation?

Recommend A for the complete ordinary baseline: make both current paths excellent and avoid adding an unmeasured matcher. B is a valid optional convenience, not an unsafe idea by definition; its discovery benefit must justify the additional bounded capability. This is a genuine founder choice, not an engineering algorithm question.

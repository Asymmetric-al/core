## Recommended next choice

**Should staff be able to reuse a saved set of ordinary request items to prepare
an independent new request draft, or compose each request through the existing
ad-hoc authoring flow without a tenant template catalog?**

Recommend **A — Offer optional reusable ordinary item sets as draft starters.**
An authorized staff member can select a suitable named template containing only
the declared reusable item definitions, inspect the items it will contribute,
and adapt them in a separate new-request draft. The template is a starting point,
not a live shared requirement, authorization decision or Send operation.

Keep **B — Ad-hoc authoring without this template catalog** as a credible
alternative. It preserves the actual request-authoring flow and existing qualified
source defaults. It avoids maintaining another reusable content catalog when
requests are infrequent or highly individual. Its cost is repeated entry and
review of similar item wording, with more opportunity for manual inconsistency.

A is a product judgment based on a useful, bounded authoring pattern documented
by current collection products. It is not a claim that Asym staff issue a known
number of repeated requests, that templates save a measured amount of time, or
that B is an inadequate product. Optional use keeps one-off work direct. The
benefit is strongest where the same legitimate ordinary document needs recur;
the feature must not encourage requesting unnecessary documents merely because
they appear in a familiar template.

The choice is not a general template engine, bulk-send feature, configurable
workflow, mandatory central approval process or three-mode tenant policy. It
does not extend Q36/Q37 to alter existing issued requests through a template.

## Concrete example

Illustrative scenario, not observed ministry usage: Elena needs to prepare
separate ordinary equipment-document requests for Nora and later for Maya.
Each request happens to need an equipment inventory and a calibration certificate.

With A, Elena can use an eligible **Equipment documents** item set as a starting
point. The new draft contains the reusable item names and generic instructions.
Elena checks whether both documents are genuinely needed for Nora's request,
adapts the instructions where appropriate, and continues through the actual
recipient/purpose/reviewer/access/target and issuance flow. Maya's later draft
is a separate occurrence. Neither draft contains Nora's files, answers, prior
acceptance, discussion, private case details or access grant.

If Elena corrects the template later, that does not silently change Nora's
already-created draft or issued request. Changes to an issued request use the
actual Q33/Q36/Q37 or other source commands where eligible. If a separate current
privacy, safety or source rule now forbids the old wording/use, that rule still
applies; independence is not an entitlement to keep using unlawful content.

With B, Elena builds each request in the existing authoring flow. That can be
simpler when each recipient's needs differ. She must enter and check the common
wording again; the product should not pretend this is the same convenience as A.

## Boundaries that keep A useful and small

1. **Reusable definitions, not copied case state.** Declare the ordinary item
   fields eligible for reuse: for example, a source-qualified item name/document
   type and generic instructions. Do not copy actual source/recipient records,
   answers, evidence, review history, clarification, prior acceptance, identity
   proof, access grants, credentials, due/access clocks or dispatch material.
   Actual existing qualified defaults may still be reused independently; do not
   impose unnecessary manual reentry merely because a template was used.
2. **Current source authority.** Template discovery/read, authoring/management,
   reuse and request issuance are distinct qualified capabilities. A tenant
   administrator or reviewer label alone does not create them. A template's
   existence does not authorize every item for every source/purpose/recipient.
   Q25 checks the actual declared request and review coverage at issuance.
3. **Independent draft content.** Application records the selected eligible
   content/basis in the request draft. Template changes do not silently replace
   that draft's edits or mutate issued work. Ordinary template retirement affects
   future selection, not source facts/history; independent restrictive source
   rules continue to apply to current uses and issuance.
4. **Preserve existing staff input.** If template application is offered after a
   new draft has been started, show its actual contribution and preserve existing
   entries. Do not silently replace, merge away or duplicate items. The simplest
   flow may choose a template before authoring; no intelligent merge engine,
   per-field conflict wizard or routine confirmation is required. Any genuinely
   destructive replacement must be deliberate and reviewable.
5. **No effects from preparation.** Saving, choosing, previewing or editing a
   template creates no participant demand, invitation, timer, review assignment,
   acceptance, email occurrence or Q22 completion hold. Issuance remains the
   actual source-owned meaningful act. An unknown prior issuance result is not
   a safely unissued draft that a template may overwrite.
6. **Keep the catalog proportionate.** Use a clear name and useful permitted
   summary/items preview. Eligible staff need a usable way to create/update and
   stop offering an obsolete set, with attributable history as the real source
   requires. No mandatory approval tier, full publishing CMS, cross-tenant sharing,
   branching, variables/interpolation language, attachments, template marketplace,
   batch automation or general workflow engine is implied.
7. **Protect reusable content itself.** A template title or instruction can
   reveal sensitive people/location/purpose facts. Current authorized discovery,
   preview, saves, search, logs and exports must respect its source/tenant scope.
   Q38 general metadata discovery does not grant body search over template prose;
   reading an eligible template during authoring is a distinct qualified purpose.
8. **Correct at the proper stage.** Before issuance, staff can correct lawful
   draft content through normal source authoring. After issuance, use only actual
   eligible Q33/Q36/Q37 or other source remedies. Editing/deleting a template is
   never an Undo for issued work, a retrospective instruction change or recall
   of evidence/messages already received.

These are guardrails for the proposed answer, not a demand for a second approver
or a reason essay. A good ordinary flow can remain **Start blank / Use template →
review and adapt items → existing request preparation and issuance**. Template
management can use the same bounded authoring controls. The participant sees a
normal correctly scoped request, not a template-management task.

## Proof direction and limits

If A is chosen, its later adversarial review should test actual source/tenant/
field permissions at every discovery/read/write/use/issue path; selected template
basis versus concurrent edits; complete definition-only copying; initialized
draft preservation; duplicate/unknown outcomes; ordinary retirement versus real
source restriction; Q25 readiness and existing issuance races; no effects on
other drafts/issued/history; actual accessible mobile/AT/locale behavior; and
bounded catalog/use/recovery work. A test that merely copies a JSON array would
not prove any of those user or source outcomes.

No current implementation, database/RLS, provider, account, private document,
real request/message, concurrency/load, accessibility-conformance or intended-user
test was performed here. Exact repository/live implementation claims are left
to the independent owner/runtime notes. No zero-cost or measured time-saving
claim follows from a familiar template pattern. The previous Q38 cost condition
was scoped to its optional body-search addition, not silently converted into a
new promise that every later feature has no resource cost.

The product-language distinction can be explained as a reusable **request
template** containing an ordinary item set, while an actual **Private Document
Request** remains a separate source-owned occurrence. Whether a new glossary
definition is useful can be reviewed after selection; no term or physical model
is adopted by this research question.

## Adversarial check

### What could go wrong with this answer?

A person could send a correction while staff accept the earlier wrong file. A failed correction could silently revive the earlier file. A multi-file item could lose its other supporting documents. A progress bar could announce success before the source records receipt. These are the principal risks; the solution is an exact source-owned correction with truthful UI, not another approval ceremony for every ordinary mistake.

### What hidden assumptions are we making?

Pending is not merely overall request-open. Viewing is not a lock. Starting a transfer is not submission. Received is not safe, previewable or accepted. A filename/hash match is not the intended correction relationship. Preserving history does not grant access to all history. Replacing one file cannot replace all its independent uses. No current implementation establishes these guarantees for the new request flow.

### How does this affect the whole product?

The ordinary native request gains a narrow correction command and coherent participant/reviewer projections. Shared custody stores exact bytes; the requesting source owns the item, correction relationship and review selection. Existing expense, application, agreement, official-document, resource and public-release owners keep their specialized transitions. The file foundation does not wait for all of Workflow Studio, nor become its own workflow or permission engine.

### How does this affect the end-user experience?

The recipient acts on the specific submitted item, selects a file, checks the target/selection inline and deliberately sends it. The interface then distinguishes transfer, receipt and checks. It returns to the same task with a durable result and permitted Q02 preview. Staff see the exact version and an explicit new-correction notice without losing their place or silently approving different bytes. No mandatory explanation, extra destructive-confirmation modal, new account or drive screen is introduced for this ordinary action.

### Does this follow modern best practices?

Yes, as a deliberate product choice with safeguards. Dropbox documents sending the correct file through the same request and retaining both. Submittable documents the contrasting organization-approved reopening model. Neither proves Asym's full correction/acceptance contract. [Dropbox](https://help.dropbox.com/share/received-file-request), [Submittable](https://submittable.help/en/articles/904890-how-can-i-edit-my-submission).

GOV.UK supports clear file-selection instructions, specific errors and opportunities to check information before submission. For this one-file action, inline target/selection review plus a deliberate Send button is our proportional application of that guidance; it does not require a second confirmation screen. W3C requires perceivable status and usable error recovery, not celebratory animations or a toast alone. [File upload](https://design-system.service.gov.uk/components/file-upload/), [check answers](https://design-system.service.gov.uk/patterns/check-answers/), [status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

### Does this fit Asym’s existing repo and product direction?

Yes. The brief already requires correction, exact-version review and preserved history; Workflow Studio requires immutable resubmissions and current source revisions. Q02 deliberately did not grant mutation. Platform principles require operational truth and surface-appropriate simplicity. Base UI/`base-maia` remains the UI system. Existing public image uploading, local attachment chips and finance-specific correction exceptions are not generic private-correction implementations.

### Should we adjust the recommendation?

Keep A, with an explicit **admission boundary**: after immutable bytes are finalized and the source durably admits the correction, the corrected occurrence leaves the current review selection immediately, even while its successor is being checked. Failure of those checks does not silently restore the earlier candidate. This substantive Q03 amendment was included in Conrad’s explicit ratification for the ordinary native profile; it is not a universal rule for other source domains.

## Corrected decision to record

> A currently authorized recipient may initiate a correction of a particular pending submission within the ordinary native private-document request, while that item's current source rules permit it. The item must be unaccepted and not explicitly frozen, closed, waived or otherwise ineligible under its owner. An overall request remaining open is insufficient. Opening a preview does not freeze correction.
>
> A correction records a new immutable submission linked to the exact prior occurrence and source context. It changes only that occurrence's role in the relevant source review set; unrelated supporting files, independent uses of the same bytes and prior decisions remain intact. Selecting a file or starting transfer has no such effect.
>
> When the source durably admits the correction after byte finalization and current authorization, it atomically records receipt, successor relationship and the review-set change. Staff can no longer accept the corrected predecessor as the current candidate. New bytes remain pending their required safety and source checks; preview readiness is separate. If the new submission is unusable, the source shows truthful receipt/failure and the permitted correction or help path, without silently reviving the predecessor or accepting the successor.
>
> Correction, acceptance and relevant source changes use the same authoritative revision boundary. One cannot unknowingly override the other. Retries recover the same durable effect; changed intent conflicts. Earlier evidence, decisions and required retention remain protected. Download, deletion, prior-history access, post-closure access, deadline extensions and specialized source corrections are not granted by this decision.
>
> The UX remains inside the task: clear target, file choice, inline review, deliberate Send corrected file, truthful progress, persistent confirmation and a clear next action. It must work with keyboard, assistive technology, mobile and poor connectivity, using Core's existing shared UI.

For a single correction, the default is one targeted file-selection step followed by one deliberate send. A source that genuinely defines a multi-file submission keeps its own permitted cardinality; the UI must identify precisely what is being corrected. This is not a mandatory one-file-per-requirement model.

**Reviewer experience:** keep the current reading context and version label stable. When a correction arrives, show an inline **A corrected file has arrived** notice. Offer **Open correction** only when a qualified, currently authorized reading path is available. While checks are pending or unavailable, show that state and its safe next step; the corrected predecessor cannot be accepted while waiting. Unsupported or blocked content must not produce an unusable open action or an unsafe fallback. Never swap displayed content under the reviewer, steal focus during typing or migrate a draft decision/comment onto another version. An attempted stale acceptance must fail safely and direct the reviewer to the changed evidence. Prior notes remain bound to the version they describe, subject to existing permissions. A source-owned aggregate decision must consider every relevant member revision, not merely one file pointer.

**Accessibility and field conditions:** reuse shared Field, Button, Alert, Dialog and Progress behavior. Announce meaningful state transitions without continuously narrating every percentage. Keep errors associated with their field; service outages use service-state messaging rather than blaming file input. Keep focus stable during async updates, move it deliberately for submitted errors, and restore it on dismissal. Maintain Core's 44 CSS-pixel touch-target convention, keyboard alternatives, zoom/reflow, reduced motion, readable contrast and actual content accessibility. Use Unicode-safe display, bidirectional isolation and a way to inspect long names without treating names as identifiers. Show local dates with clear deadline time-zone context; the server's exact source rule determines timeliness. No names/addresses need to be re-collected for this action. [Error messaging](https://design-system.service.gov.uk/components/error-message/), [error prevention](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html), [redundant entry](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html).

## Category-by-category adversarial review

Severity and likelihood are qualitative. **High** concerns confidentiality, integrity or authoritative outcome; **Medium** concerns meaningful usability, reliability or maintainability. Evidence is described in each finding and expanded in the linked research. Exact corrections are the C clauses above and P proofs below.

### 1. Problem validity, necessity and alternatives

**Material concern: yes — Medium / plausible.** A preview that reveals a wrong file without a repair route leaves ordinary work incomplete; a general editor or archive solves a larger problem. The strongest alternative, staff-opened correction, is documented by Submittable and suits intentionally frozen applications, but forces staff involvement for every ordinary pre-decision mistake. Repository contracts already require correction, so B is not a no-build option. **Effect:** retain A only for this native pending-item profile; reduced friction is a product judgment needing participant evidence. **Fix:** C01/C09/C20; provide one contextual correction action, preserve stricter sources and test actual task completion, not clicks alone.

### 2. Brittleness

**Material concern: yes — High / plausible.** A rule such as request open, latest filename or reviewer has not opened it breaks with accepted siblings, multiple supporting files, revised instructions or browser reconnect. The brief and Workflow Studio distinguish exact source versions; viewing is not authority. **Effect:** narrow pending to current item/source capability and exact occurrence. **Fix:** C01–C05/C10; current source state at commit, explicit revision evidence and no timestamp/file-name matching or hidden read locks. Test unchanged pending status with a changed candidate, not only pending-to-accepted transitions.

### 3. Technical debt

**Material concern: yes — High / likely if current helpers are copied without their contracts.** Existing public image transport crops/reencodes/uploads publicly; local Support chips do not represent received files. Finance correction has specialized key/revision behavior that cannot prove Q03's exact-content concurrency. Shared UI is useful but not the business service. **Effect:** reuse at the right boundary. **Fix:** C03–C07/C12/C14/C17; one shared source command and qualified custody seam, existing UI primitives, no per-app correction logic or copying finance exceptions. This finding does not authorize changes to unrelated financial code.

### 4. Edge cases

**Material concern: yes — High / plausible; frequency unknown.** Same-name files, multiple documents for one item, two tabs, same bytes submitted deliberately, expired sessions, late completion and a scan outage can produce wrong selection or misleading success. These are realistic test cases, not asserted ministry prevalence. **Effect:** clarify the operation rather than reject A. **Fix:** C02/C06/C07/C10; distinguish supplement from correction, retry from new intent, confirmed unsafe from unverified, and received from accepted. Do not silently discard a legitimate deliberate submission merely because its digest matches; any same-file warning must be authorized and target-scoped.

### 5. Footguns

**Material concern: yes — High / likely under naive UI reuse.** Replace/Delete labels, automatic submission on file selection, an alert-dialog close handler or a green 100% bar can imply deletion, successful receipt or approval. ReUI's demo timer and the current shared close/progress behavior make this a concrete reuse hazard. **Effect:** make every action and state honest. **Fix:** C08–C11/C15; deliberate send after inline inspection, Cancel selection versus Stop transfer, durable result readback, no fake percent, no destructive replacement and no global undo. Required acceptance checks remain server-side even if buttons are disabled.

### 6. Tenant safety

**Material concern: yes — High / plausible.** A target ID, duplicate digest, cache key, count or conflict result could reveal another tenant/request/recipient or redirect bytes into a different purpose. Shared UI and provider privacy do not enforce those relationships. **Effect:** correction is scoped beyond uploader identity. **Fix:** C02/C04/C07/C13/C14; derive trusted scope, validate exact same-scope relations, authorize before result serialization and isolate processing. Replayed outcomes, changed recipient and error details require current disclosure rights. Identical bytes cannot merge audiences or expose a duplicate elsewhere.

### 7. Database, RLS and authorization safety

**Material concern: yes — High / plausible.** A permitted UPDATE could change prior occurrence, item, classification, actor or accepted state while staying in the same tenant. Separate read-then-write calls can admit a correction after acceptance. The reached finance schema has later tenant-reference triggers and service-only access; that is not a generic participant policy. **Effect:** require C03–C07/C14, not an assumed schema. **Fix:** immutable authoritative links, required same-scope keys, restricted state/column mutation, semantic uniqueness, protected deletes and one authoritative transaction boundary. Evaluate all grants and permissive policies, USING and effective WITH CHECK, function ownership/search paths, views, storage and workers with real roles. Omitted WITH CHECK can inherit USING; SECURITY DEFINER alone does not establish a vulnerability. Q03 adds no money calculation: existing financial precision and posted facts remain untouched. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

### 8. Overengineering

**Material concern: yes — Medium / plausible.** Review leases on every open, a mandatory reason, second confirmation, universal version graph/editor or per-tenant configuration matrix would burden a small action. Conversely, separate services for every independent status would fragment ownership. **Effect:** keep the minimum explicit semantics. **Fix:** C01/C09/C17; ordinary default A, existing source exceptions, one targeted selection/send flow, shared commands and separate facts without mandatory separate services. Do not introduce a configurable workflow dependency, automatic compare view or a universal correction-count preference.

### 9. UX/UI and user friction

**Material concern: yes — Medium / plausible; real-user benefit unmeasured.** Hidden actions, repeated identity entry, toast-only receipt, vague spinner, drag-only input, premature navigation and stale reviewer content cause confusion and repeat submissions. GOV.UK/W3C support clear instructions, error recovery, deliberate confirmation and accessible status; current Core primitives provide parts of that behavior. **Effect:** A requires the complete recipient/reviewer journey above. **Fix:** C09–C12, including short inline review, specific safe errors, preserved task context, honest unknown outcomes, localization and mobile/assistive-technology proof. Do not trade accessibility for a prettier upload widget or claim an automated pass proves usable content.

### 10. Source of truth, ownership and invariants

**Material concern: yes — High / plausible.** A universal latest-file pointer could change financial evidence, sent attachments, resource publication or all uses of shared bytes. A file manager could accidentally satisfy a requirement when a new upload arrives. Existing P18/P21/P26 ownership explicitly forbids those effects. **Effect:** require source-owned occurrence and review-set change, not generic file replacement. **Fix:** C02/C03/C11/C16; immutable receipts/decisions, at most one current successor per targeted use under its source state, preserved other members and exact accepted evidence. Counts, projections, provider copies and preview outputs are not write authorities.

### 11. Hidden coupling

**Material concern: yes — High / plausible.** Waiting for preview-ready before honoring a received correction couples review truth to conversion speed. Requiring preview success to start correction traps users with unreadable files. A whole-request lock creates conflicts among unrelated items. **Effect:** explicitly separate admission, safety, preview and acceptance, while fencing real aggregate dependencies. **Fix:** C03/C05/C06/C10; admission immediately ends predecessor candidacy, inspection remains qualified, and independent items need no artificial mutual exclusion. Full Workflow Studio, a new account or a complete file explorer is not a prerequisite.

### 12. Failure modes

**Material concern: yes — High / plausible.** Provider success followed by lost response, source commit followed by outbox failure, checker outage or partial output can leave contradictory user/staff views. Automatically reviving the earlier file may cause staff to accept known-wrong evidence. **Effect:** add the substantive early admission/no-silent-revival amendment. **Fix:** C03/C06–C08/C10/C17; durable receipt and secondary intent, exact-copy reconciliation, bounded worker recovery and truthful current candidate failure. Uncertain is not failed; checker unavailable is not malware; accepted transport is not accepted evidence.

### 13. Lifecycle, temporal correctness, concurrency and idempotency

**Material concern: yes — High / plausible.** Two valid corrections, acceptance, revocation, instructions change and deadline crossing can jointly violate the source invariant. A key deduplicated without its intent or automatic rebase can apply the wrong target. **Effect:** exact operation and relevant review revisions become mandatory. **Fix:** C03–C08/C10; conditional authoritative commit, stable intended effect, changed-intent conflict, current result disclosure and no clock/session renewal. Timestamp ordering or client button suppression is insufficient. PostgreSQL transaction semantics require deliberately enforced invariants; a generic transaction wrapper alone is not proof. Test both orders and lost acknowledgments. [Transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

### 14. Data integrity risks

**Material concern: yes — High / plausible.** Same-name matching, overwritten object keys, mistaken provider ETags or replacing an entire multi-file set could lose the actual submitted evidence. Counting each correction as a new satisfied item corrupts progress. **Effect:** correction must preserve exact identity and relationships. **Fix:** C02/C03/C06/C11/C14; immutable bytes and verified digests/lengths, explicit predecessor linkage and source-selected review-set delta. Correcting one member preserves siblings; no approval or clean verdict transfers. Stable business identity survives provider movement and correction history survives restore.

### 15. Security and privacy risks

**Material concern: yes — High / plausible.** New bytes bypassing checks, old cached preview results, raw filenames in errors/telemetry, unrestricted history or fallback email attachments can disclose sensitive ministry data. Reuse of public image transport is specifically unsuitable. **Effect:** preserve all Q01/Q02 private boundaries on the mutation and every result. **Fix:** C04/C06/C12–C16; current authorization, isolated qualified processing, no public/raw-original/external-viewer fallback, no secret/private-content telemetry and separate retained-history access. A corrected sensitive upload is not erased by replacement; provide source-authorized privacy/help handling without promising legal compliance or invisible deletion.

### 16. Scalability and performance risks

**Material concern: yes — Medium–High / production frequency unknown.** Repeated corrections, abandoned reservations, many history rows and simultaneous processing can exhaust storage/workers or starve other tenants. **Effect:** finite operation and fair work are required, but no invented global human-correction limit. **Fix:** C07/C15/C18/C20; reuse exact source intake budgets and inherited preview profiles, coalesce retries, bound active reservations and paginate authorized projections. Use indexed scope/current-target/operation lookups and verify query plans at representative tenant skew. Do not convert D32's 20 MiB preview input ceiling into every source's upload limit or its two parser attempts into two permitted human corrections.

### 17. Operational burden

**Material concern: yes — Medium / plausible.** Ambiguous finalization and unavailable scanners can lead staff to edit SQL, use provider consoles, ask for email attachments or restore the wrong candidate. A vague freeze rule could also demand constant manual unlocking. **Effect:** make ordinary recovery owned and in-product. **Fix:** C08/C10/C17/C20; safe operation lookup/reconciliation, current source help routes and audited technical recovery without impersonating the recipient or bypassing checks. Preserve A's default; stronger source rules are explicit, not an unexplained disabled button.

### 18. Observability and auditability gaps

**Material concern: yes — High / plausible.** An upload log may be mistaken for receipt or acceptance, while corrections produce duplicate notifications or lose who submitted which version. Technical logs could become a second private archive. **Effect:** distinguish durable business evidence from diagnostic signals. **Fix:** C03/C07/C13/C17/C20; record actual actor/source/version/intent/outcome in the correct restricted history, keep ordinary telemetry opaque, and trace command, intake and processing IDs without raw content. View evidence does not prove human understanding and is not a new CRM interaction. Monitoring below has explicit owners and responses.

### 19. Dependency and integration risks

**Material concern: yes — High / plausible.** A registry sample simulates progress; an SDK abort does not undo server success; scanner callbacks arrive late or repeat; a library upgrade changes parsing or focus behavior. Provider and UI tooling do not own business acceptance. **Effect:** qualification must cover the actual installed adapters and complete path. **Fix:** C06/C07/C10/C12/C15/C17; retain versions until proven upgrade need, exact callback correlation, source-authorized serving and consistent durable recovery. No new editor, external viewer, upload provider or licensed block is selected. ReUI's keep-its-look guidance is subordinate to the founder's exact Core Base UI/base-maia requirement.

### 20. Migration, rollout and upgrade risks

**Material concern: yes — High / plausible.** New correction writers can coexist with old reviewers that accept stale evidence. Backfilling lineage from filenames or timestamps could rewrite history. Rolling back may revive an old candidate after new corrections exist. **Effect:** activation is a source-cohort compatibility gate. **Fix:** C16/C19/C20; additive identities and explicit mappings, real retained-data census, all affected decision writers enforcing revision fences before enabling corrections, unknowns restricted/reconciled, and kill switches that preserve admitted history. Restore replays restriction/disposition history before delivery. Roll forward or disable unsafe actions; never undo accepted correction history through a code rollback.

### 21. Testability, traceability and proof

**Material concern: yes — High / known evidence gap.** The reached source lacks the new generic correction service and full recipient journey. The 31 passing tests prove existing limited seams, not real-role or concurrency guarantees. **Effect:** no runtime-complete claim. **Fix:** C20 and P01–P24 below; link founder selection → glossary/ADR → exact owner amendments → later authorized specification/tasks → implementation → environment and participant proof. Keep acceptance criteria about actual wrong-file recovery and correct review outcomes, not implementation snapshots or a matching screenshot. No Q03 formal spec/tickets are published in this stage.

### 22. Other development hazards

**Material concern: no additional independent concern found.** The review checked scope creep into e-signing, money changes, public publication, office editing, generalized offline storage, browser-based identity assumptions and universal undo. These are already excluded or covered by the concrete ownership, privacy, lifecycle and rollout findings above. No new legal guarantee, vendor choice or broad administrative power is required to preserve A. This is not a claim that all future implementation hazards have been eliminated.

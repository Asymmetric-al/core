Do not justify B by assuming staff will renew it routinely, or A by claiming indefinite retention/low risk merely because scope is read-only. The exact [Node v24.21.0 timer documentation](https://nodejs.org/download/release/v24.21.0/docs/api/timers.html) states that delays above 2,147,483,647 ms become 1 ms and does not guarantee exact callback timing. Thirty days cannot safely be one ordinary Node timer. Fourteen days fitting the numeric bound is not a reason to make a resident timer own permission: restarts, execution delay and current revocation still matter. Existing bounded durable follow-up can remain where owned; expiry is enforced through the source/private-serving contract. No timer callback experiment was run for Q18.

Elapsed hours are materially different from local calendar arithmetic. PostgreSQL documents that adding `interval '1 day'` across DST can differ from `interval '24 hours'`; months and local dates have calendar semantics. A chosen elapsed profile must preserve its exact interval despite DST, travel or display timezone. Input without an explicit zone may adopt session TimeZone, so a date-only/local string cannot substitute for the qualified source instant. Use the existing trusted instant/precision contract and localized display; no astronomical clock framework is selected. [PostgreSQL date/time arithmetic](https://www.postgresql.org/docs/17/functions-datetime.html), [date/time types](https://www.postgresql.org/docs/17/datatype-datetime.html)

Current PostgreSQL docs also distinguish transaction-start NOW from actual current clock readings.

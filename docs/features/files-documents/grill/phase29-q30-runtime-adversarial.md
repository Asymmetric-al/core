## Required amendments and proof

### R01 — Exact current authority and effective database operations

**Severity critical; likelihood high if generic staff/comments/storage paths are reused.** Bind every accepted read/send/recovery to trusted tenant/environment, current confirmed recipient or actual authorized staff actor, source, request, item, purpose and current admission. A pre-upload question binds an existing requested item without fabricating a submitted file or version. Evidence-related messages additionally retain the exact referenced version/evidence/instruction/review basis where relevant. File reading, folder membership, task assignment, matching email, old sender status and a mention confer no message authority.

Qualify table/schema/column grants, all applicable permissive/restrictive policies, SELECT/INSERT/UPDATE/DELETE/UPSERT, old-row USING and resulting-row WITH CHECK, tenant-aware relationships, transformed rows, views, RPC/definer functions, triggers, service/worker paths and every served representation. Both clauses being present does not prevent a same-tenant row from being reassigned to a different item/author/audience. Deny unauthorized identity/context changes even where the before and after rows separately pass tenant RLS. A trusted service credential is an execution mechanism, not the actor's source permission. Include current authorization after relevant waits; stale JWT claims cannot be the sole revocation fence. Preserve Q01 request-only identity/proof without mandatory donor, missionary, staff or organization enrollment; do not create an alternate authentication system.

**Proof:** actual authenticated limited-recipient, unrelated recipient, same-tenant unrelated staff, reviewer without disclosure rights, source-authorized responder, cross-tenant actor, revoked membership, service runner and definer caller. Attempt forged actor/time/tenant/recipient/context; row reassignment; private-to-shared transformation; direct RPC/table access; cache/replay/count/search leaks. Verify denial without existence or confidential-reason leakage.

### R02 — Distinct participant-visible text, exact outward action

**Severity critical; likelihood high.** Participant-safe clarification is a distinct source-authorized content class. It does not expose the internal staff thread or convert a private note by toggling a flag. A staff reply is a new deliberate outward act with its own approved content and currently eligible audience; neither default team access nor replying to a task supplies that authority. No participant directory, arbitrary To/CC, attachment, mention-based access, external email ingestion or automatic Support conversation is implied.

Enough currently permitted shared text must be available to understand the exchange; “no history at all” would make A unusable. This narrow live context must not become a permanent archive or disclose former recipients, other purposes/items, restricted staff notes, superseded file bytes or protected excerpts. Quoting or linking old content is still disclosure. Q29 paired reading does not add recipient historical rights.

**Proof:** internal note and shared reply in the same visual context; quoted private text; same bytes reused by another source; changed recipient; staff reassignment; preview/link/export/projection of old evidence; malicious reply-to identity. Assert exact audiences for each command and projection.

### R03 — Durable receipt and accountable work must survive partial failure

**Severity high; likelihood high.** “Received/awaiting staff” requires durable message identity, exact accepted body/context, trusted attribution and a durable route into existing authorized source work. Do not silently mark a question answered because a task closes, or create a second general inbox or one task per message as the default.

**Proof:** faults before commit, between all persisted constituents, after commit/before response, before/after projection, during ownership change and with all optional email disabled. Committed message and mandatory work must reconcile to one occurrence; no false receipt, orphan, duplicate task or loss under closure/expiry. Native visibility must work without mail.

## Primary technical documentation checked

- [PostgreSQL 17 CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html): USING applies to existing rows and WITH CHECK to resulting rows; BEFORE triggers run before WITH CHECK; applicable permissive policies combine with OR. Consequently, inspect effective policies and transformed rows rather than counting policy clauses. It also explicitly supplies USING as the check when WITH CHECK is omitted for applicable policies, so an absolute claim that omission always permits reassignment would be inaccurate.
- [PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html): table-owner/BYPASSRLS behavior and cross-table policy races explain why endpoint checks and table-policy presence do not prove current source authorization.
- [PostgreSQL 17 transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html): default Read Committed snapshots do not establish the application invariant that admission, current facts and dependent decisions have one coherent order. This review requires a proved protocol without selecting an isolation level or lock implementation.
- [PostgreSQL 17 time functions](https://www.postgresql.org/docs/17/functions-datetime.html): transaction timestamps differ from current wall-clock time. Reusing a pre-wait timestamp cannot prove admission before expiry or the actual source occurrence.
- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [views](https://supabase.com/docs/guides/database/views), [API keys](https://supabase.com/docs/guides/api/api-keys), fetched through Context7 `/supabase/supabase`: user metadata is user-editable; JWT authorization facts may be stale; view-owner rights and service-role bypass must be accounted for. These facts support independent current source checking and privileged-path proof.
- [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control): service keys bypass Storage RLS and access policy behavior depends on operation. A message link cannot qualify a private object merely because database message access passed. The [changelog index](https://supabase.com/changelog.md) was consulted; no implementation or API upgrade is being performed here.
- [OWASP XSS prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html): output handling must match context; safe rendering does not establish business authorization. No native rendering test was performed.

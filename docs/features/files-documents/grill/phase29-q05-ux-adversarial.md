# Phase 29 Q05 — useful submission history without a recipient archive

Inspected 20 October 2026, Asia/Bangkok. The parent reports Conrad selected Q05 A: current files plus concise submission history. Q01–Q04 and their amendment packages are ratified. This note proposes UX amendments and acceptance outcomes for the Q05 review; it does not itself ratify them, authorize implementation or claim the journey works.

Scope is the ordinary native private-document request while the recipient currently has access. Superseded means a specific earlier occurrence corrected out of the current source file set. An older supporting member can remain current and keep its eligible Q02/Q04 actions. Historical content access and access duration are separate matters; neither a personal archive nor post-closure continuity is added here.

This work read current official documentation and the prepared Q05 question. It did not implement UI, run an authenticated comparator session, inspect private applicant data, send a request, perform a real upload/download, or conduct a participant/accessibility test. The question's older “awaiting answer” label is superseded by the parent's report of the founder's selection; no further selection is inferred.

## Recommendation

Make the current state immediately understandable, with a small **Submission history** underneath it. A short history should usually be readable without another click. Use a single secondary disclosure or bounded history navigation only when the actual length/density makes it useful. **Concise does not mean always collapsed.**

The history answers what was received and corrected. It does not reproduce the staff audit log, explain every technical event, or offer View/Download controls for superseded files. Current qualified files retain those actions above the history. A current correction undergoing checks still needs its visible status and recovery; an older file cannot be silently revived because the new one is unavailable.

Keep source-approved help for a legitimate old-file question near the history, without promising that help automatically grants access. A may be a reasonable ordinary default, but it has a real limit: timestamps and filenames cannot show which page was missing in an earlier scan. That is the strongest case for B, and it should not be disguised by polished metadata.

## Exact recommended information hierarchy

**First: current work.** For each requested item, show all source-current members and their current checking/review state. Keep eligible View, Download and Correction actions associated with the exact file. An earlier timestamp does not make a still-current supporting member historical. A newly admitted correction can be current while checks are pending; current does not mean accepted or deliverable.

**Second: a concise receipt explanation.** After a correction, say **Correction received** when its durable source admission succeeded. Show the actual current next state, such as **File checks in progress**, outside any disclosure. A permitted short sentence can explain that the earlier file is no longer the current submission for that member. Do not imply the entire request has been satisfied or all other files were replaced.

**Third: Submission history.** Render the short authorized event list in the same item. Prefer plain rows with event description and time over a decorative timeline with separate cards, avatars and icons for every event. For longer histories, a clearly labelled **Show earlier history** or appropriate pagination can reveal more. The initial view should not silently pretend to be complete if it is only a permitted subset/page.

This hierarchy is a recommendation to test, not a universal visual template. Short visible history is the baseline because hiding two useful rows may add effort without reducing clutter. Once repeated corrections genuinely compete with the task, a secondary reveal can be worthwhile. No fixed number of visible events or a new timeline component is selected.

## Empty, unavailable, partial and denied are different states

This distinction is essential because a false empty history can make someone upload again, dispute a real receipt, or believe evidence was deleted.

| Actual state                                                          | Appropriate result                                                                                                                                | Forbidden inference                                                                                                                        |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Successful authoritative read confirms no received acts for this item | Show the genuine not-yet-submitted state and applicable upload action. Avoid an unnecessary empty history section.                                | Do not infer this from a failed history query or a filtered result alone.                                                                  |
| Successful permitted projection has no visible history entries        | Omit the secondary section if that is not confusing, or use an approved neutral explanation such as **No submission history to show here**.       | **No files were received** would overstate what the projection proves. Do not reveal hidden event existence merely to explain the absence. |
| History temporarily fails to load                                     | **Submission history could not be loaded. Try again.** Preserve independently confirmed current state where its own access/freshness rules allow. | Replace the current receipt with “empty”; disable otherwise independently valid current actions solely because optional history failed.    |
| Current event is confirmed but the projection is catching up          | Keep the authoritative receipt/current result and use truthful secondary loading/unavailable messaging if needed. Recover the same projection.    | Ask the user to submit again; fabricate rows; silently remove the confirmed receipt because another read lags.                             |
| Earlier legacy coverage is genuinely incomplete                       | If the source permits disclosing that limitation, label the available coverage honestly and provide the approved help route.                      | Call it a complete audit trail, invent missing events, or equate absent legacy entries with no submission.                                 |
| Some metadata is restricted                                           | Project only currently allowed details, without misleading substitute content. A standard generic description may be appropriate.                 | Conditional “hidden entries” counts, numbered gaps or restriction explanations that themselves reveal protected facts.                     |
| Access revoked or no longer admitted                                  | Follow the source's safe denial/reauthentication behavior and stop further disclosure.                                                            | Keep serving old entries because the panel was previously opened; assert that history was deleted.                                         |
| File bytes disposed but an authorized historical receipt remains      | Show only the permitted receipt fact. A does not offer old-byte actions anyway.                                                                   | Promise a recoverable old file, imply disposal never happened, or rewrite the receipt into nonexistence.                                   |

“No results” is not an all-purpose fallback. Where two denial conditions must be indistinguishable, preserve that privacy requirement rather than adding a detailed empty-state explanation. Error handling must not leak through cached names, page titles, analytics, hidden DOM, counts or pagination controls.

## Repeated corrections, pagination and mobile use

Keep a short history simple. Once bounded loading is warranted, use explicit **Earlier history** / **More recent history** navigation or the qualified shared pagination pattern. Avoid automatically growing infinite scroll. Do not add a generic search/filter dashboard unless actual history use and volume justify it.

The following are Asym design implications rather than literal vendor requirements:

- History navigation operates on the authorized projection, not a raw log filtered after pagination. Hidden entries must not leak through totals or leave confusing empty pages. No arbitrary “last ten events” policy should silently destroy the participant view of relevant receipts.
- Use stable page/cursor semantics so a new correction does not duplicate or skip unrelated entries as the user moves backward. Current source state remains authoritative; an earlier page does not grant historical byte access.
- Preserve focus and reading position appropriately after deliberate navigation. Identify the new history range or page accessibly without announcing all rows. The loading/error state belongs to that navigation control, not a full-screen reset.
- Do not show Previous/Next controls that have no meaning; use suitable directional labels and announce the current page if actual numbered pages are used. Do not expose a total-page count unless that total is authorized and reliable.
- On narrow screens, stack the event and date rather than creating horizontally scrolling metadata tables. Make full permitted text available without hover. Maintain Core's shared touch targets, keyboard operation, visible focus and text reflow.
- If a secondary disclosure is used, its name should be **Submission history** or **Earlier submission history**, not an ambiguous **More**. Expansion state must be conveyed, and a permission/update transition must not leave focus on a removed control.
- Do not nest multiple disclosures to reach one receipt. Do not collapse a currently important receipt/error merely because another event arrived.

Do not import GOV.UK's suggestion to redirect an invalid public page number mechanically into a private history flow. A stale cursor or permission change needs current-authority refresh and a useful explanation that does not reveal restricted entries. Actual pagination and assistive behavior must be tested, not inferred from using a familiar component.

## Old-file help without creating a default archive

A requires an honest limitation: this ordinary recipient view does not reopen superseded content. Make the current file and correction record useful enough that a person does not need help merely to determine whether a correction arrived.

When the question is genuinely about earlier contents, a source-approved route may use the existing task/help channel and carry an authorized opaque item/submission reference. Explain the purpose before the person acts. Do not send a message merely because they expand history, and do not automatically attach the historical bytes to a help request.

The route is not an implied file grant, a generic “Unlock version” button, a new per-event approval queue, or an excuse to email private attachments outside the qualified delivery path. The responsible source decides what explanation or separately permitted delivery is possible, subject to current authority, safety, retention and disposal. If there is no functioning supported help route, that is a real completeness gap to resolve before release; do not promise one in copy.

Where no old-file release is permitted, explain that outcome safely. Do not invent legal rights, override another source's policy, promise recovery of disposed bytes or require the person to reconstruct a confidential filename to obtain help.

## Strongest B case remains real

If a recipient submitted several identically named scans, the concise log can identify receipt order and currentness but cannot show the missing page in the second scan. B would offer more direct self-service investigation where historical content is currently authorized and qualified. That could reduce a staff exchange; this is a reasoned possible benefit, not measured evidence.

Conrad selected A, so the practical response is clear currentness, meaningful receipt history and an actual help path. Do not smuggle B back in through thumbnail previews, old filename links, generated “history packets,” bulk downloads, a rich audit viewer or a support shortcut that routinely releases all versions. Conversely, do not depict B as inherently a drive or universally unsafe. It is a different legitimate scoped capability.

No additional founder choice about collapse thresholds, timestamp formatting or pagination mechanics is needed now. Those are implementation/qualification choices within the selected direction. A material requirement for ordinary historical content access discovered later must be raised explicitly rather than buried in a UI convenience.

## Acceptance outcomes to require later

These are proposed falsifiable outcomes, not tests passed by this note.

1. A recipient can identify all current members, determine whether a correction was received, and find the current next action without opening history.
2. A short history is understandable in the existing task without a drive/archive detour. If disclosure is introduced, people can find and operate it; current status/errors remain outside it.
3. Replaying a received correction creates one participant event; two distinct admitted corrections remain distinguishable even with equal names or displayed timestamps. Reordering/delayed events does not alter currentness.
4. A newer unusable/checking correction remains truthfully current under Q03, while unchanged older supporting members retain their eligible actions. No predecessor silently revives.
5. No unauthorized actor, filename, event existence/count, hidden content or old-byte action leaks through the visible UI, accessibility tree, URLs, metadata responses, pagination or ordinary telemetry.
6. Reassignment, shared mailbox and Party relationship changes cannot falsely label an act as personally performed by the current viewer or transfer history without source authority.
7. Load failure, projection lag, authorized-empty results and known incomplete legacy coverage produce distinct safe behavior. No failure rewrites durable receipt into “never received” or requires a duplicate upload.
8. Keyboard, speech, screen-reader and touch users can read the history, expand it if used, navigate older entries, recover from errors and return to the current item. Long/RTL names, localization, zoom and narrow screens remain usable.
9. New events and permission changes preserve truthful current state without uncontrolled focus/scroll movement or repeated full-history announcements. Current authorization governs every new read.
10. History remains bounded under the declared workload with stable authorized navigation; pagination neither leaks totals nor skips/duplicates entries during concurrent corrections. No invented fixed history-count limit substitutes for this proof.
11. The old-file help route actually reaches the accountable source with safe context, without auto-sending messages or bytes and without promising unsupported recovery or access.
12. A representative participant/reviewer exercise confirms that people distinguish received, corrected, current and accepted, and understand what the history can and cannot show. Report the sample and limitations; resolve observed safety-critical misunderstandings before expansion without inventing success percentages.

No numerical pagination size, collapse threshold, retention period, refresh interval or operational alert threshold is introduced here. Those must be qualified within the actual source and shared UI, not copied from vendor examples. No general history library, CMS-version API exposure, new identity system or timeline dependency is required by the selected outcome.

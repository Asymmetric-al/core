# Phase 29 Q24 — Person or team review responsibility: UX adversarial review

**Reviewed:** 2026-10-22, Asia/Bangkok. Conrad selected Q24 A: allow an eligible person or a qualified team to carry ordinary review responsibility. Q01–Q23 and their amendments are ratified. This note proposes focused amendments for the parent's full review; the complete Q24 package is not ratified here. The earlier question document correctly records its historical unselected state and is not edited by this research.

**Recommendation: retain A with the eight incremental clauses below.** It can remain a small experience: show who is responsible, let qualified staff do the work, and support a lawful handoff when needed. The critical distinction is that a team can be genuinely responsible without a nominal personal claim, but a team name alone cannot establish usable coverage, current review authority or successful task delivery.

Research is limited to current public primary documentation and the local Q24 question/comparative context. No product accounts, provider writes, real assignment changes, notifications, native UI tests, assistive-technology tests or intended-user studies were performed. The parent's separate owner/runtime investigation supplies exact repository and live-source authority. Local adjacent code is not native qualification.

## What A settles and what remains inherited

A permits qualified individual and shared-team responsibility before ordinary review decisions. It rejects a universal extra requirement to resolve team work to a named individual merely to make a valid review actionable. The human making each Q21 acceptance or Q23 Request changes decision remains individually attributable, currently authorized and bound to the exact current review basis.

It does not settle whether a request may be issued or collect submissions before responsibility is resolved. Existing source issuance rules govern. It does not make a generic Team, administrator role, creator, parent-record owner, queue membership or watcher sufficient. It preserves source-specific individuals, expertise and separation-of-duties constraints. Some source policies may use assignment as an input to authority; that is different from the UI granting access because an assignment label exists.

The product choice is responsibility shape, not a new notification default, permission atom, roster screen, assignment algorithm, presence service, mandatory claim, exclusive review lease, reviewer vote, second approval or workflow builder. Reuse qualified source responsibilities and the existing request/My Work surface. A source coordination change must not become a new form for the recipient or an excuse to request the same file again.

## Strongest B and the no-build counterargument

B's strongest argument is direct accountability: one person is visibly responsible before ordinary review, simplifying who is expected to coordinate a response. It still permits authorized colleagues to assist and need not add a Claim button. If a source already has a valid named responsible person, a lean A should reuse that person; introducing a team configuration screen just to exercise A would be unnecessary.

B also avoids qualifying shared responsibility where the organization has no operational team coverage. That is a real cost of A, not something cured by adding a Team dropdown. A remains preferable for the selected ordinary profile because it can represent real shared work without fictitious personal assignment. The amendment is to qualify a real work/recovery route, not to add a mandatory named coordinator back onto every team request and thereby silently implement B.

If a supported source cannot qualify shared responsibility, use its eligible individual path or its explicit unresolved-assignment recovery. Do not invent a new permission, impersonate a departed staff member, or widen to every administrator to make a team field save. Existing supported source administration may be sufficient to repair a target; this decision does not demand building another staffing or support product.

## Lean end-to-end experience and truthful copy

Provisional wording below illustrates meaning; it is not a requirement for a new enum, notification, page or translation feature. Use the current source's accurate vocabulary and disclose only what the actor may see.

1. **Open the existing work.** Where known and permitted, show **Review responsibility: Ana** or **Review responsibility: Document review team** beside the actual pending source work. An icon/avatar may reinforce the distinction but cannot be its only carrier. A team does not need a meaningless person field filled in to enable an otherwise lawful action.
2. **Review using existing actions.** The authorized reviewer inspects the exact current evidence and uses Accept or Request changes under Q21/Q23. Merely being assigned, viewing a document or saving responsibility never means Reviewed or Accepted. The actual human decision is retained. A participant with timely submitted evidence is waiting on staff, not automatically overdue because the responsible team has work pending.
3. **Change responsibility only when needed and allowed.** Use the existing source interaction; show the target type and enough permitted identity information to avoid confusing identically named users/teams. Commit deliberately with a clear action such as **Save responsibility** if a separate submit control is used. Do not force an extra “Are you sure?” confirmation for an ordinary permitted handoff. Do not unexpectedly navigate/commit while a keyboard user merely explores options.
4. **Report the real result.** **Review responsibility updated** means the source committed it. It does not mean Notified, seen, picked up or ready for all possible review actions. If source commit is known and an ancillary list refresh fails, retain the result and disclose the refresh problem where useful; do not tell the user to resubmit the assignment as though it failed.
5. **Recover genuine gaps.** A known unresolved route can say **Review needs assignment** with a permitted action for the capable source owner. A failed qualification lookup can say **We can’t check review responsibility right now. Try again.** It must not say No reviewer exists or Access expired without evidence. Use existing owner support when the current actor cannot lawfully repair the condition; do not offer an inert button or require private provider/SQL intervention for ordinary supported recovery.
6. **Keep the participant out of staffing mechanics.** Present the current permitted source status/help and actual correction path. An internal handoff must not demand a new participant account, new document copy or a response to an unknown staff email. Receipt and later work retain their own timing. Access-ended and proof/session failures retain their established distinctions; responsibility does not renew access.

No optimistic Saved/Assigned status may later silently roll back after a denied source write. A visible saved assignment also cannot overpromise that an absent colleague is presently reading the document. Preserve draft context only while currently authorized; after current authority is lost, safe recovery does not justify keeping private names, comments or evidence cached on a shared device.

## Focused qualification outcomes

The parent's full review should map these to its existing proof ledger and owners rather than create another testing framework:

1. **Person and team both work:** a real ordinary qualified human can perform an exact Q21/Q23 decision under either responsibility without a nominal personal claim; a similarly named unqualified team/person cannot.
2. **Coverage is real:** current shared work can be found in the authorized existing surface, and missing/ineligible responsibility has an actually capable owner response. No assumptions based on a stored row or simulated callback.
3. **Membership is current:** newly added, removed, disabled and permission-changed people have exactly their current allowed discovery/actions; source failures deny dependent protected actions without pretending to prove absence or expiry.
4. **Defaults do not defeat intent:** valid source inheritance is reused; allowed deliberate change survives delayed initial/default projection. A later true source restriction still applies. No new universal fallback/override precedence is assumed.
5. **History and source state survive:** handoff/departure preserves valid old actors, receipts, corrections, concerns, decisions and fulfillment. Necessary separately authorized fact correction remains distinct. Same-evidence Q23 reassessment can proceed under the new actor's actual authority without new bytes.
6. **Relevant races converge:** test person/team change, two editors, actor permission loss, recipient correction, review acceptance/changes requested and fulfillment in both material source orderings. No broad review reset for unrelated metadata; no stale permission bypass.
7. **Recovery is exact:** commit-lost-response, duplicate request/event, stale task projection and old replay after a later handoff preserve one intended source effect and truthful current result. Task/provider failures do not invent source failure or notification success.
8. **Discovery is safe:** assignment autocomplete, labels, filters, counts and history do not disclose unauthorized people/teams/records; cross-tenant/user/request/purpose changes reject late data. No generic roster disclosure or private offline cache.
9. **Participants have accurate next steps:** receipt/staff waiting/correction/ended access retain their established meaning and permitted help. Internal responsibility changes neither expose staff mechanics nor renew access or mark earlier timely receipt late.
10. **Composed UX is proven:** representative intended staff can identify responsibility, act or hand off lawfully, and recover at supported mobile/zoom/keyboard/AT/locale/poor-network conditions without extra claims or confirmations. Assignment controls do not replace document-content accessibility tests.

Operating concerns are visible stalled responsibility, unsafe current-authority results, duplicate/lost task projection, misattributed history, unexplained ordinary recovery failures and inaccessible interactions.

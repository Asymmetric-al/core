# Phase 29 Q42 — Ordinary evidence organization: one home or additional references

2026-10-24, Asia/Bangkok. Independent comparative research for the next question
after Conrad's full ratification of Q41 and its Private Document Share term.
Q01–Q41 are settled; **Q42 is unselected**. Only this assigned research note is
authored. No canonical/specification/runtime/provider/account changes, actual
messages, private-document inspection or implementation tests are performed.

## Recommended question and scope

For an ordinary request evidence entry that staff are authorized to organize,
should it have **one home folder or Unfiled, with labels and source/saved views
for other groupings (A, recommended)**, or should staff also be able to put
**explicit non-owning references to that same entry in additional folders (B)**?

The target is one admitted file contribution/use for a particular ordinary
Private Document Request/item: a participant-received contribution or qualified
Q28 staff-supplied evidence. It is **not the whole multi-file requested item**,
an underlying digest/storage object, a new universal Logical Document, or every
use of equal bytes. The source supplies the stable organizational reference and
its qualified version/correction mapping. Q42 does not invent latest-version
resolution, automatic filing inheritance for a successor or historical browsing.

Both options retain the required folders, labels, metadata/source discovery,
saved views, filters, sorting and finite bulk handling. This is a choice about
ordinary folder placement, not whether File Manager has folders or whether
staff can find records. Neither organization option creates disclosure, file
reading, Share, retention, publication, acceptance or disposal permission.

### Practical example

Elena is authorized to organize an equipment-inventory PDF received from Nora
for an ordinary request. She wants to find that **same evidence entry** while
working on **2026 Visit** and while browsing **Equipment**.

With **A**, Elena gives it one home, such as `2026 Visit`, and applies the
approved `Equipment` label or uses an appropriate source/saved view. Opening
that view finds the same entry without creating another folder location.

With **B**, Elena can keep the home in `2026 Visit` and add a clearly identified
reference in `Equipment`. Removing the additional reference removes only that
filing reference. It does not remove the original entry, submitted evidence or
source relationship, and cannot change who may read it.

This is an illustrative task, not an observed Asym workflow, ministry practice
or evidence that staff frequently need two paths.

## Fair A/B comparison and recommendation

| Choice                                               | Useful behavior                                                                                                                                                                                             | Strongest advantage                                                                                                                                  | Real cost or limitation                                                                                                                                                                                                                                                             |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — One home folder or Unfiled; recommended**      | Each admitted evidence entry has at most one ordinary home placement. Existing labels, saved/source views, filters and search can surface it in multiple working contexts without another folder reference. | One understandable filing location and Move operation. Reuses the required discovery model and avoids an extra reference lifecycle.                  | Staff who navigate primarily by folders cannot place the same entry under both trees. They must use a label/view or move the home; arbitrary handpicked groupings may not feel as direct. This cost is not dismissed as user error.                                                 |
| **B — One home plus additional explicit references** | Keep one home folder or Unfiled, with additional non-owning reference entries in other ordinary folders. The UI distinguishes a home from a reference and Remove reference from evidence deletion.          | Fits repeated cross-context folder browsing and allows convenient deliberate groupings without uploading copies or changing the source relationship. | Requires clear Move/Add reference/Remove reference distinctions, stale-target handling, authorized reference metadata and coherent selection/counting. More paths can make location and removal less obvious. None of those costs makes B inherently unsafe if correctly qualified. |

**Recommend A for this increment.** Core already requires labels and views, and
these files have useful source context. A supplies the promised practical
organization while keeping home placement simple. The recommendation is product
judgment under the no-general-drive boundary, not a measured cost saving or a
claim that one location is universally easier.

**The strongest case for B** is staff repeatedly wanting the same entry in
several deliberately curated folder groupings, where label/filter management is
less natural than direct navigation. If that is the intended workflow, B is a
reasonable choice now; it should not be described as duplicated files or a
security violation. Its references must remain non-owning, source-bound and
currently authorized. These are two product alternatives, not tenant modes or
a hidden promise to enable B later automatically.

## Practical boundaries common to either choice

1. **Source-owned entry, not a new document owner.** Operate on the exact
   organizational reference admitted by the ordinary request source. Keep
   independent contributions under a multi-file item separate. A display name,
   byte digest, item ID or provider key alone is not that reference.
2. **Organization authority is real and current.** Reading, uploading,
   reviewing or being an administrator does not automatically confer the source's
   organization capability. Reuse the existing authority system and qualified
   source command; do not ask ordinary staff to invent an owner/retention policy.
   The UI uses permitted metadata rather than forcing a body download.
3. **No new access or lifecycle effect.** Folder placement, labels and references
   do not change acceptance, outstanding work, original participant access,
   Q41 shares, retention/holds, publication or disposal. Source meaning remains
   authoritative after fulfillment, cancellation or other lifecycle changes.
4. **Identity survives organization.** A home move or rename changes organization,
   not bytes, source attribution or existing qualified references. A later
   evidence correction/version is resolved only by the source's declared
   mapping; no global follow-latest, automatic placement inheritance or expanded
   history view is selected.
5. **Metadata is protected too.** Apply current authority before folder paths,
   entry/reference titles, breadcrumbs, labels, suggestions, counts, search
   results, source links and actions. A broader folder audience cannot learn a
   hidden target exists. Do not copy Google's visible-title behavior.
6. **Unfiled is usable.** The choice must not force a folder before otherwise
   lawful contextual intake or strand existing eligible evidence. A home may be
   absent without implying absent source ownership. Removing a filing placement
   is not deleting evidence. Folder-removal/tree repair must have an explicit
   safe owner contract; Q42 does not silently borrow Media's exact behavior.
7. **B references are clearly non-owning.** If selected, Add reference is not
   Move, duplicate upload, another evidence receipt or a new share. Removing an
   extra reference leaves the source entry and home untouched. Reference loops,
   arbitrary URLs and references to references are not required by this choice.
8. **Truthful finite selection.** Apply current per-entry authority and preserve
   the intended finite selection. Multiple visible references cannot silently
   duplicate an effect or collapse independently admitted uses by byte equality.
   Show successes, blocked, failed and not-started entries; do not call partial
   work atomic or retry completed effects as new work.
9. **Recoverable organization.** A failed or ambiguous move must preserve known
   source truth and allow recovery of the actual result. Stale responses or
   concurrent moves cannot silently restore an old location. A corrective move
   is current authorized work, not restoration of old permission or evidence.
10. **Small accessible interaction.** Use the existing shared UI, visible current
    location, clear action labels and a searchable/browsable permitted folder
    chooser. Provide keyboard and single-pointer non-drag operation, touch,
    screen-reader status/focus, zoom/reflow and long/RTL/international names.
    No folder wizard, new approval stage or forced full profile follows.
11. **No new outward event.** Filing does not email Nora, change her request,
    alert a Q41 reader, create a task or select an organization-notice default.
    Staff can see the truthful result in the current native work surface.
12. **Bounded owner adoption.** Source reference/correction rules, scope and
    authorization, safe tree operations, finite hierarchy/selection budgets and
    native proof must be qualified before activation. Do not infer runtime
    readiness, unlimited depth, zero cost or a general folder/graph platform from
    this question. Existing owner-specific organization continues independently.

## Proof expected after a selection

The selected choice should be adversarially reviewed before ratification. That
later review must bind concrete source organization commands and test at least:

1. Exact evidence-entry identity for multiple contributions, equal bytes/names
   and separate uses; no universal document merge or whole-item mutation.
2. Actual organizer capability and target/source/folder authority before every
   result and effect, including legitimate administration without body Read.
3. Stable move/rename and declared version/correction behavior; preserved
   source relationships, Q41 terms and other owners' meanings.
4. Protected folder/reference metadata, cross-tenant rejection and current
   authority across chooser, counts, search, pagination, caching and late results.
5. Unfiled, placement removal, safe folder-tree repair and source withdrawal
   with no evidence deletion, permission or retention side effect.
6. Matching command recovery, concurrent/stale changes, finite batches and
   per-entry outcomes. Under B, prove duplicate references do not duplicate an
   effect or collapse genuinely independent uses.
7. Complete staff/source/participant/reader/admin journeys, with no new
   notification purpose or enrollment path.
8. Composed keyboard/non-drag pointer/mobile/AT/zoom/localization/slow-network
   behavior and understandable Move versus Add/Remove reference semantics.
9. Actual role/database/storage and source compatibility, bounded operation
   budgets and rollout/restore without treating document research as native proof.

No blanket confirmation modal, required reason essay, taxonomy governance
workflow, body index, automatic duplicate matcher or new folder permission
engine is necessary to present this decision. Exact operational limits and
owner-safe tree behavior are qualification work, not vendor defaults to copy.

## Suggested next decision

The ordinary **Q23 Request changes recipient-email choice** is genuinely unresolved and is a useful next fork. The recipient already needs current safe guidance in the request; the question is whether staff's new deliberate review outcome should initially include an optional qualified email notice, or leave that same option initially off.

Recommend a fair comparison within the **same existing meaningful review**:

| Option                                                            | Behavior                                                                                                                                                                       | Benefit                                                                                                                                                                                                                                    | Cost and boundary                                                                                                                                                                                                         |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A — Visible optional Email recipient, initially on when qualified | For each genuinely new ordinary Request changes decision, initialize the qualified email choice selected. Staff can turn it off before committing that decision.               | Helps convey an action-needed outcome without requiring the participant to repeatedly check the request or staff to remember a separate send step. Reuses the same simple control pattern as Q20, while retaining separate source meaning. | Preselection can produce unwanted outward mail if overlooked; the recipient, consequence and current choice must be clear. It is never a Delivery Plan override, permission grant, reminder program or proof of delivery. |
| B — Same visible option, initially off                            | Staff explicitly opts into the qualified recipient email while recording Request changes. Without selection, the source outcome and permitted in-request guidance still exist. | Avoids unnoticed outward communication and preserves deliberate sender choice. No additional screen is necessary.                                                                                                                          | A useful notice can be omitted; the participant may not learn of the next action promptly. The source outcome remains valid and its clock does not pause because email was not chosen.                                    |

I lean A for an ordinary outcome intended to prompt the recipient to act, **only when the exact source/actor/recipient/message/plan/channel path permits it**. This is product judgment, not evidence that all ministries prefer email, that preselection is universally better or that notices guarantee completion. Q20's selected default is a useful interaction precedent, not authorization to extend its policy automatically.

Do not weaken B into a compulsory separate post-decision sending workflow. Both options can offer one deliberate review action with a visible email choice and later governed recovery where available. “Always send without staff control” or “build a new inbox” is unnecessary additional scope.

### Defaults and failures belong to this financial domain

### Existing dedupe identity is not the native review-cycle identity

At `approval-notifications.ts:653,661`, notice keys use financial correction request ID, outcome (`approved`/`rejected`), channel and requester. That fits this financial subject's decision shape, but is not a general repeated document-review identity.

A native item can legitimately receive a new corrected submission and a later new Request changes decision under Q23. Keying all such notices solely by item/request plus the label changes_requested could suppress that later legitimate notice; using a random retry key could duplicate the earlier one. The native producer needs the **exact committed review occurrence and intended recipient/purpose**, preserving replay versus genuinely new review. This is a concrete copying hazard, not an assertion that the financial key is defective for its own domain.

## Essential constraints to carry into the question

1. **One new review occurrence, one deliberate choice.** Compare defaults only for a genuinely new ordinary Request changes action. Preserve the selected value through validation/recovery; replay must not add email to a committed review-only occurrence, and a later new substantive review must not be suppressed as the same old notice.
2. **Source outcome and notice outcome differ.** Review, current in-request guidance and history remain authoritative even if email later fails, is suppressed or becomes uncertain. A chosen combined intent must not silently downgrade before admission; where lawful, a deliberate review-only choice remains available. Do not call a blocked/unknown requested notice “not requested” or provider acceptance “read.”
3. **No permission or plan override.** The checkbox cannot enable a non-Live message, override source/current recipient or channel restrictions, edit a tenant plan or acquire arbitrary communication rights. Default-on only makes sense for a currently qualified option. Required specialist notices, if any, remain under their own contracts.
4. **Current applicability at dispatch and use.** A correction, acceptance, fulfillment, expiry, revocation, recipient change or later guidance revision can make old upload instructions false. The producer must use its exact qualified applicability/variant rules or stop dispatch, without rewriting an immutable prepared message into another purpose. Existing access clocks and source decisions never reset. Already accepted external delivery cannot be promised recall.
5. **Recipient identity is exact.** Use the source's current permitted intended recipient/contact and Q01 closed identity/action contract. Do not equate the issuing staff member, financial requestedByProfileId, uploader profile, common email or reviewer team with the intended recipient. Do not force a new donor/Party account merely to reuse the old sender.
6. **Minimal safe notice.** Point to the current qualified request/action through the established doorway; do not include private files, direct storage URLs, internal reasons, unrelated guidance or a general text reply/composer by default. A notice never promises that the recipient currently has correction authority when access has ended. Any useful neutral variant still needs source/P17 qualification.
7. **Reuse P6/P17 durability.** Source effect, chosen condition and required handoff must be durably coherent. Exact release includes zero-member results; compilation/lookup failure is not a valid empty plan. Preserve permanent business identity beyond provider dedupe windows; safe recovery of selected intent is not a new review, grant or message blast.
8. **Keep the fork narrow.** No acceptance/completion notice, periodic reminder, escalation, staff alert, initial-invitation/proof default, other channel, roster, notification center or new sending system is selected. The choice does not automatically authorize old historical returns to be emailed after rollout.

These are inherited/source qualification boundaries and foreseeable implications, not a completed selected-answer review or proposal to ask each as another founder question.

## Priority against other open questions

This fork is a strong next dependency because Q23 creates a recipient next action and already requires in-request guidance, while explicitly reserving notification. It can be decided in one useful A/B choice without changing correction, acceptance, assignment or issuance.

Initial-invitation/proof messaging remains a distinct source topic; Q01 defines protected entry and Q25 defines the first-issuance gate without selecting a new general notification default. Do not pretend Q26 resolves that policy. No inspected runtime dependency requires deciding its default before this bounded review-outcome choice, provided the protected doorway and exact message consumer remain qualification gates.

A new recipient text-only clarification channel or general feedback conversation could be useful, but would add a different action/data scope and is not necessary to decide whether to notify about the already-selected Request changes outcome. Detailed periodic reminder/accepted/completed messaging should remain separate. Mandatory standalone send after every return is a weaker alternative than default-off opt-in in the same review, because it adds ceremony without a distinct source decision.

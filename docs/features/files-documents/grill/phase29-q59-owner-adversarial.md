## Outcome and strongest simpler alternative

Keep one private personal reference to a P28 organization-resource publication. The same qualified native human has one list inside the exact Tenant/environment/source organization, even when that person can act in different qualified staff or missionary contexts. Content is always projected through the selected current context alone. Saving does not combine grants or copy content. A separate narrow own-preference purpose permits safe maintenance of a neutral saved entry when content has become unavailable, without preserving its title, link or hidden reason. Removing the entry is always a preference operation, never deletion of the resource.

The strongest B remains required, well-designed search/categories/navigation plus permitted stable links, with no persistent saved list. B avoids private state, ordering, retention and permission-loss costs. A is a modest return convenience, not demonstrated demand: no Asym repeat-visit frequency, time saving, conversion gain or cost-neutrality measurement exists. The user's selection settles the capability; it does not justify a folder platform, favorites ranking, custom names/tags, notifications, an offline queue or a new permission console.

The material corrections to the researched question are concrete: qualify the native person mapping instead of assuming a profile or inert persons row; explicitly adopt own-preference rights separate from resource rights; settle neutral unavailable versus transient unknown; retain a private reference across recoverable source loss without resurrecting an intentionally removed one; make Save/Remove an ordered desired-state command rather than a blind toggle; and prevent an acknowledged same-state Remove from leaving an older delayed Save free to recreate it. No new glossary entity is needed.

## Exact proposed decision — sixteen clauses

**Q59-O01 — Narrow personal return capability.** Add optional Save for later, Remove from saved and a private Saved for later destination within the existing P28 organization-resource reader experience for the exact qualified staff and missionary cohorts. Retain complete ordinary search/categories/language/navigation and direct source Open/Download. Saving is an explicit personal return preference only: it grants no content, publication, curation, Support, report-handling, review, subscription, assignment, acknowledgment, completion, communication or audience power. Do not add named collections, folders/tags, shared lists, recommendations, reminders, offline content or a general cross-product bookmark store. This explicitly adopts a narrow new source purpose; it is not inferred from a role, library access or an adjacent preference API.

**Q59-O02 — One qualified owner and exact scope.** The active personal relationship is unique for the stable qualified native human/principal owner, exact Tenant, environment, actual existing source organization and exact resource publication identity. Use the existing organization identity; do not manufacture a duplicate Tenant/Party/organization row or require the inert persons anchor. The same person can see the same preference from different independently qualified contexts within this scope, but every request has exactly one validated current source/P12 context and never unions other hats' grants. Context or credential changes cannot copy preferences to another person, Tenant, environment or organization. Email/name equality or an unqualified profile merge proves nothing. Any native identity continuity migration must use the actual identity owner's qualified mapping, preserve restrictions and never transfer lists casually to a successor employee.

**Q59-O03 — Source publication reference, not a snapshot.** Store only the private preference facts and exact protected source reference needed for current return; do not retain resource titles, URLs, thumbnails, body text or downloaded bytes as a saved-content snapshot. The reference follows the same publication's current qualified head under P28/Q58. A separate publication, language/audience edition, copied file or distinct successor stays separate, even if names/bytes match. Existing source-permitted successor guidance may be offered without automatically changing the saved target or granting access. A deliberate new Save is required for the separate publication. Open and Download always use the actual current source destination and permission; Save/list must not prefetch bodies, mint download links, contact an external site or record that a resource was read.

**Q59-O04 — Separate Save and own-preference purposes.** Register compatible current source/P12 powers and shared static classification for Save and own-preference read/remove before exposing the feature. A new Save requires a currently published, currently discoverable permitted publication in the selected resource-reader context, plus the exact own-save permission. It does not require opening/downloading the file or a successful body transfer; genuine technical body failure is not proof of ineligibility. The separate own-preference maintenance purpose may expose only the person's permitted preference identity, saved time/state and removal control while that person has current qualified native organization participation and purpose authority. Participation/row ownership alone is insufficient. Current purpose, classification, restricted-person, residency and account floors apply to preference facts too. No ordinary staff, curator, manager, coach, NHI or administrator can browse another person's list merely by role or resource ownership; real audited privacy/security/records powers remain independently scoped.

**Q59-O05 — Calm complete interaction.** Use one plainly labelled Save for later/Remove from saved action and a discoverable private Saved for later destination in Resources. The reader supplies no collection name, folder, reason or extra confirmation. Open stays distinct and primary. The saved list uses newest actual Save first with a stable unique reference tie-breaker; repeat Save does not refresh the saved time or reorder it. Remove then a fresh qualified Save creates a new current personal occurrence with a trusted new saved time, not revival of the old action. Server evidence records a feasible trusted time in the committing operation, not a client clock or an impossible future commit timestamp. Empty, loading, load failure, mutation failure and unknown outcome remain visibly different; Browse resources is the ordinary empty-list route. No arbitrary new maximum copied from vendor favorites is imposed.

**Q59-O06 — Current coherent Save.** A deliberate Save resolves its exact publication identity and own-preference state under trusted current scope, source eligibility and the relevant reviewed control basis at the actual admission boundary, including after waits. It commits one coherent preference/control/result effect, or none. An unrelated metadata edit need not invalidate a save to the same still-eligible publication; a changed relevant owner/context/source/purpose or control basis cannot silently retarget it. Same-state Save can acknowledge Already saved without duplicate membership, changed saved time or resource effect, but must participate in the ordering fence below when needed to reject an older opposite action. A current permission/source failure leaves the existing lawful preference unchanged and never fabricates success.

**Q59-O07 — Remove and accidental-removal recovery.** Remove changes only the exact current owner's saved preference under its maintenance purpose; it does not withdraw/delete/hold the resource, mutate another user's list or require current resource bytes/title. A lawful neutral row can therefore be removed when its content is unavailable. No confirmation or typed reason is required for this reversible convenience. After an accidental Remove, the permanent ordinary remedy is a fresh Save of the same currently eligible publication through Resources. If an optional Undo affordance is used, it invokes that same freshly qualified Save, not an old command replay or hidden historical grant. There is no mandatory trash, restore-history screen, timed Undo policy or new source-copy mechanism. A resource that is currently unavailable cannot be resaved merely because the person once saved it.

**Q59-O08 — Known unavailable and unknown are different.** A retained own preference may display a neutral Unavailable resource entry, its own saved time and Remove only when the current maintenance projection independently permits those facts. It must disclose no old/current resource title, URL, thumbnail, body, internal reference or reason such as audience removal, classification, deletion or another hat's permission. Known absence and known denial must not be distinguished through that resource lookup. A transient failed/unknown source or authorization evaluation is not known loss, unsaved state or complete empty: retain the preference, show a safe Could not check this saved resource/Retry state where the own relation is lawful, and withhold resource fields. If own-preference authority itself is unresolved or denied, withhold that list/entry too rather than treating a neutral placeholder as a floor exemption. Source failure cannot block independently lawful own Remove; own-purpose failure must block it without false success.

**Q59-O09 — Return, reappearance and offboarding.** Publication withdrawal/audience removal/restriction stops resource projection and new serving through every saved path. It does not automatically delete the user's private intent or create a special content retention right. If the exact same publication later becomes currently permitted again, a still-retained saved preference can show it again after fresh source/P12 checks; this is current access, not restoration of an old grant. A removed preference remains removed. Separate successors are never substituted. Loss of current native account or organization-purpose authority fences the whole list immediately; stale JWT/profile or a remaining database row is not fallback authority. Retained preferences are not transferred to managers/new staff. A lawful return by the same verified principal can expose only still-retained preferences under current authority; an account recreated with the same email gets no old list by inference.

**Q59-O10 — Ordered intent, replay and no-op safety.** Use explicit desired-state Save/Remove commands and an existing source-owned operation boundary, not a blind toggle. Resolve a matching original operation result first under exact trusted identity/scope and full canonical intent, then apply current disclosure rules; replay does not create another save, redate, reorder, remove or advance control state. New conflicting/stale intents do not silently rebase. A newly acknowledged same-state command must still fence an older opposite intent where necessary: absent-state Remove cannot leave an older r0 Save eligible to recreate it, and present-state Save cannot leave an older r0 Remove eligible to erase it. Minimal relevant control ordering is allowed even when visible membership does not change; it is not a new business-history event or another domain entity. Preserve ABA distinction and actual identity after Remove/re-add. Within one UI, reconcile an uncertain original action before issuing its opposite; different devices remain protected at the source. Retain bounded minimal replay/control evidence or reject unverifiable stale commands after readable/result retention expires, so deletion, restart or backup restore cannot make an old key a fresh action.

**Q59-O11 — One authorization boundary and every door.** Save/list/remove/result recovery and all resource metadata/byte doors use the same current P12 producer, exact unified Tenant context and shared static field classification/subtract-only projection. Personal owner checks belong to the qualified source/PDP, while the database retains P12-prescribed coarse Tenant RLS; do not introduce fine-grained capability logic in a competing SQL policy engine. Prove actual effective grants, schemas, named/PUBLIC/default/inherited EXECUTE, invoker/definer composition, safe search paths, trigger/alternate writers, old and resulting row scopes and effective ENABLE/FORCE/owner/BYPASS/service roles. INSERT, SELECT, UPDATE, DELETE, UPSERT/MERGE and RETURNING must not permit reparenting, forged ownership, broad preference reads or direct UI-bypass mutations. Existing permissive policies can widen exposure; adding one own-row policy or a FORCE flag is not proof. No raw localStorage/sessionStorage or unpartitioned persisted client query cache may retain protected saved titles/URLs across users/contexts. Fence late results and invalidate or withhold stale projections at current revocation; already delivered bytes are not recalled.

**Q59-O12 — Downstream invariants and private meaning.** Saving does not alter Q55 current review applicability/date/history, Q57 reports/own return/handling, Q58 audiences/content/lifecycle, Support D27-C guides, ordinary evidence views or the source's content version. It produces no P6/P17 notification, coach disclosure, popularity score, manager readership evidence or training completion. Optional independent resource actions still require their own gates. The personal reference is not a custody use that blocks legitimate deletion, retention expiry or source withdrawal; it must not preserve file bytes or dangling content credentials. A retained neutral preference is private convenience evidence, not proof that the resource still exists or was read.

**Q59-O13 — Retention, privacy remedy and restore.** Keep active saved preferences while their legitimate personal purpose remains and until the owner removes them or actual source/account/privacy retention requires disposal; do not expire them arbitrarily with a resource review date or copy a notification retention window. This is not a permanent-content guarantee. Before activation, bind the preference and minimal control/result evidence to the existing explicit source retention/disposal schedule, including bounded offboarding and exceptional holds; do not invent an automatic indefinite archive or a calendar product. Governed export/erasure may include only currently lawful own preference facts, not withheld resource labels/bytes. Required restricted security evidence remains separately scheduled. Provide an actual scoped operator/privacy cleanup route when self-service is unavailable, without blanket administrative list inspection or raw SQL as the routine remedy. Restore/reconciliation must apply complete later removal, identity, authority, restriction and disposal evidence before release; an old snapshot cannot recreate removed saves or restore obsolete content rights. Confirmed purged facts are not reconstructed from titles/emails or unqualified logs.

**Q59-O14 — Accessible, resilient return UX.** Use Core components/tokens and clear action or pressed-state semantics, with keyboard/touch/screen-reader, 320-CSS-pixel reflow, zoom, RTL and long translated names. No hover-only icon, color-only Saved state, unexpected focus movement or routine modal. A successful removal from the list moves focus predictably to the adjacent entry or empty-state action and announces the result; failure/unknown preserves a usable, honestly labelled row. Maintain safe source search/filter return position. Optimistic pending display must not masquerade as confirmed persistence, silently roll back a newer action or apply a response after identity/context change. A known-failed save offers retry without trapping ordinary reading; list lookup failure has Retry rather than false empty. Own unavailable-entry cleanup remains usable without first opening forbidden content.

**Q59-O15 — Bounded and operable, without a new platform.** Use bounded paginated own-preference reads, set-wise current source projection, stable keyset identity and source-qualified indexes; avoid whole-library scans, per-item network authorization/body fetch/signing and member fanout. Apply the actual P12 R6 logical governance budget and relevant P28 C49 resource thresholds. Declare and measure finite page/payload/operation/lock/retry/retention/cleanup limits before native activation; capacity failure is explicit and never silently evicts old saved entries, reduces upload/content allowances or returns truncated data as complete. Scope diagnostics to safe cause codes and bounded counters, without names/URLs/hidden source IDs, relationship-interest analytics or a new dashboard. Bind each operating signal to a threshold, accountable owner and concrete response. No mandatory Realtime, worker, third-party service, universal favorites table or general synchronization engine is selected.

**Q59-O16 — Adoption, qualification and stage.** Register the narrow P28 personal-save/own-maintenance source contract, its static fields and actual native owner mapping through the existing P12/data-access boundaries. Both cohorts require positive and negative qualification; do not fabricate Party/person/roles or auto-import donor bookmarks, P23 views, browser history or old localStorage. Source-first additive rollout must fence incompatible alternate writers/readers and preserve restriction-first restore and existing required library access. Prove all category/journey/native cases below with actual effective roles/grants/source serving, concurrency, currentness, retention/restore, browser/AT and intended-user workload before activation. No conceptual model or documented vendor pattern substitutes for native evidence. Save for later, Remove from saved and Saved for later are UI names; personal saved reference is sufficiently defined here without a new glossary entity. Existing root definitions and all 32 Files terms remain unchanged. Record Q59 A with these required amendments pending full ratification; no Q60, formal /to-prd or /to-issues publication, implementation or hosted change follows.

## Seven founder questions, answered

### What could go wrong with this answer?

Saved can imply content permanence, leak prior titles, become a hidden interest list, or be undone by delayed opposite commands. They do not pretend that a star icon is safe persistence.

That some readers revisit guidance and benefit from a private list, and that the native identity/source boundary can qualify one same-person list across contexts. We assume no universal device/offline support.

It adds one personal P28 preference purpose without changing publication, content, review/report, Support, ordinary documents, donor identity or communications. The global identity/currentness floors still apply. A new private relationship must have actual retention/cleanup/restore proof, but it need not become a cross-product bookmark platform.

The ordinary flow is Save once, return through Saved for later, Remove when no longer useful. A neutral own entry can be removed after resource loss without revealing the hidden material. Unknown outcomes remain recoverable. A same-person context change does not require duplicate lists, but resource visibility never borrows the other context's grants. There is no mandatory name, read ritual or extra confirmation.

It uses documented personal-return patterns, clear action/state semantics and native current authorization.

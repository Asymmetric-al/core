## 1. Recommended complete product

Keep the useful choice small: **Correct acceptance** is a deliberate source action on one exact eligible acceptance while the ordinary request is unfinished. It preserves the receipt and original decision and returns the affected item to actual **staff review**. It does not automatically ask the recipient for another file, revive old Request changes text, erase a previous reviewer, or reopen a completed request.

After actual fulfillment or other terminal closure, offer **Record acceptance error** under the appropriate current source authority. That records the error/current-reliance consequence while preserving the original acceptance and F. Where actual work remains, a guided **Prepare corrective request** route must continue through genuine independently authorized issuance for the same intended recipient and only that work. A draft is not a completed remedy. Urgent actual source/privacy restriction is independent and does not wait for a new request.

There are three distinct outcomes users must understand: the original acceptance happened; the source now records that it was mistaken or no longer applicable for the asserted error; and the source determines what current work remains. These are not one mutable green badge. A later changed requirement or a harmless record-description typo is not necessarily an erroneous acceptance and must not trigger unnecessary recollection.

The strongest B remains guided separate corrective work every time, with the same truthful error recording and safe evidence reuse. That offers a uniform new-work boundary but can move a healthy unfinished collection for one mistake. A is proportionate because it keeps local work together until the real terminal boundary. No measured Asym mistake frequency, time saving or user preference establishes superiority; this is evidence-informed product judgment.

## Adversarial check

### What could go wrong with this answer?

An implementation could copy a vendor toggle, rewrite historical acceptance/F, revive old recipient access, or treat correction as rejection and demand another file. Terminal errors could still lead to powerless Help. Required amendments specify real current truth, actual staff review and actual record-error/prepare/issue/operator remedies, with both source race orders and original-operation recovery.

### What hidden assumptions are we making?

Mistaken acceptance is a plausible recovery need, but no Asym frequency, workload or user study was measured. Current source authority, safe target identification, retained sufficient evidence and a legitimate corrective purpose must actually exist. Same bytes and an old Accepted badge are not those facts. A coherent source transaction and inherited components remain proof obligations.

### How does this affect the whole product?

It fills the ordinary review remedy without turning custody, comments, task status or source-general metadata into approval authority. Existing specialist/financial/public outcomes remain owned. Current review, access, notice and retention dependencies require explicit source adoption; no receipt replay or universal compensation follows.

### How does this affect the end-user experience?

The staff action has one exact target and understandable consequence. Good submissions and unrelated accepted work survive. Recipients see actual current work without blame or false missing status. Completed cases have a real correction and, only where needed, actual new work. Weak-network mistakes preserve original outcomes and safe context instead of multiplying requests.

### Does this follow modern best practices?

Current primary collection products document contextual reversal; broader submission products distinguish receipt and final review outcomes. Their semantics are not Core authority. W3C supports meaningful error prevention and accessible status/input behavior, not a compulsory extra confirmation ritual. Human task/accessibility qualification is still required; no universal or measured benefit claim is made.

### Does this fit Asym's existing repo and product direction?

Yes as explicit source adoption. Q21/Q22/Q23 preserve original decisions/current applicability/F and Q52 requires a capable remedy without granting Undo. The selected ordinary command must live with that source/P12/native boundary, use existing review/issuance/communication owners and preserve exact custody. GEN-06/UI/source scaffolding is not activated proof; current public-read hardening does not implement this act.

### Should we adjust the recommendation?

Retain A with the exact amendments. Return eligible unfinished work to staff review, retain a real terminal error/corrective-work path, and keep B's separate-work option as honest counterevidence. Do not add a new workflow engine, universal Undo, forced resupply or automatic notification. Material owner/runtime refinements must be reconciled before whole-package closure; Q60 remains selected pending full ratification.

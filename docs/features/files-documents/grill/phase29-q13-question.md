**Status:** Historical researched question prepared 2026-10-21, Asia/Bangkok.
Conrad selected A and ratified its complete required amendment package on

## Historical question and alternatives

**When ordinary unfinished access has expired but the request itself is still
unfinished and otherwise eligible, should properly authorized staff be able to
approve fresh, finite access to finish that same request?**

| Option                                                             | Behavior                                                                                                                                                                                                                                                                                                                                         | Practical tradeoff                                                                                                                                                                                                      |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Allow fresh staff-approved unfinished access (recommended)** | Make a distinct, prospective source decision for the same recipient and still-needed work in the same request. Preserve its earlier access history and received work. If the source subsequently completes while this fresh authority is valid, permit the separately bounded Q07 read-only stage under an explicit prospective owner amendment. | Avoids making someone restart legitimate work solely because access time elapsed. Requires a qualified issuance command, current permission checks and safe handling of races; approval is not automatic or guaranteed. |
| **B — Keep expiry final for this unfinished request**              | Do not issue fresh unfinished access to this request. Preserve received work and independently permitted source review/completion; provide an owned help route and use only genuinely authorized distinct source procedures where appropriate.                                                                                                   | Simpler and avoids another access-granting command. A recipient cannot finish remaining work in this request after expiry; help may be unable to resolve that need without a separately legitimate source process.      |

B does not require duplicating the request, re-uploading already received files,
emailing private attachments or changing dates in the database. Those are not
safe substitutes for a governed capability. A is not an automatic extension,
renewed sixty-day allowance, recipient self-renewal or reopening completed work.

## Why this question comes next

Q12 now fixes the ordinary initial profile at up to 1,440 elapsed hours from
qualified original issuance. Q10 permits independent source work to continue
after recipient access expires; expiry is not cancellation or rejection.
Therefore a still-unfinished request can have genuine outstanding work while
its original recipient access has ended.

Q08 covers fresh read access following an eligible completed-view expiry.
It deliberately did not authorize unfinished intake recovery. Extending Q08's
read-only permission would be an undeclared new capability. Choosing a recovery
duration first would wrongly assume that this capability is wanted at all.

The strongest simpler alternative is B, not an automatic reset disguised as a
new request. Both options preserve the purposeful Asym file model: exact work
needed by a source process, not a personal file repository.

## Recommendation and evidence limits

Recommend A. A controlled way to finish the same legitimate work is preferable
to a dead end or duplicate records when only ordinary access time has elapsed.
This is a product judgment supported by recoverable workflow patterns, not a
verified estimate of how frequently ministries need it. No representative Asym
recipient/staff recovery study or measured expiry-support rate is available.

The real cost of A is new authorization behavior. File read permission, a
reviewer role, support access, membership or possession of an old link cannot
stand in for the exact source issuance/administration capability and P12's
current scope and assignable ceiling. If those checks cannot be made reliable,
the capability must not activate; an attractive screen is insufficient.

## Exact boundaries proposed with A

1. **A new prospective admission, preserving the old one.** Prove the original
   lawful admission and ordinary unfinished expiry. The original issuance,
   deadline, receipt facts and history remain unchanged. New permission begins
   only through its own qualified source act; nothing authorizes the gap.
   Reauthentication, resending, returning to the page and retrying are not
   new permission. Recover an uncertain prior effect before trying to issue
   another one.
2. **The same still-unfinished purpose and intended recipient.** Limit scope
   to originally admitted request requirements intersected with current
   eligibility. This permits first submissions and exact Q03 correction
   successors for eligible pending requirements, rather than freezing scope
   to file IDs that existed before expiry. Accepted/frozen items remain so.
   New recipients, requirements or purposes use their actual owner procedures;
   no changed email address or copied request silently inherits authority.
3. **Elapsed time is the reason for this lane.** It cannot override revocation,
   cancellation, a genuine overall/purpose cap, disposal, an applicable intake
   prohibition or another current restriction. Nor may it bypass a genuine
   earlier binding shortening or reclassify an adverse ending as ordinary
   expiry merely because its cause was later removed. A preservation hold does not
   itself grant access, and its exact restrictions remain binding. Proof or
   policy unavailability is not proof of ordinary expiry; remain closed for
   protected actions and give a truthful recovery status.
4. **Completion has an explicit prospective consequence.** A would amend Q10
   for this exact new continuation lane: if fresh unfinished authority exists
   in the source causal order at eligible normal fulfillment, fulfillment
   stops writes and may admit Q07's at-most-720-hour completed reading from
   that fulfillment occurrence, under genuine applicable caps/current checks.
   The fresh unfinished-only end does not also become an overall end. Early
   completion may yield an earlier final read end. No completed clock starts
   at approval, first entry or observation. No completion in the access gap or
   before fresh admission receives retroactive recipient eligibility.
5. **One coherent source decision, not a generic override.** Recheck issuer,
   recipient, purpose, requirement state and current restrictions at the
   authoritative mutation boundary, including after waits. Serialize against
   completion, correction and adverse changes; retain attributable original
   intent/outcome for replay. A lost response is not failure, and closing a
   dialog after dispatch is not cancellation. No provider call under source
   locks or second permission platform follows.
6. **A bounded capability whose remaining policy must be chosen.** Fresh
   duration/anchor, unused-admission bounds and repetition/overlap rules remain
   separate founder decisions and mandatory activation gates, as with Q08.
   None is delegated to an implementer's guess. In particular, Q12's sixty
   days does not automatically apply again, and A selects neither unlimited
   repetitions nor a one-time lifetime restriction. No pre-expiry extension,
   editable deadline, automatic message or reminder schedule is included.

The completion consequence in item 4 is a visible part of option A, not a claim
that Q10 already grants it. Ordinary Q10/Q11 historical eligibility remains
unchanged. Q08's original completed-view eligibility is not silently widened:
a later fresh read grant is not authorized merely because a continuation later
completed. Exact lineage/owner mapping would need an explicit compatible
decision before such a further capability could activate.

## UX and accessibility requirements for the proposal

Use the existing source/request screen and exact shared Base UI/base-maia
components. Recipient language should distinguish **access ended** from
**request rejected**, **files deleted**, **upload failed** or **review completed**.
Show known received work only while its disclosure is currently authorized;
otherwise provide a neutral entry/help response without leaking metadata.

Once fresh authority is currently usable and its end is resolved, use plain
language such as:

> You can continue this request. Access while it is unfinished ends
> [date, time and zone].

Commit alone does not prove present usability or a resolved end under the
not-yet-selected activation policy. Until those facts are established, show
the approved timing terms, known cutoff and truthful current state instead.

Display Requested by independently. Show the meaningful next action, including
waiting for staff when nothing more is needed. On completion, explain the
read-only change and exact end instead of calling every transition an
extension. On a technical failure, state whether an outcome is known, unknown
or recoverable; do not substitute an expiry message.

Keep one meaningful staff review of recipient/scope/timing, with refreshed
review if material terms change. Do not add a second routine confirmation or
force the staff issuer to read private file contents. Current recipient proof
must remain usable with keyboard, screen reader, autofill/paste and mobile.
Preserve entered work only under its actual secure custody/retention rules;
no new browser storage of private files, endless waiting spinner or automatic
retry that issues a second grant. Core's existing authorization flow owns
whether proof can be reused; a fresh admission does not mean mandatory fresh
account enrollment.

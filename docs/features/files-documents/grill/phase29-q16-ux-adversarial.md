# Phase 29 Q16 — one familiar read-access experience, exact historical scope

Review date: **21 October 2026, Asia/Bangkok**. The parent reports Conrad selected **Q16 A: include both valid completed-view routes**, with excellent UX/UI and no overengineering. Q01–Q15 and their full amendments are ratified. **The Q16 amendment package remains unratified.** This is an independent UX/evidence review, not implementation or a later policy choice.

Only this note was written. The Q16 question, Q08 decision, Q16 comparative research and relevant current primary guidance were inspected. No canonical document, UI, runtime, permission, private record, provider or dependency was changed or tested. No browser, assistive-technology or intended-user qualification is claimed.

## Disposition

**Keep A with a small explicit scope refinement and inherited safeguards.** Use the existing **Grant read access** action and completed-request context for both eligible origins. The user need not learn admission-route terminology. The source must still distinguish the actual histories so that a friendly common screen never broadens permission.

The additional route requires a real completed-view admission created when the request was fulfilled during valid fresh unfinished authority, followed by eligible ordinary expiry. Completion after authority had expired, a received file, stored bytes or a generic completed flag is insufficient. No prior visit, successful preview or download is required if the source truly admitted the completed view.

The governing ceiling is the actual completed admission at fulfillment, including its permitted actions/context and exact eligible file membership. It is not the broader original unfinished requirement set or a union of earlier grants. A status/context-only completed admission remains a valid limited origin; it does not acquire file-body rights through this extension.

Q16 expands consideration, not entitlement, timing or repetition. Q08's finite timing/activation/unused and repetition/overlap policy still must be adopted and qualified before activation. Q14's thirty days and Q15's repeat rules are not convenient defaults for this different capability.

## Staff, recipient, reviewer and support journeys

### 1. A completed request needs only existing staff work

Do not add a recipient grant just to let an authorized staff member inspect, process or resolve independently available source work. A valid read-recovery root is an eligibility fact, not a mandate to issue. The real question is whether current recipient access serves a permitted purpose.

The source may decline or lack authority even when a historical root exists. A finite previous view and a familiar recipient do not guarantee later approval. The user-facing help path should explain only the actual safe result and available remedy, without implying staff can bypass the source.

### 2. Authorized staff reviews a genuine later read need

Use the existing completed-request context. Show the intended recipient, source-approved prior outcome and eligible current scope, then the qualified terms and genuine limits. The source resolves whether the valid completed admission came from original or fresh unfinished authority; the actor should not choose a route from a dropdown to make the request eligible.

The action remains **Grant read access**. Its label describes a new permission, not **Reopen request**, **Extend the old link** or **Restore all files**. A compact relevant summary is enough; no new ceremony follows from the extra historical origin. If material scope, recipient, actual policy or source facts change, refresh meaningful review. Ordinary time passing under unchanged terms does not require another confirmation.

The issuer needs Q08's exact current capability and administrative scope. The expired recipient permission does not need to pass its former current-read check in order for the authorized source to make a new decision. Conversely, the ability to read a file, perform support work or send a past email is not the authority to grant it. Review can use permitted metadata without disclosing bodies the issuer cannot read.

### 3. The earlier completed view was never visited

If the source lawfully admitted the completed view and its eligible ordinary expiry is proved, lack of visits, previews, cookies or download logs does not disqualify the recipient. Do not ask the person to prove they opened a past email or show an old screenshot. No special “missed first visit” timer is introduced.

If no actual completed admission existed, the similar looking business outcome is different. The source can remain legitimately complete while this read-recovery lane is unavailable. Explain the safe limit/help outcome; do not rewrite fulfillment, revive unfinished access or invent a prior admission to make the interface consistent.

Historical facts recovered later must use the original qualified evidence and end. A delayed projection or repair date never restarts the old ordinary period. A generic F-plus-duration calculation without the required source admission evidence is not enough.

### 4. The root allows status/context only, or only a narrow file subset

The interface must represent the access actually granted. A status/context-only root can support a useful completed view without a file grid, download CTA or statement that no files were ever submitted. Where disclosure permits, a compact scope explanation such as **This access covers the request status and permitted submission history** can be more useful than an empty folder.

If the actual completed admission contained only file A, a new read grant cannot include B merely because B was requested, uploaded or retained earlier. A wider role held by the issuer is not permission to exceed this capability's historical ceiling. The source checks each current action; a preview right is not a download right, and a download right is not permission to email the original elsewhere.

Do not expose withheld file names, counts, actor details or dates merely to explain a narrower view. Current authorized status can remain available while a separately permitted file representation is temporarily unavailable. A valid empty/status-only scope, a failed lookup and a denied/disposed file are different facts.

### 5. A grant is considered or recorded, but timing/readiness is unresolved

There are two distinct situations. First, **the standard Q08 policy itself has not been adopted/qualified**: actual issuance remains gated; a friendly pending label cannot create permission while a duration or repetition rule is invented later. This is presently a design/activation dependency, not a new recipient queue or onboarding screen.

Second, a future **fully adopted finite profile** may have its own legitimately unresolved working-end state before its selected anchor. Q16 does not choose or prohibit such a profile. Follow Q08's qualified terms/known-cutoff requirements and show the exact end only when that profile establishes it. Do not copy Q14's issuance-resolved end requirement into Q08 by analogy.

Operation result, current source permission, recipient proof, available representation and separately authorized notification remain separate. A source-approved result is not necessarily **You can read now**. It is never **You have another thirty days** merely because the prior ordinary view had a thirty-day maximum.

### 6. The recipient returns to currently usable reading

Use Q01's existing qualified doorway and compatible proof rules. Once current use is established, show the completed status, actual applicable terms/end and permitted actions in main content. The person need not know which work period preceded completion.

The visible context stays completed/read-only. Preserve Q04's explicit original-download semantics, Q02's qualified preview, and Q05's concise authorized history independently. Do not add upload/correction actions, force a download as an activation event, or show all historical file versions.

A new device, repeat visit or proof refresh does not reset the adopted grant terms. The selected Q16 scope rule does not promise automatic notifications or self-service renewal. Prior lawful nonuse is not a reason for extra forms or a new full account.

### 7. Proof, representation, network or source observation fails

Repair the actual failed mechanism when current authority remains valid. A failed preview is not source expiry. Regenerating a qualified representation of the same admitted original must retain exact source/version/current permission; a new original, replacement submission, assembled export or accessible equivalent does not automatically inherit the original's rights merely because it is easier to render.

Preserve independently authorized work when only a nonauthorizing subview fails. If the authority or required historical scope cannot be established, close the affected protected action and offer the real safe recovery/help. Do not display **No files**, **Request rejected** or **Access expired** as a catch-all technical error.

On an unknown grant result, reconcile the same deliberate source effect. A lost response, post-commit observation error or failed notification is not proof that no admission exists. Recovering an old success preserves that original result and reports current access separately; it never substitutes the latest grant as the result of the old action or overwrites the current view with stale terms.

### 8. Support helps after expiry, restriction or an unavailable origin

Support first distinguishes lost proof/link, genuinely ordinarily expired completed permission, missing provenance and a real source prohibition. The same understandable help route may serve both origins, but actual available remedies depend on current authority. A familiar screen does not guarantee the same allowed files or outcome.

No support-only clone, attachment email, grant date edit, reopened intake or changed route label can recover an excluded first-ever view or bypass adverse history. Existing independently authorized specialist rights remain on their own terms; Q16 does not invent them or remove them.

If policy or qualification is missing, repair that through its owner before enabling issuance. If trustworthy evidence is missing, do not promise a successful grant or fabricate an ordinary rejection. Retention/holds/disposal remain source-owned; inability to recover rights does not mean the data has been deleted, and retained bytes do not justify new access.

## Accessibility and least-friction boundaries

Use the same existing Base UI/base-maia components and semantic tokens. Repeated Grant read access controls should be recognizably consistent; context can change the permitted scope without changing the underlying meaning. WCAG consistent identification does not require equal authority or identical wording for unlike functions.

Keep current status, terms/end and available actions in main content, with history secondary. Preserve keyboard order/focus after recovery, meaningful screen-reader status updates, touch target/reflow support, long translations and precise localized time/zone display. Essential explanations cannot rely only on disabled-button hover, color, a countdown or a toast.

Retain Q01's accessible proof/paste/autofill mechanisms and source-required assurance. Do not add manual transcription or a full signup because the historical origin changed. Short proof/session/upload timers still require their own applicable assessment; an eventual longer business grant does not establish that assessment.

An accessible viewer frame is not proof of accessible document contents. Existing qualified text/semantics and supported formats must be preserved; no image-only conversion, automatic OCR, office editing or substitute-document promise is introduced. Downloads remain explicit and current-version authorized, and browser handoff is not proof the file was saved.

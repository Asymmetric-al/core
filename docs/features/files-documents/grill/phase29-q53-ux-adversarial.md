## Disposition and smallest complete experience

**Accept with required amendments.** Authorized staff should be able to supply a new local file to an eligible ordinary requested item under their own identity. The meaningful outcome is a new staff-attributed source contribution, not a file in a general library and not a recipient submission performed by proxy. Keep recipient upload and Q28 Add existing file available. Keep genuine personal statements and specialist requirements intact.

The smallest complete interaction is contextual **Upload file**, a visible selection and actual item/recipient/purpose, then one deliberate **Upload and add** action. That act may authorize qualified transfer and finalization without a routine second confirmation or second completion click. If the already-reviewed meaning becomes materially invalid, stop or recover under the source rules; do not silently substitute a different item, recipient, requirement or file. The uploader does not need a new settings wizard, generic workflow, mandatory reason essay, preview-click ritual or extra approver.

The hardest UX requirement is honest state. Local selection, private transfer, verified custody, target admission, technical checking, readable inspection, human acceptance and request fulfillment are different facts. Present only the distinctions needed for the next action, but never collapse them into a false Uploaded/Done/Accepted badge. A lost response must recover the original operation rather than invite a duplicate contribution. A mistake after admission needs an actual source remedy, not a transient toast or a claim that an X icon erases all copies.

The strongest B alternative remains recipient-origin upload for new files, with Q28 reuse and coordination intact. It offers fewer staff-intake paths and clearer personal agency, particularly when an actual source statement or present intent matters. A adds upload/recovery/security work and permits staff selection mistakes. No measured Asym workload proves that its benefit exceeds that cost for every organization. A is still the better bounded choice because assistance can be truthful and optional; where personal participation is required, the source continues to require it. Do not recreate B by imposing a fresh participant acknowledgement on every ordinary staff upload.

## Operating restraint and practical controls

1. **No new global policy editor.** Reuse current source/tenant capability and role controls. Explain denied/unavailable intake safely. A temporary unavailable evaluation is not a proved policy prohibition and cannot delete recovery state.
2. **One actual operation context.** Keep bounded original-operation recovery in the existing request/work flow. An upload dashboard, generic file inbox or task per file is not required merely to show status; an authorized operator must still be able to find and repair stuck work through its real owner surface.
3. **Correct labels before attractive animation.** Remove fixture completion and simulated progress. Prefer quiet persistent state, measured progress and reduced-motion compatibility. Do not turn a progress component into evidence of source success.
4. **Finite, purpose-owned budgets.** Quantify admitted counts/bytes, grants/session duration, concurrency/processing, retries, source/query/read operations, staging cleanup and retained reference/history coverage using representative files. Do not import vendor file-count or byte defaults. No cost-neutrality claim is supported.
5. **Privacy-preserving observability.** Maintain enough scoped evidence to distinguish incomplete transfer, unknown finalization, admitted Checking, stuck reviewability and pending disposition. Do not retain sensitive bodies in generic logs or erase replay metadata needed to recover the known source act.
6. **Real correction route.** Pending source removal and accepted/closed/privacy remediation must be usable by an actual authorized actor. A runbook requiring raw SQL or an imaginary admin button is not a permanent product remedy.
7. **Measure the intended journey.** Later staff/recipient pilot should test correct item/file choice, attribution comprehension, successful recovery, remaining-work understanding and interaction/time costs. These are proposed measurements; none has been observed in Asym here.
8. **Stage discipline.** The chosen assistance outcome is selected, but the exact amendments, definition refinement and release gates are not ratified by this note. The parent records formal disposition after the complete independent package review.

## Domain-language proposal

No additional term is needed. The current definition of Staff-supplied Document Evidence is deliberately limited to an existing version. A minimal candidate refinement is to remove that limitation while retaining the distinction:

> An exact file version deliberately supplied by authorized staff for a Document Request Item, with attribution to that staff act. It is distinct from a participant's submission or affirmation, item acceptance and permission for other uses.

This is a proposal for the owner/root's exact review, not a canonical edit. The decision must still define the two admitted routes—qualified existing-version reuse and new private local-file intake—and their separate receipt/source facts. Removing one word from a glossary cannot independently authorize the new route, and no canonical term count changes.

## Adversarial check

### What could go wrong with this answer?

Wrong files/targets, false participant attribution, unsafe private intake and delete-on-timeout are the material risks. Current source authority, exact identities, coherent admission, original-result recovery and stage-correct removal must be real; a polished picker is insufficient.

### What hidden assumptions are we making?

The illustrative staff member lawfully possesses the document and has actual source admission power. Neither follows from a local file or staff title. The usefulness/frequency/cost of this journey in Asym is unmeasured, and no source says every ordinary item can use staff evidence.

### How does this affect the whole product?

It adds one ordinary intake actor into shared custody, preserving distinct source review, participant proof/readback, work, messages, organization and disposition. It does not convert public CMS/media, finance, Support, official artifacts or broad libraries into ordinary request evidence writers.

### How does this affect the end-user experience?

Staff can use an already-held local copy without impersonation or asking for a repeat transfer solely to get it into the item. Recipients still perform genuine personal actions. Clear per-file states and persistent original-result recovery avoid guessing whether to upload again.

### Does this follow modern best practices?

Primary products document useful contextual assistance, parallel new/existing-file choices and distinct persistence/disclosure steps. They also exhibit attribution, deletion, link and overwrite patterns Core should reject. W3C and CoreUI guidance supply testable interaction principles, not empirical proof that this design is already accessible or universally preferable.

### Does this fit Asym's existing repo and product direction?

Yes, through an explicit ordinary source amendment, qualified private custody and the current shared API/UI boundaries. ReUI file state and adjacent upload endpoints are useful evidence, not implementation qualification. Exact base-maia, source separation and current permissions remain required.

### Should we adjust the recommendation?

Keep A with the required amendments. Do not add forced acknowledgement, a second confirmation, a new general-drive flow or provider integration. Retain B's participant-control value wherever the actual source requires personal contribution; keep ordinary assistance optional and truthful.

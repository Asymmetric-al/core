## Core conclusion

Keep A, but the safe operation is **append a corrected submission and conditionally update the source's pending review target**, never replace provider bytes, mutate a submitted evidence record or use a universal latest-file pointer. The decisive revision is the exact requirement/submission/source authority; request-wide open status, uploader identity and a disabled button do not authorize a correction.

Existing source provides useful UI and specialized command patterns. It does not provide a drop-in generic atomic correction service. In particular, finance's stored-revision exception and supplied-idempotency-key behavior cannot be copied into the new exact-version file boundary. This is a limitation of reuse, not a claim that the separate financial product is newly proven vulnerable or authorization to change it.

## Essential proof for later authorized implementation

1. Different item/tenant/request/recipient/source/predecessor IDs and forged identity/state fields fail before any disclosure or write; effective real-role grants/RLS and privileged command/worker paths tested separately.
2. Same unaccepted pending item allows A; accepted/frozen/closed item denies even when request has open siblings. Merely reading preview does not freeze work. Source-specific stronger evidence/confirmation rules remain.
3. Correction/acceptance, two corrections, deadline/revocation/recipient change, job completion and cleanup races have one rightful outcome under exact revision checks; no returned conflict after an untracked contradictory durable effect.
4. Lost response/duplicate click/reconnect recovers the same semantic operation. Same supplied key with different content or target conflicts. Replay still rechecks permission before returning retained outcome metadata.
5. New bytes have their own immutable identity and fresh inspection/rendition; no original mutation, safety inheritance or generic newest pointer. Old source uses, exact reviewed version, approval/signature/receipt/publication and retention stay unchanged.
6. Received confirmation survives preview failure; pending/resumable/late/quarantined/canceled outcomes and visible counts are truthful. A file correction cannot satisfy a requirement by itself or re-enable unsafe download.
7. Shared UI works with real keyboard, assistive technology, mobile, long/RTL names, slow transfer, pending dismissal and stale scope. JSDOM primitive passes do not certify that complete journey.
8. Required source event/audit/outbox and candidate relation commit coherently, with minimal data and existing communication owners; retries do not create duplicated mail/tasks or a new acceptance decision.

No quantitative correction count, new time window, extra approval step or automatic notification rule is invented here. Use exact inherited request/source and processing limits; source owners/founder decide any new material scope/permission choice. Parent review should preserve uncertainty around old-version visibility, post-closure read and withdrawal rather than accidentally settle them through this correction action.

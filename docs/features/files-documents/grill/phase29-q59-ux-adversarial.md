Files retains its 32 definitions; existing root P28 resource vocabulary remains authoritative. This note proposes a complete small personal-reference lifecycle. ## 1. Disposition and exact small profile

Accept A with the requirements below. Add **Save for later**, **Remove from saved** and a **Saved for later** destination within the existing Resources experience. Keep the primary resource Open action and complete ordinary search/navigation. Saving is an optional personal reference, not a copy, access grant, subscription, reading record or task. No collection name, folder, note, tag, approval, extra modal, tenant setting matrix or new account is needed.

Use **one private list for the same actual person within the exact Tenant/environment/organization**, not separate staff/missionary lists. This is a proposed source-purpose adoption, not a claim that a generic profile preference already qualifies. Every resource row resolves only through the person's current qualified source context; one list does not union their hats or allow another account to inherit choices by matching email. Current list/preference authority and current resource disclosure are separate decisions.

The initial order is **newest successful unsaved-to-saved transition first**, with a stable opaque tie-breaker. Repeating Save on an already-saved current record neither changes Saved date nor moves it to the top. A real Remove followed by a fresh qualified Save is a new personal occurrence/date. Replacing the resource, visiting it or retrying an old command does not reorder personal choices. Use bounded pages and text-first existing resource rows; no new favorite-ranking, Recent activity feed or sorting/collection engine.

Keep an active opaque reference through source withdrawal, known content denial and transient evaluation failure. If current own-reference authority is proved but resource access is known unavailable, show **Unavailable resource**, the person's own **Saved [date]**, and **Remove from saved**. If resource evaluation is unknown, show **Could not check this saved resource**, **Retry**, and own-reference Remove where that independent authority is known. Neither row reveals a retained title, filename, thumbnail, resource URL, underlying denied publication identifier, audience or reason. If own-list authority itself is denied or unknown, serve no list rows/counts/placeholders; show a safe current account/context error and the actual supported assistance route.

A retained reference may show the **same exact source publication** again only when current personal-list and resource permissions freshly allow it. Deliberate Remove never revives because content access returns, a publication is re-offered, an old request replays or a backup is restored. Separate Q58 editions/successors are different identities even with matching bytes/title; safe successor guidance does not transfer personal choice. No draft/archive/old-file/language fallback.

There is no new reminder-style expiry for active saves. Persist them for their personal return purpose until deliberate Remove or actually authorized account/organization/privacy/records cleanup. Resource unavailability, an expired content token or a failed lookup is not proof for cleanup. This is not a promise of permanent content or forever preference retention. Minimal result/replay/removal evidence has its own lawful bounded policy; no stale intent can become a new Save after evidence pruning. A personal save adds no custody use/hold that blocks lawful content disposition.

**Strong B remains useful counterpressure.** Complete existing Resources search, filters, list-position return and qualified links are a finished alternative, especially for a modest library or infrequent repeat use. A's added personal state is justified as a small intentional return aid, not by measured ministry demand, conversion, workload or time savings. Those are unknown. Preserve B's excellent baseline rather than making Save necessary to use Resources.

## 3. Complete UX, exact copy and ordinary recovery

### Save from a useful current resource

The reader sees **Save for later** beside permitted resource metadata, with Open remaining the primary action. Saving can be qualified from the actual publication summary even if body loading/preview fails technically; it does not require byte download, a successful preview or a read acknowledgment. Generic metadata visibility alone, an unknown source decision or a guessed publication identity is not enough to admit a new save. Actual source target eligibility and own-save authority must be known.

Use an ordinary command button, optionally with a bookmark icon. After proved persistence, show **Saved for later** as status and **Remove from saved** as the available action. Do not combine the changing action label with a pressed-toggle meaning. There is no confirmation modal, collection name or second Save step. Typing in search, opening a row, hovering, focusing or changing context does not save anything.

The product can explain once where helpful: **Saved resources are shortcuts. Access is checked when you return.** This is not a necessary warning ritual on every click. Prefer **Save for later** rather than Download, Follow, Pin for everyone, Mark read or Favorite as a rating. The UI must not imply a saved file is available offline.

### Saved for later and ordering

Provide one discoverable destination inside Resources, available through the existing staff and missionary shells under the current personal-purpose grant. It is the same person's list in the exact Tenant/environment/organization, not a list shared with that reader family and not an aggregate across organizations. List current permitted metadata through the source's normal text-first row. One publication appears once even if several memberships match. Show the reader's own Saved date where useful, separate from content Updated/Last reviewed dates.

Default order is newest actual unsaved-to-saved transition first, with a stable opaque tie-breaker. A repeat Save is a no-op; it preserves date and order. A new qualified Save after Remove gets its new actual date. Renames, visits, content updates, retries and access reappearance do not manufacture fresh Save dates. Finite stable pagination handles more entries. No new personalized ranking, body search, folder organizer, sort-builder or tracking feed is required.

When a row is removed, preserve sensible focus: next surviving row/action, previous row if appropriate, or the Saved heading/empty-state action when the list becomes empty. Do not refocus the top of the entire app, strand focus on a detached element or unexpectedly open the resource. Feedback should remain available beyond a brief toast.

### Three independent facts, four useful display states

The personal reference exists or does not; the actor currently may or may not manage/disclose it; and the underlying resource may be permitted, known unavailable or unknown. Those are different facts. A content lookup must not mutate personal preference merely to simplify rendering.

| Qualified facts                                                                                  | Visible state and action                                                                                                                            | Forbidden inference                                                                                                         |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Own-list authority known, personal reference exists, current resource disclosure known permitted | Normal current authorized resource row, current source content/review information, own Saved date, Open/Download where qualified, Remove from saved | A save is no content grant, historical snapshot or guaranteed future availability.                                          |
| Own-reference authority known, resource unavailable by a known current source result             | **Unavailable resource**; only own Saved date and opaque personal-entry handling identity; **Remove from saved**                                    | No retained title, filename, thumbnail, denied publication ID, URL, audience, reason, historical body or claim of deletion. |
| Own-reference authority known, resource evaluation failed/is unknown                             | **Could not check this saved resource**; **Retry**; own date and Remove only under the proved personal purpose                                      | Do not call it revoked/deleted, silently unsave, serve cached restricted metadata or show a complete zero.                  |
| Own-list/preference authority denied or unknown, or list query itself unproved                   | Safe whole-list unavailable/error/current-context response; no rows, personal counts or neutral placeholders are inferred from stale storage        | Own-record privilege cannot be guessed from a signed-in account, old active hat or cached previous list.                    |

Neutral rows are an **explicit new limited own-preference disclosure**: they expose the person's prior choice and its date, not underlying resource information. The server may retain the qualified target relationship internally, but the denied-row client action can address the opaque personal entry without revealing the resource identifier. This distinction must hold in all serialized fields, accessible labels, URLs, errors, cache keys and telemetry, not only visible text. Multiple neutral rows may be distinguished by permitted personal saved date; never recover a hidden title just to make the list prettier.

The same owned row may become a normal current row on a later qualified read when that exact publication is again allowed. That is current resolution of a retained preference, not resurrection of its old access grant. A deliberate Remove or actual authorized preference cleanup prevents such reappearance. Unknown failures do not count as removal, and known source absence does not alone prove personal-data cleanup authority.

A Save or Remove response cannot overwrite newer current state. A reconciled historical Save may truthfully have succeeded earlier while the resource is now removed by a later deliberate action; show the current state rather than reinsert it. Repeated transport requests recover one original source intent. A genuinely new later Save is permitted when currently eligible, even for the same person/publication. There is no permanent content-based deduplication ban.

### Mistakes, removal and privacy remedy

Ordinary recovery from a mistaken Remove is the persistent **Save for later** action on the currently eligible same publication, found through normal Resources discovery. No new Trash, restore-history panel or mandatory time-limited Undo is necessary. If a future convenience Undo is ever offered, it must mean a fresh qualified Save under current facts—not replay of an old success, bypass of an expected-state conflict or restoration of revoked rights. This proposal does not require that extra control.

For a removed unavailable resource, the former reference does not become a permanent title/content archive to make re-saving easier. When the actual resource becomes eligible again, normal discovery/current Save can be used. A removed preference stays removed in the meantime. An actual privacy/account/organization cleanup may lawfully erase personal reference data; ordinary save operations cannot reverse that through old tokens or backup replay. Scoped privacy/security operators have their actual purpose, not a general curator/manager right to browse, create or rearrange another person's list.

### Current source, retained reference and retention

A save targets the exact P28 source publication identity/lineage. Same-publication current-head replacement can resolve normally under current source authority. Separate editions, successor publications, title matches, identical bytes and different authored languages cannot silently replace that personal target. Existing qualified successor navigation may be shown only where separately permitted; saving the successor is a new deliberate choice. No draft/archive fallback or external-site copy is introduced.

Keep active references for their useful personal-return purpose, subject to actual privacy/records/account/organization lifecycle. No arbitrary automatic expiry, reminder or new tenant setting is needed. Do not promise permanent state. Resource denial/withdrawal/not-found/unknown by itself does not delete the preference. Conversely, a preference is not a custody use/hold and must not keep bytes, old titles or source history alive against lawful disposition. Keep only minimum legitimate reference/state/time and bounded result/replay evidence; no saved title/body snapshot is necessary. After removal/cleanup, either retain lawful minimal fences or reject unverifiable stale intents so they cannot recreate old choices.

The source must qualify actual account loss, offboarding, organization closure, privacy export/erasure and backup restoration. A retained private preference does not entitle an offboarded person to enter the app or even view neutral rows. Later legitimate current authority may show a retained same-scope choice, but never through a restored old grant or a copied different-person identity. No automatic email-based account merge or cross-organization preference transfer is selected.

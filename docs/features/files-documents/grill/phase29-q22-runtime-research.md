# Phase 29 Q22 runtime research — source fulfillment without a redundant finish action

2026-10-21, Asia/Bangkok. Q01–Q21 are ratified by Conrad; Q22 is unselected. The parent is recording Q21's ratification while this read-only research proceeds. ## Recommendation and open decision

Recommend **A: the ordinary native request's owning source records fulfillment when its final actual required condition is satisfied, without a separate routine staff Complete request action**. All Q21 staff acceptance and other source predicates still apply. “Automatic” describes the follow-through of a source-owned rule, not automatic human approval, a browser count or a scanner callback.

The strongest alternative is **B: after all substantive conditions are satisfied, require an additional explicit staff Complete request action** in the same context. This can be useful when staff need a deliberate final wrap-up or handoff acknowledgment beyond the individual item decisions. It must have a clear meaning and current source authority; it is not a second person's approval by default, another required essay, or permission to waive incomplete requirements. Its cost is another action and a possible stalled request after participants and reviewers have already done the required work.

This fork is genuinely open. Q21 explicitly reserves both the extra Complete control and automatic whole-request completion. Q06/Q10 define what valid fulfillment means and its consequences, not whether a separate staff command is part of the ordinary profile's predicate. A selects no extra final click; B deliberately adds it. Neither selects a new requirement taxonomy, item waiver power, reviewer routing, completion email, grace period or new access duration.

A is the leaner ordinary default because it avoids an acknowledgment with no independently stated business purpose. That is product judgment, not proof of measured staff savings. If a source has an existing distinct final decision, required attestation, hold or downstream handoff condition, A cannot remove it merely because the files are accepted. Qualify that existing condition within the source predicate rather than hiding it behind a generic “100%” display.

`packages/api/src/admin/contribution-operations/approval-notifications.ts:600–620` projects an already-decided financial correction into completion of its linked shared task. This is the useful direction: source decision → task projection, rather than generic task → invented source decision.

## Comparing the practical flows

| Choice                                            | Flow when the last actual source condition is established                                                                                                                         | Benefit                                                                                                                                                 | Cost or necessary constraint                                                                                                                                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A: Source fulfillment follows the final condition | The owning source records one qualified fulfillment outcome and required follow-up; the UI shows completed only when that outcome is known. No extra routine staff finish action. | Avoids a second acknowledgment with no independent ordinary purpose. Reduces the chance of fully handled work lingering awaiting a click.               | Final acceptance or another source condition can have a meaningful completion consequence; explain it. Complete predicate/currentness and atomic/recoverable occurrence must be real, not a visible file count. |
| B: Separate deliberate Complete request           | After substantive conditions pass, an authorized staff member reviews readiness and invokes the source's final completion action.                                                 | Makes final wrap-up intentional where that acknowledgment has value; staff can distinguish accepted items from a request intentionally left unfinished. | Adds another step, possible forgotten work and delay. It cannot bypass unmet conditions, backdate fulfillment or promise more recipient access. No extra approver is inherently required.                       |

Illustrative example: a request has two items, each supported by several files. The second item's current evidence is accepted, but a source-required non-file condition is still unresolved. Neither option fulfills. Once that last actual condition is validly established, A follows through under the source rule; B awaits the additional authorized completion action. If no condition remains after the final staff item acceptance, A can complete as that source operation's qualified consequence; it is not approval triggered by file upload.

These examples are design cases, not observed ministry behavior. No performance or satisfaction advantage is claimed from code or vendor analogies. The recommendation favors fewer unnecessary actions while preserving the actual source predicate.

## Boundaries worth carrying into the selected-answer review

1. **One source predicate and effect.** A must identify the exact current request and complete required condition set, including valid source-authorized alternatives. No client-rendered/permission-filtered count, shared task, scan verdict or `all files accepted` boolean decides it. Unknown or failed lookup is not an empty satisfied set.
2. **Exact material races.** Final acceptance, another condition resolution, requirement membership/instruction change, waiver/freeze/closure, correction and relevant safety/authority changes must have a coherent source ordering. Do not take an earlier “all accepted” snapshot and later complete a changed request. Preserve accepted siblings and unrelated independent work; no whole-tenant lock.
3. **Completion authority is not inferred from a checkbox or event.** The source rule and its permitted command/effects need current qualified authority. If final item acceptance also fulfills, bind that consequence to its source command; a worker uses source/service authority, not an invented human completion action. B similarly needs a true source completion command, not generic task editing.
4. **Actual fulfillment time and recovery.** Prefer recording the source fulfillment outcome coherently with the transition that establishes the final condition where the source owns that boundary. A delayed consumer may recover an already-proved original occurrence; it cannot infer an earlier F merely from a later all-satisfied snapshot. Where completion has not yet been established, report honest finalization/pending state and apply the qualified actual source occurrence, rather than backdating to upload, scan, final item timestamp or task projection replay.
5. **One durable outcome.** Preserve fulfillment scope/revision/condition evidence, historical recipient-admission decision and required follow-up consistently. Duplicate callbacks/two final changes/retries produce the same effect; late task/email refresh does not undo or recreate it. The existing source command and outbox/recovery seams are sufficient in shape; no new general scheduler is selected.
6. **Recipient access is a consequence, not completion evidence.** Q06–Q19 remain: valid ordinary fulfillment can transition participant rights; independent later source completion may have no recipient admission. Both A and B must respect actual exclusive deadlines and current restrictions. No grace, automatic fresh grant, changed scope or restored expired authority follows. The user need not be online for valid source fulfillment.
7. **Historical truth stays closed.** Later requirement/safety invalidation follows source remediation without silently reopening fulfillment, restoring a predecessor or giving a new completed-read clock. Repairing a task projection cannot change the original F. Current serving and historical completion are distinct.
8. **Lean truthful UX.** Show remaining source work, staff-pending review and known fulfillment accurately. If A's final staff action completes the request, communicate the consequence within that meaningful action; no automatic new extra confirmation or all-purpose Complete button is needed. Failed/unknown outcome uses owned recovery. Do not add acceptance/result email under Q20, a whole-request waiver editor, bulk acceptance, reviewer-routing policy or a new dashboard.

## Proposed next-question shape

Ask whether ordinary requests should **finish through the source when all of their actual conditions are satisfied**, or **require one additional deliberate staff Complete request action**. Recommend A, explain that staff still perform Q21's required evidence acceptance, and state that source-specific final obligations remain real conditions. Avoid describing B as poor UX: deliberate wrap-up can have value, but this ordinary profile has not yet established such a separate purpose.

No Q22 selection, schema, exact completion permission, clock value, notification, routing, negative-outcome or implementation is inferred. This note is deliberately bounded; if A is selected, the full review should qualify the aggregate/source occurrence and completion consequence without re-asking Q21 or weakening Q03/Q10.

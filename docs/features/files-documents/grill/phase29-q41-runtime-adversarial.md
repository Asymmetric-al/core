## Current primary technical evidence

Official documentation was retrieved through Context7 and direct current pages on2026-10-24. It constrains implementation choices, not product source authority:

- [Supabase passwordless email](https://supabase.com/docs/guides/auth/auth-email-passwordless): signInWithOtp can create users by default; shouldCreateUser:false prevents new signup. Successful send alone returns no session; verification can return a session. Therefore false is not a complete path for a new reader and true can execute current signup side effects. A source-bound proof/admission layer is still required.
- [Supabase session behavior](https://supabase.com/docs/guides/auth/sessions): a valid JWT and refresh lifecycle do not automatically enforce immediate current grant/session policy. Session limits are evaluated on refresh, and stronger signout validation can check the session_id against current session existence. A shared source/P12 admission/revocation check remains necessary; do not invent a second session authority or trust a stale app_metadata claim.
- [Supabase storage delivery](https://supabase.com/docs/guides/storage/serving/downloads): signed URLs use a separate internal signing key and remain valid until expiry despite Auth JWT key rotation/revocation; support is the documented revocation route. A short signed URL is not immediate source revocation. Current requester-authorized application retrieval, or an actually proved equivalent, is required for this source's private reads. Public bucket bytes are public irrespective of a protected preceding page.
- [PostgreSQL17 CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html) and [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): prove effective grants, applicable policy composition, old-row USING and proposed-row WITH CHECK including conflict/update branches, views and owner/definer/service bypass. User-editable metadata is not permission authority; server metadata can still be stale in a token. Omitted explicit WITH CHECK may derive from USING, so test effective semantics rather than claim omission alone is a bypass.
- The [current Supabase changelog](https://supabase.com/changelog) was checked after its Markdown endpoint returned unsupported content type. Its October12 notice removes old CBC TLS1.2 suites no earlier than November10, affecting Auth/Data API/Storage HTTP endpoints. Qualify supported clients and actual provider configuration; do not weaken transport for an unsupported device. No provider upgrade/configuration was performed.

No numerical OTP lifetime, share period, rate budget, source cap or provider quota is adopted from documentation examples or local config. No compliance/assurance-level claim, human-identity guarantee or free-operation claim follows.

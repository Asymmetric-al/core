## One decision

**When staff give an ordinary request file a clearer display name, should that name stay in authorized staff views, or also be shown to the currently authorized recipient?**

| Option                                           | Practical experience                                                                                                                                                                              | Benefit                                                                                                                                                | Cost or boundary                                                                                                                                                                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Staff display name only (recommended)**    | Eligible staff can give one exact file contribution/use an optional descriptive name shared with other currently authorized staff. The recipient keeps the source-approved recipient-facing name. | Clearer staff search and organization without changing what the recipient recognizes or turning a routine rename into an external disclosure decision. | Staff and recipient can see different names. Show the permitted received filename and request-item context to staff where useful so they can identify the same file together.                                                   |
| **B — One display name for staff and recipient** | A permitted staff rename also changes the current display name on the eligible recipient's source view.                                                                                           | Both sides can use the same clearer name; useful if improving recipient navigation is the main problem.                                                | Every such change is also participant-facing content. The mutation needs the actual source's external-disclosure authority and clear audience copy. Retained evidence and previously delivered names still cannot be rewritten. |

Both options preserve exact file/use/version identity, bytes, received history, current authorization and independent uses. Neither exposes the name to everyone with the same bytes or to the public. B is a credible shared-vocabulary design, not permission to leak staff notes. A is a shared staff organizational name, not a private alias for every individual. Neither option requires naming every file.

**Recommendation: A.** The current problem is staff organization of received evidence. A supplies that with one optional staff display name and the existing recipient-facing representation. The strongest argument for B is easier conversations when both sides see identical names; that benefit is plausible, but no Asym evidence currently establishes it as the dominant need. Keep participant instructions and questions in their existing deliberate participant channels. Do not introduce an audience toggle, a second editable recipient title, automatic translation, naming templates or a general metadata editor to avoid choosing the simpler default.

Illustrative example, not a claimed ministry workflow: a received `scan_004.pdf` can appear to eligible staff as `Application supporting document`, while the authorized submitter still recognizes the source-approved `scan_004.pdf`. Staff details can show both the staff name and permitted received filename. The business status remains a separate source badge; naming something `Approved` cannot approve it.

## Why this is the next open choice

The founder's §7–§8 already require stable identities, identity-preserving rename, independent uses of the same bytes, protected names and practical discovery. Q38 allows approved names, metadata and source context in staff search; it does not decide that every editable name is participant-visible. Q42 establishes optional staff organization on each exact admitted ordinary evidence use, rather than a universal mutable document or storage object. Its Labels are organizational tags, distinct from the display name here. Q43's shared views share permitted definitions, not access. Q05 keeps recipient history and metadata within the recipient's actual purpose. Q44 keeps its exact original-download and sealed delivery-name/manifest contracts. Q45 anchors comments to exact uses and versions.

Thus, “rename versus no rename” and “one global blob name versus independent source uses” are already settled or conflict with governing decisions. The remaining choice is the audience of this routine ordinary-source display-name edit. Existing P18 official documents, P21 evidence, P22/P23 Media, P26 attachments and P28 resources keep their own naming, disclosure and provenance contracts. In particular, this question does not reinstate source names that a specialist owner requires discarded.

## Adversarial check of the recommendation

### What could go wrong with this answer?

A staff name could leak through a generic serializer, ZIP/member naming, search suggestions or shared metadata cache; a whole-row patch could mutate identity; stale retries could overwrite another staff member's change. The proposed boundary treats the name as protected source metadata, reuses one current-authorized mutation path and preserves original/delivery contracts. Under A, an internal title is still unsuitable as a repository of private care notes.

### What hidden assumptions are we making?

That staff find descriptive naming useful and that showing the permitted received reference is enough to resolve different names during recipient support. Those are product hypotheses. The founder explicitly requires rename and good discovery, but neither usage frequency nor comparative A/B success is measured. Source-specific edit/disclosure mappings and finite input/workload budgets need implementation evidence; the existing CMS filename field does not establish them.

### How does this affect the whole product?

It adds a narrow ordinary-source metadata audience contract. Custody byte identity, Q05 recipient history, Q38 discovery, Q42 tags/folders, Q43 views, Q44 delivery and Q45 exact comments keep their meanings. No universal file title, alternate source currentness, private-to-public toggle, request instruction revision or resource/receipt rename authority is created.

### How does this affect the end-user experience?

Staff get a short optional edit close to the file, visible to eligible colleagues and useful in current approved search. Recipients keep a familiar source-approved representation and receive no naming chores. The cost is two visible naming contexts; staff need a compact permitted original reference, not a second editor or naming workflow. Tenant administrators assign actual metadata-maintenance rights through the existing source controls.

### Does this follow modern best practices?

Primary nonprofit CRM, CRM/CMS and record-attachment products support descriptive metadata and small in-context editing. Shared cloud-drive names also demonstrate B's legitimate collaboration benefit. None establishes a universal audience rule or outweighs Core's private source restrictions. W3C guidance supports clear audience labels and accessible feedback; native usability and security proof remain necessary.

### Does this fit Asym's existing repo and product direction?

Yes as a proposed ordinary-source extension with explicit protected-field handling. Core already separates source meaning from custody, has mandatory metadata discovery and uses Base UI/base-maia in shared packages/ui. Existing public Media serialization is precisely why importing a generic name field without its audience contract would be wrong. Publication must follow canonical owners and incorporated OpenSpec, not hand-edit generated projections.

### Should we adjust the recommendation?

Keep **A — Staff display name only** as the recommendation, with the exact boundaries above. Choose B instead if Conrad's intended product goal is for staff to curate the name recipients see, accepting that this is participant-facing content requiring its own authority. Do not pretend that both choices are already selected or add an audience toggle merely to postpone the decision.

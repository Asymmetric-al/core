Research completed 20 October 2026, Asia/Bangkok. This is a grooming review of the founder's selected **A: recipient confirmation for every external private-document request**, including an already qualified matching signed-in session where the selected rule permits it. It is not a PRD, implementation, published owner amendment, ticket graph, security certification or proof of operation. The parent session owns the exact founder wording and final ratification.

Repository: `/home/conrad/code/core`, Ubuntu-24.04/conrad, develop `3d85897ebf1515008ef5c676b1c58a15422fb9ab`. Source-code implementation and current external guidance are being reviewed separately; conclusions here concern adopted/published owner contracts.

## Conclusion

The selected confirmation floor is compatible with the intended private-document experience, but **it cannot be implemented solely as an OTP screen or a storage permission**. Two source contracts need an explicit compatible successor: (1) Phase 4/12 must express a human's narrowly admitted request-only authority without inventing donor/missionary membership or widening anonymous access; (2) Phase 17 must admit the exact document-request/verification producer and its legitimate non-constituent recipient authority. Existing plumbing does not supply those permissions.

Email confirmation establishes control of the addressed mailbox at the qualified time. It does not establish which human controls a shared mailbox, legal identity, authority to represent another person/organization, evidence acceptance, a signature, or permission to inspect every document associated with that person. A signed-in principal, an email address, an invited recipient and the person described by a document must remain separate.

The practical journey can stay short: neutral request landing, confirm the exact admitted recipient through the qualified route, then see only the request's permitted instructions and actions. Reuse a genuinely sufficient current proof rather than challenging on every HTTP read. Source-required stronger assurance remains binding. Wrong-recipient correction and inaccessible-mailbox recovery need honest owned paths; neither can be implemented as a convenient staff override of possession proof.

## Exact identity distinctions

| Fact                                       | What it proves                                                                                               | What it does not prove                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Request created by authorized staff/source | That source deliberately requested a particular purpose and intended recipient under its own rules.          | That the typed address is correct, the individual controls it, or every person at that mailbox is authorized.            |
| Request link received                      | Possession of an invitation artifact.                                                                        | Current mailbox control, named human identity, source access, upload acceptance or current authority.                    |
| Fresh exact email proof                    | Control of the specified mailbox for the exact bound proof purpose/request/revision within its valid period. | Legal identity, exclusive mailbox control, agency/representation, consent to unrelated use, or a durable donor claim.    |
| Valid native Auth session                  | A particular native principal authenticated under a qualified method/session.                                | Current inbox possession, target-tenant membership, matching request recipient, or access to this document purpose.      |
| Current verified Auth-address match        | One address-related evidence input if its provenance, currentness and exact-purpose reuse are qualified.     | Automatic private request authorization, person equivalence or universal reusable email verification.                    |
| Request-only admitted context/session      | Current access to the exact request and approved actions under P12 plus source floors.                       | General portal membership, Party/list access, another request, earlier evidence, staff authority or document acceptance. |
| Successful upload                          | A transfer/intake occurrence, eventually an exact byte version.                                              | Malware safety, evidence completeness, business approval, signature validity or source identity.                         |

These distinctions are inherited from P25 IC01–IC03/IC06, P4 A6/claiming, P12 context rules and P34 source-evidence rules. A UI phrase such as **Email confirmed** is honest; **Identity verified** is unjustified unless a separately qualified source identity proof actually occurred.

## Proposed owner-amendment map

These are precise **amendments to bring back for adoption**, not edits already made or a formal specification.

1. **Q01 scope statement:** every newly admitted external private-document request must satisfy its confirmation floor before protected request content/actions are released. “Request” means the source-owned logical collection requirement with exact intended recipient and relevant revision, not every HTTP call and not all existing private-document retrieval products. Source-required stronger identity/assurance applies on top. An invitation link alone never meets Q01.
2. **P4 proof owner:** define exact request-recipient mailbox proof and allowed matching-session proof reuse, including issuer, normalized address/revision, principal relationship where proved, purpose, request/revision, expiry, replacement/revocation, replay, wrong-account recovery and assurance. This does not call donor `bindClaim`, create staff/missionary membership, verify legal identity or update CRM contacts by inference. Reuse qualified native mechanisms and currentness ownership rather than issuing an alternate general JWT/identity broker.
3. **P12 context owner:** adopt the compatible narrow participant context/admission successor expressly reserved by WS-Q02. Define the same trusted tenant source for API/RLS, exact request/source/recipient references, capability/action ceiling, policy/identity epochs, non-enumerating projections, revocation and deferred reproof. Preserve four existing context semantics; neither public-only nor NHI/operator becomes the human participant substitute. Choose the smallest compatible native representation after actual-source investigation.
4. **P3 projection/consent owner:** classify all pre-/post-confirmation request fields and derive permitted projections before counts/search/metadata. Register no new policy engine. Resolve recipient/request disclosure and outbound verification eligibility through exact source/recipient branch; retain restrictive contact/provider evidence. Explicitly distinguish self-service access from initiated outbound email.
5. **P17/P6 communication and protected-action owners:** admit a finite document-request producer and exact recipient-authority branch where a legitimate external recipient has no Party. Use the current protected transport/origin and P6 sole intent/dispatch/evidence. Specify initial request versus requested code/resend versus correction/reissue semantics and retention. P28's newsletter-only exception supplies a structural precedent, not authorization. Existing P6 no-Party data shape does not remove this owner step.
6. **P34/shared participant contract:** amend its generic token-to-task-session prose to make the Q01 private-document profile require qualified confirmation before authoritative participant admission. Preserve non-authorizing landing session, source limits, stronger sensitive paths and identity-owner gate. Source tasks can reuse the seam; full P34 product is not a P29 prerequisite.
7. **Consuming source owner:** define recipient kind, who may request/correct/cancel, allowed instructions/uploads/own-submission reads/corrections, stronger identity, submitted-version and requirement changes, and reviewer/evidence acceptance. Unknown identity or audience policy blocks the affected profile, not unrelated custody work.
8. **P24 host/entry owner if needed:** explicitly reconcile fixed protected Tenant Donor Portal origin with the existing application surface used for request-only participation. Keep current route until a compatible successor is accepted; do not hide a host-contract change as implementation detail.

## Questions and assumptions requiring explicit handling before ratification

### Recommended minimal owner path — review closure

This review recommends one path, rather than leaving competing identity architectures open:

1. **Keep native authentication with Phase 4/Supabase Auth.** A person may need a native authenticated principal/session under that owner's qualified admission flow, while remaining unenrolled as a donor, missionary, staff member or organization member. No second identity broker, alternate general JWT issuer, separate per-document login system or fabricated Party is introduced. Creation/linking of any native principal remains identity-owned and cannot assume away the G01 or current-account constraints.
2. **Add one closed document-request-recipient authority under its actual tenant/source owner.** It binds the exact tenant/environment, source request and revision, intended recipient/address revision, source purpose, permissible actions and lifecycle. It can exist legitimately without a Party/contact/donor row. This is the specific required P17/P6 recipient-authority amendment; P28 D43 demonstrates the closed-branch shape but does not already authorize it. It cannot be used for another email purpose or establish general private access.
3. **Adopt a narrow authenticated-human admission successor in Phase 4/12.** The existing authenticated-human/PDP path must be able to admit that exact current source request for its proved principal without requiring donor/missionary/staff organization enrollment. The source grant remains separate from authentication and binds the actual request context; it never manufactures membership or unions another hat's powers. Calling it merely a grant under present IC02 would be incorrect: present IC02 still requires membership-backed human context. The owner successor must explicitly change that admission limitation for this closed purpose, with every existing public/NHI/operator/member context unchanged. This recommends the permanent behavior and owner seam, **not** a new public role name, a generic fifth-context feature, a schema or an independent permission engine. Current verified context construction, P3 floors, P12 effective-access verification and the database tenant source must agree before activation.
4. **Keep the existing protected doorway and admit proof only after deliberate entry.** The invitation artifact itself never satisfies Q01. A deliberate eligible action requests fresh confirmation to the fixed source-approved mailbox, using the qualified safe-link plus secondary-code contract where both redeem one issuance once. A sufficient current source-qualified possession proof may avoid redundant mail only after a qualified exact mailbox/principal/purpose/request/revision binding; an ordinary signed-in JWT email flag does not. An existing qualified proof is evidence for admission, not a transferable grant. Mailbox proof is not phishing-resistant MFA or exclusive-human identity.
5. **Keep P17 presentation/preparation and P6 sole delivery.** The confirmation producer owns exact issuance and postcondition. Initial invitation, requested confirmation, resend and corrected-recipient successor have distinct exact occurrence/proof semantics, no direct provider bypass and no suppression override by labeling them security mail.

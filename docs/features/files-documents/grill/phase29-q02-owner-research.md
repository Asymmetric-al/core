# Phase 29 Q02 candidate — seeing one's submitted file

Bounded read-only owner research, 20 October 2026. This note prepares the next founder question; it does not select the answer, reopen Q01, define a formal specification, publish tickets or implement a read capability. The parent's newly ratified Q01 source and repository state were read. No repository files were changed by this subagent.

## Recommendation

The candidate is a useful unresolved decision **if framed as file-content readback for the ordinary native external document-request journey**, not as whether participants get any receipt, status or submitted-item page.

Recommend a small request page that lets the currently admitted submitter deliberately preview the exact file version the server received from them **when that request's source policy and file-safety profile permit it**. It should show truthful received/processing/review state either way. This helps a person answer “Did I send the right document?” after leaving the upload screen, without giving them a library or another person's submissions.

Call the choice **View my submitted file** rather than “a request workspace,” which could imply a broader product. Original download, replacing/deleting submissions, seeing staff materials or reviews, viewing other submitters, indefinite history, resubmission rights and post-closure access are separate decisions. Do not bundle those into this answer.

## Viable options

| Choice                                       | Ordinary user experience                                                                                                                            | Trade-off                                                                                                                                                                                                                  |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — View my submitted file (recommended)** | Return to the same request page, see the server's received item/status, and deliberately open a permitted safe preview of the exact submitted file. | Better reassurance and spotting an accidental wrong upload. Requires qualified recipient-purpose preview/delivery, current authorization and explicit unavailable states. Does not add editing or replacement.             |
| **B — Receipt and status only**              | Return to the request page and see admitted filename/type/size/time and status, but no server-provided file content through this native lane.       | Simpler and reduces retrieval exposure. The person must rely on their own retained file and staff follow-up to check what they sent. This must not remove independently authorized reads in existing P21/P34/P41 purposes. |

Both options retain receipt/status and safe recovery. Both protect other submissions and internal review. Do not offer an unrestricted participant file library as a third option; it is broader than the decision and has no source-grounded need here.

## Suggested founder framing

“A person has sent the requested document and later wonders whether they chose the correct file. We have already decided how to confirm their access. Now we are deciding what they can see after uploading.

For ordinary private document requests, should the person be able to return and open a safe preview of the exact file they submitted, or should they see only a receipt and its status?

I recommend the preview: it lets them check what Asym actually received, while showing only their own currently permitted submission. A confidential purpose can still require upload-only handling, and a quarantined or unsupported file cannot be opened. This choice does not let them replace/delete it, download originals, see staff notes, or browse other people's files.”

The final question should use simple options A/B and explain that the review outcome is distinct from receipt. “Supported preview” is a bounded, qualified reading experience, not a promise of every format's perfect original appearance.

## Precision needed if A is selected

1. **Own is source-bound, not string-based.** Bind readback to the accepted submitting actor/admission, exact request/recipient scope and file occurrence/version. Matching email, same filename, related Party, common household/organization, file digest or possessing an object key grants nothing. A replacement recipient or helper inherits no old-submission access automatically. Q01's mailbox-proof limitations still apply; do not imply the mailbox proved a unique natural person.
2. **A deliberately admitted read capability.** The selected ordinary request profile may include own-submission preview, subject to current source/P12 restrictions. Merely being an uploader is not a global ACL rule. Existing specialized source contracts still govern their users and evidence.
3. **Exact server-received bytes.** A local thumbnail or selected file on the device is not readback proof. A successful preview resolves the actual immutable accepted transfer and qualified rendition with original-source version/coverage; it never opens whatever now occupies a familiar path or rewrites the source evidence.
4. **Receipt, preview readiness and business acceptance remain separate.** Safe text distinguishes received, checking, ready for permitted preview, awaiting review, accepted/rejected, limited preview and unavailable. Preview cannot certify authenticity, signatures, completeness or approval. A scanner failure is not proof the person submitted nothing.
5. **Preview is disclosure.** It has current purpose/recipient authorization just like other private reads. Deny before metadata/thumbnail/search/count/alternate-route serialization. No raw provider URL or reusable signed URL escapes the current access boundary; full/range/conditional/ready-rendition reads recheck the owner.
6. **No unsafe or automatic fallback.** Quarantined, malformed, unsupported, expired or unqualified data does not become readable simply because the same actor supplied it. Failed preview never auto-downloads the original, emails a copy or sends content to a third-party viewer. Use truthful receipt/status and source-owned recovery.
7. **Bound the experience.** This is the same light request page, not staff File Manager. No forced eager conversion/prefetch while browsing. Reuse qualified shared preview mechanics; do not create another renderer/editor. Bring the exact inherited P26 limits and purpose profile into qualification when those mechanics are reused; do not imply support beyond their certified coverage.
8. **Do not settle mutation or historical access implicitly.** Replacement, deletion, correction submissions, previous/superseded versions, original downloads, staff-added files, post-closure continuation and retention are independent. Q02 may promise readback while the exact source-admitted submission remains accessible; it does not create a permanent archive or lengthen either grant or byte retention.
9. **Source policy, not arbitrary preference sprawl.** “Source may require upload-only” means a qualified confidentiality/purpose rule, not an unbounded per-file ACL builder or staff ability to override floors. Exceptions cannot be used to quietly omit the recommended ordinary product journey after acceptance.

## Narrow proof to carry into the answer review

- Ordinary participant can return after a lost response/reload and inspect the same received supported version, without resubmission or a new business effect.
- Unsupported/limited/quarantined/processing states preserve truthful receipt and do not grant an original-download fallback.
- One user/request cannot inspect another actor/request/tenant's files, including same mailbox string, same filename/digest, changed recipient and shared-device cases.
- Current access revocation/expiry/reclassification stops future reads without deleting independent source evidence or claiming recall of downloaded/seen copies.
- Staff notes, acceptance reasoning, other evidence and prior/superseded versions do not leak through the viewer or its navigation.
- A contextual preview is clearly distinguishable from an original and from business acceptance; keyboard/mobile/assistive-technology return to the same request remains usable.
- Existing P21 evidence retrieval, P26 staff reader, P28 resources and P34/P41 source-permitted submission visibility retain their own authority and scope.

No new runtime tests, private-data reads, provider tests or external-product benchmarking were performed for this bounded owner check. The current source paths prove planning constraints only. A participant pilot and exact read/preview/storage qualification remain future implementation evidence.

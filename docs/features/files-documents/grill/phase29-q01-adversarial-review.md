## Adversarial check

### What could go wrong with this answer?

An implementation could verify any email, create an unwanted donor profile, then use a privileged database client to expose the request. That would satisfy a superficial OTP demo while violating the decision. Another failure is to call mailbox control verified personal identity, or to treat a still-valid cookie as permission after the source cancels the request. These are concrete integration risks, not evidence that an unbuilt request feature is currently exploitable.

### What hidden assumptions are we making?

The original explanation assumed request-only authenticated participation and corresponding verification messages could reuse existing infrastructure directly. They cannot yet: current source creates a donor profile for a new Auth user; the current human authorization contract requires membership; and the existing protected-action recipient rules do not generally admit a non-Party document recipient. All three require explicit, narrow owner changes. Mail delivery, a working inbox, individual mailbox ownership and actual participant usability remain unproved. The policy must handle their absence truthfully.

### How does this affect the whole product?

Phase 4 owns native identity and proof, Phase 12 the sole current authorization decision, Phase 3 disclosure floors, Phase 17 prepared messages/protected presentation, Phase 6 dispatch, and the requesting domain its recipient and business requirement. Phase 29 owns file custody and obeys those decisions. The common seam can serve native requests before full Workflow Studio or applications ship. Q01 does not retroactively change Phase 18 receipt handoffs, Phase 21 collaboration, Phase 28 newsletter confirmation, guest giving, or every external task.

### How does this affect the end-user experience?

An ordinary recipient gets a neutral branded invitation landing, deliberately confirms access to the intended mailbox, and reaches the exact permitted request. A current, sufficiently qualified proof can avoid another email. The recipient needs no donor/missionary enrollment, password-creation exercise, profile-completion form or full File Manager. Code entry accepts paste/autofill; the existing safe-link alternative may redeem the same fresh confirmation issuance. Incorrect account, delayed email, expired proof and unavailable request have clear recovery without exposing private details or losing accepted work.

### Does this follow modern best practices?

**Yes as a recipient-bound access pattern, not as a universal high-assurance authentication claim.** Current Microsoft specific-people sharing binds access to the specified recipient. Box can require authenticated uploaders; Dropbox and Microsoft upload-only collection also demonstrate that easy collection alone does not verify the intended recipient. Donorbox and Bonterra show familiarity with passwordless donor entry, not proof of secure private-file collection. Stripe's email-based customer selection is specifically unsuitable as an Asym Party-matching rule. [Microsoft](https://learn.microsoft.com/en-us/sharepoint/shareable-links-anyone-specific-people-organization), [Box](https://support.box.com/hc/en-us/articles/360045304653-Administering-Box-File-Request), [Donorbox](https://donorbox.org/donor_one_time_codes/new), [Stripe](https://docs.stripe.com/customer-management/activate-no-code-customer-portal).

Microsoft's October 7, 2026 documentation says legacy SharePoint OTP retirement starts in October; current Entra B2B email OTP is separate. Copying a historical sharing implementation would be poor evidence. [Current migration documentation](https://learn.microsoft.com/en-us/sharepoint/sharepoint-azureb2b-integration).

NIST does not accept email as its out-of-band authenticator. Its address-confirmation exception cannot be used to relabel an access-authentication flow as compliant. Therefore this design claims neither NIST assurance level, MFA, phishing resistance nor legal identity from email alone. Source-required stronger assurance remains mandatory. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/).

### Does this fit Asym’s existing repo and product direction?

The product direction fits. The present implementation is insufficient. ADR-0214/0215 and Phase 25 IC01–IC03 separate native identity, mailbox proof, Party, claim and current source permission. ADR-0025/0037 define the shared scanner-resistant doorway, frozen verified Tenant host, explicit action, secret handling and private delivery. Workflow Studio explicitly reserves the needed compatible identity successor in WS-Q02. Reusing those owners is the permanent path; current signup, callback and public upload behavior are not ready-made request access.

### Should we adjust the recommendation?

Keep A and amend its precision. **Confirmed recipient** means source-authorized access supported by the required proof; ordinary email proof establishes mailbox control only. Every logical request needs its own admitted scope, while current authorization is checked on every protected operation. A signed-in email match is not automatically sufficient. The exact corrected decision and controls follow.

## Corrected decision to record

> Every newly admitted external private-document collection request requires confirmation bound to its source-authorized recipient before any protected request details or permitted document actions are exposed. Possession of the invitation alone is insufficient.
>
> Use the existing shared identity, authorization and protected-action owners to provide a request-only experience. Do not require donor, missionary, staff or organization enrollment, fabricate a Party, or build another login/permission system merely to let someone respond.
>
> A deliberate eligible action obtains fresh proof at the fixed source-authorized mailbox, through the qualified safe-link/code issuance, unless an existing proof is explicitly qualified for the current principal, mailbox revision, request, purpose and required freshness. Ordinary sign-in, a JWT email string or an `email_verified` flag is insufficient by itself. Successful confirmation does not grant another request or renew authority indefinitely.
>
> Mailbox proof establishes access to that mailbox, not legal identity, exclusive human ownership, representation, signature, document authenticity or business acceptance. Every source keeps its stronger assurance, current permission, disclosure, review and retention rules. Changes of recipient, delegation and lost-inbox recovery occur only through their authorized source/identity operations.
>
> All protected operations recheck current request and source authority. Revocation, expiry or supersession stops new protected admission and unaccepted late submissions under the ended authority. A durably received intake may continue source-authorized scanning, review or retention after the browser session ends; that continuation grants no renewed recipient access. Source withdrawal fences promotion where its contract requires it. Already delivered bytes cannot be recalled.

This records the founder's selected floor plus required safeguards. The membership-free admission and closed non-Party recipient branch are **substantive compatible source amendments needed to realize that choice**. They are identified here, not silently described as existing authority. Their canonical owner/OpenSpec adoption belongs in the later authorized specification stage, before implementation/activation. No separate decision between identity vendors is needed.

## Category-by-category review

Severity is potential impact if a concern is left unresolved: **H** high confidentiality/authority/integrity impact; **M** meaningful usability/reliability/maintenance impact. Likelihood is qualitative and conditional, not measured probability: **expected** follows directly from inspected naive reuse; **plausible** requires a realistic mistake/race/incident; **unknown** needs deployed/user evidence. The clause references give the exact correction, not merely advice.

### 1. Problem validity, necessity and alternatives

**Material concern: yes — M / plausible.** A universal phrase could impose repeat codes on every HTTP request or on unrelated donor giving, adding friction without improving recipient binding. The actual known need is the founder-requested private request journey; its frequency and abandonment costs have not been measured. The strongest alternative is the existing source-bound bearer-task exchange for eligible routine purposes: simpler, but transferable invitation possession remains enough. Full portal enrollment is more burdensome and does not itself prove real-world identity. **Effect:** retain A, narrow its unit/scope and permit qualified existing-proof reuse. **Fix:** C01/C05/C16; measure the actual pilot without claiming comparative conversion gains. No storage API or OTP widget is frozen by this product decision.

### 2. Brittleness

**Material concern: yes — H / plausible.** A changing email string, shared inbox, provider relay, browser session or canonical host may invalidate an apparently correct match. P4 A6 and IC03 explicitly require current exact proof; ADR-0025 binds the host. Assuming static email/role routing would strand recipients or admit the wrong one. **Effect:** changes the implementation assumptions, not A. **Fix:** C02/C05/C06/C08/C12; version recipient authority, reject stale/ambiguous proof and qualify alias/provider/host transitions. Do not globally strip plus tags/dots or infer a new recipient from an email resemblance.

### 3. Technical debt

**Material concern: yes — H / expected if current signup is reused unchanged.** The current trigger assigns a donor profile/default tenant; `requireAuth` expects profile/tenant/role; callback role redirects override request continuation. A local file-login workaround would duplicate identities and permissions. Runtime review R1/R10 provides exact source evidence. **Effect:** A requires shared foundation work. **Fix:** C03/C06/C18; neutral native identity and narrow source admission through existing owners, with regressions for actual donors/members. This is a bounded shared capability, not a redesign of all identity.

### 4. Edge cases

**Material concern: yes — H / plausible; prevalence unknown.** Wrong signed-in account, legitimate alias, shared family/office inbox, delegated helper, recycled mailbox, offline email, multiple requests and multiple tabs can confuse identity and attribution. These are test scenarios, not asserted ministry habits. **Effect:** clarifies what confirmation proves and forbids automatic reassignment. **Fix:** C02/C05/C08/C09; source-authorized representation and correction, safe account switch and explicit inability to detect unknowable mailbox recycling. Test the outcomes before admitting the relevant profile.

### 5. Footguns

**Material concern: yes — H / expected under naive defaults.** Supabase `signInWithOtp` creates a user by default; current Core then adds donor profile meaning. A client-selectable recipient, manual verified toggle, global email-template change or direct bucket helper can quietly widen access. Official Supabase docs and runtime R1/R3/R5 support this. **Effect:** requires explicit producer wiring. **Fix:** C03–C06/C09/C13/C14. Do not change global Auth templates/TTL or enable provider methods without regression proof for existing purposes. Staff never see or type a recipient's verification secret.

### 6. Tenant safety

**Material concern: yes — H / plausible.** Shared native credentials, default-tenant fallback, same email in multiple tenants, cross-host cookies, global caches or reused operation IDs could mix requests. ADR-0214 and P12 prohibit that inference. **Effect:** A remains valid only with exact tenant/source admission. **Fix:** C03/C04/C06/C10–C12/C15; independently scope every request, result, command and deferred effect, and do not union another role's authority. Denial must cover counts, errors and background work as well as bytes.

### 7. Database, RLS and authorization safety

**Material concern: yes — H / plausible; actual proposed schema is unbuilt.** A visible row could be retargeted within the same tenant, a request marked accepted/clean by its recipient, or a service-role path bypass scope. RLS alone cannot validate all transitions. Existing `withOperation` supplies a privileged client; the caller-bound membership RPC is a useful narrower precedent. **Effect:** requires C10/C11, not a new permission engine. Use required scope fields, composite FKs, exact operation uniqueness, constrained status/transition writes, deny unsafe cascades, and indexed current-grant/revocation lookups. Evaluate effective roles, grants, all combined policies, views/functions and both old/new row conditions. Omitted `WITH CHECK` can inherit `USING`; absence of the keyword is not itself a defect. Definer bypass depends on actual role/ownership/FORCE RLS. Money precision is not changed by Q01; it must never write financial facts. Real-role mutation tests remain required. [PostgreSQL 17 policy semantics](https://www.postgresql.org/docs/17/sql-createpolicy.html).

### 8. Overengineering

**Material concern: yes — M / plausible.** Treating A as a new identity provider, generic guest role, per-file ACL designer, universal OTP policy builder, custom challenge service or automated risk-scoring platform adds maintenance without solving the requested journey. **Effect:** constrains the permanent fix. **Fix:** C03/C04/C05/C16/C18: one named request purpose, existing Auth/PDP/protected doorway and a small qualified profile. Separate authoritative facts need not mean separate microservices, duplicated databases or one enormous lifecycle enum. Do not add government-ID checks to every ordinary request as a reaction to email's limitations.

### 9. UX/UI and friction

**Material concern: yes — M / plausible; Core user-study evidence absent.** Forced signup, repeated OTP, six isolated digit boxes, blocked paste, inaccessible errors, lost target after login, changing countdowns and mail delay can defeat the task. Current callback/recovery gaps make this concrete. **Effect:** A needs a short complete journey. **Fix:** C05/C06/C09/C16; source-qualified proof reuse, whole-code paste/autofill, accessible link alternative, exact return, one deliberate send and truthful retry. Avoid mandatory name splitting/address collection, preserve legitimate Unicode, and show local due time with its zone while server instants enforce security expiry. Do not advertise offline submission; preserve only safe in-memory context and recover durable accepted work after reconnect. [W3C accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html).

### 10. Source of truth, ownership and invariants

**Material concern: yes — H / expected if mailbox verification becomes a generic verified-recipient flag.** Such a flag collapses native identity, source audience, proof freshness and business acceptance. P4/P12/P17/P6 already own these separately. **Effect:** introduces explicit owner amendments, not competing owners. **Fix:** C02–C05/C07/C17. One exact request-bound proof application/redemption has at most one semantic admission result; qualified parent proof reuse requires a separate source-authorized request binding; one request recipient successor never rewrites prior proof/history; source permission remains current; bytes do not set business acceptance. A recipient authority need not create a donor/Party. Maintain separate actor and represented subject.

### 11. Hidden coupling

**Material concern: yes — H / plausible.** Signup trigger, membership guard, role-based callback, auth-hook email, frozen portal host and participant UI appear independent but jointly control entry. Changing one can break existing auth, receipt or email-change routes. A full Workflow Studio dependency would also invert the foundation. **Effect:** exposes exact shared dependencies. **Fix:** C03/C04/C06/C14/C18 and the owner adoption map below. Reuse the mechanisms; qualify their named consumers independently. Provider/global settings cannot be changed as though they belong only to File Manager.

### 12. Failure modes

**Material concern: yes — H / plausible.** Email accepted with response lost, proof consumed before cookie delivery, database committed before queue dispatch, callback delayed after cancellation or scanner unavailable can yield false failure, duplicate messages or false success. Existing ledger/claims offer limited infrastructure, not source correctness. **Effect:** requires recoverable outcomes. **Fix:** C11–C14/C17; retain original semantic occurrence, durable result/outbox, explicit unknown states and current-authorized result recovery. Deny the affected unsafe action and expose an actionable owner recovery state; never silently downgrade to a public link or fabricated acceptance.

### 13. Lifecycle, time, concurrency and idempotency

**Material concern: yes — H / plausible.** Verification can race recipient correction, code versus link, resend, revoke, finalization, cleanup or late worker output. A transport retry key does not prevent duplicated business effects. **Effect:** requires exact independent lifecycle rules. **Fix:** C08/C11/C12/C13. Declare one atomic admission point; a preceding revocation wins. Keep proof issued/consumed/expired/revoked, grant admitted/ended, transfer and source review as separate facts. A deadline display is not token expiry. Same key/different intended payload conflicts. Existing byte custody is preserved after an access grant ends.

### 14. Data integrity

**Material concern: yes — H / plausible.** A replaced address could inherit old proof, repeated completion could add two versions, lost response could prompt re-upload, or a file under a new key could become a new business document. **Effect:** strengthens exact identity and recovery requirements. **Fix:** C08/C10–C13/C17: immutable history, current heads separate from records, semantic idempotency, source-approved version lineage, foreign-key scope and accepted-result readback. Confirmation never updates contact verification, donor claim, newsletter enrollment or other business records by inference.

### 15. Security and privacy

**Material concern: yes — H / plausible.** A phished/compromised mailbox, exposed URL secret, private filename in email, reusable storage URL, stale cache or replayable restored session can disclose material. Email is not strong identity assurance; current source has public upload precedents. **Effect:** limits assurance claims and requires defense in depth. **Fix:** C02/C05–C07/C12/C13/C15/C17. Apply inherited protected headers/CSP/referrer/CSRF discipline across redirects, errors, HEAD/range/conditional routes and workers; no broad OCR/AI/search corpus follows from request access. Authentication secrets and document retention remain separate. Copies already delivered cannot be erased by revocation.

### 16. Scalability and performance

**Material concern: yes — M/H for availability / unknown at actual workload.** Unbounded challenges, reservations, scans, global locks or permission checks that enumerate a full library can exhaust provider/tenant capacity. No requested-volume measurement exists. **Effect:** no unsupported throughput promise. **Fix:** C10/C12/C15/C18: indexed exact-scope lookups, finite reservations, fair tenant queues and measured profile limits. Inherited 256-bit verifier entropy is a transport requirement; 14-day invitation or 30-minute official-document session values are not universal Q01 settings. Provider OTP defaults and global limits must be measured/qualified without silently affecting other auth purposes. Read permission remains current even if immutable bytes are cached internally.

### 17. Operational burden

**Material concern: yes — M / plausible.** Staff may become the workaround for every lost inbox, resend, stale request or stuck upload, especially with present disabled recovery pages. **Effect:** A needs normal recovery and a bounded exception workload. **Fix:** C08/C09/C11/C14/C16/C17: source-owned reissue/cancel/correct operations, safe self-service resend, delivery/processing status and exact audit. Routine recovery cannot require SQL, provider-console edits or sending private attachments manually. A lack of approved evidence for recovery produces honest unavailability, not a support bypass.

### 18. Observability and auditability

**Material concern: yes — H / plausible.** A successful email API call may be called verified/delivered, a redeemed code attributed to a named human, or logs may retain the very secrets being protected. **Effect:** tightens vocabulary and evidence. **Fix:** C02/C14/C15/C17. Separate technical request traces, durable source history, restricted security evidence and provider delivery status. Correlate opaque request/proof/operation identities and actual actor provenance. No log payloads containing codes, verifiers or private filenames. The operational signals below define thresholds, owners and responses.

### 19. Dependency and integration risks

**Material concern: yes — H / plausible.** Supabase defaults create users and share OTP/template settings across flows; provider acceptance and session revocation semantics need qualification. Mail-client fragment behavior and TLS/browser support vary. Microsoft legacy OTP illustrates migration drift rather than a dependency recommendation. **Effect:** no new vendor and no assumed certification. **Fix:** C05/C06/C11/C14/C18; version-bound adapter/host tests, exact hook field mapping where used, no implicit direct Resend send or central SMTP fallback. Supabase's October12 notice removes old TLS ciphers from November10 at the earliest; test supported clients rather than weakening transport. [Official notice](https://supabase.com/changelog/cbc-tls-ciphers-deprecated).

### 20. Migration, rollout and upgrades

**Material concern: yes — H / plausible.** Old signup writers may create donor affiliation after a new participant UI ships; a broad backfill may infer recipient authority from email or legacy public URLs; rollback may restore weaker access. **Effect:** rollout order is a release requirement. **Fix:** C03/C10/C18: additive representation, compatible readers, trusted writer fencing, no authority inferred during backfill, synthetic then real-role/provider qualification, limited purpose/cohort activation, immediate deny switch and forward repair. Preserve genuine existing donor memberships and all accepted evidence; do not delete old accounts or privately republish old public bytes merely to normalize the model.

### 21. Testability, traceability and proof

**Material concern: yes — H / certain if tests stop at OTP success.** Version checks, config, mocked sessions or the 45 passing regression tests cannot prove recipient isolation or the new grant. **Effect:** retain A as a product decision, not ready runtime. **Fix:** C18 plus the falsifiable proof matrix below. Trace Q01 to glossary/ADR, owner amendments, later authorized canonical PRD/OpenSpec, tasks, tests and exact release evidence. Preserve source provenance and distinguish accepted intent from integrated docs, implementation and activated environment. No new ticket numbers or completed implementation boxes are invented.

### 22. Other development hazards

**No independent additional material concern found for this bounded decision.** Checked for accidental payment/financial writes, CMS publication, signature claims, AI disclosure, e-signing procurement, public-giving friction, new storage selection and app-shell duplication. They are excluded by C01/C07/C13/C16 rather than silently expanded into Q01. Known hazards are covered above. This does not claim a full repository security audit, whole Phase29 specification or all future source policies have been verified.

## Database and lifecycle design obligations

Avoid prematurely choosing table names or creating a second policy store. The implementation must nevertheless make these concrete before it can pass C10–C12:

- Exactly one trusted tenant/environment and source request for each recipient authority, proof application, grant and submission. Required scope is non-null; opaque IDs are not secrets or authorization. Use same-scope constraints, not merely UUID existence.
- Proof facts and issued recipient/request references are append-only or immutable in their authority-bearing meaning. Current lifecycle/heads can be separate bounded mutable projections controlled by one owner command. A correction creates a successor instead of changing who an old proof described.
- A unique effect identity binds tenant/source/request/revision/recipient/action and semantic payload. Retry with changed bytes or target is a conflict. Database constraints enforce uniqueness; a single transaction or proved owner protocol controls admission and required local audit/outbox.
- General participant UPDATE cannot change tenant, source, recipient, request, byte version, safety verdict, reviewer, acceptance or attribution. Composite FKs prevent cross-scope links; authorized transitions also prevent same-tenant retargeting. Deletes cannot cascade into independently retained evidence.
- Exposed tables have appropriate grants and enabled RLS. Evaluate all effective SELECT/mutation policies, UPDATE's old/new states, view execution context and function execution grants/search path. Internal service operations require their own trusted scope checks. An `authenticated` database role is not sufficient request authority.
- Preserve the actual shared native Auth email-uniqueness contract, while inferring no global business recipient/person identity or tenant authority from email. No client-supplied author/owner/reviewer, mutable historical legal facts or floating-point money field. Q01 creates no money calculation at all. Security instants use timezone-aware server chronology; human due dates preserve the source's zone/date semantics separately.
- Index the actual tenant/request/principal/current-grant and reconciliation/expiry paths, then prove plans and contention with shaped data. Do not add speculative global search or per-file ACL machinery.

Meaningful sequence: source request/recipient revision exists → deliberate neutral entry → exact confirmation proof → current request admission → finite private transfer → verified receipt/processing → source review. Confirmation alone cannot jump to submission or acceptance. Cancellation/revocation fences new affected participant admission and source-forbidden promotion; retention/holds remain source-owned. Browser-session expiry does not cancel independently authorized scanning, review or retention of durably received intake. A transfer authorized before revocation may already have placed private bytes, but cannot later become accepted content using stale authority. Existing in-flight delivery and already-received copies need honest bounded behavior, not an impossible recall promise.

## Ruthless synthesis and dependency order

**Resolved before recording this decision:** the unit is the logical external private-document request; confirmation means exactly the proof obtained; invitation alone is insufficient; qualified reuse is permitted; stronger source rules and separate actions remain intact; full platform membership is not required. The strongest simpler alternative was considered and rejected because invitation transfer alone would retain authority. Broad signup and bespoke auth are both unnecessary.

**Capture in the later authorized owner/specification package:** one closed document-recipient purpose and narrow authenticated-human admission successor, correct proof/reuse rule, exact recipient correction/representation/recovery ownership, communication class and suppression behavior, source action ceilings, and reference/retention semantics. The minimum dependency graph is identity/proof + sole PDP + source recipient authority + shared protected messages/doorway → native request admission → private transfer/review. Whole P34/P41/P42 products are not predecessors. Complete Phase29 library, formats and records-policy questions remain separate grooming decisions; they are not silently decided here.

**Require during implementation:** correct the shared signup/profile assumptions, preserve true existing memberships, implement exact callback return, real-role database constraints/policies, atomic/recoverable admission, governed dispatch, bounded private staging/processing and safe recovery. Use existing shared primitives; do not create a separate File Manager identity or dispatch stack. Qualification includes the actual Auth project, host, mail clients, provider settings and CDN, not only local fixtures.

**Require before activation:** all applicable Q01-P proofs, exact source-purpose approval, finite profile settings and their boundary evidence, migration compatibility, safe disable/roll-forward, operational ownership and participant pilot. If a source's identity or recipient policy is absent, that profile stays unavailable; no generic email-default override. This is a falsifiable implementation gate, not an unanswered founder technology choice.

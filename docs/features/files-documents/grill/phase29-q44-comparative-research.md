## Recommended single question

**When staff deliberately select several eligible ordinary request files to download, should Asym prepare one private ZIP with an itemized manifest (A), or a prepared list of individual file downloads with the same manifest and outcome information (B)?**

| Option                                       | Practical behavior                                                                                                                                                                                                                                                                                                                                  | Strongest advantage                                                                                                                                                                          | Real cost                                                                                                                                                                                                                                                                                 |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — One bounded private ZIP; recommended** | The person reviews a finite exact set. Asym prepares a protected archive containing the authorized originals and manifest, then offers one deliberate package download. The interface identifies preparation, omissions/failures and actual transfer status separately. Existing individual download remains available under its own current rules. | One deliverable keeps a selected group and its manifest together and avoids making the person coordinate many download actions.                                                              | Preparation, temporary derived custody and archive compatibility need qualification. The person must extract the ZIP to work with its contents; a large package can be inconvenient on a weak connection or small device. Packaging is not a promise of smaller bytes or faster transfer. |
| **B — Prepared individual-download list**    | The same finite exact selection is prepared as an itemized list with a manifest and current per-file outcome/actions. The person deliberately downloads the files they need from that prepared selection; the app does not silently launch every download at once.                                                                                  | Each file can be fetched separately without extraction, and a large or failed file need not require fetching an entire package again. Suits a person who needs only part of the set locally. | More separate actions and local files to keep aligned with the manifest. The person must track which pieces they obtained. The feature still needs exact selection, current permission, outcome/retry and manifest handling; it is not no-build.                                          |

Preparation and delivery are distinct facts, not necessarily separate clicks or a required second confirmation. A qualified simple case may honor one deliberate Download action for the same reviewed set under current authority; slow or returning cases can expose Ready and Download. Material changed-set or permission outcomes still need truthful permitted recovery. This does not make B an automatic burst of individual downloads.

**Recommend A** as the normal bounded multi-file handoff. The founder's existing selection, manifest and custody requirements already require treating the set deliberately; a single package gives that set a useful browser delivery form. Keep ordinary individual-file actions as independently qualified alternatives for a person who needs one file or cannot conveniently handle an archive. This does not quietly adopt both full batch modes, an archive-management platform or a third product option.

B is a credible permanent choice, especially for small sets, selective retrieval, very large originals or weak connections. It avoids the extra archive artifact and extraction step. It should not be caricatured as a burst of blocked popups: this proposed B is an explicit prepared list with deliberate per-file actions. Chrome's automatic-download controls illustrate why blindly firing every download is a poor substitute for a designed B journey; they do not prove every ordinary per-file click triggers a prompt.

The recommendation is product judgment. No research establishes Asym's usual set size, frequency, device mix, bandwidth, task success, staff preference, error rate, operating cost or time saved. Primary comparators demonstrate that package delivery is common and useful, while documenting important limits. They do not establish universal best practice or native feasibility at a particular Core limit.

## Recognizable example

Elena is authorized to obtain local working copies of an equipment inventory PDF and three related photographs from ordinary requests. She selects those **four exact eligible files**, not the entire Equipment saved view or every item that might later enter a folder. This is illustrative, not an observed ministry workflow or proof that downloading is the right action in every review task.

Under A, she reviews the selected set and prepares a ZIP. The page shows which selected files are ready, blocked, failed or not started without revealing newly forbidden details. When a deliverable is actually ready and remains authorized, she downloads it and opens the archive using her device's normal file tools. A readable manifest identifies what it contains and any qualified omission. It is a copy of that selected set, not a live folder or a declaration that all evidence for the request is complete.

Under B, she gets a prepared list for those same four files plus the manifest. She can deliberately fetch each original, handle one large photograph separately and return to the known set after an interruption. The app does not infer that every listed file was received just because preparation succeeded or a download link was clicked. Neither option accepts evidence, completes a request, shares with another person, changes home folders or deletes the originals.

## Common boundaries that are not additional product questions

1. **Bind a finite explicit set.** Selected rows differ from all matching files, all pages, current folder contents and future query results. Resolve exact permitted source/use/version references before preparation. No folder recursion, hidden file inclusion, latest-version substitution or automatic expansion follows a selector label.
2. **Keep current authority throughout.** Metadata discovery, preview, original download, preparing a package and delivering its bytes/manifest are distinct permitted actions. Each included original and the composed artifact must meet actual current source/P12 rules. A visible checkbox, prior successful preparation, owner role or ZIP URL is not continuing authority. The same requirement applies to each B download.
3. **Use exact originals, not transformed documents.** Preserve byte identities and source relationships. No merged PDF, OCR, preview substitution, signature alteration, comment transcript, hidden metadata enrichment or new business artifact is selected. Safe archive filenames are delivery labels, not changes to source originals.
4. **Show truthful completeness and progress.** Prepared, ready, requested/started transfer, transport completion and verified local receipt are different facts. Show available evidence only. The manifest must identify the actual admitted included set and qualified outcomes; a package or manifest is not proof that a request is fulfilled or an official records package is complete.
5. **Protect omission and failure details.** Unknown authorization cannot mean eligible, a true empty set or a safe omitted filename. Reports, manifests, names, paths, counts and errors must obey current disclosure. Do not include blocked originals or silently call a changed subset the reviewed complete set. The selected-answer review must make precise the existing truthful-partial-results requirement and concrete recovery without creating another founder choice by stealth.
6. **Keep package preparation bounded and private.** Use short-lived qualified staging and exact immutable package/manifest identity with current governed retrieval and cleanup; there is no permanent shared folder, reusable external grant or archive catalog. ZIP packaging itself is not encryption, DRM, malware clearance or independent retention authority. No external email or ready-notice purpose is selected.
7. **Name entries safely.** Long/international/colliding names must remain distinguishable without exposing hidden source paths or other uses. Protect reserved names and unsafe archive paths; never overwrite one included original with another same-named file. Map delivery names to exact permitted source references in the manifest. Do not unpack submitted archives as part of wrapping originals.
8. **Recover the intended work.** Lost preparation responses and repeated clicks recover the same admitted result, not new selection/latest versions. New restrictions, source corrections, expiration, cancellation and partial preparation have truthful outcomes and an actual permitted retry/repair path. No stale original/package or completed transport is erased from history to simplify the UI.
9. **Keep a usable browser path.** A can preserve existing individual-file actions; B is a prepared list, not a multi-download storm. A large/unsupported package must have a truthful finite limit and usable smaller-selection or independently authorized individual recovery. No required desktop app, external storage connector, automatic cloud transfer, or arbitrary fixed vendor limit.
10. **Preserve source work and device boundaries.** Neither option changes acceptance, request completion, review ownership, source retention, folder placement, shared-view defaults, external Q41 access or source deletion authority. A downloaded copy is outside future server revocation; no claim of recall or verified destination custody. No blanket offline synchronization or silent reconnect replay.
11. **Keep the journey accessible and clear.** Use existing Core selection/status/dialog/list primitives with keyboard and non-drag pointer paths, mobile/zoom/RTL/IME support, persistent authorized selection and meaningful progress/error status. Do not require a reason essay, a new permission form or routine second confirmation merely to download already eligible files.
12. **Do not confuse qualification with product choice.** Exact bounds, private artifact serving, authority/cleanup/selection races, byte integrity, current-role tests and actual device workload remain engineering release proof. A is not considered delivered because a server can emit a ZIP; B is not delivered because one file endpoint exists. No promise about unchanged bills, maximum supported files, compression ratio, timing or browser behavior has been measured.

## Recommended next genuine choice

**Should general staff File Manager discovery match approved names, metadata and source context, or additionally search inside eligible documents?**

Recommend **A — Approved names, metadata and source context** for the general File Manager. Provide the already-promised folders, labels, filters, recent work, saved views and useful source-aware results. Match only owner-approved fields; do not inspect document bodies to select or rank results through a body index, direct scan or preview-text fallback. Keep existing qualified document readers and their bounded Find where supported.

**B — Also search qualified document text** is a strong practical alternative, not inherently overengineering or prohibited product scope. It can find a file from wording staff remember when they do not know the name or owning record. It would require an actual useful declared cohort of source-approved uses, immutable versions, formats and text coverage, with qualified extraction/indexing, current disclosure, lifecycle/restriction handling and honest incomplete states. It does not inherently require OCR, AI, semantic answers, a new vendor or a universal search platform. Selecting B would authorize that bounded product capability for later full review and qualification; it would not make all existing readable files eligible by default.

A's real cost must remain explicit: a phrase occurring only inside a file cannot locate that file in the general finder. Staff may have to narrow candidates through record/type/date/context, then inspect a permitted reader. In-document Find is available only where that reader actually qualifies it; image-only, unavailable or omitted content is not magically searchable. Do not compensate by demanding that staff rename every upload or copy confidential body text into ordinary labels.

The recommendation is a scope judgment, not measured retrieval success. Core's source context and approved metadata provide a plausible useful foundation, while the session has not observed the frequency/value of body-only retrieval tasks. A avoids adding another extraction/index-retention/coverage lifecycle to the general finder without that evidence. B becomes stronger when finding documents from remembered internal wording is a required staff workflow. Existing product contracts and current code do not settle that preference or prove either native path complete.

Illustrative example: Elena remembers an equipment handover record and a September inventory but not its uploaded filename; both options can use permitted source context and metadata. If she remembers only “annual calibration” inside `scan-017.pdf`, A cannot match those body words. B can only if the exact source use/version and relevant searchable text are admitted and covered. This is an illustrative comparison, not observed ministry data; no OCR or all-file/all-language coverage is inferred from the filename or the example.

## Necessary product boundaries and practical journeys

1. **Approved fields, not automatically harmless metadata.** Search source-permitted display names/titles, labels/types/dates and exact safe record/use context. Original filenames, hidden provenance, restricted-person/location details and other linked-use identities may be unavailable or deliberately discarded. Source-approved catalog descriptions remain fields; extracted body text cannot be renamed metadata to evade the selected boundary.
2. **A is a matching boundary, not merely a storage choice.** Do not inspect file bodies to select or rank general File Manager results through persistent indexes, on-demand scans, cached preview text or another invisible body-derived fallback. Separate already-qualified source searches remain in their actual contexts. Do not create a new body-search permission prohibition for every product or promise an automatic future implementation.
3. **B adds a real purpose-qualified capability.** Declare useful source uses, exact current version/coverage and matching behavior; qualify reusable extraction only where actual purpose/retention permits it. New extraction need not mean a second parser or vendor. Neither source read permission, a preview output nor a generic tenant switch is sufficient. OCR, semantic answers, AI, translation, file-writing and new provider access are not implied.
4. **Source permission precedes enumeration.** The lawful field/source contribution must be known before a result, rank, count, facet, suggestion, thumbnail, duplicate warning or serialization. No first-page filtering or provider object listing supplies authority. A visible use cannot reveal other uses of shared bytes; metadata discovery does not automatically grant preview, original download, sharing or export.
5. **Navigation preserves actual identity and context.** A result leads to the exact owner-qualified source/use/version or its expressly qualified current-version rule, rechecked when opened. It must not silently swap another file with the same name or a currently wider association. Preserve useful query/filter/return state only while current disclosure permits it.
6. **Complete within declared scope, honest outside it.** A can truthfully report no matches for approved metadata without claiming body text was absent. B reports unsupported/nonsearchable/unprocessed/partial/failed coverage separately where that fact is itself permitted. Neither exposes hidden-match counts or mislabels timeout, truncated candidates or failed authorization as a complete zero. Exact totals require complete authorized predicates/coverage.
7. **No forced metadata cleanup ritual.** Source context and existing type/date/recent affordances should make sparse names usable. Do not require manual tagging, rename original evidence or paste private body text into broad labels merely to make A viable. Poor metadata remains a real limitation to test, not a reason to invent body search under A.
8. **Existing source work stays independent.** Search is a read/discovery capability, not acceptance, satisfaction, publication, a received/sent fact or a new communication occurrence. An index/query outage must not undo lawful source admission or disable unrelated qualified work. Current restrictive source facts apply immediately before any stale projection contributes, with owned bounded reconciliation and lawful cleanup.
9. **No invented universal engine or numeric profile.** Reuse current native API, metadata/view/UI and qualified query primitives where appropriate. P9, Support D22, D32 and P23 have different purpose-specific formats, matching, workload and retention contracts. Do not inherit their numbers or SQL mechanism as a universal File Manager contract; native design must establish and test its selected finite workload.
10. **Real user proof is still needed.** Use representative source-authorized retrieval with ambiguous/sparse filenames, multiple permitted uses, multilingual names and body-only clues. Test current access changes, classification, late results, keyboard/AT/mobile/slow-network behavior and recovery. No measured ministry preference, benchmark or source-runtime qualification follows from this grooming recommendation.

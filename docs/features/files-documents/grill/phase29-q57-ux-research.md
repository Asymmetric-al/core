## 4. Small complete experience recommended for A

**Reader entry.** Put **Report a problem** beside the resource's existing information/actions, available only in the actual current source-qualified reader context. It should not interrupt normal Open/Download, appear as a public rating or require the whole file to be downloaded first. The report form keeps the exact resource/publication/language or other relevant published context automatically where permitted. A reader does not choose an internal department, curator email, permission group or a second resource ID.

**Short deliberate input.** Use one labeled plain-text field: **What is wrong with this resource?** A hint such as **For example, a broken link or an instruction that is out of date** can help without forcing a classification menu. The field needs useful bounded text, not an essay or AI judgment of quality. Show a concise purpose/privacy hint where useful: **Describe the resource problem; do not include private personal details.** This is not an automatic sanitizer. No attachments, screenshots, general questions about a person's case, public comments, mentions or automatic external URL fetching are implied.

**Honest recipient and receipt.** Before the final **Submit report**, explain the actual recipient class, for example **This goes to the people responsible for this resource** only when that route is truly qualified. Do not promise anonymity, a personal reply, a delivery channel or a response deadline. Use trusted current reader attribution rather than asking the person to re-enter an email as identity proof. A recorded source outcome can say **Report received**; it means durable accepted report and owned handling, not that a curator read it, agreed or fixed the publication. An unknown result says **We could not confirm the result. Check report status before trying again**, recovering the same original act rather than duplicating it.

**Actual handling and return.** The source must admit a report only into a genuinely capable maintenance route and preserve responsibility through curator departure/reassignment. Existing resource management is the right place to find pending reports and their exact observed context. Do not infer that ordinary role membership or the last publisher is always the right handler. A curator reviews the claim, uses an existing publish/correct/withdraw or actual technical repair when needed, then deliberately records a truthful report handling outcome. **Handled** must not imply **fixed** when the issue was unconfirmed, already addressed, out of scope or no resource change was warranted. Closing a report does not record Q55's actual resource review or alter Last reviewed by itself.

The smallest complete loop includes the reader's lawful durable receipt and an attributable source handling state/outcome that can be shown on a permitted return, with current disclosure rules. It need not add chat, email, a global My reports inbox, read receipts, an SLA or a multi-status workflow builder. If the implementation exposes a status, label it as report status, not resource safety/currentness. The selected-answer review would settle the exact minimal lifecycle and correction/withdrawal/reopen behavior; this question does not silently copy a vendor's irreversible Closed rule.

**B's complete alternative.** If no report feature is selected, an existing authorized help/coordination route may be sufficient, including a contextual route that already knows the resource where actually qualified. The reader must not be told to paste protected content into any convenient email/Support/CRM note. Help must actually reach a capable source owner under the correct audience and retain its own current permissions. A route with no responsible handler is incomplete under either answer.

## Adversarial check

### What could go wrong with this answer?

A can become an ignored inbox, expose private report text, mislabel a claim as a factual defect or promise that a report was fixed when merely closed. B can push readers into unsafe context sharing or an ineffective contact route. The deciding requirement is a capable source-owned handoff and truthful receipt/outcome under either path.

### What hidden assumptions are we making?

That the current P28 reader can identify a useful problem, that a real curator/source route can act, and that report context may be disclosed to that handler. We have no observed frequency, curator response time, demand for replies or improvement metrics. The report is an allegation to evaluate, not proof that the resource is inaccurate or unsafe.

### How does this affect the whole product?

A adds one P28 resource-report producer and handling purpose. It does not expand general staff-resource readership, turn resources into a social feed, borrow ordinary evidence comments, create a new Support conversation or authorize Q51/Q48 messaging. Publication, actual review, custody, access and retention keep their owners.

### How does this affect the end-user experience?

A offers a short contextual action with trusted identity and resource reference, a real receipt and meaningful permitted return status. B reuses existing coordination and can be simpler where it already works. Neither needs mandatory attachments, an essay, duplicate personal data, a new account, automatic email or a repeated confirmation ritual.

### Does this follow modern best practices?

Documented knowledge/CRM products attach feedback to its subject and provide handling. Their richer ratings, watches, tickets, forms and mail behavior are distinct choices, not requirements. W3C guidance supports a small labeled form with truthful errors/status. The recommendation is a reasoned fit for this gap, not a claim of universal consensus or measured ministry benefit.

### Does this fit Asym’s existing repo and product direction?

Yes if P28 explicitly owns this bounded new reader action and responsible route, P12 controls current report/resource visibility, and existing management/maintenance surfaces are reused. D12's warning against a dead Ask curator button is preserved. Current source intent and demo/help UI are not proof that the native report producer already exists.

### Should we adjust the recommendation?

Recommend A with actual scoped handling and private truthful loop closure. Keep B fair, with a capable authorized existing route rather than a strawman. Do not add another general feedback platform, new notification default or broader library audience. Q57 remains unselected.

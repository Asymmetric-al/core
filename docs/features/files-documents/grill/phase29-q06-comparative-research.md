# Phase 29 Q06 — recipient access after successful request completion

Research inspected 20 October 2026, Asia/Bangkok. The parent reports Q01–Q05 and their amendments are ratified. This prepares the next founder decision; no Q06 choice is presumed. Scope is ordinary successful completion of a native private-document request, not cancellation, withdrawal, denial, security revocation, recipient reassignment or specialized financial/application/document rules.

Official-documentation research only. No authenticated comparator test, real applicant record, registration, upload, download, message, provider action or code change occurred. Documented product behavior, evidence gaps and Asym design judgment are distinguished below.

## Recommendation

Recommend **time-limited read-only return access** after ordinary successful completion: the same confirmed recipient can revisit the source-approved completion status, concise Q05 history and currently eligible final/current files, with Q02 preview and Q04 download independently qualified. Uploading and ordinary self-correction end with completion; reading does not reopen the request.

The source must supply a finite, clearly communicated access end, with continuing current authority and stricter restrictions taking precedence. This note chooses no number of days. There is no evidence here for a universal 30-day default, and the access period must not become an indefinitely renewable session, public link or permanent archive.

This is a product judgment. It preserves a useful route back to the outcome without requiring the person to obtain every copy during the exact moment the request is completed. The strongest narrower alternative is completion status and concise history only, with file content unavailable after completion. Ending return access entirely is also coherent for a tightly minimized collection experience, but leaves more questions dependent on the source's help route.

## Six boundaries that must not be collapsed

| Boundary                        | Meaning in this decision                                                                                                                                                                                                            |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Successful business completion  | The source has authoritatively finished this request under its own rules. It is not merely all bytes uploaded, checks completed, an empty task list or the recipient closing a tab.                                                 |
| Upload/correction closure       | No further ordinary submissions or self-corrections are admitted. Q03 already preserves the source-owned reopening/correction route after closure.                                                                                  |
| Read-only return-access end     | The source's finite boundary for revisiting this request's permitted outcome/history/current files. It can differ from the upload deadline.                                                                                         |
| Session/assurance expiry        | The current proof/session must be refreshed under Q01/P4/P12 if return access still exists. Refreshing identity does not extend the business access window or undo revocation.                                                      |
| File/representation eligibility | Each current original and preview still requires current source authority, safety, integrity and qualified serving. A window that remains open cannot override a later restriction or make an unqualified representation available. |
| Retention/disposition           | How long the source must or may keep evidence. Retention does not grant recipient access, and ending recipient access does not delete files or history.                                                                             |

[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), current guidance inspected today, distinguishes idle/absolute session expiration and server-side invalidation, with reauthentication after expiry. That supports keeping session validity separate from a business access period. It does not define Asym's period or authorize extending it. Existing Q01 assurance remains binding; no new authentication system or timeout number is proposed.

## Practical alternatives

| Option                                                     | What the recipient gets after successful completion                                                                                                                                                                         | Benefit                                                                                                              | Cost                                                                                                                                                                |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Time-limited read-only return access (recommended)** | Until the source's communicated end, currently permitted completion status, concise history and the final/current eligible file set. View and Download remain independent qualified actions. No ordinary upload/correction. | Smooth continuity for checking the outcome or obtaining an allowed own-file copy later, without a permanent archive. | Extends the period of possible metadata/byte disclosure; needs an explicit finite end and current permission/serving controls.                                      |
| **B — Time-limited status/history only**                   | The permitted completion result and concise Q05 history remain visible for a communicated period. File content is no longer exposed through this completed-request view.                                                    | Retains evidence of what happened with narrower post-completion byte disclosure.                                     | A person needing the file itself must use an existing local copy or a separately authorized source route. Metadata remains sensitive and still needs an access end. |
| **C — End ordinary return access at completion**           | The authorized completion response confirms the outcome; subsequent returns receive only an appropriate safe help/denial route unless another source authority applies.                                                     | Smallest ongoing exposure and a simple purpose cutoff.                                                               | Can feel abrupt and make ordinary later verification depend on staff. A remembered/expired link must recover usefully without revealing private metadata.           |

All options preserve source evidence and existing specialist rights. B is not a total information blackout; C is not deletion. Neither narrower option prevents someone retaining a copy they already downloaded. A grants no superseded bytes: Q05's concise history remains metadata-only for those occurrences. No option grants a personal archive, cross-request library, public sharing, bulk export or restoration.

The comparison keeps the post-completion period finite under A and B without choosing a number. It does not assume B's metadata access lasts forever. Under A, expiry ends this ordinary return grant; continuing to show private receipt/history afterward would require separate authority rather than an unannounced permanent metadata fallback.

## Concrete UX if A is selected

1. **At actual completion**, lead with **Request complete** only when the source says so. Explain the completed outcome and any next step. Show the finite return-access end with an understandable date, time and timezone; distinguish it from the earlier submission deadline.
2. **Make read-only meaning obvious.** Keep the source-approved final/current file rows, qualified View/Download and concise history. Remove ordinary upload/correction controls instead of leaving a wall of disabled actions. Offer the existing source-owned help route for a genuine correction or concern.
3. **Use the same task context on return.** No mandatory new portal account, general “My archive,” or extra confirmation just to read an otherwise admitted result. Reapply Q01 assurance when it expires, then current source authorization; being authenticated alone is insufficient.
4. **When a file becomes unavailable**, explain the permitted current status safely. Completion is not a perpetual safe-file verdict. Do not substitute an older file, silently serve a preview as original, or reopen a superseded member.
5. **At the access end**, stop new reads under this grant and present a safe next step. Example, where its disclosure is allowed: **Access to this request has ended. Contact [approved route] if you need help.** On anonymous or enumeration-sensitive paths, use the source's more neutral response. Do not claim the record was deleted.
6. **Handle bookmarks deliberately.** A saved link is a locator, not lasting authority. It must not reveal private filenames, outcome details or recipient identity before current admission. Avoid a broken-page dead end and avoid suggesting that resending the old link automatically renews access.
7. **Do not manufacture communication or proof.** No automatic expiry reminders, new emails, summary-PDF generator, read receipt or forced “download now” flow is selected. An existing communication purpose may later carry the actual access policy when separately authorized.

[GOV.UK Confirmation pages](https://design-system.service.gov.uk/patterns/confirmation-pages/), current guidance, recommends clear outcome/next steps and helpful return behavior for people who bookmark the page. It supports planning the return journey, not permanent public receipt access or a mandatory PDF export for Core.

Illustrative completion copy:

> Request complete  
> You can return to view this result and the files available to you until [date, time, timezone]. This request no longer accepts uploads or corrections.  
> [Current eligible file actions]  
> [Concise submission history]  
> Get help with this request

The wording is conditional on actual qualified capability and current source policy. The date is an access boundary, not a guarantee against earlier security/privacy restriction or a promise to retain content contrary to source obligations. Avoid overwhelming the ordinary screen with hypothetical warnings; explain an earlier change when it actually occurs, within allowed disclosure.

## Issues to pressure-test after the founder answer

- **Define the exact transition.** Normal success must be distinguishable from cancel/withdraw/deny, manual archival, security closure and an abandoned request. A is not an automatic grace period after every adverse event.
- **Qualify the finite policy before activation.** The source must define how the end is derived, which audience/actions it covers and how the recipient learns it. “Keep access for a while” is not an implementation contract. Do not silently select a universal duration during this question.
- **Do not auto-renew it.** Reading, downloading, reauthenticating, retrying, emailing the same link or receiving a technical event must not push the end forward. An explicit source-authorized extension or reopening is a separate accountable decision, not an incidental UI behavior.
- **Keep exact current file scope.** “Final files” is the source-approved set, not every upload ever received or whichever provider object was modified last. Multiple final/current members may exist; Q05 continues to deny superseded content in this profile.
- **Align the promised experience with source custody.** A should provide real qualified reads for its declared ordinary profiles, not a nominal window filled with unavailable placeholders. It must still respect actual restriction, integrity and disposition; no new retention override is implied.
- **Recheck the boundary everywhere.** Metadata, history counts, previews, original bytes, old links, range/resume, cached responses and help paths cannot bypass the access end. In-flight stream handling follows Q04/P12's qualified rules; no recall of bytes already displayed or downloaded is possible.
- **Keep expiry distinct from failure.** A temporary outage during an otherwise valid period is not expiry; an expired grant is not “try again” indefinitely. Current rights must be revalidated without losing the truthful business outcome.
- **Help is not implicit release.** A responder can explain what is possible under their current authority. No personal inbox attachments, automatic historical export, guaranteed recovery, or default extension follows.
- **Do not force deadline anxiety.** Communicate the actual end clearly, without unsupported countdown urgency or mandatory device download. Accessibility and mobile return flows must work without relying on a disappearing toast.

These are review implications, not a newly ratified specification. No duration, polling frequency, service-level promise, expiry-reminder schedule or file-retention rule is established by this note.

## Suggested founder question

“Once an ordinary document request is successfully complete, should the recipient have a clearly limited period to return and read the result, concise history and their final eligible files, or should file access end at completion?

I recommend time-limited read-only return access, with the end clearly shown and current permission still checked. They could confirm the outcome or get an allowed copy later, but could not upload, correct, reopen old versions or build an archive. A narrower alternative would keep only the status/history; the strictest option would end return access after the completion confirmation. We would choose the actual source-owned period separately, rather than inventing a universal number of days.”

This is one decision about post-success continuity. Do not bundle cancellation/security closure, superseded-byte access, a permanent account history or retention policy into the answer. After selection, adversarially review the complete return, reauthentication, expiry and help journeys before ratification.

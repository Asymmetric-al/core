## Ratified decision and amendments

**Q59-C01 — Scope and proportional alternative.** Allow optional personal Save for later for currently qualified staff and missionary readers of P28 organization-resource publications. Keep the complete required Resources search, categories/language, Open/Download and safe return available without saving. The strongest alternative is the same finished library without an Asym personal saved list; choose A for deliberate cross-visit/device return, without claiming measured Asym demand, task savings or cost benefit. Preserve Q58 shared/independent publication identity, Q55 review, Q57 reports, Support Staff guides, ordinary evidence and P23 saved-view ownership. No arbitrary file, donor-feed post, Support guide or public-CMS record is automatically in this corpus. No global favorites/collections platform, subscription, notification, reminder, assignment, read receipt, training completion, popularity analytics or curator obligation is added.

**Q59-C02 — One person’s preference, exact current context.** One active saved relationship exists per stable qualified native human/principal owner, exact Tenant, environment, actual existing source organization and publication identity. Reuse existing source organization identity; do not invent a new organization axis where the source already fixes it. The same person's qualified staff/missionary contexts may reflect that same private preference, but each request uses exactly its currently validated context for content and personal-purpose authorization; never union hats or other organizations. Derive owner/actor/scope from trusted native context, not caller fields, email, display name, a role label, Party or an assumed profile/person table. An inert persons/person_id or principal preparation seam is not an activated owner mapping. No automatic preference transfer on email match, account replacement or identity merge; any such mapping needs its own explicit qualified identity transition. No new login/account/Party is required merely to save.

**Q59-C03 — Source ownership and a narrow personal-maintenance purpose.** P28 owns the personal saved reference and its Save/list/Remove commands; P12/shared identity owns current principal/context and authorization; the publication owner owns all content/status/audience/current-head facts; custody retains its existing byte/version/disposition duties. Explicitly adopt a narrow own-preference purpose and shared field projection for qualified current organization participants, distinct from publication reading and curator management. Membership alone is insufficient: the actual purpose, capability, classification and all floors must permit each action/field. The smallest own-entry projection is an opaque entry handle, its own saved timestamp/state and permitted maintenance actions; it exposes no denied publication ID, name, URL, filename, thumbnail, audience or denial cause. Own-reference counts are counts of permitted personal relationships, never counts of hidden publications. Do not dynamically relabel protected resource fields to render placeholders. If own-preference authority is denied or unknown, serve no rows/counts/placeholders; use the actual safe account/privacy recovery route. Any required shared policy widening follows ADR0211 rather than masquerading as a UI preference.

**Q59-C04 — Exact target and qualified admission.** Save accepts only the exact currently admitted publication identity/lineage presented under the current source context and personal-save authority. Saving may use a qualified publication summary without opening, previewing or downloading the body; search visibility alone or unknown source qualification is not admission. Unsupported preview or a narrower byte action does not by itself disqualify otherwise lawful summary-based Save. Store a source reference, not duplicated content, signed URL, mutable title/path or byte digest. On return resolve only that publication's currently admitted head and current allowed metadata/actions. A separately authored language/audience edition or successor remains a different target even if bytes/title match. A safe current successor hint may navigate normally but cannot silently transfer the saved relationship. No draft/archive/old-version fallback, content retention hold or offline copy follows from saving.

**Q59-C05 — The simple complete interface.** Use the existing Resources experience and shared Base UI/base-maia components: one ordinary named Save for later command, changing to Remove from saved when confirmed saved, and one Saved for later destination. Keep Open/Download visually distinct and do not require preview. Use changing command labels with ordinary button semantics, not a changing label combined with an inconsistent pressed-toggle contract. No confirmation modal, reason, folder/name/tag, staff approval, rating or new tenant setting matrix is required for ordinary Save/Remove. Default the list to newest actual unsaved-to-saved transition first with a stable unique opaque tie-breaker; same-state Save and content updates do not rewrite that saved date or reorder it. Display normal current qualified resource metadata and Q55 information, with secondary personal Saved date where useful. Empty copy is “No saved resources yet” plus Browse resources. Save from a usable resource does not move focus or navigate away; Remove in Saved restores focus to the next sensible item or list/empty heading. Accidental Remove is corrected by a fresh currently qualified Save, not a trash/restore engine or historical access grant.

**Q59-C06 — Known unavailable, unchecked and inaccessible personal state.** When own-entry access remains qualified but current publication access is definitively unavailable, retain a neutral “Unavailable resource” row with only its permitted own-entry metadata and Remove from saved. Do not expose the former title, target identifier, cause, hidden edition or resource existence beyond the person's already-authorized personal relationship. When current publication evaluation cannot complete, use “Could not check this saved resource” with Retry; do not call it revoked, deleted, empty or permanently unavailable, or erase the preference. Remove may still operate if its independent current own-entry authority is known. If list/own-entry authorization or loading itself fails, show a safe list failure/recovery state without rows or fabricated counts. Never interpret a security-uniform not-found response as authoritative resource disposal. Remove addresses the opaque owned entry without requiring forbidden target disclosure or content access. An opaque handle is not authority; forged other-owner/scope handles remain uniformly denied.

**Q59-C07 — Preference lifecycle and reappearance.** Saved versus removed is authoritative personal intent; resource available/unavailable/unchecked is a current derived presentation, not copied publication state. Resource withdrawal, audience removal, transient lookup failure, ordinary logout or context switching alone does not delete or reassign a saved preference. If that exact publication later becomes currently readable again and the preference is still retained/saved, it may show its newly qualified current metadata automatically; this neither republishes the resource nor restores an old grant. A deliberate Remove remains removed through republish, later access restoration, retries and backup restore. A fresh deliberate Save is a new unsaved-to-saved transition with a new saved time. Loss of current organization/account/personal-purpose authority fences the whole personal surface; no cross-organization aggregate or alternate-hat bypass. Actual governed offboarding/privacy/records/source-disposition cleanup may retire references under C13; a routine unknown/denied read is never that cleanup authority.

**Q59-C08 — Explicit desired intent, concurrency and no-op ordering.** Use explicit desired Save or Remove with an exact current preference/control basis and stable operation identity, not a blind durable toggle. One authoritative command boundary linearizes the same owner/scope/publication relationship; stale conflicting intents do not silently overwrite a newer admitted intent. A new currently authorized command that matches the visible state must still fence an earlier opposite intent when necessary: absent→Remove→late old Save cannot recreate a relationship, and saved→Save→late old Remove cannot clear it. This control ordering does not create a new saved date, recency change or fabricated content/business event. A matching replay of an already admitted operation returns its original result and never advances ordering. Reusing an operation identity with a different owner/scope/target, desired state, expected basis or other immutable intent payload is a conflict. A stale fresh command preserves safe user intent, refreshes actual current state and requires a deliberate current action where still wanted. Do not create ordering rows for arbitrary hidden targets or forged handles; admission/ownership and finite abuse limits apply. A no-record Remove acknowledgment/fence requires a genuine server-bound own preference/control or pending-intent basis, or an exact currently eligible target qualified for that personal purpose; only a complete scoped determination establishes absence. A denied, failed, incomplete or otherwise unknown lookup is not known absence and cannot authorize arbitrary control allocation. Minimal control evidence or expired-intent rejection must prevent ABA after cleanup; a forgotten old request is never treated as a new Save.

**Q59-C09 — Coherent outcomes and truthful recovery.** Commit personal effect, ordering basis, original operation result and any required source/audit evidence coherently; rollback reports no accepted effect. At authoritative acceptance, revalidate relevant current personal/source facts after any waits and order admission against their actual revocation/withdrawal boundary. Lost publication eligibility prevents a new Save; an independently authorized known-own Remove does not require resource reading, while loss of its own purpose still blocks it. An unrelated metadata edit is not automatically a preference conflict when target identity, relevant basis and current qualification remain valid. Check authenticated current receipt/own-purpose scope and recover the original operation outcome before applying new-save eligibility, rate or same-state logic, while reapplying current disclosure rules. A committed Save followed by withdrawal or later Remove must not be reported as an uncommitted failure or reapplied as new work; show only the currently permitted original result and present state. Lost responses remain checking/unknown until authoritative recovery resolves them; preserve a useful page and offer Retry. Pending feedback may be responsive but must not assert durable Saved or Removed solely from local state; no hidden offline mutation queue. A late response from an old session/context/revision cannot overwrite newer UI or expose old metadata. Required P12 tier-specific audit/outbox rules remain; no new email, external dispatch or bookmark-specific background workflow is needed to commit a preference.

**Q59-C10 — Structural data integrity without freezing a schema.** Enforce non-null trusted owner and exact Tenant/environment/source organization for retained preferences and control evidence; structural tenant-aware relationships bind the actual publication/owner scope. Enforce the one-active-relationship cardinality, valid revisions and timestamps, immutable ownership/target binding, bounded payloads and valid saved/removed/control combinations through database constraints plus the authoritative command. An allowed update cannot reparent, retarget, spoof actor, widen fields or revive stale intent. Store actual server-observed save/effect time as timezone-aware instants; localize display without client clocks authorizing order. Choose native key/index/enum representation during design, not generic JSON with caller-controlled authority or mandatory new table names. No money/amount precision changes arise. Delete/disposition behavior must neither cascade-delete required audit/replay evidence nor let a personal preference retain resource bytes indefinitely. Any severed target/retired pointer is an explicit governed cleanup state with tested constraints, not an accidental orphan. Existing historical publication identity may be retained only under its own lawful source retention.

**Q59-C11 — P12, coarse RLS and every effective access path.** All personal preference and referenced-content release/mutation uses the one current P12/source boundary and shared static/subtract-only projection. Preserve Core's coarse Tenant RLS contract: do not import Supabase's generic per-user RLS example as a second identity/capability engine. Application and database Tenant Authorization Context must agree at the qualified boundary, be established from trusted native authority rather than caller fields, and fail closed when absent, forged or mismatched. Prove transaction/connection scope and pooled reset after success, failure, cancellation and retry; do not introduce a second identity/capability resolver in SQL. Where coarse RLS cannot make a raw table/collection safe, revoke that direct browser/Data API path and expose only the qualified source command/projection. Prove effective named/default/inherited grants, roles/owners, SELECT/INSERT/UPDATE/DELETE and old/resulting-state checks, including USING and WITH CHECK, triggers, RETURNING, UPSERT, MERGE, COPY/bulk/admin/GraphQL/views/functions, collection and privileged service/operator paths; unused doors remain closed. PostgreSQL can derive a missing WITH CHECK from USING in applicable policies, but actual effective checks and all permissive-policy OR combinations must be verified; a narrow new policy does not narrow an existing broad one. FORCE RLS does not constrain BYPASSRLS. Invoker views/functions still need actual grants/context; necessary definer code requires explicit callable-role closure, fixed safe search_path, trusted scope and no caller-asserted owner privilege. REVOKE FROM PUBLIC alone does not prove removal of named/default EXECUTE grants. Do not inherit the CRM named-view RPC security pattern without qualification.

**Q59-C12 — Supabase Auth and live source currentness.** Authenticate through the actual shared native session and qualified human/principal/assignment mapping. Validate the selected Tenant context, ownership, active membership/assignment, source purpose and current governance/identity-transition fences at each protected boundary; unknown or missing mappings fail closed with safe recovery. A valid JWT, auth.uid(), verified email, authenticated database role, app_metadata claim or selected role is not by itself current resource or personal-purpose authority; user_metadata is never authority. Logout/user deletion/token refresh or cookie removal must not be assumed to invalidate every already-issued token immediately. Use the repository's qualified shared session/currentness integration rather than inventing a second auth/session system. Use the existing qualified cookie-command origin/CSRF/request-integrity boundary; GET, rendering, prefetch, hovering, search and opening a resource never perform Save/Remove. Do not claim to recall metadata or bytes already delivered to a reader. Current prepared persons/principals/assignment RPCs are not proof this integration is wired. Source revocation/withdrawal and privacy restrictions win over stale cache/replay/restore and downstream byte paths. A save creates no Storage grant, signed URL, download/prefetch or provider entitlement; actual Open/Download continues through its current qualified owner.

## Vocabulary decision

No glossary addition or refinement is proposed. Existing Organization-managed resource library and Resource Problem Report remain authoritative and exact; Files retains32 definitions. “Save for later”, “Remove from saved” and “Saved for later” are the interface labels. A personal saved reference is the source-owned private relationship described in C02–C04, distinct from a saved query, downloaded file, subscription or read/completion fact. An extra generic Bookmark/Favorite domain term would add ambiguity rather than resolve it.

## Complete UX and lifecycle

An illustrative reader finds permitted guidance, selects Save for later and keeps reading. Confirmed feedback says “Saved for later” with a quiet route to the personal destination; no body fetch, subscription or new task follows. Another supported session reads the real current preference. Saved for later uses ordinary current resource rows and a secondary Remove command. It does not require a directory/profile picker, curator mode, new account or collection setup. A staff reader follows the same source-qualified journey in Mission Control; a missionary uses their own workspace. This is intended UX, not tested screens or observed user behavior.

The only new durable product fact is a personal saved choice. Available/unavailable/unchecked is derived at current read time. Technical control revisions and operation receipts are not new publication states or a user-visible event stream. A source-disposition event can end a reference only through actual governing cleanup authority; an indistinguishable not-found result cannot. If the source's own retention removes the publication identity, the reference must be retired/severed through its explicit constrained cleanup path, not left as an accidental foreign-key orphan or used to keep the bytes forever.

## Recommended genuine next question

**Should staff be able to start a new ordinary document request from a reusable item checklist, or write the items individually each time?**

| Option                                                                                   | Practical result                                                                                                                                                                                                                                                                                           | Real tradeoff                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Optional reusable item sets, copied into an independent new draft (recommended).** | Authorized staff maintain a small source-qualified collection of ordinary request starters. Choosing one copies its selected current item definitions/instructions into the new draft. Staff review and adapt that draft before the usual source-owned issuance. Starting without a set remains available. | Less repeated authoring and fewer accidental omissions where the same legitimate request recurs. The collection needs an actual maintainer, current eligible content, tenant/source permissions and a clear copied-draft boundary; stale or overbroad defaults can repeat mistakes. |
| **B — Individual request authoring; no new tenant item-set catalog.**                    | Staff prepare each new request with the normal item authoring and issuance paths. Existing specialist/workflow/form/message capabilities remain in their owners.                                                                                                                                           | Smaller product and less template upkeep, especially for infrequent or highly varied work. Repeating useful wording/items costs effort and can drift. It does not require a speculative clone-request feature or copying live recipient/evidence history.                           |

Illustrative situation, not observed ministry research: Elena regularly requests an equipment handover inventory and condition photographs from different workers. Under A, she selects an Equipment handover starter, sees its items in a new draft, removes anything irrelevant and adjusts the instructions before issuing to Nora through the normal source action. Under B she writes those items each time. Neither path copies the previous worker, files, review decisions, messages or access period. A mistaken template edit cannot change Nora's already issued request.

Recommend A as a bounded authoring convenience, conditional on real repeated use making it worthwhile. There is no measured Asym frequency, time saving or template-error rate in this session. B is the stronger option if requests are mostly one-off or there is no accountable upkeep. No artificial third choice, universal rule builder, automatic issuance or mandatory template use is needed. Comparative external product evidence belongs to the parallel UX research; this owner note does not present another agent's vendor reading as its own authenticated product test.

## Necessary boundaries for either option

1. **Optional starting point, not live policy.** A proposes a reusable ordinary request item/instruction set into an independent unissued draft. It is not an issued request, access grant, approved evidence, reusable communication or execution recipe. B leaves normal authoring complete. No mandatory-template ceremony is introduced.
2. **Real narrow owner.** The ordinary request source owns supported item definitions and legitimate scope; custody does not. Catalog authoring/use/disclosure stays inside current tenant/source/P12 rules. Different sources cannot reuse a preset merely because its name sounds suitable. No universal all-staff catalog visibility is inferred.
3. **Copy appropriate structure, not previous-person state.** Start with reusable source-qualified item labels/types/instructions and their actual supported definition fields. Do not clone recipient identities, subject records, submissions, approvals, messages, protected links, grants, timers or prior private answers. A reusable source-purpose description does not itself establish the new instance's legitimate purpose or subject.
4. **Independent reviewable draft.** Make copied items visible/editable through normal source authoring before issuance; show what will be requested without forcing a redundant approval. Do not silently fill private defaults or auto-issue. Preserve permitted preparation if a template disappears, permissions change or a check fails, while current disclosure/source restrictions still govern.
5. **Stable adopted meaning.** An edit to a starter changes future uses, not existing copied drafts or issued requests automatically. Keep enough actual copied-definition/source provenance for truthful diagnosis. Retention of a past starter does not grant access to forbidden historic content. A real current legal/privacy/source restriction may still fence affected use; snapshotting is not a bypass.
6. **Current instance qualification.** Actual recipient, source/record/purpose, instruction/item validity and Q25 review readiness are checked at the existing real issuance boundary. Source-required statements, specialist restrictions, separation of duties and recipient proof remain. Reuse valid derived defaults where current owner rules permit them; do not force staff to reselect a good team merely because a starter was used.
7. **No propagation shortcut.** Updating a starter cannot perform Q33 removal, Q34 cancellation, Q36 additions or Q37 instruction revisions. Issued work uses those exact source commands. Accepted evidence/history, completed/canceled requests and fixed access ends are untouched.
8. **No hidden platform expansion.** No condition builder, automatic scheduling, branching, per-template workflow, cross-tenant import/export/marketplace, AI generation, new attachment corpus, clone-live-request action or email default is selected. Templates may help repeated authoring without the full future Studio.
9. **Useful upkeep and recovery.** A needs an actual responsible maintainer and a way to stop future use of unsuitable starters without deleting existing request truth. Exact edit/withdrawal concurrency and copied-draft behavior belong in the selected-answer review. Do not qualify a catalog solely from a template UI screenshot.
10. **Human clarity and minimum friction.** One optional starter choice, visible item set, ordinary adjustments and usual issuance. Manual preparation remains available. Sparse/unsupported/obsolete starters have an honest route; keyboard/mobile/AT/localization and source-safe display still apply. Do not claim observed time saving or corpus quality.

# Phase 29 Q08 — fresh read access after ordinary expiry

Researched 20 October 2026, Asia/Bangkok. The parent reports Q01–Q07 and all amendments are ratified. Q07 fixes the ordinary completed-view ceiling at up to 720 elapsed hours from authoritative normal fulfillment, preserves earlier binding limits and prohibits incidental extension or revival. **No Q08 answer is selected by this research.**

This is current public primary-documentation research and product reasoning. No authenticated comparator account, private document, provider mutation, message, real grant or recipient test was exercised. Only this research note was written.

## Recommended next decision

Ask whether **specifically authorized source staff may make a fresh, narrowly scoped, finite read-access decision after ordinary completed-view time expiry**, or whether the ordinary product should keep its governed help route **without adding that fresh-grant capability**.

Recommend **A: allow the fresh source-authorized decision**, for a continuing legitimate request-specific need and a currently eligible recipient/content scope. It should use the existing source/PDP/custody ownership and the same request experience. The expired grant and its original end remain historical facts; the source does not make the original deadline untrue.

This is a product recommendation, not a universal nonprofit practice or evidence that a fresh grant must always be approved. B is a strong, simpler choice if the ordinary deadline is meant to end this self-service purpose and a further grant is not part of it. Two choices are enough; automatic renewal is contrary to the ratified baseline and is not a meaningful third alternative.

**No fresh duration, count limit, lifetime aggregate cap, notification, grace period, extension-before-expiry behavior or approval hierarchy is chosen here.** Selecting A would require those relevant boundaries to be expressly resolved in the source contract before activation. It does not silently mean another 30 days, once only, indefinitely repeatable, or a free-form expiry picker.

## What A must mean to remain compatible with Q01–Q07

**Ordinary expiry is the trigger, not sufficient authorization.** The source must establish that the ended access was an ordinary time-bound view and that a fresh act is allowed now. A “time expired” status does not by itself authorize access when an underlying purpose deadline, recipient reassignment, privacy decision or security restriction still forbids it.

**A new act does not rewrite the old one.** Preserve the original completion, 720-hour maximum, earlier controlling end and ended grant. The fresh act has its own current source basis and finite scope; it is not changing the prior expiry to make the historical grant appear never to have ended.

**Specific staff authority matters.** Being able to view a record, answer a help ticket or administer unrelated tenant settings is not automatically permission to grant recipient access. Use the existing source/PDP delegation rather than inventing a universal staff override or another permission engine.

**Current exact scope matters.** Do not grant an entire site, organization, library, recipient's other requests or an entire folder merely to satisfy one request need. Limit the act to the qualified same recipient/request and eligible own current members. Q05 still excludes superseded content; Q04 still independently qualifies originals and previews. Any new recipient, broader purpose or previously unavailable historical file is a different source decision, not smuggled into this recovery action.

**No security or privacy bypass.** Revocation, account compromise, a binding purpose stop, restricted original, quarantine, disposal or changed recipient identity requires its governing source path. A fresh-grant button cannot clear those facts. Retained bytes or an audit hold do not establish reader authority, and an absent record cannot be recreated from a stale cached link.

**Recovery is not automatic renewal.** A request for help, an old link visit, a successful login, a reminder, staff reading a ticket or a duplicate grant command cannot create a fresh period automatically. A later repeat need requires whatever explicit repeat policy is ultimately adopted; this question does not assume unlimited grants or an arbitrary one-time restriction.

**A new grant is not necessarily a new user-visible task.** It can use the existing completed-request surface without reopening submission/correction or generating another application. Do not require a duplicate request solely to create authority. The grant fact must be new; visible URL/token behavior requires later source/security design. An ended capability token cannot itself become valid authority again just because the stable page has new access for a currently confirmed recipient.

**No period is inferred.** The new act must eventually have a concrete finite start/end under its resolved policy before it can be enabled. Q07's ordinary 30-day cap does not, by itself, select the fresh grant's period or anchor. Do not present “another 30 days,” a number of extensions, a lifetime total or a reminder schedule as already decided.

## A small plausible journey

These are interaction recommendations to evaluate, not implemented screens or a selected workflow engine.

### Recipient: use the existing help route

1. A return to an ended request shows only the source-permitted neutral state and the established help route. Where request existence may be disclosed, “Access has ended” is appropriate. Otherwise use a generic unavailable-link response. Neither an **Expired** badge nor the existence of a **Request more time** action may disclose a private request to someone without current authority.
2. The person contacts the responsible source through that existing route. Avoid a separate renewal portal or forcing them to retype a verified request identifier already safely carried by the authorized context. Do not auto-send a message from a page view or silently turn help into an approval.
3. After a genuinely approved fresh grant, the recipient uses the usual Q01-qualified entry to the same completed request. Show the actual current finite end and eligible read actions. Do not restart downloads automatically, ask them to submit again or create membership.

The recipient should never see “Your access is renewed” merely because a help request was sent. This note does not select an automatic grant-notification email or new in-app inbox. Any existing authorized delivery/communication path must truthfully distinguish request received, source decision committed and message delivered.

### Staff: one contextual review and one explicit action

1. Open the existing source request/help context under current staff permission. Show the permitted intended recipient, source purpose, current eligible members, why the original access ended and relevant current blocking restrictions. A staff view may contain facts the recipient is not allowed to see.
2. Where A is allowed, present one compact review of **who**, **which request/content/actions**, and the **actual finite end produced by the resolved policy**. Reuse the source's existing case/purpose evidence. Do not introduce a mandatory essay, arbitrary date picker or second approver merely because the action changes permission; any such requirement needs its own source justification.
3. Use an explicit action such as **Grant read access**. The committed result says what access was granted and its actual end. It must not claim a message was sent unless delivery was separately performed and confirmed. A lost response reconciles the same issuance instead of creating another grant from a second click.

One intentional review/action is appropriate because this changes permission. A second generic “Are you sure?” confirmation adds little if it repeats the same information. If a source requires stronger authorization or a separate approver, honor that contract without generalizing it to every ordinary case.

If blocked, staff see a truthful permitted explanation and the existing owner escalation route. Do not show a tempting universal “Override” control or suggest removing a restriction just to complete the task.

### Accessible and low-friction details

Retain the Base UI/base-maia request structure and the already-ratified mobile, keyboard, speech, screen-reader, focus and re-entry requirements. The end is ordinary readable main content, not hover-only or a ticking display. Clear disabled/blocked explanations must be available without hover, and a status update should not repeatedly interrupt a reader.

The minimal recipient journey should work without downloading all files just to request help. Use the existing qualified assistance route, not an unselected private offline cache. Device-local copies remain outside expiry recall, as already decided. No claim is made that this flow has been tested with recipients or assistive technology.

## Distinctions the founder question must preserve

| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Entry token or browser proof expired while source access remains valid                     | Q01 re-entry/recovery; no fresh source grant is required merely to authenticate again.                                                                |
| A recipient lost a still-valid link                                                        | Repair the entry route under its existing policy; resending is not a grant extension. SafeSend's active-only resend rule illustrates the distinction. |
| Ordinary completed read period ended, with a continuing current permitted purpose          | The actual Q08 choice: a fresh authorized read act under A, or governed help without this new capability under B.                                     |
| Binding underlying purpose access ended or a security/privacy denial remains               | The responsible source contract governs. Q08 does not override it by labelling a grant “fresh.”                                                       |
| A preview failed or rendition expired while source permission remains                      | Q04 qualified representation recovery; no grant extension or new authority is needed just to repair a technical representation.                       |

## Is a different next question more urgent?

Q08 is a strong next decision because Q07's end state already promises governed help but intentionally leaves its possible outcome unresolved. Decide whether this capability exists **before** choosing its duration, number of uses, staff-facing date controls or communications. Otherwise an interface could accidentally promise extension when the product has never authorized it.

Active-request lifetime remains an important independent source qualification dependency. It must be resolved before activating affected profiles, but it does not prevent asking this narrowly framed post-completion question now. If owner inspection discovers that an existing binding source contract already decides the recovery outcome, reconcile that authority rather than asking Conrad to override it through a generic preference.

Do not ask for a reminder cadence next merely because expiry is now selected. Notifications do not resolve whether any new permission may be issued. Likewise, do not prematurely ask for “7 more days or 30 more days” before the existence/scope choice.

## Suggested founder framing

> After an ordinary completed request's read-access period has ended, should specifically authorized staff be able to grant the same intended recipient fresh, narrowly scoped, finite read access when the source still permits that purpose—or should help leave the request's read access ended, using only already-existing independent source routes?

Recommend **A — Allow a fresh source-authorized read grant**, with the unchanged request completion and old expiry preserved. Explain its added authorization and operating cost. Offer **B — Help without adding post-expiry read grants** as the strong simpler alternative. State that approval is not automatic, binding security/privacy/source limits still win, and no new period, repetition limit or notification policy is being selected.

## Evidence still needed after a choice

The current evidence does not quantify how often Asym recipients need later access, whether the first 30-day period is usually useful, or whether staff can responsibly handle the new act. It does not prove effective source delegation, exact recipient/content scoping, race-safe issuance, private ended-page responses or usable recipient/help flows.

If A is chosen, the subsequent adversarial review should test whether repeated grants could defeat the intended purpose limit; whether the staff role can actually grant; whether a broad site/member permission is accidentally inherited; and whether a changed recipient or restricted file slips through an apparently routine renewal. Preserve old ends and replay identity, deny unknown policy, and distinguish committed access from notification or browser success. Those are proof obligations, not claims already verified here.

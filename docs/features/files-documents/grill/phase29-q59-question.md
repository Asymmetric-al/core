## The next decision

**Should qualified staff and missionary readers be able to save organization resources to a private “Saved for later” list inside Asym?**

| Option                                                      | What the reader gets                                                                                                                                                                                | Main tradeoff                                                                                                       |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **A — Optional personal Save for later (recommended)**      | A simple Save/Remove control and a private Saved for later destination within Resources, alongside ordinary search and navigation. Saves persist for later authorized visits and supported devices. | Adds a small personal preference with real persistence, privacy, permission-loss and recovery behavior to maintain. |
| **B — Search and navigation without a personal saved list** | The complete qualified library: search, categories/language, useful navigation, return position and permitted stable links. Browser bookmarks remain available where appropriate.                   | Leaner product and no new saved state, but repeat readers must search again or manage links outside Asym.           |

I recommend **A**, narrowly. Remembering a useful resource is a familiar convenience that can reduce repeated searching. It should require no naming a collection, choosing a folder or configuring a notification. B remains a strong alternative for a modest easy-to-navigate library. We do not have Asym usage evidence proving repeat-resource frequency, demand, conversion gains or time savings; this is a product judgment informed by comparable products, not a measured ministry workflow.

The proposed meaning is **a private reference to the actual source publication**, reopened under current permission. It is not a downloaded copy, frozen file version, subscription, shared collection, read receipt, training completion or curator task. The source's already-qualified current head may change within that same publication identity. A separate Q58 publication remains separate even if its title or bytes match; a permitted successor hint does not silently transfer a saved relationship.

## A concrete user journey

Illustrative, not observed ministry research: a missionary finds a useful organization guide on a phone and wants to return from a laptop next week. Under A, they select **Save for later**, receive a truthful saved state and later open **Resources → Saved for later**. The resource opens only if it is currently permitted. A staff reader has the same simple journey in their own qualified staff context, without entering curator tools or impersonating a missionary.

The secondary action is **Remove from saved**, which changes only that person's preference. It does not delete or withdraw the resource. The primary resource Open action stays visually clear. Empty Saved explains how to save and offers **Browse resources**. Loading, failure and no saved resources are visibly different. A failed save preserves a usable page and offers retry; an uncertain response does not falsely promise persistence or ask for a fresh blind toggle.

This describes the proposed experience, not a finished screen. Use existing shared components and tokens; a labelled control must work with keyboard, touch and assistive technology without hover. If using a changing action label, follow ordinary command-button semantics; if using a stable-label toggle, expose its pressed state coherently. Keep resource names, language and source context readable at narrow width/zoom. No persistent sensitive browser cache or offline-content promise is implied.

## Adversarial check of the recommendation

### What could go wrong with this answer?

The list may add clutter or a misleading promise of offline/permanent access; a saved name could leak after permission loss, and a local-only icon could falsely imply durable saving. Those are meaningful design costs, not reasons to build a complex bookmarking system. A must stay source-bound, private, small and truthfully persisted; B avoids those new costs.

### What hidden assumptions are we making?

That some qualified readers revisit particular resources, and a personal list is easier than repeating search. We have no measured Asym frequency or task study. Actual staff/missionary return tasks and content volumes would verify that assumption. An illustrative guide is not a discovered ministry workflow. No universal format/device/native persistence support is assumed.

### How does this affect the whole product?

It adds a personal preference in the existing P28 Resources experience. It does not change Q58 publication ownership/audiences, Q55 review, Q57 reporting, Support Staff guides, donor feed saving, ordinary-evidence views or File Manager custody. Do not generalize to a cross-product collection platform or infer downstream marketing/notification demand.

### How does this affect the end-user experience?

A supplies a short route back to resources a reader chose. Search remains the primary way to discover them. Explicit Save for later/Remove wording and a single destination are clearer than competing Bookmark/Favorite/Pin terms or mandatory organization. B keeps fewer controls but relies on repeated discovery or external links. Both need excellent mobile, accessibility and truthful current access.

### Does this follow modern best practices?

It follows a well-established optional saved-reference pattern in Confluence, Document360 and SharePoint. Proven presence is not proof of best fit or safe permissions. We deliberately reject Salesforce draft/archive fallback and SharePoint's unsupported-user false-save behavior where they conflict with Core's source/currentness or UX requirements.

### Does this fit Asym's existing repo and product direction?

Yes, if the existing resource owner and P12 integrate the private preference coherently. Existing saved-view and local donor-save code supply adjacent examples, not an implementation or authorization shortcut. Core's source ownership, one PDP, coarse RLS and field projection remain binding. No fine-grained client/SQL policy fork or new provider is needed merely to choose A.

### Should we adjust the recommendation?

Recommend A as a small optional private saved-resource list, retaining B as the lean alternative. Do not include subscriptions, folders, shared lists, history copies or analytics to make A seem more valuable. The founder decision is whether this convenience belongs in the product. Exact selected-answer safeguards and acceptance criteria follow the answer; they do not get ratified by presenting the question.

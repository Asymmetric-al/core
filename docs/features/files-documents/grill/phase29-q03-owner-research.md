Bounded owner research, 20 October 2026. No new decision is selected or ratified by this note. No shared repository document, code, GitHub record, permission or provider was changed. The parent reports Conrad explicitly ratified Q02 A and all review amendments; the local decision log was still recording the earlier selection status when this read began, so that lag is not treated as a reversal of the founder's latest answer.

## Recommended next question

**For an ordinary new native document request that is still awaiting a review decision, may the recipient send a corrected file themselves, or must the responsible reviewer first ask for a correction?**

Recommend allowing the recipient to **Send corrected file** while the source still permits submissions to that pending request. This is a new immutable submission version presented for review, never overwrite or deletion. Once the source has accepted the evidence, closed the request or applied a stricter specialized rule, the source-owned correction/reopening route is required. The permission remains request-bound and current; Q01 identity confirmation and Q02 preview do not themselves grant the mutation.

This is the highest-leverage next decision because the newly selected preview lets someone discover an accidental wrong file. The next practical question is whether they can fix that mistake without waiting for staff. It determines the normal user action, reviewer versioning/conflict UX and source command. It does not require choosing a storage API or general workflow engine.

A third blanket option—any recipient may replace accepted evidence at any time—would conflate independent source acceptance/financial/application decisions with generic file state. It is not a defensible general default and need not be offered merely to fill three choices. A future exact source could support a governed post-decision correction, but that is different authority.

## Suggested founder wording

“Someone opens the file they just sent and realizes it is last year's document. Staff have not made a decision on the request yet.

Should they be able to send the corrected file immediately, or should staff have to ask them for a correction first?

I recommend immediate correction while the request is still awaiting a decision. Staff see that a new version arrived and review that exact version; the earlier submission stays in its proper history. Once evidence has been accepted or the request closed, its owner controls any correction. This would not let the person delete the evidence or change a completed decision.”

The ordinary explanation should avoid suggesting that opening the preview ends the opportunity to correct. **Viewing is not approval**, and the current contracts do not make a reviewer page view a universal lock. If a source deliberately needs a review freeze, it must be an explicit qualified source state with clear recipient UX, not a side effect of a browser request.

## Exact scope if A is selected

1. **Ordinary new native request profile only.** It does not rewrite Phase18 issued documents, Phase21 claims/attestations, Phase22/23 public releases, Phase28 resource publications or completed Phase41 decisions. Their correction mechanisms remain source-owned.
2. **Current permission and state govern.** The recipient must still have an admitted request and source permission; the request must permit a further submission under its current version, deadline and other rules. Preview access does not grant a write. Q03 does not renew an expired link/session or extend a due date.
3. **New version, never mutate original.** Use “Send corrected file” or equivalent honest action. Record exact predecessor/successor source occurrence and byte version without silently rewriting the received confirmation, accepted evidence links or old review.
4. **No approval inheritance.** The new candidate carries no older review/acceptance. Reviewer UI identifies which exact received version is being considered and that an authorized successor exists; a stale screen cannot unknowingly approve a different current candidate.
5. **Source operation defines the race.** A newly chosen local file or started transfer is not yet an accepted correction and does not silently invalidate a completed source decision. Admission of the new candidate and the review decision compare the same current source state/version at their authoritative boundary. If review/closure wins before the correction is admitted, the upload cannot supersede it and must explain the real source-owned next action. If correction admission wins, staff cannot submit a stale decision for the superseded pending candidate as though nothing changed. The exact pending/scan/readiness UI should be resolved in the answer's adversarial pass; no “uploaded means accepted” shortcut.
6. **Do not hide retained evidence or promise deletion.** Earlier versions remain under the source's access and retention rules. Q03 does not grant the participant a complete prior-version archive, nor make the old evidence publicly or broadly visible. Accidental sensitive-file withdrawal/disposition remains a separate source action.
7. **Retry is not correction.** Lost response/repeated click resumes the same source command and transfer outcome. Only a deliberate new intended submission creates the successor. Same logical key with different target/bytes conflicts; failed background work does not demand another upload identity.
8. **No extra platform.** Use existing shared source tasks, current permissions, private custody, version references and exact communication purposes. A correction does not require full Workflow Studio or a second inbox. Do not invent reminder/notification defaults in this question.

## Why the other candidates follow rather than lead

**Original-download rights** remain a real unresolved choice, since preview is not original download and unsupported preview cannot auto-download. It controls additional disclosure/export and offline handling. However, it does not solve the immediate mistake detected by View my submitted file, and existing specialized owner rights differ. Ask it later for the same ordinary native profile without altering P18/P21 rights.

**Access duration after submission/closure** also remains unresolved. The current owners already distinguish request due date, assurance/session lifetime, source read authority, preview expiry and original retention. A universal “keep it available N days” question now would risk conflating these. Resolve the request's correction/review lifecycle first, then ask a focused participant-continuity question using that lifecycle and exact source floors.

## What the parent should not accidentally ratify

- A general “any uploader owns/replaces the file” rule.
- Changes to recipient, document purpose, instructions, required item set or accepted business facts hidden inside replacement.
- A deletion right or automatic destruction of superseded bytes.
- Previous-version history, original downloads or post-closure duration merely because a new candidate is permitted.
- Reviewer-read telemetry becoming a workflow lock, or old approval moving to new bytes.
- A fresh global workflow run, communication replay or new account for every corrected file.

These are safeguards/dependencies for later answer review, not a selected Q03 amendment package. The parent should ask one initiation-policy question, receive the founder's answer and then perform the requested adversarial review before recording ratification.

# Phase 29 Q06 — a calm, bounded completed-request experience

Inspected 20 October 2026, Asia/Bangkok. The parent reports Conrad selected Q06 A: a bounded read-only completed view after normal successful fulfillment. Q01–Q05 remain ratified. This note proposes UX amendments and acceptance outcomes for the adversarial review; it does not itself ratify them, choose an access duration or certify implementation.

Scope is the ordinary native private-document request and the same currently authorized recipient. Successful fulfillment is a source fact. Cancellation, withdrawal, rejection, revocation, privacy restriction and retention remain separate source decisions. Q05 continues to withhold superseded content from this ordinary recipient experience.

This is official-documentation research and product reasoning. The prepared Q06 question was read. No authenticated comparator workflow, real recipient account, private record, original download, browser accessibility test or participant study was performed. No product code, provider state, messages or permissions were changed.

## Recommendation

Return the person to the same request, now clearly read-only: its actual completion outcome, currently permitted files and independently qualified View/Download actions, concise submission history, the applicable access-end information, and a real source-approved help route. Do not introduce another account, an archive dashboard, repeated confirmations or a new document library.

The initial completion message and a later return page should reflect the source's **current** permitted facts. A completion recorded yesterday does not guarantee that no later source-directed clarification or restriction can arise. Do not promise “nothing else is ever needed.” A is also not a fresh grace period: completing the request must not silently extend an access end that already exists.

Show the actual source-approved end clearly once the duration/start policy is resolved. Use an access-end statement rather than a promise of guaranteed file availability through every future restriction. Q06 does not select days, a clock anchor, automatic extensions, reminders or renewal behavior.

## Timing accessibility without renewing source authority

Assess **session inactivity**, **absolute session/proof validity**, **interaction/technical limits**, and the **source access-end policy** separately. They can overlap, but they are not interchangeable clocks. The later duration/anchor decision must include the applicable accessibility assessment, not simply choose a number and call it secure.

For a content-set limit subject to SC 2.2.1, document the actual mechanism or applicable exception. If the extension route is used, it has specific warning/opportunity/repetition requirements; a vague toast or reauthentication page alone is not proof. Do not label every security limit essential without analysis. Conversely, the accessibility workflow must not silently extend source authority after its authorized end.

Where an existing qualified session warning is appropriate, its action must say what it actually does. **Keep reading** or **Stay signed in** is misleading if the source access end has already been reached or cannot be extended. If only fresh proof is possible and the source still permits access, use the real re-entry route. If source authority ended, show the safe ended state.

Session-warning focus, keyboard operation and screen-reader announcement need real testing. Warn about an actual active session limit rather than showing repeated generic warnings on every completed page. Do not announce every countdown tick. Do not infer that DWP's sample timing is Core's required value or that an extension of a session extends the source's purpose deadline.

The Level AAA reauthentication/data-loss criteria add useful guidance but must not be misrepresented as AA. A completed read-only view should preserve safely recoverable task position through re-entry where possible. If a help form contains unsent input, its persistence/loss handling must follow its own qualified privacy policy; do not create a private offline cache merely to avoid retyping. None of this changes the already received evidence.

This note selects no timing mechanism, numeric warning lead, access duration, start anchor or renewal policy. Qualification of the actual policy is an activation requirement, not permission to leave it undefined forever.

A denied or expired anonymous link must not become a request-enumeration screen. Wording that distinguishes “complete,” “revoked,” “recipient changed” or “file deleted” is appropriate only where the source permits that disclosure. A neutral response may intentionally combine states; that is different from showing a false business fact.

## Calm access-end communication

Put the actual end in normal task content, near the completed status or a small access-details section. Keep it readable on mobile and available to assistive technology. Explain what will end rather than only saying “expires.” A recipient should be able to distinguish the completed business outcome from the remaining viewing opportunity.

Do not create artificial urgency with a permanent live countdown, flashing warning, forced download, repeated modal or message implying their evidence will vanish. No automatic expiry email/SMS/reminder is selected. If a later authorized communication uses this information, it must carry the actual policy and obey its own privacy/purpose rules.

The access end is an outer boundary, not a guaranteed service-availability commitment or immunity from earlier restriction. Avoid a long defensive disclaimer on every file; when an earlier change actually occurs, give its safe current explanation and route. The system's authority rules, not the warning copy, must enforce it.

If the source changes an end through an explicit authorized operation, refresh the permitted display coherently. Do not invent a new date in client code or conceal a real change behind the same “until” text. This is an accurate-display requirement, not a decision granting extension or selecting a renewal process.

## Minimization and existing boundaries

- Keep the same request/item context and only its currently permitted metadata. No account-wide completed-request archive, old thumbnails, internal review rationale, new recipient list or superseded bytes.
- Re-entry must not demand identity details that the existing qualified mechanism already has without a source reason. Preserve paste/autofill and useful error recovery; do not add memory quizzes or forced transcription.
- Expose no private descriptor in generic ended pages, page titles, URLs, ordinary analytics or unauthenticated help parameters. An approved opaque reference may support source help where allowed.
- “Read-only” describes the ordinary request mode. It does not forbid asking for help through an existing permitted channel, but help is a deliberate separate action and does not silently send content or alter the request.
- Source retention, legal holds, actual disposition, session invalidation and representation cleanup keep their own owners. Readback cannot extend them; ending access cannot authorize deleting required evidence.
- Q04's browser truth still applies. Download is deliberate, browser/device handling varies, and Asym cannot infer saving/reading or recall already emitted bytes.
- Current source remediations must be distinguishable from ordinary completed reading. A historical success label must not suppress a legitimate present source instruction or fabricate one.

These recommendations preserve the no-general-drive direction and existing stronger source rules. They do not authorize a new identity scheme, new permission engine or new notification program.

## Strongest B case

Status/history-only continuation would retain a useful outcome record while ending routine post-completion file-content disclosure. It is a genuine narrower product choice; someone needing a copy could use a previously saved file or separately authorized source route. The cost is potential extra work for that person and staff, whose frequency is not established.

Conrad chose A because current-file readback remains useful in the completed mode. That choice still requires original/preview qualification and actual expiry enforcement. Do not weaken A into a nominal period with every ordinary file unavailable, and do not overstate its benefit as measured demand or a universal standard. If a source legitimately cannot provide post-completion bytes, its explicit stricter policy must remain clear rather than pretending the ordinary guarantee was met.

## Acceptance outcomes for the eventual implementation

These are future proof obligations, not completed tests.

1. Normal source-confirmed fulfillment produces the completed view; upload success, scan completion, task resolution, clock expiry and tab close do not.
2. A still-authorized recipient returns directly to the current permitted completed context without unnecessary signup or confirmation. Actual assurance expiry takes the qualified re-entry path.
3. Successful re-entry restores safe task context but cannot extend the source period, expose a different recipient's request or trigger automatic original download.
4. The displayed access end is the real source value, readable with timezone context, and does not claim guaranteed availability through earlier restriction. No fixed duration or start anchor is invented by the UI.
5. Session/proof limits, source access end and technical rendition lifetimes produce correctly distinguished behavior. Each applicable content-set timing rule has an evidenced accessibility mechanism or exception; reauthentication alone is not accepted as proof.
6. Current-file View/Download remain independently qualified; an individual failure does not erase completion or separately valid history/other files. No superseded bytes, public fallback or regenerated “original” appears.
7. Correction/completion races, stale pages, account switches, revocation, expiry during viewing/download and later explicit source remediation yield source-correct results without silent reopening or renewal.
8. Ended access provides safe, understandable help without disclosing protected request existence/details. It does not imply evidence deletion or leave an endless retry loop.
9. Keyboard, speech, screen reader, touch, zoom/reflow, slow-network and supported mobile users can find the outcome/end, re-enter, use qualified actions and recover. Session warnings and focus/announcements are tested with actual assistive technology.
10. Any approved help route reaches its accountable source with permitted context and a truthful outcome. It does not automatically send a file, unlock history or create a new business request.
11. No private archive persists through unqualified client caches, expired endpoints or generic telemetry. Already delivered/saved information is not falsely claimed recalled.
12. Representative participant tasks can distinguish “request complete,” “session ended,” “file unavailable” and “request access ended.” Report the sample and observed limits; resolve harmful misunderstandings before expansion without inventing success statistics.

No duration, anchor, warning timing, renewal policy, retention period, automatic communication or numerical monitor threshold is selected in this note. The next dependent policy decision and actual owner/serving qualification must settle the remaining operational limits before activation.

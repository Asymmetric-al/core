# Q59 runtime adversarial review — private Save for later

27 October 2026. Independent reviewer: `/root/q31_runtime_research`. Q59 A is selected; this is research and proposed qualification language, not full ratification, a deployed feature, or permission to change a database. Q01–Q58 remain binding. Only this note is written. No Q60 is asked.

## Outcome and smallest complete model

Recommend a small durable **private preference for an exact P28/Q58 resource publication**, with explicit desired Save and Remove commands, one private Saved destination in the qualified Resources experience, and normal current source reading. A preference is not a publication, copied file, retained rendition, grant, subscription, report, review, acknowledgment, curator task or popularity measurement. The current source offers reusable presentation and settings patterns, but does not prove this resource preference is implemented or safely authorized.

The proposed product owner is the actual qualified native human, within Tenant, environment and source organization, for one exact publication identity. The same person's lawful staff and missionary contexts can share personal intent; each current resource result/open is nevertheless evaluated solely in the selected current context. Do not union hats, transfer another person's preferences, or force a missionary/Party record merely to save. The physical principal key must be qualified against the actual native identity owner. Current `persons` infrastructure is explicitly inert, so this review does not mandate populating that new table or pretend it already resolves stable people.

Use a small coherent native write with uniqueness, trusted scope, current preference/source authority and a relevant expected preference basis. Preserve enough bounded command/result or ordering evidence to recover an original operation and reject stale opposites after deletion/cleanup. This is **not** a requirement for an append-only business ledger, generic event store, new identity service, replay platform, background worker, Realtime channel, object copy or external provider. The implementation may choose existing qualified mechanisms if they prove the invariants below.

The main non-obvious race is an absent-state Remove. If an old Save holds absent revision r0, acknowledging Remove while retaining that same valid r0 can let the delayed Save recreate the preference. A newly admitted desired-state command may therefore need an internal ordering advance even when the visible Saved/Unsaved state does not change. Original matching replay never advances it. Duplicate same-state Save must not refresh the visible saved date or reorder the list. This distinction is an explicit Q59 amendment; do not mechanically import other domains' rule that every visible no-op leaves every internal generation unchanged.

- PostgreSQL distinguishes old-row `USING` and new-row `WITH CHECK`; where permitted, omitted CHECK inherits USING. Applicable permissive policies combine by OR, restrictive by AND. BEFORE-trigger changes, UPSERT/MERGE actions and required SELECT/RETURNING access must be tested in the actual statement. A weak new self policy does not narrow an existing broad permissive read. [CREATE POLICY](https://www.postgresql.org/docs/17/sql-createpolicy.html).
- RLS applies alongside privileges; table owners ordinarily bypass unless subject to FORCE, and superuser/BYPASS roles remain special. Whole-table operations and policy composition require actual-role inspection. [Row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html). Definer functions execute as their owner, so inspect that owner, search path, overload and EXECUTE grants; the keyword alone is neither safety nor universal bypass. [CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html).
- A correctly chosen UPSERT can provide an atomic insert/update outcome, but it does not establish trusted scope, authorize a source act, encode expected intent or make several HTTP calls transactional. A conflict condition that updates no row is not a successful state change. [INSERT](https://www.postgresql.org/docs/17/sql-insert.html). Transaction isolation and bounded whole-transaction retries must be chosen for the actual race; no global Serializable prescription is made. [Transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html).
- Nullable uniqueness can allow duplicates; same-scope relationships need appropriate non-null/unique/FK rules. A referencing FK does not automatically provide its own index, and cross-row current authorization is not a static CHECK constraint. [Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html).
- Supabase warns against user-editable metadata authorization and stale JWT membership claims. Current native assignment/P12 facts still matter; an Auth session is not a resource/preference permission. Test real allowed/denied returned effects, not merely absence of an SQL exception. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). Session settings and JWT refresh have their own timing; do not replace source currentness with a new arbitrary JWT interval. [Sessions](https://supabase.com/docs/guides/auth/sessions).

## Eighteen exact proposed amendments

### C01 — One private convenience, within the actual resource source

Q59 adopts optional private Save for later and Remove for a current eligible P28/Q58 publication, alongside search/navigation. Save changes only the person's return preference. It creates no file copy, download entitlement, historical-content promise, shared collection, notification, follower relation, review/report fact, completion, assignment or audience modification. First scope excludes generic files, Support guides and unrelated favorites unless their owners later explicitly qualify them.

### C02 — Stable personal ownership without identity fabrication

Bind the preference to the current server-established native human and exact Tenant/environment/source organization/publication. Qualify the native human mapping; do not prescribe the inert `persons` table or infer identity from email, an arbitrary profile, a Party or an authenticated role string. Scope identity and attribution are immutable through ordinary writes. Same lawful human across qualified staff/missionary contexts shares the preference; source reading always uses one selected current context, never a union or fallback to another hat. No automatic cross-account/person merge, ownership transfer, shared credential inference or migration of another person's private list is authorized.

### C03 — Distinct current preference rights and resource rights

New Save requires current qualified participation in the source organization, permission to manage one's preference, and current eligibility to discover/read the exact publication in the selected context. Private list/reconcile/Remove requires the explicit current own-preference purpose and actual active organization participation; retained ownership or a valid JWT alone is insufficient. Removing a known own entry may proceed when resource metadata/bytes are unavailable or forbidden. Curator/manager/Support power grants no routine view of another person's saves. Exceptional privacy/security operations need their separately qualified current purpose and attribution.

### C04 — Exact publication reference and current resolution

Store the source reference, not a cached title, arbitrary URL, provider object, digest, output rendition or immutable edition snapshot masquerading as the source. Reopen resolves the same publication's currently qualified source head and current metadata/actions. Rename/current lawful head change may appear under that identity; an independent publication, successor, organization move or merged identity is not silently substituted. Q55 due status and Q57 report rights remain their own current projections. Saving is not proof of any prior version read or consent to automatic successor access.

### C05 — Explicit desired state, reviewed relevant basis and atomic result

The durable command expresses Save or Remove, immutable scoped target/owner binding, operation identity and relevant expected preference basis; it is not a blind toggle or client-clock last-write-wins. The source checks current applicable authority and relevant facts after waits, compares the exact basis, and coherently commits desired state, required ordering evidence and safe original result. No partial preference with missing required recovery evidence, and no receipt before commit. Use one qualified native boundary; multiple SDK calls do not constitute one transaction. Unrelated resource/global revisions are not automatic conflicts, but current publication eligibility is independently checked for new Save.

### C06 — Original recovery before new intent; stale intent stays stale

Match an existing operation's complete immutable intent before fresh new-command eligibility/no-op logic, under current permission to disclose its safe outcome. Matching committed replay returns that original fact without reenactment, new saved date or ordering advance. Same operation identity with changed desired state/scope/basis conflicts. A new transport key is not authority to bypass an expected-basis conflict; preserve safe desired input for deliberate refresh/retry. Current projection may show a newer state than the recovered original result and must identify that distinction; an old response cannot overwrite the newer UI state. Unknown commit requires reconciliation, never automatic opposite compensation or a fresh key disguised as retry.

### C07 — Desired-state ordering, no-op Remove, ABA and cleanup

One active relationship per qualified owner/scope/publication is enforced, including concurrent first saves. New admitted desired-state commands must order against old opposite intents. A visible no-op Remove may require internal generation/control advancement to fence an already-authorized delayed Save; same-state Save must not refresh visible saved time or list position. A matching original replay never advances. Stale expected basis, including unsaved→saved→unsaved ABA, fails rather than being treated as a new no-op. Retention/GC/restore must preserve the rejection of unverifiable old requests, through finite retained control or another qualified expiry scheme. No particular tombstone/table/token algorithm is mandated and no unbounded button ledger is required.

### C08 — Known absent, unknown, unavailable and forged target differ

Only a complete scoped result establishes absence. An error, denied query, unresolved person/source mapping or incomplete page does not mean no record. A legitimate own-entry or genuine current own pending-intent binding may support safe Remove/absent acknowledgment and its required ordering fence. Arbitrary hidden publication IDs must not allocate unlimited private control/tombstone rows or disclose whether a resource exists. If a no-record command cannot prove that bound personal intent/current eligible target, reject or require a fresh qualified basis without hidden-resource details. Resource lookup uncertainty need not erase a proven saved relation; do not misreport Saved state, remove it automatically, or claim a complete empty list.

### C09 — Unavailable placeholders, reappearance and separate source lifecycle

While current own-preference rights remain, a retained save whose resource cannot presently be disclosed can expose only a neutral own-entry placeholder and Remove/reconcile action, with no cached title, thumbnail, URL, hidden cause, source state or successor hint. A temporary lookup failure is an honest failure/unknown state, not proof of withdrawal. If the same publication later becomes lawfully available in the selected context, a still-retained save may display it again. A removed/erased preference, independent new publication or re-created database row must not resurrect personal intent. None of this grants historical bytes or recalls copies already lawfully delivered. No inaccessible-resource details may enter search, filters, facets, counts or timing/error distinctions.

### C10 — Offboarding, privacy, custody and bounded retention

Loss of current qualifying organization participation blocks personal-list access and mutations even if the credential/row remains. Lawful retained preference may become accessible again only under an actual later qualified same-human/scope context and current rights; no automatic cross-person merge or staff takeover. Provide source-governed privacy removal/retention with bounded minimal ordering/result evidence, and enforce deletion/restore fences before serving. Save creates no hold or retention extension on the resource bytes. Resource withdrawal, byte disposition and preference removal are separate purposes; neither an empty Saved list nor an orphan FK is disposition authority. No resource-byte or private report retention is created by a saved reference.

### C11 — One PDP, trusted current context and static projection

Use P12's single PDP and source PEPs, prescribed coarse Tenant RLS, registered stable capability meaning and static field classification plus the shared subtract-only projection. Application and database Tenant Authorization Context must agree, be unforgeable by caller data and fail closed when missing/mismatched; pooled context clears on success/error/cancel/retry. Do not implement another per-row membership/capability policy engine in RLS. Classify preference fields and permit the actual self-purpose projection explicitly; owning a relation cannot declassify resource content. Raw endpoints must preserve this boundary or be closed. P12 R6 remains at most one logical governance SELECT and one ledger UPDATE, with its qualified physical-sharding provision; it is not a ban on all bounded business queries.

### C12 — Structural integrity and every effective database door

Enforce expressible non-null scope, valid state, immutable owner/source attribution and same-Tenant/environment/organization relationships using appropriate constraints/keys and controlled writes. A unique active preference or equivalent must handle nulls/first-write races; FK existence does not grant access. Test actual SELECT/INSERT/UPDATE/DELETE/UPSERT/MERGE and required SELECT/RETURNING, transformed rows and trigger writes. Inspect PUBLIC/named/default/inherited schema/table/column/sequence/function privileges, overloads/search paths, invoker/definer ownership, ENABLE/FORCE and superuser/BYPASS/service/NHI/operator composition. An UPDATE must not retarget owner, Tenant, organization or publication. Direct Data API/GraphQL/views/RPC/collections/import/restore paths must enforce the same source boundary or remain unavailable. Neither named-view reuse nor FORCE is assumed safe.

### C13 — No content or personal-state leak through reads and caches

Every saved-list/status query is private to the current owner/scope; every disclosed resource field/action uses current selected-context authorization before result/count/facet/thumbnail/URL construction. Cache keys and invalidation include the qualified owner/context/scope/current restriction basis; logout, account/Tenant/hat changes and revocation cannot expose old cached personal data. Do not persist sensitive labels, URLs, control tokens or owner snapshots in generic localStorage, public CDN caches, telemetry or shareable URLs. Save/list does not eagerly fetch bytes or create signed URLs. Open/Download/HEAD/range/conditional/preview/resume remain governed by existing current source and delivery fences; the bookmark is never a carrier grant.

### C14 — Plain complete UX and truthful recovery

Use one discoverable Save/Remove control with accessible state and one private Saved return destination, in both qualified staff and missionary contexts. No curator role, new profile, custom list name, folder, essay, routine double confirmation or forced preview is required. Distinguish local pending, known committed, known rejected and unknown. Preserve known successful state when an optional list refresh fails. A conflict refreshes authoritative state and retains safe intent for deliberate action; no automatic stale override. Removed items can be deliberately saved again only as a new current action. An optional Undo affordance, if used, is that new authorized action—not replay or snapshot rollback. Keyboard/touch/AT/narrow/zoom/RTL and weak-network paths must work.

### C15 — Bounded indexed queries and measurable cost

Qualify finite per-person active saves, page/payload size, query work/time, mutation concurrency/retries, control/result retention and cleanup batches against actual native workloads. Use indexed owner/scope relationships, bounded keyset pagination with a stable unique tie-breaker and set-wise current resource projection; no whole-library materialization, per-pin membership/PDP/byte queries, per-reader fanout or mandatory polling/Realtime. A complete known own-preference count may be permitted under its own rights, but it cannot become a hidden resource count or resource-field filter oracle. Unknown/incomplete authorization is not a complete-zero result. Do not inherit P23 caps or assert constant-time, zero incremental bill or measured capacity without evidence.

### C16 — Minimal audit and capable operations

Maintain the minimum private state/ordering/result facts required for correctness, security and source retention; do not create a curator-readable activity stream of saves or a lifelong per-click business history. Required security evidence is attributable and protected; routine diagnostics use opaque identifiers/reason classes and bounded metrics without resource titles, private list contents, tokens, query payloads or other persons' preferences. Provide a scoped source/privacy operator path for deletion/repair when the user cannot act, preserving applicable denial/erasure fences. Do not require raw SQL or a new management product for ordinary support.

### C17 — Additive qualification, controlled rollout and restoration

Activate only after the actual resource/principal/P12/private-store path passes native qualification in the intended deployed environment. No backfill from UI-local saves, browser storage, CRM favorites or inferred interests without separately authorized migration. Old writers, raw RPCs and incompatible clients cannot bypass expected-basis or privacy rules; additive schema/grants/index changes are compatibility-tested before exposure. A rollout stop may stop new Save while preserving lawful own Remove/reconciliation where safe; security containment can deny affected reads without turning ordinary library navigation into a bookmark dependency. Restore current ownership, removals/erasure and command-expiry fences before serving; old backups/late workers must not revive removed intent. No new provider or whole-platform migration is selected.

### C18 — Proof scope and stage

All proofs below are release requirements, not passed tests. UI mocks, TypeScript types, migrations, provider docs, local browser state and existing personal-view APIs are insufficient. Demonstrate real intended actors, current assignments, actual grants/RLS/PDP/transactions and all serving paths under failures and races. Qualification may reuse capable native infrastructure; absent capability is a cohort blocker, not permission to fabricate a successful Saved state. No glossary, automatic notice, public sharing, new business authority or Q60 decision is implied by this review.

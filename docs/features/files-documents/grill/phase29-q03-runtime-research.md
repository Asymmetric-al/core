## Decision that is genuinely open

The next useful founder question is **whether an ordinary recipient can initiate a corrected submission while the request is still open and unaccepted, or must first wait for staff to request it**. This is a product action/timing choice, not a choice about overwriting bytes.

Already settled: original received bytes and prior decisions remain immutable; source owns what is required, what evidence means, currentness/acceptance/correction and retention; Q02 readback does not imply mutation, earlier-version-history or post-closure access. A new file can never silently replace an accepted receipt, expense claim, signature, published artifact or prior evidence. No generic File Manager command may reopen every source domain or undo downstream facts.

No reached accepted contract gives the new generic request recipient an unconditional self-service corrected-file action. Contracts do require meaningful correction/successor paths and immutable submissions. Therefore the timing/initiative question is real, provided it is explicitly restricted to the ordinary new request profile and does not override stronger existing source rules.

## Least-complex safe default to recommend

**Recommendation for the ordinary new request profile:** allow the currently authorized recipient to **Send a corrected file** for the **same unaccepted pending requirement** while its source still admits that action and no acceptance, explicit source freeze, closure or deadline restriction has ended that opportunity. An accepted/frozen/closed requirement cannot be changed merely because other items keep the overall request open. It appends a new submission linked to the earlier one; it never overwrites or deletes the earlier received bytes. The source marks the new candidate clearly for review. After acceptance/closure, the recipient can use the source's defined request-correction/contact action; staff/source may issue an explicit new correction opportunity or successor request where allowed. The File Manager does not generically reopen or roll back the underlying source.

This avoids staff having to unlock a simple wrong-scan correction, while retaining all received evidence. A stricter source profile can require staff-requested corrections from the outset. This is a recommendation awaiting the founder's next answer, not a newly ratified universal permission or requirement that every source implement the same states.

Do **not** choose “reviewer opened it” as the generic cutoff. Opening a preview is a read, not an authoritative lock/decision. That cutoff creates fragile locks when staff switch tasks, lose connectivity or reopen tabs, and adds another workflow state. Instead, review/acceptance commits bind the exact version and source revision. If a correction wins first, a stale acceptance attempt must reload/review; if acceptance/closure wins first, late finalization cannot silently replace it. The owner may retain received late bytes privately with a truthful nonaccepted state under its policy; it must not mislabel them accepted or erase retained data.

Avoid scope creep: the proposed action is one corrected submission, not an editor, compare/merge tool, personal version browser, rename command or broad upload/delete entitlement. Supplementary additional evidence is not necessarily correction of an earlier file; the source must distinguish “another required item/additional evidence” from “use this corrected submission for review.”

## Essential consequences to explain alongside the founder choice

1. **Earlier evidence remains.** Staff can retain the exact file they received and any prior decision. Participant access to previous versions remains separately source-authorized; retaining history does not grant a browse-history screen.
2. **Review remains exact.** New candidate is visibly distinct; old preview/decision never silently becomes a decision about the new file. The source, not upload time alone, selects the review target/current accepted evidence.
3. **Safety is per new bytes.** Every corrected file gets its own intake/limits/checks/rendition lineage. “Correction” cannot bypass quarantine or reuse a clean label from the prior file. Failed correction does not erase prior received confirmation or satisfy the requirement.
4. **Deadlines and receipt are honest.** Retrying the same submission reconciles the same durable result; new content is a new deliberate operation. A replacement does not extend deadline or revive an ended grant automatically. Technical receipt time, source timeliness and business acceptance are separate.
5. **Submitted business facts are protected.** Expense evidence/claim confirmation, official documents, signatures, publication and application decisions require their owning successor commands. A generic file correction cannot undo payment, acceptance, approval, signature or release.
6. **No silent replacement through sharing.** Another source use pointing at earlier bytes remains earlier bytes unless that owner deliberately changes its own qualified reference. Same filename/hash/uploading account never decides provenance, audience or currentness.
7. **One race winner and clear recovery.** Correction, acceptance, expiry, recipient change and withdrawal compare exact current revision. A lost success response is replayed safely; a stale operation cannot revive closed authority. New candidate processing after an auth session ends follows source worker authority as already ratified in Q01/Q02.

## Suggested founder-level question framing

Recognizable situation: “You open View my submitted file and realize you sent the wrong scan. Staff have not accepted it yet.”

Decision: whether the person may send a corrected file themselves for the same unaccepted pending requirement under current source permission, or staff must open every correction opportunity. Overall request-open status alone is insufficient.

- **Self-service correction while open — recommended:** quickest recovery and less staff chasing; Asym keeps the earlier submission, clearly flags the new one for review and prevents stale approval. Accepted/closed work uses the source's explicit correction path.
- **Staff-requested corrections only:** fewer recipient actions and tighter control, but a simple mistake requires messaging/waiting and can miss a deadline. The same immutable version/acceptance safeguards are still required.

Do not present overwriting or deleting old submissions as a third equal option: those conflict with already accepted evidence/history boundaries. Do not ask whether corrections should exist at all; the supplied outcome and predecessors already require them.

## Remaining questions this decision does not settle

Who can request/reopen a correction opportunity, previous-version participant visibility, post-closure read duration, participant withdrawal/deletion requests, whether a reason is required, multiple file items/partial satisfaction, review outcomes, notifications and acceptance effects still need their exact source contracts. Do not silently decide them in Q03. Existing source rights remain intact. A brief optional explanation may help staff, but compulsory reason fields or automatic notifications are product decisions, not assumed engineering necessities.

No further source-only tests are needed to choose between the two product options. Later implementation proof must cover stale review versus new correction, quarantined correction, lost responses, deadline/closure/recipient races, downstream-source immutability and independently authorized reads of older retained versions.

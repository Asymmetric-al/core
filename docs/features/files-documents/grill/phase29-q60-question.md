## The next decision

**When staff discover that they accepted the wrong evidence while an ordinary document request is still unfinished, should they be able to correct that acceptance within the same request, or should the correction always use a new request?**

| Option                                                                            | Practical experience                                                                                                                                                                                                                                                | Main tradeoff                                                                                                                                                                                                                       |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Allow deliberate correction in eligible unfinished requests (recommended)** | An actually authorized staff member selects the exact mistaken acceptance, records an attributed correction and returns the affected item to current review in the same request. Other valid work stays intact.                                                     | Requires explicit correction authority, exact current basis, truthful history/current applicability and ordering against fulfillment or other decisions.                                                                            |
| **B — Always use separately reviewed corrective work**                            | Record the mistake and stop inappropriate current reliance. For unfinished ordinary collection, deliberately cancel the old collection through actual Q34 authority where needed and prepare/issue a new corrective request for only the remaining legitimate work. | Keeps the ordinary request away from a same-request correction transition, but introduces a new request/access/handoff and can move still-pending work. It must be guided and recoverable, not manual rebuilding or powerless Help. |

**I recommend A**, narrowly scoped to eligible unfinished work. An accidental acceptance should not normally make a recipient navigate a second request or repeat valid submissions. The historical acceptance remains true as a record of what staff did; the correction changes current reliance and next work prospectively. Neither option silently erases history, edits the original uploaded evidence or makes an incorrectly accepted document still count as valid merely to preserve a green status.

**Already completed or closed work is a shared boundary, not another choice hidden in A:** preserve the actual fulfillment occurrence F, terminal history and existing access clocks. Record the mistake through its qualified source remedy and use independently authorized fresh corrective work if needed. Do not silently reopen, recalculate the old F or revive expired access. Specialized application/financial/official-document outcomes keep their own correction contracts.

## A concrete journey and the important boundary

Illustrative example, not an observed ministry workflow: Nora is reviewing three required documents from Alex. She accepts one, then realizes it is the wrong form while another required item is still outstanding.

Under A, Nora uses a deliberate **Correct acceptance** action on that exact item. The UI identifies the accepted evidence/version, who accepted it, the current result and what the correction will change. Only actual source-qualified information is shown. The correction is attributed; the receipt and original decision remain. The item returns to genuine current review. If the existing evidence is sufficient, staff can complete a fresh lawful review without forcing new bytes. If the recipient must supply a correction, use the existing Request changes/self-correction journey with clear safe guidance and current recipient access. The product must not blame the recipient for staff's mistaken click.

If Nora's acceptance was the last outstanding requirement and F has already occurred, A's same-request lane is no longer available. The source must provide the qualified historical-error/current-reliance correction and fresh corrective-work route, preserving F and existing access endings. A stale screen cannot turn a completed request back into unfinished work. Correction-versus-fulfillment order is an authoritative source fact, not the browser's badge or click timestamp.

Under B, Nora records the same truthful error/current-reliance disposition, then uses guided separate corrective work. If the old ordinary collection is still unfinished, ending it uses actual deliberate Q34 cancellation—not fake fulfillment or a quiet waiver—and the new request covers only remaining legitimate work. Unaffected accepted facts remain historical and need not be requested again. Any reuse of existing evidence follows its actual qualified source route; approvals, attestations and grants are not cloned. This would be an explicit same-recipient corrective-remedy adoption, not permission borrowed from Q49's different-person replacement.

New-request preparation must not delay a separately authorized correction of known erroneous reliance. Independently authorized urgent safety/privacy restriction also remains available without waiting for acceptance correction or a new draft; neither Q60 option creates that restriction authority. Conversely, merely recording a mistake does not issue a new request, grant access, reset a reminder or send a new message. Existing independently qualified Q40/Q48/P6 purposes retain their exact contracts. Both alternatives require a real capable remedy and recovery from partial failure.

## Adversarial check of the recommendation

### What could go wrong with this answer?

A could be implemented as a dangerous reverse toggle that erases acceptance, reopens completed work, restarts access or invalidates unrelated items. B could become a powerless Help link or continue treating a known mistaken acceptance as currently valid. Both require truthful new correction facts, actual source authority and complete recovery. The question's narrow continuity choice does not authorize those shortcuts.

### What hidden assumptions are we making?

That accidental acceptance is a realistic recovery case and avoiding an unnecessary new request helps users. The founder explicitly requires correction and recovery, and comparable collection products document approval reversal. No Asym frequency/user study was measured. Exact ordinary source binding and native implementation remain unqualified; nearby UI or GEN-06 names do not prove this capability exists.

### How does this affect the whole product?

It fills one missing ordinary source-action contract between historical acceptance and current applicability. It preserves Q21/Q22 history/F, Q23 unaccepted review, Q52 accepted-effect integrity, access/communication owners, immutable custody and specialist finality. It is not an additional resource feature, a generic Undo engine or permission to broaden every request source.

### How does this affect the end-user experience?

A preserves one request's context and valid work for an eligible mistake. Clear current review and guidance avoid making the recipient redo good work or interpreting staff error as their failure. B offers a conservative new-work boundary but needs a guided remaining-work handoff and may change the active request/access path. Both need a truthful completed-case route and safe recovery, not silent status edits.

### Does this follow modern best practices?

Close collection products support recoverable approvals, while the cited broader application system distinguishes terminal review outcomes. Its use of terminal terminology alone does not prove immutable history or prohibit every later status change. The appropriate adaptation is explicit ordinary item correction before actual closure plus source-owned new work after closure. Blind toggles, staff editing submitted answers, automatic notifications and universal reopening are not imported. Simplicity means complete recovery with the fewest reasonable steps, not omission of history or authorization.

### Does this fit Asym's existing repo and product direction?

Yes as a narrow explicit source amendment if selected. Q21/Q22/Q23 and Q52 require truthful history/current state and a capable remedy but do not define this ordinary command. P12, native source and task/communication owners remain authoritative. The new raw-read migration does not implement acceptance correction or change those product boundaries. Formal source/OpenSpec reconciliation and native qualification remain separate.

### Should we adjust the recommendation?

Recommend A for exact eligible unfinished work, with the completed/closed case explicitly preserved and routed to fresh authorized corrective work. B remains the strongest practical conservative alternative, with its real cancellation/new-request and recovery cost disclosed. The founder still chooses; neither option is ratified by this research.

## One decision

**Should authorized staff be able to accept several explicitly selected, reviewed items within one ordinary request in one action, or should each item continue to be accepted separately?**

| Option                                            | Practical experience                                                                                                                                                | Benefit                                                                                                                                 | Cost                                                                                                                                                               |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A — Allow Accept selected items (recommended)** | Review the actual current requirements and evidence, explicitly select eligible items in this request, then use **Accept selected (N)**. Individual Accept remains. | Fewer repeated acceptance actions when several genuine review decisions are ready together; a clear selected scope and coherent result. | Adds selection and conflict recovery. One changed selected member can block this action's new decisions until staff reviews or deliberately changes the selection. |
| **B — Keep individual acceptance only**           | Use the contextual Q21 Accept action separately for each reviewed item, retaining the same useful request/document navigation.                                      | Smaller action scope and simpler failure handling; one item's change need not block another item's separate acceptance.                 | Repeated acceptance actions even when several items have already been reviewed. It does not inherently improve the quality of that review.                         |

**I recommend A, narrowly:** an optional convenience within one request, after substantive human review. Keep individual acceptance equally usable. This is a product judgment informed by comparable collection workflows, not a measured Asym time saving or a claim that most ministry requests contain many items. B is credible if actual requests rarely have several items ready at once. Neither option adds a compulsory preview, an essay, a second reviewer or a routine extra confirmation.

## A concrete journey

**Illustration, not an observed ministry workflow:** Elena sends an ordinary request for an equipment inventory, a packing list and a venue layout. Nora is an authorized staff reviewer. She has reviewed the inventory and packing list against their current requirements; the layout still needs clarification. The inventory has two supporting files, which remain one item's evidence set.

With A, Nora selects the first two items. The existing request review surface shows their identities, useful current evidence context and **2 selected**, with **Accept selected (2)**. The layout remains unchanged. With B, Nora uses Accept on each of those two items. Neither option approves each file separately or equates the visible selection with the complete request.

If the recipient corrects the inventory before the command commits, the old selection cannot accept its successor evidence. The proposed A command saves all its **new selected acceptances** coherently, or none from that action when a required basis/permission fails. Staff gets a safe explanation, retains still-lawful context, and can review the change or deliberately remove that item before trying again. The UI must not quietly accept a reduced subset.

An independently existing exact acceptance by another reviewer remains true, with that reviewer's actor and time. It cannot be rolled back or relabeled as Nora's work. On a known failed attempt, use language such as **“No new acceptances were saved by this action.”** A lost response is different: recover the original operation before retrying a smaller or changed set.

## Twelve boundaries proposed with A

These make the option reviewable; they are not a selected answer or a frozen schema design.

1. **One request, finite items.** Allow only eligible ordinary requested items within one request, Tenant/environment and source purpose. Bind stable exact item identities and each complete relevant evidence set. Start empty, show the actual selected count and scope. Any select-all affordance must name its finite scope; filtering, paging or future uploads cannot silently expand the set. No global File Manager approval.

2. **Substantive human review.** Preserve current requirement/instructions, relevant evidence/review basis, required safety/admissibility and sufficient qualified inspection for every item. Selection, receipt, scanning, thumbnails or AI do not prove acceptance. No mechanical preview/dwell/download checks, per-file approval, essay or routine extra reviewer. Unsupported preview may use an actually sufficient qualified inspection route; unknown required proof blocks acceptance.

3. **Current authority for each member.** One actual staff actor must have the Q21/P12 source acceptance power for every selected item. Derive trusted Tenant/actor/context on the server; do not accept claimed powers from the client. Q24 responsibility, a task, folder, label, template, team membership or staff title is not authority. Do not union different humans' rights or require personal claim when the existing team route does not. Preserve any genuinely applicable specialist or separation-of-duties rule.

4. **Exact current bases.** Admission checks the intended item, requirement/instructions, evidence and relevant review/authority dependencies. Correction, withdrawal, applicable requested changes, relevant comments/clarifications, demand changes and actual closure participate in the existing source order. A stale selection cannot accept successor evidence or manufacture a concern resolution. Unrelated context changes should not create a global conflict. Q23 permits lawful same-evidence reassessment only when fresh review records the actual resolution of the prior concern.

5. **All-or-none new decisions.** The source command commits all its new selected acceptances with required local history and durable follow-through coherently, or none from that action when a required member fails. No silent skip, automatic smaller-set retry or hidden chunking. Exact applicable acceptances already committed independently can be recognized under Q21; they keep their original actor/time and are reported separately from this action's new work. No existing source success is undone to make a batch appear atomic.

6. **Q22 fulfillment remains distinct.** The complete authoritative request predicate, including relevant hidden/non-file/remaining requirements, controls actual fulfillment. Following the selected changes, evaluate or durably arrange that evaluation through the qualified aggregate boundary. Known acceptance may remain known while fulfillment follow-through is unresolved; recovery needs no second business approval. No visible-count/empty-set completion or new Complete button. Explain the possible end-of-work/access consequence before commitment when qualified, without promising completion from a stale view. Actual F and its clocks remain source-owned.

7. **Recover the original operation.** Distinguish local selection, submitting, known committed, known no-effect and unknown. After a lost response reconcile the original command/basis before any changed selection or new-work eligibility check. Preserve original-result recovery even after later state change. Overlapping reviewers must not duplicate acceptance, rewrite attribution or repeat required effects. A changed intended set is a new deliberate act after the previous outcome is known.

8. **Truthful small UI.** Keep contextual individual Accept. Add labeled selection, useful item/evidence summaries, the visible count and **Accept selected (N)**. One clear inline impact presentation suffices when it explains the action; no mandatory second modal. Preserve lawful reading position, notes, selection and focus through recoverable errors. If any member becomes restricted, disclose only currently authorized reasons/counts; do not leak its identity to explain the failure. Results distinguish newly accepted, already accepted and unresolved operation status.

9. **Complete user journeys.** Keyboard, screen reader, speech, touch, mobile/zoom, long international names, RTL/IME and slow-network users must see and operate the same meaningful scope/result. No hover-only explanation, forced visual inspection or offline approval queue. Participant readback reflects current source-approved status and remaining work without staff-only details. Local selection cancellation is not source cancellation; committed mistakes use the already-governed source remediation, not a new blanket Undo/unaccept/reopen.

10. **No new timing or messaging policy.** Independently authorized staff may review after participant access expires without renewing it. Q52 adds no acceptance email, task-per-item, completion notice, reminder schedule or automatic attention request. Existing independently qualified source/communication effects retain their actual purpose, deduplication, current-utility and tenant controls. Notification failures do not erase acceptance or prove fulfillment.

11. **Qualified source boundary.** Use a real bounded source command in the governed operational API/domain, not client loops, CMS writes or a generic status PATCH. Preserve one current fine-grained policy decision per required source action and prescribed coarse Tenant RLS across all doors. Effective grants, USING/WITH CHECK, immutable tenant-aware relationships, functions/triggers and privileged paths must enforce the same invariants. Serialize relevant request/item dependencies, not a whole Tenant. Keep scanning, inspection and providers outside locks; required durable intent is not external success.

12. **Measured implementation, additive rollout.** Qualify maximum selected count, request/response bytes, indexed proof queries, lock/transaction/retry and retained-result/history budgets against actual native data and workloads before activation. Exceeding a supported bound is explicit; keep individual acceptance available. Do not invent a vendor-derived number, extra provider, generic batch framework or bill-neutral promise. Preserve original outcomes through retention, compatible rollout and restore; disabling the new entry point must not destroy records or replay downstream work.

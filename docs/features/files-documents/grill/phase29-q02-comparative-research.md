# Phase 29 Q02: what recipients can see after submitting

Research inspected 2026-10-20, Asia/Bangkok. Q01A and its amendments are ratified according to the parent; this note addresses the next unresolved product choice only. Scope: the first generic new external private-document request profile. Existing Phase18 official documents, Phase21 evidence collaboration, and other source-owned retrieval rules are not amended here. No external writes, invitations, product tests, private-file reads, or source changes performed.

## Assessment

Safe access to one's own submitted document is a defensible product choice, but the three requested file-request comparators do **not** establish it as the standard. Their documented baseline is collection with confirmation and no general folder access. A recommendation for Asym to do more should be stated as a reasoned product judgment: it can help a recipient answer “Did I send the correct document?” after the original browser session is gone. That benefit has not been measured with Asym participants.

Recommend a two-part promise if the founder chooses the richer experience: a dependable, authorized receipt/status for the submission; and a read-only preview of the exact received version when the source permits it and processing has produced a qualified rendition. The preview is a separate read permission, not an automatic consequence of having uploaded bytes. A received file remains received if preview generation is delayed or unsupported.

Recommend the second choice for an ordinary profile **only as an explicit source-qualified capability**, with receipt/status as the reliable baseline. The first choice is a legitimate simpler option, particularly for a deliberately one-way collection. Calling the second universally safe would overstate what Q01 proves. If the source has not approved recipient reading or the rendition has not qualified, the interface must say that preview is unavailable instead of exposing original bytes as a fallback.

## Necessary distinctions for the founder explanation

1. **Selected locally:** a filename or browser preview shows what the user picked. It says nothing about receipt, integrity, processing, or review on the server.
2. **Received:** custody confirms the exact submission/version. Show the permitted name or label, receipt reference and time, together with a clear state. Those metadata are private too; they require current authorization.
3. **Preview available:** the system has a qualified display derived from that exact received version. It may omit unsupported portions; disclose meaningful coverage limitations. “Safe to display” does not mean authentic evidence, fully accessible, or business-approved.
4. **Reviewed/accepted:** only the business owner can decide whether the requested requirement is satisfied. A green upload check or available preview must not imply this.

“Own submission” is an authorization relationship for this exact request, not a global search for every file with the same uploader email. A helper, guardian, organization representative, or changed recipient does not automatically gain historical bytes; the source's actor/represented-subject and correction rules decide that. Q02 must not change those rules implicitly.

## Minimum boundaries if preview is selected

- Current source permission controls each status, preview and retrieval request, including alternate/range/conditional routes. Confirmation once does not create perpetual access. Do not invent a universal access duration; bind it to the approved request profile and clearly state the end condition before activation.
- Viewing is a separate capability from original download, replacing/withdrawing a submission, editing facts, or seeing the full history. Do not silently bundle these into “preview my upload.” A browser-visible preview can be copied or photographed; removing a Download button does not guarantee no copy.
- The preview must identify its exact received version and its processing/coverage state. A newer submission cannot change what an older review or receipt referred to. A local preview is never substituted as proof of what the server received.
- Quarantined, malicious, encrypted, malformed, unsupported or still-processing bytes remain unavailable through the normal recipient viewer. No insecure inline original/provider URL fallback. A processing failure does not falsely erase the receipt of bytes or mark the business request satisfied.
- Revocation/cancellation/recipient correction ends the relevant new admissions according to source policy. Later access by a successor does not inherit earlier participants' submissions by default. Already displayed/delivered copies cannot be recalled.
- Receipt/status availability and byte-preview availability can differ. The product should distinguish “received; preparing preview,” “received; preview unavailable,” and owner-visible review states without exposing internal review notes or confidential reasons. Exact labels remain a product-writing/qualification task.

## Suggested plain-language orientation

“Imagine someone sends two similarly named scans, then returns tomorrow and wants to check which one Asym actually received. We can show a receipt and progress only, or also let them reopen a safe view of the specific file they sent. Microsoft, Box and Dropbox document the simpler collection experience. I recommend the second option for ordinary requests because it gives people a clearer way to check their submission, provided the request's owner allows it. It still shows only their permitted submission, and a file being received or previewable does not mean it has been accepted.”

This is proposed question context, not a recorded founder answer. Compare only the two relevant options; do not reopen Q01 or ask the founder to choose storage/rendition APIs. Preview safety, supported formats and current-permission enforcement are engineering qualification work. The genuine choice is whether the ordinary participant should be entitled to that additional own-submission reading experience.

## Evidence still required

The pilot must determine whether reopening a received preview helps people distinguish the correct version and avoids unnecessary reuploads without causing confusion between received and accepted. Test wrong-file correction, same names, repeated submissions, unavailable previews, mobile/assistive technology, delayed processing, shared-device use and revoked access. No conversion/time savings or universal confidentiality guarantee can be claimed from these comparator docs.

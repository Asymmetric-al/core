## Frontier assessment

This is a genuine remaining product choice, now that Q53 has selected ordinary staff local-file intake. Q28 already provides deliberate **Add existing file**, and explicitly left automatic matching out of that decision. Q53 supplies the new-file path but expressly adds no duplicate suggestion. The founder distinguishes byte equality from provenance and business meaning and warns that even a duplicate indicator can reveal a protected file. The question is therefore whether to add a new assistance signal, not whether reuse exists or whether repeated transport must create duplicate business effects.

## The single practical choice

**When staff choose a local file for an ordinary request, should Asym keep the deliberate Add existing file option, or also proactively suggest an eligible existing file that may match before they commit the upload?**

| **B — Add optional proactive possible-copy suggestions** | Before a deliberate Upload and add, a bounded fingerprint of the local selection may be used only as untrusted query input to find independently discoverable/reusable held exact versions. B is not forced deduplication, automatic replacement, global duplicate cleanup or a warning that a new contribution is wrong. Two uses of identical bytes can have different subjects, origin, consent, rights or retention. The staff member's deliberate action and actual source eligibility remain decisive. A does not remove existing independently qualified Media duplicate behavior or any custody-layer physical reuse; those retain their owners and cannot acquire ordinary business authority from this question.

No empirical ministry frequency, user-testing result or cost advantage supports either option here. The recommendation weighs a known usable manual route against a new optional helper whose best timing and measurable value have not been qualified. B is a credible stronger convenience option, not a strawman; its unknown-file discovery benefit is precisely what A gives up.

## Concrete illustration and the important timing distinction

**Illustration only, not observed ministry behavior.** Nora is supplying a local equipment inventory for Elena's ordinary request. A byte-identical version is already lawfully held under another permitted source use, with a different display name. Nora is allowed to discover and deliberately reuse that exact version for the target item.

With A, Nora can choose **Add existing file**, use approved metadata/source context to find the eligible version, and add it through Q28. If she does not know to look, she can still choose **Upload file** and complete the ratified Q53 path. The system must preserve correct provenance and distinct source uses either way. It must not call the second lawful contribution an error merely because some bytes match.

With B, a quiet inline cue could say **An existing file may match**, with **Review existing file**. A browser fingerprint may help locate the candidate, but independently current candidate-existence disclosure, safe metadata and target reuse eligibility must be qualified. The held file's exact identity is authoritative; the comparison with the still-local selection remains advisory. Review opens the existing source-aware selection context; choosing **Use existing file** makes a deliberate Q28 act on that exact held version, not an automatic switch or a certification of the local bytes. The ordinary **Upload and add** action remains available. No routine modal, new acknowledgement, compulsory preview or duplicate-resolution queue is needed.

The phrase before the upload decision is essential. Q53's one deliberate Upload and add already authorizes finalization of that exact chosen new-file act. A late comparison cannot stop it for a duplicate question, silently substitute a prior version, undo an admitted contribution or change its provenance. If the cue was not ready before that intent, B must let the original path continue and discard the stale suggestion for that operation. It must not rely on a new post-admission duplicate notification or cleanup feature that the founder has not chosen.

The strongest practical B does not require staging a file merely to display independently authorized candidate metadata. A browser-computed digest may be untrusted candidate-search input within an expressly admitted purpose. It cannot establish verified incoming-byte equality, replace Q53's later integrity check or authorize disclosure. Deliberate Q28 selection uses the actual held version, with its current source rights and meaningful identity/context. If a system separately proves full equality, it can describe only what that proof supports; such verification is not a mandatory extra step for this advisory helper. No extra transfer or inspection gate is justified merely to make the hint sound certain.

The runtime reviewer identified the client resource concern, and this pass independently read [MDN's digest documentation](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest), modified 2025-12-28: that API requires the complete input in memory and does not stream it. This does not select that API, algorithm or implementation. It shows why a finite supported file/device cohort and measured cancellation/memory behavior matter, especially on mobile. B must demonstrate useful pre-intent candidate lookup without delaying Upload and add; it must not promise instant hashing, complete matching or guaranteed transfer savings. No new hash/index/provider design is selected here.

If the existing file is not discoverable or reusable by Nora for this exact purpose, neither its name nor a generic duplicate badge/count may appear. If only the file's title is visible but reuse is not allowed, visibility alone does not qualify a suggestion to use it. If no hint appears, the interface must not claim the file is unique or that no such bytes exist anywhere.

## Practical UI and noise judgment

For A, retain the two clear existing choices. An authorized source picker should help staff find exact eligible versions by the already-qualified metadata and context; it should not become intentionally poor to make B look necessary. The lack of a proactive cue is not a new restriction on lawful manual reuse.

For B, show a hint only when there is an actual eligible, independently disclosable candidate. Avoid routine Checking for duplicates spinners, warning colors, duplicate counts detached from visible candidates, toast interruptions or forced decisions on every upload. A possible copy is not necessarily a problem. Suggested labels are **An existing file may match**, **Review existing file** and a deliberate **Use existing file** in the actual Q28 context, with **Upload and add** still available. The definitive word identical is reserved for separately proved equality; the proposed client-fingerprint helper does not claim it.

No cue can be preferable to a speculative or late one. But an explicitly shown comparison failure must not become No duplicates or Unique. A qualified bounded comparison may explain no eligible suggestion in its declared scope if that statement is actually established and safe; it cannot claim complete tenant-wide absence. The ordinary upload must remain available during optional-comparison latency/failure, while all its independent Q53 safety checks still apply.

Neither option needs a new notification, digest, read receipt, duplicate-cleanup task, reusable search history, general cache, tenant policy matrix, settings page or independent global file identity. Any additional control must solve a concrete supported journey rather than compensate for a noisy helper by adding more switches.

# Phase 29 Q26 — Recipient email when staff request changes

**Research date:** 2026-10-22, Asia/Bangkok. Q01–Q25 and their complete amendments are ratified according to the parent's current instruction. Q26 has no selected answer. This note researches a candidate ordinary notification default; it is not a full selected-answer adversarial review, canonical publication or native/provider proof.

## Recommended single fork

**When authorized staff commit ordinary Request changes, should the visible optional recipient-email choice start selected, or should staff select it?**

Recommend **A — Email initially selected, with staff control**, only for the exact ordinary source/sender/recipient/channel path that is actually qualified and eligible. Place the choice in the existing meaningful Request changes interaction, preserve a deliberate off choice, and make the final action's communication consequence clear. The guidance remains in the source request whether or not this notice is requested.

The strongest alternative is **B — The same integrated email choice initially unselected**. Staff can select it in that interaction without a second screen. B gives more deliberate control over outward mail and may better fit frequent item-by-item review or direct assistance. It does not eliminate notifications or force a separate composer.

This is an initial choice default, not a recipient preference, communication consent determination, always-send rule, task-state trigger or automatic email on every database update. It does not select a tenant preference editor or per-user sticky setting. Staff intent for the current action must survive validation and safe recovery instead of being replaced by the default on rerender or retry.

## Why this is a valuable next question

Q23 established recoverable Request changes, exact current guidance and a source-owned next step. It expressly did not choose review-result email policy. Q20 chose the default for fresh-access notices only; it cannot silently supply this new review-feedback notice. The original request may now require the recipient to act, so whether the ordinary interaction helps tell them is an immediate end-to-end product question.

This is more useful now than choosing a reminder cadence, a general notification-settings matrix or a new messaging interface. The comparison should be two integrated defaults, not the false binary “automatic mail with no control” versus “no notice.” A separate later message remains a governed manual/recovery path only where actually supported, not a third mandatory product mode.

The parent/owner review must qualify the new source notice purpose, exact recipient/current state and communication class. Reusing Q20's UX lesson is appropriate; pretending its fresh-access contract already authorizes review-feedback mail is not. The default question should not be a shortcut around those owner conditions or the user's earlier no-Party/request-only identity choices.

## Action needed versus review noise

Request changes asks the recipient to do something if current source/access rules permit it. That is a stronger reason to offer an external notice than a passive internal assignment change or a staff viewing event. The useful handoff is “there is current requested work in your request,” with the exact message/action constrained by its source and communication owners. Receipt, acceptance and mere field modification are different events; they do not inherit Q26's proposed default.

Noise is a real cost. If staff make several separate Request changes decisions while reviewing a request, repeated optional notices may be unwelcome. A staff member working directly with the recipient may already have supplied the handoff. Under A, leaving email off for the particular review action is meaningful control; under B, not selecting it is the normal quiet path. Neither is evidence that all independent source/security messages are suppressed.

Do not solve this by silently introducing a delay window, digest, “email after all items reviewed” mode, bulk review command, per-request notification quota or automatic grouping rule. Those alter timing or workflow and are not selected here. Likewise, do not wire notice creation to every affected file/field row: the meaningful review action and its expressly selected communication intent are the relevant boundary. Exact source/action-to-intent identity must be qualified without claiming physical exactly-once delivery.

If future user evidence shows that ordinary review naturally involves many successive actions and staff consistently struggle with notice noise, revisit the relevant policy with that evidence. It is not appropriate to claim that an unbuilt digest or an invented staff review habit already removes A's downside.

## Strongest B and why A is still recommended

B preserves the same integrated experience and costs only a deliberate opt-in when a notice is wanted. It has a credible usability advantage: the user is more likely to consciously authorize an outward message, and the final action need not depend on noticing a checked option. GOV.UK's preselection caution strengthens this argument. B is not an outdated or unhelpful alternative.

A favors completing the handoff when staff deliberately request new work. The request already has a bounded recipient access period; a source outcome stored correctly does not prove the recipient knows to return. A does not require a second message task and can still be quiet when staff turn the choice off. These are reasoned benefits, not measured reductions in missed notices or faster turnaround.

Recommend A only with a conspicuous optional choice, a truthful final action, exact permitted recipient/context and real qualification of the communication path. Staff should not have to perform an artificial toggle to demonstrate intent; nor should the system hide the checked state in advanced settings. If the qualified source policy requires a particular notice, that is not this optional choice and cannot be suppressed here. If the optional notice is unavailable, unknown or not permitted, do not disguise it as a ready checked option or silently treat a selected request as successfully sent.

The no-build/manual alternative is to keep Q23 guidance and use an existing governed communication path where necessary. It is a real scope fallback if this native notice path cannot yet be qualified, but not evidence that recipients will discover every new change request. It must not require arbitrary email sharing, raw storage links or another application account. The founder question should remain A versus B, not expand to a third obligatory post-review messaging workflow.

## Practical example and lean interaction

Illustrative example, not observed ministry behavior: Elena reviews Nora's current submitted form and finds a missing page. Q23 already requires useful safe guidance and preserves received evidence; Q03 supplies the separately authorized correction path.

1. Elena reviews the exact item and enters or selects sufficient permitted guidance in the existing Request changes interaction. No mandatory essay is introduced by this notice decision.
2. Where the notice is eligible, **Notify recipient by email** appears beside the meaningful action. A starts it on; B starts it off. Show only the source-approved recipient/destination and message consequence Elena may see. Do not add To/CC/BCC, attachment selection or a general composer.
3. The final action makes the difference understandable, for example **Request changes and notify** versus **Request changes**, using accurate visible and accessible wording. These are provisional copy examples, not mandatory new controls or an immediate-delivery promise.
4. If Elena is already assisting Nora and this notice would be redundant, she can record the outcome without it. Her current choice survives validation and safe recovery. A refresh or retry must not silently re-check email.
5. The source review outcome and its actual notice status are reported separately. A committed change request remains true if the email fails. A failed or unknown review result does not authorize a success message or a notice that assumes it committed. Recover the same intent instead of repeating Request changes to retry mail.
6. Nora's request remains the current authority for what needs attention and what she can currently do. An email is not a new upload/read grant, confirmation of identity or a fresh access period. If access or the requested work changed before dispatch/opening, the qualified communication/source path must produce truthful current behavior rather than promise immediate upload from an old link.

The participant should not need to understand internal reviewer routing or find a private staff comment. The outward message must not automatically include filenames, sensitive rationale, raw attachments, full reviewer notes or provider retrieval URLs. The exact safe message/action is an owner qualification issue; Q26's default alone does not authorize broader disclosure.

## Important limits for the final question

- **One ordinary optional-notice default.** Q20 fresh-access notice policy is not expanded by implication. Initial invitations, identity proof, reminders, acceptance/fulfillment notices, staff alerts, bulk sends, SMS/push/other channels and specialist mandatory notices remain outside this choice.
- **Real source review first.** Q23's exact current item/outcome/guidance and all Q21/Q24 source authority remain. The email choice cannot create review authority or a Changes requested state from a transport event.
- **Communication qualification is separate.** Sender, intended recipient/destination, purpose, contactability/suppression, approved message/action, host and dispatch rules must actually support this native notice. A generic staff profile/email match or Q20 template is not enough.
- **Keep off meaningful.** A staff-off choice means this optional notice was not requested, not that every independent email was prevented. It does not remove the source review outcome or current authorized guidance. Preserve it for the same intended action through retries and ordinary validation.
- **Keep unavailable truthful.** Unsupported, denied, suppressed, non-applicable and unknown states are not a hidden selected default. A legitimate changes-only path can continue where allowed and explicitly understood; no surprise downgrade of a reviewed notification promise. Do not force staff to obtain new permissions simply to record a lawful review outcome.
- **No new lifecycle from mail.** Later correction, reassessment, acceptance, fulfillment, recipient change, expiry or revocation must not be contradicted by stale dispatch. An action-needed notice does not guarantee the recipient can upload now and does not renew anything. Existing fresh-access/help rules remain separate.
- **No automatic resend or notification engine.** A checkbox default is not a new scheduler or provider guarantee. Distinguish requested, queued, accepted, delivered, failed/unknown and read only as supported by actual evidence. Avoid duplicate mail from source retries or per-file row fanout.
- **Test comprehension later.** Current sources support a plausible integrated choice and a real counterargument. After a founder answer, the full review should qualify visible consequence, repeated-action noise, state retention, privacy, current dispatch, faults and accessible intended-user behavior. This note does not claim those outcomes have passed.

## Recommendation and the genuine open choice

Recommend **A: useful source-purpose-bound exact-version staff comments with explicit supported page/sheet/location references and navigation**. Preserve a general comment on the exact version when a finer supported reference is not needed or is unavailable. **B adds optional visual point/region callouts on qualified static PDF/image surfaces**, while retaining every part of A. Both are substantive complete choices. “Comments versus no comments,” “version-only with no supported location,” and “use a generic Support conversation instead” would remove required baseline scope and are not neutral alternatives.

A keeps the first interaction understandable across the inherited reading profiles: select the actual version, comment, optionally name or select an actual supported page/location, and return to that location where the reader can do so safely. Its real cost is prose and manual finding within a page: “the signature area below the second table” can remain ambiguous. B lets staff point at that precise place and can reduce this friction for scans, images and visually dense pages. It adds coordinate capture/replay, transform correctness, marker access and accessible alternatives. Neither the frequency of that need nor the incremental effort has been measured in Asym. The absence of native code does not itself make B unsuitable.

The bounded first B does not require arbitrary text-range highlights, freehand ink, editing/redaction, annotations embedded into originals, comparison/diff, Office editing or automatic anchor migration. Choosing A does not ban a later independently qualified B. Choosing B must not make coordinate-capable preview a prerequisite for every lawful general comment.

## Primary technical evidence, not a library choice

The [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/) separates a comment body, target resource, segment selector and resource state. That supports keeping exact source/version identity distinct from an optional page/region selector. It does not mandate importing a JSON-LD platform, external annotation protocol, all selector types or permissions from an annotation standard. A selector is not an access grant.

[Mozilla's PDF.js examples](https://mozilla.github.io/pdf.js/examples/) describe page viewport transforms for scale, rotation and PDF-versus-canvas coordinates, with separate HiDPI drawing size. Context7's `/mozilla/pdf.js` current source corroborates that viewport construction includes the page view box and user unit. Thus a screen pixel rectangle without its exact page/geometry context is insufficient to persist a region. This is evidence of B's real transform work, not a selection of PDF.js or proof Core already uses it.

The practical consequence is source-aware geometry rather than arbitrary screenshot coordinates. Exact storage fields, normalization method and viewer implementation remain later qualification. No new vendor, OCR/extraction pipeline, converter or coordinate engine is selected by this research. UX research separately covers comparison products and keyboard/non-drag/mobile interaction; those examples cannot override current source confidentiality or grant permissions.

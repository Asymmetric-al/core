# Core CRM, CMS and database: WP1.5 census of the hosted Supabase projects

**Status.** Read-only census for the owner's sign-off, package WP1.5 of [`core-crm-cms-database-target-architecture.md`](./core-crm-cms-database-target-architecture.md) ("the plan"), section 12, WP1 census. Tracking issue [#2674](https://github.com/Asymmetric-al/core/issues/2674). Taken on 17 November 2026, between about 03:47 and 04:45 UTC, with the repository at `3e9ed22b4`.

**Scope.** The hosted Supabase project `development` (`pnmlrbgjiqzzsthsoikm`, us-east-1) and the hosted project named `production` (`btewedpsxwsjczvmegby`, us-west-2), and what points at them: the three Vercel projects of this repository, Vercel Blob, the Stripe sync engine and the GitHub repository settings. This report holds counts, names and classifications only. It contains no personal data and no secret. The row exports sit outside the repository (section 2.4).

## 1. Summary

Both hosted databases hold demo data. Nineteen `public` tables are byte-identical in the two projects, every one of the 36 donations carries a made-up `pi_demo_` payment reference, and the remaining rows belong to seed logins, a preview-smoke login or test personas that team members created for themselves. Development's CMS holds four starter templates and two untitled drafts, none published. Neither project stores a file in Supabase Storage, the team has no Vercel Blob store, and `cms.media` is empty in both. The Stripe sync engine in the production-named project mirrors 556 cancelled test-mode payment intents from one test account, nothing in Core reads it, and it still runs every minute. The census found real people's logins: six confirmed logins, most of them team members', and one unconfirmed sign-up on a public mailbox domain. Their data is test data, but resetting either project removes those logins. The live production domains (`admin`, `donor` and `missionary.asymmetric.al`) point at the production-named project and run commit `fb168d89` of 20 June 2026. Every preview and the `core-development` environment point at development. Payload connects as `postgres` in both projects, and the production-named project carries Payload's schema-push marker. Both projects take daily backups with point-in-time recovery off. Both are far behind source, and development's migration ledger records four changes under version numbers the repository does not use. The proposal is to classify everything as fixtures, with one owner decision on the real logins and three on the production-named project (section 8).

## 2. How the census was taken

### 2.1 Read path and read-only proof

- **SQL.** Every statement went through the Supabase CLI 2.121.0 (the version the repository pins) as `supabase db query --linked --project-ref <ref>`, which sends the SQL to the Management API. The repository wrapper `bun run supabase` could not start its pinned fallback inside the repository on this machine (an npm override conflict), so the same pinned version was run with `npx` from a scratch directory outside the repository. A helper wrapped each batch as `begin; set transaction read only; <selects>; rollback;` and refused any batch that contained a write keyword. Every result carries `current_setting('transaction_read_only')`, and every one returned `on`. The first batch was a harmless `select 1` probe.
- **Counts.** Every count in this report is an exact `count(*)`, run for each table inside the read-only transaction. No planner estimate is used.
- **Other services.** Supabase Management API reads through the CLI (`projects list`, `functions list`, `backups list`, `config diff`). Each was first run with debug output filtered to its URLs, which showed GET requests only. Vercel reads through `vercel api -X GET` and `vercel whoami`/`teams ls`. GitHub reads through `gh` (secret and variable names, environments, `ls-remote`, the Supabase CLI's own source). The census also sent plain GET requests to the six public app domains and their client scripts.
- **Secrets.** No query selected `encrypted_password`, a token column, or the contents of `vault.secrets`. Cron commands were reduced in SQL to their function name, URL path and two flags. Environment variable values were classified in memory and never printed or stored. The export SQL dropped every column whose name looks secret and replaced secret-named JSON keys and token-shaped values with `"[excluded]"` before the data left the database. 556 payment-intent client secrets inside `stripe.payment_intents._raw_data` were removed this way. A scan of all 96 export files afterwards found no secret-shaped key or value.

### 2.2 Side effects, disclosed

1. **Temporary CLI credential.** `supabase db query --linked` resolves a direct connection before it uses the Management API, and in doing so asks the platform to issue a temporary password, valid for about five minutes, for the platform's own role `cli_login_postgres` (the CLI prints "Initialising login role..."). The CLI source states that this connection is discarded and the query runs through the Management API. The audit met the same effect (audit 2.4). The census ran **22 query batches**, 12 against development and 10 against the production-named project, so the platform issued 22 such credentials. Two of the 22 batches stopped on a SQL error in the census query and changed nothing. No schema, data, setting or other role changed.
2. **Query statistics.** The census queries are now recorded in each project's `pg_stat_statements` and in the Management API's logs.
3. **Local only.** The CLI rewrote the tracked file `supabase/.temp/cli-latest` twice. It was restored with `git restore` both times, and the tree was clean before this report was written. A scratch database `wp15_census_source` was created in the shared disposable test Postgres (`core-crmcms-pg`), as the implementation record's rule 5 allows, to replay the migration chain for the drift comparison. It was dropped afterwards.

### 2.3 Drift method

`DATABASE_URL=<scratch database> node scripts/verify/supabase-migrations.mjs` replayed all 100 forward migrations and passed both of its gates. The same catalog query then ran against the replay and against each hosted project, and the results were compared by object name, for the schemas the repository owns: `public`, `authz`, `private`, `tenant_guard` and `platform`, plus the schema and role lists, Storage policies and buckets. `cms` was compared against the Payload migrations in `apps/admin/src/migrations`. Roles are cluster-wide in the shared container, so roles that other packages had created there, `cms_owner` and `cms_runtime`, are not counted as source.

### A.2 What each proposal emphasized

- **Proposal A (Fable 5.2).** Two server lanes — caller token by default, SQL commands for governed writes — and a database role per runtime. One real foreign key between the CMS Site record and the operational Site. Missionary updates operational. A live reader with cache tags for public pages. Rebuild rather than repair. Deferred the Phase 23 machinery.
- **Proposal B (GPT-6.1 Sol).** The most detailed money design: one claim protocol with leases and fencing, business-effect keys scoped by provider account, refund reservations, frozen document manifests, and a release classification of every financial ADR group. Required database policies inside `cms` and whole-site generations. Stripe Connect per legal entity. Preserve and classify existing data.
- **Proposal C (Gemini 4 Carbon).** Publish-time release rows in Core so the public site never depends on the admin app. JSON block storage and UUID keys. Private media with a sanitizing pipeline. A fuller Party model. Payload as the authoring store for missionary updates. A service-key gateway into tenant-guard commands.

### A.5 Limits of this round

- Proposals rest on the audit and on source reading. Nothing was run, and no proposal's mechanism has been tested on the pinned Payload pre-release.
- Upstream capabilities were checked against tagged source and official documentation by the seats and, for the adapter options and request-header access, once more by the coordinator.
- A Claude-based multi-agent verification pass failed on the account usage limit during Round 1. Cross-provider verifiers replaced it there; Round 2 relied on cross-review between seats.
- After this report was written, three read-only checking agents reviewed both reports. In this one they found a real gap — no database lane for guest giving — and ordering and consistency problems in the plan. Sections 5, 6, 10 and 12 were corrected in response.
- A second verification pass ran after that check, on a different Claude account. Its record and its limits are in the audit's section 11.1. For this report it raised 83 issues, none blocking and 32 material, several of them raised by more than one reviewer. The ones that changed the design or the plan:
  - Tenant administration and publishing had no membership to rest on (5.1).
  - The Web Studio tenant cookie could not reach Payload's `/api` routes, and it departs from ADR-0174 (5.2, 14).
  - The Site foreign key is an exception to ADR-0029, and ADR-0124 already settles the giving target (6.4, 14, 15.1).
  - Gift intake also trusts the donor server for a signed-in giver's identity, and the Site does not select the legal entity (5.3, 5.4).
  - Media upload needed a finalize step, because stripping changes the bytes a content-addressed key is computed from (6.6).
  - WP3 dropped Stripe columns that code still reads and reused a donor-bound invitation table (WP3, WP8).
  - The sign-up interim rule needed the host resolver that only WP3 delivers (WP2).
  - The target CMS cannot be built beside the prototype in one schema or configuration (WP6, WP7), and the name-collision gate needed an exception until then (7.4).
  - The WP11 journey could not run on a database already marked production, and development's marker was unstated (7.5, WP11).
  - Withdrawal cannot return 404 before the cache expiry is delivered (6.6, WP7). Round 5 superseded this: admission is read on every request (C.3).
  - Communications had no work package and is now an explicit deferral; findings covered in substance are now named where they land (section 12).
- A third council round then reviewed the finished plan. Its record is Appendix B.

### B.3 Preserved dissent

- **Admission on every request.** Seat B holds that every public request should read current admission before cached content is served, and fail closed when it cannot. The plan withdraws by command and keeps the admission read as the fallback, pending the bound the owner sets (15.1). Round 5 adopted Seat B's position (C.3).
- **Recurring giving before any real tenant.** Seats A and C judge that a support-raising product cannot launch without it. The plan names it first among the launch items and leaves the gate to the owner. Round 4 made it a package, WP12 (C.2).
- **A site-level generation head.** Seat B's dissent from Round 2 (11.3) stands. No seat reopened it in this round.

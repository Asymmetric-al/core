# TP4: one provider operation recovered after a lost response

**Purpose.** This is the fourth thin proof of plan section 12 ("Packages are containers, not single issues"): one provider operation recovered after a lost response, a WP8a issue with the resolve command of WP8c. It settles the row "Recovery after the provider's idempotency window" of plan 15.2: lose a response, pass the window, confirm the operation parks and creates nothing, then resolve it both ways, adopt and abandon.

**Base.** Integration branch at `6b1bfa01c`, stage 1 of the plan, with TP2's prototype applied (`tp2-prototype.patch`, made against `bec3bf06a`; only documents differ between the two). The prototype is not for merge. It is kept as one patch that includes TP2's (section 15).

**Where it ran.** Disposable Postgres 17.10 databases in the shared test container, on 17 and 18 November 2026: `tp4_proof` for the behaviour tests and `tp4_cost` for the cost measurement. No hosted project and no payment provider were used. The provider is a local fake that follows Stripe's documented idempotency rules.

## 1. Verdict

**It works, with changes to the plan's wording.** A provider request can be built so that no path sends it again after the provider's idempotency window and no path makes a second gift from one provider payment. Three things carry it. First, the window rule is a database rule on the outbox row, not a worker rule: the database clock fixes the first send time at the first claim, the deadline is that time plus 23 hours (Stripe's 24 less a margin), and a claim whose lease would end after the deadline is refused by the claim function, by a trigger and by a check, each alone. Second, the apply command learns one more match: when no intake holds a paid object, the object's metadata names the request that created it, on the same account. A provider event that arrives while that request is still in flight answers the lost response and makes the one gift; one that arrives after the request parked is held as evidence for a person and makes nothing. Third, the resolve command runs in the human lane with `contributions.use_provider_actions`, a reason, and one outcome per case. Adopt records the provider's object through the same code path as the worker entry and ends in exactly one gift at the amount the provider collected; abandon creates nothing and records that a payment may exist. 49 database tests pass, and each rule they rely on is shown failing when it is removed, apart from the few that section 6 marks as not removed: without the window rule, the fake provider charges twice. Parking costs well under the 9.2 budget for a transactional write, and so does each resolve path, alone and with twenty sessions, on a million rows a table (section 8). The list a person decides from was far too slow at that scale until it paged before joining and joined on plain keys; the final version reads a page of 50 in 40 ms at p95. The outbox design does not need to change before WP8 is groomed. Fourteen places in the plan need new wording (section 10). The catalog gate admits every command unchanged, and cannot see whether a human command checks the right capability (section 11).

## 3. Method

**Databases.** `tp4_proof` and `tp4_cost` each have the chain at `6b1bfa01c`, TP2's three migrations and TP4's three (114 in all), applied by `node scripts/verify/supabase-migrations.mjs`, and `scripts/proofs/tp4/harness.sql`. Both gates passed on each without edits to either gate.

**Calls.** As in TP2, each call emulates the Data API: one transaction, `SET LOCAL ROLE`, and for a person the claims settings and the `x-asym-assignment` request header. A worker's call runs as `service_role` in a transaction where no tenant is set; the test asserts that before every worker call.

**The worker.** The test's worker is WP8a's outbox worker reduced to its rules: claim the request, send exactly the key, parameters and account the claim returned, then report the provider's answer for the attempt it holds. A dropped response is reported as `unknown`. The webhook stand-in stores each provider event as the account-bound endpoint of 8.2 would, with the tenant taken from the event's connected account, and the event worker claims it and applies it. Reconciliation is reduced to its one effect here: it reads the provider's objects for a request and stores each as an event.

**Time.** A test moves time forward by moving a request's stored times back (first send, deadline, lease, next attempt), as the database owner with triggers off for that one statement, and the fake provider's clock forward by the same amount. Every rule compares a stored time with the database clock, so the two are equivalent. The window and margin are the real values, 24 hours and 1 hour.

**Fixtures.** Each tenant has a legal entity in dollars, two funds and the reserved fee-cover fund, one connected account in test mode and an active binding. An intake is as begin gift leaves it: lines of 6,000 and 4,000 on two funds and 300 on the fee-cover fund (10,300 in all), the frozen binding, giver name and email, status `pending`, no payment reference. Its provider request is unsent, with the key `gift:<intake>:create_payment`, the parameters (amount, currency, the saved payment method, and `metadata.asym_operation` naming the request), and their SHA-256 digest. People are a tenant administrator (`staff`, `finance`, administrator flag) in each tenant and a finance staff member without the flag in tenant one.

**Protection removed.** A rule under test is shown failing without it, except where section 6 says it was not removed. A function's rule is removed by patching its body for one case and restoring it; a table rule by disabling its trigger or dropping its constraint, in a rolled-back transaction or restored after the case.

Catalog: `public.resolve_parked_provider_work(uuid, uuid, text, text, uuid, jsonb)` and `public.parked_provider_work(uuid, timestamptz, uuid, integer)` are owned by `postgres`, invoker, EXECUTE for `authenticated` only. Their `tenant_guard` functions are owned by `tenant_guard`, definer, EXECUTE for `authenticated` only, and open with the two-argument preamble. The three worker entries and their wrappers are EXECUTE for `service_role` only. The core and the parking helper are owned by `postgres`, invoker, EXECUTE for `tenant_guard` only.

**Nothing from `auth`.** No TP4 object references the `auth` schema. The human commands reach the caller only through the preamble, which reads it through `tenant_guard.caller_id()`. On this base that function still calls `auth.uid()`; on Supabase's image it reads the request's claims instead, and the TP4 commands need no change for either.

**What a person resolving a case sees.** `parked_provider_work(tenant)` returns the tenant's open cases, newest first, keyset-paged by `(created_at, id)`, at most 100 a page. Each item has only:

- the case: its ID, kind, when it opened and why it parked (`window_passed` or `attempts_exhausted`);
- the request: its ID, kind, status, amount, currency, key, first send, deadline, whether the window is still open, attempts and last error;
- the intake: its ID, amount, currency, status, giver name and email, and payment reference;
- the evidence: the event's ID and type, the payment object, the amount asked and collected, the currency, the provider's time, and whether the object names this request;
- the outcomes allowed: retry while the window is open, adopt when there is paid evidence, abandon always.

No raw provider payload, no connected account of another tenant and no row of another tenant appears. Tenant two's administrator sees tenant two's case and not tenant one's. Naming another tenant, or calling without the capability, is refused (`42501`). With the function's tenant filter removed, the guard's row security still shows only the entered tenant's cases. Paging two at a time returns every case once, in order.

## 8. Cost

### 8.1 Method

`tp4_cost` has the chain, the prototype, the harness and `scripts/proofs/tp4/fixture.sql` with a million rows: two tenants, each with a million Parties, donors, intakes, intake lines, provider events, observations, staged gifts, lines, follow-up outbox rows and audit rows (TP2's fixture), plus a million completed provider requests, a hundred thousand resolved cases, an administrator, and 2,000 each of: requests whose response was lost and whose window passed (to park), parked requests with the provider's evidence (to adopt), and parked requests without it (to abandon). Half the adoptable intakes carry an existing donor's email and name, half a new email. The database is 11 GB. The load took 40.5 minutes with `session_replication_role = replica`; afterwards a sample of 1,000 lines and 500 open cases was deleted and re-inserted with every key and rule on, and passed.

The server is TP2's: Postgres 17.10 in the shared container on this Windows workstation, 20 CPUs, `shared_buffers` 128 MB, `work_mem` 4 MB, `synchronous_commit` on. Each call is one transaction in one round trip: begin, the caller's role (and for a person the claims and assignment header), the wrapper, commit. Every call acts on work no earlier call used: each park call parks, each adopt makes a gift with its Party or attribution, three lines, two follow-ups and two audit rows, and each abandon closes a request and its intake.

**Where the time goes.** Parking is a key read of the request and its update, one case and one audit row. Adopt is TP2's apply plus the case, the request and the intake; alone it costs about what TP2 measured for the apply (54 ms here at the median against TP2's 70 ms). Under twenty sessions, a sampler read the sessions' wait events every 25 ms. Most samples waited on reading data files, which is cold reads: 128 MB of shared buffers hold under 2% of an 11 GB database (adopt, one tenant: 1,473 of 2,179 samples). The next largest wait was flushing the commit log (adopt, one tenant: 425). Across all six concurrent phases, one sample showed a heavyweight lock wait, and it was a relation extension lock (`Lock:extend`, a file growing), not another session's row. No deadlock occurred.

**Locks.** Just before it commits, a call holds row locks on its own rows only. Adopt locks the case (`FOR UPDATE`), then the request, the evidence event and the intake (`FOR NO KEY UPDATE`), in that order; abandon locks the case, the request and the intake; parking locks the request. Each holds row-exclusive locks on the tables it writes, key-share locks on the parent rows its keys check (tenant, legal entity, binding, account, funds, currency, the donor or Party), and its transaction ID. Adopt also holds the per-tenant, per-email advisory lock of TP2's identity step. Calls on different cases share only parent rows, and key-share locks are compatible with each other, so one tenant and two tenants measure alike.

**The list read, three versions.** The first version joined every open case to the request, intake and event tables and then sorted and limited them: at 11 GB, p50 9.4 s. Part of that run overlapped the rebuild of `tp4_proof` on the same server, so its tail is inflated; its median alone is far past any budget. Paging the cases first, then joining the page of 50, cut it to p50 1.95 s. The plan showed why it was still slow: joined on `COALESCE(evidence_event_id, provider_event_id)`, the planner hashed all of the tenant's million events (22.9 s cold under `EXPLAIN`, 3.2 s of it JIT compilation). With the evidence ID computed as a column of the page and the event joined on it, every join is a key lookup: 5.9 ms under `EXPLAIN`, p50 16 ms and p95 40 ms through the Data API emulation. The patch has the final version. The tests passed on all three, because they check what the list returns, not how fast.

**Plans.** Every lookup the write paths make is an index scan under the guard role and its policy: the request by primary key (0.4 ms), the case by primary key (3 ms), the intake by `donations_payment_reference_key` (5 ms), the open case per request by `payment_repair_cases_one_open_per_operation` (0.7 ms, index only), the staged gift by `staged_gifts_donation_unique` (1.5 ms), and the list's page by `payment_repair_cases_open_list` (5.7 ms).

## 9. The shape WP8a and WP8c should adopt

**The record.** The provider-operation record is the outbox row of kind `provider_request` (plan 8.2: "extends the outbox"). It carries what it will send before it is sent, and the database fixes when it first went out:

```sql
ALTER TABLE public.donation_saga_outbox
  ADD COLUMN request_kind TEXT,                 -- 'create_payment'; refunds and cancels join in WP8c
  ADD COLUMN provider_account_ref UUID,         -- the bound account, the intake's
  ADD COLUMN request_params JSONB,              -- exactly what is sent, with metadata.asym_operation = id
  ADD COLUMN request_digest TEXT,               -- sha256 of request_params::text
  ADD COLUMN first_sent_at TIMESTAMPTZ,         -- set by the database at the first claim
  ADD COLUMN send_deadline TIMESTAMPTZ,         -- first_sent_at + 23 hours
  ADD COLUMN lease_expires_at TIMESTAMPTZ,      -- the lease (plan 8.2)
  ADD COLUMN max_attempts INTEGER NOT NULL DEFAULT 5,
  ADD COLUMN outcome_unknown BOOLEAN NOT NULL DEFAULT false,
  ADD COLUMN provider_object_id TEXT,
  ADD COLUMN parked_at TIMESTAMPTZ;
-- status adds 'parked', 'adopted', 'abandoned'
ALTER TABLE public.donation_saga_outbox
  ADD CHECK (request_digest = encode(sha256(convert_to(request_params::text, 'UTF8')), 'hex')),
  ADD CHECK ((request_params ->> 'amount') = amount::text AND (request_params ->> 'currency') = currency
             AND (request_params -> 'metadata' ->> 'asym_operation') = id::text),
  ADD CHECK (kind <> 'provider_request' OR idempotency_key = 'gift:' || donation_id || ':' || request_kind),
  ADD CHECK ((first_sent_at IS NULL) = (send_deadline IS NULL)
             AND (send_deadline IS NULL OR send_deadline <= first_sent_at + interval '23 hours')),
  ADD CHECK (lease_expires_at IS NULL OR send_deadline IS NULL OR lease_expires_at <= send_deadline),
  ADD CHECK (status <> 'parked' OR (outcome_unknown AND parked_at IS NOT NULL AND first_sent_at IS NOT NULL)),
  ADD CHECK (kind <> 'provider_request' OR status <> 'dead_letter' OR NOT outcome_unknown),
  ADD FOREIGN KEY (tenant_id, donation_id, provider_account_ref)
      REFERENCES public.donations (tenant_id, id, provider_account_ref);
CREATE UNIQUE INDEX ON public.donation_saga_outbox (tenant_id, donation_id, request_kind)
  WHERE kind = 'provider_request';
```

**The rules trigger** (`BEFORE INSERT OR UPDATE OR DELETE`, for `provider_request` rows): a request is created unsent; its tenant, intake, account, kind, key, parameters, digest, amount and currency never change; its first send time, deadline and provider object never change once set; attempts count up one claim at a time; a claim (attempt plus one) moves it to `processing` only from `pending`, `failed` or an expired lease, sets the first send time and deadline from `clock_timestamp()` on the first claim, marks the outcome unknown on a reclaim, and needs a lease that ends after now and no later than the deadline; the other transitions are `pending → abandoned`, `processing → completed | failed | parked | dead_letter`, `failed → completed | parked | dead_letter`, `parked → adopted | abandoned`, and `parked → failed` only before the deadline; an unknown outcome is cleared only by an answer to an attempt that went out or by a resolution; a request that went out is never deleted.

**The cases.** TP2's `payment_repair_cases` gains `operation_id`, `evidence_event_id` and the resolution (`resolution`, `resolution_reason`, `resolved_by`, `resolved_assignment_id`, `resolved_at`, `resolution_details`), the kinds `outcome_unknown`, `unmatched_payment` and `operation_contradiction`, a key `(tenant_id, operation_id, donation_id)` to the request, a check that a resolved case has its resolution, actor, time and a reason of 3 to 500 characters, a check that an adoption has evidence, one open case per request, and a trigger that makes a resolved case final and every case undeletable.

**The commands.**

**The claim's window rule**, the part that settles the risk:

```sql
v_now := clock_timestamp();
v_lease := v_now + make_interval(secs => p_lease_seconds);       -- 5 to 900 seconds
v_window_passed := v_op.first_sent_at IS NOT NULL AND v_lease > v_op.send_deadline;
IF v_window_passed OR v_op.attempt_count >= v_op.max_attempts THEN
  IF v_op.outcome_unknown OR v_op.status = 'processing' THEN
    -- one transaction: status 'parked', one 'outcome_unknown' case, one audit row
    v_case := tenant_guard.money_park_operation(v_op.id, 'outcome_unknown', ...);
    RETURN jsonb_build_object('outcome', 'parked', 'case_id', v_case);
  END IF;
  UPDATE ... SET status = 'dead_letter' ...;                    -- every attempt was definite
  RETURN jsonb_build_object('outcome', 'dead_letter');
END IF;
UPDATE ... SET status = 'processing', attempt_count = attempt_count + 1, lease_expires_at = v_lease ...;
```

**The core's operation match.** When no intake on the event's account holds the event's payment object, the core reads `metadata.asym_operation` from the stored object and locks that request on the same account. If the request is `completed` or `adopted` with this object, another writer just recorded it, and the core applies as usual. If it is `processing` or `failed`, has gone out, and the object's amount and currency are the request's, the core records the payment reference on the intake, completes the request and applies. If it is parked, the core attaches a paid or cancelled object to the open case as evidence. Otherwise it opens an `operation_contradiction` case. In the last two cases it creates nothing else. With no such request, the result is TP2's `unmatched`.

**Adopt.** Locks in one order: case, request, evidence event, intake. The evidence must be the case's own and a paid object naming the request. If the intake has no payment reference and the collected amount and currency are the intake's, adopt records the reference; otherwise it makes a new intake at the collected amount with the lines the person gives (no fee-cover line), on the request's binding or, with no request, the latest binding version of the event's account, and closes the request's intake as abandoned. Then it calls the core with the evidence, marks the request `adopted`, resolves the case and writes an audit row with the actor.

**Abandon.** For an `outcome_unknown` case: the request `abandoned`, its intake `abandoned` if it has no gift, and the case resolved with what may exist at the provider. For the other kinds: the case resolved, nothing else.

**Grants.** The guard adds `UPDATE` on the outbox and on `payment_repair_cases`, and `INSERT` on `donations` and `donation_intake_lines`, behind TP2's `tenant_guard_isolation` policies. The service key needs `SELECT` on the outbox for the wrapper's anchor read.

## 10. Where the plan's wording must change

1. **The window rule is a database rule with a margin, and its clock is the database's.** 8.1 says "the same key and parameters, and only inside the provider's guaranteed window, 24 hours for Stripe". A rule in the worker binds only that worker: the legacy saga claim or a direct write would still send. The prototype sets the first send time from the database clock at the first claim, puts the deadline 23 hours later, and refuses any claim whose lease would end after it; the request's lease, and the worker's HTTP timeout inside it, keep every send inside the provider's 24 hours. Stripe's documentation describes the window as a minimum: a key may be removed once it is at least 24 hours old, and a reused key after that is a new request. So 24 hours is the earliest a key may be forgotten, not a promise that it will be. Proposed: "A request goes out only while a lease that ends before its first claim plus 23 hours can be granted; the database records the first claim and refuses a later one."
2. **One request of each kind per gift.** 8.1's key is "derived from the gift". A key derived from the gift is not enough if a writer can create a second request for the same gift: the prototype adds one `create_payment` request per intake, so no key can charge an intake twice. Proposed: "derived from the gift and the request kind; one request of each kind per gift".
3. **The record states what it sends.** 8.1 stores "the request, a digest of its parameters and its first submission time before dispatch". The prototype stores the parameters themselves, checks the digest against them, ties their amount and currency to the row and names the request in the provider metadata. The worker sends what the claim returns and nothing it builds. Proposed: add "the parameters themselves, and the request's own ID in the provider metadata".
4. **A lost response is not unmatched.** 8.3 parks "a provider payment that matches no local operation". With the request named in the object's metadata, a late event for a request in flight matches that request and makes the one gift, so it does not park. Only an object that names no request on that account and matches no intake is unmatched (TP2 item 2). Proposed: "matches no intake and names no request on that account".
5. **A parked request takes evidence, not effects.** Neither 8.1 nor 8.3 says what the late event does after parking. The prototype attaches it to the case and creates nothing; a person adopts it. Proposed: add to "Resolve parked provider work": "a provider event for a parked request becomes the case's evidence and changes nothing else".
6. **Adopt goes through "the same apply command" by sharing its code, not its entry.** The worker entry needs a claimed event and the current attempt. Adopt has neither: its evidence is an event already processed. The prototype splits TP2's command into a shared core and two callers. Proposed: "through the same apply code as the worker entry".
7. **Reconciliation stores what it finds as evidence.** 8.2 says a difference "opens a repair case; nothing is changed blindly". Adopt needs the provider's object as stored evidence when no event arrived. The prototype stores reconciliation's read in the event store, where it attaches to the case like a webhook event. Proposed: "stores the provider's object it compared as evidence, and opens or annotates a repair case".
8. **Adopt at another amount takes its lines from the person.** 8.1 says staff "set its lines through allocation review". Under TP2's line-sum rules a staged gift cannot exist without lines that sum to its amount, so the lines must exist when adopt makes the gift. The prototype takes them in the adopt call and holds the gift for review. A placeholder line on a per-entity suspense fund would work too, and would need a reserved fund like the fee-cover fund. Proposed: "adopt records a gift at the amount the provider collected with the lines the person gives, held for review".
9. **Abandon of a payment request closes the intake; a new request is a new intake.** 8.1 says abandon "lets a new request be made under a new key". For a payment, one request per intake (item 2) means a new attempt is a new checkout. The prototype closes the intake as abandoned and records that a payment may exist. A late event after abandon opens a contradiction case; adopting it makes the one gift, consistent with "a payment that succeeded first wins". For a refund (WP8c), a new refund command is a new request, as the plan says.
10. **"Resets the attempts" must not reset the attempt counter.** 8.1's retry "resets the attempts". The attempt counter is the lease's fencing number (TP2 item 11): reset to zero, a dead worker holding attempt 1 could finish the request again. The prototype raises the attempt budget and leaves the counter, and a trigger refuses any decrease. Proposed: "raises its attempt budget and queues it again".
11. **Two more case kinds, and a read path.** 8.1 resolves parked operations and dead-lettered events. The prototype also needs `unmatched_payment` (TP2 item 2) and `operation_contradiction` (evidence that contradicts a closed request), and a read for the people who resolve them. 5.4 has no read path for cases; the prototype uses a read entry point with the same capability. WP8c should name both.
12. **The worker's "success" is a link, not a payment.** 8.1 does not say what the worker's own report may create. In the prototype it records the payment reference and completes the request, and no gift comes from it; the gift comes only from the provider's signed event or reconciliation's stored object. Proposed: say so in "Create provider objects".
13. **The dead-lettered event retry cannot reuse "one case per event".** 8.1 lists "Retry: for a dead-lettered inbound event". TP2's `payment_repair_cases_event_key` allows one case per event ever. A retried event that dead-letters again could not park a second case, and its evidence would sit unflagged. The prototype does not build the event retry. WP8c should make the key "one open case per event".
14. **The acceptance line needs the parking step.** WP8's "A provider response that is lost and retried after the provider's idempotency window parks the operation for reconciliation and creates nothing twice" describes a retry after the window. Under the rule nothing is retried then. Proposed: "A request whose response is lost is not sent again after its window: the next claim parks it and creates nothing."

**TP2's items after building on them.**

- **Item 2** (an unmatched payment parks when its event runs out of attempts): agree. Built and tested: 8 `unmatched` attempts and no case, then one `unmatched_payment` case at dead-letter. With the operation match (item 4 above), a lost response no longer reaches this path, so only payments Core never asked for do.
- **Item 7** (the staged gift's key freezes the intake's amount, so adopt first creates an intake at the collected amount): agree, and it is narrower than it reads. When the collected amount and currency are the intake's, adopt only records the payment reference on the existing intake; no new intake is needed. A new intake is needed when the amount differs or there is no intake, and then the person must give its lines (item 8 above).
- **Item 11** (event completion carries the lease's attempt): agree, and it applies to the outbox too. The worker's report carries the attempt; a stale one is refused (`55000`), and without that check the dead worker's report takes the live worker's lease. Item 10 above is the same point for the retry.

## 11. What the convention and the gate need

**The convention has a place for every command**, and the gate admitted them unchanged: three worker entries, two human entries, five wrappers. The human entries use a two-argument preamble, `begin_human_command(tenant, capability)`, which the gate's first-statement check already accepts. Two helpers live in `tenant_guard` owned by `postgres`, invoker, EXECUTE for the guard only: the shared core and the parking helper. The convention has no line for such helpers. Proposed for "Command lane": "A helper that a command calls is owned by `postgres`, SECURITY INVOKER, EXECUTE for `tenant_guard` only, so it runs as the guard under its policies."

**What the gate cannot see.** `scripts/proofs/tp4/gate-plants.mjs` plants eight variants in a rolled-back transaction and runs the gate's evaluator on each:

| Plant                                                                  | Gate                                                                                           |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| A human resolve command with the one-argument preamble (no capability) | passes                                                                                         |
| A human command naming a capability the registry does not have         | passes                                                                                         |
| A worker entry that never enters a tenant                              | passes (TP2's `WORKER_NO_ENTER`)                                                               |
| A worker wrapper that passes its caller's tenant to the guard          | passes (TP2's `WORKER_WRAPPER_TENANT_ARGUMENT`)                                                |
| The shared core executable by the service key                          | passes; refused at run time one level down, `permission denied for function current_tenant_id` |
| The shared core executable by signed-in users                          | `COMMAND_HUMAN_NO_PREAMBLE`                                                                    |
| A worker entry also executable by signed-in users                      | `COMMAND_LANE_MIXED`, `COMMAND_HUMAN_NO_PREAMBLE`                                              |
| The human resolve wrapper also executable by the service key           | passes; refused at run time by the guard function's grants                                     |

Proposed checks, beside TP2's three:

- `COMMAND_CAPABILITY`: a human entry point that writes a governed table opens with `begin_human_command(<tenant>, '<capability>')` naming a capability literal that the code registry has. The one-argument preamble stays for entry points on a reviewed list (today `resolve_command_assignment`). The gate reads the capability names from a generated list of `packages/auth/capabilities/registry.ts`.
- `COMMAND_HELPER_EXPOSED`: a function in `tenant_guard` that `service_role` may execute is owned by `tenant_guard`, is SECURITY DEFINER, and opens with `tenant_guard.enter(...)`. This catches the core given to the service key.
- `WRAPPER_GRANTS_HUMAN`: a wrapper that calls only human entry points gives no EXECUTE to `service_role`. It is hygiene: the guard function refuses anyway.

## 12. What the worker must and must never do

These are WP8a's rules for the outbox worker, each testable with the fake provider.

The worker must:

1. Send only after a `claimed` result, and send exactly the `idempotency_key`, `request` and `provider_account` it returned, once per claim.
2. Use an HTTP timeout shorter than its lease, and report within the lease.
3. Report the answer for the attempt it holds, classified: the provider object (`succeeded`); a definite refusal the provider stored under the key, such as a declined card (`refused`); a request the provider certainly did not run, such as a refused connection, a rate-limit answer before execution, or an idempotency error (`not_performed`); anything else, including a timeout, a 5xx and a reset after sending (`unknown`). An idempotency error never counts as `refused`: it says nothing about the first request with that key.
4. Stop on any other claim result (`held`, `not_due`, `closed`, `parked`, `dead_letter`) and on a `55000` refusal of its report, logging the provider object ID if it has one.
5. Treat its own `succeeded` as a link only. The gift comes from the provider's event.

The worker must never:

1. Build a key or parameters, or send a request the claim did not return.
2. Send a request whose claim was refused, or retry a request itself.
3. Write the outbox row, the intake or a case directly.
4. Report `not_performed` when it cannot prove the request never left, or `refused` for an answer the provider did not store under the key.
5. Resolve a case. Only a person does, in the human lane.

## 13. Other findings

- **WP8a's own requests mostly move no money.** A one-time checkout's "create payment intent" makes an unconfirmed object; the browser confirms it with the client secret, which a lost response never delivered. After the window a resend makes a second unconfirmed object, not a second charge. It can still collect money once: if the server hands the client secret to the browser and then fails to record the object, the donor pays an object Core does not know. That is the same lost response, and the operation match covers it. The requests that move money are refunds (WP8c) and charges the server confirms with a saved payment method (signed-in giving and WP12). A cancel moves none. The rule and the record are the same for all of them; adopt's effect differs, because a refund adopts a refund and not a gift. The proof used the worst case.
- **The match uses provider metadata inside one account.** NR-05 forbids taking a tenant from metadata. The core does not: the tenant comes from the event's account, and the metadata only selects a request on that account. An object forged by the account's own owner can only name that tenant's requests, and it must also match the requested amount and currency; anything else parks a contradiction. A Stripe event also names the API request that caused it, with that request's idempotency key, which could confirm the match. It is empty when no request caused the event, as when an asynchronous payment settles later, so the prototype does not rely on it.
- **The legacy writers fail on the new rules.** `claim_donation_saga_event` cannot claim a provider request (`55000`: a claim needs a lease; tested). `begin_donation_saga` inserts a provider request without the request fields, which `donation_saga_outbox_request_complete` refuses (read from its body, not run). Both go in the same release as the record (TP2 item 8).
- **Replacing a guard-owned function.** TP4's commands migration replaces TP2's `tenant_guard.apply_payment_outcome` with `CREATE OR REPLACE` as `postgres`. Here `postgres` is a superuser. On hosted Supabase it is not, and replacing a function owned by `tenant_guard` needs the same rights as the owner transfer (WP1's hosted proof).
- **The read bypasses the field-policy projection.** `parked_provider_work` returns the giver's name and email from SQL. Their field policies admit them on the Mission Control surface, but the projection layer in `packages/api` does not run. WP8c should read cases through that layer, or WP2a's read policy for staff with the capability should replace the read entry.
- **The resolver is the tenant administrator by default.** `contributions.use_provider_actions` is in the finance approver bundle, which only the administrator flag grants (`packages/auth/capabilities/bundles.ts`). Finance staff without the flag cannot adopt or abandon. That matches the registry; whether finance staff should resolve is an owner's call (15.1).
- **A Mission Control list over money tables must page before it joins, and join on plain keys.** The first list read joined every open case to three million-row tables before it limited them (p50 9.4 s). Paged first but joined to the events on a `COALESCE`, it still hashed the tenant's million events (p50 1.95 s). Joined on a column of the page, it takes 16 ms at the median. The behaviour tests passed on all three. WP8c, and every Mission Control list built on these tables, should carry a plan check at fixture scale in its acceptance evidence, as 9.2's "no unbounded read" implies.
- **The time travel needs replica mode.** Moving a request's stored times back is refused by the rules trigger, as it should be. The test does it as the owner with `session_replication_role = replica` for one statement.

## 14. Not measured

- **A real provider.** Stripe in test mode would show when a key is in fact pruned, what a concurrent request with the same key returns, whether every event for an object carries its metadata, and when events carry `request.idempotency_key`. None was called.
- **Hosted Supabase.** The owner transfer and the replacement of a guard-owned function, `session_replication_role`, clock skew between the database and the provider, and timings on a hosted compute size.
- **The Data API.** Calls emulate PostgREST with `SET LOCAL ROLE`.
- **Real elapsed time.** Tests move stored times, not the clock. A run that waits out a short window would add little: every rule reads the same clock.
- **The rest of WP8c.** Refund, cancel and capture requests, the reservation an abandon releases, the reconciliation job's paging and comparison, the retry of a dead-lettered event, and the Mission Control task each case should raise. Disconnected bindings parking their queued requests (8.2) use the same table and were not built.
- **The other capability bundles and the tenant-status check.** The stand-in encodes the money bundles only, and no tenant status exists on this base (WP3).
- **Bloat and vacuum** of the outbox's updates over time, and the growth of resolved cases.

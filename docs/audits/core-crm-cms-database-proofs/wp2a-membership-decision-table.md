# WP2a decision table: every fixture user, tenant and role under the old rules and the new

**Purpose.** The plan requires this table before cutover (section 12, WP2 "Writer and cutover"): there is no traffic to compare, so the comparison is made person by person. It records, for every fixture identity and for every class of hosted login the census found, what each surface admits under the rules before WP2a and after it. Review it before the change is integrated.

**Package.** WP2a, the membership core (issue AL-2675). The application treats membership as the only authority from this package; the database does so from the second release of WP2b.

**Sources.** Old rules: `packages/auth/permissions.ts`, `packages/auth/context.ts`, `packages/auth/resolve-user-role.ts`, the three `proxy.ts` files and `apps/admin/src/cms/auth/supabase-strategy.ts` at the WP2a base (`d2fcbf525`). New rules: the same files after WP2a, the migrations `…_membership_lifecycle_and_tenant_admin_flag.sql`, `…_assignment_capability_function.sql` and `…_membership_readers_and_member_directory.sql`, and `packages/auth/capabilities/bundles.ts`. Hosted login classes: the census, section 4.1 (`docs/audits/core-crm-cms-database-census.md`).

## 5. Choices this table makes

- **Sub-role.** Every staff row the data step creates, and every existing member-care staff row, takes the development sub-role. The table names no other. Where a person already holds a development row in that tenant, it carries the access and the member-care row is revoked (kept, with `revoked_at`).
- **The flag on `super_admin` profiles.** The plan's data rule flags admin profiles' staff rows. This table also flags the staff row of a `super_admin` profile in its own tenant, so that a team operator keeps administering that one tenant until WP2c's operator list exists; it gains nothing in any other tenant and no platform function. Dropping this choice is one condition in step 4b and 4c of the migration.
- **Revocations stand, with one exception the one-row rule forces.** A class that has any row in the tenant, live or revoked, gets no new row (step 4b), so the backfill never creates access a deactivation took away (A03). The exception is step 4a: when a person holds a live member-care staff row and a revoked development row in the same tenant, the development row is made live again and the member-care row is revoked. The person kept staff access throughout, through the member-care row; plan 5.1 gives a person one staff row per tenant to act under, and member care is no longer a default sub-role, so the access moves to the development row instead of a second row being created. The real-stack data step proves it (`careAndDev` in `tests/unit/acceptance/issue-2675/membership-core.realstack.acceptance.test.ts`: the development row ends live, the member-care row revoked). A person whose staff access was revoked outright, with no live staff row, gets nothing back.
- **The missionary workspace is for missionaries.** Staff without a missionary row no longer enter it (plan 5.1: the workspace acts on the missionary row).

## 6. Deliberate behaviour changes to review

1. A profile role grants nothing on any surface. A person whose only authority was `profiles.role` (A03) is refused unless the data step gave them a row.
2. `super_admin` is no longer platform-wide; its platform gates are closed until WP2c. No request carries the `super_admin` role now: the auth context and the Payload strategy give `admin` for a flagged staff row and the class otherwise. These gates therefore admit nobody until WP2c's operator list (council round 1, F10); the handler gates are pinned by count in `tests/unit/acceptance/issue-2675/role-names.acceptance.test.ts`:
   - **Eve kill switches** (`packages/api/src/eve/governance/route.ts`, PATCH): nobody changes a kill switch, the global one included. A tenant administrator still reads the governance state and the tenant's audit history (GET).
   - **Eve notification channels and recipients** (`packages/api/src/eve/notifications/route.ts`, PATCH): nobody pauses, enables or re-points a channel or changes a recipient. A tenant administrator still reads them (GET). Item 8 says who receives.
   - **Eve release safety** (`set_eve_release_safety_control` in `20260718102000_eve_final_launch_verification.sql`): clearing emergency-off and disabling release without an emergency admit only the `super_admin` actor role, so nobody can do either. A tenant administrator still engages emergency-off: since council round 2 (R1) the SQL checks the actor's live staff row with the flag in the tenant, as the application does, so it admits a flagged administrator whatever the profile's role or tenant column says, and refuses an unflagged, revoked or foreign row (section 7).
   - **Eve launch permissions** (`packages/api/src/eve/launch-readiness/control.ts`, `grantEveLaunchPermission`): nobody grants one, so no new launch can be prepared until WP2c.
   - **Eve model policy** (`packages/api/src/eve/model-policy/permissions.ts`): the platform owner's branch admits nobody; a holder of an Eve AI settings grant still passes. The Eve policy permission in SQL (`has_eve_policy_permission`, `20260718015747_eve_approval_budget_policy.sql`) likewise admits only an existing grant.
   - **Global Eve retention expiry** (`packages/api/src/eve/retention/control.ts`, `runEveRetentionExpiry`): nobody runs it. Retention holds stay open to a tenant administrator, checked by the same live flagged staff row (section 7).
   - **Cross-tenant Eve audit**: the `super_admin` audit tenant override (`packages/api/src/eve/audit/identity.ts`) and the all-tenant audit history in the governance GET and PATCH answers. Everyone sees their own tenant's history.
   - **Cross-tenant CRM** (`packages/api/src/crm/auth/access.ts`, `isSuperAdmin`): nobody reads another tenant's CRM records.
   - **Cross-tenant fund and missionary directories** (`packages/api/src/admin/fund-directory.ts`, `packages/api/src/admin/missionary-directory.ts`): both list the caller's tenant only.
   - **Member care and Support Hub** (`packages/api/src/admin/member-care/route-helpers.ts`, `packages/api/src/admin/support-hub/route-helpers.ts`): the contexts' `isSuperAdmin` is false for everyone.

   - **`withOperation`'s `roles` option** (`packages/api/src/shared/with-operation.ts`): only the gates above pass it.
   - **GraphQL `updateUserRole`** (`packages/graphql/handler.ts`, `public.atomic_update_user_role_with_audit`): closed by the surface, not by `super_admin`. What the role-change command writes since WP2a: it changes the profile role, which the restricted-note policies and the release already running still read; it grants and revokes no application access, which membership alone decides. No person can reach it: GraphQL is mounted in the donor app only, whose proxy fixes the donor class, and a donor row never holds `people.manage_members`.    `docs/guides/operations/eve-emergency.md` says what an Eve operator can and cannot do in an incident until then.

## Observed limits and existing failures

- Admin and missionary routes have existing reduced-motion hydration mismatches. Original admin server logs also contain the TanStack live-query `Missing getServerSnapshot` SSR fallback; provider-backed table behavior is not verified by the fallback captures. The server rendered motion opacity/transform differs from the initial reduced-motion client state. Existing `DynamicIcon` warnings also report `XCircle` as unknown. These were observed before implementation.
- Missionary profile renders its actual retry/error state because admin endpoints require a service-role key. Its productive profile form was not verified against a local seeded database. Missionary partner rows are absent in this datasource, so the row-specific Edit Partner dialog was not reachable in the product app.
- Admin CRM, reports, contributions, care/directory and related data surfaces may remain in loading or show their unavailable-data errors without configured business data. Available shell, empty board, page structure, and local scaffold interactions were captured. Sorting/filtering over productive server records and a care profile were not verified.
- Donor portal bootstrap uses the repository's existing deterministic E2E fixture. Donor ministry feed endpoints return 503 without provider data. Donor `/where-we-work` produced browser errors and an unavailable map; this does not establish a successful geographic workflow.
- An unknown donor CMS slug renders the product error boundary when Payload data is unavailable. A worker-specific unknown route yields the actual 404. CMS publication and authenticated backend workflows remain unverified.
- The existing Base UI compliance harness renders actual first-party shared/application components with inert boundary adapters. The supplemental shared fixture also adapts Next Image to a native image with the same fill geometry and uses placeholder environment values. Its screenshots are explicitly labelled `shared-*` and establish component rendering only; they are not substitutes for product route screenshots.
- Native `/email` and `/pdf` returned HTTP 200, but their productive studio chrome did not become available in the baseline runtime. `/web-studio` and the five inspected gallery/create/detail paths returned HTTP 500 with the real configuration/error boundary because a Payload database was unavailable. Native gallery, wizard, editor, and studio navigation states are not verified by these error captures.
- Cold compilation of additional admin routes exhausted the 16 GiB runtime while all apps ran concurrently; the browser and admin process failed. The owned donor, missionary, and Eve processes were stopped, and the correct admin routes were retried with one app and one browser. Failed cold-start attempts were not counted as successful checks. All owned original Next, Eve, and Vite servers were stopped after baseline capture.
- Initial selector attempts for FAQ/search and floating-bar capture were corrected against actual component APIs. The corrected FAQ no-results, default expanded answer, and selected-row screenshots are retained. The historical `faq-answer` interaction filename records toggling the initially expanded first answer closed; it is not an open-answer claim. Failed attempts in the metadata are not counted as passed behavior checks.

The supplementary CMS/studio fixture mounts the actual StudioLayout, template-create form, studio controls, and lazy Recharts report factories. Auth, preferences, router and config use the existing unit seams; network is disabled except one locally held fixture promise. Baseline narrow navigation lacks a studio navigation trigger, and rejecting a pending create request produces an unhandled error with preserved input but no alert. Those are component contract observations, not a successful CMS workflow. The actual shared DataGrid and five-stage Mobilize pipeline also have original-source fixture captures.

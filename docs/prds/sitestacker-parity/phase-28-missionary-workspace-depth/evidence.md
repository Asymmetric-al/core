## Actual implementation inspected versus intended Phase 28

Current missionary task creation and updates use the canonical API package.
Creation derives `missionary_id` from authenticated context; associated donor
access checks include tenant and missionary. Current task list/item queries
are profile-scoped through a privileged client; updates set `completed_at` from
the requested status. This establishes basic task CRUD, not the developing
multi-purpose obligation, exact source-event, immutable completion evidence,
correction or durable retry semantics. Do not assume the existing scope or
mutation behavior qualifies those stronger contracts.

Current donor mutations record activity separately from tasks and update
relationships through the API package. Phase 28's “record actual work once”
needs proof of the combined public business result, including no fabricated
call from opening a dialer and no duplicate interaction after a lost response.

The missionary Email Studio route currently renders **Coming Soon** and a
disabled notification button. Its feature description is not evidence of
newsletter composition, membership, delivery, print or qualified AI behavior.
Bounded searches of missionary/API implementation found no native referral,
coaching, saved-preparation or newsletter producer that establishes the complete
new lifecycle. Other owner surfaces must be verified independently; absence in
these paths is not a claim that the entire repository contains no related work.

`getAuthContext` calls server `auth.getUser`, then resolves profile and
memberships. A valid Auth user with no profile produces `isAuthenticated: false`
in that workforce-oriented context. D42 public signed-in readers therefore need
their exact qualified identity-owner path; tests must not force a fake profile,
tenant membership or staff role merely to exercise Join.

Committed Supabase configuration has email confirmation disabled for local
signup; demo-user provisioning explicitly sets `email_confirm: true`. Thus a
demo confirmed timestamp cannot be the positive mailbox-proof fixture for D42.
Use the qualified Auth producer evidence required by the adopted decision, plus
negative fixtures for auto-confirmed/imported/admin-marked/unknown evidence.

## What is verified, selected and still to prove

- **Verified repository facts:** existing sources and test seams described above, source ownership declarations, exact prior decisions, canonical P27 authoring convention, current tracker readback and source-file consistency. Documentation qualification is reported separately in the publication record.
- **Selected intended behavior:** the canonical D1–D50/C01–C20 synthesis and narrow owner amendments. These are implementation contracts, not descriptions of shipped behavior.
- **Product judgments:** reuse familiar native work, fewer settings, optional coaching/guidance, persistent truthful feedback and bounded purpose-specific controls. They follow the user's decisions and inspected design system; no quantitative donor-conversion claim is made.
- **Implementation qualification still required:** exact source producer availability, real Auth provenance, grants/RLS/concurrency, provider contract, complete financial scope, migration/restore, performance budgets and complete user journeys. Each is mapped by the normative proof and domain requirements; missing proof gates its exact dependent effect.

No new interviews, usability sessions, live tenant dataset or mission-specific workflow validation occurred during synthesis. The spec records tasks/outcomes and blocking-friction response instead of pretending that desk research proves usability.

No old research program, source-bound simulation or unrelated green test is reused as evidence that new production behavior passes. This documentation-only task does not run live providers, post gifts, send supporter messages, change tenant configuration or mutate a hosted database.

## Problem Statement

Every missions organization tracks ministry-specific data that no CRM vendor can predict — visa category, language proficiency, home-assignment cycle, sending-church tier, church-partnership stage, mobilization milestone, training progress, coaching status, certifications and their expiry dates, references, regional-assignment history. Today, adding any of these to Asym means an engineering ticket or an off-platform spreadsheet. Staff cannot shape the CRM to their ministry without a developer, so ministry-critical data lives outside the system, ungoverned and un-reportable.

But custom fields are also the single easiest way for a tenant to create **sensitive, unclassified, ungoverned, leak-prone data.** Every custom field is a potential surface leak, export column, report field, workflow trigger, public-page field, email merge field, and public-API field — unless the platform governs it _from birth_. In a missions context this is not hypothetical: an "un-classified" custom field on a restricted-ministry worker is a physical-safety risk, and an accidentally-public "internal note" field is a donor-trust and compliance failure. This is precisely why this capability sits **after** Phase 10 (classification) and Phase 3 (projection): a custom field that isn't born classified and policy-bound is a landmine.

Additionally, a naive custom-field system creates its own kind of technical debt: a second, ungoverned database inside the product — unbounded schema sprawl, per-tenant migrations, raw entity-attribute-value (EAV) tables that make reporting impossible, fields that break every report/import/workflow when renamed or deleted, and picklist changes that silently corrupt years of historical records.

## Solution

A tenant-admin **Custom Fields & Custom Collections** product that gives organizations controlled extensibility on their CRM records without engineering involvement and without compromising governance:

- **Tenant admins define their own fields** (16 safe types) and **repeatable child collections** (e.g. a person with many Certifications) on approved CRM record types, through a guided, plain-language admin experience — with **zero tenant-triggered database migrations** and **no raw EAV**.
- **Every field is born governed.** At creation an admin answers one plain-language question — _"Who should be able to see this?"_ — which sets the field's sensitivity classification and its exposure across **every egress channel** (screens, exports, reports, imports, the public API, workflows, email merge, receipts, webhooks, search, logs, and the database tier). The safe default is Mission-Control-only; opening anything up is a deliberate, audited, sometimes reviewed action, and the most dangerous exposures aren't even offered in the UI.
- **Custom fields are first-class everywhere** — list columns, filters, saved views, governed CSV exports, the report builder, imports, the public API, and workflows all consume the field with full **type fidelity** and **policy enforcement**, through _one_ shared field-catalog contract that nothing can bypass.
- **The CRM is safe to evolve.** Renaming a field or a dropdown option never corrupts history; making a field required or setting a default never silently rewrites or locks existing records; retiring a field is previewed ("here's everything that uses it"), reversible (archive, then a recycle bin), and never silently breaks a report, import, or workflow.
- **Everything is auditable and supportable** — a tamper-evident audit trail of every definition and sensitive-value change, quotas that keep the product fast, and a data-health cleanup surface.

The result: Asym fits any missions organization without engineers adding fields every time, while remaining one coherent, governed platform — not a collection of ungoverned tenant mini-databases.

## User Stories

### Tenant admin — creating & configuring

1. As an org admin, I want to add a custom field (e.g. "Visa Status") to a record type without writing code, so that we can track ministry-specific data ourselves.
2. As an org admin, I want to pick what _kind_ of information a field holds (text, number, date, dropdown, checkbox, etc.) from plain-language options with nonprofit examples, so that I don't need to understand data types.
3. As an org admin, I want the field's internal/machine name derived automatically and shown read-only, so that I never accidentally break an integration by "renaming" it.
4. As an org admin, I want to answer one plain-language "Who should be able to see this?" question, so that the field's privacy and exposure are set correctly without me understanding security jargon.
5. As an org admin, I want "Our team only" pre-selected by default, so that a field I create without thinking is safe (Mission-Control-only) by default.
6. As an org admin, I want a live preview of how the field will look on the record as I configure it, so that I can see the result before saving.
7. As an org admin, I want to add dropdown options to a single/multi-select field, so that staff choose from a controlled list.
8. As an org admin, I want to mark a field required _on specific surfaces_ (e.g. the staff form) without it blocking imports or editing old records, so that new data is complete without breaking anything.
9. As an org admin, I want to set a default value that only applies to new records, so that I never fabricate data on historical records.
10. As an org admin, I want to place fields into named sections and order them within the record, so that the record reads sensibly.
11. As an org admin, I want to build a repeatable "collection" (e.g. Certifications) with its own fields, so that one person can have many of them.
12. As an org admin, I want to classify a collection once and have its child fields inherit that classification, so that I don't forget to secure a field.
13. As an org admin, I want to reorder collection items by dragging, so that the most important entry appears first.
14. As an org admin, I want examples and teaching empty states, so that I know what to do the first time.
15. As an org admin, I want to see how many fields/collections/options I've used against the limits, so that I can plan and clean up.

### Data-governance admin — classification & change control

16. As a data-governance admin, I want the sensitive actions (making a field public, lowering its privacy, exposing it to the API) restricted to my role, so that an ordinary admin can't accidentally expose data.
17. As a data-governance admin, I want a widening (making something more visible) to require review and show me its blast radius ("this exposes X to the public API and N historical records"), so that I approve exposures with full sight.
18. As a data-governance admin, I want reclassifying a populated field to a more-exposed state to require typing a confirmation phrase, so that it can't happen by reflex.
19. As a data-governance admin, I want care/security-classified fields to have no "export" or "make public" toggle at all, so that the dangerous option is impossible, not just discouraged.
20. As a data-governance admin, I want making a field stricter to take effect immediately and trigger the forward-exposure scrub, so that newly-sensitive data stops leaking going forward.
21. As a data-governance admin, I want an honest notice that a stricter reclassification cannot retract already-sent emails/receipts/exports, so that I understand the residual exposure.
22. As a data-governance admin, I want every classification and exposure change recorded immutably with who/when/before→after, so that we can prove our governance.

### Staff operators, finance, care, missionary-support

23. As a staff operator, I want custom fields to appear on the record detail exactly where the admin placed them, so that the record is complete and organized.
24. As a staff operator, I want to enter and edit custom values where I'm permitted, with type-appropriate inputs, so that data entry is fast and correct.

30. As a field leader, I want a restricted-ministry worker's custom fields withheld from every public and external surface automatically, so that identity safety is never left to manual configuration.
31. As a staff operator, I want a custom field I'm not cleared to see to simply not appear (for existence-sensitive fields), or show a clear "hidden by policy" marker (for ordinary sensitive fields), so that I'm never confused or leaked-to.

33. As an org admin, I want retiring a field that's wired into a live workflow or the public API to be blocked until I unwire it, so that I can't silently break an integration.

40. As an org admin, I want permanently deleting a field with data to require an explicit, audited, type-to-confirm action, so that I never lose data by accident.

### Platform / engineering / the organization

59. As the organization, I want to shape the CRM to our ministry without engineering, while trusting that nothing leaks and history is never corrupted, so that the platform is both flexible and safe.
60. As the organization, I want to add data types our vendor never imagined and still report, import, export, and automate on them, so that we're not boxed in.

## Implementation Decisions

> The thirteen ratified decisions (D1–D13) are the architecture. Each was deep-researched against current best practice and adversarially verified; the fixes from a final congruence sweep are folded in. Grouped below by layer. **These are decisions, not code** — schema/interface shapes are given where they encode a decision precisely.

### A. Storage & engine (D1, D2, D3)

**A1. Value storage = hybrid JSONB + promoted hot-field indexes (D1).** Custom-field _values_ live in a single JSONB "extension" column, keyed by an **immutable field-definition UUID** (never the label); _definitions_ live in a separate catalog. **No per-tenant DDL. No raw EAV.** Adding a custom field never changes the database schema. Reject: a single polymorphic value table, raw EAV, per-tenant DDL, and per-tenant _partial_ indexes (the Postgres-documented anti-pattern). Write values server-side in one statement (`jsonb_set`) — never app-side read-modify-write (closes the lost-update hole). DB `CHECK (jsonb_typeof(extension_values) = 'object')` for coarse shape; real validation is Zod at the API write-path (matches the repo's existing JSONB precedent).

**A2. Hot-field promotion (D1).** Reporting/filtering on arbitrary JSONB is slow; a small governed set of "hot" fields are _promoted_ to fast typed access via **per-partition typed, immutable-cast expression indexes** built online (`CREATE INDEX CONCURRENTLY`). Ship the **promotion seam** in v1 — a catalog `promoted` flag + `access_path`/`state`, a query-routing resolver (index-path vs bounded JSONB scan), a per-tenant quota + fleet-wide ceiling, one fleet-wide `GIN(jsonb_path_ops)` for ad-hoc containment, and invalid-index/dead-tuple/TOAST/HOT observability — and **fill** the promoted set from real query evidence as a fast-follow. Promotion is a durable, idempotent, monitored worker (a `CREATE INDEX CONCURRENTLY` cannot run in a transaction). Values normalized on write (ISO dates, canonical numerics) so casts are immutable. Reserve a _nullable typed column + concurrent backfill_ pattern for the rare materialized case — **never** a one-shot `STORED` generated column (a full-table rewrite). Virtual generated columns are rejected (non-indexable; not on Supabase).

**A3. One record-type-agnostic engine over per-record-type sibling tables (D2).** The engine (catalog + resolver + write-path + policy + promotion + quotas + audit + a target registry) is **record-type-agnostic**; the _values_ live in **per-record-type sibling tables**, each with a **real foreign key + `ON DELETE CASCADE`** to its target (`party_extensions` → `parties`, `fund_extensions` → `funds`). This gives DB-enforced existence + cascade integrity — decisive because an orphaned/type-confused value on a public-adjacent record (a fund) is a wrong string on a donation form or receipt. `party_extensions` is **hash-partitioned by `tenant_id`**, composite `(tenant_id, party_id)` key, FK carries `tenant_id` (partitioned-parent PK must include the partition key; FK→partitioned-parent is PG12+). Inline-on-parties vs side-table is a benchmark-gated implementation choice; the sibling-table + real-FK decision is fixed. **Policy shape is per-target-polymorphic** (a party carries `security_level`; a fund carries per-surface publication) — a shared resolver _interface_ with per-target strategies dispatched off `target_type`, exhaustively type-checked; never one nullable superset row.

**A4. v1 targets + the `extensible_targets` registry (D2).** v1 targets = the **Party spine** (person / org incl. church via `org_type` / household) + **funds**. `extensible_targets` is a controlled **table** (`target_type` PK, `enabled`, `value_table`, `partition_strategy`, `public_exposable`, `hot_promotion_allowed`, per-type quotas), not a native enum, not free-text — adding/enabling a target is a data change, not `ALTER TABLE`. **Campaign is seeded disabled** (`enabled=false`, no `value_table`) and activates additively when Phase 13 defines the real campaign/designation record. **General fail-closed invariant:** a registry row is _live_ only when `enabled=true` **and** a compiled value-table code arm exists for its `target_type`; registry-data-ahead-of-code fails closed (reads/writes reject before resolving the value table). The registry (data) gates enablement; the finite, code-enumerated value-table union is what's actually buildable — the two must agree, **code-side wins.** Fund custom fields default-closed, receipt-excluded, and reachable publicly only through the firewall.

**A5. Configurable child collections (D3).** A collection (repeatable sub-records, e.g. Certifications) rides the same engine. Items live in **one shared `party_collection_items` table** (real cols `tenant_id, id, collection_definition_id, parent_party_id, position integer, item_external_id, created_at, updated_at, archived_at` + `extension_values jsonb`), hash-partitioned by `tenant_id`, **single real FK `(tenant_id, parent_party_id)` → `parties` `ON DELETE CASCADE`** (the shared-PK spine means any party kind is one clean FK — no polymorphic discriminator). **No per-collection tables.** Collection definitions + their field-defs live in the **same catalog**; items are field values keyed by field-def UUID → the **same resolver + `field_policies` + `effectiveSensitivity`** composed with the _parent party's_ `security_level` (zero new enforcement surface). **v1 collections attach to the Party spine only.** **Collection-vs-relationship rule:** a "bag of fields" is a COLLECTION; an openable/ownable/two-sided record is a RELATIONSHIP (`crm_relationships` stored edge) — the catalog validator **rejects** any typed record-reference field inside a collection definition (prevents rebuilding the Phase-9 relationship graph); the item-count cap surfaces a "this looks like a relationship" review nudge.

**A6. Collection item ordering — drag-reorder ships in v1, bounded-integer renumber (D3, hardened).** `position integer NOT NULL`, contiguous `0..n-1` per `(tenant_id, parent_party_id, collection_definition_id)` over active items — **not** fractional indexing (over-engineering for a ≤500-item list; imports key-growth/rebalancer cliffs, float exhaustion, and the Supabase `COLLATE "C"` trap). Integer renumber makes that bug family structurally impossible. Sort **everywhere** by `ORDER BY position, id`. A reorder renumbers changed rows inside one transaction serialized by `pg_advisory_xact_lock(hash(tenant_id||':'||parent_party_id||':'||collection_definition_id))` (tenant_id **in** the key). Anchor-based move API (`{before_id, after_id, idempotency_key}` — client sends neighbors, never a raw index). **Four correctness invariants (P0):** (1) the advisory lock is cooperative → **enforce it**: route every position write through one locked DB function and revoke direct `UPDATE` of `position` from the app role; (2) staleness guard = in-transaction anchor-adjacency re-validation (→ 409 STALE), not a moved-row version; (3) the partial unique slot index firing (23505) → caught and translated to a handled 409+retry, never a raw 500; (4) parent-merge (Phase 4) must take the survivor's list lock; the idempotency store must outlive the max client retry window.

### B. Field-type system (D4)

**B1. Two axes: `storage_type` + `input_type`.** A field has a `storage_type` (engineering-owned — drives storage/validation/projection/operators/promotion) and an `input_type` (tenant-selectable UI control). One storage type backs many controls with **zero new code** (kills near-duplicate-type debt; rich text later = long-text storage + a sanitizer + a new input_type, not a new storage type). **All consumers branch on `storage_type`, NEVER on `input_type`** (D4 is the sole type authority).

**B2. Each type = a self-contained descriptor (strategy registry).** A code-side discriminated-union registry keyed by `storage_type`; each descriptor carries: `storageKind` (`scalar|array|reference|derived` — v1 ships scalar/array), a Zod validator derived from the catalog row, a `projector` (the resolver's only shape-emit), a typed `operators[]` allow-list, `sortable`/`promotable`, `pgTypeForIndex`, `importParse`/`exportFormat`/`jsonEncoding`, and `version`. All per-type behavior lives in one place → no switch-statement smear. New type = new descriptor + review (Open/Closed). A startup assertion requires every `storage_type` present in data to have a registered descriptor. **Types are engineering artifacts; definitions are tenant data.** No DB `CHECK(type IN …)` enum (that would turn a new type into a per-partition migration) — the type gate stays application/registry-level.

**B3. v1 = 16 types.** short text, long text (plain), integer, decimal, currency (using Phase-2 currency rules — **not** a new money primitive), percent, date, datetime, checkbox/boolean, single-select, multi-select (array), email, phone (stored E.164), URL, country (ISO), locale (BCP-47). Select/multi-select store the stable **option-id**, never the label; country/locale store canonical codes validated against Phase-2 reference data; decimal/percent carry precision/scale as per-definition constraints.

**B4. Reserved seams (future-proof, near-zero cost).** File, computed/formula, rollup, and rich-text are additive later via: the `storageKind` discriminator (reference/derived arms declared but unused); optional descriptor members implemented by nobody (`dereference`, `compute`/`dependsOn`, `richTextSanitizer`); nullable catalog columns (`expression`, `expression_lang`, `depends_on`); and one `resolveCell(catalogRow, storedCell, ctx)` chokepoint keyed by a `storage_kind` timing enum (`stored | derived_on_read | derived_materialized`, v1 = one arm). **File** (future) = a typed _reference_ to the Phase-29 document system (a `document_id` in JSONB, never bytes, never a signed URL); double-gated (resolver authoritative for the reference, the file store for the bytes). **Computed/formula** (future) = a safe non-Turing-complete evaluator (e.g. Google CEL — provably terminating, cost-estimable), never `eval`; stored as opaque `expression` text + `expression_lang` (engine swappable). **Rollup** (future) = a `derived_materialized` aggregate (closed enum: count/sum/min/max/avg) over collection items. **Build no evaluator, no formula engine, no DB enum, no reserved empty columns now.**

**B5. The projector contract (v1, load-bearing).** `projector(cell, ctx): Promise<Projected>` where `Projected` is a discriminated union `{resolved} | {withheld} | {referenceOnly}`. Async + ctx + partial-return is required for classification-withholding anyway, and it makes file/computed strictly additive (no signature change later).

**B6. Derived-classification policy (ships in v1 as policy, no code).** A derived field's sensitivity = **strictest of its inputs**, non-lowerable by anyone — enforced at admission and at read, and materialized derived cells carry the inherited category so promotion/index/export honor it. Closes the Salesforce-documented FLS bypass where a formula launders a hidden input into a visible output. (No derived fields exist in v1, but the policy must be load-bearing from the start; a future computed field referencing an undeclared input **cannot resolve it** — the resolver is the only accessor.)

### C. Policy-at-birth (D5) — the safety linchpin

**C1. Canonical axis model (computed, cached).** Per-surface/per-axis exposure is **computed** from the field's type (D4 descriptor) + its sensitivity category + opt-in widenings; the Phase-3 `field_policies` rows are the **materialized cache** of that computation (one per surface), regenerated on definition/policy change — **not** rows an admin hand-sets. The birth policy is the Policy Administration Point; the resolver contract is unchanged (custom fields are just another `field_policies` census generator).

**C2. The complete egress checklist (26 doors).** Every field is born with an answer for every way it could leave the system: per-surface **read** (Mission Control / donor portal / missionary workspace / public-CMS / public-API); per-surface **write** (incl. import as a classified write surface — non-settable fields rejected on import; public-API write); **bulk/structured** (CSV export, report-builder column _and_ filter/group/sort dimension, search-index, webhook payload, public projection); **comms/doc** (email/merge, receipt/statement, support-hub); **platform-pipe** (workflow condition _and_ action-payload split, telemetry/logs, AI/LLM context, derived-field input eligibility); and the **data-tier** (CDC/replication, BI/warehouse direct-connect, ETL/reverse-ETL, backup/restore, read-replica). Any unregistered egress → strictest (`internal`) → omitted, and a meta-test fails the build until it's wired through the resolver.

**C3. Tier-driven, secure-by-default.** The sensitivity tier (the fixed six: public/contact/internal/financial/care/security) is the primary control; a pure function `defaultAxesFor(category)` generates the fail-closed axis bundle. A field born with only a tier and zero widenings is Mission-Control-only across every door. Widenings are opt-in, named, justified, one-directional; **financial/care/security → external is hard-blocked** (absent from the UI, not merely gated); **contact → external (public / public-API / email-merge-to-non-owner / CSV) is a second-approver ceremony**, not a mere confirm (contact PII → public is the top accidental-doxxing risk).

**C4. Enforcement = one sealed decision point (PDP/PEP).** `resolveProjection` is the single Policy Decision Point (subtract-only, fail-closed, never grants); every egress module is a dumb Policy Enforcement Point that calls it and contains no policy logic. `publicationFirewall.toPublicProjection` is the sole external door (an inner PDP ring inside the firewall). **The resolver gates filter/sort/group-by _inputs_ too, not just output columns** (closes the WHERE/ORDER-BY inference side-channel). Aggregates/rollups inherit strictest input. `effectiveSensitivity(field, party)` composes field sensitivity with the party's `security_level`.

**C5. Data-tier floor (a deliberate narrow Postgres exception).** Because the app-layer rings can't reach non-TypeScript readers, non-Mission-Control DB roles (replication/BI/reverse-ETL/reporting) get `SELECT` **only** on a `SECURITY DEFINER` **governed view** that joins `field_policies` and emits `NULL` for anything not cleared at the export/public surface — never the base table (Salesforce `stripInaccessible` at the DB boundary). **Surface-binding:** one public/export-floor governed view for all non-MC roles (the fail-closed floor); stricter per-role views reserved (addable without changing the base-table `REVOKE`). RLS still does tenant isolation.

**C6. Atomic birth.** The create function's input type (Zod) makes sensitivity + per-surface `{visible, editable, exportable}` required/non-nullable — a field can't be _expressed_ without its policy. Definition + all per-surface `field_policies` rows are written in one transaction; a DB `CHECK`/`AFTER INSERT` trigger rejects a definition whose materialized-cache row count is incomplete (even a rogue direct SQL insert). Under-specification resolves to the strict default; derived-field birth computes strictest-input and ignores any admin-supplied category.

**C7. Change control & reclassification.** Widening (more visible/exportable/public/API/workflow/merge, lowering the tier, `toPublicProjection` inclusion, **plus** hardLock removal, `derivedInputs` edits, and `storage_type`/`input_type` changes) requires maker-checker (maker ≠ checker) + a blast-radius dry-run computed by the same resolver ("exposes X to the public API + N historical records"). No "born wide" backdoor (a non-default policy at creation fires the gate at birth). Narrowing is immediate + audited + triggers the Phase-10 retro-scrub; it never retroactively exposes historical rows (that's a separate deliberate action). Classification is gated on the `classify:manage` capability; lowering/exposing care/security additionally requires the actor to hold the matching Phase-10 clearance; `toPublicProjection` inclusion needs the highest clearance + a second approver; derived sensitivity is non-lowerable by anyone.

### D. Exposure contracts — first-class everywhere (D9)

**D1. One field-catalog contract, served only by the sealed field-policy package.** `getFieldCatalog(collectionId, {surface, actor})` returns a typed, policy-annotated, per-viewer projection of `(type-descriptor catalog ⋈ field_policies)`. Two physical forms of one logical contract: the `SECURITY DEFINER` governed SQL view (the data-tier door) and an in-process typed TS projection (list predicate builder, saved views, API validation, workflow predicate compiler) — both generated from the same catalog+policies; **no consumer touches raw JSONB, re-derives type, or re-derives policy.** Materialized/cached, invalidated on field/policy change (fail-closed on stale).

**D2. Contract fields.** Identity (`field_key` immutable UUID = the JSONB key; `value_key` stable handle; `collection_id`); type (`storage_type`, `input_type`, `type_version`, `operators[]`, `pg_type_for_index`, encodings); display (`label`, `description`, group, order — _do not key on_); options (`{option_id, value_key, label, state, order}`); the resolved exposure outcomes per surface/axis; state & promotion (`required`, `default`, `has_unique`, `archived`, `promotion_state`, provenance). Maps 1:1 to Salesforce FieldDefinition / HubSpot Properties / Oracle x-oi.

**D3. Stability.** The contract is keyed exclusively on immutables (`field_key`, `value_key`, `option_id`, `type_version`). A label rename touches only `label` and never breaks an import mapping, saved report, API integration, workflow predicate, or merge token.

**D4. Anti-drift (build-breaking).** One module resolves type→consumer facts; one resolves policy→exposure (fail-closed, subtract-only); all downstream artifacts (OpenAPI schema, report pickers, import template, workflow allow-list, export column set) are **generated** from `getFieldCatalog`, never hand-maintained; non-MC DB roles reach values only via the governed view; external egress only via `toPublicProjection`. **Ship the anti-drift CI lint in Phase 11** (the Phase-3 A2 import-ban pattern): ban importing the descriptor registry or touching the `*_extensions` JSONB outside the field-policy package. The existing client `OPERATORS_BY_TYPE` map becomes a _projection_ of the server descriptor, not the authority.

**D5. Per-consumer contracts (defined now; the product built by the owning phase).** **Ships in Phase 11:** list columns (typed projector), typed filters (server-side operator set; the resolver **rejects** a predicate on an uncleared field — never silently drops, which would widen results and leak by exclusion), saved views (UUID-keyed, re-resolved, graceful degradation on archived fields), typed sorts, governed CSV export (`emitGovernedCsv`, exportable-gated, type-fidelity, formula-injection neutralized), Tier-A promotion, and the reserved "field changed" event schema. **Report builder (Phase 33):** `resolveReportableCatalog` — typed catalog, type-derived aggregations (currency carries Phase-2 minor-units + ISO and blocks mixed-currency sums), a selection gate + an aggregate/inference gate (`groupableOnSurface` + `minGroupSize(k)` k-anonymity, a configurable per-tenant threshold) that extends the firewall to derived values. **Import (Phase 30):** the import-template descriptor (columnHeader from `value_key`, `importParse`, required/restricted, option `value_key` mapping, collection flat-with-parent-key) + a bulk validated write API through the **same** write-path (no second weaker path). **Public API (Phase 31):** the field-exposure schema (read iff api_readable, write iff api_writable, addressed by `value_key`, `jsonEncoding` for type fidelity) + a dynamic self-describing OpenAPI generator + writes through the same write-path + `toPublicProjection` as the sole door for any unauthenticated API. **Workflow (Phase 34):** typed condition predicate (reuses the Phase-9 predicate grammar), policy-gated action payload (care/security structurally excludable), and a "changed" event that carries `field_key`/`value_key` + a change signal — **never the raw value**; value delivery re-enters the resolver at the subscriber boundary. **Merge (Phase 6):** a merge-field resolver — valid only if merge-cleared **and** recipient-bound; care/security never merge-eligible.

**D6. Type fidelity + round-trip.** Guaranteed by the one descriptor; a date filters/sorts/aggregates as a date, etc.; export⇄import is structurally inverse for multi-select and currency (structured, `value_key`/minor-units-keyed; `importParse` the sole re-parser; a round-trip property test). Default `type_version` degradation = fail-closed (a saved artifact referencing a field whose descriptor version changed → refuse/mark-inactive, never execute with stale authority).

### E. Behavior & lifecycle (D6 layout, D7 options, D8 required/defaults)

**E1. Record layout (D6).** A light **layout-as-data** model — `layout(record_kind, is_default, surface, assignment_rule?)` → `layout_section(key, label, position, kind, target_socket, columns 1|2, collapsed_default)` → `layout_placement(ref_kind, field_def_id|collection_def_id, col_span, position)`. Placement references the **immutable definition UUID** and lives on `layout_placement`, never on the field-def catalog row (delivers the roadmap parity target: fields movable between groups by editing one row). v1 = admin-named sections + field/collection placement + order (reusing the collection reorder primitive), custom fields render only in the reserved Phase-9 **Custom Fields socket** (not injected into the 8 native tabs), collections render inline as a repeatable table (shared `DataTableResponsive`), exactly one layout per record-kind, one doc with view|edit modes. **Security invariant: resolver first, layout second, always** — the renderer is a pure client-side arranger over an already-filtered projection; placement is never a security control; a boundary type prevents the renderer from resurrecting an omitted field; CI asserts it. **Existence-leak rule:** default = truly absent; a section whose placements are all policy-omitted is dropped **server-side** (client-side collapse of a labeled-but-empty fieldset is itself the leak) + a save-time sensitive-token lint on section labels; external/narrow surfaces → truly absent; ordinary-sensitivity MC → may show a "hidden by policy" affordance; existence-sensitive (care/security/restricted-ministry) → truly absent even in MC. Reserved seams: multiple layouts per kind via `assignment_rule` + `position` (dropped `variant_key`), per-collection sub-tab via `target_socket`, `surface` column for future narrow-surface layouts; component/widget columns are documented intent only, not shipped.

**E2. Option lifecycle (D7).** Three-way option identity: `id` (uuid, immutable — stored in JSONB), `value_key` (stable machine handle, the import/export/API anchor), `label` (freely editable, retroactive display). Lifecycle: active → archived (not selectable for new, but existing values still resolve/display/filter/report) → hard-delete only when refcount == 0 (fail-closed, checking both single-select `->>` and multi-select `?` JSONB paths, in the same serializable transaction as the delete). **Rename vs new option:** "same thing, better words → rename (retroactive, zero data movement); different meaning → new option + archive old (history keeps the old meaning)." **Merge/Replace** is a governed, previewed (affected-row count), batched, idempotent, reversal-logged value-migration; the merge **target must be active** at execution; multi-select re-point dedupes and may reduce per-record cardinality (documented + reversal-log-flagged). Reorder = presentation-only. Default = `default_option_id` on the definition (never rewrites history; a default doesn't satisfy `required`). **Restricted by default;** unknown option on import rejects with a diagnostic (open fields opt-in to auto-create ACTIVE-but-flagged, under quota, acquiring the reorder advisory lock). Option labels ride the same firewall/classification as the field value (label resolution happens _inside_ the firewall) + a save-time sensitive-token lint. Global/shared option sets are reserved via an `option_set_id` FK + `scope` discriminator (v1 = field-local 1:1). Caps: label ≤255 single / ≤40 multi-select, `value_key` ~80, per-record multi-select byte governor. `option.value_key_corrected` is a governed audited event (zero-row-rewrite since values store `id`).

**E3. Required & default behavior (D8).** **Required is a per-surface enforcement policy, never a global `NOT NULL`.** Three layers: surface/context-scoped (default), conditional (deferred), universal (an explicit gated escalation with a preflight). **Never-retroactive rule:** making a field required never mutates history, never marks rows invalid at rest, never blocks a save that doesn't touch that field; enforced only for fields present-and-editable on this surface **and** participating in this write. **NULL vs NOT-SET vs EMPTY** is load-bearing — enforcement tests key existence (`values ? field_uuid`), never `->> IS NULL` (which collapses absent into null); never run `jsonb_strip_nulls` on stored blobs; payload semantics follow REST PATCH (absent key = leave unchanged). **Defaults materialize on create only** (a real audited value, `source=default`), never resolve-on-read (admin-editable defaults are effectively volatile → resolve-on-read is read-time fabrication) and never back-fill; a default never satisfies `required` (a value re-inserted by the seed layer never counts — re-check against the pre-seed payload); v1 defaults = static + a closed dynamic-token allow-list (`today`/`now`/`current_user`), computed-at-create then frozen; formula defaults reserved. **Legacy edits never blocked**; a newly-required absent field on an untouched record is `legacy-not-set` (a non-blocking nudge). **Deliberate backfill** via a previewed, batched, audited Phase-8 data-health action (reusing the D7 migration engine) — never a silent side effect. Collection required = two axes (min/max items at parent-write; a field-within-item required per item), enforced only when the collection is in the write payload (never on an unrelated scalar save). Value **provenance** (`source = default|user|backfill|import`) is stored in a sibling structure keyed by field-def UUID, never by mutating the value.

### F. Governance & operations (D10 quotas, D11 audit, D12 archive/delete)

**F1. Quotas (D10).** Generous where cheap, tight where expensive, every limit a raisable soft default, fail-closed at creation. Defaults: ~200 custom fields per record-kind (~500 hard ceiling); ~20–25 **indexed/promoted** fields per record-kind as an _anchor_ — the real governor is measured write-load (HOT-update ratio / WAL amplification) + a **fleet-wide per-physical-table ceiling** (pinned to a concrete starting integer; the promoted-field budget is _shared_ across a record-kind's flat fields and its collections' partial-index promotions); 50 collections/tenant, 50 fields/collection, 100 soft-warn / 500 hard / 1000 ceiling items per parent, 200 options/field (1000 ceiling) + multi-select byte governor. Limits are stored as per-tenant settings (the plan-tier seam; no billing logic now). Cheap limits raise freely; expensive (indexed) limits raise only via governance + measured load. Breach = a clear actionable message + a Phase-8 data-health nudge; import auto-create respects the ceiling.

**F2. Audit log (D11).** **One append-only stream** extending the existing `crm_command_logs` pattern into `crm_audit_events` (typed `event_type` enum + `before`/`after` JSONB — never N per-feature tables; two tables absolute ceiling), month-range-partitioned. **Tamper-evidence = per-epoch signed Merkle checkpoints anchored out-of-band — not a per-row hash chain, not a ledger DB** (a per-row chain breaks on pruning/erasure, is O(n) to verify, is forkable under concurrency, and is defeatable by a privileged consistent-rewrite; ledger DBs = a second datastore, and QLDB is EOL). When a month-epoch closes, a worker computes a Merkle root over the epoch's canonicalized rows → a tiny `crm_audit_checkpoints` table (chain checkpoint-to-checkpoint only); each root is Ed25519-signed (KMS) + written to WORM object storage (the default anchor; RFC-3161/OpenTimestamps only on tenant demand). **Retention** = whole-epoch partition drop of _anchored_ epochs (integrity lives in the external checkpoint, so pruning never severs verification). **Append-only enforced in-DB** (revoke `UPDATE`/`DELETE` + a `SECURITY DEFINER` writer that applies redaction + a reject trigger); retention is DDL by a separate itself-audited role (bypasses the row trigger by design). **Change-detection stores nothing value-derived** — a monotonic version counter proves "it changed" with zero plaintext (a keyed HMAC of low-cardinality values is defeated by frequency analysis — the "second leak"; transient high-cardinality-only HMAC is a P0 code gate, never persisted). **GDPR/CCPA erasure = segregation-first** (immutable rows hold no subject value → erasure is a no-op for tamper-evidence) **+ crypto-shred fallback** (destroy a per-subject key; never delete a row); the Art. 17(3) legal basis is recorded per tenant/tier in the DPIA. The store is ≥ internal, export-restricted, never through the firewall; reads of the audit are themselves logged (audit-of-audit). **Build requirements:** byte-exact canonicalization (RFC 8785 JCS, versioned, with a reverify-all-roots CI test — never `row_to_json`); a checkpoint-liveness control with an SLO (an unanchored epoch has no tamper-evidence while appearing sealed → alert + block retention drop; tamper-evidence applies only to anchored epochs).

**F3. Safe archive/delete (D12).** Retirement is safe **by construction.** **Dependency model (3 layers):** a choke-point (`persistArtifactReferences` writes the artifact **and** its edge rows in one transaction — no artifact stores a raw `field_key` via ad-hoc SQL); an authoritative live recompute (`resolveReferences` re-parses every artifact's stored JSON through the **same extractor** across the finite artifact-table set, run synchronously before every destructive action + on a schedule that heals drift and emits a Phase-8 finding per drift); and a value-presence probe (`WHERE values ? field_key LIMIT 1` on a `GIN(jsonb_path_ops)` index). The edge table is a freshness-stamped serving cache; the destructive gate re-runs the live scan and fail-closes. **The load-bearing wall (P0):** the reference extractor is **complete and identical between write-time and scan-time** (one module per artifact type, called both ways, with a CI round-trip + fuzz test — a parser gap is a silent-break, not just a cache gap); and the pre-delete scan is **transitively live to every hard-stop node**, never cache-transitive. **Five-state lifecycle:** ACTIVE → ARCHIVED (indefinite, no timer, values read-only-preserved, hidden from pickers, reversible) → PENDING_PURGE (30-day recycle bin, reversible) → TOMBSTONE (irreversible; values crypto-shredded; a `{field_key, tombstoned_at}` marker so the resolver returns a "removed" chip) + a governed FORCE-REMOVE transition. **Graceful degradation** through the one resolver: `{resolved} | {archived} | {removed}` — never a crash. **Hard-stop vs warn (verb-split):** hard-stop = live execution (active workflow, public-API exposure, active/scheduled import, live dependent rollup); warn = passive display (layout, saved view, saved report); draft/inactive workflow = warn-on-archive, block-on-delete. **Auto-purge re-runs the fail-closed live scan** (a new hard-stop reference acquired during the window → bounce to ARCHIVED + notify, never silently tombstone). Value writes participate in the same advisory-lock domain as the delete gate. An in-flight-job snapshot **lease registry** blocks purge while a job holds a reference. Restore beats Salesforce: immutable-UUID references reactivate automatically. The audit stores `field_key` as an immutable literal string + `label_at_time`, never an FK (survives tombstone). UX: undo for reversible, type-to-confirm only for irreversible; on any gate/preview discrepancy re-render with the newly-found blocker highlighted; bulk archive names each skipped field + blocker inline.

## Testing Decisions

**What makes a good test here:** assert **external behavior and invariants**, not implementation details — "a default-classified field is invisible on the donor portal / CSV / public API," not "the resolver called function X." Drive the real code with local mocks or dependency injection (per the repo's vitest-module-mock caveat: `vi.mock` of `packages/*` internals by relative path silently no-ops in the full suite). Tenant isolation is tested with **vitest**, not pgTAP (prior art: `tests/unit/cms/tenant-access.test.ts`, `tests/unit/packages/api/admin/support-hub/tenant-isolation.test.ts`). Projection/redaction prior art: `packages/api/tests/unit/public-giving-projection.test.ts` (+ `FORBIDDEN_PUBLIC_COLUMNS`/`assertNoForbiddenPublicColumns`).

**Modules to test (external behavior):** the field-policy package (the highest-value target), the type-descriptor registry, the write-path validator, the dependency engine, the migration engine, the option lifecycle, the audit writer/checkpoints, the promotion worker, the presence counter.

**The P0 CI invariants (acceptance gates — a PR cannot merge without these green):**

1. **No-bypass lint** — nothing outside the field-policy package imports the descriptor registry or reads a `*_extensions` JSONB column / value accessor (a deliberately-violating fixture proves the rule is live). No `SELECT *` on extension-bearing tables.
2. **Default-field-invisible** — a field created with the minimum is absent from donor/missionary/public/CSV/email/receipt/public-API/workflow/search/filter, present only in Mission Control.
3. **Every-egress-through-the-resolver meta-test** — enumerate every registered surface; each egress module's import graph reaches the resolver/firewall and nothing lower; a new unwired surface fails the build (the egress set is provably closed).
4. **Surface × category property/fuzz** — for random policy configs, `resolved ⊆ (field_policies ∩ row_scope ∩ record_flags ∩ record_state)` always (subtract-only, never grants).
5. **Filter/sort inference guard** — a query/report/search filtering or ordering by an over-classified field is rejected server-side, not silently executed.
6. **Derived non-lowerability** — a derived field over a financial input can't be set to a lower category at birth or via update; aggregate-over-hidden classified as strictest input.
7. **Atomic-birth integrity** — a direct-SQL insert of a definition with no policy cache is rejected; a simulated txn failure leaves no orphan; under-spec materializes the strict default.
8. **Round-trip property test** — export→import is set-equal for multi-select and currency (structured, `value_key`/minor-units-keyed).
9. **`type_version` degradation** — a saved artifact referencing a bumped-version descriptor refuses/marks-inactive, never executes with stale authority.
10. **Reorder concurrency** — two simultaneous drags, a drag during a merge, a drag of a just-archived item, and a retry double-apply all produce a correct order or a clean 409, never a wrong order or a raw 500; direct `UPDATE` of `position` by the app role fails.
11. **Option history integrity** — rename never mutates a stored value; hard-delete of an in-use option is refused (both JSONB paths, transaction-consistent); merge into an archived target is refused; merge preview count matches the migration.
12. **Required/default retroactive-safety** — making a field required never blocks an unrelated edit to a legacy record and never mutates history; a default materializes on create only, never back-fills, never satisfies `required`; enforcement uses key-existence, not `->> IS NULL`.
13. **Dependency extractor round-trip + fuzz** — for every artifact type, write-time extraction and scan-time re-derivation are set-equal on a corpus.
14. **Transitively-live gate** — deleting a field whose transitive path reaches a hard-stop node (rollup→API, rollup→active-workflow) is blocked by the _live_ scan, not the cache.
15. **Auto-purge re-gate** — a reference acquired during the recycle-bin window bounces the field back to ARCHIVED instead of tombstoning.
16. **Audit** — append-only enforced (app-role `UPDATE`/`DELETE` fails; retention-role partition `DROP` succeeds); Merkle roots reverify after retention drop; canonicalization drift is caught; no value-derived digest is persisted for low-cardinality fields.
17. **Data-tier floor** — a non-MC DB role reads only NULL-redacted values through the governed view; a replication publication / BI grant on the raw extension table fails CI.
18. **Admin UX a11y/design-system** — every `/crm/settings/data-model` route passes the e2e a11y spec; no raw palette hex on the classification surface; keyboard reorder + live-preview AT behavior verified.

## Out of Scope

- **Deferred field types (reserved seams, not built):** file (typed reference to the Phase-29 document system), computed/formula (a safe CEL-class evaluator), rollup (aggregate over collection items), rich text. Their seams ship; their engines do not.
- **The downstream _products_ themselves:** the full report builder (Phase 33), the import product's file parsing / mapping UI / dedupe / staging (Phase 30), the public-API endpoints / auth / runtime / doc-portal (Phase 31), the workflow engine / evaluator / executor / event bus (Phase 34), the email template editor / send pipeline (Phase 6). Phase 11 ships their **contracts** and the shared write-path/read-gate, not the products.
- **The full permission-config product (Phase 12).** Phase 11 ships only the additive `classify:manage` capability it needs.
- **Money-record _transaction_ custom fields** (gifts, pledges): out of v1 (funds are in). **Campaigns** as a target: reserved to Phase 13 (seeded disabled). Top-level _shared_ option-sets: reserved (`option_set_id` seam). A richer drag-drop layout/form builder, conditional-visibility rules, multiple layouts per kind: reserved (data-shape only). A shared searchable-select UI primitive: only if later needed (authored in `packages/ui`, never `apps/*`).
- **External audit attestation** (RFC-3161 TSA, OpenTimestamps): tenant-demand only; default anchor is Ed25519 + WORM.
- **Plan-tier billing logic:** the per-tenant quota table is the seam; billing is not built.
- **Never built:** per-tenant DDL, raw EAV, an arbitrary SQL/formula engine, a ledger database, per-column Postgres masking for field values, a second (weaker) write path, a bespoke drag-drop form builder, a second audit table per feature.

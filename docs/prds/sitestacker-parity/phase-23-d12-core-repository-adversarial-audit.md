# Phase 23 D12 — Core Repository Adversarial Audit

**Status:** repository evidence for decision grooming; no decision ratification and no runtime implementation  
**Audited:** 2026-08-22  
**Scope:** current Payload collection configuration, version and lock access, Web Studio editing state, public reads, restore behavior, migrations, and tests relevant to a bounded working-draft/version/lease contract

## Executive verdict

Core already has useful Payload primitives: draft-enabled editorial collections, version tables, authenticated draft preview, ordinary tenant-scoped document access, and one public-content reader that explicitly leaves access enforcement on. Those primitives are not yet a safe D12 contract.

Four repository facts are release blockers for B-prime as currently groomed:

1. **Version history is not tenant-safe.** The editorial collections define `read`, `create`, `update`, and `delete`, but not `readVersions`. In the exact installed Payload build, a missing access function allows any authenticated Payload user; version list/detail operations call `access.readVersions`, not ordinary `access.read`.
2. **The generated lock surface is not tenant-safe.** Payload's generated `payload-locked-documents` collection uses authenticated-only access for create/read/update/delete. Core exposes Payload's REST handlers, and the provider UI calls that collection directly. The lock rows have no first-class tenant/site key.
3. **Autosave does not provide an exact concurrency contract.** The installed UI deliberately skips its `updatedAt` stale-data check for autosave-enabled collections. Its document lock treats two tabs belonging to the same user as the same editor. Core's collections autosave every 300 ms. Without an expected-revision compare-and-set, same-user tabs and custom Local API callers can overwrite one another.
4. **Raw restore can change the provider document instead of creating a recovery draft.** The exact installed restore operation defaults `draft` to `false`, preserves the historical `_status` in that mode, writes the parent document directly, and does not enforce a document lock. Until D1's immutable Site Generation reader replaces the current mutable `_status` reader, that can immediately change what public routes return.

The permanent implementation path is therefore: close tenant access on versions and locks first; introduce one Core-owned command boundary with an exact source revision and session-bound lease; make restore create a new draft only; then adapt Web Studio to a calm status/action surface and prove that public output cannot change until the D1 release boundary advances.

## Current repository evidence

### Collection and access configuration

- [`Pages`](../../../apps/admin/src/cms/collections/pages.ts#L50) defines ordinary read/create/update/delete access at lines 50–58 and audit hooks at lines 59–63. Its draft autosave is 300 ms at lines 64–71. It has no `readVersions`, explicit `maxPerDoc`, or explicit `lockDocuments` policy.
- [`MinistryUpdates`](../../../apps/admin/src/cms/collections/ministry-updates.ts#L46) has the same access shape at lines 46–54 and 300 ms autosave at lines 60–67.
- [`PageTemplates`](../../../apps/admin/src/cms/collections/page-templates.ts#L40) uses 300 ms autosave at lines 40–47 and spreads the shared tenant helper at line 83.
- [`buildPageBuilderVersions`](../../../apps/admin/src/cms/collections/page-builders.ts#L568) supplies the same 300 ms configuration to missionary and project pages; [`withTenantAccessAndHooks`](../../../apps/admin/src/cms/collections/page-builders.ts#L587) supplies only ordinary read/create/update/delete access.
- [`MissionaryGivingPages`](../../../apps/admin/src/cms/collections/missionary-giving-pages.ts#L49) and [`ProjectPages`](../../../apps/admin/src/cms/collections/project-pages.ts#L50) use those helpers and therefore inherit the same omissions.
- [`Navigation`](../../../apps/admin/src/cms/collections/navigation.ts#L16) explicitly has `versions: false` at lines 16–18. This is a current implementation gap against the already-groomed versioned navigation/release direction, not a reason to create another history engine.
- [`tenantScopedReadAccess`](../../../apps/admin/src/cms/access/tenant-access.ts#L7) correctly constrains ordinary staff reads to the actor's tenant at lines 7–31; update and delete delegate to it at lines 33–39. There is no corresponding tenant-scoped `readVersions` helper.
- [`logCmsChangeAudit`](../../../apps/admin/src/cms/hooks/audit.ts#L8) emits one logger event for every `afterChange` at lines 8–26. It does not record an expected/source revision, editor session, lease, version id, acknowledgement id, conflict/takeover cause, or durable recovery outcome.

The exact Payload family is pinned to `4.0.0-internal.1f9ae9a` in [`apps/admin/package.json`](../../../apps/admin/package.json#L39) at lines 39–44 and 64. Inspection of that exact installed artifact established:

- `payload/dist/auth/executeAccess.js:2-24`: if an access callback is absent, `req.user` is sufficient for access.
- `payload/dist/collections/operations/findVersions.js:31-40` and `findVersionByID.js:31-35`: version reads execute `collectionConfig.access.readVersions`; they do not inherit ordinary document `read` access.
- `payload/dist/locked-documents/config.js:3-54` plus `payload/dist/auth/defaultAccess.js:1`: every lockable collection is included and create/read/update/delete all resolve to `Boolean(user)`.
- `@payloadcms/ui/dist/providers/DocumentInfo/index.js:121-146,163-189`: the editor directly lists, deletes, and patches `/payload-locked-documents` records.
- `@payloadcms/ui/dist/views/Edit/index.js:168-184`: omitted `lockDocuments` defaults to enabled with a 300-second duration.
- `@payloadcms/ui/dist/views/Edit/index.js:378-395`: the `updatedAt` stale-data check is disabled whenever autosave is enabled.
- `payload/dist/collections/operations/local/update.js:7-24` and `payload/dist/utilities/checkDocumentLockStatus.js:3-72`: Local API update defaults `overrideAccess` to `true`; lock checking defaults to bypassed and runs only when `overrideLock === false`.
- `payload/dist/collections/config/sanitize.js:202-208`: omitted collection retention defaults to 100 versions in this build. Core should still pin it explicitly so a provider default cannot silently change the product contract.
- `payload/dist/collections/operations/restoreVersion.js:22-63,208-219`: restore defaults `draft` to `false`, obtains the raw version before applying parent-document update access, retains the historical status in non-draft mode, and updates the parent document directly. The operation has no lock argument.

Core exposes the provider REST methods through [`app/(payload)/api/[...slug]/route.ts`](<../../../apps/admin/app/(payload)/api/[...slug]/route.ts#L1>), lines 1–16. Consequently, the weak generated version and lock access policies are reachable surfaces, not merely internal implementation details.

### Editing UI and exact-revision gaps

- [`WebStudioCollectionConfig`](../../../apps/admin/src/cms-ui/web-studio/collections/config.ts#L25) manually duplicates `hasDrafts` and `hasVersions`; individual values appear at lines 55–56, 73–74, 98–99, 115–116, 132–133, 150–151, 168–169, and 190–191. Collection configuration and UI capability can drift independently.
- [`NativeCollectionEditView`](../../../apps/admin/src/cms-ui/web-studio/collections/shared/document-workspace/NativeCollectionEditView.tsx#L92) receives provider lock/version facts at lines 98–112, but derives read-only state solely from save permission at line 299. A lock can therefore coexist with copy that says the user may edit and with visible save/publish controls at lines 470–483; the provider form may block the eventual action, but the shell does not explain the conflict or expose a bounded takeover/recovery flow.
- The same view exposes a dense action bar—preview, save, publish, unpublish, workspace settings, back, versions, raw API, and live preview—at lines 470–515, plus four persistent state cards at lines 637–684. That is serviceable diagnostic UI, but it is too technical and noisy for the proposed quiet D12 experience.
- [`editor-state.ts`](../../../apps/admin/src/cms-ui/web-studio/collections/shared/document-workspace/editor-state.ts#L42) gives a lock priority at lines 42–50, but the four-card composition at lines 148–161 is descriptive only. It has no saved revision id, local-vs-server comparison, lease owner/session, expiry, retry acknowledgement, recovery draft, or takeover action.
- The same adapter says `_status: published` is available to public readers at lines 125–130 and that public routes read that version at lines 175–203. Those statements encode today's provider `_status` reader, not D1's immutable Site Generation authority, and would mislead staff after D1 cutover.
- [`authenticated preview`](<../../../apps/admin/app/(payload)/web-studio/preview/[collection]/[id]/page.tsx#L39>) correctly authenticates and calls `findByID` with `draft: true` and `overrideAccess: false` at lines 39–64. Its URL contains only collection and document id, however, so preview is not bound to the exact revision the user just saw or saved.

### Public authority and Local API boundaries

- [`published-content-reader.ts`](../../../apps/admin/src/cms/public/published-content-reader.ts#L27) is deliberately the single current public Payload read boundary and keeps `overrideAccess: false` at lines 27–46 and 146–160.
- [`publicWhere`](../../../apps/admin/src/cms/public/published-content-reader.ts#L128) adds `_status: published`; [`getPublishedPage`](../../../apps/admin/src/cms/public/published-content-reader.ts#L199) selects the newest matching mutable document by `-updatedAt` at lines 199–239. This is a valid pre-D1 bridge, but it means a raw non-draft restore can alter public output before an immutable Site Plan release exists.
- [`publishedPublicReadAccess`](../../../apps/admin/src/cms/access/public-read.ts#L203) correctly composes tenant and published constraints at lines 203–235. It protects current document reads, not version history or generated lock rows.
- [`create-from-template-endpoint.ts`](../../../apps/admin/src/cms/create-from-template-endpoint.ts#L95) performs explicit staff and tenant checks, but its Local API calls (for example lines 202–209, 312–317, 374–379, 478–486, 613–621, 701–706, and 734–739) omit `overrideAccess: false`. Its current manual checks are meaningful compensating controls; the pattern is still a footgun for D12 commands because Payload Local API access defaults to bypassed. D12 must not copy this calling convention.

### Storage and migrations

- The initial CMS migration creates version tables carrying `version_tenant_id`, including pages at [`20260515_173042_init_payload_cms.ts`](../../../apps/admin/src/migrations/20260515_173042_init_payload_cms.ts#L262) lines 262–265, page templates at 495–498, missionary pages at 730–733, project pages at 967–970, and ministry updates at 1033–1036.
- Those version tables have useful parent/tenant/status/latest/autosave indexes; representative page indexes are at lines 1337–1347, with corresponding template, missionary, project, and update indexes at 1408–1418, 1482–1495, 1558–1570, and 1588–1598.
- Version tenant keys are nullable and their tenant foreign keys use `ON DELETE set null`, for example lines 1160–1162, 1187–1189, 1215–1217, 1243–1245, and 1252–1254. A hard-delete sequence can therefore leave retained versions without a tenant binding. Tenants themselves expose super-admin delete at [`tenants.ts`](../../../apps/admin/src/cms/collections/tenants.ts#L13), lines 13–20.
- The generated lock table at migration lines 1088–1110 stores timestamps plus polymorphic relationships but no direct tenant/site/resource-generation key. Its indexes at lines 1606–1621 likewise have no compound tenant/resource/session uniqueness constraint.
- Navigation has only current tables at lines 988–1005 and no version table. No reusable-section collection currently exists; when the D8 reusable-section runtime is introduced, D12 coverage must be added in the same migration rather than left as a later exception.

## Best implementation path, in dependency order

1. **Freeze the eligible resource census and exact provider contract.** Cover pages, navigation revisions, templates, missionary/project page builders, ministry updates, and D8 reusable sections when present. Configure the qualified Payload build explicitly: approximately 2-second trailing autosave, 5-minute renewable edit lease, draft validation policy, and 100-version retention. Keep one version engine.
2. **Close access before exposing history or collaboration.** Implement tenant/site/parent-aware `readVersions`; remove ordinary access to generated locks; block raw restore/API affordances. Prove anonymous, unaffiliated, cross-tenant, wrong-site, and revoked-permission denial at query and command seams.
3. **Create one narrow Core editing command boundary.** Save, meaningful checkpoint, takeover, and restore commands carry tenant, site, typed resource, session, expected revision, and idempotency key. Reprove all scope inside the transaction, then compare-and-set. A stale command returns conflict without changing content.
4. **Keep the database model small.** Reuse Payload version snapshots. Persist only the bounded active lease/revision/acknowledgement facts needed for atomicity and recovery; do not duplicate page bodies, create CRDT operations, or retain keystroke history. Enforce one active lease per resource and index tenant/resource/expiry lookups.
5. **Make recovery safe by construction.** A takeover first creates a meaningful recovery checkpoint of the displaced acknowledged draft. Restore always creates a new draft and revision. Lost responses are safe to retry with the same idempotency key. Client-local unsent text remains recoverable after network/save failure.
6. **Adapt, do not fork, Web Studio.** Replace the four-card diagnostic strip with a single accessible status and cause-owned actions. Display who is editing and lease freshness without exposing sensitive identity outside the tenant. Bind preview/comparison/release preparation to an exact acknowledged revision and flush pending input before those actions.
7. **Keep D1 authoritative.** Draft, autosave, takeover, comparison, and restore must not mutate the immutable Site Generation or public response. Release consumes an exact acknowledged revision through D1's Site Plan release; the UI must distinguish “draft saved,” “ready for release,” and “currently public.”
8. **Migrate and activate atomically by capability.** Add/backfill required version and lease structures, preserve tenant bindings, deploy readers before writers, and enable D12 UI only after a complete collection/profile census passes. No tenant-specific concurrency knobs.
9. **Ship only after the adversarial matrix is green.** Require non-skippable database tests for cross-tenant versions/locks, simultaneous browser contexts, stale CAS, takeover, expiry, revocation, idempotent retry, restore-as-draft, D1 public immutability, retention, performance, and accessible/mobile status UX.

## What should not be built

- No CRDT, operational transform, automatic rich-text/block merge, or real-time multi-cursor editor.
- No second history store containing page bodies.
- No tenant-configurable lock duration, autosave interval, retention count, or conflict algorithm.
- No blind last-write-wins save, raw provider restore, destructive rollback, or public-state mutation from recovery.
- No assumption that a hidden Payload collection, a disabled button, or ordinary document `read` policy secures versions or locks.
- No claim that Payload `_status: published` is the same fact as D1's immutable Site Generation being public.

This audit intentionally stops at repository evidence and implementation guardrails. It does not ratify D12 or edit runtime behavior.

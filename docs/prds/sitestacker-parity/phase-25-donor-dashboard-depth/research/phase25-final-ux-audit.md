## U01 — Resolve the `/pledges` collision permanently

**Observed / High consequence / deterministic if the pathname is reused:** `apps/donor/features/donor/components/DonorSubNav.tsx:27–28` calls `/donor-dashboard/pledges` **Recurring Giving**. Its page-client consumes `mapRecurringGiftToPledgeView`. Q26's newly accepted **Pledges** destination means fixed-total **Campaign commitments**. Reusing the old route for the new meaning could send bookmarked recurring-management links to the wrong product and confuse donors about whether a pledge automatically collects money.

**Builder recommendation:** make `/donor-dashboard/recurring` the canonical recurring-management route. Retain `/donor-dashboard/pledges` as a narrow compatibility redirect to recurring management. Use `/donor-dashboard/campaign-commitments` for fixed-total records, with the visible navigation label **Pledges** and the explanatory donor noun **Campaign commitment** in the destination. This is implementation reconciliation, not a new product vote.

Implement the canonical recurring destination before moving internal links. Apply a normal validated GET/HEAD compatibility redirect, preserving only supported same-Tenant recurring target/view/return context. Current page-client inspection found no query-driven detail contract to preserve, but migration tests must inventory existing emitted links and any owner-qualified historical forms. Unknown parameters must not become a fixed-pledge selector. Do not redirect legacy mutation endpoints or translate legacy `pledge` IDs into fixed-total IDs. Both canonical destinations retain their independent owner readers and authorization; neither maps by amount, cadence or fund name. A short route adapter is sufficient; no broad app-path rename or duplicated page implementation is needed.

## U02 — Replace the coarse route gate without removing resource protection

**Observed / High / affects accepted reader and representative paths:** `apps/donor/proxy.ts:22–34` protects `/donor-dashboard` and `/checkout` with only `donor`/`super_admin`, redirects unauthenticated checkout to `/` without the destination, and uses a generic dashboard auth return. `apps/donor/app/(dashboard)/donor-dashboard/layout.tsx:24,56–77` repeats that coarse role condition and has `/login?next=/donor-dashboard` as its fallback. This is not a complete current P4/P12 capability model for Q04's representative-only user, Q19/Q24's permitted reader without a financial donor record, or Q08's exact document doorway.

**Required reconciliation:** qualify current account-route admission through the existing identity/access owner, then authorize every actual resource/field/purpose and mutation independently. Preserve the exact approved destination and active giving context through authentication. Do not fabricate a personal donor row to pass the shell, infer access from an email match, admit every staff role, or let the layout's sibling gate substitute for protection at a page/API/read boundary. Handle the exact independent guest-document capability as its own route, not a full dashboard session. Q14 G01 and provider readiness remain separate unresolved Auth gates; this UX reconciliation does not solve or waive them.

This is a researched decision and execution review, not a PRD, formal specification or implementation ticket. Q01–Q11 remain ratified. ## Corrected decision to record

> **Q12 — One compact, source-owned Needs attention section.** On Home, below the current greeting/account context and before ordinary overview content, show a calm section of distinct currently authorized needs. Each ordinary action row has a useful owner-supplied step, clear title, sufficient privacy-safe context, a meaningful proven consequence or deadline only when needed, and one primary navigation link to the existing owning journey. A required continuing status row can omit a link when its owner supplies no permitted destination. The section does not execute changes or decide that a gift, verification or repair is complete.
>
> Start with three ordinary rows as a proposed product default. Use a visible **More actions** control for a proved remainder, expanding the same section in normal page flow through bounded current continuation. Required source safety presentation overrides the ordinary preview cap. Exact totals are unnecessary and must not be invented from a partial result. Keep Ministry Updates, documents and ordinary navigation directly accessible.
>
> Ordinary admission requires a present useful donor step from a qualified identity request, canonical recurring action-required problem, or durable authorized preparation/change request already governed by Q03/Q09/Q11. A mere draft, past failure, paused gift, processing payment, optional missed-gift review, available receipt, new post, missing profile field or unqualified provider status does not create a chore. Separately preserve continuing presentation required by an admitted owner or Live contract until its exact source-end predicate, including ordinary source-actionable Attention as well as Urgent/safety. If the current instruction is to wait, do not invent new work or infer source resolution from an absent button.
>
> Read, visited, dismissed-looking UI, elapsed time, a successful request, cached return and list removal do not establish completion. Preserve current scope, source identity, actual grouping, partial knowledge and safe recovery on every read and destination. Reuse current owner projections and applicable Phase6/17 records; add no competing attention/task/read ledger, new reminder sender, generic workflow, urgency score or staff-data shortcut.

The three-row preview, inline continuation, placement and stable order are explicit presentation recommendations, not claims of a universal optimum. They are included in the requested ratification. No change to the ratified business-authority or notification lifecycle rules is proposed.

## Adversarial check

### What could go wrong with this answer?

A attractive list could invent obligations from old failures, obscure which gift is affected, hide a second need, expose staff/private data, or remove work merely because it was opened. A failing source could look like no action is needed. These are the primary concerns; color and spacing cannot repair them.

### What hidden assumptions are we making?

There may be more than one need, but no measured donor task-frequency distribution was supplied. Three rows is a restrained starting judgment. Some pending states require a donor step; others require waiting or staff work. A source is not qualified merely because a table, status label or provider field exists.

### How does this affect the whole product?

The donor portal composes source-owned needs. Mission Control retains staff tasks and repairs; missionaries retain permission-safe support views; public giving remains guest-first. The same source outcome drives each authorized surface. This choice does not create newsletter reminders, debt, document issuance or a new workflow product.

### How does this affect the end-user experience?

The donor sees what matters now, understands the object involved, and goes directly to a useful next step. They can choose their own ordinary task order and still read Updates or retrieve documents. Short rows and truthful partial states keep Home useful without a compulsory checklist.

### Does this follow modern best practices?

Yes, when implemented as concise main-page content with current state, clear navigation and progressive disclosure. Modern product precedents support both grouped and contextual action presentation; none proves three rows, a particular rank or improved donor retention. Accessible semantics, full essential text and stable focus must be proved in the actual composition.

### Does this fit Asym’s existing repo and product direction?

It fits R01's self-service Home and exact Maia, ADR-0001's domain ownership, and ADR-0027/Phase17's separate availability, engagement and source state. The current Home has real reads but no complete attention contract. Existing staff attention persistence and the seven initial staff notification mappings are not donor Home authority.

### Should we adjust the recommendation?

Keep A. Narrow admission, preserve required safety independently from ordinary actions, use one small readable section with proved continuation, and qualify the source reader and handoffs. The strongest alternative remains contextual notices beside each related Home area; its context advantage is preserved by sufficient row context and detail in the owning journey.

## The row design

Use one neutral shared **Card**, a real **Needs attention** heading, and a semantic list composed with the existing shared Item primitives where suitable. The initial location is after the greeting/current permitted context and before ordinary summaries. This makes current needs easy to notice while preserving normal navigation and the prominent Ministry Updates destination/preview.

Each ordinary action row follows a small grammar, not a mandatory four-line form. A required continuing status row uses the same readable title/context but has a link only when its owner permits one:

1. **Title:** name the problem or remaining task in familiar sentence case: “Finish your email change.”
2. **Context:** include only what distinguishes the actual target: the permitted organization, gift or current request. Several similar gifts must be distinguishable with owner-approved facts. Do not expose a hidden missionary name, another Party's record or a raw provider ID.
3. **Consequence/date:** add one short proven consequence or meaningful owner deadline only when the donor needs it. Avoid repetitive status badges, relative countdowns and generic “Urgent” decoration. If an amount is genuinely necessary, use the source's original currency/minor units; do not total unlike currencies or summarize unrelated gifts into a fictitious debt.
4. **One primary navigation link:** a clear next step such as “Continue email change” or the exact owner-approved recurring review label. Preserve native link semantics. Full detail and consequential confirmation remain in the existing journey.

**Illustrative two-row content, assuming both source steps are currently admitted:**

| Needs attention | Next step |
| --- | --- |
| **Finish your email change** · Confirm the contact address you chose for Global. | Continue email change |
| **Continue updating your payment method** · Finish the verification for the method you are adding. | Continue verification |

The example shows different source tasks, not a combined command. A donor can choose either ordinary task. Labels are illustrative content, not proof those exact services are currently wired. A waiting-only method would not produce the second row.

Prefer whitespace, alignment, a subtle separator and the existing theme over colored card stacks. A small optional semantic icon can aid scanning, but text carries meaning. No decorative portraits, hero image, progress ring, completed-task trophy, permanent red unread badge, dismiss checkbox or nested options menu is needed for ordinary rows. Do not duplicate every same warning in multiple Home cards; its owning detail page still presents necessary context.

### Exact shared-component caveats

The checked-in system is `base-maia`, Base UI1.5.0 and shared semantic tokens. Current upstream docs describe features the installed wrappers do not all expose. Do not copy latest Card `size`/spacing or Item `xs` APIs into this repo blindly, or migrate primitives just to render this section.

Actual source/SSR confirmed CardTitle defaults to a div; ItemGroup supplies list role while Item does not automatically supply listitem; Alert defaults to alert role; ItemDescription includes a two-line clamp. Supply a real heading and list relationships, keep essential text unclipped, and use ordinary content rather than an Alert for every row. Existing props can compose valid heading/list/link markup. ## Ordering, preview and continuation

**Proposed ordinary default: three rows.** This displays the illustrative two needs together without an extra disclosure step, and reserves Home space for ordinary service content. It is a product judgment for ratification, not “three is scientifically best.” Required safety presentation follows its exact source contract and cannot disappear behind a numerical cap.

Preserve exact contract-required immediate/prominent presentation and source-qualified Urgent treatment first. Among ordinary items, show present donor steps before any owner-required continuing status that needs no donor step; use oldest-current-need-first with a stable opaque source tie-break within those peers. Required continued existence alone does not make an ordinary item Urgent or require top placement. The time means when that current need became actionable, certified by its owner; do not substitute last retry, last email, unread time or browser time. Adapters must supply a qualified ordering basis rather than mix unrelated date meanings. This order provides stability, not a claim that an older need is financially or morally more important. Exact required deadlines remain visible where useful; gift amount, expected revenue and missionary popularity never rank rows.

Authorize, evaluate current applicability and source policy, establish exact duplicate equivalence, then select the bounded preview. Do not fetch three arbitrary raw records and filter afterward. A same-source request can have multiple notification copies; one row is allowed only where the owner supplies the same current episode/next-step meaning and exact viewer boundary. Similar labels or last-four digits do not establish equivalence. Separate rows in one section never merge authority or completion.

**More actions** reveals the next bounded set in the same section, using normal page scroll. The first continuation should add three ordinary rows, retaining the same row grammar and source qualification. The end/control says More, not Show all when it fetches only another part. No separate inbox route, carousel, nested scroll region or forced infinite scrolling is introduced. Once the donor deliberately expands the section, Updates remains directly reachable through normal navigation. Do not silently discard earlier revealed rows; any eventual bounded-window eviction must preserve a reachable backward/reading anchor and be proved before use. Neither a small DOM nor a server page alone proves bounded total client memory.

Before repeatable More actions ships, declare and verify bounds for retained client data as well as rendered rows under the qualified workload. If maintaining those bounds drops earlier rows, preserve keyboard- and screen-reader-reachable backward continuation and a revalidated same-context reading anchor. If the prior window expired or changed, explain that limit and reload from a safe current position rather than promise exact restoration. This requires no separate inbox, numbered pagination or durable client task ledger.

An exact total badge is omitted by default. A proved current remainder is sufficient for More. If a source is incomplete or unavailable, do not turn an unknown remainder into false, a zero count or a complete-list claim. A continued reader must reach every admitted ordinary need without duplicate/skip under its currentness rules. An exact contract requiring immediate/prominent presentation may need a separate bounded treatment; do not summarize it away merely to meet the preview target. Ordinary continuing Attention remains reachable through the current list and is never locally ended just to reduce visible rows.

Keep rows stable during a reading/activation interaction. Background refetch must not move a link under the pointer or steal focus. Required state changes still apply; never retain revoked private content for animation. A new urgent item must obey its source's required presentation rather than wait behind a cosmetic “refresh later” policy.

### Failure, concurrency and client currentness

Owner operations are unchanged by Home reads. Healthy independent sources may render while another fails. A failed read produces a narrow retry/checking state, not a fictitious task, a global crash or zero. A typed401/403 is not a transient network error; preserve status/reason so existing authentication and no-retry handling can act. Current code loses that status in two fetch helpers, as R11 demonstrates.

Key client state by the current authenticated scope and relevant source/access revisions. Cancel/ignore old in-flight results on scope change, clear both approved caches/materialized collections as required, and avoid persistent private rows or capability URLs in browser storage. On permission loss, promptly discard protected content and active cursors. On offline/unknown state, do not offer an unqualified executable action or restore another account's old row as continuity.

Direct current-owner reads may become available again under newly valid authorization if that owner permits them. This must not revive a revoked historical notification occurrence: Phase17's no-revival and presentation deadlines stay with that occurrence. Do not solve this distinction with a second read ledger or by manufacturing a new event for every refresh.

Source transitions can race read, continuation, navigation and return. Use source revisions and stable identities; stale response arrival cannot replace newer scope/currentness. A more-recent invalidation is not business completion. A required safety status can remain after the donor step until its exact source end; conversely, an old notification cannot keep a resolved business action executable. Tests must cover both directions and multiple tabs.

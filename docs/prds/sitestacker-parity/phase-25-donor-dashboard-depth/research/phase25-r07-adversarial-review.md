## Corrected decision to record

> Donors independently control whether a ministry's Asym posts appear in their ordinary Ministry Updates reading list and whether they request eligible Asym emails about those posts. Each control addresses the same owner-certified, stable canonical publishing source and purpose, not a person, Page or arbitrary group. Every placement/coauthor view of an Update resolves to that one controlling source; mixed Page feeds do not create composite preferences or a path around hiding.
>
> Each deliberate change saves only its own source-owned preference, using an explicit desired value, current authority and revision, and a reliable operation identity. The interface shows local pending/confirmed/rejected/unknown outcomes and never reports a timer, callback or stale snapshot as success. Another control's change or failure cannot overwrite it. A fresh safe Off remains possible when an earlier On is unresolved, and stale On cannot undo a later accepted withdrawal.
>
> Hiding affects the ordinary reading list and dashboard preview, before pagination. It changes neither email consent nor content permission. Hidden sources remain safely manageable, with independent email control and reversible display choice. A deliberately opened exact-post link may show currently authorized content without restoring that source to the ordinary list. Restoring posts changes display only. R02's optional filter remains a non-mutating view choice.
>
> Email preference is separate from contact verification, higher contact/suppression rules, source publication/notification intent and actual delivery. No new scope starts emailing from missing data, a default, a gift or a follow. On creates no notification or backlog. A valid Off accepted before the owning dispatch-admission point suppresses matching unstarted optional mail; already-admitted/unknown delivery is reconciled honestly. Later On does not revive withdrawn old work or change the frozen recipients of a released plan.
>
> Notify the initiating donor with concise local status and accessible feedback. Do not generate a preference-change email, missionary alert, task, badge, engagement score or newsletter request merely because a switch changed. Preserve separately required source-qualified verification/security notices without inventing them. All four preference combinations remain valid. No change affects giving, external newsletters, protected audience membership or required organization messages by association.

**Explicit owner refinements:** certify the single canonical controlling source/purpose and its mapping across placements; add persistent Hide alongside R02's transient filter; complete per-source email purpose/default/provenance/adoption and source-fenced save/withdrawal contracts. This is narrow source-owner work, not a second subscriber registry. Existing columns/identities should be reused where they express the meaning correctly. A required relationship cannot be fabricated to make the UI work.

## Adversarial check

### What could go wrong with this answer?

A stale full-page save can overwrite an opt-out; a post can return through another Page; a hidden row can remove the only email control; a worker can send from stale consent. Current source also has fake settings saves, contradictory defaults, discarded unsupported fields and a broken unfiltered feed request. These are concrete implementation gaps, not reasons to replace the selected two-control design.

### What hidden assumptions are we making?

“Ministry” is not necessarily one author or Page. Known absence is not a failed read, and a current-looking switch is not consent or delivery proof. The four use cases are sensible product possibilities, not measured donor behavior. Current catalog/source command completeness and end-to-end quality are not established by existing prototypes or the fixture results.

### How does this affect the whole product?

The preference owner supplies current choices; Phases 22/9/28 supply the certified content source/purpose and audience; Phases 3/4/10/12 govern current person, contact and sensitive-data authority; Phases 6/17 own compiled message plans, admission and delivery. Mission Control reads appropriate evidence; missionaries do not receive a new disengagement signal. Phase 32 later consumes the same consent boundary. No content, financial or notification truth moves into the portal.

### How does this affect the end-user experience?

Two stable labels, each saving independently, avoid a whole-form Save and hidden side effects. A short local status explains saving, failure or uncertainty. Hidden sources remain recoverable. The donor can keep reading without emails, receive eligible emails without cluttering the ordinary list, use both, or use neither. Necessary verification or current blocks remain understandable.

### Does this follow modern best practices?

Independent content and notification preferences are useful precedents in Mastodon/Substack; accessible state and explicit desired-value updates are durable engineering patterns. The exact installed Maia/Base UI/TanStack behavior, current PostgreSQL documentation and source contract take precedence over generic advice or a provider's default. No claim of improved retention or measured task completion follows from vendor documentation.

### Does this fit Asym’s existing repo and product direction?

Yes, with the explicit source mapping and owner adoption above. Current email consent code provides real blocking behavior, but is not yet a per-source subscription/withdrawal model. The donor portal's read composition and server commands must replace or safely adapt inconsistent legacy paths. Public newsletter request work remains a separate qualified handoff.

### Should we adjust the recommendation?

Keep A and ratify the corrected decision plus C01–C22 below. The material changes are scope precision, persistent-hide semantics and qualified reliable email preference/adoption. The user need and independent effects remain. Source/runtime/provider/browser proof is required before activation, and this review does not declare the full Phase 25 ready.

## The calm, complete donor journey

**Illustrative situation:** Alex wants Maya's Asym post emails but prefers other ministries in the ordinary dashboard list. Maya's currently authorized settings row shows her safe ministry label and two controls. Alex turns Show off. Only that control saves. The email setting stays as it was. Once the owner confirms Hide, the row can say **Hidden from your Updates. Email notifications remain on**—but only if the current email setting is actually known to be On. Otherwise say only **Hidden from your Updates** and explain that this action changes reading visibility only.

This is content/interaction guidance, not a claim that a particular donor was observed or a pixel layout was tested. The source label must identify the ministry's actual canonical stream. A person's name or avatar alone is not sufficient when that person belongs to more than one ministry.

## Data and command design: exact meaning without another platform

Use the existing source-owned preference/consent boundaries, not two independent applications storing duplicate copies. Physical table names/count are implementation choices; the following logical facts and invariants are required. A view/DTO composes them for the donor.

| Logical fact | Required identity/evidence | Owner and invariant |
| --- | --- | --- |
| Display preference | Trusted Tenant/reader + certified canonical source/purpose; explicit hidden/shown fact or qualified absence; display revision | Personal preference/read composition. One current fact; no contact permission effect |
| Update-email choice | Exact recipient/source/purpose/channel and applicable contact authority/revision; authored/qualified provenance; current email/withdrawal revision | Existing consent/contact owner. No defaults-as-opt-in or clearing of higher blocks |

Commands accept a bounded target reference, one explicit desired value, the relevant expected revision and an operation identity. The server resolves actor, Tenant, reader/recipient, allowed purpose and canonical mapping; it does not accept caller-authoritative identity, audit fields, verified flags or message classification. A repeat with changed immutable content conflicts. A repeat of a completed intent returns its historic result only where still authorized, alongside or followed by current state so an old success cannot render as a new On.

Canonical source and command references preserve the owning Legal Entity/environment and any other required namespace from the source contract. One entity at launch is not permission to omit those boundaries or cross test/production scope. These are server-derived source facts, not additional donor-facing settings.

Persist the chosen fact, correct revision and necessary private change/fence evidence atomically. Preserve a successful sibling. Per-control versions avoid unrelated conflicts; serialization and current authority fences cover same-field changes and revocation. The exact server algorithm must prove a fresh Off can be established despite unresolved On, while old On cannot win later. This review does not substitute a client queue or session timestamp for that proof.

Required schema properties: non-null required scope, exact current-fact uniqueness, tenant-aware foreign keys, valid closed states/revisions, immutable operation/evidence identity, explicit contact scope, indexed owner lookup, controlled deletion and purpose retention. No money field, fee calculation or new financial record belongs here. Empty/legacy schema fields must not be silently promoted into identity or permission. A delete or rollback cannot revive old mail permission by making a row disappear.

Browser privileges and row policy are separate. Use source commands for these effects where audit, current source authority, contact consent and dispatch fences apply. Read projections remain current-role safe. Privileged functions/views must enforce the same boundaries. The actual target proof must include allowed-old-row to forbidden-new-row transformations, stale scope, revocation during a wait and direct Data API paths. Fixture SESSION_USER is not a recipe for Supabase JWT/pool authorization.

The invoked Supabase skill overstates two rules: an omitted UPDATE WITH CHECK can inherit USING; SECURITY DEFINER uses the function owner's privileges and does not universally bypass every policy regardless of role. Current PostgreSQL documentation and effective catalog/role tests govern. Do not add broad grants to fix an error, assume RLS alone gives table access, or treat a compatibility bootstrap's service-role denial as a proved hosted defect. [PostgreSQL policies](https://www.postgresql.org/docs/17/sql-createpolicy.html), [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [locking](https://www.postgresql.org/docs/17/explicit-locking.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Notification behavior: no more, no less

- **To the donor changing a control:** local pending/result/error and one appropriate accessible acknowledgement. No automatic preference-change email or bell item merely because it changed.
- **To the missionary:** no new notice that a donor hid posts or disabled Asym update email; no disengagement score or support-health change.
- **For actual Ministry Update notifications:** the producer must deliberately admit the notification occurrence. On is only one current eligibility input, not a send trigger or consent to unrelated topics.
- **For a compiled plan:** the complete evaluated members are frozen at release. Later checks can suppress based on current contact/consent/source authority; they cannot add recipients, retarget another address or revive a zero-member result.
- **For Off:** establish the relevant current preference/withdrawal fence. Before the exact Phase 6 dispatching admission point, matching unstarted work is suppressed. After it, reconcile the actual already-in-flight result without a recall promise. Re-On does not revive work invalidated by Off.
- **For external newsletter requests or mandatory verification/security communication:** only their separately qualified source contracts may create messages. This review neither implements the public request nor adds a default acknowledgement/reminder campaign.

Current RFC 8058 still requires a narrow recipient/list-purpose token-bound POST without login/cookies/extra confirmation; GET is inert. The donor settings route is a separate authenticated editing journey into compatible source meaning. Both paths must share withdrawal semantics without allowing a mailbox token to expose a full preference page or unrelated identity. Gmail distinguishes a body preference link from its required header action and allows list-specific withdrawal; its 48-hour expectation is not an excuse to delay Asym's accepted source opt-out. [RFC 8058](https://datatracker.ietf.org/doc/html/rfc8058), [Gmail FAQ](https://support.google.com/mail/answer/14229414?hl=en).

The permanent design is a small composition of existing owners. It does not require a generic subscriber registry, new queue, copied feed, global command bus or another realtime service.

## Complete concerns and required execution language

These are reviewed grooming requirements for later authorized contracts and implementation. They are not a published formal specification or new tickets. Material source refinements are presented for ratification.

### F01 — A ministry label is not a stable preference scope

**What could go wrong:** Controls follow an author, Page, participant or changing source set; the same Update reappears through another placement after hiding, or a new author inherits email permission.

**Why it matters:** The donor's choice changes meaning and can expose or email content they did not select.

**Severity:** High. **Likelihood:** Concrete contract-completion gap: Pages can select source sets and ministries can have multiple participants; target mapping is not implemented.

**Evidence/reasoning:** P22 D3:386–398, D11:1793–1816, D19:3318–3335; owner review O01.

**Effect on the answer:** Requires an explicit narrow owner amendment; preserves A.

**Best permanent prevention:** Normalize each Update and all placements/coauthor displays to one owner-declared canonical controlling source/purpose. Reuse existing source identity where sufficient; no new registry merely for UI labels.

**Exact language to add:**

> C01 — Each Update and donor control resolves to one certified stable canonical publishing source and purpose. Page source sets decompose into their authorized canonical members; they are not composite preference targets. Deduplicate the canonical Update in the ordinary list and apply its declared source's Hide choice once. Authors, participants, Sites, labels and placements cannot move or bypass the choice. Genuine source succession requires explicit owner migration and consent qualification.

### F02 — A valid read can outlive the user's authority

**What could go wrong:** A command checks access, waits for another write, then changes a preference after that authority has been revoked; a represented-giving context edits another person's preferences.

**Why it matters:** Tenant and person isolation must survive races, not only initial page rendering.

**Severity:** Critical for cross-person disclosure or unauthorized consent; High for stale authorized scope. **Likelihood:** Conditional design risk; synthetic E36–E40 reproduce an unfenced authority race and its bounded prevention.

**Evidence/reasoning:** P3/P4/P9/P12 ownership; R04; SQL E01–E04,E33–E34,E36–E40; legacy fixed-Tenant/email lookup.

**Effect on the answer:** Requires current source authority at the owning mutation boundary; no new grants.

**Best permanent prevention:** Derive actor/reader/Tenant from trusted context and serialize admission with the relevant current authority fences. A server credential is not actor proof. Recheck permission before returning earlier operation details.

**Exact language to add:**

> C02 — Read and write only the current human's owner-authorized preference scope; represented giving, shared email and a generic donor role grant no additional rights. Derive actor and attribution server-side. Current authority/revocation is fenced with mutation admission, including conflict/replay paths. Scope includes the exact Tenant, canonical source/purpose and applicable reader/recipient/contact context. Never use demo-Tenant, email-match or service-role fallback as authority.

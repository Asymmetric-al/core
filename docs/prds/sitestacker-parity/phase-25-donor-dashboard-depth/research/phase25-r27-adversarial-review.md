# Q27 — One current mailing address, easy to update

9 September 2026. **Disposition: Accept with required amendments.** Conrad selected A. The corrected execution below is proposed for explicit ratification; Q01–Q26 remain ratified. This is grooming authority, not a shipped feature, canonical ADR/OpenSpec amendment or permission to implement or publish.

The right donor experience is one optional Mailing address block in My details, one focused editor, and an accurate confirmation. The small interface must sit over a precise personal contact owner: otherwise a successful move can be undone by a wallet, applied to another person, or leave unsubmitted mail using an obsolete destination.

The full source checkpoint, primary references and verification limits are in the [evidence companion](phase25-r27-evidence.md). Requirements below are normative proposed language. Examples are illustrative, not observed ministry workflows. Severity and likelihood describe credible implementation risks, not measured production incidents.

## Evidence and strongest alternative

**Repository facts:** P19/ADR0041 already distinguish current-primary contacts, specifically reviewed destinations, immutable statement plans and actual postal handoff. P7 freezes issued identity/address facts. P9 requires a thin Party, transactional CRM writes and audit/activity, while deferring general contact normalization. P12 owns fine-grained authorization. Current donor settings has a disabled postal placeholder and its strict PATCH accepts no address; existing profile/donor updates are sequential. A postal editor is an explicit new, narrow capability, not completed behavior discovered in current code.

The existing CRM Core OpenSpec still describes Twenty and a separate datastore. Accepted ADR0001 and the founder's current direction retire Twenty and put CRM truth in Asym Postgres. Record this exact reconciliation before implementation; do not revive the stale vendor integration or pretend the canonical documents already agree. Q27 additionally proposes narrow changes to P9/#620's postal audit, retry and retention rules, explicitly identified in A3/A5.

**External facts:** Fundraise Up documents a focused donor-profile address edit, separate recurring-plan effects, and a real stale-wallet overwrite pitfall. Its automatic receipt-reissue behavior in other edit paths conflicts with Core and is not adopted. PayPal documents saved addresses and current-address selection, showing that B is a legitimate stronger alternative. Neither source proves Asym donors need a saved-address library. [Fundraise Up](https://fundraiseup.com/support/set-update-mailing-address/), [PayPal](https://www.paypal.com/us/cshelp/article/how-do-i-add-change-or-remove-a-street-address-on-my-paypal-account-help239).

**Product judgment:** choose one current address because the selected task is a move or correction, not managing repeated destination switching. Staff alternatives and historical source evidence remain; the UI choice is not a one-row storage limit. Re-entering a former address is an acceptable cost for this scope. Address-book frequency, donor completion and country coverage have not been established with Asym user research.

**Design evidence:** international formats vary; country-specific fields and manual entry must fit real addresses. Input purpose, retained entered values and clear success/error feedback reduce avoidable effort. No evidence establishes that paid address lookup, a verification badge or a second confirmation improves this occasional profile task. [GOV.UK address pattern](https://design-system.service.gov.uk/patterns/addresses/), [UPU addressing](https://www.upu.int/en/postal-solutions/programmes-services/addressing-solutions), [W3C input purpose](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html), [W3C form feedback](https://www.w3.org/WAI/tutorials/forms/notifications/).

## Corrected decision to record

### A1 — One optional current personal mailing contact with this organization

The donor portal SHALL show one current personal mailing address in My details for the exact authorized person and organization. It SHALL provide Add address, Edit and Remove address according to their independent current capabilities. Absence is valid: this optional personal-mailing profile field is not a prerequisite to complete an account, give digitally or dismiss a profile-completion prompt. Independent checkout/billing or exact-issuer receipt-fact requirements remain under their own owners; Q27 does not waive them. No saved-address library, seasonal schedule, primary/default selector, grid or address score is introduced.

This purpose belongs to the organization's personal CRM contact source. It is not the global login profile, household address-of-record, represented organization's legal address, missionary public profile, card billing address, legal-donor identity or another Tenant. Matching an email, name or postal address grants no ownership. The current personal view cannot edit represented records by implication. Exact source history and staff alternatives are preserved within their existing authority and retention; they are not offered as automatic fallbacks.

### A2 — A complete, quiet, international edit journey

Use the existing My details overview. Edit replaces only the Mailing address summary with a single-column form in place; other settings remain stable. Prefill the exact admitted current value, retaining meaningful spelling, scripts and units. Use a visible Country or region field, address lines and country-appropriate locality, region and postal fields. Show only fields the qualified format uses and require only its necessary parts. Use text for postal codes, preserve leading zeros and support PO boxes, military/diplomatic, rural, care-of and no-postcode formats where applicable. No residence, citizenship or tax status is inferred.

Country changes SHALL preserve all entered content and expose any re-mapping for review; they SHALL NOT discard a unit, district or postal value. Where a structured format cannot faithfully express the address, offer the quiet “Use address lines instead” action within the same editor. Countries without a qualified template open that manual form directly. Label it “Address as written for mail,” with a brief reminder to include locality and postal code where used. This is an input representation, not a second saved address. A source-owned tagged representation prevents both structured and manual values from becoming independent authorities. Store the country explicitly; never geolocate the person to choose it. The current saved country may be prefilled; a new address begins with no inferred country. Consumers must explicitly support the selected representation: preserve manual line order, never parse guessed city/postcode values, and never claim every mail-house accepts it. Unsupported physical fulfillment is an owner-qualified route limitation, not a failed contact save or reason to invent a complete global template engine.

Manual entry and browser autofill work without an address vendor. Do not split a house number/street, transliterate, force all-uppercase storage, strip accents or require a lookup match. A future suggestion may be offered only as an editable, explicitly accepted convenience with a manual bypass; a match does not prove identity, occupancy, deliverability or permission.

Proposed defensive input defaults: a closed country/territory code from the qualified catalog; up to eight ordered delivery lines of 200 Unicode scalar values each in manual mode; structured street lines use the same eight-line capacity, locality/region/dependent-locality each at most 200, postal code at most 64; total address-value payload at most 16 KiB UTF-8. These are generous product limits, not international postal standards. Reject excess with an inline explanation, never truncate. Do not show eight empty inputs: begin with the fields of the selected format and reveal extra address lines when requested. Care-of belongs in a delivery line and cannot change the legal addressee.

Save address is the sole primary action. Normal edits need no inbox visit, postal verification, routine reauthentication, reason, staff approval or extra review screen. Current session and exact server authorization remain mandatory. Cancel makes no write. Only a genuinely dirty form needs an unsaved-changes warning. Validation appears on blur/submit and clears as corrected; do not announce errors while a donor is still entering an incomplete value.

### A3 — A narrow CRM owner and one atomic mutation

Qualify a Personal mailing contact within the existing CRM owner in packages/api. Its logical aggregate is `(Tenant, person Party, personal-mailing purpose)` with at most one current revision and a monotonic revision/guard that survives clearing. A value revision is immutable; correction creates a successor. Preserve the source-selected current binding separately from imported observations and historical destination snapshots. This is a finite postal extension to P9, not activation of a general contact-normalization product or use of P4's reserved email/phone contact_points as if they already own postal data. No new inline Party address, shared profile mirror or unvalidated JSON shadow is permitted.

The same source guard also carries the **personal-mailing use generation**. Source-qualified formatting-only successors retain that generation; a material replacement or Clear withdraws it, and a new usable address receives a new non-reusable generation. Value revisions carry the trusted generation reference. This is a small addition to the existing purpose guard, not a general address-equivalence registry or ancestry scan. P19 freezes both exact value revision and its use-generation authority.

The authorized mutation SHALL validate the whole intended value, compare the observed current revision, and atomically record the current binding/value successor or clear, the narrowly scoped superseded-purpose withdrawal in A4, one CRM audit event and one CRM activity event. An unchanged semantic value is a no-op: no new revision, withdrawal, audit/activity change or postal review. Durable downstream invalidation/review work uses the established transactional event mechanism; it is not a separate provider command ledger. P9's audit resource/source-surface vocabulary receives explicit personal-mailing/donor-profile extensions. **Explicit P9/#620 postal audit exception:** before/after snapshots for this resource contain only safe revision/state references; generic audit/activity stores never contain full address diffs. These Q27-only rows remain immutable while retained but undergo the governed bounded disposal in A5, instead of inheriting #620's unconditional never-delete rule. This exception does not reclassify other CRM audit resources or notes. Exact retained values remain in restricted source custody.

**Explicit P9 A17 precision amendment:** this local postal operation requires expected-revision compare-and-set plus a scoped mutation nonce/result reference on its immutable source change evidence. Unique `(Tenant, person, purpose, nonce)` admits one business effect. The nonce is correlation, not authorization; the server binds actor and payload identity. An equivalent retry returns the original result without another revision, audit/activity emission or downstream task. A reused nonce with different intent is rejected. If a newer change exists, return the prior operation outcome separately from the presently authorized current revision. Expired result evidence cannot permit replay against an old revision. No money-path Idempotency-Key protocol, crm_command_logs, provider-idempotency log or provider availability gate is introduced.

Database constraints SHALL enforce tenant-aware composite relationships, personal subtype, one current binding, current-to-own-value ownership, trusted attribution and non-null actor-kind/timestamps/revision, bounded tagged value shape and no cross-purpose reassignment. A human actor reference is server-derived; later identity disposal follows its qualified owner rules without inventing a name snapshot. Internal source rows are not raw browser-writable; grants, RLS, invoker/definer functions and service-role paths must be independently proved. P12 is the sole fine-grained PDP for the exact read/add/change/clear field and purpose. A user-supplied ID or expected revision is only a target assertion, re-resolved server-side. Ownership, Tenant, author, actor, approval and audit attribution cannot be patched by the caller. Deletes cannot cascade into issued documents or fulfillment evidence.

The portal reads a minimal authorized server projection through TanStack Query and the approved database hook boundary; the form uses TanStack Form/Zod. Do not fetch a complete profile/history merely to confirm a saved address. No TanStack DB collection, Table, Virtual or Store is needed for this single server-owned contact mutation unless an independently approved existing seam already uses it. ReUI remains inspiration for actual grids elsewhere; this is a form. Do not upgrade dependencies or build competing state stores for this question.

### A4 — Clear future-use effects without rewriting history or misdirecting mail

A materially changed address or Remove address SHALL withdraw future personal-mailing use of the superseded current revision's **use generation** within this exact person/organization purpose, including all still-usable formatting predecessors in that generation. This narrow withdrawal is an explicit Q27 source-policy addition: it does not merely relabel the old address, mark the physical address invalid for every person, or withdraw all communication consent. It provides the current safety evidence P19 requires. It also prevents a stale import, wallet value or retained staff alternative from becoming current again without a new authorized choice. A proved same-delivery-point formatting-only correction does not assert a move or revoke an independently reviewed safe destination; absent proof, use material-change handling. Throughout this decision, withdrawing the old personal revision includes its source-qualified use generation: A→B formatting followed by B→C move must also stop a not-yet-admitted P19 route frozen on A. No synchronous predecessor enumeration is required.

The address mutation and an affected route's final irreversible-handoff admission SHALL serialize on the source safety revision through P19's existing guard. If withdrawal wins, no later admission may use the old revision. If handoff already crossed the guard, classify it as submitted/possibly submitted and reconcile; a later save cannot promise to prevent or recall the external effect. This is not an atomic transaction spanning Postgres and provider/postal I/O. Safety does not wait for eventual cache invalidation or a worker to enumerate old routes. Referencing the withdrawn personal-purpose revision makes an otherwise explicitly reviewed destination no longer usable under that same purpose. A genuinely independent, still-authorized purpose-specific destination is not silently retargeted or withdrawn. P19 current-primary selection changes stale preflight or hold affected unsubmitted work; source-qualified successors require its existing review/current proof and new semantic occurrence identity. There is no automatic switch to the new address, alternate address, email or new print run.

Prepared/downloaded/printed material is not proof of postal handoff. Unsubmitted controlled artifacts are revoked or held as supported; existing staff containment handles already downloaded physical copies. Submitted or indeterminate mail reconciles before any new attempt. The UI never promises recall of an envelope or deletion of an external copy. Source save can succeed while an affected fulfillment operation needs review; these are separate outcomes.

Remove address means no current address and no fallback for this personal-mailing purpose. It does not erase required records, stop donations, cancel recurring arrangements, unsubscribe from marketing, change independent statement-specific authorizations or alter issued PDFs. Use a short removal confirmation explaining this distinction; where a current affected mail operation is known, show only the necessary authorized handoff/review explanation. A blank edit is not implicit removal. Restoring an address later requires a new authorized save under a new revision.

P7/P18 retain frozen document facts and source-correction/successor rules. P19 retains destinations, fulfillment and containment. Email Studio/Resend are not invoked by an address save: it creates neither an email verification requirement nor a receipt resend. A separately justified owner communication must use P17/P6 rather than an ad hoc callback. Mailing contact is not opt-in or delivery enrollment.

### A5 — Bounded private custody, safe rollout and proof

Keep the current value only while this personal-mailing purpose is active. Proposed contact-owner custody defaults: superseded/cleared raw address revisions leave the current-contact/editor projection immediately and leave this contact owner's live raw-value storage within **24 elapsed hours after retirement**, with earlier applicable erasure and exact lawful holds handled by the owner. Future-use withdrawal follows A4's material-change rule; proved formatting-only changes do not revoke a separately frozen valid destination. No donor undo/address-library purpose has been established to justify a longer raw-copy window. Minimal address-change/nonce evidence has a proposed **365-day diagnostic ceiling after the event**; the monotonic live guard and reference-needed withdrawal evidence remain for their separately defined active purpose. Once the purpose ends and no consumer references remain, the remaining safety metadata enters the same 365-day bounded disposal class from that terminal event. No raw address, reversible fingerprint or indefinite identity trail may be smuggled into that guard. These are privacy ceilings for this new contact class, not statutory retention rules or authority to purge another owner's financial/delivery evidence. Backup expiration follows its qualified copy-class schedule and restore suppression; live-store deletion is not a claim of immediate physical destruction from every backup.

Where an applicable lawful floor/hold conflicts with a proposed ceiling, restrict use and qualify the exact owner schedule before activation; do not invent a universal legal period. Required P7/P18/P19 copies retain their own purposes and schedules. ADR0038 supplies a design precedent, not a platform-wide contact-retention owner. Backups, exports, restricted-person handling, restoration suppression and disposal must preserve these distinctions. No automatic identity matching, public publication or external address-validation transmission is authorized.

Roll out the source contract and constraints first, then consumer fences and the minimal read/mutation seam, then the editor. Legacy donor address/work_address JSON is evidence to reconcile, not proof of an authorized current personal choice; ambiguous ownership/currentness stays unresolved, and the donor is not shown another Party's candidate. Migrate incrementally with provenance and parity checks, stop old writers, and use one authority at cutover. After new revisions exist, disabling the UI must preserve source revisions and safety withdrawals; rollback to an old writer is forbidden. Never reset the guard or silently resume withdrawn mail.

The target tests, accessibility review and consumer/migration evidence below are activation requirements. This review does not claim that they have passed. Q14 G01 remains unresolved and is not solved by this contact editor. Keep the source safety and permission prerequisites explicit, without making ordinary profile writes depend on an unrelated payment or mail provider.

## Independent adversarial category review

### C01 — Problem validity, necessity, and alternatives

**Material concern: Yes. Severity: Moderate. Likelihood: Likely if scope is inferred from the prototype.** A disabled address placeholder could become a compulsory profile task, while e-commerce precedent could expand it into an unnecessary address book. P19 establishes a real mailing purpose, but no Asym repeated-switching research establishes B's extra value. This matters because an occasional task should not burden every donor. **Effect:** accept A, narrow it to optional personal organization contact. **Required language:** “Provide one optional current personal mailing address; preserve source alternatives/history without exposing saved-address management or requiring collection for digital giving” (A1). **Proof:** J01–J04/T01; verify a donor with no address can complete unrelated tasks without a prompt. B remains the strongest alternative, reconsidered only on M5 evidence.

### C02 — Brittleness

**Material concern: Yes. Severity: High. Likelihood: Likely with a universal US form or last-activity merge.** Fixed state/ZIP requirements reject legitimate addresses, while wallet/import activity can undo a move. Fundraise Up documents the latter and UPU/GOV.UK support the former format concern. **Effect:** changes field and ownership execution, not A. **Required language:** “Preserve country-appropriate and manual representations; no automatic imported observation may replace an explicit current mailing choice” (A2/A3). **Proof:** T02–T04/T12 cover no-postcode, multiline, country-change and late-wallet fixtures, including absent templates and no lookup connection. Validate actual round trips and consumer admission, not only field visibility.

### C03 — Technical debt

**Material concern: Yes. Severity: High. Likelihood: Likely if extending current settings PATCH.** Its sequential profile/donor mirrors have no postal owner and could partially succeed. New JSON fields would encode a second authority and make later Party migration expensive. P9 explicitly rejects Party contact columns and reserves general normalization. **Effect:** requires a narrow owner amendment and dedicated seam before UI activation. **Required language:** “Implement personal-mailing changes through one CRM-owned atomic transaction; do not add shared-profile/Party postal mirrors or activate generic contact normalization” (A3). **Proof:** T05/T07/T17; fail injected audit/activity writes and verify no current address change; ensure unrelated settings adapters cannot write the new owner.

### C04 — Edge cases

**Material concern: Yes. Severity: Moderate to High. Likelihood: Likely across international and shared records.** Rural delivery, care-of, no postcode, long scripts, two donors at one address, represented records, missing data and unsafe old mail defeat happy-path forms. They can lose units or expose another person's contact. **Effect:** broadens the journey proof without adding an address book. **Required language:** “No formatting assumption, household membership, name or address equality may manufacture personal ownership; preserve complete admitted values and distinguish absent, unreadable and unresolved current state” (A1/A2/J03/J18). **Proof:** T02/T06/T16 includes identical addresses for different Parties, ambiguous legacy contacts, old-address removal, and inaccessible current values. No hidden default person/country is permitted.

### C05 — Footguns

**Material concern: Yes. Severity: High. Likelihood: Plausible.** A Save all endpoint or copied checkbox can change billing, mailing consent, historical receipts or household facts. A clear action can silently choose a retained alternative. These outcomes exceed donor intent. **Effect:** narrows exact commands and copy. **Required language:** “Save/Remove affect only the current personal-mailing purpose; clearing selects no fallback and creates no charge, preference enrollment, document reissue or other Party change” (A1/A4). **Proof:** T06/T11/T13 assert forbidden payload keys fail and unrelated values/events are byte/identity unchanged. Confirm removing in the UI cannot be triggered by blanking a field or ordinary Cancel.

### C06 — Tenant safety

**Material concern: Yes. Severity: Critical. Likelihood: Plausible without layered scoping.** A shared account, reused query key or stale response can reveal or overwrite another organization's private contact. P12 and the data boundary require exact scope, not a browser tenant filter. **Effect:** requires source and cache isolation. **Required language:** “Bind reads, mutations, result replay, cache identity and invalidation to server-resolved Tenant/person/purpose and current authorization context; revoke and fence old-context responses on switching” (A3/J18). **Proof:** T06/T14, including same Auth user in two Tenants, second tab, revoked delegation, delayed fetch and nonce collision. One actual cross-context disclosure triggers M1 containment, not routine monitoring tolerance.

### C07 — Database, RLS, and authorization safety

**Material concern: Yes. Severity: Critical. Likelihood: Plausible if a generic authenticated update is added.** An allowed update could repoint a current binding to a foreign Tenant/person/revision, or privileged code could bypass RLS and P12. Current legacy JSON/policies do not prove the target. **Effect:** requires the explicit invariant contract in A3. **Required language:** “Use composite Tenant/person/purpose relationships, one current binding, monotonic CAS and immutable value revisions; prohibit caller identity/owner mutation; prove both old-row USING and resulting-row WITH CHECK behavior plus grants and privileged paths.” PostgreSQL may inherit USING as WITH CHECK when omitted; omission alone is not a vulnerability. **Proof:** T05–T08 use actual SQL/grants/functions, foreign IDs, direct table attempts, malformed shape, stale revision, and malicious reparenting. Money precision is unaffected because this owner stores no monetary values.

### C08 — Overengineering

**Material concern: No additional material concern in the corrected design.** Checked address books, seasonal automation, verification vendors, global normalization, provider gates, wizard flows and forcing all TanStack libraries into one form; all are excluded. The necessary complexity is bounded: a current contact revision, one transaction, exact safety references and a structured/manual value representation. No new workflow engine is justified. **Required language:** “Do not build general address management, a provider validation dependency or independent synchronization authority for Q27” (A1–A3). **Effect:** accept the minimal architecture with these exclusions. **Proof:** T17/T20 dependency and traceability review; a later justified capability needs its own explicit scope rather than a speculative reservation here.

### C09 — UX/UI and user friction

**Material concern: Yes. Severity: Moderate. Likelihood: Likely if all exceptions dominate the normal form.** Required address entry, stacked dialogs, clipped lines, a noisy verification badge or toast-only results make a move hard to complete or understand. Shared component names do not guarantee headings, touch targets or focus behavior. **Effect:** changes presentation and recovery defaults. **Required language:** “Use one optional summary and one inline editor; preserve drafts, full postal lines, accessible input purpose and persistent truthful result feedback; display operational caveats only when relevant” (J01–J18/V01–V14). **Proof:** T15/T19, keyboard/screen-reader, 320px/reflow, mobile keyboard, multilingual and low-bandwidth tasks. A research-backed design is not a claim of perfect usability; real donor task evidence is required before general release.

### C10 — Source of truth, ownership, and domain invariants

**Material concern: Yes. Severity: High. Likelihood: Likely without naming owners.** Current profile, latest gift, provider address, historical receipt and delivery snapshot could disagree and each overwrite the others. P7/P9/P19 assign different facts to different owners. **Effect:** requires one finite postal source and explicit consumer references. **Required language:** “Only the CRM personal-mailing owner selects current; providers/imports supply observations, P7/P18 preserve issued facts, and P19 freezes exact destinations. A read model never writes authority” (A3/A4). **Proof:** T05/T11/T12 verify one current binding, lawful zero current, immutable historical snapshots, no mirroring loop and no relation inferred from address strings. Physical table names remain implementation choices; these logical constraints do not.

### C11 — Hidden coupling

**Material concern: Yes. Severity: High. Likelihood: Plausible.** Mail preparation could depend on a mutable current address without a frozen selection reason, or a save could fail because the mail provider or full dashboard refresh is unavailable. P19 and P9 explicitly oppose those couplings. **Effect:** separates local write result from later delivery work. **Required language:** “A local address save commits without a provider gate; future handoffs re-prove source safety, and current-primary versus independent reviewed destination semantics remain explicit” (A3/A4). **Proof:** T09/T11/T13 run provider-down, failing unrelated snapshot and affected/unaffected destination cases. Save succeeds when its transaction succeeds; mail status is reported independently.

### C12 — Failure modes

**Material concern: Yes. Severity: High. Likelihood: Plausible.** Lost responses can cause duplicate revisions; audit failure can leave invisible changes; delayed invalidation can allow obsolete mail; an unknown provider handoff can invite a duplicate. **Effect:** requires truthful outcomes and recovery. **Required language:** “Source write/audit/activity/safety transition are atomic; reconcile the same nonce after ambiguity; fence handoff from live source evidence; never retry submitted/indeterminate mail as new work” (A3/A4/J10–J14). **Proof:** T07–T10 inject transaction failures, dropped response, worker crash, out-of-order delivery and network recovery. Durable acceptance is distinct from current display state and downstream review completion. Recovery belongs in the existing owner tooling, not direct SQL repair.

### C13 — Lifecycle, temporal correctness, concurrency, and idempotency

**Material concern: Yes. Severity: High. Likelihood: Plausible.** Two edits can win together, clear/re-add can cause ABA, a retried old save can undo a staff correction, or a mail worker can cross after withdrawal. P9 client-only duplicate protection is insufficient for the new operation outcome requirement. **Effect:** explicitly amends A17 with source-event correlation and CAS, without importing its rejected provider ledger. **Required language:** “Monotonic versions survive clear; equivalent nonce replay returns one original transition plus independently current state; stale versions cannot mutate; source withdrawal and irreversible handoff serialize on a compatible guard” (A3/A4). **Proof:** T08–T10 cover all race orderings. Effective time is trusted commit time, not a donor-entered date; no scheduled/backdated address switching is added.

### C14 — Data integrity risks

**Material concern: Yes. Severity: High. Likelihood: Plausible.** Parsing manual addresses, truncating long lines, choosing a legacy work address, or silently converting normalized equivalence into a move corrupts contact or delivery meaning. **Effect:** requires typed representations, explicit migration provenance and conservative equivalence. **Required language:** “Preserve full input; accept exactly one representation; qualify consumer formatting; infer neither current choice nor same delivery point from a fuzzy match or latest timestamp” (A2/A5). **Proof:** T02–T05/T16 compare round trips and frozen downstream lines for US/UK/Canada, no-postcode, rural, military and non-Latin cases; invalid old records remain unresolved. A sanitized display is not rewritten source truth.

### C15 — Security and privacy risks

**Material concern: Yes. Severity: Critical for protected people. Likelihood: Plausible.** Postal addresses can reveal a missionary's real location through logs, public profile reuse, autocomplete vendors, unrestricted CRM audit snapshots or shared browser storage. P10 restricts real country/precise location; donor status does not cancel those controls. **Effect:** requires purpose/field safety and minimized custody. **Required language:** “Do not publish or externally transmit this address by default; redact telemetry/session replay; use restricted raw-value custody and the A5 bounded schedules; preserve independent financial/delivery evidence without granting general reuse.” **Proof:** T06/T14/T18 test API, logs, exports, caches, roles, hidden fields, restore and disposal. No new legal compliance certification or global residency inference is made.

### C16 — Scalability and performance risks

**Material concern: Yes. Severity: Moderate to High. Likelihood: Plausible in large mail runs.** Saving one address must not synchronously enumerate every historical gift or mail piece, nor depend on unbounded client history. The proposed current guard/indexed source pointer makes normal work bounded; worker fanout handles grouped downstream review. **Effect:** requires quantitative proof, not “fast” promises. **Required language:** “Current reads and mutations use indexed Tenant/person/purpose lookups; safety closes at commit; downstream fanout is resumable and bounded, with no per-item synchronous save loop” (A3/A4). **Proof:** T19 measures proposed p95 API read ≤500ms and save ≤1s, excluding network, at 50 concurrent mixed address requests, 100,000 people/Tenant and 100,000 referencing operations. These are unmeasured release targets, not existing capacity claims. M3 covers regression.

### C17 — Operational burden

**Material concern: Yes. Severity: Moderate. Likelihood: Plausible if exceptions have no owner.** A contact update may strand physical work or leave staff discovering bad values through returned mail and direct database fixes. **Effect:** requires source-owned explanation and finite repair paths. **Required language:** “Existing P19 operations own affected holds/containment and safe destination succession; CRM owns contact conflicts/migration; group actionable exceptions and provide exact evidence without another address inbox” (A4/A5). **Proof:** T10/T16/T17 show a support user can distinguish saved address, stale route, handed-off mail and inaccessible data using current rights. No automatic support request, duplicate notification or promised staff response deadline is created by Save.

### C18 — Observability and auditability gaps

**Material concern: Yes. Severity: High. Likelihood: Plausible.** A success toast can conceal partial writes, and generic logs containing raw before/after values leak more than they explain. P9 audit/activity and P19 delivery history have different purposes. **Effect:** requires minimized durable business evidence plus separate diagnostics. **Required language:** “Record trusted actor, source surface, purpose, prior/result revision, operation nonce/result and safe outcome atomically; keep raw values outside generic audit/activity; correlate downstream holds without claiming mail delivery” (A3/A5). **Proof:** T07/T18/T20 verify both missing-event rollback and absent raw address in telemetry. Monitoring is confined to M1–M5 with named accountable roles, thresholds and responses; it does not substitute for invariant proof.

### C19 — Dependency and integration risks

**Material concern: Yes. Severity: High. Likelihood: Plausible.** A mail-house may demand parsed components; a wallet may return stale data; mutable country metadata may reformat old evidence; raw Supabase access may bypass the API. **Effect:** requires admitted representations and explicit adapter ownership, not a new vendor. **Required language:** “Country/format rules are versioned and code-owned; consumers explicitly admit structured/manual forms; adapters cannot overwrite current choice or reinterpret frozen facts; provider outage cannot block a local save” (A2–A4). **Proof:** T11/T12/T17 test unsupported consumer format, provider-down and changed format metadata. Current dependency versions remain governed by the repository; no unverified latest-version migration is part of this UI decision.

### C20 — Migration, rollout, and upgrade risks

**Material concern: Yes. Severity: High. Likelihood: Likely if legacy JSON is backfilled mechanically.** Existing address/work_address fields may lack personal ownership/current-choice provenance. Mixed old/new writers can undo new revisions, and UI rollback could reopen withdrawn mail. **Effect:** requires owner-first cutover. **Required language:** “Backfill only proved personal current choices; quarantine ambiguity; stop legacy writers before activation; preserve source guards, withdrawals and frozen records during kill-switch or rollback” (A5). **Proof:** T16/T17 include mixed versions, repeated backfill, interrupted migration, ambiguous household/work address, restore and UI disable after successful change. No broad CRM upgrade or destructive cleanup is authorized as a prerequisite to reviewing this answer.

### C21 — Testability, traceability, and proof

Likelihood: Likely if “easy and beautiful” is the acceptance criterion.** A polished form can pass unit tests while violating source choice, tenant isolation or print currentness. Existing predecessor tests do not exercise the proposed owner. **Effect:** converts intent into the J/V/A rules and T01–T20 release families. **Required language:** “Trace each Q27 invariant to the glossary, scoped P9/P19/P12 amendments, OpenSpec scenarios, implementation work, tests and release evidence; label current behavior, intended behavior and pending proof separately” (A5). **Proof:** T20 checks all identifiers, conflict resolutions and explicit exclusions; T05/T09/T15 must include real SQL/concurrency/manual accessibility evidence, not mirrored mocks. Q14 G01 remains visibly unresolved.

# Question 21 — A calm Preferences overview with focused editing

8 September 2026. Phase 25 `donor-portal-depth`, Grill with Docs. **A is selected; corrected execution awaits ratification.** Questions 01–20 remain ratified, including ReUI as the reference for all actual Asym/Core grids. This is a completed adversarial research review and proposed execution contract, not a canonical ADR/OpenSpec publication, implementation ticket, live preference change or shipped-feature claim.

**Disposition: Accept with required amendments.** Keep **A — One calm overview, edit as needed**. The overview should show real current choices, remain short as the number of topics/ministries grows, and route every edit to its existing owner. The significant amendment is that a single visible page does **not** have one common preference subject, revision, permission or Save operation.

Three concrete findings drive the correction. Current donor notification controls use hard-coded state and timer-based success. Other existing API paths write coarse preference fields that do not implement the ratified purpose/source/issuer contracts. The current full donor snapshot also depends on financial records/services that a valid nonfinancial preference task should not require. A polished overview over those paths would preserve the underlying defects.

## Exact corrected decision to record

> On neutral entry, Preferences presents the current authorized communication and Ministry Updates choices in three understandable purpose areas: organization emails, Ministry Updates and receipt emails, where each applies. A single exact qualified choice is directly editable; a larger set has a truthful, bounded summary and a clear focused management view. The overview does not enumerate every ministry, show invented totals, or reduce every area to a navigation tile with no current information.
>
> Each area retains its own source, subject, permission and revision. Personal reading/contact choices remain personal when a person manages another legal donor's giving. A separately authorized receipt preference identifies its issuer/legal-donor scope explicitly. A shared layout never creates combined authority or a cross-area transaction.
>
> Each ordinary preference change saves independently through the existing owner command, with an explicit desired value, current authority, expected revision, operation identity and truthful local result. Read failure is not Off. Saved intent is not delivery confirmation. Unknown outcomes reconcile without blind rollback, queued stale opt-in or automatic replay after sign-in. Back/Done is navigation, not Save or cancellation of accepted work.
>
> Use shared shadcn/Base UI Maia and ReUI as the reference where a genuine grid is useful. Preserve Q07's independent Show/post-email controls, Q13's narrow routine-receipt policy, Q11's contact repair and the exact scoped unsubscribe path. Externally sent missionary newsletters remain request-and-handoff. No general preference engine, new consent database, master switch, dashboard builder, additional notification family or reporting interface is introduced.

### A1 — A real overview, with a bounded one-versus-many rule

Use a stable product-owned sequence: **Emails from [organization] → Ministry Updates → Receipt emails**. These are purpose areas, not three guaranteed operational cards for every person. For one qualified organization topic, show its exact control directly. For one qualified ministry source, show its two Q07 controls directly. For multiple topics/sources, show separate owner-certified qualitative current-state summaries with focused Manage; no numeric overview counts or arbitrary first-three/last-used/gift-ranked previews. The exact eligible Q13 receipt control remains direct. Missing, not applicable, read-only, incomplete and temporarily unavailable states remain distinct.

The one-versus-many presentation and order are proposed product defaults, not measured universal optima. A summary stating All/None/Mixed requires complete current authorized catalog/default evidence. Neutral Manage copy is allowed during an explicit unknown/unavailable state; it cannot masquerade as a successful current summary or become the permanent substitute for the selected overview.

### A2 — Keep each control's real subject visible and authoritative

Use one trusted session/Tenant envelope and independently resolved section scopes. Organization communication binds the authorized recipient/contact/topic/channel; personal Hide binds the human reader/canonical source; post email binds recipient/source/purpose/contact; routine receipt email binds exact issuer/legal-donor Party/purpose. A represented-giving selection can select a qualified, clearly named receipt context only. It must not change the reader or recipient of the personal areas. No fake donor row, shared-email inference or giving/document grant may substitute for the correct preference authority.

### A3 — Independent, truthful reads and saves

Ready areas remain usable if another area fails. Each command changes one named preference and preserves successful siblings. Stable labels and local Saving/Saved/error/unknown feedback make the outcome clear. No global Save, shared dirty form, overview revision or optimistic confirmation. Reuse the already-ratified fresh-Off/reconciliation safeguards; prevent library queues from replaying stale opt-ins on reconnect. Preserve the distinct Q07 dispatch-withdrawal and Q13 receipt-admission effects rather than claiming every queued email stops immediately.

### A4 — Complete the reached owners and retire incompatible paths

Implement the overview as a small read composition in Core's existing API/data boundary, with fixed product-owned section adapters and existing source commands. Add only the qualified read/summary/descriptor support needed by those owners. Organization topics require an actual purpose/contact/consent/consumer contract; P17 templates are not a topic catalog. Before activating each capability, reconcile or retire its old writer as well as its old UI. No broad compatibility PATCH may silently retain authority that the new command removes. This is owner completion and adoption work, not a second preferences platform.

## The seven Grill with Docs checks

### What could go wrong with this answer?

An overview can look clear while grouping different people's preferences under one heading, showing a failed read as Off, summarizing only a loaded page as All, or claiming a timer completed a save. It can also become either a wall of controls or the category chooser the donor did not select. The corrected execution makes scope, coverage, state and focused editing explicit.

### What hidden assumptions are we making?

We have no measured distribution of Asym donor topic/ministry counts or completed donor comprehension study. Three purpose areas come from accepted product jobs, not research proving an ideal number. A server-certified qualitative summary is proposed source projection work, not an existing complete feature. Some topic/command/dispatch capabilities are still unqualified. The UI cannot manufacture them from a template or local boolean.

### How does this affect the whole product?

All entries must converge on the same owner facts and commands, including contextual post/receipt links and staff views of authorized evidence. The page does not become a communications sender, recipient directory, donor ledger or CMS page. Existing P3/P6/P12/P17/P22, identity and receipt owners keep their boundaries. The reached legacy writers must be closed during adoption, otherwise the new page would coexist with broader contradictory authority.

### How does this affect the end-user experience?

A donor can understand current choices immediately, edit a simple setting directly, or open a larger set without losing their place. Hidden ministries remain manageable. Saving one setting does not block unrelated settings or require a second page-wide Save. Unknown results remain understandable, and a pending On cannot indefinitely prevent a fresh authorized Off when the owner is reachable.

### Does this follow modern best practices?

Current CRM and customer examples support both overview and category-first patterns. Named settings, stable switch labels, focused detail and current state are useful practices; provider defaults, bulk unchecked-field saves and broad notification matrices are not automatically appropriate. Current TanStack documentation also confirms that disabling mutation error retries alone does not prevent delayed offline execution. These are specific lessons, not a claim that vendors have solved Asym's exact problem.

### Does this fit Asym’s existing repo and product direction?

Yes with the required amendments. Q07 expressly left the containing layout open, while its independent controls remain ratified. Q13 already names the receipt preference and direct destination. Q11/Q17 retain identity/contact and notification ownership. P12's single PDP and coarse Tenant RLS forbid a second permission engine hidden in new policies. Exact Maia and Core-owned private account composition prevail over generic UI examples.

### Should we adjust the recommendation?

Keep A. Category-first is a credible alternative for extensive settings and one known task; targeted links make either equally direct. A better serves the chosen self-service goal when someone wants to understand more than one communication effect. Preserve focused editing for large sets instead of changing the whole product to B. Return the explicit summary/scope/adoption refinements for ratification, not another unrelated product fork.

### Lifecycle, concurrency and the correct meaning of Off

One command proposes one desired value against one exact target and observed revision. The server derives trusted actor/Tenant/reader/recipient/issuer/contact/purpose, verifies current authority and enforces semantic idempotency. Repeated identical intent returns its existing effect/current state as permitted; a different payload under the same identity conflicts. A historical successful response cannot overwrite a newer revision merely because it arrived last.

<!-- prettier-ignore -->
| Condition | Required result |
| --- | --- |
| New read pending/failed | Local unknown/loading/error; never initialize a real-looking Off or write a default. |
| Known qualified absence | Show only the owner's legitimate effective default or Not set treatment; reading creates no instruction or donor record. |
| Change accepted | Commit its fact, revision, result/evidence and relevant fence atomically. Show the confirmed local state; preserve siblings. |
| Definite rejected/no-write | Explain locally and show/refetch the current known state; do not roll back another command. |

| Stale expected revision | Return current conflict state; do not auto-retry old On against a new revision. |
| Fresh Off after uncertain On | Reuse the owner-qualified fence/reconciliation path; older work cannot win afterward. A client serial queue is not the solution. |
| Verification or delivery block | Keep saved intent, proof state and transport restriction distinct; use the existing exact repair/verification journey. No broad-block clearing or automatic test email. |
| Rename/retire/merge/contact change | Follow the exact source identity/adoption policy; do not move a choice by label/email or union permissions. Q11 controls contact changes and prepared-message behavior. |
| Logout/context loss/re-auth | Retire protected state and pending UI replay. Re-read current permission and facts; do not submit an old edit automatically. |

**Q07 post-email Off** establishes the relevant withdrawal fence for matching work before Phase6 dispatch admission. These different semantics are preserved even when the controls are adjacent. Do not label both as stopping every queued email immediately. On affects future qualified decisions, never a backlog or resurrection of work previously withdrawn/closed. Frozen plans cannot gain newly opted-in recipients or retarget another address.

Normal preference-page navigation remains authenticated and read-only. The already-required [RFC8058](https://www.rfc-editor.org/rfc/rfc8058) recipient/list-purpose-bound POST remains a distinct token-authorized withdrawal without a login or extra confirmation. A normal GET/scanner does not mutate, and its narrow token cannot expose the full preference center. No new preference-change email, missionary alert, staff disengagement signal, bell item or Home task is created by this page. Only separately qualified verification/security/source events may send messages.

## Client state and failure isolation

TanStack Query owns the owner-read and mutation/result transport through shared hooks. A scoped read-only DB materialization may serve a genuine catalog; Table/Virtual serve a real long grid where useful. Store/local state can hold expansion/search/interaction state, not a writable authoritative copy of the whole overview. The ratified compatible shared-stack migration remains separate proof. Do not install every library in each small switch merely to satisfy a package checklist.

Query keys and DB materialization lifetimes bind to the actual human, Tenant/assignment/governance and each required recipient/source/contact/issuer/purpose context. One global snapshot key or broad invalidation event is not exact ownership. On context loss cancel requests, retire protected keys/materialization and reject late generations independently of abort success. No module-global private SSR store, persistent raw preferences in localStorage, private labels in URLs, or raw financial/contact realtime subscription.

Current [TanStack mutation](https://tanstack.com/query/latest/docs/framework/react/guides/mutations) and [network-mode](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode) docs distinguish error retry from paused/offline execution and serial mutation queues. **`retry: false` alone does not prevent a mutation from waiting offline and executing on reconnect.** The preference adapter must explicitly avoid queued automatic consent edits, not persist/resume them on hydration and not place protective Off behind unresolved On. Current online checks can fail; server current-authority and revision fences remain decisive. Successful server writes still require result reconciliation even if the component has unmounted.

Each section is independently readable; do not make a financial snapshot or another failing provider a prerequisite for personal preferences. After a mutation, update/revalidate its exact owner state and affected summary. A summary not yet reconciled is marked refreshing rather than retaining a contradictory old All/None claim as current. A Hide save followed by failed feed refresh remains a successful Hide plus a separate read-refresh problem.

## Individual adversarial category review

### C01 — Problem validity, necessity, and alternatives

**Material concern:** Yes. **Evidence/reasoning:** Q07 explicitly deferred the layout. HubSpot supports current named choices; Church Center/LinkedIn support category-first. Existing Settings neither proves a working overview nor makes a new full settings product necessary.

**Effect:** Accept A with a precise one-versus-many rule. **Permanent prevention:** Direct qualified simple choices and certified finite summaries with focused detail.

### C02 — Brittleness

**Material concern:** Yes. **What/why:** labels, missing rows, loaded subsets or one selected donor can become accidental identity/default/summary authority. **Severity:** High. **Likelihood:** Concrete coarse defaults and email/Tenant shortcuts exist in inspected source.

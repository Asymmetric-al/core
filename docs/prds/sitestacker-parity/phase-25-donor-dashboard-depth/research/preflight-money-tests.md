## Recommended confirmation in one sentence

**Use the real donor journey as the primary acceptance seam: browser → protected Core API/owner → actual isolated Postgres/storage → donor-visible result; support it with narrowly targeted real permission/concurrency tests and provider/document qualification at the existing adapter boundaries.** Reuse the existing Playwright, Vitest, psql migration and provider-client seams. Do not create29 unrelated test architectures or rely on a page-only green test to certify money, access or documents.

“One primary seam” does not mean every race, currency/date boundary, denied database grant or provider uncertainty must be driven through a slow browser. Those require a small supporting layer under the same owner contracts. Fast pure tests remain useful for the exact schedule kernel, money/currency/calendar serialization and policy predicates, but their assertions do not replace final donor outcomes.

## Actual database prior art and minimum necessary extension

`scripts/verify/supabase-migrations.mjs` is a reusable **real psql/PostgreSQL** seam. It requires `DATABASE_URL`, rejects non-local hosts by default, bootstraps compatibility schemas and applies sorted forward SQL files with `ON_ERROR_STOP=1` (foundation uses one transaction). This verifies actual migration execution against a disposable target. **It mutates that target**; reading it in this preflight did not run it.

`scripts/sql/supabase-compat-bootstrap.sql` explicitly calls itself a minimal compatibility bootstrap, not a production migration. It creates `anon`/`authenticated`, a `service_role BYPASSRLS`, stub auth tables/functions using request settings, and storage tables. This is useful to execute many SQL structures, but does not instantiate real GoTrue, PostgREST, Storage HTTP authorization or a deployed Supabase JWT lifecycle.

The inspected `.github/workflows/ci-integration.yml` migration job uses `postgres:15-alpine`, applies the migration verifier and seed, and checks a profile count. In contrast, `supabase/config.toml:34` declares `major_version=17`. Migration green on compatibility Postgres15 is not target-version Supabase17 proof and is not a financial/PDP/RLS isolation suite. The subsequent smoke/E2E jobs use placeholder Supabase and `E2E_AUTH_BYPASS=true`; the presence of a Postgres service in the workflow does not make the browser smoke a real financial-data integration.

`tests/integration/supabase/eve-final-launch-verification.sql` is committed prior art for a rollback-isolated **functional SQL assertion**: BEGIN, synthetic fixtures, owner-function calls, explicit `RAISE EXCEPTION` on incorrect durable/audit outcomes, and ROLLBACK. It sets a service-role claim and exercises Eve launch functions, not donor money or ordinary restricted roles. The bounded current search found no equivalent committed Phase25 financial/document direct-role suite and no discovered automatic invocation of this Eve proof in the inspected scripts/workflows. This is a format/harness precedent, not portable donor authorization proof.

**Minimum source-level support under the primary browser seam:** reuse the migration/proof approach on a disposable target matching the supported actual PostgreSQL/Supabase version, then exercise the **real shared public API/owner and actual database** with separate actors/Tenants/Party grants. Add direct database/RPC/storage bypass tests only where they prove an enforcement path that the API cannot cover. Assert actual visible and durable outcomes, not SQL text. Use two genuine concurrent database sessions for remove-versus-bind, accepted command replay, source admission/withdrawal, correction/current-head promotion and source snapshot races. A sequential mock or one transaction with scripted return values cannot prove these races.

P12's sole PDP and coarse Tenant RLS must remain the product architecture; test both layers without duplicating fine-grained capability policy into test-only RLS. Include grants, owner/service-role bypass paths, actual `USING` and effective `WITH CHECK` behavior, composite relationships and immutable scope. Omitted `WITH CHECK` in applicable PostgreSQL policies can inherit `USING`; do not assert a fictitious automatic hole. The necessary database suite is a supporting integration mode for existing owners, not a new production test API, second authorization engine or synthetic replacement schema.

## Suggested minimal acceptance coverage beneath the donor journey

1. **Money and recurring/wallet:** the real API accepts one exact reviewed command and durable result; repeat/late callbacks/transport loss cannot create another effect; Remove versus new binding is serialized; all independent selected groups/legs retain truthful partial outcomes; normal Add/preference/replacement/pause do not create charges. Exact current funds, currencies, dates and accepted source identities drive History/Home.
2. **Document/export bytes:** donor navigates from History or Receipts & statements to the same qualified current artifact/download endpoint; assert real bytes/hash/content disposition, permitted purpose and source-current correction behavior. Revocation/withdrawal, separate record-only grants, range/HEAD requests, Ready/expiry, no read-triggered generation, annual-context CSV scope and QCD/DAF differences require actual owner/storage integration. A PDF success stub or receipt-link regex is insufficient.
3. **Provider qualifications:** keep normal deterministic tests offline with an injected provider boundary. In a separately explicit test-only account/mode/rail profile, qualify the actual hosted fields/native authentication, exact commands, webhook/reconciliation shape and old/in-flight/unknown outcomes. Verify test environment **before** any operation and preserve Core's accepted provider pins. The current opt-in `.stripe-live` files are only limited prior art; their nonempty-key condition and post-create livemode assertion are not the final safe activation guard.
4. **Fast supporting deterministic rules:** exact schedule/calendar kernel, integer money/currency serialization, filter/measure descriptors, document purpose/case admission, clock equality and canonical data projection invariants. Prefer exported owner contracts over internal helpers. Use property/boundary tests where a complete browser fixture would be needlessly expensive, then connect representative cases to the high seam.

No new broad framework is needed. The key additions are an actually source-backed donor acceptance mode and real database/concurrency/storage proof under it, not new libraries or more source-string assertions.

# Variables

Variables are a first-class Statement Studio product surface. They must be robust enough for many PDF families while staying clean and safe for tenant admins.

## Triggers

Use this doc when planning or implementing variable catalogs, source maps, custom fields, variable validation, preview data, resolver contracts, or template bindings.

## Workflow Steps

1. Run Phase 0 source research across CRM, CMS, Supabase, donor, missionary, finance, events, care, reports, tasks, and legal/signing.
2. Define approved context contracts before exposing variables.
3. Create source-map records for built-in variables.
4. Add tenant-level labels, grouping, fallbacks, formatting, sample values, and custom variables.
5. Validate variables before preview, publish, assignment, and production render.
6. Resolve production variables on the server at render time.

## Variable Families

- Tenant/branding: logo, colors, letterhead, address, tax id, signatures.
- Donor/CRM: donor, household, business/church, contact preferences, privacy.
- Giving: gifts, pledges, recurring, refunds, split gifts, in-kind, allocations.
- Funds/projects: fund name, restrictions, project images, goals, progress.
- Missionary: profile, support goal, donor roster, field redaction, updates.
- Finance/bookkeeping: batches, deposits, GL, reconciliation, restricted funds.
- Events: attendee, speaker, ticket, badge, sessions, meals, rooming, waivers.
- Care/support: care plans, activity logs, private/redacted packets.
- Legal/signing: policies, consent, waiver, audit certificate, signature metadata.
- Reports/leadership: KPIs, trends, board packet sections, BI summaries.
- System/audit: timestamps, generated by, template version, retention status.

## Source Map

Each built-in variable needs:

- Key and friendly label.
- Family and type.
- Owning domain.
- Approved resolver/context contract.
- Source tables/collections for engineers.
- Required scope.
- Permission and sensitivity rules.
- Fallback behavior and sample value.
- Readiness state.
- Used-by templates/jobs.
- Version and compatibility notes.

Admins should see labels and settings, not raw SQL, JSON paths, or resolver internals.

## Custom Variables

Tenant admins can create or customize:

- Static tenant text.
- Branded assets.
- Aliases to approved fields.
- Registered custom fields for approved entities.
- Simple no-code derived variables such as concatenate, format date, format currency, conditional fallback, sum, count, and approved filters.

Do not allow raw SQL, arbitrary joins, arbitrary JavaScript, unsafe resolver access, or cross-tenant references.

## Edge Cases

Plan for:

- Many-to-many and polymorphic relationships.
- Household and organization rollups.
- Soft credits and matching gifts.
- Imported legacy IDs.
- Archived or deleted source records.
- Stale cached values.
- Missing media and expired signed image URLs.
- Redacted field locations.
- Minors and consent restrictions.
- Anonymous/private donors.
- Translated labels/content.
- Currency, timezone, and date formatting.
- Corrected or voided records.
- Large table limits.
- Variable deprecation and renamed variables.
- Conflicting source ownership.

## Checklist

- [ ] Variable source maps are documented.
- [ ] Variables are grouped, searchable, and labeled plainly.
- [ ] Sensitivity and readiness are visible.
- [ ] Validation catches missing, unavailable, deprecated, incompatible, or unsafe variables.
- [ ] Published templates use versioned variable keys.
- [ ] Production values resolve server-side from tenant-scoped DTOs.
- [ ] Generated artifacts store snapshot/hash/metadata for auditability.
